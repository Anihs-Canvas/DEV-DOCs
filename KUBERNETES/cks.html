⚠️ CKS Exam Context — Why Chapter 1 Matters

The CKS is a hands-on, performance-based exam (2 hours, ~15–20 CLI tasks). While Chapter 1 isn't directly tested, the security mindset it builds determines how fast you reason through every task. Internalise these four ideas now:

  • Least Privilege is the default answer — whenever a CKS task says "restrict access", you remove permissions rather than add them.
  • Defence in Depth — the exam often tests multiple controls in the same scenario (NetworkPolicy + RBAC + Seccomp). You need all of them.
  • Assume the attacker is already inside — the 4Cs model means even if the cluster boundary is breached, container and code controls must hold.
  • Verify your changes — every task should end with a kubectl or systemctl check to confirm the control is active.

1.1 Why Kubernetes Security Is Different

If you've secured a traditional Linux server before, Kubernetes will feel familiar — and then surprise you. The same operating system concepts (users, files, processes, network ports) exist, but Kubernetes layers on a completely different control model that multiplies both your capabilities and your attack surface.

📖 Key Concept: The Attack Surface

An attack surface is the sum of all entry points through which an attacker can try to compromise a system. In Kubernetes, with thousands of pods, a dynamically changing API, and a shared OS kernel, the attack surface is orders of magnitude larger than a single server.

Traditional IT vs. Kubernetes Security

Here is why the old mental model breaks down:

Traditional IT Security Kubernetes Security
One server = one firewall rule1,000 pods = 1,000 potential targets — all changing dynamically
Static IPs and hostnamesEphemeral pods, rotating IPs — perimeter firewalls don't work
Update OS once a monthImages rebuilt and deployed daily — supply chain matters every time
Users log in via SSHPods authenticate with ServiceAccount tokens — token theft = lateral movement
Audit logs in /var/log/auth.logAudit logs via K8s API policy — not enabled by default!
Firewall blocks at edgeNetworkPolicy inside the cluster — east-west traffic is open by default
App runs as its own Linux userBy default: runs as root 🔴 — you must explicitly prevent this
Secret in /etc/app.confSecret in etcd — unencrypted at rest by default 🔴
🏙️ Analogy: Kubernetes as a City

Think of your Kubernetes cluster as a city. The API server is the city hall — all requests go through it. Worker nodes are city blocks where people (pods) live and work. Without security controls, all the roads (network) are open, everyone runs with a master key (root), and there are no cameras (no audit logs). CKS is the process of installing locks, cameras, gates, and guards — on every street.

The Unique Challenges of Kubernetes Security

🧠 Control Plane — The Mayor's Office
  • API server exposed on the network → primary target for attackers
  • etcd stores all secrets in plaintext by default → must encrypt at rest
  • One weak RBAC rule → attacker reads all secrets in all namespaces
🏘️ Worker Nodes — The City Blocks
  • Pods run as root by default → privilege escalation is trivial
  • Containers share the OS kernel → container escape leads to node compromise
  • Kubelet API exposed → if not hardened, attackers can exec into any pod
🌐 Networking — The City Roads
  • All pods can talk to each other by default → lateral movement is trivial
  • East-west traffic is completely unrestricted without NetworkPolicy
  • Compromised pod → reach the database → read all user data

1.2 The 4Cs of Cloud-Native Security

The Cloud Native Security model organises every security control into four concentric layers: Cloud → Cluster → Container → Code. Each inner layer depends on the outer layer being secure. If an attacker breaks through the cloud layer, no amount of container hardening will save you.

☁️ Cloud (Outermost)
  • IAM policies, VPC security groups, firewall rules
  • Node OS hardening (unused ports, packages, SSH keys)
  • Managed Kubernetes provider security (EKS, GKE, AKS settings)
☸️ Cluster
  • RBAC, ServiceAccount permissions, API server hardening
  • NetworkPolicy (default-deny), Audit logging
  • Admission controllers (OPA, PSS, ImagePolicyWebhook)
📦 Container
  • Image scanning (Trivy), non-root user, read-only filesystem
  • Seccomp profiles, AppArmor, Linux capabilities (drop ALL)
  • Pod Security Standards, resource limits
💻 Code (Innermost)
  • SAST tools (kube-linter, conftest), dependency scanning
  • No secrets in source code, no hardcoded credentials
  • cosign image signing, SBOM, SLSA provenance
⚠️ Key Rule: A Breach in an Outer Layer Compromises All Inner Layers

Security is only as strong as its weakest layer. If the cloud IAM is misconfigured, the attacker has the node. If the node is compromised, container isolation fails. Every layer must be independently secured — this is Defence in Depth.

3.1 How CKS Security Maps to Kubernetes Components

Every Kubernetes component has a distinct security responsibility. Understanding this ownership model is essential — the CKS exam frequently asks you to harden a specific component, and you need to know where each control lives.

🌐 kube-apiserver (port 6443) — The Security Enforcement Hub

  • Authorization: RBAC, Node authorizer, Webhook authorizer
  • Admission Control: OPA, Pod Security Standards, ImagePolicyWebhook
  • Audit Logging: every request logged with who, what, when, result

🗄️ etcd (port 2379) — The Secret Keeper

  • Firewall: only API server may reach port 2379 — never expose externally
⚙️ kubelet (port 10250) — The Node Agent
  • Runs pods on the node — must not accept anonymous requests
  • Hardened by: --anonymous-auth=false, --authorization-mode=Webhook
  • NodeRestriction admission plugin: kubelet can only modify its own node/pods
  • Read-only kubelet API port (10255) should be disabled
📦 Container Runtime (containerd / CRI-O) — The Pod Executor
  • Applies Seccomp profiles: filter allowed syscalls per container
  • Applies AppArmor profiles: restrict file/network/capability access
  • Supports sandboxed runtimes: gVisor (runsc), Kata Containers
  • Enforces runAsNonRoot, readOnlyRootFilesystem from pod spec

  • Authentication failures → 401. Fix: certificates, tokens, OIDC config. (Ch 8)

The Center for Internet Security (CIS) is a non-profit that publishes security configuration guidelines for technology systems. The CIS Kubernetes Benchmark is a document containing over 200 numbered checks — each one a specific configuration setting that makes your cluster more secure.

📖 Key Term: CIS Benchmark

A CIS Benchmark is a consensus-based security best practice document. For Kubernetes, it covers every major component (API server, etcd, kubelet, nodes, policies) and specifies the exact configuration value each should have. The CKS exam is built around these benchmarks.

🔑
200+ Checks

Over 200 numbered security checks across all Kubernetes components. Every CKS hardening task traces back to a specific check number.

🏛️
Industry Standard

Used by Google, AWS, Azure, and every major Kubernetes platform. Passing CIS checks = meeting the industry baseline for cluster security.

🔧
kube-bench Automates

You don't read 200 checks manually. kube-bench runs them automatically on your cluster and tells you exactly what to fix.

📋
Versioned

The benchmark is versioned (e.g. CIS Kubernetes 1.8). Always match the benchmark version to your Kubernetes version for accurate results.

4.4 kubelet Hardening — CIS Node Checks

The kubelet runs on every worker node and manages pod lifecycle. An insecure kubelet allows unauthenticated access to list pods, read node status, and even exec commands. Hardening the kubelet is a CKS Section 4 requirement.

❌ Insecure kubelet (default)
  • authentication.anonymous.enabled: true
  • authentication.webhook.enabled: false
  • authorization.mode: AlwaysAllow
  • readOnlyPort: 10255 (open)
  • Anyone who reaches port 10250/10255 gets data
✅ Hardened kubelet
  • authentication.anonymous.enabled: false
  • authentication.webhook.enabled: true
  • authorization.mode: Webhook
  • readOnlyPort: 0 (closed)
  • All requests must be authenticated + authorized
📝 /var/lib/kubelet/config.yaml — Hardened Configuration 
apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration
authentication:
  anonymous:
    enabled: false           # CIS 4.2.1 — no anonymous requests
  webhook:
    enabled: true            # CIS 4.2.2 — delegate auth to API server
authorization:
  mode: Webhook              # CIS 4.2.3 — use API server for authz
readOnlyPort: 0               # CIS 4.2.4 — disable read-only port
protectKernelDefaults: true   # CIS 4.2.6 — protect kernel tuning
tlsCertFile: /var/lib/kubelet/pki/kubelet.crt
tlsPrivateKeyFile: /var/lib/kubelet/pki/kubelet.key

🔐 Bonus: etcd Hardening — CIS Section 2

etcd stores the entire state of your Kubernetes cluster — every Secret, every config, every pod spec. If an attacker reads etcd, they read everything. If they write to it, they own the cluster. CIS Section 2 focuses exclusively on etcd security.

⚠️ Why etcd Is the Most Critical Component to Protect

etcd is a key-value store — not a database with complex access control. It has no row-level permissions. Anyone with access to etcd's port (2379) can read every Secret in your cluster in plaintext — unless encryption at rest is configured. This is why access to etcd must be locked to the API server only, and why encryption at rest is mandatory.

❌ Insecure etcd
  • No TLS between API server and etcd
  • etcd port 2379 accessible to all pods
  • No client certificate authentication
  • Secrets stored as base64 (readable) in etcd
  • No encryption-at-rest config
✅ Hardened etcd
  • TLS for all etcd traffic (peer + client)
  • NetworkPolicy: only API server can reach port 2379
  • Client cert auth: --client-cert-auth=true
  • Encryption at rest: EncryptionConfiguration with AES-CBC or AES-GCM
  • etcd data directory permissions: 700 (root only)
📝 Enabling Encryption at Rest for Kubernetes Secrets

apiVersion: apiserver.config.k8s.io/v1

5.1 Why the Kubernetes Dashboard Is Dangerous

The Kubernetes Dashboard gives you a web-based visual interface to view pods, deployments, secrets, logs, and — critically — an exec shell into any container. This makes it enormously powerful. It also makes it an extremely attractive target.

Tesla 2018 Crypto-Mining via Dashboard

What happened: Attackers found Tesla's Kubernetes Dashboard exposed on the public internet with no authentication. They logged in, opened an exec shell into a pod, exfiltrated AWS credentials from environment variables, and used Tesla's cloud resources to mine Monero cryptocurrency.

How it started: Dashboard deployed with type: LoadBalancer — no token required, no network controls.

The fix: Authentication required, Dashboard restricted to ClusterIP, access only via kubectl port-forward from a VPN-connected machine.

😰 The anihpj Cluster — Dashboard Left Public (Before Tesla-Proof Fix)
  • 🔴 Dashboard exposed as type: LoadBalancer on port 443 — accessible from any internet browser
  • 🔴 No authentication required — any visitor lands directly on the dashboard home page
  • 🔴 Attacker browses to the cluster's external IP → opens exec terminal into anihpj pod
  • 🔴 Reads environment variables → finds DB_PASSWORD, AWS_SECRET_KEY, DJANGO_SECRET_KEY
  • 🔴 Uses AWS credentials to spin up crypto-mining instances — your cloud bill explodes
🎉 The anihpj Cluster — Dashboard Hardened
  • ✅ Dashboard Service type: ClusterIP — not reachable from outside the cluster at all
  • ✅ Access only via kubectl port-forward from an admin machine behind VPN
  • ✅ Dedicated read-only ServiceAccount with short-lived token (1 hour expiry)
  • ✅ NetworkPolicy denies all ingress to the dashboard namespace from non-admin pods
  • ✅ No attacker can reach the dashboard — it literally doesn't exist on the internet

5.2 Deploying Dashboard Securely

If the Dashboard is needed (e.g., for an internal ops team), deploy it following these principles: ClusterIP only, scoped RBAC, access via port-forward, and a dedicated read-only ServiceAccount.

❌ Insecure — Never Do This

  --type=LoadBalancer \
  --port=443
# Exposes dashboard on public IP
# Anyone on internet can reach it
# Exactly how the Tesla breach started
✅ Secure — The Correct Workflow
  1. Dashboard Service type = ClusterIP (internal only)
  2. kubectl port-forward svc/kubernetes-dashboard 8443:443 -n kubernetes-dashboard
  3. Access at https://localhost:8443 only
  4. Login with a scoped SA token (NOT admin)

6.2 NetworkPolicy Fundamentals

A NetworkPolicy is a Kubernetes resource that works like a firewall rule for pods. It uses label selectors to identify which pods it protects, and specifies which traffic is allowed in (ingress) and out (egress).

📝 NetworkPolicy Anatomy — Every Field Explained (anihpj example) 
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-anihpj-to-postgres
  namespace: anihpj-prod       # NetworkPolicy is namespaced
spec:
  podSelector:                  # Which pods does this policy PROTECT?
    matchLabels:
      app: postgres             # Applies to pods with label app=postgres
  policyTypes:
  - Ingress                    # We are controlling INCOMING traffic to postgres
  ingress:
  - from:                      # Allow traffic FROM:
    - podSelector:
        matchLabels:
          app: anihpj          # Only pods labeled app=anihpj
    ports:
    - protocol: TCP
      port: 5432               # Only on the postgres port
# Result: postgres pod accepts connections from anihpj pod on 5432 ONLY
#         All other incoming traffic to postgres is BLOCKED
⚡
Non-Isolated Pod (No Policy)

A pod with no NetworkPolicy applied accepts traffic from everywhere. This is the Kubernetes default. It is only safe in dev clusters with no sensitive data.

🔒
Isolated Pod (Policy Exists)

The moment any NetworkPolicy selects a pod, that pod is isolated. Only traffic explicitly allowed by matching policies can reach it. Everything else is dropped.

➕
Policies Are Additive

Multiple NetworkPolicies can target the same pod. Their rules are OR'd together — traffic is allowed if any matching policy permits it. They do not conflict.

⚠️
Ingress ≠ Egress

policyTypes: [Ingress] only restricts incoming traffic. Egress (outgoing) remains unrestricted. To control both, declare both in policyTypes.

📖 The Key NetworkPolicy Rules to Memorise

Rule 1: A pod with no NetworkPolicy applied is non-isolated — all traffic allowed.
Rule 2: A pod with any NetworkPolicy applied is isolated — only explicitly allowed traffic passes.
Rule 3: policyTypes: [Ingress] only — egress is still unrestricted for that pod.
Rule 4: policyTypes: [Ingress, Egress] with no rules = deny ALL in + out.
Rule 5: Multiple NetworkPolicies on the same pod are additive — traffic is allowed if ANY policy permits it.

🪤 Bonus: The 5 Most Common NetworkPolicy Mistakes (and How to Avoid Them)

🔴
Mistake 1: Forgetting DNS Egress

You apply a default-deny-all-egress policy. Suddenly pods can't resolve service names. DNS runs on port 53/UDP. Always add a DNS allow-egress policy whenever you deny egress — or everything breaks silently.

🔴
Mistake 2: The OR vs AND Selector Trap

Two selectors in the same from list item = AND (both must match). Two separate from list items = OR (either can match). This is the most common NetworkPolicy bug on the CKS exam.

🟠
Mistake 3: Wrong Namespace for the Policy

NetworkPolicy is namespaced. A policy in anihpj-prod only affects pods in anihpj-prod. Creating it in the default namespace does nothing to your production pods.

🟠
Mistake 4: Protecting the Wrong Pod

The podSelector at the top-level of spec selects which pods the policy protects (applies to). The podSelector inside from selects which pods are allowed to connect. These are two different selectors with opposite meanings.

🟡
Mistake 5: Testing with the Wrong Pod Label

You create a test pod to verify your policy blocks traffic — but you accidentally give the test pod the label app: anihpj, which makes your policy allow its traffic. Always test with a pod that has NO matching labels.

🔍 The OR vs AND Selector Trap — Illustrated

📝 AND vs OR in NetworkPolicy from: rules 
# ❌ COMMON MISTAKE — this is AND logic:
# Only allows pods that BOTH have app=anihpj label AND are in monitoring namespace
  ingress:
  - from:
    - namespaceSelector:       # ← same list item (dash)
        matchLabels:
          kubernetes.io/metadata.name: monitoring
      podSelector:             # ← same list item (no dash) = AND
        matchLabels:
          app: prometheus

# ✅ CORRECT — this is OR logic:
# Allows pods with app=anihpj (any namespace) OR pods in monitoring namespace
  ingress:
  - from:
    - namespaceSelector:       # ← first list item (dash)
        matchLabels:
          kubernetes.io/metadata.name: monitoring
    - podSelector:             # ← second list item (another dash) = OR
        matchLabels:
          app: anihpj

💡 The Mental Model for NetworkPolicy Selectors

Think of each - (dash) in the from: list as an OR gate. Traffic is allowed if it matches any of the listed items.

Within a single item (same dash, no new dash), multiple selector fields form an AND gate. The traffic source must match all fields within that item.

So: namespaceSelector + podSelector under the same dash = "pods matching podSelector AND residing in namespaces matching namespaceSelector". Two separate dashes = either of those conditions alone is sufficient.

7.2 TLS Certificates in Kubernetes

Kubernetes stores TLS certificates as Secrets of type kubernetes.io/tls. The Secret contains two keys: tls.crt (the certificate) and tls.key (the private key). The Ingress controller reads this Secret and presents the certificate to users connecting via HTTPS.

7.3 cert-manager — Automated Certificate Management

Managing TLS certificates manually is tedious and error-prone. cert-manager is a Kubernetes add-on that automates the entire certificate lifecycle: requesting, issuing, storing, and renewing certificates — entirely hands-free.

🔐
ClusterIssuer

A cluster-wide CA or ACME server configuration. Used with Let's Encrypt. One ClusterIssuer can serve all namespaces.

📜
Certificate

A cert-manager resource that describes the cert you want. cert-manager creates the Secret automatically when you create this resource.

🔄
Auto-Renewal

cert-manager monitors expiry and renews 30 days before. Let's Encrypt certs expire every 90 days — renewal is fully automatic.

✅
ACME Challenges

HTTP-01 (uses a temporary URL on your domain) or DNS-01 (adds a DNS TXT record). HTTP-01 is simpler; DNS-01 works for wildcard certs.

7.4 Enforcing HTTPS — Redirects, HSTS & Security Headers

Having a TLS certificate is only step one. You also need to ensure that users who accidentally navigate to http://anihpj.com are redirected to https://anihpj.com, and that browsers remember to always use HTTPS for your domain (HSTS).

📝 Ingress YAML with Full Security Annotations 
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: anihpj-secure-ingress
  namespace: anihpj-prod
  annotations:
    cert-manager.io/cluster-issuer: "letsencrypt-prod"

    # Force HTTP → HTTPS redirect (301)
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
    nginx.ingress.kubernetes.io/force-ssl-redirect: "true"

    # Only allow TLS 1.2 and 1.3 (no old insecure versions)
    nginx.ingress.kubernetes.io/ssl-protocols: "TLSv1.2 TLSv1.3"

    # Rate limiting — 10 requests per second per IP
    nginx.ingress.kubernetes.io/limit-rps: "10"

    # Add security response headers
    nginx.ingress.kubernetes.io/configuration-snippet: |
      add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
      add_header X-Frame-Options "DENY" always;
      add_header X-Content-Type-Options "nosniff" always;
      add_header X-XSS-Protection "1; mode=block" always;
      add_header Referrer-Policy "strict-origin-when-cross-origin" always;
spec:
  ingressClassName: nginx
  tls:
  - hosts: [anihpj.com, www.anihpj.com]

  - host: anihpj.com

💡 What HSTS Does — and Why It Matters

HTTP Strict Transport Security (HSTS) is a response header that tells the browser: "For the next year, always connect to anihpj.com using HTTPS — even if the user types 'http://'."

Once a browser receives the HSTS header, it will automatically redirect HTTP to HTTPS locally — before even sending a request to the server. This closes the window for SSL-stripping attacks where an attacker on the network intercepts the initial HTTP request before the server can redirect it.

Key detail: includeSubDomains applies HSTS to all subdomains (api.anihpj.com, admin.anihpj.com, etc.). Only add this if all your subdomains support HTTPS.

💡 Always Use Staging First — Let's Encrypt Rate Limits Are Real

Let's Encrypt enforces a limit of 5 duplicate certificates per week per domain. If you're testing cert-manager and keep recreating Certificate resources, you will hit this limit and be locked out for up to a week.

Best practice: Create a letsencrypt-staging ClusterIssuer (uses Let's Encrypt's test endpoint with no rate limits) and test your entire flow with it. Only switch to letsencrypt-prod once staging succeeds.

📖 TLS vs mTLS — The Key Difference

Standard TLS: only the server presents a certificate. The client (your browser) trusts the server's cert, but the server doesn't verify who the client is. This is what we've configured in Chapter 7.

Mutual TLS (mTLS): both sides present certificates. The server verifies the client's cert, and the client verifies the server's cert. This creates cryptographically verified two-way authentication — even if a request comes from inside the cluster.

mTLS is covered in depth in Chapter 22 where we implement it with a service mesh (Istio / Linkerd). It forms the backbone of zero-trust service-to-service communication — every service proves its identity on every request.

8.2 Disabling Anonymous Authentication

By default, unauthenticated requests are assigned the identity system:anonymous in the system:unauthenticated group. The anonymous user has very limited access, but misconfigured clusters have been found granting it dangerous permissions. The correct posture: disable anonymous auth so every request must carry a valid credential.

❌ Anonymous Auth Enabled (Default)
  • Unauthenticated request → gets identity system:anonymous
  • Any RBAC binding for system:unauthenticated = public access
  • API server responds with 200/403, revealing its existence
  • Certain info endpoints leaked without auth (e.g. /version)
✅ Anonymous Auth Disabled
  • Unauthenticated request → immediate 401 Unauthorized
  • All requests must carry a valid certificate, token, or OIDC JWT
  • No information leakage to unauthenticated callers
  • CIS Benchmark 1.2.1: PASS

💡 Why OIDC Is Better Than Static Certificate Auth for Teams

9.2 RBAC Misconfigurations — The Top Security Risks

Most Kubernetes breaches that involve RBAC are caused by one of five patterns. Learn to recognise them in YAML and know the fix instantly.

🔴
Wildcard Verbs (verbs: ["*"])

Grants every verb (get, list, create, delete, update, patch, exec, escalate) on the matched resources. Functionally equivalent to cluster-admin for those resources. Fix: enumerate exact verbs: ["get","list","watch"]

🔴
Wildcard Resources (resources: ["*"])

Grants access to every resource in the API group — including secrets, pods/exec, serviceaccounts. Fix: list explicit resources: ["pods","services"]

🟠
Wildcard API Groups (apiGroups: ["*"])

Grants access across all API groups — core, apps, rbac, extensions. Fix: specify groups explicitly: ["","apps"]

🟠
escalate / bind / impersonate Verbs

These verbs allow privilege escalation. escalate: create roles with more permissions than you have. bind: bind any role. impersonate: act as any user. Fix: never grant these to non-admin subjects.

🟡
Secrets Read Access

Any subject with get on secrets can read every Secret in the namespace — DB passwords, TLS certs, API keys. Fix: grant Secrets access only to subjects that strictly need it.

📝 Dangerous vs Secure RBAC — Side by Side 
# ❌ DANGEROUS — this is equivalent to cluster-admin for the namespace
rules:
- apiGroups: ["*"]        # ← ALL API groups
  resources: ["*"]        # ← ALL resources including secrets
  verbs: ["*"]             # ← ALL verbs including exec, escalate

# ✅ SECURE — developer can view and create pods, read logs only
rules:
- apiGroups: [""]         # core API group only
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch", "create"]

💡 Bonus: The RoleBinding + ClusterRole Trick

💡 One ClusterRole, Scoped to a Single Namespace via RoleBinding

Here's a powerful RBAC pattern you must know for the CKS exam and real clusters:

ClusterRoleBinding → ClusterRole = permissions apply cluster-wide

RoleBinding → ClusterRole = permissions apply only in the namespace the RoleBinding lives in

This means you can create one reusable ClusterRole (e.g. pod-reader) and then bind it in multiple namespaces individually with separate RoleBindings — each scoped to its own namespace. You don't need to create a separate Role per namespace. This is the correct pattern for the built-in view, edit, and admin ClusterRoles.

📝 ClusterRole bound to one namespace via RoleBinding 
# ClusterRole defined once (cluster-wide)

metadata:
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list", "watch"]
---
# Bind it in anihpj-dev (scoped to that namespace only)
kind: RoleBinding              # ← RoleBinding, NOT ClusterRoleBinding
metadata:
  name: alice-pod-reader
  namespace: anihpj-dev       # ← only works in this namespace

- kind: User
  name: alice
roleRef:
  kind: ClusterRole            # ← references a ClusterRole
  name: pod-reader

💡 RBAC Least-Privilege Design Process — 4 Questions to Ask for Every Subject

ServiceAccount Token Mounting — Know Both Controls

The CKS exam tests two ways to disable automatic token mounting:

  • On the ServiceAccount: automountServiceAccountToken: false — affects all pods using this SA
  • On the Pod spec: automountServiceAccountToken: false — overrides SA setting for this pod
  • Pod-level setting overrides the SA-level setting. If the SA says false but the pod says true, the token IS mounted.
  • Best practice: set both to false, then explicitly opt-in only the pods that need API access

10.1 How Pods Authenticate to the Kubernetes API

When a pod starts, kubelet automatically mounts a ServiceAccount token into it. Any code running inside the container can read this token and use it to call the Kubernetes API. The API server validates the token, then applies RBAC to decide what the pod can do.

ServiceAccount Token Flow — Pod → API Server
  1. Pod starts → kubelet creates projected volume with token
     Mount path: /var/run/secrets/kubernetes.io/serviceaccount/
     Files:  token   (JWT signed by K8s)
             ca.crt  (cluster CA certificate)
             namespace (the pod's namespace)

  2. Code inside pod reads the token:
     $ cat /var/run/secrets/kubernetes.io/serviceaccount/token
     → eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9...

  3. Code calls the K8s API with the token:
     $ curl https://kubernetes.default.svc/api/v1/pods \
         -H "Authorization: Bearer $(cat /var/run/.../token)"
         --cacert /var/run/.../ca.crt

  4. API server validates token → RBAC check → responds

  IF automountServiceAccountToken: false:
     Step 1 never happens → /var/run/secrets/ is EMPTY
     → Pod CANNOT call the K8s API at all ✅
     → This is what you want for most application pods

10.2 The Dangers of the Default ServiceAccount

❌ Default SA — Shared Identity Risk
  • All pods in namespace share default SA
  • Grant any permission to default SA → ALL pods get it
  • Token auto-mounted even for pods that don't use it
  • Compromised app pod has API access (unnecessary)
  • One exploited pod = API access for all pods
✅ Dedicated SAs — Isolated Identity
  • anihpj-sa → no API access, no token mount
  • postgres-sa → no API access, no token mount

🔍 Bonus: What's Actually Inside the ServiceAccount Token Mount

When a pod has a ServiceAccount token mounted, three files appear at /var/run/secrets/kubernetes.io/serviceaccount/. Understanding what each file contains helps you understand the entire pod-to-API authentication flow.

🎫
token

A signed JWT (JSON Web Token). Contains: the ServiceAccount name, namespace, expiry time, and audience. The API server validates the JWT signature to prove it was issued by Kubernetes. This is what goes in the Authorization: Bearer <token> header.

🔐
ca.crt

The cluster's Certificate Authority certificate. The pod uses this to verify it's talking to the real API server — not an impersonator. Without it, the pod cannot establish a trusted TLS connection to kubernetes.default.svc.

📍
namespace

A plain text file containing the pod's namespace name (e.g. anihpj-prod). Applications use this to know which namespace they're running in without needing to read it from environment variables.

🚫
When automountServiceAccountToken: false

None of these files exist in the pod. The /var/run/secrets/ directory is empty or absent. The pod cannot make any authenticated API calls — which is exactly what you want for most application pods.

💡 Why Token Expiry Matters — A Thought Experiment

Imagine a pod in the anihpj cluster writes its ServiceAccount token to a log file by mistake (a common developer error). That log file gets shipped to a centralised log aggregator. An attacker who gains read access to the log aggregator now has a Kubernetes API token.

With old static tokens: The attacker can use that token forever. The only way to invalidate it is to delete the Secret in Kubernetes — which requires you to know the breach happened.

With new bound tokens (1-hour expiry): By the time the attacker finds the token in the logs, it's already expired. The window of exposure is reduced from "forever" to "at most 1 hour".

This is why you should always use bound projected tokens in Kubernetes 1.22+, and why the old static token approach is being deprecated.

11.3 Protecting Node-Level Access

Even with a hardened API server, an attacker who gets SSH access to a node can bypass Kubernetes entirely — running containers directly, reading secrets from the filesystem, or modifying kubelet config.

🔑
SSH Key Hygiene

Rotate SSH keys regularly. Remove stale keys from ~/.ssh/authorized_keys. Use SSO (Teleport, Boundary) so you don't need to distribute SSH keys at all.

🚫
Disable Root SSH Login

Set PermitRootLogin no in /etc/ssh/sshd_config. Attackers who gain SSH as root have full node access — including modifying kubelet.

🌐
Firewall Port 10250

The kubelet API on port 10250 must not be reachable from outside the cluster. Firewall rule: allow only from control plane and other nodes.

📋
Audit Node Access

Log all SSH logins (auditd or cloud trail). Alert on SSH to production nodes outside business hours. Review /var/log/auth.log regularly.

Kubernetes supports only the current version and 2 prior minor versions. Once your version falls to N-3, there are no more patches — including for critical CVEs. Running an unsupported version = running known, publicly disclosed vulnerabilities.

Current support (as of 2026): v1.32 ✅, v1.31 ✅, v1.30 ✅ — v1.29 and below: ❌ EOL

🧭 Bonus: The 5 Node Hardening Principles — A Mental Framework

1
Minimum Viable Surface

Install only what Kubernetes requires. Every extra package, service, or binary is a potential entry point. Start from a minimal OS image (Ubuntu Minimal, Amazon Linux Minimal) and add only what's explicitly needed.

2
Deny by Default

For ports: default deny all incoming; explicitly allow only required ports. For users: default deny root login; explicitly allow named admin accounts. The burden of proof is on "why this should be open", not "why this should be closed".

3
Identity Is Not Shared

No shared admin account. No shared SSH keys. Every person and every process gets a unique identity. When Bob leaves, you revoke Bob's identity — not every admin's. When a pod is compromised, you revoke that pod's SA — not all pods'.

4
Immutability Over Patching

Ideally, production nodes are immutable: never SSH'd into, never manually modified after provisioning. Node changes go through infrastructure-as-code (Terraform, Ansible). This prevents configuration drift and ensures every node matches a known-good state.

5
Assume Escape, Limit Blast Radius

Design as if containers will escape. Assume a container breaks out and the attacker lands on the node. The hardening work in this chapter is designed to make that moment as unproductive for the attacker as possible: no cron jobs to abuse, no open services to pivot through, no root access.

14.1 What Is AppArmor?

💡 Key Term: Linux Security Module (LSM)

A Linux Security Module (LSM) is a framework in the Linux kernel that allows additional security checks to be inserted into kernel operations. AppArmor, SELinux, and Seccomp all work as LSMs. When enabled, an LSM hooks into system calls and other kernel operations to apply policy decisions before the operation completes — not at the application layer, but inside the kernel itself. This makes them very difficult for a compromised application to bypass.

AppArmor (Application Armor) is a Linux Security Module built into the Ubuntu/Debian kernel. Unlike traditional file permissions (which control who accesses a file), AppArmor controls what a specific program can do — regardless of which user runs it.

❌ anihpj Container WITHOUT AppArmor
  • Django process can read /etc/shadow (if running as root)
  • Can write to /proc/ kernel interfaces
  • Can open raw network sockets (craft packets)
  • Can access /dev/ devices
  • Can execute arbitrary binaries in /bin/
  • Container escape = full node access
✅ anihpj Container WITH AppArmor Profile
  • Can ONLY read files under /app/ (its own code)
  • Can ONLY write to /tmp/ and /app/media/
  • Can ONLY connect TCP to postgres:5432 and redis:6379
  • All other file, network, and capability operations → DENIED + logged
  • Even if container is fully compromised: attacker is locked in a tiny cage
💡 AppArmor vs Linux File Permissions

File permissions (chmod/chown) say: "user alice can read this file." They're tied to user identity. AppArmor says: "the program /usr/bin/python3 can only access these files." The program is the subject, not the user. This means a compromised web app can be locked down even if it runs as root — the kernel enforces the profile regardless of the process's UID.

14.2 AppArmor Modes

🔴
Disabled

No AppArmor profile loaded for this process. The process runs without any AppArmor restrictions — same as not having AppArmor at all. This is the default for most processes.

🟡
Complain (Audit Mode)

The profile is loaded but violations are only logged — not blocked. Use this during development to discover what resources your app actually needs. Check logs with: journalctl -k | grep apparmor.

Violations are blocked AND logged. This is the mode you use in production. The process cannot perform any action not explicitly allowed by the profile. Use aa-enforce to switch a profile to enforce mode.

14.3 Writing AppArmor Profiles for anihpj

💡 Key Term: AppArmor Profile

An AppArmor profile is a plain-text file stored in /etc/apparmor.d/ that defines the security policy for a specific executable. The profile name typically matches the binary path (e.g., a profile for /usr/bin/python3) or a descriptive name. Each rule in the profile specifies a path pattern and permissions (r=read, w=write, x=execute, k=lock). Anything not explicitly allowed is denied when the profile is in enforce mode.

A profile defines exactly what the anihpj process is allowed to do. It lists paths (with permissions), network access, and capabilities. Everything not listed is denied by default when the profile is in enforce mode.

📝 AppArmor profile for anihpj Django container (/etc/apparmor.d/anihpj-django) 
# AppArmor profile for the anihpj Django/Gunicorn process
#include <tunables/global>

profile anihpj-django flags=(attach_disconnected) {
    #include <abstractions/base>
    #include <abstractions/python>       # Python stdlib paths

    # Allow reading application code (read-only)
    /app/** r,

    # Allow writing to uploads and temp directories
    /app/media/** rw,
    /tmp/** rw,

    # Allow outbound TCP connections (to postgres and redis)
    network tcp,

    # Allow reading system config (needed by Python)
    /etc/ld.so.cache r,
    /etc/localtime r,
    /etc/ssl/certs/** r,

    # Deny sensitive files explicitly
    deny /etc/shadow r,
    deny /proc/** rw,
    deny /sys/** rw,
    deny /root/** rw,
}

💡 Profile Abstractions — Reusable Building Blocks

AppArmor abstractions are pre-written include files that grant common permissions. Instead of manually listing every Python library path, #include <abstractions/python> covers them all. Common ones to know:

  • abstractions/base — minimal permissions needed by any process
  • abstractions/python — Python interpreter and standard library paths
  • abstractions/nameservice — DNS resolution (needed for most networked apps)
  • abstractions/ssl_certs — read access to TLS certificate stores

14.4 Applying AppArmor in Kubernetes

⚠️ Profile Must Be Loaded on the Node — Not Just in the Pod Spec

A very common mistake: the pod annotation or securityContext.appArmorProfile is correct, but the profile was never loaded on the node with apparmor_parser. The pod will fail to start with an error like "container failed to run: AppArmor profile not found". Always verify with ssh <node> "aa-status | grep <profile-name>" before applying the pod spec. In a multi-node cluster, every node where the pod might land must have the profile loaded.

The AppArmor profile must be loaded on every node where the pod can be scheduled. Then you reference the profile in the pod spec using one of two methods.

🔴 Bonus: Why AppArmor Matters — The runc Container Escape (CVE-2019-5736)

CVE-2019-5736 2019 CVSS 8.6 — runc Container Escape

What it did: An attacker with the ability to execute code inside a container (e.g., via a web shell in a Django app like anihpj) could overwrite the host's runc binary — the container runtime. When the container was restarted or a new container was created on the same node, the malicious runc executed with root privileges on the host OS, giving the attacker full node-level control.

Affected systems: All Docker versions before 18.09.2 and runc versions before 1.0-rc6 — meaning virtually every Kubernetes cluster in production at the time.

How AppArmor mitigates it: An AppArmor profile for the container that denies writes to /usr/bin/runc and /proc/self/exe would have blocked the exploit. The attacker inside the container could not overwrite the binary the profile restricted. This is why AppArmor profiles should explicitly deny writes to system binary paths.

⚠️ The CKS Exam Trap: Complain Mode vs Enforce Mode

One of the most common mistakes on the CKS exam is loading a profile in complain mode instead of enforce mode. The pod will start, the annotation will be correct, and you might think the task is done — but the profile is not blocking anything.

How to avoid it:

  • After loading a profile with apparmor_parser -q, always run: aa-status | grep <profile-name>
  • Confirm the output shows (enforce) — NOT (complain)
  • If it shows (complain), switch it: aa-enforce /etc/apparmor.d/<profile>
  • Then re-verify: aa-status | grep <profile-name>

Also verify from inside the running pod: kubectl exec -it <pod> -- cat /proc/1/attr/current — should show profile-name (enforce).

15.1 What Is Seccomp?

💡 Key Term: System Call (syscall)

A system call (syscall) is the interface between a userspace program and the Linux kernel. When your Django app reads a file, it doesn't read it directly — it calls the read() syscall, which asks the kernel to do it on its behalf. Every OS-level operation (file I/O, network, memory, process management) goes through a syscall. Seccomp works by placing a filter on this interface — intercepting every syscall before the kernel executes it and deciding whether to allow or deny it based on the profile.

Seccomp (Secure Computing Mode) is a Linux kernel feature. When enabled for a process, the kernel intercepts every syscall the process makes and checks it against the filter. If the syscall isn't allowed — the kernel kills the process (SIGKILL) or returns an error. No exceptions.

The Linux kernel has over 300+ syscalls. A typical Django web application uses approximately 40–60 for normal operation (file reads, socket connections, memory allocation, etc.). 16.2 Cloud IAM for Kubernetes Nodes

💡 Key Term: Instance Metadata Service (IMDS)

The Instance Metadata Service (IMDS) is a local HTTP endpoint available on every cloud VM (AWS: http://169.254.169.254, GCP: http://metadata.google.internal, Azure: http://169.254.169.254). Any process on the VM can query it to retrieve the VM's cloud identity credentials. On Kubernetes, this means any pod on a node can potentially reach IMDS and steal the node's cloud IAM credentials — unless you explicitly block this access or use IMDSv2 with a hop limit of 1 (which prevents requests from within containers).

When running on AWS/GCP/Azure, each Kubernetes node has a cloud identity (EC2 instance profile, GCP Service Account, Azure Managed Identity). If that identity has broad permissions, a compromised node = a compromised cloud account.

💡 The IMDS Attack — Why Node IAM Matters

The Instance Metadata Service (IMDS) is a local HTTP endpoint that cloud nodes can call to get their credentials: http://169.254.169.254/latest/meta-data/iam/security-credentials/ (AWS). If an attacker compromises a pod and the pod can reach IMDS, they inherit the node's cloud IAM permissions. If the node has AdministratorAccess, the attacker now has full AWS access — they can create IAM users, exfiltrate S3 data, and spin up resources. This is how the Capital One breach (2019) occurred.

Defence: Minimal node IAM + block IMDS access from pods using NetworkPolicy or IMDSv2 (hop limit = 1) on AWS.

16.3 etcd Security — Hardening the Cluster Brain

💡 Key Term: etcd

etcd is a distributed key-value store that serves as Kubernetes' persistent data store. Every object in the cluster — pods, deployments, services, secrets, configmaps — is ultimately stored as a JSON/protobuf value in etcd. The key format follows the pattern /registry/<resource>/<namespace>/<name>. When you run kubectl get pod anihpj, the API server reads from etcd. When you run kubectl apply, the API server writes to etcd. The cluster literally cannot function without etcd — and anyone with direct etcd access has the keys to the kingdom.

etcd stores all Kubernetes state: every pod spec, every service, every ConfigMap, and every Secret. If Secrets encryption at rest is not enabled (covered in Chapter 19), etcd contains your database passwords, API keys, and TLS certificates in plaintext. Direct access to etcd bypasses all Kubernetes RBAC.

❌ Insecure etcd Configuration
  • etcd port 2379 accessible from all worker nodes
  • No TLS between API server and etcd
  • No client certificate authentication required
  • etcd directory world-readable
  • Attacker reads: etcdctl get /registry/secrets/anihpj-prod/db-password
  • Plaintext database credentials exposed instantly
✅ Hardened etcd Configuration
  • etcd port 2379 firewalled: only API server IP allowed
  • TLS for all etcd communications
  • Client certificates required (mutual TLS)
  • etcd data directory: chmod 700 /var/lib/etcd
  • Secrets encryption at rest (EncryptionConfig) — covered in Ch 19
  • Regular snapshots: etcdctl snapshot save
🔒 etcd TLS flags and firewall — hardening the anihpj control plane 
# etcd TLS flags (in /etc/kubernetes/manifests/etcd.yaml)
# These should already be set by kubeadm — verify they are present:
    - --cert-file=/etc/kubernetes/pki/etcd/server.crt
    - --key-file=/etc/kubernetes/pki/etcd/server.key
    - --trusted-ca-file=/etc/kubernetes/pki/etcd/ca.crt
    - --client-cert-auth=true       # Require client certs
    - --listen-client-urls=https://127.0.0.1:2379  # Only local + specific IPs
    - --peer-client-cert-auth=true  # Mutual TLS between etcd peers

# Firewall: restrict etcd port 2379 to ONLY the API server IP
# (assuming API server is on 10.0.0.10 on the control plane)
iptables -A INPUT -p tcp --dport 2379 -s 127.0.0.1 -j ACCEPT
iptables -A INPUT -p tcp --dport 2379 -j DROP   # deny all others

# Restrict etcd data directory permissions
chmod 700 /var/lib/etcd

# Verify etcd is NOT exposed to all interfaces
ss -tlnp | grep 2379
# Should show only: 127.0.0.1:2379  (not 0.0.0.0:2379)
⚠️ etcd Direct Access Bypasses All Kubernetes RBAC

RBAC, admission controllers, and audit logging all exist at the API server level. They protect the Kubernetes API. But if an attacker has direct etcd access (e.g., port 2379 is exposed and unauthenticated), they bypass every single Kubernetes security control. They can read and write cluster state directly — adding admin users, reading all Secrets, or corrupting the entire cluster state. etcd must be treated as the most sensitive component in the cluster.

17.1 What Are Pod Security Standards?

💡 Key Term: Pod Security Standards (PSS)

Pod Security Standards is a built-in Kubernetes admission controller (PodSecurity) that evaluates pods against a named security profile before allowing them to be created or updated. Unlike RBAC (which controls who can do what), PSS controls what a pod is allowed to look like — preventing dangerous configurations like privileged containers, host networking, and running as root from ever reaching the scheduler.

🔓
Privileged

No restrictions. Full host access allowed. For cluster infrastructure pods only: CNI plugins (calico), node monitoring daemons (node-exporter). Never for user workloads like anihpj.

🔶
Baseline

Prevents known privilege escalation. Disables: hostNetwork, hostPID, hostIPC, privileged containers. Allows: running as any user, most capabilities. Good for dev environments.

🔒
Restricted

Maximum security. Requires: runAsNonRoot: true, seccompProfile: RuntimeDefault, drop: [ALL] capabilities. Disables host namespaces, privileged mode. Use for all production workloads including anihpj.

📊
Three Enforcement Modes

enforce — pod rejected if it violates the profile. audit — pod allowed but violation logged to the audit log. warn — pod allowed, user gets a warning message. Mix them to migrate gradually.

18.2 Running as Non-Root

By default, a Docker container runs as root (UID 0) unless the Dockerfile has a USER instruction. Root inside a container has the same capabilities as root on the host if the container escapes. This is the most impactful single security change you can make.

❌ Default: anihpj Running as Root
  • Container runs as UID 0
  • Can read /etc/shadow, /root/
  • Can overwrite system binaries
  • Container escape → attacker has root on node
  • Can install persistence mechanisms
  • PSS Restricted level rejects this pod
✅ Hardened: anihpj Running as UID 1000
  • Container runs as UID 1000 (non-privileged user)
  • Cannot read root-owned files
  • Cannot modify system binaries
  • Container escape → attacker is UID 1000 on node (very limited)
  • Cannot install rootkits without privilege escalation
  • PSS Restricted level accepts this pod
📝 Pod spec + matching Dockerfile USER instruction 
# In Dockerfile — create non-root user for anihpj
FROM python:3.11-slim
RUN groupadd -r anihpj && useradd -r -g anihpj -u 1000 anihpj
WORKDIR /app
COPY --chown=anihpj:anihpj . .
USER 1000   # switch to non-root user
CMD ["gunicorn", "anihpj.wsgi:application", "--bind", "0.0.0.0:8000"]

# In pod spec — enforce at Kubernetes level too
spec:
  securityContext:
    runAsNonRoot: true     # Kubernetes rejects pod if UID = 0
    runAsUser: 1000         # Override to UID 1000 (matches Dockerfile)
    runAsGroup: 1000        # Primary group GID 1000
    fsGroup: 2000           # Volume ownership: chown to GID 2000

18.3 Linux Capabilities — Drop ALL

💡 What Are Linux Capabilities?

Traditional Linux has two privilege levels: root (can do everything) and non-root (restricted). Linux capabilities break root's power into ~40 granular privileges. A process can have some capabilities without being full root. Containers by default get ~14 capabilities — far more than a web application needs. The CKS best practice: drop: ["ALL"] to remove every capability, then explicitly add back only the specific ones your app requires (usually none for a Django app).

  • SYS_PTRACE — debuggers and profilers (never in production)

For 99% of web application containers (including anihpj), the correct answer is: drop: ["ALL"] and add: [] (empty).

18.4 Privilege Escalation Flag

Even a non-root container can escalate privileges if it runs a setuid binary (a program that temporarily elevates to root). The allowPrivilegeEscalation flag prevents this at the kernel level.

⚠️ Always Set allowPrivilegeEscalation: false

If allowPrivilegeEscalation is not set, a non-root container can still escalate to root using a setuid binary (e.g., sudo, su, or a vulnerable SUID program in the image). Setting it to false makes the kernel refuse any such escalation attempt. The PSS Restricted level requires this field to be explicitly set to false. There is no valid reason for a web application container to need privilege escalation.

📝 Prevent privilege escalation for anihpj 
containers:
- name: anihpj
  securityContext:
    allowPrivilegeEscalation: false   # blocks setuid binary escalation
    runAsNonRoot: true
    runAsUser: 1000

18.5 Read-Only Root Filesystem

A read-only root filesystem means the container's own filesystem is immutable — the running process cannot write to it. This is a powerful defence: even if an attacker executes code inside the container, they cannot install backdoors, modify binaries, or write persistence files.

🎯 What Needs to Be Writable in anihpj?
  • 📁 /app/media/ — user file uploads (job application attachments)
  • 📁 /tmp/ — Django temp files during request processing
  • 📁 /app/staticfiles/ — only during collectstatic (init container)
  • 📁 /var/log/ — optional (prefer stdout logging in Kubernetes)
  • 🔒 Everything else: read-only

19.1 Secrets in etcd Are Plaintext

⚠️ base64 Is Not Encryption — It's Just Encoding

When you create a Kubernetes Secret, the values are base64-encoded — not encrypted. Base64 can be decoded instantly: echo "cGFzc3dvcmQ=" | base64 -d → password. The CKS exam specifically tests that you understand this distinction and can enable real encryption.

💡 The Provider Order Matters

The first provider in the list is used for encrypting new writes. All providers in the list are tried for decrypting existing reads. Once all secrets are re-encrypted, remove identity entirely — at that point, unencrypted secrets will no longer be readable, which is exactly what you want.

💡 Key Concept: Dynamic Secrets

Dynamic secrets are generated on-demand by Vault. Instead of storing a static database password, Vault connects to your PostgreSQL server and creates a new unique credential for each requesting service, with a short TTL (e.g., 1 hour). This is one of Vault's most powerful features for database-backed applications like anihpj.

20.3 External Secrets Operator (ESO)

The External Secrets Operator is a Kubernetes controller that syncs secrets from external providers (Vault, AWS Secrets Manager, GCP Secret Manager) into Kubernetes Secrets. Pods still consume standard Kubernetes Secrets — the operator handles the synchronization transparently.

💡 ESO vs Vault Agent Sidecar — Which to Use?

External Secrets Operator: Creates a standard Kubernetes Secret. Pod doesn't know secrets came from AWS/Vault. Simpler to operate. Secret is stored in etcd (use with encryption at rest). Best for teams already using the K8s Secret API.

Vault Agent Sidecar: Injects secrets directly into the pod's filesystem or environment — they never touch etcd. Maximum security. More complex to configure. Best for high-security environments or when you need dynamic/rotating credentials.

22.2 Mutual TLS (mTLS) — How It Works

💡 Regular TLS vs Mutual TLS

Regular TLS (one-way): Only the server presents a certificate. The client verifies the server is legitimate (like HTTPS to a website). The server doesn't verify who the client is. Mutual TLS (mTLS): Both the server and the client present certificates. The server also verifies the client's identity. This ensures that only authorised services can connect to each other — not just "any pod" on the cluster network.

kubectl label namespace anihpj-prod istio-injection=enabled

# Step 2: Enforce STRICT mTLS — reject all non-mTLS traffic
apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication
metadata:
  name: anihpj-mtls
  namespace: anihpj-prod
spec:
  mtls:
    mode: STRICT   # PERMISSIVE: accept both; STRICT: reject non-mTLS

# Step 3: Optionally define AuthorizationPolicy
# Only allow anihpj to call postgres, not other services
apiVersion: security.istio.io/v1beta1
kind: AuthorizationPolicy
metadata:
  name: postgres-allow-anihpj
  namespace: anihpj-prod
spec:
  selector:
    matchLabels:
      app: postgres
  rules:
  - from:
    - source:
        principals: ["cluster.local/ns/anihpj-prod/sa/anihpj-sa"]

💡 STRICT vs PERMISSIVE mTLS Mode

PERMISSIVE: The sidecar accepts both mTLS and plaintext traffic. Use during migration when some services haven't joined the mesh yet. Never leave in production.

STRICT: The sidecar rejects all plaintext traffic. Only mTLS connections are accepted. This is the target state — every service must present a valid Istio certificate. If a service not in the mesh tries to connect, it gets a TLS handshake failure.

Migration pattern: start with PERMISSIVE, bring all services into the mesh, verify connectivity, then switch to STRICT.

Q2
What is the difference between mTLS and regular (one-way) TLS in terms of certificate exchange?
Show Answer
Answer

Regular TLS: Only the server presents a certificate. The client verifies the server's identity but the server does not verify the client's identity. Any client can connect.

Mutual TLS (mTLS): Both the server AND the client present certificates. Each side verifies the other's identity. Only clients with a valid certificate signed by the trusted CA can connect — preventing unauthorised services from making requests.

Explanation

In Kubernetes with Istio, both certificates are automatically issued and managed by Istio's CA (SPIFFE/SVID format). Each pod gets a unique identity certificate tied to its ServiceAccount. This enables zero-trust networking inside the cluster.
