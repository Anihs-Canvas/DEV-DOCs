1.1 The Secret Sprawl Nightmare

Before we understand why Vault exists, we need to understand the problem it solves. In modern software, a "secret" is any piece of sensitive information that an application needs to function — passwords, API keys, TLS certificates, database credentials, encryption keys, tokens. Without a central management system, these secrets end up scattered everywhere — a phenomenon called "secret sprawl."

🔍 How Secret Sprawl Happens — A Day in the Life

Imagine you're a developer on the anihpj team. Your Django app needs a database password to connect to PostgreSQL. You add it to settings.py for local testing — "I'll fix it before production." But the deadline looms, and the password gets committed to Git. A colleague needs it for their local setup, so you Slack it to them. The DevOps engineer copies it into a Kubernetes Secret YAML. Six months later, the password is in 5 different places, nobody knows who has access, and it hasn't been rotated since day one. This is secret sprawl.

The average organization has thousands of secrets spread across source code, CI/CD pipelines, config files, cloud consoles, and chat messages. Manual management doesn't scale — you can't audit who accessed what, you can't rotate secrets without breaking things, and a single leaked credential can compromise your entire infrastructure.

Any sensitive data: password, key, token, certificate. The "what" that Vault protects.

🪪

1.2 What is HashiCorp Vault? (The Simple Answer)

HashiCorp Vault is a centralized secrets management platform. At its core, Vault is a tool for securely accessing secrets. It encrypts data at rest, controls access via policies, audits every interaction, and can even generate and auto-rotate secrets dynamically.

Written in: Go | License: MPL 2.0 (open-source) | Enterprise: Available

🧠 The Philosophy Behind Vault

Vault was born from a simple insight: secrets should never be stored alongside the code that uses them. This principle — separation of secrets from application logic — is the foundation of modern security architecture. Vault doesn't just encrypt secrets; it acts as a trusted intermediary between applications and their sensitive data. Every interaction goes through Vault's policy engine, which answers one question: "Should THIS caller be allowed to do THAT operation?"

Think of Vault as a central bank for secrets. Just as you don't carry your life savings in cash everywhere, your applications shouldn't carry credentials. They go to the "bank" (Vault), prove their identity (authenticate), and withdraw only what they're authorized to access (policy check). Every transaction is recorded (audit), and some "currencies" even expire automatically (dynamic secrets with TTL). This is fundamentally different from the .env file approach where secrets sit in plaintext on every developer's laptop.

1.3 The 4 Pillars of Vault — Visual Overview

Vault's architecture rests on four foundational pillars that together create a complete secrets management solution:

🔐
PILLAR 1: Secure Secret Storage

AES-256-GCM96 encryption at rest. Data is NEVER stored as plaintext on disk. An encryption barrier ensures all data is encrypted before touching storage. "Like a bank vault — everything locked inside."

🔑
PILLAR 2: Access Control

Identity-based ACL policies with per-path control. Default is DENY ALL. Policies use HCL syntax. Multiple policies combine as a UNION (most permissive wins). Supports templated policies for dynamic access. "Like a security guard checking every ID badge."

📋
PILLAR 3: Audit Everything

Every single request is logged — who, what, when. Tamper-proof audit trail. Multiple audit devices: file, socket (→ Logstash/Splunk), syslog (→ SIEM). "Like CCTV cameras recording every interaction."

🔄
PILLAR 4: Automate Rotation

Dynamic DB credentials with TTL — auto-expire. Auto-renew leases. Zero-touch certificate rotation via PKI. Root credential rotation. "Like a self-cleaning system — nothing stale."

🎓 EXAM TIP

Remember the 4 Pillars in order: Storage → Access → Audit → Rotation. A common exam question asks "Which Vault feature ensures credentials are automatically changed?" — The answer is Dynamic Secrets with TTL/Lease (Pillar 4).

🔗 How the 4 Pillars Work Together

These pillars are not independent — they form a chain of trust. Pillar 1 (Secure Storage) ensures secrets are encrypted, but without Pillar 2 (Access Control), anyone could decrypt them. Pillar 2 controls access, but without Pillar 3 (Audit), you'd never know if someone abused their access. Pillar 3 records everything, but without Pillar 4 (Rotation), a compromised secret remains valid indefinitely. All four are required for a complete security posture. This is why Vault is fundamentally different from a password manager or a KMS — it's not just about storing secrets; it's about managing their entire lifecycle with cryptographic guarantees at every stage.

🧱 Understanding Each Layer

Vault's architecture follows the separation of concerns principle. Listeners handle the network (TCP, TLS, rate limiting) — they're the "front door." The Core is a pipeline: Auth Methods verify identity (WHO you are), the Token Store creates a session token, the Policy Engine checks authorization (WHAT you can do), and Secrets Engines perform the actual work. The Audit Broker logs everything in parallel (non-blocking). Finally, the Encryption Barrier ensures that even if an attacker gains physical access to storage, all data is encrypted. Storage Backends only ever see encrypted blobs. This layered design means security is not a single point but a defense in depth system where each layer independently contributes to security.

2.2 The Seal/Unseal Mechanism (EXAM CRITICAL) 🎯

When Vault starts, it's SEALED — the master key is NOT in memory, and ALL operations (except status and unseal) are blocked. This is Vault's strongest security guarantee.

🔐 Why the Seal State Matters

The seal state is Vault's ultimate security control. When Vault is sealed, the encrypted data sits on disk but is mathematically impossible to decrypt without the master key — and the master key exists nowhere in the system. It must be reconstructed through the unseal process. This means: (1) a stolen hard drive with Vault data is useless without unseal keys, (2) a compromised Vault process can be instantly locked down with vault operator seal, and (3) Vault restarts are safe — data remains protected until explicitly unsealed. This is fundamentally different from a typical database that auto-decrypts on startup. Vault refuses to operate until enough key holders explicitly authorize it.

🔬 Understanding Recovery Keys vs Unseal Keys

This distinction is heavily tested on the exam. Unseal keys reconstruct the master key — they let Vault decrypt data. Recovery keys are used to regenerate the root token or rotate the underlying encryption key. They serve different purposes: unseal keys = "open the vault," recovery keys = "reset the admin password." In auto-unseal setups, you don't have unseal keys (the cloud KMS handles that), but you still get recovery keys during initialization. If you lose recovery keys AND the root token, you lose administrative access permanently — even though Vault is unsealed and operational.

🎓 EXAM TIP

Shamir keys = manual, need K of N. Auto-Unseal = automatic via cloud KMS. Recovery Keys are DIFFERENT from unseal keys — they regenerate the root token, not the master key. This is a common exam trick!

🪵 Debugging Permission Denied — Using the Lifecycle

When you see 403 Permission Denied, the lifecycle tells you exactly where to look: Step 4 (Token invalid or expired?), Step 5 (Correct policies attached?), or Step 6 (Policy covers this path with the right capability?). Use vault token lookup to check TTL and policies. Use vault token capabilities <token> <path> to test exactly what a token can do on a given path without actually making the request. This command is your #1 debugging tool and is frequently tested on the exam. The audit log (Step 9) also records every denied request with the exact reason — check it first when troubleshooting.

⚡ Performance Implications of the Lifecycle

Each of the 10 steps adds latency. In a typical production setup, the full roundtrip is 5-15ms. Storage backend choice has the biggest impact — Raft adds sub-millisecond overhead for reads (from followers) but requires a quorum write to the leader (1-3ms). The TLS handshake (Step 2) is amortized over persistent connections. Policy evaluation (Step 6) is extremely fast because policies are compiled and cached in memory. The audit broker (Step 9) is non-blocking — Vault doesn't wait for audit writes before responding. For high-throughput scenarios (>10K requests/sec), consider using batch tokens (lighter verification) and enabling performance standbys (Enterprise) to distribute read load.

Q1
What is the Encryption Barrier in Vault and why is it critical?
Show Answer
Answer

The Encryption Barrier is Vault's security foundation — ALL data is encrypted with AES-256-GCM96 before it touches any storage backend. The master key exists ONLY in memory, never on disk. This means even if an attacker gains access to the physical storage, the data is encrypted and useless without the master key.

Explanation

This is the reason Vault must be "unsealed" — the master key needs to be reconstructed in memory before any data can be decrypted. When Vault is sealed, ALL operations (except status and unseal) return errors.

Q2
What is Shamir's Secret Sharing and how does it work in Vault?
Show Answer
Answer

Shamir's Secret Sharing is a cryptographic algorithm that splits the master key into N shares (e.g., 5), where K shares (e.g., 3) are needed to reconstruct it. Each key holder gets one share. No single person can unseal Vault alone — it requires collaboration of K key holders.

Explanation

This provides both security (2 keys = useless) and fault tolerance (2 keys can be lost, 3 remain). The command is: vault operator init -key-shares=5 -key-threshold=3. This is called "M of N" or "threshold cryptography."

Q3
What is the difference between Shamir Unseal and Auto-Unseal?
Show Answer
Answer

Shamir: Manual — requires K of N key holders to enter their keys via vault operator unseal. Auto-Unseal: Automatic — Vault uses a cloud KMS (AWS, Azure, GCP) to decrypt the master key on startup. No manual intervention needed.

Explanation

Auto-unseal is preferred for production because it eliminates the manual unseal process on restart. However, it requires a cloud KMS dependency and additional cost. Important: Recovery Keys (for root token regeneration) are DIFFERENT from unseal keys.

Q4
Which storage backend is recommended for new Vault deployments and why?
Show Answer
Answer

Raft (integrated) is recommended for all new deployments since Vault 1.4. It requires zero external dependencies, supports HA natively, provides automatic snapshots, and is simpler to operate than Consul-backed deployments.

Explanation

Consul is still supported and recommended if you already have a Consul cluster running. Filesystem should NEVER be used in production (single point of failure, no HA). Inmem is dev-only (data lost on restart).

Q5
In a Vault HA cluster with Raft, what happens when the Active node crashes?
Show Answer
Answer

1. Raft detects the leader failure and elects a new leader from the standby nodes. 2. The load balancer detects the old active as unhealthy. 3. ALL traffic is routed to the new active. Total downtime: typically <5 seconds.

Explanation

Standby nodes forward ALL requests to the active node during normal operation. After failover, the newly elected active starts handling reads and writes directly. This is why the load balancer must point to /v1/sys/health which returns 200 only for the active node.

Q6
List the 10 steps of a Vault request lifecycle in order.
Show Answer

1. Parse, 2. TLS, 3. Parse Token, 4. Verify Token, 5. Load Policies, 6. ACL Check, 7. Route, 8. Decrypt, 9. Audit Log, 10. Response. Steps 4-6 are where 90% of permission errors occur.

Explanation

Understanding this lifecycle helps you debug "permission denied" errors. If you get a 403, the issue is in steps 4-6 (token invalid, TTL expired, policies don't allow the operation, or ACL denied it).

Q7
What does "vault operator seal" do and when would you use it?
Show Answer
Answer

vault operator seal is an emergency lockdown command. It wipes the master key from memory, putting Vault back into the sealed state. ALL operations are immediately blocked. Use it when you suspect a security breach.

Explanation

After sealing, Vault must be unsealed again (via Shamir keys or auto-unseal) to resume operations. This is Vault's "big red button" — it instantly protects all secrets when you detect suspicious activity.

Q8
Can the Filesystem storage backend be used in production?
Show Answer
Answer

NO — NEVER use Filesystem in production. It's a single point of failure with no HA support. If the disk fails, all Vault data is lost. Production requires Raft (integrated) or Consul (external) with multiple nodes.

Explanation

Filesystem is acceptable for development and testing only. Even then, inmem (dev mode) is often more convenient. The exam may ask which storage backends are production-ready — the answer is Raft, Consul, and cloud backends (DynamoDB, GCS, etc.).

Q9
How does the Audit Broker work in Vault's architecture?
Show Answer
Answer

The Audit Broker sits inside Vault's Core and logs EVERY request — including who made it, what path was accessed, what operation was performed, and the response. It supports multiple audit devices simultaneously: File (local disk), Socket (→ Logstash/Splunk), and Syslog (→ SIEM).

Explanation

Audit logging is non-blocking — if an audit device fails, Vault continues to operate. However, if ALL audit devices fail, Vault will eventually block requests (configurable). Sensitive data in audit logs is HMAC'd (hashed) by default.

4.2 KV v1 — Simple Key-Value Storage

KV v1 is the original, simpler version of the KV engine. It stores secrets at the path you specify — no versioning, no soft delete, no metadata. What you write is what you get. It's still available for backward compatibility but KV v2 is the default since Vault 1.0.

KV v1 Operations
# Enable KV v1
vault secrets enable -version=1 kv

# Write (path is direct — no /data/ prefix)
vault kv put kv/anihpj db_user=anihpj db_pass=s3cr3t

# Read (same path)
vault kv get kv/anihpj

# Delete (permanent — no recovery!)
vault kv delete kv/anihpj
# → Data is GONE. No undelete. No versioning.
⚠️ KV v1 Limitations

No version history, no soft delete, no metadata tracking, no patch (partial update), no Check-And-Set. For all new deployments, use KV v2 unless you have a specific reason to use v1.

Q5
What is Check-And-Set (CAS) in KV v2 and how is it used?
Show Answer
Answer

CAS is a concurrency control mechanism that prevents conflicting writes. You specify the expected version number: vault kv put -cas=3 secret/anihpj key=value. If the current version is not 3, the write is rejected. This prevents two clients from overwriting each other's changes.

Explanation

CAS requires the -cas flag with the expected version. If version 3 is the latest and you CAS write expecting version 3, it succeeds and creates version 4. If someone else already wrote version 4, your CAS write fails. This is the "optimistic locking" pattern.

5.5 Lease Management — TTL, Renew, Revoke 🎯

Every dynamic secret comes with a lease — a time-limited permission to use the credential. Understanding leases is essential for both the exam and production operations.

Q1
What is the fundamental difference between static and dynamic secrets in Vault?
Show Answer
Answer

Static secrets are pre-existing values stored in Vault (like KV secrets) — everyone gets the same value. Dynamic secrets are generated on-demand by Vault — each request creates a unique credential with a TTL that auto-expires. Static = shared key. Dynamic = unique temporary key per person.

Explanation

Dynamic secrets are Vault's killer feature. They eliminate the "shared password" problem — if a dynamic credential is leaked, it's useless after TTL. The blast radius is limited to one consumer, not the entire system.

    username=postgres \
    password=rootpassword
Explanation

The connection_url uses {{username}} and {{password}} placeholders that Vault fills dynamically. The root credentials (postgres/rootpassword) are used ONLY by Vault to create/delete temporary users.

Q3
What are default_ttl and max_ttl in a database role?
Show Answer
Answer

default_ttl: The initial lease duration when credentials are generated. Can be renewed up to max_ttl. max_ttl: The absolute maximum lifetime of a credential — even if continuously renewed, Vault will revoke it when max_ttl is reached.

Explanation

Example: default_ttl=1h, max_ttl=24h means credentials last 1 hour initially, can be renewed hourly, but will be FORCEFULLY revoked after 24 hours regardless of renewal. This is a safety limit — no credential lives forever.

Q4
What command generates dynamic database credentials?
Show Answer
Answer
vault read database/creds/anihpj-role
Explanation

Note: vault read (not vault kv get) is used for dynamic secrets. The path is database/creds/<role-name>. Each call creates a NEW database user and returns unique credentials.

Q5
What happens when a dynamic credential's TTL expires?
Show Answer
Answer

Vault automatically revokes the credential by running the role's revocation_statements SQL (or by default, dropping the database user). The lease is marked as expired, and the credential becomes invalid. The application loses database access — which is why Vault Agent proactively renews before expiry.

Explanation

This is the security guarantee of dynamic secrets: even if you forget about a credential, Vault remembers. No manual cleanup needed. No stale database users accumulating over months. This is fundamental to least-privilege security.

Q6

Show Answer

vault lease renew database/creds/anihpj-role/abc123
vault lease revoke database/creds/anihpj-role/abc123
Explanation

Renew extends TTL by default_ttl (up to max_ttl). Revoke immediately terminates the credential and runs revocation SQL. You can also revoke by prefix: vault lease revoke -prefix database/creds/anihpj-role.

Q7
What does the {{name}} and {{password}} template syntax do in creation_statements?
Show Answer
Answer

These are template placeholders that Vault fills dynamically when generating credentials. {{name}} becomes a unique username (e.g., v_token_anihpj_role_abc123), {{password}} becomes a randomly generated password, and {{expiration}} becomes the TTL timestamp. This allows you to write generic SQL that works for every credential.

Explanation

Templates make the role reusable — you write the SQL once, and Vault substitutes values for each credential request. Available placeholders: name, password, expiration, role, and custom metadata.

The plugin architecture means Vault can support virtually any database. The plugin_name field in the config determines which database driver to use. The exam focuses on PostgreSQL but expects you to know that multiple databases are supported.

Q9
Why is it safe for Vault to store root database credentials?
Show Answer

This is the "trusted intermediary" pattern: Vault acts as a secure broker between applications and databases. The root password can be extremely complex and rarely changed because only Vault uses it.

6.2 Transit Secrets Engine — Encryption as a Service 🎯

The Transit engine performs cryptographic operations without storing your data. You send plaintext, Vault returns ciphertext — the encryption key NEVER leaves Vault. You manage the ciphertext wherever you want.

TRANSIT ENGINE — Encrypt/Decrypt Flow
┌──────────┐          ┌──────────┐
│ anihpj   │          │  Vault   │
│ Django   │          │  Transit │
└────┬─────┘          └────┬─────┘
     │ 1. "Encrypt:        │
     │  Django SECRET"     │
     │────────────────────▶│
     │                     │ 2. AES-256-GCM96 encrypt
     │                     │ (key NEVER leaves Vault!)
     │ 3. ciphertext:      │
     │ "vault:v1:abc..."  │
     │◀────────────────────│
     │ 4. "Decrypt:        │

Transit Operations
# Create encryption key
vault write transit/keys/anihpj-key type=aes256-gcm96

# Encrypt data

# Decrypt data

6.3 SSH Secrets Engine — One-Time SSH Passwords

The SSH engine generates one-time passwords (OTP) for SSH access. Instead of managing SSH keys across your team, you request a temporary password from Vault that works for a single login only.

SSH OTP Usage
vault write ssh/creds/otp_key_role ip=192.168.1.100
→ Returns one-time SSH password valid for single login
💡 Use Case

Emergency production server access for SRE team. No permanent SSH keys on anyone's machine. Every access generates an audit trail. Password expires after single use — impossible to reuse if intercepted. This eliminates the "who has the production SSH key?" problem entirely.

6.4 Identity Secrets Engine

The Identity engine manages Entities, Groups, and Aliases — Vault's internal identity system. An Entity represents a single user or machine that can authenticate via multiple methods. Aliases map each auth method's identity to the entity. Groups organize entities and can inherit policies.

👤
Entity

Represents a single identity across ALL auth methods. "Alice" can login via userpass OR LDAP — Vault recognizes her as the same entity.

🏷️
Alias

Maps a specific auth method login to an entity. Alice's userpass login and LDAP login are both aliases pointing to Entity:Alice.

👥
Group

Collects entities. Policies attached to a group apply to ALL members. "engineering-team" group gets eng-policy.

📜
Policy Inheritance

Entity policies + Group policies = UNION. Multiple groups combine — Alice gets policies from ALL her groups.

See Chapter 9 for the full Identity system deep dive with hands-on anihpj examples.

6.5 Cubbyhole Secrets Engine

Cubbyhole is a per-token, ephemeral storage space. Secrets stored in cubbyhole are scoped to YOUR token only — no other token can read them, even with root privileges. When your token expires or is revoked, all cubbyhole data is automatically destroyed.

📖 Primary Use Case

Response wrapping: Vault wraps a secret in a one-time token, you pass that token to another process, and that process unwraps it. The cubbyhole stores the wrapped response. Once unwrapped, the token is destroyed. This is how AppRole SecretIDs are securely delivered.

6.6 TOTP Secrets Engine — Time-Based One-Time Passwords

The TOTP engine generates time-based one-time passwords (like Google Authenticator). Vault stores the TOTP key and generates 6-digit codes on demand — you never see the underlying secret.

TOTP Usage
# Generate TOTP key
vault write totp/keys/anihpj-user generate=true issuer=anihpj account_name=admin

# Get current 6-digit code
vault read totp/code/anihpj-user
→ code: 482951

Use case: 2FA for anihpj admin panel. Vault generates the TOTP code, Django validates it. No shared secrets stored in application code.

What is the key principle of the Transit Secrets Engine?
Show Answer
Answer

Q5
What does Transit key rotation do and how does it affect existing encrypted data?
Show Answer
Answer

Key rotation creates a new key version. New encryption operations use the latest version. Old ciphertexts can still be decrypted because Vault keeps old key versions. Existing encrypted data is NOT affected — it continues to work. To update old ciphertexts to the latest key, use the rewrap operation.

Explanation

This is critical for zero-downtime rotation. You don't need to re-encrypt all your data immediately. Old ciphertexts decrypt with their original key version. Rewrap lets you gradually migrate to the new key. vault write -f transit/keys/my-key/rotate adds a new version.

Q8

Show Answer

7.3 AppRole Auth Method — For Machines and Applications 🎯🎯

AppRole is the #1 auth method for machines. It's designed for applications, services, and CI/CD pipelines — anything that isn't a human. The pattern is beautifully simple: a RoleID (like a username, not secret) + a SecretID (like a password, VERY secret). Both must match for login to succeed.

🤖 RoleID — The "Who"
  • Non-secret identifier
  • Can be embedded in app config
  • Like a username for machines
  • Retrieved once, reused
🔑 SecretID — The "Prove It"
  • SECRET credential
  • Single-use by default
  • Has its own TTL
  • Must be securely delivered

🔒CIDR Bindingtoken_bound_cidrs restricts which IP ranges can use the token. For anihpj pods on K8s overlay network (10.244.0.0/16), this prevents token theft from outside the cluster.
⏱️SecretID TTLsecret_id_ttl=10m means the SecretID is only valid for 10 minutes after generation. After that, a new one must be generated. This limits the window for credential theft.
🔢SecretID Num Usessecret_id_num_uses=1 means the SecretID is single-use — after one login, it's consumed. Set to 0 for unlimited uses (less secure).
🔗Token Bindingbind_secret_id=true locks the token to the specific SecretID used. If false, any valid SecretID for the role works.
🎯 EXAM TIP: The exam WILL ask about the difference between RoleID and SecretID. Remember: RoleID is NOT secret — it identifies WHICH role. SecretID IS secret — it proves you're authorized for that role. Think of RoleID as a username and SecretID as a password.

7.4 Kubernetes Auth Method — Pod Authentication 🎯🎯🎯

~15% of Vault Associate Exam — MASTER THIS SECTION

Kubernetes Auth is the most important auth method for the exam. It lets pods authenticate to Vault using their Kubernetes ServiceAccount JWT token — the same token that's automatically mounted at /var/run/secrets/kubernetes.io/serviceaccount/token in every pod. This means zero passwords, zero hardcoded credentials, zero manual secret distribution.

🔑 How It Works (Simple): The pod sends its ServiceAccount JWT to Vault → Vault calls the Kubernetes TokenReview API to validate the JWT → If valid, Vault checks the role bindings (which SA, which namespace) → If everything matches, Vault returns a Vault token with the configured policies. The pod now has access to Vault secrets.

7.5 Other Auth Methods — Quick Reference

Beyond AppRole and Kubernetes, Vault supports 20+ auth methods. Here are the ones you need to know for the exam and real-world use.

7.5a Userpass — Simple Username/Password

The simplest auth method for human operators. Users are created within Vault (not external). Good for small teams, labs, and initial setup. Not recommended for production at scale — use LDAP/OIDC instead.

vault auth enable userpass
vault write auth/userpass/users/alice password="s3cur3p@ss" policies=admin
vault login -method=userpass username=alice password="s3cur3p@ss"
7.5b LDAP — Enterprise Directory Integration

Integrates with Active Directory or any LDAP server. Users authenticate with their existing corporate credentials. Vault doesn't store passwords — it binds to LDAP to verify. Supports group-based policy mapping.

vault auth enable ldap
vault write auth/ldap/config \
    url="ldaps://ldap.corp.local:636" \
    binddn="cn=vault,ou=services,dc=corp,dc=local" \
    bindpass="s3rv1c3p@ss" \
    userdn="ou=users,dc=corp,dc=local" \
    groupdn="ou=groups,dc=corp,dc=local" \
    groupfilter="(&(objectClass=group)(member={{.UserDN}}))"
vault write auth/ldap/groups/engineering policies=eng-policy
vault login -method=ldap username=alice password="corpP@ss"
7.5c JWT/OIDC — Federated Single Sign-On

Authenticate using JWTs from any OIDC provider (Okta, Auth0, Azure AD, Google, etc.). Vault validates the JWT signature against the provider's public keys. Supports role-based claims mapping and bound claims for fine-grained access.

vault auth enable jwt
# Or: vault auth enable oidc

vault write auth/jwt/config \
    oidc_discovery_url="https://accounts.google.com" \
    default_role="gcp-admin"

vault write auth/jwt/role/my-role \
    user_claim="email" \
    bound_claims="{'hd':'company.com'}" \
    policies="admin" \
    ttl=1h

vault login -method=jwt role=my-role jwt=$(cat id_token.txt)
7.5d GitHub — Developer Access via PAT

Authenticate using GitHub Personal Access Tokens. Ideal for developer access to Vault in CI/CD pipelines. Map GitHub teams to Vault policies.

vault auth enable github
vault write auth/github/config organization=my-org
vault write auth/github/map/teams/engineering value=eng-policy
vault login -method=github token=ghp_xxxxxxxxxxxxxxxxxxxx
7.5e TLS Certificates — Mutual TLS Authentication

Authenticate using client TLS certificates. The client presents its certificate during the TLS handshake. Vault validates the certificate chain. Used for machine-to-machine communication where mTLS is already in place.

7.5f Cloud Auth (AWS, Azure, GCP)

Authenticate cloud resources using their native identity: AWS IAM roles/instance profiles, Azure Managed Service Identity (MSI), GCP service accounts. Vault verifies the cloud provider's identity signature.

☁️AWS AuthUses AWS IAM credentials or EC2 instance metadata. vault auth enable aws. Binds to AMI ID, IAM role, EC2 tags.
🔷Azure AuthUses Azure MSI or VMSS identities. vault auth enable azure. Binds to subscription, resource group, VMSS.
🔴GCP AuthUses GCP service account JWTs. vault auth enable gcp. Binds to project, service account, instance labels.

An auth method verifies identity. It validates credentials (password, JWT, RoleID+SecretID, etc.) and, on success, returns a Vault token with attached policies. The auth method itself does NOT grant access — it proves who you are. Policies determine what you can access.

Explanation

Q62

Show Answer

Q65
What happens when a pod's ServiceAccount JWT expires during Kubernetes auth?
Show Answer
Answer

Explanation

For anihpj: bind to the K8s pod CIDR (10.244.0.0/16) and service CIDR (10.96.0.0/12). If the token leaves the cluster, it's useless.

8.2 Token Auth Configuration — Token Roles

The Token auth method supports token roles that control what kind of tokens can be created via auth/token/create. This is different from vault token create (which uses the root/sudo privilege path). Token roles let you delegate controlled token creation to non-administrators.

Bash — Token Role Configuration
# Create a token role that restricts what tokens can be created
vault write auth/token/roles/limited-role \
    allowed_policies="app-policy,db-policy" \
    orphan=true \
    renewable=true \
    explicit_max_ttl=2h \
    token_explicit_max_ttl=2h

# Now, when using this role to create tokens:
vault write auth/token/create/anihpj-role \
    policies="app-policy"

# The resulting token will:
# - Only have "app-policy" and "default" (restricted by allowed_policies)
# - Be orphan (survives parent token revocation)
# - Have max TTL of 2 hours
# - Be renewable

8.3a RoleID — The Identity Half

The RoleID is a UUID that identifies the role. It is NOT a secret — you can store it in configuration files, CI variables, or even commit it to version control. Vault generates it automatically when you create a role, but you can also supply a custom value.

    role_id="my-custom-app-id" \
    token_policies="app-policy"

# RoleID is NOT encrypted — it's just an identifier
# Think: "username" for machines
8.3b SecretID — The Secret Half

The SecretID is the actual credential. It must be protected like a password. By default, SecretIDs are single-use (secret_id_num_uses=1) and have a TTL (secret_id_ttl). After generation, distribute via response wrapping or Vault Agent — never in plaintext over insecure channels.

# Generate a SecretID (default: single-use)
vault write -f auth/approle/role/anihpj-app/secret-id
# Key                  Value
# ---                  -----
# secret_id            hvs.CAESIKmR8oQMli...
# secret_id_accessor   1a2b3c4d-5e6f-7a8b-9c0d-1e2f3a4b5c6d

# Generate with custom metadata + CIDR
vault write auth/approle/role/anihpj-app/secret-id \
    cidr_list="10.244.0.0/16" \
    metadata='{"env":"production","deploy":"v1.2.3"}'

# SecretID accessor can be used to:
# - Look up SecretID metadata (without exposing the secret)
# - Revoke a specific SecretID
# - Track which SecretID was used for an audit event
💡 Best Practice: Use response wrapping to deliver SecretIDs. Wrap the secret-id creation response in a one-time token, then the application unwraps it. This ensures the SecretID is only seen by the intended recipient and only once.
8.3c CIDR Binding — Network-Locked Tokens

CIDR binding restricts which IP addresses can use the token. Set at the role level (token_bound_cidrs) for all tokens from that role, or at SecretID generation time (cidr_list) for granular per-SecretID control.

# Role-level CIDR binding (all tokens from this role)
vault write auth/approle/role/anihpj-app \
    token_bound_cidrs="10.244.0.0/16" \
    ...

# SecretID-level CIDR binding (specific SecretID only)
vault write auth/approle/role/anihpj-app/secret-id \
    cidr_list="10.244.3.0/24,10.244.4.0/24"
8.3d Token Binding — Lock Token to SecretID

When bind_secret_id=true, the resulting token is cryptographically bound to the specific SecretID that was used to create it. This means: (1) The token can only perform operations that require the SecretID if that specific SecretID is still valid, (2) Revoking the SecretID also invalidates the token. When bind_secret_id=false, any valid SecretID for the role can create a token, and the token is independent of the SecretID.

🔐 BEST PRACTICE — Secure SecretID Delivery via Response Wrapping: Never send a SecretID in plaintext over email, chat, or CI logs. Instead, use response wrapping (covered in detail in Part 4, Chapter 11). The SecretID generation response is wrapped in a single-use "wrapping token." Only the intended recipient can unwrap it — and unwrapping consumes the token, so any eavesdropper who tries to unwrap it will fail (already consumed). This is the recommended way to deliver SecretIDs to CI/CD pipelines and applications.

8.5 JWT/OIDC Auth Configuration

JWT/OIDC auth allows Vault to accept tokens from any OIDC-compliant identity provider (Okta, Auth0, Azure AD, Google, etc.). Vault validates the JWT signature against the provider's JWKS endpoint and checks bound claims before issuing a Vault token.

Bash — JWT/OIDC Configuration
# Enable JWT auth (or 'oidc' — functionally identical)
vault auth enable jwt

# Configure with OIDC discovery (auto-fetches JWKS, issuer, etc.)
vault write auth/jwt/config \
    oidc_discovery_url="https://accounts.google.com" \
    default_role="gcp-user"

# Or configure manually (without OIDC discovery)
vault write auth/jwt/config \
    jwt_validation_pubkeys=@public-key.pem \
    issuer="https://my-idp.company.com"

# Create role with bound claims
vault write auth/jwt/role/my-role \
    role_type="jwt" \
    user_claim="sub" \
    bound_claims='{"group":"engineering","email_verified":true}' \
    bound_audiences="vault-audience" \
    policies="eng-policy" \
    ttl=1h \
    max_ttl=8h

# Login with JWT
vault write auth/jwt/login role=my-role jwt="eyJhbGci..."
# Returns Vault token with eng-policy attached
🔑 Key Parameters: user_claim — which JWT claim identifies the user (typically "sub" or "email"). bound_claims — JSON map of required claim values (all must match). bound_audiences — which aud values are accepted. oidc_discovery_url — auto-configures issuer, JWKS endpoint, and algorithms from OIDC discovery document.

8.6 Multi-Factor Authentication (MFA) 🔐

MFA adds a second layer of authentication on top of any auth method. After successful primary authentication, Vault requires a second factor (TOTP code, Duo push, Okta verify) before issuing a token. MFA is configured per mount accessor — each auth method mount has its own MFA configuration.

Bash — MFA Configuration Examples
# Enable TOTP MFA for the userpass auth method
# First, get the mount accessor for userpass
vault auth list -format=json | jq '."userpass/".accessor'

# Create TOTP MFA method enforcement
vault write identity/mfa/method/totp/admin-totp \
    issuer=vault \
    period=30 \
    key_size=20 \
    algorithm=SHA256 \
    digits=8

# Enforce MFA on userpass login
vault write identity/mfa/login-enforcement/admin-mfa \
    mfa_method_ids=admin-totp \
    auth_method_accessors="auth_userpass_xxx" \
    auth_method_types=userpass

# Now, users authenticating via userpass must also
# provide a valid TOTP code to complete login

# Supported MFA types:
# - TOTP (Time-based One-Time Password)
# - Okta (Push notification + verify)
# - Duo (Push, phone call, passcode)
# - PingID (Push, OTP)
⚠️ IMPORTANT: MFA login enforcement applies to all login attempts on the specified auth method. There's no per-user MFA — it's all-or-nothing per auth method mount. To have different MFA policies for different users, mount the same auth type at multiple paths with different MFA configs.
🏗️ PRODUCTION MFA STRATEGY — Multi-Mount Approach

Since MFA is per-mount (not per-user), here's how to implement tiered MFA for the anihpj team:

# Strategy: Mount userpass at TWO paths with different MFA requirements

# Admin mount — REQUIRES TOTP MFA
vault auth enable -path=admin-userpass userpass
vault write auth/admin-userpass/users/admin password="s3cur3"
vault write identity/mfa/login-enforcement/admin-mfa \
    mfa_method_ids=admin-totp \
    auth_method_accessors=$(vault auth list -format=json | jq -r '."admin-userpass/".accessor')

# Developer mount — NO MFA (or lighter MFA like Duo)
vault auth enable -path=dev-userpass userpass
vault write auth/dev-userpass/users/dev1 password="d3vP@ss"
# No MFA enforcement on this mount

# Now:
# vault login -method=userpass -path=admin-userpass → prompts for TOTP
# vault login -method=userpass -path=dev-userpass  → no MFA required

This pattern lets you enforce strict MFA for privileged accounts while keeping developer access friction-free. Each mount can have different TTLs, policies, and MFA requirements — all using the same underlying userpass auth type.

    token_policies=my-policy \
    token_ttl=30m
Explanation

secret_id_ttl=10m: The SecretID expires 10 minutes after generation. secret_id_num_uses=1: The SecretID can only be used once — after a successful login, it's consumed. This is the most secure configuration: the credential is short-lived AND single-use.

Q74
What is bind_secret_id in AppRole and what are its security implications?
Show Answer
Answer

When bind_secret_id=true (default), the resulting Vault token is cryptographically bound to the specific SecretID used for login. If that SecretID is later revoked, the token becomes invalid. When bind_secret_id=false, the token is independent of the SecretID — revoking the SecretID doesn't affect the token. Always use bind_secret_id=true for production. Set to false only when SecretID is unavailable at token usage time.

Explanation

Security recommendation: bind_secret_id=true + secret_id_num_uses=1 + secret_id_ttl=10m = maximum security. The SecretID is single-use, short-lived, and the resulting token is bound to it.

Q75

Q76
How does JWT/OIDC auth validate a token from an external identity provider?
Show Answer
Answer

Vault fetches the OIDC provider's JWKS (JSON Web Key Set) from the discovery URL, then uses the provider's public keys to verify the JWT signature. After signature verification, Vault checks: (1) iss claim matches configured issuer, (2) aud claim is in bound_audiences, (3) All bound_claims match the JWT claims, (4) JWT is not expired (exp claim). If all checks pass, Vault issues a token with the role's policies.

Explanation

This is a multi-layer validation: cryptographic (signature), temporal (expiration), and semantic (claims matching). Vault never sees the user's password — it trusts the OIDC provider's assertion.

🏷️ Entity

A single identity in Vault. Represents a person or machine. Has a unique ID, name, metadata, and can be a member of groups. Entities don't have policies directly — they inherit them from groups.

🔗 Alias

A mapping from an auth method identity to an Entity. Each alias says: "When someone logs in as 'alice' via userpass, they are Entity Alice." One entity can have many aliases (one per auth method).

👥 Group

A collection of entities. Groups hold policies. When an entity is a member of a group, tokens created for that entity inherit the group's policies. Two types: Internal (managed in Vault) and External (managed by LDAP/Okta, synced to Vault).

📋 Mount Accessor

Each auth method mount has a unique accessor (UUID). Aliases use the accessor to identify WHICH auth method mount they belong to. Even if two userpass mounts exist (prod-userpass, dev-userpass), each has a different accessor.

How do you ensure she has the same permissions as when she authenticates via userpass?" Answer: Create an entity with aliases for both auth methods, add the entity to a group with the required policies.

9.4 Aliases — Mapping Auth Method Identities to Entities

An Alias is the bridge between an auth method's login identity and a Vault Entity. Each alias says: "When someone logs in as X via auth method Y, they are Entity Z." Without aliases, Vault treats each auth method login as a separate, anonymous identity.

vault write identity/entity-alias \

Q81
What is the purpose of Vault's Identity system (Entities, Aliases, Groups)?
Show Answer
Answer

The Identity system unifies multiple auth methods under a single identity. It solves the problem of a user authenticating via different methods (userpass, LDAP, OIDC) being treated as different identities. With Identity: (1) Entities represent a single person/machine, (2) Aliases map auth method logins to entities, (3) Groups organize entities and carry policies that all members inherit.

Explanation

Without Identity: Alice logs in via userpass = Identity A with policies X. Alice logs in via LDAP = Identity B with policies Y. Different access depending on auth method. With Identity: Both auth methods map to Entity:Alice via aliases → Alice always gets policies from her groups, regardless of how she authenticates.

Q82
What is the difference between an Internal and External group in Vault Identity?
Show Answer
Answer

Internal Groups: Members are managed manually within Vault using member_entity_ids. You explicitly add/remove entities. External Groups: Members are managed by an external identity provider (LDAP, Okta). Vault syncs membership from the external source. Both types carry policies that members inherit. External groups require the auth method to support group syncing (e.g., LDAP, OIDC with groups claim).

Explanation

Use internal groups when you manage team structure in Vault directly (small teams, machine identities). Use external groups when team structure is managed in your corporate directory (LDAP/AD) and you want Vault to automatically reflect changes.

Q83
How do you ensure a user has the same Vault access regardless of which auth method they use?
Show Answer
Answer

Create an Entity for the user, create Aliases for each auth method they use (pointing to the same entity), add the entity to Groups that carry the required policies. Now, when they authenticate via ANY of the configured auth methods, Vault recognizes them as the same entity and attaches all group policies.

Explanation

Q84
How do policies flow from Groups to an Entity's tokens?
Show Answer
Answer

When a token is created for an entity, Vault computes the UNION of: (1) Policies from ALL groups the entity is a member of, (2) Policies attached directly to the auth method role, (3) The "default" policy (unless token_no_default_policy=true). The resulting token has the sum of all these policies. Vault uses a most-permissive model — if ANY source grants a capability, it's allowed. There are no "deny" policies.

Explanation

Example: Alice is in group "developers" (policy: read-secrets) and group "db-admins" (policy: manage-db). Her token gets BOTH policies. She can read secrets AND manage databases. Policy inheritance is additive, never subtractive.

Q85
What is a Mount Accessor and why is it important for Aliases?
Show Answer
Answer

A Mount Accessor is a UUID that uniquely identifies each auth method mount. Aliases use the mount accessor to specify WHICH auth method mount they belong to. This is critical because you can have multiple mounts of the same auth type (e.g., prod-userpass/ and dev-userpass/) — each has a different accessor, so aliases are correctly scoped to the right mount.

Explanation

Find a mount's accessor: vault auth list -format=json | jq '."userpass/".accessor'. The accessor stays the same even if you tune the auth method, but changes if you disable and re-enable it (new accessor is assigned).

Q86
What happens when you merge two entities in Vault?
Show Answer
Answer

When you merge Entity A into Entity B: (1) All aliases from Entity A are moved to Entity B, (2) Entity A's group memberships are transferred to Entity B, (3) Entity A is deleted, (4) Entity B keeps its original aliases and groups. Explanation

Q89
What are the key differences between Group policy inheritance and Token policy assignment?
Show Answer
Answer

Group policies: Inherited indirectly through entity membership. Changes to group policies affect ALL entity tokens (existing tokens continue until renewal — new policies apply on next login/renewal). Token policies: Assigned directly at token creation time (via -policy flag or auth method role). They're "baked into" the token and don't change even if the source role changes. Group policies are more dynamic and manageable at scale.

Explanation

Exam scenario: "You change a group's policies. When do existing tokens get the new policies?" Answer: On the NEXT renewal or when a NEW token is created. Existing tokens keep their original policies until they expire or are renewed.

Explanation

The lookup chain: Login → Alias (name + mount_accessor) → Entity → Group Memberships → Group Policies → Token policies. This happens transparently — the user just sees their token with all the right policies.

10.2 Service Tokens vs Batch Tokens (EXAM CRITICAL) 🎯🎯🎯

THE #1 EXAM DISTINCTION — Know every difference!

This is the most tested topic in the Token domain. The exam will ask multiple questions about Service vs Batch tokens. The core distinction: Service tokens are stored in Vault's memory (they have leases, can be renewed, can be revoked, can have children). Batch tokens are encrypted blobs (not stored, no lease, cannot be renewed, cannot be revoked — they just expire).

10.2a Service Tokens — The Workhorse

Service tokens are the default token type. They're stored in Vault's internal storage, have leases, can be renewed, can be revoked by ID, and can create child tokens. Use service tokens for long-lived applications like the anihpj Django app, Vault Agent sidecars, and any workload that needs persistent, renewable access.

# Create a service token (default)
vault token create -policy=anihpj-policy -ttl=4h

# Look up any service token by its ID
vault token lookup s.A1b2C3d4E5f6...

# Renew the token
vault token renew s.A1b2C3d4E5f6...

# Revoke the token
vault token revoke s.A1b2C3d4E5f6...

# Create a child token (only service tokens can do this!)
vault token create -policy=child-policy -ttl=1h
10.2b Batch Tokens — The Lightweight Speedster

Batch tokens are encrypted blobs — Vault does NOT store them. They have no lease, no renewal, no revocation, no children. They're ideal for high-volume, short-lived operations where you don't want to burden Vault's storage. Batch tokens DO count against rate limits but NOT against the token count limit.

# Create a batch token
vault token create -type=batch -policy=read-only -ttl=30s

# Batch tokens CAN self-lookup
vault token lookup
# Shows: type=batch, policies, ttl, creation_time

# Batch tokens CANNOT be looked up by others
vault token lookup b.A1b2C3d4...  # → ERROR: bad token

# Batch tokens CANNOT be renewed
vault token renew b.A1b2C3d4...    # → ERROR

# Batch tokens CANNOT be revoked
vault token revoke b.A1b2C3d4...   # → ERROR (just wait for expiry)
10.2c Orphan Tokens — No Parent, No Inheritance

Orphan tokens are service tokens with no parent. They survive the revocation of the token that created them. Use orphans when you want a token to be independent — e.g., a long-lived application token that shouldn't die when an admin's token is revoked.

# Create an orphan token (survives parent revocation!)
vault token create -orphan -policy=app-policy -ttl=24h
10.2d Periodic Tokens — Auto-Renew Forever

Periodic tokens auto-renew indefinitely — until explicitly revoked. They have a period instead of a max_ttl. Each renewal extends the TTL by the period value. Use periodic tokens for long-running services that should never expire. Requires root/sudo to create.

# Create a periodic token (auto-renews every 24h FOREVER)
vault token create -period=24h -policy=app-policy

10.4 Periodic & Orphan Tokens — Special Purpose Tokens

👻 Orphan Tokens

No parent. Created with -orphan flag. Survives the revocation of the token that created it. Use when you need a token to be independent of its creator's lifecycle. Must be a service token (batch tokens have no parent concept).

vault token create -orphan -policy=app -ttl=72h
🔄 Periodic Tokens

Auto-renews forever. Has a period instead of max_ttl. Each renewal extends TTL by the period value. Continues until explicitly revoked. Requires root/sudo to create. Perfect for long-running services.

vault token create -period=24h -policy=service
🔑 Key Distinction: Orphan = about parent relationship (no parent). Periodic = about TTL behavior (auto-renews). A token can be BOTH orphan AND periodic: vault token create -orphan -period=24h. This creates a token with no parent that auto-renews forever — ideal for critical infrastructure services.

Q91
What is a Vault token and what three things does Vault check on every API request?
Show Answer
Answer

A token is the result of successful authentication — it's your digital keycard. On every API request, Vault checks: (1) Is the token valid? (not expired, not revoked), (2) What policies are attached? (what capabilities does this token grant), (3) Is the path allowed? (does the policy match the requested API path). If ALL pass, the request succeeds. If ANY fail, Vault returns 403 Forbidden.

Explanation

Think of a token as a hotel keycard: it identifies you, it has a time limit, and it only opens specific doors. The token itself doesn't contain secrets — it's a reference that Vault uses to look up your identity and permissions.

Q92
What is the fundamental difference between a Service token and a Batch token?
Show Answer
Answer

Service tokens are stored in Vault's memory — they have leases, can be renewed, revoked, and can have children. Batch tokens are encrypted blobs — NOT stored in Vault. They cannot be renewed, revoked, or have children. Batch tokens can only self-lookup; they cannot be looked up by ID. Batch tokens are lightweight (don't count against token limits) but disposable (just wait for TTL expiry).

Explanation

This is the #1 exam distinction. Memorize: "Batch = NOT stored, NOT renewable, NOT revocable." The exam WILL ask: "Which token type is NOT stored in Vault?" → Batch. "Which token type can have children?" → Service only.

Q93
What happens when you revoke a parent Service token? What about orphan tokens?
Show Answer
Answer

Revoking a parent Service token recursively revokes ALL children — the entire subtree is destroyed. However, orphan tokens survive — they have no parent link, so parent revocation doesn't affect them. This is called "cascading revoke." Note: when a token simply expires (TTL runs out), children are NOT automatically revoked — expiry is not cascading.

Explanation

Cascading revoke applies to explicit vault token revoke only, not to natural TTL expiry. This distinction is important: if a parent token expires at 2 PM, its children continue until their own TTLs expire. But if you revoke the parent at 1:59 PM, all children are immediately revoked.

Q94
What are the three TTL-related constraints on child tokens?
Show Answer
Answer

When creating a child token from a parent: (1) Child TTL ≤ Parent TTL — a child cannot outlive its parent's current TTL, (2) Child MaxTTL ≤ Parent MaxTTL — a child's maximum lifetime cannot exceed the parent's, (3) Child policies ⊆ Parent policies — a child can only have a subset of the parent's policies, never additional policies the parent doesn't have.

Explanation

This enforces the principle of least privilege through the token hierarchy. A token can never create a child that is more powerful or longer-lived than itself. This prevents privilege escalation through token creation.

Q95
Can you renew a Batch token? Can you revoke a Batch token? Can you look up a Batch token by its ID?
Show Answer
Answer

NO to all three. Batch tokens cannot be renewed, cannot be revoked, and cannot be looked up by ID (only self-lookup works). If you need renewability or revocability, use a Service token. Batch tokens simply expire when their TTL runs out — there's no other way to end them early.

Explanation

Why? Batch tokens are encrypted blobs — Vault doesn't store them, so there's nothing to look up, nothing to renew, and nothing to revoke. They're designed for high-volume, short-lived, fire-and-forget operations where storage overhead would be wasteful.

Q96
What is the difference between an Orphan token and a Periodic token?
Show Answer
Answer

Explanation

11.1 Response Wrapping — The Tamper-Proof Envelope 🎁🎯

11.2 Token Accessors Deep Dive — Separation of Duties

vault kv get secret/anihpj -accessor 7hS9kW2mX5vB8nQ3cR6tY1uI

Explanation

Vault Agent uses a configurable retry block for renewal failures. If renewal fails repeatedly, Vault Agent can be configured to re-authenticate from scratch — ensuring the application always has a valid token.

Q108
Can you use a token accessor to read secrets from Vault?
Show Answer
Answer

NO. Token accessors are for token management only: lookup properties, renew, revoke. You cannot use an accessor to read secrets, write data, or perform any path-based Vault operation. Only the actual token string (s.xxxxx or hvs.xxxxx) can access secrets. This is by design — accessors are safe to share with ops/audit teams.

Explanation

Accessors can do: vault token lookup -accessor <id>, vault token renew -accessor <id>, vault token revoke -accessor <id>. Accessors CANNOT do: vault kv get secret/foo (or any data operation).

Q109
What is the difference between vault token renew and vault lease renew?
Show Answer
Answer

vault token renew extends a token's TTL (the authentication credential). vault lease renew extends a dynamic secret's lease (e.g., database credentials generated by the DB secrets engine). Tokens are for authentication; leases are for dynamic secrets. They're separate concepts — a token can be alive while a lease expires, and vice versa.

Explanation

From Chapter 5 (Secrets Engines): Dynamic secrets have leases. You renew leases to keep database credentials alive. Tokens are what let you call Vault at all. You renew tokens to stay authenticated. Both need renewal, but they're independent.

🟡 Part 4 Key Takeaways — What You Must Remember

🎫Token = Authentication ResultEvery Vault API call carries a token. Valid + Policies + TTL = Access.
⚖️Service ≠ BatchService stored/renewable/revocable. Batch NOT stored/NOT renewable/NOT revocable.
🌳Parent Revoke = CascadingRevoke parent → ALL children destroyed. Orphans survive. Expiry is NOT cascading.
👻Orphan ≠ PeriodicOrphan = no parent. Periodic = auto-renew. They're orthogonal (can be both).
🎁Wrap = Tamper-ProofSingle-use envelope. Unwrap consumes token. Detect interception.
🔑Accessors ≠ SecretsAccessors manage tokens. Only token strings access data. Separation of duties.
⏱️Renew at TTL/2Renew when 50% TTL remains. MaxTTL forces re-auth. Vault Agent auto-handles.
👑Root = NuclearGenerate → Use → Revoke. Never store. Requires quorum of unseal keys.
🚀 Part 4 Implementation Blueprint — Token Strategy for anihpj/jobpost

Here's how tokens flow through the complete anihpj stack:

1
Pod authenticates via K8s Auth — SA JWT → Vault verifies → Returns Service token (TTL=1h, MaxTTL=24h). Vault Agent stores it in sink file.
2
Vault Agent auto-renews — At TTL/2 (30 min), Vault Agent renews the token. On MaxTTL, it re-authenticates automatically. Application never manages tokens directly.
3
Health checks use Batch tokens — Readiness probes get disposable 30s batch tokens via K8s Auth. No storage, no renewal, no cleanup needed.
4
CI/CD gets Orphan Service token — GitHub Actions pipeline authenticates via AppRole. SecretID delivered via response wrapping. Orphan token survives pipeline job completion.
5
Admins auth via OIDC — Human operators get short-lived Service tokens (15m). Revocable if compromised. Accessors shared with audit team — never token values.
6
Root token used only for emergencies — Generate via quorum, use for the specific task (e.g., changing seal config), revoke immediately. Never stored.
