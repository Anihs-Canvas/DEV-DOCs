SECTION 1: SYSTEMCTL — SERVICE MANAGEMENT
================================================================================

systemctl
---------
Control the systemd system and service manager.

Synopsis
systemctl is the central management tool for controlling the systemd system
and service manager. It is used to introspect and control the state of the
systemd system, manage system services (both at runtime and persistently),
manage system states (poweroff, reboot, etc), and inspect the system state.

For the anihpj/jobpost project, systemctl manages the Gunicorn WSGI server,
Celery workers, Nginx reverse proxy, and periodic backup/cleanup timers.

SYNTAX:
  systemctl [OPTIONS...] COMMAND [UNIT...]

COMMANDS OVERVIEW:
  systemctl start UNIT...          # Start (activate) one or more units
  systemctl stop UNIT...           # Stop (deactivate) one or more units
  systemctl restart UNIT...        # Restart one or more units
  systemctl reload UNIT...         # Reload configuration
  systemctl status UNIT...         # Show runtime status
  systemctl enable UNIT...         # Enable unit to start at boot
  systemctl disable UNIT...        # Disable unit from starting at boot
  systemctl is-enabled UNIT...     # Check if unit is enabled
  systemctl is-active UNIT...      # Check if unit is active (running)
  systemctl is-failed UNIT...      # Check if unit is in failed state
  systemctl list-units             # List loaded units
  systemctl list-unit-files        # List installed unit files
  systemctl daemon-reload          # Reload systemd configuration
  systemctl show UNIT...           # Show properties of unit(s)
  systemctl cat UNIT...            # Show unit file(s) and overrides
  systemctl edit UNIT...           # Edit unit drop-in override
  systemctl mask UNIT...           # Mask unit (symlink to /dev/null)
  systemctl unmask UNIT...         # Unmask unit
  systemctl kill UNIT...           # Send signal to processes
  systemctl clean UNIT...          # Clean runtime data

STATUS VALUES:
  active (running)     — Unit is active and running
  active (exited)      — One-shot service completed successfully
  active (waiting)     — Unit is running, waiting for an event
  inactive (dead)      — Unit is not running
  activating (start)   — Unit is in the process of starting
  deactivating (stop)  — Unit is in the process of stopping
  failed               — Unit encountered an error and failed


systemctl start
---------------
Start (activate) one or more units.

Synopsis
Start a systemd unit. If the unit is already active, this is a no-op.
Units can be services (.service), sockets (.socket), timers (.timer),
or targets (.target). The .service extension is assumed if omitted.

SYNTAX:
  systemctl start UNIT...

Examples:
  systemctl start nginx
  systemctl start gunicorn.service celery-worker.service
  systemctl start jobpost.target


systemctl stop
--------------
Stop (deactivate) one or more units.

Synopsis
Stop a running unit. If the unit is not running, this is a no-op.
Stopping a service sends the configured kill signal (SIGTERM by default).

SYNTAX:
  systemctl stop UNIT...

Examples:
  systemctl stop gunicorn
  systemctl stop celery-worker celery-beat


systemctl restart
-----------------
Stop and then start one or more units.

Synopsis
Restart a running unit. If the unit is not running, it will be started.
This is equivalent to "stop" followed by "start" but is handled atomically.

SYNTAX:
  systemctl restart UNIT...

Examples:
  systemctl restart nginx
  systemctl restart gunicorn


systemctl reload
----------------
Reload the configuration of a unit without restarting it.

Synopsis
Asks the service to reload its configuration. The service must support
the ExecReload= directive in its unit file. If ExecReload is not defined,
the reload request is ignored. This is the preferred way to apply config
changes without dropping connections.

SYNTAX:
  systemctl reload UNIT...

Examples:
  systemctl reload nginx          # Graceful config reload
  systemctl reload gunicorn       # HUP signal: reload workers


systemctl reload-or-restart
----------------------------
Reload configuration if the unit supports it, otherwise restart.

This is the safest "apply config" command. If ExecReload is defined,
it reloads; otherwise it falls back to a full restart.

SYNTAX:
  systemctl reload-or-restart UNIT...

Examples:
  systemctl reload-or-restart nginx


systemctl status
----------------
Show the runtime status of one or more units.

Synopsis
Displays: unit name, description, loaded/enabled state, active state,
PID, start time, recent log lines, and resource usage. This is the
primary diagnostic command for any systemd service.

SYNTAX:
  systemctl status UNIT...

Examples:
  systemctl status gunicorn
  systemctl status nginx celery-worker


systemctl enable / disable
---------------------------
Enable units to start at boot, or disable automatic startup.

SYNTAX:
  systemctl enable UNIT...
  systemctl disable UNIT...
  systemctl enable --now UNIT...    # Enable AND start immediately
  systemctl disable --now UNIT...   # Disable AND stop immediately

Examples:
  systemctl enable nginx
  systemctl enable --now gunicorn celery-worker
  systemctl disable old-service


systemctl list-units
--------------------
List all loaded units.

SYNTAX:
  systemctl list-units [PATTERN...]
  systemctl list-units --type=service
  systemctl list-units --state=failed
  systemctl list-units --all          # Include inactive units

Examples:
  systemctl list-units --type=service
  systemctl list-units --state=failed
  systemctl list-units 'gunicorn*'


systemctl daemon-reload
-----------------------
Reload the systemd manager configuration.

This must be run after creating, modifying, or deleting unit files.
It makes systemd aware of the changes. Does NOT restart any services.

SYNTAX:
  systemctl daemon-reload

Examples:
  cp gunicorn.service /etc/systemd/system/
  systemctl daemon-reload
  systemctl start gunicorn


systemctl show / cat / edit
------------------------------
Inspect and modify unit configuration.

SYNTAX:
  systemctl show UNIT             # All properties (key=value)
  systemctl show UNIT -p Property  # Specific property
  systemctl cat UNIT               # Show unit file + overrides
  systemctl edit UNIT              # Create/edit drop-in override

Examples:
  systemctl show gunicorn | grep ExecStart
  systemctl cat nginx
  systemctl edit gunicorn


systemctl mask / unmask
-----------------------
Mask a unit (prevent ANY start) or unmask it.

SYNTAX:
  systemctl mask UNIT
  systemctl unmask UNIT

Examples:
  systemctl mask NetworkManager    # Prevent starting
  systemctl unmask NetworkManager


systemctl kill
--------------
Send a signal to one or more processes of a unit.

SYNTAX:
  systemctl kill UNIT...
  systemctl kill -s SIGNAL UNIT...  # Specific signal (HUP, TERM, KILL, etc.)

Examples:
  systemctl kill -s HUP gunicorn     # Graceful reload
  systemctl kill -s TERM celery-worker

SECTION 2: JOURNALCTL — LOG VIEWING AND ANALYSIS
================================================================================

journalctl
----------
Query the systemd journal — the centralized logging system.

Synopsis
journalctl is the primary tool for viewing and filtering logs collected
by systemd-journald. It provides timestamped, structured log entries from
the kernel, services, and applications. Supports filtering by service,
time range, priority, boot session, and more.

For the anihpj/jobpost project, journalctl is used to:
- Monitor Gunicorn and Celery service logs
- Debug application startup failures
- Track cron/timer job execution
- Analyze kernel OOM events and security audit logs

SYNTAX:
  journalctl [OPTIONS...] [MATCHES...]


journalctl — Basic Viewing
----------------------------
SYNTAX:
  journalctl                     # All logs (oldest first)
  journalctl -r                  # Reverse: newest first
  journalctl -e                  # Jump to end of journal
  journalctl -f                  # Follow: live tail
  journalctl -n 50               # Last 50 lines
  journalctl -n 50 -f            # Last 50 + follow

Examples:
  journalctl -f -n 20
  journalctl -r


journalctl — Service Filtering
-------------------------------
SYNTAX:
  journalctl -u UNIT             # Logs for a specific unit
  journalctl -u UNIT -f          # Follow a unit's logs
  journalctl -u UNIT1 -u UNIT2   # Multiple units
  journalctl _SYSTEMD_UNIT=UNIT  # Alternative filter syntax

Examples:
  journalctl -u gunicorn -f
  journalctl -u gunicorn -u celery-worker -n 100
  journalctl -u nginx --since today


journalctl — Time Filtering
-----------------------------
SYNTAX:
  journalctl --since "DATE"       # Logs since a point in time
  journalctl --until "DATE"       # Logs until a point in time
  journalctl --since "1 hour ago"
  journalctl --since "2026-06-06 09:00:00"
  journalctl --since today
  journalctl --since yesterday --until today
  journalctl -S "2026-06-01" -U "2026-06-06"

Examples:
  journalctl -u gunicorn --since "1 hour ago"
  journalctl --since today --until "23:59"
  journalctl -S "2026-06-06 08:00:00" -U "2026-06-06 12:00:00"


journalctl — Boot Filtering
-----------------------------
SYNTAX:
  journalctl -b                  # Current boot
  journalctl -b -1               # Previous boot
  journalctl -b -2               # Boot before previous
  journalctl --list-boots        # List all boots
  journalctl -b 0                # Current boot (boot ID)

Examples:
  journalctl -b -1               # Why did the last boot fail?
  journalctl --list-boots
  journalctl -b -1 -u gunicorn   # Gunicorn logs from previous boot


journalctl — Priority/Error Filtering
---------------------------------------
SYNTAX:
  journalctl -p PRIORITY         # Filter by syslog priority
  journalctl -p 3                # Priority 3 (err) and above
  journalctl -p err              # Same as -p 3
  journalctl -p warning          # -p 4: warning and above
  journalctl -p emerg..err       # Range: emerg (0) to err (3)

PRIORITY LEVELS:
  0  emerg     System is unusable
  1  alert     Action must be taken immediately
  2  crit      Critical conditions
  3  err       Error conditions
  4  warning   Warning conditions
  5  notice    Normal but significant
  6  info      Informational
  7  debug     Debug-level messages

Examples:
  journalctl -p err              # Errors and worse
  journalctl -u gunicorn -p warning
  journalctl -b -p crit


journalctl — Kernel Messages
------------------------------
SYNTAX:
  journalctl -k                  # Kernel messages (dmesg equivalent)
  journalctl -k -b               # Kernel messages for current boot
  journalctl -k -b -1            # Previous boot kernel messages
  journalctl -k --since today
  journalctl -k -p err

Examples:
  journalctl -k --since today
  journalctl -k -b               # Check OOM events at boot


journalctl — Output Formats
-----------------------------
SYNTAX:
  journalctl -o FORMAT
  journalctl --output=FORMAT

FORMATS:
  short          Default: syslog-like
  short-full     Timestamps with full timezone
  short-iso      ISO 8601 timestamps
  short-precise  Microsecond timestamps
  verbose        Full structured fields
  json           JSON (one object per line)
  json-pretty    Pretty-printed JSON
  json-sse       Server-Sent Events format
  cat            Just the message text (no metadata)
  export         Binary export for archiving

Examples:
  journalctl -u gunicorn -o json-pretty | head -50
  journalctl -o short-iso --since "1 hour ago"
  journalctl -u nginx -o cat


journalctl — Advanced Filtering
---------------------------------
SYNTAX:
  journalctl _UID=1000            # By user ID
  journalctl _PID=1234            # By process ID
  journalctl _GID=1000            # By group ID
  journalctl _COMM=nginx          # By command/executable name
  journalctl _EXE=/usr/sbin/nginx # By executable path
  journalctl _TRANSPORT=stdout    # By transport (stdout, syslog, kernel, etc.)
  journalctl --grep=PATTERN       # Grep through message text (Perl regex)
  journalctl --case-sensitive     # Case-sensitive grep

Examples:
  journalctl _COMM=gunicorn
  journalctl --grep="OOM killer"
  journalctl -u gunicorn --grep="ERROR|CRITICAL"


journalctl — Disk Usage and Maintenance
-----------------------------------------
SYNTAX:
  journalctl --disk-usage         # Show disk space used by journal
  journalctl --vacuum-size=500M   # Keep only 500MB
  journalctl --vacuum-time=7d     # Keep 7 days of logs
  journalctl --vacuum-size=1G --vacuum-time=30d
  journalctl --rotate             # Rotate journal files
  journalctl --flush              # Flush journal from /run to /var
  journalctl --sync               # Sync unwritten entries to disk
  journalctl --header             # Show journal header info

Examples:
  journalctl --disk-usage
  journalctl --vacuum-size=500M
  journalctl --vacuum-time=7d

SECTION 3: WRITING SYSTEMD UNIT FILES
================================================================================

Unit File Fundamentals
-----------------------
Systemd unit files define how services, sockets, timers, and other
resources are managed. They are plain-text INI-style configuration
files placed in specific directories.

UNIT FILE LOCATIONS:
  /usr/lib/systemd/system/     # Distribution-provided units (DO NOT EDIT)
  /etc/systemd/system/         # Administrator-managed units (EDIT HERE)
  /run/systemd/system/         # Runtime units (volatile)
  /etc/systemd/system/UNIT.d/  # Drop-in overrides

PRIORITY (highest to lowest):
  /etc/systemd/system/UNIT.d/*.conf  (drop-in overrides)
  /etc/systemd/system/UNIT
  /run/systemd/system/UNIT
  /usr/lib/systemd/system/UNIT

After creating/modifying a unit file, always run:
  systemctl daemon-reload


Unit File Structure — Sections
--------------------------------
Every unit file has [Unit], [Service] (or [Socket], [Timer], etc.),
and [Install] sections.

[Unit] — Unit metadata and dependencies
  Description=       Human-readable description
  Documentation=     URLs to documentation
  Requires=          Hard dependencies (unit fails if these fail)
  Wants=             Soft dependencies (started alongside)
  After=             Ordering: start AFTER these units
  Before=            Ordering: start BEFORE these units
  BindsTo=           Strong binding (stops if bound unit stops)
  PartOf=            Part of a larger unit (restart/stop propagates)
  Conflicts=         Mutually exclusive units
  Condition*=        Conditions that must be true for unit to start
  Assert*=           Assertions (fail unit if not true)

[Service] — Service-specific configuration
  Type=               Service startup type (simple, forking, oneshot, dbus, notify, idle)
  ExecStart=          Command to start the service
  ExecStartPre=       Commands run BEFORE ExecStart
  ExecStartPost=      Commands run AFTER ExecStart
  ExecReload=         Command to reload configuration
  ExecStop=           Command to stop the service
  ExecStopPost=       Commands run AFTER service stops
  Restart=            Restart policy (no, on-success, on-failure, on-abnormal, always)
  RestartSec=         Time to wait before restarting
  TimeoutStartSec=    Timeout for startup
  TimeoutStopSec=     Timeout for graceful stop
  User=               Run service as this user
  Group=              Run service as this group
  WorkingDirectory=   Working directory for Exec* commands
  Environment=        Set environment variable
  EnvironmentFile=    Load environment from file
  StandardOutput=     Redirect stdout (journal, syslog, file:/path, null)
  StandardError=      Redirect stderr
  SyslogIdentifier=   Identifier in syslog/journal
  PIDFile=            PID file path (for Type=forking)
  PrivateTmp=         Use private /tmp namespace
  ProtectSystem=      Mount /usr, /boot read-only (yes, full, strict)
  ProtectHome=        Protect /home (yes, read-only, tmpfs)
  NoNewPrivileges=    Prevent privilege escalation
  ReadOnlyPaths=      Paths mounted read-only
  ReadWritePaths=     Paths mounted read-write
  LimitNOFILE=        File descriptor limit
  LimitNPROC=         Process limit
  MemoryLimit=        Memory limit (now MemoryMax=)
  CPUQuota=           CPU quota percentage

[Install] — Installation configuration (enable/disable)
  WantedBy=           Target(s) that "want" this unit (typically multi-user.target)
  RequiredBy=         Target(s) that require this unit
  Alias=              Alternative names for the unit
  Also=               Additional units to enable/disable together


Service Types
--------------
Type=simple    (Default) Systemd considers the service started immediately.
               ExecStart is the main process. Don't fork.

Type=forking   Service forks a child process. Parent exits after startup.
               Must specify PIDFile=. Used for traditional daemons.

Type=oneshot   Short-lived process. Systemd waits for it to exit before
               continuing. Use RemainAfterExit=yes to consider active.

Type=notify    Service sends a readiness signal via sd_notify().
               Most modern services support this.

Type=dbus      Service registers on D-Bus. Systemd waits for the bus name.

Type=idle      Like simple, but delayed until all jobs are dispatched.
               Useful for avoiding console output interleaving.


Restart Policies
-----------------
Restart=no              Never restart (default)
Restart=on-success      Restart only on clean exit (exit code 0)
Restart=on-failure      Restart on unclean exit, signal, or timeout
Restart=on-abnormal     Restart on signal or timeout (not clean exit)
Restart=on-watchdog     Restart on watchdog timeout
Restart=always          Always restart (even on clean exit)

Use Restart=on-failure with RestartSec=5s for production services.


Example 1: Simple Gunicorn Service
------------------------------------
# /etc/systemd/system/gunicorn.service
# Django WSGI server for the anihpj jobpost application

[Unit]
Description=Gunicorn WSGI server for anihpj jobpost
Documentation=https://docs.gunicorn.org/
After=network.target network-online.target
Requires=gunicorn.socket

[Service]
Type=notify
User=anihpj
Group=anihpj
WorkingDirectory=/lpj
EnvironmentFile=/lpj/ops/systemd/gunicorn.env
ExecStart=/lpj/env/bin/gunicorn anihpj.wsgi:application \
    --workers 4 \
    --bind unix:/run/gunicorn.sock \
    --access-logfile /lpj/ops/logs/gunicorn-access.log \
    --error-logfile /lpj/ops/logs/gunicorn-error.log
ExecReload=/bin/kill -s HUP $MAINPID
Restart=on-failure
RestartSec=5s
TimeoutStopSec=30s
KillMode=mixed

# Security hardening
PrivateTmp=yes
ProtectSystem=strict
ProtectHome=yes
NoNewPrivileges=yes
ReadWritePaths=/lpj/ops/logs /run/gunicorn.sock

# Resource limits
LimitNOFILE=65536
MemoryMax=2G

[Install]
WantedBy=multi-user.target


Example 2: Gunicorn Socket Activation
---------------------------------------
# /etc/systemd/system/gunicorn.socket
# Socket-activated Gunicorn — starts on first connection

[Unit]
Description=Gunicorn socket for anihpj jobpost

[Socket]
ListenStream=/run/gunicorn.sock
SocketUser=anihpj
SocketGroup=www-data
SocketMode=0660
Backlog=2048

[Install]
WantedBy=sockets.target


Example 3: Celery Worker Service
----------------------------------
# /etc/systemd/system/celery-worker.service
# Celery background task worker for anihpj jobpost

[Unit]
Description=Celery Worker for anihpj jobpost
Documentation=https://docs.celeryproject.org/
After=network.target network-online.target
Requires=gunicorn.service
PartOf=jobpost.target

[Service]
Type=forking
User=anihpj
Group=anihpj
WorkingDirectory=/lpj
EnvironmentFile=/lpj/ops/systemd/celery.env
PIDFile=/run/celery-worker.pid
ExecStart=/lpj/env/bin/celery -A anihpj worker \
    --loglevel=INFO \
    --concurrency=4 \
    --pidfile=/run/celery-worker.pid \
    --logfile=/lpj/ops/logs/celery-worker.log
ExecReload=/bin/kill -s HUP $MAINPID
ExecStop=/bin/kill -s TERM $MAINPID
Restart=on-failure
RestartSec=10s
TimeoutStopSec=60s
KillMode=mixed

PrivateTmp=yes
NoNewPrivileges=yes
LimitNOFILE=65536

[Install]
WantedBy=jobpost.target

---------------------------------------------
# /etc/systemd/system/backup.service

SECTION 7: COMMON TROUBLESHOOTING WORKFLOWS
================================================================================

Workflow 1: Service Won't Start
--------------------------------
  1. systemctl status UNIT                    # Current state
  2. journalctl -u UNIT -b --no-pager -n 50   # Recent logs
  3. systemctl cat UNIT                       # Inspect unit file
  4. systemd-analyze verify UNIT.service      # Validate syntax
  5. journalctl -u UNIT -p err                # Errors only
  6. systemctl show UNIT -p ExecStart         # Check ExecStart


Workflow 2: Service Crashed — Post-Mortem
-------------------------------------------
  1. systemctl is-failed UNIT                 # Confirm failure
  2. journalctl -u UNIT -b -1                 # Previous boot logs
  3. journalctl -k -b -1 | grep -i oom        # OOM killer?
  4. coredumpctl list UNIT                    # Core dumps (if any)
  5. coredumpctl info PID                     # Core dump details


Workflow 3: High CPU / Memory Investigation
---------------------------------------------
  1. systemctl status UNIT                    # Current resource usage
  2. systemctl show UNIT -p MemoryCurrent     # Memory usage
  3. systemctl show UNIT -p CPUUsageNSec      # CPU usage
  4. journalctl -u UNIT --since "30 min ago"  # Recent activity
  5. systemctl set-property UNIT MemoryMax=2G # Add resource limit


Workflow 4: Boot Performance Analysis
---------------------------------------
  1. systemd-analyze time                     # Boot time
  2. systemd-analyze blame | head -20         # Slowest units
  3. systemd-analyze critical-chain           # Critical path
  4. systemd-analyze plot > boot.svg          # Visualization
  5. systemctl list-units --state=failed      # Failed units


Workflow 5: Deploying a New Unit File
---------------------------------------
  1. cp myapp.service /etc/systemd/system/
  2. systemd-analyze verify /etc/systemd/system/myapp.service
  3. systemctl daemon-reload
  4. systemctl enable myapp.service
  5. systemctl start myapp.service
  6. systemctl status myapp.service
  7. journalctl -u myapp.service -f          # Monitor logs

SECTION 9: SYSTEMD TIMERS — DEEP DIVE
================================================================================

Timer Units
------------
Systemd timers replace cron jobs. They are more flexible, support
monotonic and realtime events, and are integrated with journald logging.

TIMER TYPES:
  OnCalendar=       Real-time (wall clock) — like cron
  OnActiveSec=      Relative to timer activation
  OnBootSec=        Relative to system boot
  OnStartupSec=     Relative to systemd startup
  OnUnitActiveSec=  Relative to last activation
  OnUnitInactiveSec= Relative to last deactivation
  Persistent=true   Catch up on missed runs (system was off)

CALENDAR EVENT SYNTAX (OnCalendar):
  minutely, hourly, daily, weekly, monthly, yearly
  *-*-* 02:30:00              # Every day at 02:30
  Mon..Fri *-*-* 09:00:00     # Weekdays at 9am
  Sat,Sun *-*-* 00:00:00      # Weekends at midnight
  *-01,15-* 03:00:00          # 1st and 15th at 3am
  hourly: 00:00               # At the top of every hour (with second precision)

AccuracySec=       Randomize start time to spread load (default 1min)
RandomizedDelaySec= Max random delay (for spreading load across machines)


Example: Jobpost Database Backup Timer
----------------------------------------
# /etc/systemd/system/backup-jobpost.service
[Unit]
Description=PostgreSQL backup for anihpj jobpost
After=network.target

[Service]
Type=oneshot
User=anihpj
WorkingDirectory=/lpj
ExecStart=/lpj/ops/scripts/backup-db.sh
StandardOutput=journal
StandardError=journal

# /etc/systemd/system/backup-jobpost.timer
[Unit]
Description=Daily jobpost database backup at 2 AM
Requires=backup-jobpost.service

[Timer]
OnCalendar=*-*-* 02:00:00
Persistent=true
RandomizedDelaySec=300
AccuracySec=1min

[Install]
WantedBy=timers.target

Management:
  systemctl enable backup-jobpost.timer
  systemctl start backup-jobpost.timer
  systemctl list-timers backup-jobpost.timer
  journalctl -u backup-jobpost.service


Example: Hourly Cleanup Timer
-------------------------------
# /etc/systemd/system/cleanup-sessions.timer
[Unit]
Description=Hourly session cleanup for anihpj

[Timer]
OnCalendar=hourly
Persistent=true

[Install]
WantedBy=timers.target


Timers vs Cron Comparison
---------------------------
  | Feature        | Cron              | Systemd Timer       |
  |----------------|-------------------|---------------------|
  | Scheduling     | Fixed minutes     | Calendar + relative |
  | Logging        | Email/syslog      | Journald (queryable)|
  | Random delay   | sleep hack        | RandomizedDelaySec  |
  | Catch-up       | anacron           | Persistent=true     |
  | Dependencies   | None              | Requires/After/Wants|
  | Resource limits| None              | CPU/Memory limits   |
  | Security       | User-based        | Full sandboxing     |
  | Environment    | Minimal           | EnvironmentFile     |

SECTION 10: SOCKET UNITS — DEEP DIVE
================================================================================

Socket Units (.socket)
-----------------------
Socket units enable on-demand service activation. The service starts
when the first connection arrives, saving resources when idle.

SOCKET TYPES:
  ListenStream=       TCP socket (SOCK_STREAM)
  ListenDatagram=     UDP socket (SOCK_DGRAM)
  ListenSequentialPacket=  Unix sequential packet
  ListenFIFO=         Named pipe (FIFO)
  ListenNetlink=      Netlink socket
  ListenSpecial=      Special file in /proc, /sys
  ListenMessageQueue= POSIX message queue


Socket Options:
  Accept=yes|no         yes: spawn one instance per connection
                        no: all connections to one service
  Backlog=              Connection backlog (default 4294967295)
  SocketUser=           Owner of socket file
  SocketGroup=          Group of socket file
  SocketMode=           Permissions (e.g., 0660)
  MaxConnections=       Max simultaneous connections
  Service=              Which service to activate (default: same-name .service)
  TriggerLimitBurst=    Rate limiting threshold
  TriggerLimitIntervalSec= Rate limiting interval


Example: Nginx Reverse Proxy with Socket Activation
-----------------------------------------------------
# /etc/systemd/system/nginx-proxy.socket
[Unit]
Description=Nginx proxy socket for anihpj

[Socket]
ListenStream=80
ListenStream=443
Backlog=4096
NoDelay=true
ReusePort=true

[Install]
WantedBy=sockets.target

# /etc/systemd/system/nginx-proxy.service
[Unit]
Description=Nginx reverse proxy for anihpj
After=network.target

[Service]
Type=notify
ExecStart=/usr/sbin/nginx -c /lpj/ops/nginx/nginx.conf
ExecReload=/usr/sbin/nginx -s reload
Restart=on-failure

[Install]
WantedBy=multi-user.target

Path Units (.path)
-------------------
Path units monitor files/directories and activate services when changes occur.
Replacement for inotify-based scripts and some cron-based polling.

PATH TYPES:
  PathExists=         Trigger when path exists
  PathExistsGlob=     Trigger when any matching path exists
  PathChanged=        Trigger when file is modified/created (not on every write)
  PathModified=       Trigger on every modification (more events)
  DirectoryNotEmpty=  Trigger when directory has files

  MakeDirectory=yes   Create the directory if missing
  DirectoryMode=      Permissions for created directory
  Unit=               Which service to activate (default: same-name .service)

SECTION 12: USER-SPECIFIC SYSTEMD UNITS

User Units (~/.config/systemd/user/)
---------------------------------------
Systemd supports per-user service management. User units run as the
logged-in user, without root privileges, and can persist after logout
with "lingering" enabled.

LOCATIONS:
  ~/.config/systemd/user/           # User-managed units
  /usr/lib/systemd/user/            # Distribution-provided user units
  /etc/systemd/user/                # Administrator-managed user units

COMMANDS (user mode):
  systemctl --user start UNIT       # Start user service
  systemctl --user enable UNIT      # Enable user service
  systemctl --user status UNIT      # Check user service
  systemctl --user daemon-reload    # Reload user config

MANAGEMENT:
  loginctl enable-linger USER       # Allow user services after logout
  loginctl disable-linger USER      # Disable lingering
  loginctl show-user USER           # Check linger status
  export XDG_RUNTIME_DIR=/run/user/$(id -u)  # Must be set

Example: User-Level Django Development Server
-----------------------------------------------

[Install]

SECTION 15: SYSTEMD SECURITY SANDBOXING — DEEP DIVE
================================================================================

Security Directives Reference
------------------------------
Systemd provides 30+ security hardening directives. Apply the principle
of least privilege to every service.

CORE SECURITY:
  NoNewPrivileges=yes       # Block privilege escalation via setuid/setgid
  ProtectSystem=strict      # Mount /usr, /boot read-only
  ProtectSystem=full        # Mount /usr, /boot, /etc read-only
  ProtectHome=yes           # Make /home inaccessible
  ProtectHome=read-only     # Mount /home read-only
  ProtectHome=tmpfs         # Mount empty tmpfs over /home

PROCESS ISOLATION:
  PrivateTmp=yes            # Private /tmp and /var/tmp namespace
  PrivateDevices=yes        # Private /dev with only pseudodevices
  PrivateNetwork=yes        # No network access (loopback only)
  PrivateUsers=yes          # Private user namespace
  PrivateMounts=yes         # Private mount namespace
  PrivateIPC=yes            # Private IPC namespace

FILESYSTEM RESTRICTIONS:
  ProtectKernelTunables=yes # /proc/sys, /sys read-only
  ProtectKernelModules=yes  # Cannot load/unload kernel modules
  ProtectKernelLogs=yes     # Cannot read kernel log
  ProtectClock=yes          # Cannot change system clock
  ProtectControlGroups=yes  # Cannot modify cgroups
  ProtectProc=invisible     # Hide other users' processes in /proc

READ-ONLY / INACCESSIBLE PATHS:
  ReadOnlyPaths=/etc /usr   # Paths mounted read-only
  InaccessiblePaths=/root   # Paths made inaccessible
  ReadWritePaths=/var/log   # Exceptions within protected areas
  BindPaths=/src:/dst       # Bind mount into the namespace
  BindReadOnlyPaths=/src:/dst # Read-only bind mount

CAPABILITY RESTRICTIONS:
  CapabilityBoundingSet=    # Limit process capabilities
  AmbientCapabilities=      # Grant ambient capabilities

SYSTEM CALL FILTERS:
  SystemCallFilter=         # Allow/deny syscalls
  SystemCallFilter=~@clock  # Deny clock syscalls
  SystemCallFilter=@default # Allow default safe set
  SystemCallArchitectures=  # Limit to specific architectures

Predefined Syscall Sets:
  @default    Safe, essential syscalls
  @basic-io   read, write, open, close
  @file-system File operations
  @network-io Socket operations
  @process    fork, clone, exec
  @mount      Mount operations
  @privileged All privileged syscalls
  @resources  Set resource limits
  @clock      Modify system clock
  @debug      Debug/trace syscalls


Security Hardening: Production vs Development
-----------------------------------------------
DEVELOPMENT SERVICE (relaxed):
  PrivateTmp=yes
  NoNewPrivileges=yes
  ProtectSystem=full

PRODUCTION SERVICE (hardened):
  NoNewPrivileges=yes
  ProtectSystem=strict
  ProtectHome=yes
  PrivateTmp=yes
  PrivateDevices=yes
  ProtectKernelTunables=yes
  ProtectKernelModules=yes
  ProtectKernelLogs=yes
  ProtectControlGroups=yes
  ProtectClock=yes
  RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6
  SystemCallFilter=@default
  RestrictRealtime=yes
  MemoryDenyWriteExecute=yes
  LockPersonality=yes


Security Audit Commands:
  systemd-analyze security UNIT                # Score and recommendations
  systemd-analyze security --json=pretty UNIT  # Detailed JSON output
  systemd-analyze security --no-pager UNIT     # Full report

SECTION 16: COMMON ERROR PATTERNS & SOLUTIONS
================================================================================

Error: "Unit is masked"
  # systemctl unmask UNIT
  # systemctl start UNIT

Error: "Unit is not running, refusing reload"
  # systemctl restart UNIT
  # Or: systemctl reload-or-restart UNIT

Error: "Failed to start UNIT: Unit is not loaded properly"
  # systemctl daemon-reload
  # systemd-analyze verify /etc/systemd/system/UNIT.service

Error: "A dependency job for UNIT failed"
  # systemctl list-dependencies UNIT
  # Check that all Requires/Wants units are active

Error: "Start request repeated too quickly" (rate-limited restart)
  # journalctl -u UNIT -b --no-pager -n 50
  # Check RestartSec= and the underlying error
  # systemctl reset-failed UNIT

Error: "Connection refused" on socket-activated service
  # systemctl status UNIT.socket
  # ss -tlnp | grep PORT
  # Check SocketUser/SocketGroup/SocketMode permissions

Error: "PID file not readable" (Type=forking)
  # Ensure the service actually writes the PID file
  # Check PIDFile= path is writable by User=
  # Verify the daemon doesn't fork twice (double-fork)

Error: OOM — service killed by Out-Of-Memory killer
  # journalctl -k | grep -i oom
  # systemctl show UNIT -p MemoryCurrent
  # Add MemoryMax= to unit file
  # Consider MemoryHigh= for soft limit warnings

Error: Service times out on stop (SIGKILL after TimeoutStopSec)
  # Increase TimeoutStopSec=
  # Check ExecStop= handles shutdown properly
  # Use KillMode=mixed for worker processes

Error: User lingering not working
  # loginctl enable-linger USER
  # ls /var/lib/systemd/linger/   # Should contain user file
  # Check XDG_RUNTIME_DIR is set

Error: journalctl "No journal files found"
  # Check /etc/systemd/journald.conf: Storage=persistent
  # mkdir -p /var/log/journal
  # systemctl restart systemd-journald

Error: Timer not firing
  # systemctl list-timers TIMER
  # systemctl status TIMER.timer
  # Check Persistent=true for missed runs
  # journalctl -u TIMER.service  # Check last execution log
