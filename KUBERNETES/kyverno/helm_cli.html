⎈ Helm Base Command

The Helm base command and its global configuration. Helm is the package manager for Kubernetes that helps you define, install, and upgrade applications on your cluster. The anihpj/jobpost project uses Helm to manage all Kubernetes deployments.

helm — The Kubernetes Package Manager

CORE Helm CLI Package Manager Fundamental

The Kubernetes package manager — define, install, and upgrade even the most complex Kubernetes applications

helm is the Kubernetes package manager. It helps you manage Kubernetes applications — Helm Charts — which are pre-configured Kubernetes resources. Charts are easy to create, version, share, and publish. Helm uses a packaging format called charts — a collection of files that describe a related set of Kubernetes resources.

For the anihpj/jobpost project, helm is used for:

  • Deploying the jobpost Django application with all its dependencies (PostgreSQL, Redis, Nginx)
  • Managing releases across staging and production environments with values-*.yaml overrides
  • Versioning the entire application stack through Chart.yaml and Chart.lock
  • Rolling back failed deployments instantly with helm rollback
  • Packaging and distributing the jobpost chart via charts.anihpj.io

Syntax

helm [command] [flags]

Global Options

CONFIG Helm CLI Global Flags Configuration

Global flags that apply to every Helm command — control Kubernetes connectivity, output formatting, and caching

Helm global options are flags that apply to every Helm command. They control how Helm connects to Kubernetes, formats output, and manages local cache and configuration. These flags are inherited by all subcommands and can be set via command-line flags or environment variables.

For the anihpj/jobpost project, global options are used for:

  • Setting the Kubernetes context with --kube-context to switch between staging and production clusters
  • Specifying the target namespace with --namespace for environment isolation
  • Enabling debug output with --debug when troubleshooting failed deployments
  • Configuring the registry for OCI-based chart storage with --registry-config

Syntax

helm [command] [--global-flag=VALUE]...

# Common global patterns in anihpj:
helm install jobpost ./charts/jobpost --namespace production --kube-context anihpj-prod
helm list --namespace staging --kube-context anihpj-staging
helm upgrade jobpost ./charts/jobpost --debug --namespace production

helm dependency build

BUILD Dependency Management Reproducible Builds

Rebuild the charts/ directory based on the Chart.lock file — reproducible dependency resolution

helm dependency build reconstructs the charts/ directory to match the exact versions recorded in Chart.lock. Unlike update, it does NOT re-negotiate versions — it builds exactly what the lock file specifies. If no lock file exists, it mirrors update behavior.

This is the command for reproducible builds: every developer and CI pipeline gets the same dependencies. Always use build after cloning a repository or in CI/CD — never use update in automated pipelines unless you intend to change dependency versions.

helm dependency build CHART [flags]

helm install

DEPLOY Install & Upgrade Core Operation

Install a chart — deploy a Helm release to the Kubernetes cluster

helm install is the primary deployment command. It takes a chart (from a repo, local path, URL, or OCI registry) and installs it as a named release on the Kubernetes cluster. Six ways to specify the chart: chart reference (bitnami/postgresql), packaged chart (.tgz), unpacked directory, absolute URL, --repo flag, or OCI registry.

For the anihpj/jobpost project, helm install deploys the jobpost Django application with PostgreSQL, Redis, and Nginx to staging and production namespaces with environment-specific values files.

Syntax

helm install [NAME] [CHART] [flags]

# Six ways to specify a chart:
helm install mydb bitnami/postgresql                    # Chart reference
helm install myapp ./nginx-1.2.3.tgz                    # Packaged chart
helm install myapp ./nginx/                             # Unpacked directory
helm install myapp https://example.com/charts/nginx.tgz # Absolute URL
helm install myapp nginx --repo https://example.com     # --repo flag
helm install myapp oci://example.com/charts/nginx       # OCI registry

Parameters

FlagDescription
-f, --valuesSpecify values in a YAML file or URL (can specify multiple; last takes priority)
--setSet values on command line (key1=val1,key2=val2; last takes priority)
--set-stringSet STRING values (forces string type)
--set-jsonSet JSON values (objects/arrays from command line)
--set-fileSet values from file contents
-g, --generate-nameAuto-generate release name (omit NAME parameter)
--dry-runSimulate install without persisting (client/server)
--debugEnable verbose output for troubleshooting
--create-namespaceCreate the release namespace if not present
--dependency-updateUpdate dependencies before installing
--waitWait until resources are ready (up to --timeout)
--timeoutTime to wait for Kubernetes operations (default: 5m0s)

--verifyVerify the package signature before installing

--post-rendererPost-renderer plugin to modify rendered manifests
--hide-secretHide Secrets in --dry-run output
--disable-openapi-validationSkip OpenAPI schema validation
--skip-crdsSkip CRD installation (CRDs installed by default if not present)
--take-ownershipTake ownership of existing resources (ignores helm annotations)

Return Value

Exit CodeDescription
0Success — release installed and deployed
1Error — chart not found, values invalid, or Kubernetes API error
💡 Key Concept — Values Priority: Multiple --values and --set flags can be combined. The last (right-most) value takes priority. Priority order: default values.yaml → parent chart values → first -f file → last -f file → each --set flag (last wins). Use --dry-run --debug to preview computed values. --set-json supports JSON objects/arrays: --set-json 'master.sidecars=[{"name":"sidecar"}]'.

helm upgrade

Upgrade a release to a new version of a chart — update configuration, chart version, or both

helm upgrade upgrades an existing release to a new chart version or with new configuration values. It supports the same value override mechanisms as install: --values, --set, --set-string, --set-json, and --set-file. Use --reuse-values to keep existing values and only apply specific changes.

Syntax

helm upgrade [RELEASE] [CHART] [flags]

# Common patterns:
helm upgrade jobpost-prod /lpj/charts/jobpost/ -f values-prod.yaml
helm upgrade jobpost-prod /lpj/charts/jobpost/ --set replicaCount=5
helm upgrade jobpost-prod /lpj/charts/jobpost/ --reuse-values --set image.tag=v3.4.0

Parameters

FlagDescription
-f, --valuesSpecify values in a YAML file (last takes priority)
--set / --set-string / --set-jsonOverride values from command line
--reuse-valuesKeep all existing values, only apply new overrides
--reset-valuesReset to chart defaults before applying new values

helm rollback

REVERT Install & Upgrade Recovery

Roll back a release to a previous revision — instant disaster recovery for failed deployments

helm rollback reverts a release to a previous revision. It's Helm's most powerful disaster recovery tool — a single command undoes a bad deployment. If the revision number is omitted or set to 0, it rolls back to the previous release. Use helm history to see available revisions.

Syntax

helm rollback  [REVISION] [flags]

helm rollback jobpost-prod          # Roll back to previous revision
helm rollback jobpost-prod 12       # Roll back to specific revision 12

Parameters

FlagDescription
REVISIONRevision number to roll back to (0 or omitted = previous)
--dry-runSimulate rollback without applying
--waitWait until resources are ready
--timeoutTime to wait for operations (default: 5m0s)
--history-maxMax revisions to keep (default: 10)

Return Value

Exit CodeDescription
0Success — release rolled back
1Error — revision not found or Kubernetes API error
💡 Key Concept: Rollback creates a NEW revision (e.g., rolling back from 13→12 creates revision 14 that replicates revision 12's configuration). The original revision 13 remains in history for auditing. Rollback is NOT a destructive operation — it's just another deployment using previous configuration.

📄 Context — Emergency Rollback:

# Carol's post-upgrade checklist:
# 1. Check pod status: kubectl get pods -n production
# 2. Check logs: kubectl logs -l app=jobpost -n production --tail=50
# 3. If errors detected: helm rollback jobpost-prod
# 4. Verify with: helm history jobpost-prod
Example 1: Rollback to Previous Revision

Scenario: Carol discovers a bug immediately after upgrading and rolls back to the previous working revision.

Command:

helm rollback jobpost-prod -n production && helm history jobpost-prod -n production | tail -3

Output:

Rollback was a success! Happy Helming! 12 Fri Jun 6 08:00 superseded jobpost-2.3.1 v3.2.1 Upgraded 13 Fri Jun 6 09:00 superseded jobpost-2.4.0 v3.4.0 Upgraded (failed) 14 Fri Jun 6 09:05 deployed jobpost-2.3.1 v3.2.1 Rollback to 12

📝 What happened: Revision 14 was created as a rollback to revision 12. Revision 13 (the failed upgrade) is preserved in history for analysis. The application is now running the previous stable version. Total recovery time: ~5 seconds. This is Helm's killer feature for production safety.

Example 2: Rollback to Specific Revision

Scenario: Alice identifies that revision 10 was the last known-good version and rolls back specifically to it.

Command:

📝 What happened: Alice skipped revision 9 and went directly to revision 10 — the last confirmed-good deployment. helm history helps identify which revision to target. Always verify the rollback target with helm history before executing.

Example 3: Dry-Run Rollback Before Executing

Scenario: Carol previews what a rollback will change before committing.

Command:

📝 What happened: --dry-run confirms the rollback would succeed without actually executing. Always dry-run in production. While rollback is safe (it creates a new revision), verifying first gives confidence before touching production.

Example 4: Rollback with Wait for Readiness

Scenario: Carol rolls back and waits for all resources to become ready before confirming recovery.

Command:

📝 What happened: --wait ensures the rollback is fully applied before the command returns. The && echo only executes after all pods are ready. This is essential for automated recovery scripts — don't assume a rollback is complete just because the command exited.

💡 Helm Pro Tip: Rollback is Helm's superpower — it creates a new revision (never destroys history). Use helm history to find the right revision. Always --dry-run first in production. Set --history-max to keep enough revisions for meaningful rollback. Auto-rollback in CI/CD with --atomic or explicit || rollback.
