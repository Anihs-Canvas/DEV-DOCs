1.1 Kubernetes Networking Fundamentals (Q1-Q10)

Architecture Q1 of 200
What are the four fundamental Kubernetes networking rules that every CNI plugin must satisfy?
A) Each Pod gets its own IP. Pods can communicate across nodes without NAT. Node agents can communicate with all pods on that node. Pods communicate without NAT between each other.
B) All pods share the node IP. Pods communicate through NAT. Services use iptables. DNS is optional.
C) Pods use host networking by default. CNI creates overlay networks only. Containers share pod IP.
D) Each container gets a unique IP. Pods on different nodes always need NAT. Services replace DNS.
✅ Correct Answer: A

The four fundamental rules: (1) Every pod gets its own unique IP address, (2) Pods on a node can communicate with all pods on all nodes without NAT, (3) Agents on a node (like kubelet) can communicate with all pods on that node, (4) Pods can communicate with each other without Network Address Translation.

📝 Detailed Explanation
The 4 Fundamental K8s Networking Rules
  RULE 1                    RULE 2                    RULE 3                    RULE 4
  ┌─────────────────┐      ┌─────────────────┐      ┌─────────────────┐      ┌─────────────────┐
  │ Each Pod gets   │      │ Pods can talk   │      │ Node agents     │      │ No NAT between  │
  │ its OWN IP      │      │ across nodes    │      │ can reach all   │      │ pods            │
  │                 │      │ WITHOUT NAT     │      │ pods on node    │      │                 │
  │ Pod A: 10.0.1.5│      │ 10.0.1.5 ───►  │      │ kubelet ───►   │      │ 10.0.1.5 ───►  │
  │ Pod B: 10.0.1.6│      │   10.0.2.9     │      │   10.0.1.5     │      │   10.0.2.9     │
  │ Pod C: 10.0.2.9│      │ (same IP seen) │      │ (direct access)│      │ (source IP     │
  └─────────────────┘      └─────────────────┘      └─────────────────┘      │  preserved)    │
                                                                             └─────────────────┘
  ✅ Cilium: eBPF O(1) hash maps    ❌ Legacy: iptables O(n) rule walking

These rules are the foundation of Kubernetes networking. Rule 1 means each pod has a routable IP — unlike Docker where containers share the host IP. Rule 2 is WHY CNI plugins exist: they must set up routes so pod IPs are reachable cross-node. Rule 3 enables health checks and readiness probes. Rule 4 preserves source IPs for NetworkPolicy enforcement. Cilium implements all four using eBPF instead of iptables/overlays, providing O(1) performance at scale.

Architecture Q2 of 200
What is the primary role of a CNI (Container Network Interface) plugin in Kubernetes?
A) Managing container storage volumes and persistent volume claims
B) Allocating IP addresses to pods and setting up network routes so pods can communicate across nodes
C) Providing DNS resolution for Kubernetes services and external domains
D) Managing authentication and RBAC for pod-to-pod communication
✅ Correct Answer: B

The CNI plugin's core job is IPAM (IP Address Management) — assigning each pod a unique IP — and establishing network routes so those IPs are reachable from any node in the cluster.

📝 Detailed Explanation

CNI is called by the kubelet at pod creation time (CMD_ADD) and deletion time (CMD_DEL). The CNI spec defines a simple JSON config file in /etc/cni/net.d/. When a pod is created, kubelet calls the CNI binary which: (1) allocates an IP from the pod CIDR range, (2) creates a veth pair connecting the pod namespace to the host, (3) configures routes so the pod IP is reachable. Cilium's CNI does this via eBPF — allocating IPs through its IPAM and creating eBPF-based routes instead of iptables rules.

Architecture Q3 of 200
How does a Kubernetes Service provide stable networking for pods that are constantly being created and destroyed?
A) Services create static IP addresses for each pod that never change
B) Services use DNS round-robin that updates instantly when pods change
C) Services provide a stable virtual IP (ClusterIP) and use label selectors to automatically discover matching pods, with kube-proxy or Cilium handling the traffic routing
D) Services create a dedicated proxy container for each application to handle routing

Services get a stable virtual IP (ClusterIP) that never changes, even as pods come and go. Label selectors match pods to the service, and kube-proxy (or Cilium's eBPF) handles the actual traffic routing to backend pods.

Architecture Q4 of 200
What is the difference between overlay networking and native routing in Kubernetes?
A) Overlay is for cloud only; native routing is for bare metal only
B) Overlay encapsulates pod traffic inside another protocol (VXLAN/Geneve) so the physical network doesn't need pod routes; native routing adds pod CIDR routes directly to the network
C) Overlay is faster than native routing; native routing is more secure than overlay
D) Overlay uses eBPF; native routing uses iptables. They cannot be used together.
✅ Correct Answer: B

Overlay encapsulates pod traffic inside VXLAN or Geneve tunnels, hiding pod IPs from the physical network. Native routing adds actual pod CIDR routes to the network's routing table so routers can forward pod traffic directly.

📝 Detailed Explanation

Overlay (VXLAN/Geneve): Pod packet is wrapped in another IP+UDP header. The outer header uses node IPs that the physical network understands. Advantage: works on any network without reconfiguration. Disadvantage: ~50 bytes overhead per packet, slight CPU cost for encap/decap. Native routing: Pod CIDR routes are added to the network (via BGP or static routes). Physical routers forward pod traffic directly. Advantage: no encapsulation overhead, better performance. Disadvantage: requires the network to know about pod IPs — usually needs BGP. Cilium supports both modes: tunnel mode (VXLAN/Geneve) and native routing mode (with or without BGP).

Architecture Q5 of 200
In a Kubernetes cluster with Cilium, how does a pod on node-1 (IP 10.0.1.5) send a packet to a pod on node-2 (IP 10.0.2.9) using VXLAN tunnel mode?
A) Pod-1 sends to node-2 IP directly. Node-2 NATs to pod-2 IP.
B) Pod-1 sends to 10.0.2.9. Cilium eBPF on node-1 encapsulates the packet in VXLAN with outer dst=node-2 IP. Node-2 Cilium decapsulates and delivers to pod-2.
C) Pod-1 sends to kube-proxy which creates an iptables DNAT rule to pod-2 IP.
D) Pod-1 sends to the service ClusterIP which then routes to pod-2 through the API server.
✅ Correct Answer: B

In VXLAN tunnel mode, Cilium's eBPF programs on the source node encapsulate the original packet inside a VXLAN header with the destination node's IP. The destination node decapsulates and delivers to the target pod.

📝 Detailed Explanation
VXLAN Tunnel — Step-by-Step Packet Walk
  STEP 1: Pod-1 sends packet           STEP 2: Cilium eBPF on node-1
  ┌────────────────────────┐           ┌──────────────────────────────┐
  │ anihpj-web pod         │           │ TC ingress on veth (host)    │
  │ eth0: 10.0.1.5         │           │ • Lookup dst 10.0.2.9        │
  │                        │           │ • Found: pod-2 on node-2     │
  │ Src: 10.0.1.5          │           │ • Node-2 IP: 192.168.1.2     │
  │ Dst: 10.0.2.9 ─────────┼──►        │ • Encapsulate in VXLAN!      │
  └────────────────────────┘           └──────────────┬───────────────┘
                                                      │
  STEP 3: Physical network routes     STEP 4: Cilium eBPF on node-2   STEP 5: Deliver
  ┌──────────────────────────────┐    ┌──────────────────────────────┐ ┌──────────────┐
  │ VXLAN packet:                │    │ VXLAN interface (cilium_vxlan)│ │ anihpj-api   │
  │ Outer: 192.168.1.1→.1.2      │──► │ • Decapsulate VXLAN          │ │ pod          │

  └──────────────────────────────┘    └──────────────────────────────┘ └──────────────┘
  
  ⚡ All in kernel via eBPF — no userspace proxying! < 1ms overhead.

The packet flow: (1) Pod-1 sends packet with src=10.0.1.5, dst=10.0.2.9 via its veth. (2) Cilium's eBPF TC program on the veth sees the packet and looks up the destination. (3) It finds pod-2 is on node-2 and encapsulates in VXLAN. (4) The physical network routes this to node-2. (5) Node-2 decapsulates and delivers to pod-2.

Architecture Q7 of 200
How does CoreDNS provide service discovery in Kubernetes?
A) CoreDNS watches pod IPs and creates /etc/hosts entries in every pod
B) CoreDNS watches the Kubernetes API for Services and Pods, and responds to DNS queries with ClusterIPs for services and pod IPs for headless services
C) CoreDNS is an external DNS service that requires manual configuration for each service
D) CoreDNS replaces kube-proxy and handles all service traffic routing
✅ Correct Answer: B

CoreDNS watches the Kubernetes API server for Services and Pods, automatically creating DNS records. A service `anihpj-api` in namespace `anihpj` gets the FQDN `anihpj-api.anihpj.svc.cluster.local` resolving to its ClusterIP.

📝 Detailed Explanation

CoreDNS runs as a Deployment in kube-system and uses the `kubernetes` plugin to watch the API server. For every Service, it creates: (1) An A/AAAA record for the service name → ClusterIP, (2) SRV records for named ports. For headless services (clusterIP: None), it returns pod IPs directly. DNS is critical — if CoreDNS is blocked by a NetworkPolicy, pods cannot resolve service names. Cilium can enforce DNS-based policies (toFQDNs) that integrate with CoreDNS responses for identity-aware filtering of external domains.

Architecture Q9 of 200
Why is iptables-based kube-proxy considered problematic at scale (5000+ services)?
A) iptables cannot handle UDP traffic, only TCP
B) iptables rules are evaluated sequentially (O(n) complexity) — with 5000 services, every packet may traverse 5000+ rules. Rule updates take 30+ seconds and connection tracking tables overflow
C) iptables requires a kernel module that is deprecated since Linux 5.0
D) iptables can only handle 100 services maximum before crashing the kube-proxy process
✅ Correct Answer: B

iptables walks rules sequentially — every packet must traverse all matching rules. With thousands of services, this becomes extremely slow (O(n) vs Cilium's O(1)). Rule updates are also expensive and cause connection tracking table pressure.

📝 Detailed Explanation
Aspectiptables kube-proxyCilium eBPF KPR
LookupO(n) — walks ALL rules sequentiallyO(1) — single hash map lookup
10k ServicesEvery packet traverses 10,000+ rulesSame single lookup regardless of count
Rule Updates30+ seconds to update iptablesInstant — atomic BPF map swap

Cilium's KPR solves all three problems: (1) eBPF hash maps provide O(1) backend lookup regardless of service count, (2) eBPF programs at the socket layer intercept connect() before the TCP stack — no iptables traversal, (3) Maglev consistent hashing ensures even backend distribution.

Architecture Q10 of 200
What is a veth (virtual ethernet) pair and how is it used in Kubernetes pod networking?
A) A veth pair is a virtual switch that connects multiple pods on the same node
B) A veth pair is a pair of connected virtual network interfaces — one end goes into the pod's network namespace (as eth0), the other stays in the host namespace. It acts like a virtual cable connecting the pod to the host
C) A veth pair is a virtual ethernet bridge used exclusively by the Docker runtime
D) A veth pair is a Kubernetes resource that defines virtual host-to-pod routing rules
✅ Correct Answer: B

A veth pair is like a virtual Ethernet cable — one end in the pod (`eth0`), the other end in the host namespace (named something like `lxcXXXX`). Packets sent through one end appear on the other.

What happens when a Cilium agent restarts? Do existing connections survive?

📦 A1 — A5: Pod-to-Pod Communication Failures

🔴 5 Most Likely Causes
  1. Veth pair disconnected or missing: Check ip link show lxc_<endpoint-id>. The virtual ethernet to the pod may not exist or be DOWN. Run cilium endpoint list.
  2. BPF datapath not attached: Run cilium-dbg endpoint config <ep-id>. Look for "Conntrack: Enabled" and "Policy: Enforced". If the BPF program is detached, packets drop.
  3. NetworkPolicy denial: A default-deny CiliumNetworkPolicy may be silently dropping same-node traffic. Run hubble observe --from-pod ns/pod-a --to-pod ns/pod-b --verdict DROPPED.
  4. Pod CIDR conflict: Two pods on the same node may have duplicate IPs. Check kubectl get pod -o wide for duplicate PodIP entries.
  5. Cilium agent endpoint sync stalled: The agent may not have registered the pod endpoint. Run cilium endpoint get <ep-id> and check state is "ready".
🟡 5 Less Likely Causes
  1. Kernel BPF verifier rejecting program on load
  2. eBPF map (cilium_ipcache) corruption causing wrong identity lookup
  3. Conntrack table full — net.netfilter.nf_conntrack_max reached
  4. iptables rule left over from previous CNI intercepting traffic
  5. ARP/NDP cache poisoning from a misconfigured neighbor entry
🟣 5 New Cluster Causes
  1. Cilium not fully installed: Agent pod may still be in CrashLoopBackOff. Check kubectl get pods -n kube-system -l k8s-app=cilium.
  2. Wrong CNI conflist: /etc/cni/net.d/05-cilium.conflist may point to wrong socket. Verify with cat /etc/cni/net.d/05-cilium.conflist.
  3. Container runtime not using Cilium: containerd/cri-o config may still reference old CNI. Check containerd config.toml for plugins.cni.
  4. Kubelet CNI args mismatch: --network-plugin=cni --cni-conf-dir=/etc/cni/net.d may be wrong. Check kubelet flags.
  5. Cilium ConfigMap not propagated: Run kubectl get cm -n kube-system cilium-config -o yaml and verify values match expected.
🔍 What to Look At / Take Note Of: cilium endpoint list output -- state must be "ready". Check ip link show lxc_* for veth pairs. cilium-dbg bpf policy get <id> shows if BPF programs are attached. Note: same-node failures are the rarest Cilium issue -- usually a recent CNI change.
🔧 How to Solve:

1. cilium endpoint list — find the endpoint ID for both pods
2. cilium-dbg endpoint config <id> — verify BPF programs are attached
3. cilium-dbg bpf policy get <id> — check if policies are denying
4. ip link show lxc_<id> — verify veth is UP
5. If all good, restart Cilium agent: kubectl -n kube-system delete pod -l k8s-app=cilium --field-selector spec.nodeName=node-1

💡 Personal Advice: Same-node failures are rare with Cilium — the BPF datapath is very reliable. When they happen, it is usually a recent CNI config change or a policy change. Always run cilium connectivity test first — it catches same-node issues immediately. For anihpj: keep a simple allow-all CNP in your dev namespace so you can isolate whether it is a policy vs. datapath issue.

🟢 CATEGORY 1: ARCHITECTURE — Issue A2
Pod Cannot Reach Another Pod on DIFFERENT Node

🔍 Symptom: anihpj-web pod on node-1 (IP 10.0.1.5) cannot ping anihpj-api pod on node-2 (IP 10.0.2.9). Same-node pod communication works fine.

  Node-1 (10.0.1.0/24)                 Node-2 (10.0.2.0/24)
  ┌─────────────────────┐              ┌─────────────────────┐
  │ anihpj-web 10.0.1.5 │———— ❌ ————→ │ anihpj-api 10.0.2.9 │
  │ ✅ local pods work   │              │ ✅ local pods work   │
  └─────────────────────┘              └─────────────────────┘
🔴 5 Most Likely Causes
  1. VXLAN/Geneve tunnel not established: Run cilium status | grep Encapsulation. Check ip link show cilium_vxlan or ip link show cilium_geneve. Must be UP.
  2. Cross-node route missing: In native routing mode, each node needs routes to other pods. Run ip route | grep 10.0.2. Should show route via node-2 IP.
  3. Firewall blocking VXLAN/UDP 8472 or Geneve/UDP 6081: Check cloud security groups, host firewall. Run nc -u <node-2-ip> 8472 from node-1.
  4. MTU blackhole: VXLAN overhead (50 bytes) reduces effective MTU. Packets > 1450 may get silently dropped. Test: ping -M do -s 1400 10.0.2.9.
  5. Identity mismatch across nodes: Cilium uses numeric identities. If identity sync fails, packets may be dropped. Run cilium identity list on both nodes.
🟡 5 Less Likely Causes
  1. Cilium agent running different versions on nodes (identity format mismatch)
  2. BPF tunnel map (cilium_tunnel_map) corrupted
  3. Kernel module vxlan not loaded: lsmod | grep vxlan
  4. ARP cache stale on node-1 for node-2 after IP change
  5. Network fabric dropping fragmented UDP (VXLAN with large payloads)
🟣 5 New Cluster Causes
  1. Tunnel mode not configured: Check cilium config | grep tunnel. Default is "vxlan". Ensure all nodes agree.
  2. Node ports not open in firewall: 8472/UDP (VXLAN) or 6081/UDP (Geneve). Check iptables/security groups.
  3. Pod CIDR ranges not unique per node: Check cilium config | grep cluster-pool-ipv4-cidr and node CIDRs via kubectl get ciliumnodes.
  4. cilium-operator not running: Operator assigns per-node CIDRs. Check kubectl get pods -n kube-system -l name=cilium-operator.
  5. BPF Host Routing not enabled: On new kernels (5.10+), enable with cilium config set bpf-host-routing true for performance.
🔍 What to Look At / Take Note Of: ip link show cilium_vxlan -- interface MUST be UP. Cloud security groups MUST allow UDP 8472 (VXLAN) or 6081 (Geneve) between ALL worker nodes. MTU: if using VXLAN, packets > 1450 bytes get fragmented. cilium-health status is the fastest cross-node check.
🔧 How to Solve:

1. cilium connectivity test — identifies which cross-node scenarios fail
2. hubble observe --from-pod ns/pod-a --to-pod ns/pod-b — see where packets die
3. ip link show cilium_vxlan — tunnel must be UP on both nodes
4. For MTU: cilium config set mtu 1400 (or use auto-detection: cilium config set mtu auto)
5. For routing: ensure node-1 has ip route add 10.0.2.0/24 via <node-2-ip>

💡 Personal Advice: Cross-node failures are the #1 post-install issue. MTU is the silent killer — packets look like they should work but get dropped silently at the fabric level. For anihpj running in AWS: VXLAN + AWS VPC = effective MTU of ~8950 for jumbo frames, so if you are using standard 1500, you are fine. The issue is almost always the security group not allowing UDP between worker nodes.

🟢 CATEGORY 1: ARCHITECTURE — Issue A3
Pod-to-Pod Latency Spikes (>100ms for Same-Region Nodes)

🔍 Symptom: anihpj-api responds with latency spikes — sometimes 2ms, sometimes 300ms. Intermittent. No packet loss visible with ping. Hubble shows forwarded packets.

🔴 5 Most Likely Causes
  1. BPF conntrack table full: Each connection needs a conntrack entry. Full table = slow GC. Run cilium-dbg bpf ct list global | wc -l. If > 500k, investigate.
  2. eBPF map contention: Under high connection churn, BPF map locks cause tail latency. Check with cilium-dbg map events for map pressure metrics.
  3. Node CPU throttling: Cilium agent competes for CPU. Check kubectl top pod -n kube-system -l k8s-app=cilium. Agent should have guaranteed CPU.
  4. L7 proxy (Envoy) bottleneck: If L7 policies are applied, every new flow goes through Envoy. Check cilium status | grep "L7 Proxy". Envoy may need more resources.
  5. DNS resolution delays: Every new connection triggers DNS if toFQDNs policies are used. Check CoreDNS latency: kubectl logs -n kube-system -l k8s-app=kube-dns.
🟡 5 Less Likely Causes
  1. Kernel lock contention on vxlan/veth path under load
  2. Hubble exporting flows to slow backend causing buffer backpressure
  3. SELinux/AppArmor auditing every BPF syscall (check auditd logs)
  4. Transparent encryption (WireGuard/IPSec) key rotation happening mid-flow
  5. Network fabric ECMP rebalancing causing packet reordering
🟣 5 New Cluster Causes
  1. Cilium agent resource limits too low: Default requests may be too small for production. Increase CPU/memory limits in Helm values.
  2. Hubble enabled without relay: Hubble exports flows to nowhere, filling buffers. Disable if not needed: helm upgrade cilium cilium/cilium --set hubble.enabled=false.
  3. No resource limits on noisy neighbor pods: Other pods starving Cilium agent of CPU. Set QoS Guaranteed for Cilium.
  4. WireGuard encryption enabled on underpowered nodes: WireGuard adds ~5-10% CPU overhead. Ensure nodes have AES-NI support.
  5. iptables rules still active from kube-proxy: If KPR is partial, some traffic still hits iptables (slow path). Check cilium status | grep KubeProxyReplacement.
🔍 What to Look At / Take Note Of: cilium-dbg bpf ct list global | wc -l -- conntrack > 100k on a node is a red flag. Default GC interval is 5 min (too slow for high-churn). cilium-dbg monitor --type drop shows retransmissions. Envoy proxy at :9090/metrics for L7 latency.
🔧 How to Solve:

1. Profile with Hubble: hubble observe -o json | jq ".flow.latency" to find the hop adding latency
2. Check BPF maps: cilium-dbg bpf ct list global | tail -20 — look for CLOSING entries accumulating
3. Increase conntrack GC: cilium config set conntrack-gc-interval 30s
4. Scale Envoy if L7 proxy is the bottleneck: increase hubble.ui.replicas and proxy resources
5. Use cilium-dbg monitor --type drop to see if packets are being retransmitted due to drops

💡 Personal Advice: Tail latency in BPF datapath is almost always conntrack GC pressure. The default conntrack GC interval of 5 minutes is too long for high-churn workloads. Reduce it to 30s. For anihpj specifically: if you use toFQDNs policies referencing external APIs (like AWS RDS endpoints), every FQDN lookup adds DNS latency. Cache those IPs in CiliumCIDRGroup instead.

🟢 CATEGORY 1: ARCHITECTURE — Issue A4
Packet Drops Between Pods in Different Namespaces

🔍 Symptom: anihpj-web (namespace: anihpj) cannot reach postgres (namespace: database). Same-namespace communication works. The packets are dropped with POLICY_DENIED verdict.

🔴 5 Most Likely Causes
  1. NetworkPolicy with namespaceSelector mismatch: If a CNP selects pods via namespaceSelector, verify labels exist. Run kubectl get ns anihpj --show-labels.
  2. Default deny policy in either namespace: Check kubectl get cnp -A | grep "default-deny". A deny-all in either namespace blocks cross-namespace traffic.
  3. Ingress policy missing on destination: CiliumNetworkPolicy must have an ingress rule allowing the source. Ingress is always evaluated at the destination endpoint.
  4. Wrong entity type in policy: Using fromEndpoints instead of fromEntities for cluster-internal traffic. fromEntities: [cluster] may be needed.
  5. DNS policy blocking namespace discovery: If toFQDNs rule references a service name, DNS resolution may fail if DNS is denied for the source namespace.
🟡 5 Less Likely Causes
  1. CiliumNetworkPolicy and Kubernetes NetworkPolicy conflict (union behavior)
  2. Proxy redirection for L7 taking >5s timeout on first packet
  3. Cilium identity for namespace stuck in "deleting" state
  4. CNP applied to wrong cluster with CCNP (CiliumClusterwideNetworkPolicy)
  5. FQDN policy caching stale IP after pod restart in target namespace
🟣 5 New Cluster Causes
  1. No policies configured at all: In a new cluster with no CNPs, all traffic is allowed. If you see DENIED, a policy exists somewhere. Run cilium policy get.
  2. Namespace labels not yet applied: Namespace selector policies may fail if labels are missing. Example: kubectl label ns database app=db.
  3. Imported policies from another cluster (Cluster Mesh): If Cluster Mesh is active, policies from another cluster may apply. Check with cilium policy selectors.
  4. Policy audit mode enabled: Traffic is allowed but logged as DENIED for audit. Check hubble observe --verdict DROPPED — if audit mode, flow still succeeds.
  5. Wrong CNP API version: CiliumNetworkPolicy requires apiextensions.k8s.io/v1 CRDs. Run kubectl api-resources | grep cilium.
🔍 What to Look At / Take Note Of: CiliumNetworkPolicy + Kubernetes NetworkPolicy use UNION semantics -- a KNP ALLOW + CNP DENY = ALLOW. cilium policy trace ALWAYS shows the truth. Namespace labels are NOT set by default. Check BOTH namespaces for default-deny policies.
🔧 How to Solve:

1. cilium policy trace --src-k8s-pod anihpj:anihpj-web-xxx --dst-k8s-pod database:postgres-yyy --dport 5432 — shows which policy rule matches
2. hubble observe --from-pod anihpj/anihpj-web-xxx --to-pod database/postgres-yyy --verdict DROPPED — see the exact drop reason
3. Verify namespace labels: kubectl get ns anihpj database -o yaml | grep labels -A5
4. Check all CNPs: kubectl get cnp,ccnp -A — a CCNP may apply cluster-wide
5. Use audit mode to test: apply policy with --set policyAuditMode=true to log without blocking

💡 Personal Advice: Cross-namespace policy debugging is the #1 time sink in Cilium. Always use cilium policy trace before writing policies — it tells you exactly which rule matches. For anihpj: create a dedicated "allow-all-within-anihpj" CNP first, then add restrictive rules one by one. The union behavior of CiliumNetworkPolicy + Kubernetes NetworkPolicy catches everyone off guard — a KNP allow + CNP deny = ALLOW (union wins).

🟢 CATEGORY 1: ARCHITECTURE — Issue A5
WireGuard/Transparent Encryption Breaking Pod Communication

🔍 Symptom: After enabling WireGuard encryption, some cross-node pod pairs cannot communicate. Hubble shows packets forwarded but never arrive. Encryption status shows "Enabled" but partial.

  Node-1                          Node-2
  ┌──────────┐                    ┌──────────┐
  │ WG Key A │—— secure tunnel ——→│ WG Key B │
  │ OK ✅    │                    │ ❌ FAIL   │
  └──────────┘                    └──────────┘
  Node-1 has key for Node-2, but Node-2 does NOT have key for Node-1
  Result: traffic flows one-way only
🔴 5 Most Likely Causes
  1. Missing kernel module: WireGuard needs wireguard kernel module. Run lsmod | grep wireguard. If missing: modprobe wireguard.
  2. Node-to-node key exchange failed: Cilium uses kube-apiserver to exchange WireGuard public keys. Check cilium-dbg encrypt status — shows per-node key state.
  3. WireGuard port (51871/UDP) blocked: The default WireGuard port must be open between all nodes. Check firewall rules and security groups.
  4. MTU not adjusted for WireGuard overhead: WireGuard adds ~60 bytes overhead. With VXLAN + WireGuard, MTU should be 1400 or lower. Test: ping -M do -s 1380 <target>.
  5. Encryption enabled only on some nodes: Node restart may have missed the encryption config. Check cilium config | grep enable-wireguard on ALL nodes.
🟡 5 Less Likely Causes
  1. WireGuard key rotation in progress — new key not propagated to all nodes yet
  2. Node-2 agent restarted and lost in-memory peer table (requires full resync)
  3. WireGuard kernel bug with certain kernel versions (check compat matrix)
  4. Encryption key stored in k8s secret deleted accidentally
  5. Node IP changed but WireGuard peer still uses old IP
🟣 5 New Cluster Causes
  1. WireGuard not enabled in Helm: Must set encryption.enabled=true and encryption.type=wireguard or cilium install --set encryption.type=wireguard.
  2. Kernel too old: WireGuard requires kernel 5.6+. Check uname -r. On older kernels, install wireguard-dkms.
  3. Node-to-node connectivity via pod CIDR, not node IP: WireGuard tunnels use node IPs, not pod IPs. Verify nodes can reach each other on their primary IPs.
  4. cilium-operator not deployed: Operator manages key rotation. Must be running.
  5. Encryption strict mode causing ALL traffic to drop if any node lacks keys: Check with cilium config | grep encryption-strict-mode.
🔍 What to Look At / Take Note Of: WireGuard uses UDP port 51871 by default. Kernel module wireguard must be loaded on ALL nodes. MTU for VXLAN+WireGuard: 1400 (1500 - 50 VXLAN - 60 WG). cilium-dbg encrypt status shows per-node key state. One-way encryption = missing key on one side.
🔧 How to Solve:

1. cilium-dbg encrypt status — shows per-node encryption state and key count
2. kubectl get ciliumnodes -o yaml | grep -A10 "encryption" — verify keys are stored
3. ip link show cilium_wg0 — WireGuard interface must exist
4. wg show — shows WireGuard peer table directly
5. Restart agent: kubectl -n kube-system rollout restart daemonset cilium

💡 Personal Advice: WireGuard issues are almost always MTU-related or missing kernel modules. On AWS EKS Bottlerocket, WireGuard works out of the box. On Ubuntu, you may need linux-modules-extra-$(uname -r). For anihpj: if you use WireGuard, set MTU to 1400 in your Cilium config AND in your application. Nothing is more confusing than TCP connections that hang because the SYN reaches but the data does not.

🟢 CATEGORY 1: ARCHITECTURE — Issue A6
ClusterIP Service Not Routing to Backend Pods

🔍 Symptom: anihpj-api ClusterIP (10.96.100.50:8080) returns connection refused or timeout. Pods exist and are healthy. Direct pod IP access works fine.

  Client Pod                     ClusterIP Svc                  Backend Pods
  ┌──────────┐     ❌ TIME       10.96.100.50:8080             ┌──────────┐
  │curl svc  │────────────────→  ┌─────────────┐    ✅ OK     │anihpj-api│
  │          │                   │ No backends! │────────────→│ 10.0.1.9 │
  └──────────┘                   └─────────────┘              └──────────┘
  Direct pod IP access works — service selector/labels broken
🔴 5 Most Likely Causes
  1. Service label selector mismatch: Run kubectl describe svc anihpj-api. Compare selector with pod labels: kubectl get pods -l app=anihpj-api. If labels don't match, service has no endpoints.
  2. Endpoints object empty: Check kubectl get endpoints anihpj-api. If no endpoints, the service cannot route. May be caused by pod not being Ready.
  3. Cilium service BPF map not updated: Run cilium-dbg service list | grep anihpj-api. If service is missing from BPF map, agent hasn't synced it. Restart agent.
  4. KPR (kube-proxy replacement) partial mode: In partial KPR, some services still use kube-proxy. Check cilium status | grep KubeProxyReplacement. If "Partial", some services may use iptables path.
  5. NetworkPolicy blocking service traffic: A CNP may block traffic to the service VIP. Run cilium policy trace --src-k8s-pod src:pod --dst-k8s-svc anihpj:anihpj-api --dport 8080.
🟡 5 Less Likely Causes
  1. BPF service map (cilium_services) full — max service entries reached
  2. Maglev backend selection table corruption (KPR strict mode)
  3. Service sessionAffinity causing sticky sessions to dead backends
  4. kube-apiserver watch connection broken — agent missed service create event
  5. Cilium operator overwriting service entries during reconciliation
🟣 5 New Cluster Causes
  1. Service type misconfigured: Check kubectl get svc anihpj-api -o yaml | grep type. Must be ClusterIP (or NodePort/LoadBalancer).
  2. Pods not yet Ready: New pods take time to pass readiness probes. Check kubectl get pods -l app=anihpj-api — all must be 1/1 Ready.
  3. Cilium agent not running on node where backend pods are: Agent must run on every node with pods. Check kubectl get pods -n kube-system -l k8s-app=cilium -o wide.
  4. kube-proxy still running: In KPR strict mode, kube-proxy must be removed. Check kubectl get pods -n kube-system | grep kube-proxy.
  5. DNS not resolving service name: Test with nslookup anihpj-api.anihpj.svc.cluster.local. If DNS fails, check CoreDNS.
🔍 What to Look At / Take Note Of: kubectl get endpoints is the single most important command -- empty endpoints = selector mismatch. Service selector matches pod LABELS (from template), NOT deployment name. BPF service map: cilium-dbg service list. KPR mode matters: Partial may use iptables.
🔧 How to Solve:

1. kubectl get endpoints anihpj-api — must show at least one IP:port pair
2. kubectl describe svc anihpj-api — verify selector matches pod labels exactly
3. cilium-dbg service list | grep anihpj-api — service must appear in BPF map
4. If missing from BPF: cilium-dbg service list to see all services, then kubectl -n kube-system delete pod -l k8s-app=cilium to resync
5. Test with cilium connectivity test — includes service connectivity checks

💡 Personal Advice: Service selector mismatch is the #1 cause. People copy YAML and forget to update labels. Always verify with kubectl get endpoints — if empty, your selector is wrong. For anihpj: the service selector must match the pod template labels in your Deployment, NOT the labels on the Deployment itself. This distinction catches many beginners.

🟢 CATEGORY 1: ARCHITECTURE — Issue A7
DNS Resolution Fails for Kubernetes Services

🔍 Symptom: anihpj-web cannot resolve anihpj-api.anihpj.svc.cluster.local. nslookup returns NXDOMAIN or timeout. Direct IP access works.

🔴 5 Most Likely Causes
  1. CoreDNS pods not running: Check kubectl get pods -n kube-system -l k8s-app=kube-dns. CoreDNS must be Running.
  2. NetworkPolicy blocking DNS (UDP 53): Check hubble observe --to-port 53 --protocol UDP. If DROPPED, CNP is blocking DNS. Add toEndpoints: [{matchLabels: {"k8s-app": "kube-dns"}}] to your policy.
  3. CoreDNS ClusterIP not reachable from pod: Test with kubectl run -it --rm debug --image=busybox -- nslookup anihpj-api.anihpj.svc.cluster.local. If this works but your pod doesn't, it's a policy issue.
  4. Pod DNS config wrong: Check kubectl exec anihpj-web -- cat /etc/resolv.conf. Should have nameserver 10.96.0.10 (CoreDNS ClusterIP) and search anihpj.svc.cluster.local.
  5. toFQDNs policy interfering: A restrictive toFQDNs policy may block DNS for non-matching domains. Check with cilium policy trace.
🟡 5 Less Likely Causes
  1. CoreDNS ConfigMap corrupted — upstream DNS unreachable
  2. DNS cache poisoning from a previous misconfiguration
  3. Hubble DNS visibility interfering (Hubble captures DNS but doesn't block)
  4. Service mesh DNS proxy (Istio/Consul) intercepting DNS requests
  5. NodeLocal DNSCache misconfigured and bypassing CoreDNS
🟣 5 New Cluster Causes
  1. CoreDNS not deployed: Some minimal cluster setups don't include CoreDNS. Check kubectl get svc -n kube-system kube-dns.
  2. CoreDNS ClusterIP changed: If the DNS service IP changes, all pods need restart to pick up the new /etc/resolv.conf.
  3. Pod in different namespace: Short name resolution (anihpj-api) only works within the same namespace. Use FQDN across namespaces.
  4. Cilium L7 DNS proxy enabled but not configured: Check cilium config | grep dns-proxy. If enabled, ensure CoreDNS traffic is allowed.
  5. CNI not setting up pod DNS correctly: Cilium should set /etc/resolv.conf. Check if kubelet --cluster-dns flag is set correctly.
🔍 What to Look At / Take Note Of: DNS is ALWAYS UDP port 53 first, TCP/53 only for large responses. Default-deny policy MUST include DNS allow rule FIRST. Pod /etc/resolv.conf should point to 10.96.0.10 (CoreDNS ClusterIP). Cross-namespace resolution REQUIRES FQDN.
🔧 How to Solve:

1. kubectl get pods -n kube-system -l k8s-app=kube-dns — verify CoreDNS is Running
2. kubectl exec anihpj-web -- nslookup anihpj-api.anihpj.svc.cluster.local 10.96.0.10 — test DNS directly
3. hubble observe --to-port 53 -n anihpj — check if DNS packets are forwarded or dropped
4. If dropped by policy: add DNS allow rule to CNP
5. If CoreDNS is down: kubectl -n kube-system rollout restart deployment coredns

💡 Personal Advice: DNS is the silent dependency everyone forgets. When you create a default-deny NetworkPolicy, the first thing that breaks is DNS — and then nothing else works because services can't be resolved. Always include a DNS allow rule FIRST in any restrictive policy. For anihpj: add toEndpoints: [{matchLabels: {"k8s-app": "kube-dns"}}] with toPorts: [{ports: [{port: "53", protocol: UDP}]}] as the very first egress rule.

🟢 CATEGORY 1: ARCHITECTURE — Issue A8
NodePort Service Unreachable from Outside

🔍 Symptom: anihpj-api NodePort (30080) is not reachable from outside the cluster. curl <node-ip>:30080 times out. Pod is healthy, ClusterIP works internally.

🔴 5 Most Likely Causes
  1. KPR not handling NodePort: In KPR mode, Cilium must handle NodePort via BPF. Check cilium status | grep KubeProxyReplacement. Must be "Strict" for full NodePort support.
  2. Host firewall blocking port: Check iptables on the node: iptables -L -n | grep 30080. Also check cloud security group/firewall rules.
  3. externalTrafficPolicy: Local with no local backends: If set to Local and the receiving node has no backend pod, traffic is dropped. Check with kubectl describe svc anihpj-api | grep externalTrafficPolicy.
  4. NodePort range mismatch: Default NodePort range is 30000-32767. Check kubectl get svc anihpj-api -o yaml | grep nodePort. Must be within range.
  5. BPF NodePort map not initialized: Run cilium-dbg bpf nodeport list. If empty, NodePort acceleration is not active. Check cilium config | grep enable-nodeport.
🟡 5 Less Likely Causes
  1. DSR (Direct Server Return) misconfigured causing asymmetric routing
  2. SNAT for NodePort not working (hairpin traffic from pod to own node's NodePort)
  3. NodePort BPF map limit reached (max entries configurable)
  4. Conntrack entry collision for NodePort flows from same source IP
  5. ARP responder for ExternalIPs not answering on node interface
🟣 5 New Cluster Causes
  1. Cilium NodePort not enabled: Set nodePort.enabled=true in Helm or cilium install --set nodePort.enabled=true.
  2. kube-proxy still running: Cilium KPR strict mode requires kube-proxy to be removed. Check kubectl get ds -n kube-system kube-proxy.
  3. Cloud load balancer health check failing: AWS NLB health check may hit wrong port. Check target group health status.
  4. Node firewall/security group not allowing inbound on NodePort range: Add rule for 30000-32767 TCP.
  5. kubelet --nodeport-addresses restricts NodePort listening: Check kubelet args for explicit IP binding.
🔍 What to Look At / Take Note Of: KPR MUST be "Strict" for full NodePort (not "Partial"). externalTrafficPolicy: Local drops traffic if receiving node has NO local backend. Cloud NLB health checks: use TCP on NodePort. NodePort range: 30000-32767 only.
🔧 How to Solve:

  5. Cluster Mesh enabled without identity sync configured: Cross-cluster identities may have different GC policies.

💡 Personal Advice: Identity GC killing active identities is a silent catastrophe — pods are running but traffic randomly drops.   1. SELinux/AppArmor profile blocking BPF system calls (bpf() syscall denied)
  2. Transparent hugepages causing BPF map allocation failure

  3. Cilium DaemonSet securityContext wrong: Agent needs privileged: true and hostPID: true. Check DaemonSet spec.
  4. Node has incompatible OS: Windows nodes are not supported by Cilium. Check kubectl get nodes -o wide for OS.
  5. Required kernel modules not loaded: lsmod | grep -E "vxlan|geneve|ip6_tunnel". Load missing modules.

1. kubectl logs -n kube-system <cilium-pod> --previous — check the crash logs
2. cilium status --node <node> — if agent partially started, this shows what failed
3. kubectl describe pod -n kube-system <cilium-pod> — check for OOMKilled, liveness probe failures

  2. Syntax: policyAudit: true at top level of CNP spec, not under rules.
  3. No denies on new cluster: If nothing denies, audit shows nothing. Create test deny.

Switching Audit to Enforce Breaks Traffic

🔍 Symptom: Policy in audit for days showing no drops. Switched to enforce — immediately broke production. False confidence from audit.

🔴 5 Most Likely Causes
  1. Audit only shows THAT policy: Multiple policies. Audit on one doesn't show what OTHER policies deny. Union matters.
  2. Hubble filters hid drops: Your observe command may have filtered out some drops. Use unfiltered.
  3. Race on switch: Removing audit + reapply = brief gap where old policy removed, new not active.
  4. DNS behavior differs: Audit allows DNS so FQDNs resolve. Enforce blocks DNS so FQDNs can't resolve.
  5. Policy edited between: Different revision between audit and enforce. Rules changed.
🟡 5 Less Likely Causes
  1. Sidecar/init container traffic not in Hubble (short-lived)
  2. Health probes blocked but missed in audit window
  3. Metrics scraping blocked (periodic, may miss)
  4. CRD lag: some nodes still running old policy
  5. Hubble sampling hiding some flows
🟣 5 New Cluster Causes
  1. No test traffic: New cluster with no traffic — audit shows nothing. Generate test traffic.
  2. Audit too short: 24-48h minimum. Some traffic is daily/weekly (cronjobs, batches).
  3. Only checking ingress: Policy has both directions. Audit applies to both.
  4. UI vs CLI: UI has time limits. CLI with --since 72h captures more.
  5. Multiple ns not checked: Policy in ns-A may audit fine, but ns-B policy also affects.
🔍 What to Look At: Unfiltered Hubble: NO flags on observe. Check ALL policies (cnp+ccnp). DNS behavior differs audit vs enforce. Switch one policy at a time.
🔧 How to Solve:

2. kubectl get cnp,ccnp -A — ALL policies
3. Switch one at a time, wait 30min
4. Have rollback ready
5. Monitor: watch hubble observe --verdict DROPPED

💡 Personal Advice: Audit is probability, not guarantee. Longer audit = more confidence but never 100%. For anihpj: switch during maintenance window with rollback plan.
P13
🔊 CATEGORY 2: NETWORK POLICY — Issue P13
Audit Mode Performance Impact

🔍 Symptom: Audit mode on many policies causes agent CPU spike and Hubble flow loss. 'event queue full, dropping events' in logs.

🔴 5 Most Likely Causes
  1. Event generation rate: Every WOULD-BE denied packet = Hubble event. High traffic = millions/sec. Overwhelms buffer.
  2. Buffer too small: Default 4095 events. Under audit with high traffic, fills in ms. Increase to 65535.
  3. Multiple audit policies: 5 policies = 5x events. Audit one at a time.
  4. Relay bottleneck: Relay aggregates from all agents. Undersized relay = backpressure.
  5. perf ring buffer overflow: Kernel-side BPF events overflow before reaching agent.
🟡 5 Less Likely Causes
  1. TLS encryption overhead on event transmission
  2. Agent Go GC from event allocation
  3. Disk I/O for Hubble Timescape
  4. Network bandwidth agent→relay
  5. Prometheus cardinality from per-flow metrics
🟣 5 New Cluster Causes
  1. Audit on default-deny: NEVER audit default-deny on busy cluster — generates events for ALL traffic.
  2. No rate limiting: Hubble doesn't rate-limit. Traffic spike = event storm.
  3. All policies in audit: Audit one policy at a time, not all.
  4. Relay not scaled: Single relay for large cluster. Increase replicas/resources.
  5. No retention: Events accumulate. Set up consumer or Timescape.
🔍 What to Look At: Event queue depth. Agent CPU during audit. Audit scope: specific pods/ports. Relay CPU/memory. Sampling for high-traffic envs.
🔧 How to Solve:

1. Limit scope: audit specific ports/protocols
2. Increase buffer: hubble-event-queue-size: 65535
3. Scale relay: more replicas/resources
4. cilium-dbg bpf events list | wc -l
5. Flow sampling: capture 1/N flows

💡 Personal Advice: Audit is for VALIDATION, not constant monitoring. Turn on, observe 24-48h, enforce. For anihpj: audit during low traffic with specific scope.
