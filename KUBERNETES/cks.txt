    CKS EXAM STRATEGY — TOP 10 MISTAKES TO AVOID
    ─────────────────────────────────────────────
    ┌──────────────────────────────────────────────────────────────┐
    │  ❌ COMMON MISTAKES                 ✅ WHAT TO DO INSTEAD    │
    │                                                              │
    │  1. Mixing up AppArmor vs         Know: AppArmor = profile  │
    │     Seccomp (most common          on node. Seccomp = syscall │
    │     exam mistake)                 filter in pod spec        │
    │                                                              │
    │  2. Forgetting to enable          Always check namespace:    │
    │     PodSecurity admission         kubectl label ns <name>    │
    │     on the right namespace        pod-security.k8s.io/...   │
    │                                                              │
    │  3. Not switching cluster         ALWAYS verify first:       │
    │     context before starting       kubectl config             │
    │                                   current-context            │
    │                                                              │
    │  4. Creating RBAC but not        Test it:                   │
    │     verifying it works            kubectl auth can-i get pods│
    │                                   --as=<user>               │
    │                                                              │
    │  5. Forgetting to verify         Use: kubectl exec pod --    │
    │     NetworkPolicy actually        cat /proc/net/fib_trie    │
    │     blocks traffic                or ping to verify block    │
    │                                                              │
    │  6. Confusing PodSecurity        Enforce = blocks pods      │
    │     admission modes              Audit = just logs          │
    │     (enforce/audit/warn)         Warn = warns but allows    │
    │                                                              │
    │  7. Skipping audit log           Check apiserver manifest   │
    │     configuration flags          in /etc/kubernetes/manifests│
    │                                                              │
    │  8. Not knowing Falco            Know: falco.yaml,          │
    │     rule syntax                  output formats,            │
    │                                  /etc/falco/falco.yaml      │
    │                                                              │
    │  9. Leaving privileged           Always check SecurityContext│
    │     containers untouched         runAsNonRoot: true         │
    │     when fixing questions         allowPrivilegeEscalation   │
    │                                                              │
    │  10. Not using docs              Bookmarks are allowed!     │
    │      (kubernetes.io allowed       Prep 15+ bookmarks before  │
    │      during exam)                 the exam                  │

Chapter 1: Introduction to Kubernetes Security
--------------------------------------------------------------------------------
    1.1  Why Kubernetes Security Is Different
         - Kubernetes is powerful — and that power creates a large attack surface
         - A single misconfiguration can expose all workloads in the cluster
         - Real-world breaches: Tesla, Capital One, Shopify — all had K8s incidents
         - Security is not an add-on — it must be built into every layer
         - The "assume breach" mindset: act as if attackers already got in
         [ANALOGY CARD: Kubernetes cluster = a city. Security = locks on every door,
          camera on every street, guard at every gate]

         [TRADITIONAL IT vs KUBERNETES SECURITY — what changes]

    1.2  The 4Cs of Cloud Native Security (The Layered Model)
         - The security model: Cloud → Cluster → Container → Code
         - Each layer builds on the security of the layer below it
         - If the cloud is insecure, cluster security won't save you
         - Every layer must be independently secured

    1.3  Security Principles You Will Apply Throughout This Guide
         - Principle of Least Privilege: grant only what is needed, nothing more

         - Immutability: containers should not change after being deployed
         - Audit Everything: know what happened and when, with logs

    2.3  Kubernetes Security Threat Model (STRIDE)
         - S: Spoofing — impersonating a user or service account
         - T: Tampering — modifying pod specs or cluster configs
         - R: Repudiation — actions without audit trails
         - I: Information Disclosure — secrets leaked from etcd or env vars
         - D: Denial of Service — resource exhaustion attacks on nodes
         - E: Elevation of Privilege — breaking out of container to node

    2.4  The anihpj/jobpost Security Threat Scenario
         - Scenario: anihpj is running in Kubernetes, serving job listings globally
         - What attackers might want:
           • User email addresses from the User model
           • Company data from the JobPost model
           • Database credentials (postgres password)
           • Django SECRET_KEY from settings.py
           • Access to cloud storage (media files)
         - What would happen without CKS knowledge:
           • Pod running as root → container escape possible
           • All secrets in environment variables → readable by anyone in namespace
           • No NetworkPolicy → database reachable from any pod
           • No image scanning → vulnerable packages deployed silently
           • No audit logging → attacker leaves no trace

    3.2  Authentication vs Authorization vs Admission Control

Chapter 6: Network Policies — Zero-Trust Pod Networking
--------------------------------------------------------------------------------
    6.1  The Default: All Pods Can Talk to All Pods
         - Without NetworkPolicy: every pod in the cluster can reach every other
         - This is the "flat network" problem — one breach = lateral movement everywhere
         - The anihpj jobpost app: Django pods can reach postgres, redis, other namespaces
         - Zero-trust networking: default-deny everything, then allow only what's needed
         [DIAGRAM: Flat network (all arrows) vs Zero-trust (only allowed arrows)]

         [FLAT NETWORK vs ZERO TRUST — side by side]
         ┌──────────────────────────────┐   ┌──────────────────────────────┐
         │  ❌ FLAT NETWORK (default)   │   │  ✅ ZERO TRUST + NetPolicies │
         │                              │   │                              │
         │  anihpj ←──────────────────▶ │   │  anihpj ──────────────▶ pg  │
         │      ↕          ↕            │   │  (only anihpj → pg:5432)    │
         │  postgres ◀────▶ redis       │   │                              │
         │      ↕          ↕            │   │  All other traffic: BLOCKED  │
         │  monitoring ◀──▶ other-ns    │   │                              │
         │                              │   │  Attacker in pod X:          │
         │  Attacker in any pod:        │   │  cannot reach postgres ✅    │
         │  can reach EVERYTHING 🔴     │   │  cannot reach secrets ✅     │
         └──────────────────────────────┘   └──────────────────────────────┘

    6.2  NetworkPolicy Fundamentals
         - NetworkPolicy is a namespaced resource
         - Uses label selectors to identify which pods it applies to
         - policyTypes: Ingress (incoming) and/or Egress (outgoing)
         - Empty ingress rules = deny all incoming; empty egress = deny all outgoing
         - CNI plugin MUST support NetworkPolicy (Calico, Cilium, Weave — yes; Flannel alone — no)
         [CODE: Basic NetworkPolicy YAML explained field by field]

         │  kind: NetworkPolicy                                         │
         │  metadata:                                                   │
         │    name: postgres-netpol                                     │
         │    namespace: anihpj-prod                                   │
         │  spec:                                                       │
         │    podSelector:                 ← which pods this protects  │

    6.3  Common NetworkPolicy Patterns You Must Know
         - Default-deny all ingress in a namespace
         - Default-deny all egress in a namespace
         - Allow pod-to-pod within same namespace
         - Allow specific pod to reach a specific port
         - Allow external IP ranges (CIDR) to reach ingress
         - Allow DNS egress (port 53) — critical, else DNS breaks
         [CODE: 5 ready-to-use NetworkPolicy YAML patterns]

         [COMMON NETWORKPOLICY PATTERNS]
         | Pattern                       | Use Case                    | Exam Frequency |
         | Default deny all ingress      | Isolate namespace           | Very High      |
         | Default deny all egress       | Prevent data exfiltration   | High           |
         | Allow same-namespace only     | Team isolation              | High           |
         | Allow specific port to pod    | Database access control     | Very High      |
         | Allow DNS egress (53/UDP)     | Apps need name resolution   | Medium         |
         | Allow namespaceSelector       | Multi-namespace allowed     | High           |
         | Allow specific CIDR (ingress) | External IPs only           | Medium         |

Chapter 7: Ingress with TLS — Encrypted External Traffic
--------------------------------------------------------------------------------
    7.1  Why TLS Matters for Kubernetes Ingress
         - Without TLS: all traffic between users and anihpj is plaintext
         - User passwords, job applications, session cookies — all visible
         - HTTPS = HTTP + TLS = encrypted connection end-to-end
         - Kubernetes Ingress can terminate TLS (decrypt at the edge)
         [DIAGRAM: User → HTTPS → Ingress (TLS termination) → HTTP → pod]

         [TLS TERMINATION — what it means for anihpj]
         ┌──────────────────────────────────────────────────────────────────────┐
         │                                                                      │
         │  WITHOUT TLS:                                                        │
         │  👤 User ──── HTTP (plaintext) ───────────────── anihpj pod        │
         │  "password=secret" visible on any network hop                      │
         │                                                                      │
         │  WITH TLS (termination at Ingress):                                 │
         │                        Ingress                                      │
         │  👤 User ──── HTTPS ──── [decrypt] ──── HTTP ─── anihpj pod       │
         │     encrypted          TLS cert         internal plain               │
         │     on internet        stored here       (inside cluster)           │
         │                                                                      │
         │  WITH END-TO-END TLS (mTLS — Chapter 22):                          │
         │  👤 User ──── HTTPS ──── Ingress ──── HTTPS ─── anihpj pod        │
         │     encrypted          re-encrypts      pod cert   pod cert        │
         │     both hops          to pod           verified   verified        │
         │                                                                      │
         └──────────────────────────────────────────────────────────────────────┘

         [TLS CERTIFICATE TYPES — which to use when]
         ┌────────────────────────┬─────────────────────────────────────────────┐
         │  Certificate Type      │  Use Case                                   │
         ├────────────────────────┼─────────────────────────────────────────────┤
         │  Self-signed           │  Local dev, testing only                    │
         │  (openssl req -x509)   │  ⚠️  Browser shows "not secure" warning     │
         ├────────────────────────┼─────────────────────────────────────────────┤
         │  Let's Encrypt (free)  │  Production public domains                  │
         │  via cert-manager      │  ✅ Auto-renewed, trusted by all browsers   │
         ├────────────────────────┼─────────────────────────────────────────────┤
         │  Private CA (internal) │  Internal services, air-gapped environments │
         │                        │  ✅ Your org controls the CA                │
         ├────────────────────────┼─────────────────────────────────────────────┤
         │  Wildcard cert         │  *.anihpj.com covers all subdomains         │
         │                        │  ⚠️  One cert compromise = all subdomains   │
         └────────────────────────┴─────────────────────────────────────────────┘

    8.1  The API Server is the Crown Jewel

Chapter 9: RBAC — Role-Based Access Control for Security
--------------------------------------------------------------------------------
    9.1  RBAC Refresher — The Security Lens
         - RBAC controls what authenticated users/pods CAN DO in the cluster
         - Principle of Least Privilege: minimum permissions needed, nothing more
         - 4 key resources: Role, ClusterRole, RoleBinding, ClusterRoleBinding
         - Common mistake: using ClusterRole when a namespaced Role would do

         [RBAC 4-RESOURCE ANATOMY — how they connect]
         ┌──────────────────────────────────────────────────────────────────────┐
         │                                                                      │
         │  WHO                    BINDING               WHAT CAN DO           │
         │  (Subject)              (Connects who         (Role/ClusterRole)    │
         │                          to what)                                   │
         │                                                                      │
         │  👤 User: alice  ──────▶ RoleBinding       ──▶ Role               │
         │  🤖 SA: anihpj-sa        (namespace-scoped)     (namespace-scoped) │
         │  👥 Group: devs  ──────▶                        verbs + resources  │
         │                                                                      │
         │  👤 User: bob    ──────▶ ClusterRoleBinding ──▶ ClusterRole        │
         │  🤖 SA: monitoring       (cluster-wide)          (cluster-wide)    │
         │                                                   verbs + resources │
         │                                                                      │
         │  SCOPE RULE:                                                         │
         │  Role         = permission within ONE namespace                     │
         │  ClusterRole  = permission across ALL namespaces OR cluster objects │
         │  RoleBinding  = binds Role OR ClusterRole to subject in namespace  │
         │  ClusterRoleBinding = binds ClusterRole to subject cluster-wide    │

Chapter 10: Service Accounts — Securing Pod Identity
--------------------------------------------------------------------------------
    10.1  How Pods Authenticate to the API Server
          - Every pod gets a Service Account (default if not specified)
          - The ServiceAccount token is mounted at /var/run/secrets/kubernetes.io
          - Pods can use this token to call the Kubernetes API
          - The default ServiceAccount in most namespaces has no permissions
          - But: a compromised pod CAN use its token to explore the API
          [DIAGRAM: Pod → reads mounted token → calls API server → RBAC check]

    10.2  The Dangers of the Default Service Account
          - The default ServiceAccount is shared by all pods in a namespace
          - If you grant the default SA any permissions, ALL pods inherit them
          - Best practice: create dedicated ServiceAccounts per workload
          - Disable token auto-mount for pods that don't need API access
          [CODE: Disabling automount on ServiceAccount and individual pods]

          [DEFAULT vs DEDICATED SERVICE ACCOUNT — security comparison]
          ┌──────────────────────────────┐   ┌──────────────────────────────┐
          │  ❌ DEFAULT SERVICEACCOUNT   │   │  ✅ DEDICATED SERVICEACCOUNT │
          │                              │   │                              │
          │  All pods → "default" SA    │   │  anihpj pod → anihpj-sa     │
          │  Grant permissions to default│   │  postgres pod → postgres-sa │
          │  → ALL pods get permissions  │   │  Each SA → minimal permissions│
          │                              │   │                              │
          │  Compromised pod:            │   │  Compromised anihpj pod:     │
          │  → can access API as default │   │  → can only do what         │
          │  → may reach secrets across  │   │    anihpj-sa is allowed     │
          │    the namespace             │   │  → nothing else              │
          └──────────────────────────────┘   └──────────────────────────────┘

    10.3  Bound Service Account Tokens (Projected Tokens)
          - Old tokens: never expire, static, stored as Secrets
          - New tokens (K8s 1.21+): time-limited, audience-bound, auto-rotated
          - Use TokenRequest API for short-lived tokens
          - Projected volumes: mount token into pod with expiry
          [CODE: Pod spec with projected ServiceAccount token]

          [OLD vs NEW SERVICE ACCOUNT TOKENS — security comparison]
          ┌──────────────────────────────────────────────────────────────────────┐
          │  FEATURE             │ OLD (Static) TOKEN      │ NEW (Bound) TOKEN  │
          ├──────────────────────┼─────────────────────────┼────────────────────┤
          │  Stored as           │ K8s Secret (auto-created)│ Projected volume  │
          │  Expiry              │ Never expires! ← 🔴     │ 1 hour (default)  │

Chapter 11: Node Restriction & Hardening Authorization
--------------------------------------------------------------------------------
    11.1  The NodeRestriction Admission Plugin
          - NodeRestriction limits what kubelets can modify via the API
          - Without it: a compromised kubelet can modify ANY node/pod labels
          - With it: kubelets can only modify their OWN node and pods they run
          - CIS Benchmark 1.2.17: NodeRestriction must be enabled
          [CODE: API server flag to enable NodeRestriction]

          [NodeRestriction — WHAT EACH KUBELET CAN AND CANNOT TOUCH]
          ┌──────────────────────────────────────────────────────────────────────┐
          │  SCENARIO: node-worker-2's kubelet is compromised                   │
          │                                                                      │
          │  WITHOUT NodeRestriction:                                            │
          │  Compromised kubelet on node-worker-2 CAN:                          │
          │  ❌ Modify labels on node-worker-1 (impersonate another node)       │
          │  ❌ Evict pods from node-worker-3 (disrupt other nodes)             │
          │  ❌ Modify labels on pods it doesn't run (bypass scheduling)        │
          │  ❌ This enables privilege escalation across the entire cluster     │
          │                                                                      │
          │  WITH NodeRestriction enabled:                                       │
          │  Compromised kubelet on node-worker-2 CAN ONLY:                     │
          │  ✅ Read its own node object (node-worker-2)                        │
          │  ✅ Modify its own node status and labels                           │
          │  ✅ Read/write pods scheduled ON node-worker-2 only                │
          │  ✅ Cannot touch anything on node-worker-1 or node-worker-3        │
          └──────────────────────────────────────────────────────────────────────┘

    11.2  Authorization Modes — Understanding the Chain
          - Kubernetes supports multiple authorization modes simultaneously
          - Modes checked in order; first ALLOW stops the chain
          - Recommended modes: Node,RBAC
          - Never use: AlwaysAllow (disables all authorization — catastrophic)
          [CODE: API server --authorization-mode flag — secure configuration]

          [AUTHORIZATION MODE COMPARISON]
          | Mode           | How it works                     | Security Level |
          | AlwaysAllow    | Allow everything, no checks       | 🔴 NEVER use   |
          | AlwaysDeny     | Deny everything (testing only)    | ⚠️  Testing    |
          | RBAC           | Roles + Bindings                  | ✅ Use this    |
          | Node           | Kubelet access control            | ✅ Required    |
          | Webhook        | External authorization service    | ✅ Advanced    |
          | ABAC           | Attribute-based, file-based       | ⚠️  Legacy    |

    11.3  Protecting Node-Level Access
          - SSH access to nodes: use SSO, audit keys, remove stale users
          - Disable root SSH login on all nodes
          - Use node groups and IAM roles for cloud-managed nodes
          - Never expose kubelet API (port 10250) to the internet

          - Always upgrade control plane before worker nodes

          - Drain nodes before upgrading worker node components

          - Patch release (1.28.1 → 1.28.5): security fixes, bug fixes
          - Minor release (1.28 → 1.29): new features + deprecations
          - Always apply patch releases immediately (they fix CVEs)
          - Plan minor releases with 1-2 version lag from latest

Chapter 14: AppArmor — Application-Level Sandboxing
--------------------------------------------------------------------------------
    14.1  What Is AppArmor and Why Does It Matter for Containers?
          - AppArmor = Linux security module that restricts program capabilities
          - Creates per-process security profiles: what files, networks, capabilities it can access
          - Without AppArmor: a container with a vulnerability can do anything on the node
          - With AppArmor: even a compromised container can only do what its profile allows
          [ANALOGY: AppArmor = a security clearance badge — you can only enter rooms on your badge]

          [APPARMOR CONCEPT — before and after]
          ┌──────────────────────────────────────────────────────────┐
          │  📦 Container WITHOUT AppArmor                           │
          │                                                          │
          │  Django process (anihpj) can:                           │
          │  ❌ read /etc/shadow (password file)                    │
          │  ❌ write to /proc (kernel interfaces)                  │
          │  ❌ open raw network sockets                            │
          │  ❌ access /dev devices                                 │
          │                                                          │
          │  📦 Container WITH AppArmor profile                      │
          │                                                          │
          │  Django process (anihpj) can ONLY:                      │
          │  ✅ read /app/ directory (its own code)                 │
          │  ✅ write to /tmp/ and /app/media/                      │
          │  ✅ connect TCP to postgres:5432                        │
          │  ✅ connect TCP to redis:6379                           │
          │  🚫 everything else → DENIED                            │
          └──────────────────────────────────────────────────────────┘

    14.2  AppArmor Modes — Disabled, Complain, Enforce
          - Disabled: AppArmor off for this process
          - Complain (learning): logs violations but does NOT block them
          - Enforce: blocks all actions not allowed by the profile
          - Start with Complain to learn what your app actually needs

Chapter 15: Seccomp — Filtering System Calls
--------------------------------------------------------------------------------
    15.1  What Is Seccomp and Why Does It Protect Containers?
          - Seccomp = Secure Computing Mode (Linux kernel feature)
          - Every program communicates with the kernel via system calls (syscalls)
          - Seccomp filters which syscalls a process is ALLOWED to make
          - A container should only need ~50 syscalls — Linux has 300+ available
          - Block the other 250+ → massive reduction in kernel attack surface
          [DIAGRAM: App → makes syscall → Seccomp filter → allow/deny → kernel]

          [SYSCALL ATTACK REDUCTION]
          ┌──────────────────────────────────────────────────────────┐
          │  🐧 LINUX KERNEL HAS ~300+ SYSCALLS                     │
          │                                                          │
          │  A typical Django app uses ≈ 40-60 syscalls:            │
          │  read, write, open, close, socket, connect, accept...   │
          │                                                          │
          │  WITHOUT Seccomp:                                        │
          │  Attacker can use ANY of 300+ syscalls to:              │
          │    → ptrace another process                              │
          │    → mount filesystems                                   │
          │    → load kernel modules                                 │
          │    → create raw sockets                                  │
          │                                                          │
          │  WITH Seccomp (RuntimeDefault profile):                 │
          │  Only the ~60 needed syscalls are allowed               │
          │  240+ dangerous syscalls: blocked at kernel level        │
          └──────────────────────────────────────────────────────────┘

         [DANGEROUS SYSCALL EXAMPLES — what attackers use, what Seccomp blocks]
         ┌──────────────────────────────────────────────────────────────────────┐
         │  DANGEROUS SYSCALL  │ WHAT IT ENABLES                │ Blocked by   │
         ├─────────────────────┼────────────────────────────────┼──────────────┤
         │  ptrace             │ Attach to another process,     │ RuntimeDefault│
         │                     │ read its memory                │              │
         ├─────────────────────┼────────────────────────────────┼──────────────┤
         │  mount              │ Mount filesystems              │ RuntimeDefault│
         │                     │ (escape container isolation)   │              │
         ├─────────────────────┼────────────────────────────────┼──────────────┤
         │  kexec_load         │ Replace running kernel         │ RuntimeDefault│
         ├─────────────────────┼────────────────────────────────┼──────────────┤
         │  create_module      │ Load kernel module             │ RuntimeDefault│
         ├─────────────────────┼────────────────────────────────┼──────────────┤
         │  setns              │ Join another namespace          │ RuntimeDefault│
         │                     │ (namespace escape)             │              │
         ├─────────────────────┼────────────────────────────────┼──────────────┤
         │  unshare            │ Create new namespaces          │ RuntimeDefault│
         ├─────────────────────┼────────────────────────────────┼──────────────┤
         │  socket (raw)       │ Create raw network sockets     │ Custom profile│
         │                     │ (craft malicious packets)      │              │
         └──────────────────────────────────────────────────────────────────────┘

    15.2  Seccomp Profiles — RuntimeDefault and Custom
          - RuntimeDefault: provided by the container runtime (containerd/CRI-O)
          - Covers syscalls needed by most applications — safe default
          - Custom (Localhost): JSON file defining exact allowed/denied syscalls
          - Unconfined: no seccomp filter (insecure default for older clusters)

Chapter 19: Secrets Management — Encryption at Rest
--------------------------------------------------------------------------------
    19.1  The Problem: Secrets in etcd Are Stored in Plaintext (By Default)
          - Kubernetes Secrets are base64-encoded, not encrypted
          - base64 is NOT encryption: echo "cGFzc3dvcmQ=" | base64 -d → "password"
          - Without encryption: anyone who can access etcd can read all secrets
          - Encryption at rest: secrets are encrypted before writing to etcd
          [DIAGRAM: Secret → API server → encrypted before etcd storage]

          [BASE64 ≠ ENCRYPTION — the common misconception]
          ┌──────────────────────────────────────────────────────────┐
          │                                                          │
          │  kubectl create secret generic db-creds                 │
          │    --from-literal=password=supersecret123               │
          │                                                          │
          │  kubectl get secret db-creds -o yaml                    │
          │  data:                                                   │
          │    password: c3VwZXJzZWNyZXQxMjM=    ← "encrypted"? ❌ │
          │                                                          │
          │  echo "c3VwZXJzZWNyZXQxMjM=" | base64 -d               │
          │  → supersecret123    ← anyone can decode this! 🔴       │
          │                                                          │
          │  WITHOUT etcd encryption at rest:                       │
          │  Direct etcd read → plaintext secret exposed            │
          │                                                          │
          └──────────────────────────────────────────────────────────┘

    19.2  Enabling Encryption at Rest
          - Configure EncryptionConfiguration resource
          - Specify: which resources to encrypt (secrets), which provider (AES-CBC, AES-GCM)
          - Pass config file to API server: --encryption-provider-config flag
          - After enabling: NEW secrets are encrypted; OLD ones must be rotated

          [ENCRYPTION AT REST — configuration flow]
          ┌──────────────────────────────────────────────────────────────┐
          │  Step 1: Create encryption key                               │

Chapter 21: Container Runtime Sandboxing — gVisor and Kata Containers
--------------------------------------------------------------------------------
    21.1  The Container Isolation Problem
          - All containers on a node share the same Linux kernel
          - A kernel exploit in one container = game over for entire node
          - Sandboxed runtimes add an extra layer between container and kernel
          - gVisor: intercepts syscalls in userspace (Google's solution)
          - Kata Containers: lightweight VM per container (hardware isolation)

Chapter 22: mTLS and Service Mesh Security
--------------------------------------------------------------------------------
    22.1  Why Pod-to-Pod Traffic Is Insecure by Default
          - HTTP between pods: plaintext (anyone on the node can sniff it)
          - An attacker with pod access can read inter-service traffic
          - Solution: mutual TLS (mTLS) — every pod gets a cert, all traffic encrypted
          [DIAGRAM: Without mTLS (plaintext) vs with mTLS (encrypted both directions)]

    22.2  Mutual TLS (mTLS) — How It Works
          - Both parties (client AND server) present certificates
          - The client verifies the server is who it claims to be
          - The server verifies the client is who it claims to be
          - If either cert is invalid → connection refused

          [mTLS HANDSHAKE — anihpj → postgres step by step]
          ┌──────────────────────────────────────────────────────────────────────┐
          │                                                                      │
          │  anihpj pod (client)                postgres pod (server)           │
          │        │                                    │                        │
          │        │ 1. ClientHello                     │                        │
          │        │ ─────────────────────────────────▶ │                        │
          │        │                                    │                        │
          │        │ 2. ServerHello + Server Cert       │                        │
          │        │ ◀───────────────────────────────── │                        │
          │        │                                    │                        │
          │        │ 3. anihpj verifies postgres cert   │                        │
          │        │    (signed by Istio cluster CA?)   │                        │
          │        │ ─────────────────────────────────▶ │                        │
          │        │                                    │                        │
          │        │ 4. ServerCertificateRequest         │                        │
          │        │ ◀───────────────────────────────── │                        │
          │        │                                    │                        │
          │        │ 5. anihpj sends its own cert       │                        │
          │        │ ─────────────────────────────────▶ │                        │
          │        │                                    │                        │
          │        │ 6. postgres verifies anihpj cert   │                        │
          │        │    ✅ Both sides authenticated!    │                        │
          │        │                                    │                        │
          │        │ 7. Encrypted channel established   │                        │
          │        │ ◀──────────── TLS ───────────────▶ │                        │
          │        │                                    │                        │
          │  If anihpj cert is missing or invalid:      │                        │
          │  → Connection REFUSED (mTLS strict mode)    │                        │
          │  → Attacker pod without cert → blocked ✅   │                        │
          └──────────────────────────────────────────────────────────────────────┘

          [REGULAR TLS vs mTLS — key difference]
          ┌────────────────────┬──────────────────────────────────────────────┐
          │  Regular TLS       │  Only server proves its identity             │
          │  (HTTPS websites)  │  Client is anonymous (any browser can visit) │
          ├────────────────────┼──────────────────────────────────────────────┤
          │  mTLS              │  BOTH server AND client prove their identity │
          │  (pod-to-pod)      │  Unauthorized pods cannot connect at all     │
          └────────────────────┴──────────────────────────────────────────────┘

Chapter 29: Falco — Runtime Threat Detection in Real-Time
--------------------------------------------------------------------------------
    29.1  What Is Falco and Why It's CKS Critical?
          - Falco: open-source, CNCF project for cloud-native runtime security
          - Monitors: system calls, network connections, file access in real-time
          - Generates alerts when containers behave suspiciously
          - Unlike audit logs (API-level), Falco sees INSIDE containers at the OS level
          - CKS exam: Falco rules, falco.yaml, alert output formats
          [DIAGRAM: Falco architecture — kernel module/eBPF → event stream → rules → alerts]

          [FALCO vs AUDIT LOGGING — complementary tools]
          ┌──────────────────────────────────────────────────────────────┐
          │  AUDIT LOGGING                 FALCO                        │
          │  ─────────────                 ─────                        │
          │  Sees: API server calls        Sees: Kernel syscalls        │
          │  "kubectl exec into pod"       "shell spawned in container" │
          │  "secret read by user X"       "cat /etc/shadow inside pod" │
          │  "deployment updated"          "network conn to external IP"│
          │                                "binary written to /etc/"    │
          │                                                              │
          │  After attacker gets IN:       BEFORE/WHILE attacker acts:  │
          │  audit shows how they got in   Falco shows what they DO     │
          │                                                              │
          │  TOGETHER: complete picture of attack lifecycle              │
          └──────────────────────────────────────────────────────────────┘

    29.2  Falco Architecture
          - Falco collects events from the Linux kernel via:
            • Kernel module (traditional, efficient)
            • eBPF probe (modern, safer, no kernel module needed)
          - Events match against rules defined in YAML files
          - Alerts sent to: stdout, file, Slack, Elasticsearch, webhooks

          [FALCO ARCHITECTURE DIAGRAM — event flow from kernel to alert]
          ┌──────────────────────────────────────────────────────────────────────┐
          │                                                                      │
          │  🐧 LINUX KERNEL                                                     │
          │  Container makes a syscall (e.g., open /etc/shadow)                │
          │         │                                                            │
          │         │ kernel event stream                                        │
          │         ▼                                                            │
          │  ┌─────────────────────────────────────────────────────────────┐   │
          │  │  FALCO DRIVER (choose one):                                  │   │
          │  │  • Kernel module (kmod): fast, needs kernel build headers    │   │
          │  │  • eBPF probe: safe, no recompile needed, CO-RE compatible  │   │
          │  │  • Modern eBPF (libbpf): newest, best for production        │   │
          │  └──────────────────────────────┬──────────────────────────────┘   │
          │                                 │ structured events                  │
          │                                 ▼                                    │
          │  ┌─────────────────────────────────────────────────────────────┐   │
          │  │  FALCO ENGINE                                                 │   │
          │  │  Loads rules from: /etc/falco/falco_rules.yaml              │   │
          │  │                    /etc/falco/falco_rules.local.yaml         │   │
          │  │  Matches event against rule conditions                       │   │
          │  └──────────────────────────────┬──────────────────────────────┘   │
          │                                 │ rule matched!                      │
          │                                 ▼                                    │
          │  ┌─────────────────────────────────────────────────────────────┐   │
          │  │  OUTPUT CHANNELS (configured in /etc/falco/falco.yaml)      │   │
          │  │  → stdout (default — good for kubectl logs falco-pod)       │   │
          │  │  → file  (/var/log/falco/falco.log)                         │   │
          │  │  → HTTP webhook (Slack, PagerDuty, SIEM)                    │   │
          │  │  → gRPC (falcosidekick for fan-out to multiple outputs)    │   │
          │  └─────────────────────────────────────────────────────────────┘   │
          └──────────────────────────────────────────────────────────────────────┘

Chapter 31: Immutable Containers — Read-Only Filesystems
--------------------------------------------------------------------------------
    31.1  Why Immutability Is a Security Property
          - An attacker who can write to the container filesystem can:
            • Replace binaries with backdoored versions
            • Write malware to /etc/cron.d
            • Modify configuration to open backdoors
          - Immutable container: filesystem is read-only, nothing can change
          - Changes must go through the CI/CD pipeline and image rebuild

    31.2  Enforcing Read-Only Filesystems in Kubernetes

    | Error / Symptom                          | Cause                          | Fix                                    |

    | Pod fails: AppArmor profile not found    | Profile not loaded on node     | aa-apparmor-parser -r /path/to/profile |

    | Seccomp RuntimeDefault breaks app        | App uses unusual syscall       | Use custom seccomp profile with that syscall |
    | Anonymous auth still works after disable | Manifest not updated/applied   | Check kube-apiserver restarted with new flag |
    | SA token still automounts after disable  | Old pod still running          | Delete and let Deployment recreate pod |
    | Audit log not created                    | Log path not writable          | Check /var/log/kubernetes/ permissions |

Appendix D: Security Terminology Glossary
--------------------------------------------------------------------------------
    [Alphabetical glossary of 100+ security terms with K8s-specific definitions]

    A
    - Admission Controller: a plugin that intercepts and can modify/reject API requests
    - AppArmor: a Linux security module that restricts process capabilities via profiles
    - Attack Surface: the sum of all possible points where an attacker can try to enter
    - Audit Log: a chronological record of all API server requests
    - Authentication (AuthN): verifying the identity of a user or service ("who are you?")
    - Authorization (AuthZ): determining what an authenticated entity can do ("what can you do?")

    B
    - Base Image: the foundational image layer your Dockerfile builds upon
    - Baseline (PSS): Pod Security Standard level preventing known privilege escalation

    C
    - CA (Certificate Authority): entity that issues and signs digital certificates
    - Capabilities (Linux): fine-grained privileges split from the root superuser role
    - CIS Benchmark: Center for Internet Security configuration security standards
    - ClusterRole: RBAC role granting permissions across all namespaces or cluster-level resources
    - Container Escape: exploiting a vulnerability to break out of a container to the host
    - cosign: a tool for signing and verifying container images (part of Sigstore project)
    - CVE: Common Vulnerabilities and Exposures — a public database of known security flaws

    D
    - Defense in Depth: using multiple security layers so no single failure is catastrophic
    - distroless: minimal container images containing only the app and its runtime dependencies
    - Dynamic Secret: a secret generated on-demand with a limited lifetime (e.g., Vault DB secrets)

    E
    - eBPF: extended Berkeley Packet Filter — kernel technology used by Falco for event collection
    - Encryption at Rest: encrypting stored data (e.g., Secrets in etcd) so disk reads are safe
    - Encryption in Transit: encrypting data while it moves over the network (TLS)

    F
    - Falco: open-source runtime security tool that detects anomalous container behaviour
    - 4Cs: Cloud, Cluster, Container, Code — the four layers of cloud native security

    G
    - gVisor: a sandboxed container runtime from Google that intercepts syscalls in userspace
    - GitOps: operational model where Git is the source of truth for infrastructure/app configs

    H
    - HSTS: HTTP Strict Transport Security — tells browsers to always use HTTPS
    - hostNetwork: pod setting that uses the node's network namespace (dangerous)
    - hostPID: pod setting that uses the node's PID namespace (dangerous)

    I
    - Image Digest: a SHA256 hash uniquely identifying an exact image version (immutable)
    - Image Tag: a mutable label on an image (e.g., :latest) — can change to point to new content
    - Immutable Container: a container whose filesystem cannot be modified after start
    - IRSA: IAM Roles for Service Accounts (AWS) — pod-level cloud permission scoping

    K
    - Kata Containers: sandboxed container runtime using lightweight VMs per container
    - kube-bench: tool for checking Kubernetes cluster against CIS Benchmark standards
    - Kyverno: Kubernetes-native policy engine using YAML (no Rego needed)

    L
    - Lateral Movement: after breaching one system, moving to others within the same network
    - Least Privilege: principle of granting only the minimum permissions required

    M
    - mTLS: mutual TLS — both client and server verify each other's identity
    - Multi-stage Build: Dockerfile pattern to compile in one stage, run in a minimal final stage

    N
    - NetworkPolicy: Kubernetes resource defining allowed pod-to-pod network traffic rules
    - NodeRestriction: admission plugin limiting what each kubelet can modify via the API
    - Non-root Container: container running as a non-root Linux user (UID > 0)

    O
    - OIDC: OpenID Connect — identity protocol used for Kubernetes authentication
    - OPA: Open Policy Agent — general-purpose policy engine using Rego language
    - OPA Gatekeeper: Kubernetes-specific integration of OPA via admission webhooks

    P
    - Pod Security Admission: the built-in K8s admission controller enforcing PSS levels
    - Pod Security Standards (PSS): built-in K8s policy profiles (Privileged/Baseline/Restricted)
    - Privileged Container: container with full host root access (extremely dangerous)
    - Privilege Escalation: gaining more permissions than originally granted

    R
    - RBAC: Role-Based Access Control — the primary K8s authorization system
    - readOnlyRootFilesystem: securityContext field making the container filesystem immutable
    - Rego: OPA's policy language (functional, declarative)
    - Restricted (PSS): most secure Pod Security Standard level

    S
    - SBOM: Software Bill of Materials — list of all components in a software artifact
    - Seccomp: Secure Computing Mode — kernel feature filtering which syscalls a process can make
    - SecurityContext: pod/container field defining security settings (user, caps, seccomp, etc.)
    - ServiceAccount: Kubernetes identity assigned to pods for API server access
    - Sigstore: ecosystem of tools for supply chain security (cosign, fulcio, rekor)
    - SLSA: Supply-chain Levels for Software Artifacts — framework for build provenance
    - Static Pod: pod defined by a YAML file on a node and managed directly by kubelet

    T
    - TLS: Transport Layer Security — cryptographic protocol for securing network connections
    - TokenReview: API to validate a ServiceAccount JWT token
    - Trivy: open-source vulnerability scanner for container images, filesystems, and repos

    V
    - Vault (HashiCorp): enterprise secret management with dynamic secrets and audit logs
    - ValidatingWebhookConfiguration: K8s resource defining an external policy webhook

    Z
    - Zero Trust: security model assuming no implicit trust, verify every request
