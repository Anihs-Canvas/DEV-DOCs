1.1 The Problem Before DevOps

Imagine you've built anihpj — a Django app with a jobpost module where employers list jobs filtered by Skills, Location, and Author. It works perfectly on your laptop. But how do you get it to production so thousands of users can access it reliably?

The Wall of Confusion

Before DevOps, Development and Operations were separate teams with opposing goals. Developers were measured on how fast they shipped new features. Operations was measured on system stability. Every deployment was a conflict.

The Pain of Manual Deployments — anihpj Edition

😰 Deploying anihpj WITHOUT DevOps
  • 🔴 Dev pushes code Friday 5 PM → Ops called at 2 AM when it breaks
  • 🔴 "Works in dev but production has Python 3.8 not 3.12"
  • 🔴 Manual SSH into EC2 → copy files → restart gunicorn by hand
  • 🔴 No rollback plan — if it breaks, pray for a backup
  • 🔴 Database migration fails → site down for 4 hours
  • 🔴 Who changed the nginx config? Nobody knows...
  • 🔴 Scaling = launch new EC2, configure everything from scratch
🎉 Deploying anihpj WITH DevOps
  • ✅ Git push → CodePipeline builds, tests, deploys automatically
  • ✅ Docker container = identical in dev, staging, AND production
  • ✅ CloudFormation = infrastructure versioned in Git
  • ✅ CodeDeploy Blue/Green = instant rollback if anything goes wrong
  • ✅ Database migrations = automated in the pipeline
  • ✅ CloudTrail + Config = every change tracked and audited
  • ✅ Auto Scaling = handles traffic spikes without human intervention
📖 Key Insight: DevOps = Breaking the Wall

DevOps is not a tool. It's not a job title. It's a cultural shift where Developers and Operations share responsibility for the entire application lifecycle — from code to production. The "wall" is replaced with collaboration, shared ownership, and automation.

🫂
Culture

People over process. Blameless postmortems, shared responsibility, trust between teams. DevOps starts with culture — tools alone won't fix a toxic environment.

🤖
Automation

Machines do repetitive work. CI/CD pipelines, Infrastructure as Code, automated testing, GitOps. Humans focus on creative problem-solving.

📊
Measurement

You can't improve what you don't measure. CloudWatch metrics, X-Ray traces, DORA metrics. Data-driven decisions over gut feelings.

📖
Sharing

Knowledge silos are dangerous. Runbooks, wikis, post-mortems, pair programming. If only one person knows how it works, you have a bus factor of 1.

IAM Deep Dive — The Foundation of AWS Security

IAM is the #1 most important AWS service for DevOps. Every other service depends on it. Here are the core concepts you must master:

👤
IAM User

An individual person. Has long-term credentials (username + password + access keys). Use for humans who need console/CLI access. Rotate access keys every 90 days.

👥
IAM Group

A collection of users. Attach policies to groups, not individual users. Example: "DevOps-Engineers" group gets CodePipeline, EKS, CloudWatch access.

🎭
IAM Role

Temporary identity assumed by services. No long-term credentials! EC2 instances, Lambda functions, EKS Pods (via IRSA) assume roles. Always prefer roles over users.

📜
IAM Policy

JSON document defining permissions. Specifies: Effect (Allow/Deny), Action (s3:GetObject), Resource (arn:aws:s3:::bucket/*). Explicit DENY always overrides ALLOW.

IAM Policy Example — anihpj S3 Read Access
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:GetObject", "s3:ListBucket"],
    "Resource": [
      "arn:aws:s3:::anihpj-static-files",
      "arn:aws:s3:::anihpj-static-files/*"
    ]
  }]
}
💡 IAM Best Practices for DOP-C02

(1) Principle of Least Privilege — start with NOTHING, add only what's needed. (2) Use IAM Roles over Users — roles have temporary credentials that auto-rotate. (3) Enable MFA on root and all IAM users. (4) IRSA for EKS — Pods get IAM roles via OIDC, no credentials in code. (5) IAM Access Analyzer — find overly permissive policies. (6) Policy evaluation logic: Explicit DENY > SCP > Resource Policy > Identity Policy > Session Policy.

Q1

You deploy anihpj EKS Pods across 3 Availability Zones in us-east-1. If AZ-a experiences a power outage, what happens to the Pods running there?

Show Answer & Explanation
✅ ANSWER

The Pods in AZ-a become unhealthy, and EKS reschedules them to AZ-b and AZ-c. The ALB health checks detect the failed Pods and routes traffic only to healthy Pods in the remaining AZs. The ReplicaSet controller creates replacement Pods on healthy nodes.

📖 EXPLANATION
# Multi-AZ High Availability — Q1 Scenario
# AZ-a FAILS → Self-Healing in Action
# ─────────────────────────────────────────────
# BEFORE AZ-a FAILURE:
#   AZ-a: EKS Node → [anihpj Pod ✓] [anihpj Pod ✓]
#   AZ-b: EKS Node → [anihpj Pod ✓]
#   AZ-c: EKS Node → [anihpj Pod ✓]
#   ALB: Routes to ALL healthy Pods across 3 AZs
#
# AFTER AZ-a FAILURE (within 2-3 minutes):
#   AZ-a: EKS Node → [💀 DEAD]      ← Power outage!
#   AZ-b: EKS Node → [anihpj Pod ✓] [anihpj Pod ✓ ← NEW!]
#   AZ-c: EKS Node → [anihpj Pod ✓] [anihpj Pod ✓ ← NEW!]
#   ALB: Stops routing to AZ-a (failed health checks)
#        Routes ALL traffic to AZ-b + AZ-c only
#   RDS: Automatic failover to standby in AZ-b
# ─────────────────────────────────────────────
# KEY: ReplicaSet controller ensures desired=actual Pod count

This is multi-AZ high availability in action: EKS self-heals by rescheduling dead Pods, ALB routes around failures, and RDS Multi-AZ provides automatic database failover — all without human intervention.

🐋 Container Networking Basics

Bridge (default): Containers on same host communicate via docker0 bridge. Isolated from host network.
Host: Container shares host's network stack directly. No isolation. Faster but less secure.
None: Container has no network. Use for batch jobs that don't need networking.
Overlay: Multi-host networking for Docker Swarm. Not used with K8s (K8s uses CNI plugins instead).
Kubernetes networking model: Every Pod gets its own IP. Pods on different nodes communicate via CNI plugins (Calico, Cilium, Flannel). Containers within a Pod share localhost.

Q4

What is the primary difference between a Docker IMAGE and a Docker CONTAINER?

Show Answer & Explanation
✅ ANSWER

Image = read-only template (built from Dockerfile). Container = running instance of an image with a writable layer. You build an image once (docker build). You can run many containers from the same image (docker run). Containers are ephemeral — when you delete a container, its writable layer is lost.

📖 EXPLANATION
# Image vs Container — Q4 ANSWER
# ─────────────────────────────────────────────
# IMAGE (Read-Only Template):
#   Dockerfile → docker build → anihpj:v1
#   Stored in ECR (immutable layers)
#   Like a CLASS in OOP (blueprint)
#
# CONTAINER (Running Instance):
#   docker run anihpj:v1 → container-abc123
#   Image layers (read-only) + Writable layer
#   Like an INSTANCE of a class (object)
#
# 1 Image → MANY Containers:
#   anihpj:v1 → container-1 (Pod-1 on Node-A)
#   anihpj:v1 → container-2 (Pod-2 on Node-B)
#   anihpj:v1 → container-3 (Pod-3 on Node-C)
#   Same image, 3 separate running instances
#   Each has its own writable layer (logs, temp)

When a container dies, only the writable layer is lost; the image layers are immutable and shared across all containers.

# Init Container approach (runs before main container)

- name: db-migrate

# Main container starts only after init succeeds
containers:
- name: anihpj
  image: anihpj:v1
📖 EXPLANATION

Best practices for Django migrations on K8s: (1) Init Container — runs before main app, Pod only starts if migration succeeds; (2) Kubernetes Job — run migration separately, then deploy; (3) CI/CD pipeline — run migration as part of CodeDeploy lifecycle hook. NEVER run migrations in the main container's startup (CMD/ENTRYPOINT) — if you scale to 3 Pods, you'd have 3 simultaneous migration attempts which could corrupt the database.

4.1 Why Kubernetes? — The Problem It Solves

Running one container is easy: docker run anihpj:v1. Running 100 containers across 10 servers is chaos. What happens when a container crashes at 3 AM? When traffic spikes 10x? When you need to deploy a new version with zero downtime? Manual container management doesn't scale — that's why Kubernetes exists.

💀 WITHOUT KUBERNETES

Manual management. You SSH into servers, restart crashed containers, configure load balancers by hand. You ARE the orchestrator — and you need sleep.

"anihpj pod down!" → You wake up at 3 AM
"Traffic 10x spike" → Site crashes before you can react
"Deploy v2" → SCP files, pray nothing breaks
"Rollback" → Hope you made a backup

☸️ WITH KUBERNETES

Declarative automation. You tell K8s WHAT you want ("3 copies of anihpj, always running") and it figures out HOW to make it happen across the cluster.

Pod crashes → Auto-restarted in 2 seconds
Traffic spikes → HPA auto-scales Pods
Deploy v2 → Rolling update, zero downtime
Rollback → kubectl rollout undo (1 command)

4.5 Control Plane Components — Deep Dive

🧠 The Brain — Control Plane Components

📡kube-apiserver
The front door of Kubernetes. EVERYTHING goes through the API server — kubectl commands, node heartbeats, controller actions, scheduler decisions. It authenticates (Who are you?), authorizes (Can you do this?), and validates (Is this YAML correct?). If the API server is down, the cluster is blind — but running workloads continue unaffected.
💾etcd
The cluster's brain memory. A distributed, consistent key-value store holding ALL cluster state — every Pod, Service, ConfigMap, Secret. Uses RAFT consensus (3-5 nodes for HA). If you lose etcd without a backup, you lose your ENTIRE cluster. On EKS, AWS manages etcd for you — but you still need to know how to back it up for self-managed clusters.
🎯kube-scheduler
The matchmaker. Watches for new Pods with no node assigned, then picks the best node. Two phases: FILTER (remove nodes that can't fit — not enough CPU/memory, tainted, cordoned) and SCORE (rank remaining nodes by fit — least requested, image already cached, affinity rules). The Pod gets nodeName set — now the kubelet takes over.
🔄controller-manager
The watchdog. Runs controller loops that continuously compare desired state (from etcd) vs actual state (from cluster) and take corrective action. Examples: "ReplicaSet wants 3 Pods, only 2 running → create 1 more." "Node went down 5 minutes ago → evict its Pods." "Deployment strategy is RollingUpdate → gradually replace old Pods with new ones."
🔐 DEEP DIVE: API Server — The 3 Security Gates
Every API request goes through THREE gates in order:

GATE 1: AUTHENTICATION — "WHO ARE YOU?"
  • X.509 Client Certificates (kubeconfig certs)
  • Bearer Tokens (ServiceAccount tokens mounted in Pods)
  • OIDC (OpenID Connect — integrates with AWS IAM via EKS)

GATE 2: AUTHORIZATION — "CAN YOU DO THIS?"
  • RBAC: Role/ClusterRole + RoleBinding/ClusterRoleBinding
  • Node Authorizer: kubelet can only access its own node's Pods
  • Webhook: external authz (OPA/Gatekeeper/Kyverno)

GATE 3: ADMISSION CONTROL — "IS THIS REQUEST VALID?"
  • Mutating Webhooks (run FIRST): inject sidecars, set defaults
  • Validating Webhooks (run SECOND): reject non-compliant requests
  • Built-in: ResourceQuota, LimitRanger, PodSecurity

🎯 EXAM: Order is ALWAYS AuthN → AuthZ → Admission.
   A request passes ALL three before touching etcd!
💾 DEEP DIVE: etcd — RAFT Consensus & Quorum
etcd uses RAFT consensus: a LEADER is elected, ALL writes go through
the leader, then replicate to followers. Write is COMMITTED only when
majority (N/2+1) acknowledges.

QUORUM = (N/2) + 1:  3 nodes → quorum=2,  5 nodes → quorum=3

FAILURE SCENARIOS:
  ✅ 3 nodes, lose 1 follower → WORKS (2/3 have quorum)
  ❌ 3 nodes, lose 2 → DOWN (1/3, no quorum!)
  ✅ 5 nodes, lose 2 → WORKS (3/5 have quorum)
  ❌ 5 nodes, lose 3 → DOWN (2/5, no quorum)

SPLIT BRAIN: RAFT PREVENTS this — a leader without quorum
cannot accept writes. This guarantees consistency.

💡 On EKS, AWS manages etcd. For self-managed clusters:
   ALWAYS 3-5 etcd nodes in different AZs.
   ALWAYS: etcdctl snapshot save → push to S3 regularly.
🎯 DEEP DIVE: Scheduler — Filter → Score → Assign
PHASE 1: FILTERING (Remove nodes that can't fit)
  • NodeResourcesFit: enough CPU/Memory?
  • NodeUnschedulable: is node cordoned?
  • NodeSelector / NodeAffinity: matching labels?
  • TaintToleration: Pod tolerates node's taint?
  • NodePorts: port conflict?
  • PodTopologySpread: even zone distribution?
  • VolumeZone: volume available in this AZ?

PHASE 2: SCORING (Rank remaining nodes 0-10)
  • LeastRequestedPriority: prefer less-loaded nodes
  • ImageLocality: bonus if image already cached
  • NodeAffinityPriority: bonus for preferred affinities
  • BalancedResourceAllocation: balanced CPU/Mem ratio

Highest-scoring node wins → pod.spec.nodeName = "node-3"
🔄 DEEP DIVE: controller-manager — Many Controllers, One Binary
"controller-manager" runs DOZENS of controllers, each with its own
reconciliation loop:

Deployment Controller:   "Deploy wants 3 → RS has 2 → create Pod"
ReplicaSet Controller:   "RS says 3 replicas, only 2 Pods → create 1"
Node Controller:         "Node-2 no heartbeat 5min → NotReady, evict"
Service Controller:      "Service type=LB → call AWS API, create NLB"
EndpointSlice Ctrl:      "Service selector matches 3 Pods → update IPs"
Job Controller:          "Job needs 1 success → create Pod, monitor"
PV/PVC Controller:       "PVC 10Gi, no PV → dynamic provision via SC"
Namespace Controller:    "Namespace marked delete → delete all inside"
Garbage Collector:       "Owner deleted → cascade delete dependents"

🧠 Each controller does ONE thing, loops forever, reads state
   from etcd (not memory). If it crashes, kubelet restarts it —
   and reconciliation picks up where it left off!

4.6 Worker Node Components — Deep Dive

💪 The Muscles — Worker Node Components

🏗️kubelet
The node agent running on every worker. Watches the API server for Pods assigned to its node, calls the container runtime (containerd/CRI-O) to pull images and start containers, runs health probes (liveness/readiness), and reports Pod/node status back to the API server. If the kubelet stops, the node shows as NotReady.
🚦kube-proxy
The network plumber. Maintains network rules (iptables or IPVS) on every node so Pods and Services can communicate. When you create a Service, kube-proxy writes rules: "Traffic to Service IP 10.100.50.2:8000 → randomly route to Pod-1 (10.0.1.5), Pod-2 (10.0.2.8), or Pod-3 (10.0.3.12)." On AWS EKS, kube-proxy manages the VPC networking rules.
🐋Container Runtime
The engine that actually runs containers. Kubernetes supports any CRI-compatible runtime: containerd (default since v1.24), CRI-O (Red Hat), or others. Docker's built-in runtime (dockershim) was removed in v1.24. On EKS, the default is containerd. The runtime pulls images (from ECR!), creates containers, and manages their lifecycle.
🏗️ DEEP DIVE: kubelet — The Bridge Between API and Containers
The kubelet is NOT a container — it's a SYSTEMD SERVICE running directly
on the node's OS. It's the ONLY component that talks to both the API
server AND the container runtime.

KUBELET WORKFLOW:
  1. Registers node with API server (or joins existing cluster)
  2. Watches API server: "Any Pods assigned to MY node?"
  3. For each new Pod:
     a. Call CRI (containerd): "Pull image from ECR"
     b. Call CNI: "Set up network for this Pod (assign IP)"
     c. Call CSI: "Mount any volumes needed (EBS, EFS)"
     d. Start the container
  4. Run probes continuously:
     • livenessProbe: "Is the app alive?" → if fails, RESTART container
     • readinessProbe: "Can the app serve traffic?" → if fails, remove from Service
     • startupProbe: "Has the app finished starting?" → protects slow-starting apps
  5. Report Pod status back to API server every few seconds
  6. If Pod crashes → go back to step 3 (restart)

CRITICAL INTERFACES the kubelet uses:
  • CRI (Container Runtime Interface): talks to containerd/CRI-O
  • CNI (Container Network Interface): sets up Pod networking
  • CSI (Container Storage Interface): mounts volumes

💡 If kubelet stops → node = NotReady → scheduler stops placing Pods there
   → existing Pods keep running (container runtime is independent)
   → after 5 min, controller-manager starts evicting Pods from dead node
🚦 DEEP DIVE: kube-proxy — iptables vs IPVS Modes
kube-proxy maintains network rules so traffic reaches the right Pods.
It has TWO modes — understanding the difference matters for the exam:

┌──────────────────────────────────────────────────────────────────────┐
│  IPTABLES MODE (default in most clusters)                             │
│  ─────────────────────────────────────                                │
│  • Writes iptables rules on every node                                │
│  • For each Service: creates a chain of rules                         │
│  • Traffic to Service IP → random DNAT to a backend Pod IP            │
│  • PRO: Simple, battle-tested, works everywhere                       │
│  • CON: With 1000+ Services, iptables rules become slow (O(n) lookup) │
│  • CON: Random load balancing only (no least-connection)              │
│                                                                       │
│  IPVS MODE (better for large clusters)                                │
│  ──────────────────────────────────                                   │
│  • Uses Linux IP Virtual Server (kernel-level L4 load balancer)       │
│  • O(1) lookup regardless of how many Services you have               │
│  • Supports multiple scheduling algorithms:                           │
│    rr (round-robin), lc (least-connection), dh (destination hashing)  │
│  • PRO: Much faster at scale, more scheduling options                 │
│  • CON: Requires IPVS kernel modules loaded on every node             │
│                                                                       │
│  🎯 EXAM: EKS defaults to iptables. IPVS requires extra setup.        │
│     For production at scale (>1000 Services), prefer IPVS.            │
└──────────────────────────────────────────────────────────────────────┘

Q1

You deploy anihpj on EKS. The Deployment specifies replicas: 3. One of the worker nodes suddenly fails. What happens to the Pods on that node?

✅ ANSWER

The controller-manager detects the node failure, marks the Pods for eviction, and the ReplicaSet controller creates replacement Pods on healthy nodes. Within minutes, 3 Pods are running again — the desired state is restored automatically.

# 5. Scheduler assigns new Pods to healthy nodes
# 6. kubelet on healthy nodes starts new containers
#
# RESULT: Zero human intervention. Self-healing in action!

Q3

What is the role of etcd in a Kubernetes cluster?

Show Answer & Explanation
✅ ANSWER

etcd is the distributed key-value store that holds ALL cluster state — every Pod, Service, ConfigMap, Secret, and Node definition. It's the "source of truth" for the entire cluster. All cluster data lives in etcd. Losing etcd without a backup = losing the entire cluster.

# All of this data? Stored in etcd (AWS-managed).

Q6

A Deployment specifies replicas: 5. Due to a bug, 2 Pods crash. What Kubernetes component ensures 5 Pods are running again?

Show Answer & Explanation
✅ ANSWER

The ReplicaSet controller (part of kube-controller-manager). It continuously compares desired replicas (5) vs actual (3 after crash) and creates 2 new Pods to restore the desired state.

📖 EXPLANATION
# Reconciliation Loop — ReplicaSet Controller
# ─────────────────────────────────────────────
# LOOP (runs continuously):
#   1. OBSERVE: "Deployment anihpj, replicas: 5"
#              "Currently running: Pod-1✓ Pod-2✓ Pod-3✓"
#              "Pod-4💀 crashed, Pod-5💀 crashed"
#   2. DIFF:    Desired=5, Actual=3, Gap=2
#   3. ACT:     Create Pod-6, Pod-7
#
# This is the RECONCILIATION LOOP — the heart of K8s.
# Every controller (Deployment, ReplicaSet, Node, Job...)
# runs the same: OBSERVE → DIFF → ACT → REPEAT

What does "declarative management" mean in Kubernetes?

Show Answer & Explanation
✅ ANSWER

You declare WHAT you want (desired state in YAML), and Kubernetes continuously ensures the cluster matches that state. You don't give step-by-step instructions ("start this container on node 2"). You say "I want 3 copies of anihpj" and K8s figures out where and how.

5.2 Pods — The Smallest Deployable Unit

A Pod is the smallest deployable unit in Kubernetes. It's a group of one or more containers that share the same network namespace (localhost), IPC namespace, and volumes. Pods are ephemeral — they can die and be replaced at any time.

A Pod goes through a well-defined lifecycle. Understanding each phase
helps you debug issues faster:

┌──────────────────────────────────────────────────────────────────────┐
│  POD PHASES (from kubectl get pods STATUS column):                    │
│                                                                       │
│  Pending → Running → Succeeded (or) Failed                            │
│                                                                       │
│  PENDING:                                                             │
│  "Pod accepted by API server, but not running yet"                    │
│  • Image being pulled (especially large images from ECR)              │
│  • Waiting for scheduler to assign a node                             │
│  • Waiting for volume to be provisioned (EBS/EFS)                     │
│  • Init containers still running                                      │
│  💡 Stuck Pending? Check: kubectl describe pod → Events               │
│     "0/3 nodes available: insufficient memory"                        │
│                                                                       │
│  RUNNING:                                                             │
│  "All containers created, at least one is running"                    │
│  • Does NOT mean the app is healthy! That's what readinessProbe does  │
│  • Container could be running but app still starting (port not open)  │
│                                                                       │
│  SUCCEEDED:                                                           │
│  "All containers terminated successfully (exit code 0)"               │
│  • Only for Pods with restartPolicy: Never or OnFailure               │
│  • Common for Jobs — run once, exit clean                             │
│                                                                       │
│  FAILED:                                                              │
│  "All containers terminated, at least one failed (non-zero exit)"     │
│                                                                       │
│  CRASHLOCKBACKOFF:                                                    │
│  Not a phase — it's a REASON. K8s waits longer between restarts:      │
│  10s → 20s → 40s → 80s → ...max 5min. This prevents infinite loops.  │
│                                                                       │
│  RESTART POLICIES (spec.restartPolicy):                               │
│  • Always (default for Pods): restart on any exit                     │

📦 DEEP DIVE: Init Containers & Sidecar Pattern
Pods can have THREE types of containers:

1. INIT CONTAINERS (spec.initContainers)
   • Run BEFORE app containers, run to COMPLETION
   • Run in order (init-1 finishes → init-2 starts → ...)
   • If any init fails, Pod restarts (all inits re-run)
   • USE CASES:
     - Wait for database to be ready (nc -z db 5432)
     - Run database migrations (python manage.py migrate)
     - Download files from S3 before app starts
     - Generate config files from templates

2. APP CONTAINERS (spec.containers)
   • The main application containers
   • Run for the life of the Pod
   • Can have health probes (liveness, readiness)

3. SIDECAR CONTAINERS (K8s 1.29+, initContainers with restartPolicy: Always)
   • Run ALONGSIDE the main container for the Pod's lifetime
   • USE CASES:
     - Log shipper (Fluentd/Fluent Bit → CloudWatch)
     - Service mesh proxy (Istio envoy)
     - Config reloader (watches for ConfigMap changes)
     - Metrics exporter (Prometheus sidecar)

  Example Init Container for anihpj:
  initContainers:
  - name: wait-for-db
    image: busybox
    command: ['sh', '-c', 'until nc -z anihpj-db 5432; do sleep 2; done']
  - name: migrate-db
    image: anihpj:v1
    command: ['python', 'manage.py', 'migrate']

5.4 Deployments — Managing Application Lifecycle

A Deployment is the most common way to run applications on Kubernetes. It manages ReplicaSets and provides rolling updates (gradually replace old Pods with new ones, zero downtime) and rollbacks (kubectl rollout undo — instant!).

Deployment → ReplicaSet → Pod Hierarchy

│  Deployment: anihpj (replicas: 3, strategy: RollingUpdate)  │
│  │                                                         │
│  ├── ReplicaSet: anihpj-v1-abc123  (revision 1, scaled 0) │
│  │   └── Pod × 0 (old version, no longer active)           │
│  │                                                         │
│  └── ReplicaSet: anihpj-v2-def456  (revision 2, active)    │
│      ├── Pod-1 (anihpj:v2, Node-1) ✅                      │
│      ├── Pod-2 (anihpj:v2, Node-2) ✅                      │

🚀 DEEP DIVE: Deployment Strategies — RollingUpdate vs Recreate
Deployments support TWO strategies for updating Pods:

┌──────────────────────────────────────────────────────────────────────┐
│  STRATEGY 1: RollingUpdate (default, recommended)                     │
│  ─────────────────────────────────────────────                        │
│                                                                       │
│  "Gradually replace old Pods with new ones — zero downtime!"          │
│                                                                       │
│  Timeline: anihpj v1 → v2 (3 replicas)                               │
│                                                                       │
│  Step 0: [v1] [v1] [v1]     ← all v1                                 │
│  Step 1: [v1] [v1] [v1] [v2]← v2 created (maxSurge=1)                │
│  Step 2: [v1] [v1]     [v2]← v1 removed (maxUnavailable=0)            │
│  Step 3: [v1] [v1] [v2] [v2]← another v2 created                     │
│  Step 4: [v1]     [v2] [v2]← another v1 removed                      │
│  Step 5: [v1] [v2] [v2] [v2]← last v2 created                        │

│  • maxSurge: How many EXTRA Pods can exist during update (default 25%)│
│    → maxSurge=1 means at most 4 Pods during 3-replica update          │

│    → maxUnavailable=0 means NEVER drop below 3 serving Pods!         │
│                                                                       │
│  ─────────────────────────────────────────────────────────────────    │

│  ───────────────────                                                  │
│                                                                       │
│  "Kill ALL old Pods FIRST, then create new ones — DOWNTIME!"          │
│                                                                       │
│  Step 1: [v1] [v1] [v1] → ALL deleted → ❌ SERVICE DOWN              │
│  Step 2:                → [v2] [v2] [v2] created → ✅ BACK UP         │
│                                                                       │
│  ⚠️ Only use when:                                                    │
│     • You cannot have two versions running simultaneously             │

│     • Downtime is acceptable (dev environment)                        │
│     • You need a full cleanup before starting fresh                   │
│                                                                       │

│     maxUnavailable: 0 + maxSurge: 1 = guaranteed zero-downtime.       │

🔄 DEEP DIVE: ReplicaSet Self-Healing — How It Detects Failure
How does the ReplicaSet controller KNOW a Pod died?

The ReplicaSet controller doesn't actively "ping" Pods. Instead, it
uses a WATCH MECHANISM on the API server:

1. RS Controller watches Pod events via the API server
2. kubelet on each node reports Pod status to API server
3. When kubelet detects container crash → reports "Pod-2 status: Failed"
4. API server updates etcd → fires watch event
5. RS Controller receives event: "Pod-2 Failed"
6. RS checks: "I need 3 running, Pod-2 is dead → create Pod-4"

The BEAUTY of this design:
  • RS controller does NOT connect directly to Pods
  • It does NOT ping containers
  • It ONLY watches the API server
  • If RS controller itself crashes → kubelet restarts it
  • When RS restarts, it reads DESIRED state from etcd:
    "Oh, I'm supposed to have 3 replicas!"
  • Then checks ACTUAL state: "Only 2 running"
  • Creates the 3rd — back to desired state!

💡 This is LEVEL-TRIGGERED (not edge-triggered): the controller
   doesn't care about HOW we got here — it just ensures current
   state matches desired state. This is the core of K8s resilience.

5.5 Services — Exposing Your Application

Pod IPs are ephemeral — they change when Pods restart. Services provide a stable IP address and DNS name. This is why Services exist: Pods come and go, but the Service IP stays the same.

Kubernetes offers 4 Service types, each for different use cases:

🏠
ClusterIP

Default. Internal-only IP accessible within the cluster. Used for Pod-to-Pod communication.

🚪
NodePort

Exposes the Service on each Node's IP at a static port (30000-32767). Good for dev/testing.

☁️
LoadBalancer

Creates an AWS ALB/NLB that routes external traffic to the Service. Production standard on EKS.

🔗
ExternalName

Maps a Service to an external DNS name (CNAME). Used for external services like RDS.

5.5d Ingress — Advanced Routing

While Services handle simple Layer 4 (TCP) routing, Ingress provides Layer 7 (HTTP/HTTPS) routing: path-based routing, host-based routing, TLS termination, and more. On EKS, the AWS Load Balancer Controller automatically provisions an ALB when you create an Ingress resource.

Ingress YAML — anihpj with ALB
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: anihpj-ingress
  namespace: anihpj
  annotations:
    kubernetes.io/ingress.class: "alb"
    alb.ingress.kubernetes.io/scheme: "internet-facing"
    alb.ingress.kubernetes.io/target-type: "ip"
    alb.ingress.kubernetes.io/listen-ports: '[{"HTTPS":443}]'
    alb.ingress.kubernetes.io/certificate-arn: "arn:aws:acm:..."
    alb.ingress.kubernetes.io/healthcheck-path: "/health/"
spec:
  rules:
  - host: anihpj.example.com
    http:
      paths:
      - path: /api/
        pathType: Prefix
        backend:
          service:
            name: anihpj-api-svc
            port:
              number: 80
      - path: /
        pathType: Prefix
        backend:
          service:
            name: anihpj-svc
            port:
              number: 80
💡
Service vs Ingress — Quick Decision Guide

Use Service (ClusterIP/NodePort/LoadBalancer): Simple TCP exposure, one service per port, internal communication. Use Ingress: Need path-based routing (/api vs /), host-based routing (api.example.com vs app.example.com), TLS termination at the edge, or multiple services behind one ALB. In production on EKS, you typically use BOTH: ClusterIP Service internally + Ingress/ALB externally.

Labels are key-value pairs attached to objects for organization and selection. Selectors filter objects by labels (the core mechanism connecting Services to Pods, Deployments to ReplicaSets). Annotations store non-identifying metadata for tools.

Equality vs Set-Based Selectors

Equality-based: app: anihpj, environment != production. Simple = / != matching. Used by Services and ReplicaSets.

Set-based: environment in (staging, production), tier notin (frontend, backend), app (exists check). Used by Deployments, NetworkPolicies, and Node affinity rules. More flexible for complex filtering.

# Set-based selector (kubectl)
kubectl get pods -l 'environment in (dev,staging),!critical'

A Pod running anihpj on EKS crashes. The Deployment specifies replicas: 3. What ensures that 3 Pods are running again?

Show Answer & Explanation

The ReplicaSet controller (managed by the Deployment). It continuously monitors running Pods. When actual count (2) ≠ desired (3), it creates a new Pod. This is the reconciliation loop at work.

# 6. kubelet starts new container

🔧 DEEP DIVE: How kubectl apply Actually Works
kubectl apply is NOT the same as kubectl create. Here's the difference:

┌──────────────────────────────────────────────────────────────────────┐
│  kubectl create -f deploy.yaml                                       │
│  ─────────────────────────────                                        │
│  • Sends the FULL object to API server                                │
│  • If object already exists → ERROR "already exists"                 │
│  • Use for: ONE-TIME creation (namespaces, secrets)                   │
│                                                                       │
│  kubectl apply -f deploy.yaml                                         │
│  ─────────────────────────────                                        │
│  • Stores a "last-applied-configuration" annotation on the object    │
│  • Calculates a THREE-WAY MERGE PATCH:                                │
│                                                                       │
│    1. ORIGINAL (last-applied-configuration): what YOU last sent      │
│    2. CURRENT (live object in etcd): what EXISTS now                 │
│    3. MODIFIED (your new YAML): what you WANT now                    │
│                                                                       │
│  THREE-WAY MERGE LOGIC:                                               │
│  ┌─────────────────────────────────────────────────────────────┐    │
│  │  Field in ORIGINAL | Field in MODIFIED | Field in CURRENT    │    │
│  │  ─────────────────┼───────────────────┼──────────────────── │    │
│  │  app: web         │ app: api          │ app: web → CHANGE   │    │
│  │                   │                   │ to "api" (you said) │    │
│  │  replicas: 3      │ replicas: 3       │ replicas: 5 → KEEP  │    │
│  │                   │                   │ "5" (someone else   │    │
│  │                   │                   │ changed it — and    │    │
│  │                   │                   │ you didn't touch it)│    │
│  │  memory: 256Mi    │ (removed)         │ memory: 256Mi       │    │
│  │                   │                   │ → REMOVE (you      │    │
│  │                   │                   │ deleted the field)  │    │
│  └─────────────────────────────────────────────────────────────┘    │
│                                                                       │
│  🎯 THIS is why apply is safe for teams:                              │
│     • If someone manually scaled replicas to 5, and you run apply    │
│       with replicas: 3 → it does NOT scale down! (you didn't change  │
│       it from the original)                                           │
│     • kubectl create would error. kubectl replace would overwrite.   │
│     • kubectl apply does the RIGHT thing — merge intelligently.      │
│                                                                       │
│  STRATEGIC MERGE PATCH vs JSON MERGE PATCH:                           │
│  • Strategic merge (default for apply): understands K8s semantics —  │
│    for lists of containers, uses "name" as merge key. If you add a   │
│    container with name: "sidecar", it MERGES it into the list. If    │
│    you remove a container, it removes ONLY that one by name.         │
│  • JSON merge patch (RFC 7396): simple replace. Entire list replaced │
│    as one unit. Would delete ALL containers if you sent just one.    │
│                                                                       │
│  💡 kubectl apply is the STANDARD for production. kubectl create     │
│     is for one-time setup. kubectl replace is rarely used.            │
└──────────────────────────────────────────────────────────────────────┘

Before ANY YAML is persisted to etcd, it passes through Admission
Webhooks. This is where you enforce organizational policies:

Q1

What are the 4 required top-level fields in every Kubernetes YAML manifest?

Show Answer & Explanation
✅ ANSWER

apiVersion, kind, metadata, spec. These appear in EVERY K8s YAML file regardless of resource type. status is added by K8s — you don't write it.

📖 EXPLANATION
# The 4 required fields — memorize these!
apiVersion: v1        # WHICH API version?
kind: Pod             # WHAT are you creating?
metadata:             # WHAT is it called?
  name: my-pod
spec:                 # WHAT should it do? (DESIRED STATE)
  containers: [...]
# status: {}          # K8s writes this — you don't
Q2

How do you find the correct apiVersion for a Kubernetes resource?

Show Answer & Explanation
✅ ANSWER

kubectl api-resources lists all resources and their API versions. Or use kubectl explain <resource> to see detailed field documentation.

📖 EXPLANATION
# Find apiVersion for any resource
kubectl api-resources | grep -i deploy
# deployments  deploy  apps/v1  true  Deployment

# Get detailed field docs
kubectl explain deployment.spec
kubectl explain pod.spec.containers --recursive
Q3

How do you validate a YAML file before applying it to the cluster?

Show Answer & Explanation
✅ ANSWER

kubectl apply --dry-run=server -f manifest.yaml. This sends the YAML to the API server for full validation but doesn't persist it. --dry-run=client only validates syntax locally.

📖 EXPLANATION
# Validate before applying
kubectl apply --dry-run=server -f deploy.yaml  # Full server validation
kubectl apply --dry-run=client -f deploy.yaml  # Client-side only

# If validation passes, apply for real:
kubectl apply -f deploy.yaml
Q4

What's the correct apiVersion for a Deployment?

Show Answer & Explanation
✅ ANSWER

apps/v1. Deployments moved from extensions/v1beta1 to apps/v1 in Kubernetes 1.16. Always use apps/v1 — the old versions are removed.

📖 EXPLANATION
# Correct (K8s 1.16+):
apiVersion: apps/v1
kind: Deployment

# DEPRECATED — do not use:
apiVersion: extensions/v1beta1  # Removed in 1.16
apiVersion: apps/v1beta1        # Removed in 1.16
apiVersion: apps/v1beta2        # Removed in 1.19
Q5

Can you define multiple Kubernetes resources in a single YAML file?

Show Answer & Explanation
✅ ANSWER

Yes — use --- (triple dash) as a document separator. Each section between --- markers is a separate YAML document. kubectl apply -f processes all documents in order.

📖 EXPLANATION
# multi-resource.yaml — apply with one command
---
apiVersion: v1
kind: Namespace
metadata:
  name: anihpj
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: anihpj
  namespace: anihpj
spec:
  replicas: 3
# ...
---
apiVersion: v1
kind: Service
metadata:
  name: anihpj
  namespace: anihpj
# ...

# Apply ALL at once:
kubectl apply -f multi-resource.yaml
Additional Practice Questions (Q6–Q10)

Q6. What is the difference between spec.selector and spec.template.metadata.labels in a Deployment YAML?

Answer: spec.selector.matchLabels tells the Deployment which Pods to manage (must match existing Pods). spec.template.metadata.labels defines labels on new Pods the Deployment creates. They must match, or the Deployment will reject the YAML.

Q7. Write a YAML snippet that sets environment variables DJANGO_SECRET_KEY from a Secret and DB_HOST from a ConfigMap in a container.

Answer: 
env:
- name: DJANGO_SECRET_KEY
  valueFrom:
    secretKeyRef:
      name: anihpj-secret
      key: secret-key
- name: DB_HOST
  valueFrom:
    configMapKeyRef:
      name: anihpj-config
      key: db-host

Q8. What does kubectl explain deployment.spec.strategy do, and why is it useful for YAML writing?

Answer: kubectl explain shows the schema, documentation, and valid values for any Kubernetes resource field — right from the CLI. It's the fastest way to check field names, types, and nesting without leaving the terminal. Use --recursive to see all nested fields.

Q9. What's wrong with this YAML snippet? 

spec:
replicas: 3
selector:
matchLabels:
app: nginx

Answer: The indentation is wrong. replicas should be indented under spec, and matchLabels should be indented under selector. YAML uses spaces (not tabs) and proper nesting is critical. Correct version: 
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx

Q10. You applied a YAML file and nothing changed. You check with kubectl diff -f deploy.yaml and see no output. What does this mean?

Answer: kubectl diff compares the YAML file with what's currently running. No output means the live state already matches the file — nothing would change if applied. This is a best practice before applying changes to verify what exactly will change. Use kubectl diff -f <file> before every kubectl apply in production!
