    AWS DEVOPS EXAM STRATEGY — TOP 10 MISTAKES TO AVOID
    ─────────────────────────────────────────────────────
    ┌──────────────────────────────────────────────────────────────┐
    │  ❌ COMMON MISTAKES                 ✅ WHAT TO DO INSTEAD    │
    │                                                              │
    │  1. Memorizing YAML by heart       Use kubectl create       │
    │                                     --dry-run=client -o yaml│
    │                                                              │
    │  2. Ignoring K8s on the exam       ~50% of scenarios involve│
    │     (thinking it's only EC2/Lambda)  ECS, EKS, or containers │
    │                                                              │
    │  3. Forgetting IAM roles for pods  Always use IRSA (IAM     │
    │     (using node-level credentials)  Roles for Service Accts) │
    │                                                              │
    │  4. Not knowing CloudFormation      IaC is 17% of the exam!  │
    │     intrinsic functions             Know !Ref, !Sub, !Join   │
    │                                                              │
    │  5. Skipping deployment strategies  Blue/Green, Canary,      │
    │     (CodeDeploy + Lambda hooks)     All-at-Once — know all   │
    │                                                              │
    │  6. Ignoring cost optimization      Spot instances, Savings  │
    │     (it's embedded in scenarios)    Plans, Graviton instances│
    │                                                              │
    │  7. Not reading CloudWatch logs     Log Insights, Metrics    │
    │     query syntax carefully          Filter, Contributor      │
    │                                     Insights are tested      │
    │                                                              │
    │  8. Confusing CloudTrail vs Config  Trail = API audit log    │
    │                                     Config = resource history│
    │                                                              │
    │  9. Forgetting multi-account        AWS Organizations,       │
    │     strategy patterns               Control Tower, SCPs      │
    │                                                              │
    │  10. Not doing hands-on labs        killer.sh, EKS Workshop, │
    │      (reading alone won't pass)     AWS DevOps workshops     │
    └──────────────────────────────────────────────────────────────┘

    The anihpj & jobpost Project — Your Learning Companion
    ──────────────────────────────────────────────────────
    • anihpj = The Django PROJECT (the whole thing: settings, URLs, WSGI)

    • Models: Skills, User, Author, Location, JobPost

         ┌────────────────────────────────────────────────────────────────────┐

         │                                                                     │
         │  ┌──────────────────────────────────────────────────────────────┐  │
         │  │ STEP 1: 👨‍💻 You run:                                            │  │
         │  │   kubectl apply -f deployment.yaml                            │  │
         │  │   "I want 3 anihpj Pods with image anihpj:v1"                 │  │
         │  └───────────────────────────┬──────────────────────────────────┘  │
         │                              │ HTTPS request                        │
         │                              ▼                                      │
         │  ┌──────────────────────────────────────────────────────────────┐  │
         │  │ STEP 2: 📡 kube-apiserver                                     │  │
         │  │   • Authenticates you (kubeconfig cert / IAM / OIDC)           │  │
         │  │   • Authorizes you (RBAC: can you create Deployments?)        │  │
         │  │   • Validates the YAML (is apiVersion correct? kind valid?)   │  │
         │  │   • If OK → accepts request                                    │  │
         │  └───────────────────────────┬──────────────────────────────────┘  │
         │                              │ write                                │
         │                              ▼                                      │
         │  ┌──────────────────────────────────────────────────────────────┐  │
         │  │ STEP 3: 💾 etcd (The Cluster Memory)                          │  │
         │  │   • Stores: "Deployment anihpj, desired: 3 replicas"           │  │
         │  │   • This is now the DESIRED STATE                             │  │
         │  │   • RAFT consensus: written to majority of etcd nodes         │  │
         │  └───────────────────────────┬──────────────────────────────────┘  │
         │                              │ watch event                          │
         │                              ▼                                      │
         │  ┌──────────────────────────────────────────────────────────────┐  │
         │  │ STEP 4: 🔄 Deployment Controller (in kube-controller-manager) │  │
         │  │   • "New Deployment! I need to create a ReplicaSet..."        │  │
         │  │   • Creates ReplicaSet object → writes back to API server     │  │
         │  └───────────────────────────┬──────────────────────────────────┘  │
         │                              │ watch event                          │
         │                              ▼                                      │
         │  ┌──────────────────────────────────────────────────────────────┐  │
         │  │ STEP 5: 🔄 ReplicaSet Controller                              │  │
         │  │   • "ReplicaSet anihpj-7d8f9 × 3 replicas needed"             │  │
         │  │   • "Currently 0 Pods → create 3 Pod objects"                 │  │
         │  │   • Creates 3 Pods (status: Pending, no node assigned yet)    │  │
         │  └───────────────────────────┬──────────────────────────────────┘  │
         │                              │ watch event                          │
         │                              ▼                                      │
         │  ┌──────────────────────────────────────────────────────────────┐  │
         │  │ STEP 6: 🎯 kube-scheduler                                     │  │
         │  │   • "3 Pods need a home! Which nodes have space?"             │  │
         │  │   │ FILTER: Remove nodes that can't fit:                       │  │
         │  │   │  • Node 1: tainted (NoSchedule) → REMOVED                 │  │
         │  │   │  • Node 2: only 128Mi free (needs 256Mi) → REMOVED        │  │
         │  │   │  • Node 3: 4Gi free, no taints → CANDIDATE ✅            │  │
         │  │   │ SCORE: Rank candidates by fit                             │  │
         │  │   │  • Node 3: score 9.2/10 → ASSIGNED!                      │  │
         │  │   • Binds Pod anihpj-7d8f9-x1 to Node 3                       │  │
         │  └───────────────────────────┬──────────────────────────────────┘  │
         │                              │ pod.spec.nodeName = "node-3"         │
         │                              ▼                                      │
         │  ┌──────────────────────────────────────────────────────────────┐  │
         │  │ STEP 7: 🏗️ kubelet (on Node 3)                                │  │
         │  │   • "New Pod assigned to me! Let me start it..."              │  │
         │  │   │ 1. Call CRI (containerd): "Pull image anihpj:v1"          │  │
         │  │   │    → containerd pulls from ECR (or local cache)           │  │
         │  │   │ 2. Create container from image                            │  │
         │  │   │ 3. Start container (runs gunicorn, port 8000)             │  │
         │  │   │ 4. Run liveness/readiness probes if defined               │  │
         │  └───────────────────────────┬──────────────────────────────────┘  │
         │                              │ report status                        │
         │                              ▼                                      │
         │  ┌──────────────────────────────────────────────────────────────┐  │
         │  │ STEP 8: 📡 kubelet → API server → etcd                        │  │
         │  │   • "Pod anihpj-7d8f9-x1 is now RUNNING on Node 3!"          │  │
         │  │   • ACTUAL STATE now matches DESIRED STATE for this Pod      │  │
         │  └───────────────────────────┬──────────────────────────────────┘  │
         │                              │                                      │
         │                              ▼                                      │
         │  ┌──────────────────────────────────────────────────────────────┐  │
         │  │ STEP 9: 🚦 kube-proxy (on ALL nodes)                          │  │
         │  │   • "New Pod with IP 10.0.3.45 on port 8000! Updating rules" │  │
         │  │   • Updates iptables/IPVS: traffic to Service → this Pod     │  │
         │  │   • Now users hitting the ALB → Service → Pod get response!  │  │
         │  └──────────────────────────────────────────────────────────────┘  │
         │                                                                     │
         │  ⏱️ TOTAL TIME: ~2 seconds (image cached) to ~60 sec (large pull)   │
         │  🔁 Steps 6-9 repeat for EACH of the 3 Pod replicas!               │
         │  🔍 Run: kubectl get events --watch to see this live!              │
         └────────────────────────────────────────────────────────────────────┘

Chapter 12: CI/CD Fundamentals — Concepts & Strategies                🟡 🎯
--------------------------------------------------------------------------------
    12.1 What is CI/CD?
         - Continuous Integration: merge code frequently, run automated tests
         - Continuous Delivery: every change is releasable
         - Continuous Deployment: every change goes to production automatically
         [CI/CD PIPELINE DIAGRAM: Code → Build → Test → Deploy → Monitor]

    12.2 Deployment Strategies — Complete Guide
         12.2a All-at-Once (In-Place)
               - Stop old, start new — downtime!
               - Fastest but riskiest
         12.2b Rolling Update
               - Replace instances one by one, zero downtime
               - Default in Kubernetes Deployments
               [DIAGRAM: Rolling update — Pod-by-Pod replacement]
         12.2c Blue/Green Deployment
               - Two identical environments, switch traffic at once
               - Instant rollback by switching back
               - Requires double capacity during deploy
               [DIAGRAM: Blue → Green traffic switch via Route 53/ALB]
         12.2d Canary Deployment
               - Send small % of traffic to new version
               - Gradually increase if metrics are healthy
               - Advanced: automated rollback if errors spike
               [DIAGRAM: Canary — 10% → 25% → 50% → 100% traffic shifting]
         12.2e A/B Testing
               - Route users based on cookies/headers
               - Compare metrics between variants
         12.2f Linear (Traffic Shifting)
               - CodeDeploy Lambda/ECS — increment traffic in steps
         [COMPARISON TABLE: All 6 deployment strategies — risk, speed, rollback ease]

    12.3 CI/CD Best Practices
         - Small, frequent commits (merge daily, not weekly)
         - Fast feedback loops (tests must complete in < 10 minutes)
         - Immutable infrastructure (never patch, always rebuild)
         - Everything as code (pipelines, infrastructure, config)
         - Shift left (security, testing, compliance as early as possible)
