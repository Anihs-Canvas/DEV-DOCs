1.1 The Problem Docker Solves

Imagine you've built anihpj — a Django app with a jobpost module listing jobs filtered by Skills, Location, and Author. It works perfectly on your laptop. But when a teammate clones the repo, it crashes because they have Python 3.8 instead of 3.11. Or the staging server has Django 4.2 instead of 5.2. Or production has a different version of psycopg2.

This is "dependency hell" — the universal developer frustration. Docker solves this by packaging your app AND all its dependencies into a single, standardized unit called a container that runs identically everywhere.

1.2 What is Docker? (The Simple Answer)

Docker is a platform for building, shipping, and running containers. A container is a lightweight, standalone, executable package that includes everything needed to run a piece of software: code, runtime, system tools, libraries, and settings.

The best analogy is shipping containers in the physical world. Before standardized shipping containers, every item (cars, furniture, food) had to be loaded differently onto ships, trucks, and trains. After standardization, any container fits on any ship, truck, or train — regardless of what's inside. Docker does the same for software.

1.3 Containers vs Virtual Machines — The Critical Difference

Understanding the difference between containers and VMs is fundamental. They solve similar problems but in completely different ways.

Virtual Machines virtualize the hardware — each VM runs a full guest OS with its own kernel. This gives strong isolation but is heavy (GBs of RAM, minutes to boot).

Containers virtualize the operating system — all containers share the host's kernel. This makes them lightweight (MBs, seconds to start) but with slightly weaker isolation.

🐳 Docker Client

The CLI tool you interact with. Sends commands to the daemon via REST API over a Unix socket (/var/run/docker.sock) or TCP.

⚙️ Docker Daemon (dockerd)

The background service that does the actual work: building images, running containers, managing networks and volumes. Uses containerd as the container runtime.

🗄️ Docker Registry

Stores and distributes Docker images. Docker Hub is the default public registry. Private options include Amazon ECR, Google Artifact Registry, Azure ACR, and GitHub Container Registry.

🔧 Under the Hood — How the Daemon Actually Runs Containers: containerd → runc → OCI Runtime
🗺️ The Container Runtime Chain

When you run docker run, here's the actual chain of components:

  ┌──────────────────────────────────────────────────────────────────────────┐
  │                     🔧 DOCKER DAEMON INTERNALS                            │
  │                                                                          │
  │  dockerd ───▶ containerd ───▶ containerd-shim ───▶ runc ───▶ Container  │
  │  (API,       (Image mgmt,     (Handles stdio,     (OCI      (Your app)   │
  │   Build,      Pull/Push,      exit signals,       runtime,              │
  │   Network)    Lifecycle)      keeps container     creates               │
  │                               alive after         namespaces)            │
  │                               dockerd restart)                           │
  │                                                                          │
  │  Key: dockerd manages HIGH-LEVEL stuff (API, build, networking)          │
  │        containerd manages MID-LEVEL (image pull/push, lifecycle)         │
  │        runc does the LOW-LEVEL (creates namespaces, cgroups, starts proc)│
  └──────────────────────────────────────────────────────────────────────────┘

dockerd — The Docker daemon. Handles the Docker API, builds images, manages networks. Does NOT directly run containers.

containerd — The container runtime. Manages the complete container lifecycle: image transfer, container execution, storage, and networking. Originally spun out from Docker, now a CNCF graduated project used by Kubernetes too.

containerd-shim — A small process that stays between containerd and the container. Allows containerd to be restarted without killing running containers, and handles STDIO.

runc — The OCI runtime. Creates and starts containers by setting up Linux namespaces (PID, NET, MNT, IPC, UTS, USER, CGROUP) and cgroups. This is where the actual Linux magic happens.

📖 Why This Matters for DCA

The DCA exam expects you to understand this architecture chain, especially for the Installation & Configuration domain (15%). Questions may ask about containerd's role, how to configure the daemon (daemon.json), or what happens when you restart dockerd (shim keeps containers alive).

📝 Chapter 1 — DCA Practice Questions

Q1
What is the primary problem that Docker solves in software development?
Show Answer & Explanation
ANSWER

Docker solves the "works on my machine" problem by packaging applications and ALL their dependencies into standardized containers that run identically across any environment — development, staging, and production.

EXPLANATION

Before Docker, each environment (dev, staging, prod) could have different OS versions, library versions, and configurations. A container bundles the application code WITH its exact runtime environment, ensuring consistency everywhere.

Q2
What is the key architectural difference between containers and virtual machines?
Show Answer & Explanation
ANSWER

Virtual Machines virtualize the HARDWARE and each runs a full guest OS with its own kernel. Containers virtualize the OPERATING SYSTEM and share the host's kernel.

EXPLANATION

This is why containers are so much lighter: they don't need to boot a full OS, don't need a hypervisor, and can share memory and disk resources. A VM needs GBs of RAM for the guest OS alone; a container adds only MBs on top of the host.

Q3
Name the three main components of Docker's architecture and their roles.
Show Answer & Explanation
ANSWER

1. Docker Client — CLI that sends commands to the daemon via REST API.
2. Docker Daemon (dockerd) — Background service that builds images, runs containers, manages networks/volumes.
3. Docker Registry — Stores and distributes images (Docker Hub, ECR, etc.)

EXPLANATION

The client and daemon can run on the same machine or different machines. Communication happens over a Unix socket (default: /var/run/docker.sock) or TCP. The registry is where images are pushed to and pulled from — Docker Hub being the default public registry.

Q4
A developer says "Docker containers are just like lightweight VMs." Is this accurate? Explain.
Show Answer & Explanation
ANSWER

Not accurate. While both provide isolation, containers share the host OS kernel and do NOT include a full operating system. VMs each have their own kernel, making them fundamentally different architecturally.

EXPLANATION

This misunderstanding is common. Containers feel like VMs because they provide process isolation, but under the hood they use Linux namespaces and cgroups — NOT hardware virtualization. This is why you can't run a Windows container on a Linux host (kernel must match).

Q5
Which container runtime does modern Docker use, and what is its role?
Show Answer & Explanation
ANSWER

Modern Docker uses containerd as the container runtime. containerd manages the complete container lifecycle: image transfer, container execution, storage, and networking. It uses runc (an OCI-compliant runtime) to actually create and start containers.

EXPLANATION

Docker's architecture evolved: originally dockerd did everything. Now dockerd delegates to containerd, which delegates to runc. This modular design means you can swap components (e.g., use CRI-O instead of containerd in Kubernetes).

Q6
What is Docker Hub? How does it differ from a private registry like Amazon ECR?
Show Answer & Explanation
ANSWER

Docker Hub is Docker's public registry — anyone can pull public images and push their own (with an account). Private registries like Amazon ECR, Google Artifact Registry, or Azure ACR are hosted within your cloud account, offering better security, lower latency, and integration with your cloud's IAM.

EXPLANATION

For production, you typically use a private registry close to your deployment environment. ECR ensures your images stay within your AWS VPC, reducing pull latency and eliminating public exposure. Docker Hub is great for development and sharing open-source images.

Q7
You can run 100 containers on a single host. How many VMs could you typically run on the same hardware?
Show Answer & Explanation
ANSWER

Typically only 5-15 VMs on the same hardware that can run 100+ containers. Containers share the host kernel and use MBs of RAM each, while each VM needs GBs for its own OS.

EXPLANATION

This is the "density advantage" of containers. A 16GB RAM server can run ~10 VMs (each needing ~1.5GB OS overhead) but can run 100+ containers (each adding only ~50MB). This is why cloud-native architectures favor containers.

Q8
What are Docker Desktop, Docker Engine, and Docker Compose? How do they relate?
Show Answer & Explanation
ANSWER

Docker Engine = core (daemon + CLI + containerd). Docker Desktop = Engine + GUI + Kubernetes + Scout + Compose bundled for dev machines. Docker Compose = tool for defining multi-container apps with YAML — included in Desktop, installable separately on Linux.

EXPLANATION

Docker Desktop is the "batteries included" package for development. On production Linux servers, you typically install only Docker Engine. Compose is always useful (dev AND production-like environments), but on production you'd more likely use Kubernetes or Swarm for orchestration.

Q9
A container is deleted. What happens to the data inside the container?
Show Answer & Explanation
ANSWER

By default, ALL data inside a container is lost permanently when the container is deleted. Containers are ephemeral by design. To persist data, you must use Docker volumes or bind mounts — these exist independently of the container.

EXPLANATION

This is a critical concept for the DCA exam. A common mistake is storing database data inside the container without a volume. The mantra: "Containers are cattle, not pets." They should be disposable. Persistent data belongs in volumes.

Q10
Which Docker tool would you use to scan images for vulnerabilities before pushing to production?
Show Answer & Explanation
ANSWER

Docker Scout — built into Docker Desktop and available as a CLI command: docker scout quickview <image>. It analyzes image layers, identifies known vulnerabilities (CVEs), and provides remediation recommendations.

EXPLANATION

Docker Scout replaced the older docker scan command. It integrates with Docker Hub and can be used in CI/CD pipelines. Alternative tools include Trivy (Aqua Security, open source) and Snyk. The DCA exam may test knowledge of image scanning as part of the Security domain (15%).

2.1 Docker Images — The Blueprint

A Docker image is a read-only template containing your application code, runtime, libraries, environment variables, and configuration files. Think of an image as a class in programming — it's a blueprint. A container is an instance of that class — a running object.

Images are identified by repository:tag (e.g., anihpj:v1.0, python:3.11-slim). If no tag is specified, Docker defaults to :latest.

2.2 Docker Containers — The Running Instance

A container is a runnable instance of an image. You can create, start, stop, move, or delete a container using the Docker CLI. Containers are ephemeral by design — treat them like cattle, not pets. If one dies, you spin up a new one from the same image.

Key characteristics: containers are isolated (process, network, filesystem), lightweight (share host kernel), and portable (run anywhere Docker runs).

2.4 Image Layers — The Secret to Docker's Speed

Each instruction in a Dockerfile creates a layer. Layers are stacked to form the final image. Layers are cached — if a layer hasn't changed, Docker reuses it instead of rebuilding. This is why Docker builds are so fast after the first one.

Docker Image Layer Cake — anihpj Example
  ┌───────────────────────────────────────────────┐
  │  Layer 6 (R/W): Container Writable Layer      │  ← Container-only (ephemeral!)
  ├───────────────────────────────────────────────┤
  │  Layer 5: CMD ["gunicorn", "anihpj.wsgi:app"] │  ← Startup command (~0 bytes)
  ├───────────────────────────────────────────────┤
  │  Layer 4: COPY . /app/                        │  ← Your code! (~500 KB)
  │  (models.py, views.py, urls.py, settings.py)  │
  ├───────────────────────────────────────────────┤
  │  Layer 3: RUN pip install -r requirements.txt │  ← Dependencies (~80 MB)
  │  (Django 5.2, gunicorn, psycopg2, etc.)      │
  ├───────────────────────────────────────────────┤
  │  Layer 2: COPY requirements.txt .             │  ← Deps list (~200 bytes)
  ├───────────────────────────────────────────────┤
  │  Layer 1: FROM python:3.11-slim               │  ← Base image (~150 MB)
  │  (Debian 12 + Python 3.11)                    │
  └───────────────────────────────────────────────┘
💡 Layer Caching Strategy

Order your Dockerfile from LEAST to MOST frequently changing. Copy requirements.txt BEFORE copying your source code. This way, when you change your code (Layer 4), Layers 1-3 remain cached — saving minutes of rebuild time!

🔧 Under the Hood — Copy-on-Write (CoW) and Union Filesystems (Overlay2)
🗺️ How Docker Stores Images Efficiently

Docker uses two key Linux technologies to make images fast and space-efficient:

Copy-on-Write (CoW) — When a container modifies a file from the image, Docker doesn't copy the entire image. Instead, it copies ONLY the specific file being modified to the container's writable layer. This means 100 containers from the same image share 99.9% of the storage — only their changes take extra space.

  ┌──────────────────────────────────────────────────────────────────────────┐
  │                   📋 COPY-ON-WRITE (CoW) IN ACTION                         │
  │                                                                          │
  │  Image Layers (READ-ONLY, shared)       Container Layer (READ-WRITE)      │
  │  ┌─────────────────────────────┐       ┌─────────────────────────────┐   │
  │  │ /app/models.py   ← SHARED │       │ (no copy needed!)           │   │
  │  │ /app/views.py    ← SHARED │       │                             │   │
  │  │ /usr/lib/python  ← SHARED │       │                             │   │
  │  │ /etc/os-release  ← SHARED │──COPY▶│ /etc/os-release (modified)  │   │
  │  │                  100 containers     │ ← ONLY this file copied!    │   │
  │  │                  share these!       │   (rest still shared)       │   │
  │  └─────────────────────────────┘       └─────────────────────────────┘   │
  └──────────────────────────────────────────────────────────────────────────┘

Union Filesystem (Overlay2) — The default storage driver. It "stacks" the read-only image layers and the read-write container layer into a single unified view. The container sees one filesystem, but it's actually composed of multiple layers. Overlay2 uses:

  • LowerDir — The read-only image layers (your Dockerfile instructions)
  • UpperDir — The writable container layer (changes made at runtime)
  • Merged — The unified view the container sees (LowerDir + UpperDir combined)
  • WorkDir — Internal working directory for Overlay2 operations

2.5 Tags and Versioning

A tag is a human-readable label for a specific version of an image. The :latest tag is convenient but dangerous — it always points to the most recent build, which can cause unexpected changes in production.

2.6 Docker Manifest and Multi-Architecture Images

A manifest is a JSON file that describes an image — its layers, digests, architecture, and OS. Multi-architecture images use a manifest list to point to different platform-specific images. One tag (anihpj:v1) can serve linux/amd64, linux/arm64, and windows/amd64 — Docker automatically pulls the right one for your platform.

📖 Buildx for Multi-Arch

Use docker buildx build --platform linux/amd64,linux/arm64 -t anihpj:v1 . to build a single tag that works on both Intel/AMD and Apple Silicon (M1/M2/M3) machines. This is essential for modern development teams with mixed hardware.

Q1
What is the relationship between a Docker image and a Docker container?
Show Answer & Explanation
ANSWER

An image is a read-only template (like a class). A container is a runnable instance of an image (like an object). One image can spawn many containers, just as one class can create many objects.

Q2
How do Docker image layers work, and why does layer order matter?
Show Answer & Explanation
ANSWER

Each Dockerfile instruction creates a read-only layer. Layers are cached. If a layer changes, ALL layers after it are rebuilt. Therefore, put frequently-changing layers (source code) LAST and rarely-changing layers (base image, dependencies) FIRST.

Q3
What is the difference between Docker Hub and a private registry like ECR?
Show Answer & Explanation
ANSWER

Docker Hub is a public registry with free tier. Private registries (ECR, GCR, ACR) are cloud-managed, provide lower latency, better security (IAM integration), and are typically used for production workloads.

Q4
What are the valid states in a container's lifecycle?
Show Answer & Explanation
ANSWER

Created → Running → Paused / Stopped → Deleted. A container starts as "created" (on disk but not started), transitions to "running," can be "paused" (frozen) or "stopped" (exited), and finally "deleted" (gone).

Q5
Why is the :latest tag considered dangerous for production?
Show Answer & Explanation
ANSWER

:latest is mutable — it points to whatever was most recently built/pushed. This means docker pull anihpj:latest can silently pull a completely different version than expected, causing production incidents. Always use explicit version tags.

Q6
What is a multi-architecture image and how is it built?
Show Answer & Explanation
ANSWER

A multi-architecture image uses a manifest list to serve different platform-specific images (amd64, arm64) under a SINGLE tag. Built with docker buildx build --platform linux/amd64,linux/arm64 -t anihpj:v1 .

Q7
What happens to data stored inside a container when the container is deleted?
Show Answer & Explanation
ANSWER

All data inside the container's writable layer is permanently lost. Only data stored in Docker volumes or bind mounts survives container deletion. This is by design — containers are meant to be ephemeral.

Q8
What command authenticates you to a private Docker registry?
Show Answer & Explanation
ANSWER

docker login <registry-url> — e.g., docker login (Docker Hub), docker login ghcr.io (GitHub), or aws ecr get-login-password | docker login --username AWS --password-stdin <aws-account-id>.dkr.ecr.region.amazonaws.com (ECR).

Q9
How does Docker's layer caching decide whether to rebuild a layer?
Show Answer & Explanation
ANSWER

Docker compares the instruction text AND the files being copied (checksums). If either changed, the layer is rebuilt — and ALL SUBSEQUENT layers are also rebuilt. This is why order matters: keep frequently-changing layers at the bottom.

Q10
What is an image digest and why is it more reliable than a tag?
Show Answer & Explanation
ANSWER

An image digest is a SHA256 hash of the image's content — it's immutable. Tags like :latest can be moved to point to different images, but a digest always identifies the EXACT same image. Use anihpj@sha256:abc123... for guaranteed reproducibility.

3.1 Installing Docker Desktop (Windows/Mac)

Docker Desktop is the recommended way to run Docker on development machines. It includes Docker Engine, Docker Compose, Kubernetes, Docker Scout, and a GUI dashboard — all in one package.

📖 Installation Steps

1. Download from docker.com
2. Run the installer (Windows: enable WSL2 if prompted — Docker Desktop uses WSL2 as its Linux backend for better performance)
3. Launch Docker Desktop — the whale icon appears in your system tray
4. Open a terminal and verify: docker --version and docker run hello-world

💡 Windows + WSL2

On Windows, Docker Desktop runs inside WSL2 (Windows Subsystem for Linux 2). This gives you a real Linux kernel, near-native performance, and full compatibility with Linux containers. Make sure WSL2 is installed and set as the default: wsl --install and wsl --set-default-version 2.

3.2 Installing Docker Engine on Linux

For Linux servers, install Docker Engine directly (no Desktop GUI). The process varies by distribution:

📖 Ubuntu/Debian

sudo apt-get update && sudo apt-get install docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
Then: sudo usermod -aG docker $USER (add yourself to docker group, log out and back in)
Start on boot: sudo systemctl enable docker

📖 CentOS/RHEL/Fedora

sudo yum install docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
Then: sudo systemctl enable --now docker

💡 Verify Installation

After installation, verify with: docker --version (shows client + server version) and docker info (shows detailed system info including Storage Driver, Cgroup Driver, number of containers/images). Both must succeed before proceeding.

3.3 Your First Docker Command — Hello World

The docker run hello-world command is the "Hello World" of Docker. It pulls a tiny image (~13KB), runs it, and prints a message confirming Docker is working. Let's understand exactly what happens:

docker run hello-world — 5 Steps
  ┌──────────────────────────────────────────────────────────────────────────┐
  │              ⚡ docker run hello-world — WHAT ACTUALLY HAPPENS              │
  │                                                                          │
  │  1. You type: $ docker run hello-world                                   │
  │  2. Docker Client sends command to Docker Daemon (dockerd)               │
  │  3. Daemon checks local images → "hello-world" NOT FOUND                 │
  │  4. Daemon PULLS hello-world image from Docker Hub (~13 KB)              │
  │  5. Daemon creates a container FROM the image → runs → prints message → EXITS│
  └──────────────────────────────────────────────────────────────────────────┘
💡 Key Insight

Notice that Docker automatically PULLS the image when it's not found locally. You don't need to run docker pull separately. Every docker run implicitly checks local images first, then pulls from the registry if needed.

🔧 Under the Hood — Linux Namespaces & cgroups: How Docker Actually Isolates Containers
🗺️ The Two Linux Kernel Features That Make Containers Possible

Docker containers aren't magic — they're built on two Linux kernel features that have existed since the mid-2000s. Understanding these helps you grasp why containers are lightweight (they use kernel features, not hardware virtualization).

1. Linux Namespaces — "What You Can See"

Namespaces limit what a process can see. Each container gets its own set of namespaces, making it think it's the only thing running on the system. There are 7 types:

NamespaceWhat It IsolatesContainer Effect
PIDProcess IDsContainer sees its own PID 1 (init), can't see host processes
NETNetwork interfacesContainer has its own eth0, routing table, iptables
MNTMount pointsContainer has its own root filesystem view
UTSHostname, domainContainer can have its own hostname
IPCInter-process communicationContainer's shared memory is isolated
USERUser/group IDsUID 0 (root) in container ≠ root on host (with userns)
CGROUPControl group viewContainer sees only its own cgroup limits
2. Control Groups (cgroups) — "What You Can Use"

cgroups limit what a process can use. They enforce resource limits so one container can't hog all the CPU or RAM. When you type docker run --memory=512m --cpus=1.5, Docker configures cgroups behind the scenes.

4.4 Building an anihpj Dockerfile — Step by Step

Let's build the complete Dockerfile for our anihpj Django application. Every line is explained:

DOCKERFILE
# Step 1: Choose the base image
# python:3.11-slim = Debian + Python 3.11, stripped down (~150 MB)
# Why slim not alpine? Alpine uses musl libc, can cause issues with some Python packages
FROM python:3.11-slim

# Step 2: Set working directory (all subsequent commands run here)
WORKDIR /app

# Step 3: Copy requirements FIRST (layer caching trick!)
# If requirements.txt hasn't changed, this layer is CACHED
COPY requirements.txt .

# Step 4: Install dependencies
# --no-cache-dir: don't cache pip packages (saves ~100 MB in image)
RUN pip install --no-cache-dir -r requirements.txt

# Step 5: Copy application code (changes most often, so goes LAST)
COPY . .

# Step 6: Set environment variables
ENV PYTHONDONTWRITEBYTECODE=1 \    # Don't generate .pyc files
    PYTHONUNBUFFERED=1 \            # Don't buffer stdout (better logging)
    DJANGO_SETTINGS_MODULE=anihpj.settings

# Step 7: Document the port (does NOT publish it — use -p flag with docker run)
EXPOSE 8000

# Step 8: Command to run when container starts
CMD ["gunicorn", "anihpj.wsgi:application", "--bind", "0.0.0.0:8000", "--workers", "3"]
📖 Why This Order?

The order is intentional: FROM (never changes) → requirements.txt (rarely changes) → pip install (rarely changes) → source code (changes constantly). This maximizes layer caching. When you edit views.py, only the last COPY layer rebuilds — everything else is cached!

5.3 Layer Caching Deep Dive

Layer caching is Docker's superpower. When rebuilding, Docker checks if each instruction's result is already cached. If it is, Docker SKIPS that instruction and uses the cached layer. This is why smart Dockerfiles rebuild in seconds.

Cache Hit vs Cache Miss
  ┌──────────────────────────────────────────────────────────────────────────┐
  │               🏎️ LAYER CACHING — WHY ORDER MATTERS                        │
  │                                                                          │
  │  BAD ORDER (cache useless after code change):                            │
  │  ┌──────────────────────────┬─────────────────────────────────┐         │
  │  │ FROM python:3.11-slim    │ ✅ CACHED (never changes)        │         │
  │  │ COPY . /app/             │ ❌ REBUILT (code changed!)       │         │
  │  │ COPY requirements.txt .  │ ❌ REBUILT (previous changed)    │         │
  │  │ RUN pip install -r req.. │ ❌ REBUILT (rerun install!)     │         │
  │  └──────────────────────────┴─────────────────────────────────┘         │
  │                                                                          │
  │  GOOD ORDER (only changed layers rebuilt):                               │
  │  ┌──────────────────────────┬─────────────────────────────────┐         │
  │  │ FROM python:3.11-slim    │ ✅ CACHED (never changes)        │         │
  │  │ COPY requirements.txt .  │ ✅ CACHED (same requirements)    │         │
  │  │ RUN pip install -r req.. │ ✅ CACHED (same install)         │         │
  │  │ COPY . /app/             │ ❌ REBUILT (only code changed!) │         │
  │  └──────────────────────────┴─────────────────────────────────┘         │
  │                                                                          │
  │  RESULT: Good = 3 layers cached (~3 sec) | Bad = 4 layers rebuilt (~45s)│

📖 Containers Are "Cattle, Not Pets"

In traditional server management, servers are treated like pets — you name them, nurse them back to health, and panic when they go down. Containers are cattle — you number them, expect them to die, and automatically replace them from the same image. This mindset shift is fundamental to Docker: never manually fix a broken container; just docker rm it and docker run a fresh one from the same image.

TERMINAL
# Create a container (but don't start it)
$ docker create --name anihpj-dev anihpj:v1

# Start a stopped container
$ docker start anihpj-dev

# Stop a running container (SIGTERM, then SIGKILL after grace period)
$ docker stop anihpj-dev

# Force kill immediately (SIGKILL)
$ docker kill anihpj-dev

# Pause / Unpause (freeze all processes)
$ docker pause anihpj-dev
$ docker unpause anihpj-dev

# Restart a container
$ docker restart anihpj-dev

# Remove a container (must be stopped first, or use -f)
$ docker rm anihpj-dev
$ docker rm -f anihpj-dev  # Force remove (even if running)

7.4 Saving & Loading Images (Offline Transfer)

CommandWhat It DoesUse Case
