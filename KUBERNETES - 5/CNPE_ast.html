💡 Understanding "Why" Matters on the CNPE Exam

The CNPE is a performance-based exam (2 hours, hands-on tasks). While Chapter 1 is conceptual, understanding why we build platforms helps you make the right design decisions. Key concepts to internalize:

  • Cognitive Load — Developers shouldn't need to know 12 different tools to deploy code. Your platform reduces this to "push and done."
  • Platform as a Product — Treat your platform like a product with real customers (developers). Measure adoption, satisfaction, and time-to-deploy.
  • Golden Paths — Paved, supported, automated workflows. The CNPE exam tests your ability to design and implement these self-service paths.

1.1 The Problem Before Platform Engineering

Imagine you're a developer on the anihpj team. You've built a Django app with a jobpost module that lists jobs. It works on your laptop. Now you need to deploy it so real users can access it. What do you need?

😰 What a Developer Needs to Deploy anihpj WITHOUT a Platform
  • 🔴 A server (or VM) — file a ticket, wait 2 weeks for IT to provision it
  • 🔴 Install Python, Django, gunicorn, nginx — hope versions match your laptop
  • 🔴 Configure a database (PostgreSQL) — more tickets for DBAs
  • 🔴 Set up networking — DNS, load balancer, firewall rules
  • 🔴 Configure HTTPS/TLS certificates — don't let them expire!
  • 🔴 Set up monitoring — otherwise you won't know if it's down at 3 AM
  • 🔴 Set up logging — so you can debug when something breaks
  • 🔴 Configure backups — because databases fail
  • 🔴 Set up CI/CD — so you don't deploy manually every time
  • 🔴 Document everything — so the next developer doesn't start from scratch
🎉 What a Developer Needs to Deploy anihpj WITH a Platform
  • ✅ Push code to GitHub — the platform does the rest
  • ✅ CI pipeline builds, tests, and packages your app automatically
  • ✅ ArgoCD deploys it to Kubernetes with zero-downtime
  • ✅ TLS certificates auto-provisioned and auto-renewed
  • ✅ Monitoring dashboards, alerts, and logs available immediately
  • ✅ Database provisioned automatically with backups configured
  • ✅ Preview environment created for every Pull Request

📖 Key Insight: Cognitive Load

Cognitive load is the mental effort required to complete a task. In software, it's the number of tools, concepts, and processes a developer must understand to ship code. Platform Engineering reduces cognitive load by abstracting infrastructure complexity behind simple, self-service interfaces. A developer should deploy an app in 5 minutes — not 2 weeks.

1.2 Platform Engineering Defined

Platform Engineering is the discipline of building and maintaining the internal tools, services, and workflows that enable development teams to deliver software rapidly, safely, and efficiently — without needing deep infrastructure expertise.

Platform Engineering — The Elevator Pitch

What Platform Engineering IS vs What It ISN'T

✅ Platform Engineering IS:

🏗️Building self-service tools that devs love
📐Designing golden paths for common workflows
👥Treating the platform as a product with real users
📊Measuring developer experience and adoption
🔄Automating repetitive operational tasks
🛡️Embedding security by default in every path
🔌Building platform APIs for self-service

❌ Platform Engineering ISN'T:

🚫Just "DevOps renamed" with fancier tools
🚫Only managing Kubernetes clusters
🚫A single team doing all the ops work
🚫Building without developer feedback
🚫Just writing YAML files all day
🚫Throwing tools at developers and walking away
🚫Centralized ticket-based infrastructure requests

🛡️
kube-apiserver

The front door. ALL communication goes through it. REST API. Authentication, authorization, admission control. kubectl, kubelet, controllers — everyone talks to the API server, NOT to etcd directly.

💾
etcd

Distributed key-value store. The cluster's single source of truth. All cluster state lives here. Uses Raft consensus. ALWAYS BACKUP ETCD. If etcd is lost without backup, the cluster state is gone.

📍
kube-scheduler

Watches for unscheduled pods. Decides WHICH node to place each pod on. Considers: resource requests, affinity rules, taints/tolerations. If scheduler is down, NEW pods stay Pending — existing pods keep running.

🔄
kube-controller-manager

Runs controller loops (observe → diff → act). Deployment controller ensures replica count. Node controller monitors node health. 20+ controllers run here. The "reconciliation loop" is the heart of K8s.

Worker Node Components

🤖
kubelet

Agent on every node. Receives Pod specs from API server. Ensures containers are running via container runtime. Reports node/pod status back to API server. If kubelet stops, node shows NotReady.

🌐
kube-proxy

Network proxy on every node. Maintains iptables/IPVS rules. Enables Service abstraction — routes traffic to correct pod. Without kube-proxy, Services don't work.

Pods & Deployments

Pod: Smallest deployable unit. One or more containers sharing network/storage. Deployment: Manages ReplicaSets, enables rolling updates and rollbacks.

📖 Platform Pattern

Almost NEVER create bare Pods in production. Always use Deployments (or StatefulSets for databases). Deployments give you self-healing, scaling, and zero-downtime updates.

Services & Ingress

Service: Stable network endpoint for a set of pods (pods are ephemeral — IPs change). Ingress: HTTP/HTTPS routing to Services based on host/path.

ConfigMaps & Secrets

ConfigMap: Non-sensitive config (DB host, log level). Secret: Sensitive data (passwords, API keys). Both decouple config from container images — change config without rebuilding.

Namespaces & CRDs

Namespace: Logical partition for multi-tenancy. Custom Resource Definition (CRD): Extend the K8s API with your own resource types. This is how ArgoCD, Crossplane, and Kyverno work — they add CRDs that Kubernetes understands natively.

Q7
What is a StorageClass in Kubernetes? How does it enable dynamic provisioning?
Show Answer
Answer

A StorageClass defines a type of storage (e.g., "fast SSD" or "standard HDD") with a provisioner (AWS EBS, GCP PD). When a PVC references a StorageClass, K8s dynamically provisions a PV — no manual PV creation needed.

Q8
What happens if the kube-scheduler goes down? Do existing pods stop running?
Show Answer
Answer

NO — existing pods keep running. Only newly created pods stay in Pending state because there's no scheduler to assign them to a node. The scheduler only handles pod placement; it doesn't manage running pods.

Q9
How does a Service discover which Pods to route traffic to? What happens if labels don't match?
Show Answer
Answer

Services use label selectors to find pods. A Service with selector: app=anihpj routes traffic only to pods with label app=anihpj. If labels don't match, the Service has no endpoints — traffic goes nowhere. Always verify with kubectl get endpoints.

Q10
Why can't other components (scheduler, controller-manager, kubelet) communicate directly with etcd?
Show Answer
Answer

Only the kube-apiserver communicates with etcd. This architecture provides: (1) Security — all access goes through authentication/authorization, (2) Consistency — the API server handles validation and optimistic concurrency, (3) Abstraction — components don't need to know etcd's protocol.

3.1 Container Fundamentals

Think of a container like a shipping container 🚢 — standardized, stackable, works on any ship/truck/train. In software, a container packages your application with ALL its dependencies, so it runs identically on your laptop, in CI, and in production.

Containers vs Virtual Machines

✅~50 MB disk per image
✅Seconds to start

💻 Virtual Machines

❌Full OS per VM
❌~10-40 GB disk per VM
❌Minutes to start

OCI Standards & Runtimes

The Open Container Initiative (OCI) defines standards for container images and runtimes. Common runtimes: containerd (default in modern K8s), CRI-O (lightweight), gVisor/Kata (sandboxed for security).

Image Layers & Caching

Docker images are built in layers — each instruction in a Dockerfile creates a new layer. Layers are cached: if a layer hasn't changed, Docker reuses it. This is why you COPY requirements.txt BEFORE copying source code — dependencies change less often than code, so they're cached.

3.2 Building Production-Grade Docker Images

Multi-Stage Builds

Multi-stage builds separate the build environment from the runtime environment, resulting in drastically smaller, more secure images.

Dockerfile — anihpj multi-stage build 
# Stage 1: BUILD
FROM python:3.12-slim AS builder
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
RUN python manage.py collectstatic --noinput

# Stage 2: RUNTIME (smaller, no build tools)
FROM python:3.12-slim
WORKDIR /app
COPY --from=builder /usr/local/lib/python3.12 /usr/local/
COPY --from=builder /app .
USER 1000:1000
EXPOSE 8000
CMD ["gunicorn", "anihpj.wsgi:application", \
     "--bind", "0.0.0.0:8000", "--workers", "4"]
💡 Why Multi-Stage?

Stage 1 might be ~1.2 GB with gcc and build tools. Stage 2 is only ~200 MB — 6x smaller. Smaller images = faster pulls, smaller attack surface, less storage cost.

Distroless Images

Distroless images contain ONLY your application and its runtime dependencies — no shell, no package manager, no utilities. This makes them extremely secure (attackers can't get a shell) but harder to debug.

Image Tagging Strategy

What is the purpose of a multi-stage Docker build? Give a concrete benefit for the anihpj project.
Show Answer
Answer

Multi-stage builds separate the build environment from the runtime environment. Stage 1 compiles, installs dependencies, and collects static files. Stage 2 copies ONLY the artifacts needed to run. For anihpj, this reduces image size from ~1.2 GB to ~200 MB — 6x smaller. Smaller images pull faster and have a smaller attack surface.

Q2
Why should you never use the :latest tag in production?
Show Answer
Answer

:latest is a mutable tag — it can point to a different image tomorrow than it does today. This breaks reproducibility and can cause unexpected deployments. Use semantic versioning (v1.2.3) or Git SHA (abc1234) for immutable, traceable deployments.

Q3
What is a distroless image? What is its main security advantage and its main operational challenge?
Show Answer
Answer

A distroless image contains only the application and its runtime — no shell, no package manager, no utilities. Advantage: Attackers can't get a shell if they compromise the container. Challenge: You can't docker exec into the container to debug — you need external observability (logs, metrics, traces).

What is the difference between Docker Hub, ECR, and Harbor? When would you choose each?
Show Answer

Q6
What does the USER 1000:1000 directive do in a Dockerfile? Why is it important?
Show Answer
Answer

It runs the container as a non-root user (user ID 1000) instead of root (UID 0). If an attacker compromises the container, they have limited privileges — they can't install packages or modify system files. This is a critical security practice required by Pod Security Standards.

Q7
What is SBOM? Why is it important for Platform Engineers?
Show Answer
Answer

SBOM (Software Bill of Materials) is a detailed list of every component, library, and dependency in your container image. It's important for: (1) Vulnerability management — know if you're affected by a CVE, (2) Compliance — regulatory requirements, (3) Supply chain security — know exactly what's running. Generate with Syft, attach with cosign.

Q8
When should you use Docker Compose vs Kubernetes for the anihpj project?
Show Answer
Answer

Docker Compose: Local development with hot reload, single machine, simple setup. Kubernetes: Staging/production, multi-node, auto-scaling, self-healing, rolling updates, GitOps, TLS automation, monitoring integration. Most teams use Compose locally and K8s for deployed environments.

Q9
Explain image layer caching. How should you order COPY instructions in a Dockerfile for optimal caching?
Show Answer
Answer

Docker caches each layer. If a layer hasn't changed, it's reused. Order COPY instructions from least frequently changed to most frequently changed: (1) COPY requirements.txt first (rarely changes), (2) RUN pip install (cached if requirements unchanged), (3) COPY source code last (changes most often). This way, dependency installation is cached across builds — only the final COPY runs.

Q10
What is cosign? How does it help prevent supply chain attacks?
Show Answer
Answer

cosign (part of Sigstore) signs container images to prove their origin and integrity. It creates a cryptographic signature that can be verified before deployment. This prevents supply chain attacks where an attacker replaces a legitimate image with a malicious one. Combined with Kyverno admission control, you can require all images to be signed before they run.

8.5 Argo Rollouts — Advanced Deployment Strategies

Rolling Update & Recreate

Rolling Update: K8s default strategy — replaces pods one by one with zero downtime. The Deployment controller creates new pods and terminates old ones gradually. Recreate: Stops ALL existing pods first, then starts new ones. Causes downtime but is the simplest strategy — use only for non-critical batch jobs or database migrations where concurrent old+new would cause issues.

Blue/Green Deployments

Two complete, identical environments — Blue (current v1) and Green (new v2). Traffic switches instantly via Service selector change from Blue to Green. Advantage: Instant rollback — just switch the Service selector back to Blue. Disadvantage: Double resource usage during cutover (both environments run at full capacity).

Canary, A/B Testing & Shadow

Canary: Gradual percentage-based traffic shift with automated metric analysis between each step. A/B Testing: Route based on user attributes (headers, cookies, geography) — different from canary which is purely percentage-based. Shadow/Mirror: Duplicate production traffic to the new version, but discard its responses. The new version processes real traffic silently — perfect for risk-free production testing before going live.

📝 Chapter 9 — CNPE Practice Questions

Q1
What is the difference between a Rolling Update and a Canary deployment?
Show Answer
Answer

Rolling Update: Replaces pods one by one with no traffic control — K8s default. Canary: Explicitly controls traffic percentages (10%→25%→50%→100%) with metric analysis between each step. Canary auto-rolls back if metrics degrade; rolling update doesn't.

Q2
Why does Blue/Green deployment require double the resources?
Show Answer
Answer

During cutover, BOTH the Blue environment (v1) and Green environment (v2) run simultaneously with full replicas. If anihpj runs 3 replicas normally, Blue/Green needs 6 replicas during the switch. This is the cost of instant rollback capability.

Q3
How does Argo Rollouts automatically roll back a Canary deployment?
Show Answer
Answer

Each canary step runs a Prometheus analysis. If the analysis detects: error rate > threshold, latency p99 > threshold, or any defined metric violation — Argo Rollouts automatically reverts all traffic back to the stable version (v1). No human intervention needed.

Q4
What is the difference between feature flags and deployment strategies like canary?
Show Answer
Answer

Canary/Blue-Green: Controls which VERSION of code receives traffic (v1 vs v2). Feature Flags: Controls which FEATURES are enabled within the same code version. You can deploy code with Feature X disabled, then enable it via flag — without redeploying.

Q5
What is a "dark launch"? How do feature flags enable it?
Show Answer
Answer

A dark launch deploys new code to production but keeps it hidden from users via a feature flag. The platform team (or internal testers) can enable it for themselves to test in production. If it breaks, disable the flag — instant rollback without redeploying.

Q6
What is a release gate? Give 3 examples of automated gates.
Show Answer
Answer

A release gate is a checkpoint that must pass before deployment proceeds. Examples: 1. Tests pass (CI green), 2. Security scan clean (no critical CVEs), 3. Metrics healthy (error rate < 1%, latency p99 < 200ms). Gates prevent bad code from reaching production.

Q7
How does A/B testing differ from canary deployment?
Show Answer
Answer

Canary: Traffic split by percentage (10% get v2). A/B Testing: Traffic split by user attributes (beta users get v2, regular users get v1). Canary is about risk reduction; A/B testing is about measuring user behavior differences between versions.

Q8
What is a "kill switch" in the context of feature flags?
Show Answer
Answer

A kill switch is a feature flag that can instantly disable a broken feature in production — without redeploying. If the jobpost export feature starts crashing, flip the flag to "off" and the feature disappears for all users. Fix the bug, test, then re-enable. Zero-downtime mitigation.

Q9
What's the difference between automated and manual approval for production deploys? When use each?
Show Answer
Answer

Automated: Metric-based gates pass → deploy automatically. Use for most services. Manual: Human clicks "approve" in ArgoCD. Use for: financial transactions, healthcare data, or when regulatory compliance requires human sign-off.

Q10
You're deploying anihpj v2 via canary. 10% traffic shows doubled error rate. What happens?
Show Answer
Answer

Argo Rollouts' Prometheus analysis detects the error spike → the canary step FAILS → Argo Rollouts automatically reverts ALL traffic back to v1 (100% v1, 0% v2). The v2 pods are scaled down. On-call is alerted. The deployment is aborted. Developers investigate the v2 issue.

  target:
    name: db-credentials       # K8s Secret to create/update
    creationPolicy: Owner      # ESO owns and manages this secret
  data:
    - secretKey: POSTGRES_USER
      remoteRef:
        key: anihpj/prod/db
        property: username

💡 ESO Auto-Refresh

ESO periodically reconciles (default: 1 hour). When the external secret value changes (e.g., after rotation), ESO detects the difference and updates the K8s Secret. Your pods need to reload/restart to pick up the new value — use Reloader or stakater to auto-restart pods on secret/configmap changes.

AWS Secrets Manager

Store secrets in AWS Secrets Manager. ESO uses IRSA (IAM Roles for Service Accounts) to authenticate — no static credentials. Define a ClusterSecretStore with the AWS region and an ExternalSecret referencing the secret ARN or name. Supports JSON secret properties (username/password in one secret).

HashiCorp Vault

Enterprise-grade secret management with dynamic secrets (auto-generated, short-lived DB credentials), audit logging, and fine-grained policies. ESO authenticates via Kubernetes auth method or AppRole. Vault is the go-to for multi-cloud, regulated industries, and when you need encryption-as-a-service.

GCP/Azure Backends

GCP Secret Manager and Azure Key Vault work similarly — ESO authenticates via workload identity (GCP) or managed identity (Azure). Both are deeply integrated with their respective cloud IAM systems, making them the simplest choice for single-cloud platforms.

Only the cluster's sealing controller can decrypt it — the sealed data is useless outside your cluster. Commit SealedSecret YAML to Git, and ArgoCD syncs it normally.

📖 When to Use Sealed Secrets

Sealed Secrets is ideal for GitOps-first teams that want everything in Git. It's simple, requires no external secret store, and the encryption is cluster-specific. Trade-off: secrets are tied to ONE cluster — if that cluster dies, you need the private key backup to decrypt.

12.4 SOPS (Secrets OPerationS) — Cloud KMS Encryption

SOPS encrypts YAML/JSON/ENV files using cloud KMS (AWS KMS, GCP KMS, Azure Key Vault) or age/PGP keys. Unlike Sealed Secrets (cluster-specific), SOPS-encrypted files are portable — anyone with KMS access can decrypt. It integrates natively with ArgoCD for GitOps.

SOPS + AWS KMS Workflow

# STEP 1: Create .sops.yaml config (which KMS keys to use)
cat > .sops.yaml << EOF
creation_rules:
  - kms: arn:aws:kms:us-east-1:123456789012:key/abc-123-def
    encrypted_regex: '^(password|secret|key|token)$'
EOF

# STEP 2: Create a plain secret file
cat > anihpj-secrets.yaml << EOF
apiVersion: v1
kind: Secret
metadata:
  name: db-credentials
stringData:
  POSTGRES_PASSWORD: supersecret
  API_KEY: sk-1234567890
EOF

# STEP 3: Encrypt with SOPS (only values matching regex are encrypted)
sops --encrypt anihpj-secrets.yaml > anihpj-secrets.enc.yaml

# STEP 4: Commit ONLY the encrypted file to Git
git add anihpj-secrets.enc.yaml .sops.yaml
git commit -m "Add encrypted secrets for anihpj"
git push

# STEP 5: ArgoCD decrypts automatically before applying
# (ArgoCD needs KMS decrypt permission via IRSA)

ArgoCD + SOPS Integration

ArgoCD can natively decrypt SOPS-encrypted files before applying them to the cluster. Configure ArgoCD with the KMS decrypt permission (via IRSA or service account), and it handles decryption transparently. The encrypted file sits in Git; the decrypted Secret only exists in the cluster.

Are Kubernetes Secrets encrypted by default? What's the risk?

What is the External Secrets Operator? How does it work?
Show Answer
Answer

ESO syncs secrets from external stores (AWS Secrets Manager, Vault) into K8s Secrets. You define a ClusterSecretStore (backend config) and an ExternalSecret (mapping external secret → K8s Secret). ESO periodically refreshes to keep them in sync.

Q3
What is the difference between Sealed Secrets and SOPS?
Show Answer
Answer

Sealed Secrets: Encrypt via cluster-side controller, decryptable only by that specific cluster. SOPS: Encrypt via cloud KMS (AWS KMS, GCP KMS), decryptable wherever you have KMS access. Sealed Secrets are cluster-specific; SOPS is more portable across clusters.

Q4
You accidentally commit a K8s Secret YAML to GitHub. What's the risk? What should you do?
Show Answer
Answer

Risk: Anyone with repo access can decode the base64 values and obtain your secrets. They're also in Git history forever. Action: (1) Immediately rotate all exposed secrets, (2) Remove the file and rewrite Git history (BFG Repo-Cleaner), (3) Implement pre-commit hooks (gitleaks) to prevent recurrence.

Show Answer

Q6
Why would you choose HashiCorp Vault over cloud-native secret managers?
Show Answer
Answer

Vault offers: multi-cloud (one tool for all clouds), dynamic secrets (auto-generated, short-lived DB credentials), audit logging, fine-grained policies, and encryption-as-a-service. Cloud secret managers are simpler but tied to a single cloud.

Q7
How does Sealed Secrets enable GitOps-friendly secret management?
Show Answer
Answer

Q8
What is etcd encryption at rest? Why is it critical for secret security?
Show Answer
Answer

It encrypts all data stored in etcd using a KMS plugin. Without it, anyone with filesystem access to the etcd data directory can read Secrets in plain text. Enable it via --encryption-provider-config on the API server. This is a cluster-level security MUST.

Q9
How does ESO handle secret rotation? Does it auto-refresh K8s Secrets?
Show Answer
Answer

Yes. ESO periodically reconciles (default: every 1 hour, configurable). If the external secret value changes (e.g., after rotation), ESO detects the difference and updates the K8s Secret. Pods need to restart or reload to pick up the new value.

📊 Metrics (Prometheus)

Metrics are numeric measurements collected over time — CPU usage, request count, error rate, latency percentiles. They're lightweight, cheap to store, and perfect for alerting and dashboards. Prometheus is the CNCF-standard metrics system. Metrics answer: "How many? How fast? How often?"

📋 Logs (Loki)

Logs are timestamped text records of events — "User 42 created a job posting at 10:32:15". They're verbose, moderately expensive to store, and essential for debugging specific issues. Grafana Loki stores logs efficiently by indexing only labels (like Prometheus for logs). Logs answer: "What exactly happened at 10:32:15?"

🔍 Traces (Tempo)

Traces follow a single request as it travels through multiple services — nginx → anihpj → PostgreSQL → Redis. Each service adds a "span" to the trace. Traces show you exactly where time is spent and where failures occur. Grafana Tempo is the CNCF-standard tracing backend. Traces answer: "Why is this request slow? Where did it fail?"

📖 MELT — The Modern Acronym

The observability industry now uses MELT: Metrics, Events, Logs, Traces. Events are discrete occurrences (deployment happened, config changed, autoscaler fired). They provide crucial context that bridges metrics, logs, and traces — especially useful for correlating infrastructure changes with application behavior.

💡 Error Budgets — Your Release Safety Net

If your SLO is 99.9% uptime, your error budget is 0.1% = ~43 minutes of allowed downtime per month. When you've "burnt" your error budget (too many incidents), you freeze all feature releases and focus on reliability. This creates a healthy tension between "move fast" (devs) and "keep it stable" (platform team). Google's SRE book calls this the most important concept in production engineering.

📖 Real-World SLO: anihpj Job Post API

You define an SLO for the anihpj job posting endpoint (POST /api/jobs/):

SLI: p99 latency measured over a 28-day rolling window.
SLO: 99% of requests complete in under 200ms over 28 days.
Error Budget: 1% of requests can exceed 200ms = ~40,000 slow requests/month (at 100 req/s).

This means: if you burn through those 40,000 slow requests early in the month, the platform team freezes all new feature deploys and the dev team must fix performance before shipping anything new. This is how SLOs align incentives between platform and dev teams.

14.1 Prometheus Deep Dive

Prometheus uses a pull-based model: it actively scrapes HTTP endpoints on your services to collect metrics. Histograms are aggregatable across instances (you can sum bucket counts from multiple pods) and are the standard choice for K8s. 14.3 Alerting with Alertmanager

Alertmanager handles alerts from Prometheus — it deduplicates, groups, and routes them to the right team via Slack, PagerDuty, Opsgenie, email, or webhook. Without Alertmanager, every Prometheus server fires its own alerts, causing duplicate pages.

Alert Rules — When to Fire

# Critical alert: anihpj API error rate is too high
groups:
  - name: anihpj-critical
    rules:
      - alert: HighErrorRate
        expr: |
          sum(rate(http_requests_total{job="anihpj",status=~"5.."}[5m]))
          /
          sum(rate(http_requests_total{job="anihpj"}[5m])) > 0.05
        for: 5m  # Must be true for 5 minutes before firing
        labels:
          severity: critical
        annotations:
          summary: "anihpj error rate > 5%"
          description: "Error rate is {{ $value | humanizePercentage }}"

      - alert: HighLatency
        expr: |
          histogram_quantile(0.99,
            rate(http_request_duration_seconds_bucket{job="anihpj"}[5m])
          ) > 0.2
        for: 10m
        labels:
          severity: warning
        annotations:
          summary: "anihpj p99 latency > 200ms"

15.2 Grafana Loki — Prometheus for Logs

Loki is designed like Prometheus but for logs: it indexes only labels (not the full text of every log line), making it extremely cost-efficient. Logs are stored as compressed chunks in object storage (S3, GCS). Full-text search is available but not indexed — it's done on-demand.

{job="anihpj"} != "health check"

pip install opentelemetry-instrumentation-redis      # Redis cache

# settings.py — minimal config
OTEL_SERVICE_NAME = "anihpj"
OTEL_EXPORTER_OTLP_ENDPOINT = "http://otel-collector:4317"

# Run Django with auto-instrumentation
opentelemetry-instrument \
  --traces_exporter otlp \
  --metrics_exporter otlp \
  python manage.py runserver

# Result: Every HTTP request → automatically traced!
# Spans: nginx → Django view → DB query → Redis cache → response
📖 Span Attributes — The Details That Matter

OTel automatically adds useful attributes to each span: http.method (GET/POST), http.status_code (200/500), db.statement (the SQL query), db.system (postgresql). You can add custom attributes: span.set_attribute("user.id", request.user.id). These attributes make traces searchable and meaningful during debugging.

15.4 Correlating Metrics, Logs, and Traces — The Power of Three

The real magic happens when you jump seamlessly between the three pillars. Grafana's Explore view lets you start from a metric spike, drill into related logs, and from a log line jump directly to the full distributed trace.

Incident Debugging Walkthrough — The Complete Flow

  🚨 ALERT: anihpj API p99 latency > 200ms

  STEP 1: METRICS (Grafana + Prometheus)
  ┌────────────────────────────────────────────────────────────┐
  │ Open anihpj RED dashboard → p99 latency spiked at 10:32   │
  │ → Drill down: which endpoint? → POST /api/jobs/ is slow   │
  │ → Which pod? → pod-7 is 5× slower than pod-6              │
  └────────────────────────────────────────────────────────────┘
                          │
                          ▼
  STEP 2: LOGS (Grafana + Loki)
  ┌────────────────────────────────────────────────────────────┐
  │ Search logs for pod-7 at 10:32:                            │
  │ {pod="anihpj-7"} |= "ERROR"                                │
  │ → [ERROR] PostgreSQL query timeout after 30s               │
  │ → trace_id=abc123 found in log line                        │
  └────────────────────────────────────────────────────────────┘
                          │
                          ▼
  STEP 3: TRACES (Grafana + Tempo)
  ┌────────────────────────────────────────────────────────────┐
  │ Open trace abc123 in Tempo:                                │
  │ → PostgreSQL INSERT span = 28 SECONDS (not ms!)            │
  │ → Query: "INSERT INTO jobs ... WHERE skills IN (500 IDs)"  │
  │ → ROOT CAUSE: Missing index on jobs.skills FK              │
  │ → FIX: CREATE INDEX CONCURRENTLY idx_jobs_skills           │
  │ → Deploy fix → RED dashboard returns green                 │
  └────────────────────────────────────────────────────────────┘

  ⏱️ Time to diagnose: 3 minutes (vs 30+ without correlation)

Exemplars — The Missing Link

Exemplars link specific metric data points to specific traces. When you see a latency spike on your Grafana dashboard, you can click the spike point and jump directly to the trace that caused it. This is the ultimate observability superpower — it closes the loop between metrics, logs, and traces.

💡 CNPE Golden Rule

Your platform isn't truly observable until a developer can go from alert → metric spike → log line → distributed trace → root cause in under 5 minutes — without SSH-ing into a single pod. This is the bar. Everything you deploy in Part 5 should serve this goal.

📝 Chapter 15 — CNPE Practice Questions

Q1
Why is centralized logging essential for Kubernetes? What problem does it solve?
Show Answer
Answer

K8s pod logs are ephemeral — they disappear when pods restart, get evicted, or are replaced by new replicas. Centralized logging ships logs off-node to persistent storage. It also enables searching ALL logs from a single UI, correlating logs with metrics, and never needing to kubectl logs individual pods.

Q2
What makes Loki different from Elasticsearch for log storage?
Show Answer
Answer

Loki only indexes labels (like Prometheus), not full-text content. This makes it dramatically cheaper to operate — logs are stored as compressed chunks in object storage (S3). Elasticsearch indexes every word, giving faster full-text search but requiring much more CPU, memory, and disk. Loki is the K8s-native choice.

Q3
What is a span? What is a trace? How do they relate?
Show Answer
Answer

A span is a single unit of work with a start time, duration, and metadata (e.g., "PostgreSQL query: 45ms"). A trace is a collection of spans that share the same trace ID, representing one complete request through the system. A trace answers: "What happened to THIS specific request?"

Q4
What is context propagation? How is it implemented?
Show Answer
Answer

Context propagation passes the trace ID and span ID across service boundaries so downstream services can add spans to the same trace. Implemented via HTTP headers: W3C Trace Context (traceparent: 00-traceId-spanId-flags). OTel SDKs handle this automatically — you just need to propagate the headers through your HTTP client.

Q5
What is the difference between head-based and tail-based sampling for traces?
Show Answer
Answer

Head-based: Sampling decision made at the START of a trace (e.g., sample 10% of all requests). Simpler but might miss rare errors. Tail-based: Sampling decision made at the END — you keep ALL traces in a buffer, then decide "keep errors, sample successes." More complex but ensures you never miss an error trace.

Q6
Write a LogQL query to find all ERROR logs from anihpj pods containing "database" in the last hour, and count them per minute.
Show Answer
Answer

Search: {job="anihpj"} |= "ERROR" |~ "(?i)database". Count rate: rate({job="anihpj"} |= "ERROR" |~ "(?i)database" [1h]). This shows you how many database errors per second, grouped by time — just like Prometheus rate() for metrics.

Q7
How does Grafana Tempo find a trace without indexing spans? Isn't that slow?
Show Answer
Answer

Tempo stores traces as blobs in object storage keyed by trace ID. You provide the trace ID (from logs, exemplars, or a metric), and Tempo does a direct lookup — no scanning, no indexing. It's fast because it's O(1) lookup by ID. The trade-off: you can't search traces by arbitrary attributes (that's what indexing-based systems do).

Q8
What are exemplars? How do they connect metrics to traces?
Show Answer
Answer

Exemplars attach a specific trace ID to a metric data point. When your Grafana dashboard shows a latency spike at 10:32:15, you can click the spike and jump directly to the exact trace that caused it. They're configured in Prometheus: --enable-feature=exemplar-storage. This closes the metrics→traces loop.

Q9
What collector would you use for K8s log aggregation and why?
Show Answer
Answer

Use Fluent Bit as a DaemonSet (collects all pod logs, extremely lightweight at ~10MB RAM) or Promtail if using Loki (auto-discovers K8s metadata, adds pod/namespace/labels automatically). Fluent Bit sends to Fluentd for buffering/enrichment, then to Loki/Elasticsearch for storage. Both are industry standard for K8s.

Q10
Walk through debugging an anihpj latency spike using all three pillars. What's your flow?
Show Answer
Answer

1. Metrics: Grafana RED dashboard → p99 spike at 10:32, POST /api/jobs/ affected. 2. Logs: Loki query {job="anihpj"} |= "ERROR" at 10:32 → "PostgreSQL timeout" with trace_id=abc123. 3. Traces: Open trace abc123 in Tempo → PostgreSQL INSERT span = 28s → missing index found. 4. Fix, deploy, verify. Total time: 3-5 minutes. Without observability: 30+ minutes of SSH + grep.
