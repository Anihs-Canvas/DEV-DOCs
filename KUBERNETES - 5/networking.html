1.1 Why Networking Matters for DevOps & Platform Engineers

Every production outage has a network dimension. When a user reports "the site is down" or "jobpost.anihpj.com is timing out" — where do you start? Is it the application code? The database? DNS? A firewall rule? A misconfigured Kubernetes service?

⚠️ GOTCHA: "Ping Works but Curl Doesn't"

A common trap: You ping the server and it responds, so you think "the network is fine." This is wrong. ICMP (ping) is often allowed through firewalls while TCP ports (like 8000 for your Django app) are blocked. Always test the actual protocol and port your application uses.

The Layered Observability Mindset — Start at the Bottom, Work Up
  🔍 NETWORKING = LAYERED OBSERVABILITY

  Layer 7 (Application):  "Is the app responding?"  → curl, HTTP status codes
  Layer 4 (Transport):    "Is the port open?"        → nc -zv, ss -tlnp, telnet
  Layer 3 (Network):      "Can I reach it?"           → ping, traceroute, ip route
  Layer 2 (Data Link):    "Is ARP resolving?"         → ip neigh show, arping
  Layer 1 (Physical):     "Is the link up?"           → ip link show, ethtool

  🥇 Golden Rule:  START AT THE BOTTOM AND WORK UP
  🥈 Second Rule:  THE PACKETS DON'T LIE. Trust tcpdump.

1.2 The OSI Model — Networking's Periodic Table

The Open Systems Interconnection (OSI) model is the universal framework for understanding how data moves across networks. It breaks networking into 7 distinct layers — each with a specific job. Think of it as networking's periodic table: once you understand the layers, everything else falls into place.

📖 Historical Context

The OSI model was developed in the 1970s by the International Organization for Standardization (ISO). While the OSI protocols never gained wide adoption, the OSI model became the standard teaching framework. The Internet actually runs on the simpler TCP/IP model (4 layers), which we'll cover in Section 1.4.

⚠️ GOTCHA: OSI is a Teaching Tool

The OSI model is a conceptual framework, not a blueprint. The Internet runs on the TCP/IP model (4 layers). Don't obsess over which exact OSI layer a protocol belongs to — focus on understanding which layer your problem is at so you know which tool to reach for.

1.3 Encapsulation — The Russian Doll of Networking

2.1 What Actually Travels Through a Cable?

At the physical layer, data is just signaling — voltage changes on copper, light pulses on fiber, or radio waves through the air. The NIC converts 1s and 0s into these physical signals using an encoding scheme (Manchester, NRZ, PAM4).

        ↓
  🧠 KERNEL:       TCP → IP → Ethernet Frame
        ↓
  🔌 NIC:          Encodes bits as voltage transitions
        ↓
  🔌 CABLE:        1011001011100101... (Manchester encoding)
        ↓
  🔌 SWITCH:       Reads voltage → decodes back to bits

⚠️ GOTCHA: UP ≠ Healthy

A link can be "UP" at L1 but have 90% packet loss from a bad cable, duplex mismatch, or EMI interference. Always check ip -s link show eth0 for error counters — RX errors, dropped packets, and overruns tell the real story.

2.4 Switches — The Silent Workhorses

A network switch is essentially a multi-port bridge that forwards Ethernet frames based on destination MAC addresses. Unlike hubs (which repeat to all ports), switches learn which MAC addresses are on which ports and forward intelligently.

How a Switch Learns — The 4-Step MAC Learning Process
  SWITCH MAC ADDRESS TABLE (initially empty)
  ┌──────────────────┬─────────┐
  │    MAC Address    │  Port   │
  ├──────────────────┼─────────┤
  │     (empty)      │         │
  └──────────────────┴─────────┘

  STEP 1: Host A (MAC: aa:bb:cc:11:22:33) on Port 1 → sends frame to Host B
  STEP 2: Switch LEARNS: aa:bb:cc:11:22:33 → Port 1 (records in CAM table)
  STEP 3: Switch doesn't know B's MAC → FLOODS frame to ALL ports (except Port 1)
  STEP 4: Host B responds → Switch LEARNS B's MAC → Port 2
  RESULT: Now A↔B traffic is FORWARDED only between Ports 1 and 2

  🎯 THE THREE F's:
  - FORWARD: Known MAC → send only to the correct port
  - FLOOD:   Unknown MAC → send to ALL ports (learning opportunity)
  - FILTER:  Same port as source → do NOT forward (already on that segment)

2.5 ARP — How IP Addresses Become MAC Addresses

The Address Resolution Protocol (ARP) solves a fundamental problem: you know an IP address (192.168.1.5), but to deliver an Ethernet frame, you need the corresponding MAC address. ARP bridges Layer 3 (IP) and Layer 2 (MAC).

ARP Exchange — Annotated tcpdump Output
  # ARP REQUEST (Broadcast to ff:ff:ff:ff:ff:ff)
  10:23:45.123456 ARP, Request who-has 10.0.1.5 tell 10.0.1.1, length 28
  0x0000:  ffff ffff ffff  ← Destination MAC = Broadcast!
  0x0006:  aabb ccdd ee01  ← Source MAC = 10.0.1.1's interface
  0x000c:  0806            ← EtherType = 0x0806 (ARP)

  # ARP REPLY (Unicast back to requester)
  10:23:45.123458 ARP, Reply 10.0.1.5 is-at aa:bb:cc:dd:ee:05, length 28

ARP Request & Reply

ARP request: broadcast frame asking "Who has IP X? Tell IP Y." ARP reply: unicast frame saying "IP X is at MAC Z." The requesting host then caches this mapping in its ARP cache (ip neigh show).

ARP Cache & States

The ARP cache has entries with states: REACHABLE (confirmed working), STALE (still usable, will verify on next use), DELAY (waiting for confirmation), PROBE (actively verifying), FAILED (unreachable).

⚠️ GOTCHA: STALE ≠ Broken

ip neigh show showing STALE doesn't mean broken. STALE = "still usable, will verify on next use." Only FAILED means the neighbor is truly unreachable.

Gratuitous ARP

An unsolicited ARP announcement: "I am 192.168.1.5 at MAC aa:bb:cc:dd:ee:ff." Used for IP takeover during failover (keepalived, VRRP) and duplicate IP detection. When a floating IP moves to a new node, a GARP updates everyone's ARP cache instantly.

ARP Spoofing & Security

An attacker sends forged ARP replies claiming to be the gateway's IP at the attacker's MAC — redirecting all traffic through the attacker (Man-in-the-Middle). Mitigation: static ARP entries, DHCP snooping, dynamic ARP inspection (DAI) on managed switches.

No, STALE is not broken. STALE means the ARP entry hasn't been used recently but is still considered valid. On the next packet to 10.0.1.1, the kernel will use this entry and then move it to REACHABLE. Only entries in FAILED state are truly unreachable.

Explanation

ARP states: REACHABLE → STALE (timer expiry) → DELAY (first use after stale) → PROBE (actively arping) → REACHABLE or FAILED. This is the kernel's way of balancing performance (cached entries) with correctness (verifying stale entries).

Q5
What are the "Three F's" of switch operation? Explain each.
Show Answer
Answer

FORWARD: Destination MAC is in the CAM table → send frame only to the specific port.
FLOOD: Destination MAC is unknown → send frame to ALL ports (except source).
FILTER: Destination MAC is on the same port as source → do NOT forward (already on that segment).

Explanation

These three operations are the core of L2 switching. Flooding for unknown MACs is how the switch learns — the destination will eventually respond, and its MAC gets added to the CAM table. Filtering prevents unnecessary traffic on already-saturated segments.

Q6
What is a VLAN (802.1Q) and why would you use one? How does it affect broadcast domains?
Show Answer
Answer

A VLAN (Virtual LAN) splits one physical switch into multiple logical switches using 802.1Q tags in the Ethernet header. Each VLAN is a separate broadcast domain — a broadcast on VLAN 10 does NOT reach VLAN 20. This provides network segmentation without needing separate physical switches. Trunk ports carry multiple VLANs; access ports carry only one.

# Linux VLAN interface creation
ip link add link eth0 name eth0.10 type vlan id 10
ip addr add 10.0.10.1/24 dev eth0.10
ip link set eth0.10 up
Explanation

VLANs are fundamental to network segmentation. In Kubernetes, some CNI plugins use VLANs for pod network isolation. The 802.1Q tag adds 4 bytes to the Ethernet frame, increasing the minimum frame size to 68 bytes.

Q7
What is the difference between unicast, broadcast, and multicast MAC addresses? Give an example MAC for each.
Show Answer
Answer

Unicast: First byte is EVEN (bit 0 = 0). Example: aa:bb:cc:dd:ee:ff. Sent to ONE specific host.
Broadcast: ff:ff:ff:ff:ff:ff. Sent to ALL hosts on the L2 segment. Used by ARP requests, DHCP discover.
Multicast: Starts with 01:00:5E (IPv4) or 33:33 (IPv6). Sent to a GROUP of subscribed hosts. Used by OSPF, streaming, VRRP.

Explanation

The first byte's least significant bit determines unicast (0) vs multicast (1). Broadcast is a special case of multicast (all bits set). Switches treat these differently — unicast is forwarded to one port, broadcast/multicast are flooded to all ports (unless IGMP snooping is enabled for multicast).

Explain gratuitous ARP (GARP). When is it used and why is it important for high availability?
Show Answer
Answer

A gratuitous ARP is an unsolicited ARP announcement — a host broadcasts "I am IP X at MAC Y" without being asked. It's used for: (1) IP takeover during failover (keepalived/VRRP moves a floating IP to a backup node), (2) duplicate IP detection (if another host responds, there's a conflict), (3) updating ARP caches after a MAC address change.

3.2 tcpdump — The Command-Line Packet Sniffer

tcpdump is the universal packet capture tool — available on every Linux distribution, container image, and even inside Kubernetes pods. It uses BPF (Berkeley Packet Filter) expressions to filter packets at the kernel level before they reach userspace.

# Basic syntax
tcpdump -i <interface> [BPF filter expression]

# Essential filters
tcpdump -i eth0 host 10.0.1.5          # Only traffic to/from 10.0.1.5
tcpdump -i eth0 port 8000              # Only port 8000 traffic
tcpdump -i eth0 net 10.0.1.0/24       # Only subnet traffic
tcpdump -i eth0 tcp                    # Only TCP
tcpdump -i eth0 'tcp and port 8000'   # TCP + port 8000
tcpdump -i eth0 'src host 10.0.1.5'   # FROM 10.0.1.5 only
tcpdump -i eth0 'dst port 443'        # TO port 443 only

# Save to file, read back
tcpdump -i eth0 -w capture.pcap        # Save raw packets
tcpdump -r capture.pcap                # Read pcap file
tcpdump -r capture.pcap 'port 8000'    # Filter on read

# Production-safe ring buffer
tcpdump -i eth0 -W 5 -C 100 -Z root   # 5 files × 100MB = 500MB max
⚠️ GOTCHA: Default Snap Length

tcpdump by default only captures the first 96 bytes of each packet. Use -s 0 for full packet capture. Without -s 0, you'll miss HTTP bodies, long headers, and application payload data.

What is the difference between a capture filter (BPF) and a display filter in Wireshark?
Show Answer
Answer

Capture filters (BPF): Applied BEFORE capture. Uses Berkeley Packet Filter syntax. Runs in kernel — very efficient. Limits what packets are captured. Example: tcp port 8000.

Q1
What is a Linux network namespace? How does Docker use them?
Show Answer
Answer

A network namespace is a completely isolated network stack — its own interfaces, routing table, iptables rules, and socket table. Docker creates one network namespace per container, giving each container its own private network environment. Containers in different namespaces can't see each other's interfaces or connections — unless connected by veth pairs + bridges.

Explanation

This is the foundation of container networking. When you run docker run, Docker: (1) creates a netns, (2) creates a veth pair (one end in container, one end in docker0 bridge), (3) assigns an IP. Kubernetes does the same for pods via CNI plugins.

Q2
You need to run tcpdump inside a container's network namespace from the host. The container doesn't have tcpdump installed. What command do you use?
Show Answer
Answer
# Find the container's PID
PID=$(docker inspect -f '{{.State.Pid}}' container-name)
# Enter its network namespace
sudo nsenter -t $PID -n tcpdump -i eth0 port 8000

This uses the HOST's tcpdump binary inside the container's network namespace — no need to install anything in the container image.

Explanation

nsenter -t <pid> -n enters the target process's network namespace. The -n flag is for network. You can also use -m (mount), -u (UTS/hostname), -i (IPC), -p (PID). For Kubernetes, use crictl inspect <container-id> | jq .info.pid to find the PID.

Q3
What is the difference between ip link, ip addr, and ip route? Give one example of each.
Show Answer
Answer
ip linkL2 — Manage interfacesip link set eth0 up
ip addrL3 — Manage IP addressesip addr add 10.0.1.5/24 dev eth0
ip routeL3 — Manage routing tableip route add default via 10.0.1.1
Explanation

Think of it as building up the stack: first create the link (ip link), then assign it an address (ip addr), then tell it how to reach other networks (ip route). These three subcommands replace the legacy tools ifconfig, route, and arp.

Q4
What is the /proc/net/ filesystem? List three key files and what they expose about the kernel's networking state.
Show Answer
Answer

/proc/net/ is a pseudo-filesystem that exposes the kernel's raw networking tables. Key files: /proc/net/tcp — raw TCP socket table (hex-encoded IPs in little-endian!); /proc/net/dev — per-interface packet/byte/error counters; /proc/sys/net/ipv4/ — kernel tunables (ip_forward, tcp_congestion_control, etc.). Use ss instead of reading /proc/net/tcp directly — it decodes everything for you.

Explanation

IPs in /proc/net/tcp are stored as hex in little-endian: 10.0.1.5 → 0501000A. This is why tools like ss exist — they parse and present this data in human-readable form. However, knowing the raw files exist is invaluable when debugging in minimal container environments where ss might not be available.

Q5
Create two network namespaces, connect them with a veth pair, assign IPs, and test connectivity. Write the complete sequence of commands.
Show Answer
Answer
# Create two namespaces
ip netns add ns1
ip netns add ns2

# Create veth pair (virtual cable)
ip link add veth1 type veth peer name veth2

# Move each end into a namespace
ip link set veth1 netns ns1
ip link set veth2 netns ns2

# Assign IPs
ip netns exec ns1 ip addr add 10.0.1.1/24 dev veth1
ip netns exec ns2 ip addr add 10.0.1.2/24 dev veth2

# Bring interfaces up
ip netns exec ns1 ip link set veth1 up
ip netns exec ns2 ip link set veth2 up

# Test!
ip netns exec ns1 ping -c 3 10.0.1.2  # WORKS! 🎉
Explanation

This is the EXACT pattern Docker and Kubernetes use for container networking — just with bridges added for multiple containers. The veth pair acts like a virtual Ethernet cable with two ends. Each namespace has its own isolated network stack (interfaces, routes, ARP cache). Understanding this hands-on exercise is the foundation of all container networking.

Q6
What is a Linux bridge and how does Docker use it? Write the commands to create a bridge, add two interfaces, and inspect the MAC forwarding table.
Show Answer
Answer
# Create bridge
ip link add br0 type bridge
ip link set br0 up

# Add interfaces to bridge
ip link set veth1 master br0
ip link set veth2 master br0

# Inspect
bridge link show        # Show all bridge ports
bridge fdb show br0     # MAC forwarding table (CAM table equivalent)

Docker's docker0 and Kubernetes' cni0 are Linux bridges. Each container/pod gets a veth pair — one end in the container's namespace, the other end plugged into the bridge. The bridge forwards frames between containers just like a physical switch.

Explanation

A Linux bridge is a software L2 switch running in the kernel. It maintains a MAC forwarding table (like a switch's CAM table) and forwards frames based on destination MAC. This is the core mechanism that allows all containers on the same Docker network to communicate with each other.

Q7
Your gunicorn process for anihpj fails to start with "Address already in use" on port 8000. How do you identify what process is using the port?
Show Answer
Answer
# Method 1: ss (preferred)
ss -tlnp | grep 8000
# LISTEN  0  128  0.0.0.0:8000  0.0.0.0:*  users:(("python",pid=12345,fd=3))

# Method 2: lsof
lsof -i :8000
# COMMAND   PID USER   FD   TYPE DEVICE SIZE/OFF NODE NAME
# python  12345 root    3u  IPv4  12345      0t0  TCP *:8000 (LISTEN)

# Method 3: /proc
cat /proc/net/tcp | awk '{print $2}'  # (hex, needs decoding)

# Method 4: netstat (legacy)
netstat -tlnp | grep 8000
Explanation

"Address already in use" (EADDRINUSE) means another process is already bound to port 8000. This is common in Docker/K8s when a container restart doesn't properly release the port, or when multiple gunicorn workers try to bind. Always check with ss first before killing anything.

Q8
Explain the path a packet takes through the Linux kernel when arriving at a NIC. Include the order of: netfilter hooks, routing decision, and socket delivery.
Show Answer
Answer

Incoming packet path: NIC → driver/DMA → netfilter PREROUTING → routing decision → (if for local host) netfilter INPUT → TCP/UDP stack → socket → application. Forwarded packet path: NIC → PREROUTING → routing → netfilter FORWARD → netfilter POSTROUTING → output NIC. Outgoing packet path: socket → TCP/UDP → routing → netfilter OUTPUT → netfilter POSTROUTING → NIC driver.

Explanation

The 5 netfilter hooks (PREROUTING, INPUT, FORWARD, OUTPUT, POSTROUTING) are where iptables/nftables rules are attached. NAT happens in PREROUTING (DNAT) and POSTROUTING (SNAT/masquerade). Understanding this order is essential for writing correct firewall rules and debugging why a packet is or isn't being modified.

Q9
What is the difference between ip netns and nsenter? When would you use each?
Show Answer
Answer

ip netns manages named network namespaces — create, delete, list, and execute commands inside them. Only works with namespaces mounted at /var/run/netns/.
nsenter enters the namespace of a running process identified by PID. Works with ANY namespace type (network, mount, PID, etc.) and doesn't require the namespace to be named.

# ip netns — for named namespaces you created
ip netns add myns
ip netns exec myns bash

# nsenter — for any running process (Docker container, K8s pod)
docker inspect -f '{{.State.Pid}}' mycontainer
nsenter -t <pid> -n bash
Explanation

Docker doesn't create named namespaces (they're anonymous), so ip netns list won't show them. Use lsns -t net to see ALL network namespaces on the system, or use nsenter to enter a specific container's namespace by PID.

Q10
How would you enable IP forwarding on a Linux host and verify it? Why is this essential for Kubernetes nodes?
Show Answer
Answer
# Enable immediately
echo 1 > /proc/sys/net/ipv4/ip_forward

# Make permanent
sysctl -w net.ipv4.ip_forward=1
# Or add to /etc/sysctl.conf: net.ipv4.ip_forward = 1

# Verify
sysctl net.ipv4.ip_forward       # Should show = 1
cat /proc/sys/net/ipv4/ip_forward # Should show 1

# Also needed for iptables to work correctly in K8s
modprobe br_netfilter
sysctl -w net.bridge.bridge-nf-call-iptables=1

Kubernetes nodes MUST have IP forwarding enabled — without it, pods on different nodes can't communicate because the node won't forward packets between its network interfaces (pod network → physical network).

Explanation

This is a prerequisite in EVERY Kubernetes installation guide. If ip_forward=0, the Linux kernel drops any packet that arrives on one interface but is destined for an IP that requires routing through another interface. K8s nodes act as routers for pod traffic, so forwarding is essential.
