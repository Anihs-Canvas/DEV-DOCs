    WHAT IS PROMETHEUS? — ONE SENTENCE
    ───────────────────────────────────
    Prometheus is an open-source monitoring and alerting toolkit
    that collects metrics (numbers) from your applications and
    infrastructure, stores them as time-series data, lets you
    query them with PromQL, and fires alerts when things go wrong.

    ─────────────────────────────────────────────
    ┌──────────────────────────────────────────────────────────────┐
    │  ❌ COMMON MISTAKES                 ✅ WHAT TO DO INSTEAD    │
    │                                                              │
    │  1. Using rate() on Gauges          rate()/irate() are ONLY  │
    │     (returns meaningless data)      for Counters. Gauges use │
    │                                     the raw value directly.  │
    │                                                              │
    │  2. histogram_quantile() on raw     ALWAYS rate() the bucket │
    │     buckets (skipping rate)         FIRST, then apply        │
    │                                     histogram_quantile().    │
    │                                                              │
    │  3. Forgetting the 'for' duration   Alert rules with no      │
    │     in alerting rules               'for: 5m' fire on EVERY  │
    │                                     evaluation — spam city!  │
    │                                                              │
    │  4. High-cardinality labels         NEVER use user_id,       │
    │     (user IDs, request IDs)         session_token, or email  │
    │                                     as Prometheus labels.    │
    │                                                              │
    │  5. Confusing sum by vs sum without  by(endpoint) KEEPS      │
    │                                     endpoint. without(pod)   │
    │                                     DROPS pod. Know which!   │
    │                                                              │
    │  6. Not using recording rules       Pre-compute expensive    │
    │     for heavy dashboards            queries so dashboards    │
    │                                     load in <1s, not 15s.    │
    │                                                              │
    │  7. Wrong scrape_interval           Too fast = overload.     │
    │     (too fast or too slow)          Too slow = miss spikes.  │
    │                                     15s-60s is sweet spot.   │
    │                                                              │
    │  8. Forgetting label matchers       = is exact, != is NOT,   │
    │     syntax in PromQL                =~ is regex, !~ is NOT   │
    │                                     regex. Common exam trap! │
    │                                                              │
    │  9. Confusing instant vs range      Instant = current value. │
    │     vectors in PromQL               Range = values over time │
    │                                     (adds [5m] at the end).  │
    │                                                              │
    │  10. Not practicing hands-on        Reading PromQL ≠ writing │
    │      PromQL before the exam         PromQL. Use the demo     │

    1.4  Beyond Metrics — Logs, Events, and Traces (LF Exam Topic!)
         - Metrics are not the whole picture. The PCA exam explicitly tests:
         - Logs: Timestamped text records of discrete events
           (e.g., "ERROR: database connection refused at 14:32:01 UTC")
           → Prometheus does NOT handle logs — use Loki or Elasticsearch
         - Events: State changes in a system (pod started, deployment rolled back)
           → Kubernetes events are NOT Prometheus metrics
         - Traces/Spans: Follow a single request through multiple services
           (e.g., nginx → Django → PostgreSQL → Redis → response)
           → Prometheus does NOT do tracing — use Tempo or Jaeger
         - How they work TOGETHER: Metrics tell you WHAT, logs tell you WHY,
           traces tell you WHERE the time went

         [METRICS + LOGS + TRACES — THE FULL OBSERVABILITY STACK]
         ┌─────────────────────────────────────────────────────────────────────┐
         │                                                                     │
         │   📊 METRICS (Prometheus)    📝 LOGS (Loki/ELK)    🔍 TRACES (Tempo)│
         │   ──────────────────────    ──────────────────    ───────────────── │
         │   "error rate = 5%"         [ERROR] DB timeout    nginx → 10ms      │
         │   "p99 = 1.2s"              at 14:32:01           auth → 50ms       │
         │   "CPU = 78%"               trace_id=abc123       DB query → 800ms  │
         │                                                    render → 90ms    │
         │   Aggregated NUMBERS        Individual EVENTS     Request JOURNEY   │
         │   Answers: WHAT?            Answers: WHY?         Answers: WHERE?    │

    1.4  RED Method (Rate, Errors, Duration) — USE Method — The Four Golden Signals
         - RED: Rate (requests/sec), Errors (failed/sec), Duration (latency)
         - USE: Utilization, Saturation, Errors (for infrastructure)
         - Four Golden Signals: Latency, Traffic, Errors, Saturation
         [COMPARISON TABLE: RED vs USE vs Golden Signals — when to use each]

    1.5  SLIs, SLOs, and SLAs — The Reliability Stack
         - SLI (Service Level Indicator): What you measure (e.g., p99 latency = 200ms)
         - SLO (Service Level Objective): Your target (e.g., p99 latency < 300ms)
         - SLA (Service Level Agreement): Your promise with consequences
         - anihpj example: "99.9% of /api/jobs/ requests complete in under 500ms"

         [SLI → SLO → SLA PYRAMID]
         ┌─────────────────────────────────────────────┐
         │                                             │
         │              ╔═══════════╗                  │
         │              ║   SLA    ║  💰 CONTRACT     │
         │              ║ Promise  ║  "99.95% uptime  │
         │              ║ + penalty║   or refund"     │
         │              ╚══════════╝                   │
         │             ╔═════════════╗                 │
         │             ║    SLO      ║  🎯 TARGET      │
         │             ║  Objective  ║  "p99 < 300ms  │
         │             ║  (internal) ║   99.9% avail" │
         │             ╚═════════════╝                 │
         │           ╔═══════════════════╗             │
         │           ║       SLI         ║  📏 MEASURE │
         │           ║    Indicator       ║  "Actual    │
         │           ║   (What we see)    ║   p99=200ms │
         │           ╚═════════════════════╝   avail=99.97%"│
         │                                             │
         │  SLO > SLA (internal target tighter than    │
         │  customer promise = safety buffer)           │
         └─────────────────────────────────────────────┘

         [PCA Practice Questions — 10 Questions]

         [WHEN PROMETHEUS DOES NOT FIT — OFFICIAL GUIDANCE]
         ┌─────────────────────────────────────────────────────────────────────┐
         │                                                                     │
         │  ❌ Prometheus is NOT the right choice when:                         │
         │                                                                     │
         │  1. You need 100% ACCURACY (e.g., per-request billing)              │
         │     → Prometheus prioritizes reliability over completeness          │
         │     → Scrapes can miss data points between intervals                │
         │     → Use: dedicated billing/audit system + Prometheus for monitoring│
         │                                                                     │
         │  2. You need to store INDIVIDUAL EVENTS/LOGS                        │
         │     → Prometheus stores aggregated metrics, not raw events          │
         │     → Use: Loki, Elasticsearch, or OpenSearch for logs              │
         │                                                                     │
         │  3. Your data is NOT NUMERIC                                         │
         │     → Prometheus only handles float64 and histograms                │
         │     → Strings, text, images don't fit the time-series model         │
         │                                                                     │
         │  4. You need a PUSH-BASED model (apps pushing to a central server)  │
         │     → Prometheus is pull-first (PushGateway is for edge cases only) │
         │     → Use: InfluxDB, Graphite, or Datadog if push is essential     │
         │                                                                     │
         │  5. You need COMPLEX JOINS or TRANSACTIONS across data              │
         │     → PromQL is NOT SQL — no JOINs, no transactions                 │
         │     → Each PromQL query operates on time series independently       │
         │                                                                     │
         │  ✅ Prometheus IS the right choice for:                              │
         │  • Numeric time-series monitoring (CPU, memory, request rates)      │
         │  • Alerting based on thresholds and patterns                        │
         │  • Multi-dimensional metric analysis (by service, endpoint, region) │
         │  • Cloud-native, Kubernetes-native monitoring                       │
         │  • Reliable monitoring during outages (no external dependencies)    │
         └─────────────────────────────────────────────────────────────────────┘

    2.2  Counter, Gauge, Histogram, Summary — The 4 Metric Types
         - Counter: Only goes UP (total requests, total errors) — like a car odometer
         - Gauge: Goes up AND down (CPU %, memory bytes, temperature) — like a thermometer
         - Histogram: Distribution into buckets (request latency: <10ms, <50ms, <100ms...)
         - Summary: Like Histogram but calculates quantiles on the client side

         │   "Which histogram type provides atomicity across the network?"     │

    2.3  Labels — Adding Context to Metrics
         - Labels are key-value pairs that add dimensions to metrics
         - Good labels: method, endpoint, status_code, instance
         - Bad labels: user_id, session_token, request_body (too many unique values!)
         - Cardinality explained: why high-cardinality labels kill performance
         - anihpj example: Labeling by jobpost endpoint (/api/jobs/, /api/skills/)

         [CARDINALITY — THE SILENT KILLER]
         ┌─────────────────────────────────────────────────────────────────────┐
         │                    LABEL CARDINALITY EXPLAINED                       │
         │                                                                     │
         │  CARDINALITY = Number of unique label value combinations             │
         │                                                                     │
         │  ✅ GOOD (Low Cardinality — ~10-100 unique values)                  │
         │  ┌──────────────────────────────────────────────────────┐          │
         │  │  method="GET|POST|PUT|DELETE"      →    4 values     │          │
         │  │  status="200|301|400|404|500|502"   →   ~6 values    │          │
         │  │  endpoint="/api/jobs|skills|users"  →   ~10 values   │          │
         │  │  instance="pod-1..pod-5"            →    5 values    │          │
         │  │                                                      │          │
         │  │  TOTAL TIME SERIES: 4 × 6 × 10 × 5 = 1,200 series   │          │
         │  │  ✅ Very manageable!                                   │          │
         │  └──────────────────────────────────────────────────────┘          │
         │                                                                     │
         │  ❌ BAD (High Cardinality — Millions of unique values)              │
         │  ┌──────────────────────────────────────────────────────┐          │
         │  │  user_id="user_abc123..."          →  MILLIONS        │          │
         │  │  session_token="eyJhbG..."         →  MILLIONS        │          │
         │  │  email="user@example.com"          →  MILLIONS        │          │
         │  │  request_id="req-abc-def-ghi"      →  BILLIONS        │          │
         │  │                                                      │          │
         │  │  TOTAL TIME SERIES: M × M × M × B = 💥 EXPLOSION     │          │
         │  │  ❌ Each unique series = memory + disk + CPU cost     │          │
         │  │  ❌ Prometheus OOM kills → monitoring goes BLIND      │          │
         │  └──────────────────────────────────────────────────────┘          │
         │                                                                     │
         │  RULE OF THUMB: Keep cardinality < 100 per label, < 10 labels       │
         │  per metric. NEVER put user IDs, emails, or request IDs in labels.  │
         └─────────────────────────────────────────────────────────────────────┘

    2.4  Time-Series Data — The Heart of Prometheus
         - A time series = metric name + unique label combination + timestamp + value
         - How Prometheus stores time series: append-only, on-disk, 2-hour blocks
         - Retention: default 15 days (configurable)
         - anihpj example: Tracking jobpost request counts over 24 hours

         - Metric names: lowercase, underscores, meaningful suffixes
         - Standard suffixes: _total (counter), _seconds (duration), _bytes (size)
         - anihpj naming: jobpost_http_requests_total, anihpj_db_connections

Chapter 6: PromQL Fundamentals — Thinking in PromQL
─────────────────────────────────────────────────────
    6.1  PromQL by Analogy: SQL for Time-Series
         - SQL asks "What's the current state of this table?"
         - PromQL asks "How has this metric changed over time?"
         - Key difference: PromQL works with RANGES of time, not just snapshots
         [COMPARISON TABLE: SQL vs PromQL — concepts side by side]

    6.2  Instant Vectors — A Snapshot in Time
         - Returns the most recent value for each time series at a given moment
         - http_requests_total{job="anihpj"} → 1,247 at this exact second
         - Like asking "What's the score RIGHT NOW?"

    6.3  Range Vectors — A Window of Time
         - Returns all values for a time series over a duration
         - http_requests_total{job="anihpj"}[5m] → [1244, 1245, 1246, 1247, 1248]
         - Like asking "What was the score every 15 seconds for the last 5 minutes?"
         [RANGE VECTOR VISUAL — Timeline with data points in a 5-minute window]

    6.4  Selectors and Matchers — Finding Your Data
         - Exact match: method="GET"
         - Not equal: method!="POST"
         - Regex match: endpoint=~"/api/.*"

         - anihpj: Calculate jobpost error rate as a percentage

    7.2  Comparison Operators (==, !=, >, <, >=, <=)
         - Filtering: "Show me ONLY pods using more than 80% CPU"

         [AGGREGATION — BEFORE AND AFTER]
         ┌─────────────────────────────────────────────────────────────────────┐
         │                                                                     │
         │   BEFORE AGGREGATION (3 pods × 2 endpoints = 6 time series)        │
         │   ┌────────────────────────────────────────────────────────┐       │
         │   │  {pod="web-1", endpoint="/api/jobs"}   → 45 req/s      │       │
         │   │  {pod="web-2", endpoint="/api/jobs"}   → 52 req/s      │       │
         │   │  {pod="web-3", endpoint="/api/jobs"}   → 48 req/s      │       │
         │   │  {pod="web-1", endpoint="/api/skills"} → 12 req/s      │       │
         │   │  {pod="web-2", endpoint="/api/skills"} → 15 req/s      │       │
         │   │  {pod="web-3", endpoint="/api/skills"} → 11 req/s      │       │
         │   └────────────────────────────────────────────────────────┘       │
         │                                                                     │
         │   AFTER sum(...) by (endpoint)                                       │
         │   ┌────────────────────────────────────────────────────────┐       │
         │   │  {endpoint="/api/jobs"}   → 145 req/s   ← 45+52+48    │       │
         │   │  {endpoint="/api/skills"} →  38 req/s   ← 12+15+11    │       │
         │   └────────────────────────────────────────────────────────┘       │
         │                                                                     │
         │   AFTER sum(...) without (pod) — drops pod label only               │
         │   ┌────────────────────────────────────────────────────────┐       │
         │   │  {endpoint="/api/jobs"}   → 145 req/s                  │       │
         │   │  {endpoint="/api/skills"} →  38 req/s                  │       │
         │   └────────────────────────────────────────────────────────┘       │
         │                                                                     │
         │   KEY DIFFERENCE:                                                   │
         │   • by(X): KEEP label X, aggregate everything else                  │
         │   • without(X): DROP label X, keep everything else                  │
         └─────────────────────────────────────────────────────────────────────┘

    7.4  Rate & Increase — The Most Important Functions (80% of PCA PromQL!)
         - rate(): Per-second average rate of increase (for counters)
         - irate(): Instant rate (more sensitive to changes, good for graphs)
         - increase(): Total increase over a time range
         - GOLDEN RULE: ALWAYS use rate() or irate() on counters!
         - anihpj: rate(jobpost_http_requests_total[5m]) — requests per second

         [RATE vs INCREASE — WHAT'S THE DIFFERENCE?]
         ┌─────────────────────────────────────────────────────────────────────┐
         │                                                                     │
         │   COUNTER VALUE OVER TIME:                                          │
         │   ┌─────────────────────────────────────────────────────────┐      │
         │   │  500 ┤                                        ╭─        │      │
         │   │      │                                   ╭────╯          │      │
         │   │  400 ┤                              ╭────╯               │      │
         │   │      │                         ╭────╯                    │      │
         │   │  300 ┤                    ╭────╯                         │      │
         │   │      │              ╭─────╯                              │      │
         │   │  200 ┤         ╭────╯                                    │      │
         │   │      │    ╭────╯                                         │      │
         │   │  100 ┤╭───╯                                              │      │
         │   │      └────────────────────────────────────────────────── │      │
         │   │      10:00    10:05    10:10    10:15    10:20           │      │
         │   └─────────────────────────────────────────────────────────┘      │
         │                                                                     │
         │   rate(http_requests_total[5m])                                     │
         │   → Per-second AVERAGE over the window                              │
         │   → (500 - 100) / 300 seconds = 1.33 req/s (smoothed)              │
         │   → Use for: graphs, dashboards, alert rules (STABLE)              │
         │                                                                     │
         │   irate(http_requests_total[5m])                                    │
         │   → Per-second rate using ONLY last 2 data points                  │
         │   → More sensitive — shows spikes immediately                      │
         │   → Use for: real-time graphs, debugging sudden changes            │
         │                                                                     │
         │   increase(http_requests_total[5m])                                 │
         │   → TOTAL increase over the window                                  │
         │   → 500 - 100 = 400 requests (absolute count)                      │
         │   → Use for: "How many requests in the last hour?"                 │
         │                                                                     │
         │   ⚠️ GOLDEN RULE: NEVER apply rate() to a Gauge!                   │
         │   rate() requires a Counter (monotonically increasing)             │
         │   Applying rate() to a Gauge returns garbage data!                 │
         └─────────────────────────────────────────────────────────────────────┘

    7.5  Histogram Functions — Percentiles Made Easy
         - histogram_quantile(): Calculate p50, p95, p99 from histogram buckets
         - Rate before quantile: histogram_quantile(0.99, rate(http_duration_seconds_bucket[5m]))
         - anihpj: "99% of jobpost requests complete in under X seconds"
         - Common mistake: using histogram_quantile on the raw histogram (don't!)

         [HISTOGRAM BUCKETS — HOW THEY WORK]
         ┌─────────────────────────────────────────────────────────────────────┐
         │                                                                     │
         │   BUCKET BOUNDARIES: 0.01, 0.05, 0.1, 0.5, 1.0, +Inf             │
         │                                                                     │
         │   Observed Request Latencies (10 requests):                         │
         │   0.008s, 0.012s, 0.045s, 0.08s, 0.09s, 0.12s, 0.45s, 0.55s,     │
         │   0.6s, 1.2s                                                       │
         │                                                                     │
         │   BUCKET COUNTS (CUMULATIVE — each bucket includes all smaller):   │
         │   ┌───────────────────────────────────────────────────────────┐    │
         │   │                                                           │    │
         │   │  ≤ 0.01s:  █ 1     (only 0.008s)                         │    │
         │   │  ≤ 0.05s:  ███ 3   (+0.012s, 0.045s)                     │    │
         │   │  ≤ 0.1s:   █████ 5 (+0.08s, 0.09s)                      │    │
         │   │  ≤ 0.5s:   ████████ 8 (+0.12s, 0.45s, 0.55s — WAIT!    │    │
         │   │                0.55s goes to ≤1.0, not ≤0.5!)            │    │
         │   │  ≤ 1.0s:   █████████ 9 (+0.6s)                          │    │
         │   │  ≤ +Inf:   ██████████ 10 (+1.2s, catches everything)     │    │
         │   │                                                           │    │
         │   └───────────────────────────────────────────────────────────┘    │
         │                                                                     │
         │   histogram_quantile(0.50, rate(bucket[5m])) = p50 ≈ 0.1s          │
         │   histogram_quantile(0.90, rate(bucket[5m])) = p90 ≈ 0.6s          │
         │   histogram_quantile(0.99, rate(bucket[5m])) = p99 ≈ 1.2s          │
         │                                                                     │
         │   ⚠️ CORRECT: histogram_quantile(0.99, rate(bucket[5m]))           │
         │   ❌ WRONG:   histogram_quantile(0.99, bucket)  ← DON'T DO THIS!   │
         │   (Always rate() the histogram buckets before quantile!)           │
         │                                                                     │
         │   📐 CHOOSING BUCKETS:                                              │
         │   • Too few → inaccurate percentiles                                │
         │   • Too many → more time series = more cost                        │
         │   • Good rule: 10-15 buckets covering your expected range           │
         │   • anihpj: [0.01, 0.05, 0.1, 0.25, 0.5, 1.0, 2.5, 5, 10]        │
         └─────────────────────────────────────────────────────────────────────┘

    7.6  Time-Based Functions — Looking at the Past & Predicting the Future
         - offset: Compare to last week — http_errors[5m] offset 1w
         - predict_linear(): When will the disk fill up?
         - resets(): Detect counter resets (app restart)
         - changes(), delta(), idelta(), deriv(), holt_winters()

         [TIME FUNCTIONS QUICK REFERENCE]
         ┌──────────────────────────────────────────────────────────────────┐
         │  offset X         Shift query back (or forward with -X)          │
         │  @ timestamp       Query at specific Unix time (@ 1609746000)    │
         │  predict_linear()  Linear regression → "disk full in 4h"         │
         │  resets()          Count counter resets (app restart detection)  │
         │  changes()         Count value changes in range                  │
         │  delta()           Difference: last - first (gauges)              │
         │  idelta()          Difference: last two points (gauges)           │

         │  holt_winters()    Smoothed trend (less common)                  │
         └──────────────────────────────────────────────────────────────────┘

    7.7  Subqueries & @ Modifier — Advanced Time Control
         - Subquery: Run an instant query over a range at a resolution
           Syntax: <instant_query>[<range>:<resolution>]
           Example: rate(http_requests_total[5m])[1h:1m]
           → "Give me the 5-min rate at 1-min intervals for the last hour"
         - @ modifier: Evaluate a query at a specific Unix timestamp
           Example: http_requests_total @ 1609746000
           → "What was the value at Jan 4, 2021 07:40 UTC?"
         - start() and end() can be used as special @ values for range queries

         [SUBQUERY — VISUAL EXPLANATION]
         ┌─────────────────────────────────────────────────────────────────────┐
         │   rate(http_requests_total[5m])[1h:1m]                               │
         │                                                                     │
         │   "For the last 1 hour, give me the 5-minute rate every 1 minute"   │
         │                                                                     │
         │   ┌─────────────────────────────────────────────────────────────┐   │
         │   │  1h ago                                                now   │   │
         │   │  ├─────┼─────┼─────┼─────┼─────┼─────┼─────┼─────┼─────┤   │   │
         │   │  r1    r2    r3    r4    r5   ...   r58   r59   r60        │   │
         │   │                                                             │   │
         │   │  Each rN = rate(http_requests_total[5m]) evaluated at that  │   │
         │   │  time step. Result = range vector (60 data points)          │   │
         │   └─────────────────────────────────────────────────────────────┘   │
         │                                                                     │
         │   USE CASES:                                                        │
         │   • rate(...)[1h:5m] — smooth graph showing hourly trend           │
         │   • max_over_time(rate(...)[1h:]) — peak rate in last hour         │
         │   • avg_over_time(cpu_usage[1d:5m]) — daily CPU average            │
         │                                                                     │
         │   @ MODIFIER EXAMPLES:                                              │
         │   • http_total @ 1609746000 — value at specific Unix timestamp      │
         │   • rate(http_total[5m] @ 1609746000) — rate at that time           │
         │   • http_total @ start() — value at range query start              │
         │   • http_total offset 5m @ 1609746000 — 5min before that time      │
         └─────────────────────────────────────────────────────────────────────┘

    7.8  Staleness — Why Metrics Disappear (PCA Exam Concept!)
         - When a target stops being scraped, its metrics go "stale"
         - Default lookback delta: 5 minutes (configurable via --query.lookback-delta)
         - After 5 min of no new samples → metric disappears from queries
         - This is INTENTIONAL: Prometheus assumes the target is gone
         - Staleness prevents graphing flat lines forever after a pod dies
         - track_timestamps_staleness: for exporters that set their own timestamps

         [STALENESS — HOW IT WORKS]
         ┌─────────────────────────────────────────────────────────────────────┐
         │                                                                     │
         │   Pod "anihpj-web-abc" is running, scraped every 15s:               │
         │   ┌──────────────────────────────────────────────────────────┐     │
         │   │  ●──●──●──●──●──●──●──●──●──●──●──●──●──●──●──●         │     │
         │   │  T-4m                                          now       │     │
         │   │  ✅ All queries return this metric normally               │     │
         │   └──────────────────────────────────────────────────────────┘     │
         │                                                                     │
         │   Pod dies at T+0. Prometheus last scraped at T-1s:                  │
         │   ┌──────────────────────────────────────────────────────────┐     │
         │   │  ●──●──●──●──●──●──●──●──●──●──●──●──●──●──●──●  ✗      │     │
         │   │  T-4m                                          T-1s  dead│     │
         │   │  ✅ For 5 min after T-1s: metric STILL returns last value│     │
         │   │  ❌ After 5 min: metric GONE from queries (staleness)    │     │
         │   └──────────────────────────────────────────────────────────┘     │
         │                                                                     │
         │   WHY THIS MATTERS FOR PCA:                                         │
         │   • "Why did my graph go blank?" → target died, staleness kicked in │
         │   • "Why is up{} still 1?" → up{} is the last scrape before death  │
         │     Use up{} == 1 with care — it lags by up to 5 min after death!   │
         │   • For faster detection, use: up{} == 0 (instantly 0 when down)   │
         │   • Federation + staleness = metrics disappear from global view     │
         │     if regional Prometheus doesn't forward them                     │
         └─────────────────────────────────────────────────────────────────────┘

    7.9  Aggregating OVER TIME — The `_over_time` Functions (LF Exam!)
         - These are DIFFERENT from aggregation operators (sum, avg, etc.)
         - Aggregation operators work ACROSS series (dimensions)
         - `_over_time` functions work WITHIN a single series (time window)
         - They take a RANGE VECTOR as input and return an INSTANT VECTOR

         [AGGREGATING OVER TIME vs OVER DIMENSIONS — KNOW THE DIFFERENCE!]
         ┌─────────────────────────────────────────────────────────────────────┐
         │                                                                     │
         │   ACROSS DIMENSIONS (sum/avg by)     WITHIN TIME (avg_over_time)    │
         │   ┌───────────────────────────┐     ┌───────────────────────────┐   │
         │   │  pod-1: 45 req/s          │     │  pod-1 at T+0:   45 req/s │   │
         │   │  pod-2: 52 req/s  ──sum──▶│     │      at T+15s:  47 req/s │   │
         │   │  pod-3: 48 req/s          │     │      at T+30s:  44 req/s │   │
         │   │         = 145 total       │     │                          │   │
         │   │                           │     │  avg_over_time(pod1[1m]) │   │
         │   │  sum() by (endpoint)      │     │  = (45+47+44)/3 = 45.3  │   │
         │   └───────────────────────────┘     └───────────────────────────┘   │
         │                                                                     │
         │   ALL _over_time FUNCTIONS:                                         │
         │   ┌─────────────────────────────────────────────────────────────┐   │
         │   │  avg_over_time(range-vector)    Average of values in range  │   │
         │   │  max_over_time(range-vector)    Maximum value in range      │   │
         │   │  min_over_time(range-vector)    Minimum value in range      │   │
         │   │  sum_over_time(range-vector)    Sum of ALL values in range  │   │
         │   │  count_over_time(range-vector)  Count of values in range    │   │
         │   │  stddev_over_time(range-vector) Standard deviation in range │   │
         │   │  stdvar_over_time(range-vector) Variance in range           │   │
         │   │  last_over_time(range-vector)   Last value in range         │   │
         │   │  present_over_time(range-vector)Count of present values     │   │
         │   │  quantile_over_time(scalar,     φ-quantile of values in     │   │
         │   │     range-vector)               range                       │   │
         │   └─────────────────────────────────────────────────────────────┘   │
         │                                                                     │
         │   anihpj EXAMPLES:                                                  │
         │   • max_over_time(node_cpu_usage[1h]) — Peak CPU in the last hour  │
         │   • avg_over_time(jobpost_response_latency[30m]) — Avg latency     │
         │   • count_over_time(up[1h]) — How many scrapes happened?           │
         │   • quantile_over_time(0.95, cpu[1h]) — 95th percentile CPU        │
         └─────────────────────────────────────────────────────────────────────┘

    7.10 Binary Operators — Matching Series Between Metrics (LF Exam!)
         - Arithmetic: +, -, *, /, %, ^ (between two instant vectors)
         - Comparison: ==, !=, >, <, >=, <= (filter or return bool)
         - Logical/Set: and, or, unless (between two instant vectors)
         - Vector matching: how labels are matched between left and right sides

         [BINARY OPERATOR VECTOR MATCHING]
         ┌─────────────────────────────────────────────────────────────────────┐
         │                                                                     │
         │   ONE-TO-ONE MATCHING (default):                                     │
         │   ┌──────────────────────────────────────────────────────────┐     │
         │   │  Left: method_code:errors{method="GET", code="500"} = 12  │     │
         │   │  Right:method_code:total{method="GET", code="500"}  = 240 │     │
         │   │                                                           │     │
         │   │  errors / total = 12/240 = 0.05 (5% error rate)           │     │
         │   │  ✅ Matched on labels {method, code}                       │     │
         │   └──────────────────────────────────────────────────────────┘     │
         │                                                                     │
         │   MANY-TO-ONE / ONE-TO-MANY (with group_left/group_right):         │
         │   ┌──────────────────────────────────────────────────────────┐     │
         │   │  Left:  cpu_usage{instance="node-1", cpu="0"} = 45       │     │
         │   │         cpu_usage{instance="node-1", cpu="1"} = 52       │     │
         │   │  Right: node_memory{instance="node-1"} = 16777216        │     │
         │   │                                                           │     │
         │   │  cpu_usage * on(instance) group_left node_memory          │     │
         │   │  → Adds memory label to each CPU series                   │     │
         │   └──────────────────────────────────────────────────────────┘     │
         │                                                                     │
         │   KEY KEYWORDS:                                                     │
         │   • on(label1, label2)  — Match ONLY on these labels               │
         │   • ignoring(label1)    — Match on ALL labels EXCEPT these         │
         │   • group_left          — Many samples on left match one on right   │
         │   • group_right         — One sample on left matches many on right  │
         │                                                                     │
         │   LOGICAL/SET OPERATORS:                                            │
         │   • and — Intersection: keep left where right exists                │
         │   • or  — Union: left + right where left is missing                 │
         │   • unless — Complement: keep left where right does NOT exist       │
         │                                                                     │
         │   anihpj EXAMPLE:                                                   │
         │   sum(rate(http_errors[5m])) by (endpoint)                          │
         │     /                                                                │
         │   sum(rate(http_total[5m])) by (endpoint)                           │
         │   → Error rate per endpoint (auto-matched on "endpoint" label)      │
         └─────────────────────────────────────────────────────────────────────┘

    7.11 Timestamp Metrics — Working with Time Itself (LF Exam!)

         - Example: timestamp(up{job="anihpj-django"})
           → Returns the Unix time (in seconds) of each up{} sample's scrape
         - time(): Returns the current query evaluation time as a scalar

         - Not commonly used in dashboards, but VERY useful for debugging

    11.2 Writing Alerting Rules (YAML)
         - alert: the name of the alert
         - expr: the PromQL condition
         - for: how long the condition must be true before firing
         - labels: severity, team, component
         - annotations: summary, description, runbook_url

    12.1 Alertmanager Architecture
         - Receives alerts from Prometheus (and other sources)
         - Deduplicates (same alert from multiple Prometheus instances)
         - Groups (related alerts sent together, not one-by-one)
         - Routes (different alerts → different receivers)
         - Inhibits (suppress low-priority alerts when high-priority is firing)
         - Silences (temporary mute for maintenance windows)

    12.3 Grouping — Don't Flood the On-Call Engineer
         - group_by: alerts with same labels grouped into one notification
         - group_wait: how long to wait for more alerts in the group
         - group_interval: how often to send updates for the same group
         - Example: 50 pods all go down → ONE alert saying "50 pods down"
           (not 50 separate alerts!)

         [GROUPING — 50 ALERTS → 1 NOTIFICATION]
         ┌─────────────────────────────────────────────────────────────────────┐

Chapter 13: Recording Rules — Pre-Compute for Speed
─────────────────────────────────────────────────────
    13.1 Why Recording Rules? (Performance & Consistency)
         - Expensive queries run every time someone opens a dashboard
         - Recording rules pre-compute results at evaluation_interval
         - Dashboard queries become instant reads, not expensive calculations
         - Example: computing 99th percentile latency over 30 days is SLOW
           → pre-compute it every 60 seconds → dashboard loads instantly

         [RECORDING RULES — BEFORE vs AFTER]
         ┌─────────────────────────────────────────────────────────────────────┐
         │                                                                     │
         │   ❌ WITHOUT RECORDING RULES:                                        │
         │   ┌──────────────────────────────────────────────────────────┐     │
         │   │  User opens dashboard                                     │     │
         │   │     │                                                    │     │
         │   │     ▼                                                    │     │
         │   │  Grafana queries Prometheus                              │     │
         │   │     │                                                    │     │
         │   │     ▼                                                    │     │
         │   │  PromQL: histogram_quantile(0.99,                        │     │
         │   │    rate(http_duration_bucket[30d]))  ← 30 DAYS of data!  │     │
         │   │     │                                                    │     │
         │   │     ▼                                                    │     │
         │   │  ⏱️ 15 seconds waiting... ⏱️                              │     │
         │   │     │                                                    │     │
         │   │     ▼                                                    │     │
         │   │  Dashboard finally loads 😤                              │     │
         │   │                                                          │     │
         │   │  EVERY user who opens the dashboard repeats this wait!   │     │
         │   └──────────────────────────────────────────────────────────┘     │
         │                                                                     │
         │   ✅ WITH RECORDING RULES:                                           │
         │   ┌──────────────────────────────────────────────────────────┐     │
         │   │  Recording Rule (evaluated every 60s):                    │     │
         │   │    record: job:http_latency:p99_30d                       │     │

         │   │                          │                                │     │
         │   │                          ▼                                │     │
         │   │  Pre-computes result → stores as new metric               │     │
         │   │                          │                                │     │
         │   │                          ▼                                │     │
         │   │  Dashboard just reads: job:http_latency:p99_30d           │     │

    15.3 Long-Term Storage — Beyond 15 Days
         - Prometheus local storage is NOT for years of data
         - Remote Write: send metrics to external storage (Thanos, Cortex, VictoriaMetrics)
         - Remote Read: query external storage transparently
         - Thanos: adds global query view, downsampling, and object storage
         - anihpj: retain 15 days in Prometheus, 2 years in Thanos/S3

    15.4 Agent Mode — Prometheus Without Storage or Querying
         - Introduced in Prometheus v2.32 (stable in v2.40+)
         - Prometheus runs as a "forward-only" agent — no local TSDB, no querying
         - What it does: scrape targets → remote write to central Prometheus/Thanos
         - Use case: edge clusters, IoT, environments where you don't need local queries
         - Benefit: much lower resource usage (no disk I/O for TSDB)
         - Configuration: add --agent flag to prometheus command
         - anihpj edge: agent mode on each edge cluster → remote write to global Prometheus

Appendix H: Common PromQL Patterns & Recipes
─────────────────────────────────────────────
    - Rate calculations, error budgets, SLO tracking
    - Apdex scores, uptime calculations, saturation detection
    - Top-N queries, YoY comparisons, forecasting

    [ERROR BUDGET & SLO PATTERNS]
    ┌──────────────────────────────────────────────────────────────────┐
    │  ERROR BUDGET REMAINING (30-day window, 99.9% SLO):              │
    │  (1 - 0.999) * 30 * 24 * 3600 = 2592 seconds budget             │
    │                                                                  │
    │  ERROR BUDGET BURN RATE:                                         │
    │  rate(http_errors_total[1h]) / (rate(http_total[1h]) * 0.001)   │
    │  > 1 = burning budget faster than allowed                        │
    │                                                                  │
    │  SLO COMPLIANCE (last 30 days):                                  │
    │  sum(rate(http_total{status!~"5.."}[30d]))                       │
    │  /                                                                │
    │  sum(rate(http_total[30d]))                                      │
    │                                                                  │
    │  APDEX SCORE FOR API:                                            │
    │  (count of fast requests + count of slow requests / 2)           │
    │    / total count                                                 │
    │  fast: < 300ms, slow: 300ms-1200ms, intolerable: > 1200ms       │
    └──────────────────────────────────────────────────────────────────┘

    [ANOMALY DETECTION & FORECASTING]
    ┌──────────────────────────────────────────────────────────────────┐
    │  WEEK-OVER-WEEK COMPARISON:                                      │
    │  rate(http_total[5m]) / rate(http_total[5m] offset 1w)          │
    │  > 1.5 = 50%+ increase vs last week                             │
    │                                                                  │
    │  SPIKE DETECTION:                                                │
    │  rate(http_total[5m])                                            │
    │  >                                                                 │
    │  avg_over_time(rate(http_total[5m])[1h]) * 2                    │
    │  (current rate > 2× the 1-hour average = spike)                  │
    │                                                                  │
    │  DISK FULL PREDICTION:                                           │
    │  predict_linear(node_filesystem_free_bytes{mountpoint="/"}[1h],  │
    │    24 * 3600) < 0                                                │
    │  → Disk will be full within 24 hours                             │
    │                                                                  │
    │  MEMORY LEAK DETECTION (steady increase over 6h):                │
    │  deriv(node_memory_MemAvailable_bytes[6h]) < 0                   │
    │  (negative derivative = memory decreasing = leak)                │
    └──────────────────────────────────────────────────────────────────┘

Appendix I: Glossary — Prometheus & Observability Terms
────────────────────────────────────────────────────────
    - A-Z glossary of every term used in this guide
    - Cross-references to relevant chapters

    [A-Z GLOSSARY]
    ┌──────────────────────────────────────────────────────────────────┐
    │  Alertmanager — External service that handles alerts sent by     │
    │    Prometheus. Deduplicates, groups, routes, silences. (Ch 12)   │
    │                                                                  │
    │  Cardinality — Number of unique label value combinations for a   │
    │    metric. HIGH cardinality = memory/performance problems. (2.3) │
    │                                                                  │
    │  Counter — Metric type that only increases (or resets to zero).  │
    │    Example: http_requests_total. Use rate() on counters. (2.2)   │
    │                                                                  │
    │  Exporters — Programs that expose app-specific metrics in        │
    │    Prometheus format at /metrics. (Ch 5)                         │
    │                                                                  │
    │  Federation — Hierarchical Prometheus: regional instances        │
    │    scrape targets, global instance scrapes regionals. (15.2)     │
    │                                                                  │
    │  Gauge — Metric type that can go up or down. Example:            │
    │    node_memory_usage_bytes. Use directly, no rate() needed. (2.2)│
    │                                                                  │
    │  Histogram — Metric type that counts observations into           │
    │    configurable buckets. Use histogram_quantile() for percentiles.│
    │    Two types: Classic (multiple series) and Native (one sample). │
    │                                                                  │
    │  Instant Vector — Set of time series, each with ONE sample at    │
    │    the same timestamp. Result of most PromQL expressions. (6.2)  │
    │                                                                  │
    │  Job — Auto-label identifying the scrape job name from           │
    │    prometheus.yml. Often used for aggregation. (4.6)             │
    │                                                                  │
    │  Labels — Key-value pairs attached to metrics for dimensional    │
    │    filtering and aggregation. (2.3, 2.4)                         │
    │                                                                  │
    │  PromQL — Prometheus Query Language. Functional language for     │
    │    selecting, aggregating, and transforming time series. (Ch 6-8)│
    │                                                                  │
    │  PushGateway — Intermediary for short-lived jobs to push metrics │
    │    to Prometheus. Use ONLY for batch/CronJobs, not services.(3.2)│
    │                                                                  │
    │  Range Vector — Set of time series, each with MULTIPLE samples   │
    │    over a time range. Created by adding [duration]. (6.3)        │
    │                                                                  │
    │  Recording Rules — Pre-computed PromQL expressions saved as new  │
    │    metrics. Use for expensive dashboard queries. (Ch 13)         │
    │                                                                  │
    │  Relabeling — Modifying or filtering labels before/after scrape. │
    │    relabel_configs (before) vs metric_relabel_configs (after).   │
    │                                                                  │
    │  Remote Write — Send metrics to external storage (Thanos, etc.)  │
    │    for long-term retention beyond local TSDB. (15.3)             │
    │                                                                  │
    │  Scrape — Prometheus fetches /metrics from a target at           │
    │    scrape_interval. The core data collection mechanism. (3.2)    │
    │                                                                  │
    │  Service Discovery — Automatically finding monitoring targets    │
    │    via K8s API, Consul, DNS, EC2, etc. (Ch 4)                    │
    │                                                                  │
    │  SLI/SLO/SLA — Service Level Indicator (measurement), Objective  │
    │    (target), Agreement (contract). Reliability stack. (1.5)      │
    │                                                                  │
    │  Staleness — Metrics disappear from queries 5 min after target   │
    │    stops being scraped. Controlled by --query.lookback-delta.    │
    │                                                                  │
    │  Summary — Metric type similar to Histogram but calculates       │
    │    quantiles client-side. Less flexible than Histogram. (2.2)    │
    │                                                                  │
    │  Thanos — CNCF project adding global query view, long-term       │
    │    storage (S3/GCS), and downsampling to Prometheus. (15.3)     │
    │                                                                  │
    │  TSDB — Time-Series Database. Prometheus's local storage engine  │
    │    using 2-hour blocks on disk. Default retention: 15 days.(3.1) │
    └──────────────────────────────────────────────────────────────────┘
