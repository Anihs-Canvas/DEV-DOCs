WHAT IS A CLOUD NATIVE PLATFORM ENGINEER (CNPE)?
═══════════════════════════════════════════════════════════════════════

A Cloud Native Platform Engineer builds and maintains the INTERNAL DEVELOPER
PLATFORM (IDP) that enables developers to deploy, run, and manage applications
without needing deep infrastructure knowledge.

    ┌──────────────────────────────────────────────────────────────┐
    │ 🏗️ Platform Engineer = Building the FACTORY (platform)       │
    │ 🎨 Developer         = Using the factory (apps)               │
    │                                                              │
    │ You are the bridge between:                                  │
    │   • Infrastructure (servers, networks, storage)              │
    │   • Operations (monitoring, security, compliance)            │
    │   • Development (CI/CD, developer tools, self-service)       │
    └──────────────────────────────────────────────────────────────┘

CNPE vs CKA vs CKAD — WHAT'S THE DIFFERENCE?
─────────────────────────────────────────────
    ┌──────────────────────────────────────────────────────────────────┐
    │                    CKA              CKAD           CNPE           │
    │  Focus:           Administrator     App Developer   Platform Eng  │
    │  You manage:      The CLUSTER       The APPS        The PLATFORM  │
    │  Scope:           Single cluster    App lifecycle   Multi-cluster, │
    │                                                 multi-tool, IDP  │
    │  Tools:           kubeadm, etcd,    kubectl, Helm,  ArgoCD, Tofu, │
    │                   kubelet, certs    ConfigMaps,     Crossplane,    │
    │                                     Secrets, Pods   Backstage,     │
    │                                                      Prometheus    │
    │  Think of it:     🏗️ Building      🎨 Decorating   🏭 Building    │
    │                   the house         the rooms       the factory   │
    └──────────────────────────────────────────────────────────────────┘

of what a Cloud Native Platform IS, why it exists, and how all the pieces
fit together. Essential for novices; useful refresher for experienced engineers.

F.1 The Problem Before Platform Engineering
    • Traditional Ops: "File a ticket, wait 2 weeks for a VM"
    • Developers drowning in infrastructure complexity
    • The cognitive load problem — what devs must know without a platform
    • The "it works on my machine" production gap
    • Real scenario: anihpj team wants to deploy jobpost — needs database,
      secrets, ingress, monitoring, backups... without a platform
    • The Shipping Port Analogy: Platform = Port, App = Ship, Container = Box
    🟢 Novice | 🎯 Foundational

F.2 Containers 101 — Docker, OCI & Image Registries
    • What IS a container? (Process isolation, not a "mini VM")
    • Dockerfile anatomy (FROM, WORKDIR, COPY, RUN, CMD, EXPOSE)
    • Multi-stage builds and distroless images for production
    • Image layers, caching, and why COPY requirements.txt before COPY .
    • Container registries: Docker Hub, ECR, Harbor, GHCR
    • anihpj/jobpost Dockerfile walkthrough (Django + Gunicorn + PostgreSQL client)
    🟢 Novice | 🟡 Intermediate: Layer optimization, SBOM, image signing

F.3 Kubernetes Core Concepts — The "Big Picture" Mental Model
    • Cluster = Control Plane + Worker Nodes (ASCII diagram)
    • Pod = smallest deployable unit (1+ containers sharing network namespace)
    • Declarative vs Imperative: "I want 3 replicas" vs "start 3 pods"
    • Desired State vs Actual State — the reconciliation loop
    • kubectl: your remote control for the cluster
    • How CNPE extends K8s: CRDs, Operators, Admission Webhooks
    🟢 Novice | 🟡 Intermediate: Controller pattern, custom controllers

F.4 The anihpj/jobpost Application Stack

    • API tier (Django REST Framework) — anihpj-api
    • Database tier (PostgreSQL 15) — anihpj-db
    • Redis (Celery task queue + caching) — anihpj-redis
    • How these tiers talk to each other (Service discovery via DNS)
    • Complete file tree diagram of the Django project
    • Dockerfile for anihpj (multi-stage build, non-root user, health checks)
    🟢 Novice

F.5 Platform Engineering vs DevOps vs SRE — Understanding the Roles
    • DevOps: Culture of collaboration between dev and ops
    • SRE: Reliability engineering with SLOs, error budgets, toil reduction
    • Platform Engineering: Building the IDP that enables DevOps at scale
    • "You build it, you run it" — how platforms make this possible
    • The Platform as a PRODUCT (not just infrastructure)
    • Golden Paths: paved roads for common developer workflows
    🟢 Novice | 🎯 Foundational

F.6 The CNCF Landscape — Tools You'll Use as a CNPE

    • Incubating projects: Backstage, Crossplane, ArgoCD, Kyverno, OpenTelemetry

CATEGORY 1: PLATFORM ARCHITECTURE & INFRASTRUCTURE (15% = 30 Questions) — Q1-Q30
───────────────────────────────────────────────────────────────────────
"This category is about the FOUNDATION of your platform — the infrastructure
that everything else runs on. Think of it as building the FACTORY FLOOR.
You'll design networks, storage systems, compute nodes, and multi-tenant
structures that support all the apps and teams using your platform."

1.1 Platform Architecture Fundamentals (8 Qs)
    Q1:  What is an Internal Developer Platform (IDP)?
         (The "factory floor" analogy — building the system that lets devs ship)
    Q2:  Platform vs Infrastructure — what's the difference?
         (Infrastructure = raw materials; Platform = the assembly line)
    Q3:  The 5-Layer Cloud Native Platform Stack
         (Infra → Orchestration → Observability → Delivery → Developer Experience)
    Q4:  Platform Engineering vs DevOps vs SRE — role boundaries
         (PE builds the platform; DevOps uses it; SRE measures reliability)
    Q5:  High Availability patterns for platform services
         (Active-Passive vs Active-Active, load balancers, health checks)
    Q6:  Disaster Recovery — RPO (Recovery Point Objective) vs RTO (Recovery Time Objective)
         (How much data can you lose? How fast must you recover?)
    Q7:  Capacity Planning — right-sizing nodes for platform workloads
         (CPU/memory headroom, overcommit ratios, node pool sizing)
    Q8:  Platform SLAs, SLOs, and SLIs — measuring platform reliability
         (anihpj platform: 99.9% uptime SLO, measured by API availability SLI)

1.2 Networking for Platform Engineers (8 Qs)
    Q9:  Kubernetes networking model — every pod gets a unique IP
         (Why "IP-per-pod" eliminates port conflicts across teams)
    Q10: CNI (Container Network Interface) — Calico, Cilium, Flannel compared
         (Overlay vs BGP vs eBPF — which CNI for your platform?)
    Q11: Service mesh — Istio, Linkerd, Cilium Service Mesh
         (When does your platform need a service mesh? mTLS, traffic splitting)
    Q12: Ingress vs Gateway API — routing external traffic to platform services
         (Ingress for simple; Gateway API for multi-team, role-based routing)
    Q13: Multi-cluster networking — Submariner, Cilium Cluster Mesh, Istio multicluster
         (Connecting anihpj API in cluster-A to anihpj DB in cluster-B)
    Q14: DNS in Kubernetes — CoreDNS, stub domains, custom DNS policies
         (anihpj-api.anihpj.svc.cluster.local — how service discovery works)
    Q15: NetworkPolicy vs CiliumNetworkPolicy — securing platform traffic
         (L3/L4 vs L7 policies; DNS-based, HTTP-based filtering)
    Q16: Load balancing strategies — external LB, NodePort, Ingress controller placement
         (AWS NLB → Ingress Controller → Service → Pod)

1.3 Storage Architecture for Platforms (7 Qs)
    Q17: StorageClass and Dynamic Provisioning for multi-tenant platforms
         (Each team gets their own StorageClass with resource quotas)
    Q18: CSI (Container Storage Interface) — pluggable storage for any backend
         (AWS EBS CSI, Azure Disk CSI, NFS CSI, local-path)
    Q19: RWX (ReadWriteMany) — when multiple pods across nodes need shared storage
         (anihpj uploads volume shared by all API pods via NFS/EFS)
    Q20: StatefulSet vs Deployment — when your platform apps need stable identity
         (PostgreSQL needs stable network identity + persistent storage ordering)
    Q21: Backup strategies for platform data — Velero, etcd snapshots, CSI snapshots
         (anihpj database backup: Velero backup --include-resources pvc,pv)
    Q22: Volume Snapshots and Restore — CSI snapshotting for disaster recovery
         (Point-in-time snapshots of anihpj-db PVC before schema migration)
    Q23: Storage performance tiers — SSD vs HDD, IOPS, throughput, latency
         (anihpj-db needs high IOPS SSD; anihpj-logs can use HDD)

1.4 Compute, Scaling & Multi-Tenancy (7 Qs)
    Q24: Node pools and node selectors — segregating platform workloads
         (System pool for control plane; App pool for tenant apps; GPU pool for ML)
    Q25: Taints and Tolerations — "this node is reserved for database pods only"
         (Dedicated node for anihpj-db PostgreSQL with taint db=true:NoSchedule)
    Q26: Cluster Autoscaler and Karpenter — automatic node provisioning
         (When all nodes are full, autoscaler adds new nodes for pending pods)
    Q27: Multi-tenancy models — namespace-as-a-service, cluster-as-a-service, vcluster
         (anihpj team gets namespace "anihpj-dev"; another team gets "ml-pipeline")
    Q28: Resource Quotas and Limit Ranges — preventing tenant resource hogging
         (anihpj-dev namespace: max 10 pods, 20Gi storage, 4 CPU, 8Gi memory)
    Q29: Cost management — Kubecost, right-sizing, spot instances, FinOps
         (anihpj platform costs: $X/month compute + $Y/month storage + $Z/month network)
    Q30: Platform capacity dashboard — visualizing resource usage across all tenants
         (Grafana dashboard: CPU/Memory/Storage/Network per namespace, per team)

CATEGORY 2: GITOPS & CONTINUOUS DELIVERY (25% = 50 Questions) — Q31-Q80
───────────────────────────────────────────────────────────────────────
"This is the biggest category alongside Platform APIs. GitOps is the backbone

2.1 GitOps Fundamentals & Principles (10 Qs)
    Q31: What is GitOps? The 4 Principles
         (Declarative, Versioned/Immutable, Pull Automatically, Continuously Reconciled)
    Q32: Push vs Pull deployment models — why GitOps prefers PULL
         (Push: CI pushes to cluster; Pull: ArgoCD pulls from Git — more secure)
    Q33: Git as the single source of truth — everything in Git
         (Infra, apps, policies, dashboards, alerts — all in Git repos)
    Q34: The GitOps reconciliation loop — observe → diff → sync
         (ArgoCD checks Git every 3 minutes; if drift detected, auto-sync)
    Q35: Declarative vs Imperative — why "desired state" matters for platforms
         ("I want 3 replicas" vs "start 3 pods" — GitOps only works with declarative)
    Q36: Git repository structure for platform teams — monorepo vs polyrepo
         (anihpj monorepo: /apps/jobpost, /infra/terraform, /policies/kyverno)
    Q37: Branching strategies for GitOps — trunk-based, GitFlow, environment branches
         (anihpj: main → auto-deploy to staging; release/* → manual deploy to prod)
    Q38: GitOps Environment Management — dev/staging/prod separation
         (Kustomize overlays: /base → /overlays/dev, /overlays/staging, /overlays/prod)
    Q39: Secrets Management in GitOps — Sealed Secrets, External Secrets Operator, Vault
         (NEVER commit plaintext secrets to Git — use SealedSecrets or ESO)
    Q40: Drift Detection and Auto-Healing — when reality doesn't match Git
         (Someone kubectl-edited a deployment manually → ArgoCD detects and reverts)

2.2 ArgoCD Deep Dive (12 Qs)
    Q41: ArgoCD Architecture — API Server, Repository Server, Application Controller

    Q44: ArgoCD Sync Policies — manual vs automatic, pruning, self-heal

CATEGORY 3: PLATFORM APIs & SELF-SERVICE CAPABILITIES (25% = 50 Questions) — Q81-Q130

3.1 Custom Resource Definitions (CRDs) Deep Dive (10 Qs)
    Q81: What is a CRD? Extending the Kubernetes API with your own resource types
         (Kubernetes knows Pod, Service, Deployment; YOU teach it "Database", "Environment")
    Q82: CRD Schema — OpenAPI v3 validation for custom resources
         (Define required fields, types, enums, minimum/maximum for your CRD)
    Q83: CRD Versions — alpha, beta, v1 stability levels and conversion strategies
         (v1alpha1 → v1beta1 → v1 — each version adds stability guarantees)
    Q84: CRD Conversion Webhooks — converting between CRD versions
         (When a user submits v1alpha1, webhook converts to v1beta1 for storage)
    Q85: CRD Subresources — /status and /scale for custom resources
         (kubectl get databases shows STATUS: Ready; kubectl scale database --replicas=3)
    Q86: CRD Printer Columns — customizing kubectl get output for your resource
         (kubectl get databases shows: NAME, ENGINE, VERSION, SIZE, STATUS, AGE)
    Q87: CRD Categories — grouping custom resources for kubectl get all
         (kubectl get databases → included in kubectl get all for anihpj resources)
    Q88: CRD Admission Webhooks — validating and mutating custom resources
         (Validation webhook: "Database size must be between 5Gi and 500Gi")
