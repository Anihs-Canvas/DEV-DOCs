Core Fundamentals Q1 of 200
What is the key difference between declarative and imperative resource management in platform engineering, and why do platforms like anihpj prefer declarative approaches?
A) Declarative means you write scripts; imperative means you write YAML — platforms prefer scripts for flexibility
B) Declarative specifies the DESIRED end state ("I want 3 replicas"); imperative specifies the EXACT steps ("start 3 pods one by one") — platforms use declarative because it's self-healing, idempotent, and version-controlled in Git
C) There is no real difference — declarative and imperative are synonyms used interchangeably in Kubernetes documentation
D) Declarative is used only for cloud resources (AWS, GCP); imperative is used only for on-premises infrastructure
✅ Correct Answer: B

Declarative ("what") — you describe the DESIRED state. The platform figures out HOW to achieve it. Imperative ("how") — you specify each exact step. This distinction is THE foundational concept of platform engineering.

📝 Detailed Explanation
Declarative vs Imperative — Why Platforms MUST Be Declarative
  DECLARATIVE (What you want)              IMPERATIVE (How to do it)
  ┌────────────────────────────┐          ┌────────────────────────────┐
  │ kubectl apply -f deploy.yaml│          │ kubectl run anihpj-api      │
  │                             │          │ --image=anihpj:v1.2.3     │
  │ replicas: 3                 │          │ --replicas=3               │
  │ image: anihpj/jobpost:v1.2.3│          │ --port=8000               │
  │ resources:                  │          │                            │
  │   requests: {cpu:250m}      │          │ Then check, scale, update  │
  │                             │          │ manually each time...      │
  └────────────────────────────┘          └────────────────────────────┘
  
  WHY DECLARATIVE WINS FOR PLATFORMS:
  ✅ Self-healing: Controller sees 2 pods → creates 1 to match desired 3
  ✅ Git as truth: YAML in Git → ArgoCD syncs → cluster matches Git
  ✅ Idempotent: apply 1 time or 100 times → same result
  ✅ Diff-friendly: Git shows what changed; code review catches issues
  ✅ Rollback: git revert → ArgoCD auto-reverts cluster
  
  For anihpj/jobpost: The entire platform stack (Deployments, Services,
  Ingress, ConfigMaps, NetworkPolicies) is declared in YAML, stored in
  Git, and auto-synced to the cluster via ArgoCD. Nobody runs kubectl
  commands manually in production — that's imperative thinking.

This is why GitOps exists — it takes declarative resource management to its logical conclusion: Git becomes the single source of truth, and the platform continuously reconciles the cluster to match Git. Any manual kubectl edit to a running pod is drift that the platform detects and corrects.

Core Fundamentals Q2 of 200
You are designing the anihpj platform. The team currently uses imperative scripts (kubectl run, kubectl scale, kubectl set image) to manage deployments. Why should the platform architecture be rebuilt around declarative resource management instead?
A) Declarative commands are faster to type and require fewer keystrokes than imperative ones
B) Declarative configurations can only be written in YAML, which is the industry standard for Kubernetes
C) Declarative management enables self-healing (controller reconciles actual → desired), GitOps (Git as single source of truth), idempotency (apply N times = same result), and auditability (every change tracked in Git history)
D) Imperative commands are deprecated in Kubernetes 1.30+ and will be removed in future versions
✅ Correct Answer: C

Declarative management is the architectural foundation of platform engineering — not just a "style preference." It enables four critical platform capabilities that imperative approaches fundamentally cannot deliver.

📝 Detailed Explanation
Why Platforms MUST Be Declarative — The Four Pillars
  IMPERATIVE (How)                          DECLARATIVE (What)
  ┌────────────────────────────┐           ┌────────────────────────────┐
  │ $ kubectl run anihpj-api   │           │ $ kubectl apply -f deploy/  │
  │ $ kubectl scale --replicas=5│          │                              │
  │ $ kubectl set image ...    │           │ # deploy/anihpj-api.yaml:    │
  │ $ kubectl expose ...       │           │ #   replicas: 5              │
  │                             │           │ #   image: anihpj:v1.2.3    │
  │ ❌ What if scale fails?    │           │ #   resources: {cpu:250m}   │
  │ ❌ Who ran set image?      │           │ #   ports: [8000]            │
  │ ❌ What's the current state?│          │                              │
  └────────────────────────────┘           └────────────────────────────┘

  FOUR PILLARS OF DECLARATIVE PLATFORMS:
  
  🔄 SELF-HEALING: Controller constantly reconciles
     • Actual: 2 pods running  →  Desired: 3 pods  →  Controller creates 1
     • Pod crashes? Controller notices and replaces it automatically
     • No human intervention needed — the platform fixes itself
  
  📋 GITOPS: Git is the single source of truth
     • Every change = a Git commit with author, timestamp, diff
     • ArgoCD watches Git → auto-syncs cluster to match
     • Rollback = git revert → ArgoCD auto-reverts the cluster
     • Audit: "Who changed replicas from 3 to 5?" → git log shows answer
  
  🔁 IDEMPOTENCY: Apply 1 time or 100 times → same result
     • kubectl apply is safe to re-run; kubectl create fails on 2nd run
     • CI/CD pipelines can re-apply manifests safely
     • No "already exists" errors — controller handles it gracefully
  
  📊 AUDITABILITY & COMPLIANCE:
     • Every change is a Git commit with review (PR → approve → merge)
     • SOC2/PCI-DSS: "Show me every production change in the last 90 days"
     • Answer: git log --since="90 days ago" -- production/
     • Imperative: "Uh, someone ran kubectl edit at 3am... maybe?"
  
  For anihpj/jobpost: The entire platform — Django API, PostgreSQL DB,
  Redis cache, Ingress, NetworkPolicies — is in Git. ArgoCD auto-syncs.
  Nobody runs kubectl commands in production. Every change is reviewed.

Imperative commands are not deprecated (D is false), YAML is common but not required (B is false — you can use JSON), and keystroke count is irrelevant (A misses the point). The correct answer is C: declarative management unlocks self-healing, GitOps, idempotency, and auditability — the four pillars that make a platform a platform, not just a cluster.

Core Fundamentals Q3 of 200
A Kubernetes manifest for anihpj-api declares apiVersion: apps/v1, kind: Deployment, metadata: {name: anihpj-api}, and spec: {replicas: 3}. After applying, the manifest also shows status: {availableReplicas: 2}. What do the spec and status fields represent in Kubernetes' declarative model?
A) spec = DESIRED state (what you WANT — "3 replicas"); status = ACTUAL state (what IS — "2 available") — controllers reconcile actual → desired
B) spec = the specification of the physical hardware the pod runs on; status = whether the YAML file has syntax errors
C) Both spec and status are identical copies — Kubernetes duplicates spec into status for redundancy
D) spec is read-only (set by controllers); status is read-write (set by users via kubectl edit)
✅ Correct Answer: A

The spec/status split is the most fundamental design pattern in Kubernetes — it's how declarative APIs work. You write what you WANT (spec), and controllers make it HAPPEN (status). This is the reconciliation loop at the object level.

📝 Detailed Explanation
Kubernetes Object Anatomy — The spec/status Split
  apiVersion: apps/v1          ← API group & version (tells K8s which schema to use)
  kind: Deployment             ← Resource type (Deployment, Service, Pod, etc.)
  metadata:                    ← Identity (name, namespace, labels, annotations)
    name: anihpj-api
    namespace: anihpj-prod
    labels: {app: anihpj, tier: api}
  ─────────────────────────────────────────────────────────────────
  spec:                        ← DESIRED STATE (YOU write this)
    replicas: 3                ← "I want 3 pods running"
    selector: {matchLabels: {app: anihpj-api}}
    template:                  ← Pod template (what each replica looks like)
      spec:
        containers:
        - name: api
          image: anihpj/jobpost:v1.2.3
          ports: [{containerPort: 8000}]
          resources: {requests: {cpu: 250m, memory: 256Mi}}
  ─────────────────────────────────────────────────────────────────
  status:                      ← ACTUAL STATE (CONTROLLER writes this)
    observedGeneration: 5
    replicas: 3                ← "Currently 3 pods exist"
    availableReplicas: 2       ← "But only 2 are Ready"
    conditions:                ← Why? Readiness probe failing on 1 pod
    - type: Available
      status: "False"
      reason: MinimumReplicasUnavailable

  THE RECONCILIATION LOOP:
  ┌──────────┐     ┌──────────────┐     ┌──────────┐
  │  SPEC    │────▶│  CONTROLLER  │────▶│  STATUS  │
  │ (desired)│     │  reads spec  │     │ (actual) │
  │          │     │  acts on diff│     │          │
  └──────────┘     └──────────────┘     └──────────┘
       ▲                                      │
       │         Controller notices           │
       └──────── status ≠ spec ───────────────┘
  
  For anihpj/jobpost: When you set replicas: 5 in the Deployment spec,
  the Deployment Controller reads it, sees only 3 pods running in
  status, and creates 2 more pods. It continuously watches — if a pod
  crashes, status shows availableReplicas: 4, and the controller
  creates a replacement. This is self-healing in action.

B is wrong — spec has nothing to do with hardware. C is wrong — spec and status are fundamentally different. D is backwards — YOU write spec (your desired state); the CONTROLLER writes status (the actual state). The spec/status split is the engine that drives every Kubernetes controller — from Deployments to custom Operators you'll build as a CNPA.

Core Fundamentals Q4 of 200
You run kubectl apply -f anihpj-api.yaml to deploy anihpj-api. A colleague runs kubectl create -f anihpj-api.yaml on the same file. What is the critical difference between these two commands, and why does GitOps exclusively use kubectl apply?
A) apply is faster because it uses HTTP/2 multiplexing; create uses HTTP/1.1 with one request per resource
B) apply is DECLARATIVE and idempotent — it compares desired (file) vs actual (cluster) and patches only what changed. create is IMPERATIVE — it fails with "AlreadyExists" on second run, making it unsuitable for GitOps reconciliation loops
C) apply works only for Deployments and Services; create works for all resource types including CRDs and Namespaces
D) There is no difference — apply and create are aliases for the same underlying API call
✅ Correct Answer: B

kubectl apply is the declarative gateway to Kubernetes — it computes a 3-way diff (file vs live object vs last-applied-configuration) and sends only the changes. kubectl create is imperative — it makes a single POST request and fails if the resource already exists. GitOps needs apply because ArgoCD runs reconciliation every 3 minutes — create would fail on the second run.

📝 Detailed Explanation
kubectl apply vs kubectl create — The GitOps Imperative
  ┌─────────────────────────────────────────────────────────────────┐

💾 Category 1: Storage Troubleshooting (10 Issues)ST1-ST10

🟢 Storage Issues — PVC, PV, StorageClass, and Mount Failures

Storage is often the FIRST thing to break because it involves multiple components: PVC → StorageClass → Provisioner → PV → Mount. When any link in this chain fails, your pod can't start or your data is at risk.

📌 ST1–ST3: PVC Binding Failures

ST1
💾 CATEGORY 1: STORAGE — Issue ST1
PVC Stuck in Pending State — No PV Bound

🔍 Symptom: kubectl get pvc shows STATUS: Pending indefinitely. kubectl describe pvc shows "no persistent volumes available for this claim." The anihpj-db PostgreSQL pod can't start because its PVC won't bind.

  kubectl get pvc
  NAME         STATUS    VOLUME   CAPACITY   STORAGECLASS   AGE
  anihpj-pvc   Pending                      fast-ssd       5m

  kubectl describe pvc anihpj-pvc
  Events:
    Warning  VolumeBinding  no persistent volumes available for this claim
    Warning  VolumeBinding  storageclass.storage.k8s.io "fast-ssd" not found
🔴5 Most Likely Causes
  1. StorageClass does not exist: The PVC references a StorageClass that hasn't been created. kubectl get sc — if "fast-ssd" is missing, create it or fix the PVC's storageClassName.
  2. No matching PV available: In static provisioning, no PV matches the PVC's storage size, access mode, or selector. kubectl get pv — check capacity and accessModes.
  3. StorageClass provisioner not installed: The CSI driver (e.g., ebs.csi.aws.com) is not deployed. kubectl get pods -n kube-system | grep csi — provisioner pods must be Running.
  4. Access mode mismatch: PVC requests ReadWriteMany but only ReadWriteOnce PVs exist. Check kubectl get pv -o yaml | grep -A2 accessModes.
  5. StorageClass has volumeBindingMode: WaitForFirstConsumer and no pod uses the PVC yet. The PV is only created when a pod actually references the PVC.
🟡5 Less Likely Causes
  1. CSI driver pod CrashLoopBackOff — provisioner can't create volumes
  2. Cloud provider API rate limiting — too many PVCs created simultaneously
  3. PVC selector labels don't match any PV labels
  4. Node where CSI driver runs has taint without toleration
  5. storageClassName: "" (empty string, not null!) — requests a PV with NO StorageClass, but all PVs have one
🟣5 New Cluster Causes
  1. No default StorageClass set: kubectl get sc — look for "(default)". Without it, PVCs without storageClassName won't bind. Set: kubectl patch sc <name> -p '{"metadata":{"annotations":{"storageclass.kubernetes.io/is-default-class":"true"}}}'
  2. CSI driver not yet installed — common in fresh kubeadm clusters
  3. Cloud credentials not configured for CSI driver to provision volumes
  4. RBAC for CSI driver service account missing
  5. kubelet missing --cloud-provider flag for legacy in-tree provisioners
🔍 What to Look At:
kubectl get sc,pv,pvc --all-namespaces The full storage stack in one view — see StorageClass, PV, and PVC together.
kubectl describe pvc <name> The Events section tells you exactly why binding failed — always read the events first.
🎯 #1 Root Cause: StorageClass does not exist or is misnamed. The PVC references a StorageClass that hasn't been created — the most common CKA exam pitfall.
🔧 How to Solve:
1. Verify StorageClass exists kubectl get sc If the StorageClass referenced by the PVC is missing, create it or fix the PVC's storageClassName.
2. Check provisioner and parameters kubectl describe sc <name> Verify the provisioner is correct and the CSI driver is installed and running.
3. Static provisioning kubectl get pv Create a PV matching the PVC's requested size, accessMode, and selector labels.
4. Dynamic provisioning Install the CSI driver: kubectl apply -f <csi-driver-url>. Verify CSI pods are Running in kube-system.
5. Set default StorageClass kubectl patch sc <name> -p '{"metadata":{"annotations":{"storageclass.kubernetes.io/is-default-class":"true"}}}' PVCs without an explicit storageClassName will use the default.
💡 Personal Advice:
Always verify StorageClass FIRST. The #1 PVC issue on the CKA exam is a missing or misnamed StorageClass. Run kubectl get sc before writing any PVC YAML.
Empty string is NOT null. storageClassName: "" Requests a PV with NO StorageClass — different from omitting the field entirely. Know this distinction.
CSI driver must be Running. Even with correct StorageClass, if the CSI provisioner pod is CrashLoopBackOff, no volumes will be created.
WaitForFirstConsumer delays binding. If volumeBindingMode is WaitForFirstConsumer, the PV is only created when a pod actually uses the PVC. Don't mistake this for a failure.

M.1 — etcd Backup & Restore (Full TLS Flags)
1

Backup:

ETCDCTL_API=3 etcdctl --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  snapshot save /opt/etcd-backup.db

Restore:

ETCDCTL_API=3 etcdctl --data-dir=/var/lib/etcd-restore \
  snapshot restore /opt/etcd-backup.db

⚠️ After restore: Update etcd static pod manifest (/etc/kubernetes/manifests/etcd.yaml) to point --data-dir to the new path, then restart kubelet. Also update the --initial-cluster-token to a new value.

M.2 — kubeadm Cluster Upgrade Sequence
2

On Control Plane:

# 1. Unhold and upgrade kubeadm

apt-mark unhold kubeadm && apt-get update && apt-get install -y kubeadm=1.30.x-*

kubeadm upgrade plan
# 3. Apply upgrade
kubeadm upgrade apply v1.30.x
# 4. Upgrade kubelet & kubectl
apt-mark unhold kubelet kubectl && apt-get install -y kubelet=1.30.x-* kubectl=1.30.x-*
apt-mark hold kubelet kubectl
systemctl daemon-reload && systemctl restart kubelet

On Each Worker:

# 1. Drain the worker first (from CP)

kubectl drain worker-1 --ignore-daemonsets --delete-emptydir-data
# 2. SSH to worker, upgrade kubeadm + kubelet
apt-get install -y kubeadm=1.30.x-* kubelet=1.30.x-*
kubeadm upgrade node
systemctl restart kubelet
# 3. Uncordon
kubectl uncordon worker-1
