🔥 What Is Terraform?

Terraform = Infrastructure as Code, by HashiCorp

Terraform is an open-source Infrastructure as Code (IaC) tool that lets you define, provision, and manage infrastructure across 300+ cloud providers and services using a declarative configuration language called HCL (HashiCorp Configuration Language). Instead of clicking through cloud consoles or writing imperative scripts, you describe your desired infrastructure state in `.tf` files, and Terraform makes it happen — safely, predictably, and repeatably.

💡 The Big Idea: Terraform treats infrastructure like software. You write code, version it in Git, review it in pull requests, test it in CI/CD, and apply it to any cloud — exactly the same way you'd build an application. Infrastructure becomes fast, consistent, and auditable.

❓ Why anihpj/jobpost Needs IaC

anihpj: A Django Application with Real Infrastructure Needs

anihpj is a Django-based job posting platform with the jobpost app. It needs a database (PostgreSQL), caching (Redis), static file storage (S3), a web server (EC2/ECS), networking (VPC), DNS (Route 53), monitoring (CloudWatch), and CI/CD pipelines. Managing all of this manually through cloud consoles is error-prone, slow, and impossible to reproduce.

❌ Without Terraform (Manual)

  • Click through AWS console for each resource
  • No version history — "who changed the security group?"
  • Dev ≠ Staging ≠ Prod — constant drift
  • Onboarding takes weeks — "what did the last person configure?"
  • Disaster recovery? Hope you have screenshots

✅ With Terraform (Automated)

  • All infrastructure in .tf files, versioned in Git
  • Full audit trail — every change is a commit
  • Exact replicas: dev = staging = prod
  • New team member? `git clone && terraform apply`
  • DR site? Re-run the same code in another region

🧠 How Terraform Thinks — Declarative vs Imperative

Terraform is declarative: you describe the desired end state ("I want 3 EC2 instances, a VPC, and an RDS database"), and Terraform figures out how to get there. This is fundamentally different from imperative tools like Ansible or Bash scripts where you specify each step.

AspectDeclarative (Terraform)Imperative (Ansible/Bash)
What you write"I want a VPC with CIDR 10.0.0.0/16""Create VPC, then create subnet, then..."
IdempotencyBuilt-in via stateYou must code it yourself
What if it fails mid-way?State tracks what was created, retry is safeScript restarts from beginning — duplicates!
Drift detectionterraform plan shows driftNone — you discover drift manually

⚠️ Top 10 Exam Mistakes That Cost Points

1. Not knowing variable precedence. CLI -var beats *.auto.tfvars beats terraform.tfvars beats TF_VAR_* beats defaults. This is asked in multiple ways.
2. Confusing count and for_each. count uses numbers and lists; for_each uses maps and sets. If you remove an item from the middle of a list, count recreates wrong resources. for_each uses keys, so it's stable.
3. Forgetting that state contains secrets. Yes, terraform.tfstate stores ALL resource attributes including passwords in plain text (unless marked sensitive). Always use remote backends with encryption.
4. Not understanding terraform import. Import only updates state — it does NOT generate .tf configuration. You must write the config yourself first, then import.
5. Mixing up provisioners and user_data. Provisioners are a LAST RESORT. Use user_data, cloud-init, or pre-baked AMIs instead. The exam loves to test this distinction.
6. Thinking terraform refresh updates configuration. Refresh only updates STATE to match reality. It does NOT change your .tf files or the actual infrastructure.
7. Forgetting sentinel vs OPA. Sentinel is HashiCorp's policy-as-code (Terraform Cloud/Enterprise). OPA is a separate CNCF tool. Don't confuse them.
8. Misunderstanding backend configuration. Backend config CANNOT use variables or references. It must be hardcoded or passed via -backend-config at init time.
9. Not knowing module sources. Local path, Terraform Registry, GitHub, S3, Git — know all the source types and their syntax.
10. Assuming terraform destroy removes everything. Destroy only removes what's in state. Resources created manually outside Terraform are NOT destroyed.

1.3 Declarative vs Imperative IaC — The Key Distinction

This is the most important conceptual distinction in IaC — and a favorite exam topic.

Declarative means you describe the desired end state. You tell Terraform "I want a VPC with CIDR 10.0.0.0/16, 3 subnets, and an RDS database." Terraform figures out the API calls, the order of operations, and the dependency chain. You don't tell it HOW to create resources — you tell it WHAT you want.

Imperative means you describe the exact steps to reach the state. You write a script: "Step 1: Call the VPC API. Step 2: Wait for VPC to be ready. Step 3: Call the Subnet API with the VPC ID..." If any step fails, your script doesn't know what was already created and what wasn't. You have to handle error recovery, retries, and idempotency yourself.

Real-world anihpj example: If you declare resource "aws_instance" "anihpj_web" { count = 3 }, Terraform ensures exactly 3 EC2 instances exist. If one is terminated manually, Terraform detects the drift on the next plan and recreates it. If you run apply 10 times with no changes, nothing happens — Terraform sees the desired state matches the actual state and takes no action. A Bash script, by contrast, would try to create 3 new instances every time it runs — giving you 30 instances instead of 3.

Declarative = WHAT you want. Imperative = HOW to get it. Terraform is declarative. The exam will test this distinction in multiple ways — often by asking "which approach does Terraform use?" or "what happens if you run terraform apply twice?"

1.7 Idempotency & Immutability — Why They Matter

Two concepts that make IaC safe and reliable. Both are tested on the exam — often together in the same question to see if you can tell them apart.

🔁 Idempotency

Running the same operation multiple times produces the same result. Like a light switch — flipping it 100 times always gives you the same on/off state. Like setting an alarm clock — setting it to 7am 10 times doesn't make it go off at 7:10am.

Terraform example: Running terraform apply 10 times when nothing changed = no changes made. Terraform compares desired state (your .tf files) with actual state (terraform.tfstate + real infrastructure) and only makes changes when they differ.

Why it matters: You can run Terraform in CI/CD pipelines, retry failed applies, and run apply as a scheduled job for drift detection — all without worrying about creating duplicate resources or corrupting state. Idempotency is what makes automation safe.

🧊 Immutability

Resources are never modified — they're replaced. Like a disposable cup — you don't wash it, you throw it away and get a new one. Like a phone screen protector — you don't repair a crack, you replace the whole thing.

Terraform example: Changing an EC2 instance's AMI triggers create_before_destroy — Terraform creates a NEW instance from the new AMI, waits for it to be healthy, then destroys the old one. No in-place modification, zero downtime.

Why it matters: Immutable infrastructure eliminates configuration drift entirely. You never have to ask "what version of nginx is running on this server?" — because no server lives long enough to accumulate changes. Every deployment is a fresh build from a known-good image.

How they work together in anihpj: When the anihpj team updates their Django application, they build a new Docker image, push it to ECR, update the Terraform config to reference the new image tag, and run terraform apply. Terraform (being idempotent) detects that only the image tag changed. It then performs an immutable deployment — launching new EC2 instances with the new image, waiting for them to pass health checks, and terminating the old ones. The result: zero-downtime deployment with complete rollback capability (just change the image tag back).

Don't confuse idempotency with immutability! Idempotent = same result when re-run (Terraform's behavior). Immutable = never changed, only replaced (your resource strategy). Terraform is idempotent; your resources can be either mutable or immutable depending on lifecycle rules. The exam WILL test this distinction.

2.5 Terraform Architecture — Providers, Resources, State, Plan

Understanding Terraform's internal architecture helps you debug issues, understand error messages, and answer exam questions about how Terraform works under the hood. Terraform Core is a single Go binary that orchestrates everything — but the real work is done by provider plugins.

TERRAFORM CORE ARCHITECTURE
👤 YOU (DevOps Engineer) │ │ Write .tf files (HCL) ▼ ┌───────────────────────────────────────────────┐ │ TERRAFORM CORE (Go Binary) │ │ ┌──────────┐ ┌──────────┐ ┌───────────────┐ │ │ │ CONFIG │ │ STATE │ │ PLAN ENGINE │ │ │ │ LOADER │ │ MANAGER │ │ (Diff Engine) │ │ │ └──────────┘ └──────────┘ └───────┬───────┘ │ └────────────────────────────────────┼──────────┘ │ ┌────────────────────────────────────┼──────────┐ │ PROVIDER PLUGINS │ │ │ ┌────────┐ ┌────────┐ ┌────────┐ │ │ │ │ AWS │ │ Azure │ │ GCP │◀┘ │ │ │(Go Bin)│ │(Go Bin)│ │(Go Bin)│ │ │ └───┬────┘ └───┬────┘ └───┬────┘ │ └──────┼──────────┼──────────┼──────────────────┘ │ │ │ ▼ ▼ ▼ ┌─────────┐ ┌─────────┐ ┌─────────┐ │ AWS API │ │ Azure │ │ GCP API │ │ (REST) │ │ REST API│ │ (REST) │ └─────────┘ └─────────┘ └─────────┘

How the pieces fit together: When you run terraform plan, Terraform Core reads all your .tf files, builds a resource graph, and asks each provider "what does the current real-world state look like?" It then compares that against your desired state and produces the plan. When you terraform apply, Terraform Core executes the plan by telling each provider "create/update/delete this resource" — and the provider translates that into the specific REST API calls for its cloud.

Why this architecture matters: Providers are separate binaries — they're downloaded during terraform init and stored in .terraform/providers/. Each provider is versioned independently. This means the AWS provider team at HashiCorp can release updates without touching Terraform Core. It also means you can use providers from different organizations in the same configuration — the AWS provider from HashiCorp, the Datadog provider from Datadog, and a custom provider your team built.

2.9 The Execution Plan — Understanding What Terraform Will Do

The execution plan is Terraform's most powerful and important feature. Before making any changes to your infrastructure, Terraform shows you exactly what will happen — what will be created, updated, or destroyed. This is your safety net. You review the plan, confirm it looks correct, and only then apply. No other IaC tool provides this level of confidence before making changes to production infrastructure.

terraform plan OUTPUT — ANNOTATED
$ terraform plan Terraform will perform the following actions: # aws_vpc.main will be created ← + means CREATE + resource "aws_vpc" "main" { cidr_block = "10.0.0.0/16" ... } # aws_security_group.web will be updated in-place ← ~ means UPDATE ~ resource "aws_security_group" "web" { ~ description = "Old desc" -> "New desc" ← Old → New } # aws_instance.old will be destroyed ← - means DESTROY - resource "aws_instance" "old" { id = "i-abc123" } Plan: 2 to add, 1 to change, 1 to destroy.

What makes the plan so powerful? Terraform reads the current state from your state file, queries the real infrastructure via provider APIs to detect any drift, compares both against your desired configuration, and computes the minimum set of API calls needed to reconcile reality with your desired state. You can save plans to files (terraform plan -out=tfplan), share them with teammates for review, apply them later, and even use them in CI/CD pipelines where a plan is generated on pull request and applied on merge.

Plan safety in practice: At anihpj, every infrastructure change starts with a pull request. GitHub Actions runs terraform plan and posts the output as a PR comment. The team reviews which resources will change, discusses the impact, and only then merges — triggering terraform apply. Nothing changes in production without human review of the plan first.

The plan symbols are essential for the exam: + = create, - = destroy, ~ = update in-place, -/+ = replace (destroy then create). Know what each means and when they appear. Also know that terraform plan does NOT modify anything — it's a read-only operation.

2.10 Resource Graph — How Terraform Builds Dependency Trees

Terraform is a single Go binary — no dependencies, no runtime, no package manager required. You can download it, unzip it, and run it. For production use, HashiCorp provides official package repositories.

3.4 The Core Workflow — Write → Init → Plan → Apply → Destroy

The Terraform workflow is a loop you'll repeat thousands of times. Each step has a specific purpose:

1

Write

Create .tf files describing desired infrastructure

2

Init

3

Plan

terraform plan — preview what will change

4

Apply

5

Destroy

3.5 Your First Terraform File — main.tf for anihpj

# Error: Reference to undeclared resource
💡 CI/CD pattern: Run terraform fmt -check && terraform validate on every pull request. These run in seconds and catch 80% of common mistakes before they reach production.
