  └─────────────────────────────────────────────────────────────────────────┘

                        🌊 THE SEA OF INFRASTRUCTURE 🌊
    ┌─────────────────────────────────────────────────────────────────────┐
    │                                                                     │
    │   🏗️ TERRAFORM = The Port Crane Operator                           │
    │   ┌─────────────────┐                                               │
    │   │  Terraform Plan  │──▶ Decides WHAT infrastructure to build      │
    │   │  (Blueprint)    │                                              │
    │   └────────┬────────┘                                               │
    │            │                                                        │
    │   ┌────────▼────────┐                                               │
    │   │  Terraform Apply │──▶ Lifts & places containers (resources)     │
    │   │  (Crane Hook)   │      onto ships (cloud providers)            │
    │   └────────┬────────┘                                               │
    │            │                                                        │
    │   ┌────────▼────────────────────────────────────────────────────┐  │
    │   │                 🚢 THE CARGO SHIP (AWS / Azure / GCP)       │  │
    │   │  ┌──────┐  ┌──────┐  ┌──────┐  ┌──────┐  ┌──────┐        │  │
    │   │  │ VPC  │  │ EC2  │  │ RDS  │  │  S3  │  │ IAM  │        │  │
    │   │  │Container│Container│Container│Container│Container│        │  │
    │   │  └──────┘  └──────┘  └──────┘  └──────┘  └──────┘        │  │
    │   │  Each container = One Terraform Resource                   │  │
    │   └────────────────────────────────────────────────────────────┘  │
    │                                                                     │
    │   📦 DOCKER = The Container (inside the ship)                       │
    │   ┌─────────────────────────────────────────────────────────────┐  │
    │   │  ┌─────────────────────┐    ┌─────────────────────┐         │  │
    │   │  │  🐳 Docker Container │    │  🐳 Docker Container │         │  │
    │   │  │  ┌───────────────┐  │    │  ┌───────────────┐  │         │  │
    │   │  │  │ anihpj Django │  │    │  │  PostgreSQL   │  │         │  │
    │   │  │  │ (App Code)    │  │    │  │  (Database)   │  │         │  │
    │   │  │  └───────────────┘  │    │  └───────────────┘  │         │  │
    │   │  └─────────────────────┘    └─────────────────────┘         │  │
    │   └─────────────────────────────────────────────────────────────┘  │
    │                                                                     │
    └─────────────────────────────────────────────────────────────────────┘

    KEY INSIGHT:
    • Terraform manages WHERE containers run (ships, ports, cranes = AWS/GCP/Azure)
    • Docker manages WHAT runs inside containers (app code, DB, cache)
    • Terraform PROVISIONS the ship; Docker RUNS the cargo

     │  DIAGRAM 5.3: STATE LOCKING — Preventing Disaster (DynamoDB)        │
     └─────────────────────────────────────────────────────────────────────┘

         SCENARIO: Two engineers run terraform apply at the SAME time

         ❌ WITHOUT LOCKING (Disaster):        ✅ WITH LOCKING (DynamoDB):
         ┌────────────────────────┐          ┌────────────────────────────┐
         │ Alice: terraform apply │          │ Alice: terraform apply     │
         │ Bob:   terraform apply │          │  │ Gets LOCK from DynamoDB │
         │                        │          │  ▼ (LockID: "alice-123")   │
         │ Both read state file   │          │ Alice reads & applies ✅    │
         │ Both apply changes     │          │  │ Releases LOCK            │
         │ RESULT:                │          │  ▼                         │
         │ • Duplicate resources  │          │ Bob: terraform apply       │
         │ • Corrupted state      │          │  │ Tries to get LOCK       │
         │ • $$$ wasted           │          │  ▼                         │
         └────────────────────────┘          │ ⛔ "Error: state locked    │
                                              │  by alice-123. Wait..."   │
                                              │  │ Waits...                │
                                              │  ▼                         │
                                              │ Gets LOCK → applies ✅     │
                                              └────────────────────────────┘

         PRODUCTION SETUP (AWS):
         ┌─────────────────────────────────────────────────────────────────┐
         │ backend "s3" {                                                  │
         │   bucket         = "anihpj-terraform-state"   ◀── S3 stores    │
         │   key            = "prod/terraform.tfstate"   ◀──   state file │
         │   region         = "us-east-1"                                 │
         │   dynamodb_table = "terraform-locks"          ◀── DynamoDB     │
         │   encrypt        = true                       ◀──   for locks  │
         │ }                                                               │
         └─────────────────────────────────────────────────────────────────┘

     ┌─────────────────────────────────────────────────────────────────────┐
     │  DIAGRAM 8.1: RESOURCE DEPENDENCY — Implicit vs Explicit            │
     └─────────────────────────────────────────────────────────────────────┘

          IMPLICIT DEPENDENCY (Terraform figures it out):
          ┌─────────────────────────────────────────────────────────────────┐
          │ resource "aws_vpc" "main" {                                     │
          │   cidr_block = "10.0.0.0/16"                                   │
          │ }                                                               │
          │                                                                 │
          │ resource "aws_subnet" "public" {                                │
          │   vpc_id = aws_vpc.main.id    ◀── Terraform sees this reference │
          │   cidr_block = "10.0.1.0/24" │   and KNOWS subnet depends on   │
          │ }                             │   VPC. Creates VPC FIRST.      │
          └─────────────────────────────────────────────────────────────────┘

          EXPLICIT DEPENDENCY (You tell Terraform):
          ┌─────────────────────────────────────────────────────────────────┐
          │ resource "aws_s3_bucket" "assets" {                             │
          │   bucket = "anihpj-assets"                                      │
          │ }                                                               │
          │                                                                 │
          │ resource "null_resource" "upload_files" {                       │
          │   depends_on = [aws_s3_bucket.assets]  ◀── No reference to      │
          │                                          │   bucket in body     │
          │   provisioner "local-exec" {             │   so Terraform       │
          │     command = "aws s3 sync ./static s3://anihpj-assets/"        │
          │   }                                     │   wouldn't know.     │
          │ }                                       │   depends_on fixes   │
          └─────────────────────────────────────────────────────────────────┘          this!


     ┌─────────────────────────────────────────────────────────────────────┐
     │  DIAGRAM 8.2: LIFECYCLE RULES — Controlling Resource Lifecycle      │
     └─────────────────────────────────────────────────────────────────────┘

          THE 4 LIFECYCLE META-ARGUMENTS:

          ┌─────────────────────────────────────────────────────────────────┐
          │ lifecycle {                                                     │
          │   create_before_destroy = true    ◀── Create new FIRST, then    │
          │   prevent_destroy       = true    ◀── BLOCK accidental destroy  │
          │   ignore_changes        = [...]   ◀── Ignore specific attribute │
          │   replace_triggered_by  = [...]   ◀── Custom replace trigger    │
          │ }                                                               │
          └─────────────────────────────────────────────────────────────────┘

          create_before_destroy (avoid downtime):
          ┌─────────────────────────────────────────────────────────────────┐
          │  WITHOUT:   Destroy old EC2 → (downtime!) → Create new EC2     │
          │  WITH:      Create new EC2  → (both running) → Destroy old EC2 │
          │             ───────────────────────────────────────────────     │
          │  ✅ Zero downtime!  ⚠️ Need enough quota for 2x resources      │
          └─────────────────────────────────────────────────────────────────┘

          prevent_destroy (safety lock for critical resources):
          ┌─────────────────────────────────────────────────────────────────┐
          │ resource "aws_db_instance" "prod_db" {                          │
          │   lifecycle {                                                   │
          │     prevent_destroy = true   ◀── If someone tries to destroy   │
          │   }                          │   this DB, Terraform REFUSES    │
          │ }                            │   "Error: Instance cannot be    │
          │                              │    destroyed"                   │
          │  To destroy anyway: manually remove prevent_destroy first!     │
          └─────────────────────────────────────────────────────────────────┘

          ignore_changes (stop Terraform from fighting external changes):
          ┌─────────────────────────────────────────────────────────────────┐
          │ resource "aws_ecs_service" "anihpj" {                           │
          │   desired_count = 3                                             │
          │   lifecycle {                                                   │
          │     ignore_changes = [desired_count]  ◀── Auto-scaling changes │
          │   }                                │   desired_count externally.│
          │ }                                  │   Terraform won't reset it │
          │                                    │   back to 3 on next apply. │
          └─────────────────────────────────────────────────────────────────┘


     ┌─────────────────────────────────────────────────────────────────────┐
     │  DIAGRAM 8.3: PROVISIONERS — The "Last Resort" Pattern              │
     └─────────────────────────────────────────────────────────────────────┘

          PROVISIONER HIERARCHY (best to worst):
          ┌─────────────────────────────────────────────────────────────────┐
          │ ✅ BEST: Use provider-native features (user_data, cloud-init)  │
          │ ✅ GOOD: Pre-baked AMI / Docker image with everything needed   │
          │ ⚠️ OK:   Configuration management (Ansible after Terraform)    │
          │ 🔴 LAST: Terraform provisioners (local-exec, remote-exec)      │
          └─────────────────────────────────────────────────────────────────┘

          local-exec (runs on YOUR machine):
          ┌─────────────────────────────────────────────────────────────────┐
          │ provisioner "local-exec" {                                      │
          │   command = "echo ${self.public_ip} >> inventory.ini"           │
          │ }                                                               │
          │ ⚠️ Runs on Terraform host, NOT the resource                     │
          │ ❌ Not captured in state — if it fails, Terraform may not know  │
          └─────────────────────────────────────────────────────────────────┘

          remote-exec (runs ON the resource via SSH):
          ┌─────────────────────────────────────────────────────────────────┐
          │ provisioner "remote-exec" {                                     │
          │   inline = [                                                   │
          │     "sudo apt-get update",                                      │
          │     "sudo apt-get install -y nginx",                            │
          │     "sudo systemctl start nginx"                                │
          │   ]                                                             │
          │ }                                                               │
          │ ⚠️ Requires SSH access (connection block)                       │
          │ ❌ Terraform can't track what provisioner did                   │
          └─────────────────────────────────────────────────────────────────┘


     ┌─────────────────────────────────────────────────────────────────────┐
     │  DIAGRAM 8.4: TERRAFORM TAINT — Force Resource Recreation           │
     └─────────────────────────────────────────────────────────────────────┘

          WHEN TO TAINT:
          ┌─────────────────────────────────────────────────────────────────┐
          │ • Provisioner failed partially (resource exists but broken)    │
          │ • Underlying resource corrupted (disk failure, bad config)     │
          │ • You want to test create_before_destroy in production         │
          └─────────────────────────────────────────────────────────────────┘

          $ terraform taint aws_instance.anihpj_web[0]
          ┌─────────────────────────────────────────────────────────────────┐
          │ Resource aws_instance.anihpj_web[0] is marked as tainted.       │
          │                                                                 │
          │ Next terraform apply will:                                      │
          │   1. DESTROY the tainted resource                               │
          │   2. CREATE a brand new replacement                             │
          │                                                                 │
          │ ⚠️ If prevent_destroy = true, taint will NOT work!             │
          │ 💡 Use terraform untaint to remove the mark if it was a mistake │
          └─────────────────────────────────────────────────────────────────┘


     ┌─────────────────────────────────────────────────────────────────────┐
     │  TABLE 8.1: WHEN DOES TERRAFORM REPLACE vs UPDATE-IN-PLACE?         │
     └─────────────────────────────────────────────────────────────────────┘

     ┌────────────────────────────────┬──────────────┬─────────────────────┐
     │ CHANGE MADE                    │ ACTION       │ EXAMPLE             │
     ├────────────────────────────────┼──────────────┼─────────────────────┤
     │ Change tags                    │ Update       │ ~ name = "new"      │
     │ Change instance_type           │ Recreate 🔄   │ -/+ t2.micro→t3.sm │
     │ Change AMI                     │ Recreate 🔄   │ -/+ new AMI ID     │
     │ Change security group          │ Update       │ ~ sg-abc→sg-xyz     │
     │ Change subnet                  │ Recreate 🔄   │ -/+ (new IP space) │
     │ Change volume size (up)        │ Update       │ ~ 20GB→50GB         │
     │ Change volume size (down)      │ Recreate 🔄   │ -/+ (AWS won't     │
     │                                │              │   shrink volumes)   │
     └────────────────────────────────┴──────────────┴─────────────────────┘
     │ FORCE recreate: terraform taint + apply OR lifecycle { replace_     │
     │                 triggered_by = [attribute] }                         │
     │ FORCE update:   lifecycle { ignore_changes = [recreate_trigger] }   │
     └─────────────────────────────────────────────────────────────────────┘

     ┌─────────────────────────────────────────────────────────────────────┐
     │  DIAGRAM 10.1: FOR EXPRESSIONS — Transforming Lists & Maps          │
     └─────────────────────────────────────────────────────────────────────┘

          LIST TRANSFORMATION:
          ┌─────────────────────────────────────────────────────────────────┐
          │ Input:  ["dev", "staging", "prod"]                              │
          │                                                                 │
          │ [for env in ["dev", "staging", "prod"] : upper(env)]            │
          │                                                                 │
          │ Output: ["DEV", "STAGING", "PROD"]                              │
          └─────────────────────────────────────────────────────────────────┘

          FILTERING WITH IF:
          ┌─────────────────────────────────────────────────────────────────┐
          │ variable "subnet_cidrs" {                                       │
          │   default = ["10.0.1.0/24", "10.0.2.0/24", "10.0.3.0/24"]     │
          │ }                                                               │
          │                                                                 │
          │ [for cidr in var.subnet_cidrs : cidr                            │
          │   if can(regex("^10\\.0\\.[135]\\.", cidr))]                    │
          │                                                                 │
          │ Only subnets starting with 10.0.1, 10.0.3, 10.0.5...           │
          └─────────────────────────────────────────────────────────────────┘

          MAP TRANSFORMATION:
          ┌─────────────────────────────────────────────────────────────────┐
          │ variable "instance_types" {                                     │
          │   default = {                                                   │
          │     dev  = "t3.micro"                                           │
          │     prod = "t3.medium"                                          │
          │   }                                                             │
          │ }                                                               │
          │                                                                 │
          │ {for env, type in var.instance_types : env => upper(type)}      │
          │                                                                 │
          │ Output: {dev = "T3.MICRO", prod = "T3.MEDIUM"}                  │
          └─────────────────────────────────────────────────────────────────┘


     ┌─────────────────────────────────────────────────────────────────────┐
     │  DIAGRAM 10.2: DYNAMIC BLOCKS — Programmatic Nested Blocks          │
     └─────────────────────────────────────────────────────────────────────┘

          PROBLEM: Security groups need N rules. Hardcoding = repetitive.

          WITHOUT dynamic (repetitive):
          ┌─────────────────────────────────────────────────────────────────┐
          │ ingress { from_port=80;  to_port=80;  protocol="tcp"; ... }    │
          │ ingress { from_port=443; to_port=443; protocol="tcp"; ... }    │
          │ ingress { from_port=22;  to_port=22;  protocol="tcp"; ... }    │
          │ ... (20 more rules)                                             │
          └─────────────────────────────────────────────────────────────────┘

          WITH dynamic (elegant):
          ┌─────────────────────────────────────────────────────────────────┐
          │ variable "ingress_rules" {                                      │
          │   default = [                                                   │
          │     {port=80,  cidr="0.0.0.0/0", desc="HTTP"},                 │
          │     {port=443, cidr="0.0.0.0/0", desc="HTTPS"},                │
          │     {port=22,  cidr="10.0.0.0/8", desc="SSH (internal only)"}, │
          │   ]                                                             │
          │ }                                                               │
          │                                                                 │
          │ dynamic "ingress" {                                             │
          │   for_each = var.ingress_rules                                  │
          │   content {                                                     │
          │     from_port   = ingress.value.port                            │
          │     to_port     = ingress.value.port                            │
          │     protocol    = "tcp"                                         │
          │     cidr_blocks = [ingress.value.cidr]                          │
          │     description = ingress.value.desc                            │
          │   }                                                             │
          │ }                                                               │
          │                                                                 │
          │ ✅ 3 lines of dynamic → generates 3 ingress blocks              │
          │ ✅ Add a rule = add one map entry (no code duplication!)        │
          └─────────────────────────────────────────────────────────────────┘

     │  DIAGRAM 10.3: TRY & CAN — Graceful Error Handling in HCL           │
     └─────────────────────────────────────────────────────────────────────┘

          try() — Try values, return first that doesn't error:
          ┌─────────────────────────────────────────────────────────────────┐
          │ try(var.production_config, var.staging_config, var.dev_config)  │
          │                                                                 │
          │ • If production_config exists → use it                          │
          │ • If not, try staging_config                                    │
          │ • If not, fall back to dev_config                               │
          │ • Perfect for environment-specific overrides!                   │
          └─────────────────────────────────────────────────────────────────┘

          can() — Test if an expression succeeds:
          ┌─────────────────────────────────────────────────────────────────┐
          │ can(regex("^v[0-9]+\\.[0-9]+", var.version_string))            │
          │                                                                 │
          │ • Returns true if var.version_string matches "v1.2" pattern    │
          │ • Returns false otherwise (no error!)                           │
          │ • Use in validation blocks or conditional resource creation    │
          └─────────────────────────────────────────────────────────────────┘

          EXAMPLE SENTINEL POLICIES:
          ┌─────────────────────────────────────────────────────────────────┐
          │ # 1. Cost Control: Block instances > $500/month                 │
          │ # 2. Security: Require encryption on all S3 buckets             │
          │ # 3. Security: Block public S3 buckets                          │
          │ # 4. Compliance: All resources must have "Owner" tag            │
          │ # 5. Networking: Block 0.0.0.0/0 in security groups             │
          │ # 6. Regions: Restrict to approved regions only                 │
          └─────────────────────────────────────────────────────────────────┘

          ┌─────────────────────────────────────────────────────────────────┐
          │ advisory   = "This is a suggestion" (warning only)              │
          │ soft-mandatory = "Override possible with approval"              │
          │ hard-mandatory = "NO OVERRIDE — apply is BLOCKED"               │

          MONOREPO (one repo for all Terraform):
          ┌─────────────────────────────────────────────────────────────────┐
          │ terraform-infra/                     ◀── ONE Git repo            │
          │ ├── modules/       (shared)                                     │
          │ ├── dev/           (env)                                        │
          │ ├── staging/       (env)                                        │
          │ └── prod/          (env)                                        │
          │                                                                 │
          │ ✅ Easy code sharing               ❌ Large repo, slow clones   │
          │ ✅ Single CI/CD pipeline           ❌ Prod changes can break    │
          │ ✅ Atomic cross-env changes           dev (tight coupling)      │
          └─────────────────────────────────────────────────────────────────┘

          POLYREPO (separate repo per component):
          ┌─────────────────────────────────────────────────────────────────┐
          │ terraform-modules/    ◀── Shared modules repo                   │
          │ terraform-networking/ ◀── Networking lives here (tagged)        │
          │ terraform-compute/    ◀── Compute lives here (tagged)           │
          │ terraform-database/   ◀── Database lives here (tagged)          │
          │                                                                 │
          │ ✅ Independent versioning          ❌ Harder to coordinate       │
          │ ✅ Smaller, faster clones          ❌ Module version hell        │
          │ ✅ Isolated blast radius           ❌ Multiple CI/CD pipelines   │
          └─────────────────────────────────────────────────────────────────┘

     ┌─────────────────────────────────────────────────────────────────────┐
     │  TABLE 17.1: TERRAFORM UPGRADE STRATEGY — Moving Between Versions   │
     └─────────────────────────────────────────────────────────────────────┘

     ┌────────────┬──────────────────────────────────────────────────────────┐
     │ STEP       │ ACTION                                                   │
     ├────────────┼──────────────────────────────────────────────────────────┤
     │ 1. Read    │ Check CHANGELOG for breaking changes between versions     │
     │ 2. Pin     │ Pin current version in required_version & .terraform.lock │
     │ 3. Test    │ Run terraform plan in non-prod env with NEW version       │
     │ 4. Upgrade │ terraform init -upgrade (gets new providers too)          │
     │ 5. Plan    │ terraform plan — look for "noop" (no changes expected)    │
     │ 6. Apply   │ If plan is clean, apply to non-prod first                 │
     │ 7. Verify  │ Check resources manually in cloud console                 │
     │ 8. Promote │ Repeat for staging, then prod                             │
     │ 9. Rollback│ If issues: pin old version, terraform init, re-apply      │
     ├────────────┼──────────────────────────────────────────────────────────┤
     │ ⚠️ State   │ Once state is upgraded by new version, old Terraform     │
     │    Warning │ CANNOT read it. Always backup state before upgrading.     │
