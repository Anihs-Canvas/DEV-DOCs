🛠️ SRE / Platform Engineer — Practical GPU Ops

Beyond the Exam: Running NVIDIA GPU Infrastructure in Production

As an SRE/Platform Engineer, your job is keeping GPU clusters healthy, automating everything, and ensuring AI workloads run reliably. This section maps certification knowledge to real-world operational patterns.

📋 Daily SRE Tasks with GPU Infrastructure

🌅
Morning Health Check

nvidia-smi across all nodes. Check GPU utilization, memory, temp. dcgmi diag -r 1 quick diagnostic. Prometheus alerts review. Any XID errors overnight?

📊
Capacity Planning

GPU utilization trends. If >80% → plan expansion. If <50% → investigate idle GPUs. Monitor GPU memory pressure — OOM kills waste $100K+ GPU hours.

🔧
Troubleshooting GPUs

GPU falls off bus? dmesg | grep NVRM. XID 79/48? GPU may need RMA. ECC errors exceeding threshold? Schedule replacement. DCGM for proactive monitoring.

🔄
Maintenance Windows

Driver update: drain→cordon→update→reboot→uncordon→verify. Firmware: even more critical. Always test on non-production first. Automate with Ansible.

  • 2. Not knowing Tensor Core precision modes (FP8→FP16→TF32→FP64)
  • 3. Forgetting NVLink speeds: 600→900→1800 GB/s
  • 4. CUDA threads: Grid > Block > Warp(32) > Thread
  • 5. MIG limits: Max 7 for A100 and H100
  • 6. InfiniBand: HDR=200, NDR=400, XDR=800 Gb/s

  • 8. DCGM: DCGM_FI_DEV_GPU_UTIL, DCGM_FI_DEV_FB_USED
  • 9. Precision: FP16=fast, FP32=stable, FP8=fastest (H100)

📋 Domain 2: AI Infrastructure — Detailed Breakdown

🖥️
1. Compute Platforms

GPU: A100 (Ampere, 312 TFLOPS), H100 (Hopper, 989 TFLOPS), B200 (Blackwell, 20 PFLOPS), L40S (Ada, inference-optimized). CPU: Grace ARM CPU (72 cores, 1 TB/s mem BW), x86 from Intel/AMD. DPU: BlueField-3 offloads networking, storage, security from host CPU → more cycles for AI.

🌐
2. Networking for AI

InfiniBand: NDR 400 Gb/s, XDR 800 Gb/s — ultra-low latency (~1µs), native RDMA. Spectrum Ethernet: 400/800 GbE with RoCEv2. NVLink 4.0: 900 GB/s GPU-to-GPU. NVSwitch: Connect up to 8 GPUs all-to-all. GPUDirect RDMA: GPU memory → NIC → network → NIC → GPU memory — zero CPU copies.

💾
3. Storage for AI

NVMe SSDs: 7+ GB/s per drive, 30TB in DGX H100. GPUDirect Storage: GPU reads directly from NVMe via PCIe — bypasses CPU and system memory. Parallel FS: Lustre, Weka, VAST — scale to TB/s aggregate bandwidth. Object Storage: S3-compatible for datasets, model checkpoints, training artifacts.

CUDA Cores — The Workhorses

CUDA cores handle general-purpose floating-point and integer arithmetic. On H100, each SM has 128 FP32 CUDA cores. Across 132 SMs = 16,896 FP32 cores (some are dual-purpose FP32/INT32). These execute standard math operations — add, multiply, divide — on every GPU cycle.

Tensor Cores — The AI Engines

Tensor Cores are NVIDIA's secret weapon. They perform matrix multiply-accumulate (MMA) — the core operation of neural networks — in a single clock cycle. One Tensor Core does the work of 64 CUDA cores for matrix operations. The H100 has 576 Tensor Cores (4 per SM × 132 SMs + extras).

RT Cores — Real-Time Ray Tracing

RT Cores (introduced with Turing in 2018) accelerate ray tracing — simulating how light rays bounce through a scene. While primarily used for graphics and Omniverse rendering, RT Cores also accelerate certain scientific computing workloads that involve ray-surface intersection calculations. The H100 has no dedicated RT Cores (data center focus), but consumer RTX GPUs have them for gaming and professional visualization.

📖 Key Concept: Write code for ONE thread, launch MILLIONS

You write a kernel function that describes what ONE thread does. Then you launch it with thousands of blocks × hundreds of threads = millions of parallel executions. CUDA automatically distributes the work across all available GPU cores. Example: myKernel<<<1000, 256>>>(data) launches 1000 blocks × 256 threads = 256,000 parallel executions!

Warps and SIMT — How Threads Execute

A warp is a group of 32 threads that execute in lockstep on a single SM. This is the fundamental execution unit in NVIDIA GPUs. All threads in a warp execute the same instruction at the same time — this is called SIMT (Single Instruction, Multiple Threads). If one thread in a warp takes a different branch, the warp serializes (warp divergence) — a major performance killer.

GPU Hardware → CUDA Runtime/Driver → CUDA Libraries (300+) → Developer Tools. Each layer builds on the one below — hardware executes instructions, runtime manages memory/launches kernels, libraries provide optimized primitives, tools enable profiling/debugging.

Q2

How many threads are launched with myKernel<<<1000, 256>>>(data)?

✅ ANSWER

256,000 threads (1000 blocks × 256 threads per block). Each thread runs the same kernel code but operates on different data based on its thread ID.

Q3

Which CUDA library would you use for GPU-accelerated matrix multiplication in an anihpj job-matching system?

✅ ANSWER

cuBLAS (CUDA Basic Linear Algebra Subprograms). It provides highly optimized matrix multiply (GEMM) operations that compute job-candidate similarity scores as dot products in milliseconds on GPU.

Q4

What is the purpose of NCCL and when would you use it?

✅ ANSWER

NCCL (NVIDIA Collective Communications Library) provides multi-GPU and multi-node collective operations (All-Reduce, All-Gather, Broadcast). Used for distributed training across multiple GPUs — synchronizing gradients after each training step.

Q5

Which CUDA memory type is the fastest but most limited in size?

✅ ANSWER

Registers — ~0 cycle latency, but only ~255 per thread. Next fastest is Shared Memory (~20 cycles, 256KB per SM). Slowest is Global Memory (HBM3) (~400 cycles, 80GB).

Q6

✅ ANSWER

Q7

What is TensorRT and what optimizations does it perform?

✅ ANSWER

TensorRT is NVIDIA's high-performance inference optimizer. It performs: Layer Fusion (combine Conv+BN+ReLU into one kernel), Precision Calibration (FP32→FP16→INT8), Kernel Auto-Tuning (select best algorithm for specific GPU), and Memory Optimization (reuse buffers). Results: 5-10x faster inference.

4.3 Tensor Cores — The AI Engine

Tensor Cores perform D = A×B + C — matrix multiply-accumulate — in a single clock cycle. One Tensor Core replaces ~64 CUDA cores for matrix math. The H100 has 576 Tensor Cores (4 per SM × 132 SMs + extras).

CUDA C++ — First Kernel (hello_gpu.cu)
// hello_gpu.cu — Your first CUDA program
#include <stdio.h>

// __global__ means this function runs ON THE GPU, called FROM THE CPU
__global__ void hello_kernel() {
    // Calculate unique global thread ID
    int idx = threadIdx.x + blockIdx.x * blockDim.x;
    printf("Hello from GPU thread %d!\n", idx);
}

int main() {
    // Launch 2 blocks, each with 4 threads → 8 total threads
    hello_kernel<<<2, 4>>>();

    // Wait for GPU to finish before exiting
    cudaDeviceSynchronize();

    printf("Hello from CPU!\n");
    return 0;
}

// Compile:  nvcc hello_gpu.cu -o hello_gpu
// Run:      ./hello_gpu
// Output:   8x "Hello from GPU thread N!" + 1x "Hello from CPU!"

⚠️ Gotcha: Missing cudaDeviceSynchronize

If you forget cudaDeviceSynchronize(), the CPU may exit main() before the GPU finishes — and you'll see no GPU output at all! Always synchronize before reading GPU results.

🧭 Decision Tree: Which CUDA Memory Type Should I Use?

Do you need both CPU and GPU to access the same data?
✅ YES → Use Unified Memory (cudaMallocManaged)
Simplest — one pointer, auto-migration
❌ NO — GPU only
Is data < 48 KB per block AND reused by multiple threads?
✅ YES → Shared Memory (__shared__)

❌ NO → Global Memory (HBM)

📌 Golden Rule: Keep hot data in registers/shared memory. Minimize HtoD transfers. Use pinned memory for faster copies.

⚠️ Gotcha: Unified Memory on Pre-Pascal GPUs

On Kepler/Maxwell GPUs, Unified Memory requires cudaDeviceSynchronize() before the CPU can read GPU-written data. On Pascal+ (P100, V100, A100, H100), page faulting handles this automatically.

7.4 CUDA Error Handling

CUDA functions return cudaError_t. Always check the return value — silent GPU errors lead to corrupted results that are hard to debug.

CUDA C++ — Error Handling Macro (Best Practice)
// CHECK macro — wrap every CUDA API call
#define CHECK(call) {                                                    \
    cudaError_t err = call;                                             \
    if (err != cudaSuccess) {                                           \
        fprintf(stderr, "CUDA Error at %s:%d — %s\n",                  \
                __FILE__, __LINE__, cudaGetErrorString(err));            \
        exit(EXIT_FAILURE);                                             \
    }                                                                   \
}

// Usage:
CHECK(cudaMalloc(&d_data, N * sizeof(float)));
CHECK(cudaMemcpy(d_data, h_data, N * sizeof(float), cudaMemcpyHostToDevice));
kernel<<<blocks, threads>>>(d_data, N);

// After kernel launch — catch launch errors
cudaError_t launch_err = cudaGetLastError();
if (launch_err != cudaSuccess) {
    printf("Kernel launch failed: %s\n", cudaGetErrorString(launch_err));
}
CHECK(cudaDeviceSynchronize());  // catches async kernel errors too
⚠️ Common CUDA Errors
  • cudaErrorInvalidConfiguration — too many threads per block (>1024) or shared memory exceeded
  • cudaErrorMemoryAllocation — out of GPU memory
  • cudaErrorIllegalAddress — out-of-bounds memory access in kernel
  • cudaErrorNoDevice — no GPU detected or driver not loaded

CUDA C++ — Multi-Stream Pattern
// Create 2 streams for overlapped execution
cudaStream_t stream0, stream1;
cudaStreamCreate(&stream0);
cudaStreamCreate(&stream1);

// Split data into 2 chunks
int chunk_size = N / 2;

// Launch copy + kernel + copy on each stream (they overlap!)
cudaMemcpyAsync(d_a,       h_a,       chunk_size, HtoD, stream0);
cudaMemcpyAsync(d_a + chunk, h_a + chunk, chunk_size, HtoD, stream1);

kernel<<<blocks, threads, 0, stream0>>>(d_a, chunk_size);
kernel<<<blocks, threads, 0, stream1>>>(d_a + chunk, chunk_size);

cudaMemcpyAsync(h_c,       d_c,       chunk_size, DtoH, stream0);
cudaMemcpyAsync(h_c + chunk, d_c + chunk, chunk_size, DtoH, stream1);

cudaStreamSynchronize(stream0);  // Wait for stream0 to finish
cudaStreamSynchronize(stream1);  // Wait for stream1 to finish

cudaStreamDestroy(stream0);
cudaStreamDestroy(stream1);

✅ Verify: nvprof Stream Overlap

Run nsys profile --stats=true ./your_app and look at the timeline. Overlapping streams show as concurrent HtoD + Compute + DtoH bars. If they're serialized, check: (1) using cudaMemcpyAsync not cudaMemcpy, (2) using pinned memory, (3) GPU supports concurrent copy+execute (most do from Kepler onwards).

⏱️ CUDA Events — Timing GPU Kernels Accurately

CUDA Events let you measure GPU execution time with microsecond precision. Unlike CPU timers, events capture actual GPU execution time — including kernel launches and memory transfers.

CUDA C++ — Timing Kernels with CUDA Events
// CUDA Events — the right way to measure GPU time
cudaEvent_t start, stop;
cudaEventCreate(&start);
cudaEventCreate(&stop);

cudaEventRecord(start, 0);           // Record time BEFORE kernel
kernel<<<blocks, threads>>>(args);
cudaEventRecord(stop, 0);            // Record time AFTER kernel
cudaEventSynchronize(stop);          // Wait for stop event to complete

float milliseconds = 0;
cudaEventElapsedTime(&milliseconds, start, stop);
printf("Kernel time: %.3f ms\n", milliseconds);

cudaEventDestroy(start);
cudaEventDestroy(stop);
// ⚡ Events measure GPU time, not CPU wall-clock time!

📐 Beyond 1D — 2D & 3D Grid and Block Dimensions

CUDA supports up to 3-dimensional grids and blocks — essential for 2D images, 3D volumes, and matrix operations.

CUDA C++ — 2D Kernel Launch
// 2D kernel — perfect for image processing, matrix operations
dim3 threads_per_block(16, 16);  // 16×16 = 256 threads per block
dim3 blocks_per_grid(
    (width  + threads_per_block.x - 1) / threads_per_block.x,
    (height + threads_per_block.y - 1) / threads_per_block.y
);

__global__ void image_filter_kernel(float* image, int width, int height) {
    int x = threadIdx.x + blockIdx.x * blockDim.x;
    int y = threadIdx.y + blockIdx.y * blockDim.y;
    if (x < width && y < height) {
        int idx = y * width + x;  // Row-major flattened index
        image[idx] = process_pixel(image[idx]);  // One thread per pixel!
    }
}

image_filter_kernel<<<blocks_per_grid, threads_per_block>>>(d_image, W, H);

// anihpj_job_matcher.cu
// GPU-accelerated candidate-job similarity for jobpost app

#define EMBEDDING_DIM 512  // Embedding vector size

// Kernel: each thread computes similarity for ONE job
__global__ void compute_similarities(
    const float* jobs_matrix,   // [num_jobs × EMBEDDING_DIM] on GPU
    const float* candidate_vec, // [EMBEDDING_DIM] on GPU
    float* scores,              // [num_jobs] output on GPU
    int num_jobs)
{
    int job_idx = threadIdx.x + blockIdx.x * blockDim.x;

    if (job_idx < num_jobs) {
        float dot = 0.0f;
        // Dot product: candidate_vec · jobs_matrix[job_idx]
        for (int d = 0; d < EMBEDDING_DIM; d++) {
            dot += candidate_vec[d] * jobs_matrix[job_idx * EMBEDDING_DIM + d];
        }
        scores[job_idx] = dot;  // Higher = better match
    }
}

// Host function — callable from Django via ctypes/FFI
extern "C" void match_jobs_gpu(
    const float* h_jobs,   // CPU: jobs matrix
    const float* h_cand,   // CPU: candidate vector
    float* h_scores,       // CPU: result scores (pre-allocated)
    int num_jobs)
{
    float *d_jobs, *d_cand, *d_scores;
    size_t jobs_bytes = num_jobs * EMBEDDING_DIM * sizeof(float);
    size_t cand_bytes = EMBEDDING_DIM * sizeof(float);
    size_t score_bytes = num_jobs * sizeof(float);

    // 1. Allocate GPU memory
    cudaMalloc(&d_jobs, jobs_bytes);
    cudaMalloc(&d_cand, cand_bytes);
    cudaMalloc(&d_scores, score_bytes);

    // 2. Copy data to GPU
    cudaMemcpy(d_jobs, h_jobs, jobs_bytes, cudaMemcpyHostToDevice);
    cudaMemcpy(d_cand, h_cand, cand_bytes, cudaMemcpyHostToDevice);

    // 3. Launch kernel — 256 threads/block, enough blocks for all jobs
    int threads = 256;
    int blocks = (num_jobs + threads - 1) / threads;
    compute_similarities<<<blocks, threads>>>(
        d_jobs, d_cand, d_scores, num_jobs);

    // 4. Copy results back to CPU
    cudaMemcpy(h_scores, d_scores, score_bytes, cudaMemcpyDeviceToHost);

    // 5. Cleanup
    cudaFree(d_jobs);
    cudaFree(d_cand);
    cudaFree(d_scores);
}

Click to reveal answer
✅ ANSWER

You launch a kernel but see no GPU output. What did you likely forget?

How many threads are in one CUDA warp, and why does this number matter?

Click to reveal answer
✅ ANSWER

32 threads on all NVIDIA GPUs. This matters because threads within a warp execute in lockstep — if one thread diverges (takes a different branch), all 32 threads serialize both paths. Always use thread counts that are multiples of 32.

Q7

What CUDA API call transfers data from GPU back to CPU?

Click to reveal answer

Q8

How do CUDA streams improve performance?

Click to reveal answer
✅ ANSWER

Streams enable concurrent execution — while one stream's kernel is computing, another stream can be transferring data. This overlaps HtoD transfers with kernel execution and DtoH transfers, effectively hiding data transfer latency and achieving 2-3× throughput improvement.

Q9

In the anihpj job matching CUDA kernel, why does each thread handle exactly one job?

Click to reveal answer
✅ ANSWER

It's the natural parallel decomposition: 100K jobs → 100K threads, each computing one dot product independently. This maximizes parallelism. If num_jobs > max threads, you'd use a grid-stride loop (for (int i = global_id; i < num_jobs; i += grid_stride)) so each thread handles multiple jobs.

Q10

Why should threads per block always be a multiple of 32?

Click to reveal answer
✅ ANSWER

Because a warp is 32 threads and the SM schedules work in warp granularity. If you launch 50 threads per block, you get 1 full warp (32) + 1 partial warp (18). The partial warp wastes 14 thread slots that could have done useful work. Always use multiples of 32: 128, 256, 512, 1024.

8.1 Memory Coalescing — Aligning Memory Access

When threads in a warp access contiguous memory addresses, the GPU combines them into a single wide transaction (32/64/128 bytes). Strided or scattered access requires multiple transactions — dramatically reducing effective bandwidth.

Coalesced vs Strided Memory Access
  ┌──────────────────────────────────────────────────────────────────────────┐
  │  ✅ COALESCED (Contiguous — 1 Transaction):                              │
  │  Warp threads:     T0  T1  T2  T3  T4  T5  ...  T31                     │
  │  Memory:          [A0][A1][A2][A3][A4][A5] ... [A31]                      │
  │  → All 32 addresses fit in 128B cache line = 1 MEMORY TRANSACTION        │
  │                                                                          │
  │  ❌ STRIDED (Scattered — 32 Transactions):                               │
  │  Warp threads:     T0  T1  T2  T3  T4  T5  ...  T31                     │
  │  Memory:          [A0][A100][A200][A300][A400] ... [A3100]                │
  │  → Each address in different cache line = 32 MEMORY TRANSACTIONS         │
  │  → 32× SLOWER!                                                            │
  │                                                                          │
  │  Solution: Data Structure of Arrays (SoA) → Array of Structures (AoS)    │
  │  BAD (AoS): struct {float x,y,z;} particles[N];  // x,y,z scattered     │
  │  GOOD (SoA): struct {float *x,*y,*z;} particles; // x,x,x... contiguous │
  └──────────────────────────────────────────────────────────────────────────┘
CUDA C++ — Coalesced vs Strided for anihpj embeddings
// BAD: Strided access — each thread jumps by EMBEDDING_DIM
// Thread i reads jobs[i * 512 + d] — 32× memory transactions!
__global__ void dot_product_bad(float* jobs, float* cand, float* out, int N) {
    int tid = threadIdx.x + blockIdx.x * blockDim.x;
    float sum = 0;
    for (int d = 0; d < 512; d++)
        sum += jobs[tid * 512 + d] * cand[d];  // STRIDED!
    out[tid] = sum;
}

// GOOD: Coalesced access — contiguous threads read contiguous addresses
// Thread i reads jobs[d * N + tid] — 1 MEMORY TRANSACTION per d!
__global__ void dot_product_good(float* jobs, float* cand, float* out, int N) {
    int tid = threadIdx.x + blockIdx.x * blockDim.x;
    float sum = 0;
    for (int d = 0; d < 512; d++)
        sum += jobs[d * N + tid] * cand[d];  // COALESCED! 32× faster
    out[tid] = sum;
}
// Key insight: Transpose the jobs matrix from [N, 512] to [512, N] storage!

⚡ Speed Tip: Always Access by Thread ID First

The golden rule: the array dimension indexed by threadIdx.x should be the contiguous dimension. If your data is stored [rows, cols] and each thread processes one row, the inner loop should iterate over cols — each column access across threads is strided!

8.2 Shared Memory Optimization — Tiling Techniques

Shared memory is an on-chip SRAM (~100× faster than HBM, ~1 TB/s per SM) shared by all threads in a block. Tiling loads a small chunk of data from global memory into shared memory, then computes on that tile — drastically reducing global memory traffic.

Tiling: Matrix Multiplication Example

  │  Without Tiling (Naive — 2N³ global memory reads):                        │
  │  for each row of A:                                                       │
  │    for each col of B:                                                     │
  │      read entire row of A + entire col of B from GLOBAL MEMORY            │
  │  → Each element read N times from slow HBM!                              │
  │                                                                          │
  │  With Tiling (Optimized — N³/T global memory reads):                     │
  │                                                                          │
  │  ┌──────┬──────┐       ┌──────┬──────┐                                  │
  │  │TILE  │TILE  │       │TILE  │TILE  │    Tile size: T×T                 │
  │  │A_00  │A_01  │   ✕   │B_00  │B_01  │    Each tile: T² elements         │
  │  ├──────┼──────┤       ├──────┼──────┤    Loaded ONCE into shared memory  │
  │  │A_10  │A_11  │       │B_10  │B_11  │    Then reused T times!            │
  │  └──────┴──────┘       └──────┴──────┘                                  │
  │                                                                          │
  │  Shared Memory | Tile (T×T): 1 load per element → T reuses               │

⚠️ Gotcha: __syncthreads() is Mandatory

After loading a tile into shared memory, you MUST call __syncthreads() before any thread reads the tile. Without it, some threads may read before others have finished writing — producing garbage results. Same rule applies after computation and before loading the next tile.

8.3 Occupancy — Maximizing Active Warps per SM

Occupancy is the ratio of active warps to the maximum possible warps per SM. Higher occupancy means more warps available to hide latency (memory stalls, instruction latency) by context-switching. But there's a trade-off: more registers per thread = fewer threads per SM.

💡 Occupancy Formula
// Warps per block = ceil(threads_per_block / 32)
// Blocks per SM (register limit) = registers_per_SM / (registers_per_thread × 32 × warps_per_block)
// Blocks per SM (shared mem limit) = shared_mem_per_SM / shared_mem_per_block
// Active warps = min(blocks_from_registers, blocks_from_shmem, max_blocks) × warps_per_block

// Example: 256 threads/block, 64 registers/thread, no shared mem on A100
// warps_per_block = 256/32 = 8
// registers per block = 64 × 256 = 16,384
// blocks from registers = 65536 / 16384 = 4
// active warps = 4 × 8 = 32 → Occupancy = 32/64 = 50%  (could be better!)

8.4 Bank Conflicts — Shared Memory Pitfalls

Shared memory is divided into 32 banks (one per warp thread), each 4 bytes wide. If two threads in the same warp access different addresses in the same bank, the accesses serialize — this is a bank conflict.

Always declare shared memory arrays with one extra column: __shared__ float smem[BLOCK_SIZE][BLOCK_SIZE + 1]. The +1 shifts all subsequent rows to different banks, eliminating most bank conflicts in matrix operations. Cost: negligible memory overhead.

8.5 Warp Divergence — The Cost of Branching

All 32 threads in a warp execute the same instruction (SIMT). If an if/else causes some threads to take one path and others another, the GPU executes both paths sequentially — doubling execution time.

Warp Divergence — Why if/else Kills GPU Performance
  ┌──────────────────────────────────────────────────────────────────────────┐
  │  ❌ BAD — Thread-level branching (divergent — 2× slower):                 │
  │                                                                          │
  │  if (threadIdx.x % 2 == 0) {                                            │
  │      do_A();  // 16 even threads execute (mask: 0x55555555)             │
  │  } else {                                                                │
  │      do_B();  // 16 odd threads execute (mask: 0xAAAAAAAA)              │
  │  }                                                                       │
  │  → 16 threads run A (others idle), THEN 16 run B (others idle)          │
  │  → 50% utilization → 2× SLOWER                                          │
  │                                                                          │
  │  ✅ GOOD — Warp-aligned branching (no divergence — full speed):          │
  │                                                                          │
  │  if (threadIdx.x / 32 % 2 == 0) {  // First 32 threads → path A        │
  │      do_A();                                                             │
  │  } else {  // Next 32 threads → path B                                  │
  │      do_B();                                                             │
  │  }                                                                       │
  │  → Entire warps take same path → 100% utilization                       │
  │                                                                          │
  │  🔑 RULE: All 32 threads in a warp must take the same branch            │
  └──────────────────────────────────────────────────────────────────────────┘
⚠️ Common Divergence Sources
  • Data-dependent conditions: if (data[idx] > threshold) — values vary per thread
  • Loop bounds: for (int i=0; i < variable_limit; i++) — different threads do different iterations
  • Edge cases: if (idx < N) at the end of arrays — last warp is partially active
  • Solution: Group same-condition data together so whole warps take same path

🔄 Warp Shuffle Instructions — Cross-Thread Communication Without Shared Memory

Warp shuffle instructions (__shfl_down_sync, __shfl_xor_sync) let threads within a warp exchange register values directly — no shared memory needed. This is the fastest form of intra-warp communication and is essential for warp-level reductions.

CUDA C++ — Warp Shuffle Reduction (Faster than Shared Memory!)
// Warp-level reduction using __shfl_down_sync
// Each thread has a value in 'val', we want the sum of all 32 values
__inline__ __device__ float warp_reduce_sum(float val) {
    // Butterfly reduction: halve participants each step
    for (int offset = 16; offset > 0; offset /= 2) {
        val += __shfl_down_sync(0xFFFFFFFF, val, offset);
    }
    return val;  // All threads in warp now have the same sum
}

// float my_val = data[threadIdx.x];
// float warp_sum = warp_reduce_sum(my_val);
// if (threadIdx.x % 32 == 0) shared[threadIdx.x / 32] = warp_sum;

⚡ Warp Shuffle vs Shared Memory

Warp shuffle: ~5 cycles latency, no memory traffic. Shared memory: ~20 cycles, requires load/store + __syncthreads(). Always use warp shuffle first for intra-warp reductions, then shared memory for inter-warp reduction. The _sync variants (CUDA 9+) require an explicit mask — use 0xFFFFFFFF for all 32 threads.

8.6 Atomic Operations & Synchronization

Atomic operations guarantee that a read-modify-write completes without interference from other threads. They're essential for parallel reductions, histograms, and counters — but can serialize if many threads contend for the same address.

CUDA C++ — Atomic Operations for anihpj Skill Counters
// Atomic add — count how many jobs match each skill
__global__ void count_matching_skills(
    const int* job_skills,   // Each job has skill ID
    int* skill_counts,       // Output histogram [num_skills]
    int num_jobs)
{
    int tid = threadIdx.x + blockIdx.x * blockDim.x;
    if (tid < num_jobs) {
        int skill_id = job_skills[tid];
        atomicAdd(&skill_counts[skill_id], 1);  // Thread-safe increment!
    }
}

// Atomic operations available:
// atomicAdd, atomicSub, atomicMin, atomicMax, atomicInc, atomicDec
// atomicExch, atomicCAS (Compare-And-Swap), atomicAnd, atomicOr, atomicXor

// ⚡ Optimize: Use shared memory reduction first, then atomicAdd once per block
__global__ void count_skills_optimized(int* job_skills, int* counts, int N) {
    __shared__ int block_counts[1024];  // Per-block histogram in shared mem
    int tid = threadIdx.x + blockIdx.x * blockDim.x;

    // Phase 1: Build per-block histogram in shared memory (no atomics!)
    if (threadIdx.x < 1024) block_counts[threadIdx.x] = 0;
    __syncthreads();
    if (tid < N) atomicAdd(&block_counts[job_skills[tid]], 1);  // In shared mem
    __syncthreads();

    // Phase 2: One atomic per block to global memory (reduces contention!)
    if (threadIdx.x < 1024 && block_counts[threadIdx.x] > 0)
        atomicAdd(&counts[threadIdx.x], block_counts[threadIdx.x]);
}

⚠️ Gotcha: Atomic Contention

If all threads do atomicAdd(&same_address, 1), they serialize — 1000 threads = 1000× slower! Always use shared memory to aggregate per-block results, then do ONE atomic per block to global memory.

8.8 Common CUDA Performance Anti-Patterns

These are the most frequent mistakes that make CUDA code slow. Recognizing them is half the battle.

1️⃣ Too Few Blocks

Each SM needs multiple blocks to hide latency via context switching. Launch at least 4-8× the number of SMs in blocks. A100 (108 SMs): at least 432 blocks.

2️⃣ Thread Divergence

if/else where threads in a warp take different paths — serializes both. Fix: group data so warp-aligned decisions.

3️⃣ Uncoalesced Access

Strided global memory access (thread i reads element i×stride). Fix: transpose data or use SoA layout.

4️⃣ Ignoring Shared Memory

Re-reading data from HBM repeatedly. Fix: tile into shared memory and reuse.

5️⃣ Atomic Bomb

All threads hammering the same atomic address. Fix: shared-memory block reduction first.

✅ The Fix Formula

Profile→Find bottleneck→Fix→Profile again. Use ncu for kernel analysis and nsys for system timeline.

Q1

What is memory coalescing and why does it matter?

Click to reveal answer
✅ ANSWER

Memory coalescing is when threads in a warp access contiguous memory addresses, allowing the GPU to combine all 32 accesses into a single wide memory transaction (128 bytes). Non-coalesced (strided) access requires 32 separate transactions — up to 32× slower. It's the single most impactful CUDA optimization.

Q2

How does shared memory tiling reduce global memory traffic in matrix multiplication?

Click to reveal answer
✅ ANSWER

Without tiling, each element of matrices A and B is read from global memory N times (once per row/column combination). With tiling of size T×T, each element is loaded once into shared memory and then reused by T threads — reducing global memory reads by a factor of T. For T=32, this is 32× less bandwidth.

Q3

On an A100, what is the maximum number of warps per SM?

Click to reveal answer
✅ ANSWER

64 warps = 2048 threads per SM. This is the theoretical maximum. Actual occupancy depends on register usage per thread and shared memory per block.

Q4

How many shared memory banks are there and what is a bank conflict?

Click to reveal answer
✅ ANSWER

32 banks, each 4 bytes wide. A bank conflict occurs when two or more threads in the same warp access different addresses in the same bank. The accesses serialize: 2-way conflict = 2× slower, 32-way conflict = 32× slower. Solution: pad arrays with +1 element to shift bank mappings.

Q5

You have if (data[idx] > 0) do_A(); else do_B();. When does this cause warp divergence?

Click to reveal answer
✅ ANSWER

When some threads in the same warp have data > 0 and others don't. Since all 32 threads in a warp execute lockstep, the GPU must execute do_A() for the "true" threads while others idle, then execute do_B() for the "false" threads — serializing both paths and doubling execution time.

Q6

Why should you use shared memory reduction before calling atomicAdd to global memory?

Click to reveal answer
✅ ANSWER

Atomic operations serialize when threads contend for the same address. If 256 threads all call atomicAdd(&global_counter, 1), they execute one at a time — 256× slower. Instead, accumulate in shared memory per block first, then use one atomicAdd per block to global memory. This reduces contention by blockDim× factor.

Q7

What is the difference between Nsight Systems and Nsight Compute?

Click to reveal answer
✅ ANSWER

Nsight Systems (nsys): System-level timeline profiler showing CPU threads, GPU kernels, memory transfers, and API calls over time. Best for finding bottlenecks between host and device. Nsight Compute (ncu): Kernel-level profiler diving deep into a single kernel's register usage, occupancy, memory throughput, and stall reasons. Best for optimizing individual kernels.

Q8

You change kernel registers from 128 to 64 per thread. How does this affect occupancy?

Click to reveal answer
✅ ANSWER

Occupancy increases. On A100: 128 registers/thread × 256 threads/block = 32,768 registers/block → 65536/32768 = 2 blocks/SM → 16 warps (25% occupancy). With 64 registers: 64 × 256 = 16,384 registers/block → 65536/16384 = 4 blocks/SM → 32 warps (50% occupancy). Doubling occupancy lets the SM hide more latency.

Q9

What's wrong with launching only 8 blocks on an A100 GPU with 108 SMs?

Click to reveal answer
✅ ANSWER

Only 8 of 108 SMs are utilized — 93% of the GPU is idle! Each SM can work on one block at a time (assuming max resource usage), so you need at least 108 blocks to occupy all SMs. The rule of thumb: launch 4-8× the number of SMs in blocks (432-864 for A100) to fully utilize the GPU with context switching.

Q10

You profile a kernel and see "Long Scoreboard" as the top stall reason. What does this mean and how do you fix it?

Click to reveal answer
✅ ANSWER

Long Scoreboard means warps are stalled waiting on global memory reads (HBM latency ~300-800 cycles). Fixes: (1) Use shared memory tiling to reduce global reads. (2) Increase occupancy so more warps can hide latency. (3) Prefetch data into registers before use. (4) Ensure memory access is coalesced to maximize bandwidth.

9.3 Numba — JIT-Compile Python to CUDA Kernels

Numba's @cuda.jit decorator compiles Python functions into native CUDA kernels. You write Python but get C++-level GPU performance. This is perfect for custom algorithms that CuPy/PyTorch don't cover.

Python — Numba CUDA Kernel for anihpj Ranking
# anihpj/jobpost/numba_ranker.py
from numba import cuda
import numpy as np

@cuda.jit
def rank_candidates_kernel(jobs_matrix, candidate_vector, scores, num_jobs):
    """
    GPU kernel: each CUDA thread computes dot product for ONE job.
    This is Python that compiles to the SAME PTX as CUDA C++!
    """
    job_idx = cuda.threadIdx.x + cuda.blockIdx.x * cuda.blockDim.x

    if job_idx < num_jobs:
        dot = 0.0
        for d in range(512):  # EMBEDDING_DIM
            dot += jobs_matrix[job_idx, d] * candidate_vector[d]
        scores[job_idx] = dot

def match_with_numba(jobs_np, cand_np):
    """Host function — manages GPU memory and launches kernel"""
    num_jobs = jobs_np.shape[0]

    # Allocate and copy to GPU
    d_jobs = cuda.to_device(jobs_np)
    d_cand = cuda.to_device(cand_np)
    d_scores = cuda.device_array(num_jobs, dtype=np.float32)

    # Launch: 256 threads/block, enough blocks for all jobs
    threads_per_block = 256
    blocks_per_grid = (num_jobs + threads_per_block - 1) // threads_per_block

    rank_candidates_kernel[blocks_per_grid, threads_per_block](
        d_jobs, d_cand, d_scores, num_jobs)

    # Copy result back
    scores = d_scores.copy_to_host()

    # Top 10 (CPU — GPU argsort also available via CuPy!)
    return np.argsort(scores)[-10:][::-1]

# Performance: ~3 ms for 100K jobs (vs ~500 ms CPU NumPy = 167× faster!)
# The @cuda.jit decorator compiles Python → PTX → SASS automatically!

⚡ When to Use Numba vs CuPy

CuPy: when your computation can be expressed as NumPy array operations (dot, sum, argsort, etc.). Numba @cuda.jit: when you need custom per-element logic, loops, or conditions that aren't expressible as vectorized NumPy ops. Numba gives you CUDA C++ performance with Python syntax.

9.4 PyTorch CUDA Extensions — Custom GPU Ops for Deep Learning

When PyTorch's built-in ops aren't enough, you can write custom CUDA kernels directly in PyTorch using torch.utils.cpp_extension. This is the bridge between Python deep learning and raw CUDA power — commonly used for custom attention mechanisms, tokenizers, and embedding operations.

Python + CUDA — PyTorch Custom Extension for anihpj Embedding Similarity
# anihpj/jobpost/torch_cuda_ext.py
import torch
from torch.utils.cpp_extension import load_inline

# CUDA C++ kernel as a Python string — compiled at runtime!
cuda_source = """
#include <torch/extension.h>
#include <cuda.h>
#include <cuda_runtime.h>

// CUDA kernel for batched cosine similarity
__global__ void cosine_sim_kernel(
    const float* __restrict__ embeddings,  // [batch, emb_dim]
    const float* __restrict__ query,       // [emb_dim]
    float* __restrict__ output,            // [batch]
    int batch_size, int emb_dim)
{
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    if (idx >= batch_size) return;

    float dot = 0.0f, norm_a = 0.0f, norm_b = 0.0f;
    const float* row = embeddings + idx * emb_dim;

    for (int d = 0; d < emb_dim; d++) {
        dot   += row[d] * query[d];
        norm_a += row[d] * row[d];
        norm_b += query[d] * query[d];
    }
    output[idx] = dot / (sqrtf(norm_a) * sqrtf(norm_b) + 1e-8f);
}

torch::Tensor cosine_similarity_cuda(torch::Tensor embeddings, torch::Tensor query) {
    auto batch_size = embeddings.size(0);
    auto emb_dim = embeddings.size(1);
    auto output = torch::empty({batch_size}, embeddings.options());

    const int threads = 256;
    const int blocks = (batch_size + threads - 1) / threads;

    cosine_sim_kernel<<<blocks, threads>>>(
        embeddings.data_ptr<float>(), query.data_ptr<float>(),
        output.data_ptr<float>(), batch_size, emb_dim);

    return output;
}
"""

cpp_source = """
torch::Tensor cosine_similarity_cuda(torch::Tensor embeddings, torch::Tensor query);
"""

# Compile and load at import time!
cosine_sim_ext = load_inline(
    name='cosine_sim_ext',
    cpp_sources=cpp_source,
    cuda_sources=cuda_source,
    functions=['cosine_similarity_cuda'],
    verbose=False
)

def match_jobs_torch(embeddings, query):
    """Use custom CUDA kernel from PyTorch"""
    return cosine_sim_ext.cosine_similarity_cuda(embeddings, query)

11.3 Fine-Tuning LLMs with NeMo

Fine-tuning adapts a pre-trained LLM (like Llama 3 or Mistral) to your specific domain using your own data. NeMo supports PEFT/LoRA (Parameter-Efficient Fine-Tuning) which modifies only a small fraction of weights — making fine-tuning feasible on a single GPU.

Python — NeMo Fine-Tuning Script for anihpj (jobpost/finetune_job_llm.py)
# anihpj/jobpost/finetune_job_llm.py
# Fine-tune Llama 3 on anihpj job posting data with PEFT/LoRA

import torch
from nemo.collections.nlp.models import PEFTModel
from omegaconf import OmegaConf

# Load pre-trained model from NGC
model = PEFTModel.from_pretrained("nvidia/Llama-3-8B-NeMo")

# Prepare anihpj training data (job title + description → formatted output)
# train.jsonl format:
# {"input": "Generate job description for: Senior Python Dev in Lagos",
#  "output": "We are seeking a Senior Python Developer..."}

train_data = "anihpj_jobpost_train.jsonl"

# Configure PEFT/LoRA
peft_cfg = OmegaConf.create({
    "peft_scheme": "lora",
    "lora_rank": 16,           # Small rank = fewer trainable params
    "lora_alpha": 32,
    "target_modules": ["q_proj", "v_proj"],  # Only tune attention
})

model.setup_peft(peft_cfg)

# Train on 2 GPUs
trainer = torch.distributed.launch(
    model,
    train_data=train_data,
    num_gpus=2,
    max_epochs=3,
    learning_rate=2e-4,
    batch_size=4,
    gradient_accumulation=4,   # Effective batch size = 4×4 = 16
)

trainer.fit(model)

# Save fine-tuned model
model.save_pretrained("./anihpj_job_llm_finetuned")

# Result: Llama 3 fine-tuned to generate professional job descriptions
# in anihpj's style, with company-specific terminology and format!

⚡ PEFT/LoRA: Fine-tune on a Single GPU

Full fine-tuning of an 8B model needs ~80 GB VRAM (multiple A100s). With LoRA (rank=16), you train only ~0.1% of parameters — fitting on a single RTX 4090 (24 GB). The trade-off: ~98% of full fine-tuning quality for 1% of the compute cost.

12.4 Dynamic Batching — Maximizing GPU Throughput

Dynamic batching is Triton's killer feature. Instead of processing one request at a time (underutilizing the GPU), Triton collects multiple individual requests into a batch — then processes them all in one GPU pass. The result: 10-100× higher throughput with minimal latency impact.

  │  WITHOUT DYNAMIC BATCHING (1 request at a time — GPU idle 90%):          │
  │  Time →  Req1[████████░░░░░░░░░░]Req2[░████████░░░░░░░░]Req3[░░████████] │

  │  WITH DYNAMIC BATCHING (Collect & batch — GPU saturated):                │

⚡ Dynamic Batching Best Practice

Set max_queue_delay_microseconds to 100-500 for interactive apps (low latency), 1000-5000 for batch processing (high throughput). Use preferred_batch_size to tell Triton your model's sweet spot (e.g., multiples of tensor core dimensions).

This increases GPU utilization from ~20% to ~85%, yielding 10-100× higher throughput.

NVIDIA Collective Communications Library (NCCL) optimizes all-reduce, all-gather, and broadcast operations across the GPU fabric. It automatically selects the best communication path (NVLink for intra-node, InfiniBand for inter-node) and uses ring/tree algorithms for maximum bandwidth utilization.

15.3 Storage for AI — Feeding the GPU Beast

AI training is I/O intensive. A single DGX H100 can consume data at ~20 GB/s. If storage can't keep up, expensive GPUs sit idle waiting for data. GPUDirect Storage enables DMA transfers from NVMe directly to GPU memory — bypassing the CPU entirely.

15.4 Power & Cooling — The 40kW+ Rack Challenge

A single DGX H100 draws 10.2 kW. A rack of 4 DGX systems = 40 kW — far exceeding traditional data center rack capacity (typically 5-15 kW). GPU clusters require fundamental rethinking of power distribution and cooling.

🔌 Power Requirements

• DGX H100: 10.2 kW each
• 4× DGX per rack: 40-50 kW
• Requires 3-phase power (415V)
• UPS + generator for training continuity
• Budget: $10-15K/month per rack (power)

❄️ Cooling Solutions

• Air: Hot-aisle containment, max ~25 kW/rack
• Direct Liquid: Cold plates on GPUs/CPUs, ~50 kW/rack
• Immersion: Servers submerged in dielectric fluid, ~100 kW/rack
• DGX B200: Liquid cooling recommended

15.5 Cluster Sizing — How Many GPUs Do You Need?

Sizing a GPU cluster requires understanding your workload. The key metric: GPU-hours per training run. Multiply by the number of runs per day, add inference serving, and buffer for growth.

📝 Cluster Sizing Formula
Required GPUs = (Training GPU-hours/day + Inference GPU-hours/day) ÷ 24 × 1.3 (30% buffer)

Example: anihpj cluster
• Training: 2 DGX × 4 hrs/run × 1 run/day = 8 GPU-hrs × 8 GPUs/DGX = 64 GPU-hrs
• Inference: Need 4 GPUs 24/7 serving Triton = 96 GPU-hrs
• Total: (64 + 96) ÷ 24 × 1.3 = 8.7 → 12 GPUs minimum (round to 2× DGX H100)
• Future: Add 1 DGX for R&D = 3× DGX H100 recommended cluster

Q1

What are the three tiers of a GPU cluster architecture?

Click to reveal answer
✅ ANSWER

Compute nodes (GPU servers), Network fabric (InfiniBand/Ethernet interconnect), and Storage nodes (NVMe/parallel filesystem). All three must be balanced — a slow storage tier starves GPUs, and a weak network limits distributed training scaling.

Q2

What is the bandwidth hierarchy for GPU communication?

Click to reveal answer
✅ ANSWER

NVLink/NVSwitch (900 GB/s, intra-node) → InfiniBand NDR/XDR (400-800 GB/s, inter-node) → RoCE v2 (200-400 GB/s, Ethernet-based, lower cost). The goal is non-blocking fabric — no link should be oversubscribed.

Q3

What is GPUDirect Storage and why is it important?

Click to reveal answer
✅ ANSWER

GPUDirect Storage enables DMA transfers from NVMe storage directly into GPU memory, bypassing the CPU entirely. This eliminates the CPU as a bottleneck in the data pipeline and reduces latency from milliseconds to microseconds — critical for keeping GPUs fed during training.

Q4

Why is NFS not suitable for GPU training storage?

Click to reveal answer
✅ ANSWER

NFS throughput (~10 GB/s) is far below what GPUs need (a single DGX H100 can consume ~20 GB/s). NFS introduces CPU overhead and latency that causes GPUs to stall waiting for data. Use local NVMe, GPUDirect Storage, Lustre, or WEKA instead.

Q5

What power does a rack of 4 DGX H100 systems require?

Click to reveal answer
✅ ANSWER

40-50 kW (4 × 10.2 kW per DGX, plus networking and storage). This requires 3-phase 415V power and liquid cooling (direct-to-chip or immersion). Traditional air-cooled data centers (5-15 kW per rack) cannot support this density.

Q6

What is the difference between fat-tree and rail-optimized network topologies?

Click to reveal answer
✅ ANSWER

Fat-tree: Full bisection bandwidth — every node has equal BW to every other node. General purpose. Rail-optimized: GPUs at the same position across nodes share a dedicated rail, optimized for all-reduce communication patterns in distributed training. More efficient for AI workloads but less flexible.

Q7

How do you calculate the required number of GPUs for a cluster?

Click to reveal answer
✅ ANSWER

Required GPUs = (Training GPU-hrs/day + Inference GPU-hrs/day) ÷ 24 × 1.3. The 1.3 factor is a 30% buffer for growth, maintenance, and unexpected workloads. GPU-hours = nodes × GPUs per node × hours used.

Q8

What is NCCL and what does it optimize?

Click to reveal answer
✅ ANSWER

NVIDIA Collective Communications Library (NCCL) optimizes collective operations (all-reduce, all-gather, broadcast, reduce-scatter) across GPUs. It automatically selects the best communication path (NVLink within node, InfiniBand across nodes) and uses ring/tree algorithms for maximum bandwidth. Essential for distributed training.

What cooling technology is recommended for DGX B200 and why?
