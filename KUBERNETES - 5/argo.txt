    KEY ANALOGIES:
    ┌────────────────────────────────────────────────────────────────────┐
    │  🏭 Factory     = CI Pipeline (GitHub Actions / Jenkins)            │
    │     Builds the container image (builds the "shipping container")    │
    │                                                                     │
    │  📦 Warehouse   = Container Registry (Docker Hub / GHCR)            │
    │     Stores built images ready for deployment                        │
    │                                                                     │
    │  📋 Manifest    = Kubernetes YAML files in Git                       │
    │     "Shipping manifest" — declares what, how many, where            │
    │                                                                     │
    │  ☸️ Captain     = ArgoCD                                             │
    │     Reads the manifest, ensures the dock has exactly what's ordered │
    │                                                                     │
    │  🏗️ Dock/Harbor = Kubernetes Cluster                                │
    │     Where containers are unloaded, run, and managed                 │
    │                                                                     │
    │  📦 Container   = Docker Container (Pod)                             │
    │     Standardized, sealed, runs the same anywhere                    │
    │                                                                     │
    │  🔄 Tugboat     = ArgoCD Sync                                       │
    │     Brings new containers from the warehouse to the dock            │
    └────────────────────────────────────────────────────────────────────┘

    ┌────────────────────────────────────────────────────────────────────┐
    │  🎯 THE KEY INSIGHT: GitOps = The Captain Doesn't Push             │
    │                                                                    │
    │  In TRADITIONAL CI/CD (Push):                                      │
    │  The factory (CI) ships directly to the dock (K8s)                 │
    │  → Factory needs dock keys 🔑 (SECURITY RISK!)                     │
    │  → No one checks what's at the dock vs the manifest                │
    │                                                                    │
    │  In GITOPS (Pull):                                                 │
    │  The factory updates the manifest (Git)                            │
    │  The captain (ArgoCD) continuously checks the manifest vs dock     │
    │  → Captain is INSIDE the dock (no external credentials exposed!)   │
    │  → Captain detects drift: "There's a container I didn't order!"    │
    │  → Captain auto-corrects: "Removing unauthorized container..."     │
    └────────────────────────────────────────────────────────────────────┘

Chapter 2: Introduction to ArgoCD — Core Concepts
--------------------------------------------------------------------------------
    2.1  What is ArgoCD?
         - Official definition: "A declarative, GitOps continuous delivery tool for Kubernetes"
         - ArgoCD = Argo + CD (Continuous Delivery)
         - Part of the larger Argo Project (Argo Workflows, Argo Rollouts, Argo Events)
         - Created by Intuit (now CNCF Graduated)
         [QUICK FACTS CARD: Creator, CNCF status, first release, latest version]

    2.2  How ArgoCD Works — The 30-Second Elevator Pitch
         - You define your app's desired state in Git (YAML manifests, Helm charts, Kustomize)
         - ArgoCD polls Git every 3 minutes (configurable)
         - Compares desired state (Git) vs actual state (K8s)
         - If different → shows as "OutOfSync"
         - Click "Sync" (or auto-sync) → ArgoCD brings K8s to desired state
         [SIMPLE DIAGRAM: Git → ArgoCD → K8s Cluster flow]

    2.3  Key ArgoCD Terminology
         - Application: A group of K8s resources defined by a Git repo
         - Project: Logical grouping of Applications + RBAC + restrictions
         - Target/Cluster: The K8s cluster where apps are deployed
         - Repository: Git repository containing app manifests
         - Sync: The process of making K8s match Git
         - Sync Status: Synced / OutOfSync / Unknown
         - Health Status: Healthy / Progressing / Degraded / Suspended / Missing
         - Refresh: Re-evaluate desired vs actual state (3-way diff)
         - Prune: Delete resources in K8s that are no longer in Git
         - Self-Heal: Auto-sync when drift is detected
         [GLOSSARY TABLE: Term → Definition → Example with anihpj]

    2.4  ArgoCD Application Types
         - Helm Charts (ArgoCD natively understands Helm)
         - Kustomize (built-in Kustomize support)
         - Plain YAML / Directory of Manifests
         - Jsonnet / Ksonnet
         - Custom Config Management Plugins (CMP)
         [VISUAL: 5 application type cards with icons]

    2.5  ArgoCD vs Traditional CI/CD — The Paradigm Shift
         - Traditional: CI builds → pushes to K8s (push model)
         - GitOps: CI builds → pushes to Git registry → ArgoCD pulls to K8s
         - CI builds images, CD deploys them — separation of concerns
         - ArgoCD doesn't build; it deploys (complementary to CI, not replacement)

    4.2  Core Components Deep Dive
         4.2a API Server — The Gateway
              - REST API + gRPC (argocd CLI connects via gRPC)
              - Web UI communicates via REST API
              - Stateless, horizontally scalable
              - Authentication + Authorization enforcement point
              [COMPONENT CARD: API Server — responsibilities + ports]

         4.2b Repository Server — The Git Connector
              - Clones Git repositories
              - Generates Kubernetes manifests from Helm/Kustomize/Jsonnet
              - Caches repos locally for performance
              - Runs as an internal service (not exposed externally)
              [COMPONENT CARD: Repo Server — responsibilities + caching]

         4.2c Application Controller — The Brain
              - Continuously compares desired state (Git) vs actual state (K8s)
              - Detects drift and triggers sync (if auto-sync enabled)
              - Invokes user-defined hooks (PreSync, Sync, PostSync)
              - Manages application health assessment
              [COMPONENT CARD: App Controller — reconciliation loop]

         4.2d ApplicationSet Controller — The Bulk Manager
              - Automates creation of multiple Applications from generators
              - Generators: List, Cluster, Git, Matrix, Merge, SCM Provider, Pull Request
              - Use case: One ApplicationSet → N Applications for N environments
              [COMPONENT CARD: AppSet Controller — generators explained]

         4.2e Notifications Controller — The Messenger
              - Sends notifications on application events
              - Triggers: on-sync, on-health-degraded, on-deployed
              - Services: Slack, Email, Webhook, Teams, Telegram, Grafana
              - Templates define notification content + format
              [COMPONENT CARD: Notifications Controller — triggers + services]

         4.2f Redis — The Cache Layer
              - Caches application state, repository metadata
              - Improves performance (avoids repeated Git clones)
              - Used for inter-component communication
              - Can be replaced with external Redis for HA

Chapter 20: Introduction to Argo Workflows

    20.1  What is Argo Workflows? 🎯 CAPA
         - Container-native workflow engine for Kubernetes
         - Each step in a workflow = a container (Pod)
         - DAG (Directed Acyclic Graph) or Steps-based
         - Use cases: CI/CD pipelines, ML training, data processing, infrastructure automation
         - Argo Workflows is a separate CNCF project from ArgoCD
         [DIAGRAM: Argo ecosystem — ArgoCD (CD) + Argo Workflows + Argo Rollouts + Argo Events]

    20.2  Argo Workflows Architecture
         - Workflow Controller: Watches Workflow CRDs, creates Pods
         - Workflow CRD: Defines the workflow spec
         - Each step = a Pod that runs to completion
         - Artifact repository (S3/GCS/MinIO) for passing data between steps
         - Workflow UI: Visualize DAG execution
         [ARCHITECTURE DIAGRAM: Workflow components]
