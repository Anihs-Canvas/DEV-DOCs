    1.4  The Problems That Created Kubernetes
         - Manual deployment pain points (SSH, config drift, snowflake servers)
         - The "it works on my machine" problem
         - Scaling nightmares: Black Friday traffic spike on jobpost
         - Recovery: 3 AM crashes with nobody to restart
         [PAIN POINT CARDS: 4 real-world disaster scenarios without K8s]
         [BEFORE/AFTER DIAGRAM: Manual ops nightmare vs K8s automation]

         [4 PAIN POINTS THAT KUBERNETES SOLVES]
         ┌──────────────────────────────────────────────────────────────┐
         │  😰 PAIN POINT 1: DEPLOYMENT NIGHTMARE                      │
         │  ──────────────────────────────────────────────────────────  │
         │  WITHOUT K8s:  SSH → stop old → copy files → start new →     │
         │                repeat on 5 servers → took 2 hours!           │
         │  WITH K8s:     kubectl apply -f deployment.yaml → 30 seconds │
         │                (automatic rolling update, zero downtime)      │
         │                                                              │
         │  😰 PAIN POINT 2: 3 AM CRASHES                               │
         │  ──────────────────────────────────────────────────────────  │
         │  WITHOUT K8s:  PagerDuty alert → wake up → SSH → restart     │
         │  WITH K8s:     Pod crashes → K8s detects → auto-restarts     │
         │                You sleep through it. K8s handles recovery.   │
         │                                                              │
         │  😰 PAIN POINT 3: BLACK FRIDAY TRAFFIC SPIKE                 │
         │  ──────────────────────────────────────────────────────────  │
         │  WITHOUT K8s:  Job board gets 10x traffic → server melts     │
         │                Users see "500 Server Error" → lost revenue   │
         │  WITH K8s:     HPA detects spike → auto-scales 3→30 pods     │
         │                Users never notice → revenue protected        │
         │                                                              │
         │  😰 PAIN POINT 4: CONFIGURATION DRIFT                         │
         │  ──────────────────────────────────────────────────────────  │
         │  WITHOUT K8s:  Dev server Python 3.8, Prod Python 3.11       │
         │                "It works on my machine!" → "Not on prod!"    │
         │  WITH K8s:     Same container image runs EVERYWHERE          │
         │                Dev = Staging = Production — IDENTICAL        │
         └──────────────────────────────────────────────────────────────┘

    1.5  Introduction to Containers (Preview)
         - The shipping container analogy (the BEST way to understand containers)
         - What is a container? (simplified: an isolated package with everything)
         - Why containers changed everything
         - Relationship: Container → Docker → Kubernetes
         [SHIPPING ANALOGY ILLUSTRATION: Physical containers on a ship → Software containers on a server]
         [CONTAINER ANATOMY: What's inside a container — app + dependencies + config]

         [THE SHIPPING CONTAINER ANALOGY — How physical shipping transformed trade]
         ┌──────────────────────────────────────────────────────────────────────┐
         │  🚢 THE ANALOGY THAT EXPLAINS EVERYTHING                              │
         │                                                                      │
         │  Before 1956: Shipping was CHAOS                                      │
         │  ┌────────────────────────────────────────────────────────────────┐  │
         │  │  🧳🧳🧳  Each item had DIFFERENT sizes, shapes, and handling    │  │
         │  │  Workers spent DAYS loading/unloading each ship differently     │  │
         │  │  No standard — every port was a unique mess                     │  │
         │  └────────────────────────────────────────────────────────────────┘  │
         │                                                                      │
         │  After 1956: The STANDARD SHIPPING CONTAINER was invented            │
         │  ┌────────────────────────────────────────────────────────────────┐  │
         │  │  📦📦📦  ALL containers are SAME size (20ft/40ft)               │  │
         │  │  ANY ship can carry ANY container                                │  │
         │  │  Loading: HOURS → MINUTES (standardized cranes!)                │  │
         │  │  ANY port can handle ANY container (standardized docks!)        │  │
         │  └────────────────────────────────────────────────────────────────┘  │
         │                                                                      │
         │  SOFTWARE CONTAINERS did the SAME THING for applications:             │
         │  ┌────────────────────────────────────────────────────────────────┐  │
         │  │  BEFORE: Each app = unique setup (Python 3.8/Debian/PostgreSQL) │  │
         │  │          → "It works on MY machine!" nightmare                  │  │
         │  │                                                                  │  │
         │  │  AFTER:  Standard CONTAINER IMAGE wraps app + ALL dependencies   │  │
         │  │          → Runs ANYWHERE (laptop, server, cloud)                │  │
         │  │          → Docker = the "crane" that moves containers around     │  │
         │  │          → Kubernetes = the "port authority" managing everything │  │
         │  └────────────────────────────────────────────────────────────────┘  │
         └──────────────────────────────────────────────────────────────────────┘

         │  📦 SOFTWARE CONTAINER (anihpj example)     │
         │                                             │
         │  ┌─────────────────────────────────────┐    │
         │  │  🐍 Application:                    │    │
         │  │     Django + jobpost code            │    │
         │  │     (views.py, models.py, urls.py)   │    │

         - What is a Dockerfile? (a text file with build instructions)

         [ANNOTATED DOCKERFILE: Every instruction explained with comments and arrows]
         [LAYER CACHING DIAGRAM: How cache hits and misses work]

         [DOCKERFILE INSTRUCTION REFERENCE — 8 Key Instructions]
         ┌──────────────────────────────────────────────────────────────────────┐
         │  INSTRUCTION    │ WHAT IT DOES              │ EXAMPLE                  │
         │  ────────────── │ ───────────────────────── │ ───────────────────────  │
         │  FROM           │ Sets the base image       │ FROM python:3.11-slim    │
         │  WORKDIR        │ Sets working directory    │ WORKDIR /app             │
         │  COPY           │ Copies files from host    │ COPY requirements.txt .  │
         │  RUN            │ Executes build commands   │ RUN pip install -r ...   │
         │  ENV            │ Sets environment variable │ ENV DEBUG=False           │
         │  EXPOSE         │ Documents container port  │ EXPOSE 8000              │
         │  CMD            │ Default startup command   │ CMD ["gunicorn", ...]    │
         │  ENTRYPOINT     │ Fixed entrypoint command  │ ENTRYPOINT ["python"]    │
         │                                                                      │
         │  💡 KEY: COPY requirements BEFORE code = cache dependencies!         │
         │  💡 KEY: CMD can be overridden; ENTRYPOINT cannot                    │
         └──────────────────────────────────────────────────────────────────────┘

         [LAYER CACHING — Why order matters so much]
         ┌──────────────────────────────────────────────────────────────────────┐
         │  ❌ BAD ORDER (cache MISSES on every code change)                      │
         │  ──────────────────────────────────────────────────────────────────  │
         │  1. FROM python:3.11-slim      ← Cached ✅                           │
         │  2. COPY . .                   ← CHANGED! Cache MISS ❌              │
         │  3. RUN pip install -r req.txt ← Re-runs EVERY time! Slow! 😱        │
         │                                                                      │
         │  ✅ GOOD ORDER (cache HITS even when code changes)                     │
         │  ──────────────────────────────────────────────────────────────────  │

    5.1  The Origin Story: From Google Borg to Kubernetes
         - Google's internal container system: Borg (launched ~2003)
         - The problem: Google was the only company that could run containers at scale
         - 2014: Google open-sources Kubernetes (donated to CNCF)
         - Name: Greek for "helmsman" or "pilot" (κυβερνήτης)
         - K8s = K + 8 letters + s (the numeronym)
         [TIMELINE: 2003 Borg → 2013 Docker → 2014 K8s → 2015 CNCF → Today]

    5.2  Kubernetes Defined (Simply)

Chapter 7: Pods — The Atomic Unit of Kubernetes
--------------------------------------------------------------------------------
    7.1  What is a Pod?
         - The smallest deployable unit in Kubernetes
         - A pod = one or more containers + shared resources
         - Shared: network namespace (same IP), storage volumes, IPC
         - Pods are ephemeral — they can be created, destroyed, and replaced
         [POD ANATOMY DIAGRAM: Container(s) + shared volume + shared network + pod IP]
         [ANALOGY: Pod = a "logical host" for your containers]

    7.2  Single-Container vs Multi-Container Pods
         - Single-container pod: most common (one app per pod)
         - Multi-container pod: sidecar pattern (helper containers)
         - Real examples: app container + logging sidecar, app + proxy
         - Pods share: localhost (yes, containers in same pod use localhost!)
         [SIDE-BY-SIDE: Single-container pod vs multi-container pod diagram]

    7.3  The Pod Lifecycle
         - Pending: Pod created, waiting for node assignment or image pull
         - Running: At least one container is running
         - Succeeded: All containers terminated successfully
         - Failed: All containers terminated, at least one with error
         - CrashLoopBackOff: Container keeps crashing → K8s waits between restarts
         [LIFECYCLE STATE MACHINE DIAGRAM: States and transitions]
         [CRASHLOOPBACKOFF EXPLAINED: Why it happens and what it means]

         [POD LIFECYCLE STATE MACHINE]
         ┌──────────────────────────────────────────────────────────────────────┐
         │                        POD LIFECYCLE                                  │
         │                                                                      │
         │                              ┌──────────┐                            │
         │                              │  Pending  │ ← Pod created, waiting     │
         │                              │ (0/1)     │   for node + image pull   │
         │                              └─────┬─────┘                            │
         │                                    │ Image pulled, containers start  │
         │                                    ▼                                  │
         │  ┌──────────┐               ┌──────────┐                             │
         │  │ CrashLoop│◀────crash─────│ Running  │─────crash─────▶┌──────────┐ │
         │  │ BackOff  │   → restart  │ (1/1)    │   → restart   │  Failed   │ │
         │  │ (waiting)│              │          │               │ (error)   │ │
         │  └──────────┘              └─────┬─────┘               └──────────┘ │
         │                                  │ completion (exit 0)               │
         │                                  ▼                                  │

Chapter 9: etcd — The Cluster's Brain Database
--------------------------------------------------------------------------------
    9.1  What is etcd?
         - A distributed, reliable key-value store
         - Stores ALL Kubernetes cluster data (config, state, secrets)
         - The "source of truth" for the entire cluster
         - Developed by CoreOS, now part of CNCF
         [etcd POSITION DIAGRAM: Central data store — everything reads/writes through API server]

    9.2  How etcd Works
         - Key-value model (like a super-reliable dictionary)
         - Distributed consensus (Raft algorithm) — all members agree on data
         - Leader election — one etcd member is the leader, handles all writes
         - Reads can be served by any member
         - Quorum: majority of members must be healthy (N/2 + 1)
         [RAFT CONSENSUS DIAGRAM: Leader → Followers — write flow]
         [QUORUM DIAGRAM: 3-node etcd — 2 must be up; 5-node — 3 must be up]

         [RAFT CONSENSUS — How etcd Keeps Data Consistent]
         ┌──────────────────────────────────────────────────────────────────────┐
         │  🗄️ RAFT CONSENSUS IN ACTION (3-node etcd cluster)                     │
         │                                                                      │
         │  WRITE FLOW:                                                          │
         │  ┌──────────────────────────────────────────────────────────────┐    │
         │  │  1. Client sends WRITE to Leader (or any member → forwarded)  │    │
         │  │  2. Leader appends entry to its log                          │    │
         │  │  3. Leader sends AppendEntries to ALL followers               │    │
         │  │  4. Followers acknowledge: "Got it!"                          │    │
         │  │  5. MAJORITY (2/3) acknowledged → Leader commits entry        │    │
         │  │  6. Leader tells followers: "Commit this!"                    │    │
         │  │  7. Leader responds to client: "Write successful!"            │    │
         │  └──────────────────────────────────────────────────────────────┘    │
         │                                                                      │
         │  QUORUM REQUIREMENT:                                                  │
         │  ──────────────────                                                   │
         │  ┌──────────────────────────────────────────────────────────────┐    │
         │  │  3-node etcd: Quorum = 2 (can lose 1 node)                   │    │
         │  │  ┌────┐   ┌────┐   ┌────┐                                     │    │
         │  │  │ LDR│──▶│ F1 │──▶│ F2 │   ✅ LDR+F1 = 2/3 = Quorum        │    │
         │  │  │ ✅ │   │ ✅ │   │ ❌ │   💀 F2 failed — cluster still works │    │
         │  │  └────┘   └────┘   └────┘                                     │    │
         │  │                                                                │    │
         │  │  5-node etcd: Quorum = 3 (can lose 2 nodes)                   │    │
         │  │  More fault-tolerant but more overhead (5 copies of all data) │    │
         │  └──────────────────────────────────────────────────────────────┘    │
         │                                                                      │
         │  🎯 KCNA TIP: etcd = THE most critical component. If etcd loses       │
         │     quorum, the ENTIRE cluster stops working (no writes possible)     │
         └──────────────────────────────────────────────────────────────────────┘

    9.3  Why etcd Matters (Even for KCNA)
         - If etcd fails, the cluster has amnesia — it forgets what's running
         - etcd backup is THE most critical cluster maintenance task
         - etcd performance = cluster performance
         - etcd runs on control plane nodes (usually 3 or 5 for HA)
         [etcd FAILURE SCENARIO: What happens when etcd loses quorum]
         [HA CONFIGURATION: 3-node vs 5-node etcd cluster tradeoffs]

    9.4  What etcd Stores
         - All Kubernetes objects: pods, services, deployments, configmaps, secrets
         - Node information and health status
         - Cluster configuration
         - Service account tokens and certificates
         - Basically: everything you create in the cluster

Chapter 12: Scheduling — How Kubernetes Decides Where Pods Run
--------------------------------------------------------------------------------
    12.1  The Scheduler's Job
         - Watches for new pods with no assigned node
         - Evaluates ALL nodes against pod requirements
         - Selects the BEST node for each pod
         - Two phases: Filtering (which nodes CAN run it?) + Scoring (which is BEST?)
         [SCHEDULER DECISION FLOW: New Pod → Filter Nodes → Score Nodes → Assign Best Node]
         [FILTERING CRITERIA LIST: Resource availability, taints, node selectors, affinity]

    12.2  Resource Requests and Limits
         - Requests: minimum resources a container needs (scheduler uses this)
         - Limits: maximum resources a container can use (enforced by kubelet)
         - CPU: measured in millicores (100m = 0.1 CPU core)
         - Memory: measured in bytes (Mi, Gi)
         - Why they matter: prevent noisy neighbors, ensure fair scheduling
         [REQUEST vs LIMIT DIAGRAM: Pod with 500m request, 1000m limit — visual bar]
         [OVERCOMMIT SCENARIO: What happens when pods use more than requested]

    12.3  Node Selectors and Affinity
         - nodeSelector: simple key-value — "only run on nodes with disk=ssd"
         - nodeAffinity: more expressive — "prefer or require nodes with..."
         - podAffinity: co-locate pods — "run near the cache pod"
         - podAntiAffinity: spread pods apart — "don't run on same node"
         [AFFINITY VISUAL: Pods placed based on rules — node labels determine placement]
         [PRODUCTION PATTERN: AntiAffinity ensures pods spread across nodes for HA]

    12.4  Taints and Tolerations — VIP Access for Nodes
         - Taint: "No pods allowed here!" (applied to node)
         - Toleration: "I can handle that taint" (added to pod)
         - Use case: dedicated GPU nodes, special hardware, isolated workloads
         - Default control-plane taint: NoSchedule (prevents normal pods on CP)
         [TAINT-TOLERATION MATCHING: Tainted node + tolerant pod = allowed]
         [ANALOGY: Taint = "No Entry" sign; Toleration = "VIP Pass"]

Chapter 13: Other Workload Resources — Jobs, CronJobs, DaemonSets, StatefulSets
--------------------------------------------------------------------------------
    13.1  Jobs — Run Once, Then Done
         - Job: creates one or more pods, ensures they complete successfully
         - Use case: Django database migrations, batch processing, one-time scripts
         - Completion count: how many successful completions needed
         - Parallelism: how many pods can run simultaneously
         [JOB LIFECYCLE DIAGRAM: Create → Run → Complete → Done (pod stays for logs)]
         [EXAMPLE: anihpj migration job — runs python manage.py migrate]

    13.2  CronJobs — Run on a Schedule
         - Like a Job, but runs on a cron schedule
         - "Run database backup every day at 2 AM"
         - Cron syntax: minute hour day month weekday
         - Use case: periodic cleanup, report generation, health checks
         [CRONJOB TIMELINE: Job runs at scheduled intervals — periodic execution]

    13.3  DaemonSets — One Pod Per Node
         - Ensures ALL (or some) nodes run a copy of a pod
         - Use case: log collectors, monitoring agents, storage daemons, network plugins
         - As nodes are added, pods are automatically added
         - As nodes are removed, pods are garbage collected
         [DAEMONSET VISUAL: 5 nodes = 5 DaemonSet pods, one per node]

    13.4  StatefulSets — For Stateful Applications
         - Unlike Deployments, pods have stable, unique identities
         - Each pod gets: stable hostname (pod-0, pod-1, pod-2), stable storage
         - Ordered deployment and scaling (0→1→2, reverse for scale-down)
         - Use case: databases (PostgreSQL), message queues, distributed systems
         [STATEFULSET vs DEPLOYMENT COMPARISON: Identity, storage, ordering differences]
         [EXAMPLE: Running PostgreSQL on K8s with StatefulSet]

Chapter 14: Kubernetes Networking Fundamentals
--------------------------------------------------------------------------------
    14.1  The Kubernetes Networking Model
         - Every pod gets its own IP address (flat, cluster-wide network)
         - Pods on any node can communicate with pods on any other node
         - No NAT (Network Address Translation) between pods
         - Pods see each other's real IP addresses
         [NETWORK MODEL DIAGRAM: Pod-to-pod communication across nodes]
         [IP ADDRESSING: Pod IP vs Node IP vs Service IP — what each means]

    14.2  CNI — Container Network Interface
         - CNI = the plugin system for Kubernetes networking
         - Popular CNI plugins: Calico, Flannel, Cilium, Weave
         - What CNI plugins do: assign IPs, set up routes, enforce policies
         - The CNI plugin is what makes "all pods can talk" possible
         [CNI PLUGIN COMPARISON TABLE: Calico vs Flannel vs Cilium — features, performance]

    14.3  DNS in Kubernetes (CoreDNS)
         - Pods can find each other by NAME (not IP)
         - Service DNS: my-service.my-namespace.svc.cluster.local
         - Pod DNS: pod-ip-address.namespace.pod.cluster.local
         - CoreDNS runs as a deployment in kube-system
         [DNS RESOLUTION DIAGRAM: Pod → DNS Query → CoreDNS → Service IP]
         [DNS NAME BREAKDOWN: service.namespace.svc.cluster.local — each part explained]

    14.4  Network Policies — The Firewall
         - Control which pods can talk to which pods
         - Ingress rules: who can call ME?
         - Egress rules: who can I call?
         - Default: all traffic allowed (unless NetworkPolicy restricts)
         - KCNA focus: understand the CONCEPT (not writing complex YAML)
         [NETWORK POLICY VISUAL: Allow/block rules between pods — like a firewall]
         [EXAMPLE: Only allow anihpj-web to call anihpj-api — block everything else]

Chapter 15: Services — How Users and Pods Find Each Other
--------------------------------------------------------------------------------
    15.1  The Problem Services Solve
         - Pods are ephemeral — they get new IPs when replaced
         - You can't rely on pod IPs — they change!
         - Services provide a STABLE IP and DNS name
         - Service IP never changes — pods come and go behind it
         [SERVICE CONCEPT DIAGRAM: Stable Service IP → routes to whichever pods are alive]
         [WITH/WITHOUT SERVICE: Pod IP changes → broken connections vs Service → always works]

Chapter 16: Volumes and Persistent Storage
--------------------------------------------------------------------------------
    16.1  The Storage Problem
         - Containers are ephemeral — data disappears when container stops
         - But your database needs to KEEP data across restarts!
         - Solution: Volumes — storage that outlives containers
         [EPHEMERAL STORAGE PROBLEM: Container dies → data gone — visual]
         [VOLUME SOLUTION: Container → Volume (separate lifecycle) — data survives]

    16.2  Volume Types Overview
         - emptyDir: temporary storage (deleted with pod) — good for cache/scratch
         - hostPath: mounts a file/directory from the node (use sparingly)
         - PersistentVolume (PV): cluster-wide storage resource
         - PersistentVolumeClaim (PVC): a request for storage
         - ConfigMap/Secret: inject configuration and sensitive data
         [VOLUME TYPE COMPARISON TABLE: Lifetime, use case, persistence]

    16.3  PersistentVolumes (PV) and PersistentVolumeClaims (PVC)
         - PV: a piece of storage in the cluster (like a parking spot)
         - PVC: a request for storage (like "I need a parking spot")
         - Dynamic provisioning: StorageClass + PVC = automatic PV creation
         - Access modes: ReadWriteOnce (RWO), ReadOnlyMany (ROX), ReadWriteMany (RWX)
         [PV-PVC BINDING DIAGRAM: PVC → matches → PV → bound → pod can use]
         [STORAGE CLASS FLOW: PVC → StorageClass → Dynamic PV creation → Binding]

         [PV-PVC BINDING — The Storage Request Flow]
         ┌──────────────────────────────────────────────────────────────────────┐
         │  💾 PV-PVC BINDING — How Pods Get Storage                              │
         │                                                                      │
         │  STEP 1: ADMIN CREATES PV (or StorageClass creates it dynamically)     │
         │  ┌──────────────────────────────────────────────────────────────┐    │
         │  │  PV: "storage-01"                                             │    │
         │  │  • Capacity: 10Gi                                             │    │

         │  │  • Request: 5Gi                                               │    │
         │  │  • Access: ReadWriteOnce                                      │    │
         │  │  • Status: Pending ← looking for matching PV                 │    │
         │  └──────────────────────────────────────────────────────────────┘    │
         │       │                                                              │
         │       ▼                                                              │

         │  │  ✅ PVC requests 5Gi ≤ PV has 10Gi (sufficient capacity)      │    │

    16.4  StorageClasses — Storage on Demand
         - Define "classes" of storage: fast-ssd, slow-hdd, encrypted
         - Provisioner: the plugin that creates storage (AWS EBS, GCE PD, NFS)
         - Dynamic provisioning: PVC + StorageClass = storage created automatically
         - Reclaim policy: what happens when PVC is deleted (Retain, Delete, Recycle)

         - Application code: uses Docker image (doesn't need persistence)
         - Static files: served from container image or CDN

Chapter 17: ConfigMaps and Secrets — Configuration Management
--------------------------------------------------------------------------------
    17.1  Why Separate Configuration from Code?
         - Code changes rarely; config changes often
         - Same Docker image, different config for dev/staging/prod
         - Without separation: rebuild image for every config change!
         - With K8s: change ConfigMap → restart pods → new config applied
         [IMAGE + CONFIG DIAGRAM: Same anihpj:v1 image, different ConfigMap per environment]
         [BEFORE/AFTER: Rebuild image vs Update ConfigMap]

    17.2  ConfigMaps — Non-Sensitive Configuration
         - Store: database URLs, feature flags, environment names, API endpoints
         - Created from: literal values, files, or directories
         - Consumed as: environment variables, command-line arguments, or volume mounts
         - Example: anihpj database URL, DEBUG mode, ALLOWED_HOSTS
         [CONFIGMAP FLOW: Create → Mount as env vars → App reads settings → pod runs]
         [REAL EXAMPLE: anihpj ConfigMap with Django settings]

    17.3  Secrets — Sensitive Configuration
         - Store: passwords, API keys, TLS certificates, tokens
         - Base64 encoded (NOT encrypted! Use encryption at rest for production)
         - Types: Opaque (generic), kubernetes.io/tls, docker-registry
         - KCNA: understand that Secrets exist — CKA covers deeper security
         [SECRET vs CONFIGMAP COMPARISON: What goes where]

    17.4  Environment Variables in Kubernetes
         - How pods get configuration: env, envFrom, volume mounts
         - env: individual key-value pairs
         - envFrom: import all keys from a ConfigMap/Secret
         - KCNA focus: understanding the concept, not writing YAML
         [ENVIRONMENT VARIABLE FLOW: ConfigMap/Secret → Pod container → Application code]

Chapter 18: Kubernetes Security Fundamentals
--------------------------------------------------------------------------------
    18.1  The 4 Cs of Cloud Native Security
         - Cloud (or Co-Lo/Corporate Datacenter) — infrastructure security
         - Cluster — Kubernetes component security
         - Container — image security, least privilege
         - Code — application-level security
         [4Cs PYRAMID DIAGRAM: Cloud → Cluster → Container → Code — layered defense]
         [KCNA TIP: Each layer assumes the layer below is secure]

    18.2  Authentication — Who Are You?
         - Normal users: managed outside K8s (OIDC, client certificates)
         - Service accounts: for pods and services inside the cluster
         - Every pod gets a service account (default unless specified)
         - KCNA: understand the DIFFERENCE between user and service account
         [AUTHENTICATION FLOW: User/SvcAccount → API Server → Verify Identity → Allow]

    18.3  RBAC — Role-Based Access Control
         - Role: defines permissions WITHIN a namespace (what you can do)
         - ClusterRole: defines permissions ACROSS the cluster
         - RoleBinding: gives a Role to a user/service account (who can do it)
         - Principle of least privilege: give minimum permissions needed
         [RBAC RELATIONSHIP DIAGRAM: User → RoleBinding → Role → Permissions]
         [EXAMPLE: anihpj-api service account + role that allows GET on pods in anihpj ns]

         [RBAC — How Roles, Bindings, and Subjects Connect]
         ┌──────────────────────────────────────────────────────────────────────┐
         │  🔐 RBAC — 4 Key Objects to Remember for KCNA                         │
         │                                                                      │
         │  ┌─────────────┐     ┌──────────────┐     ┌─────────────────────┐   │
         │  │ 👤 SUBJECT   │     │ 🔗 BINDING    │     │ 📋 ROLE             │   │
         │  │ (Who?)      │────▶│ (Connects)   │────▶│ (What can they do?) │   │
         │  │             │     │              │     │                     │   │
         │  │ • User      │     │ RoleBinding  │     │ Role (namespaced)   │   │
         │  │ • Group     │     │ (namespace)  │     │ • get pods          │   │
         │  │ • Service   │     │              │     │ • list deployments  │   │
         │  │   Account   │     │ ClusterRole  │     │ • create services   │   │
         │  │             │     │ Binding      │     │                     │   │
         │  │             │     │ (cluster-wide)│     │ ClusterRole        │   │
         │  │             │     │              │     │ (cluster-wide)      │   │
         │  │             │     │              │     │ • get nodes         │   │
         │  │             │     │              │     │ • list namespaces   │   │
         │  └─────────────┘     └──────────────┘     └─────────────────────┘   │
         │                                                                      │
         │  EXAMPLE — anihpj-api Service Account:                                │
         │  ┌──────────────────────────────────────────────────────────────┐    │
         │  │ # Create a Role that allows reading pods in anihpj namespace  │    │
         │  │ apiVersion: rbac.authorization.k8s.io/v1                     │    │
         │  │ kind: Role                                                    │    │
         │  │ metadata: { namespace: anihpj, name: pod-reader }            │    │
         │  │ rules:                                                        │    │
         │  │ - apiGroups: [""]                                            │    │
         │  │   resources: ["pods"]                                        │    │
         │  │   verbs: ["get", "list"]                                     │    │
         │  │                                                               │    │
         │  │ # Bind the Role to the anihpj-api ServiceAccount              │    │
         │  │ kind: RoleBinding                                             │    │
         │  │ metadata: { namespace: anihpj, name: read-pods }             │    │
         │  │ subjects:                                                     │    │
         │  │ - kind: ServiceAccount, name: anihpj-api, namespace: anihpj  │    │
         │  │ roleRef: { kind: Role, name: pod-reader, apiGroup: rbac... } │    │
         │  └──────────────────────────────────────────────────────────────┘    │
         │                                                                      │
         │  🎯 KCNA TIP: Role = namespace-scoped; ClusterRole = cluster-wide    │
         └──────────────────────────────────────────────────────────────────────┘

    18.4  Security Context — Pod-Level Security
         - Run containers as non-root user (securityContext.runAsNonRoot: true)
         - Drop Linux capabilities (remove unnecessary privileges)
         - Read-only root filesystem (prevents writing to container filesystem)
         - These are BASIC security hygiene — always configure them
         [SECURITY CONTEXT COMPARISON: Insecure pod vs Secure pod — side by side]
         [PRIVILEGE ESCALATION PREVENTION: What capabilities to drop]

    18.5  Pod Security Standards
         - Privileged: unrestricted (NOT for production!)
         - Baseline: minimal restrictions, prevents known privilege escalations
         - Restricted: heavily restricted, follows pod hardening best practices
         - KCNA: know the three levels and their purpose
         [PSS LEVELS DIAGRAM: Privileged → Baseline → Restricted — increasing security]

Chapter 19: Observability — Seeing Inside Your Cluster
--------------------------------------------------------------------------------
    19.1  What is Observability?
         - The ability to understand what's happening inside your system
         - Three pillars: Logging, Metrics, Tracing
         - "You can't fix what you can't see"
         - Kubernetes gives you the foundation — you add the tools
         [OBSERVABILITY PILLARS TRIANGLE: Logging ⇄ Metrics ⇄ Tracing]

    19.2  Logging — What Your Apps Are Saying
         - Container logs: captured from stdout/stderr
         - kubectl logs pod-name — the simplest way to see logs
         - Log aggregation: Fluentd, Elasticsearch, Loki (for production)
         - KCNA: know kubectl logs and the concept of log aggregation

    19.3  Metrics — Measuring Your System

         - Metrics Server: lightweight cluster-wide metrics aggregator
         - Prometheus: the standard for Kubernetes metrics collection
         - Grafana: dashboards and visualization

    20.2  GitOps — Git as the Single Source of Truth
         - Declarative configuration stored in Git
         - Git is the control center — all changes via pull requests
         - Tools: ArgoCD, Flux — watch Git repo, sync to cluster
         - Benefits: audit trail, easy rollback (git revert), collaboration
         [GITOPS LOOP: Developer → Git Push → ArgoCD detects → Syncs to K8s → Cluster matches Git]

    20.3  Deployment Strategies
         - Recreate: stop old → start new (downtime!)
         - Rolling Update: replace pods one at a time (zero downtime)
         - Blue-Green: two identical environments, switch traffic (instant rollback)
         - Canary: send small % of traffic to new version (test before full rollout)
         [4 DEPLOYMENT STRATEGY CARDS: Visual diagrams for each strategy]
         [STRATEGY DECISION MATRIX: Which strategy for which risk level?]

         [4 DEPLOYMENT STRATEGIES — Visual Comparison]
         ┌──────────────────────────────────────────────────────────────────────┐
         │  1️⃣ RECREATE — Stop ALL old, start ALL new (DOWNTIME!)                 │
         │  ┌──────────────────────────────────────────────────────────────┐    │
         │  │  T=0: [v1][v1][v1] → T=1: STOP ALL → T=30: [v2][v2][v2]     │    │
         │  │  ❌ DOWNTIME during switch! Users see errors                   │    │
         │  │  ✅ Simple, fast, good for dev environments                    │    │
         │  └──────────────────────────────────────────────────────────────┘    │
         │                                                                      │
         │  2️⃣ ROLLING UPDATE — Replace pods one at a time (ZERO DOWNTIME)        │
         │  ┌──────────────────────────────────────────────────────────────┐    │
         │  │  T=0: [v1][v1][v1]                                           │    │
         │  │  T=10: [v2][v1][v1][v1]  (add 1 new, keep 3 old)            │    │
         │  │  T=20: [v2][v2][v1][v1]  (remove 1 old, add 1 new)          │    │

         │  │  BLUE (v1):  [v1][v1][v1] ← LIVE traffic                     │    │

         │  │  SWITCH: Service selector → BLUE to GREEN                    │    │

Appendix B: Kubernetes Terminology Glossary
    B.1  Core Concepts (A-Z)
         - API Server: Front door to K8s — ALL communication goes through it
         - Cluster: A set of nodes running containerized apps managed by K8s
         - ConfigMap: Store non-sensitive configuration (env vars, settings)
         - Container: Isolated package with app + all dependencies
         - Control Plane: The "brain" — manages the cluster (API server, etcd, scheduler)
         - DaemonSet: Ensures one pod runs on every node (or selected nodes)
         - Deployment: Manages ReplicaSets — handles rolling updates, scaling
         - etcd: Distributed key-value store — the cluster's memory/database
         - Ingress: HTTP/HTTPS routing rules for external access
         - Job: Creates pods that run to completion (one-time tasks)
         - kubelet: Agent on every node — ensures containers are running
         - kubectl: CLI tool for talking to the Kubernetes API
         - Namespace: Virtual cluster within a physical cluster (isolation)
         - Node: A machine (physical or VM) in the cluster
         - Pod: Smallest deployable unit — one or more containers
         - PersistentVolume (PV): Cluster-wide storage resource
         - PersistentVolumeClaim (PVC): Request for storage by a user
         - ReplicaSet: Maintains a stable set of replica pods
         - Secret: Store sensitive data (passwords, tokens, keys)
         - Service: Stable network endpoint for accessing pods
         - ServiceAccount: Identity for pods (used for API access)
         - StatefulSet: For stateful apps — stable pod identities + storage
         - StorageClass: Defines classes of storage (fast, slow, encrypted)
         - Volume: Storage that outlives individual containers
    B.2  Acronyms and Abbreviations
         - K8s: Kubernetes (K + 8 letters + s)
         - CNCF: Cloud Native Computing Foundation
         - CNI: Container Network Interface (networking plugins)
         - CRI: Container Runtime Interface (runtime plugins)
         - CSI: Container Storage Interface (storage plugins)
         - CRD: Custom Resource Definition (extend K8s API)
         - RBAC: Role-Based Access Control
         - PVC: PersistentVolumeClaim
         - PV: PersistentVolume
         - HPA: Horizontal Pod Autoscaler
         - VPA: Vertical Pod Autoscaler
         - OCI: Open Container Initiative
         - PSS: Pod Security Standards
         - GitOps: Git-based operations (Git as single source of truth)
         - IaC: Infrastructure as Code
         - CI/CD: Continuous Integration / Continuous Delivery
         - mTLS: Mutual TLS (two-way certificate verification)
         - SPIFFE: Secure Production Identity Framework For Everyone
         - SVID: SPIFFE Verifiable Identity Document
    B.3  Common Confusions Clarified
         - Pod ≠ Container: Pod CONTAINS containers (1+)
         - Service ≠ Ingress: Service = L4 routing; Ingress = L7 HTTP routing
         - Deployment ≠ StatefulSet: Deployment = stateless; StatefulSet = stateful
         - ConfigMap ≠ Secret: ConfigMap = non-sensitive; Secret = sensitive
         - NodePort ≠ LoadBalancer: NodePort = node IP:port; LB = cloud external IP
         - etcd ≠ any regular DB: etcd = distributed consensus key-value store
