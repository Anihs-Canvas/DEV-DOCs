    CAPA EXAM STRATEGY — TOP 10 MISTAKES TO AVOID
    ─────────────────────────────────────────────
    ┌──────────────────────────────────────────────────────────────┐
    │  ❌ COMMON MISTAKES                 ✅ WHAT TO DO INSTEAD    │
    │                                                              │
    │  1. Forgetting to check Argo CD    ALWAYS verify: argocd     │
    │     context/session first          context (which cluster)   │
    │                                                              │
    │  2. Writing YAML from scratch      Use argocd app create     │
    │     for Application manifests      --dry-run or kubectl      │
    │                                     create --dry-run -o yaml │
    │                                                              │
    │  3. Not verifying sync status      ALWAYS: argocd app get    │
    │     after applying changes         <app> to confirm SYNCED   │
    │                                                              │
    │  4. Confusing Workflow and         WorkflowTemplate = reuse, │
    │     WorkflowTemplate purposes      Workflow = one-time run   │
    │                                                              │
    │  5. Ignoring sync waves causing    Use wave annotations:     │
    │     dependency deployment failures argocd.argoproj.io/sync-  │
    │                                     wave: "0" (or -1, 1...)  │
    │                                                              │
    │  6. Not setting resource limits    Always set limits on      │
    │     on workflow pods (OOM kills)   Workflow/WorkflowTemplate │
    │                                                              │
    │  7. Using Rollout without          Rollout needs activeService│
    │     activeService & previewService & previewService defined  │
    │                                                              │
    │  8. EventSource webhook not        Check: kubectl get events │
    │     receiving — no EventBus        -n argo-events, verify    │
    │                                     EventBus pod is running   │
    │                                                              │
    │  9. Not bookmarking Argo docs      Before exam: bookmark     │
    │     pages before the exam          argoproj.github.io docs   │
    │                                                              │
    │  10. Skipping hands-on labs        killer.sh + own cluster   │
    │      for memorization only         practice > memorization   │
    └──────────────────────────────────────────────────────────────┘

Chapter 1: What is GitOps? (The Philosophy Behind Argo)
--------------------------------------------------------------------------------
    1.1  The Problem Before GitOps
         - Traditional deployment: manual SSH + scripts + human error
         - Configuration drift: "It worked in staging, why not in prod?"
         - Audit nightmare: "Who changed what and when?"
         - The anihpj pain point: deploying jobpost manually at 2 AM
         [PAIN POINT CARDS — "Without GitOps" scenario]
         ┌────────────────────────────────────────────────────┐
         │ 😰 Deploying anihpj WITHOUT GitOps                 │
         │                                                    │
         │  • Developer: "I ran the deploy script"            │
         │  • Ops: "The script failed halfway, DB migrated    │
         │    but new code didn't deploy"                     │
         │  • Manager: "Which version is in production?"      │
         │  • Everyone: "Let's check the server... oh wait"   │
         │  • RESULT: 45 min downtime, unknown state          │
         └────────────────────────────────────────────────────┘

    1.2  GitOps Defined — The 4 Principles
         - Principle 1: Declarative — Everything described as code (YAML)
         - Principle 2: Versioned & Immutable — Git is the single source of truth
         - Principle 3: Pull Automatically — Agents pull desired state, don't push
         - Principle 4: Continuously Reconciled — Software agents ensure actual = desired
         [ICON GRID: 4 principle cards with emoji icons]
         ┌──────────────┐  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐
         │ 📋 Declarative│  │ 📚 Versioned │  │ ⬇️ Pull Based │  │ 🔄 Reconciled│
         │ Everything    │  │ Git = single │  │ Agents pull   │  │ Actual state  │
         │ described     │  │ source of    │  │ desired state │  │ constantly    │
         │ as code/YAML  │  │ truth        │  │ (not push)    │  │ = desired     │
         └──────────────┘  └──────────────┘  └──────────────┘  └──────────────┘

Chapter 9: Introduction to Argo Workflows
--------------------------------------------------------------------------------
    9.1  What is Argo Workflows?
         - Container-native workflow engine for Kubernetes
         - Each step runs in its own container
         - DAGs (Directed Acyclic Graph), Steps, and parallel execution
         - Use cases: CI/CD, data processing, ML pipelines, infrastructure automation
         [CONCEPT DIAGRAM: Workflow = DAG of containers]

    9.2  Why Not Just Use Kubernetes Jobs?
         - Jobs are linear, Workflows are graphs
         - Workflows support parallelism, conditionals, loops
         - Workflows have artifact passing between steps
         - Workflows have richer output, retry, and timeout control
         [COMPARISON TABLE: Kubernetes Job vs Argo Workflow]
         ┌────────────────────────────────────────────────────────────┐
         │  KUBERNETES JOB vs ARGO WORKFLOW                           │
         │                                                            │
         │  ┌─────────────────┬─────────────────┬───────────────────┐ │
         │  │ FEATURE         │ K8S JOB         │ ARGO WORKFLOW     │ │
         │  ├─────────────────┼─────────────────┼───────────────────┤ │
         │  │ Structure       │ Linear (1 task) │ DAG / Steps       │ │
         │  ├─────────────────┼─────────────────┼───────────────────┤ │
         │  │ Parallelism     │ Fixed completions│ Dynamic fan-out  │ │
         │  ├─────────────────┼─────────────────┼───────────────────┤ │
         │  │ Dependencies    │ ❌ No            │ ✅ depends: [...] │ │
         │  ├─────────────────┼─────────────────┼───────────────────┤ │
         │  │ Conditionals    │ ❌ No            │ ✅ when: <expr>  │ │
         │  ├─────────────────┼─────────────────┼───────────────────┤ │
         │  │ Loops           │ ❌ No            │ ✅ withItems/Seq  │ │
         │  ├─────────────────┼─────────────────┼───────────────────┤ │
         │  │ Artifact Passing│ ❌ No            │ ✅ S3/GCS/MinIO   │ │
         │  ├─────────────────┼─────────────────┼───────────────────┤ │
         │  │ Retry Strategy  │ Basic (backoff) │ ✅ Exponential +  │ │
         │  │                 │                 │ custom policies   │ │
         │  ├─────────────────┼─────────────────┼───────────────────┤ │
         │  │ Scheduling      │ CronJob         │ CronWorkflow      │ │
         │  ├─────────────────┼─────────────────┼───────────────────┤ │
         │  │ UI              │ ❌ No native    │ ✅ Built-in web   │ │
         │  ├─────────────────┼─────────────────┼───────────────────┤ │

Chapter 14: Introduction to Progressive Delivery
--------------------------------------------------------------------------------
    14.1  The Problem with Kubernetes Deployments
          - Standard Deployment: all-or-nothing rollout
          - Risk: A bad version affects ALL users instantly
          - No way to test with a small percentage first
          [PAIN POINT CARDS: Risks of standard deployments]

    14.2  What is Progressive Delivery?
          - Gradually shift traffic to new version
          - Monitor for errors before full rollout
          - Automated rollback if problems detected
          [DIAGRAM: Progressive delivery — 10% → 25% → 50% → 100%]

    14.3  Blue-Green Deployments
          - Blue = current/stable, Green = new version
          - Instant cutover (switch service selector)
          - Instant rollback (switch back to Blue)
          [DIAGRAM: Blue-Green deployment flow]
          ┌────────────────────────────────────────────────────────────┐
          │  BLUE-GREEN DEPLOYMENT                                     │
          │                                                            │
          │  BEFORE:                     AFTER CUTOVER:                │
          │  ┌─────────┐                ┌─────────┐ inactive          │
          │  │ BLUE (v1)│◀── traffic    │ BLUE (v1)│                  │
          │  │ 3 pods  │                │ 3 pods  │                  │
          │  └─────────┘                └─────────┘                   │
          │  ┌─────────┐                ┌─────────┐ active            │
          │  │GREEN (v2)│ inactive      │GREEN (v2)│◀── traffic      │
          │  │ 3 pods  │                │ 3 pods  │                  │
          │  └─────────┘                └─────────┘                   │
          │                                                            │
          │  ⏱️ Cutover: ~1 second (swap selector label)               │
          │  ↩️ Rollback: Swap label back (instant)                    │
          └────────────────────────────────────────────────────────────┘

    14.4  Canary Deployments
          - Send small percentage to new version
          - Increase gradually while monitoring
          - Auto-rollback if error rate exceeds threshold
          [DIAGRAM: Canary deployment stages]
          ┌────────────────────────────────────────────────────────────┐
          │  CANARY DEPLOYMENT — Gradual Traffic Shift                  │
          │                                                            │
          │  TIME ──────────────────────────────────────────────▶      │
          │                                                            │
          │  STEP 1: 10% canary     STEP 2: 25% canary                │
          │  ┌─────────────────┐    ┌─────────────────┐               │
          │  │ ██░░░░░░░░░░░░░ │    │ █████░░░░░░░░░░ │               │
          │  │ v2 ░░░░░░░░v1░░│    │  v2  ░░░░░v1░░░ │               │
          │  └─────────────────┘    └─────────────────┘               │
          │  ⏱️ Wait 30s             ⏱️ Wait 2 min                     │
          │  ✅ Check error rate     ✅ Check latency                  │
          │                                                            │
          │  STEP 3: 50% canary     STEP 4: 100% rollout              │
          │  ┌─────────────────┐    ┌─────────────────┐               │
          │  │ ██████████░░░░░ │    │ ███████████████ │               │
          │  │    v2   ░░v1░░ │    │      v2 (all)   │               │
          │  └─────────────────┘    └─────────────────┘               │
          │  ⏱️ Wait 5 min            ✅ v2 fully deployed              │
          │  ✅ Check all metrics                                      │
          │                                                            │
          │  AT ANY STEP: If error rate > 5% → AUTO-ROLLBACK to v1    │
          │                                                            │

Appendix F: anihpj/jobpost — Complete Manifests (Your CAPA Reference)
    ═══════════════════════════════════════════════════════════════
    ALL YAML files needed to deploy anihpj/jobpost Django app
    using every Argo tool. Use as CAPA exam reference!
    ═══════════════════════════════════════════════════════════════
    F.1  Dockerfile — Multi-stage build for anihpj
         python:3.12-slim → pip install -r requirements.txt →
         copy code → collectstatic → gunicorn on port 8000
         [Full annotated Dockerfile in Chapter 2.6]

    F.2  K8s Base Manifests
         deployment.yaml: image anihpj:v1.0, port 8000, liveness
         probe /health/, readiness probe /ready/, resources limits
         service.yaml: ClusterIP port 80→8000, selector app=anihpj
         configmap.yaml: DJANGO_SETTINGS_MODULE, DB_HOST, DEBUG
         secret.yaml: DB_PASSWORD (base64), SECRET_KEY (base64)
         namespace.yaml: anihpj-dev, anihpj-staging, anihpj-prod

    F.3  Kustomize Layout (base + overlays)
         base/ → common resources; overlays/dev/ → 1 replica;
         overlays/staging/ → 2 replicas; overlays/prod/ → 5 replicas
         + resource limits (CPU: 500m-2000m, Mem: 512Mi-2Gi)
         + configmap-patch.yaml per environment

    F.4  Argo CD Application YAMLs (3 files)
         anihpj-dev.yaml → source path overlays/dev, dest ns anihpj-dev
         anihpj-staging.yaml → source path overlays/staging
         anihpj-prod.yaml → source path overlays/prod
         All with: syncPolicy.automated.prune=true, selfHeal=true

    F.5  Argo CD ApplicationSet (1 file → generates 3 Applications)
         Generator: List [dev, staging, prod]
         Template: source path overlays/{{env}}, dest ns anihpj-{{env}}
         Matrix option: env × region = 6+ Applications

    F.6  Argo Workflows — CI Pipeline WorkflowTemplate
         DAG: clone anihpj → parallel(unit tests, lint, SAST) →
         docker build -t registry.io/anihpj:{{version}} →
         docker push → update GitOps repo (commit new image tag)
         Artifacts: test-results.json, lint-report.txt

    F.7  Argo Workflows — DB Migration CronWorkflow
         schedule: "0 2 * * *" (2 AM nightly)
         Steps: pg_dump backup → python manage.py migrate →
         python manage.py check --deploy → Slack notification
         concurrencyPolicy: Forbid, historyLimit: 7

    F.8  Argo Rollouts — Canary Rollout + AnalysisTemplate
         Rollout: replicas 5, canary steps: 10%(30s)→25%(2m)→
         50%(5m)→100%. AnalysisTemplate: query Prometheus for
         sum(rate(http_errors{app="anihpj"}[1m])) < 0.01
         activeService: anihpj-active, previewService: anihpj-preview

    F.9  Argo Events — Webhook EventSource + Sensor
         EventSource: GitHub webhook, port 12000, POST /push
         Sensor: filter on push to main, extract commit SHA,
         trigger CI WorkflowTemplate with parameters:
         repo_url=github.com/team-anihpj/anihpj, commit_sha={{sha}}

    F.10 App-of-Apps Bootstrap YAML
         Single Application: source path argo-apps/, syncs
         all F.4-F.9 files. ONE kubectl apply → entire anihpj
         infrastructure running on Argo CD + Workflows + Events!

    ┌────────────────────────────────────────────────────────────┐
    │  TOP 15 CAPA ERRORS & FIXES                                │
    │                                                            │
    │  1. "repo not found" → Check repoURL is correct + accessible│
    │  2. "namespace not found" → syncOptions: CreateNamespace=true│
    │  3. "permission denied" → Check AppProject destinations    │
    │  4. "invalid spec" → Run: kubectl explain application.spec│
    │  5. "out of sync" stuck → argocd app sync --force <name>  │
    │  6. Workflow pod OOMKilled → Set memory limits in template│
    │  7. DAG task never starts → Check depends: field spelling  │
    │  8. Artifact "no such file" → Verify artifact repo config │
    │  9. Rollout not progressing → activeService selector wrong │
    │  10. AnalysisRun "unknown" → Prometheus URL incorrect     │
    │  11. Sensor "not ready" → EventBus pod not running        │
    │  12. Webhook returns 404 → EventSource port-forward wrong │
    │  13. "context deadline exceeded" → Check repo-server logs │
    │  14. ApplicationSet not generating → Check generator spec │
    │  15. Sync fails on CRDs → May need ServerSideApply=true   │
    └────────────────────────────────────────────────────────────┘

Appendix I: Argo Glossary — All Terminology Defined
    [GLOSSARY TABLE]
    ┌────────────────────────────────────────────────────────────┐
    │  ARGO GLOSSARY                                             │
    │                                                            │
    │  Application — Argo CD CRD linking Git repo to K8s cluster │
    │  AppProject — Groups Applications + enforces restrictions  │
    │  ApplicationSet — Template that generates Applications     │
    │  Sync — Process of making cluster state match Git state    │
    │  Drift — When actual cluster state ≠ desired Git state     │
    │  Prune — Delete cluster resources not in Git               │
    │  Self-Heal — Automatically correct drift                   │
    │  Workflow — DAG or Steps-based container execution         │
    │  WorkflowTemplate — Reusable workflow blueprint            │
    │  DAG — Directed Acyclic Graph (tasks + dependencies)       │
    │  Artifact — File passed between workflow steps             │
    │  CronWorkflow — Scheduled workflow (cron expression)       │
    │  Rollout — Argo's replacement for K8s Deployment           │
    │  Blue-Green — Instant cutover deployment strategy          │
    │  Canary — Gradual traffic shift deployment strategy        │
    │  AnalysisTemplate — Metric-based promotion criteria        │
    │  EventSource — Listener for external events                │
    │  Sensor — Filters + transforms + triggers on events        │
    │  EventBus — Internal NATS streaming transport              │
    │  GitOps — Git as single source of truth for operations     │
    │  Kustomize — K8s-native YAML patching (overlay model)      │
    │  Helm — Package manager for K8s (Go template charts)       │
    │  CRD — Custom Resource Definition (extends K8s API)        │
    └────────────────────────────────────────────────────────────┘
