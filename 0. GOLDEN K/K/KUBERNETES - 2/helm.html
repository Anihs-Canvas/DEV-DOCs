Helm certification exams test your ability to use Helm in real scenarios. You'll need to understand not just the commands, but why Helm was designed this way. Key mental models to internalize:

1.1 The Problem Before Helm — "YAML Hell" Explained

Imagine you've built anihpj — a Django application with a jobpost module where employers list jobs filtered by Skills, Location, and Author. It runs in Kubernetes. How do you manage all the YAML files needed to deploy it across development, staging, and production?

📖 Key Term: YAML Hell

YAML Hell is the pain of managing dozens of nearly-identical Kubernetes manifest files across multiple environments. Each environment needs its own copy with slightly different values (image tags, replica counts, resource limits). Without templating, you end up copy-pasting and find-and-replacing across 30+ files — a recipe for drift, errors, and 3 AM emergencies.

The anihpj Pain Point — Before Helm

Let's look at what managing anihpj looks like without Helm. You have 12 YAML files (Deployment, Service, Ingress, ConfigMap, Secret, HPA) across 3 environments — that's 36 files to maintain manually:

❌ WITHOUT HELM: 36 Files to Maintain
📁dev/: deployment.yaml, service.yaml, ingress.yaml, configmap.yaml, secret.yaml, hpa.yaml
📁staging/: deployment.yaml, service.yaml, ingress.yaml, configmap.yaml, secret.yaml, hpa.yaml
📁prod/: deployment.yaml, service.yaml, ingress.yaml, configmap.yaml, secret.yaml, hpa.yaml
❌Change image tag? Edit 3 deployment.yaml files
❌Add health probe? Edit 3 files, hope you don't miss one
❌Roll back? Find old YAML files, re-apply manually
❌What's deployed? kubectl get all, guess the version
✅ WITH HELM: 1 Chart, Many Environments
📦anihpj-chart/: Chart.yaml, values.yaml, dev-values.yaml, prod-values.yaml, templates/ (7 files)
✅Change image tag? Edit values.yaml ONCE
✅Add health probe? Edit the template ONCE
✅Roll back? helm rollback anihpj 1
✅What's deployed? helm history anihpj

The Real Cost of YAML Hell

Without Helm, every change to your application means finding and editing multiple files across multiple directories. This creates several critical problems:

🔀
Configuration Drift

Dev, staging, and production slowly diverge. A fix applied in dev gets forgotten in prod. "It worked in staging!" becomes your most-dreaded phrase.

📋
No Version History

Raw YAML files have no built-in version tracking. What changed between last Tuesday's deploy and today's? You're relying on git commits and memory.

🚨
Manual Rollback Risk

Rolling back means finding the old YAML files and reapplying them. In an emergency at 3 AM, this is error-prone and slow.

👥
No Reusability

Every team copies the same YAML patterns. The "nginx deployment" written by Team A is slightly different from Team B's. No standard, no sharing.

💡 Pro Tip: The "Copy-Paste-Fix" Anti-Pattern

If you find yourself copying a YAML file and changing 3 values for a new environment, you need Helm. Every copy-paste is a future bug waiting to happen. Helm templates let you write the logic once and parameterize the differences.

1.2 What is Helm? — The Simple Answer

📖 Official Definition

Helm is the package manager for Kubernetes. Just like apt installs software on Ubuntu, brew installs software on macOS, or yum installs on RHEL — Helm installs applications on Kubernetes. It packages all your Kubernetes YAML manifests (Deployments, Services, ConfigMaps, Secrets, Ingress, etc.) into a single reusable unit called a Chart.

Helm as a Package Manager — The Analogy

📦 ChartA packaged set of Kubernetes manifest templates + default configuration. Contains Chart.yaml, values.yaml, and templates/. Think of it as a .deb package for Kubernetes.
🏪 RepositoryWhere charts are stored and shared. Like Docker Hub for container images, chart repositories (or OCI registries) distribute charts. Examples: Bitnami, Artifact Hub, ghcr.io.

⚠ Helm 2 vs Helm 3 — The Tiller Story

Helm 2 had a server-side component called Tiller that ran inside the cluster with broad RBAC permissions. This was a security nightmare — any user with Helm access could potentially access any resource. Helm 3 removed Tiller entirely. The Helm client now talks directly to the Kubernetes API server using your kubeconfig credentials. This is simpler, more secure, and aligns with standard Kubernetes RBAC.

1.3 Helm vs kubectl — When to Use Which

A common question from Kubernetes beginners: "I already use kubectl apply -f to deploy my YAML files. Why do I need Helm?" The answer lies in understanding the fundamental difference between these tools:

TaskkubectlHelm
Deploy appkubectl apply -f . (all YAML files)helm install app ./chart (one command)
Change replicasEdit deployment.yaml, re-applyhelm upgrade --set replicaCount=5
Roll backkubectl rollout undo (last only)helm rollback app 3 (any revision)
See historykubectl rollout history (limited)helm history app (complete log)
Template variables❌ Not possible✅ {{ .Values }}, {{ .Release }}
Package & share❌ Manual copy-paste✅ Chart repos / OCI registries
Hooks & tests❌ Not built-in✅ pre/post-install hooks, helm test
Best forQuick debugging, one-off tasksProduction deployments, app distribution

The Hybrid Approach: Use Both!

Helm and kubectl are not mutually exclusive. The best practice is:

  • Helm for installing, upgrading, and managing application releases
  • kubectl for inspecting running resources, debugging issues, and running one-off commands
  • After helm install, use kubectl get pods to verify everything is running
  • When troubleshooting, kubectl describe pod and kubectl logs are your go-to tools

📝 Chapter 1 Practice Questions — 10 Questions

Q1
What is the primary problem that Helm solves in Kubernetes application management?
✅ Answer
ANSWER

Helm solves "YAML Hell" — the problem of managing dozens of nearly-identical Kubernetes YAML manifest files across multiple environments. Without Helm, you must copy-paste and manually edit deployment.yaml, service.yaml, ingress.yaml, etc. for each environment (dev, staging, prod). Q2
What are the 4 core Helm concepts? Define each briefly.
✅ Answer
ANSWER

Chart — A packaged set of Kubernetes manifest templates + default configuration (analogous to a .deb package). Repository — Where charts are stored and shared (like Docker Hub for charts). 5.3 Values Files — Making Charts Reusable

values.yaml is the default configuration. Users override these defaults using --set, --values, or multiple values files. The precedence order determines which value "wins":

Values Precedence — Who Wins?
  🔝 HIGHEST PRIORITY
  ┌──────────────────────────────────────────────────────┐
  │  1. --set image.tag=v2         (inline CLI override)  │
  │  2. --values prod-secrets.yaml (parent values file)   │
  │  3. --values prod-values.yaml  (parent values file)   │
  │  4. values.yaml in child chart (subchart defaults)    │
  │  5. values.yaml in chart       (chart defaults)       │
  └──────────────────────────────────────────────────────┘
  🔜 LOWEST PRIORITY

  💡 EXAMPLE:
  values.yaml:    replicaCount: 1
  prod-values:    replicaCount: 3
  CLI:    --set replicaCount=5
  RESULT: replicaCount = 5  (--set always wins!)
bash
# Multiple values files (later files override earlier ones)
helm install anihpj ./chart -f base.yaml -f prod.yaml -f secrets.yaml

# Inline overrides (highest priority)
helm install anihpj ./chart --set image.tag=v2.0.0 --set replicaCount=5

# File-based value
helm install anihpj ./chart --set-file config.data=./config.json

7.1 Chart Dependencies in Chart.yaml

Chart.yaml
dependencies:
  - name: postgresql
    version: "^12.0.0"           # SemVer range
    repository: https://charts.bitnami.com/bitnami
    condition: postgresql.enabled  # Conditional dependency
    tags:
      - database                    # Group with tags
  - name: redis
    version: "~17.0.0"
    repository: https://charts.bitnami.com/bitnami
    condition: redis.enabled

Version constraints: ^12.0.0 (compatible with 12.x), ~17.0.0 (patch-level), >=1.0.0 <2.0.0 (range).

7.3 Subcharts & Global Values

Subcharts are charts placed in the charts/ directory (or fetched via helm dependency update). They can access global values from the parent chart:

values.yaml
global:
  postgresql:
    auth:
      username: anihpj
      password: secret123
      database: jobpost

postgresql:
  enabled: true
  primary:
    persistence:
      size: 10Gi
  fullnameOverride: anihpj-db  # ← Avoids naming conflicts!

fullnameOverride is a critical pattern: without it, the PostgreSQL subchart names its resources RELEASE-postgresql. If you install the same chart twice, names collide. Set fullnameOverride to a fixed name (like anihpj-db) or use it to keep names short and predictable. The nameOverride variant only overrides the chart name portion while keeping the release prefix.

⚠ Don't Forget Global Value Propagation

Global values in the parent chart's values.yaml are automatically available to ALL subcharts under .Values.global. Use this to share credentials, registry settings, or common configuration across your entire chart stack without duplicating values.

8.3 Chart Tests

Tests are Kubernetes pods annotated with "helm.sh/hook": test. They run when you execute helm test RELEASE and must exit with code 0 to pass. Tests verify your deployment works correctly without affecting running workloads:

templates/tests/test-connection.yaml
apiVersion: v1
kind: Pod
metadata:
  name: "{{ include "anihpj.fullname" . }}-test-connection"
  labels: {{- include "anihpj.labels" . | nindent 4 }}
  annotations:
    "helm.sh/hook": test
    "helm.sh/hook-delete-policy": hook-succeeded
spec:
  containers:
    - name: wget
      image: busybox
      command: ['wget']
      args: ['{{ include "anihpj.fullname" . }}:{{ .Values.service.port }}/healthz']
  restartPolicy: Never

The helm.sh/hook: test annotation tells Helm this is a test resource. It's NOT deployed during normal install/upgrade — only when helm test is explicitly run. Combined with hook-delete-policy: hook-succeeded, the test pod is automatically cleaned up after passing.

  • Job listing endpoint: wget anihpj-web:8000/jobs/ — verifies jobpost app works

What does the hook deletion policy hook-succeeded do?
✅ Answer
ANSWER

✅ Answer
ANSWER

✅ Answer

9.1 Value Sources & Precedence

Helm merges values from multiple sources. Understanding the order is critical for predictable deployments:

bash
# Multiple values files (last one wins for duplicate keys)
helm install anihpj ./chart -f base.yaml -f prod.yaml -f secrets.yaml

# Inline overrides (highest priority)
helm install anihpj ./chart --set image.tag=v2.1.0 --set replicaCount=5

# File-based values (useful for large configs)
helm install anihpj ./chart --set-file config.data=./config.json

# String values (prevents type conversion issues)
helm install anihpj ./chart --set-string app.version=v2.1.0

Precedence (highest to lowest): --set > --set-file > --values (last file) > --values (first file) > values.yaml in child chart > values.yaml in parent chart

9.2 Schema Validation (values.schema.json)

Place a values.schema.json file in your chart to validate user-supplied values. Helm automatically checks values against this schema during helm lint, helm install, and helm upgrade:

values.schema.json
{
  "$schema": "https://json-schema.org/draft-07/schema#",
  "properties": {
    "replicaCount": { "type": "integer", "minimum": 1, "maximum": 10 },
    "image": {
      "type": "object",
      "properties": {
        "repository": { "type": "string" },
        "tag": { "type": "string", "pattern": "^v?\\d+\\.\\d+\\.\\d+$" }
      },
      "required": ["repository", "tag"]
    },
    "service": {
      "type": "object",
      "properties": {
        "type": { "type": "string", "enum": ["ClusterIP", "NodePort", "LoadBalancer"] },
        "port": { "type": "integer", "minimum": 1, "maximum": 65535 }
      }
    }
  },
  "required": ["replicaCount", "image"]
}

⚠ Schema Validation Prevents Production Disasters

Without a schema, a user could set replicaCount: "three" instead of replicaCount: 3 — Helm would render it without error, and Kubernetes would reject it with a cryptic message. Schema validation catches these issues at helm lint time, before they reach your cluster.

9.3 Environment-Specific Configurations

Manage dev/staging/prod with separate values files and secrets via External Secrets Operator (ESO):

bash
# Dev: SQLite, Debug mode, 1 replica
helm install anihpj-dev ./chart -f values.yaml -f dev-values.yaml

# Prod: PostgreSQL, no debug, 3 replicas, TLS
helm install anihpj-prod ./chart -f values.yaml -f prod-values.yaml -f secrets-prod.yaml --atomic

For secrets, use External Secrets Operator (ESO) or Sealed Secrets instead of committing sensitive values. ESO syncs secrets from AWS Secrets Manager, Azure Key Vault, or HashiCorp Vault into Kubernetes Secrets that Helm can reference.

9.4 Advanced Template Techniques

Recursive templates with tpl: Evaluate a value string as a Go template — powerful when users define their own template snippets in values.yaml.

values.yaml (advanced)
customLabel: '{{ .Release.Name }}-{{ .Chart.Version }}'
# In template: {{ tpl .Values.customLabel . }}

.Files.Glob: Load external config files into ConfigMaps at render time — no need to template them:

templates/configmap.yaml
data:
  nginx.conf: |
{{ (.Files.Glob "configs/nginx.conf").AsConfig | indent 4 }}
  {{- range $path, $_ := .Files.Glob "configs/*.json" }}
  {{ base $path }}: |
{{ $.Files.Get $path | indent 4 }}
  {{- end }}

Dynamic resource generation: Use {{ range }} to create multiple similar resources from a list in values.yaml (e.g., multiple Ingress rules, multiple Secrets). Conditional inclusion: Wrap entire resources in {{ if .Values.featureX.enabled }} to optionally deploy them.

12.1 What is Helmfile?

Helmfile is a declarative spec for Helm releases. Instead of running helm install and helm upgrade for each chart individually, you define all your charts, their values, and environment overrides in a single helmfile.yaml. One command (helmfile apply) installs or updates everything.

  │ 4 commands. Manual order. │          │ Declarative. Repeatable.   │
  └──────────────────────────┘          └──────────────────────────┘
📖 Key Concept: Helmfile = Docker Compose for Helm

Just as Docker Compose defines multiple containers in one docker-compose.yml, Helmfile defines multiple Helm releases in one helmfile.yaml.

Define anihpj-web, anihpj-db, and anihpj-redis as separate releases with environment-specific overrides:

  dev:
    values: [dev-env.yaml]
  prod:
    values: [prod-env.yaml, secrets-prod.yaml]

releases:
  - name: anihpj-web
    chart: ./anihpj-chart
    values:
      - "{{ .Environment.Name }}-web-values.yaml"
    set:
      - name: image.tag
        value: "{{ .Values | getOrNil \"web.image.tag\" | default \"latest\" }}"

  - name: anihpj-redis

    version: ~17.0.0
    condition: redis.enabled

16.1 Multi-Cluster Helm Management

One chart, many clusters: The same anihpj chart deploys to dev (minikube), staging (EKS us-east-1), and prod (EKS eu-west-1 + us-west-2). Each cluster gets its own values file (dev-values.yaml, staging-values.yaml, prod-us.yaml, prod-eu.yaml). This is the core pattern of multi-cluster Helm: one chart, per-cluster configuration. You maintain a single chart codebase but deploy it to any number of clusters by swapping the values file and switching kubeconfig contexts. This ensures consistency — the same templates render for dev, staging, and prod, but with environment-appropriate settings (resource limits, replica counts, domain names, TLS certificates).

How it works in practice: You keep cluster-specific values files in a clusters/ directory within your chart repo (or a separate GitOps repo). CI/CD pipelines detect which cluster to target based on the branch or tag, then run kubectl config use-context <cluster> && helm upgrade .... The key insight: the chart does not change between environments — only the values do.

16.2 Multi-Tenant Helm Patterns

Namespace-scoped releases: Each tenant gets their own namespace and release. For example: helm install anihpj-tenantA ./chart -n tenant-a --create-namespace. The namespace acts as an isolation boundary — Tenant A's pods, services, configmaps, and secrets live entirely within tenant-a, completely separate from Tenant B's resources in tenant-b.

Tenant-specific values: Override branding, resource limits, and features per tenant through dedicated values files (tenant-a-values.yaml, tenant-b-values.yaml). Each tenant can have different resource quotas, different company logos, different feature flags — all controlled declaratively through values, not by maintaining separate chart copies.

RBAC for Helm: Create per-tenant ServiceAccounts with RoleBindings that limit which namespaces they can deploy to. This prevents Tenant A from accidentally (or maliciously) affecting Tenant B's releases. Helm uses the kubeconfig context of the deploying user/service account, so properly scoped RBAC is your defense-in-depth layer.

bash — Multi-Tenant Deployment
# Tenant A deployment
helm install anihpj-tenantA ./anihpj-chart \
  -n tenant-a --create-namespace \
  -f tenant-a-values.yaml \
  --set branding.company="Acme Corp" \
  --set resources.limits.cpu=500m

# Tenant B deployment (isolated namespace)
helm install anihpj-tenantB ./anihpj-chart \
  -n tenant-b --create-namespace \
  -f tenant-b-values.yaml \
  --set branding.company="Globex Inc" \
  --set resources.limits.cpu=1000m
YAML — Tenant RBAC (Role + RoleBinding)
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: helm-tenant-a
  namespace: tenant-a
rules:
  - apiGroups: [""]
    resources: ["pods", "services", "configmaps", "secrets"]
    verbs: ["*"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: helm-tenant-a-binding
  namespace: tenant-a
subjects:
  - kind: ServiceAccount
    name: tenant-a-deployer
    namespace: tenant-a
roleRef:
  kind: Role
  name: helm-tenant-a
  apiGroup: rbac.authorization.k8s.io
💡 Pro Tip: Prevent Cross-Tenant Access

Each tenant's ServiceAccount can ONLY deploy to their own namespace. Even if Tenant A knows Tenant B's namespace, the RBAC RoleBinding prevents access. This is defense-in-depth for multi-tenant Helm.

16.3 Helm + Service Mesh

Integrate Istio or Linkerd sidecar injection via Helm values. The service mesh configuration becomes part of your Helm chart — versioned, tested, and deployed consistently across all environments. Instead of manually applying mesh annotations after deployment (error-prone and inconsistent), you template them directly into your workload manifests.

How it works: Template the injection annotation: sidecar.istio.io/inject: "{{ .Values.istio.enabled | toString }}". When istio.enabled is true, the Istio mutating webhook automatically injects the Envoy sidecar proxy into every pod. Configure mesh-specific settings (mTLS mode, traffic splitting weights, retry policies, circuit breakers) through values.yaml — all versioned in Git alongside your application code. This is a massive operational win: the mesh config for anihpj in prod is the same mesh config you tested in staging, because it's all part of the same chart.

values.yaml — Service Mesh Configuration
istio:
  enabled: true
  inject: true
  mtls:
    mode: STRICT
  trafficPolicy:
    loadBalancer: LEAST_REQUEST
  retry:
    attempts: 3
    perTryTimeout: 2s
templates/deployment.yaml — Istio Labels
spec:

    metadata:
      labels:
        {{- include "anihpj.selectorLabels" . | nindent 8 }}
        {{- if .Values.istio.inject }}
        sidecar.istio.io/inject: "true"
        {{- end }}

17.3 Zero-Downtime Migration — Step by Step

Dry-run first: Always run helm install --dry-run --debug to verify the rendered manifests match expectations before touching any real resources. The dry-run output should be identical (or intentionally different) from your current kubectl get -o yaml output. If something looks wrong, fix it in the template — no real resources were changed.

Adopt existing resources: If resources already exist in the cluster (created by kubectl apply), add Helm's standard labels (app.kubernetes.io/managed-by: Helm) so Helm can take ownership. Without these labels, Helm will refuse to manage existing resources. This is a safety mechanism to prevent Helm from accidentally overwriting resources it doesn't own.

Zero-downtime pattern: Deploy Helm-managed resources alongside existing ones (using a different release name or label selector), verify everything works, then remove the old resources. Never delete first. Keep original YAML files as backup in a backup/ directory for at least 2 weeks — if anything goes wrong, kubectl apply -f backup/ restores the original state in seconds.

18.3 Artifact Hub — The Helm Chart Marketplace

Visit artifacthub.io to discover thousands of community-maintained charts. This is the central registry for Helm charts (and other cloud-native artifacts). Evaluate chart quality by checking: stars (community approval — more stars = more users have vetted it), downloads (usage popularity — charts with millions of downloads are battle-tested), security scans (vulnerability reports — avoid charts with HIGH or CRITICAL CVEs), official status (verified publisher badge — published by the project maintainers, not a third party), and recent updates (active maintenance — a chart last updated in 2022 may not work with Kubernetes 1.32). For anihpj dependencies, search for PostgreSQL operators, Redis clusters, and Django-optimized ingress controllers on Artifact Hub.

18.4 Contributing to Helm

Helm is a CNCF graduated project — the highest maturity level in the cloud-native ecosystem, alongside Kubernetes itself, Prometheus, and Envoy. This means Helm has proven itself in production at thousands of organizations and has a mature governance model. Contribute at github.com/helm/helm: fix bugs (look for "good first issue" labels), improve documentation (helm.sh/docs), add new template functions, or review pull requests. 📖 Appendix E: Helm GlossaryReference

Chart
A packaged set of Kubernetes manifest templates + default configuration. Contains Chart.yaml, values.yaml, and templates/.
Release
A running instance of a chart in a Kubernetes cluster. One chart can have multiple named releases.
Repository
Where charts are stored and shared. Can be traditional HTTP with index.yaml or OCI-compliant registry.
Revision
Every install/upgrade/rollback creates a numbered revision. helm history shows all revisions.
Values
Configuration data injected into templates. Defined in values.yaml and overridden via --set/--values.
Template
A Kubernetes manifest file with Go template syntax. Rendered with values at deploy time.
Hook
A resource executed at specific lifecycle points (pre/post-install, upgrade, delete). Usually a Job.
Subchart
A chart used as a dependency within another chart. Stored in charts/ directory.
Library Chart
A chart (type: library) providing reusable template snippets only. No resources generated.
OCI Registry
Open Container Initiative-compliant registry. Same infrastructure as Docker images. Helm 3.8+.
Provenance
Cryptographic proof (.prov file) of chart origin. Created with helm package --sign.
Tiller
Server-side component in Helm 2 (removed in Helm 3). Ran inside cluster with broad permissions.
Capabilities
Built-in object providing Kubernetes cluster version and API resource information.
Fullname Override
Values key that overrides the generated resource name. Prevents naming conflicts.
Chart.lock
Lock file recording exact dependency versions. Used by helm dependency build for reproducible builds.
Artifact Hub
Web-based marketplace (artifacthub.io) for discovering and sharing Helm charts and other CNCF artifacts.
SemVer
Semantic Versioning (MAJOR.MINOR.PATCH). Helm charts use SemVer 2.0.0 for version numbers.
Go Templates
Go's built-in templating language used by Helm. Uses {{ }} syntax with dot-context navigation.
Pipeline
Chaining template functions with |. Example: {{ .Values.data | toYaml | nindent 6 }}.
Dry Run
Simulating an operation without applying. --dry-run renders templates and validates YAML.
Atomic
--atomic flag that auto-rollbacks on failure. Essential for production upgrades.
GitOps
Declarative infrastructure pattern where Git is the source of truth. Tools: ArgoCD, FluxCD.
Helmfile
Declarative specification for managing multiple Helm releases. Sync entire stack with one command.
kubeconfig
Configuration file (~/.kube/config) that defines clusters, users, and contexts for kubectl/Helm.
CNCF
Cloud Native Computing Foundation. Helm is a CNCF graduated project (highest maturity level).
ChartMuseum
Open-source Helm chart repository server. Alternative to OCI registries for hosting charts.
Values Precedence
The order in which values are merged: --set > --values > child defaults > parent defaults.
Release Namespace
The Kubernetes namespace where a release is installed. Set via --namespace or HELM_NAMESPACE.
fullnameOverride
Values key that overrides the generated resource name. Prevents naming conflicts in subcharts.

G.1 Fundamentals (10 Questions)

Q1
What is Helm and what problem does it solve?
✅ Answer
ANSWER

Helm is the package manager for Kubernetes. It solves "YAML Hell" — managing dozens of nearly-identical YAML files across environments by introducing templating with values.yaml.

Q2
Name the 4 core Helm concepts.
✅ Answer
ANSWER

Chart (package), Repository (store), Release (installation), Revision (version snapshot).

Q3
What component did Helm 3 remove and why?
✅ Answer
ANSWER

Tiller — a server-side pod with broad cluster-admin permissions. Removed for security; Helm 3 CLI talks directly to the API server.

Q4
Where does Helm store release data by default?
✅ Answer
ANSWER

Kubernetes Secrets (type: helm.sh/release.v1). Each revision gets its own Secret.

Q5
What command renders templates locally without deploying?
✅ Answer
ANSWER

helm template ./chart — renders all templates and outputs YAML to stdout.

Q6
What is values precedence (highest to lowest)?
✅ Answer
ANSWER

--set > --set-file > --values (last) > --values (first) > child values.yaml > parent values.yaml.

Q7
What file provides reusable template snippets?
✅ Answer
ANSWER

_helpers.tpl — defines named templates called via {{ include "name" . }}.

Q8
How do you add a chart repository?
✅ Answer
ANSWER

helm repo add NAME URL then helm repo update to fetch the index.

Q9
What is the only required file in a Helm chart?
✅ Answer
ANSWER

Chart.yaml — must contain apiVersion (v2), name, and version at minimum.

Q10
What command shows all revisions of a release?
✅ Answer
ANSWER

helm history RELEASE_NAME — shows revision numbers, status, chart version, and timestamps.

G.2 Chart Development (10 Questions)

Q11
How do you check what would be deployed without applying?
✅ Answer
ANSWER

helm install NAME ./chart --dry-run --debug

Q12
What annotation makes a resource a Helm hook?
✅ Answer
ANSWER

"helm.sh/hook": post-install (or pre-install, pre-upgrade, etc.)

Q13
How do you declare chart dependencies?
✅ Answer
ANSWER

In the dependencies: section of Chart.yaml with name, version, and repository.

Q14
What command runs chart tests?
✅ Answer
ANSWER

helm test RELEASE_NAME

Q15
What is the difference between include and template?
✅ Answer
ANSWER

include returns a string (supports pipelines); template writes directly to output. Always prefer include.

Q16
How do you iterate over a list in templates?
✅ Answer
ANSWER

{{- range .Values.list }}...{{ end }}

Q17
What does {{- "hello" -}} do?
✅ Answer
ANSWER

Trims whitespace on both sides of the action. The - removes whitespace before/after.

Q18
How do you validate a chart before packaging?
✅ Answer
ANSWER

helm lint ./chart

Q19
What is the purpose of Chart.lock?
✅ Answer
ANSWER

Locks exact dependency versions for reproducible builds. Used by helm dependency build.

Q20
What does .Release.IsInstall return?
✅ Answer
ANSWER

true for install operations, false for upgrade operations. Useful for conditional logic.

G.3 Advanced & Production (10 Questions)

Q21
What Helm 3.8+ feature eliminates the need for separate chart repos?
✅ Answer
ANSWER

OCI registry support — push/pull charts via oci:// using the same registries as Docker images.

Q22
What is the purpose of values.schema.json?
✅ Answer
ANSWER

JSON Schema validation of values.yaml. Helm validates against it during lint, install, and upgrade.

Q23
What does --atomic do on helm install/upgrade?
✅ Answer
ANSWER

Automatically rolls back the release if the operation fails. Essential for production deployments.

Q24
What Helm plugin shows diff before upgrade?
✅ Answer
ANSWER

helm-diff — previews changes between current and proposed release.

Q25
What is the 3-phase migration strategy?
✅ Answer
ANSWER

Phase 1: Wrap raw YAML in chart. Phase 2: Extract values. Phase 3: Add conditionals and env files.

Q26
How do you sign a Helm chart?
✅ Answer
ANSWER

helm package --sign --key 'NAME' ./chart — creates a .prov provenance file.

Q27
What is a library chart?
✅ Answer
ANSWER

A chart with type: library that provides reusable template snippets only. No Kubernetes resources generated.

Q28
What does helmfile do?
✅ Answer
ANSWER

Declarative management of multiple Helm releases. Sync entire stack with helmfile apply.

Q29
Name 3 production best practices for Helm.
✅ Answer
ANSWER

Pin versions (never "latest"), use --atomic, lint in CI/CD, namespace isolation, verify provenance, use securityContext.

Q30
How do you troubleshoot "nil pointer evaluating interface"?
✅ Answer
ANSWER

The .Values key doesn't exist. Use {{ default "fallback" .Values.key }} or add the key to values.yaml.
