WHAT IS CNPA? — THE BIG PICTURE
═══════════════════════════════════════════════════════════════════════

CNPA (Certified Cloud Native Platform Engineering Associate) certifies your ability
to design, build, and operate Internal Developer Platforms (IDPs) using cloud native
technologies. Unlike CKA (cluster admin) or CKAD (app developer), CNPA focuses on
the PLATFORM LAYER — the self-service infrastructure that enables developers to
deploy code without touching Kubernetes directly.

    ┌──────────────────────────────────────────────────────────────┐
    │ 🏗️ Platform Engineer = Building the FACTORY (the IDP)        │
    │ 🎨 Developer         = Using the factory (apps)              │
    │                                                              │
    │ You are the bridge between:                                  │
    │   • Infrastructure (servers, networks, storage)              │
    │   • Operations (monitoring, security, compliance)            │
    │   • Development (CI/CD, developer tools, self-service)       │
    └──────────────────────────────────────────────────────────────┘

CNPA vs CKA vs CKAD — QUICK COMPARISON
───────────────────────────────────────
    ┌──────────────────────────────────────────────────────────────────┐
    │                    CKA              CKAD           CNPA           │
    │  Focus:           Administrator     App Developer   Platform Eng  │
    │  You manage:      The CLUSTER       The APPS        The PLATFORM  │
    │  Scope:           Single cluster    App lifecycle   Multi-cluster, │
    │                                                 multi-tool, IDP  │
    │  Tools:           kubeadm, etcd,    kubectl, Helm,  ArgoCD, Tofu, │
    │                   kubelet, certs    ConfigMaps,     Crossplane,    │
    │                                     Secrets, Pods   Backstage,     │
    │                                                      Prometheus    │
    │  Think of it:     🏗️ Building      🎨 Decorating   🏭 Building    │
    │                   the house         the rooms       the factory   │
    └──────────────────────────────────────────────────────────────────┘

    │     📊 ILLUSTRATION: The Reconciliation Loop (THE KEY CONCEPT)
    │     ┌─────────────────────────────────────────────────────────┐
    │     │                                                         │
    │     │  📝 DESIRED STATE                🔍 ACTUAL STATE        │
    │     │  (You declare in YAML)            (What's running now)  │
    │     │  ┌──────────────────┐            ┌──────────────────┐   │
    │     │  │ replicas: 3      │            │ Pods running: 2   │   │
    │     │  │ image: anihpj:v2 │            │ Image: anihpj:v2  │   │
    │     │  │ cpu: 250m        │            │ CPU usage: 180m   │   │
    │     │  └────────┬─────────┘            └────────┬─────────┘   │
    │     │           │                               │             │
    │     │           └─────── COMPARE ────────────────┘             │
    │     │                       │                                 │
    │     │               DIFFERENCE FOUND?                         │
    │     │                  │        │                              │
    │     │               YES        NO                             │
    │     │                │         │                               │
    │     │           ┌────▼────┐   ┌▼──────┐                        │
    │     │           │ TAKE    │   │ DO    │                        │

    │     │           │ (create │   │(sleep │                        │

    │     │           │ pod)    │   │       │                        │

│   │     • What IS an IDP? The self-service layer — "a unified portal + API
│   │       that abstracts infrastructure complexity from developers"
│   │     • IDP Architecture — 5 Layers:
│   │       Layer 1: Infrastructure (K8s, cloud, networking)
│   │       Layer 2: Orchestration (ArgoCD, Helm, Crossplane)

│   │       Layer 5: Developer Experience (Backstage, CLI, docs)
│   │     • Golden Paths: paved roads for common developer workflows
│   │       — "Instead of 20 manual steps, one command or one click"
│   │     • The Platform as a PRODUCT mindset — treat your IDP like a SaaS
│   │     • IDP Maturity Model (Crawl → Walk → Run → Fly)

├── Chapter 2: Declarative Resource Management [ch2]
│   ├── 2.1 Declarative vs Imperative — The Foundation [s2-1]
│   │     • "What you want" vs "How to do it" — the fundamental distinction
│   │     • Why platforms MUST be declarative: self-healing, idempotency, GitOps
│   │     • anihpj example: kubectl apply -f deployment.yaml (declarative) vs
│   │       kubectl run anihpj --image=anihpj:v1 (imperative)
│   │     • Imperative: "Start 3 pods, then check, then start more if needed"
│   │     • Declarative: "I want 3 replicas" — K8s makes it happen and keeps it that way
│   │
│   │     📊 DECLARATIVE vs IMPERATIVE — SIDE BY SIDE
│   │     ┌─────────────────────────────────────────────────────────┐
│   │     │                                                         │
│   │     │  IMPERATIVE ("HOW")          DECLARATIVE ("WHAT")       │
│   │     │  ┌──────────────────────┐   ┌──────────────────────┐   │
│   │     │  │ $ kubectl run anihpj  │   │ $ kubectl apply -f   │   │
│   │     │  │   --image=anihpj:v1  │   │   deployment.yaml    │   │
│   │     │  │   --replicas=3       │   │                      │   │
│   │     │  │   --port=8000        │   │ replicas: 3           │   │
│   │     │  │                      │   │ image: anihpj:v1      │   │
│   │     │  │ $ kubectl scale      │   │ ports: [8000]         │   │
│   │     │  │   deployment anihpj  │   │                      │   │
│   │     │  │   --replicas=5       │   │ All in Git ✅          │   │
│   │     │  │                      │   │ Self-healing ✅        │   │
│   │     │  │ What if scale fails? │   │ Idempotent ✅          │   │
│   │     │  │ Who changed what?    │   │ Auditable ✅           │   │
│   │     │  │ State unknown ❌      │   │ Rollback = git revert │   │
│   │     │  └──────────────────────┘   └──────────────────────┘   │
│   │     │                                                         │
│   │     │  WHY PLATFORMS MUST BE DECLARATIVE:                     │
│   │     │  🔄 Self-Healing: Controller reconciles actual→desired  │
│   │     │  📋 GitOps: Every change is a Git commit with history   │
│   │     │  🔁 Idempotent: apply 1 time = apply 100 times          │
│   │     │  📊 Auditable: git log shows who changed what, when     │
│   │     │  🔙 Rollback: git revert → ArgoCD auto-reverts cluster  │
│   │     └─────────────────────────────────────────────────────────┘

│   ├── 2.2 Kubernetes Manifests as Declarative API Objects [s2-2]
│   │     • The universal K8s object structure — every resource follows this pattern:
│   │       apiVersion + kind + metadata + spec + status
│   │     • The spec/status split — THE most important K8s design pattern
│   │     • spec = DESIRED state (YOU write this): "I want 3 replicas"
│   │     • status = ACTUAL state (CONTROLLER writes this): "2 available, 1 pending"
│   │     • How controllers reconcile spec → status continuously
│   │
│   │     📊 KUBERNETES OBJECT ANATOMY — The Universal Pattern
│   │     ┌─────────────────────────────────────────────────────────┐
│   │     │                                                         │
│   │     │  apiVersion: apps/v1        ← WHICH API group/version   │
│   │     │  kind: Deployment           ← WHAT type of resource     │
│   │     │  metadata:                  ← WHO is this?              │
│   │     │    name: anihpj-api                                     │
│   │     │    namespace: anihpj-prod                                │
│   │     │    labels: {app: anihpj, tier: api}                     │
│   │     │  ─────────────────────────────────────────────          │
│   │     │  spec:                      ← WHAT YOU WANT (desired)   │
│   │     │    replicas: 3              ← "I want 3 pods"           │
│   │     │    selector: {matchLabels: {app: anihpj-api}}           │
│   │     │    template:                ← Pod blueprint             │
│   │     │      metadata: {labels: {app: anihpj-api}}             │
│   │     │      spec:                                               │
│   │     │        containers:                                       │
│   │     │        - name: api                                       │
│   │     │          image: anihpj/jobpost:v1.2.3                   │
│   │     │          ports: [{containerPort: 8000}]                 │
│   │     │          resources: {requests: {cpu: 250m, mem: 256Mi}} │
│   │     │  ─────────────────────────────────────────────          │
│   │     │  status:                    ← WHAT IS (actual, controller│
│   │     │    replicas: 3              ← 3 pods exist              │
│   │     │    availableReplicas: 2     ← but only 2 are Ready      │
│   │     │    conditions: [{type: Available, status: "False"}]     │
│   │     │                                                         │
│   │     │  THE RECONCILIATION LOOP (Every controller does this):  │
│   │     │  ┌──────────┐   ┌──────────────┐   ┌──────────┐       │
│   │     │  │  SPEC    │──▶│  CONTROLLER  │──▶│  STATUS  │       │
│   │     │  │ (desired)│   │  reads spec  │   │ (actual) │       │
│   │     │  │          │   │  acts on diff│   │          │       │
│   │     │  └──────────┘   └──────────────┘   └──────────┘       │
│   │     │       ▲                                    │            │
│   │     │       │    Controller notices              │            │
│   │     │       └──── status ≠ spec ─────────────────┘            │
│   │     └─────────────────────────────────────────────────────────┘
│   │
│   ├── 2.3 kubectl apply vs kubectl create [s2-3]
│   │     • kubectl apply — DECLARATIVE: computes 3-way diff (file vs live
│   │       vs last-applied-configuration) and patches only what changed
│   │     • kubectl create — IMPERATIVE: makes a single POST, fails with
│   │       "AlreadyExists" on second run — unsuitable for GitOps loops
│   │     • The three-way merge: how apply compares your file, the live object
│   │       in etcd, and the last-applied-configuration annotation
│   │     • Why GitOps REQUIRES kubectl apply: ArgoCD syncs every 3 minutes —
│   │       create would fail on every sync after the first
│   │
│   │     📊 kubectl apply — THE THREE-WAY MERGE
│   │     ┌─────────────────────────────────────────────────────────┐
│   │     │                                                         │
│   │     │  ┌──────────┐   ┌──────────────┐   ┌──────────────┐   │
│   │     │  │  FILE    │   │ LIVE OBJECT  │   │ LAST-APPLIED │   │
│   │     │  │ (desired)│   │  (in etcd)   │   │ CONFIGURATION│   │
│   │     │  │          │   │              │   │ (annotation) │   │
│   │     │  │replicas:5│   │ replicas:3   │   │ replicas:3   │   │
│   │     │  └────┬─────┘   └──────┬───────┘   └──────┬───────┘   │
│   │     │       │               │                   │            │
│   │     │       └───────────────┼───────────────────┘            │
│   │     │                       │                                │
│   │     │                  THREE-WAY DIFF                        │
│   │     │                       │                                │
│   │     │            Only changed fields PATCHED                 │
│   │     │                       │                                │
│   │     │            ┌──────────▼──────────┐                    │
│   │     │            │ API Server PATCHES  │                    │
│   │     │            │ replicas: 3 → 5     │                    │
│   │     │            └─────────────────────┘                    │
│   │     │                                                         │
│   │     │  $ kubectl apply -f anihpj-api.yaml    # 1st: CREATED  │
│   │     │  $ kubectl apply -f anihpj-api.yaml    # 2nd: no-op    │
│   │     │  $ kubectl apply -f anihpj-api.yaml    # 100th: no-op  │
│   │     │  ✅ Safe to run in a loop (ArgoCD syncs every 3 min)    │
│   │     │                                                         │
│   │     │  $ kubectl create -f anihpj-api.yaml   # 1st: CREATED  │
│   │     │  $ kubectl create -f anihpj-api.yaml   # 2nd: ❌ ERROR │
│   │     │  Error: deployments.apps "anihpj-api" already exists    │
│   │     │  ❌ Cannot be used in GitOps reconciliation loops       │
│   │     └─────────────────────────────────────────────────────────┘
│   │
│   ├── 2.4 YAML vs JSON for Declarative Configuration [s2-4]
│   │     • YAML won for HUMAN-authored config because of: comments (# for WHY),
│   │       readability (no braces/quotes noise), anchors (&name for DRY),
│   │       multi-line strings (| and >), and NO trailing comma errors
│   │     • JSON is what Kubernetes STORES internally (in etcd)
│   │     • kubectl converts YAML → JSON before sending to the API server
│   │     • YAML is the UX layer; JSON is the storage format
│   │
│   │     📊 YAML vs JSON — Why YAML Won the Configuration War
│   │     ┌─────────────────────────────────────────────────────────┐
│   │     │                                                         │
│   │     │  YAML ✅                         JSON ❌ (for config)    │
│   │     │  ┌──────────────────────┐       ┌──────────────────────┐│
│   │     │  │ # Owner: platform    │       │ // NOT VALID JSON!   ││
│   │     │  │ # Version: 1.2.3     │       │ // No comments 😭     ││
│   │     │  │ image: anihpj:v1    │       │ "image": "anihpj:v1" ││
│   │     │  │ env: &db            │       │ (no anchors, must     ││
│   │     │  │   DB_HOST: db.svc   │       │  copy-paste repeats)  ││
│   │     │  │ command: |          │       │ "cmd": "line1\nline2"││
│   │     │  │   line1              │       │ (escaped strings 😱)  ││
│   │     │  │   line2              │       │                      ││
│   │     │  └──────────────────────┘       └──────────────────────┘│
│   │     │                                                         │
│   │     │  CRITICAL FACT: K8s stores everything as JSON in etcd  │
│   │     │  YAML → kubectl → JSON → API Server → etcd (JSON)       │
│   │     │  YAML is HUMAN-FRIENDLY INPUT; JSON is the MACHINE format│
│   │     └─────────────────────────────────────────────────────────┘

│   ├── 2.5 Infrastructure as Code (IaC) with Tofu/Terraform [s2-5]
│   │     • Declarative infrastructure: "I want a VPC with CIDR 10.0.0.0/16"
│   │       NOT "provision this, then that, then configure this..."
│   │     • anihpj infrastructure as code: VPC, subnets, security groups,
│   │       RDS instance, EKS cluster — ALL in Terraform
│   │     • State management: Terraform tracks what it created in state file
│   │     • Drift detection: terraform plan shows if reality ≠ declared state
│   │
│   │     📊 INFRASTRUCTURE AS CODE — The Declarative Infrastructure Pattern
│   │     ┌─────────────────────────────────────────────────────────┐
│   │     │                                                         │
│   │     │  # anihpj/infra/main.tf                                 │
│   │     │  resource "aws_vpc" "anihpj" {                          │
│   │     │    cidr_block = "10.0.0.0/16"                           │
│   │     │    tags = { Name = "anihpj-vpc" }                       │
│   │     │  }                                                      │
│   │     │                                                         │
│   │     │  resource "aws_db_instance" "anihpj_db" {               │
│   │     │    engine         = "postgres"                          │
│   │     │    engine_version = "15.4"                              │
│   │     │    instance_class = "db.t3.medium"                      │
│   │     │    allocated_storage = 20                               │
│   │     │    username = var.db_username                           │
│   │     │    password = var.db_password  # from secrets manager   │
│   │     │  }                                                      │
│   │     │                                                         │
│   │     │  $ terraform plan    # Shows: 2 to add, 0 to change    │
│   │     │  $ terraform apply   # Creates VPC + RDS               │
│   │     │  $ terraform plan    # Shows: 0 to change (no drift!)  │
│   │     │                                                         │
│   │     │  KEY CONCEPT: IaC = declarative infrastructure.         │
│   │     │  Same principles as Kubernetes manifests — just for     │
│   │     │  cloud resources instead of container workloads.        │

│   ├── 2.6 Git as the Single Source of Truth [s2-6]
│   │     • Every platform change = a Git commit with author, timestamp, diff
│   │     • Audit trail: "Who changed replicas from 3 to 5?" → git log answers
│   │     • Rollback: git revert → ArgoCD auto-reverts the cluster
│   │     • Code review: PR → review → approve → merge → auto-deploy

│   │     • Compliance: SOC2/PCI-DSS auditors LOVE Git-based audit trails

│   ├── 4.3 Containers vs Virtual Machines [s4-3]
│   │     • Containers: Process-level isolation sharing host kernel. Fast, small,
│   │       portable. "Not a mini VM — a process with boundaries"
│   │     • VMs: Full OS per instance. Strong isolation. Heavy. Slow to boot.
│   │     • When to use which: Containers for apps (stateless, microservices).
│   │       VMs for strong isolation needs (multi-tenant hosting, legacy apps,
│   │       different OS kernels, untrusted workloads)
│   │     • The CNPA mostly works with containers — but may manage VM-based infra too
│   │
│   ├── 4.4 Kubernetes as the Universal Control Plane [s4-4]
│   │     • Abstracting infrastructure behind a SINGLE consistent API
│   │     • kubectl apply works the same whether your cluster is on AWS, GCP,
│   │       Azure, or bare metal — the K8s API masks the underlying differences
│   │     • This is WHY platform engineering uses K8s: one API to rule all infra
│   │     • Crossplane takes this further: manage cloud resources via K8s API
│   │       (kubectl create -f rds-instance.yaml → provisions actual AWS RDS)
│   │
│   ├── 4.5 Cluster API (CAPI) — Managing Clusters with K8s [s4-5]
│   │     • Meta-Kubernetes: Use K8s to manage K8s clusters
│   │     • Define a "Cluster" CRD → CAPI controller provisions VMs,
│   │       installs K8s, configures networking → working cluster
│   │     • CAPI supports: AWS (EKS), GCP (GKE), Azure (AKS), vSphere, bare metal
│   │     • "The platform that builds platforms" — very meta, very CNPA
│   │
│   ├── 4.6 Namespaces, Labels, and Annotations [s4-6]
│   │     • Namespaces: Logical isolation within a cluster — "virtual clusters"
│   │       • anihpj-dev, anihpj-staging, anihpj-prod — separate namespaces
│   │       • Each namespace gets: ResourceQuota, NetworkPolicy, RBAC, PSA
│   │     • Labels: Key-value pairs for organization and selection
│   │       • app=anihpj, environment=production, team=platform, version=v1.2.3
│   │       • Used by: Services (selectors), Deployments (matchLabels),
│   │         NetworkPolicies (podSelector), scheduling (nodeSelector)
│   │     • Annotations: Key-value pairs for metadata (NOT for selection)
│   │       • kubernetes.io/change-cause: "Scaled to 5 replicas for Black Friday"
│   │       • prometheus.io/scrape: "true" — tells Prometheus to scrape this pod
│   │

│   ├── 4.7 Resource Requests, Limits & QoS [s4-7]
│   │     • Requests: MINIMUM guaranteed resources ("this pod needs at least 256Mi")
│   │     • Limits: MAXIMUM allowed resources ("this pod can't exceed 512Mi")
│   │     • QoS Classes (Quality of Service) — how K8s prioritizes pods under pressure:
│   │       • Guaranteed: requests == limits for CPU AND memory (highest priority)
│   │       • Burstable: at least one container has request < limit (medium)
│   │       • BestEffort: no requests or limits set (lowest — killed FIRST)
│   │     • anihpj-api: requests={cpu:250m, mem:256Mi}, limits={cpu:500m, mem:512Mi}
│   │       → Burstable QoS
│   │
│   │     📊 QOS CLASSES — Who Gets Killed First Under Memory Pressure
│   │     ┌─────────────────────────────────────────────────────────┐
│   │     │                                                         │
│   │     │  Memory Pressure: Node running out of RAM               │
│   │     │                                                         │
│   │     │  🥇 GUARANTEED (requests == limits)                     │
│   │     │     • Killed LAST — K8s tries hard to keep these alive  │
│   │     │     • anihpj-db: requests=2Gi, limits=2Gi               │
│   │     │                                                         │
│   │     │  🥈 BURSTABLE (request < limit)                         │
│   │     │     • Killed if needed, after BestEffort                │
│   │     │     • anihpj-api: requests=256Mi, limits=512Mi          │
│   │     │                                                         │
│   │     │  🥉 BESTEFFORT (no requests/limits)                     │
│   │     │     • Killed FIRST — no guarantees at all               │
│   │     │     • Only use for dev/test, NEVER for production apps  │
│   │     │                                                         │
│   │     │  CNPA BEST PRACTICE: Always set requests + limits for   │
│   │     │  production workloads. Use LimitRange to enforce in     │
│   │     │  namespaces. Use ResourceQuota to cap per-namespace.    │
│   │     └─────────────────────────────────────────────────────────┘
│   │
│   ├── 4.8 Service Discovery & Load Balancing [s4-8]
│   │     • How anihpj-api finds anihpj-db: DNS resolution
│   │       • anihpj-db.anihpj-prod.svc.cluster.local
│   │       • Resolves to ClusterIP (virtual IP) → kube-proxy → pod IP
│   │     • Service types: ClusterIP (internal), NodePort (external on node),
│   │       LoadBalancer (cloud LB), ExternalName (DNS alias), Headless (no ClusterIP)
│   │     • kube-proxy modes: iptables (default), IPVS (high-performance)
│   │     • Load balancing: Service distributes across all Ready pods

│   │     • HA control plane: 3+ master nodes, etcd quorum (odd number ≥3)
│   │     • HA data plane: pods replicated across nodes, topology spread
│   │     • Scaling: Cluster Autoscaler (adds/removes nodes), HPA (scales pods
│   │       based on CPU/memory/custom metrics), VPA (adjusts resource requests)
│   │     • Node pools: different instance types for different workloads
│   │       (spot instances for batch jobs, on-demand for production APIs)

│   ├── 5.6 Platform Extensibility — CRDs, Operators, Webhooks [s5-6]
│   │     • Extend K8s API for platform-specific resources
│   │     • CRDs: "I want K8s to understand what a 'Database' is"
│   │       → kubectl get databases → shows all provisioned databases
│   │     • Operators: CRD + custom controller = automated lifecycle management
│   │       → "When a Database CR is created, provision PostgreSQL on AWS RDS"
│   │     • Admission Webhooks: Intercept API calls to validate/mutate
│   │       → Mutating: auto-inject sidecars, labels, defaults
│   │       → Validating: reject if security policies violated
│   │     • anihpj: Custom "JobBoard" CRD → operator provisions Deployment,
│   │       Service, Ingress, PVC, NetworkPolicy — all from ONE custom resource

│   ├── 5.7 Platform Security Architecture [s5-7]
│   │     • Defense in depth — no single security layer, MULTIPLE overlapping layers:
│   │       Layer 1: Network Policies (pod-to-pod firewall)
│   │       Layer 2: mTLS via service mesh (encrypt ALL pod traffic)
│   │       Layer 3: RBAC (who can do what)
│   │       Layer 4: Pod Security Admission (restricted by default)
│   │       Layer 5: Admission Controllers (Kyverno policies)
│   │       Layer 6: Image scanning (Trivy in CI)
│   │       Layer 7: Image signing (Cosign + Kyverno verify)
│   │       Layer 8: Runtime detection (Falco)
│   │       Layer 9: Audit logging (who did what, when)
│   │       Layer 10: Secrets encryption (etcd EncryptionConfiguration)
│   │
│   ├── 5.8 Platform Networking & Storage Architecture [s5-8]
│   │     • Networking: CNI plugin (Cilium/Calico/Flannel) → pod networking
│   │       Service Mesh (Istio/Linkerd) → mTLS, traffic management, observability
│   │       Ingress Controller (NGINX/Contour) → external traffic routing
│   │       Egress Gateway → controlled outbound access
│   │     • Storage: CSI drivers → attach cloud storage to pods
│   │       StorageClasses → dynamic provisioning (GP3 for anihpj-db)
│   │       Backup/DR → Velero backs up entire cluster to S3
│   │     • anihpj platform: Cilium CNI + Istio mesh + NGINX Ingress
│   │       + EBS CSI + Velero backup

│   │     • Speed: Deploy in minutes, not weeks. anihpj target: <5 min from push to prod

│   ├── 6.4 Build vs Buy vs Adopt Decisions [s6-4]
│   │     • Adopt (open source): K8s, ArgoCD, Prometheus, Backstage
│   │       — FREE, community support, industry standard, but YOU operate it
│   │     • Buy (managed/SaaS): EKS/GKE/AKS, GitHub Actions, PagerDuty
│   │       — Less operational burden, but cost $$$, less control
│   │     • Build (custom): Custom operator for anihpj, Backstage plugins,
│   │       internal CLIs — Perfect fit, but maintenance burden is YOURS
│   │     • Decision framework: Is it core to your business? Build.
│   │       Is it commodity infrastructure? Adopt or Buy.

│   │     ┌─────────────────────────────────────────────────────────┐

│   ├── 6.6 What is Continuous Integration (CI)? [s6-6]
│   │     • Merging code frequently (multiple times per day) with automated
│   │       verification: lint → type-check → unit tests → build → scan
│   │     • CI catches issues EARLY — "a bug caught in CI costs $20; a bug
│   │       caught in production costs $500 + customer trust"
│   │     • anihpj CI pipeline: GitHub Actions workflow triggered on every push:
│   │       → checkout code → setup Python 3.12 → install dependencies
│   │       → ruff lint → mypy type-check → pytest with coverage
│   │       → docker build → trivy scan → push to ECR → update Git SHA

├── Chapter 7: Observability Fundamentals [ch7]
│   ├── 7.1 The Three Pillars — Metrics, Logs, Traces [s7-1]
│   │     • Metrics = WHAT is happening (numerical measurements over time)
│   │     • Logs = WHY it happened (timestamped text records of activity)
│   │     • Traces = WHERE it happened (follow a request across services)
│   │     • Events = WHEN something changed (discrete state changes)
│   │     • Together they provide COMPLETE system visibility

│   ├── 7.2 Metrics with Prometheus [s7-2]
│   │     • Prometheus: The de-facto standard for cloud native metrics
│   │     • Data model: Counter (only increases — http_requests_total),
│   │       Gauge (goes up/down — cpu_usage_percent), Histogram (buckets
│   │       — request_duration_seconds), Summary (quantiles)
│   │     • PromQL: rate(http_errors[5m]) / rate(http_requests[5m]) > 0.05
│   │       → "Alert when error rate exceeds 5% over 5 minutes"
│   │     • Scraping /metrics endpoints: Prometheus pulls metrics from
│   │       pods every 15-60 seconds (PULL model, not PUSH)
│   │
│   │     📊 PROMETHEUS ARCHITECTURE — How It Works
│   │     ┌─────────────────────────────────────────────────────────┐

│   ├── 7.3 Logs with Loki [s7-3]
│   │     • Loki: Log aggregation with Prometheus-like query language (LogQL)
│   │     • "Like Prometheus, but for logs" — label-based indexing
│   │     • LogQL: {app="anihpj-api"} |= "ERROR" | json | line_format "{{.msg}}"
│   │     • Structured logging: anihpj emits JSON logs for easy parsing
│   │       {"ts":"2026-06-15T14:30:00Z","level":"error","msg":"DB timeout",
│   │        "app":"anihpj-api","duration_ms":320,"endpoint":"/api/jobs/"}
│   │     • Loki is CHEAP — it only indexes metadata (labels), not full text
│   │       (unlike Elasticsearch). Full text is stored compressed in object store.
│   │
│   │     📊 LOKI ARCHITECTURE — Log Aggregation for Platforms
│   │     ┌─────────────────────────────────────────────────────────┐
│   │     │                                                         │
│   │     │  ┌────────────────┐  ┌────────────────┐                │
│   │     │  │  anihpj-api    │  │  anihpj-web    │                │
│   │     │  │  stdout/stderr │  │  stdout/stderr │                │
│   │     │  └───────┬────────┘  └───────┬────────┘                │
│   │     │          │                   │                          │

├── Chapter 8: Secure Service Communication [ch8]
│   ├── 8.1 mTLS (Mutual TLS) [s8-1]
│   │     • Regular TLS: Client verifies SERVER's certificate (is this really
│   │       google.com?). Server does NOT verify the client.
│   │     • mTLS: BOTH sides verify each other's certificates
│   │       ("You prove you're anihpj-api, I prove I'm anihpj-db")
│   │     • Zero-trust networking: "Never trust, always verify" — even inside
│   │       your own cluster, every connection must be authenticated
│   │     • anihpj-api → anihpj-db: Both present certs signed by platform CA
│   │     • SPIFFE/SPIRE: Standard for workload identity in cloud native
│   │       • SPIFFE ID: spiffe://anihpj.io/ns/prod/sa/anihpj-api
│   │
│   │     📊 TLS vs mTLS — What's the Difference?
│   │     ┌─────────────────────────────────────────────────────────┐
│   │     │                                                         │
│   │     │  STANDARD TLS (One-way)                                 │
│   │     │  ┌──────────┐                    ┌──────────┐         │
│   │     │  │ CLIENT   │───────request──────▶│ SERVER   │         │
│   │     │  │ (Browser)│◀──certificate──────│ (Website)│         │
│   │     │  │          │  "Yep, it's legit"  │          │         │
│   │     │  │ ✅ Trusts│                    │ Who are   │         │

│   ├── 8.2 cert-manager — Automatic TLS [s8-2]
│   │     • cert-manager: K8s-native certificate management
│   │     • Auto-issues TLS certs from Let's Encrypt (or your own CA)

│   │       and *.anihpj.example.com (wildcard)

│   ├── 8.3 Service Mesh mTLS — Istio/Linkerd [s8-3]
│   │     • Service mesh: Infrastructure layer for service-to-service communication
│   │     • Sidecar proxy (Envoy/Linkerd-proxy) injected into every pod
│   │     • ALL traffic flows through the sidecar → automatic mTLS with
│   │       ZERO application code changes
│   │     • Beyond mTLS: traffic splitting, retries, timeouts, circuit breaking,
│   │       fault injection, observability (Golden metrics automatically)
│   │     • CNPA note: Service mesh is advanced; understand the concept,
│   │       value prop, and when to use vs when NOT to use

│   │     • Default: ALL traffic allowed between all pods (deny-all is opt-in)
│   │     • Policy defines: which pods (podSelector), can talk to which
│   │       pods/namespaces/IPs (ingress/egress), on which ports

│   │       • anihpj-api → anihpj-db :5432 ALLOW
│   │       • anihpj-api → anihpj-redis :6379 ALLOW
│   │       • Everything else → DENY (default-deny posture)
│   │     • CNPA EXAM: You'll be tested on NetworkPolicy YAML, label selectors,
│   │       namespace selectors, and default-deny policies

│   ├── 8.5 Ingress & Egress Controls [s8-5]
│   │     • Ingress: Controls EXTERNAL traffic INTO the cluster
│   │       • NGINX Ingress Controller + cert-manager for auto-TLS
│   │       • Path-based routing: /api/* → anihpj-api, /* → anihpj-web
│   │     • Egress: Controls OUTBOUND traffic FROM pods to outside
│   │       • Restrict pods can only reach: *.github.com, *.amazonaws.com
│   │       • Prevent data exfiltration: pod can't reach unknown IPs
│   │     • NetworkPolicy for egress + Egress Gateway (Istio) for L7 control

│   │     • External Secrets Operator (ESO): Syncs secrets from external

│   │       HashiCorp Vault) into K8s Secrets — auto-refresh!
│   │     • HashiCorp Vault: Enterprise-grade secrets management with
│   │       dynamic secrets, leasing, rotation, audit logging
│   │     • anihpj DB password flow:
│   │       AWS Secrets Manager → ESO → K8s Secret → Pod env var

│   │     ┌─────────────────────────────────────────────────────────┐
│   │     │                                                         │

├── Chapter 9: Policy Engines for Platform Governance [ch9]
│   ├── 9.1 What is Policy-as-Code? [s9-1]
│   │     • Automating governance with machine-enforceable rules
│   │     • "Policy: All deployments must have resource limits" — enforced by
│   │       CODE, not by email, not by manual review, not by hoping
│   │     • Three levels of policy enforcement:
│   │       Level 1: Documentation ("Please set limits") — nobody reads it
│   │       Level 2: Manual review ("PR reviewer checks") — humans miss things
│   │       Level 3: Policy-as-Code ("Kyverno rejects if no limits") — 100% enforced
│   │     • Policy engines: OPA/Gatekeeper (Rego), Kyverno (YAML), jsPolicy (JS)
│   │
│   │     📊 POLICY-AS-CODE — Three Levels of Enforcement
│   │     ┌─────────────────────────────────────────────────────────┐
│   │     │                                                         │
│   │     │  LEVEL 1: DOCUMENTATION (Doesn't Work)                  │
│   │     │  "README.md: Please set resource limits on all pods"    │
│   │     │  Result: 0% compliance. Nobody reads README.            │
│   │     │                                                         │
│   │     │  LEVEL 2: MANUAL REVIEW (Partially Works)               │
│   │     │  "PR reviewer: Check that limits are set"               │
│   │     │  Result: ~60% compliance. Humans miss things at 2am.    │
│   │     │                                                         │
│   │     │  LEVEL 3: POLICY-AS-CODE (Actually Works)               │
│   │     │  ┌──────────────────────────────────────────────────┐  │
│   │     │  │  Kyverno ClusterPolicy:                           │  │
│   │     │  │  "validate-resources":                            │  │
│   │     │  │    match: {kinds: [Deployment]}                   │  │
│   │     │  │    validate:                                      │  │
│   │     │  │      message: "You MUST set resource limits!"    │  │
│   │     │  │      pattern:                                     │  │
│   │     │  │        spec.template.spec.containers[].resources  │  │
│   │     │  │          .limits: {memory: "?*", cpu: "?*"}      │  │
│   │     │  └──────────────────────────────────────────────────┘  │
│   │     │  Result: 100% compliance. K8s rejects non-compliant.   │
│   │     │         Cannot be bypassed. Cannot be forgotten.        │
│   │     └─────────────────────────────────────────────────────────┘
│   │
│   ├── 9.2 Open Policy Agent (OPA) / Gatekeeper [s9-2]
│   │     • OPA: General-purpose policy engine (not just K8s — can govern
│   │       Terraform, Envoy, Kafka, SQL, any system with JSON input)
│   │     • Rego: OPA's policy language — declarative, query-based
│   │       "deny[msg] { input.request.kind == 'Deployment';
│   │         not input.request.object.spec.template.spec.containers[0]
│   │         .resources.limits }" → DENIED!
│   │     • Gatekeeper: K8s-specific integration of OPA — CRD-based
│   │       ConstraintTemplate (defines the policy LOGIC) +
│   │       Constraint (applies the policy with PARAMETERS)
│   │
│   ├── 9.3 Kyverno — Kubernetes-Native Policy Engine [s9-3]
│   │     • Kyverno: K8s-native policy engine — NO Rego required!
│   │       Policies are written in PURE YAML — same as K8s manifests
│   │     • Four policy types:
│   │       Validate: "Reject pods without liveness probes" — BLOCKS
│   │       Mutate: "Add default resource limits if missing" — MODIFIES
│   │       Generate: "Auto-create a NetworkPolicy in every new namespace" — CREATES
│   │       Verify Images: "Only allow images signed by Cosign" — CHECKS
│   │     • anihpj example: Kyverno policy auto-adds NetworkPolicy to every
│   │       namespace, validates all images are signed, enforces PSS restricted
│   │
│   │     📊 KYVERNO vs OPA/GATEKEEPER — Which to Choose?
│   │     ┌─────────────────────────────────────────────────────────┐
│   │     │                                                         │
│   │     │  KYVERNO (YAML-based)          OPA/GATEKEEPER (Rego)    │
│   │     │  ┌────────────────────────┐   ┌──────────────────────┐ │
│   │     │  │  ✅ Pure YAML policies  │   │  ✅ Extremely powerful│ │
│   │     │  │  ✅ Easy to learn       │   │  ✅ Not just K8s      │ │
│   │     │  │  ✅ Mutate + Generate   │   │  ✅ Large community   │ │
│   │     │  │  ✅ Built-in reporting  │   │  ✅ Fine-grained logic│ │
│   │     │  │  ⚠️  Less flexible      │   │  ❌ Rego learning curve│ │
│   │     │  │  ⚠️  K8s only           │   │  ❌ YAML+Rego mixing  │ │
│   │     │  └────────────────────────┘   └──────────────────────┘ │
│   │     │                                                         │
│   │     │  CNPA RECOMMENDATION: Start with Kyverno (easy).        │
│   │     │  Graduate to OPA/Gatekeeper if you need Rego's power.  │
│   │     │  Many platforms use BOTH — Kyverno for K8s policies,    │
│   │     │  OPA for Terraform and application-level policies.      │
│   │     └─────────────────────────────────────────────────────────┘
│   │
│   ├── 9.4 Admission Controllers & Webhooks [s9-4]
│   │     • Admission controllers: Intercept API requests to K8s API server
│   │       BEFORE the object is persisted to etcd
│   │     • MutatingAdmissionWebhook: Can MODIFY the request
│   │       (add sidecar, add labels, set defaults, inject secrets)
│   │     • ValidatingAdmissionWebhook: Can ACCEPT or REJECT
│   │       (reject privileged containers, reject unsigned images)
│   │     • Order: Mutating webhooks run FIRST, then Validating
│   │     • Built-in admission controllers: NamespaceLifecycle, ResourceQuota,
│   │       PodSecurity, LimitRanger, etc. (30+ built-in)
│   │
│   │     📊 ADMISSION CONTROL — The Request Flow
│   │     ┌─────────────────────────────────────────────────────────┐
│   │     │                                                         │
│   │     │  kubectl apply -f deployment.yaml                       │
│   │     │       │                                                 │
│   │     │  ┌────▼─────────────────────────────────────────────┐  │
│   │     │  │           KUBERNETES API SERVER                    │  │
│   │     │  │                                                  │  │
│   │     │  │  1. AUTHENTICATION ("Who are you?")              │  │
│   │     │  │     • Certificates, tokens, OIDC                  │  │
│   │     │  │     → IDENTITY: "user=alice, group=platform-team" │  │
│   │     │  │                                                  │  │
│   │     │  │  2. AUTHORIZATION ("What can you do?")            │  │
│   │     │  │     • RBAC: RoleBindings + ClusterRoleBindings    │  │
│   │     │  │     → ALLOWED: alice can create Deployments       │  │
│   │     │  │                                                  │  │
│   │     │  │  3. ADMISSION CONTROL ("Should we allow this?")   │  │
│   │     │  │                                                  │  │
│   │     │  │     a. MUTATING ADMISSION (can modify)            │  │
│   │     │  │        • Inject sidecar (Istio)                   │  │
│   │     │  │        • Add default resource limits (Kyverno)    │  │
│   │     │  │        • Add labels/annotations                  │  │
│   │     │  │                                                  │  │
│   │     │  │     b. VALIDATING ADMISSION (accept/reject)       │  │
│   │     │  │        • Reject if no liveness probe (Kyverno)    │  │
│   │     │  │        • Reject unsigned images (Kyverno)         │  │
│   │     │  │        • Reject privileged containers (PSA)       │  │
│   │     │  │                                                  │  │
│   │     │  │  4. PERSIST to etcd ✅                            │  │
│   │     │  └──────────────────────────────────────────────────┘  │
│   │     └─────────────────────────────────────────────────────────┘

│   ├── 9.5 Pod Security Standards (PSS) & Pod Security Admission (PSA) [s9-5]
│   │     • PSS defines 3 levels of pod security:
│   │       • Privileged: No restrictions (kube-system, CNI, CSI drivers)
│   │       • Baseline: Prevents known privilege escalations (no hostPath,
│   │         no hostNetwork, no privileged containers)
│   │       • Restricted: Most secure — enforces best practices (non-root,
│   │         readOnlyRootFilesystem, seccomp, drop ALL capabilities)
│   │     • PSA: Built-in K8s admission controller that enforces PSS
│   │       Label namespace: pod-security.kubernetes.io/enforce=restricted
│   │     • anihpj namespaces enforce "restricted" — no privileged containers
│   │       allowed in application namespaces ever
│   │
│   │     📊 POD SECURITY STANDARDS — The 3 Levels
│   │     ┌─────────────────────────────────────────────────────────┐
│   │     │                                                         │
│   │     │  🔓 PRIVILEGED (Unrestricted) — kube-system, infra      │
│   │     │  ┌──────────────────────────────────────────────────┐  │
│   │     │  │  • Can do ANYTHING                                │  │
│   │     │  │  • hostPath volumes allowed                       │  │
│   │     │  │  • hostNetwork, hostPID allowed                   │  │
│   │     │  │  • Privileged containers allowed                  │  │
│   │     │  │  Use ONLY for: CNI plugins, CSI drivers, kube-proxy│  │
│   │     │  └──────────────────────────────────────────────────┘  │
│   │     │                                                         │
│   │     │  🟡 BASELINE (Minimum security) — Legacy apps          │
│   │     │  ┌──────────────────────────────────────────────────┐  │
│   │     │  │  • Blocks KNOWN privilege escalations             │  │
│   │     │  │  • NO hostPath (except allowed types)             │  │
│   │     │  │  • NO hostNetwork, hostPID                        │  │
│   │     │  │  • NO privileged containers                       │  │
│   │     │  │  Use for: Apps that need some host access         │  │
│   │     │  └──────────────────────────────────────────────────┘  │
│   │     │                                                         │
│   │     │  🟢 RESTRICTED (Best practice) — anihpj apps!          │
│   │     │  ┌──────────────────────────────────────────────────┐  │
│   │     │  │  • Everything in Baseline PLUS:                   │  │
│   │     │  │  • MUST run as non-root (UID > 0)                 │  │
│   │     │  │  • MUST have readOnlyRootFilesystem               │  │
│   │     │  │  • MUST drop ALL capabilities                     │  │
│   │     │  │  • MUST have seccomp profile                      │  │
│   │     │  │  Use for: ALL anihpj application pods              │  │
│   │     │  └──────────────────────────────────────────────────┘  │
│   │     │                                                         │
│   │     │  Enforcement: pod-security.kubernetes.io/enforce:       │
│   │     │  restricted (on anihpj-prod namespace label)           │
│   │     └─────────────────────────────────────────────────────────┘

├── Chapter 10: Kubernetes Security Essentials [ch10]
│   ├── 10.1 The 4 C's of Cloud Native Security [s10-1]
│   │     • Defense in depth across four layers — no single point of failure:
│   │       Cloud: Provider security (AWS/GCP/Azure IAM, VPC, encryption)
│   │       Cluster: K8s security (RBAC, PSA, NetworkPolicies, audit logging)
│   │       Container: Image security (scanning, signing, non-root, read-only)
│   │       Code: Application security (SAST, dependency scanning, secrets)
│   │
│   │     📊 THE 4 C's OF CLOUD NATIVE SECURITY
│   │     ┌─────────────────────────────────────────────────────────┐
│   │     │   CODE → CONTAINER → CLUSTER → CLOUD (Defense in depth) │
│   │     │   • Code: SAST (bandit), dep scan (safety), secrets     │
│   │     │   • Container: Trivy scan, Cosign sign, non-root user   │
│   │     │   • Cluster: RBAC, PSA restricted, NetworkPolicies      │
│   │     │   • Cloud: IAM roles, VPC, encryption at rest           │
│   │     │   An attacker must breach ALL 4 layers — not just one   │
│   │     └─────────────────────────────────────────────────────────┘
│   │
│   ├── 10.2 Authentication, Authorization & Admission (AAA) [s10-2]
│   │     • AuthN: "Who are you?" — Certificates, tokens, OIDC
│   │     • AuthZ: "What can you do?" — RBAC: Role → RoleBinding
│   │     • Admission: "Should we allow this request?" — Mutating → Validating
│   │
│   │     📊 AAA FLOW — Every API Request Goes Through This
│   │     ┌─────────────────────────────────────────────────────────┐
│   │     │  kubectl create deploy anihpj --image=anihpj:v1         │
│   │     │    │                                                    │
│   │     │    ├─▶ AUTH N ("Who?") → Cert/Token → ✅ Alice          │
│   │     │    ├─▶ AUTH Z ("What?") → RBAC → ✅ Can create deploys  │
│   │     │    └─▶ ADMISSION ("Should we?") → Kyverno/PSA → ✅/❌   │
│   │     │  IF ANY STAGE FAILS → REJECTED (401/403)                │
│   │     └─────────────────────────────────────────────────────────┘
│   │
│   ├── 10.3 RBAC — Role-Based Access Control [s10-3]
│   │     • Role: Namespace-scoped permissions (pods in anihpj-dev)
│   │     • ClusterRole: Cluster-wide permissions (nodes, PVs, all NS)
│   │     • RoleBinding: Binds Role → User/Group/SA in ONE namespace
│   │     • ClusterRoleBinding: Binds ClusterRole → User/Group/SA cluster-wide
│   │     • anihpj: anihpj-devs Role (pods, svc, deploy in anihpj-dev)
│   │
│   │     📊 RBAC — The Four Objects
│   │     ┌─────────────────────────────────────────────────────────┐
│   │     │  Role (permissions) → RoleBinding (connection) → Subject│
│   │     │  anihpj-dev-role: [get, list, create pods, deployments] │

├── Chapter 14: CI/CD Relationship & Deployment Strategies [ch14]
│   ├── 14.1 What is Continuous Delivery (CD)? [s14-1]
│   │     • CD: Automating deployment to production-ready state
│   │     • Every merge to main → auto-deploy to staging → manual approval → prod
│   │     • "Your software is ALWAYS in a deployable state"

│   ├── 14.2 CI vs CD — Where One Ends, the Other Begins [s14-2]
│   │     • CI: Code → Test → Build → Artifact (ends with a tested artifact)
│   │     • CD: Artifact → Deploy → Verify → Promote (deployment pipeline)
│   │     • "CI builds it. CD ships it."
│   │
│   │     📊 CI vs CD — The Boundary
│   │     ┌─────────────────────────────────────────────────────────┐
│   │     │                                                         │
│   │     │  ┌────────────── CI ──────────────┐                    │
│   │     │  │  Push → Lint → Test → Build    │                    │
│   │     │  │            → Artifact          │                    │
│   │     │  └──────────────┬─────────────────┘                    │
│   │     │                 │ Docker image + SBOM                  │
│   │     │  ┌──────────────▼─────────────────┐                    │
│   │     │  │       CD (Continuous Delivery) │                    │
│   │     │  │  Deploy Staging → Verify       │                    │
│   │     │  │  → Manual Approval → Deploy    │                    │
│   │     │  │  Production → Verify → Monitor │                    │
│   │     │  └────────────────────────────────┘                    │
│   │     └─────────────────────────────────────────────────────────┘
│   │
│   ├── 14.3 Continuous Delivery vs Continuous Deployment [s14-3]
│   │     • Delivery: Auto to staging, MANUAL approval to production
│   │     • Deployment: Auto ALL THE WAY to production (no human gate)
│   │     • anihpj: Uses Delivery (manual prod approval) — safer for business
│   │
│   ├── 14.4 Deployment Strategies [s14-4]
│   │     • Rolling update: Replace pods one-by-one (default in K8s)
│   │     • Blue/Green: Deploy new version alongside old, switch traffic at once
│   │     • Canary: Send small % of traffic to new version, increase gradually
│   │     • A/B Testing: Route users based on headers/cookies (not just %)
│   │     • anihpj: Rolling for patches, Blue/Green for majors, Canary for risky
│   │
│   │     📊 DEPLOYMENT STRATEGIES COMPARISON
│   │     ┌─────────────────────────────────────────────────────────┐
│   │     │                                                         │
│   │     │  ROLLING (default)          BLUE/GREEN                  │
│   │     │  ┌──┐ ┌──┐ ┌──┐           ┌──────────┐ ┌──────────┐   │
│   │     │  │v1│→│v2│→│v2│           │ v1 (BLUE)│ │v2 (GREEN)│   │
│   │     │  └──┘ └──┘ └──┘           │  active  │ │ standby  │   │
│   │     │  Gradual replacement      └──────────┘ └──────────┘   │
│   │     │  ✅ Simple, zero downtime     Switch traffic: v1→v2     │
│   │     │  ⚠️  Mixed versions briefly   ✅ Instant rollback       │
│   │     │                               ⚠️  Double resources     │
│   │     │                                                         │
│   │     │  CANARY                     A/B TESTING                 │
│   │     │  90% → v1  10% → v2        User-A → v1  User-B → v2   │
│   │     │  Gradual traffic shift     Route by user/header        │
│   │     │  ✅ Safe testing           ✅ User-specific features    │
│   │     │  ⚠️  Complex metrics       ⚠️  Requires Istio/Envoy    │
│   │     └─────────────────────────────────────────────────────────┘
│   │
│   ├── 14.5 Feature Flags — Decoupling Deploy from Release [s14-5]
│   │     • Deploy code HIDDEN behind feature flag
│   │     • Enable for 10% of users → verify → 50% → 100%
│   │     • If issues: DISABLE flag (instant), don't rollback code
│   │     • "Deploy is technical. Release is business decision."
│   │     • Tools: LaunchDarkly, Unleash, custom ConfigMap-based

│   ├── 14.6 Deployment Automation Tools [s14-6]

│   │     • Declarative: Desired state expressed as code (YAML manifests)
│   │     • Versioned: Every change is a Git commit with history
│   │     • Pulled Automatically: Agent pulls from Git (not pushed by CI)
│   │     • Continuously Reconciled: Agent constantly ensures cluster = Git
│   │     • These 4 principles from Weaveworks define what IS and ISN'T GitOps

│   ├── 15.3 Push vs Pull Deployment Models [s15-3]
│   │     • PUSH: CI/CD tool has cluster credentials → pushes YAML via kubectl
│   │       • Risk: If CI/CD is compromised, attacker has cluster access
│   │     • PULL: ArgoCD runs INSIDE the cluster, pulls from Git
│   │       • Safer: No external system has cluster credentials
│   │       • Auditable: ArgoCD logs "synced commit abc123 at 14:30"

├── Chapter 17: The Kubernetes Reconciliation Loop [ch17]
│   ├── 17.1 Observe → Diff → Act — The Heart of K8s [s17-1]
│   │     • Every controller runs an infinite loop: Observe current state →
│   │       Compare with desired state → Take action to converge
│   │
│   │     📊 THE RECONCILIATION LOOP (Every Controller Does This)
│   │     ┌─────────────────────────────────────────────────────────┐
│   │     │  ┌──────────┐    ┌───────────┐    ┌──────────┐        │
│   │     │  │ OBSERVE  │───▶│ COMPARE   │───▶│   ACT    │        │
│   │     │  │ (Get     │    │ (Diff?)   │    │ (Create/ │        │
│   │     │  │  current │    │           │    │  Update/ │        │
│   │     │  │  state)  │    │  Yes→Act  │    │  Delete) │        │
│   │     │  └──────────┘    │  No→Sleep │    └──────────┘        │
│   │     │                   └───────────┘                        │
│   │     │  Deployment Controller: wants 3 replicas, has 2 →     │
│   │     │  Act: create 1 more pod. Has 4 → Act: delete 1.       │
│   │     └─────────────────────────────────────────────────────────┘
│   │
│   ├── 17.2 Controllers and the Controller Pattern [s17-2]
│   │     • Each resource type has its own controller
│   │     • Deployment controller, ReplicaSet controller, Job controller, etc.
│   │     • Custom controllers (Operators) follow the SAME pattern
│   │
│   ├── 17.3 Controller Manager [s17-3]
│   │     • kube-controller-manager: Runs ALL built-in controllers
│   │     • Node controller, Replication controller, Endpoints controller,
│   │       ServiceAccount controller, Token controller... 30+ controllers
│   │
│   ├── 17.4 Level-Triggered vs Edge-Triggered [s17-4]
│   │     • K8s is LEVEL-triggered: "The world should look like THIS"
│   │       (current state compared to desired state)
│   │     • NOT edge-triggered: "This EVENT happened, react to it"
│   │     • If controller crashes, on restart it re-checks the full state
│   │       — no events are lost, the desired state is always in etcd
│   │
│   ├── 17.5 Controller Idempotency [s17-5]
│   │     • Running reconcile 1 time = running reconcile 100 times
│   │     • Safe to retry, safe to restart, no side effects from duplicates
│   │     • "Create pod if it doesn't exist" — after 1st run, pod exists,
│   │       subsequent runs are no-ops

│   │     │  ┌────▼────────────────────────────────────────────┐   │
│   │     │  │  JobBoard CRD (Custom Resource)                  │   │
│   │     │  │  name: anihpj-jobpost                            │   │
│   │     │  │  spec: {image: anihpj:v1.2.3, replicas: 3,      │   │
│   │     │  │         db: {engine: postgres, size: 20Gi}}     │   │
│   │     │  └────────────────────┬───────────────────────────┘   │
│   │     │                       │                                │
│   │     │  ┌────────────────────▼───────────────────────────┐   │
│   │     │  │  anihpj OPERATOR (Custom Controller)            │   │
│   │     │  │  Watches: JobBoard resources                    │   │
│   │     │  │  Reconcile: Creates/updates:                    │   │
│   │     │  │    ✅ Deployment (anihpj-api, 3 replicas)       │   │
│   │     │  │    ✅ Service (ClusterIP :8000)                 │   │
│   │     │  │    ✅ Ingress (anihpj.example.com)              │   │

│   │     │  │    ✅ NetworkPolicy (web→api, api→db)           │   │

│   │     • Day 0: Install/Create (provision everything)
│   │     • Day 1: Configure/Update (rolling upgrade)
│   │     • Day 2: Backup, Restore, Scale, Failover, Monitor
│   │     • "An Operator does Day 2 operations AUTOMATICALLY"

│   ├── 20.3 Operator SDK Frameworks [s20-3]
│   │     • Kubebuilder (Go): Most popular, used by K8s SIGs
│   │     • Operator SDK (Go/Helm/Ansible): Red Hat's framework
│   │     • Kopf (Python): Pythonic operator framework — great for anihpj
│   │     • Java Operator SDK: For JVM-based platforms

│   ├── 20.4 OLM — Operator Lifecycle Manager [s20-4]

│   │     • Idempotent reconciler (safe to re-run)

│   │     • Finalizers: Clean up external resources before deletion
│   │     • Owner References: Child resources auto-deleted with parent
│   │     • Error handling: Retry with backoff, never panic
