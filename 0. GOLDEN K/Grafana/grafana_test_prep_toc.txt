    │     │ POST /api/ds/query                                   │    │
    │     │ {                                                    │    │
    │     │   "queries": [{                                      │    │
    │     │     "refId": "A",                                    │    │
    │     │     "datasource": {"type": "prometheus", "uid": ".."}│    │
    │     │     "expr": "rate(http_requests_total{job=\"api\"}[5m│    │
    │     │              ])",                                    │    │
    │     │     "range": true,                                   │    │
    │     │     "interval": "15s"                                │    │
    │     │   }],                                                │    │
    │     │   "range": {"from": "now-1h", "to": "now"}           │    │
    │     │ }                                                    │    │
    │     └──────────────────────────────────────────────────────┘    │
    │                                                                 │
    │  3. Data source plugin (Go backend) forwards to Prometheus:     │
    │     GET /api/v1/query_range?                                    │
    │       query=rate(http_requests_total{job="api"}[5m])&          │
    │       start=1689000000&end=1689003600&step=15s                  │
    │                                                                 │
    │  4. Prometheus scans TSDB blocks, evaluates expression,         │
    │     returns: [{metric: {job:"api"}, values: [[t1,v1],...]}]    │
    │                                                                 │
    │  5. Grafana converts response → Data Frames (columnar format)   │
    │     ┌──────────────────────────────────────────────────────┐    │
    │     │ Data Frame:                                          │    │
    │     │   Fields:                                            │    │
    │     │     - time ([]time.Time)                              │    │
    │     │     - Value ([]float64)                              │    │
    │     │   Labels: {job: "api", method: "GET"}                 │    │
    │     │   Meta: {type: "timeseries-multi"}                   │    │
    │     └──────────────────────────────────────────────────────┘    │
    │                                                                 │
    │  6. Transformations applied (if any) → Data Frame modified     │
    │  7. Panel plugin receives Data Frames → renders SVG/Canvas     │
    │                                                                 │
    │  QUERY PERFORMANCE TIPS:                                        │
    │  • Use $__interval instead of hardcoded step values             │
    │  • Narrow time range in dashboard (don't query 30d in a panel)  │
    │  • Use recording rules for expensive queries                    │
    │  • Grafana caches query results per time range (configured      │
    │    per data source)                                             │

    │ 🔬 UNDER THE HOOD 4.1-4.4: Alert Evaluation Pipeline            │
    │ (How a metric crossing a threshold becomes a Slack message)      │
    ├─────────────────────────────────────────────────────────────────┤
    │                                                                 │
    │  ALERT LIFECYCLE (Grafana-managed alert):                        │
    │                                                                 │
    │  1. Alert Rule Definition:                                      │
    │     ┌──────────────────────────────────────────────────────┐    │
    │     │ Rule: "High Error Rate — anihpj-api"                  │    │
    │     │   Query A: rate(django_http_errors_total[5m])        │    │
    │     │   Reduce: avg (over 5m)                              │    │
    │     │   Threshold: IS ABOVE 5                               │    │
    │     │   Evaluate every: 1m                                  │    │
    │     │   For: 3m (Pending → Firing after 3 consecutive fails)│    │
    │     └──────────────────────────────────────────────────────┘    │
    │                                                                 │
    │  2. Grafana Scheduler (runs every 1m):                          │
    │     • Executes Query A against Prometheus                       │
    │     • Gets result: avg(error_rate) = 7.2                        │
    │     • Reduce: 7.2                                               │
    │     • Threshold check: 7.2 > 5 → TRUE                           │
    │                                                                 │
    │  3. State Machine:                                              │
    │     ┌──────────────────────────────────────────────────────┐    │
    │     │                                                      │    │
    │     │    ┌──────┐    condition true     ┌─────────┐        │    │
    │     │    │Normal│──────────────────────▶│Pending  │        │    │
    │     │    └──┬───┘                       └────┬─────┘        │    │
    │     │       │ condition false                 │              │    │
    │     │       ◀─────────────────────────────────┘              │    │
    │     │       │                                │              │    │
    │     │       │               true for 3m      │              │    │
    │     │       │              ┌──────────────────┘              │    │
    │     │       │              ▼                                 │    │
    │     │       │        ┌────────┐    resolved     ┌────────┐  │    │
    │     │       │        │Firing  │────────────────▶│Resolved│  │    │
    │     │       │        └────────┘                 └────────┘  │    │
    │     │       │                                              │    │
    │     │  Pending: Condition met, waiting "For" duration      │    │
    │     │  Firing:  Condition met for ≥ "For" duration         │    │
    │     │  Resolved: Condition no longer met (was Firing)      │    │
    │     └──────────────────────────────────────────────────────┘    │
    │                                                                 │
    │  4. Notification Routing:                                       │
    │     Alert enters root notification policy → matches labels:    │
    │     ┌──────────────────────────────────────────────────────┐    │
    │     │ Root Policy                                          │    │
    │     │   ├─ severity=critical  → PagerDuty (on-call)        │    │
    │     │   ├─ severity=warning   → Slack #alerts              │    │
    │     │   ├─ team=platform      → Slack #platform-alerts     │    │
    │     │   └─ (default)          → Email alerts@company.com   │    │
    │     └──────────────────────────────────────────────────────┘    │
    │                                                                 │
    │  5. Notification Template (Go template):                        │
    │     ┌──────────────────────────────────────────────────────┐    │
    │     │ 🔴 [FIRING] {{ .Alerts.Firing | len }} alert(s)      │    │
    │     │                                                     │    │
    │     │ {{ range .Alerts.Firing }}                          │    │
    │     │  Alert: {{ .Labels.alertname }}                     │    │
    │     │  Value: {{ .Values.B }} (threshold: {{ .Values.C }})│    │
    │     │  Dashboard: {{ .DashboardURL }}                     │    │
    │     │  Runbook: {{ .Annotations.runbook_url }}           │    │
    │     │ {{ end }}                                           │    │
    │     └──────────────────────────────────────────────────────┘    │
    │                                                                 │
    │  KEY INSIGHT: The "For" duration prevents alert flapping.       │
    │  Without it, a momentary spike (1 second of 100% error)         │
    │  would trigger the alert. With "For: 3m", only sustained         │
    │  problems fire. This is the difference between "the SRE         │
    │  ignores the alert" and "the SRE wakes up for it."             │
    └─────────────────────────────────────────────────────────────────┘

    │  5. Grafana uses access token to fetch user info:               │
    │     GET https://api.github.com/user                             │
    │     GET https://api.github.com/user/emails                      │
    │  6. Grafana maps GitHub user → Grafana user:                    │
    │     ┌──────────────────────────────────────────────────────┐    │
    │     │ GitHub User              → Grafana User              │    │
    │     │ login: "anihpj"          → username: "anihpj"        │    │
    │     │ email: "anihpj@dev.com"  → email: "anihpj@dev.com"  │    │
    │     │ teams: ["platform-eng"]  → role: Editor (via mapping)│    │
    │     └──────────────────────────────────────────────────────┘    │
    │  7. If user doesn't exist → auto-create (if allow_sign_up=true) │
    │  8. Grafana creates a session cookie (grafana_session)          │
    │  9. All subsequent requests: cookie → session → user identity   │
    │                                                                 │
    │  RBAC AUTHORIZATION FLOW:                                       │
    │  1. Request: GET /api/dashboards/uid/anihpj-overview            │
    │  2. Grafana checks: Is user authenticated? → YES                │
    │  3. Grafana checks: Does user have permission? → Check:         │
    │     • Org role: Viewer/Editor/Admin?                           │
    │     • Folder permission: Viewer/Editor/Admin for this folder?  │
    │     • Dashboard permission: Override?                          │
    │  4. If ANY permission level ≥ required → ALLOW                  │
    │  5. If NONE → 403 Forbidden                                     │
    │                                                                 │
    │  PERMISSION INHERITANCE:                                        │
    │  Org Role (Admin) → Folder (Editor) → Dashboard (Viewer)        │
    │  More specific permissions override less specific ones.         │
    │  Org Admin always has full access to everything.                │

───────────────────────────────────────────────────────────────────────
"This is about what to do when something breaks — a panel shows 'No Data,'
a query times out, a dashboard won't load. Troubleshooting is the skill
that separates Grafana users from Grafana experts. It's the equivalent of
the control tower radar going dark — you need to know exactly where to look."

Official sub-topics: Panel Troubleshooting | Data Source Errors | Query Failures |
Plugin Issues | Performance Problems | Log Investigation

6.1 Dashboard & Panel Troubleshooting (6 Qs)
    Q181: Panel shows "No data" — the systematic diagnostic checklist
          (Is data source healthy? Is time range correct? Is query correct? Are there results?)
    Q182: Panel shows "Data source not found" — UID mismatch, deleted data source, org mismatch
    Q183: Panel renders but values are wrong — incorrect query, wrong aggregation, wrong unit
    Q184: Dashboard import fails — JSON version mismatch, missing plugin, missing datasource
    Q185: Dashboard is slow to load — too many panels, too many queries, large time range
    Q186: Panel shows error messages — decoding the common Grafana error codes

    🟢 Q181-Q183: Novice | 🟡 Q184-Q186: Intermediate

6.2 Data Source Troubleshooting (4 Qs)
    Q187: "Data source connection refused" — wrong URL, service down, network policy, firewall
    Q188: "Authentication failed" — wrong credentials, expired token, TLS cert issue
    Q189: "Query timeout" — query too expensive, data source overloaded, time range too large
    Q190: "Bad Gateway / Proxy Error" — Grafana can't reach the data source through its proxy

    🟡 Q187-Q188: Intermediate | 🟣 Q189-Q190: Advanced

6.3 Query & Plugin Troubleshooting (4 Qs)
    Q191: PromQL query returns empty — label mismatch, counter reset, stale data
    Q192: LogQL query returns wrong results — label selector too broad/narrow, regex typo
    Q193: SQL query returns "relation does not exist" — schema mismatch, wrong database, permissions
    Q194: Plugin troubleshooting — unsigned plugin, incompatible version, missing dependency

    🟡 Q191-Q192: Intermediate | 🟣 Q193-Q194: Advanced

6.4 Performance & Log Investigation (6 Qs)
    Q195: Why is Grafana slow? — Browser dev tools, Network tab, Grafana server logs
    Q196: Grafana server logs — where to find them, how to read them, common log patterns
    Q197: High memory usage — too many dashboards, too many users, data source caching issues
    Q198: Grafana database issues — sqlite3 locked, PostgreSQL connection pool exhausted
    Q199: Common Grafana misconfigurations that cause problems:
          • root_url wrong → OAuth redirect loops
          • domain wrong → cookie issues
          • secret_key changed → all sessions invalidated
          • allow_sign_up=false + no admin → locked out!
    Q200: The Ultimate Grafana Troubleshooting Flowchart — START HERE for any issue:
          NODE 1: Is Grafana itself running? → systemctl status grafana-server → docker ps
          NODE 2: Is the data source healthy? → Data Sources → test connection
          NODE 3: Does a simple query work in Explore? → eliminate dashboard complexity
          NODE 4: Check server logs → /var/log/grafana/grafana.log
          NODE 5: Check browser console → CORS errors? JS errors?
          NODE 6: Isolate: create a new dashboard with ONE simple panel → does it work?
          NODE 7: If all else fails: restart Grafana, check disk space, check DB integrity

    🟡 Q195-Q198: Intermediate | 🟣 Q199-Q200: Advanced
