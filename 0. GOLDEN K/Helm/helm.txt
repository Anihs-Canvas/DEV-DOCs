    WHAT IS HELM?
    ─────────────
    Helm is the package manager for Kubernetes. Think of it as "apt/yum for K8s."
    It packages Kubernetes YAML manifests into reusable, versioned, configurable
    units called Charts. One `helm install` command can deploy an entire application
    stack — Deployments, Services, ConfigMaps, Ingresses, PVCs — all at once.

    WHY HELM MATTERS
    ────────────────
    Before Helm: Copy/paste 20 YAML files, manually change namespace, image tag,
    replicas in each. Error-prone, not reusable, not versioned.

    With Helm: `helm install easypj ./easypj-chart --set image.tag=v2.1`
    One command. Versioned. Reusable. Parameterized.

    Chapter 2: Installing & Configuring Helm
        WHY THIS CHAPTER EXISTS: You can't run a single command in the
        rest of this guide without a working `helm` binary talking to a
        real cluster. This chapter is the 10-minute setup tax you pay
        once so nothing else stalls on "command not found."
        🧠 MENTAL MODEL: Installing Helm is like installing a remote
        control — it doesn't do anything by itself, it just needs to be

    Chapter 4: Values & Configuration
        WHY THIS CHAPTER EXISTS: This is how ONE chart becomes THREE
        different deployments (dev/staging/prod) without three copies of
        the templates. Skip this and you're back to copy-paste YAML.
        🧠 MENTAL MODEL: values.yaml is a form with pre-filled defaults;
        --set and -f files are sticky notes covering specific fields —
        the form underneath never changes, only what's visible on top.

    🎯 EXAM TERMINOLOGY: update vs build — Not Interchangeable
    ┌───────────────────────────────────────────────────────────────────┐
    │ `helm dependency update` — reads Chart.yaml's dependencies        │
    │   block, resolves version constraints against the REPOSITORY      │
    │   (network call), downloads .tgz files into charts/, and          │
    │   regenerates Chart.lock.                                         │
    │ `helm dependency build` — reads the EXISTING Chart.lock and       │
    │   fetches the EXACT pinned archives (from local cache if present, │
    │   otherwise still a network call) WITHOUT re-negotiating version  │
    │   constraints against the repo. Use this in CI for reproducible   │
    │   builds — deterministic even if the repo's index has moved on.   │
    │ 🔑 Changed a version constraint in Chart.yaml? You need update.    │
    │    Just need charts/ repopulated from a committed Chart.lock?     │

    Chapter 10: Hooks & Lifecycle Management
        WHY THIS CHAPTER EXISTS: Some operations can't be a plain K8s
        resource — running a DB migration BEFORE the new pods start is
        a timing problem, not a resource problem. Hooks solve timing.
        🧠 MENTAL MODEL: Hooks are stage directions in a play script —
        "before Act 2 begins, dim the lights" — they run at a specific
        MOMENT in the install/upgrade lifecycle, not as part of the cast.
        ⚠️ GOTCHA: hook resources are NOT tracked by `helm uninstall` or
        `helm rollback` the way normal resources are — a failed hook Job
        can be left behind and needs manual cleanup. Two sanctioned
        cleanup paths beyond hook-delete-policy: the `helm.sh/resource-
        policy: keep` annotation (prevents Helm from EVER deleting a
        resource, distinct from hook-delete-policy) or Kubernetes' own
        Job field `ttlSecondsAfterFinished` (auto-cleanup independent
        of Helm entirely).
        📖 hook-weight defaults to 0 if the annotation is omitted —
        hooks without an explicit weight still execute, just at the
        "0" position relative to weighted ones.
        ⚡ SPEED TIP: `kubectl logs job/<hook-name>` is faster than
        digging through `helm get hooks` output when a hook fails.

    HOOK EXECUTION ORDER — HELM LIFECYCLE
    ──────────────────────────────────────
    ┌──────────────────────────────────────────────────────────────┐
    │  HELM INSTALL LIFECYCLE WITH HOOKS                           │
    │                                                              │
    │  helm install myapp ./chart                                  │
    │       │                                                      │
    │       ▼                                                      │
    │  ┌─────────────────┐                                         │
    │  │ pre-install     │  ← Hook: Job/ConfigMap (weight: -5)     │
    │  │ (run DB backup) │                                         │
    │  └────────┬────────┘                                         │
    │           ▼                                                  │
    │  ┌─────────────────┐                                         │

    │  │ K8s Manifests   │    (Deployment, Service, ConfigMap...)  │
    │  └────────┬────────┘                                         │
    │           ▼                                                  │
    │  ┌─────────────────┐                                         │
    │  │ post-install    │  ← Hook: Job (weight: 5)                │

    │           ▼                                                  │
    │  ┌─────────────────┐                                         │
    │  │ test            │  ← helm test (test pods)                │
    │  │ (verify app)    │                                         │

    │  HOOK TYPES: pre-install, post-install, pre-delete,          │

    │  WEIGHTS: Lower numbers run FIRST (-5 before 0 before 5)     │

    ┌──────────────────────────────────────────────────────────────────┐
    │ helm.sh/hook-delete-policy controls what happens to a COMPLETED  │
    │ hook Job so it doesn't collide with the next one (K8s Jobs are   │

    Chapter 13: Security Best Practices
        WHY THIS CHAPTER EXISTS: Helm has the same permissions as
        whoever runs it — get this wrong and a compromised CI pipeline
        can deploy anything, anywhere, with no guardrails.
        🏢 Not one of the 6 official exam domains — this is professional,
        production-hardening material every real deployment still needs.
        🧠 MENTAL MODEL: RBAC for Helm is a hotel keycard system — Helm
        itself has no master key, it only opens doors your kubeconfig can.
        ⚠️ GOTCHA: base64 in a K8s Secret is ENCODING, not encryption —
        anyone with `kubectl get secret -o yaml` access decodes it in one
        command. Treat Secrets as "obscured," not "protected."
        ⚡ SPEED TIP: "never commit to Git" questions almost always want
        Sealed Secrets or External Secrets Operator as the answer.

    SECRETS STRATEGY DECISION TREE — WHICH APPROACH DO I NEED?

    │       └─ YES ─▶ Must it be encrypted at rest in the repo?         │

    Appendix A: Helm CLI Quick Reference
        [WHY THIS APPENDIX EXISTS] Every command named anywhere in this
        guide, in one place, grouped by task — so a lookup never means
        re-reading a whole chapter.

        INSTALL, UPGRADE, ROLLBACK, UNINSTALL (Ch5)
        • helm install <name> <chart> [-f values.yaml] [--set k=v] — deploy a new release
        • helm install <name> <chart> -n <ns> --create-namespace — install into a new namespace
        • helm install <name> <chart> --atomic --wait --timeout 5m — on install, --atomic
          DELETES the failed release (nothing existed before to roll back to)
        • helm upgrade <name> <chart> --atomic --wait — on upgrade, --atomic auto-ROLLS BACK
          to the previous revision on failure — different behavior from install, same flag
        • helm upgrade <name> <chart> [--reuse-values|--reset-values] — update an existing release
        • helm upgrade --install <name> <chart> — idempotent install-or-upgrade (CI/CD)
        • helm rollback <name> [revision] [--wait] — revert to a previous revision
        • helm uninstall <name> [--keep-history] — remove a release (optionally keep history)

        CHART MANAGEMENT (Ch3, Ch12)
        • helm create <name> — scaffold a new chart
        • helm package ./chart [-d dir] — build a .tgz archive
        • helm package ./chart --sign --key '<id>' — sign the package (provenance)
        • helm verify chart.tgz — verify a signed chart's provenance
        • helm pull <chart> [--untar] — download a chart from a repo
        • helm show chart|readme|values|all <chart> — inspect a chart without installing

        REPO & REGISTRY (Ch2, Ch12)
        • helm repo add <name> <url> — register a chart repository
        • helm repo update — refresh local repo index cache
        • helm repo list / helm repo remove <name> — list / remove repos
        • helm repo index ./dir [--url <base-url>] — (re)generate index.yaml for an HTTP repo
        • helm search repo <term> — search only locally-added repos
        • helm search hub <term> — search Artifact Hub (global)
        • helm push chart.tgz oci://registry/repo — publish to an OCI registry
        • helm registry login/logout <registry> — authenticate to an OCI registry

        TEMPLATE DEBUGGING (Ch7, Ch11)
        • helm template ./chart [--debug] — render YAML locally, no cluster needed
        • helm lint [--strict] ./chart — validate structure & best practices, no cluster needed
        • helm install <name> <chart> --dry-run --debug — server-side validation, nothing created

        RELEASE INSPECTION (Ch5)
        • helm list / helm ls [-A] [--failed] [-n <ns>] — view releases
        • helm history <name> — revision timeline for a release
        • helm status <name> [--revision N] [-o yaml|json] — current release state
        • helm get all|values|manifest|hooks|notes <name> [--all] [--revision N] — inspect a release

        DEPENDENCY MANAGEMENT (Ch9)
        • helm dependency update — resolve + download deps from Chart.yaml (network, rewrites Chart.lock)
        • helm dependency build — fetch pinned versions from EXISTING Chart.lock (no re-negotiation)
        • helm dependency list — show declared vs. downloaded dependency status

        HOOKS & TESTING (Ch10, Ch11)
        • helm test <name> [--logs] — run a release's test hooks

        ENVIRONMENT & PLUGINS (Ch2)
        • helm version [--short] — client version (no cluster needed)
        • helm env — show all Helm paths/config locations
        • helm plugin install/list/update/uninstall — manage plugins
        • helm completion bash|zsh|fish|powershell — shell autocompletion setup

    Appendix B: Chart.yaml & values.yaml Reference
        [WHY THIS APPENDIX EXISTS] Two files every chart has; here's
        every field either can contain, in one lookup table.

        Chart.yaml FIELDS
        • apiVersion (REQUIRED, string) — v2 unlocks Helm-3-only features
          (Chart.yaml dependencies, library charts). v1 charts still
          install fine on Helm 3 for everything that doesn't need those.
        • name (REQUIRED, string) — must match the chart's directory name
        • version (REQUIRED, semver) — the CHART's own version, bumped on any chart change
        • kubeVersion (optional, semver range) — e.g. ">=1.25.0-0"; blocks incompatible clusters
        • description (optional, string) — one-line summary shown in helm search
        • type (optional, string) — application (default, deployable) or library (template-only)
        • appVersion (optional, string) — version of the deployed APPLICATION, independent of version
        • dependencies (optional, array) — subchart declarations: name, version,
          repository, condition, plus tags/alias/import-values (see Ch9 depth below)
        • deprecated (optional, boolean) — marks a chart deprecated; helm shows
          a warning on install (⚠️ missing from earlier versions of this appendix)
        • maintainers (optional, array) — name + email of chart maintainers
        • icon (optional, URL) — icon shown on Artifact Hub
        • annotations (optional, map) — arbitrary metadata, used for Artifact Hub categorization
        • keywords (optional, array) — search keywords
        • home / sources (optional) — project homepage / source repo URLs

        values.yaml BEST PRACTICES (Ch4, Ch3.1b)
        • Comment every key — the comments ARE the documentation
        • Ship SAFE, FUNCTIONAL defaults — `helm install name ./chart` should work with zero flags
        • Never put real secrets in values.yaml — placeholders only (Ch13.3)
        • Prefer nested objects over flat dotted keys (image.tag not imageTag) — matches dot-notation access

        SCHEMA VALIDATION SYNTAX — values.schema.json (Ch4.5, Ch11.6)
        • "type" — data type constraint (string/integer/boolean/object/array)
        • "required": [...] — mandatory top-level or nested keys
        • "minimum"/"maximum" — numeric bounds (e.g. replicaCount 1-50)
        • "enum": [...] — restrict to an allow-list (e.g. service.type)
        • "pattern" — regex constraint on a string (e.g. semver-shaped image tags)
        • "allOf"/"if"/"then" — conditional validation (e.g. "if tls=true, host is required")

    Appendix C: Template Functions Cheat Sheet
        [WHY THIS APPENDIX EXISTS] The 70+ Sprig functions plus Helm's
        own, organized by what you're trying to do — Ch7's deep dive
        compressed to one lookup pass.

        STRING — quote "x" · upper/lower "x" · trim "x" · trunc N "x"
                 replace "old" "new" "x" · nospace "x" · indent N · nindent N
                 EXAMPLE: {{ .Values.name | upper | quote }} → "EASYPJ"

        TYPE & CONVERSION — toYaml/fromYaml · toJson/fromJson · toString
                 EXAMPLE: {{ .Values.resources | toYaml | nindent 10 }}

        MATH — add · sub · mul · div · mod · max · min
                 EXAMPLE: {{ div .Values.usedCPU .Values.totalCPU | mul 100 }}

        DATE — now · date "2006-01-02" · dateModify "-24h" · htmlDate
                 EXAMPLE: {{ now | date "2006-01-02" }}

        DEFAULT & SAFETY — default "fallback" · required "msg" · empty · coalesce
                 EXAMPLE: {{ .Values.image.tag | default "latest" }}

        FLOW CONTROL — if/else/end · with/end · range/end · eq/ne/lt/gt/and/or/not
                 EXAMPLE: {{ if eq .Values.env "production" }}...{{ end }}

        NAMED TEMPLATES — define "name" ... end · template "name" . · include "name" . | pipe
                 RULE: always prefer include over template — only include supports pipelines

        PIPELINES — chain any of the above left-to-right with |
                 EXAMPLE: {{ .Files.Get "cfg" | fromYaml | toYaml | indent 4 }}

        ENCODING & HASHING — b64enc/b64dec · sha256sum · snakecase/camelcase/kebabcase
                 EXAMPLE: {{ include "x.configmap" . | sha256sum }} — config-change checksum (Ch7.16)

    │           "/configmap.yaml") . | sha256sum }}                          │

    Appendix E: Common Errors & Solutions
        [WHY THIS APPENDIX EXISTS] Every error a novice actually hits
        while building this guide's own examples, indexed by message —
        so hitting one means a 10-second lookup, not a re-read of Ch2-20.

        INSTALL / UPGRADE ERRORS (Ch2, Ch5, Ch20)
        1. "cannot re-use a name that is still in use" — Cause: a
           release with that name already exists (deployed OR failed).
           Fix: pick a new name, or `helm upgrade` instead of install.
        2. "another operation (install/upgrade/rollback) is in progress"
           — Cause: a prior op is stuck in pending-*. Fix: wait for it,
           or check `helm history` (Ch20.6) for a stuck revision.
        3. "Kubernetes cluster unreachable" — Cause: bad/expired
           kubeconfig, or cluster down. Fix: `kubectl cluster-info`
           first — Helm can't work if kubectl can't either.
        4. "helm: command not found" — Cause: binary not in PATH.
           Fix: move the binary to /usr/local/bin or fix PATH (Ch2.1).
        5. Client shows "v2.x.x" — Cause: Helm 2 (deprecated, Tiller-
           based) installed instead of v3. Fix: uninstall, reinstall v3
           via the official script (Ch2.1).
        6. "no repositories found" / "repo ... not found" — Cause: repo
           never added, or local cache stale. Fix: `helm repo add` then
           `helm repo update` (Ch2.4, Ch12.1).
        7. "timed out waiting for the condition" (with --wait) — Cause:
           a resource never reached Ready — bad readiness probe or
           image pull failure. Fix: `kubectl describe` the stuck pod.
        8. "rendered manifests contain a resource that already exists"
           — Cause: a same-named resource exists outside Helm's
           management. Fix: delete the conflicting resource, or adopt
           it deliberately with Helm's ownership annotations.

        TEMPLATE ERRORS (Ch6, Ch7, Ch11)
        9. "nil pointer evaluating interface {}.x" — Cause: referenced
           a .Values key that doesn't exist. Fix: wrap it in
           `| default "fallback"` or `required "msg"` (Ch7.3).
        10. YAML parse error, "did not find expected key" — Cause:
            usually `indent` used where `nindent` belongs, or vice
            versa, breaking indentation. Fix: see the indent/nindent
            gotcha box in Ch7.
        11. "template: chart/templates/X.yaml:14:23: executing..." —
            Cause: a syntax/logic error at that EXACT file:line. Fix:
            the error always names the file — open it, go to that line
            (Ch11's "tracking down error paths" box).
        12. "unable to build kubernetes objects from release manifest"
            — Cause: chart uses an apiVersion the cluster doesn't
            support. Fix: check `.Capabilities.KubeVersion` logic
            (Ch6.7), or the cluster's actual K8s version.
        13. "executing... map has no entry for key" — Cause: accessed
            a map key with dot notation on a nil/undeclared map. Fix:
            initialize the parent key in values.yaml, even as {}.

        DEPENDENCY ERRORS (Ch9)
        14. "found in Chart.yaml, but missing in charts/" — Cause:
            Chart.lock is out of sync with Chart.yaml's dependencies
            block. Fix: `helm dependency update` (Ch9.2).
        15. "unable to fetch chart from repository" during dependency
            update — Cause: wrong repository URL in the dependency
            entry, or stale repo cache. Fix: verify the URL, run
            `helm repo update` first.
        16. Subchart values not taking effect — Cause: values placed
            at the wrong nesting level (need `<subchart-name>: {...}`
            or `global:` — see Ch9.4). Fix: check the subchart's own
            values.yaml for its expected top-level key.

        HOOK & TEST ERRORS (Ch10, Ch11)
        17. "failed pre-install: job failed" — Cause: the hook Job's
            container errored. Fix: `kubectl logs` on the hook Job's
            pod — the real error is in there, not in Helm's output.
        18. Hook Job already exists on re-run — Cause: missing or
            wrong `helm.sh/hook-delete-policy`. Fix: add
            `before-hook-creation` (Ch10.3's annotation box).
        19. `helm test` shows FAILED with no useful detail — Cause:
            forgot the --logs flag. Fix: `helm test <name> --logs`.
            📖 Trivia: `"helm.sh/hook": test-success` is the pre-v3
            legacy test annotation — still accepted for backward
            compatibility, but new charts should use `test`.
        20. Release shows "deployed" but the live cluster looks
            different — Cause: someone changed resources directly
            with kubectl, bypassing Helm (release drift). Fix:
            `helm get manifest <name> | kubectl diff -f -`, or install
            the helm-diff plugin (Ch20.6).

    Appendix G: Helm & Kubernetes Glossary (NEW)
        [WHY THIS APPENDIX EXISTS] A novice hits unfamiliar vocabulary
        from BOTH Helm and Kubernetes at once. Every 📖 Key Term box in
        the guide points back here — this is the landing page for any
        term that resurfaces after its first explanation.

        HELM-SPECIFIC TERMS
        • Artifact Hub — public search engine indexing charts across
          many repositories; not itself a repository.
        • Atomic Install — --atomic flag; auto-rolls back the whole
          release if install/upgrade fails partway through.
        • Chart — a packaged, versioned bundle of Kubernetes YAML
          templates plus default values; Helm's unit of distribution.
        • Chart.lock — auto-generated file pinning exact dependency
          versions/digests for reproducible `helm dependency build`.
        • Chart.yaml — a chart's metadata file (name, version,
          apiVersion, type, dependencies).
        • ChartMuseum — open-source, self-hostable chart repository
          server.
        • Dry Run — --dry-run flag; renders and validates without
          actually applying anything to the cluster.
        • Global Values — values under `.Values.global`, visible to a
          parent chart and every subchart, for shared config.
        • Helmfile — a third-party tool for declaratively managing many
          Helm releases across environments from one file.
        • .helmignore — like .gitignore; excludes files from
          `helm package` archives.
        • Hook — a chart resource (usually a Job) that runs at a
          specific lifecycle moment (pre-install, post-upgrade, etc.)
          instead of alongside normal resources.
        • Hook Weight — an integer controlling hook execution order;
          lower numbers run first.
        • Library Chart — a chart of type `library`; provides reusable
          named templates only, cannot be installed on its own.
        • Named Template — a reusable template snippet defined with
          `define` and invoked with `template` or `include`.
        • OCI Registry — a container registry (e.g. ghcr.io, ECR) used
          to store charts as OCI artifacts alongside Docker images.
        • Pipeline (Helm) — chaining functions with `|`, each stage's
          output feeding the next stage's input.
        • Post-Renderer — an external tool Helm pipes its rendered YAML
          through before applying it (e.g. for Kustomize patches).
        • Provenance File (.prov) — a signature file proving a chart
          package's integrity and origin, created by `helm package --sign`.
        • Release — a specific running instance of an installed chart,
          identified by name + namespace.
        • Release Revision — an incrementing integer tracking every
          install/upgrade/rollback of a release.
        • Repository — a storage location (HTTP, OCI, or local) where
          charts are published and fetched from.
        • Rollback — reverting a release to a previous revision's
          configuration; creates a NEW revision, doesn't rewind time.
        • Schema Validation — validating user-supplied values against a
          chart's values.schema.json before install/upgrade.
        • SemVer (Semantic Versioning) — the MAJOR.MINOR.PATCH
          versioning scheme charts must follow.
        • Sprig — the Go template function library (70+ functions)
          Helm bundles in addition to Go's built-ins.
        • Storage Backend — where Helm persists release state
          (Kubernetes Secrets by default, historically ConfigMaps).
        • Subchart — a chart declared as a dependency of another chart,
          nested inside its charts/ directory.
        • Three-Way Merge — Helm 3's upgrade strategy comparing old
          manifest, new manifest, and live cluster state to avoid
          clobbering changes made outside Helm.
        • Tiller — Helm 2's removed server-side component; ran with
          broad cluster permissions and was a security liability.
        • Umbrella Chart — a parent chart with no templates of its own,
          existing only to bundle several unrelated charts together.
        • Values — the configuration layer (values.yaml, -f files,
          --set) that parameterizes a chart's templates.
        • values.schema.json — a JSON Schema file constraining what
          values a chart will accept.

        ADJACENT KUBERNETES TERMS
        • API Server — the Kubernetes control-plane component every
          client (including Helm) talks to; the single source of truth.
        • ClusterRole / RoleBinding — RBAC objects granting permissions
          cluster-wide or within a namespace.
        • ConfigMap — a Kubernetes object storing non-sensitive
          key-value configuration, mountable as env vars or files.
        • CRD (Custom Resource Definition) — extends the Kubernetes API
          with a new resource type (e.g. what Operators are built on).
        • CronJob — a Kubernetes object that runs a Job on a schedule.
        • Deployment — manages a set of identical Pods, handling
          rolling updates and self-healing.
        • etcd — the distributed key-value store backing the entire
          cluster's state.
        • HorizontalPodAutoscaler (HPA) — automatically scales replica
          count based on observed CPU/memory/custom metrics.
        • Ingress — routes external HTTP/HTTPS traffic into cluster
          Services based on host/path rules.
        • Job — runs a Pod to completion (e.g. a database migration),
          as opposed to a Deployment which runs indefinitely.
        • kubeconfig — the file (usually ~/.kube/config) holding cluster
          connection details and credentials kubectl/Helm both use.
        • kubectl — the Kubernetes command-line client for direct,
          imperative resource management.
        • Kubelet — the per-node agent that actually starts/stops
          containers as instructed by the API server.
        • Label / Selector — key-value tags on resources (Labels) and
          the queries that match them (Selectors) — how Services find Pods.
        • Namespace — a virtual cluster partition for isolating
          resources, RBAC, and quotas between environments/teams.
        • NetworkPolicy — rules restricting which Pods can talk to
          which other Pods/endpoints.
        • PersistentVolumeClaim (PVC) — a request for durable storage
          that a Pod can mount, surviving Pod restarts.
        • Pod — the smallest deployable unit in Kubernetes; one or more
          containers that share network/storage.
        • RBAC (Role-Based Access Control) — the permission system
          governing what a user/ServiceAccount is allowed to do.
        • Rolling Update — the default Deployment strategy: replace old
          Pods with new ones gradually, with zero downtime.
        • Secret — like a ConfigMap but for sensitive data
          (base64-encoded at rest, not encrypted by default).
        • SecurityContext — Pod/container-level settings controlling
          privilege, user ID, filesystem permissions, etc.
        • Service — a stable network endpoint routing traffic to a set
          of Pods (ClusterIP, NodePort, or LoadBalancer).
        • ServiceAccount — an identity Pods use to authenticate to the
          Kubernetes API — what Helm's RBAC permissions are usually tied to.
        • StatefulSet — like a Deployment but for stateful workloads
          needing stable network identity and storage per replica.

        CI/CD & ECOSYSTEM-ADJACENT TERMS
        • Argo CD — a GitOps continuous-delivery tool that can sync
          Helm releases from a Git repository automatically.
        • Blue-Green Deployment — running two full environments and
          switching traffic between them for zero-downtime releases.
        • Canary Deployment — gradually shifting a small percentage of
          traffic to a new version before a full rollout.
        • CNCF (Cloud Native Computing Foundation) — the foundation
          hosting Kubernetes, Helm, and related graduated projects.
        • Container Registry — a service storing container images
          (Docker Hub, ECR, GCR, ghcr.io).
        • GitOps — a delivery model where Git is the single source of
          truth and a controller (like Argo CD) reconciles the cluster
          to match it.
        • Kustomize — a template-free, patch-based Kubernetes
          customization tool, often compared/combined with Helm.
        • Operator — a Kubernetes controller + CRD pair automating
          day-2 operations for complex stateful applications.
