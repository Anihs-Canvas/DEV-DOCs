THE PROSE (as it would read)
-----------------------------
🏢 Real-World Analogy: Running an Apartment Portfolio

Think of a Kubernetes cluster as a property-management company that
runs dozens of apartment buildings. You, the administrator, don't
personally paint walls or fix leaks — you write down the rules every
unit must meet ("working water, heat, two smoke detectors") and the
management system enforces them around the clock. If a unit fails
inspection, nobody calls you at 3 AM: the system already knows the
rule, finds the gap, and fixes it or moves the tenant to a working
unit on its own. That is the entire idea behind Kubernetes in one
sentence — you declare the desired state, and the system relentlessly
makes reality match it, without you standing over its shoulder.

WHY THIS BOX, AND WHY NOT .cka-gotcha
--------------------------------------
Goal: correct the 3 wrong mental models almost every newcomer walks
in with, BEFORE Chapter 1 builds on top of them — this is the "hasten
understanding" lever discussed: fixing a wrong assumption early is
cheaper than un-learning it three chapters later.

I looked at reusing the existing .cka-gotcha component (the chapter-
closing "Gotchas" box, with red left-border + gotcha-wrong/correct
spans) but its CSS auto-injects the banner text
"⚠️ EXAM GOTCHA — common mistakes" via a ::before rule. That framing
is wrong here — this isn't an exam-technique gotcha, it's a beginner-
orientation correction before the reader has even met the material.

So instead this reuses .info-box.warning (generic amber callout,
already used throughout the guide for "heads up" notes) with plain
❌ / ✅ prefixes — no dependency on .cka-gotcha's exam-specific styling
or auto-banner.


THE PROSE (as it would read)
-----------------------------
🧭 Before You Start: 3 Things Beginners Get Wrong

❌ "Kubernetes is just a fancier way to run Docker."
✅ Docker (or any runtime) builds and runs ONE container. Kubernetes is
   the layer above it — deciding WHERE containers run, restarting them
   when they die, and keeping a whole fleet matching a rule you wrote,
   across many machines at once.

❌ "A Pod is basically a lightweight virtual machine."
✅ A Pod has no OS of its own and no fixed identity. It's a thin,
   disposable wrapper around one or more containers. Kubernetes
   EXPECTS Pods to die and be replaced — you don't patch them in
   place the way you'd patch a VM.

❌ "When something's broken, exec into the Pod (or SSH the server)
   and fix it directly."
✅ That fix vanishes the moment the Pod restarts or reschedules. The
   Kubernetes way: fix the YAML (the desired state) and let the
   cluster re-apply it everywhere — automatically, and permanently.

PART 1 COVER — VISUAL REDESIGN (DRAFT #3)
================================================================

THE PROBLEM WITH THE CURRENT LAYOUT
--------------------------------------
Checked the actual CSS (not guessing): .part-goal (green), .analogy-box
(purple), and .info-box.warning (amber) are all THE SAME visual pattern
— left-border color stripe + tinted background + rounded corners —
just recolored. Stacked three in a row, full-width, it reads as a
repeating "pile of colored stripes" rather than a designed cover, even
though each box's color is different.

MY FIRST IDEA (superseded below)
-----------------------------------
Originally proposed: put analogy-box and the myths box side-by-side in
a 2-column grid (.card-grid.cols-2) to break the vertical stack.
Rejected after closer look: the myths content is naturally a
myth-to-reality PAIRING (like a mini comparison table), and squeezing
that into a half-width column would cramp line-wrapping and hurt the
exact scannability this box exists for. Fighting the content's natural
shape isn't worth it just to get a 2-column layout.

THE BETTER FIX: VARY THE SHAPE, NOT JUST THE COLOR
-------------------------------------------------------
Instead of 3 same-shaped stripe-boxes, alternate the SHAPE:

  1. part-goal      -> stripe-box   (short single-paragraph statement)
  2. analogy-box     -> stripe-box   (narrative prose + ASCII diagram)
  3. myths            -> TABLE        (converted from stacked paragraphs
                                        into a real .comparison-table:
                                        "❌ What Beginners Think" |
                                        "✅ What's Actually True",
                                        3 rows)

A table has header-row gradient, alternating row shading, rounded
corners with shadow — a completely different visual rhythm from a
stripe-box. Box -> box -> table reads as "designed", not "the same
component copy-pasted with a new color." This ALSO reuses only
existing styling (.comparison-table is already used 100+ times in the
guide) — no new CSS.

The section label above the table reuses .diagram-title (the same
label style already used above the chapter-flow ASCII diagram lower on
this same cover) instead of an <h5> inside another stripe-box — so the
heading rhythm matches, without needing a 4th colored box.
