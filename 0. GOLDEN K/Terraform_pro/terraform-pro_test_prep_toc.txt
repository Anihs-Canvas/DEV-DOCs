F.1 What Problem Does Infrastructure as Code (IaC) Solve? 🟢 Novice
    • The "Snowflake Server" Problem — Every server is unique and irreproducible
    • From Manual Click-Ops → Shell Scripts → Config Management → IaC
    • Declarative vs Imperative — "I want 3 servers" vs "Create server 1, then 2, then 3"
    • The "It Works in Staging, Why Not Prod?" Problem — Config drift elimination
    • Real-world scenario: Deploying anihpj/jobpost manually vs with Terraform
        - Manual: 5 days, ~$1,500 engineering cost, unreproducible
        - Terraform: 25 minutes, ~$10, infinitely repeatable
    🟢 Novice | Visual: IaC Evolution Timeline + Before/After comparison diagrams
    🚀 Beyond: Platform Engineering — IaC as the foundation of Internal Developer Platforms

F.2 Terraform vs Other IaC Tools — The Landscape 🟢 Novice
    • Terraform vs CloudFormation vs Pulumi vs Ansible vs Bicep vs Crossplane
    • What makes Terraform unique: Multi-cloud, State File, Plan Preview, Dependency Graph
    • HCL (HashiCorp Configuration Language) — why a DSL instead of YAML/Python?
    • Terraform's 6 Killer Features:
        1. Multi-Cloud — One language for AWS, GCP, Azure, K8s, GitHub, etc.
        2. State File — Single source of truth (terraform.tfstate)
        3. Plan — Preview BEFORE you execute (THE safety feature)
        4. Dependency Graph — Automatic ordering (VPC → Subnet → EC2)
        5. Modules — Don't Repeat Yourself (build once, reuse everywhere)
        6. Providers — 3,000+ integrations (ANY API = a Terraform provider)
    • Comparison table: Tool | Type | Multi-Cloud | State Mgmt | Language | Maturity
    🟢 Novice | Visual: Tool comparison matrix + 6 Killer Feature cards

F.3 HCL (HashiCorp Configuration Language) — First Principles 🟢 Novice
    • What IS HCL? A declarative, human-readable configuration language
    • .tf file anatomy: Blocks, Arguments, Expressions, Identifiers
    • The 3 essential block types:
        - terraform {} — Settings (required_version, required_providers, backend)
        - provider {} — Cloud platform configuration (AWS region, credentials)
        - resource {} — Infrastructure objects you want to create
    • data {} blocks — Reading existing infrastructure (look up, don't create)
    • variable {} and output {} — Parameterizing and exposing values
    • locals {} — Named intermediate values (DRY principle)
    • Your first main.tf: A single aws_instance for anihpj-web
    • HCL syntax rules: comments (#, //, /* */), string interpolation (${var.name}),
      multi-line strings (<<EOT), boolean/null values
    🟢 Novice | Visual: HCL block anatomy diagram — every section labeled
    🟡 Intermediate: Type constraints, validation, sensitive variables

F.5 The Terraform Workflow — Core Loop (init → plan → apply → destroy) 🟢 Novice
    • terraform init — Initialize directory (download providers, configure backend)
        - What happens: reads provider requirements → downloads binaries → sets up .terraform/
        - -upgrade flag: Upgrade to latest allowed provider version
        - -reconfigure flag: Reconfigure backend (migrate state)
        - Provider lock file (.terraform.lock.hcl) — why you commit this to Git
    • terraform plan — Preview changes (NO side effects, SAFE to run anytime)
        - What happens: reads config → reads state → compares → outputs diff
        - Understanding plan output: + create, - destroy, ~ update in-place, -/+ replace
        - -out=FILE: Save plan for later apply (CI/CD: plan in PR, apply on merge)
        - -refresh-only: Update state to match reality (drift detection)
        - -target=RESOURCE: Plan only specific resources (use sparingly!)
    • terraform apply — Execute changes (THIS modifies infrastructure!)
        - What happens: re-runs plan → prompts for confirmation → executes changes
        - -auto-approve: Skip confirmation prompt (CI/CD pipelines)
        - -replace=RESOURCE: Destroy and recreate a specific resource (taint replacement)
        - Applying a saved plan file: terraform apply plan.out
    • terraform destroy — Tear down everything (USE WITH CAUTION!)
        - What happens: reads state → generates destroy plan → prompts → destroys ALL
        - -target=RESOURCE: Destroy only specific resource
        - The protection mechanisms: prevent_destroy lifecycle, deletion_protection
    • The State File Deep Dive:
        - terraform.tfstate — JSON map of config ↔ real infrastructure
        - Why state is critical: Without it, Terraform is blind
        - State locking (DynamoDB/S3) — prevents concurrent modifications
        - NEVER edit state manually (terraform state mv/rm/import instead)
    🟢 Novice | Visual: Core workflow cycle diagram + state file anatomy
    🟡 Intermediate: CI/CD integration, GitHub Actions pipeline example
