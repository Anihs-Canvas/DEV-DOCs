    1.1  The "Hello World" of K8s Networking — What Happens When a Pod Talks?
         - Two pods on the same node: how do they communicate?
         - Two pods on different nodes: the cross-node challenge
         - The Kubernetes Network Model — 4 fundamental rules every pod must follow
         - Analogy: Pod networking is like an office phone system
           • Each desk (pod) has its own extension (IP address)
           • The office PBX (CNI plugin) routes calls between extensions
           • Calling another building (cross-node) requires inter-office routing

         📖 Key Term: Kubernetes Network Model
         ┌──────────────────────────────────────────────────────────────┐
         │  THE 4 FUNDAMENTAL RULES (from kubernetes.io):               │
         │                                                               │
         │  1. Every Pod gets its OWN unique IP address                 │
         │     (No NAT, no port mapping — like every house has its      │
         │      own street address)                                     │
         │                                                               │
         │  2. Pods on a node can communicate with ALL pods on ALL      │
         │     nodes WITHOUT NAT (Network Address Translation)          │
         │     (Like being able to call any extension in any building)  │
         │                                                               │
         │  3. Agents on a node (kubelet, daemons) can communicate      │
         │     with ALL pods on that node                               │
         │     (Like the building manager can reach every desk)         │
         │                                                               │
         │  4. Pods see their OWN IP as what other pods see             │
         │     (No "inside vs outside" IP confusion)                    │
         │                                                               │
         │  💡 These 4 rules define the "flat network" model.           │
         │     CNI plugins implement these rules differently.           │
         │     Cilium implements them with eBPF — fastest way!          │
         └──────────────────────────────────────────────────────────────┘

    1.2  The CNI (Container Network Interface) Explained — Like Plugging in a Cable
         - What is a CNI plugin? Think of it as the "network driver" for Kubernetes
         - Analogy: CNI is like a USB standard
           • USB defines HOW devices connect (the interface)
           • CNI defines HOW pods get network connectivity (the interface)
           • Calico, Flannel, Cilium = different "USB devices" that follow the CNI spec
         - Popular CNIs: Calico (iptables), Flannel (VXLAN), Cilium (eBPF)
         - How CNI works: kubelet calls CNI → CNI assigns IP → Pod gets network
         - CNI configuration file: /etc/cni/net.d/*.conf

         📖 Key Term: Container Network Interface (CNI)
         ┌──────────────────────────────────────────────────────────────┐
         │  CNI is a SPECIFICATION, not software. It defines:           │
         │                                                               │
         │  • ADD command: "Give this container a network!"             │
         │    → CNI plugin allocates IP, creates veth pair, sets routes │
         │                                                               │
         │  • DEL command: "Remove this container's network!"           │
         │    → CNI plugin releases IP, removes veth, cleans up rules   │
         │                                                               │
         │  • CHECK command: "Is this container's network healthy?"     │
         │    → CNI plugin verifies connectivity                        │
         │                                                               │
         │  • VERSION command: "What CNI spec version do you support?"  │
         │                                                               │
         │  💡 CNI plugins are BINARIES on the node filesystem.          │
         │     kubelet executes them directly — no daemon needed!       │
         └──────────────────────────────────────────────────────────────┘

         [CNI FLOW DIAGRAM — kubelet → CRI → CNI Plugin]
         ┌──────────────────────────────────────────────────────────────┐
         │                                                               │
         │  ① kubelet watches API Server for new Pod assignments        │
         │       │                                                      │

    1.3  Where Cilium Fits in the Kubernetes Stack
         - Cilium replaces your old CNI (Calico/Flannel/Weave)
         - But it also replaces: kube-proxy, service mesh sidecars, network policy engine
         - One Cilium agent on each node = 4 tools consolidated into 1

         │  ┌─────────────────────────┐       ┌─────────────────────┐   │
         │  │ Tool 1: Calico/Flannel  │       │                     │   │

    2.1  What Happens When You Run "docker run anihpj"?
         - The Linux kernel features behind containers: namespaces (isolation) + cgroups (limits)
         - Types of namespaces: PID, Mount, UTS, IPC, User, and NETWORK
         - Network namespace: each container gets its own virtual network stack
           • Own interfaces (lo, eth0)
           • Own routing table
           • Own iptables rules
           • Own IP addresses (no conflict with host or other containers!)

         📖 Key Term: Linux Network Namespace
         ┌──────────────────────────────────────────────────────────────┐

         │  PRIVATE NETWORK ROOM. Inside the room:                      │

         │  • It has its own routing table ("how to reach the internet")│
         │  • It has its own firewall rules (iptables/nftables)         │
         │  • It has its own IP addresses                               │
         │                                                               │
         │  But it CAN'T see what's in OTHER rooms!                      │
         │  (unless connected via bridges/veth pairs)                   │
         │                                                               │
         │  💡 Namespaces are the reason containers can all use port    │
         │     8000 without conflicting — they're in different rooms!   │
         └──────────────────────────────────────────────────────────────┘

    2.2  How Containers in the Same Pod Share a Network Namespace
         - A Pod is NOT a container — it's a GROUP of containers sharing resources
         - The KEY shared resource: NETWORK NAMESPACE
         - The "pause container" (infra container) — the first container, holds the NS
         - Other containers JOIN the pause container's network namespace
         - Result: All containers in pod share localhost, same IP, same port space!

         [POD NETWORK NAMESPACE — The "Pause Container" Pattern (CRITICAL CONCEPT)]
         ┌──────────────────────────────────────────────────────────────┐
         │                                                               │
         │  POD: anihpj-web (One Pod, Three Containers)                  │
         │  ┌─────────────────────────────────────────────────────────┐ │
         │  │                                                          │ │
         │  │  ① PAUSE CONTAINER (created FIRST)                       │ │
         │  │     ┌────────────────────────────────────┐               │ │
         │  │     │  Creates & HOLDS the Network NS     │               │ │
         │  │     │  • IP Address: 10.0.0.55            │               │ │
         │  │     │  • Network interfaces: eth0, lo     │               │ │
         │  │     │  • Routing table, iptables rules    │               │ │
         │  │     │  • Just sleeps forever (PID 1)      │               │ │
         │  │     └───────────┬────────────────────────┘               │ │
         │  │                 │ "Join my network namespace!"            │ │
         │  │     ┌───────────┼───────────┐                            │ │
         │  │     │           │           │                            │ │
         │  │     ▼           ▼           ▼                            │ │
         │  │  ② DJANGO      ③ NGINX      ④ LOG SHIPPER                │ │
         │  │  Container     Container    Container                     │ │
         │  │  :8000         :80          (any port)                   │ │

         │  │  ✅ Can communicate via localhost (127.0.0.1)             │ │

         │  💡 This is why CNI only needs to network the PAUSE          │
         │     container — all other containers automatically           │

         [THE PAUSE CONTAINER — Why It Exists]
         ┌──────────────────────────────────────────────────────────────┐
         │  "Why not just network the first app container?"             │
         │                                                               │
         │  ❌ PROBLEM: If the first container crashes, the network     │

    2.5  kube-proxy Modes and Why Cilium Bypasses It Entirely
         - iptables mode: sequential rule matching — O(n) rules, slow at scale
         - IPVS mode: hash-based lookup — O(1), better but still in netfilter
         - nftables mode: newer kernel framework — still sequential
         - Cilium eBPF mode: O(1) hash lookup, kernel-native, NO iptables at all!
         - The performance gap: 5000 services → iptables: 5s update, eBPF: <1ms

         [KUBE-PROXY PERFORMANCE — iptables vs IPVS vs eBPF (Cilium)]
         ┌──────────────────────────────────────────────────────────────┐
         │                                                               │
         │  METRIC               IPTABLES      IPVS         CILIUM eBPF │
         │  ───────────────────  ────────────  ───────────  ─────────── │
         │                                                               │
         │  Rule Lookup Type     O(n) linear   O(1) hash    O(1) hash   │
         │  10 Services          ~1ms          <0.5ms       ~0.01ms     │
         │  100 Services         ~10ms         ~1ms         ~0.01ms     │
         │  1000 Services        ~100ms        ~5ms         ~0.02ms     │
         │  5000 Services        ~500ms+       ~25ms        ~0.05ms ⚡  │
         │                                                               │
         │  Rule Update Time     30+ seconds   500ms         INSTANT     │
         │  CPU at 5K Services   80%           40%          5% ⚡        │
         │  Connection Tracking   Yes           Yes          Yes (eBPF) │
         │  L7 Aware?            ❌            ❌            ✅ HTTP etc│
         │  DSR Mode?            ❌            ❌            ✅          │
         │  Observability?       ❌            ❌            ✅ Hubble   │
         │                                                               │
         │  💡 At scale, iptables becomes UNUSABLE. Cilium stays fast.  │
         │     This is why Cilium was built — iptables couldn't handle  │
         │     modern Kubernetes clusters with 1000s of services.       │
         └──────────────────────────────────────────────────────────────┘

         ┌──────────────────────────────────────────────────────────────┐
         │                                                               │
         │  For ONE Service with 3 endpoints, iptables creates:          │
         │                                                               │
         │  ┌──────────────────────────────────────────────────────┐    │

            → FIX: Use different PORTS for different containers in a pod.

         ❌ MISTAKE 2: Deleting the pause container manually
            → TRUTH: This destroys the network namespace for ALL pod containers.
            → FIX: Never manually touch the pause container.

         ❌ MISTAKE 3: Confusing Service ClusterIP with Pod IP
            → TRUTH: ClusterIP is VIRTUAL (no interface has this IP). Pod IPs are REAL.
            → FIX: Service IP only exists in iptables/eBPF rules — not on any interface.

    3.2  A Brief History: From BPF to eBPF — The Journey
         - 1992: BPF (Berkeley Packet Filter) created by Steven McCanne and Van Jacobson
           → Simple virtual machine for filtering packets (tcpdump -i eth0 'port 80')
         - 1997: Linux gets BPF support for socket filtering (SO_ATTACH_FILTER)
         - 2011: Eric Dumazet optimizes BPF with JIT compilation (3-4x speedup)
         - 2014: Alexei Starovoitov extends BPF → eBPF (10 registers, 512-byte stack, maps!)
           → Merged into Linux 3.18 — "the biggest kernel innovation in decades"
         - 2016: eBPF gets verifier improvements, map types expanded
         - 2017: Cilium project founded — first eBPF-based CNI
         - 2020: Cilium becomes CNCF incubating project
         - 2023: Cilium graduates CNCF — eBPF is now mainstream
         - Today: Meta, Google, Netflix, Cloudflare all use eBPF in production

    3.3  How eBPF Programs Work — The Complete Lifecycle
         - Step 1: WRITE (C code → compile to eBPF bytecode with clang/LLVM)
         - Step 2: LOAD (bpf() syscall → kernel verifier checks safety)
         - Step 3: VERIFY (verifier checks: no loops, bounds, valid memory, max 1M instructions)
         - Step 4: JIT COMPILE (bytecode → native x86/ARM machine instructions)
         - Step 5: ATTACH (hook to event: network packet, syscall, tracepoint, kprobe, etc.)
         - Step 6: EXECUTE (kernel runs your program on EVERY matching event!)
         - Step 7: COMMUNICATE (eBPF Maps — share data between kernel and userspace)

    3.6  Why eBPF is Faster Than iptables — The Architectural Difference
         - iptables: sequential rule matching — O(n), check rule 1, then 2, then 3...
         - eBPF: hash table lookup — O(1), directly find the right rule
         - At 1,000 rules: iptables ~10ms, eBPF ~0.01ms (1,000x faster!)
         - At 10,000 rules: iptables ~1,000ms (UNUSABLE), eBPF ~0.02ms (50,000x faster!)
         - Why: iptables walks a linked list. eBPF does a hash table lookup.
         - BONUS: eBPF runs in kernel space with JIT-compiled native code

         [PERFORMANCE DEEP DIVE — Why iptables Doesn't Scale]
         ┌──────────────────────────────────────────────────────────────┐
         │                                                               │
         │  IPTABLES (Sequential Chain Walk)         eBPF (Hash Lookup) │
         │  ┌──────────────────────────────┐        ┌──────────────┐    │
         │  │ For EACH packet:              │        │ Hash(key) →   │    │
         │  │                               │        │ bucket →      │    │
         │  │ Rule 1: dest 10.0.0.55?  ❌  │        │ value         │    │
         │  │ Rule 2: dest 10.0.0.99?  ❌  │        │              │    │
         │  │ Rule 3: dest 10.0.1.10?  ❌  │        │ ONE lookup!   │    │
         │  │ Rule 4: dest 10.0.1.88?  ❌  │        │ Independent   │    │
         │  │ ...                           │        │ of table size │    │
         │  │ Rule 4999: dest...       ❌  │        └──────────────┘    │
         │  │ Rule 5000: dest 10.0.5.5?✅ │                            │

    4.2  The Cilium Agent Deep Dive — What Happens at Startup?
         - Boot sequence of the Cilium Agent (the "brain" on each node):
           Step 1: Read ConfigMap for configuration
           Step 2: Detect kernel features (does this kernel support eBPF?)

    4.4  Identity-Based Networking — Cilium's Secret Sauce (CRITICAL CONCEPT!)
         - Traditional networking: rules based on IP ADDRESSES (fragile!)
           • "Allow 10.0.0.55 → 10.0.0.99 on port 5432"
           • Problem: Pod restarts → new IP → rules break!
         - Cilium networking: rules based on POD LABELS (robust!)
           • "Allow {app: anihpj} → {app: postgres} on port 5432"
           • Pod restart = new IP, SAME labels → rules still work!
         - How it works: Labels → hash → numeric identity → stored in eBPF maps
         - The identity number is a 32-bit integer (e.g., 12345)
         - eBPF maps store: IP → Identity, Identity → Policy (ALLOW/DENY)

         [IDENTITY-BASED POLICY — Complete Flow from Label to Enforcement]
         ┌──────────────────────────────────────────────────────────────┐
         │                                                              │
         │  STEP 1: LABELS → IDENTITY (Cilium Operator)                 │

         │  │  │ app: anihpj      │         │ app: postgres    │     │ │
         │  │  │ component: django│  hash   │ component: db    │ hash│ │
         │  │  │ env: production  │────────▶│ env: production  │────▶│ │
         │  │  └──────────────────┘         └──────────────────┘     │ │

    4.5  Cilium's eBPF Datapath — What Happens to EVERY Packet (DEEP DIVE)
         - This is the "hot path" — executed for every single packet
         - The eBPF programs are JIT-compiled to native code
         - Processing happens at TC hook (Traffic Control layer)

         [CILIUM eBPF DATAPATH — Complete Per-Packet Processing Pipeline]
         ┌──────────────────────────────────────────────────────────────┐
         │                                                              │
         │  📨 PACKET ARRIVES (from pod or network)                     │
         │       │                                                      │
         │       ▼                                                      │
         │  ┌──────────────────────────────────────────────────────┐   │
         │  │ 1. PRE-FILTER                                        │   │
         │  │    Is this packet for a Cilium-managed endpoint?     │   │
         │  │    • Check destination IP against Cilium IPAM        │   │
         │  │    • If NO → let kernel handle it normally           │   │
         │  │    • If YES → continue Cilium processing             │   │
         │  └──────────────────────┬───────────────────────────────┘   │
         │                         │ YES                               │
         │                         ▼                                   │
         │  ┌──────────────────────────────────────────────────────┐   │
         │  │ 2. IDENTITY LOOKUP (eBPF Map: IP_TO_IDENTITY)        │   │
         │  │    • Hash(src IP) → Source Identity (e.g., 12345)    │   │
         │  │    • Hash(dst IP) → Destination Identity (e.g.,67890)│   │
         │  │                                                       │   │
         │  │    If lookup fails → DROP with "unknown identity"    │   │
         │  └──────────────────────┬───────────────────────────────┘   │
         │                         │                                   │
         │                         ▼                                   │
         │  ┌──────────────────────────────────────────────────────┐   │
         │  │ 3. POLICY ENFORCEMENT (eBPF Map: POLICY_RULES)       │   │
         │  │    • Is there a CiliumNetworkPolicy for this dest?   │   │
         │  │    • Check L3/L4: SrcID→DstID:Port allowed?          │   │
         │  │    • Check L7 (if applicable): HTTP method? path?    │   │
         │  │                                                       │   │
         │  │    ┌─────┐                                            │   │
         │  │    │ALLOW?├──NO──▶ DROP packet 🔴                     │   │
         │  │    └──┬──┘           (Hubble: POLICY_DENIED)          │   │
         │  │       │ YES                                           │   │
         │  └───────┼──────────────────────────────────────────────┘   │
         │          │                                                   │
         │          ▼                                                   │
         │  ┌──────────────────────────────────────────────────────┐   │
         │  │ 4. CONNECTION TRACKING (eBPF Map: CT_MAP)            │   │
         │  │    • Is this an established connection?               │   │
         │  │    • If YES → fast-path forward (skip policy check)  │   │
         │  │    • If NO → create CT entry for future packets      │   │
         │  │                                                       │   │
         │  │    💡 CT dramatically improves performance!          │   │
         │  │       Only FIRST packet does full policy check.      │   │
         │  └──────────────────────┬───────────────────────────────┘   │
         │                         │                                   │
         │                         ▼                                   │
         │  ┌──────────────────────────────────────────────────────┐   │
         │  │ 5. FORWARD / DELIVER                                 │   │
         │  │    • Deliver packet to destination pod's interface   │   │
         │  │    • Or forward to next hop (cross-node)             │   │
         │  │    • Apply service load balancing if ClusterIP       │   │
         │  │    • Apply encryption if WireGuard enabled           │   │
         │  └──────────────────────┬───────────────────────────────┘   │
         │                         │                                   │
         │                         ▼                                   │
         │  ┌──────────────────────────────────────────────────────┐   │
         │  │ 6. HUBBLE EXPORT (eBPF Ring Buffer)                  │   │
         │  │    • Send flow event: {src, dst, port, verdict, bytes}│   │
         │  │    • Hubble Relay reads from Ring Buffer             │   │
         │  │    • Available in Hubble CLI and UI                   │   │
         │  └──────────────────────────────────────────────────────┘   │
         │                                                              │
         │  ⏱️ STEPS 1-6 complete in ~microseconds (JIT-native code!)  │
         └──────────────────────────────────────────────────────────────┘

    4.6  How Cilium Routes Cross-Node Traffic
         - Two modes for cross-node pod-to-pod communication:
         - Tunnel mode (default): VXLAN or Geneve encapsulation
           • Pod A packet → encapsulate in UDP → send to Node 2 → decapsulate → Pod B
           • Pro: Works on ANY network. Con: Some overhead (headers)
         - Direct routing mode: No encapsulation! Direct L3 routing
           • Requires the underlying network to know pod CIDRs
           • Pro: FASTER (no headers). Con: Requires network configuration
         - Cilium auto-detects the best mode

         [CROSS-NODE TRAFFIC — Tunnel vs Direct Routing]

         │                                                              │
         │  TUNNEL MODE (VXLAN/Geneve) — Default                        │

         │  │ Pod A (10.0.0.55) ──▶ Route table: "10.0.1.0/24 via   │  │
         │  │                        10.0.1.1" ──▶ Pod B (10.0.1.88) │  │
         │  │                                                         │  │
         │  │  No extra headers! Pure L3 routing. Faster!             │  │
         │  │  Requires: Network knows pod CIDRs (BGP, static routes) │  │
         │  └────────────────────────────────────────────────────────┘  │
         └──────────────────────────────────────────────────────────────┘

    ⚠️  Common Pitfalls (Chapter 4):

            → TRUTH: It's a DaemonSet — one per node. Critical distinction!
            → FIX: Check with: kubectl get ds -n kube-system cilium

         ❌ MISTAKE 2: Confusing CiliumIdentity with K8s ServiceAccount
            → TRUTH: CiliumIdentity is for network policy. ServiceAccount is for RBAC.
            → FIX: Identity = networking identity. ServiceAccount = API access identity.

         ❌ MISTAKE 3: Deleting CRDs without understanding Cilium's dependency
            → TRUTH: Deleting CiliumNode or CiliumIdentity CRDs can break networking!
            → FIX: Never manually delete Cilium CRDs. Use cilium uninstall.

         │  apiVersion: cilium.io/v2                                    │

         [HOW CILIUM EVALUATES NETWORK POLICIES — Rule Processing Order]
         ┌──────────────────────────────────────────────────────────────┐
         │                                                              │
         │  For EACH packet, Cilium checks in this order:               │
         │                                                              │
         │  ┌─────────────────────────────────────────────────────────┐ │
         │  │ 1. CNP (CiliumNetworkPolicy) — namespaced policies      │ │
         │  │    • Most specific — checked FIRST                       │ │
         │  │    • If CNP has a rule → USE IT (ALLOW or DENY)         │ │
         │  │                                                          │ │
         │  │ 2. CCNP (CiliumClusterwideNetworkPolicy) — cluster-wide │ │
         │  │    • Checked if NO matching CNP rule                    │ │
         │  │    • If CCNP has a rule → USE IT                         │ │
         │  │                                                          │ │
         │  │ 3. Default DENY (Cilium's secure default)                │ │
         │  │    • If NO policy matches → DENY the traffic 🔴          │ │
         │  │    • This is the "zero trust" default                    │ │
         │  └─────────────────────────────────────────────────────────┘ │
         │                                                              │
         │  💡 CNP OVERRIDES CCNP! Namespace policies take priority.   │
         │     Rule of thumb: more specific wins over more general.     │
         └──────────────────────────────────────────────────────────────┘

         │  │   │                       label (the TARGET)           │ │ │

         │  │   ┌───────────────────────────────────────────────────┐ │ │

         ┌──────────────────────────────────────────────────────────────┐
         │                                                              │
         │  ⚠️  NEVER enforce a policy immediately in production!        │
         │                                                              │
         │  THE 3-STEP SAFE ROLLOUT:                                    │
         │                                                              │
         │  STEP 1: AUDIT (1-7 days)                                    │

         │  └──────────────────────────────────────────────────────┘   │
         │            │                                                 │
         │            ▼                                                 │
         │  STEP 2: MONITOR                                              │

         │  │ Review audit logs in Hubble for 1-7 days              │   │
         │  │ Check: Any legitimate traffic being flagged?          │   │
         │  │ Tune policy if needed (add missing allows)            │   │
         │  └──────────────────────────────────────────────────────┘   │
         │            │                                                 │
         │            ▼                                                 │
         │  STEP 3: ENFORCE                                              │
         │  ┌──────────────────────────────────────────────────────┐   │
         │  │ Remove: enableAudit  (or set to false)                │   │
         │  │ Now policy actually DENIES traffic 🔴                 │   │
         │  │ Monitor closely for first 24 hours                    │   │
         │  └──────────────────────────────────────────────────────┘   │
         │                                                              │
         │  💡 Pro tip: Use audit mode for 1 WEEK before enforcing.     │

    ⚠️  Common Pitfalls (Chapter 7):
    ────────────────────────────────
         ❌ MISTAKE 1: Forgetting to allow DNS (port 53 to CoreDNS!)
            → SYMPTOM: Pods work then suddenly can't resolve any hostnames
            → FIX: Always add an egress rule allowing UDP 53 to kube-system

         ❌ MISTAKE 2: Using the wrong selector labels
            → SYMPTOM: Policy seems to have no effect
            → FIX: kubectl get pods --show-labels and verify exact label names

         ❌ MISTAKE 3: Confusing ingress and egress
            → TRUTH: ingress = traffic COMING INTO the selected pod
            → TRUTH: egress = traffic GOING OUT FROM the selected pod
            → FIX: For DB protection, use ingress on the DB pod selector
