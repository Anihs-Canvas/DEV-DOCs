📖 Key Term: Cognitive Load

Cognitive load is the mental effort required to navigate multiple disconnected tools, remember where information lives, and maintain context across systems. Backstage reduces cognitive load by providing a single, unified interface — one URL, one login, one search bar for everything.

1.2 What is an Internal Developer Portal (IDP)?

An Internal Developer Portal (IDP) is a centralized, self-service application that gives developers a single interface to discover, create, and manage all the software and infrastructure in their organization.

📖 Key Term: Internal Developer Portal (IDP)

An IDP acts as the "single pane of glass" for your engineering organization — it aggregates information from all your tools (GitHub, Jira, CI/CD, monitoring, docs) into one unified interface. Think of it as the office building directory that shows you every room, who sits where, and how to get there — instead of having to visit 10 separate information desks.

Backstage's 4 Core Pillars — The "What" Behind the Portal

Every IDP needs these capabilities. Backstage was built with all four from day one. Think of them as the four legs of a table — remove any one, and the developer experience collapses:

📋
Software Catalog — "What do we have?"

The central registry of every service, API, website, library, and resource in your organization. Think of it as a living CMDB that updates automatically from your repositories.

🚀
Software Templates — "How do I create something new?"

Pre-built scaffolding for new projects. Instead of every team inventing their own way to create a service, Backstage provides golden paths — one click, and you have a repo, CI/CD, and catalog registration.

📖
TechDocs — "Where are the docs?"

Documentation that lives WITH your source code (in /docs), built automatically by mkdocs, and displayed right on the service's page. Docs are always in sync because they're versioned with your code.

🔐
Plugins — "How do I see everything else?"

The extensibility layer. Plugins integrate every external tool (CI/CD, monitoring, cloud, project management) into Backstage. 200+ community plugins mean you rarely need to build integrations from scratch.

📋 1. Software Catalog

The beating heart of Backstage. A centralized registry of every service, API, website, library, and resource in your org — all described in YAML, stored alongside your code. For anihpj: jobpost-api, jobpost-web, postgres, redis — all visible in one place.

🚀 2. Software Templates

Golden paths to production. Instead of every developer figuring out how to create a new service, Backstage provides pre-built templates that scaffold a new repo, register it in the catalog, set up CI/CD — all in one click. anihpj's "New Django Microservice" template creates a fully bootstrapped service in 30 seconds.

📖 3. TechDocs

Documentation that lives with your code. Markdown files in your repo's /docs folder are automatically built into a static documentation site and embedded right on the entity page. No more "where's the wiki for this service?" — TechDocs is always up-to-date because it's versioned with your code.

🔐 4. Plugins

The extensibility superpower. Plugins are UI + backend modules that integrate external tools into Backstage. Want to see CI/CD status on your service page? Add the GitHub Actions plugin. Want Grafana dashboards? Add the Grafana plugin. 200+ community plugins available.

🏢 anihpj Scenario: Before vs After Backstage

Before: A new developer joins anihpj. They spend 2 weeks getting access to GitHub, Jira, Jenkins, Grafana, Confluence, Slack, PagerDuty, AWS, and the Kubernetes cluster. They have no idea which services exist, who owns them, or how to deploy.

After: The same developer opens backstage.anihpj.com on day one. They see all anihpj services in the Catalog, read their docs via TechDocs, create a test service from a template in 30 seconds, and deploy it — all from ONE interface. They're productive by lunchtime.

1.3 Backstage Architecture — The Big Picture

Backstage is a full-stack Node.js application with a React frontend and an Express.js backend — the same technology stack used by companies like Netflix, Uber, and (of course) Spotify. Let's look at the high-level architecture. Fun fact: Backstage was the first developer portal accepted into the CNCF, joining the ranks of graduated projects like Kubernetes, Prometheus, and Envoy.

📖 Key Concept: Plugin Architecture

Everything in Backstage is a plugin. The Catalog page is a plugin. The Templates page is a plugin. TechDocs is a plugin. Even Search is a plugin. This means Backstage is not a monolithic app — it's a plugin shell where every capability is an independently developed, tested, and versioned plugin. You can add, remove, or customize plugins without touching Backstage's core.

2.1 Frontend Architecture

📖 Key Concept: Plugin Mounting System

The frontend is not a monolithic React app — it's a plugin shell. When you create a Backstage app with createApp(), you register plugins that provide React components. These components are "mounted" into the app at specific extension points (entity pages, sidebar, homepage, etc.). Each plugin is isolated — it doesn't need to know about other plugins to function.

Frontend Plugin Structure

Every frontend plugin follows this pattern:

TypeScript — Frontend Plugin Pattern
// plugins/my-plugin/src/plugin.ts
import { createPlugin, createRoutableExtension } from '@backstage/core-plugin-api';

export const myPlugin = createPlugin({
  id: 'my-plugin',
  routes: {
    root: createRoutableExtension({
      name: 'MyPluginPage',
      component: () => import('./components/MyComponent').then(m => m.MyComponent),
      mountPoint: '/my-plugin',
    }),
  },
});

How the anihpj Portal Frontend Works

When a developer visits backstage.anihpj.com, here's what happens:

  1. React Router matches the URL to a route (e.g., /catalog/default/component/jobpost-api)
  2. The Catalog plugin renders the entity page for jobpost-api
  3. Other plugins (GitHub Actions, Grafana, TechDocs) mount their cards and tabs on that entity page
  4. Each plugin's frontend component makes API calls to its backend plugin via the Backstage proxy

📖 Key Concept: Backend Plugin Registration

Backend plugins are registered in packages/backend/src/index.ts. Each plugin creates an Express router and mounts it at a specific path prefix (e.g., /api/catalog). The main backend server composes all plugin routers into a single Express application. Plugins can also register database migrations that run on startup.

Database: PostgreSQL (Production) vs SQLite (Development)

Backstage ships with SQLite for local development (zero-config, file-based). For production, you must use PostgreSQL. The database stores:

  • Catalog entities — every Component, API, Resource, System, Domain, User, Group
  • User identities and tokens — authentication data
  • Search indices — if using PostgreSQL for search (alternative: Elasticsearch)
  • Scaffolder task history — logs of all template executions
  • Plugin-specific data — settings, preferences, etc.

2.3 The Plugin System — Extensibility Core

The plugin system is what makes Backstage more than just a static website. Everything is a plugin — even the core features like Catalog, Templates, and TechDocs.

Plugin Types

Plugin Communication

Plugins communicate through defined APIs — they don't directly import each other's code:

  • Frontend → Backend: Via the Backstage proxy (/api/proxy) or direct API calls to the backend plugin's router.
  • Backend → Backend: Via the plugin environment's service discovery — one backend plugin can call another's API.
  • Frontend → Frontend: Via shared React contexts and the Backstage core API — plugins can expose data to other plugins through extension points.
📖 Key Concept: Plugin Isolation

Plugins are independently developed, tested, and versioned. A bug in the Grafana plugin won't crash the Catalog plugin. This isolation is achieved through Backstage's plugin API — each plugin registers its routes, components, and APIs through well-defined interfaces, not by directly modifying the core application.

app-config.yaml — The Central Configuration Hub

YAML — app-config.yaml structure

organization:
  name: "anihpj"

backend:
  baseUrl: https://backstage.anihpj.com
  database:
    client: pg  # PostgreSQL for production
    connection:
      host: ${POSTGRES_HOST}
      port: ${POSTGRES_PORT}
      user: ${POSTGRES_USER}
      password: ${POSTGRES_PASSWORD}

auth:
  providers:
    github:
      development:
        clientId: ${GITHUB_CLIENT_ID}

catalog:
  locations:
    - type: url
      target: https://github.com/anihpj/jobpost-api/blob/main/catalog-info.yaml

scaffolder:
  github:
    token: ${GITHUB_TOKEN}

Configuration Hierarchy

  1. app-config.yaml — Base configuration (checked into git)
  2. app-config.local.yaml — Local overrides (gitignored, for development)
  3. app-config.production.yaml — Production overrides
  4. Environment Variables — Highest priority, used for secrets (never in YAML files)
⚠ CBA Exam Tip: Secrets Management

Never store secrets in app-config.yaml! Use environment variables (${ENV_VAR} syntax) for sensitive values like database passwords, GitHub tokens, and OAuth client secrets. app-config.yaml files are committed to git — secrets in them would be exposed.

FrontendWebpack dev server with HMR (hot module replacement)Compiled static files served by backend
Backendts-node with auto-reload on file changesCompiled JavaScript, no auto-reload
DatabaseSQLite (file-based, auto-created)PostgreSQL (must be configured)
AuthGuest access or development providersReal OAuth/OIDC providers
PortsFrontend :3000, Backend :7007 (separate)Single port :7007 (backend serves frontend)
Configapp-config.yaml + app-config.local.yamlapp-config.yaml + app-config.production.yaml
📖 Key Concept: Hot Module Replacement (HMR)

In development mode, when you edit a React component, Webpack's HMR injects the updated module into the running browser without a full page reload. This means you see changes in milliseconds rather than waiting for a rebuild. HMR is only available in development mode.

1
Build
yarn build — Compiles TypeScript to JavaScript, bundles frontend assets
2

yarn build-image — Creates a Docker image with the compiled app
3

Set app-config.production.yaml with PostgreSQL, real auth providers
4
Deploy
Deploy to Kubernetes, Cloud Run, or any container platform

3.3 Configuration Quick Start

Let's configure Backstage for the anihpj project. The minimum configuration you need:

YAML — app-config.yaml for anihpj
app:
  title: "anihpj Developer Portal"
  baseUrl: http://localhost:3000

organization:
  name: "anihpj"

backend:
  baseUrl: http://localhost:7007
  listen:
    port: 7007
  database:
    client: better-sqlite3  # SQLite for development
    connection: ':memory:'   # In-memory database for fast dev

auth:
  providers:
    guest: {}  # No login required for local development

catalog:
  import:
    entityFilename: catalog-info.yaml
  rules:
    - allow: [Component, API, Resource, System, Domain, User, Group]

scaffolder: {}

Configuring GitHub Integration for anihpj

To connect Backstage to anihpj's GitHub repositories, add a GitHub integration:

YAML — GitHub Integration
integrations:
  github:
    - host: github.com
      token: ${GITHUB_TOKEN}  # Personal access token (env variable!)

catalog:
  providers:
    github:
      organization: anihpj  # Auto-discover catalog-info.yaml in all repos
      schedule:
        frequency: { minutes: 30 }
        timeout: { minutes: 3 }
⚠ Important: Never commit tokens

The GitHub token uses ${GITHUB_TOKEN} — this reads from an environment variable, not the YAML file itself. Create a .env file (gitignored) or export the variable in your shell.

Chapter 3 Practice Questions (10)

Q1
What command creates a new Backstage application?
Click to reveal answer
✔ Correct Answer

npx @backstage/create-app@latest — this scaffolds a complete Backstage project with frontend, backend, and configuration.

📖 Explanation

The create-app package generates the entire monorepo structure: packages/app (frontend), packages/backend (backend), plugins/ directory, app-config.yaml, and all necessary configuration files.

Q2
What command starts Backstage in development mode?
Click to reveal answer
✔ Correct Answer

yarn dev — starts the frontend on port 3000 and the backend on port 7007, with hot module replacement enabled.

📖 Explanation

In dev mode, the frontend runs on Webpack dev server with HMR, and the backend runs on ts-node with auto-reload. Both watch for file changes automatically.

Q3
What are the three key directories in a Backstage project?
Click to reveal answer
✔ Correct Answer

packages/app (frontend), packages/backend (backend), and plugins/ (custom plugins). The root contains app-config.yaml, package.json, and TypeScript config.

📖 Explanation

Backstage uses a monorepo structure managed by Yarn workspaces. packages/app contains the React frontend, packages/backend contains the Express.js backend, and plugins/ contains custom plugins developed for your organization.

Q4
What database does Backstage use by default in development mode?
Click to reveal answer
✔ Correct Answer

SQLite — using either a file (better-sqlite3) or in-memory database. This is zero-config and ideal for development.

📖 Explanation

SQLite requires no installation or configuration — it's a self-contained file database. For production, you must switch to PostgreSQL for concurrent access, replication, and scaling.

Q5
How do you create a new plugin in Backstage?
Click to reveal answer
✔ Correct Answer

yarn backstage-cli plugin:create — this scaffolds a new plugin in the plugins/ directory with the proper TypeScript structure.

📖 Explanation

The CLI prompts for a plugin ID and generates the complete scaffold: src/index.ts (plugin registration), src/plugin.ts (plugin definition), src/components/ (React components), and package.json.

Q6
What is the difference between yarn dev and yarn start?
Click to reveal answer
✔ Correct Answer

yarn dev runs in development mode with hot reload, separate frontend/backend servers, and SQLite. yarn start runs a production build where the backend serves the compiled frontend on a single port.

📖 Explanation

yarn dev: Frontend on :3000 (Webpack HMR) + Backend on :7007 (auto-reload). yarn start: Single process on :7007 serving compiled static files + API. You must run yarn build before yarn start.

Q7
Where does Backstage store its configuration?
Click to reveal answer
✔ Correct Answer

In app-config.yaml at the project root. Environment-specific overrides go in app-config.local.yaml (dev) or app-config.production.yaml (prod).

📖 Explanation

app-config.yaml is the base configuration checked into git. app-config.local.yaml (gitignored) provides local overrides. app-config.production.yaml provides production overrides. Environment variables have the highest priority.

Q8
How do you configure authentication in Backstage?
Click to reveal answer
✔ Correct Answer

In the auth section of app-config.yaml. For development, you can use guest: {} (no login). For production, configure OAuth/OIDC providers like GitHub, Okta, or Google.

📖 Explanation

The auth section specifies which auth providers to enable and their credentials (via environment variables). Backstage supports GitHub, GitLab, Google, Okta, Auth0, Azure AD, and more.

Q9
What does the catalog-info.yaml file in the project root do?
Click to reveal answer
✔ Correct Answer

It registers Backstage itself as an entity in the catalog — self-documenting the portal. This is Backstage "eating its own dog food."

📖 Explanation

Backstage uses its own catalog-info.yaml to register itself as a Component. This means the Backstage instance appears in its own catalog, demonstrating the self-documenting nature of the platform.

Q10
How do you configure GitHub integration for the anihpj organization?
Click to reveal answer
✔ Correct Answer

Add an integrations.github section to app-config.yaml with the GitHub host and a personal access token (stored as an environment variable). Then add catalog.providers.github to auto-discover catalog-info.yaml files in anihpj repositories.

📖 Explanation

The GitHub integration requires a host entry (github.com) and a token for API access. The catalog provider scans the specified organization's repositories for catalog-info.yaml files on a schedule, automatically adding discovered entities.
