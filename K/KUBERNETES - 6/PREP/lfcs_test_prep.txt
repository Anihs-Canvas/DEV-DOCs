PRE-LEARNING: LINUX FOUNDATIONS — Your Mental Model (Novice Foundation)
═══════════════════════════════════════════════════════════════════════
Before diving into the exam domains, this section builds your mental model
of what Linux IS, why it exists, and how it powers everything from your
laptop to the cloud. Essential for novices; useful refresher for everyone.

F.1 What Is Linux & Why Does It Run the World?
    • The "Operating System" concept — the bridge between hardware and apps
    • Linux vs Windows vs macOS — key philosophical differences
    • The Linux Kernel — the core engine (Linus Torvalds, 1991)
    • Distributions (distros): Ubuntu, Debian, RHEL, CentOS, Fedora, Arch
    • Why Linux dominates servers: stability, security, open-source, free
    • The "Everything is a File" philosophy — /dev/sda, /proc/cpuinfo, /sys
    • Where Linux fits in your application stack — the server OS underneath
      your API (Python/Node.js/Java/Go), database (PostgreSQL/MySQL), and proxy (Nginx/HAProxy)
    🟢 Novice

F.2 The Linux Filesystem — Your Foundation
    • The Filesystem Hierarchy Standard (FHS) — the "floor plan" of Linux
    • / (root), /home, /etc, /var, /tmp, /usr, /opt — what lives where
    • /etc = configuration files (the "control panel")
    • /var = variable data (logs, databases, spools, caches)
    • /home = user home directories (personal workspaces)
    • /tmp = temporary scratch space (cleared on reboot)
    • How a generic web application maps to the filesystem:
      /opt/anihpj/ — application code (Django/Rails/Express/Spring Boot)
      /etc/anihpj/ — configuration files (YAML, JSON, .env, .conf)
      /var/log/anihpj/ — application and database logs
      /var/lib/postgresql/ (or /var/lib/mysql/) — database data files
      /srv/ — alternative for serving data (static files, uploads)
    • ASCII diagram: Full FHS tree with color-coded zones
    🟢 Novice

F.3 The Shell & Essential Tools — Your "Command Center"
    • What is a shell? (bash, zsh) — the text-based interface
    • Terminal vs Shell vs Console — clearing up the terminology
    • bash basics: prompt ($ vs #), commands, arguments, flags
    • PATH — how Linux finds commands (/usr/bin, /usr/local/bin)
    • stdin (0), stdout (1), stderr (2) — the three data streams
    • Pipes (|) and redirection (>, >>, <, 2>&1) — connecting commands
    • man pages — the built-in manual (man ls, man systemd)
    • Essential navigation: cd, ls, pwd, mkdir, rmdir, tree
    🟢 Novice

F.4 A Generic Web Application Stack — Your "Living Laboratory"
    • The pattern: API server → database → cache → reverse proxy → users
    • This architecture powers apps in EVERY language:
      ┌─────────────────────────────────────────────────────────┐
      │ Python/Django  │ Node.js/Express │ Java/Spring Boot     │
      │ Go/net/http    │ Ruby/Rails      │ PHP/Laravel          │
      │ Rust/Actix     │ C#/.NET         │ Elixir/Phoenix       │
      └─────────────────────────────────────────────────────────┘
    • The common Linux stack underneath them all:
      ├── Application server (gunicorn, puma, npm start, java -jar, go run)
      ├── PostgreSQL (or MySQL/MariaDB) — relational database on port 5432
      ├── Redis (or Memcached) — in-memory cache on port 6379
      └── Nginx (or HAProxy/Caddy) — reverse proxy on ports 80/443
    • How every component runs on Linux:
      ├── App server → systemd service (anihpj-api.service)
      ├── Database → systemd service (postgresql.service or mysql.service)
      ├── Cache → systemd service (redis-server.service)
      └── Reverse proxy → systemd service (nginx.service)
    • Complete file structure of a deployed application (language-agnostic)
    • How every LFCS domain maps to running ANY web application:
      Operations Deployment → systemd services, cron, containers, SELinux
      Networking → reverse proxy, SSH, firewall, DNS, bonding
      Storage → LVM for DB volumes, filesystems, swap, NFS
      Essential Commands → Git, SSL certs, performance monitoring, diskspace
      Users & Groups → app user, ACLs, LDAP, resource limits
    🟢 Novice

F.5 Your Linux Lab Environment — Where You'll Practice
    • Your lab: Ubuntu 22.04/24.04 VMs (local or cloud)
    • SSH access: ssh user@host — your remote control
    • sudo — "superuser do" (admin powers when needed)
    • apt — package manager (apt update, apt install, apt upgrade)
    • Essential tools: vim, curl, git, htop, net-tools, lvm2, libvirt, podman
    • How each LFCS domain maps to hands-on practice
    • Safety: Use snapshots before destructive operations!
    🟢 Novice

CATEGORY 1: OPERATIONS DEPLOYMENT (25% = 50 Questions) — Q1-Q50
───────────────────────────────────────────────────────────────────────

Official sub-topics:

  • Diagnose, identify, manage, and troubleshoot processes and services
  • Manage or schedule jobs for executing commands
  • Search for, install, validate, and maintain software packages or repositories

1.1 Kernel Parameters — Persistent & Non-Persistent (6 Qs)
    Q1:  sysctl — viewing and changing kernel parameters at runtime
         sysctl -a → list ALL kernel parameters | sysctl net.ipv4.ip_forward
    Q2:  /proc/sys/ — the virtual filesystem for kernel tunables
         echo 1 > /proc/sys/net/ipv4/ip_forward → non-persistent (lost on reboot!)
         cat /proc/sys/vm/swappiness → current swap tendency
    Q3:  /etc/sysctl.conf + /etc/sysctl.d/ — PERSISTENT kernel parameters
         sysctl -p → apply from /etc/sysctl.conf
         sysctl --system → load ALL config files (sysctl.d/*.conf + sysctl.conf)
    Q4:  Common kernel parameters for production servers
         net.ipv4.ip_forward=1 → required for routers/containers/NAT
         vm.swappiness=10 → reduce swap tendency (better for databases)
         net.core.somaxconn=1024 → increase max pending connections
         fs.file-max=2097152 → increase max open files system-wide
    Q5:  Kernel modules — lsmod, modprobe, modinfo, rmmod, /etc/modprobe.d/
         lsmod → list loaded | modprobe nfs → load NFS module
         modprobe -r dccp → remove insecure module | blacklist in /etc/modprobe.d/
    Q6:  Tuning kernel for a production web app — practical sysctl settings
         Database: vm.dirty_ratio=15, vm.dirty_background_ratio=5
         Reverse proxy: net.core.somaxconn=1024, net.ipv4.tcp_fastopen=3
         Cache/Memory: vm.overcommit_memory=1 (required for Redis background saves!)

1.2 Diagnose, Manage & Troubleshoot Processes and Services (8 Qs)
    Q7:  ps — process snapshot (ps aux, ps -ef, ps aux --sort=-%mem)
         Interpret: USER, PID, %CPU, %MEM, VSZ, RSS, TTY, STAT, START, TIME, COMMAND
         STAT codes: R=running, S=sleeping, D=uninterruptible sleep, Z=zombie, T=stopped
         ps aux --sort=-%mem | head → top 10 processes by memory usage
    Q8:  top and htop — real-time process monitoring
         top keys: P=sort CPU, M=sort memory, k=kill, r=renice, 1=per-CPU view
         htop — color-coded, mouse support, F5=tree view, F6=sort, F9=kill
    Q9:  pgrep, pkill, pidof — find/signal processes by name
         pgrep -u anihpj → all processes owned by "anihpj" user
         pgrep -f "app-server" → match full command line | pkill -HUP nginx → graceful reload
    Q10: kill and signals — the process communication system (64 signals!)
         kill -l → list all | SIGTERM(15)=polite, SIGKILL(9)=force, SIGHUP(1)=reload config
         SIGSTOP(19)=pause, SIGCONT(18)=resume | kill -HUP $(pgrep nginx)
    Q11: strace — the "X-ray machine" for process syscalls
         strace -p PID → trace live | strace -e open,read,write -p $(pgrep app-server) → file I/O only
         strace -c ls → summary: which syscalls took the longest?
    Q12: lsof — "what files/sockets/pipes does this process have open?"
         lsof -p PID → everything | lsof -i :5432 → who's on the database port?
         lsof /var/log/anihpj/app.log → which process is writing to this log?
    Q13: systemctl — service lifecycle management
         systemctl start/stop/restart/reload/enable/disable/status anihpj-api
         systemctl list-units --type=service --state=running → all active services
         systemctl is-active/is-enabled/is-failed anihpj-api → quick status
    Q14: journalctl — systemd's unified logging
         journalctl -u anihpj-api → service logs | journalctl -u nginx --since "1 hour ago"
         journalctl -xe → last logs with explanations | journalctl --vacuum-size=500M

1.3 Manage or Schedule Jobs for Executing Commands (6 Qs)
    Q15: cron — the classic time-based scheduler (crontab -e, -l, -r)
         Format: minute hour day-of-month month day-of-week command
         0 2 * * * /opt/anihpj/scripts/backup.sh → daily 2AM backup
         */5 * * * * /opt/anihpj/healthcheck.sh → every 5 minutes
    Q16: cron directories + system crontab
         /etc/cron.hourly|daily|weekly|monthly/ → drop scripts directly
         /etc/crontab → system-wide (includes username field!) | /etc/cron.d/ → packages
    Q17: anacron + at — catch-up jobs and one-time scheduling
         anacron: runs missed jobs after boot (for laptops/dev servers)
         at 3:00 AM → run once | atq → list pending | atrm → cancel
    Q18: systemd timers — the modern cron replacement
         Timer unit triggers service unit | systemctl list-timers → all timers + next run
         OnCalendar=daily | OnCalendar=*-*-* 02:00:00 → daily at 2AM
         Advantages: journald integration, randomized delays, monotonic timers
    Q19: Verifying scheduled job execution
         journalctl -u anihpj-backup.timer | grep CRON /var/log/syslog
         Add logging to scripts: echo "$(date): Backup completed" >> /var/log/backup.log
    Q20: Job scheduling for a production web app — practical examples
         Daily: database dump backup at 2AM | Every 5 min: health check endpoint
         Weekly: log rotation + old uploads cleanup | Monthly: SSL cert renewal check

1.4 Software Packages & Repositories (6 Qs)
    Q21: apt — Debian/Ubuntu package management
         apt update → refresh index | apt upgrade → install updates
         apt install nginx postgresql redis → multiple packages at once
         apt remove --purge nginx → remove + config | apt search python3-
    Q22: dpkg — low-level package manager (apt uses dpkg underneath)
         dpkg -l → list all | dpkg -L nginx → package files | dpkg -S /usr/bin/python3 → owner?
         dpkg --configure -a → fix interrupted installs
    Q23: Package repositories — /etc/apt/sources.list + sources.list.d/
         main, universe, multiverse, restricted (Ubuntu components)
         Adding PPAs: add-apt-repository ppa:deadsnakes/ppa → newer Python versions
    Q24: Package integrity, holding, snap/flatpak
         debsums → verify installed files | apt-mark hold kubeadm → prevent upgrade
         snap install certbot --classic → auto-updating sandboxed packages
    Q25: Compiling from source — when packages aren't available
         ./configure → make → make install (classic triplet)
         checkinstall → create .deb from source (cleaner uninstall!)
    Q26: Package management for a full web stack
         App dependencies via language-specific tools (pip/npm/maven/go mod/bundler)
         Infrastructure (PostgreSQL/Redis/Nginx) via apt/rpm
         Containers (Docker/Podman) for language-agnostic deployment alternative

1.5 System Recovery — Hardware, OS & Filesystem Failures (6 Qs)
    Q27: GRUB recovery — when the system won't boot
         GRUB → 'e' edit kernel line → add single or init=/bin/bash
         Rescue mode: systemd.unit=rescue.target | Emergency: systemd.unit=emergency.target
    Q28: Root password recovery
         GRUB → add rw init=/bin/bash → mount -o remount,rw / → passwd → reboot
    Q29: Filesystem recovery — fsck (File System Consistency checK)
         fsck /dev/sda1 → check (MUST be unmounted!) | fsck -y → auto-repair
         tune2fs -c 30 /dev/sda1 → force fsck every 30 mounts
    Q30: Recovering deleted files
         lsof | grep deleted → still held open by a process?
         cp /proc/PID/fd/N /recovery/ → recover from process file descriptor
    Q31: Boot process troubleshooting
         dmesg → kernel ring buffer | journalctl -b → current boot | journalctl -b -1 → previous
         systemd-analyze blame → which services slowed down boot?
    Q32: Backup strategies for a production web application
         Database: pg_dump (PostgreSQL) or mysqldump (MySQL) daily
         Files: rsync -avz /opt/anihpj/ backup-server:/backups/
         Configuration: /etc/anihpj/, /etc/nginx/, /etc/postgresql/ → git version control!

1.6 Virtual Machines — libvirt (6 Qs)
    Q33: libvirt architecture — libvirtd + virsh + virt-manager + QEMU/KVM
         KVM = Kernel-based Virtual Machine (hardware virt via /dev/kvm)
    Q34: virsh — the VM command-line manager
         virsh list --all → all VMs | virsh start/shutdown/destroy/reboot dev-vm
         virsh dominfo dev-vm → CPU, memory, state | virsh domstats → performance
    Q35: Creating VMs with virt-install
         virt-install --name anihpj-test --ram 2048 --vcpus 2 --disk size=20 \
           --cdrom ubuntu-24.04-server.iso --os-variant ubuntu24.04
    Q36: VM networking — bridge, NAT, isolated
         virsh net-list → available networks | default = NAT (192.168.122.0/24)
         Bridge mode: VM on same network as host (like physical machine)
    Q37: VM storage — qcow2 (thin-provisioned), snapshots
         virsh snapshot-create-as dev "pre-update" | virsh snapshot-revert dev "pre-update"
    Q38: libvirt for dev/staging — safe testing environments
         Clone prod: virt-clone --original prod --name debug-copy → troubleshoot safely!

1.7 Container Engines — Create & Manage Containers (6 Qs)
    Q39: Container fundamentals — namespaces (7 types) + cgroups (resource limits)
         Containers share host kernel (unlike VMs which each have their own)
    Q40: Docker — the most popular container engine
         docker run -d --name anihpj-api -p 8080:8080 anihpj:v2.1.0
         docker ps/logs/exec/build | docker network create anihpj-net
    Q41: Podman — daemonless, rootless container engine (RHEL family)
         podman run = docker run syntax | podman generate systemd → systemd unit!
         Rootless: podman run --user 1000:1000 → no root privileges needed
    Q42: Dockerfile — defining container images (multi-stage builds)
         FROM node:20-slim | WORKDIR /opt/anihpj | COPY package*.json .
         RUN npm ci --production | CMD ["node", "server.js"] | USER 1000
         (Also covers Python/pip, Java/gradle, Go/mod patterns)
    Q43: Container networking — bridge, host, overlay
         docker network ls | bridge=default (172.17.0.0/16) | custom network: DNS by container name
    Q44: Containerizing a full web stack
         Multi-stage Dockerfile: builder → distroless runtime | docker-compose for local dev
         Security: non-root USER 1000, readOnlyRootFilesystem, drop ALL capabilities
         Language-agnostic: same Docker patterns for Python, Node.js, Java, Go, Ruby

1.8 SELinux — Mandatory Access Control (MAC) (6 Qs)
    Q45: SELinux fundamentals — DAC vs MAC
         DAC (Discretionary) = owner decides (chmod/chown) — the "honor system"
         MAC (Mandatory) = system-wide policy even root can't override — the "law"
         SELinux labels EVERYTHING: files, processes, ports, sockets + policy rules
    Q46: SELinux modes — enforcing, permissive, disabled
         getenforce → current mode | setenforce 0 → permissive (log only)
         setenforce 1 → enforcing (block+log) | /etc/selinux/config → persistent
    Q47: SELinux contexts — user:role:type:level
         ls -Z /opt/anihpj/ → system_u:object_r:httpd_sys_content_t:s0
         ps -eZ | grep "app-server" → unconfined_u:unconfined_r:unconfined_t:s0
    Q48: chcon, restorecon, semanage — managing file contexts
         chcon -t httpd_sys_content_t /opt/anihpj/static/ → temporary change
         restorecon -Rv /opt/anihpj/ → restore DEFAULT context
         semanage fcontext -a -t httpd_sys_content_t "/opt/anihpj(/.*)?" → PERMANENT
    Q49: SELinux booleans — on/off switches for specific behaviors
         getsebool -a | setsebool httpd_can_network_connect on → app servers need this!
         setsebool -P → make persistent
    Q50: Troubleshooting SELinux denials
         sealert -a /var/log/audit/audit.log → human-readable explanation
         grep "denied" /var/log/audit/audit.log | audit2why → why was it denied?
         audit2allow -a -M custom_policy → generate custom module (review BEFORE applying!)

  OPERATIONS DEPLOYMENT:
  • systemd → anihpj-api.service, postgresql.service (any app server + DB)
  • kernel tuning → sysctl for database/cache memory optimization
  • cron → daily database backups, log rotation
  • containers → Docker/Podman for language-agnostic app deployment
  • SELinux → protecting web server and database files
  • libvirt → dev/staging VMs for safe testing

  NETWORKING:
  • sshd → remote server access for deploys and troubleshooting
  • iptables/nftables → firewall allowing only ports 22, 80, 443
  • reverse proxy (Nginx/HAProxy/Caddy) → routing traffic to app server (port 3000/8000/8080)
  • DNS → resolving db.internal to the database server
  • Bonding → dual NIC for production server redundancy

  STORAGE:
  • LVM → flexible resizing for database and upload volumes
  • XFS/ext4 → high-performance filesystems for database data
  • /etc/fstab → auto-mount volumes at boot
  • NFS → shared file storage across multiple app servers
  • swap → emergency memory for OOM prevention

  ESSENTIAL COMMANDS:
  • git → version control for /opt/anihpj/ and /etc/ configs
  • SSL/TLS → Let's Encrypt certificates for HTTPS
  • performance → iostat/vmstat/sar for capacity planning
  • diskspace → df/du/logrotate for preventing disk-full outages

  USERS AND GROUPS:
  • anihpj system user → runs the application (never as root!)
  • postgres/mysql user → owns database processes
  • developers group → access to /opt/anihpj/ for deploys
  • ACLs → granular file permissions for multi-admin teams
  • LDAP → centralized authentication for enterprise deployments
