    VAULT EXAM STRATEGY — TOP 10 THINGS TO KNOW
    ─────────────────────────────────────────────
    ┌──────────────────────────────────────────────────────────────┐
    │  ❌ MISTAKE                          ✅ CORRECT APPROACH     │
    │                                                              │
    │  1. Confusing token types          Learn: service, batch,    │
    │     (root vs service vs batch)     periodic, orphan — know   │
    │                                     when each is used        │
    │  2. Not understanding policy       Practice writing policies │
    │     syntax and capabilities        from scratch — path +     │
    │                                     capabilities + params    │
    │  3. Forgetting auth method         Know which auth method    │
    │     configuration patterns         to use: k8s, approle,     │
    │                                     userpass, LDAP, token    │
    │  4. Ignoring seal/unseal flow      Know Shamir keys, auto-   │
    │     and importance of unseal       unseal (KMS/HSM), and     │
    │                                     what happens when sealed │
    │  5. Skipping Kubernetes auth       Kubernetes auth is ~15%   │
    │     role and SA configuration      of exam — master it with  │
    │                                     the ServiceAccount flow  │
    │  6. Not knowing secret engine      KV v1 vs v2 is CRITICAL   │
    │     differences (KV v1 vs v2)      v2 has versioning +       │
    │                                     destroy/metadata paths   │
    │  7. Forgetting dynamic secrets     Understand DB secrets:    │
    │     lifecycle (lease, renew,       create role -> issue creds│
    │     revoke)                        -> auto-revoke on TTL     │
    │  8. Not understanding seal types   Shamir vs Auto-Unseal     │
    │     and recovery procedures        (Cloud KMS, HSM, Transit) │
    │                                     and Recovery Key usage   │
    │  9. Skipping audit device config   Know file, socket, syslog │
    │     and log analysis               audit devices and how to  │
    │                                     enable/disable them      │
    │  10. Not practicing CLI commands   vault write, read, list,  │
    │      daily (vault CLI fluency)     delete, policy, secrets   │
    │                                     — practice DAILY          │
    └──────────────────────────────────────────────────────────────┘

    1.2  What is HashiCorp Vault? (The Simple Answer)
         - Vault = Centralized Secrets Management Platform
         - "Vault is a tool for securely accessing secrets"
         - Core promise: Encrypt data at rest, control access via policies,
           audit every access, rotate secrets automatically
         - Built by HashiCorp (Terraform, Consul, Nomad, Boundary family)
         - Written in Go, open-source (MPL 2.0), Enterprise features available
         - Used by: Adobe, SAP, eBay, Splunk, Barclays, Comcast, Robinhood

    2.2  The Seal/Unseal Mechanism (EXAM CRITICAL) 🎯
         - Sealed = data encrypted, master key not in memory, CANNOT access
         - Shamir's Secret Sharing: Split master key into N shares, need K
         - Auto-Unseal: Cloud KMS decrypts master key automatically
         - vault operator seal: Emergency lockdown button
         
         [SHAMIR'S SECRET SHARING — How It Works Visually]
         ┌──────────────────────────────────────────────────────────────┐
         │  🔑 SHAMIR'S SECRET SHARING — The Math Behind Unseal        │
         │                                                              │
         │  ┌─────────────────────────────────────────────────────┐    │
         │  │  STEP A: INIT — Master Key is generated              │    │
         │  │                                                       │    │
         │  │  ┌──────────────────┐                                 │    │
         │  │  │  🔑 MASTER KEY   │  ← AES-256-GCM96 key          │    │
         │  │  │  (single key)    │     Encrypts ALL Vault data    │    │
         │  │  └────────┬─────────┘                                 │    │
         │  │           │                                            │    │
         │  │           │ vault operator init                        │    │
         │  │           │ -key-shares=5 -key-threshold=3             │    │
         │  │           │                                            │    │
         │  │           ▼                                            │    │
         │  │  ┌─────────────────────────────────────────────┐      │    │
         │  │  │  Shamir's Algorithm splits Master Key into:  │      │    │
         │  │  │                                               │      │    │
         │  │  │  Key 1 ████████  Key 2 ████████  Key 3 ████████    │    │
         │  │  │  Key 4 ████████  Key 5 ████████                    │    │
         │  │  │                                               │      │    │
         │  │  │  N = 5 total shares                            │      │    │
         │  │  │  K = 3 needed to reconstruct                    │      │    │
         │  │  │                                               │      │    │
         │  │  │  Each key holder gets ONE share                │      │    │
         │  │  │  Person A → Key 1                              │      │    │
         │  │  │  Person B → Key 2                              │      │    │
         │  │  │  Person C → Key 3                              │      │    │
         │  │  │  Person D → Key 4                              │      │    │
         │  │  │  Person E → Key 5  (stored in safe)            │      │    │
         │  │  └─────────────────────────────────────────────┘      │    │
         │  │                                                       │    │
         │  │  💡 No SINGLE person can unseal Vault alone            │    │
         │  │  💡 Any 3 of the 5 can reconstruct the Master Key      │    │
         │  │  💡 2 keys = USELESS, cannot reconstruct               │    │
         │  │  💡 Even if 2 keys are lost/stolen, 3 remain safe      │    │
         │  │  💡 This is "M of N" threshold cryptography            │    │
         │  └─────────────────────────────────────────────────────┘    │
         │                                                              │
         │  ┌─────────────────────────────────────────────────────┐    │
         │  │  STEP B: UNSEAL — 3 Key Holders Provide Keys         │    │
         │  │                                                       │    │
         │  │  Person A: vault operator unseal <key1>  ✅          │    │
         │  │  Person B: vault operator unseal <key2>  ✅          │    │
         │  │  Person C: vault operator unseal <key3>  ✅          │    │
         │  │                                                       │    │
         │  │  ┌──────┐  ┌──────┐  ┌──────┐                       │    │
         │  │  │Key 1 │ +│Key 2 │ +│Key 3 │ = 🔓 MASTER KEY       │    │
         │  │  └──────┘  └──────┘  └──────┘   RECONSTRUCTED       │    │
         │  │                                                       │    │
         │  │  → Master Key loaded into MEMORY (never to disk)     │    │
         │  │  → Vault can now decrypt data from storage           │    │
         │  │  → Vault transitions: SEALED → UNSEALED              │    │
         │  └─────────────────────────────────────────────────────┘    │
         └──────────────────────────────────────────────────────────────┘

         │  └──────────────────────┬──────────────────────────────────┘│
         │                         │                                    │
         │  ┌──────────────────────▼──────────────────────────────────┐│
         │  │ 2. UPDATE (creates NEW version)                          ││
         │  │ vault kv put secret/anihpj db_pass=NEWPASS              ││
         │  │ → Creates Version 2 (v1 still exists!)                  ││
         │  └──────────────────────┬──────────────────────────────────┘│
         │                         │                                    │
         │  ┌──────────────────────▼──────────────────────────────────┐│
         │  │ 3. READ LATEST                                           ││
         │  │ vault kv get secret/anihpj  → Returns Version 2         ││
         │  │ vault kv get -version=1 secret/anihpj → Returns v1      ││
         │  └──────────────────────┬──────────────────────────────────┘│
         │                         │                                    │
         │  ┌──────────────────────▼──────────────────────────────────┐│
         │  │ 4. SOFT DELETE (recoverable)                             ││
         │  │ vault kv delete secret/anihpj                            ││
         │  │ → Marks as DELETED but recoverable via "undelete"       ││
         │  │ vault kv get secret/anihpj → "No value found at ..."    ││
         │  └──────────────────────┬──────────────────────────────────┘│
         │                         │                                    │
         │  ┌──────────────────────▼──────────────────────────────────┐│
         │  │ 5. UNDELETE (recover)                                    ││
         │  │ vault kv undelete -versions=2 secret/anihpj              ││
         │  │ → Version 2 is back!                                    ││
         │  └──────────────────────┬──────────────────────────────────┘│
         │                         │                                    │
         │  ┌──────────────────────▼──────────────────────────────────┐│
         │  │ 6. PERMANENT DESTROY (unrecoverable!)                    ││
         │  │ vault kv destroy -versions=2 secret/anihpj               ││
         │  │ → Version 2 is GONE FOREVER                             ││
         │  └──────────────────────────────────────────────────────────┘│
         │                                                              │

    12.1 What Are Policies?
         - Policies = "Who can do WHAT on WHICH path"
         - Default: DENY ALL (if not explicitly allowed, it's denied)
         - Policy language: HCL or JSON
         - Multiple policies → UNION of capabilities (most permissive wins)
         
         [POLICY CONCEPT — Visual Decision Flow]
         ┌──────────────────────────────────────────────────────────────┐
         │  🎫 HOW POLICIES WORK — The Decision Flow                    │
         │                                                              │
         │  User/App authenticates                                       │
         │       │                                                       │
         │       ▼                                                       │
         │  ┌─────────┐                                                 │

         │  └────┬────┘                                                 │
         │       │                                                       │
         │       ▼                                                       │
         │  App tries: vault read anihpj/data/database                  │
         │       │                                                       │
         │       ▼                                                       │
         │  ┌─────────────────────────────────────────┐                │
         │  │ POLICY CHECK (UNION of all policies)     │                │
         │  │                                          │                │
         │  │ app-policy says:                         │                │
         │  │   path "anihpj/data/*" {                 │                │
         │  │     capabilities = ["read"]              │                │
         │  │   }                                      │                │
         │  │                                          │                │
         │  │ default policy says:                     │                │
         │  │   path "cubbyhole/*" {                   │                │
         │  │     capabilities = ["create","read"]     │                │
         │  │   }                                      │                │
         │  └────────────────────┬────────────────────┘                │
         │                       │                                       │
         │              ┌────────▼────────┐                             │
         │              │ PATH MATCHES?   │                             │

Chapter 14: Vault + Kubernetes — The Complete Integration 🎯🎯

    14.1 Why Vault on Kubernetes?
         - K8s Secrets = base64 encoding (NOT encryption!)
         - kubectl get secret -o yaml → base64 -d → plaintext in 2 seconds
         - etcd encryption at rest ≠ application-level secret management
         - Vault provides: Dynamic secrets, audit, policy control, auto-rotation
         
         [K8s SECRETS vs VAULT — The Security Gap]
         ┌──────────────────────────────────────────────────────────────┐
         │  ⚠️ K8s SECRETS vs HASHICORP VAULT — Why Vault is Needed     │
         │                                                              │
         │  K8s SECRET (base64 encoded):                                │
         │  ────────────────────────────                                │
         │  $ kubectl create secret generic db-secret \                 │
         │      --from-literal=password=s3cr3t                          │
         │  $ kubectl get secret db-secret -o yaml                      │
         │  → password: czNjcjN0  ← base64, NOT encrypted!             │
         │  $ echo 'czNjcjN0' | base64 -d                               │
         │  → s3cr3t  ← ANYONE with kubectl access can read this!      │
         │                                                              │
         │  VAULT SECRET (AES-256 encrypted):                           │
         │  ────────────────────────────────                            │
         │  $ vault kv get secret/database                              │
         │  → Access controlled by: Token, Policy, Identity             │
         │  → Every access LOGGED in audit trail                        │
         │  → Can be DYNAMIC (auto-generated + TTL)                    │
         │  → Can be auto-ROTATED                                      │
         │                                                              │
         │  💡 K8s Secrets = "PLEASE DON'T LOOK" (obfuscation)          │
         │     Vault Secrets = "YOU CAN'T LOOK" (encryption + ACL)     │
         └──────────────────────────────────────────────────────────────┘

         ┌──────────────────────────────────────────────────────────────┐

         │                                                              │
         │  $ vault operator raft snapshot save /backup/vault.snap      │
         │                                                              │
         │  ┌──────────┐          ┌──────────┐                         │
         │  │ VAULT-1  │          │ BACKUP   │                         │
         │  │ (Active) │          │ STORAGE  │                         │
         │  │          │          │          │                         │
         │  │ Raft DB  │──snap──▶│ S3/GCS/  │                         │
         │  │ Encrypted│          │ NFS      │                         │
         │  └──────────┘          └──────────┘                         │
         │                                                              │
         │  WHAT'S IN THE SNAPSHOT:                                     │
         │  ✅ All KV secrets (every version)                           │
         │  ✅ All policies + auth methods + roles                      │
         │  ✅ All tokens (service tokens only)                         │
         │  ✅ All identity entities + groups                           │
         │  ✅ All configuration (listeners, storage, seals)            │
         │  ✅ Encryption keys (still encrypted by barrier)             │
         │                                                              │
         │  AUTOMATED BACKUP (K8s CronJob):                             │
         │  ┌─────────────────────────────────────────────────────────┐│
         │  │ apiVersion: batch/v1                                    ││
         │  │ kind: CronJob                                           ││
         │  │ metadata:                                               ││
         │  │   name: vault-backup                                    ││
         │  │ spec:                                                   ││
         │  │   schedule: "0 */6 * * *"  # Every 6 hours             ││
         │  │   jobTemplate:                                          ││
         │  │     spec:                                               ││
         │  │       template:                                         ││
         │  │         spec:                                           ││
         │  │           containers:                                   ││
         │  │           - name: backup                                ││
         │  │             image: vault:latest                         ││
         │  │             command:                                    ││
         │  │             - /bin/sh                                   ││
         │  │             - -c                                        ││
         │  │             - |                                         ││
         │  │               vault operator raft snapshot save \       ││
         │  │               /backup/vault-$(date +%Y%m%d-%H%M).snap   ││
         │  └─────────────────────────────────────────────────────────┘│
         └──────────────────────────────────────────────────────────────┘

    18.2 Raft Restore Procedures 🎯
         
         [RAFT SNAPSHOT RESTORE — Step by Step]
         ┌──────────────────────────────────────────────────────────────┐
         │  🔄 RAFT RESTORE — Complete Procedure                        │
         │                                                              │
         │  SCENARIO: Vault cluster corrupted, need to restore          │
         │                                                              │
         │  STEP 1: STOP ALL VAULT NODES                                │
         │  $ systemctl stop vault   (or kubectl scale sts vault --rep 0)│
         │                                                              │
         │  STEP 2: CLEAR EXISTING DATA (on ALL nodes)                  │
         │  $ rm -rf /vault/data/*                                      │
         │                                                              │
         │  STEP 3: RESTORE SNAPSHOT (on node that will be new leader)  │
         │  $ vault operator raft snapshot restore \                    │
         │      -force /backup/vault-20250101.snap                      │
         │  → Restored snapshot into /vault/data/                       │
         │                                                              │
         │  STEP 4: START VAULT (on restored node)                      │
         │  $ systemctl start vault                                     │
         │                                                              │
         │  STEP 5: UNSEAL VAULT (need unseal keys!)                    │
         │  $ vault operator unseal <key1>                              │
         │  $ vault operator unseal <key2>                              │
         │  $ vault operator unseal <key3>                              │
         │                                                              │
         │  STEP 6: JOIN OTHER NODES TO NEW CLUSTER                     │
         │  $ vault operator raft join https://restored-node:8200       │
         │                                                              │
         │  ⚠️ CRITICAL: You MUST have unseal keys to restore!          │
         │  Without unseal keys = CANNOT restore = DATA LOST           │
         └──────────────────────────────────────────────────────────────┘

         [DR REPLICATION — Primary → Secondary Topology]
         ┌──────────────────────────────────────────────────────────────┐
         │  🌍 DISASTER RECOVERY REPLICATION — Multi-Region Setup       │
         │                                                              │
         │  REGION: us-east-1 (PRIMARY)          REGION: eu-west-1 (DR) │
         │  ┌─────────────────────────┐    ┌─────────────────────────┐  │
         │  │ ┌───────┐ ┌───────┐    │    │ ┌───────┐ ┌───────┐    │  │
         │  │ │Active │ │Standby│    │    │ │Standby│ │Standby│    │  │
         │  │ │ Vault │ │ Vault │    │DR  │ │ Vault │ │ Vault │    │  │
         │  │ │  🟢   │ │  ⚪   │    │───▶│ │  ⚪   │ │  ⚪   │    │  │
         │  │ └───────┘ └───────┘    │    │ └───────┘ └───────┘    │  │
         │  │     Raft Cluster       │    │     Raft Cluster       │  │
         │  └─────────────────────────┘    └─────────────────────────┘  │
         │                                                              │
         │  DR REPLICATION CHARACTERISTICS:                             │
         │  ┌─────────────────────────────────────────────────────────┐│
         │  │ ✅ All data replicated: secrets, policies, tokens, ident ││
         │  │ ✅ Async replication (near real-time, seconds delay)     ││
         │  │ ✅ Secondary is READ-ONLY (cannot write locally)         ││
         │  │ ✅ PROMOTE: vault write -f sys/replication/dr/promote   ││
         │  │    → Secondary becomes PRIMARY (takes over traffic)     ││
         │  │ ✅ DEMOTE: Primary can become secondary after promotion ││
         │  │ ⚠️ Requires Enterprise license                          ││
         │  └─────────────────────────────────────────────────────────┘│
         │                                                              │
         │  DR SETUP COMMANDS:                                          │
         │  # On PRIMARY:                                               │
         │  $ vault write sys/replication/dr/primary/enable             │
         │  $ vault write sys/replication/dr/primary/secondary-token \  │
         │      id=eu-dr-secondary ttl=1h                               │
         │                                                              │
         │  # On SECONDARY:                                             │
         │  $ vault write sys/replication/dr/secondary/enable \         │
         │      token=<secondary-token> \                               │
         │      primary_api_addr=https://vault-primary:8200             │
         │                                                              │
         │  🚨 DR PROMOTION (when primary region is DOWN):              │
         │  $ vault write -f sys/replication/dr/promote                 │
         │  → eu-west-1 secondary is NOW the primary!                   │
         └──────────────────────────────────────────────────────────────┘

         │  ────────────────────────────────────                        │
         │  $ vault operator step-down                                  │
         │  → Vault-1 steps down, Vault-2 becomes new leader            │
         │  → Vault-2 (v1.18.x) is now ACTIVE                          │
         │                                                              │
         │  STEP 3: UPGRADE OLD PRIMARY                                 │
         │  ─────────────────────────────                               │
         │  $ systemctl stop vault (on vault-1)                         │
         │  $ [replace binary with v1.18.x]                             │
         │  $ systemctl start vault                                     │
         │  $ vault operator unseal                                     │
         │  → Old primary now standby on v1.18.x                        │
         │                                                              │
         │  RESULT: All 3 nodes on v1.18.x — ZERO downtime!            │
         │                                                              │
         │  ⚠️ IMPORTANT:                                               │
         │  • Check upgrade compatibility matrix BEFORE upgrading       │
         │  • Vault supports upgrade by +1 minor version (1.17→1.18)   │
         │  • CANNOT skip major versions (can't go 1.15→1.18 directly) │
         │  • Always take Raft snapshot BEFORE upgrading                │

    20.1 Transit Engine Architecture
         - Encryption-as-a-Service: Keys NEVER leave Vault
         - Supported: AES-256-GCM96, ChaCha20-Poly1305, RSA-2048/4096, ECDSA
         
         [TRANSIT ENCRYPT/DECRYPT — Complete Data Flow]
         ┌──────────────────────────────────────────────────────────────┐
         │  🔒 TRANSIT ENGINE — Encryption as a Service (EaaS)          │
         │                                                              │
         │  THE PRINCIPLE: "Keys stay in Vault. Vault does the crypto." │
         │                                                              │
         │  ┌─────────────┐          ┌──────────────┐                  │
         │  │ APPLICATION │          │ VAULT TRANSIT │                  │
         │  │ (anihpj)    │          │ ENGINE        │                  │
         │  │             │          │               │                  │
         │  │ Has:         │  ──TLS──▶│ Has: Keys ONLY │                  │
         │  │ Plaintext   │          │ NO plaintext   │                  │
         │  │ data        │          │ stored!        │                  │
         │  └──────┬──────┘          └───────┬───────┘                  │
         │         │                         │                           │
         │         │  ENCRYPT FLOW:          │                           │
         │         │                         │                           │
         │  1. Application has               │                           │
         │     plaintext:                    │                           │
         │     "DB_PASSWORD=s3cr3t"         │                           │
         │         │                         │                           │
         │         │ POST /v1/transit/       │                           │
         │         │ encrypt/anihpj-key      │                           │
         │         │ { plaintext: base64     │                           │
         │         │   ("DB_PASSWORD=s3cr3t")│                           │
         │         │ }                       │                           │
         │         │────────────────────────▶│                           │
         │         │                         │ 2. Vault encrypts with    │
         │         │                         │    AES-256-GCM96 key      │
         │         │                         │    (key NEVER leaves)     │
         │         │                         │                           │
         │         │ 3. Returns ciphertext:  │                           │
         │         │ { ciphertext:           │                           │
         │         │   "vault:v1:abc123..."  │                           │
         │         │ }                       │                           │
         │         │◀────────────────────────│                           │
         │         │                         │                           │
         │  4. Application STORES            │                           │
         │     ciphertext safely            │                           │
         │     (in DB, file, anywhere)      │                           │
         │     🔑 KEY NEVER LEFT VAULT!     │                           │
         │         │                         │                           │
         │         │  DECRYPT FLOW:          │                           │
         │         │                         │                           │
         │  5. Application needs             │                           │
         │     original data:               │                           │
         │     POST /v1/transit/            │                           │
         │     decrypt/anihpj-key           │                           │
         │     { ciphertext:                │                           │
         │       "vault:v1:abc123..."       │                           │
         │     }                            │                           │
         │         │────────────────────────▶│                           │
         │         │                         │ 6. Vault decrypts with    │
         │         │                         │    SAME key (version 1)   │
         │         │ 7. Returns plaintext:   │                           │
         │         │ { plaintext: base64     │                           │
         │         │   ("DB_PASSWORD=s3cr3t")│                           │
         │         │ }                       │                           │
         │         │◀────────────────────────│                           │
         │                                                              │
         │  💡 WHY THIS IS POWERFUL:                                     │
         │  • Application NEVER has the encryption key                   │
         │  • If app/db is breached → ciphertext is USELESS without Vault│
         │  • Key rotation is transparent to application                 │
         │  • All encrypt/decrypt operations are AUDITED in Vault        │
         │  • Same key can encrypt MILLIONS of records                   │
         └──────────────────────────────────────────────────────────────┘

         │          │ Version 2│ ← NEW encrypts use V2                  │
         │          │ (latest) │                                         │
         │          └──────────┘                                        │
         │                                                              │
         │  Day 60: $ vault write -f transit/keys/anihpj-key/rotate    │
         │          ┌──────────┐                                        │
         │          │ Version 1│ ← Can still decrypt old ciphertexts    │
         │          │ Version 2│                                         │
         │          ├──────────┤                                        │
         │          │ Version 3│ ← NEW encrypts use V3                  │
         │          └──────────┘                                        │
         │                                                              │
         │  KEY CONFIGURATION:                                          │
         │  $ vault write transit/keys/anihpj-key/config \              │
         │      min_decryption_version=1 \   # Oldest version that     │
         │                                     # can still decrypt      │
         │      min_encryption_version=2 \    # Oldest version that     │
         │                                     # can encrypt (force V2+)│
         │      auto_rotate_period=720h       # Auto-rotate every 30d  │
         │                                                              │
         │  REWRAP (migrate all ciphertexts to latest key):             │
         │  $ vault write transit/rewrap/anihpj-key \                   │
         │      ciphertext=<old-ciphertext>                             │
         │  → Returns ciphertext encrypted with Version 3              │
         │                                                              │
         │  TRIM (delete old key versions):                             │
         │  $ vault write transit/keys/anihpj-key/trim \                │
         │      min_available_version=2                                 │
         │  → Deletes Version 1 (can no longer decrypt V1 ciphertexts!)│
