These three nodes run etcd (the cluster database), the API server (the front door), the scheduler (which decides where Pods go), and the controller manager (which runs control loops). They form an HA cluster via etcd Raft consensus — any one can fail without losing the cluster.

🔑 Why 3 control plane nodes? etcd uses the Raft consensus algorithm, which requires a majority (quorum) of members to agree on every write. With 3 nodes, quorum is 2 — the cluster survives 1 node failure. With only 1 node, any failure is catastrophic. With 2 nodes, quorum is 2 — losing either node kills the cluster. 3 is the minimum for production HA.

🧠 The Three-Network Mental Model: Every Kubernetes cluster has three networks layered on top of each other: (1) Node Network — the physical IPs you SSH to. (2) Pod Network — 10.244.0.0/16, where Pods live, routed by Calico BGP. (3) Service Network — 10.96.0.0/12, virtual IPs that kube-proxy translates to Pod IPs via iptables. When a Pod at 10.244.4.72 calls a Service at 10.96.50.100, kube-proxy rewrites the destination to a real Pod IP. The Pod network is real; the Service network is virtual.

🔧 Part 1 — kubeadm Deep Dive: How the Cluster Is Built

kubeadm is the official CNCF tool for bootstrapping production-ready Kubernetes clusters. It doesn't provision VMs or install an OS — it takes existing Linux machines and transforms them into a fully operational Kubernetes cluster. This section covers every phase, every certificate, every bootstrap token, and every join sequence in detail.

For the anihpj-prod cluster, kubeadm v1.31.0 was used to bootstrap 3 control plane nodes and 5 worker nodes across the 10.0.0.0/24 and 10.0.4.0/24 networks. All nodes connect through an HAProxy load balancer at 10.0.0.100:6443.

1.1 What is kubeadm?

kubeadm is a CLI tool that follows the principle of "do one thing well": it bootstraps Kubernetes clusters. It does NOT manage infrastructure — you bring the Linux machines; kubeadm installs Kubernetes on them.

✅ What kubeadm DOES
  • Generates ALL certificates (CA, apiserver, etcd, front-proxy, ServiceAccount)
  • Writes static Pod manifests for control plane components
  • Bootstraps a 3-node etcd cluster via static Pods
  • Starts kube-apiserver, kube-scheduler, kube-controller-manager
  • Generates kubeconfig files for all components
  • Uploads cluster config to a ConfigMap for future upgrades
  • Manages the bootstrap token flow for joining new nodes
  • Phases can be run individually for fine-grained control
❌ What kubeadm does NOT do
  • Does NOT install kubelet, kubeadm, or kubectl (you do that via apt/yum)
  • Does NOT install a container runtime (containerd/CRI-O — you set that up)
  • Does NOT install a CNI plugin (Calico/Flannel/Cilium — applied after init)
  • Does NOT provision VMs or networking between nodes
  • Does NOT configure external load balancers for the API server
  • Does NOT manage certificates after initial generation (you renew them)
🧠 Mental Model: Think of kubeadm as the "cluster assembler". You bring the parts (Linux machines with a container runtime installed), and kubeadm assembles them into a working Kubernetes cluster. It's like IKEA for Kubernetes — kubeadm provides the instructions and the fittings, but you need to bring the furniture (the nodes).

1.2 The kubeadm Configuration File

This single YAML file — ~/kubeadm-config.yaml on cp-01 — defines the entire cluster. After kubeadm init, it's uploaded to the cluster as a ConfigMap (kube-system/kubeadm-config) so future upgrades know exactly how the cluster was built.

It has four YAML documents separated by ---, each configuring a different part of the system:

DocumentKindWhat It Configures
Document 1InitConfigurationNode-specific: advertise address, node name, CRI socket, kubelet flags
Document 2ClusterConfigurationCluster-wide: K8s version, networking CIDRs, API server flags, etcd config, cert SANs
Document 3KubeletConfigurationKubelet behavior: cgroup driver, max pods, eviction thresholds, system reserved
Document 4KubeProxyConfigurationkube-proxy mode (iptables/ipvs) and cluster CIDR
🔑 Why is this file so important? It's the single source of truth for your cluster. If you lose this file and need to rebuild a control plane node from scratch, you'd have to reverse-engineer the configuration from running Pods. Always keep a copy in git! The anihpj team stores kubeadm-config.yaml in the infrastructure repo alongside the Terraform/Ansible code.

⚠️ Certificate Expiry = Cluster Failure: If the API server certificate expires, kubectl stops working and no component can communicate. The kubelet's serving cert auto-rotates, but the static Pod certs (apiserver, etcd) do NOT auto-rotate. Set a calendar reminder 30 days before expiry. CA certificates have 10-year validity — if the CA expires, you need to rebuild the cluster.

🧠 The Pause Container — The Invisible Backbone: Every Pod has a pause container that does absolutely nothing except hold the Pod's network namespace open. All other containers in the Pod join the pause container's namespaces (network, IPC). This is why containers in the same Pod share localhost — they're in the same network namespace, owned by the pause container. If the pause container dies, the Pod's IP is released and all containers lose network connectivity. The pause container image is tiny (~300KB) and literally just calls pause() in an infinite loop.

A control plane node like cp-01 (10.0.0.10) has EVERYTHING a worker has, PLUS four static Pods that form the control plane. These Pods are defined in /etc/kubernetes/manifests/ and run with hostNetwork: true — they use the node's network directly, not the Pod network.

#Static PodKey PortsWhat It Does

🧠 Static Pods vs Regular Pods — The Critical Difference: Static Pods are managed by kubelet directly, not by the API server. kubelet watches /etc/kubernetes/manifests/ and guarantees these Pods are ALWAYS running. If you delete them via kubectl delete pod, kubelet immediately recreates them. To stop a static Pod, you must MOVE the manifest file out of the directory (mv etcd.yaml /tmp/). This is why the control plane survives API server restarts — the API server is itself a static Pod, managed by kubelet, which doesn't need the API server to function.

When two Pods on the same node communicate, the traffic never leaves the node. Calico routes it directly between veth pairs:

🔍 Step-by-Step — What Actually Happens at the Kernel Level:
  1. Pod A (10.244.4.72) sends a TCP SYN packet to 10.244.4.73:8080
  2. The packet exits Pod A's network namespace through its veth (virtual ethernet) interface and enters the node's root network namespace
  3. The Linux kernel looks up 10.244.4.73 in the routing table — Calico has programmed: 10.244.4.73 dev cali1234567890 scope link → "Send directly to Pod B's veth"
  4. The packet passes through Calico's iptables FORWARD chain (cali-FORWARD) where NetworkPolicy rules are enforced — if a NetworkPolicy denies this traffic, the packet is dropped here
  5. The packet crosses into Pod B's network namespace through its veth interface
  6. Pod B's Linux kernel delivers the packet to the container process listening on :8080
Total latency: ~0.05 milliseconds. No overlay encapsulation. No tunnel. No packets leaving the node.
⚡ Why Calico is fast: Calico programs routes directly into the Linux kernel's routing table using ip route. There's no overlay network (VXLAN, IP-in-IP) unless your network requires it. Same-node Pod-to-Pod traffic has latency in the microsecond range because it's just a kernel routing decision between two veth interfaces. No packets leave the node.

5.4 Service to Pod — iptables DNAT Deep Dive

This is the magic of Kubernetes Services. A ClusterIP is not a real IP — it's a virtual address that exists only as iptables rules. Here's exactly what happens:

Service: webapp-svc — ClusterIP 10.96.50.100:8080

Endpoints: 10.244.3.45:8080 (wk-03), 10.244.4.72:8080 (wk-04), 10.244.5.18:8080 (wk-05)

Step-by-Step iptables Processing

StepChainWhat Happens
1PREROUTINGPacket with dst=10.96.50.100:8080 enters netfilter
2KUBE-SERVICESMatches dst=10.96.50.100, dport=8080 → JUMP to KUBE-SVC-WXYZ
3KUBE-SVC-WXYZRandom selection: Rule 1 (33.3% → wk-03), Rule 2 (50% → wk-04), Rule 3 (100% → wk-05)
4KUBE-SEP-XXXXDNAT: rewrites destination to the selected Pod IP:Port
5(routing)Kernel routes the rewritten packet to the Pod's node
🧠 The Probability Math: iptables rules are evaluated sequentially. With 3 endpoints: Rule 1 matches with probability 0.333 (1/3 of traffic goes to wk-03). Rule 2 has probability 0.500, but only 66.7% of traffic reaches it — so 0.500 × 66.7% = 33.3% goes to wk-04. Rule 3 catches the remaining 33.3% for wk-05. The result: statistically even distribution. The cost: every packet evaluates O(n) rules where n = number of endpoints.
📊 iptables Rule Count Per Service: For this one Service with 3 endpoints, kube-proxy creates approximately 12 iptables rules: 1 rule in KUBE-SERVICES (the match), 3 probability rules in KUBE-SVC-WXYZ (the selection), 3 DNAT rules in KUBE-SEP chains (the rewrite), plus connection tracking and forwarding rules. Multiply by the number of Services in your cluster — this is why iptables rule count grows linearly with Service count.
⚠️ iptables Scalability Limit: Each Service with 3 endpoints creates ~12 iptables rules. A cluster with 100 Services × 5 endpoints = ~6,000 rules. At 5,000 Services, you have hundreds of thousands of rules. iptables evaluates rules sequentially (O(n)), so packet processing time grows with every new Service. This is why IPVS mode exists — it uses a kernel hash table (O(1)) instead of sequential rules, and supports multiple scheduling algorithms (round-robin, least-connection, source-hash, destination-hash). For the anihpj cluster (well under 1,000 Services), iptables mode is perfectly fine.

🧠 Why Probability Mode? The Math Behind iptables Load Balancing: iptables rules are evaluated sequentially — there is no hash table or round-robin counter. To achieve statistically even distribution across 3 endpoints, kube-proxy writes rules with carefully calculated probabilities:
  • Endpoint 1 (wk-03): probability 0.33333333 — 1/3 of traffic matches and gets DNAT'd to 10.244.3.45:8080
  • Endpoint 2 (wk-04): probability 0.50000000 — of the remaining 66.7%, half (33.3%) goes to 10.244.4.72:8080
  • Endpoint 3 (wk-05): probability 1.00000000 — all remaining traffic (33.3%) goes to 10.244.5.18:8080
This gives statistically even load distribution without needing a separate load balancer process. The trade-off: every packet evaluates O(n) iptables rules where n = number of endpoints.
⚠️ iptables Scalability Ceiling: For 100 Services with 5 endpoints each: ~6,000 iptables rules. For 5,000 Services: hundreds of thousands of rules. iptables evaluates rules sequentially (O(n)), so adding a new Service gets progressively slower. This is why iptables mode doesn't scale past ~5,000 Services — IPVS mode uses a kernel hash table instead, which is O(1) vs O(n). For the anihpj cluster (well under 1,000 Services), iptables mode is perfectly fine.
💡 IPVS Mode Alternative: If you switch kube-proxy to mode: "ipvs" in the kubeadm config, the iptables rules are replaced with a kernel-level IP Virtual Server. IPVS uses a hash table for Service lookup (O(1) vs O(n)) and supports multiple scheduling algorithms (round-robin, least-connection, source-hash). For clusters with thousands of Services, IPVS is the preferred mode.

🧠 Part 6 — etcd: The Brain of the Cluster

etcd is the single source of truth for the entire Kubernetes cluster. Every object you create — Pods, Services, Deployments, Secrets, Nodes — is stored as a key-value pair in etcd. If etcd goes down, the cluster has amnesia. If etcd is lost, the cluster is lost. Understanding etcd isn't optional — it's the most critical skill for any Kubernetes administrator.

This deep dive covers everything: Raft consensus internals, the complete data model, how the API server interacts with etcd, MVCC time-travel, performance requirements, backup/restore procedures, TLS security, etcdctl commands, and real disaster scenarios.

6.2 Raft Consensus — How 3 Nodes Agree on State

Raft is the consensus algorithm that keeps all etcd nodes in sync. There is exactly one Leader and two (or more) Followers. All writes go through the Leader, which replicates them to the Followers.

Leader Election — What Happens When the Leader Dies

🔁 Election Process:
  • If the Leader dies (or fails to send heartbeats within ~100ms), Followers detect a timeout and start an election
  • Each Follower increments its term and votes for ONE candidate (itself or another Follower)
  • A candidate needs majority (2 out of 3 votes) to become the new Leader
  • Election timeout: ~150-300ms — randomized per node to prevent split votes (every node waits a different random duration before starting its election)
  • During election: NO writes are accepted. Reads still work if quorum exists
  • Once a Leader is elected, it starts sending AppendEntries (heartbeats) and normal operation resumes
⚠️ The Split-Vote Problem: In a 3-node cluster, if two Followers start elections at exactly the same time, each votes for itself — neither gets a majority (each has 1 of 3 votes). The election fails, both wait for another random timeout, and try again. This is why the election timeout is randomized: it makes simultaneous elections statistically unlikely.

6.4 How the API Server Interacts with etcd

The API server is the ONLY component that talks directly to etcd. No other component — kubelet, scheduler, controller-manager, kubectl — ever touches etcd directly. They all go through the API server.

OperationAPI Server → etcdWhat Happens
LIST Range (prefix scan) kubectl get pods → API server sends a Range request on /registry/pods/default/ (prefix). etcd returns all matching keys sorted by key. The API server decodes each protobuf value and returns JSON.
GET Range (single key) kubectl get pod webapp-xxx → Range on the exact key. Returns one key-value pair.
WATCH Watch (stream) kubectl get pods -w opens a long-lived gRPC stream. etcd pushes every create/update/delete event in real time. This is how controllers (scheduler, deployment controller, kube-proxy) know about changes instantly — they all watch the API server, which watches etcd.
CREATE Put API server validates → admits (webhooks) → encodes as protobuf → Put to etcd. etcd Leader appends to WAL, replicates to Followers, commits. Returns the new revision number.
UPDATE Put (same key, new value) Uses optimistic concurrency via resourceVersion. If another client modified the object first → 409 Conflict. The client must re-read and retry. This prevents lost updates without locking.
DELETE Delete Soft-deletes with a tombstone marker. The data isn't physically removed until compaction runs later. This allows watches to see the deletion event.
🧠 Optimistic Concurrency Explained: Every object in Kubernetes has a metadata.resourceVersion field. When you update an object, you must send the resourceVersion you read. If etcd's current resourceVersion doesn't match (someone else updated it), the update is rejected with 409 Conflict. This is the same idea as "compare-and-swap" — no locks, no deadlocks, just "try again if someone beat you to it."

6.5 etcd MVCC & Revisions — Time Travel in the Database

etcd uses Multi-Version Concurrency Control (MVCC). Every write creates a NEW revision — old values are preserved until compaction removes them. This means you can read the state of any key at any historical revision.

Timeline of a Pod's Life in etcd Revisions

⏱️ Revision Timeline — /registry/pods/default/webapp-xxx
Revision 100,000: Created (phase: Pending) Revision 100,050: ContainerCreating (image pulled, volumes mounted) Revision 100,100: Running (container started, IP assigned) Revision 100,500: Running (status heartbeat updated) Revision 105,000: Running (another heartbeat update) Revision 110,000: Terminating (deletionTimestamp set, grace period starts) Revision 110,001: Deleted (tombstone marker — removed after compaction)
MVCC FeatureWhy It Matters for Kubernetes
Historical reads
etcdctl get /key --rev=100000		You can read the Pod spec as it was at any past revision. Useful for auditing and debugging "what changed and when."
Watches from revision
etcdctl watch /key --rev=100000		Watches can start from ANY revision, not just "now." If a controller restarts, it can replay events from its last known revision — no events are lost.
Optimistic concurrency
resourceVersion		"Only update if current revision == 110,000." Prevents lost updates when multiple clients modify the same object.
⚠️ Compaction — The Silent Killer: Old revisions accumulate and consume disk space. Without compaction, etcd eventually runs out of disk and dies. Kubernetes defaults: compact every 5 minutes, keep the last 5 minutes of history. If you need longer history for auditing, increase --auto-compaction-retention and monitor disk usage. DO NOT disable compaction.
💡 Compaction Command: etcdctl compaction 110000 --physical removes all revisions older than 110,000 and defragments the database file. The --physical flag actually shrinks the file on disk (without it, space is just marked as reusable).

6.7 etcd Performance Requirements

etcd is extremely sensitive to disk I/O. Every write calls fsync() to guarantee data is on physical disk — slow disk = slow cluster.

MetricRequirementWhy
Disk typeSSD/NVMe REQUIREDEvery etcd write calls fsync() to guarantee data is on physical disk. Spinning disks have 5-10ms fsync latency → etcd becomes unusable.
Disk latency< 10ms p99Raft consensus waits for fsync on the Leader AND Followers. If fsync takes more than ~100ms, heartbeats are missed and elections trigger.
Disk IOPS500+ sequential writeThe WAL is append-only (sequential), but snapshots are bulk writes. Both matter.
Network latency< 5ms between membersRaft heartbeats every 100ms. If latency exceeds this, elections fire. Run CP nodes in the same availability zone.
Memory4-8GB recommendedetcd caches the entire keyspace in memory (B-tree). More objects = more memory.
CPU2-4 coresgRPC processing, protobuf serialization/deserialization, Raft consensus logic.

The fsync call must flush to physical media — NFS and low-IOPS cloud volumes can take 50-200ms per fsync. This causes frequent leader elections and makes the cluster unstable.

mv /tmp/etcd.yaml /etc/kubernetes/manifests/etcd.yaml

# 7. Once cp-01 is running, start etcd on cp-02 and cp-03:
mv /tmp/etcd.yaml /etc/kubernetes/manifests/etcd.yaml
# They join cp-01's cluster and sync automatically

# 8. Verify cluster health:
etcdctl endpoint health --cluster

# 9. Start the API server:
mv /tmp/kube-apiserver.yaml /etc/kubernetes/manifests/

# 10. Verify the cluster works:
kubectl get nodes
kubectl get pods -A

🗜️ Defrag — Reclaim Fragmented Disk Space

💡 When to defrag: etcd stores data in 4KB pages. Over time, deletes leave gaps (fragmentation). The database file size grows even if the actual data size hasn't. If DB SIZE in etcdctl endpoint status is near the 8GB quota but actual keyspace is small, you need defrag.
🗜️ Defrag Procedure
# Check fragmentation:
etcdctl endpoint status --write-out=table
# Look at DB SIZE — near 8GB = defrag needed

# Defrag ONE NODE AT A TIME (to avoid quorum loss):
etcdctl defrag --endpoints=https://10.0.0.11:2379

# CAUTION: Defrag LOCKS the database on that node for 30s-5min
# depending on database size. Do it during maintenance windows.
# Never defrag more than one node simultaneously.

7.1 Upgrading the Cluster with kubeadm

kubeadm supports upgrading one minor version at a time (e.g., 1.31 → 1.32). You cannot skip minor versions — 1.30 → 1.32 is NOT supported. Each upgrade follows a strict sequence: Control Plane first, Workers second, one node at a time.

⚠️ Pre-Upgrade Checklist:
  • ✅ Backup etcd — snapshot before touching anything (see Part 6.8)
  • ✅ Read the release notes — check for breaking changes and deprecated API removals
  • ✅ Verify CNI compatibility — is Calico v3.28 compatible with the new k8s version?
  • ✅ Check the upgrade plan — kubeadm upgrade plan tells you exactly what will change
  • ✅ Schedule a maintenance window — API server may be briefly unavailable during CP upgrades

Step 1: Upgrade kubeadm on the FIRST Control Plane Node (cp-01)

📦 Step 1 — Upgrade kubeadm binary
# On cp-01 ONLY:
apt-mark unhold kubeadm
apt-get update && apt-get install -y kubeadm=1.31.4-*
apt-mark hold kubeadm

Step 2: Verify the Upgrade Plan

📋 Step 2 — Check what kubeadm will upgrade
kubeadm upgrade plan
# Output shows:
#   - Current version: v1.31.0
#   - Available upgrades: v1.31.4 (stable), v1.32.0 (stable)
#   - Components that CAN be upgraded: kube-apiserver, kube-controller-manager,
#       kube-scheduler, kube-proxy, CoreDNS, etcd
#   - Components that MUST be upgraded manually: kubelet (you do this next)

Step 3: Apply the Upgrade (on cp-01)

🚀 Step 3 — kubeadm upgrade apply
kubeadm upgrade apply v1.31.4
# This performs:
#   1. Renews certificates if they're close to expiry
#   2. Upgrades static Pod manifests (etcd, apiserver, scheduler, controller-manager)
#   3. Upgrades kubelet configuration on this node
#   4. Updates kubeadm-config and kubelet-config ConfigMaps in the cluster
#   5. Upgrades CoreDNS and kube-proxy addons
#   6. Does NOT upgrade kubelet itself — you do that in Step 4
💡 What "upgrade apply" actually does: kubeadm reads the current cluster configuration from the kubeadm-config ConfigMap, compares it with the new version's defaults, and generates updated static Pod manifests in /etc/kubernetes/manifests/. The kubelet detects the changed manifests and restarts the containers with the new images. The API server is briefly unavailable during this restart (typically 5-30 seconds).

Step 4: Upgrade kubelet and kubectl on cp-01

📦 Step 4 — Upgrade kubelet + kubectl

  echo "=== $node complete ==="
done
🧠 Why "drain before upgrade" matters: kubectl drain gracefully evicts all Pods from the node. This ensures zero-downtime for your applications — the Deployment controller sees the evicted Pods and creates replacements on healthy nodes. The --ignore-daemonsets flag skips DaemonSet Pods (like Calico and kube-proxy) because they can't be evicted — they run on every node by design. --delete-emptydir-data allows eviction of Pods using emptyDir volumes (the data is lost, which is expected for ephemeral storage).

8.1 Pre-requisites — All 10 Nodes

Run this script as root on EVERY node (cp-01..03, wk-01..05, fe-01..02) BEFORE running kubeadm init/join. This configures the Linux kernel, installs containerd, and installs the Kubernetes binaries:

Part A: Kernel Modules & System Configuration

🔧 Kernel & System Prep — Run on ALL nodes
#!/bin/bash
# Run as root on EVERY node before kubeadm init/join

# ── Load required kernel modules ──
cat <<EOF | tee /etc/modules-load.d/k8s.conf
overlay
br_netfilter
EOF
modprobe overlay
modprobe br_netfilter
💡 Why these modules? overlay is the kernel module that enables the OverlayFS filesystem — required by containerd for container image layers. br_netfilter enables iptables to see bridged traffic — without it, Pod-to-Pod network policies (NetworkPolicy) won't work because iptables rules are bypassed on bridge interfaces.
📡 Kernel Networking Parameters
# ── Set kernel networking parameters ──
cat <<EOF | tee /etc/sysctl.d/99-kubernetes.conf
net.bridge.bridge-nf-call-iptables  = 1
net.bridge.bridge-nf-call-ip6tables = 1
net.ipv4.ip_forward                 = 1
EOF
sysctl --system

# ── Disable swap (REQUIRED by Kubernetes) ──
swapoff -a
sed -i '/swap/d' /etc/fstab
💡 Why these sysctls? bridge-nf-call-iptables ensures that packets traversing Linux bridges (used by containers) pass through iptables. Without this, kube-proxy's iptables rules would be invisible to Pod traffic. ip_forward enables the node to forward packets between Pods. Swap must be OFF because Kubernetes' QoS model assumes guaranteed memory — if a Pod is swapped to disk, the kubelet can't accurately track its memory usage and QoS guarantees break.

Part B: Install Container Runtime (containerd)

📦 Install & Configure containerd
# ── Install containerd ──
apt-get update && apt-get install -y containerd
mkdir -p /etc/containerd
containerd config default | tee /etc/containerd/config.toml

# CRITICAL: Use systemd as the cgroup driver (matches kubelet default)
sed -i 's/SystemdCgroup = false/SystemdCgroup = true/' /etc/containerd/config.toml
systemctl restart containerd
systemctl enable containerd
🧠 The cgroup driver mismatch is the #1 bootstrap failure: containerd defaults to cgroupfs driver, but kubelet defaults to systemd. If they mismatch, the kubelet can't properly enforce resource limits, and you'll see errors like "Failed to create pod sandbox". ALWAYS set containerd to systemd to match kubelet.

Part C: Install Kubernetes Binaries

📦 Install kubeadm, kubelet, kubectl
# ── Install Kubernetes packages ──
apt-get update && apt-get install -y apt-transport-https ca-certificates curl gpg

# Add the Kubernetes package repository
curl -fsSL https://pkgs.k8s.io/core:/stable:/v1.31/deb/Release.key | \
  gpg --dearmor -o /etc/apt/keyrings/kubernetes-apt-keyring.gpg

echo 'deb [signed-by=/etc/apt/keyrings/kubernetes-apt-keyring.gpg] https://pkgs.k8s.io/core:/stable:/v1.31/deb/ /' | \
  tee /etc/apt/sources.list.d/kubernetes.list

💡 Why apt-mark hold? This prevents unattended-upgrades from accidentally upgrading Kubernetes packages. Kubernetes upgrades must be done deliberately, in a specific order, one node at a time — an automatic upgrade could break the cluster. The kubelet is enabled here but will crash-loop until kubeadm init or kubeadm join creates the required configuration files — this is expected behavior.

          httpGet:
            path: /readyz
            port: 8080
          initialDelaySeconds: 5
          periodSeconds: 5
EOF
💡 Why two probes? The liveness probe tells Kubernetes "restart me if I'm stuck" — if /healthz fails, the container is killed and restarted. The readiness probe tells Kubernetes "I'm ready to receive traffic" — if /readyz fails, the Pod is removed from the Service's endpoints but NOT restarted. This distinction prevents traffic from being sent to Pods that are temporarily overloaded or still initializing.

9.8 Cluster Reset — DESTROY and Start Over

🔴 DANGER: This DESTROYS all Kubernetes state on the node. This is irreversible — all Pods, configurations, and certificates on this node will be deleted. Only use this when decommissioning a node or rebuilding a broken cluster. For the full reset/rejoin procedure, see Part 7.2.
CommandWhat It Destroys
kubeadm reset -fStops the kubelet. Deletes /etc/kubernetes/ (all manifests, certs, kubeconfigs). Removes the node from the cluster if the API server is reachable. The -f flag skips confirmation prompts.
rm -rf /etc/cni/net.d /var/lib/kubelet /var/lib/etcdRemoves CNI configuration (Calico IPAM state), kubelet state (Pod data, volumes, secrets), and etcd data (the entire database — ONLY run this on CP nodes you're resetting).
iptables -F && iptables -t nat -F && iptables -t mangle -FFlushes ALL iptables rules in all tables. Removes kube-proxy's iptables rules and any leftover Calico/CNI rules. The node's networking returns to pre-Kubernetes state.
IP link cleanupip link delete cni0 2>/dev/null; ip link delete flannel.1 2>/dev/null — removes CNI bridge interfaces. The 2>/dev/null suppresses errors if the interfaces don't exist (if using a different CNI).
systemctl restart containerdRestarts the container runtime to clean up any lingering container state. After this, the node is completely clean and ready to re-join the cluster with kubeadm join.
🔄 Complete Node Reset Procedure (Copy-Paste)
# === DESTROY KUBERNETES ON THIS NODE ===
# WARNING: This is IRREVERSIBLE

kubeadm reset -f
rm -rf /etc/cni/net.d /var/lib/kubelet /var/lib/etcd
iptables -F && iptables -t nat -F && iptables -t mangle -F
ip link delete cni0 2>/dev/null
ip link delete flannel.1 2>/dev/null
systemctl restart containerd

# Now the node is clean.
# To re-join as a worker: kubeadm join 10.0.0.100:6443 --token <token> --discovery-token-ca-cert-hash sha256:<hash>
# To re-join as a CP:     Add --control-plane --certificate-key <key>
# To re-init as cp-01:    kubeadm init --config=kubeadm-config.yaml --upload-certs
