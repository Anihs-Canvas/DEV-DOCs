0.1 Node Specifications — What Runs Where

🟣 Control Plane Nodes (3) — The Cluster's Brain

These three nodes run etcd (the cluster database), the API server (the front door), the scheduler (which decides where Pods go), and the controller manager (which runs control loops). They form an HA cluster via etcd Raft consensus — any one can fail without losing the cluster.

Runs: etcd (Raft follower), kube-apiserver, kube-scheduler, kube-controller-manager, kubelet, containerd, kube-proxy, Calico

🔑 Why 3 control plane nodes? etcd uses the Raft consensus algorithm, which requires a majority (quorum) of members to agree on every write. With 3 nodes, quorum is 2 — the cluster survives 1 node failure. With only 1 node, any failure is catastrophic. With 2 nodes, quorum is 2 — losing either node kills the cluster. 3 is the minimum for production HA.

🔑 Why are frontend nodes outside the cluster? Nginx runs on the host directly, not as a Pod. This gives us predictable TLS performance (no overlay network overhead) and independence from the cluster — if the Kubernetes control plane goes down, Nginx still serves 503 error pages instead of dropping connections. The load balancer in front of fe-01/fe-02 distributes traffic; if one Nginx node fails, the other handles all traffic.

0.3 Network Allocation — IP Architecture

Three separate IP spaces coexist in the cluster. Understanding which IP belongs to which space is critical for debugging connectivity issues:

CIDR / AddressValueWhat It's For
Node Network (CP)10.0.0.0/24Physical IPs of cp-01 (.10), cp-02 (.11), cp-03 (.12). These are the IPs you SSH to.
Node Network (Workers)10.0.4.0/24Physical IPs of wk-01 (.21) through wk-05 (.25).
Node Network (Frontend)10.0.5.0/24Physical IPs of fe-01 (.10), fe-02 (.11).
API Server VIP10.0.0.100:6443HAProxy virtual IP. All kubectl commands and kubelets connect here — never to individual CP IPs.
Pod CIDR10.244.0.0/16Every Pod gets an IP from here. Calico carves it into /26 subnets per node. Pod IPs are routable across the cluster.
Service CIDR10.96.0.0/12ClusterIP Services get virtual IPs from here. These IPs only exist in iptables/IPVS rules — they're never assigned to any interface.
DNS Service IP10.96.0.10CoreDNS ClusterIP. Every Pod's /etc/resolv.conf has nameserver 10.96.0.10.
🧠 The Three-Network Mental Model: Every Kubernetes cluster has three networks layered on top of each other: (1) Node Network — the physical IPs you SSH to. (2) Pod Network — 10.244.0.0/16, where Pods live, routed by Calico BGP. (3) Service Network — 10.96.0.0/12, virtual IPs that kube-proxy translates to Pod IPs via iptables. When a Pod at 10.244.4.72 calls a Service at 10.96.50.100, kube-proxy rewrites the destination to a real Pod IP. The Pod network is real; the Service network is virtual.

Every design choice in the anihpj cluster was made for a specific reason. Understanding the why behind each decision turns you from someone who can describe the cluster into someone who can design one:

etcd Topology Stacked (co-located with CP) Simpler operations — fewer nodes to manage. 3 CP nodes run both etcd and control plane. For clusters under 50 nodes, stacked etcd has negligible performance impact. External etcd (separate 3-node cluster). Adds 3 more machines. Better for 100+ node clusters where etcd I/O competes with API server load.
API Server Access HAProxy VIP (10.0.0.100) Single endpoint for all clients. HAProxy does TCP load balancing (Layer 4) — no TLS termination. CNI Plugin Calico with BGP (no overlay) Best performance — no encapsulation overhead. BGP routes Pod IPs directly between nodes. NetworkPolicy support is first-class. Weave (overlay overhead).
Container Runtime containerd (CRI) CNCF graduated project. Direct CRI implementation — no dockershim needed. Lighter than full Docker. systemd cgroup driver prevents cgroup mismatch issues. CRI-O (Red Hat ecosystem, less tooling). Docker (deprecated dockershim, heavier).
Worker Sizing 3 standard (2vCPU/8GB) + 2 high-cap (4vCPU/16GB) Standard workers for stateless web/API Pods. High-cap workers isolated for stateful workloads via nodeSelectors and taints. Frontend Placement Outside K8s cluster (bare nginx) Independence from cluster failures. No overlay network overhead for TLS. Simpler certificate management (certbot on host). 🧠 Design Principle: Every decision above follows the same pattern: simplicity over complexity, reliability over convenience, and isolation over density. The cluster is designed to be understandable by a single admin at 2 AM — not to maximize resource utilization at the cost of debuggability.

How the Cluster Is Built

kubeadm is the official CNCF tool for bootstrapping production-ready Kubernetes clusters. It doesn't provision VMs or install an OS — it takes existing Linux machines and transforms them into a fully operational Kubernetes cluster. This section covers every phase, every certificate, every bootstrap token, and every join sequence in detail.

🔧 kubeadm v1.31 📜 27 Phases 🔐 3 CAs ⏱ ~45 min Bootstrap

1.1 What is kubeadm?

kubeadm is a CLI tool that follows the principle of "do one thing well": it bootstraps Kubernetes clusters. It does NOT manage infrastructure — you bring the Linux machines; kubeadm installs Kubernetes on them.

✅ What kubeadm DOES
  • Generates ALL certificates (CA, apiserver, etcd, front-proxy, ServiceAccount)
  • Writes static Pod manifests for control plane components
  • Bootstraps a 3-node etcd cluster via static Pods
  • Starts kube-apiserver, kube-scheduler, kube-controller-manager
  • Generates kubeconfig files for all components
  • Uploads cluster config to a ConfigMap for future upgrades
  • Manages the bootstrap token flow for joining new nodes
  • Phases can be run individually for fine-grained control
❌ What kubeadm does NOT do
  • Does NOT install kubelet, kubeadm, or kubectl (you do that via apt/yum)
  • Does NOT install a container runtime (containerd/CRI-O — you set that up)
  • Does NOT install a CNI plugin (Calico/Flannel/Cilium — applied after init)
  • Does NOT provision VMs or networking between nodes
  • Does NOT configure external load balancers for the API server
  • Does NOT manage certificates after initial generation (you renew them)
🧠 Mental Model: Think of kubeadm as the "cluster assembler". You bring the parts (Linux machines with a container runtime installed), and kubeadm assembles them into a working Kubernetes cluster. It's like IKEA for Kubernetes — kubeadm provides the instructions and the fittings, but you need to bring the furniture (the nodes).

🔑 Part 1 Key Takeaways — kubeadm Deep Dive

🏗️
kubeadm Assembles, It Does NOT Provision

You bring Linux machines with containerd installed. kubeadm generates certs, writes static Pod manifests, creates kubeconfigs, and uploads configuration — it does NOT install containerd, kubelet, or a CNI plugin.

📜
27 Phases, One Tool

Every phase can be run individually with kubeadm init phase <name>. If preflight fails, fix the issue and re-run just the preflight phase. This granularity is your best debugging tool.

🔐
Three CAs, Three Trust Domains

Cluster CA signs K8s component certs. Front-Proxy CA signs aggregation layer certs. etcd CA is completely isolated — the API server is the ONLY component with an etcd client cert. Defense in depth.

📄
Static Pods Are Managed by Kubelet

The 4 control plane components (etcd, apiserver, scheduler, ctrl-mgr) are static Pods. They exist as YAML files in /etc/kubernetes/manifests/. Kubelet watches this directory and guarantees they're always running — even if kubectl is unavailable.

🔗
Bootstrap Tokens = Temporary Trust

Format: 6 chars + dot + 16 chars. TTL: 24 hours. The CA cert hash prevents MITM attacks during join. For CP joins, the certificate key decrypts the shared cert bundle. Store both securely — they grant cluster access.

⏱️
Certificates Expire — Track Them

Most certs expire in 1 year. CAs expire in 10 years. Run kubeadm certs check-expiration monthly on every CP node. Set calendar reminders. If the API server cert expires, the cluster stops working.

📁 Part 2 — Directory Tree Filesystem

Complete Filesystem Maps

Every file and directory on a Kubernetes node exists for a reason. This section maps out the complete filesystem for both control plane and worker nodes — what each directory contains, which component created it, and what happens if it's missing. 🔑 Part 2 Key Takeaways — Directory Tree

📁
kubeadm Owns /etc/kubernetes/

Every file under /etc/kubernetes/ is created by kubeadm init or join. Manual edits to these files are overwritten by kubeadm operations. Use kubeadm commands to manage them.

🔍
/etc/kubernetes/manifests/ Is Watched by Kubelet

Kubelet uses inotify to monitor this directory. Add a YAML → kubelet creates a static Pod. Remove a YAML → kubelet deletes the Pod. This is how control plane components are managed.

⭐
/var/lib/etcd/ Is the Most Critical Directory

The snap/db file contains ALL cluster state. If lost without a backup, the cluster has amnesia. Always back up etcd before any maintenance operation on CP nodes.

🔌
/run/ Is tmpfs — Gone After Reboot

containerd.sock, kubelet.sock, and other runtime sockets live in /run. They're recreated on every boot. If a socket is missing, the daemon that creates it isn't running.

🛡️
Workers Are Simpler by Design

Workers only have ca.crt (to verify the API server) and kubelet.conf (to authenticate). No etcd data, no static Pod manifests, no audit logs. This is least-privilege at the filesystem level.

📝
Logs Are Symlinked

/var/log/pods/ and /var/log/containers/ are symlinked to the actual CRI log locations. If kubectl logs is empty but the container is running, check if these symlinks are broken.

🧠 The Pause Container — The Invisible Backbone: Every Pod has a pause container that does absolutely nothing except hold the Pod's network namespace open. 🧠 Static Pods vs Regular Pods — The Critical Difference: Static Pods are managed by kubelet directly, not by the API server. kubelet watches /etc/kubernetes/manifests/ and guarantees these Pods are ALWAYS running. If you delete them via kubectl delete pod, kubelet immediately recreates them. To stop a static Pod, you must MOVE the manifest file out of the directory (mv etcd.yaml /tmp/). This is why the control plane survives API server restarts — the API server is itself a static Pod, managed by kubelet, which doesn't need the API server to function.

🔑 Part 3 Key Takeaways — Node Runtime

🔧
systemd Manages Kubelet + Containerd

Only two Kubernetes-related services run via systemd: kubelet and containerd. Everything else — kube-proxy, Calico, CoreDNS, application Pods — is managed by kubelet as Pods.

⏸️
The Pause Container Holds the Network Namespace

Every Pod has a pause container that holds the network namespace open. All other containers join it. If pause dies, the Pod loses its IP and all containers lose connectivity.

🔄
Pod Lifecycle Follows a Predictable State Machine

Pending → ContainerCreating → Running → Succeeded/Failed/CrashLoopBackOff. Each state has specific causes. Check kubectl describe conditions to find the blockage.

🐳
containerd-shim Decouples Container Lifecycle

The shim process per Pod allows you to restart containerd without killing running containers. This is critical for node maintenance and upgrades.

🛡️
system-node-critical Is the Highest Priority

etcd and kube-apiserver use this priority class. The kubelet will NEVER evict them, even under extreme memory pressure. If they get evicted, your node is failing.

📊
CNI Plugin Chain Executes in Order

Calico conflist runs 3 plugins sequentially: calico (IP allocation, routes), portmap (hostPort DNAT), bandwidth (tc limits). If any plugin fails, the Pod creation fails.

🔍 Step-by-Step at the Kernel Level:
  1. Pod A (10.244.4.72) sends TCP SYN to 10.244.4.73:8080
  2. Packet exits Pod A's namespace through its veth into the node's root namespace
  3. Kernel looks up 10.244.4.73 in routing table — Calico programmed: 10.244.4.73 dev cali123 scope link
  4. Packet passes through Calico's iptables FORWARD chain where NetworkPolicy is enforced
  5. Packet crosses into Pod B's namespace through its veth
  6. Pod B's kernel delivers to the container process on :8080
Total latency: ~0.05ms. No overlay, no tunnel, no packets leaving the node.
⚡ Why Calico is fast: Calico programs routes directly into the Linux kernel's routing table using ip route. There's no overlay network (VXLAN, IP-in-IP) unless required. Same-node Pod-to-Pod traffic has microsecond latency — it's just a kernel routing decision between two veth interfaces.

5.4 Service to Pod — iptables DNAT Deep Dive

This is the magic of Kubernetes Services. A ClusterIP is not a real IP — it's a virtual address that exists only as iptables rules.

Service: webapp-svc — ClusterIP 10.96.50.100:8080

Endpoints: 10.244.3.45:8080 (wk-03), 10.244.4.72:8080 (wk-04), 10.244.5.18:8080 (wk-05)

StepChainWhat Happens
1PREROUTINGPacket with dst=10.96.50.100:8080 enters netfilter
2KUBE-SERVICESMatches dst → JUMP to KUBE-SVC-WXYZ
3KUBE-SVC-WXYZRandom: Rule 1 (33.3% → wk-03), Rule 2 (50% → wk-04), Rule 3 (100% → wk-05)
4KUBE-SEP-XXXXDNAT: rewrites destination to the selected Pod IP:Port
5(routing)Kernel routes the rewritten packet to the Pod's node
🧠 The Probability Math: iptables rules are sequential. Rule 1: 33.3% → wk-03. Rule 2: 50% of remaining 66.7% = 33.3% → wk-04. Rule 3: all remaining 33.3% → wk-05. Result: statistically even distribution. Every packet evaluates O(n) rules where n = endpoints.
📊 Rule Count Per Service: For 1 Service with 3 endpoints, kube-proxy creates ~12 iptables rules. 100 Services × 5 endpoints = ~6,000 rules. At 5,000 Services, hundreds of thousands of rules. iptables evaluates sequentially (O(n)), so packet processing time grows linearly with Service count.
⚠️ iptables Scalability Limit: iptables mode doesn't scale past ~5,000 Services. IPVS mode uses a kernel hash table (O(1)) instead of sequential rules, supporting round-robin, least-connection, and source-hash scheduling. For anihpj (well under 1,000 Services), iptables is fine.

🌐 Three Networks, One Cluster

6.2 Raft Consensus — How 3 Nodes Agree on State

Raft is the consensus algorithm that keeps all etcd nodes in sync. There is exactly one Leader and two (or more) Followers. All writes go through the Leader, which replicates them to the Followers.

Write Flow — What Happens When You Run kubectl create deployment

StepComponentAction
1API serverReceives the create request, validates it, encodes as protobuf
2API server → etcd LeaderSends Put request to the etcd Leader (cp-01)
3etcd Leader (cp-01)Appends the entry to its WAL (Write-Ahead Log) — this is an fsync'd write to disk
4etcd Leader → FollowersSends AppendEntries RPC to ALL Followers (cp-02, cp-03)
5Followers (cp-02, cp-03)Write to their WAL and send ACK back to Leader
6etcd LeaderOnce quorum (2 out of 3 nodes) ACKs → entry is COMMITTED
7etcd LeaderApplies the entry to its state machine (the in-memory B-tree key-value store)
8etcd Leader → API serverResponds with the new revision number
9API server → kubectlReturns 201 Created

Leader Election — What Happens When the Leader Dies

🔁 Election Process:
  • If the Leader dies (or fails to send heartbeats within ~100ms), Followers detect a timeout and start an election
  • Each Follower increments its term and votes for ONE candidate (itself or another Follower)
  • A candidate needs majority (2 out of 3 votes) to become the new Leader
  • Election timeout: ~150-300ms — randomized per node to prevent split votes
  • During election: NO writes are accepted. Reads still work if quorum exists
  • Once a Leader is elected, it starts sending AppendEntries (heartbeats) and normal operation resumes
⚠️ The Split-Vote Problem: In a 3-node cluster, if two Followers start elections at exactly the same time, each votes for itself — neither gets a majority (each has 1 of 3 votes). The election fails, both wait for another random timeout, and try again. This is why the election timeout is randomized: it makes simultaneous elections statistically unlikely.

6.4 How the API Server Interacts with etcd

The API server is the ONLY component that talks directly to etcd. No other component — kubelet, scheduler, controller-manager, kubectl — ever touches etcd directly. They all go through the API server.

OperationAPI Server → etcdWhat Happens
LISTRange (prefix scan)kubectl get pods → API server sends a Range request on /registry/pods/default/ (prefix). etcd returns all matching keys sorted by key.
GETRange (single key)kubectl get pod webapp-xxx → Range on the exact key. Returns one key-value pair.
WATCHWatch (stream)kubectl get pods -w opens a long-lived gRPC stream. etcd pushes every create/update/delete event in real time.
CREATEPutAPI server validates → admits (webhooks) → encodes as protobuf → Put to etcd. Returns the new revision number.
UPDATEPut (same key, new value)Uses optimistic concurrency via resourceVersion. If another client modified the object first → 409 Conflict.
DELETEDeleteSoft-deletes with a tombstone marker. Data isn't physically removed until compaction runs later.
🧠 Optimistic Concurrency Explained: Every object in Kubernetes has a metadata.resourceVersion field. When you update an object, you must send the resourceVersion you read. If etcd's current resourceVersion doesn't match (someone else updated it), the update is rejected with 409 Conflict. This is the same idea as "compare-and-swap" — no locks, no deadlocks, just "try again if someone beat you to it."

6.5 etcd MVCC & Revisions — Time Travel in the Database

etcd uses Multi-Version Concurrency Control (MVCC). Every write creates a NEW revision — old values are preserved until compaction removes them. This means you can read the state of any key at any historical revision.

  Revision 100,050: ContainerCreating (image pulled, volumes mounted)
  Revision 100,100: Running          (container started, IP assigned)
  Revision 100,500: Running          (status heartbeat updated)
  Revision 105,000: Running          (another heartbeat update)
  Revision 110,000: Terminating      (deletionTimestamp set, grace period starts)
  Revision 110,001: Deleted          (tombstone marker — removed after compaction)
MVCC FeatureWhy It Matters for Kubernetes
Historical reads
etcdctl get /key --rev=100000		You can read the Pod spec as it was at any past revision. Useful for auditing and debugging.
Watches from revision
etcdctl watch /key --rev=100000		Watches can start from ANY revision, not just "now." If a controller restarts, it can replay events from its last known revision.
Optimistic concurrency
resourceVersion		"Only update if current revision == 110,000." Prevents lost updates when multiple clients modify the same object.
⚠️ Compaction — The Silent Killer: Old revisions accumulate and consume disk space. Without compaction, etcd eventually runs out of disk and dies. Kubernetes defaults: compact every 5 minutes, keep the last 5 minutes of history. DO NOT disable compaction.
💡 Compaction Command: etcdctl compaction 110000 --physical removes all revisions older than 110,000 and defragments the database file. The --physical flag actually shrinks the file on disk.

6.13 etcd Disaster Scenarios — What Happens When Things Go Wrong

ScenarioImpactRecovery
Scenario A: 1 etcd node fails✅ Cluster still has quorum (2/3). Writes continue. All operations normal. No user impact.Replace the failed node within hours. No data loss. No downtime.

🥇 Golden Rule of etcd: The more backups you have, the better you sleep. Test your restore procedure monthly. A backup you haven't tested is not a backup — it's a hope. And hope is not a disaster recovery strategy.

🧠 Raft Consensus Visualized — How 3 Nodes Agree on Every Write

📝 Step 1: Leader Receives Write

kubectl apply → API server → etcd client → cp-01 (Leader) receives the write. Appends to its own WAL but does NOT commit yet.

📤 Step 2: Replicate to Followers

Leader sends AppendEntries RPC to cp-02 and cp-03. Each follower writes to its WAL and ACKs. Waits for quorum (2/3).

✅ Step 3: Commit & Apply

After 2/3 ACK, leader commits → increments commit index → applies to state machine. Followers learn commit on next AppendEntries heartbeat.

🔑 Why 3 nodes? Quorum = 2, can lose 1. With 5 nodes, quorum = 3, can lose 2. Each additional node adds replication overhead. Never use an even number — a 2-node cluster has quorum of 2 and can't survive ANY failure.

🔑 Part 6 Key Takeaways — etcd: The Brain

🗳️
Raft Needs Quorum to Write

3 nodes: quorum=2, lose 1 safely. 5 nodes: quorum=3, lose 2. Never use even numbers. If quorum is lost, the cluster becomes read-only.

🔐
API Server Is the ONLY etcd Client

No other component talks to etcd directly. This is by design — the API server validates, authenticates, and authorizes every operation before it reaches etcd.

💾
Backups Are Non-Negotiable

Snapshot every 6 hours. Test restore monthly. A backup you haven't tested is hope, not a strategy. If all 3 nodes fail, your last snapshot is your only recovery path.

⚡
SSD Is Mandatory for etcd

Every write calls fsync(). Spinning disks = 5-10ms per fsync = unusable cluster. NFS/EBS without Provisioned IOPS = frequent leader elections. Use local SSD or high-IOPS cloud volumes.

📊
MVCC Enables Time Travel

Every write creates a new revision. Old values are kept until compaction. You can read any key at any past revision. This enables watches to replay from any point in time.

🔒
Encrypt Secrets at Rest

etcd stores data as plain protobuf. Anyone with root access to a CP node can read all Secrets (they're base64-encoded, not encrypted). Enable EncryptionConfiguration.

7.1 Upgrading the Cluster with kubeadm

kubeadm supports upgrading one minor version at a time (e.g., 1.31 → 1.32). You cannot skip minor versions. Each upgrade follows a strict sequence: Control Plane first, Workers second, one node at a time.

⚠️ Pre-Upgrade Checklist
  • ✅ Backup etcd — snapshot before touching anything (see Part 6.8)
  • ✅ Read the release notes — check for breaking changes and deprecated API removals
  • ✅ Verify CNI compatibility — is Calico v3.28 compatible with the new k8s version?
  • ✅ Check the upgrade plan — kubeadm upgrade plan tells you exactly what will change
  • ✅ Schedule a maintenance window — API server may be briefly unavailable during CP upgrades

Step 1: Upgrade kubeadm on cp-01

terminal — cp-01 
apt-mark unhold kubeadm
apt-get update && apt-get install -y kubeadm=1.31.4-*
apt-mark hold kubeadm

Step 2: Verify the Upgrade Plan

terminal — upgrade plan 
kubeadm upgrade plan
# Output shows:
#   - Current version: v1.31.0
#   - Available upgrades: v1.31.4 (stable), v1.32.0 (stable)
#   - Components that CAN be upgraded: kube-apiserver, kube-controller-manager,
#       kube-scheduler, kube-proxy, CoreDNS, etcd
#   - Components that MUST be upgraded manually: kubelet (you do this next)

Step 3: Apply the Upgrade

terminal — kubeadm upgrade apply 
kubeadm upgrade apply v1.31.4
# This performs:
#   1. Renews certificates if they're close to expiry
#   2. Upgrades static Pod manifests (etcd, apiserver, scheduler, controller-manager)
#   3. Upgrades kubelet configuration on this node
#   4. Updates kubeadm-config and kubelet-config ConfigMaps in the cluster
#   5. Upgrades CoreDNS and kube-proxy addons
#   6. Does NOT upgrade kubelet itself — you do that in Step 4
💡 What "upgrade apply" actually does: kubeadm reads the current cluster configuration from the kubeadm-config ConfigMap, compares it with the new version's defaults, and generates updated static Pod manifests in /etc/kubernetes/manifests/. The kubelet detects the changed manifests and restarts the containers. The API server is briefly unavailable (~5-30 seconds).

systemctl restart kubelet

Bulk Worker Upgrade Loop

terminal — bulk worker upgrade loop 
for node in wk-{01..05}; do
  echo "=== Upgrading $node ==="
  kubectl drain $node --ignore-daemonsets --delete-emptydir-data --timeout=5m
  ssh $node "apt-get update && apt-get install -y kubeadm=1.31.4-* && \
             kubeadm upgrade node && \
             apt-get install -y kubelet=1.31.4-* && \
             systemctl restart kubelet"
  kubectl uncordon $node
  kubectl wait --for=condition=Ready node/$node --timeout=120s
  echo "=== $node complete ==="
done
🧠 Why "drain before upgrade" matters: kubectl drain gracefully evicts all Pods from the node. The Deployment controller sees the evicted Pods and creates replacements on healthy nodes — zero downtime. --ignore-daemonsets skips Calico/kube-proxy Pods (they run on every node by design). --delete-emptydir-data allows eviction of Pods using emptyDir volumes.

🔑 Part 7 Key Takeaways — Day 2 Operations

⬆️ Upgrade CP First, Then Workers

cp-01 uses kubeadm upgrade apply. Other CPs use kubeadm upgrade node. Workers: drain → upgrade → uncordon. One node at a time, never skip minor versions.

📅 Renew Certs Before They Expire

Leaf certs expire in 1 year. CAs in 10 years. Run kubeadm certs check-expiration monthly. Set a calendar reminder 30 days before expiry.

🔍 Follow the Decision Tree

Pending? Check scheduling. ContainerCreating? Check image pull. CrashLoopBackOff? Check logs --previous. Running but not Ready? Check readiness probes.

💾 Always Backup etcd First

Before any upgrade or maintenance on CP nodes, take an etcd snapshot. If something goes wrong, you can always restore. A backup you haven't tested is hope, not a strategy.

8.1 Pre-requisites — All 10 Nodes

Run this as root on EVERY node (cp-01..03, wk-01..05, fe-01..02) BEFORE running kubeadm init/join. This configures the Linux kernel, installs containerd, and installs Kubernetes binaries:

Part A: Kernel Modules & System Configuration

bash — run on ALL nodes as root 
#!/bin/bash
# ── Load required kernel modules ──
cat <<EOF | tee /etc/modules-load.d/k8s.conf
overlay
br_netfilter
EOF
modprobe overlay
modprobe br_netfilter
💡 Why these modules? overlay enables OverlayFS — required by containerd for container image layers. br_netfilter enables iptables to see bridged traffic — without it, NetworkPolicy won't work because iptables rules are bypassed on bridge interfaces.
bash — kernel networking + swap 
# ── Set kernel networking parameters ──
cat <<EOF | tee /etc/sysctl.d/99-kubernetes.conf
net.bridge.bridge-nf-call-iptables  = 1
net.bridge.bridge-nf-call-ip6tables = 1
net.ipv4.ip_forward                 = 1
EOF
sysctl --system

# ── Disable swap (REQUIRED by Kubernetes) ──
swapoff -a
sed -i '/swap/d' /etc/fstab
💡 Why these sysctls? bridge-nf-call-iptables ensures bridge-traversing packets pass through iptables for kube-proxy rules. ip_forward enables Pod-to-Pod packet forwarding. Swap must be OFF — Kubernetes' QoS model assumes guaranteed memory; swapped Pods break memory accounting.

Part B: Install Container Runtime (containerd)

bash — install & configure containerd 
apt-get update && apt-get install -y containerd
mkdir -p /etc/containerd
containerd config default | tee /etc/containerd/config.toml

# CRITICAL: Use systemd as the cgroup driver (matches kubelet default)
sed -i 's/SystemdCgroup = false/SystemdCgroup = true/' /etc/containerd/config.toml
systemctl restart containerd
systemctl enable containerd
🧠 The cgroup driver mismatch is the #1 bootstrap failure: containerd defaults to cgroupfs driver, but kubelet defaults to systemd. If they mismatch, kubelet can't enforce resource limits. ALWAYS set containerd to systemd.

Part C: Install Kubernetes Binaries

bash — install kubeadm, kubelet, kubectl 
apt-get update && apt-get install -y apt-transport-https ca-certificates curl gpg

curl -fsSL https://pkgs.k8s.io/core:/stable:/v1.31/deb/Release.key | \
  gpg --dearmor -o /etc/apt/keyrings/kubernetes-apt-keyring.gpg

echo 'deb [signed-by=/etc/apt/keyrings/kubernetes-apt-keyring.gpg] https://pkgs.k8s.io/core:/stable:/v1.31/deb/ /' | \
  tee /etc/apt/sources.list.d/kubernetes.list

apt-get update && apt-get install -y kubelet kubeadm kubectl
apt-mark hold kubelet kubeadm kubectl

# Enable kubelet (will fail until kubeadm init/join — that's OK!)
systemctl enable kubelet
💡 Why apt-mark hold? Prevents unattended-upgrades from accidentally upgrading Kubernetes packages. K8s upgrades must be deliberate. Kubelet crash-loops until init/join creates config — this is expected.

8.6 Deploy the anihpj Application Stack

Create Namespace + Deploy Webapp + Expose Service + Ingress

terminal — deploy anihpj stack 
kubectl create namespace anihpj-prod

apiVersion: apps/v1
kind: Deployment
metadata:
  name: webapp
  namespace: anihpj-prod
spec:
  replicas: 3
  selector:
    matchLabels:
      app: webapp
  template:
    metadata:
      labels:
        app: webapp
    spec:
      containers:
      - name: webapp
        image: registry.anihpj.io/webapp:v1.2.3
        ports:
        - containerPort: 8080
        resources:
          requests: { cpu: 250m, memory: 256Mi }
          limits:   { cpu: 1000m, memory: 512Mi }
        livenessProbe:
          httpGet: { path: /healthz, port: 8080 }
          initialDelaySeconds: 15
          periodSeconds: 10
        readinessProbe:
          httpGet: { path: /readyz, port: 8080 }
          initialDelaySeconds: 5
          periodSeconds: 5
EOF

# Verify:
kubectl get all -n anihpj-prod
curl -k https://anihpj.io/api/jobs
# {"jobs": [...]}  ← Application is live!
💡 Why two probes? Liveness = "restart me if I'm stuck" — failing /healthz kills and restarts the container. Readiness = "I'm ready for traffic" — failing /readyz removes the Pod from Service endpoints but does NOT restart it.
