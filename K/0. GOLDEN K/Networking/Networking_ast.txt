Chapter 1: What Is Networking? (The Big Picture)
--------------------------------------------------------------------------------
    1.1  Why Networking Matters for SRE/Platform Engineers
         - Every outage has a network dimension — "it's always DNS... or the network"
         - The SRE networking mindset: observe → hypothesize → verify
         - Real incident: "Users can't reach jobpost.anihpj.com" — where do you start?
         - What you'll actually observe: timeout errors, connection refused, 502 Bad Gateway, half-open connections
         [INCIDENT FLOWCHART: User reports outage → Network? App? DNS? DB?]
         [⚠️ GOTCHA] "ping works but curl doesn't" does NOT mean the network is fine. ICMP is often allowed while TCP ports are blocked.

    1.3  Encapsulation — The Russian Doll of Networking
         - Data flows DOWN the stack (encapsulation: headers get ADDED at each layer)
         - Data flows UP the stack (decapsulation: headers get STRIPPED at each layer)
         - Each layer only looks at ITS header — L3 doesn't care about L4's TCP flags
         [⚠️ GOTCHA] When you see "TCP payload" in a packet, it's the HTTP request. When you see "IP payload", it's the TCP segment. Same bytes, different perspective.
         [ENCAPSULATION WALK-THROUGH — anihpj GET /api/jobs/ request]

    1.4  The TCP/IP Model — What We Actually Use
         - 4 layers instead of 7: Link → Internet → Transport → Application
         - Why TCP/IP won and OSI stayed theoretical (TCP/IP was free, working, and already deployed)
         - Layers 5-6-7 (Session, Presentation, Application) all collapse into "Application" in TCP/IP

Chapter 2: Layer 1 — The Physical Layer (Bits on the Wire)
--------------------------------------------------------------------------------
    2.1  What Actually Travels Through a Cable?
         - Voltage changes, light pulses, radio waves — it's all just signaling
         - Encoding: how 1s and 0s become physical signals (Manchester, NRZ, PAM4)
         - Why SREs need to care: "Is the link up?" → ethtool eth0, ip link show
         - Real observation: `ip link show eth0` → state UP/DOWN, `ethtool eth0` → Speed, Duplex, Link detected
         [⚠️ GOTCHA] A link can be "UP" at L1 but have 90% packet loss from a bad cable. UP ≠ healthy.
         [DIAGRAM: Oscilloscope view of an Ethernet signal — bits → voltage transitions]

    2.2  Ethernet — The Universal LAN Protocol
         - Evolution: 10 Mbps → 100 Mbps → 1 Gbps → 10 Gbps → 25/40/100 Gbps → 400 Gbps
         - Ethernet frame structure: Preamble(8) | Dest MAC(6) | Src MAC(6) | EtherType(2) | Payload(46-1500) | FCS(4)
         - Why Ethernet won: simplicity, cost, backward compatibility (a 1990 NIC still works on a 2025 switch!)
         - Jumbo frames: MTU 9000 vs 1500 — when to use, when it breaks everything
         [⚠️ GOTCHA] Docker overlay networks add VXLAN overhead (50 bytes). If your physical NIC MTU is 1500, container MTU must be 1450 or less, or packets get silently dropped (PMTU black hole).
         [ETH FRAME ANATOMY DIAGRAM — each field labeled, byte offsets, and explanation]

    2.3  MAC Addresses — The Hardware Identity
         - Format: aa:bb:cc:dd:ee:ff (48 bits — first 24 = OUI/vendor, last 24 = NIC-specific)
         - How to find MAC addresses on Linux: ip link show | grep ether
         - Unicast (first byte even) vs Multicast (01:00:5E...) vs Broadcast (ff:ff:ff:ff:ff:ff)
         - MAC address randomization on Wi-Fi (privacy) and why it breaks enterprise networks
         [⚠️ GOTCHA] MAC addresses are L2-only — they never cross a router. If you see the same MAC on two different subnets, you're on the same L2 broadcast domain.
         [LAB 🛠️] Find the MAC of your eth0 and your Docker bridge (docker0)

    2.4  Switches — The Silent Workhorses
         - How a switch learns MAC addresses (MAC address table / CAM table)
         - Forwarding vs Flooding vs Filtering — the three F's
         - Managed vs Unmanaged switches (VLAN support, SNMP, port mirroring for tcpdump)
         - VLANs: splitting one physical switch into multiple logical networks (802.1Q tags)
         - Trunk ports vs Access ports — when a port carries multiple VLANs
         - Broadcast domains: a broadcast on VLAN 10 does NOT reach VLAN 20 (without routing)
         [⚠️ GOTCHA] A misconfigured VLAN tag means the switch drops the frame silently. No ICMP error. The packet just disappears. This is why VLAN issues are so hard to debug.
         [DIAGRAM: Switch MAC learning process — step by step with table state changes]

         [SWITCH OPERATION — 4-step learning process]
         ┌─────────────────────────────────────────────────────────────────────┐
         │  SWITCH MAC ADDRESS TABLE (initially empty)                         │
         │  ┌──────────┬─────────┐                                             │
         │  │ MAC Addr │ Port    │                                             │
         │  ├──────────┼─────────┤                                             │

    2.5  ARP — How IP Addresses Become MAC Addresses
         - The problem: I know 192.168.1.5, but what's its MAC address? IP needs L2 delivery.
         - ARP request (broadcast to ff:ff:ff:ff:ff:ff): "Who has 192.168.1.5? Tell 192.168.1.1"
         - ARP reply (unicast): "192.168.1.5 is at aa:bb:cc:dd:ee:ff"
         - ARP cache: `ip neigh show` — entries have states: REACHABLE, STALE, DELAY, PROBE, FAILED
         - Gratuitous ARP: "I am 192.168.1.5" (unsolicited) — used for IP takeover (keepalived, failover)
         - ARP spoofing/poisoning: attacker sends forged ARP replies to redirect traffic (MITM attack)
         [⚠️ GOTCHA] `ip neigh show` showing STALE doesn't mean broken. STALE = "still usable, will verify on next use." Only FAILED means the neighbor is unreachable.
         [OBSERVE] `tcpdump -i eth0 -nn arp` — watch ARP requests and replies in real time

Chapter 3: Wireshark & Packet Analysis Fundamentals
--------------------------------------------------------------------------------
    3.1  Why Packet Analysis Is an SRE Superpower
         - "The logs say timeout, but WHY?" — packets don't lie, applications do
         - tcpdump (CLI, remote servers) vs Wireshark (GUI, deep analysis) vs TShark (scriptable)
         - Capturing packets on servers, containers (`nsenter -t <pid> -n tcpdump`), and Kubernetes pods (`kubectl debug`)
         - The SRE packet capture workflow: capture → filter → analyze → fix → verify
         [⚠️ GOTCHA] Running tcpdump on a high-traffic server without a filter can overwhelm the CPU (BPF runs in kernel, but output to stdout is expensive). Always use filters.
         [DECISION TREE: Which capture tool for which scenario — local, remote, container, K8s]

    3.2  tcpdump — The Command-Line Packet Sniffer
         - Basic syntax: tcpdump -i <interface> [BPF filter expression]
         - Essential filters: host, port, net, proto (tcp/udp/icmp), src, dst, and/or/not
         - Reading tcpdump output line by line: timestamp, src > dst, flags, seq, ack, win, length
         - Writing to file (-w capture.pcap) and reading back (-r capture.pcap)
         - BPF (Berkeley Packet Filter) bytecode: tcpdump -d (see the BPF program compiled from your filter)
         - Ring buffer mode: -W 5 -C 100 -Z root (rotate files, production-safe)
         [⚠️ GOTCHA] tcpdump by default only captures the first 96 bytes of each packet. Use -s 0 for full packet capture. Without -s 0, you'll miss the HTTP body in your capture.
         [TABLE: 30 tcpdump filter recipes organized by debugging scenario]

    3.3  Wireshark — The GUI That Makes Packets Visible
         - The three-pane view: Packet List (summary) → Packet Details (tree) → Packet Bytes (hex dump)
         - Following TCP streams: right-click → Follow → TCP Stream (see the full conversation)
         - Display filters (post-capture) vs Capture filters (pre-capture, BPF-based)
         - Coloring rules: TCP RST = red, TCP SYN = dark gray, HTTP = green
         - Statistics menu: I/O Graph (throughput over time), TCP Stream Graph (seq/ack analysis)
         - Exporting objects: File → Export Objects → HTTP (extract transferred files)
         [SCREENSHOT-STYLE BREAKDOWN: Wireshark window with every pane annotated]

          [DEBUGGING 🐞] "Too many TIME_WAIT connections on the anihpj server" — root cause and fix
    8.9  TCP Keep-Alive — Detecting Dead Connections
          - The problem: a client crashes without sending FIN. The server waits forever.
          - Keep-alive probes: after idle period, send probe packets. If no response, close connection.
          - Kernel defaults: tcp_keepalive_time=7200 (2 hours!), tcp_keepalive_intvl=75, tcp_keepalive_probes=9
          - Why defaults are terrible: 2h11m to detect a dead connection! Most apps use application-level keep-alive instead.
          - HTTP Keep-Alive vs TCP Keep-Alive: different things! HTTP Keep-Alive reuses connections. TCP Keep-Alive detects dead peers.
          [⚠️ GOTCHA] TCP keep-alive at 7200s means a dead DB connection might hold resources for 2+ hours. App-level connection pools (HikariCP, pgBouncer) implement their own keep-alive at 30-60s for this reason.
          [OBSERVE] `ss -tno` shows keep-alive timer for each connection. `sysctl net.ipv4.tcp_keepalive_time` shows current setting.

    8.10  TCP Tuning for SREs — Kernel Knobs That Matter
          - tcp_tw_reuse (net.ipv4.tcp_tw_reuse=1): allow reusing TIME_WAIT sockets for OUTGOING connections (client-side, safe)
          - somaxconn (net.core.somaxconn=4096): maximum backlog for listening sockets (increase from default 128!)
          - tcp_max_syn_backlog (net.ipv4.tcp_max_syn_backlog=8192): max half-open SYNs before dropping
          - tcp_syncookies (net.ipv4.tcp_syncookies=1): protect against SYN flood attacks
          - tcp_fin_timeout (net.ipv4.tcp_fin_timeout=60): how long to wait in FIN-WAIT-2
          - tcp_keepalive_time/intvl/probes: detect dead connections (default: 7200s — way too long for most apps!)
          - BBR congestion control: `echo bbr > /proc/sys/net/ipv4/tcp_congestion_control` (better throughput on lossy links)
          [⚠️ GOTCHA] NEVER set tcp_tw_recycle=1. It was removed from Linux 4.12 because it broke NAT'd clients (timestamps from different clients behind same NAT look identical). Use tcp_tw_reuse instead.
          [OBSERVE] `sysctl net.ipv4.tcp_rmem` — read buffer auto-tuning. `ss -tim` — per-socket TCP info (rtt, cwnd, retrans, etc.)

Chapter 9: UDP — The Fast & Simple Protocol
--------------------------------------------------------------------------------
    9.1  When to Use UDP Instead of TCP
         - No connection, no guarantees — just send and hope
         - Use cases: DNS, streaming, gaming, VoIP, NTP, QUIC
         - The tradeoff: speed and simplicity vs reliability
         [COMPARISON TABLE: TCP vs UDP — 15 dimensions]

         [TCP vs UDP COMPARISON]
         ┌──────────────────┬──────────────────┬──────────────────┐
         │    FEATURE        │       TCP        │       UDP        │
         ├──────────────────┼──────────────────┼──────────────────┤
         │ Connection        │ Connection-oriented│ Connectionless  │
         │ Reliability       │ Guaranteed delivery│ Best-effort     │
         │ Ordering          │ In-order delivery │ No ordering      │
         │ Flow Control      │ Yes (sliding window)│ No              │
         │ Congestion Ctrl   │ Yes (cwnd)        │ No               │
         │ Header Size       │ 20-60 bytes       │ 8 bytes          │
         │ Speed             │ Slower (overhead) │ Faster           │
         │ Use Cases         │ HTTP, SSH, DB     │ DNS, VoIP, NTP   │
         │ anihpj example    │ Django ↔ Postgres │ jobpost metrics  │
         │                   │ gunicorn ↔ Nginx  │ to Datadog (UDP) │
         └──────────────────┴──────────────────┴──────────────────┘

    9.2  The UDP Header — Just 8 Bytes
         - Source Port, Destination Port, Length, Checksum
         - Simplicity is the feature — nothing else
         [UDP HEADER ANATOMY — 8-byte minimalist diagram]

    9.3  UDP in Modern Infrastructure
         - DNS over UDP (and when it falls back to TCP at 512 bytes)
         - HTTP/3 runs over QUIC, which runs over UDP
         - Why Kubernetes CoreDNS uses UDP by default
         - metrics, logs, traces — observability pipelines often use UDP

    9.4  Where UDP Goes Wrong — Silent Failures
         - No delivery guarantees: packet sent ≠ packet received. No ACK, no retransmission.
         - No ordering: packet 2 may arrive before packet 1. Application must reorder.
         - No congestion control: UDP can flood the network and cause collateral damage
         - Fragmentation danger: UDP packets > MTU get fragmented at IP layer. If one fragment is lost, the ENTIRE datagram is discarded
         - DNS over UDP: responses > 512 bytes trigger truncation (TC flag), forcing retry over TCP
         [⚠️ GOTCHA] UDP checksum is OPTIONAL in IPv4 (mandatory in IPv6). A corrupted UDP packet with checksum=0 will be accepted! Most modern OSes enforce UDP checksums, but it's technically legal to skip them.
         [OBSERVE] `tcpdump -i any udp and port 53` — watch DNS queries over UDP. Notice: one packet out, one packet back. No handshake.

    12.4  HTTP Headers — The Ones You See Every Day
          - Request headers: Host (which site), User-Agent (browser/curl version), Accept (formats client accepts), Authorization (Bearer tokens), Cookie (session data), Content-Type (what's being sent)
          - Response headers: Content-Type (JSON/HTML/etc.), Content-Length, Set-Cookie, Cache-Control (max-age, no-cache), Location (for redirects), Server (nginx/gunicorn)
          - Security headers: Strict-Transport-Security (HSTS — always use HTTPS), X-Content-Type-Options (nosniff), X-Frame-Options (prevent clickjacking), Content-Security-Policy (CSP — limit resource sources)
          - CORS headers: Access-Control-Allow-Origin (which domains can call this API), Access-Control-Allow-Methods, Access-Control-Allow-Headers
          [⚠️ GOTCHA] CORS is enforced by the BROWSER, not the server. curl, Postman, and backend-to-backend calls bypass CORS completely. If you get a CORS error in curl, the problem is something else.
          [OBSERVE] `curl -v https://jobpost.anihpj.com/api/jobs/ 2>&1 | grep -E '^[<>] '` — see all request and response headers

    12.5  HTTP/1.1 — The Workhorse (Keep-Alive, Pipelining, Head-of-Line Blocking)

          - Pipelining: send multiple requests without waiting (rarely used, buggy)
          - Head-of-Line (HOL) blocking: one slow response blocks all subsequent ones
          - Chunked transfer encoding: send data without knowing Content-Length ahead

    13.1  SSL vs TLS — What's the Difference? (And Why Everyone Says It Wrong)
          - SSL (Secure Sockets Layer): the ORIGINAL protocol, invented by Netscape in 1995
          - SSL 1.0: never publicly released (too broken)
          - SSL 2.0 (1995): first public version — quickly found to have serious security flaws
          - SSL 3.0 (1996): complete redesign, served the internet for years
          - TLS 1.0 (1999): the upgrade — so similar to SSL 3.0 it's essentially "SSL 3.1"
          - TLS 1.1 (2006): improved security, deprecated in 2021
          - TLS 1.2 (2008): the workhorse for 15+ years, STILL widely used today
          - TLS 1.3 (2018): the current standard — faster (1-RTT), more secure, simpler
          [⚠️ GOTCHA] Everyone says "SSL certificate" but SSL is DEAD. SSL 2.0 and 3.0 are completely broken (POODLE attack, 2014). When people say "SSL" today, they mean TLS 1.2 or 1.3. But the term "SSL certificate" stuck — even AWS, GCP, and Azure still label their cert services as "SSL/TLS certificates."

    13.2  Why TLS Exists — The Problem of the Open Internet
          - Without TLS: anyone on the network path can READ your data (passwords, credit cards, API keys)
          - Without TLS: anyone on the network path can MODIFY your data (inject ads, malware, change bank details)
          - Without TLS: you have NO idea who you're actually talking to (could be a fake server in a coffee shop)
          - The 3 guarantees of TLS: Encryption (confidentiality — no one can read it), Authentication (you know who you're talking to), Integrity (data hasn't been tampered with)
          [⚠️ GOTCHA] TLS provides ENCRYPTION IN TRANSIT only. It does NOT protect data at rest (in a database) or data in use (in memory). TLS protects the pipe, not the endpoints.
          [BEFORE/AFTER: HTTP plaintext — tcpdump shows passwords in clear text. HTTP + TLS — same tcpdump shows encrypted gibberish]

    13.3  How Encryption Works — The Two Types You NEED to Understand
          - Symmetric Encryption: ONE key for both encrypting and decrypting. Like a physical key that both locks and unlocks the same door.
            → Algorithms: AES (128/256-bit), ChaCha20
            → Pros: FAST (hardware-accelerated on modern CPUs). Cons: how do you safely share the key?
            → Used in TLS for: bulk data transfer (the actual HTTP body, images, API responses)

          - Asymmetric Encryption (Public-Key): TWO mathematically related keys — a PUBLIC key (share with everyone) and a PRIVATE key (keep secret).
            → What the PUBLIC key encrypts, ONLY the PRIVATE key can decrypt. What the PRIVATE key signs, the PUBLIC key can verify.
            → Algorithms: RSA (2048/4096-bit), ECDSA (Elliptic Curve), Ed25519
            → Pros: solves the key-sharing problem. Cons: SLOW (100-1000x slower than symmetric)
            → Used in TLS for: the handshake — proving identity and securely exchanging the symmetric key

          [⚠️ GOTCHA] TLS uses BOTH. Asymmetric crypto during the handshake (to authenticate and exchange keys securely), then switches to symmetric crypto for the rest (for speed). This is called "hybrid encryption." If you used only asymmetric crypto, your website would be 1000x slower.

          [SYMMETRIC vs ASYMMETRIC — VISUAL COMPARISON]

    13.4  Public & Private Keys — The Core Concept Made Simple
          - Key pair: generated together, mathematically linked. You CANNOT derive the private key from the public key.
          - Public key: share with EVERYONE. Post it on your website. Put it in your TLS certificate. No risk.
          - Private key: NEVER share. NEVER put in git. NEVER email. If leaked, attacker can impersonate you.
          - What the key pair does:
            → Encryption: Anyone encrypts with your PUBLIC key → ONLY your PRIVATE key can decrypt it.
            → Signing: You sign with your PRIVATE key → ANYONE with your PUBLIC key can verify it's really from you.
          - Where keys live in the real world:
            → Server's private key: /etc/nginx/ssl/privkey.pem or a Kubernetes Secret
            → Server's public key: inside the TLS certificate that nginx sends to every browser
            → CA's private key: in a hardware security module (HSM), guarded 24/7
            → CA's public key: pre-installed in your OS/browser's "trust store"
          [⚠️ GOTCHA] If you lose your private key, you can't recover it. You must generate a NEW key pair and get a NEW certificate. There is NO "forgot password" for private keys.

    13.5  What Actually IS HTTPS? (HTTP + TLS, Explained)
          - HTTPS = HTTP over TLS. The exact same HTTP requests/responses, wrapped in a TLS-encrypted tunnel.
          - The workflow: TCP 3-way handshake → TLS handshake → HTTP request/response over encrypted channel
          - The padlock 🔒 in your browser means: "the TLS handshake succeeded and the connection is encrypted"
          - Clicking the padlock shows: the certificate details, which CA verified it, the cipher suite used
          - NOT all HTTPS is equally secure — an HTTPS site with an expired cert or weak cipher is still "HTTPS" but unsafe
          [⚠️ GOTCHA] HTTPS means "the connection is encrypted." It does NOT mean "the website is trustworthy." A phishing site at "paypaI.com" (with a capital i) can have a perfectly valid TLS certificate. TLS proves identity of the SERVER, not the INTENT of the people running it.

    13.6  The TLS Handshake — Step by Step (What Happens When You See That 🔒)
          - Goal: agree on a shared symmetric key WITHOUT anyone eavesdropping being able to figure it out
          - Step 1 — ClientHello: "I support TLS 1.3 with these cipher suites. Here's my random data + ECDHE key share."
          - Step 2 — ServerHello: "Let's use TLS 1.3 with AES-256-GCM. Here's my random data + ECDHE key share + certificate."
          - Step 3 — Key Exchange (ECDHE): both sides independently compute the SAME shared secret using each other's key shares. An eavesdropper sees the key shares but CANNOT compute the secret (Diffie-Hellman magic).
          - Step 4 — Certificate verification: client checks the server's certificate — is it signed by a trusted CA? Is it expired? Does the hostname match? Is it revoked?
          - Step 5 — Finished: "Everything from here is encrypted with the agreed symmetric key."
          - Total: TLS 1.3 handshake = 1 round trip (1-RTT). TLS 1.2 = 2 round trips (2-RTT). This is why TLS 1.3 makes websites faster.
          [⚠️ GOTCHA] If ANY step fails — wrong hostname, expired cert, untrusted CA, weak cipher — the browser shows a full-page warning. Users CAN click through, but most don't. An expired cert = your site is effectively down for 99% of users.

    13.7  Cipher Suites — What Those Long Strings Actually Mean
          - A cipher suite is a negotiated SET of algorithms used for one TLS connection
          - Example: TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384
          - Breaking it down word by word:
            → TLS = the protocol
            → ECDHE = Key Exchange algorithm (Elliptic Curve Diffie-Hellman Ephemeral — how the shared secret is negotiated)
            → RSA = Authentication algorithm (how the server proves it owns the certificate's private key)
            → AES_256_GCM = Bulk Encryption algorithm (symmetric cipher used for the actual data, with GCM authenticated mode)
            → SHA384 = Hash/PRF (Pseudo-Random Function for deriving keys and HMAC)
          - TLS 1.3 simplified this: cipher suites no longer specify key exchange or authentication — just symmetric cipher + hash
          - TLS 1.3 example: TLS_AES_256_GCM_SHA384 (much shorter — the rest is negotiated separately)
          [⚠️ GOTCHA] "AES-256" sounds more secure than "AES-128" but in practice AES-128 is already unbreakable with current technology. The real-world security difference is negligible — focus on TLS version (1.3 > 1.2) not key size.

    13.8  Common TLS Errors You Encounter Daily (And What They Actually Mean)
          - NET::ERR_CERT_AUTHORITY_INVALID ("Your connection is not private"): The CA that signed this cert is NOT in your trust store. Common causes: self-signed cert (dev servers), corporate proxy MITM, missing intermediate cert.
            → FIX: Add the CA cert to your trust store, or use a proper CA (Let's Encrypt for production)

          - NET::ERR_CERT_DATE_INVALID ("Your clock is behind/ahead"): The certificate's NotBefore/NotAfter dates don't include the current time. Common causes: expired cert (most common!), server clock wrong, client clock wrong.
            → FIX: Renew the cert, or check system clock: `date; timedatectl status`

          - NET::ERR_CERT_COMMON_NAME_INVALID: The hostname in the URL does NOT match any name in the certificate's CN or SAN fields. Common: accessing a service by IP instead of hostname, wildcard mismatch (*.example.com does NOT match example.com).
            → FIX: curl -k (skip verify, dev only!), add correct SAN to cert, use the correct hostname

          - SSL_ERROR_RX_RECORD_TOO_LONG: The server is speaking plain HTTP on port 443 (TLS port). Someone configured HTTPS but the server is sending HTTP.
            → FIX: Check that TLS is actually enabled on the server

          - "unable to verify the first certificate" (curl/openssl): Same as CERT_AUTHORITY_INVALID — trust chain broken. Often happens with internal/self-signed certs.
            → FIX: curl --cacert /path/to/ca.pem or add to system trust store

          - Mixed Content Warning (⚠️ in padlock): Page loaded over HTTPS but contains resources (images, scripts) loaded over HTTP. The page is partially encrypted.
            → FIX: Use protocol-relative URLs (//cdn.example.com) or always HTTPS

          [⚠️ GOTCHA] curl -k (or --insecure) DISABLES certificate verification entirely. NEVER use it in scripts or production. It makes TLS completely useless — you lose the "Authentication" guarantee. Only use in dev against known self-signed certs.

    13.9  TLS in Everyday SRE Tools — Where You've Seen It And Didn't Know
          - git: `git clone https://github.com/...` — TLS encrypts your git traffic. `git config --global http.sslVerify false` disables it (dangerous!)
          - pip: `pip install django` — downloads packages over HTTPS/TLS. Corporate proxies often break this with custom CA certs.
          - npm: `npm install` — same as pip. `NODE_EXTRA_CA_CERTS` env var for custom CAs.
          - curl: `curl https://api.example.com` — uses TLS by default on HTTPS URLs. `-k` bypasses verification.
          - wget: `wget https://...` — same. `--no-check-certificate` bypasses.
          - kubectl: `kubectl get pods` — communicates with the K8s API server over TLS. The kubeconfig contains the CA cert.
          - docker: `docker pull nginx` — registry communication over TLS (unless using insecure registries).
          - PostgreSQL: `psql "sslmode=require"` — database connections can use TLS.
          - Redis: `redis-cli --tls` — Redis 6+ supports TLS.
          [⚠️ GOTCHA] When your company uses a TLS-intercepting proxy (like Zscaler, Netskope), it acts as a Man-in-the-Middle — it terminates your TLS connection and creates a new one to the destination. This is why you need to install your company's CA certificate on your machine. Without it, ALL HTTPS traffic will show CERT_AUTHORITY_INVALID errors.

    13.10 TLS Termination — Where Encryption Ends
          - TLS termination = the point where encrypted TLS traffic is DECRYPTED into plain HTTP
          - Common termination points:
            → Cloud Load Balancer (AWS ALB, GCP HTTPS LB): terminates TLS, forwards plain HTTP to backend
            → nginx/Envoy reverse proxy: terminates TLS at the edge, talks HTTP to gunicorn/Django
            → K8s Ingress Controller: terminates TLS at the cluster edge
            → The application itself (Django/gunicorn with HTTPS): terminates TLS inside the app
          - "End-to-end TLS": traffic is encrypted ALL the way — browser → LB → app → database
          - "TLS offloading": terminating TLS at the LB, then plain HTTP inside your network (simpler, but less secure)
          [⚠️ GOTCHA] If your cloud LB terminates TLS and forwards HTTP to your backend, the backend sees HTTP traffic. If your Django app checks `request.is_secure()`, it will return False! Fix: set the X-Forwarded-Proto header at the LB and configure Django's SECURE_PROXY_SSL_HEADER.
          [DIAGRAM: TLS termination points — browser → LB (TLS ends) → HTTP to backend vs browser → LB (TLS pass-through) → TLS to backend]

    13.11 Certificates — The Chain of Trust
          - What is an X.509 certificate? Contains: Subject (CN), Issuer, Validity (NotBefore/NotAfter), Public Key, SANs (Subject Alternative Names), Key Usage
          - Certificate Authorities (CAs): trusted third parties that sign certificates. Root CAs → Intermediate CAs → Leaf (server) certs
          - The certificate chain: browser trusts Root CA → Root CA signed Intermediate → Intermediate signed your server cert
          - Let's Encrypt: free, automated certificates via ACME protocol (HTTP-01 or DNS-01 challenge)
          - Viewing a cert: `openssl s_client -connect jobpost.anihpj.com:443 -showcerts`
          [⚠️ GOTCHA] If the SAN field doesn't include the hostname you're connecting to, the browser rejects the cert even if CN matches. SAN > CN in modern TLS.

    15.2  Docker Network Drivers — The Complete Guide
          - bridge (default): isolated network on one host, NAT to reach outside, containers talk via docker0 bridge
          - host: container shares host's network stack — NO isolation but MAX performance (no NAT overhead)
          - none: no networking at all — only loopback. For security-sensitive workloads that need zero network access
          - overlay: multi-host networking across Docker Swarm nodes (VXLAN encapsulation)
          - macvlan: container gets its own REAL MAC address on the physical network — appears as separate physical device
          - ipvlan: like macvlan but shares MAC, gets unique IP — avoids switch MAC table limits
          [TABLE: Docker network drivers — isolation level, performance, multi-host, when to use]

          - Agents on a node can communicate with all pods on that node

          - Pods in the host network can communicate with pods without NAT

    18.2  CNI — The Plugin That Makes It Work

          - CNI execution flow: kubelet → CRI → CNI binary → IPAM → configure pod netns
          - Popular CNI plugins: Calico, Cilium, Flannel, Weave, Canal, Antrea, Azure CNI, AWS VPC CNI

          [KUBERNETES CNI EXECUTION FLOW — from pod creation to network ready]
          ┌─────────────────────────────────────────────────────────────────────┐
          │  1. kubelet receives PodSpec (from API server)                      │

    18.2a  CNI IPAM — How Pods Get Their IPs
          - IPAM (IP Address Management): the CNI sub-plugin that allocates IPs to pods
          - host-local: simple IPAM — each node gets a /24 subnet, pods get sequential IPs (works with Flannel)
          - calico-ipam: IP pools with block affinity — each node gets a /26 block (62 pod IPs)
          - AWS VPC IPAM: pods get actual VPC IPs from ENI secondary addresses (native networking, no overlay)
          - IP exhaustion: /24 per node = 254 pods max. Pod stays "ContainerCreating" with "failed to allocate IP"
          - Debugging IPAM: `kubectl describe pod <pod>` — Events show IP allocation success/failure
          - [⚠️ GOTCHA] AWS VPC CNI: t3.medium supports 2 ENIs × 3 IPs each = only 4 pod IPs (after subtracting 2 primary IPs). For more pods, use larger instances, prefix delegation, or switch to Calico/Cilium.
          [LAB 🛠️] `kubectl get nodes -o wide` — check pod CIDR per node. `kubectl get ippools` (Calico).

    18.2b  CNI Troubleshooting — When Pods Get No Network
          - Symptom: Pod stuck in ContainerCreating, "failed to set up pod network"
          - Check CNI pods: `kubectl get pods -n kube-system | grep -E 'calico|cilium|flannel'` — Running?
          - Check CNI config: SSH to node, `ls /etc/cni/net.d/` — .conf file present? Correct subnet?
          - Check CNI binary: `ls /opt/cni/bin/` — plugin binary installed? Correct version?
          - Common causes: CNI pod CrashLoopBackOff (check logs), kubelet can't reach CNI socket, IP pool exhausted, node taint preventing CNI scheduling, VPC subnet too small (AWS EKS)
          [OBSERVE] `kubectl logs -n kube-system <cni-pod>` — CNI logs show IP allocations, routing updates, errors

    18.2c  NetworkPolicy — Kubernetes Firewall Fundamentals
          - NetworkPolicy: L3/L4 firewall for pods (think "security group per pod/namespace")
          - Selector-based: pods selected by labels, traffic controlled by ingress/egress rules
          - Ingress: which sources (pods, namespaces, IP blocks) can send traffic TO selected pods
          - Egress: which destinations selected pods can send traffic TO
          - Default deny-all posture: create NetworkPolicy selecting all pods with empty ingress
          - CNI requirement: Calico ✅, Cilium ✅, Flannel ❌, AWS VPC CNI ❌ (add Calico on top)
          - [⚠️ GOTCHA] If NO NetworkPolicy selects a pod, ALL traffic is allowed. Must explicitly deny!
          - [⚠️ GOTCHA] NetworkPolicies are namespace-scoped. Policy in ns "anihpj" only affects pods there.
          [CODE: NetworkPolicy YAML — allow only jobpost pods to reach postgres on port 5432]
          [LAB 🛠️] Create NetworkPolicy, verify with `nc -zv` from a test pod in another namespace

    18.3  Overlay vs Underlay — How Pod Networks Actually Work
          - Overlay: VXLAN/Geneve encapsulation (packet inside a packet). Pod sends normal Ethernet frame → CNI wraps it in a UDP packet → sent to destination node → unwrapped → delivered to destination pod
          - Underlay/BGP: pods get routable IPs on the physical network. No encapsulation — faster but requires BGP on the switches.
          - The VXLAN header adds 50 bytes (8 UDP + 8 VXLAN + 14 inner Eth + 20 IP = outer overhead). This is why pod MTU must be 1450 on a 1500 MTU network.
          - Geneve vs VXLAN: Geneve is newer, more flexible (TLV options), used by Cilium. VXLAN is simpler, used by Flannel.
          [⚠️ GOTCHA] VXLAN uses UDP port 4789. If a firewall between K8s nodes blocks UDP 4789, pod-to-pod communication across nodes breaks silently. Check: `tcpdump -i eth0 'udp port 4789'` on each node.
          [DIAGRAM: Pod packet → VXLAN encapsulation → VXLAN decapsulation → destination pod — with byte offsets]

          [VXLAN ENCAPSULATION — what actually hits the wire]
          ┌─────────────────────────────────────────────────────────────────────┐
          │  OUTER ETHERNET HEADER  │ OUTER IP │ UDP │ VXLAN │ INNER ETHERNET   │
          │  (node MACs)            │ (node IPs│(4789│(VNI= │ (pod MACs, pod    │
          │                         │  to node)│ port)│ VPC)  │  IPs, TCP, HTTP) │
          ├─────────────────────────────────────────────────────────────────────┤
          │  14 bytes   │ 20 bytes │ 8 bytes│8 bytes│  original pod packet     │
          │             │          │        │       │  (up to 1450 bytes)       │
          │             │          │        │       │                           │
          │  TOTAL OVERHEAD = 50 bytes (14+20+8+8)                              │
          │  Max pod packet on 1500 MTU link = 1500 - 50 = 1450 bytes           │
          └─────────────────────────────────────────────────────────────────────┘

            → `kubectl exec <pod> -- ip route show` — check pod's routing table (default route?)
            → `kubectl exec <pod> -- ping <other-pod-ip>` — test pod-to-pod reachability (L3)

    19.6  K8s Pod Network Debugging Decision Tree
          - Symptom: "Pod A can't reach Pod B"
          - Step 1: Are both pods Running? `kubectl get pods -o wide -A | grep <name>`
          - Step 2: Can pod A ping pod B's IP? → YES: L3 works, check L4/L7. NO: check CNI.
          - Step 3: Same node or different node? `kubectl get pods -o wide` (compare NODE column)
            → Same node: check cni0 bridge: `bridge fdb show br cni0` on the node
            → Different node: check VXLAN: `tcpdump -i eth0 'udp port 4789'` on both nodes
          - Step 4: Are there NetworkPolicies blocking? `kubectl get networkpolicy -A | grep <ns>`
          - Step 5: Check CNI pod logs: `kubectl logs -n kube-system <cni-pod> --tail=100`
          - Step 6: Check node routing: SSH to both nodes, `ip route` — routes to pod subnets?
          - Step 7: tcpdump end-to-end: capture on src node cni0, dst node cni0, and VXLAN interface

    20.3  kube-proxy Modes — iptables vs IPVS vs Userspace vs eBPF
          - iptables mode (default): random backend selection, O(n) rule evaluation, degrades at scale
          - IPVS mode: Linux kernel L4 LB, O(1) lookup, 10+ scheduling algorithms (rr, lc, sh, dh)
          - userspace mode (legacy): slow, only for debugging
          - nftables mode (new): replaces iptables, better performance
          - eBPF mode (via Cilium): replaces kube-proxy entirely
          - When to switch: 1000+ services → IPVS; performance-critical → eBPF
          - How to check: kubectl logs -n kube-system kube-proxy-xxx | grep "Using"
          [COMPARISON TABLE: iptables vs IPVS vs eBPF — lookup, latency, scale, algorithms]

Chapter 21: Ingress & Ingress Controllers
--------------------------------------------------------------------------------
    21.1  Why Ingress Exists — Beyond Services
          - Services = L4 (TCP/UDP), Ingress = L7 (HTTP/HTTPS)
          - Path-based routing: /api/* → backend-A, /admin/* → backend-B
          - Host-based routing: api.anihpj.com → one service, admin.anihpj.com → another
          - TLS termination at the Ingress (one cert for all routes, not per-app)
          - The Ingress resource alone does NOTHING — it's just a configuration. An Ingress Controller (nginx, Traefik, HAProxy, AWS ALB) watches for Ingress resources and configures itself accordingly.
          [DIAGRAM: Ingress Controller routing traffic based on Host header and path]

    21.2  Ingress Controllers Compared — nginx vs Traefik vs AWS ALB vs Contour
          - nginx Ingress: the original, battle-tested, most deployed. Configured via ConfigMap + annotations.
          - Traefik: auto-discovers services, built-in dashboard, Let's Encrypt integration, middleware chaining
          - AWS Load Balancer Controller: provisions ALB/NLB, integrates with AWS Certificate Manager, WAF
          - Contour (Envoy-based): Gateway API native, advanced load balancing, rate limiting
          - HAProxy Ingress: the HAProxy power inside K8s, excellent L7 routing
          [COMPARISON TABLE: 5 Ingress Controllers — features, performance, TLS, observability, learning curve]
          [⚠️ GOTCHA] You can run MULTIPLE Ingress Controllers in the same cluster. Use IngressClass to specify which controller handles which Ingress resource. Without IngressClass, controllers fight over Ingress resources!

    21.3  NGINX Ingress Controller Deep Dive
          - Architecture: Ingress Controller pod watches K8s API → generates nginx.conf → reloads nginx
          - Key annotations: rewrite-target, ssl-redirect, proxy-body-size, proxy-read-timeout, cors-allow-origin
          - Custom error pages, rate limiting, IP whitelisting — all via annotations (no config files!)
          - The nginx template: /etc/nginx/template/nginx.tmpl — rendered from Go template with Ingress data
          - [⚠️ GOTCHA] Every Ingress change triggers an nginx RELOAD. With 100+ Ingress resources and frequent changes, reloads cause brief downtime. Fix: use Ingress Controller with dynamic reconfiguration (like Traefik or Envoy-based ones that use API-driven config, not file reloads).
          [DIAGRAM: Ingress Controller watch loop — K8s API → controller → nginx.conf template → nginx reload]

    21.4  TLS with Ingress — cert-manager Integration
          - cert-manager: automated certificate lifecycle management in K8s
          - How it works: Ingress annotation cert-manager.io/cluster-issuer → cert-manager creates CertificateRequest → ACME challenge (HTTP-01 or DNS-01) → Let's Encrypt issues cert → stored in K8s Secret → Ingress references Secret
          - ClusterIssuer vs Issuer: ClusterIssuer is cluster-wide, Issuer is namespace-scoped
          - Auto-renewal: cert-manager automatically renews certs 30 days before expiry
          - [⚠️ GOTCHA] HTTP-01 challenge requires port 80 to be publicly accessible. If your firewall blocks port 80 (common in enterprise environments), use DNS-01 challenge instead (requires DNS provider API access, e.g., Route53, Cloudflare).

Chapter 22: Gateway API — The Next-Gen Ingress
--------------------------------------------------------------------------------
    22.1  Why Gateway API Replaces Ingress
          - Ingress limitations: too simple, no cross-namespace routing, no weighted traffic splitting, no header-based routing, no traffic mirroring, no team role separation
          - Gateway API: GatewayClass → Gateway → HTTPRoute (expressive, role-oriented, extensible)
          - Key concepts: GatewayClass (platform/infra team — "what implementation?"), Gateway (cluster admin — "where do requests enter?"), HTTPRoute (app developer — "where do requests go?")
          - Role separation: app devs create HTTPRoutes in their namespace; platform team manages Gateways
          - Built-in features: canary deployments (weighted backends), A/B testing (header matching), traffic mirroring (copy % of traffic to test), request/response header modification, URL rewriting, cross-namespace routing
          [COMPARISON TABLE: Ingress vs Gateway API — 15 dimensions: routing, TLS, team roles, extensibility]

    22.2  Gateway API Resource Model — The Full Hierarchy
          - GatewayClass: defines the controller implementation (e.g., "envoy-gateway", "istio", "nginx-gateway")
            → Cluster-scoped. Only platform admins create these. One GatewayClass per controller type.
          - Gateway: a listener endpoint defined by cluster admins — "this Gateway listens on port 443 with TLS"
            → Namespace-scoped or cluster-scoped. Defines listeners (ports/protocols) and TLS config.
            → One Gateway can have multiple listeners: port 80 (HTTP) and port 443 (HTTPS).
          - HTTPRoute: application routing rules defined by app developers
            → Matches: path prefix (/api/*), path exact (/health), header (x-canary: v2), query param (?version=v2), method (GET, POST)
            → BackendRefs: one or more K8s Services, with optional weights for traffic splitting
            → Filters: request header modifier, response header modifier, URL rewrite, request redirect, request mirror
          - ReferenceGrant: explicit permission for cross-namespace backend references (prevents namespace A from accidentally routing to namespace B)
            → "Namespace B ALLOWS namespace A to reference its Service" — opt-in permission model
          - GRPCRoute + TLSRoute + TCPRoute + UDPRoute: for non-HTTP workloads

    22.3  Gateway API Implementations — Which One for Your Cluster?
          - Envoy Gateway: CNCF project, Kubernetes-native, dynamic xDS-based reconfiguration (no reloads!)
          - Istio Gateway API: full service mesh + Gateway API in one, supports ALL route types
          - nginx Gateway Fabric (NGINX Inc): nginx-based, production-grade, familiar to nginx users
          - Traefik Gateway Provider: Traefik's Gateway API support, built-in dashboard + middleware
          - Cilium Gateway API: eBPF-native Gateway implementation (no sidecars, no proxies per-pod!)
          - Kong Gateway Operator: Kong's Gateway API implementation with plugin ecosystem
          [COMPARISON TABLE: 6 Gateway API implementations — performance, features, maturity, eBPF support]

    22.4  Gateway API in Practice — anihpj Canary Deployment

Chapter 23: Service Mesh — The Next Layer of Networking
--------------------------------------------------------------------------------
    23.1  What Is a Service Mesh and Why Does It Exist?
          - The problem: every app team re-implementing retries, timeouts, TLS, observability
          - Service mesh: moves networking concerns OUT of the app into a sidecar proxy (Envoy/Linkerd-proxy)
          - Data plane (sidecars) vs Control plane (Istiod/Linkerd controller)
          - The sidecar pattern: every pod gets an extra proxy container injected
          - How sidecar interception works: init container sets up iptables rules to redirect ALL pod traffic through the sidecar
          [⚠️ GOTCHA] The init container runs BEFORE your app container. Its only job: `iptables -t nat -A PREROUTING -p tcp -j REDIRECT --to-port 15001`. All traffic in/out of the pod goes through the sidecar. If the sidecar crashes, the pod is completely isolated — no network at all.
          [OBSERVE] In any Istio-injected pod: `iptables -t nat -L -n -v` shows the redirect rules. `kubectl exec -it <pod> -c istio-proxy -- curl localhost:15000/config_dump` shows Envoy config.
          [DIAGRAM: App container ↔ sidecar proxy ↔ sidecar proxy ↔ App container — with iptables redirect]

    23.2  Service Mesh Capabilities
          - mTLS automatically between all services (no code changes!)
          - Traffic management: retries, timeouts, circuit breaking, fault injection
          - Traffic splitting: canary deployments, blue/green, A/B testing
          - Observability: automatic metrics, distributed tracing (Jaeger/Zipkin)
          - Istio vs Linkerd vs Cilium Service Mesh — comparison

Chapter 30: The Systematic Network Debugging Methodology
--------------------------------------------------------------------------------
    30.1  The Layered Approach — Always Start at the Bottom
          - Layer 1: Is the link up? (ip link, ethtool)
          - Layer 2: Is ARP resolving? (ip neigh, arping)
          - Layer 3: Can I ping/routing OK? (ping, ip route, traceroute)
          - Layer 4: Is the port open? (nc, ss, telnet)
          - Layer 7: Is the app responding correctly? (curl, HTTP status)
          [DEBUGGING FLOWCHART: Start → L1 OK? → L2 OK? → L3 OK? → L4 OK? → L7 OK?]

          [NETWORK DEBUGGING DECISION TREE — start here for every incident]
          ┌─────────────────────────────────────────────────────────────────────┐
          │  🚨 INCIDENT: "Users can't reach the jobpost app"                   │
          │                                                                      │
          │  Q1: Is the link up?                                                │
          │  ├── ip link show eth0 → state UP?                                  │
          │  │   └── NO → Check cable, switch port, NIC driver                  │
          │  │                                                                   │
          │  Q2: Can you ARP the gateway?                                       │
          │  ├── ip neigh show → gateway MAC present?                           │
          │  │   └── NO → L2 issue: VLAN, switch config, cable                 │
          │  │                                                                   │
          │  Q3: Can you ping external IP?                                       │
          │  ├── ping 8.8.8.8 → replies?                                        │
          │  │   └── NO → Check routing: ip route get 8.8.8.8                   │
          │  │       └── No default route? → ip route add default via ...       │
          │  │                                                                   │
          │  Q4: Can you reach the port?                                         │
          │  ├── nc -zv jobpost.anihpj.com 8000 → Connection refused?           │
          │  │   └── Service not running, firewall block, or wrong port         │
          │  │                                                                   │
          │  Q5: Is DNS resolving?                                               │
          │  ├── dig jobpost.anihpj.com → returns correct IP?                   │
          │  │   └── NO → Check CoreDNS, /etc/resolv.conf, upstream DNS         │
          │  │                                                                   │
          │  Q6: Is the app healthy?                                             │
          │  ├── curl -v http://jobpost.anihpj.com/health → 200 OK?             │
          │  │   └── NO → Check pod logs, readiness probe, DB connection        │
          └─────────────────────────────────────────────────────────────────────┘

    30.2  The First 5 Minutes — What to Check for ANY Network Issue
          - 1. `ip link show` (all interfaces up?)
          - 2. `ip addr show` (correct IPs assigned?)
          - 3. `ip route show` (default route exists?)
          - 4. `ip neigh show` (ARP working?)
          - 5. `ss -tlnp` (are services listening on expected ports?)
          - 6. `curl -v localhost:PORT` (can you reach it locally?)
          [CHEATSHEET: The 10-command first response checklist]

    30.3  Connection Refused vs Connection Timeout — The Crucial Difference
          - Connection Refused (ECONNREFUSED): SYN sent → RST received. Means: "I'm here, but nothing is listening on that port."
            → The destination host IS reachable. The service is down or on a different port.
          - Connection Timeout (ETIMEDOUT): SYN sent → no response → SYN retransmitted → still no response → timeout.
            → The destination is unreachable (firewall dropping, routing issue, host down, or wrong IP).
          - No Route to Host (EHOSTUNREACH): kernel can't find a route to the destination. Check `ip route`.
          [⚠️ GOTCHA] "Connection refused" actually means the network WORKS — the destination host received your packet and actively rejected it. Don't waste time debugging the network when you get ECONNREFUSED — check if the service is running!
          [OBSERVE] `curl -v http://10.0.1.50:8000` → "Connection refused" = port closed. `curl -v --connect-timeout 5 http://10.0.1.50:8000` → "Connection timed out" = network blocked.
          [DIAGRAM: Three scenarios — ECONNREFUSED (RST), ETIMEDOUT (silent drop), EHOSTUNREACH (no route)]

    30.4  Separating "Network Problem" from "Application Problem"
          - If curl from the SAME machine works, it's not the app
          - If curl from another pod works, it's likely network policy/CNI
          - If ping works but curl doesn't, it's L4+ (port, firewall, app)

    33.6  Common Network Attacks and How to Defend
          - DDoS: volumetric (flood bandwidth), protocol (SYN flood, exhaust state), application-layer (HTTP flood)

Chapter 34: Kubernetes Network Policies
--------------------------------------------------------------------------------
    34.1  NetworkPolicy — The Pod-Level Firewall
          - Default deny: with no policies, ALL traffic is allowed between all pods (dangerous!)
          - Ingress rules: who can send traffic TO pods matching this policy
          - Egress rules: where pods matching this policy can send traffic TO
          - Namespace selectors, pod selectors, IP block selectors (CIDR)
          - NetworkPolicies are ADDITIVE — if ANY policy selects a pod, only allowed traffic passes
          [⚠️ GOTCHA] Creating your FIRST NetworkPolicy that selects a pod immediately blocks ALL other traffic to that pod (implicit deny). Always create an "allow all" policy first, then restrict.

Chapter 35: TLS & Certificate Management in Production
--------------------------------------------------------------------------------
    35.1  The TLS Certificate Lifecycle
          - Issuance: generate CSR → submit to CA → CA validates domain ownership → CA issues certificate
          - Deployment: store cert + key as Kubernetes Secret → mount in pod or reference in Ingress
          - Renewal: certs expire! Automate renewal BEFORE expiry (cert-manager: 30 days before)
          - Revocation: if key is compromised → CA adds cert to CRL (Certificate Revocation List) or OCSP staple
          - Rotation: replace cert without downtime → update Secret → rolling restart or hot reload
          [⚠️ GOTCHA] A cert renewed by cert-manager creates a NEW Secret; your Ingress still references the OLD Secret. Use cert-manager annotations on Ingress, not static Secret references.
          [CERTIFICATE LIFECYCLE STATE DIAGRAM — issue → deploy → monitor → renew → revoke → replace]

Chapter 36: Designing Resilient Networks
--------------------------------------------------------------------------------
    36.1  High Availability Networking Patterns
          - Redundant links: LACP (Link Aggregation) bundles multiple physical links into one logical link
          - Multi-AZ deployment: load balancers across availability zones, applications in each AZ
          - BGP ECMP (Equal-Cost Multi-Path): multiple equal-cost paths distribute traffic across links
          - Active/Active vs Active/Passive: both paths carry traffic vs one path is standby
          [DIAGRAM: Multi-AZ HA network design for anihpj — 3 AZs, cross-AZ LB, DB replication]

          [HA PATTERNS — QUICK COMPARISON]
          ┌────────────────────┬─────────────────┬─────────────────┬──────────┐
          │ PATTERN            │ FAILOVER TIME   │ COST            │ COMPLEXITY│
          ├────────────────────┼─────────────────┼─────────────────┼──────────┤
          │ Active/Passive     │ 30s — 5 min     │ 1.5× (idle HW)  │ Low      │
          │ Active/Active      │ Instant (ECMP)  │ 2× baseline     │ Medium   │
          │ N+1 Redundancy     │ Depends on LB   │ +1 unit per N   │ Low      │
          │ Multi-AZ (3 AZs)   │ Instant (DNS/LB)│ 3× single-AZ    │ High     │
          │ Multi-Region       │ ~60s (DNS TTL)  │ 4×+ single-reg. │ Very High│
          │ Global LB (anycast)│ Instant (BGP)   │ Premium         │ Extreme  │
          └────────────────────┴─────────────────┴─────────────────┴──────────┘

    36.2  Disaster Recovery Networking
          - Cross-region DNS failover: Route53/Cloudflare health checks → switch traffic to standby region
          - Active-Active: both regions serve traffic (needs data sync). Active-Passive: one hot, one cold.
          - Pilot Light: minimal infrastructure running in DR region, scaled up on failover
          - RTO (Recovery Time Objective) vs RPO (Recovery Point Objective) — network design drives both
          [⚠️ GOTCHA] DNS failover is limited by TTL. If your TTL is 300s, clients may cache the OLD (failed) IP for up to 5 minutes after failover. Use low TTL (60s) for critical DNS records.

    37.1  Network Capacity Planning
          - How much bandwidth does your app need?
          - Estimating traffic: RPS × average request size + overhead = minimum bandwidth
          - Headroom: plan for N+1 redundancy, peak 2-3× average for traffic spikes
          [CALCULATOR TABLE: anihpj traffic estimation — users → RPS → bandwidth]

          └─────────────────────────┴──────────┴──────────┴──────────┘
          Assumptions: avg response 20KB, avg page 200KB, HTTP/2 multiplexing

    37.2  Scaling Patterns
          - Vertical scaling: bigger pipes, faster NICs (10G→25G→100G). Limited by hardware.
          - Horizontal scaling: more load balancers, more paths via ECMP. Scales infinitely (add more nodes).
          - CDN offload: 80-95% of requests served from edge (static assets). Only 5-20% reach origin.
          - Connection pooling: reuse TCP connections instead of opening new ones. Reduces handshake overhead 10-100×.
          [⚠️ GOTCHA] Connection pooling works great until a backend restart breaks ALL pooled connections simultaneously. Always use retry logic with exponential backoff.

          [SCALING DECISION TREE]
          ┌─────────────────────────────────────────────────────────────────────┐
          │  "My app is slow under load" — which scaling to apply?              │
          │                                                                      │
          │  Is latency the problem? (each request takes too long)              │
          │  ├── YES → Check: DB queries, downstream API calls, CPU bound?     │
          │  │         → Fix the bottleneck first. More instances won't help.   │
          │  │                                                                   │
          │  Is throughput the problem? (can't handle enough concurrent reqs)   │
          │  ├── YES → Horizontal scaling: more pods + LB                      │
          │  │         → Check connection limits: somaxconn, worker_connections│
          │  │                                                                   │
          │  Is bandwidth the problem? (network interface saturated)            │
          │  ├── YES → CDN for static assets, compress responses (gzip/brotli) │
          │  │         → Vertical scaling: upgrade NIC or instance type        │
          │  │                                                                   │
          │  Are connections piling up in TIME_WAIT?                            │
          │  └── YES → Connection pooling, keep-alive, reduce new connections  │
          └─────────────────────────────────────────────────────────────────────┘
