👁️ Show Solution
✅ Three Ways Applied to anihpj:
🌊
First Way: Flow (Systems Thinking)

Problem: 2-week deployment cycle.
Practices: Trunk-based development, CI auto-tests on every push, containerized builds, automated staging deploy.
anihpj: Every git push triggers lint→test→build→push. Merged PR auto-deploys to staging.

🔄

Problem: Bugs found in prod, days later.

anihpj: Every service auto-instrumented with OTel. Alerts fire within 60s of anomaly.

Explanation

Gene Kim's "Three Ways" are the philosophical foundation of DevOps and are tested on the CNPA. The First Way is about optimizing the delivery flow (left-to-right: dev→prod). The Second Way is about amplifying feedback (right-to-left: prod→dev). The Third Way is about continuous experimentation and learning. A platform enables all three: CI/CD = Flow, Observability = Feedback, Postmortems + Runbooks = Learning.

# .github/workflows/ci.yml
name: CI
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v4
    - uses: actions/setup-python@v5
      with: { python-version: '3.12' }
    - run: pip install flake8 black
    - run: flake8 . && black --check .

  test:
    needs: lint
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:16
        env: { POSTGRES_DB: testdb, POSTGRES_PASSWORD: test }
    steps:
    - uses: actions/checkout@v4
    - run: pip install -r requirements.txt
    - run: pytest --cov=./ --cov-report=xml
    - run: python manage.py test --settings=anihpj.test_settings

  build-and-push:
    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v4
    - run: docker build -t ghcr.io/anihpj/jobpost-api:${{ github.sha }} .
    - run: trivy image ghcr.io/anihpj/jobpost-api:${{ github.sha }}
    - run: docker push ghcr.io/anihpj/jobpost-api:${{ github.sha }}

Explanation

The pipeline follows the "fail fast" principle: lint first (cheapest), then tests, then build (most expensive). Integration tests use a real PostgreSQL service container — this catches DB migration issues BEFORE merge. Vulnerability scanning (Trivy) is mandatory before pushing to registry. This pipeline is the CI part of a golden path — developers get it automatically when they create a new service through the platform.

🐳 Lab 5: Write a Multi-Stage Dockerfile for anihpj

Scenario: Write a production-ready multi-stage Dockerfile for anihpj-api that: builds in one stage, runs in another, uses a non-root user, and is optimized for size. Explain each stage and the security benefits.

👁️ Show Solution
✅ Multi-Stage Production Dockerfile:
# STAGE 1: BUILD — compiles dependencies, has dev tools
FROM python:3.12-slim AS builder
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir --user -r requirements.txt

# STAGE 2: RUNTIME — minimal image, no build tools, non-root
FROM python:3.12-slim AS runtime
RUN useradd --create-home --shell /bin/bash anihpj
USER anihpj
WORKDIR /home/anihpj/app

# Copy only installed packages (not pip, not build tools)
COPY --from=builder /root/.local /home/anihpj/.local
COPY --chown=anihpj:anihpj . .

ENV PATH=/home/anihpj/.local/bin:$PATH
EXPOSE 8000
HEALTHCHECK --interval=30s --timeout=3s \
  CMD curl -f http://localhost:8000/healthz || exit 1

CMD ["gunicorn", "anihpj.wsgi:application", "--bind", "0.0.0.0:8000", "--workers", "3"]

Explanation

Multi-stage builds separate build dependencies from runtime — the final image has NO compilers, NO pip, NO dev headers. Non-root user (anihpj) prevents container breakout. HEALTHCHECK tells K8s if the container is healthy. The CNPA expects you to understand container best practices: minimal images, non-root users, health checks, multi-stage builds.

📦 Lab 6: Implement Container Image Tagging Strategy

Scenario: Design an image tagging strategy for anihpj that supports: (a) immutable production references, (b) environment promotion (dev→staging→prod), (c) rollback capability. Show the exact tags used at each stage and explain why :latest is banned.

👁️ Show Solution
✅ Image Tagging Strategy:
🏷️ anihpj Image Promotion Pipeline
DEV:    ghcr.io/anihpj/jobpost-api:sha-a1b2c3d    (git commit SHA)
        ghcr.io/anihpj/jobpost-api:dev             (mutable — for dev env only)
                     │
                     │ PR merged → CI passes → promote
                     ▼
STAGING: ghcr.io/anihpj/jobpost-api:sha-a1b2c3d    (SAME immutable SHA)
         ghcr.io/anihpj/jobpost-api:staging         (mutable — promoted by CI)
                     │
                     │ Manual approval → promote
                     ▼
PROD:    ghcr.io/anihpj/jobpost-api:sha-a1b2c3d    (SAME immutable SHA)
         ghcr.io/anihpj/jobpost-api:v1.2.3          (semantic version)
         ghcr.io/anihpj/jobpost-api:stable          (mutable — latest prod)
🚫 Why :latest Is Banned

:latest is a mutable tag that ALWAYS points to the most recent push. If K8s node-1 pulls :latest at T+0s and node-2 pulls at T+30s (after a new push), they get DIFFERENT images. This causes inconsistent behavior, impossible rollback, and undebuggable production issues. ALWAYS use immutable references (SHA256 digest or git commit SHA) in production.

Explanation

The key principle: the EXACT same image artifact moves through environments. Dev doesn't rebuild for staging; staging doesn't rebuild for prod. SHA-tagged images are immutable — if it worked in staging, the identical bytes run in production. Semantic tags (v1.2.3) are for human readability; SHA tags are for machine precision.

🔀 Lab 8: Implement Trunk-Based Development for anihpj

Scenario: The anihpj team currently uses GitFlow with 3-week feature branches. Merge conflicts are common, integration testing happens only before release, and releases are quarterly. Design a trunk-based development workflow with short-lived branches (< 1 day), feature flags, and explain how it improves DORA metrics.

👁️ Show Solution
✅ Trunk-Based Development Workflow:
🔴 GitFlow (Current — Anti-Pattern)

• Feature branches live 3 weeks → massive merge conflicts
• Integration testing only at release time → surprises
• Quarterly releases → 90-day lead time
• Code review on 5000-line PRs → rubber-stamping

🟢 Trunk-Based (Target)

• Branches live < 1 day → minimal conflicts
• CI runs on every push → instant feedback
• Daily deploys → feature flags control release
• Code review on < 200-line PRs → thorough review

BRANCH STRATEGY:
main ──●──●──●──●──●──●──●──●──●──→ (always deployable)
        │  │      │  │
        │  │      │  └── feat/payment (4 hours, 150 lines)
        │  │      └───── feat/search (6 hours, 200 lines)  
        │  └──────────── fix/login-bug (2 hours, 15 lines)
        └─────────────── feat/job-post (8 hours, 300 lines)

FEATURE FLAGS (controlling release):
if feature_flag('new_search'):
    return new_search_algorithm()
else:
    return old_search_algorithm()  # Safe fallback

Explanation

Trunk-Based Development is DORA's #1 technical practice correlated with Elite performance. Key rules: (1) merge to main at least daily, (2) branches live < 24 hours, (3) use feature flags to decouple deployment from release. The platform enables TBD by providing fast CI (tests in < 10 min), reliable staging environments, and feature flag infrastructure.
