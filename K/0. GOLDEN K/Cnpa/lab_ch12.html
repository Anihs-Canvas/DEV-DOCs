⚡ Lab 1: Implement Matrix Builds for anihpj

Scenario: anihpj-api must be tested against Python 3.10, 3.11, 3.12 and Django 4.0, 4.1, 4.2. Implement a CI matrix to test all 9 combinations in parallel. Write the GitHub Actions matrix config.

👁️ Show Solution 
jobs:
  test-matrix:
    strategy:
      fail-fast: false    # Don't cancel other jobs if one fails
      matrix:
        python: ["3.10", "3.11", "3.12"]
        django: ["4.0", "4.1", "4.2"]
    runs-on: ubuntu-latest
    services:
      postgres: { image: postgres:16, env: { POSTGRES_DB: test } }
    steps:
    - uses: actions/checkout@v4
    - uses: actions/setup-python@v5; with: { python-version: ${{ matrix.python }} }
    - run: pip install django==${{ matrix.django }}
    - run: pytest --cov --junitxml=results-${{ matrix.python }}-${{ matrix.django }}.xml

Explanation

Matrix builds test ALL supported version combinations in parallel. This catches compatibility issues like "works on Django 4.2 but breaks on 4.0." `fail-fast: false` means one failing combination doesn't cancel others — you see the FULL picture of what's broken. The platform provides this matrix as a golden path template; developers just specify their supported versions.

💾 Lab 2: Implement Advanced CI Caching

Scenario: The anihpj CI spends 3 minutes installing pip dependencies on every run. Implement multi-level caching: pip cache, Docker layer cache, and test cache. Write the cache configuration and explain cache key strategy.

👁️ Show Solution 
# Level 1: pip cache
- uses: actions/cache@v4
  with:
    path: ~/.cache/pip
    key: pip-${{ runner.os }}-${{ hashFiles('requirements.txt') }}
    restore-keys: pip-${{ runner.os }}-

# Level 2: Docker layer cache (gha cache)
- uses: docker/setup-buildx-action@v3
- uses: docker/build-push-action@v5
  with:
    cache-from: type=gha
    cache-to: type=gha,mode=max

# Level 3: pytest cache (.pytest_cache, .coverage)
- uses: actions/cache@v4
  with:
    path: |
      .pytest_cache
      .coverage
    key: pytest-${{ github.sha }}
    restore-keys: pytest-

Explanation

CI caching is the #1 speed optimization. Cache keys should be specific: hash files that determine cache validity (requirements.txt, Dockerfile). Restore keys are fallbacks: if exact match isn't found, use the most recent matching prefix. Docker GHA cache is automatic — BuildKit stores layers in GitHub's cache. Combined, these 3 caches can reduce CI time from 15 min to 3 min.

# PR changes api/views.py (2 files) → testmon runs only 12 of 500 tests

Explanation

Test impact analysis is the next evolution beyond parallelization. Instead of running ALL tests faster, run only the AFFECTED tests. pytest-testmon tracks which tests exercise which code paths. 🔀 Lab 5: Implement Multi-Service CI Orchestration

Scenario: anihpj has 3 services (api, web, worker) in a monorepo. When lib/ changes, all 3 must be rebuilt and tested. When only api/ changes, only api is tested. Implement path-based triggers and service dependency graph.

👁️ Show Solution 
jobs:
  detect-changes:
    runs-on: ubuntu-latest
    outputs:
      api: ${{ steps.filter.outputs.api }}
      web: ${{ steps.filter.outputs.web }}
    steps:
    - uses: dorny/paths-filter@v3
      id: filter
      with:
        filters: |
          api: [api/**, lib/**, requirements.txt]
          web: [web/**, lib/**, package.json]
          worker: [worker/**, lib/**]
  test-api:
    needs: detect-changes
    if: needs.detect-changes.outputs.api == 'true'
    # ... runs only if api/ or lib/ changed
  test-web:
    needs: detect-changes
    if: needs.detect-changes.outputs.web == 'true'
    # ... runs only if web/ or lib/ changed

Explanation

Selective CI is essential for monorepo platforms. Without it, changing a single file in web/ rebuilds ALL services — wasting CI minutes and developer patience. Shared libraries (lib/) trigger ALL services. The platform team provides this as the standard CI template — developers just define their path filters.

🏷️ Lab 6: Implement PR Label-Driven CI Behavior

Scenario: Use PR labels to control CI behavior: `skip-ci` skips CI, `full-suite` runs E2E tests, `safe-to-test` allows external contributor CI. Write the conditional CI logic.

👁️ Show Solution 
jobs:
  determine-scope:
    runs-on: ubuntu-latest

      run_ci: ${{ !contains(github.event.pull_request.labels.*.name, 'skip-ci') }}

    steps: [{ run: echo "CI scope determined" }]
  
  ci:
    needs: determine-scope
    if: needs.determine-scope.outputs.run_ci == 'true' && needs.determine-scope.outputs.is_safe == 'true'
    # ... runs only for safe PRs without skip-ci
  
  e2e:
    needs: [determine-scope, ci]
    if: needs.determine-scope.outputs.run_e2e == 'true'
    # ... runs only when full-suite label is applied

Explanation

PR labels give developers control over CI without changing workflow files. `safe-to-test` is a security gate for forks: external PRs don't get CI access until a maintainer labels them (prevents crypto mining in CI). This is platform governance via convention, not mandate.

🔄 Lab 8: Implement CI Pipeline as Code Library

Scenario: Create a reusable CI workflow that all anihpj services inherit. Write the reusable workflow and explain how services customize it.

👁️ Show Solution 
# .github/workflows/ci-template.yml (reusable)
name: Reusable CI
on: { workflow_call: { inputs: { python-version: { type: string, default: '3.12' } } } }
jobs:
  lint: { uses: anihpj/platform/.github/workflows/lint.yml@main }
  test: { uses: anihpj/platform/.github/workflows/test.yml@main, with: { python-version: ${{ inputs.python-version }} } }
  build: { uses: anihpj/platform/.github/workflows/build.yml@main }

# Service using it:
# .github/workflows/ci.yml
jobs:
  ci:
    uses: anihpj/platform/.github/workflows/ci-template.yml@main
    with: { python-version: '3.12' }

Explanation

CI pipeline as code library is the platform engineering approach: define CI ONCE in a central repo, reference it everywhere. When Trivy needs an update, update ONE file, not 50 service repos. Services customize via inputs (python-version, node-version, test-flags) but the core pipeline is centrally managed. This is DRY for CI.

🔗 Lab 9: Integrate CI with ArgoCD Notifications

Scenario: After CI builds an image, notify ArgoCD to refresh the application. Write the CI step that triggers ArgoCD sync.

👁️ Show Solution 
- name: Trigger ArgoCD Sync
  run: |
    argocd app sync anihpj-api-staging \
      --server argocd.anihpj.io \
      --auth-token ${{ secrets.ARGOCD_TOKEN }} \
      --insecure
    argocd app wait anihpj-api-staging \
      --server argocd.anihpj.io \
      --auth-token ${{ secrets.ARGOCD_TOKEN }} \
      --health \
      --timeout 300

Explanation

CI → ArgoCD integration completes the delivery pipeline: CI builds + tests + pushes → notifies ArgoCD → ArgoCD syncs cluster to Git. This can be push-based (CI triggers ArgoCD) or pull-based (ArgoCD watches registry for new tags). Push-based is simpler; pull-based is more GitOps-pure. The CNPA tests both patterns.
