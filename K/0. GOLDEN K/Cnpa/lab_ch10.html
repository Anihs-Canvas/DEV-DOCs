🔑 Lab 1: Design RBAC for anihpj Teams

Scenario: Design RBAC for 3 teams: backend (needs deploy + logs), frontend (needs deploy only), data (needs read-only). Write Roles, RoleBindings, and explain the principle of least privilege.

👁️ Show Solution 
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: { name: backend-developer, namespace: anihpj-production }
rules:
- apiGroups: ["apps"]; resources: ["deployments", "replicasets"]; verbs: ["get","list","watch","update","patch"]
- apiGroups: [""]; resources: ["pods","pods/log"]; verbs: ["get","list","watch"]
- apiGroups: [""]; resources: ["configmaps","secrets"]; verbs: ["get","list"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata: { name: backend-team-binding, namespace: anihpj-production }
subjects:
- kind: Group; name: backend-team; apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role; name: backend-developer; apiGroup: rbac.authorization.k8s.io

Explanation

RBAC implements least privilege: backend devs can deploy but NOT delete namespaces or modify RBAC. Each team gets a Role scoped to their namespace. ServiceAccounts for CI/CD get even more restrictive roles. The CNPA tests RBAC as fundamental K8s security — know the difference between Role (namespace-scoped) and ClusterRole (cluster-wide).

🔐 Lab 2: Secure the CI/CD ServiceAccount

Scenario: Create a ServiceAccount for GitHub Actions that can ONLY: create deployments, update container images, and read secrets in anihpj-staging. Write the minimal Role + RoleBinding + ServiceAccount.

👁️ Show Solution 
apiVersion: v1
kind: ServiceAccount
metadata: { name: github-actions-deployer, namespace: anihpj-staging }
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: { name: ci-deployer, namespace: anihpj-staging }
rules:
- apiGroups: ["apps"]; resources: ["deployments"]; verbs: ["get","list","watch","update","patch"]
- apiGroups: [""]; resources: ["secrets"]; verbs: ["get"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata: { name: ci-deployer-binding, namespace: anihpj-staging }
subjects: [{ kind: ServiceAccount; name: github-actions-deployer; namespace: anihpj-staging }]
roleRef: { kind: Role; name: ci-deployer; apiGroup: rbac.authorization.k8s.io }

Explanation

CI/CD ServiceAccounts are high-value targets. Give them the ABSOLUTE MINIMUM permissions: only update deployments (not create/delete other resources), only in staging (not production), and no access to secrets (unless needed for external-secrets). Never use the default ServiceAccount for CI — it often has broader permissions than needed.

🛡️ Lab 3: Harden Pod Security Context

Scenario: Write the production-ready securityContext for anihpj-api: non-root user, read-only root filesystem, no privilege escalation, drop ALL capabilities, seccomp profile. Explain WHY each setting matters.

👁️ Show Solution 
securityContext:
  runAsNonRoot: true              # Container CANNOT run as root (UID 0)
  runAsUser: 1000                 # Explicit non-root UID
  readOnlyRootFilesystem: true    # / is read-only (write to /tmp via emptyDir)
  allowPrivilegeEscalation: false # No child process can gain more privs than parent
  capabilities:
    drop: ["ALL"]                 # Remove ALL Linux capabilities
  seccompProfile:
    type: RuntimeDefault          # Block dangerous syscalls (ptrace, mount, etc.)

Explanation

Each setting closes an attack vector: runAsNonRoot prevents container breakout to host root. readOnlyRootFilesystem prevents malware from writing to disk. allowPrivilegeEscalation=false prevents setuid binaries. Drop ALL capabilities and add back only what's needed. RuntimeDefault seccomp blocks ~300 of 435 syscalls. Combined, these settings make container escape extremely difficult.

📋 Lab 4: Enable and Analyze K8s Audit Logs

Scenario: Configure audit logging to track: who deleted pods, who accessed secrets, who modified RBAC. Write the audit policy and a LogQL query to find suspicious activity.

👁️ Show Solution 
apiVersion: audit.k8s.io/v1
kind: Policy
rules:
- level: Metadata    # Log metadata for all requests
- level: RequestResponse
  verbs: ["create","update","patch","delete"]
  resources:
  - group: ""; resources: ["secrets","configmaps"]
- level: RequestResponse
  verbs: ["create","update","patch","delete"]
  resources:
  - group: "rbac.authorization.k8s.io"; resources: ["*"]
- level: RequestResponse
  verbs: ["delete"]
  resources:
  - group: ""; resources: ["pods"]
{app="kube-apiserver"} | json | stage="ResponseComplete" 
| verb="delete" | objectRef_resource="pods" 
| line_format "{{.user}} deleted pod {{.objectRef_name}} at {{.requestReceivedTimestamp}}"

Explanation

Audit logs are the "black box" of K8s security. They record WHO did WHAT to WHICH resource and WHEN. Without audit logs, you can't answer "who deleted the production database pod?" — a critical question during incident response. The CNPA tests audit logging as a compliance requirement.

🔒 Lab 5: Encrypt etcd at Rest

Scenario: Configure etcd encryption for Secrets. Write the EncryptionConfiguration, explain the provider types, and describe the migration process.

👁️ Show Solution 
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
- resources: [secrets]
  providers:
  - aescbc:                    # Strongest — AES-CBC with PKCS7 padding
      keys:
      - name: key1
        secret: 
  - identity: {}               # Fallback for unencrypted secrets

Explanation

By default, K8s stores Secrets as base64 in etcd (NOT encrypted). Anyone with etcd access can read all secrets. EncryptionConfiguration encrypts secrets before writing to etcd. Provider types: aescbc (recommended, strong), secretbox (XSalsa20+Poly1305), kms (cloud KMS, strongest). Migration: add new provider → label resources → rewrite all secrets → remove old provider.

🧩 Lab 6: Implement Defense in Depth for a Pod

Scenario: For a single anihpj-api pod, list EVERY security control applied: from admission to network to runtime. Draw the layered defense model.

👁️ Show Solution
✅ Defense in Depth:
LAYER 1: CODE  → gitleaks pre-commit, Bandit SAST
LAYER 2: CI    → Trivy scan, Cosign sign, SBOM
LAYER 3: REGISTRY → Only signed images, tag immutability
LAYER 4: ADMISSION → Kyverno: verifyImages, validate securityContext, mutate defaults
LAYER 5: POD SECURITY → runAsNonRoot, readOnlyRootFS, seccomp, drop ALL caps
LAYER 6: NETWORK → NetworkPolicy deny-all, mTLS (Istio), Ingress TLS
LAYER 7: RUNTIME → Falco anomaly detection, seccomp, AppArmor
LAYER 8: SECRETS → ESO from AWS, mounted as files, etcd encryption
LAYER 9: COMPLIANCE → Audit logs, Policy Reports, SIEM export

Explanation

No single layer is sufficient. A defense-in-depth approach assumes each layer might fail and provides overlapping controls. If SAST misses a vulnerability, Trivy catches it. If admission control fails, runtime Falco detects. The CNPA tests this layered security thinking.

👁️ Lab 7: Implement Falco Runtime Security

Scenario: Configure Falco rules to detect: (a) shell spawned in container, (b) unexpected outbound network connection, (c) sensitive file read (/etc/shadow). Write the Falco rules and the alert output.

👁️ Show Solution 
- rule: Shell in Container
  desc: Detect a shell spawned in a container
  condition: >
    spawned_process and container
    and proc.name in (bash, sh, zsh)
    and not proc.args in ("-c", "sh -c")
  output: "Shell spawned in container (user=%user.name container=%container.name)"
  priority: WARNING

- rule: Unexpected Outbound Connection
  desc: Detect outbound connections to unusual IPs
  condition: >
    outbound and not fd.snet in (allowed_networks)
  output: "Unexpected outbound from %container.name to %fd.sip"
  priority: CRITICAL

- rule: Read Sensitive File
  desc: Detect reads to /etc/shadow
  condition: >
    open_read and container and fd.name=/etc/shadow
  output: "Sensitive file read: %fd.name by %proc.name"
  priority: CRITICAL

Explanation

Falco is runtime threat detection — it watches syscalls and detects anomalous behavior that static policies miss. A container running with all securityContext hardening might still be exploited at the application level. Falco catches: shell injection, crypto mining, data exfiltration, reverse shells. The CNPA tests Falco as the CNCF standard for runtime security.

🔄 Lab 8: Rotate K8s Certificates

Scenario: The anihpj cluster certificates expire in 30 days. Write the procedure to check certificate expiry, renew them with kubeadm, and verify all components trust the new certs.

👁️ Show Solution 
# Check certificate expiry
kubeadm certs check-expiration
# Output: CERTIFICATE                EXPIRES
#         apiserver                  Jan 15 2027
#         apiserver-etcd-client      Jan 15 2027

# Renew all certificates
kubeadm certs renew all

# Restart control plane components
# Static pods auto-restart when manifests change
# Wait for API server to be ready
kubectl wait --for=condition=Ready node/control-plane --timeout=120s

# Verify: all pods should use new certs
kubectl get pods -n kube-system | grep -E 'kube-apiserver|kube-controller|kube-scheduler'

# Verify cert expiry
kubeadm certs check-expiration
# Output: CERTIFICATE                EXPIRES
#         apiserver                  Jan 15 2028

Explanation

Certificate expiry is the #1 cause of unexpected cluster outages. K8s certificates expire after 1 year by default. kubeadm certs renew handles the renewal, but components need restart to pick up new certs. The platform team should set up monitoring: alert when certs are within 30 days of expiry. Fully automated renewal is possible with kubeadm operator or EKS auto-rotation.

🔐 Lab 9: Implement OIDC Authentication for kubectl

Scenario: Instead of static kubeconfig files, configure OIDC authentication so developers use their corporate SSO to access the cluster. Write the kube-apiserver flags and the kubeconfig for OIDC login.

👁️ Show Solution 
# kube-apiserver OIDC flags
--oidc-issuer-url=https://auth.anihpj.io
--oidc-client-id=kubernetes
--oidc-username-claim=email
--oidc-groups-claim=groups
--oidc-ca-file=/etc/kubernetes/pki/oidc-ca.crt
# ~/.kube/config
users:
- name: oidc
  user:
    exec:
      apiVersion: client.authentication.k8s.io/v1beta1
      command: kubectl
      args:
      - oidc-login
      - get-token
      - --oidc-issuer-url=https://auth.anihpj.io
      - --oidc-client-id=kubernetes

Explanation

OIDC eliminates static kubeconfig credentials. Developers authenticate via SSO → get a JWT token → kubectl uses it. Benefits: (1) No static credentials to leak, (2) MFA enforced by SSO, (3) Instant revocation (disable SSO account), (4) Groups from SSO map to K8s RBAC groups. The CNPA tests OIDC as the modern platform authentication standard.
