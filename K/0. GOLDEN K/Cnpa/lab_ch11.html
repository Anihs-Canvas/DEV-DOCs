📦 Lab 1: Generate and Verify an SBOM

Scenario: Generate an SBOM for anihpj-api using Syft and verify it with Grype. Write the commands, explain CycloneDX vs SPDX, and describe how SBOMs enable supply chain security.

👁️ Show Solution 
syft ghcr.io/anihpj/jobpost-api:v1.2.3 -o spdx-json > anihpj-api-sbom.spdx.json
grype sbom:anihpj-api-sbom.spdx.json -o json > anihpj-api-vulns.json
# SBOM shows: Python 3.12, Django 4.2, psycopg2 2.9, redis-py 5.0, etc.
# Grype finds: psycopg2 2.9 has CVE-2024-1234 (HIGH), Django 4.2 has CVE-2024-5678 (CRITICAL)
Without SBOM

• "What packages are in this image?" → Unknown
• Log4Shell discovered → 3 days to find all affected services
• Compliance audit → manual inventory (weeks)

With SBOM

• Every package, version, and dependency is documented
• Log4Shell → query SBOM registry → 5 minutes to find all affected
• Compliance audit → auto-generate from SBOM (minutes)

Explanation

SBOM is a "nutrition label" for software. It lists every component, library, and dependency. Without SBOMs, you don't know what's in your software — making vulnerability response slow and compliance impossible. SPDX and CycloneDX are the two standards (CNCF supports both). The CNPA tests SBOM as a supply chain security fundamental.

✍️ Lab 2: Sign Container Images with Cosign (Keyless)

Scenario: Configure Cosign keyless signing in CI using GitHub OIDC. Write the workflow step, explain how keyless signing works, and verify the signature.

👁️ Show Solution 
- uses: sigstore/cosign-installer@v3
- run: cosign sign --yes ghcr.io/anihpj/jobpost-api@${{ steps.build.outputs.digest }}
  # --yes: skip confirmation
  # Uses OIDC token from GitHub Actions (no key management!)
  
- run: |
    cosign verify \
      --certificate-identity https://github.com/anihpj/jobpost/.github/workflows/ci.yml@refs/heads/main \
      --certificate-oidc-issuer https://token.actions.githubusercontent.com \
      ghcr.io/anihpj/jobpost-api@sha256:abc123

Explanation

Keyless signing uses OIDC (OpenID Connect) instead of long-lived private keys. GitHub Actions provides an OIDC token proving "I am the CI pipeline for repo anihpj/jobpost on branch main." Cosign exchanges this for a short-lived signing certificate from Fulcio (Sigstore's CA). No key to store, rotate, or lose. The CNPA tests Sigstore/Cosign as the modern supply chain security standard.

🔗 Lab 3: Implement SLSA Provenance Generation

Scenario: Generate SLSA Level 3 provenance for anihpj-api images. Write the GitHub Actions workflow using slsa-github-generator and explain what "non-falsifiable" means.

👁️ Show Solution 
jobs:
  build:
    outputs:
      digest: ${{ steps.build.outputs.digest }}
    steps:
    - uses: slsa-framework/slsa-github-generator/.github/actions/builder_docker-based_slsa3@v2
      with:
        builder-image: 'ghcr.io/slsa-framework/slsa-builder-go:v2'
        provenance: true

Explanation

SLSA provenance answers: "Who built this? From what source? With what tools? At what time?" Non-falsifiable means the provenance is cryptographically signed — you can't forge who built it or tamper with the record. This prevents supply chain attacks where an attacker claims "this malicious image was built by anihpj CI." The CNPA tests SLSA as the industry framework for supply chain integrity.

🔍 Lab 4: Scan for Vulnerabilities in CI and Fail on Critical

Scenario: Configure Trivy to scan images in CI and FAIL the pipeline if CRITICAL CVEs are found. Write the CI step with severity thresholds and explain the difference between fixable and unfixable CVEs.

👁️ Show Solution 
- run: |
    trivy image \
      --severity HIGH,CRITICAL \
      --exit-code 1 \           # Fail pipeline on vulnerabilities
      --ignore-unfixed \        # Only fail on FIXABLE vulns
      --format json \
      --output trivy-report.json \
      ghcr.io/anihpj/jobpost-api:${{ github.sha }}
- run: |
    # Count CRITICAL vulns
    CRITICAL=$(jq '[.Results[].Vulnerabilities[] | select(.Severity=="CRITICAL")] | length' trivy-report.json)
    if [ "$CRITICAL" -gt 0 ]; then
      echo "Found $CRITICAL CRITICAL vulnerabilities. Failing pipeline."
      exit 1
    fi

Explanation

Trivy scanning in CI is a SHIFT-LEFT control: you find vulnerabilities before the image reaches the registry. --ignore-unfixed means you only fail on vulnerabilities that HAVE fixes available — otherwise you'd block deployments forever for upstream issues you can't control. The platform sets the severity threshold: CRITICAL = fail pipeline, HIGH = warn + create Jira ticket, MEDIUM = log only.

🛡️ Lab 6: Implement Artifact Attestation with Cosign

Scenario: Create a Cosign attestation proving that anihpj-api passed all CI checks (tests, SAST, Trivy). Write the attestation command and the Kyverno policy that verifies it at admission.

👁️ Show Solution 
cosign attest --predicate ci-attestation.json \
  --type https://anihpj.io/attestations/ci/v1 \
  ghcr.io/anihpj/jobpost-api@sha256:abc123
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata: { name: require-ci-attestation }
spec:
  validationFailureAction: Enforce
  rules:
  - name: check-ci-attestation
    match: { any: [{ resources: { kinds: [Pod] } }] }
    verifyImages:
    - imageReferences: ["ghcr.io/anihpj/*"]
      attestations:
      - predicateType: https://anihpj.io/attestations/ci/v1
        conditions:
        - all:
          - key: "{{ tests_passed }}"; operator: Equals; value: "true"
          - key: "{{ sast_passed }}"; operator: Equals; value: "true"
          - key: "{{ critical_vulns }}"; operator: Equals; value: "0"

Explanation

Attestations are verifiable claims about an artifact. "This image passed all CI checks" is an attestation signed by the CI pipeline. Kyverno verifies it at admission time — if the attestation is missing or shows failures, the pod is rejected. This closes the loop: CI checks → attestation → admission verifies. No unsigned or untested image can reach production.

🔄 Lab 8: Implement Image Lifecycle Management

Scenario: Design an image lifecycle: unlimited dev tags, keep staging tags 30 days, keep production tags 365 days, auto-delete everything else. Write the registry retention policy and explain the cost/security benefit.

👁️ Show Solution 
# GHCR retention rules
- name: dev-cleanup
  tag_pattern: "sha-*"         # All commit-SHA tags
  keep_most_recent: 20         # Keep last 20 dev images
  delete_older_than: 7d        # Delete after 7 days
  
- name: staging-cleanup  
  tag_pattern: "staging-*"
  keep_most_recent: 10
  delete_older_than: 30d

- name: production-retention
  tag_pattern: "v*"            # Semantic versions
  keep_all: true               # KEEP FOREVER (compliance)

Explanation

Image lifecycle management reduces registry costs AND attack surface. Old images accumulate vulnerabilities — if they're deleted, they can't be accidentally deployed. Production images are kept for compliance (365 days minimum for audit). Dev images are ephemeral. Cleanup should be automated, not manual.
