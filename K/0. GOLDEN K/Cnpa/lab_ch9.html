📋 Lab 1: Write a Kyverno Policy to Require Resource Limits

Scenario: Write a Kyverno ClusterPolicy that: (a) requires all pods in production namespaces to have CPU and memory limits, (b) auto-adds default limits (500m CPU, 512Mi memory) if not specified, (c) denies pods that explicitly set limits above 4 CPU / 8Gi. Explain the difference between validate, mutate, and generate rules.

👁️ Show Solution
✅ Kyverno Resource Limits Policy:
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: require-resource-limits
spec:
  validationFailureAction: Enforce   # Blocks violating pods
  rules:
  # RULE 1: MUTATE — add defaults if missing
  - name: add-default-resources
    match:
      any:
      - resources:
          namespaces: ["anihpj-production", "anihpj-staging"]
    mutate:
      patchStrategicMerge:
        spec:
          containers:
          - (name): "*"
            resources:
              requests:
                +(cpu): "250m"
                +(memory): "256Mi"
              limits:
                +(cpu): "500m"
                +(memory): "512Mi"
  
  # RULE 2: VALIDATE — deny excessive limits
  - name: deny-excessive-limits
    match:
      any:
      - resources:
          namespaces: ["anihpj-production"]
    validate:
      message: "CPU limit must be <= 4 and memory <= 8Gi"
      pattern:
        spec:
          containers:
          - (name): "*"
            resources:
              limits:
                cpu: "<=4"
                memory: "<=8Gi"
  
  # RULE 3: VALIDATE — require limits exist
  - name: require-limits
    match:
      any:
      - resources:
          kinds: [Pod]
          namespaces: ["anihpj-production"]
    validate:
      message: "All containers must have resource limits"
      pattern:
        spec:
          containers:
          - resources:
              limits:
                cpu: "?*"
                memory: "?*"
Rule TypeWhat It DoesUse Case
ValidateChecks if resource matches pattern. Denies if not."Must have resource limits." "No privileged containers."
MutateModifies resource before it's created. Adds defaults."Auto-add resource limits." "Inject sidecar."
GenerateCreates ADDITIONAL resources. Not a modification."Auto-create NetworkPolicy for every namespace."

Explanation

Kyverno policies are the CNPA standard for K8s governance. Validate = "check and deny." Mutate = "modify and allow." Generate = "create additional resources." The key pattern: mutate defaults (make it easy to comply), validate constraints (block what's dangerous). The platform team writes policies ONCE; they apply to ALL workloads automatically. This is governance as code — policy enforcement without human gates.

🔐 Lab 2: Enforce Image Provenance with Kyverno

Scenario: Write Kyverno policies to: (a) block images not from ghcr.io/anihpj, (b) require Cosign signatures, (c) block images with HIGH/CRITICAL CVEs. Explain how Kyverno verifyImages works.

👁️ Show Solution
✅ Image Provenance Policies:
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: verify-images
spec:
  validationFailureAction: Enforce
  rules:
  # RULE 1: Only allow images from our registry
  - name: allow-only-anihpj-registry
    match:
      any:
      - resources:
          kinds: [Pod]
    validate:
      message: "Images must come from ghcr.io/anihpj"
      pattern:
        spec:
          containers:
          - image: "ghcr.io/anihpj/*"
  
  # RULE 2: Require Cosign signature
  - name: require-cosign-signature
    match:
      any:
      - resources:
          kinds: [Pod]
    verifyImages:
    - imageReferences:
      - "ghcr.io/anihpj/*"
      attestors:
      - count: 1
        entries:
        - keys:
            publicKeys: |-
              -----BEGIN PUBLIC KEY-----
              MFkwEwYHKoZIzj0CAQYIKoZIzj0DAQcDQgAE...
              -----END PUBLIC KEY-----
  
  # RULE 3: Block HIGH/CRITICAL CVEs
  - name: block-critical-cves
    match:
      any:
      - resources:
          kinds: [Pod]
    verifyImages:
    - imageReferences:
      - "ghcr.io/anihpj/*"
      attestors:
      - count: 1
        entries:
        - keys:
            publicKeys: |-
              -----BEGIN PUBLIC KEY-----
              ...
      verifyDigest: true
      required: true
      mutateDigest: true

Explanation

Kyverno verifyImages checks image signatures and attestations BEFORE the pod is created. It uses Cosign to verify the signature against a public key. If the image isn't signed, or the signature doesn't match, the pod is rejected. Combined with Trivy scanning in CI, this ensures only signed, vulnerability-free images reach production. The CNPA tests image provenance as a supply chain security requirement.

🏷️ Lab 3: Auto-Generate Resources per Namespace

Scenario: Use Kyverno's generate rule to auto-create a NetworkPolicy, ResourceQuota, and LimitRange for every new namespace with label `platform=anihpj`. Write the ClusterPolicy and explain the generate trigger.

👁️ Show Solution
✅ Auto-Generate Resources:
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: auto-provision-namespace
spec:
  rules:
  - name: generate-default-networkpolicy
    match:
      any:
      - resources:
          kinds: [Namespace]
          selector:
            matchLabels:
              platform: anihpj
    generate:
      synchronize: true          # Keep in sync!
      apiVersion: networking.k8s.io/v1
      kind: NetworkPolicy
      name: default-deny
      namespace: "{{request.object.metadata.name}}"
      data:
        spec:
          podSelector: {}
          policyTypes: [Ingress, Egress]
  
  - name: generate-resourcequota
    match:
      any:
      - resources:
          kinds: [Namespace]
          selector:
            matchLabels:
              platform: anihpj
    generate:
      synchronize: true
      apiVersion: v1
      kind: ResourceQuota
      name: namespace-quota
      namespace: "{{request.object.metadata.name}}"
      data:
        spec:
          hard:
            requests.cpu: "20"
            requests.memory: "40Gi"
            persistentvolumeclaims: "10"
  
  - name: generate-limitrange
    match:
      any:
      - resources:
          kinds: [Namespace]
          selector:
            matchLabels:
              platform: anihpj
    generate:
      synchronize: true
      apiVersion: v1
      kind: LimitRange
      name: default-limits
      namespace: "{{request.object.metadata.name}}"
      data:
        spec:
          limits:
          - default:
              cpu: "500m"
              memory: "512Mi"
            defaultRequest:
              cpu: "250m"
              memory: "256Mi"
            type: Container

Explanation

Generate rules are Kyverno's most powerful feature: they CREATE resources in response to events. Here, creating a namespace with `platform: anihpj` label triggers generation of NetworkPolicy, ResourceQuota, and LimitRange. `synchronize: true` means Kyverno keeps these in sync — if someone deletes the generated NetworkPolicy, Kyverno recreates it. This is "self-healing governance" — the desired state is continuously enforced.

🔄 Lab 5: Write an OPA/Gatekeeper ConstraintTemplate

Scenario: Write a Gatekeeper ConstraintTemplate and Constraint that requires all Ingress resources to use HTTPS (TLS configured). Compare Gatekeeper (OPA) vs Kyverno for platform governance.

👁️ Show Solution
✅ Gatekeeper Ingress HTTPS Policy:
apiVersion: templates.gatekeeper.sh/v1
kind: ConstraintTemplate
metadata:
  name: requiringresshttps
spec:
  crd:
    spec:
      names:
        kind: RequireIngressHttps
  targets:
  - target: admission.k8s.gatekeeper.sh
    rego: |
      package requiringresshttps
      violation[{"msg": msg}] {
        input.review.object.kind == "Ingress"
        not input.review.object.spec.tls
        msg := sprintf("Ingress %v must have TLS configured", [input.review.object.metadata.name])
      }
---
apiVersion: constraints.gatekeeper.sh/v1beta1
kind: RequireIngressHttps
metadata:
  name: require-ingress-https
spec:
  match:
    kinds:
    - apiGroups: ["networking.k8s.io"]
      kinds: ["Ingress"]
Gatekeeper (OPA/Rego)

• Uses Rego (declarative policy language)
• Steeper learning curve
• More expressive (complex logic)
• Mature, widely adopted

Kyverno

• Uses YAML (K8s-native syntax)
• Easier to learn (looks like K8s YAML)
• Generate + mutate rules
• CNCF Incubating, growing fast

Explanation

The CNPA expects you to know BOTH Gatekeeper and Kyverno. Gatekeeper uses Rego (powerful but complex); Kyverno uses YAML (simpler, K8s-native). For most platform use cases, Kyverno's YAML-based policies are sufficient and easier for platform teams to maintain. Use Gatekeeper when you need complex policy logic (e.g., "deny if 3 conditions AND 2 exceptions").

⚡ Lab 6: Implement Mutation for Default Security Context

Scenario: Write a Kyverno mutate policy that auto-adds securityContext (runAsNonRoot, readOnlyRootFilesystem, allowPrivilegeEscalation=false) to every pod in production. Show before/after pod spec.

👁️ Show Solution 
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: add-default-securitycontext
spec:
  rules:
  - name: add-sec-ctx
    match: { any: [{ resources: { kinds: [Pod] } }] }
    mutate:
      patchStrategicMerge:
        spec:
          securityContext:
            +(runAsNonRoot): true
            +(seccompProfile):
              type: RuntimeDefault
          containers:
          - (name): "*"
            securityContext:
              +(allowPrivilegeEscalation): false
              +(readOnlyRootFilesystem): true
              +(capabilities):
                drop: ["ALL"]

Explanation

Mutation is Kyverno's "make it secure by default" superpower. Developers don't need to know securityContext fields — Kyverno auto-adds them. This reduces cognitive load AND improves security simultaneously. The CNPA tests mutation as a platform governance pattern.

🛡️ Lab 8: Implement Multi-Tenant Policy Isolation

Scenario: anihpj hosts 3 teams. Write Kyverno policies that: (a) prevent Team A from accessing Team B's namespaces, (b) prevent anyone except platform team from modifying Kyverno policies, (c) auto-label new namespaces with the creator's team.

👁️ Show Solution 
# Prevent cross-namespace access
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: prevent-cross-team-access
spec:
  validationFailureAction: Enforce
  rules:
  - name: block-other-team-namespace
    match: { any: [{ resources: { kinds: [Pod, Service, Ingress] } }] }
    validate:
      message: "Cannot create resources in another team's namespace"
      deny:
        conditions:
          any:
          - key: "{{request.userInfo.username}}"
            operator: NotIn
            value: ["platform-admin", "{{request.namespace}}-admin"]
---
# Protect Kyverno policies from modification
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: protect-policies
spec:
  rules:
  - name: only-platform-team
    match: { any: [{ resources: { kinds: [ClusterPolicy, Policy] } }] }
    validate:
      message: "Only platform-team can modify policies"
      deny:
        conditions:
          any:
          - key: "{{request.userInfo.groups}}"
            operator: NotIn
            value: ["platform-team"]

Explanation

Multi-tenant policy isolation uses Kyverno to enforce boundaries that RBAC alone can't catch. RBAC controls who can do WHAT; Kyverno controls HOW they do it. Together they provide defense-in-depth for multi-tenant platforms.

🏗️ Lab 9: Generate NetworkPolicy Per Namespace

Scenario: Auto-generate zero-trust NetworkPolicies for every new namespace. The policy must: deny all by default, allow prometheus scraping, allow ingress from same namespace. Write the generate rule and explain why this is better than relying on developers.

👁️ Show Solution 
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: auto-networkpolicy
spec:
  rules:
  - name: generate-default-deny
    match:
      any:
      - resources:
          kinds: [Namespace]
    generate:
      synchronize: true
      apiVersion: networking.k8s.io/v1
      kind: NetworkPolicy
      name: default-deny
      namespace: "{{request.object.metadata.name}}"
      data:
        spec:
          podSelector: {}
          policyTypes: [Ingress, Egress]
          ingress:
          - from:
            - namespaceSelector:
                matchLabels:
                  name: monitoring
          - from:
            - podSelector: {}  # Same namespace

Explanation

This is "secure by default" governance. Developers don't know (or forget) to create NetworkPolicies. Kyverno auto-creates them for every namespace. If a developer needs more permissive rules, they create a MORE specific NetworkPolicy (which takes precedence). But the default-deny baseline is always present — no unprotected namespaces.
