📋 Lab 1: Write a Declarative Deployment for anihpj-api

Scenario: Write a complete Kubernetes Deployment YAML for the anihpj API service with: 3 replicas, resource requests (250m CPU, 256Mi memory), limits (500m CPU, 512Mi memory), health checks (/healthz on port 8000), and the image anihpj/jobpost-api:v1.2.3. Then explain why each field is declarative rather than imperative.

👁️ Show Solution
✅ Declarative Deployment YAML:
apiVersion: apps/v1
kind: Deployment
metadata:
  name: anihpj-api
  labels:
    app: anihpj-api
    tier: backend
spec:
  replicas: 3          # "I WANT 3 pods" — NOT "create 3 pods"
  selector:
    matchLabels:
      app: anihpj-api
  template:
    metadata:
      labels:
        app: anihpj-api
    spec:
      containers:
      - name: api
        image: anihpj/jobpost-api:v1.2.3
        ports:
        - containerPort: 8000
        resources:
          requests:
            cpu: "250m"
            memory: "256Mi"
          limits:
            cpu: "500m"
            memory: "512Mi"
        livenessProbe:
          httpGet:
            path: /healthz
            port: 8000
          initialDelaySeconds: 10
          periodSeconds: 15
        readinessProbe:
          httpGet:
            path: /healthz
            port: 8000
          initialDelaySeconds: 5
          periodSeconds: 10

Explanation

Every field is DECLARATIVE: you state desired state (3 replicas, 250m CPU), not commands (create, start, scale). If a pod crashes, the Deployment controller reconciles: "I want 3. There are only 2. I'll create 1." This reconciliation loop is the heart of declarative management. Compare: imperative = kubectl run nginx --image=nginx (one-time command); declarative = write YAML, apply, K8s continuously ensures it matches.

🔄 Lab 2: Demonstrate the Reconciliation Loop in Action

Scenario: Your anihpj-api Deployment has 3 replicas. Execute these steps and explain what happens at each stage: (a) Delete one pod manually with kubectl delete pod. (b) Observe what happens. (c) Explain WHY it happens — include the specific K8s components involved (Deployment controller, ReplicaSet controller, Scheduler, kubelet).

👁️ Show Solution
✅ Reconciliation Loop Walkthrough:
🔄 Reconciliation Loop After Pod Deletion
T+0s:  kubectl delete pod anihpj-api-abc123
       → API Server receives DELETE request
       → etcd updated: pod marked for deletion (grace period = 30s)
       
T+1s:  Deployment Controller WATCHES API Server
       → "I declared 3 replicas. ReplicaSet reports only 2 pods."
       → "DESIRED (3) != ACTUAL (2) — MUST RECONCILE"
       → Updates ReplicaSet: desiredReplicas = 3

T+2s:  ReplicaSet Controller WATCHES
       → "I need 3 pods. Only 2 exist."
       → Creates new Pod object (anihpj-api-def456) via API Server
       
T+3s:  Scheduler WATCHES for unassigned pods
       → Pod anihpj-api-def456 has .spec.nodeName == ""
       → Runs filtering (node resources, taints) then scoring
       → Binds pod to node-2: PATCH .spec.nodeName = "node-2"

T+5s:  kubelet on node-2 WATCHES
       → "I have a new pod assigned to me: anihpj-api-def456"
       → Calls CRI: PullImage → CreateContainer → StartContainer
       → Reports PodRunning status back to API Server

T+35s: Old pod terminates (grace period expires)
       → Container stopped, resources freed
       → DESIRED(3) == ACTUAL(3) → RECONCILIATION COMPLETE ✓

Explanation

This is the RECONCILIATION LOOP — Kubernetes' superpower. No human typed "create a replacement pod." The Deployment controller observed divergence from desired state and automatically corrected it. Every K8s controller follows this pattern: WATCH (observe state) → DIFF (compare to desired) → ACT (reconcile). This is why declarative management is superior to imperative scripts — the system continuously self-heals.

🆚 Lab 3: Imperative vs Declarative — When to Use Each

Scenario: You need to perform 3 tasks: (a) Debug a production issue — quickly check which nodes are running anihpj pods. (b) Create the standard anihpj-api deployment for the 50th time. (c) Update the resource limits for all anihpj services from 500m to 1 CPU. For each task, specify whether imperative or declarative is appropriate and why.

👁️ Show Solution
✅ Imperative vs Declarative Decision Matrix:
TaskApproachCommand/YAMLWhy
(a) Debug: check nodes✅ Imperativekubectl get pods -o wide -l app=anihpj-apiOne-time query. No state to maintain. Fastest path to information.
(b) Create 50th deployment✅ Declarativekubectl apply -f anihpj-api-deploy.yamlRepeatable. Version-controlled in Git. Applying same YAML 50 times = idempotent.
(c) Update all limits✅ DeclarativeUpdate YAML in Git → kubectl apply or ArgoCD auto-syncChanges tracked in Git history. Rollback = git revert. No manual kubectl edit.

Explanation

CNPA Rule: Imperative for exploration/debugging; Declarative for operations. The exam tests this distinction. Imperative commands (kubectl run, kubectl expose) are fast for learning and debugging but dangerous for production — they bypass Git history, audit trails, and peer review. Declarative (YAML in Git + apply/sync) is the platform engineering standard.

📦 Lab 4: Resource Requests vs Limits — Prevent OOMKill

Scenario: The anihpj-api pod keeps getting OOMKilled under load. Current config: no resource requests or limits set. Diagnose the issue, set appropriate requests and limits, and explain the difference between Guaranteed, Burstable, and BestEffort QoS classes.

👁️ Show Solution
✅ Resource QoS Configuration:
# BEFORE (BestEffort — KILLED FIRST under memory pressure)
resources: {}  # Empty = dangerous!

# AFTER (Guaranteed — KILLED LAST, safest)
resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
  limits:
    cpu: "500m"      # Must EQUAL request for Guaranteed QoS
    memory: "512Mi"  # Must EQUAL request for Guaranteed QoS
QoS ClassConditionEviction PriorityUse Case
Guaranteedrequests = limits for ALL containers (CPU AND memory)🥇 KILLED LASTDatabases, payment APIs, critical services
BurstableHas requests; limits different or absent🥈 KILLED MIDDLEMost application pods
BestEffortNO requests, NO limits🥉 KILLED FIRSTNEVER in production

Explanation

The OOMKill happened because without limits, the pod could consume unlimited memory. Without requests, the scheduler doesn't reserve memory, so the node overcommits. The CNPA expects Guaranteed QoS for critical workloads — set both CPU and memory requests EQUAL to limits for all containers.

🏷️ Lab 5: Design a Label Strategy for anihpj

Scenario: Design a labeling strategy for the anihpj platform covering: (a) application identification, (b) tier/architecture, (c) environment, (d) team ownership, and (e) version tracking. Create a label schema and show how you'd query pods by each dimension.

👁️ Show Solution
✅ Label Strategy for anihpj:
# Standard Label Schema
metadata:
  labels:
    app.kubernetes.io/name: anihpj-api        # Application name
    app.kubernetes.io/component: backend      # Architecture tier
    app.kubernetes.io/part-of: anihpj         # Parent application
    app.kubernetes.io/version: v1.2.3         # Version
    app.kubernetes.io/environment: production # Environment
    app.kubernetes.io/managed-by: argo-cd     # Management tool
    team: platform-engineering                # Owning team
# Query Examples:
kubectl get pods -l app.kubernetes.io/name=anihpj-api              # All API pods
kubectl get pods -l app.kubernetes.io/component=backend             # All backend pods
kubectl get pods -l app.kubernetes.io/environment=production        # All prod pods
kubectl get pods -l team=platform-engineering                       # All platform team pods
kubectl get pods -l app.kubernetes.io/part-of=anihpj,app.kubernetes.io/environment=staging  # All anihpj staging

Explanation

Labels are the foundation of declarative selection in K8s. The app.kubernetes.io/* prefix is the Kubernetes RECOMMENDED label convention. Labels enable: Service selectors, NetworkPolicy targets, Prometheus service discovery, cost allocation, and team filtering. The CNPA expects you to know that labels (arbitrary key-value pairs for selection) are different from annotations (non-identifying metadata for tools).

🔐 Lab 6: Write a NetworkPolicy for Zero-Trust Communication

Scenario: Write a Kubernetes NetworkPolicy that: (a) allows anihpj-api pods to talk to anihpj-db on port 5432, (b) allows anihpj-web pods to talk to anihpj-api on port 8000, (c) denies all other traffic by default. Explain why this is "declarative security".

👁️ Show Solution
✅ Zero-Trust NetworkPolicy:
---
# Default deny-all (zero-trust baseline)
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-all
spec:
  podSelector: {}        # Selects ALL pods
  policyTypes:
  - Ingress
  - Egress
  # No ingress/egress rules = deny everything
---
# Allow web → api
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-web-to-api
spec:
  podSelector:
    matchLabels:
      app: anihpj-api          # Target: API pods
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: anihpj-web       # From: Web pods
    ports:
    - protocol: TCP
      port: 8000
---
# Allow api → db
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-api-to-db
spec:
  podSelector:
    matchLabels:
      app: anihpj-db            # Target: DB pods
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: anihpj-api        # From: API pods
    ports:
    - protocol: TCP
      port: 5432

Explanation

This is "declarative security" because you declare WHAT connections are allowed (not HOW to block others). The NetworkPolicy controller continuously enforces these rules. If someone deploys a rogue pod, it CANNOT communicate — the policy denies by default. This is the zero-trust model: nothing is trusted, everything must be explicitly allowed. The CNPA exam tests NetworkPolicy as a fundamental declarative security primitive.

⚡ Lab 7: Use kubectl apply with Dry-Run and Diff

Scenario: You're about to update the anihpj-api Deployment from 3 replicas to 5. Before applying, you want to: (a) see what would change without actually applying, (b) validate the YAML syntax, (c) apply and record the change. Execute the complete workflow with commands.

👁️ Show Solution
✅ Safe Declarative Update Workflow:
# STEP 1: View current state (imperative — fine for inspection)
kubectl get deployment anihpj-api -o yaml > current.yaml

# STEP 2: Update replicas in your source-of-truth YAML file
# Change: replicas: 3 → replicas: 5

# STEP 3: Dry-run — see what WOULD change (doesn't apply)
kubectl apply -f anihpj-api-deploy.yaml --dry-run=client

# STEP 4: Server-side diff — see EXACT differences
kubectl diff -f anihpj-api-deploy.yaml
# Output:
# -  replicas: 3
# +  replicas: 5

# STEP 5: Apply with record flag
kubectl apply -f anihpj-api-deploy.yaml --record

# STEP 6: Verify reconciliation
kubectl rollout status deployment/anihpj-api
# Waiting for deployment "anihpj-api" rollout to finish: 3 of 5 updated replicas...
# deployment "anihpj-api" successfully rolled out

Explanation

kubectl diff is the declarative safety net — it shows you exactly what will change BEFORE you apply. --dry-run=client validates YAML syntax without touching the cluster. --record annotates the resource with the command that changed it (deprecated in newer K8s but still on the exam). Always diff before apply — this is the declarative equivalent of "measure twice, cut once."

📝 Lab 8: Convert Imperative Commands to Declarative YAML

Scenario: A teammate created these resources imperatively and now needs them in declarative form for Git: (a) kubectl create deployment anihpj-worker --image=anihpj/worker:v1, (b) kubectl expose deployment anihpj-worker --port=9000, (c) kubectl create configmap anihpj-config --from-literal=DEBUG=false --from-literal=LOG_LEVEL=info. Convert each to declarative YAML and explain the advantages.

👁️ Show Solution
✅ Imperative-to-Declarative Conversion:
# (a) Deployment — converted from: kubectl create deployment
apiVersion: apps/v1
kind: Deployment
metadata:
  name: anihpj-worker
  labels:
    app: anihpj-worker
spec:
  replicas: 1
  selector:
    matchLabels:
      app: anihpj-worker
  template:
    metadata:
      labels:
        app: anihpj-worker
    spec:
      containers:
      - name: worker
        image: anihpj/worker:v1
---
# (b) Service — converted from: kubectl expose
apiVersion: v1
kind: Service
metadata:
  name: anihpj-worker
spec:
  selector:
    app: anihpj-worker
  ports:
  - port: 9000
    targetPort: 9000
    protocol: TCP
---
# (c) ConfigMap — converted from: kubectl create configmap
apiVersion: v1
kind: ConfigMap
metadata:
  name: anihpj-config
data:
  DEBUG: "false"
  LOG_LEVEL: "info"

Explanation

Imperative commands create resources but leave no record of HOW they were created. Declarative YAML in Git provides: (1) Version history — who changed what and when, (2) Peer review — PR before apply, (3) Reproducibility — same YAML = same result every time, (4) GitOps compatibility — ArgoCD can sync from this YAML automatically. Pro tip: use kubectl create deployment --dry-run=client -o yaml to generate YAML from imperative commands, then save to Git.

🌊 Lab 9: Self-Healing — Simulate Pod Failure

Scenario: Your anihpj-api Deployment has liveness and readiness probes configured. Simulate a scenario where a pod's /healthz endpoint starts returning 500 errors. Walk through EXACTLY what K8s does, step by step, and what the timeline looks like.

👁️ Show Solution
✅ Self-Healing Timeline:
T+0s: Application bug introduced

/healthz endpoint returns HTTP 500 (app deadlocked). Container is still running but unresponsive.

T+10s: Liveness probe first failure

kubelet performs livenessProbe.httpGet on /healthz:8000 → 500. failureThreshold=3, so no action yet.

T+25s: Liveness probe second failure

Second probe fails. Still within failureThreshold=3.

T+40s: Liveness probe third failure → KILL

Third consecutive failure. failureThreshold=3 reached. kubelet KILLS the container (SIGTERM → SIGKILL after grace period).

T+41s: ReplicaSet detects missing pod

ReplicaSet controller: "Desired=3, Actual=2 → create new pod."

T+42s-50s: New pod starts

Scheduler assigns new pod to node. kubelet pulls image. Container starts. Liveness/readiness probes begin.

T+60s: Service restored

Readiness probe succeeds. Pod added to Service endpoints. Traffic resumes. Total downtime: ~20 seconds.

Explanation

This is declarative self-healing in action. The liveness probe detects the failure. Kubelet kills the container (NOT the pod — the pod object survives). The ReplicaSet controller reconciles (desired=3, actual=2 → create new). No human intervention needed. The key concept: probes are declarative health checks — you declare "my app is healthy if /healthz returns 200" and K8s continuously verifies this.

🏗️ Lab 10: Compose a Multi-Resource Application

Scenario: Compose a single kustomization.yaml that deploys the complete anihpj stack: Deployment + Service + ConfigMap + NetworkPolicy + HPA. Explain why Kustomize (declarative composition) is preferred over Helm (templating) for platform engineering.

👁️ Show Solution
✅ Kustomize Composition:
# kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization

namespace: anihpj-production

commonLabels:
  app.kubernetes.io/part-of: anihpj
  app.kubernetes.io/managed-by: kustomize

resources:
- deployment.yaml
- service.yaml
- configmap.yaml
- networkpolicy.yaml
- hpa.yaml

images:
- name: anihpj/jobpost-api
  newTag: v1.2.3

configMapGenerator:
- name: anihpj-config
  literals:
  - DEBUG=false
  - LOG_LEVEL=info
  - DB_HOST=anihpj-db.anihpj-production.svc.cluster.local

# Apply: kubectl apply -k .
❌ Helm (Templating)

Templates with {{ .Values }} — imperative logic in YAML. Can have conditionals, loops. Rendered output not visible until install. Debugging = reading Go templates.

✅ Kustomize (Declarative)

Pure YAML overlay. No templates, no logic, no conditionals. kubectl kustomize shows final output. Built into kubectl. CNCF ecosystem standard.

Explanation

Kustomize is declarative composition: base YAML + overlays = final YAML. No template logic, no programming. Helm adds an imperative layer (Go templates) on top of declarative YAML. While both have their place, Kustomize aligns better with platform engineering principles: pure declarative, no runtime rendering, built into kubectl. The CNPA exam tests your understanding of declarative composition vs imperative templating.
