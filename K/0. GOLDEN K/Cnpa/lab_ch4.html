🔄 Lab 2: Implement Ephemeral (Preview) Environments

Scenario: Your team wants to test every PR in an isolated environment before merging. Design an ephemeral environment system that: (a) auto-creates a namespace + full stack on PR open, (b) runs tests, (c) auto-destroys on PR close. Write the key ArgoCD + GitHub Actions configuration.

👁️ Show Solution
✅ Ephemeral Environment Design:
# ArgoCD ApplicationSet for PR environments
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: anihpj-preview
spec:
  generators:
  - pullRequest:
      github:
        owner: anihpj
        repo: jobpost
      requeueAfterSeconds: 300
  template:
    metadata:
      name: 'anihpj-preview-{{branch}}-{{number}}'
    spec:
      source:
        repoURL: 'https://github.com/anihpj/jobpost.git'
        targetRevision: '{{head_sha}}'
        path: kustomize/overlays/preview
      destination:
        namespace: 'preview-{{number}}'
        server: https://kubernetes.default.svc
      syncPolicy:
        automated:
          prune: true       # Auto-delete resources when PR closes
          selfHeal: true
---
# GitHub Actions — create preview on PR
name: Preview Environment
on:
  pull_request:
    types: [opened, synchronize]
jobs:
  deploy-preview:
    runs-on: ubuntu-latest
    steps:
    - name: Create preview namespace
      run: kubectl create namespace preview-${{ github.event.pull_request.number }}
    - name: Deploy via ArgoCD
      run: |
        argocd app create anihpj-preview-${{ github.head_ref }} \
          --repo https://github.com/anihpj/jobpost.git \
          --path kustomize/overlays/preview \
          --dest-namespace preview-${{ github.event.pull_request.number }} \
          --dest-server https://kubernetes.default.svc \
          --sync-policy automated

Explanation

Ephemeral environments give every PR its own isolated copy of the full stack. PR #42 gets preview-42 namespace with its own API + DB + Redis. Tests run against this environment. When the PR is merged or closed, ArgoCD's prune: true auto-destroys everything. This is a CNPA-level platform capability: developers get production-parity testing without managing infrastructure.

⚖️ Lab 3: Choose the Right Deployment Strategy

Scenario: For each anihpj component, choose the best deployment strategy and justify: (a) anihpj-db (PostgreSQL), (b) anihpj-api (Django REST), (c) anihpj-web (React frontend), (d) anihpj-worker (Celery background jobs). Compare Rolling, Blue-Green, Canary, and Recreate.

👁️ Show Solution
✅ Deployment Strategy Selection:
ComponentStrategyWhyDowntime
anihpj-db (PostgreSQL)⚠️ RecreateDBs can't have multiple instances writing. Must stop old before starting new (or use operator with failover).Seconds (with operator)

🔧 Lab 4: Configure Environment-Specific Kustomize Overlays

Scenario: Create Kustomize overlays for anihpj dev, staging, and production. Each overlay must override: replicas, resource limits, image tag, and ConfigMap data. Write the base and one overlay, explaining the patch strategy.

👁️ Show Solution
✅ Kustomize Base + Overlays:
# base/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
- deployment.yaml
- service.yaml
- configmap.yaml
images:
- name: anihpj/jobpost-api
  newTag: v1.0.0  # Base tag — overridden per environment

# overlays/production/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
namespace: anihpj-production
resources:
- ../../base
patches:
- patch: |-
    apiVersion: apps/v1
    kind: Deployment
    metadata:
      name: anihpj-api
    spec:
      replicas: 5              # Dev=1, Staging=3, Prod=5
      template:
        spec:
          containers:
          - name: api
            resources:
              requests:
                cpu: "500m"     # Dev=125m, Staging=250m, Prod=500m
                memory: "512Mi"
              limits:
                cpu: "1"        # Dev=250m, Staging=500m, Prod=1
                memory: "1Gi"
images:
- name: anihpj/jobpost-api
  newTag: v1.2.3-stable       # Specific version for prod
configMapGenerator:
- name: anihpj-config
  behavior: merge
  literals:
  - DEBUG=false
  - LOG_LEVEL=warn
  - DB_MAX_CONNECTIONS=100    # Dev=5, Staging=20, Prod=100

Explanation

Kustomize overlays follow the DRY principle: define the base ONCE, override per environment. patches selectively modify specific fields. images override the container tag. configMapGenerator with behavior: merge adds/overrides ConfigMap entries. This is declarative environment management — no template logic, no conditionals. Each overlay is a standalone, reviewable YAML file.

🔑 Lab 5: Manage Environment-Specific Secrets

Scenario: anihpj-api needs different DB credentials in dev, staging, and production. Design a secrets management strategy using External Secrets Operator (ESO) + AWS Secrets Manager. Write the ExternalSecret and SecretStore manifests.

👁️ Show Solution
✅ External Secrets Design:
# SecretStore — points to AWS Secrets Manager
apiVersion: external-secrets.io/v1beta1
kind: SecretStore
metadata:
  name: aws-secrets-manager
  namespace: anihpj-production
spec:
  provider:
    aws:
      service: SecretsManager
      region: us-east-1
      auth:
        jwt:              # IRSA — no static credentials
          serviceAccountRef:
            name: eso-sa  # IAM role mapped to SA
---
# ExternalSecret — syncs specific secrets
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: anihpj-db-credentials
  namespace: anihpj-production
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: aws-secrets-manager
    kind: SecretStore
  target:
    name: anihpj-db-secret   # Creates K8s Secret with this name
    creationPolicy: Owner
  data:
  - secretKey: DB_USER        # Key in K8s Secret
    remoteRef:
      key: /anihpj/production/database  # Path in AWS Secrets Manager
      property: username
  - secretKey: DB_PASSWORD
    remoteRef:
      key: /anihpj/production/database
      property: password
  - secretKey: DB_HOST
    remoteRef:
      key: /anihpj/production/database
      property: host

Explanation

External Secrets Operator (ESO) synchronizes secrets from external providers (AWS, GCP, Azure, Vault) into K8s Secrets. Key principles: (1) NEVER store secrets in Git — not even encrypted (SOPS is for GitOps manifests, not secrets), (2) ESO auto-refreshes — if AWS Secrets Manager rotates the password, K8s pods get the new value within 1 hour, (3) IRSA (IAM Roles for Service Accounts) avoids static credentials — the ServiceAccount maps to an AWS IAM role.

🧪 Lab 6: Implement Chaos Engineering for anihpj

Scenario: You want to verify that anihpj-api handles dependency failures gracefully. Design a chaos experiment using LitmusChaos that: kills the anihpj-db pod, verifies the API returns proper error responses (not crashes), and auto-rolls back if the experiment fails.

👁️ Show Solution
✅ Chaos Experiment Design:
apiVersion: litmuschaos.io/v1alpha1
kind: ChaosEngine
metadata:
  name: anihpj-db-chaos
  namespace: anihpj-staging   # NEVER run chaos in production first!
spec:
  annotationCheck: 'false'
  engineState: 'active'
  chaosServiceAccount: litmus-admin
  experiments:
  - name: pod-delete
    spec:
      components:
        env:
        - name: TOTAL_CHAOS_DURATION
          value: '120'          # 2 minutes
        - name: CHAOS_INTERVAL
          value: '30'           # Kill pod every 30s
        - name: FORCE
          value: 'false'        # Graceful termination
        - name: TARGET_PODS
          value: 'app=anihpj-db'
      probe:                    # Validation probes
      - name: 'api-still-responds'
        type: 'httpProbe'
        httpProbe/inputs:
          url: 'http://anihpj-api.anihpj-staging:8000/api/jobs/'
          method:
            get:
              criteria: '=='    # Expect proper error, NOT crash
              responseCode: '503'  # Service Unavailable = graceful
        mode: 'Continuous'
        runProperties:
          probeTimeout: 5

Explanation

Chaos engineering verifies system resilience. The experiment kills DB pods and checks that the API returns HTTP 503 (graceful degradation) rather than crashing (HTTP 500 or timeout). Key principles: (1) Always run chaos in staging FIRST, (2) Define "steady state" via probes — what does "working" mean during failure?, (3) Set blast radius (only target anihpj-db, not the entire cluster), (4) Auto-rollback if probes fail. The CNPA tests platform resilience patterns.

📐 Lab 7: Size Resources Correctly with VPA

Scenario: The anihpj-api pod has been manually set to 250m CPU request but regularly spikes to 800m. Configure a VerticalPodAutoscaler in "recommendation" mode to analyze actual usage and suggest optimal settings. Explain why VPA ≠ HPA.

👁️ Show Solution
✅ VPA Configuration:
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: anihpj-api-vpa
  namespace: anihpj-production
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: anihpj-api
  updatePolicy:
    updateMode: "Off"          # Recommend only — don't auto-apply
  resourcePolicy:
    containerPolicies:
    - containerName: api
      minAllowed:
        cpu: "100m"
        memory: "128Mi"
      maxAllowed:
        cpu: "2"
        memory: "2Gi"
      controlledResources: ["cpu", "memory"]
❌ Common Confusion

VPA = Vertical scaling (resize pod). HPA = Horizontal scaling (add/remove pods). They solve DIFFERENT problems. VPA adjusts "how big each pod is." HPA adjusts "how many pods."

✅ When to Use Each

VPA: "This Java app needs more heap." Updates resource requests/limits. Requires pod restart.
HPA: "Traffic doubled." Adds more replicas. No restart needed.

Explanation

VPA in "Off" mode analyzes historical metrics and provides recommendations via kubectl describe vpa. After reviewing, you update the Deployment YAML manually (or switch to "Auto" mode). VPA replaces pods to apply new resource settings — this is why you need proper readiness probes and multiple replicas. The CNPA distinguishes between VPA (vertical — pod size), HPA (horizontal — pod count), and Cluster Autoscaler (infrastructure — node count).

🌐 Lab 8: Configure Multi-Cluster Ingress for anihpj

Scenario: anihpj runs in 2 AWS regions (us-east-1 and eu-west-1) for global users. Design the ingress/routing strategy: how traffic gets to the nearest cluster, how failover works, and what happens when one region goes down.

👁️ Show Solution
✅ Multi-Cluster Ingress Design:
🌐 Global Traffic Routing for anihpj
                         ┌─────────────────────┐
                         │   🌍 Route53 DNS     │
                         │   Latency-based      │
                         │   routing policy     │
                         └──────┬──────┬────────┘
                                │      │
                   ┌────────────┘      └────────────┐
                   ▼                                 ▼
    ┌──────────────────────────┐     ┌──────────────────────────┐
    │  🇺🇸 us-east-1 (Primary)  │     │  🇪🇺 eu-west-1 (Secondary)│
    │                          │     │                          │
    │  AWS ALB (Ingress)       │     │  AWS ALB (Ingress)       │
    │  → anihpj-web (5 pods)   │     │  → anihpj-web (3 pods)   │
    │  → anihpj-api (10 pods)  │     │  → anihpj-api (6 pods)   │
    │  → RDS PostgreSQL (Multi-AZ)│  │  → RDS Read Replica      │
    └──────────────────────────┘     └──────────────────────────┘

FAILOVER FLOW:
1. Route53 health check fails on us-east-1 ALB
2. DNS automatically routes all traffic to eu-west-1
3. Promote RDS read replica to primary in eu-west-1
4. Failover time: ~2 minutes (DNS TTL 60s + RDS promotion)

Explanation

Multi-cluster ingress uses DNS as the global load balancer. Route53's latency-based routing sends users to the nearest healthy region. Health checks on the ALB endpoint detect regional failures. Key considerations: (1) Data replication — RDS cross-region read replicas, (2) DNS TTL — lower = faster failover but more DNS queries, (3) Active-active vs active-passive — active-passive (shown) is simpler but wastes standby resources. The CNPA tests multi-cluster architecture concepts.

📦 Lab 9: Implement GitOps-Driven Environment Promotion

Scenario: Design a GitOps promotion workflow: when a new image tag is pushed, ArgoCD auto-deploys to staging. After validation, promote to production by updating the production Git repo. Write the ArgoCD Application for staging with automated sync, and explain the promotion process.

👁️ Show Solution
✅ GitOps Promotion Pipeline:
# Staging — auto-sync enabled
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: anihpj-staging
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/anihpj/jobpost-gitops.git
    targetRevision: staging      # Staging branch
    path: overlays/staging
  destination:
    server: https://kubernetes.default.svc
    namespace: anihpj-staging
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
      allowEmpty: false
    syncOptions:
    - CreateNamespace=true
---
# Production — manual sync (promotion via PR)
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: anihpj-production
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/anihpj/jobpost-gitops.git
    targetRevision: main         # Production branch — PR-gated
    path: overlays/production
  destination:
    server: https://kubernetes.default.svc
    namespace: anihpj-production
  syncPolicy: {}                 # Manual sync only — no auto!
1
Image Built

CI pushes anihpj-api:sha-abc123

2
Staging Auto-Sync

ArgoCD detects new tag → deploys to staging

3
Validate

Smoke tests pass. Metrics nominal for 10 min.

4
PR to Main

Update image tag in overlays/production → PR

5
Approve & Sync

Merge PR → ArgoCD manual sync → production updated

Explanation

GitOps promotion uses Git branches as environment gates. Staging auto-syncs (fast feedback). Production requires a PR (approval gate). The promotion "artifact" is a Git commit that changes the image tag in the production overlay. This means: (1) Every production change has a PR with reviewers, (2) Rollback = git revert + ArgoCD sync, (3) Full audit trail in Git history.

🧩 Lab 10: Design the Full anihpj Infrastructure as Code Stack

Scenario: Map the complete Infrastructure as Code stack for anihpj, from cluster provisioning to application deployment. Specify which tool handles each layer: Terraform, Crossplane, Helm/Kustomize, ArgoCD, and explain WHY each tool is chosen for its layer.

👁️ Show Solution
✅ Full IaC Stack for anihpj:
☁️Cloud InfrastructureVPC, Subnets, IAM, S3, Route53Terraform
☸️Kubernetes ClusterEKS control plane + node groupsTerraform (EKS module)
🗄️Data ServicesRDS PostgreSQL, ElastiCache RedisCrossplane
📦Cluster ServicesIngress Controller, Cert-Manager, ESO, KyvernoHelm (ArgoCD)
⚙️Platform ConfigNamespaces, RBAC, ResourceQuotas, NetworkPoliciesKustomize (ArgoCD)
🚀Applicationsanihpj-api, anihpj-web, anihpj-workerKustomize + ArgoCD

Explanation

Why each tool at its layer: (1) Terraform for cloud infra — it's the industry standard for provisioning the foundational layer (VPC, EKS). Use it for "day 0" — creating the cluster. (2) Crossplane for data services — it's K8s-native, supports self-service claims ("I need a PostgreSQL"), and auto-reconciles drift. (3) Helm for cluster services — packaged, versioned, with dependency management. (4) Kustomize + ArgoCD for platform config and apps — pure declarative, no template logic, native GitOps. The CNPA tests this layered approach: the right tool for each layer, with ArgoCD as the unified deployment controller.
