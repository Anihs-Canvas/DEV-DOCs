🔬 Lab 1: Diagnose the "Ticket Queue" Problem

Scenario: You join a 200-person engineering organization as their first Platform Engineer. Currently, every developer files a Jira ticket when they need a database, a new service, or a CI pipeline. The average wait time is 8 days. The CTO wants this reduced to under 1 hour. Your task: identify the root cause(s) and propose the platform capability that solves this.

💡 Hint: Think about the difference between ticket-based ops and self-service. What capability does an IDP provide that eliminates tickets?
👁️ Show Solution
✅ Root Cause Analysis:

Root Cause: Ticket-based operations — manual, human-gated, queue-based provisioning. Every request must be triaged → assigned → executed → verified by ops.

Platform Solution: An Internal Developer Platform (IDP) with self-service golden paths. Developers provision databases, services, and pipelines through a portal/CLI/API — no ticket, no waiting.

┌──────────────────────────────────────────────────────┐
│  BEFORE (Ticket Queue — 8 days):                     │
│  Dev → Jira → Ops reviews → Ops provisions → Dev     │
│                                                      │
│  AFTER (Self-Service IDP — < 1 hour):                │
│  Dev → Backstage portal → Click "New Service"        │
│  → Golden Path auto-provisions: DB + CI + K8s        │
└──────────────────────────────────────────────────────┘

Explanation

This is the fundamental value proposition of platform engineering: replace manual, human-gated processes with automated, self-service capabilities. The golden path template encodes the organization's best practices (security, monitoring, CI) and executes them automatically when a developer requests a new service.

Explanation

A well-designed IDP abstracts each layer. The developer only sees Layer 5 (the portal). Layers 1-4 are fully automated — the developer never writes Kubernetes YAML, never provisions databases, never configures monitoring. This is "cognitive load reduction" — the core platform engineering principle.

💸 Lab 5: Calculate the "Production Gap" Cost

Scenario: The anihpj team reports that a developer spends 12 hours/week on non-coding tasks (waiting for environments, debugging infra issues, configuring CI). The fully-loaded cost is $150/hour. There are 40 developers. Calculate: (a) Annual cost of the production gap, (b) ROI of a platform that reduces this by 80%.

👁️ Show Solution
✅ Production Gap Calculation:
📊 Current State (Without Platform)

Weekly waste per dev: 12 hours × $150 = $1,800

Annual waste per dev: $1,800 × 52 = $93,600

Total for 40 devs: $93,600 × 40 = $3,744,000/year

✅ With Platform (80% Reduction)

Remaining waste: 2.4 hours/week × $150 = $360

Annual savings per dev: ($1,800 - $360) × 52 = $74,880

Total savings: $74,880 × 40 = $2,995,200/year

ROI: If platform costs $500K/year → 6x ROI

Explanation

The "production gap" is the difference between what developers COULD produce and what they ACTUALLY produce due to infrastructure friction. At $3.7M/year in waste, a $500K platform investment pays for itself in ~2 months. This is the business case for platform engineering — it's not about technology, it's about economics.

🧠 Lab 6: Identify Cognitive Load Sources

Scenario: Interview 3 anihpj developers. Developer A says: "I need to know which AWS region my RDS instance is in." Developer B says: "I spend 2 hours configuring ServiceMonitors for every new service." Developer C says: "There are 4 different ways to deploy in this org — I don't know which one is the recommended way." For each complaint, classify the cognitive load type and propose the platform solution.

👁️ Show Solution
✅ Cognitive Load Analysis:
DeveloperCognitive Load TypePlatform Solution
A: "Which AWS region?"Extraneous — infra detail dev shouldn't knowIDP abstracts cloud provider; Crossplane handles provisioning transparently
B: "2h on ServiceMonitors"Extraneous — repetitive, automatableGolden path auto-generates ServiceMonitor YAML; Prometheus auto-discovers services
C: "4 ways to deploy"Extraneous — lack of standardizationSingle golden path for deployment; platform team enforces ONE way (with escape hatches)

Explanation

Cognitive load comes in 3 types (Sweller): Intrinsic (inherent to the task — unavoidable), Extraneous (caused by how info is presented — ELIMINATE), and Germane (productive learning — ENCOURAGE). Platform engineering targets extraneous load: developers shouldn't know cloud regions, monitoring config, or deployment choices. The IDP makes ONE recommended way the default.

📋 Lab 7: Audit an Existing Org for Platform Readiness

Scenario: You're hired to assess whether a 150-person org needs a platform team. You discover: 12 different CI/CD systems, 0 shared monitoring, average deployment frequency = 1/month, lead time = 14 days, and teams spend 40% of sprint on non-feature work. Using DORA metrics and CNCF platform maturity model, write your assessment and recommendation.

👁️ Show Solution
✅ Platform Readiness Assessment:
🔴 Current State — Platform NEEDED
  • 12 CI/CD systems → Massive cognitive load, zero standardization
  • Deploy frequency: 1/month → DORA "Low" performer (Elite = multiple/day)
  • Lead time: 14 days → DORA "Low" (Elite < 1 hour)
  • 40% sprint waste → $4M+ annual productivity loss
  • Zero shared observability → Each team reinvents monitoring
🟢 Recommendation — Build Platform Team
  • Phase 1 (3 months): Standardize on 1 CI system + shared observability (Prometheus/Grafana)
  • Phase 2 (6 months): Build golden paths for top 3 service types. Target: deploy freq = 1/week
  • Phase 3 (12 months): Full IDP with Backstage, Crossplane, ArgoCD. Target: Elite DORA

Explanation

This org exhibits ALL the symptoms that platform engineering solves: fragmentation, cognitive overload, slow delivery, and no standardization. The CNCF Platform Maturity Model says Level 1 (Provisional) orgs should start with standardization before building an IDP. You can't automate chaos — standardize first, then platformize.
