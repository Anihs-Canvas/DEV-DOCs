📊 Lab 1: Implement RED Metrics for anihpj-api

Scenario: Instrument the anihpj-api Django service with RED metrics (Rate, Errors, Duration). Write the Prometheus metric definitions, the Python instrumentation code, and the PromQL queries to alert on each.

👁️ Show Solution
✅ RED Metrics Implementation:
# anihpj/metrics.py — Prometheus instrumentation
from prometheus_client import Counter, Histogram, generate_latest
from django.http import HttpResponse
import time

# RATE — Requests per second
http_requests_total = Counter(
    'http_requests_total',
    'Total HTTP requests',
    ['method', 'endpoint', 'status']
)

# ERRORS — Failed requests
http_errors_total = Counter(
    'http_errors_total', 
    'Total HTTP errors (5xx)',
    ['method', 'endpoint']
)

# DURATION — Request latency (Histogram for p50/p95/p99)
http_request_duration_seconds = Histogram(
    'http_request_duration_seconds',
    'HTTP request latency',
    ['method', 'endpoint'],
    buckets=[0.01, 0.05, 0.1, 0.25, 0.5, 1.0, 2.5, 5.0, 10.0]
)

# Middleware to track every request
class PrometheusMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response
    
    def __call__(self, request):
        start = time.time()
        response = self.get_response(request)
        duration = time.time() - start
        
        http_requests_total.labels(
            method=request.method,
            endpoint=request.path,
            status=response.status_code
        ).inc()
        
        http_request_duration_seconds.labels(
            method=request.method,
            endpoint=request.path
        ).observe(duration)
        
        if response.status_code >= 500:
            http_errors_total.labels(
                method=request.method,
                endpoint=request.path
            ).inc()
        
        return response

# Expose /metrics endpoint
def metrics_view(request):
    return HttpResponse(generate_latest(), content_type='text/plain')
# PromQL Alert Rules
# RATE alert: sudden drop in traffic
rate(http_requests_total{endpoint="/api/jobs/"}[5m]) < 1

# ERRORS alert: error rate > 1%
rate(http_errors_total[5m]) / rate(http_requests_total[5m]) > 0.01

# DURATION alert: p95 latency > 500ms
histogram_quantile(0.95, 
  rate(http_request_duration_seconds_bucket[5m])) > 0.5

Explanation

RED metrics are the MINIMUM every service must expose. Rate = traffic volume (drops = load balancer failure). Errors = user-facing failures (spikes = deployment broke something). Duration = user experience (p95 matters more than average — it captures the worst 5% of user experiences). The platform team provides this instrumentation in the golden path — developers don't write metrics code, they inherit it.

📝 Lab 3: Implement Structured Logging for anihpj

Scenario: Configure anihpj-api to emit structured JSON logs with: trace_id, user_id, request_path, duration_ms, and status_code. Write the Python logging config and the Loki LogQL query to find all errors for user "123" in the last hour.

👁️ Show Solution
✅ Structured Logging Implementation:
# anihpj/logging_config.py
import logging
import json
import time
from pythonjsonlogger import jsonlogger

class StructuredFormatter(jsonlogger.JsonFormatter):
    def add_fields(self, log_record, record, message_dict):
        super().add_fields(log_record, record, message_dict)
        log_record['timestamp'] = time.time()
        log_record['service'] = 'anihpj-api'
        log_record['environment'] = 'production'

LOGGING = {
    'version': 1,
    'formatters': {
        'json': {
            '()': StructuredFormatter,
            'format': '%(timestamp)s %(level)s %(name)s %(message)s'
        }
    },
    'handlers': {
        'console': {
            'class': 'logging.StreamHandler',
            'formatter': 'json',
            'stream': 'ext://sys.stdout'
        }
    },
    'root': {
        'handlers': ['console'],
        'level': 'INFO'
    }
}

# Usage in views.py:
import logging
logger = logging.getLogger(__name__)

def job_list(request):
    logger.info("Fetching jobs", extra={
        'trace_id': request.headers.get('X-Trace-Id', 'unknown'),
        'user_id': request.user.id,
        'request_path': request.path,
        'duration_ms': 45,
        'status_code': 200
    })
    # ... view logic
# LogQL: Find all errors for user 123 in the last hour
{service="anihpj-api", environment="production"} 
| json 
| status_code >= 500 
| user_id = "123"
| line_format "{{.timestamp}} {{.request_path}} {{.status_code}} {{.trace_id}}"

Explanation

Structured logging is a CNPA best practice. JSON logs enable Loki to index specific fields without parsing — much cheaper than full-text indexing. Key fields: trace_id (correlate with traces), user_id (troubleshoot user-specific issues), request_path (find endpoint-specific problems). The platform team configures this in the golden path — every service gets structured logging automatically. Console output is scraped by Promtail (or Grafana Agent) and sent to Loki.

🔍 Lab 4: Implement Distributed Tracing with OpenTelemetry

Scenario: Instrument anihpj-api with OpenTelemetry to trace requests across: web → api → database → Redis. Configure auto-instrumentation, manual spans for DB queries, and the Tempo query to find the slowest trace.

👁️ Show Solution
✅ OpenTelemetry Tracing:
# settings.py — OTel auto-instrumentation
from opentelemetry import trace
from opentelemetry.instrumentation.django import DjangoInstrumentor
from opentelemetry.instrumentation.psycopg2 import Psycopg2Instrumentor
from opentelemetry.instrumentation.redis import RedisInstrumentor
from opentelemetry.exporter.otlp.proto.grpc.trace_exporter import OTLPSpanExporter
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor

# Auto-instrument Django, PostgreSQL, Redis
DjangoInstrumentor().instrument()
Psycopg2Instrumentor().instrument()
RedisInstrumentor().instrument()

# Export to Tempo via OTLP
exporter = OTLPSpanExporter(endpoint="http://tempo.observability:4317")
provider = TracerProvider()
provider.add_span_processor(BatchSpanProcessor(exporter))
trace.set_tracer_provider(provider)

# Manual span for complex business logic
tracer = trace.get_tracer(__name__)

def search_jobs(query: str):
    with tracer.start_as_current_span("search-jobs") as span:
        span.set_attribute("search.query", query)
        span.set_attribute("search.type", "fulltext")
        
        # DB query (auto-instrumented by Psycopg2Instrumentor)
        results = Job.objects.filter(title__icontains=query)
        
        span.set_attribute("search.results_count", results.count())
        return results
# Tempo TraceQL — Find slowest trace in last 15 min
{ .service.name = "anihpj-api" && duration > 2s } 
| by(duration) 
| sort(duration desc) 
| limit 5

Explanation

OpenTelemetry is the CNCF standard for distributed tracing. Auto-instrumentation covers Django, PostgreSQL, and Redis automatically — zero code changes for basic traces. Manual spans add business context (search query, result count). OTLP exporter sends to Tempo (Grafana's tracing backend). The CNPA tests OTel because it's the vendor-neutral observability standard — instrument once, switch backends freely.

🚨 Lab 5: Configure Prometheus AlertManager for anihpj

Scenario: Set up alerts for anihpj: (a) API error rate > 5% for 5 min → PagerDuty, (b) P95 latency > 1s for 10 min → Slack, (c) No metrics received for 5 min → PagerDuty (dead service). Write the PrometheusRule and AlertManager config.

👁️ Show Solution
✅ Alert Configuration:
# prometheus-rules.yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: anihpj-api-alerts
  namespace: monitoring
spec:
  groups:
  - name: anihpj-api
    rules:
    # Alert 1: High Error Rate → PagerDuty (critical)
    - alert: HighErrorRate
      expr: |
        sum(rate(http_errors_total{app="anihpj-api"}[5m])) 
        / sum(rate(http_requests_total{app="anihpj-api"}[5m])) > 0.05
      for: 5m
      labels:
        severity: critical
        team: platform
      annotations:
        summary: "anihpj-api error rate > 5%"
        description: "Error rate is {{ $value | humanizePercentage }}. Check Grafana: https://grafana.anihpj.io/d/anihpj-api"
        runbook_url: "https://backstage.anihpj.io/docs/runbooks/high-error-rate"
    
    # Alert 2: High Latency → Slack (warning)
    - alert: HighLatency
      expr: |
        histogram_quantile(0.95, 
          rate(http_request_duration_seconds_bucket{app="anihpj-api"}[10m])) > 1.0
      for: 10m
      labels:
        severity: warning
        channel: slack
      annotations:
        summary: "anihpj-api p95 latency > 1s"
        description: "P95 latency is {{ $value }}s"
    
    # Alert 3: Dead Service → PagerDuty (critical)
    - alert: ServiceDown
      expr: up{job="anihpj-api"} == 0
      for: 5m
      labels:
        severity: critical
      annotations:
        summary: "anihpj-api is DOWN"
        description: "No metrics from anihpj-api for 5 minutes"

Explanation

Prometheus alerts follow the "RED method alerting" pattern: Rate (ServiceDown detects zero traffic), Errors (HighErrorRate), Duration (HighLatency). Key design: (1) Alert on symptoms, not causes — "error rate > 5%" not "CPU > 80%", (2) Include runbook URL in annotations — incident responder clicks directly to the fix, (3) DeadMansSnitch (ServiceDown via up{} metric) catches complete service failure. The platform team configures baseline alerts in every golden path.

📦 Lab 7: Configure ServiceMonitor for Auto-Discovery

Scenario: Configure a Prometheus ServiceMonitor that auto-discovers anihpj-api pods and scrapes /metrics every 30s. Write the ServiceMonitor and explain how label matching enables automatic monitoring.

👁️ Show Solution
✅ ServiceMonitor Configuration:
# ServiceMonitor for anihpj-api
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: anihpj-api
  namespace: anihpj-production
  labels:
    release: prometheus    # Prometheus operator selects by this label
spec:
  selector:
    matchLabels:
      app: anihpj-api      # Auto-discovers Services with this label
  namespaceSelector:
    matchNames:
    - anihpj-production
  endpoints:
  - port: metrics           # Service port named "metrics"
    interval: 30s
    path: /metrics
    relabelings:
    - sourceLabels: [__meta_kubernetes_pod_label_app]
      targetLabel: app
    - sourceLabels: [__meta_kubernetes_pod_label_version]
      targetLabel: version
# Corresponding Service (must have port named "metrics")
apiVersion: v1
kind: Service
metadata:
  name: anihpj-api
  labels:
    app: anihpj-api
spec:
  selector:
    app: anihpj-api
  ports:
  - name: metrics         # Must match ServiceMonitor's port
    port: 8000
    targetPort: 8000

Explanation

ServiceMonitors implement "monitoring as code" — the monitoring configuration is declarative and versioned in Git alongside the application. Key design: (1) Label-based discovery — no hardcoded IPs or pod names, (2) Relabeling — enrich metrics with pod labels (app, version), (3) The platform team provides a ServiceMonitor template in the golden path. The CNPA tests Prometheus ServiceMonitor as the CNCF standard for K8s-native monitoring.

🔬 Lab 8: Implement SLO-Based Alerting for anihpj

Scenario: Define an SLO for anihpj-api: 99.9% availability over 28 days. Calculate the error budget, configure burn rate alerts, and write the Multi-Window, Multi-Burn-Rate alert rules.

👁️ Show Solution
✅ SLO-Based Alerting:
99.9%
SLO Target
0.1%
Error Budget
43 min
Monthly Downtime Budget
# Error budget burn rate calculation
# Burn rate = how fast you're consuming error budget
# 1x = using budget at expected rate (fine)
# 10x = using budget 10x faster (alert!)
# 100x = using budget 100x faster (page!)

# Multi-window, multi-burn-rate alert (Google SRE book pattern)
groups:
- name: anihpj-slo
  rules:
  # Short window: 1 hour, burn rate > 14.4x → critical (pages on-call)
  - alert: SLOBurnRateHigh
    expr: |
      (
        sum(rate(http_errors_total{app="anihpj-api"}[1h]))
        / sum(rate(http_requests_total{app="anihpj-api"}[1h]))
      ) > 0.1 * 14.4    # 14.4x burn rate
    labels:
      severity: critical
      slo: "api-availability"
    annotations:
      summary: "Burning error budget at {{ $value | humanizePercentage }}x rate"
      
  # Long window: 6 hours, burn rate > 1x → warning (slack)
  - alert: SLOBurnRateLow
    expr: |
      (
        sum(rate(http_errors_total{app="anihpj-api"}[6h]))
        / sum(rate(http_requests_total{app="anihpj-api"}[6h]))
      ) > 0.1 * 1.0     # 1x burn rate
    for: 1h
    labels:
      severity: warning
      slo: "api-availability"

Explanation

SLO-based alerting is the CNPA-recommended approach (from Google SRE). Instead of alerting on individual metrics, alert on ERROR BUDGET CONSUMPTION. Key insight: a 1-minute outage burns ~2% of the monthly budget — it's not an emergency. A 5-minute outage at 100x burn rate? That's a page. This prevents alert fatigue by only paging when the SLO is at risk. The CNPA tests SLO concepts as part of Domain 2 (Observability) and Domain 6 (Measuring).

🔭 Lab 10: Debug a Production Incident Using the Three Pillars

Scenario: It's 3 AM. PagerDuty wakes you: "anihpj-api error rate: 15%, p95 latency: 8 seconds." Users report timeouts. Walk through a structured debugging approach using metrics → logs → traces to find and fix the root cause within 15 minutes.

👁️ Show Solution
✅ Production Incident Debugging (MTTR < 15 min):
T+0min: Triage (Metrics)

Grafana dashboard → error rate 15% since 03:00 UTC, p95=8s. Only /api/jobs/search/ endpoint affected. Other endpoints normal. Hypothesis: search-specific issue.

T+2min: Investigate (Logs)

Loki: {app="anihpj-api"} |= "search" |= "error" → "Elasticsearch connection refused" at 03:00:01. Log shows: "ES host: 10.0.1.50:9200 timeout after 5s."

T+4min: Pinpoint (Traces)

Tempo: trace for /api/jobs/search/ → api (5ms) → es_client.query (8000ms timeout) → DB fallback (3ms). Elasticsearch is down; falling back to PostgreSQL (slow).

T+6min: Verify (Infrastructure)

Check Elasticsearch: kubectl get pods -l app=elasticsearch → 0/1 CrashLoopBackOff. kubectl logs → "max virtual memory areas vm.max_map_count too low." Node was patched at 02:55.

T+8min: Mitigate

Option A: Fix ES → 30 min (reconfigure kernel). Option B: Search uses PostgreSQL → slow but works. CHOOSE B: Set feature flag search_backend=postgres. Error rate drops to 0.5%.

T+12min: Resolve

Incident resolved. Postmortem action: ES health check alert + kernel param in node bootstrap. MTTR: 12 minutes.

Explanation

This is the CNPA observability pattern in action: Metrics detect (WHAT — error rate spiked), Logs explain (WHY — ES connection refused), Traces pinpoint (WHERE — es_client.query took 8 seconds). Without all three pillars, debugging would take hours: metrics alone = "something is wrong" (vague), logs alone = "ES connection refused" (but which endpoint?), traces alone = "query took 8s" (but why?). Together, they tell the complete story in 12 minutes.
