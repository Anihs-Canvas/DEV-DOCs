Platform APIs are the programmatic interface to the IDP. They enable: CI/CD integration (deploy via API), custom tooling (CLI wraps the API), and automation (auto-create services). The CNPA tests Platform API design as part of Domain 4.

🔒 Lab 8: Implement Multi-Tenancy for anihpj

Scenario: anihpj serves 3 teams: backend, frontend, and data. Design a multi-tenancy strategy using K8s namespaces, ResourceQuotas, NetworkPolicies, and RBAC to ensure strong isolation.

👁️ Show Solution
✅ Multi-Tenancy Implementation:
# Namespace per team
apiVersion: v1
kind: Namespace
metadata:
  name: anihpj-backend-team
  labels:
    team: backend
    cost-center: engineering
---
# ResourceQuota — prevents one team from consuming all resources
apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-quota
  namespace: anihpj-backend-team
spec:
  hard:
    requests.cpu: "10"
    requests.memory: "20Gi"
    limits.cpu: "20"
    limits.memory: "40Gi"
    persistentvolumeclaims: "10"
    services.loadbalancers: "2"
---
# NetworkPolicy — isolate teams from each other
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-from-other-teams
  namespace: anihpj-backend-team
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          team: backend     # Only allow from same team
  - from:
    - namespaceSelector:
        matchLabels:
          platform: shared  # Allow platform services (monitoring, ingress)

Explanation

Multi-tenancy in Kubernetes uses namespaces as soft-tenancy boundaries. Key isolation mechanisms: (1) Namespaces — logical separation, (2) ResourceQuotas — prevent noisy neighbor, (3) NetworkPolicies — network isolation, (4) RBAC — who can do what in which namespace, (5) Pod Security Admission — enforce security standards. The CNPA tests multi-tenancy as a platform architecture concern.

⚡ Lab 9: Right-Size Platform Infrastructure

Scenario: The anihpj EKS cluster has 10 m5.xlarge nodes (4 vCPU, 16GB each) but only 35% average utilization. Costs are $2,500/month. Propose an optimization strategy using Cluster Autoscaler, Karpenter, Spot instances, and right-sizing.

👁️ Show Solution
✅ Infrastructure Optimization:
🔴 Current (Over-Provisioned)

• 10 × m5.xlarge = 40 vCPU, 160GB RAM
• 35% utilization = 14 vCPU, 56GB used
• Wasted: 26 vCPU, 104GB RAM
• Cost: $2,500/month

🟢 Optimized (Karpenter + Spot)

• Karpenter auto-selects instance types based on pod requirements
• 70% Spot (50% savings) + 30% On-Demand
• Bin-packing: consolidate pods onto fewer nodes
• Target: 6-8 mixed instances, 65% utilization
• Cost: ~$1,200/month (52% savings)

# Karpenter NodePool
apiVersion: karpenter.sh/v1beta1
kind: NodePool
metadata:
  name: anihpj-default
spec:
  template:
    spec:
      requirements:
      - key: "kubernetes.io/arch"
        operator: In
        values: ["amd64"]
      - key: "karpenter.sh/capacity-type"
        operator: In
        values: ["spot", "on-demand"]  # Prefer spot
      - key: "node.kubernetes.io/instance-type"
        operator: In
        values: ["m5.xlarge", "m5.2xlarge", "m6i.xlarge"]
      nodeClassRef:
        name: anihpj-default
  limits:
    cpu: "100"
  disruption:
    consolidationPolicy: WhenUnderutilized
    consolidateAfter: 1m

Explanation

Karpenter is the next-gen node autoscaler: it selects the OPTIMAL instance type based on pending pod requirements, not a fixed node group. Key benefits: (1) Just-in-time provisioning — nodes created in seconds, (2) Consolidation — moves pods to fewer nodes when utilization drops, (3) Spot-native — gracefully handles spot termination. The CNPA tests node scaling and cost optimization as platform architecture concerns.

🧬 Lab 10: Blueprint a "Platform on Kubernetes" Architecture

Scenario: Your CTO asks: "Why should our platform run ON Kubernetes instead of a VM?" Create an argument backed by the 7 platform engineering attributes: self-service, composable, extensible, secure by default, observable, API-driven, and declarative.

👁️ Show Solution
✅ "Platform on K8s" — 7 Attributes Justification:
🤖
Self-Service

K8s API + CRDs = native self-service. Crossplane Claims let devs provision infra without tickets. A VM-based platform needs custom APIs built from scratch.

🧩
Composable

K8s resources compose naturally. A Claim composes RDS + SecurityGroup + Subnet. Kustomize overlays compose base + patches. VMs require external orchestration.

🔌
Extensible

CRDs + Operators extend K8s API. Crossplane adds database types. ArgoCD adds Application types. VM platforms need custom APIs for each extension.

🔒
Secure by Default

NetworkPolicies, RBAC, PSA, Kyverno — built-in security primitives. VMs need external firewalls, IAM, compliance tools — all integrated manually.

👁️
Observable

Prometheus auto-discovers services. Grafana dashboards auto-generated. OTel auto-instruments. VMs need agents installed on every host.

🔗
API-Driven

Everything in K8s has an API. kubectl, ArgoCD, Crossplane — all via the same API server. Consistent auth (RBAC), versioning, and discovery.

📜
Declarative

YAML describes desired state. Controllers reconcile continuously. Self-healing built-in. VMs need imperative scripts + manual recovery.

Explanation

Kubernetes IS the platform for building platforms. Its declarative API, reconciliation loop, extensibility (CRDs), and ecosystem (CNCF) make it the natural foundation for an IDP. The CNPA exam explicitly frames K8s as the platform substrate — the "platform for platforms." This is why Domain 1 (Core Fundamentals — 36%) is the largest domain: K8s fundamentals ARE platform engineering fundamentals.
