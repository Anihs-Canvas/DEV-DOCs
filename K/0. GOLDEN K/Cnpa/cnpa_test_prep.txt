WHAT IS A CLOUD NATIVE PLATFORM ENGINEER?
═══════════════════════════════════════════════════════════════════════

A Cloud Native Platform Engineer builds and maintains the INTERNAL DEVELOPER
PLATFORM (IDP) that enables developers to deploy, run, and manage applications
without needing deep infrastructure knowledge.

    ┌──────────────────────────────────────────────────────────────┐
    │ 🏗️ Platform Engineer = Building the FACTORY (platform)       │
    │ 🎨 Developer         = Using the factory (apps)               │
    │                                                              │
    │ You are the bridge between:                                  │
    │   • Infrastructure (servers, networks, storage)              │
    │   • Operations (monitoring, security, compliance)            │
    │   • Development (CI/CD, developer tools, self-service)       │
    └──────────────────────────────────────────────────────────────┘

CNPA vs CKA vs CKAD — WHAT'S THE DIFFERENCE?
─────────────────────────────────────────────
    ┌──────────────────────────────────────────────────────────────────┐
    │                    CKA              CKAD           CNPA           │
    │  Focus:           Administrator     App Developer   Platform Eng  │
    │  You manage:      The CLUSTER       The APPS        The PLATFORM  │
    │  Scope:           Single cluster    App lifecycle   Multi-cluster, │
    │                                                 multi-tool, IDP  │
    │  Tools:           kubeadm, etcd,    kubectl, Helm,  ArgoCD, Tofu, │
    │                   kubelet, certs    ConfigMaps,     Crossplane,    │
    │                                     Secrets, Pods   Backstage,     │
    │                                                      Prometheus    │
    │  Think of it:     🏗️ Building      🎨 Decorating   🏭 Building    │
    │                   the house         the rooms       the factory   │
    └──────────────────────────────────────────────────────────────────┘

CNPA also pairs well with: KCNA, KCSA, CBA, and OTCA

1.1 Declarative Resource Management (12 Qs)
    Q1:  What is Declarative Resource Management? Desired State vs Actual State
         ("I want 3 replicas" — NOT "start 3 pods, then check, then start more")
    Q2:  Declarative vs Imperative — why platforms MUST be declarative
         (anihpj deploy: kubectl apply -f deployment.yaml vs kubectl run)
    Q3:  Kubernetes manifests as declarative API objects
         (apiVersion, kind, metadata, spec, status — the universal K8s object structure)
    Q4:  kubectl apply vs kubectl create — declarative vs imperative commands
         (apply: "make it look like this"; create: "make one of these now")
    Q5:  YAML vs JSON for declarative configuration — why YAML won
         (Readability, comments, multi-line strings, anchors/references)
    Q6:  Infrastructure as Code (IaC) — declarative infrastructure with Tofu/Terraform
         (anihpj VPC provisioned via Terraform: resource "aws_vpc" "anihpj" {...})
    Q7:  Git as the single source of truth for declarative resources
         (All anihpj manifests in Git — the cluster is just a reflection of Git)
    Q8:  Drift Detection — when reality doesn't match declared state
         (Someone kubectl-edits a deployment → ArgoCD detects drift → auto-reverts)
    Q9:  Immutable Infrastructure — replacing, not patching
         (New anihpj version = new container image + new pod; never SSH to fix)
    Q10: Configuration as Code — ConfigMaps, Secrets, Helm values, Kustomize overlays
         (anihpj config per environment: dev/staging/prod in Git, not in cluster)
    Q11: Policy as Code — Kyverno, OPA/Gatekeeper for declarative governance
         (Policy: "All deployments must have resource limits" — enforced by code, not email)
    Q12: The Reconciliation Loop — Observe → Diff → Act (the heart of Kubernetes)
         (anihpj Deployment controller: wants 3, has 2 → creates 1 more pod)

1.2 DevOps Practices in Platform Engineering (12 Qs)
    Q13: What is DevOps? Culture, automation, measurement, sharing (CAMS)
         (DevOps = breaking the wall between Dev and Ops; Platform = the bridge)
    Q14: The "You Build It, You Run It" principle
         (anihpj team owns their app in production — platform enables, doesn't gatekeep)
    Q15: Shift-Left — moving quality, security, and testing earlier in the lifecycle
         (anihpj: lint in IDE → unit tests on commit → integration tests on PR → scan on push)
    Q16: Continuous Everything — CI, CD, CT (testing), CM (monitoring)
         (anihpj pipeline: every git push triggers build → test → scan → deploy)
    Q17: Blameless Culture — learning from failures without finger-pointing
         (anihpj outage → blameless postmortem → action items → improve platform)
    Q18: Feedback Loops — short cycles from idea to production to learning
         (anihpj deploys 5x/day; each deploy provides data on what works and what doesn't)
    Q19: Toil Reduction — automating repetitive manual work
         (Platform automates: DNS setup, TLS certs, DB provisioning, log collection)
    Q20: Collaboration Models — how platform teams and dev teams work together
         (Platform team builds IDP; anihpj dev team uses IDP to self-serve)
    Q21: Inner Source — applying open source practices within the organization
         (anihpj devs contribute improvements to platform shared libraries via PR)
    Q22: Platform as a Product — treating the IDP like a SaaS product
         (Define platform personas, user journeys, adoption metrics, NPS scores)
    Q23: Minimum Viable Platform (MVP) — start small, iterate fast
         (MVP: K8s namespace + CI/CD pipeline; iterate: add monitoring, Backstage, policies)
    Q24: Conway's Law and Platform Team Topologies
         (How team structures influence platform architecture — matching org to system design)

    Q25: Development Environments — local (minikube/kind), dev clusters, namespaces

    Q26: Environment Promotion — dev → staging → production pipeline
         (anihpj flow: merge to main → auto-deploy staging → manual approval → deploy prod)
    Q27: Infrastructure Environments — multi-cluster, multi-cloud, hybrid

    Q28: Containers vs Virtual Machines — when to use which

    Q29: Kubernetes as the Universal Control Plane — abstracting infrastructure

    Q30: Cluster API (CAPI) — managing K8s clusters with K8s

2.1 Observability Fundamentals: Traces, Metrics, Logs, and Events (10 Qs)
     Q73: The Three Pillars of Observability — Metrics, Logs, Traces (+ Events)
          (Metrics = what; Logs = why; Traces = where; Events = when something changed)
     Q74: Metrics — numerical measurements over time (Prometheus data model)
          (Counter: http_requests_total; Gauge: cpu_usage_percent; Histogram: request_duration_seconds)
     Q75: Logs — timestamped text records of application and system activity
          (anihpj-api log: {"ts":"2026-06-14T10:30:00Z","level":"info","msg":"GET /api/jobs 200 45ms"})
     Q76: Traces — following a request across multiple services (distributed tracing)
          (User → anihpj-web → anihpj-api → anihpj-db → Redis — trace shows each hop's latency)
     Q77: Events — discrete occurrences in the platform (auditable records)
          (K8s Events: Pod Scheduled, Image Pulled, Container Started, Health Check Failed)
     Q78: Prometheus — metrics collection, TSDB, PromQL, alerting
          (Scrape /metrics every 30s → store in TSDB → query: rate(errors[5m]) → alert if > threshold)
     Q79: Grafana — dashboards, panels, data sources, alerting, annotations
          (anihpj platform dashboard: request rate, error rate, latency, CPU, memory, pod status)
     Q80: OpenTelemetry (OTel) — unified standard for metrics, logs, traces
          (OTel Collector: receives → processes → exports to Prometheus/Loki/Jaeger)
     Q81: Loki — log aggregation with Prometheus-like query language (LogQL)
          (LogQL: {app="anihpj-api"} |= "ERROR" | json | line_format "{{.message}}")
     Q82: Jaeger / Tempo — distributed tracing backends
          (Jaeger UI: waterfall diagram showing each span — find the slowest service call)

2.2 Secure Service Communication (8 Qs)
     Q83: mTLS (Mutual TLS) — both client AND server verify certificates
          (anihpj-api → anihpj-db: both present certs signed by platform CA → mTLS handshake)
     Q84: cert-manager — automatic TLS certificate provisioning and renewal
          (cert-manager auto-issues TLS cert for anihpj.example.com via Let's Encrypt)
     Q85: Service Mesh mTLS — Istio/Linkerd automatic mTLS for all pod-to-pod traffic
          (Istio injects Envoy sidecar → all traffic auto-encrypted with mTLS — zero code changes)
     Q86: Network Policies — L3/L4 firewall between pods and namespaces
          (Policy: allow anihpj-web → anihpj-api:8000; deny all other ingress to anihpj-api)
     Q87: SPIFFE/SPIRE — workload identity for zero-trust networking
          (Every anihpj pod gets SPIFFE ID: spiffe://anihpj.io/ns/prod/sa/anihpj-api)
     Q88: Egress Controls — restricting outbound traffic from pods
          (anihpj pods can only egress to api.github.com, *.amazonaws.com, and anihpj-db)
     Q89: Ingress TLS — securing external traffic into the platform
          (NGINX Ingress + cert-manager: auto-TLS for all *.anihpj.example.com services)
     Q90: Secrets Management — Kubernetes Secrets, External Secrets Operator, Vault
          (anihpj DB password: stored in AWS Secrets Manager → ESO syncs to K8s Secret)

2.3 Policy Engines for Platform Governance (8 Qs)
     Q91: What is Policy-as-Code? Automating governance with machine-enforceable rules
          (Policy: "All deployments must have liveness probes" — enforced by engine, not email)
     Q92: Open Policy Agent (OPA) / Gatekeeper — Rego-based policy engine
          (Rego: deny[msg] { input.review.object.kind == "Pod"; not input.review.object.spec.containers[0].resources.limits })
     Q93: Kyverno — Kubernetes-native policy engine (no Rego required!)
          (Kyverno ClusterPolicy: "Add network policy to every new namespace" — generate rule)
     Q94: Kyverno Policy Types — Validate, Mutate, Generate, Verify Images
          (Validate: block pods without probes; Mutate: add default limits; Generate: auto-create NetworkPolicy)
     Q95: Admission Controllers — MutatingAdmissionWebhook, ValidatingAdmissionWebhook
          (Mutating webhook: inject Envoy sidecar; Validating webhook: reject privileged containers)
     Q96: Pod Security Standards (PSS) — Privileged, Baseline, Restricted
          (anihpj namespace enforces "restricted" PSS: no hostPath, no privileged, readOnlyRootFS)
     Q97: Pod Security Admission (PSA) — built-in K8s admission controller for PSS
          (Label namespace: pod-security.kubernetes.io/enforce=restricted → K8s enforces it)
     Q98: Policy Reporting — audit results, compliance dashboards, policy violations
          (Kyverno Policy Reports → Grafana dashboard → "3 namespaces have failing policies")

2.4 Kubernetes Security Essentials (8 Qs)
     Q99: The 4 C's of Cloud Native Security — Cloud, Cluster, Container, Code
          (Defense in depth: secure at EVERY layer — no single point of security failure)
     Q100: Authentication, Authorization, and Admission Control (AAA)
           (AuthN: Who are you? → AuthZ: What can you do? → Admission: Does this request comply?)
     Q101: RBAC — Role, ClusterRole, RoleBinding, ClusterRoleBinding
           (anihpj-dev role: get, list, create pods, deployments, services in anihpj-dev namespace)
     Q102: ServiceAccounts — identity for pods (each namespace has a "default" SA)
           (anihpj-api pod uses "anihpj-api-sa" SA — scoped to only DB access, no cluster-admin)
     Q103: Security Context — runAsNonRoot, runAsUser, fsGroup, capabilities, seccomp
