🔐 Lab 1: Configure cert-manager to Auto-Rotate TLS Certs

Scenario: Set up cert-manager to automatically issue and renew TLS certificates for anihpj-api using Let's Encrypt. Write the Issuer and Certificate manifests, and explain the ACME HTTP-01 challenge flow.

👁️ Show Solution
✅ cert-manager Configuration:
# ClusterIssuer — Let's Encrypt staging (test first!)
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-prod
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    email: platform@anihpj.io
    privateKeySecretRef:
      name: letsencrypt-account-key
    solvers:
    - http01:
        ingress:
          class: nginx
---
# Certificate — auto-issues and renews
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: anihpj-api-tls
  namespace: anihpj-production
spec:
  secretName: anihpj-api-tls-secret
  duration: 2160h       # 90 days (Let's Encrypt max)
  renewBefore: 360h     # Renew 15 days before expiry
  dnsNames:
  - api.anihpj.io
  - api-staging.anihpj.io
  issuerRef:
    name: letsencrypt-prod
    kind: ClusterIssuer

# ACME HTTP-01 Challenge Flow:
# 1. cert-manager creates a temporary Ingress (or uses existing)
# 2. cert-manager creates a temporary Pod serving a token
# 3. Let's Encrypt queries http://api.anihpj.io/.well-known/acme-challenge/{token}
# 4. Let's Encrypt validates → issues certificate
# 5. cert-manager stores cert in Secret: anihpj-api-tls-secret
# 6. Auto-renews 15 days before expiry

Explanation

cert-manager automates the entire TLS certificate lifecycle: issue, renew, and rotate. Without it, certificates expire silently → production outage. Key config: (1) `duration: 2160h` (90 days — Let's Encrypt max), (2) `renewBefore: 360h` (renew 15 days before expiry — safety margin), (3) ClusterIssuer is cluster-wide (shared by all namespaces). The CNPA tests cert-manager as a platform-level service — one Issuer serves all platform tenants.

🔒 Lab 2: Implement mTLS with Istio for anihpj

Scenario: Configure Istio service mesh to enforce STRICT mTLS between anihpj-api and anihpj-db. Write the PeerAuthentication and DestinationRule, and explain how Istio auto-injects sidecars.

👁️ Show Solution
✅ Istio mTLS Configuration:
# PeerAuthentication — enforce STRICT mTLS
apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication
metadata:
  name: anihpj-mtls-strict
  namespace: anihpj-production
spec:
  mtls:
    mode: STRICT    # Deny plaintext; require mTLS
---
# DestinationRule — client-side TLS settings
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: anihpj-db-mtls
  namespace: anihpj-production
spec:
  host: anihpj-db.anihpj-production.svc.cluster.local
  trafficPolicy:
    tls:
      mode: ISTIO_MUTUAL  # Use Istio-issued certs for mTLS

# How Istio injects sidecars:
# 1. Label namespace: istio-injection=enabled
# 2. Istio mutating webhook intercepts pod creation
# 3. Injects istio-proxy sidecar container into pod
# 4. Sidecar intercepts ALL traffic (iptables redirect)
# 5. Sidecar auto-discovers other services' certs via Istiod
# 6. mTLS handshake happens transparently — app code unchanged!

Explanation

mTLS with Istio provides transparent, zero-code-change encryption between services. STRICT mode rejects ANY plaintext connection — critical for PCI/HIPAA compliance. Key points: (1) PeerAuthentication = server-side ("require mTLS"), (2) DestinationRule = client-side ("use mTLS when connecting"), (3) ISTIO_MUTUAL uses Istio's own CA (auto-rotated), not cert-manager. The CNPA tests mTLS as a fundamental zero-trust platform capability.

🛡️ Lab 3: Design Zero-Trust NetworkPolicies for anihpj

Scenario: Implement zero-trust networking: (a) deny all traffic by default, (b) allow web → api on 8000, (c) allow api → db on 5432, (d) allow api → Redis on 6379, (e) allow monitoring namespace to scrape metrics, (f) deny all egress except to DNS and specific services. Write all NetworkPolicies.

👁️ Show Solution
✅ Zero-Trust NetworkPolicy Set:
# 1. Default DENY ALL (zero-trust baseline)
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-all
  namespace: anihpj-production
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  - Egress
---
# 2. Allow web → api (port 8000)
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-web-to-api
  namespace: anihpj-production
spec:
  podSelector: { matchLabels: { app: anihpj-api } }
  policyTypes: [Ingress]
  ingress:
  - from:
    - podSelector: { matchLabels: { app: anihpj-web } }
    ports:
    - protocol: TCP
      port: 8000
---
# 3. Allow api → db (port 5432)
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-api-to-db
spec:
  podSelector: { matchLabels: { app: anihpj-db } }
  policyTypes: [Ingress]
  ingress:
  - from:
    - podSelector: { matchLabels: { app: anihpj-api } }
    ports:
    - protocol: TCP
      port: 5432
---
# 4. Allow prometheus to scrape metrics
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-monitoring
spec:
  podSelector: {}
  policyTypes: [Ingress]
  ingress:
  - from:
    - namespaceSelector:
        matchLabels: { name: monitoring }
    ports:
    - protocol: TCP
      port: 8000
---
# 5. Allow egress to DNS only
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns-egress
spec:
  podSelector: {}
  policyTypes: [Egress]
  egress:
  - to:
    - namespaceSelector: {}
      podSelector:
        matchLabels: { k8s-app: kube-dns }
    ports:
    - protocol: UDP
      port: 53

Explanation

Zero-trust means DENY ALL by default, then ALLOW only what's needed. This is the opposite of traditional firewall thinking (allow all, deny bad). Key principles: (1) Default deny creates a security baseline, (2) Each allow rule is explicit and minimal (specific ports, specific sources), (3) Egress is ALSO controlled — compromised pods can't phone home. The CNPA tests NetworkPolicies as the fundamental K8s security primitive.

🔑 Lab 4: Implement External Secrets Operator

Scenario: anihpj-api needs DB credentials from AWS Secrets Manager. Configure External Secrets Operator to sync credentials into K8s Secrets, set up auto-refresh, and explain why this is better than storing secrets in Git (even encrypted with SOPS).

👁️ Show Solution
✅ External Secrets Operator:
# ClusterSecretStore — global reference to AWS
apiVersion: external-secrets.io/v1beta1
kind: ClusterSecretStore
metadata:
  name: aws-secrets-manager
spec:
  provider:
    aws:
      service: SecretsManager
      region: us-east-1
      auth:
        jwt:
          serviceAccountRef:
            name: eso-sa
            namespace: external-secrets
---
# ExternalSecret — sync specific secrets
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: anihpj-db-credentials
  namespace: anihpj-production
spec:
  refreshInterval: 1h          # Auto-refresh every hour
  secretStoreRef:
    name: aws-secrets-manager
    kind: ClusterSecretStore
  target:
    name: anihpj-db-secret
    creationPolicy: Owner      # ESO owns this K8s Secret
  data:
  - secretKey: DATABASE_URL
    remoteRef:
      key: /anihpj/production/database
      property: url
  - secretKey: DB_USER
    remoteRef:
      key: /anihpj/production/database
      property: username
  - secretKey: DB_PASSWORD
    remoteRef:
      key: /anihpj/production/database
      property: password
🔑 Why ESO > Encrypted Secrets in Git

• Rotation: ESO auto-refreshes when AWS rotates the secret. Git-based secrets are stale until someone manually updates.
• Single source of truth: Secrets live in AWS Secrets Manager — not scattered across Git repos.
• Access control: IAM controls who can read secrets. Git access ≠ secret access.
• Audit trail: CloudTrail logs every secret access. Git history shows who committed — not who READ the secret.

Explanation

ESO is the CNCF standard for secrets management in K8s. It synchronizes external secrets INTO K8s Secrets (pods still use native Secret mounts). Key design: (1) ClusterSecretStore = shared across namespaces, (2) IRSA (IAM Roles for Service Accounts) = no static AWS credentials, (3) `refreshInterval: 1h` = automatic rotation. The CNPA tests ESO as the platform-grade secrets solution — better than sealed-secrets, SOPS, or Vault sidecars for most use cases.

🔍 Lab 5: Audit K8s Secrets Security

Scenario: Audit the current anihpj setup for secrets vulnerabilities. You find: (a) Secrets stored as base64 in Git (!), (b) Secrets mounted as environment variables (visible in `docker inspect`), (c) No etcd encryption at rest. For each issue, explain the risk and provide the fix.

👁️ Show Solution
✅ Secrets Security Audit & Remediation:
FindingRiskFixSeverity
Secrets in Git (base64)Anyone with repo access can decode: echo cGFzc3dvcmQ= | base64 -d → password. Former employees, contractors, CI systems all have access.Use ESO to sync from AWS Secrets Manager. Remove all secrets from Git. Add gitleaks pre-commit hook.🔴 Critical
Secrets as env varsEnv vars visible in: docker inspect, kubectl describe pod (if envFrom), crash dumps, child processes, linked libraries.Mount secrets as FILES (tmpfs): secretKeyRef→items: - key: password, path: db_password. App reads from file.🟡 Medium
No etcd encryptionAnyone with etcd access (cluster admin) can read all secrets in plaintext. Cloud provider storage snapshots contain unencrypted secrets.Enable etcd encryption at rest: EncryptionConfiguration with aescbc provider. Use KMS plugin for production.🟡 Medium

Explanation

The CNPA tests secrets security comprehensively. Key principles: (1) NEVER store secrets in Git — not even encrypted. Git is an immutable append-only log; "deleting" a secret doesn't remove it from history. (2) Secrets as files > secrets as env vars — files are not inherited by child processes, not visible in /proc, and can have file permissions. (3) etcd encryption protects data at rest — without it, a compromised etcd backup exposes ALL secrets.

🌐 Lab 6: Configure Ingress with TLS Termination

Scenario: Set up an Nginx Ingress for anihpj-api with: TLS termination (using the cert-manager certificate), path-based routing (/api/* → anihpj-api, /admin/* → anihpj-admin), rate limiting, and CORS headers.

👁️ Show Solution
✅ TLS Ingress Configuration:
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: anihpj-api-ingress
  namespace: anihpj-production
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt-prod
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
    nginx.ingress.kubernetes.io/rate-limit: "100"
    nginx.ingress.kubernetes.io/rate-limit-burst: "50"
    nginx.ingress.kubernetes.io/enable-cors: "true"
    nginx.ingress.kubernetes.io/cors-allow-origin: "https://anihpj.io"
    nginx.ingress.kubernetes.io/proxy-body-size: "10m"
spec:
  ingressClassName: nginx
  tls:
  - hosts:
    - api.anihpj.io
    secretName: anihpj-api-tls-secret   # Created by cert-manager
  rules:
  - host: api.anihpj.io
    http:
      paths:
      - path: /api/
        pathType: Prefix
        backend:
          service:
            name: anihpj-api
            port:
              number: 8000
      - path: /admin/
        pathType: Prefix
        backend:
          service:
            name: anihpj-admin
            port:
              number: 8001

Explanation

Ingress with TLS termination is the entry point for external traffic. Key config: (1) `ssl-redirect: true` forces HTTPS, (2) `rate-limit` prevents DDoS (100 req/s per IP), (3) `enable-cors` allows frontend from anihpj.io, (4) cert-manager annotation auto-provisions TLS. The Ingress terminates TLS (decrypts) and forwards plaintext to backend services (which is fine if mTLS is configured internally). The CNPA tests Ingress as the platform's external security boundary.

🔐 Lab 7: Implement Pod Security Admission (PSA)

Scenario: Apply Pod Security Admission to enforce: (a) production namespace = "restricted" (no privileged, no host networking, must run as non-root), (b) dev namespace = "baseline" (warns on known privilege escalations). Write the namespace labels and explain the 3 PSA levels.

👁️ Show Solution
✅ Pod Security Admission:
# Production namespace — RESTRICTED (strictest)
apiVersion: v1
kind: Namespace
metadata:
  name: anihpj-production
  labels:
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/enforce-version: v1.29
    pod-security.kubernetes.io/audit: restricted
    pod-security.kubernetes.io/warn: restricted
---
# Dev namespace — BASELINE (warns only)
apiVersion: v1
kind: Namespace
metadata:
  name: anihpj-dev
  labels:
    pod-security.kubernetes.io/enforce: baseline
    pod-security.kubernetes.io/warn: restricted  # Warn if could be restricted
LevelDescriptionBlocksUse Case
PrivilegedUnrestricted. Everything allowed.NothingSystem namespaces (kube-system), CI/CD runners
BaselinePrevents known privilege escalationshostNetwork, hostPID, privileged containers, hostPath volumesDev/staging namespaces. Minimum for any workload.
RestrictedBest-practice pod hardeningAll baseline + runAsNonRoot, seccomp, capability drops, restricted volume typesProduction workloads. CNPA recommended.

Explanation

PSA is K8s' built-in pod security (replacing PSP). It's simpler, namespace-scoped, and enforced by the API server (not a webhook). Key modes: `enforce` = reject, `audit` = log only, `warn` = show warning. The CNPA tests PSA levels: Restricted is the target for production (enforces non-root, readonly rootfs, seccomp, etc.). Dev can use Baseline as a stepping stone to Restricted.

📜 Lab 8: Implement Egress Gateway for API Calls

Scenario: anihpj-api needs to call an external payment API (https://payments.example.com). Configure an Istio Egress Gateway to allow ONLY this domain, enforce TLS origination, and log all egress traffic.

👁️ Show Solution
✅ Istio Egress Gateway:
# ServiceEntry — register external service in Istio mesh
apiVersion: networking.istio.io/v1beta1
kind: ServiceEntry
metadata:
  name: payments-external
spec:
  hosts:
  - payments.example.com
  ports:
  - number: 443
    name: tls
    protocol: TLS
  location: MESH_EXTERNAL
  resolution: DNS
---
# Gateway — egress listener
apiVersion: networking.istio.io/v1beta1
kind: Gateway
metadata:
  name: istio-egress-gateway
spec:
  selector:
    istio: egressgateway
  servers:
  - port:
      number: 443
      name: tls
      protocol: TLS
    hosts:
    - payments.example.com
    tls:
      mode: PASSTHROUGH
---
# VirtualService — route through egress gateway
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: payments-egress
spec:
  hosts:
  - payments.example.com
  gateways:
  - mesh               # Internal mesh
  - istio-egress-gateway  # External egress
  tls:
  - match:
    - port: 443
      sniHosts:
      - payments.example.com
    route:
    - destination:
        host: payments.example.com
        port:
          number: 443
---
# Sidecar — restrict egress to ONLY egress gateway
apiVersion: networking.istio.io/v1beta1
kind: Sidecar
metadata:
  name: anihpj-api-sidecar
  namespace: anihpj-production
spec:
  workloadSelector:
    labels:
      app: anihpj-api
  egress:
  - hosts:
    - "./*"                    # Services in same namespace
    - "istio-system/*"         # Egress gateway
  outboundTrafficPolicy:
    mode: REGISTRY_ONLY        # Block ANY traffic not in ServiceEntry

Explanation

Egress gateways provide controlled, audited external access. Without it, any pod can call any external API (data exfiltration risk). REGISTRY_ONLY mode means pods can ONLY reach services registered in Istio (internal mesh + ServiceEntries). Key pattern: ALL egress traffic flows through a centralized egress gateway → logged → monitored. The CNPA tests egress control as a platform security capability.

🔑 Lab 9: Implement IRSA for Pod-to-AWS Authentication

Scenario: anihpj-api needs to access S3 and DynamoDB. Configure IRSA (IAM Roles for Service Accounts) so pods authenticate to AWS without static credentials.

👁️ Show Solution
✅ IRSA Configuration:
# Step 1: Create ServiceAccount with IAM role annotation
apiVersion: v1
kind: ServiceAccount
metadata:
  name: anihpj-api-sa
  namespace: anihpj-production
  annotations:
    eks.amazonaws.com/role-arn: arn:aws:iam::123456789:role/anihpj-api-role
---
# Step 2: Deployment uses the ServiceAccount
apiVersion: apps/v1
kind: Deployment
metadata:
  name: anihpj-api
spec:
  template:
    spec:
      serviceAccountName: anihpj-api-sa  # <-- THIS enables IRSA
      containers:
      - name: api
        image: anihpj/jobpost-api:v1.2.3
        env:
        - name: AWS_REGION
          value: us-east-1
        # NO AWS_ACCESS_KEY_ID or AWS_SECRET_ACCESS_KEY!
# Step 3: Terraform — IAM Role with OIDC trust
resource "aws_iam_role" "anihpj_api" {
  name = "anihpj-api-role"
  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect = "Allow"
      Principal = {
        Federated = aws_iam_openid_connect_provider.eks.arn
      }
      Action = "sts:AssumeRoleWithWebIdentity"
      Condition = {
        StringEquals = {
          "${replace(aws_iam_openid_connect_provider.eks.url, "https://", "")}:sub" = "system:serviceaccount:anihpj-production:anihpj-api-sa"
        }
      }
    }]
  })
}

Explanation

IRSA eliminates static AWS credentials from K8s. How it works: (1) Pod's ServiceAccount has an IAM role ARN annotation, (2) EKS injects a projected ServiceAccount token (JWT) into the pod, (3) AWS SDK exchanges the JWT for temporary IAM credentials via STS, (4) Credentials auto-rotate (default 1 hour). No access keys, no secret files, no vault. The CNPA tests IRSA as the CNCF-recommended K8s-to-cloud authentication pattern.
