🏗️ Lab 1: Build a CI Pipeline from Scratch

Scenario: Build a complete CI pipeline (GitHub Actions) for anihpj-api that: lints (flake8), type-checks (mypy), unit tests (pytest with coverage > 80%), SAST (Bandit), builds a multi-arch image (amd64 + arm64), scans with Trivy, signs with Cosign, and pushes to GHCR. Write the full workflow and explain each stage's purpose.

👁️ Show Solution
✅ Production-Grade CI Pipeline:
name: CI Pipeline
on:
  push: { branches: [main] }
  pull_request: { branches: [main] }

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}

jobs:
  # STAGE 1: Code Quality (runs first — fail fast!)
  lint-and-typecheck:
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v4
    - uses: actions/setup-python@v5
      with: { python-version: '3.12' }
    - run: pip install flake8 mypy
    - run: flake8 anihpj/ jobpost/ --max-line-length=120
    - run: mypy anihpj/ jobpost/ --strict

  # STAGE 2: Security Scan + Tests (parallel for speed)
  security-and-tests:
    needs: lint-and-typecheck
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:16
        env: { POSTGRES_DB: test, POSTGRES_PASSWORD: test }
    steps:
    - uses: actions/checkout@v4
    - run: pip install -r requirements.txt
    - run: pip install bandit pytest pytest-cov
    - run: bandit -r anihpj/ -ll    # SAST
    - run: pytest --cov=./ --cov-report=xml --cov-fail-under=80

  # STAGE 3: Build + Scan + Sign + Push (only on main)
  build-and-publish:
    needs: security-and-tests
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
      id-token: write  # For Cosign keyless signing
    steps:
    - uses: actions/checkout@v4
    - uses: docker/setup-buildx-action@v3
    - uses: docker/login-action@v3
      with:
        registry: ghcr.io
        username: ${{ github.actor }}
        password: ${{ secrets.GITHUB_TOKEN }}
    - uses: docker/metadata-action@v5
      id: meta
      with:
        images: ghcr.io/${{ github.repository }}
        tags: type=sha,type=ref,event=branch
    - uses: docker/build-push-action@v5
      with:
        push: true
        platforms: linux/amd64,linux/arm64
        tags: ${{ steps.meta.outputs.tags }}
        labels: ${{ steps.meta.outputs.labels }}
        cache-from: type=gha
        cache-to: type=gha,mode=max
    - run: |
        curl -sSfL https://raw.githubusercontent.com/aquasecurity/trivy/main/contrib/install.sh | sh
        trivy image --severity HIGH,CRITICAL ghcr.io/${{ github.repository }}:${{ github.sha }}
    - uses: sigstore/cosign-installer@v3
    - run: cosign sign --yes ghcr.io/${{ github.repository }}@${{ steps.build.outputs.digest }}

Explanation

This is a CNPA-grade CI pipeline. Key design decisions: (1) Fail fast: lint first (cheapest, catches syntax/style issues instantly). (2) Parallel stages: security + tests run simultaneously after lint passes. (3) Multi-arch builds: linux/amd64 AND arm64 for Graviton cost savings. (4) Keyless signing: Cosign uses OIDC (GitHub's identity), no private key management. (5) Cache: GitHub Actions cache (`gha`) speeds up builds 3-5x.

👁️ Show Solution
✅ Testing Trophy Implementation:
🔺 Old: Testing Pyramid (400 tests, 45 min)

• 250 unit tests (mock everything) — 63%
• 120 integration tests — 30%
• 30 E2E tests — 7%
Problem: Unit tests pass but DB migrations fail in staging. Mocks hide real integration issues.

🏆 New: Testing Trophy (350 tests, 12 min)

• Static analysis (ruff, mypy, bandit) — catches 40% of bugs BEFORE runtime
• 180 integration tests (real PostgreSQL, real Redis) — 51%
• 100 unit tests (pure logic only) — 29%

# pytest.ini — Test configuration for Testing Trophy
[pytest]
testpaths = tests/
python_files = test_*.py
addopts = 
    --strict-markers
    --tb=short
    -n auto                # Parallel execution
    --dist loadscope

markers =
    unit: Pure logic tests (no DB, no network)
    integration: Tests with real PostgreSQL, Redis
    contract: API contract tests (schemas, responses)
    e2e: End-to-end critical user journeys
    
# Run: pytest -m "unit"         (fast, pre-commit)
# Run: pytest -m "integration"  (CI, with service containers)
# Run: pytest -m "e2e"          (staging only, nightly)

Explanation

The Testing Trophy (Kent C. Dodds) is the CNPA-recommended approach for cloud-native applications. Why? In K8s, integration points (DB connections, network policies, service discovery) are the most common failure modes — and unit tests with mocks completely miss them. Static analysis catches bugs before runtime. Integration tests with real dependencies catch infrastructure issues. The platform provides test infrastructure (PostgreSQL service containers, Redis) so developers write integration tests by default.

🔐 Lab 4: Implement Supply Chain Security (SLSA Level 3)

Scenario: Harden the anihpj CI pipeline to achieve SLSA Level 3 (auditable, non-falsifiable provenance). Implement: hermetic builds, signed provenance, SBOM generation, and verification.

👁️ Show Solution
✅ SLSA Level 3 Implementation:
# SLSA Level 3 requires: isolated builds + signed provenance + verified dependencies
steps:
# 1. Generate SBOM (Software Bill of Materials)
- uses: anchore/sbom-action@v0
  with:
    path: ./
    format: spdx-json
    output-file: sbom.spdx.json

# 2. Build with SLSA provenance generator (hermetic, isolated)
- uses: slsa-framework/slsa-github-generator/.github/workflows/builder_docker-based_slsa3.yml@v2
  with:
    builder-image: 'ghcr.io/slsa-framework/slsa-builder-go:v2'
    private-repository: true

# 3. Attestation — signed, non-falsifiable provenance
- uses: slsa-framework/slsa-github-generator/actions/generate-provenance@v2
  with:
    base64-subjects: "${{ needs.build.outputs.image-digest }}"

# 4. Verify provenance before deployment
- name: Verify SLSA provenance
  run: |
    cosign verify-attestation \
      --type slsaprovenance \
      --certificate-oidc-issuer https://token.actions.githubusercontent.com \
      ghcr.io/anihpj/jobpost-api@${{ steps.build.outputs.digest }}

# SLSA LEVEL CHECKLIST:
# ✅ Level 1: Build scripted (GitHub Actions = scripted)
# ✅ Level 2: Build service + signed provenance (SLSA generator)
# ✅ Level 3: Isolated/hermetic + non-falsifiable (SLSA builder)
# ⬜ Level 4: Two-person review + hermetic + reproducible

Explanation

SLSA (Supply-chain Levels for Software Artifacts) is the industry standard for supply chain security. Level 3 means: (1) Builds are isolated (no network access during build), (2) Provenance is signed and non-falsifiable (you can't forge who built it), (3) SBOM generated. The CNPA tests supply chain security because platforms are responsible for the integrity of everything that flows through CI/CD.

👁️ Show Solution
✅ Artifact Promotion Pipeline:
📦 anihpj Artifact Promotion Flow
CI BUILD (once!)          PROMOTE (copy, never rebuild)
┌──────────────┐         ┌──────────────┐         ┌──────────────┐
│  Build Image  │  push   │  Dev Registry │  promote │ Stg Registry │
│  sha-abc123   │────────→│  sha-abc123   │────────→│  sha-abc123   │
│  (immutable)  │         │  + dev tag    │         │  + staging tag│
└──────────────┘         └──────┬───────┘         └──────┬───────┘
                                │                        │
                                │ tests pass             │ UAT passes
                                │                        │
                                │                  ┌─────▼─────────┐
                                │                  │  Prod Registry │
                                └──────────────────│  sha-abc123    │
                                   promote          │  + v1.2.3 tag  │
                                                    │  + stable tag  │
                                                    └────────────────┘

# Promotion is a COPY operation, NOT a rebuild:
skopeo copy docker://ghcr.io/anihpj/jobpost-api:sha-abc123 \
            docker://ghcr.io/anihpj/jobpost-api:staging

# NEVER do this (rebuilds — different binary):
# docker build -t anihpj/jobpost-api:staging .  ❌

Explanation

Artifact promotion means the EXACT same bytes move through environments. If you rebuild for staging, you get a DIFFERENT binary — different timestamps, different layer hashes, different behavior. Promotion tools (skopeo, crane, or registry-native) COPY the manifest — they don't rebuild. This is the "build once, deploy many" principle and is a fundamental CNPA concept.

🗂️ Lab 7: Implement Monorepo CI Strategy

Scenario: anihpj is moving to a monorepo with 3 services (api/, web/, worker/) plus shared libraries (lib/). Design a CI strategy that: only builds changed services, caches shared dependencies, and enables independent deployment.

👁️ Show Solution
✅ Monorepo CI Strategy:
# Path-based filtering — only trigger affected services
name: Monorepo CI
on:
  pull_request:
    paths:
    - 'api/**'          # Only api changes
    - 'lib/**'          # Shared lib changes → build everything

jobs:
  detect-changes:
    runs-on: ubuntu-latest
    outputs:
      api: ${{ steps.filter.outputs.api }}
      web: ${{ steps.filter.outputs.web }}
      worker: ${{ steps.filter.outputs.worker }}
    steps:
    - uses: dorny/paths-filter@v3
      id: filter
      with:
        filters: |
          api: ['api/**', 'lib/**']
          web: ['web/**', 'lib/**']
          worker: ['worker/**', 'lib/**']

  # Each job runs ONLY if its path changed
  test-api:
    needs: detect-changes
    if: needs.detect-changes.outputs.api == 'true'
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v4
    - run: cd api && pytest
    - run: |
        docker build -f api/Dockerfile -t anihpj-api:${{ github.sha }} .
        docker push anihpj-api:${{ github.sha }}

  test-web:
    needs: detect-changes
    if: needs.detect-changes.outputs.web == 'true'
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v4
    - run: cd web && npm test
    - run: |
        docker build -f web/Dockerfile -t anihpj-web:${{ github.sha }} .
        docker push anihpj-web:${{ github.sha }}

Explanation

Monorepo CI uses path-based triggers to avoid rebuilding unchanged services. Key design: (1) `lib/**` triggers ALL services (shared code affects everything), (2) Each service has its own Dockerfile and test suite, (3) Independent deployment — api can deploy without rebuilding web. This is the CNPA-recommended pattern for monorepo platforms: one repo, many services, selective CI.

🔄 Lab 9: Implement Auto-Merge for Dependabot PRs

Scenario: Dependabot opens 15 PRs/week for anihpj. Design an auto-merge pipeline that: auto-approves minor/patch updates if CI passes, requires manual review for major updates, and auto-rolls back if staging deployment fails after merge.

👁️ Show Solution
✅ Auto-Merge Policy for Dependencies:
# .github/dependabot.yml
version: 2
updates:
- package-ecosystem: pip
  directory: "/"
  schedule: { interval: weekly }
  open-pull-requests-limit: 10
  labels: [dependencies]
  
- package-ecosystem: docker
  directory: "/api"
  schedule: { interval: weekly }

# .github/workflows/auto-merge.yml
name: Auto-Merge Dependabot
on: { pull_request: { types: [opened, synchronize] } }
permissions:
  pull-requests: write
  contents: write

jobs:
  auto-merge:
    if: github.actor == 'dependabot[bot]'
    runs-on: ubuntu-latest
    steps:
    - name: Determine update type
      id: semver
      run: |
        # Parse version bump from PR title
        if [[ "${{ github.event.pull_request.title }}" =~ major ]]; then
          echo "auto_merge=false" >> $GITHUB_OUTPUT
        else
          echo "auto_merge=true" >> $GITHUB_OUTPUT
        fi
    - name: Auto-approve minor/patch
      if: steps.semver.outputs.auto_merge == 'true'
      run: gh pr review --approve "$PR_URL"
      env:
        PR_URL: ${{ github.event.pull_request.html_url }}
        GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
    - name: Auto-merge if CI passes
      if: steps.semver.outputs.auto_merge == 'true' && success()
      run: gh pr merge --auto --squash "$PR_URL"

Explanation

Auto-merging dependency updates reduces platform maintenance toil. Key safety: (1) Only minor/patch updates auto-merge (major = breaking changes = manual review), (2) CI must pass (tests + security scan), (3) Staging deployment verifies the update before production. If staging fails after merge, the platform auto-rolls back. This is platform engineering at scale — automating the boring so humans focus on the important.
