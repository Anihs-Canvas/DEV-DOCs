PRE-LEARNING: BACKSTAGE & DEVELOPER PORTAL FOUNDATIONS (Novice Foundation)
═══════════════════════════════════════════════════════════════════════
Before diving into the exam domains, this section builds your mental model
of what Backstage IS, why it exists, and how it revolutionizes developer
experience. Essential for novices; useful refresher for everyone.

F.1 What Problem Does Backstage Solve? — The Developer Experience Crisis
    • The "Tool Sprawl" nightmare — 15+ tools, zero integration, 10+ logins
    • Cognitive load on developers — "Where's my service? How do I deploy?"
    • Onboarding takes weeks, not days — the true cost of fragmented tools
    • The Spotify origin story — 1,000+ engineers, 10,000+ components, chaos
    • How Spotify created Backstage internally, then donated it to CNCF in 2020
    • anihpj BEFORE Backstage: scattered GitHub repos, Jira tickets, Confluence
      pages, Grafana dashboards, PagerDuty alerts — all disconnected islands
    • The "single pane of glass" vision — ONE URL to rule them all
    🟢 Novice

F.2 What Is an Internal Developer Portal (IDP)?
    • Definition: A unified interface that connects all your infrastructure,
      tooling, and documentation into one cohesive developer experience
    • The difference between an IDP and individual DevOps tools
    • Software Catalog — the beating heart: every service, API, resource, team
    • Software Templates — golden paths to production: "one click to a new service"
    • TechDocs — documentation that lives WITH your code (Markdown → portal)
    • Plugins — the extensibility superpower: connect any tool via plugins
    • How anihpj benefits: one place for jobpost-api, jobpost-web, postgres-db,
      redis, API docs, CI/CD status, Grafana dashboards, and Sentry errors
    🟢 Novice

F.3 Backstage Architecture — The Big Picture
    • Frontend: React + TypeScript + Material-UI component library
    • Backend: Node.js + Express.js API server
    • Plugin Architecture: frontend plugins (React components) + backend plugins
      (Express routers + services)
    • Database: PostgreSQL (production) or SQLite (development)
    • app-config.yaml — the central configuration hub for EVERYTHING
    • The Scaffolder — template execution engine (fetch skeleton → run actions)
    • Search engine integration (Elasticsearch or PostgreSQL-backed search)
    • Layered architecture diagram: Frontend ↔ Plugin API ↔ Backend ↔ DB ↔ External
    • How anihpj runs on this architecture: catalog entities for every service
    🟢 Novice

F.4 The anihpj/jobpost Application Stack — The App Under Management
    • Web tier (Django templates + static files) — anihpj-web (Component)
    • API tier (Django REST Framework) — anihpj-api (Component)
    • Database tier (PostgreSQL 15) — anihpj-db (Resource)
    • Redis (Celery task queue + caching) — anihpj-redis (Resource)
    • How these are modeled in Backstage's entity hierarchy:
      Domain: anihpj → System: JobPost → Components: jobpost-api, jobpost-web
      → Resources: postgres-db, redis-cache → APIs: jobpost-api (OpenAPI spec)
    • Complete file tree diagram of the Django project
    • Dockerfile: multi-stage Python build, distroless runtime, non-root user
    • Kubernetes manifests: all 14 YAML files in the k8s/ directory
    • catalog-info.yaml for each component — how they register in the catalog

1.3 Backstage Architecture Deep Dive (14 Qs)
    Q17: What programming language/framework is Backstage's FRONTEND built with?
         (React + TypeScript + Material-UI v5)
    Q18: What programming language/framework is Backstage's BACKEND built with?
         (Node.js + Express.js + TypeScript)
    Q19: What is the Backstage database abstraction layer? (Knex.js query builder —
         supports PostgreSQL and SQLite out of the box)
    Q20: What database does Backstage use in production? In development? (Production:
         PostgreSQL. Development: SQLite by default, can also use PostgreSQL)
    Q21: What is the role of app-config.yaml in Backstage? (Central configuration hub
         for database, auth, catalog providers, plugins, proxy, and all integrations)
    Q22: How does Backstage handle environment-specific configuration? (app-config.yaml
         for base config + app-config.production.yaml / app-config.development.yaml
         for overrides. Environment variables take highest precedence)
    Q23: What is the monorepo structure of a Backstage project? (packages/app = frontend,
         packages/backend = backend, plugins/ = custom plugins. Managed by yarn workspaces
         or Lerna)
    Q24: What is the Plugin API and what are its two halves? (createPlugin() for frontend
         plugins (React components) + createBackendPlugin() for backend plugins (Express
         routers + services). Plugins can have BOTH frontend and backend pieces)
    Q25: How does Backstage's frontend routing work? (React Router-based. Each plugin
         registers routes via createRoutableExtension(). The app shell mounts them)
    Q26: What component library does Backstage use for its UI? (Material-UI v5 (MUI)
         with Backstage's own design system on top — Backstage Theme)
    Q27: How does Backstage's backend handle plugin registration? (Backend plugins
         are loaded via createBackend() with feature detection. Each plugin exports
         a function that receives the logger, database, and router)
    Q28: What is the Backstage Scaffolder? (Template execution engine that fetches a
         skeleton, runs a series of actions, and publishes the result — e.g., creates
         a new GitHub repo from a template)
    Q29: How does Backstage Search work? (Search platform with pluggable backends:
         Elasticsearch or PostgreSQL. Each plugin can register collators that feed
         search indices. Results appear in the global search bar)
    Q30: What is the Catalog Processing Loop? (Continuous cycle: fetch entity from
         location → parse YAML → validate schema → enrich with annotations → stitch
         relationships → store in database. Runs on a schedule and on-demand)

2.1 Entity Model — The Building Blocks (8 Qs)
    Q71: What are the 7 standard entity Kinds in Backstage? (Component, API, Resource,
         System, Domain, User, Group — plus Template as the 8th special kind)
    Q72: What is a "Component" in Backstage? (A piece of software — a service, website,
         library, mobile app, data pipeline. In anihpj: jobpost-api, jobpost-web,
         jobpost-worker are all Components)
    Q73: What is an "API" entity in Backstage? (An API boundary — defined by an API
         specification like OpenAPI, AsyncAPI, gRPC, GraphQL. In anihpj: jobpost-api
         (OpenAPI spec at /api/schema/))
    Q74: What is a "Resource" in Backstage? (Infrastructure that Components depend on —
         databases, caches, queues, buckets, CDNs. In anihpj: postgres-db, redis-cache,
         s3-bucket)
    Q75: What is the difference between a "System" and a "Domain" in Backstage?
         (System = a collection of Components + Resources that work together (e.g.,
         "JobPost System"). Domain = a collection of related Systems (e.g., "anihpj"
         Domain). Domain is the highest-level grouping)
    Q76: What are "User" and "Group" entities? (User = an individual person in your org.
         Group = a team, squad, or department. Used for ownership. In anihpj:
         Group: "anihpj-team" owns Components, User: individual developers)
    Q77: How do entity relationships work in Backstage? (dependsOn, providesApis,
         consumesApis, partOf (reverse: hasPart), ownedBy (reverse: ownerOf).
         These create a directional graph of dependencies visible on entity pages)
    Q78: What does the "lifecycle" field on an entity indicate? (The maturity stage:
         experimental → production → deprecated. Affects catalog visibility and
         can be used for filtering. Production = fully supported, Deprecated = on
         the way out)

2.2 catalog-info.yaml — Entity Definition (8 Qs)
    Q79: What is catalog-info.yaml and where does it live? (The YAML file that defines
         an entity. Lives in the root of a Git repository. Backstage discovers it
         to register the entity in the catalog)
    Q80: What are the 4 required top-level fields in catalog-info.yaml? (apiVersion:
         backstage.io/v1alpha1, kind: <entity-kind>, metadata: {name, ...},
         spec: {type, lifecycle, owner, ...})
    Q81: What goes in the metadata section of catalog-info.yaml? (name (unique in
         namespace), namespace (default: "default"), title, description, labels
         (key-value tags), annotations (backstage-specific metadata like GitHub URL,
         TechDocs path), tags (simple string list), links)
    Q82: What goes in the spec section of a Component entity? (type: service/website/
         library, lifecycle: experimental/production/deprecated, owner: group-name,
         system (optional), subcomponentOf (optional), dependsOn, providesApis,
         consumesApis)
    Q83: What is the "type" field in a Component spec? (The kind of component: service
         (backend/frontend), website, library, cli, mobile-app, data-pipeline.
         Backstage uses this to display the appropriate icon and grouping)
    Q84: What are common annotations used on entities? (backstage.io/view-url → GitHub
         source link. backstage.io/edit-url → GitHub edit link. backstage.io/techdocs
         -ref → path to TechDocs. github.com/project-slug → org/repo. backstage.io
         /ldap-rdn → LDAP reference. pagerduty.com/integration-key → PagerDuty)
    Q85: How do you write a catalog-info.yaml for a Django service like jobpost-api?

2.3 Catalog Ingestion — How Entities Get Into Backstage (8 Qs)
    Q87: What are the 3 main paths for getting entities into the Catalog? (1. Static
         Location — direct URL to catalog-info.yaml. 2. Discovery Providers — GitHub/
         GitLab/Bitbucket auto-scan repos. 3. Manual Registration — paste URL in
         Backstage UI's "Register Existing Component" page)
    Q88: What is a "Location" entity? (kind: Location — points to where entity YAML
         files can be found. Types: url (remote URL), file (local path). The catalog
         reads locations to discover and ingest entities)
    Q89: How does GitHub Discovery work? (Configure organization in app-config.yaml
         under catalog.providers.github. Backstage scans ALL repos in the org looking
         for catalog-info.yaml files. Found entities are auto-registered. Runs on
         a configurable schedule)
    Q90: How do you configure GitHub Discovery for the anihpj organization? (In
         app-config.yaml: catalog.providers.github.anihpjOrg.organization: 'anihpj'.
         schedule: {frequency: {minutes: 30}, timeout: {minutes: 3}}. Requires
         a GitHub token or GitHub App with repo read permissions)
    Q91: What is the Catalog Processing Loop? (Continuous process: 1. Fetch entity
         YAML from location. 2. Parse YAML → entity object. 3. Validate against
         schema. 4. Enrich with processor-added annotations. 5. Stitch — resolve
         cross-entity references (dependsOn, ownedBy). 6. Store in database)
    Q92: What happens when Backstage encounters invalid catalog-info.yaml? (Entity
         processing fails with a clear error message. The entity appears in the
         catalog with an error state. Original source stays unchanged. Fix the
         YAML in the repo → Backstage re-ingests on next cycle)
    Q93: What is entity "stitching"? (The process of resolving cross-entity references
         AFTER all entities are loaded. E.g., when jobpost-api says "dependsOn:
         resource:postgres-db", stitching resolves this to the actual postgres-db
         entity and creates the bidirectional relationship)
    Q94: How often does the Catalog refresh? (Default: every 100 seconds for location
         refresh. GitHub Discovery runs on the configured schedule (e.g., every
         30 minutes). Manual refresh can be triggered via Backstage UI or API)

2.5 Catalog Advanced — Entity Processing & Policies (8 Qs)
    Q103: What are Catalog Processors? (Plugins that transform raw YAML into entities.
          Built-in processors handle GitHub discovery, location reading, YAML parsing,
          schema validation, and relationship stitching. Custom processors can
          add logic: auto-label, validate naming conventions, enforce policies)
    Q104: What is the Catalog ingestion schedule? (Default: entities refresh every
          100 seconds. Discovery providers refresh on their own schedule (e.g.,
          30 minutes). Can be configured in app-config.yaml under catalog.providers
          .<provider>.schedule)
    Q105: How does the Catalog handle duplicate entities? (An entity is uniquely
           identified by <kind>:<namespace>/<name>. If two locations define the
           same entity, the first one processed wins. Subsequent ones log warnings)
    Q106: What are Catalog Rules? (Allow/deny rules in app-config.yaml under
           catalog.rules. Control which entities are accepted: allow [Component,
           API, Resource], deny [Template] from certain locations)
    Q107: How does the Catalog handle large organizations (10,000+ entities)?
           (Pagination, incremental processing, database indexing. Search indexing
           via Elasticsearch for performance. Location refresh can be staggered.
           Catalog database can be read-replica scaled)
    Q108: What happens when a catalog-info.yaml is deleted or moved? (If the location
           becomes unreachable (404), the entity is marked as "orphaned". After a
           grace period (configurable), orphaned entities are removed from the catalog.
           This prevents stale entities from persisting forever)
    Q109: How do you add custom metadata validations for entities? (Create a custom
           Catalog Processor. Implement validateEntityKind() method. Check for
           required annotations, naming conventions, owner existence. Return
           validation errors that appear on the entity page)
    Q110: How do you set up a multi-tenant Catalog? (Use namespaces to segment
           entities by team/business-unit. Each namespace can have its own
           discovery provider. RBAC controls who can see which namespace)

    Q122: How does catalog:register work in a template? (After code is generated

          in the newly created repo. Makes the entity immediately visible)
    Q123: How do you create a custom Scaffolder action? (Create a new package:
          yarn backstage-cli plugin:create. Implement createTemplateAction() with

          function that does the work). Register it in the scaffolder backend)
    Q124: What is the scaffolder-backend-module-kubernetes? (A built-in module
          that adds Kubernetes-related actions: kubernetes:apply (apply manifests

          to directly deploy to K8s as part of scaffolding)
    Q125: How do you write a complete Template YAML for "Create Django Service"?
          (kind: Template, metadata with name and title, spec.parameters with

          github (create repo), catalog:register (add to Backstage)])

    Q134: Where can TechDocs store generated documentation? (Local filesystem (dev),

3.4 Template Examples & Best Practices (8 Qs)
    Q135: What makes a good Software Template? (Opinionated best practices baked in,
          minimal required inputs (design for the 80% use case), clear descriptions,
          produces production-ready output (not just hello-world), includes CI/CD,

    Q136: How do you test a template before publishing? (Run the Scaffolder locally:

    Q137: What is template versioning? (Templates evolve over time. Store them in

          version.Breaking template changes require migration paths)
    Q138: How do you debug a failing template execution? (Scaffolder task list at
          /create/tasks shows all running and completed tasks. Each task has
          step-by-step logs. Failed steps show error messages. Backend logs:
          yarn logs --filter backend. Task logs are stored in the database)
    Q139: How do you restrict which users can use which templates? (Template RBAC
          via the permissions framework. Define policies: "Only anihpj-team can
          use 'Create Django Service' template." Use catalog conditional rules
          to restrict based on user's group membership)
    Q140: How do you create a template that deploys to Kubernetes? (Use the
          scaffolder-backend-module-kubernetes. Add kubernetes:apply step after
          code generation. Template generates K8s manifests during scaffolding.
          The kubernetes:apply action applies them to the target cluster)
    Q141: What is the difference between a Software Template and a Scaffolder
          action? (Template = the full blueprint: parameters + steps + output.
          Action = a single step within a template: fetch, publish, register,
          kubernetes:apply. Templates compose multiple actions into a workflow)
    Q142: How do you handle secrets in templates? (Never put secrets in template
          YAML. Use environment variables in the Scaffolder backend. Secrets
          are injected at runtime via app-config or Kubernetes Secrets. Template
          parameters should ask for secret REFERENCES, not values)

4.1 Plugin Architecture — Frontend Plugins (8 Qs)
    Q151: What is a Backstage plugin made of? (A TypeScript package that can contain
          frontend code (React components), backend code (Express routers +
          services), or BOTH. Each plugin is an npm package in the monorepo)
    Q152: How do you create a frontend plugin? (yarn backstage-cli plugin:create
          → choose frontend. Creates: src/plugin.ts (exported plugin instance),
          src/components/ (React components), src/routes.ts (routing), src/index.ts
          (public API))
    Q153: What is createPlugin()? (The core function for creating a frontend plugin.
          Returns a BackstagePlugin with an ID. Plugin registers routes via
          createRoutableExtension(), provides APIs via provide(), and consumes
          APIs via useApi())
    Q154: How do plugins communicate with each other? (Via the ApiRef system. Plugin A
          creates an API (createApiRef<T>()) and provides an implementation
          (provide()). Plugin B consumes it (useApi(apiRef)). This is dependency
          injection at the plugin level)
    Q155: What is createRoutableExtension()? (Defines a mountable route for a plugin.
          The extension is a React component wrapped with routing awareness.
          The app shell mounts extensions at specific routes. This enables lazy
          loading — plugin code loads only when navigated to)
    Q156: How do you mount a plugin in the Backstage sidebar? (In packages/app/src/
          plugins.ts: import the plugin, wrap it with createRoutableExtension(),
          add it to the route configuration. The sidebar entry is defined by the
          plugin's exported route)
    Q157: How do plugins contribute to entity pages? (Via the EntityPage extension
          system. A plugin can define a card or tab for entity pages:
          createComponentExtension() with an entityFilter. When an entity matches,
          the card/tab appears. Example: Grafana plugin adds a "Grafana" tab)
    Q158: What is the relationship between the Sidebar, App, and Plugin routes?
          (App.tsx defines the layout: Sidebar + main content area. Each plugin
          registers routes. The sidebar renders navigation items linked to plugin
          routes. Root route: / → Home. Catalog: /catalog. Your plugin: /my-plugin)

4.2 Plugin Architecture — Backend Plugins (8 Qs)
    Q159: How do you create a backend plugin? (yarn backstage-cli plugin:create → choose
          backend. Creates: src/plugin.ts, src/router.ts, src/service/ (business
          logic), src/run.ts (entry point). Exports a function that creates the
          backend feature)
    Q160: What is createBackendPlugin()? (The core function for creating backend plugins.
          Takes a plugin ID and a register() function. The register function receives
          env (logger, config, database, router) and sets up routes and services)
    Q161: How do backend plugins expose REST APIs? (Create an Express router in the
          plugin's router.ts. Define routes: router.get('/health'), router.post('/data').
          The router is mounted at /api/<plugin-id>/ by the backend framework)
    Q162: How do backend plugins access the database? (Via the PluginDatabaseManager
          from env.database. Get a Knex client: const db = await env.database.getClient().
          Run migrations, queries, schema operations. Each plugin gets its own
          database namespace)
    Q163: What is the Backstage backend service discovery pattern? (Plugins export
          a createPlugin() function. Backend createBackend() discovers and loads
          all plugins. Each plugin registers its routes, database migrations,
          scheduled tasks. The framework handles startup/shutdown lifecycle)
    Q164: How do backend plugins handle configuration? (Use @backstage/config.
          Plugin config lives under the plugin's key in app-config.yaml. Read via
          config.getConfig('myPlugin'). Validate with JSON Schema. Access at
          runtime via env.config)
    Q165: How do backend plugins integrate with external services? (Use the plugin's
          service layer. Make HTTP calls with fetch or axios. Use official SDKs
          for GitHub, GitLab, Jira, etc. Store tokens in app-config.yaml
          (integration config). Respect rate limits and handle failures gracefully)
    Q166: What is the difference between a backend plugin and a backend module?
          (Backend plugin = standalone plugin that adds new functionality
          (e.g., Grafana backend). Backend module = extends an EXISTING plugin
          (e.g., a custom scaffolder action that extends the Scaffolder). Modules
          use createBackendModule() with pluginId reference)

4.3 Authentication & Identity (8 Qs)
    Q167: What authentication providers does Backstage support? (Built-in: GitHub,
          GitLab, Google, Okta, Microsoft (Azure AD), OAuth2 (generic), OIDC,
          SAML, Atlassian, Bitbucket, GitHub Enterprise, GitLab Enterprise,
          Google IAP. Custom providers via createAuthProvider())
    Q168: How does the Backstage authentication flow work? (1. User visits Backstage.
          2. Backstage redirects to configured auth provider's login page. 3. User
          authenticates with the provider. 4. Provider redirects back with auth
          code. 5. Backstage exchanges code for tokens. 6. Backstage creates a
          session. 7. User is logged in)
    Q169: What is a sign-in resolver and why is it needed? (Maps the auth provider's
          identity (e.g., GitHub user: "johndoe") to a Backstage identity (User
          entity in the catalog). Without a resolver, Backstage doesn't know who
          you are. Common resolvers: email matching, username matching, catalog
          entity lookup)
    Q170: How do you configure GitHub authentication? (In app-config.yaml:
          auth.providers.github.development.clientId, clientSecret. For production:
          GitHub OAuth App with callback URL: https://backstage.anihpj.com/api/auth/
          github/handler/frame. Sign-in resolver: match GitHub username to
          catalog User entity)
    Q171: How does Backstage handle session management? (Stateless JWT tokens stored
          in cookies. Backend validates tokens on each request. Token contains
          user identity, expiration, and provider info. Refresh tokens extend
          sessions without re-authentication. Tokens are signed with Backstage's
          backend secret)
    Q172: How do you configure multiple auth providers? (List all providers in
          app-config.yaml under auth.providers. Each provider has its own
          configuration and sign-in resolver. Backstage shows a provider
          selection screen. Users can choose which provider to sign in with)
    Q173: What is an auth backend plugin module and when do you need one? (Extends
          Backstage's auth system with custom logic. Use when: you need a custom
          auth provider not in the built-in list, custom token validation,
          custom session handling, or custom sign-in resolver that the built-in
          resolvers can't handle)
    Q174: How does Backstage handle authentication for backend-to-backend service
          calls? (Backend services use service-to-service tokens. Generated with
          a shared secret. Tokens include the calling service identity and
          expiration. Receiving service validates the token. Used for internal
          backend communication, not user-facing)

4.4 Permissions Framework (8 Qs)
    Q175: What is the Backstage Permissions Framework? (A pluggable authorization
          system that controls who can see and do what in Backstage. Supports
          RBAC (role-based), ABAC (attribute-based), and custom policies.
          Granular control: catalog entity visibility, template usage, scaffolder
          access, plugin access)
    Q176: How does the Permissions Framework work at a high level? (1. Permission
          policy is defined (who can do what). 2. Backend plugin requests a
          permission check. 3. Permission framework evaluates the request against
          the policy. 4. Returns ALLOW or DENY. 5. Plugin enforces the result)
    Q177: What are the built-in permission types? (catalog.entity.read (can see entity),
          catalog.entity.create (can register entity), catalog.entity.delete (can
          unregister entity), scaffolder.template.read (can use template),
          scaffolder.task.create (can execute template), catalog.entity.refresh)
    Q178: How do you configure RBAC for the catalog? (Define a PermissionPolicy. Use
          catalog conditions: isEntityOwner (only the owner can see/delete),
          hasAnnotation, hasLabel, hasSpec. Example: "Only the owner group can
          delete an entity. Everyone can read production entities")
    Q179: How do you create a custom permission rule? (Implement createPermissionRule()
          with name, description, resourceType (catalog-entity), paramsSchema
          (JSON Schema for rule parameters), and apply() function that returns
          true/false based on entity properties)
    Q180: What is the difference between ALLOW and CONDITIONAL in permissions?
          (ALLOW = unconditional access. CONDITIONAL = access IF a condition is
          met. Example: "ALLOW reading all production entities, CONDITIONALLY
          ALLOW reading experimental entities IF you are the owner")
    Q181: How does the permissions framework integrate with plugins? (Plugins call
          permissions.authorize() or use the usePermission() React hook. Pass a
          Permission object and optional resource reference. Framework returns
          {result: ALLOW|DENY}. Plugin shows/hides UI or blocks API calls based
          on result)
    Q182: How do you test permission policies? (Unit test: create a mock PermissionPolicy,
          call authorize() with various inputs, assert results. Integration test:
          Backstage test instance with different auth tokens, verify UI visibility
          and API access. Backstage provides testing utilities in @backstage/
          backend-test-utils)

4.5 Backstage Operations & Production (10 Qs)
    Q183: How do you deploy Backstage to Kubernetes? (Option 1: Helm chart. Option 2:
          Docker image from yarn build-image. Option 3: Custom K8s manifests.
          Production needs: Deployment (backend), Deployment or static serve
          (frontend), PostgreSQL StatefulSet, Ingress with TLS, Secrets for
          tokens, ConfigMap for app-config)
    Q184: How do you configure Backstage for production? (NODE_ENV=production.
          Database: PostgreSQL (not SQLite). app-config.production.yaml with
          production-specific settings. GitHub token with appropriate scopes.
          TLS certificates via cert-manager. Health checks: /healthcheck endpoint)
    Q185: How do you handle Backstage database migrations in production? (Knex
          migrations run automatically on backend startup via knex migrate:latest.
          Migration files in each plugin's migrations/ directory. Order: run base
          migrations first, then plugin migrations. Rollback: knex migrate:rollback
          (requires downtime planning))
    Q186: How do you upgrade Backstage to a new version? (1. Check Backstage changelog
          for breaking changes. 2. Use Backstage Upgrade Helper. 3. Update
          @backstage/* packages with yarn backstage-cli versions:bump. 4. Run
          yarn install. 5. Test in dev: yarn dev. 6. Run migrations. 7. Build
          and deploy. 8. Monitor for issues)
    Q187: How do you scale Backstage for a large organization? (Backend: multiple
          replicas behind load balancer. Frontend: CDN for static assets. Database:
          read replicas for catalog queries. Search: Elasticsearch cluster.
          TechDocs storage: S3/GCS with CDN. Rate limiting on API. Catalog:
          incremental processing, entity cache)
    Q188: How do you monitor Backstage health? (/healthcheck endpoint returns
          {status: 'ok'} if backend is healthy. Prometheus metrics via
          @backstage/plugin-app-backend. Database pool metrics. Request latency.
          Error rates. Custom metrics from plugins. Alert on: database connection
          failures, high error rates, slow responses)
    Q189: How do you set up logging in Backstage? (Backstage uses winston for
          structured logging. Configure log level in app-config.yaml: app.logging
          .level (debug, info, warn, error). Log format: JSON in production,
          pretty-printed in dev. Plugins can create their own logger from env.logger.
          Ship logs to centralized logging (ELK, Grafana Loki))
    Q190: How do you back up and restore Backstage? (Critical: PostgreSQL database
          (pg_dump). Important: app-config.yaml (in Git). Useful: user uploads
          and generated TechDocs (in S3/GCS — already durable). Not needed:
          catalog entities (re-ingestible from source repos). Restore: restore
          DB dump → Backstage re-ingests catalog from configured locations)
    Q191: How do you configure CORS for Backstage in production? (In app-config.yaml:
          backend.cors.origin: 'https://backstage.anihpj.com'. Methods: GET,POST,
          PUT,DELETE,PATCH. Credentials: true. Multiple origins: use an array.
          Wildcard * is NOT recommended for production)
    Q192: How do you set up the Proxy plugin for secure internal API access?
          (app-config.yaml: proxy.endpoints mapping. Example: '/grafana' → target:
          'https://grafana.internal.anihpj.com'. Backstage proxies requests from
          /api/proxy/grafana/* to the target. No CORS issues — all traffic goes
          through Backstage's backend. Authentication is handled by Backstage)

4.6 Backstage Ecosystem & Community (8 Qs)
    Q193: What is the Backstage Plugin Marketplace? (A directory of 200+ community
          plugins available at backstage.io/plugins. Categories: CI/CD (GitHub
          Actions, Jenkins, ArgoCD), Monitoring (Grafana, Datadog, PagerDuty),
          Cloud (AWS, GCP, Azure), Security (Snyk, OPA, Trivy), Documentation
          (TechDocs addons))
    Q194: How do you install a community plugin? (Frontend: yarn add --cwd packages/app
          @backstage/plugin-<name> → register in packages/app/src/plugins.ts.
          Backend: yarn add --cwd packages/backend @backstage/backend-plugin-<name>
          → add to packages/backend/src/index.ts. Then configure in app-config.yaml)
    Q195: What are the most commonly used Backstage plugins? (GitHub (code + CI/CD
          visibility), Kubernetes (cluster resource view), Grafana (dashboard
          embeds), PagerDuty (on-call + alerts), Sentry (error tracking), Lighthouse
          (performance audits), Tech Radar (technology adoption tracking), ArgoCD
          (GitOps deployment status))
    Q196: How does the Backstage community operate? (CNCF Incubating project. Governance:
          Technical Steering Committee (TSC). SIGs (Special Interest Groups):
          Catalog, Scaffolder, TechDocs, UX, etc. Community meetings every other
          week. RFC process for major changes. Contribution ladder: contributor →
          reviewer → maintainer → TSC)
    Q197: How do you contribute to Backstage open source? (Fork backstage/backstage on
          GitHub. Find "good first issue" or "help wanted" labels. Join Discord
          (#contributing channel). Sign CNCF CLA. Follow CONTRIBUTING.md guidelines.
          Submit PR with tests + documentation. Adopters: 500+ companies including
          Spotify, Netflix, American Airlines, Zalando, Expedia)
    Q198: What is the Backstage BEP (Backstage Enhancement Proposal) process? (Similar
          to KEPs in Kubernetes. RFC-style proposals for major changes. Template:
          Summary, Motivation, Design Details, Alternatives, Risks. Community
          review period. TSC vote for approval. Implemented after approval.
          Ensures architectural consistency across the project)
    Q199: How do you stay updated with Backstage changes? (GitHub releases page for
          changelogs. backstage.io/blog for announcements. Discord #announcements
          channel. Backstage Community Sessions (YouTube). CNCF Backstage mailing
          list. Weekly newsletter: backstage.io/weekly)
    Q200: What is the career path for a Backstage/IDP specialist? (Platform Engineer →
          Senior Platform Engineer → Staff Platform Engineer → Principal Platform
          Engineer / Developer Experience Architect. Skills: TypeScript, React,
          Node.js, Kubernetes, CI/CD, internal developer portals, developer
          experience (DevEx), platform product management. Certifications: CBA
          (this exam!) + CKA/CKAD for Kubernetes + cloud certifications)
