      1.2  Grafana Defined — The Simple Answer
           - Official definition: "Open-source analytics & interactive visualization platform"
           - Grafana connects to data sources → creates dashboards → alerts on conditions
           - NOT a data store — it's the visualization layer ABOVE your data
           - Works with: Prometheus, InfluxDB, PostgreSQL, Elasticsearch, Loki, Tempo, Mimir, 100+ sources
           - Who uses Grafana: SREs, DevOps, Developers, Managers, Data Analysts, Executives
           - Grafana's philosophy: "One pane of glass" — all your data, one dashboard

      1.3  Core Concepts & Terminology
           a) Data Source — Where Grafana pulls data FROM (Prometheus, MySQL, Loki, etc.)
              - anihpj example: Prometheus for metrics, PostgreSQL for business data, Loki for logs
           b) Dashboard — A collection of panels arranged on a page
              - anihpj example: "anihpj Production Overview" dashboard
           c) Panel — A single visualization (graph, gauge, table, stat, etc.)
              - anihpj example: HTTP request rate graph panel
           d) Row — A horizontal grouping of panels within a dashboard
              - anihpj example: "HTTP Metrics" row containing request rate, error rate, latency panels
           e) Query — The request sent to a data source to retrieve data
              - anihpj example: `rate(django_http_requests_total[5m])`
           f) Transformation — Data processing pipeline applied to query results
              - anihpj example: Merge Prometheus + PostgreSQL data into one table
           g) Variable — Dynamic placeholder (e.g., $instance, $job) for interactive dashboards
              - anihpj example: $environment variable switches between prod/staging/dev
           h) Alert Rule — A condition that triggers a notification
              - anihpj example: Error rate > 5% → send Slack notification

    Chapter 2: Installing & Configuring Grafana

      2.1  System Requirements
           - Minimum: 255MB RAM, 1 CPU core
           - Recommended: 1GB+ RAM for production
           - Supported OS: Linux, macOS, Windows, Docker, Kubernetes
           - Browser support: Chrome, Firefox, Safari, Edge (latest 2 versions)
           - Database: SQLite (default, < 10 users), PostgreSQL (10-100+ users), MySQL
           - Disk: Minimal for Grafana itself, dashboards are small JSON files

      2.2  Installation Methods Deep Dive
           a) Docker Installation
              - `docker run -d -p 3000:3000 --name=grafana grafana/grafana`
              - Docker Compose with Prometheus + PostgreSQL + anihpj
              - Volume mounts for persistent configs, plugins, data
              - Environment variables: GF_SERVER_HTTP_PORT, GF_SECURITY_ADMIN_PASSWORD
              - Custom grafana.ini via volume mount: `-v ./grafana.ini:/etc/grafana/grafana.ini`
              - Plugin installation at container startup: GF_INSTALL_PLUGINS env var
              - Health check: `curl http://localhost:3000/api/health`
           b) Kubernetes Installation (Helm Chart)
              - `helm repo add grafana https://grafana.github.io/helm-charts`
              - `helm install grafana grafana/grafana`
              - Persistent volume claims for dashboards and data
              - Ingress configuration for external access
              - ServiceMonitor for Prometheus scraping
              - Sidecar container for dashboard provisioning from ConfigMaps
              - anihpj Example: Helm values.yaml with custom dashboards, datasources, notifiers
           c) Linux (APT/YUM) Installation
              - Repository setup, GPG key import
              - `systemctl start grafana-server`
              - Default config: /etc/grafana/grafana.ini
              - Default data: /var/lib/grafana/
              - Logs: /var/log/grafana/grafana.log
           d) macOS Installation (Homebrew)
              - `brew install grafana`
              - `brew services start grafana`
           e) Windows Installation
              - MSI installer or standalone binary
              - Run as Windows service

      2.3  Configuration File Deep Dive (grafana.ini)
           - [server] section — HTTP port, domain, protocol, certs, static_root_path
           - [database] section — SQLite vs PostgreSQL vs MySQL, connection pool settings
           - [security] section — admin user, secret key, disable gravatar, cookie settings
           - [auth] section — login settings, OAuth, LDAP, disable login form
           - [smtp] section — email server for invitations & alerts
           - [paths] section — data, logs, plugins, provisioning directories
           - [alerting] section — Enable/disable, evaluation timeout, max attempts
           - [unified_alerting] section — New Grafana Alerting settings
           - [annotations] section — Cleanup settings
           - [dashboards] section — Default home dashboard, versions to keep
           - [users] section — Allow sign up, auto-assign org
           - [metrics] section — Enable Grafana's own Prometheus metrics
           - [log] section — Log level, format (console, json)
           - Environment variable override pattern: GF_<SECTION>_<KEY>
             Example: GF_SERVER_HTTP_PORT=8080 overrides [server].http_port

           d) Tracing — Tempo, Jaeger, Zipkin, AWS X-Ray
           e) Cloud Monitoring — AWS CloudWatch, Azure Monitor, Google Cloud Monitoring
           f) Other — JSON API, CSV, TestData (built-in for demos), Infinity (JSON/CSV/XML from APIs)

      4.3  Connecting anihpj Data Sources (Real Setup with Code)
           a) Prometheus → Scrapes anihpj Django metrics from /metrics endpoint
              - Data source URL: http://prometheus:9090
              - Access mode: Server (Grafana proxies all queries)
              - Auth: None (internal network) or Basic Auth
           b) PostgreSQL → Direct connection to anihpj's database (Skills, JobPost tables)

    Chapter 5: Prometheus Data Source — The Industry Standard
    ───────────────────────────────────────────────────────────
      5.1  Prometheus Overview for Grafana Users
           - Pull-based metrics collection: Prometheus scrapes targets at intervals
           - Multi-dimensional data model: metric name + key-value labels
           - PromQL: The query language for Prometheus (NOT SQL!)
           - Key data types: Counter, Gauge, Histogram, Summary
           - Prometheus's own time series database (TSDB): Local storage, not distributed
           - Retention: Default 15 days (TSDB), long-term via Mimir/Thanos/Cortex
           [CARD GRID: 4 metric types with definitions, PromQL examples, anihpj usage]
           [COUNTER: Only increases (HTTP requests total) — NEVER use raw, always rate()/increase()]
           [GAUGE: Goes up and down (CPU usage, memory, temperature)]
           [HISTOGRAM: Bucketed observations (request duration in buckets)]
           [SUMMARY: Client-side quantile calculation (less common than histogram)]

      5.2  PromQL Fundamentals
           a) Instant Vector vs Range Vector (MOST IMPORTANT CONCEPT)
              - Instant: `django_http_requests_total` (latest value, time-series selector)
              - Range: `django_http_requests_total[5m]` (values over 5 minutes, range vector)
              - Key rule: rate() and similar functions NEED range vectors, NOT instant vectors
              - Wrong: `rate(django_http_requests_total)` ❌ — missing [range]
              - Correct: `rate(django_http_requests_total[5m])` ✅
           b) Core Functions — The Big 6
              - `rate()` — Per-second rate of increase for counters (graphing)
              - `irate()` — Instant rate (higher resolution, more sensitive to resets)
              - `increase()` — Total increase over time range (calculating totals)
              - `avg()`, `sum()`, `max()`, `min()` — Aggregation operators (use with `by` or `without`)
              - `histogram_quantile()` — Calculate percentiles from histograms (P50, P95, P99)
              - `topk()` / `bottomk()` — Top/bottom K time series
           c) Filtering & Label Matching (5 Operators)
              - Exact: `{job="anihpj", method="GET"}`
              - Regex match: `{endpoint=~"/api/.*"}` (=~ means regex match)
              - Not regex: `{endpoint!~"/health.*"}` (!~ means not regex)
              - Not equal: `{status!="200"}`
              - Multiple values: `{method=~"GET|POST"}`
           d) Operators & Vector Matching
              - Arithmetic: `+`, `-`, `*`, `/` (on matching label sets)
              - Comparison: `>`, `<`, `==`, `!=` (returns filtered results)
              - Logical/Set: `and`, `or`, `unless` (vector set operations)
              - `on()` / `ignoring()` for controlling which labels are used in matching
              - `group_left` / `group_right` for many-to-one matching
           e) Subqueries
              - Syntax: `<instant_query>[<range>:<resolution>]`
              - Example: `max_over_time(rate(http_requests_total[5m])[1h:1m])`

      5.3  Building PromQL Queries for anihpj (10 Real Queries)
           a) HTTP Request Rate: `rate(django_http_requests_total{job="anihpj"}[5m])`
           b) Error Rate %: `(sum(rate(django_http_requests_total{status=~"5.."}[5m])) / sum(rate(django_http_requests_total[5m]))) * 100`
           c) P95 Latency: `histogram_quantile(0.95, sum(rate(django_http_request_duration_seconds_bucket[5m])) by (le))`
           d) Job Posts Created per Hour: `rate(jobpost_created_total[1h]) * 3600`
           e) Average Request Duration: `rate(django_http_request_duration_seconds_sum[5m]) / rate(django_http_request_duration_seconds_count[5m])`
           f) Active Users (last 5 min): `count(user_active_last_5m)`
           g) CPU Usage %: `100 - (avg(rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)`
           h) Memory Usage %: `(1 - (node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes)) * 100`
           i) Slowest 5 Endpoints: `topk(5, rate(django_http_request_duration_seconds_sum[5m]) / rate(django_http_request_duration_seconds_count[5m]))`
           j) Per-Endpoint Error Rate: `sum(rate(django_http_requests_total{status=~"5.."}[5m])) by (endpoint) / sum(rate(django_http_requests_total[5m])) by (endpoint) * 100`

      5.5  Common PromQL Patterns & Pitfalls (CRITICAL FOR EXAM)
           - PITFALL 1: Counter resets — ALWAYS use rate()/increase() with counters
             Wrong: `django_http_requests_total` (drops to 0 on restart, graph breaks)
             Right: `rate(django_http_requests_total[5m])` (handles resets gracefully)
           - PITFALL 2: The [range] trap — Missing range in rate()/increase()
             Error: `rate(http_requests_total)` → "expected type range vector"
           - PITFALL 3: Label cardinality explosion
             Bad: `{user_id="12345"}` (millions of unique IDs = KILLS Prometheus)
           - PITFALL 4: Staleness — Metrics disappear after 5 min without new samples
             Always check: Is the target still scraping?
           - PITFALL 5: Wrong histogram aggregation
             Must aggregate buckets by (le) BEFORE histogram_quantile()
           - PITFALL 6: Using rate() on gauges
             rate() is for counters only. Use avg_over_time() or deriv() for gauges
           - PITFALL 7: Double-counting with sum()
             Be careful: sum(increase(http_requests_total[5m])) double-counts if not grouped
           - PITFALL 8: Forgetting `by` or `without` in aggregations
             sum(rate(...)[5m]) without (pod) vs sum by (namespace) (rate(...)[5m])

      6.4  Building SQL Queries for anihpj (7 Real Examples)
           a) Job Posts by Location (Bar Chart):
              SELECT location, COUNT(*) as "Job Count"
              FROM jobpost_jobpost
              WHERE $__timeFilter(created_at)
              GROUP BY location ORDER BY "Job Count" DESC
           b) Top Skills in Demand (Pie Chart):
              SELECT s.name as "Skill", COUNT(*) as "Count"
              FROM jobpost_jobpost_skills js

              WHERE $__timeFilter(js.jobpost_id)
              GROUP BY s.name ORDER BY "Count" DESC LIMIT 10
           c) User Registration Trend (Time Series):

           d) Jobs by Author (Table):
              SELECT u.username as "Author", COUNT(*) as "Posts", MAX(j.created_at) as "Last Post"

           f) Job Post Status Distribution (Stat Panels):

    Chapter 7: Loki — Log Aggregation Data Source
    ──────────────────────────────────────────────
      7.1  What is Loki?
           - Grafana's log aggregation system ("Prometheus, but for logs")
           - Key design: Indexes only METADATA (labels), not full log text → cost-effective!
           - Full log text stored in compressed chunks in object storage (S3, GCS, etc.)
           - Uses LogQL: PromQL-inspired query language for logs
           - Components: Distributor, Ingester, Querier, Query Frontend, Compactor, Ruler
           - NOT like Elasticsearch: Loki does NOT do full-text indexing (different philosophy)
           [ARCHITECTURE DIAGRAM: Promtail → Distributor → Ingester → Object Storage → Querier → Grafana]

      7.2  LogQL Deep Dive (CRITICAL FOR EXAM)
           a) Log Queries — Find and filter log entries
              - Stream selector: `{job="anihpj", env="production"}`
              - Contains: `{job="anihpj"} |= "ERROR"`
              - Not contains: `{job="anihpj"} != "DEBUG"`
              - Regex match: `{job="anihpj"} |~ "status=[4-5][0-9]{2}"`
              - Not regex: `{job="anihpj"} !~ "healthcheck"`
           b) Metric Queries — Generate metrics FROM log streams
              - Log rate: `rate({job="anihpj"}[5m])`
              - Error count: `count_over_time({job="anihpj"} |= "ERROR"[5m])`
              - Bytes rate: `bytes_rate({job="anihpj"}[5m])`
              - Bytes over time: `bytes_over_time({job="anihpj"}[5m])`
           c) Log Pipeline — Parse and transform log lines
              - JSON parser: `{job="anihpj"} | json`
              - Logfmt parser: `{job="anihpj"} | logfmt`
              - Pattern parser: `{job="anihpj"} | pattern "<ip> - <user> [<timestamp>] <method>"`
              - Regexp parser: `{job="anihpj"} | regexp "(?P<status>\\d+)"`
              - Unpack parser: `{job="anihpj"} | unpack`
              - Line format: `{job="anihpj"} | line_format "{{.status}} {{.method}}"`
              - Label format: `{job="anihpj"} | label_format level=UPPER`
           d) Filter Expressions (after parsing)
              - `{job="anihpj"} | json | duration > 2s`
              - `{job="anihpj"} | json | status = 500`
              - `{job="anihpj"} | json | method =~ "POST|PUT"`
              - `{job="anihpj"} | json | duration >= 1s, duration <= 5s`
           e) Aggregation Operators for Metric Queries
              - sum, avg, min, max, count, stddev, stdvar, topk, bottomk
              - sum by (level) (count_over_time({job="anihpj"}[5m]))

      7.3  Loki Query Examples for anihpj (10 Real Queries)
           a) Django Error Logs: `{job="anihpj"} |= "ERROR"`
           b) Slow Requests (>2s): `{job="anihpj"} | json | duration > 2s`
           c) 404 URLs: `{job="anihpj"} | json | status = 404 | line_format "{{.method}} {{.path}}"`
           d) JobPost API Errors: `{job="anihpj"} |~ "/api/jobs/.*" | json | status >= 500`

    Chapter 10: Transformations — Shaping Data Before Display
    ───────────────────────────────────────────────────────────
      10.1  What Are Transformations?
           - Data processing pipeline BETWEEN query results and visualization rendering
           - Applied per-panel basis, processed in sequential order
           - Non-destructive: Original query results are not modified
           - Use when: Data source can't return data in the exact shape you need
           - Common scenarios: Merging multiple queries, filtering, computing derived fields
           [DIAGRAM: Query A → Transform 1 (Merge with B) → Transform 2 (Filter) → Transform 3 (Sort) → Visualization]

      10.2  Essential Transformations (12 Types — EXAM TOPIC)
           a) Reduce — Aggregate rows (sum, avg, min, max, count, last, first, range, diff)
           b) Merge — Combine results of multiple queries into one table (series or table mode)
           c) Filter by value — Include/exclude rows based on conditions (=, !=, <, >, contains, regex)
           d) Group by — Group rows by field(s), calculate aggregate per group
           e) Join by field — SQL-style inner/outer join between two query results
           f) Sort by — Reorder table rows by field(s), ascending/descending
           g) Rename by regex — Rename fields using regex pattern matching and replacement
           h) Organize fields — Hide, reorder, rename columns selectively
           i) Calculate field — Add computed fields (binary: A+B; unary: -A, |A|; row number, cumulative)
           j) Concatenate fields — Combine multiple fields into one (separator configurable)
           k) Convert field type — Change field type (string → number, number → string, etc.)
           l) Extract fields — Parse key=value pairs from a string field into separate columns

      10.3  Transformation Chaining Patterns (Real Examples)
           - Pattern 1: Merge + Filter + Sort
             Use case: Combine CPU and memory queries, filter high-usage nodes, sort descending
           - Pattern 2: Group by + Reduce
             Use case: Aggregate raw request logs by endpoint and calculate avg latency
           - Pattern 3: Join by field + Organize
             Use case: Join Prometheus pod metrics with K8s metadata, hide internal columns
           - Pattern 4: Calculate field + Filter by value
             Use case: Compute "error_percentage" field, filter only rows > 5%
           - anihpj Example: Join Prometheus (technical metrics) + PostgreSQL (business metrics)
             on "endpoint" to create a unified "Business Impact of Errors" table

    Chapter 11: Variables & Template Dashboards
    ─────────────────────────────────────────────
      11.1  What Are Variables? (EXAM HEAVY)
           - Dynamic placeholders that make dashboards interactive and reusable
           - Syntax: $variable_name or ${variable_name} (braces needed when adjacent to text)
           - Used in: Queries, panel titles (repeated panels), text panels, dashboard links
           - Key benefit: ONE dashboard serves ALL environments, services, instances
           - Variable lifecycle: Dashboard load → Variable query runs → User selects value → Panels re-query
           [DIAGRAM: Dashboard without variables vs with variables — code duplication eliminated]

      11.2  Variable Types Deep Dive (7 Types — KNOW ALL FOR EXAM)
           a) Query — Values populated from a data source query (most common, most powerful)
              - Example: `label_values(django_http_requests_total, job)` → returns all job label values
              - Example: `query_result(up)` → returns all targets from Prometheus
           b) Custom — Manually defined comma-separated list of values
              - Example: prod, staging, dev
           c) Text Box — Free-form user text input
              - Example: User types a specific pod name or IP
           d) Constant — Hidden, hardcoded value (for provisioned dashboards, GitOps)
              - Example: datasource="Prometheus-Production" (user can't change)
           e) Data Source — Dropdown of available data sources (switch between prod/staging Prometheus)
              - Type filter: Show only Prometheus/PostgreSQL/Loki data sources
           f) Interval — Time interval selection (1m, 5m, 15m, 30m, 1h)
              - Used as: $__interval in PromQL queries for dynamic step resolution
           g) Ad hoc filters — Auto-generated key=value filters from data source
              - User selects field → Grafana queries distinct values → user selects value
              - Example: Filter by "status_code" = "500" on Prometheus metrics

      11.3  Variable Configuration Options (Each Variable Has These)
           - Name: Used as $name in queries (letters, numbers, underscores only)
           - Label: Human-readable display name
           - Type: One of the 7 types above
           - Hide: None (visible), Label (only label shown), Variable (hidden completely)
           - Multi-value: Allow selecting multiple values simultaneously
           - Include All option: Adds "All" option that passes wildcard (`.*`) or custom value
           - Refresh: On Dashboard Load, On Time Range Change (for query variables)
           - Sort: Disabled, Alphabetical (asc/desc), Numerical (asc/desc), Alphabetical case-insensitive
           - Selection options: Multi-select checkbox, single-select dropdown, radio buttons
           - Regex filter: Filter query results (e.g., only values matching `prod-.*`)
           - Preview of values: See what values the variable will offer before saving

      11.4  Chaining Variables (Parent-Child Dependencies) — EXAM TOPIC
           - Chain: $datasource → $namespace → $deployment → $pod
           - Each child variable's query references its parent: `label_values(up{namespace="$namespace"}, deployment)`
           - When parent changes, child re-queries automatically
           - Refresh timing: "On Dashboard Load" or "On Time Range Change"
           - Example: $location → $job_role → $skill (each filters the next)
           - Select "Lagos" → only shows job roles in Lagos → only shows skills for those roles

    Chapter 12: Grafana Alerting Fundamentals
    ───────────────────────────────────────────
      12.1  The Alerting Landscape
           - Grafana Alerting: Unified alerting for ALL data sources (Prometheus, Loki, PostgreSQL, etc.)
           - How it differs from Prometheus Alertmanager: Grafana Alerting is Grafana-native, multi-source; Alertmanager is Prometheus-only
           - Alert lifecycle: Query Evaluation → Condition Check → Pending → Firing → Notification → Resolved
           - Key terms for the exam:
             • Alert Rule: "IF error rate > 5% for 5 minutes THEN fire"
             • Alert Instance: One specific firing of a rule (per label set)
             • Contact Point: Where the notification goes (email, Slack, PagerDuty)
             • Notification Policy: Routing rules (match label → send to contact point)
             • Silence: Temporarily suppress alerts (maintenance window)
             • Notification Template: Customize the message format
             • Evaluation Group: Rules evaluated together on the same schedule
           [ALERTING ARCHITECTURE DIAGRAM: Data Sources → Scheduler → Alert Rules → State Manager → Notifier → Contact Points]

      12.2  Alert Rule Anatomy — Every Field Explained
           - Rule Name: Unique identifier within folder/evaluation group
           - Folder & Evaluation Group: Organizational + scheduling grouping
           - Queries & Expressions: One or more queries (A, B, C...) with reduce/math expressions
           - Condition: The expression that triggers (e.g., C > 0.05 means "expression C > 5%")
           - Evaluate Every: How often to check (1m, 5m, 10m, 15m)
           - Evaluate For (Pending Period): How long condition must persist before alerting (0m = instant)
           - Labels: Metadata for routing (severity=critical, team=sre, env=production)
           - Annotations: Descriptive info (summary, description, runbook_url)
           - NoData State: What to do when query returns no data (OK/NoData/Alerting/Keep Last)
           - Error State: What to do when query execution fails (OK/Error/Alerting/Keep Last)
           [ANNOTATED DIAGRAM: Full alert rule form with every field labeled and explained]

      12.3  Alert States & Lifecycle (MUST KNOW FOR EXAM)
           - Normal → Pending → Firing → Resolved → Normal
           - Normal: Condition is false (everything's fine)
           - Pending: Condition is true but hasn't met the "Evaluate For" duration yet
           - Firing: Condition has been true for ≥ "Evaluate For" period → notifications sent
           - Resolved: Condition becomes false after firing → resolution notification sent
           - Key Exam Point: "Evaluate For" prevents flapping alerts
             Example: Short CPU spike (30s) won't fire if "Evaluate For" is set to 5m
           - Flapping detection: Built-in to prevent alert storms
           - anihpj example: django_error_rate > 5% for 2 minutes → Pending. Still >5% after 2 min → Firing → Slack notification

      12.4  Alert Rule Types — Three Approaches
           a) Grafana-managed rules — Evaluated by Grafana's internal alerting engine
              - Best for: Multi-source alerts (Prometheus + Loki + PostgreSQL together)
              - Best for: Teams without Prometheus Alertmanager setup
              - Limitation: Single Grafana instance = single point of failure for alerting
           b) Data source-managed rules (Prometheus/Cortex/Mimir) — Evaluated BY Prometheus
              - Best for: Existing Prometheus setups with Alertmanager
              - Benefit: Alert evaluation continues even if Grafana is down
           c) Recording rules (Prometheus only) — Precompute expensive PromQL expressions
              - NOT an alert rule — it's a performance optimization
              - Example: Precompute `job:http_error_rate:5m` so dashboards load instantly

    Chapter 13: Creating Effective Alert Rules
    ────────────────────────────────────────────
      13.1  Alert Rule Design Principles (The Art of Alerting)
           - Alert on SYMPTOMS, not causes: "Error rate > 5%" not "CPU is 95%"
           - Avoid alert fatigue: Only alert on conditions requiring HUMAN action
           - The USE Method (for infrastructure): Utilization, Saturation, Errors
           - The RED Method (for services): Rate, Errors, Duration (latency)
           - The "Four Golden Signals" (Google SRE): Latency, Traffic, Errors, Saturation
           - Include actionable runbook links in EVERY alert annotation
           - Severity classification: Critical (wake someone up), Warning (investigate soon), Info (FYI)
           [CARD GRID: USE vs RED vs Four Golden Signals — definitions, example metrics, Grafana queries]

      13.2  Building Alert Rules for anihpj (6 Real Examples with Full Config)
           a) High Error Rate Alert (RED Method):
              - Query A: `sum(rate(django_http_requests_total{status=~"5.."}[5m]))`
              - Query B: `sum(rate(django_http_requests_total[5m]))`
              - Expression C: `$A / $B` → Condition: C > 0.05
              - Evaluate every: 1m, For: 2m
              - Summary: "anihpj error rate {{ humanize $values.C.Value }}"
              - Runbook: "1. Check Loki logs for error traces. 2. Check DB connectivity. 3. Check recent deployments."

           b) P95 Latency Spike (Four Golden Signals — Latency):
              - Query A: `histogram_quantile(0.95, sum(rate(request_duration_bucket[5m])) by (le))`
              - Condition: A > 2 (seconds)
              - Evaluate every: 5m, For: 5m

           c) Pod CrashLoopBackOff (K8s Infrastructure):
              - Query A: `rate(kube_pod_container_status_restarts_total{namespace="anihpj"}[10m]) * 600`
              - Condition: A > 3
              - Labels: severity=critical, team=sre, component=kubernetes

           d) No Data / Dead Monitoring (Check if metrics stopped):
              - Query A: `absent(up{job="anihpj"})` or `up{job="anihpj"} == 0`
              - This is CRITICAL — if anihpj goes down, metrics stop, and without this alert, NO OTHER ALERT FIRES
              - Condition: A == 1

           e) Certificate Expiry:
              - Query (internal Grafana metric): `grafana_tls_cert_expiry_days < 30`
              - Summary: "Grafana TLS certificate expires in {{ $values.A.Value }} days"

           f) Disk Space Running Out:
              - Query: `(node_filesystem_avail_bytes / node_filesystem_size_bytes) < 0.1`
              - Summary: "Disk usage > 90% on {{ $labels.instance }}"

      13.3  Labels and Annotations Best Practices
           - Standard labels: severity, team, environment, component, service
           - Template variables in labels: `{{ $labels.instance }}`, `{{ $labels.job }}`
           - Template variables in annotations: `{{ $values.A.Value }}`, `{{ humanize $values.A.Value }}`
           - Annotation keys: summary (required, short), description (optional, detailed), runbook_url, dashboard_url
           - Humanize functions: `{{ humanize $value }}` → "1.5K ms", `{{ humanizePercentage $value }}` → "5.2%"

    ──────────────────────────────────────────────────────────────
      14.1  Contact Points — Where Alerts Go (EXAM TOPIC)
           a) Email — SMTP configuration in grafana.ini [smtp] required
              - Simple setup, universal reach
           b) Slack / Microsoft Teams — Webhook URLs
              - Most common for dev teams
              - Slack incoming webhook: Create app → enable incoming webhooks → get URL
           c) PagerDuty / Opsgenie / VictorOps — On-call management platforms
              - Integration keys, severity mapping, on-call schedules
           d) Webhook — Custom HTTP POST to any endpoint
              - JSON payload with alert data → your custom handler
