    Ch 1: What Is Platform Engineering?
        ─── CHAPTER OVERVIEW ───
        Before building platforms, you must understand WHY they exist. This chapter
        walks through the pain of "TicketOps," the evolution from SysAdmin to Platform
        Engineering, the definition of an Internal Developer Platform (IDP), and what
        Developer Experience (DevEx) truly means. We'll use anihpj/jobpost as our
        running example throughout.

        1.1 The "TicketOps" Problem — Why Developers Hate Waiting

            • The hidden cost: context switching kills developer productivity
            • Real anihpj example: Developer Priya needs PostgreSQL, TLS cert, and a staging namespace
            • 3 tickets, ~8 days of waiting, 0 lines of feature code written

        1.2 From SysAdmin → DevOps → Platform Engineering — The Evolution
            • The SysAdmin Era (2000-2010): Manual everything, "throw it over the wall"
            • The DevOps Era (2013-2016): "You build it, you run it" — but every team reinvents infra
            • The Kubernetes Era (2017-2020): K8s becomes standard, but raw K8s is too complex
            • The Platform Engineering Era (2021+): Build an IDP, abstract complexity, self-service
            • Key insight: Each evolution solved one problem but created a new one

        1.3 What Is Platform Engineering? (The Simple Answer)
            • Official definition: "The discipline of designing and building toolchains and
              workflows that enable self-service capabilities for software engineering
              organizations in the cloud-native era."
            • In plain English: You build the "paved road" so developers don't have to
              navigate the wilderness of cloud infrastructure.
            • The platform is a PRODUCT, not a project — it has users (developers), an API,
              documentation, support, and a roadmap.
            • Core principle: "Make the right way the easiest way" (Golden Paths)
            • What platform engineering is NOT: It's not DevOps 2.0, not just a tools team,
              not just writing Terraform modules

        1.4 Developer Experience (DevEx) — Cognitive Load, Friction, Self-Service
            • What is DevEx? — How developers FEEL when interacting with your platform
            • Cognitive Load: What developers DON'T need to know about infrastructure
              — Extraneous load: Kubernetes YAML, Terraform, Helm charts (the platform abstracts these)
              — Intrinsic load: Business logic, application architecture (developers focus here)
            • Friction points: Long wait times, unclear documentation, too many tools, context switching
            • Self-service goal: "I need a database" → one command → database provisioned in 5 minutes
            • Measuring DevEx: Time-to-first-deploy, ticket deflection rate, developer NPS surveys
            • The anihpj DevEx vision: Developer clones repo, writes code, git push — platform handles the rest

        1.5 The Internal Developer Platform (IDP) — A Product, Not a Project
            • What is an IDP? — A unified layer on top of infrastructure that developers interact with
            • IDP components: CI/CD pipelines, application configs, environment management,
              secret management, monitoring dashboards, service catalog, documentation
            • IDP as a PRODUCT mindset:
              — Product Manager: Prioritizes features based on developer feedback
              — Backlog: "Developers want one-click DB provisioning" → Build DatabaseClaim CRD
              — SLAs: "99.9% of namespace provisions complete within 60 seconds"
              — Support: Internal Slack channel, office hours, documentation portal
            • Reference architectures: Spotify Backstage, Humanitec, Port, Cortex
            • The anihpj IDP: Backstage catalog → Argo CD → Kubernetes → Prometheus/Grafana

        1.6 "You Build It, You Run It" vs "You Build It, The Platform Runs It"
            • DevOps mantra: "You build it, you run it" — developers own production
            • The problem: Not every developer WANTS to be an SRE
            • Platform engineering shifts the balance:
              — Developers: Write code, define resource needs (DatabaseClaim CR)
              — Platform: Handles deployment, scaling, monitoring, alerting, backups
            • Shared responsibility model:
              — Developer owns: Application code, business logic, feature flags
              — Platform owns: Infrastructure, deployment pipelines, observability, security
              — Shared: Performance optimization, incident response, capacity planning

        1.7 Why anihpj/jobpost Needs a Platform
            • anihpj is a Django job posting app — simple on the surface, complex underneath
            • What it really needs: PostgreSQL, Redis, Celery workers, TLS certs, monitoring,
              backups, CI/CD, staging environments, secrets rotation, RBAC, network policies
            • Without a platform: Each of these requires a ticket, manual setup, tribal knowledge
            • With a platform: All of the above is self-service, automated, standardized
            • The anihpj journey in this guide: Local Docker → Kubernetes Deployment → GitOps with
              Argo CD → CRDs for self-service → Observability stack → Security hardening

        ═══ CHAPTER 1 — SUMMARY & IMPLEMENTATION ═══
        Platform Engineering exists because developers should write code, not wait for
        infrastructure. The evolution from SysAdmin → DevOps → Platform Engineering is
        a story of increasing abstraction: each era solved speed, then fragmentation,
        then complexity. An IDP is a PRODUCT with real users (developers) who need
        self-service provisioning, golden paths, and excellent DevEx. In the next chapters,
        we'll build this platform piece by piece for anihpj/jobpost — starting with the
        cloud native foundations you need to understand the tools at your disposal.

    Ch 2: Cloud Native Foundations & Terminology
        ─── CHAPTER OVERVIEW ───
        Before you can build a cloud native platform, you must speak the language.
        This chapter covers the essential terminology: what "Cloud Native" means
        (CNCF definition), the containers/Kubernetes/microservices triad, IaC,
        GitOps, immutable infrastructure, CI/CD, observability pillars, service
        mesh, policy as code, and SLO/SLI/SLA concepts. Every term is explained
        with concrete anihpj examples.

        2.1 What Is "Cloud Native"? — The CNCF Definition
            • Official CNCF definition: "Cloud native technologies empower organizations
              to build and run scalable applications in modern, dynamic environments
              such as public, private, and hybrid clouds."
            • Key traits: Containerized, dynamically orchestrated, microservices-oriented
            • The 5 cloud native principles: containerization, CI/CD, orchestration,
              observability, service mesh — exactly what the CNPE exam covers
            • Why it matters for platform engineers: You build the FOUNDATION that enables
              all of the above

        2.2 Containers, Kubernetes, Microservices — The Core Triad
            • Containers: Lightweight, portable, isolated application packaging (Docker/OCI)
            • Kubernetes: The orchestrator that schedules containers across a cluster
            • Microservices: Architectural pattern — one container = one focused responsibility
            • How they connect: Microservices run AS containers ON Kubernetes
            • The anihpj triad: anihpj-web (Django container) + postgres (DB container) +
              redis (cache container) — all orchestrated by Kubernetes

        2.3 Infrastructure as Code (IaC) — Terraform, Crossplane, Pulumi
            • What is IaC? — Managing infrastructure through machine-readable definition
              files, not manual processes or interactive tools
            • Terraform: HCL-based, declarative, provider ecosystem (AWS, GCP, Azure, K8s)
            • Crossplane: Kubernetes-native IaC — define cloud resources as CRDs (XRD)
            • Pulumi: IaC using real programming languages (Python, TypeScript, Go)
            • Key principle: Infrastructure is VERSIONED, REVIEWED, TESTED — just like code
            • anihpj example: terraform/eks.tf defines the EKS cluster, terraform/rds.tf
              defines the PostgreSQL database — both in git, both reviewed in PRs

        2.4 GitOps — Git as the Single Source of Truth
            • What is GitOps? — A way to do Continuous Delivery where Git is the single
              source of truth for declarative infrastructure and applications
            • Pull vs Push: In GitOps, an agent (Argo CD/Flux) PULLS from Git and syncs
              to the cluster — no CI system needs cluster credentials
            • Key benefits: Git history = audit log, git revert = rollback, PR review =
              change approval, self-healing (auto-fix drift)
            • anihpj example: k8s/base/ folder in git → Argo CD syncs to staging cluster →
              PR merged → Argo CD syncs to production cluster

        2.5 Immutable Infrastructure — Never SSH Into a Server
            • Definition: Servers are never modified after deployment. If something
              changes, you destroy and recreate from a known-good image.
            • Contrast with mutable: SSH in, apt-get update, edit config files,
              server "drifts" from known state over time
            • How K8s achieves this: Pods are ephemeral, Deployments recreate from
              immutable container images, ConfigMaps/Secrets provide configuration
            • "Cattle, not pets" — servers are numbered, not named; if one dies, replace it

        2.6 CI/CD and Continuous Delivery
            • CI (Continuous Integration): Automatically build and test code on every push
              — Goal: Catch integration issues early, merge frequently
            • CD (Continuous Delivery): Automatically deploy every change that passes CI
              to a staging environment; production deploy is a manual decision
            • Continuous Deployment: Every change that passes CI/CD goes straight to
              production — fully automated (advanced orgs only)
            • anihpj CI/CD: GitHub Actions → lint → test → build Docker image → push to
              ECR → Argo CD detects new tag → deploys to staging → smoke tests → canary
              to production

        2.7 Observability — Metrics, Logs, Traces (The Three Pillars)
            • Metrics: Numeric time-series data — "How many requests? How fast? How many errors?"
              Tool: Prometheus + Grafana
            • Logs: Timestamped text records — "What happened at 14:32:05 UTC?"
              Tool: Loki / Elasticsearch + Fluentd
            • Traces: Request journey across services — "Where is the bottleneck?"
              Tool: Tempo / Jaeger + OpenTelemetry
            • Profiles: The 4th pillar — CPU/memory profiling (Pyroscope, Parca)
            • Golden signal: For every service, track Latency, Traffic, Errors, Saturation

        2.8 Service Mesh, API Gateway, Ingress Controller
            • Ingress Controller: Layer 7 HTTP routing into the cluster (NGINX, Traefik)
              — Routes example.com/jobs → anihpj-web-service:8000
            • API Gateway: More advanced than Ingress — rate limiting, auth, request
              transformation, API versioning (Kong, Ambassador, APISIX)
            • Service Mesh: Infrastructure layer for service-to-service communication
              — mTLS, retries, timeouts, circuit breaking, traffic splitting
              — Istio (Envoy sidecar), Linkerd (Rust micro-proxy), Cilium (eBPF)
            • When to use which: Ingress for external traffic, Service Mesh for internal,
              API Gateway for API management

        2.9 Policy as Code — OPA, Kyverno, Admission Controllers
            • What is Policy as Code? — Security and compliance rules written as code,
              versioned in Git, automatically enforced at deploy time
            • OPA/Gatekeeper: Uses Rego language, ConstraintTemplates define reusable policies
            • Kyverno: Kubernetes-native, policies written in YAML (no new language to learn)
            • Common policies: Block containers running as root, require resource limits,
              block images with CRITICAL CVEs, enforce specific labels
            • anihpj example: Kyverno policy blocks any Deployment without
              `app.kubernetes.io/part-of: anihpj` label

        2.10 SLO/SLI/SLA, Error Budgets, DORA Metrics
            • SLI (Service Level Indicator): The metric you measure — e.g., "99.9% of
              requests complete in under 200ms"
            • SLO (Service Level Objective): The target for your SLI — e.g., "99.95% of
              requests must complete in under 200ms over 30 days"
            • SLA (Service Level Agreement): The contractual promise to customers with
              penalties if breached — e.g., "99.9% uptime or 10% credit"
            • Error Budget: 100% - SLO = how much "unreliability" you're allowed
              — If SLO is 99.9%, error budget is 0.1% = ~43 minutes/month of allowed downtime
            • DORA Metrics: Deployment Frequency, Lead Time for Changes, Mean Time to
              Restore (MTTR), Change Failure Rate — the 4 key DevOps performance indicators

        Cloud Native is a paradigm, not just a buzzword. It's about containers, orchestration,

        4.7 The Dockerfile — Multi-Stage Build Explained

            🐳 DOCKERFILE (multi-stage build for anihpj):
            ┌──────────────────────────────────────────────────────────────┐
            │ # Stage 1: Builder — install dependencies                   │
            │ FROM python:3.12-slim AS builder                            │
            │ WORKDIR /app                                                │
            │ COPY requirements.txt .                                     │
            │ RUN pip install --no-cache-dir --user -r requirements.txt   │
            │                                                             │
            │ # Stage 2: Runtime — minimal production image               │
            │ FROM python:3.12-slim                                       │
            │ RUN useradd --create-home anihpj   # Non-root user          │
            │ WORKDIR /app                                                │
            │ COPY --from=builder /root/.local /home/anihpj/.local        │
            │ COPY . .                                                    │
            │ RUN chown -R anihpj:anihpj /app                             │
            │ USER anihpj                   # Run as non-root             │
            │ ENV PATH=/home/anihpj/.local/bin:$PATH                      │
            │ CMD ["gunicorn", "anihpj.wsgi:application",                 │
            │      "--bind", "0.0.0.0:8000", "--workers", "4"]            │
            └──────────────────────────────────────────────────────────────┘

            Key decisions in this Dockerfile:
            — Multi-stage: builder stage keeps final image small (no build tools)
            — Non-root user: anihpj user created for security (Pod Security compliance)
            — Gunicorn: production WSGI server with 4 workers (not manage.py runserver)
            — Layer caching: requirements.txt copied FIRST for Docker layer caching

            — Volumes: live code mounting for hot-reload during development

    Ch 5: Docker Deep Dive for Platform Engineers
        ─── CHAPTER OVERVIEW ───
        Docker is the foundation of modern containerization. As a platform engineer, you
        need to understand Docker beyond `docker run` — you must know how images are built,
        how layers are cached, how registries work, how to scan for vulnerabilities, and
        how to choose the right container runtime. We'll build the anihpj Docker image

        5.1 Why Containers? — The "Works on My Machine" Problem Solved
            • The problem: "It works on my laptop" → fails in production (different OS,
              different Python version, missing system libraries)
            • Containers package your app + ALL dependencies (runtime, system tools,
              libraries, settings) into one lightweight, portable unit
            • The Docker promise: "Build once, run anywhere" — same image runs on your
              laptop, on-prem server, AWS ECS, or Kubernetes
            • For platform engineers: Containers are the STANDARD unit of deployment —
              every platform tool you'll deploy (Argo CD, Prometheus, Kyverno) runs as a container

        5.2 Containers vs Virtual Machines — Technical Comparison
            • VMs: Each VM has its own guest OS kernel → heavy (GBs), slow boot (minutes),
              excellent isolation
            • Containers: Share the host OS kernel → lightweight (MBs), fast start (seconds),
              process-level isolation
            • Key trade-off: Containers are faster/lighter, VMs offer stronger isolation
            • Platform engineering relevance: You'll run HUNDREDS of containers per node —
              VMs would be completely impractical

        5.3 Docker Architecture — Daemon, Client, Registry, Images, Containers
            • Docker Daemon (dockerd): The background service that manages images,
              containers, networks, and volumes
            • Docker Client (docker CLI): The command you type (docker build, docker run) —
              sends REST API calls to the daemon
            • Registry: Where images are stored and shared (Docker Hub, ECR, Harbor)
            • Image: A read-only template with instructions for creating a container
              (built from Dockerfile, consists of layers)
            • Container: A runnable instance of an image — has its own filesystem,
              networking, and process space
            • Dockerfile → docker build → Image → docker push → Registry → docker pull → docker run → Container

        5.4 Image Layers and Caching — Multi-Stage Builds
            • Each instruction in a Dockerfile (FROM, RUN, COPY) creates a new layer
            • Layers are cached — if a layer hasn't changed, Docker reuses it (FAST)
            • COPY requirements.txt BEFORE COPY . . → pip install layer is cached
              → ONLY rebuilds when requirements.txt changes (rare), not source code changes (frequent)
            • Multi-stage build: Use one image for building (with compilers, build tools)
              and copy only the artifacts to a minimal runtime image (smaller, more secure)

            • docker build -t <name>:<tag> . — Build an image from Dockerfile
            • docker run -d -p <host>:<container> <image> — Run container detached
            • docker ps / docker ps -a — List running / all containers
            • docker logs <container> — View container logs

            • docker system prune -a — Clean up ALL unused images/containers/volumes

        5.7 Container Registries — Docker Hub, ECR, Harbor, GHCR
            • Docker Hub: Default public registry — good for open-source, rate-limited for free tier
            • Amazon ECR: AWS-native, IAM-integrated, per-account — good for AWS shops
            • Harbor: Self-hosted, vulnerability scanning, RBAC, replication — good for enterprise
            • GHCR (GitHub Container Registry): Tied to GitHub repos, OIDC auth — good for GitHub Actions
            • Image naming: <registry>/<namespace>/<image>:<tag>
              Example: 123456789012.dkr.ecr.us-east-1.amazonaws.com/anihpj:v1.0.0

        5.8 Image Scanning — Trivy, Grype, Docker Scout
            • Why scan? — 87% of container images have HIGH or CRITICAL vulnerabilities
            • Trivy (Aqua Security): Fast, comprehensive, scans OS packages + language deps
              — `trivy image anihpj:latest` — shows all CVEs with severity
            • Grype (Anchore): Similar to Trivy, good SBOM generation
            • Docker Scout: Built into Docker Desktop, CI/CD integration
            • Scanning in CI/CD: Block image push if CRITICAL CVEs found
            • CNPE exam relevance: Domain 5 (Security) tests image scanning in pipelines

        5.9 Container Runtimes — containerd, CRI-O, gVisor, Kata
            • containerd: Default K8s runtime, CNCF graduated, used by Docker under the hood
            • CRI-O: Lightweight, OCI-compliant, Red Hat's preferred runtime for OpenShift
            • gVisor (Google): User-space kernel, strong isolation (syscall filtering)
            • Kata Containers: Lightweight VMs for container isolation (hardware virtualization)
            • The CRI (Container Runtime Interface): K8s abstraction layer — any CRI-compliant
              runtime works with K8s (containerd, CRI-O, etc.)
            • Platform engineering: Choose runtime based on security requirements —
              gVisor/Kata for multi-tenant/multi-team platforms with untrusted workloads

        like the anihpj example, push images to registries like ECR/Harbor, scan them with
        Trivy, and choose runtimes like containerd or gVisor based on security requirements.
        These containers are the BUILDING BLOCKS that Kubernetes orchestrates — which
        we'll dive into next.

    Ch 6: Kubernetes Architecture for Platform Engineers
        ─── CHAPTER OVERVIEW ───
        Kubernetes is the orchestration engine that every cloud native platform runs on.
        This chapter covers the full cluster architecture: control plane components (API
        server, etcd, scheduler, controller manager), worker node components (kubelet,
        kube-proxy, container runtime), the pod creation journey, the networking model,
        etcd as the cluster's "brain," and static pods. Understanding this architecture
        is CRITICAL — 15% of the CNPE exam tests platform architecture.

        6.1 Cluster Architecture Overview — Control Plane + Worker Nodes
            • Control Plane: The "brain" — makes global decisions, responds to cluster events
            • Worker Nodes: The "muscle" — runs the actual application workloads (pods)
            • Communication: Everything goes through the API server — kubectl, kubelet,
              controllers all talk to kube-apiserver

        6.2 Control Plane Components — Deep Dive
            • kube-apiserver: The "front door" — REST API that ALL components use
              — Validates and configures data for API objects (pods, services, etc.)
              — Horizontal scaling: Run multiple API servers behind a load balancer
            • etcd: The "memory" — distributed key-value store holding ALL cluster state
              — Consistent, highly-available (Raft consensus algorithm)
              — If etcd is lost, the cluster is lost — BACK IT UP!
              — CNPE exam: etcd backup and restore is explicitly tested
            • kube-scheduler: The "placement engine" — decides which node runs a new pod
              — Factors: resource requests, affinity/anti-affinity, taints, node capacity
              — No scheduler = pods stay Pending forever
            • kube-controller-manager: The "reconciliation engine" — runs controller loops
              — Node controller, Replication controller, Endpoints controller, ServiceAccount
                controller — each watches cluster state and drives it toward desired state

        6.3 Worker Node Components — Deep Dive
            • kubelet: The "node agent" — ensures containers are running in a Pod
              — Registers node with API server, watches for PodSpecs, reports status
              — If kubelet is down, pods on that node show Unknown/NotReady
            • kube-proxy: The "network proxy" — implements Service abstraction
              — Maintains network rules (iptables/IPVS) on each node
              — Routes traffic to the correct pod based on Service selectors
            • Container Runtime: The "engine" — actually runs the containers
              — containerd (default), CRI-O, or others via CRI
              — Pulls images, starts/stops containers, reports status to kubelet

        6.4 How a Pod Gets Created — The Full Journey
            Step 1: `kubectl apply -f pod.yaml` → API server receives request
            Step 2: API server authenticates, authorizes, validates, writes to etcd
            Step 3: Scheduler watches for unassigned pods → finds best node → binds pod to node
            Step 4: kubelet on the target node watches for assigned pods → tells container runtime
            Step 5: Container runtime pulls image, creates container, starts it
            Step 6: kubelet reports pod status back to API server → etcd updated

        6.5 Cluster Networking Model — Pod-to-Pod, Pod-to-Service, External
            • Every pod gets its own IP address (CNI plugin assigns it)
            • All pods can communicate with all other pods without NAT (flat network)
            • CNI plugins (Calico, Cilium, Flannel) implement this model
            • Service provides stable DNS and IP for a set of pods
            • kube-proxy programs iptables/IPVS rules for Service load balancing

        6.6 etcd — The Cluster Database (Critical for Platform Engineers)
            • etcd stores: All K8s objects (pods, services, configmaps, secrets, RBAC, etc.)
            • Raft consensus: Requires majority (quorum) of members to agree on writes
            • 3-node etcd cluster tolerates 1 failure, 5-node tolerates 2
            • Backup: `etcdctl snapshot save snapshot.db` — saves entire cluster state
            • Restore: `etcdctl snapshot restore snapshot.db` — recovers from backup
            • CNPE exam: Expect a task to backup/restore etcd

        6.7 Static Pods and Control Plane Management
            • Static Pods: Pods managed directly by kubelet, not by API server
            • Control plane components (api-server, etcd, scheduler, controller-manager)
              run as static pods in kubeadm clusters
            • Located at: /etc/kubernetes/manifests/ — kubelet watches this directory
            • If you edit the manifest file, kubelet restarts the pod automatically
            • CNPE exam: You may need to fix a broken control plane component by editing static pod manifests

    Ch 7: Core Kubernetes Objects — Platform Engineer's Toolkit
        ─── CHAPTER OVERVIEW ───
        Every Kubernetes platform is built from the same set of core objects. This chapter
        covers Pods (the smallest unit), ReplicaSets (maintaining count), Deployments
        (managing lifecycle), Services (stable networking), Namespaces (virtual clusters),
        and Labels/Selectors/Annotations (organization). Understanding how these objects
        relate to each other is essential before we tackle platform architecture.

        7.1 Pods — The Smallest Deployable Unit
            • A Pod is a group of one or more containers sharing network and storage
            • Each pod gets its own IP address, shared by all containers inside it
            • Pods are EPHEMERAL — they can be killed and replaced at any time
            • The anihpj-web Pod: Contains Nginx container + Gunicorn/Django container

        7.2 ReplicaSets — Maintaining Pod Count
            • ReplicaSet ensures a specified number of pod replicas are running at all times
            • If a pod crashes, the ReplicaSet creates a replacement
            • Uses label selectors to identify which pods it manages
            • You rarely create ReplicaSets directly — Deployments manage them for you

        7.3 Deployments — Managing Application Lifecycle
            • Deployment provides declarative updates for Pods and ReplicaSets
            • Rolling updates: Gradually replace old pods with new ones (zero downtime)
            • Rollback: `kubectl rollout undo deployment/anihpj-web` — instant revert
            • The anihpj-web Deployment: 3 replicas, rolling update strategy, resource limits

        7.4 Services — Stable Network Endpoints
            • Pod IPs change when pods are replaced — Services provide a stable IP and DNS
            • ClusterIP: Internal-only (default) — anihpj-web can reach anihpj-db via Service
            • NodePort: Exposes service on each node's IP at a static port (30000-32767)
            • LoadBalancer: Provisions external cloud load balancer (AWS NLB/ALB)
            • Service DNS: anihpj-web-svc.anihpj.svc.cluster.local

        7.5 Namespaces — Virtual Clusters for Multi-Tenancy
            • Namespaces partition cluster resources between multiple users/teams
            • Each team gets their own namespace with quotas, RBAC, and network policies
            • Platform engineering: Namespace-as-a-Service — devs request a namespace and
              get it pre-configured with quotas, RBAC, and monitoring

        7.6 Labels, Selectors, and Annotations
            • Labels: Key-value pairs for organizing objects (app: anihpj, tier: frontend)
            • Selectors: Query objects by labels (kubectl get pods -l app=anihpj)
            • Annotations: Non-identifying metadata (build-info, git-commit, contact-email)
            • Labels are the GLUE that connects K8s objects — Services select pods by labels

        7.7 ConfigMaps and Secrets
            • ConfigMap: Non-sensitive configuration (environment variables, config files)
            • Secret: Sensitive data (passwords, tokens, keys) — base64 encoded, but NOT encrypted by default
            • Mount as: Environment variables OR files in the pod's filesystem
            • anihpj ConfigMap: Django settings (DEBUG, ALLOWED_HOSTS, DB_HOST)
            • anihpj Secret: DB_PASSWORD, SECRET_KEY, REDIS_PASSWORD

    Ch 10: Networking Architecture for Platforms
        ─── CHAPTER OVERVIEW: Networking is the circulatory system of your platform. Every pod-to-pod,
        pod-to-service, and external-to-service communication flows through the networking layer. ───

        10.1 Kubernetes Networking Model: Every pod gets unique IP, all pods communicate without NAT,
            nodes and pods share the same network space without translation
        10.2 CNI Plugins: Calico (BGP, NetworkPolicy), Cilium (eBPF, service mesh), Flannel (simple overlay),

        10.8 Network Policies: Pod-level firewall. Ingress rules (who can talk TO my pod), Egress rules

        14.5 Tekton: K8s-native — Task (single step), Pipeline (sequence of Tasks), Trigger

        14.6 Argo Workflows: DAG or step-based workflow engine — great for data pipelines and ML
        14.7 Image Building: Kaniko (no Docker daemon needed), Buildah (daemonless), Buildpacks

    Ch 16: Progressive Delivery Strategies
        ─── CHAPTER OVERVIEW: How to deploy safely. Rolling updates, Blue/Green, Canary, A/B
        testing — each strategy reduces risk in different ways. CNPE tests progressive delivery
        as part of Domain 2 (GitOps & CD — 25%). ───

        16.1 Rolling Update: Gradually replace old pods (maxSurge=1, maxUnavailable=0). Default
            K8s Deployment strategy. Zero downtime but brief moment of mixed versions.
        16.2 Blue/Green: Two complete environments. Blue = current prod, Green = new version.
            Switch Service selector to Green. Instant rollback (switch back to Blue). Requires 2x resources.
        16.3 Canary: Route small % of traffic to new version. 5% → monitor → 25% → monitor →
            50% → 100%. Auto-rollback if error rate spikes. Most sophisticated strategy.
        16.4 A/B Testing: Route users to versions based on headers/cookies. Not about safety —
            about testing features with real users.
        16.5 Argo Rollouts: Replacement for Deployment. Supports BlueGreen + Canary + AnalysisRuns
            (query Prometheus during rollout, auto-promote or abort).
        16.6 Flagger: Progressive delivery operator that works WITH Deployments (no need to
            replace them). Integrates with Istio, Linkerd, NGINX, Contour.
        16.7 Deployment Safety: Readiness probes (when is pod ready for traffic), Liveness probes
            (when to restart), PDBs (min available during voluntary disruptions).
        16.8 Feature Flags: LaunchDarkly, OpenFeature — decouple deploy from release. Code is
            deployed but feature is toggled OFF until ready.
        16.9 Dark Launching: Send real production traffic to new version but DISCARD the response.
            Test behavior under real load without affecting users.

    Ch 17: Container Registries & Image Management
        ─── CHAPTER OVERVIEW: Where your container images live, how they're pulled, scanned,
        and promoted. Registries are the "app store" for your platform. ───

        17.1 Registries: Docker Hub (public, rate-limited), ECR (AWS-native, IAM), Harbor
            (self-hosted, scanning, RBAC), GHCR (GitHub-integrated, OIDC), Quay (Red Hat)
        17.2 Pull Policies: Always (check registry every time), IfNotPresent (use cached if exists),
            Never (only use local images — good for air-gapped)
        17.3 ImagePullSecrets: K8s Secret of type docker-registry — authenticates to private registries
        17.4 Digest Pinning: Use sha256:abc123... instead of :v1.0.0. Prevents TOCTOU — tag
            could point to different image between scan and deploy
        17.5 :latest Dangers: Unpredictable (what version is :latest today?), non-reproducible
            (deployment yesterday vs today uses different images), untraceable (which git commit?)
        17.6 Lifecycle Policies: Auto-delete old images (keep last N, delete images older than X days)
        17.7 Replication: Mirror images to multiple regions (ECR cross-region replication) for
            faster pulls and disaster recovery
        17.8 Caching: Pull-through cache (registry proxies from upstream), Harbor proxy cache
            (reduce egress costs, faster pulls)
        17.9 Scanning: Trivy (CLI + CI integration), Clair (Harbor built-in), ECR Scan (AWS native).
            Block deployment on CRITICAL CVEs.
        17.10 Promotion: Dev registry → scan → promote to staging registry → smoke tests →
             promote to production registry. Each registry has different access controls.
