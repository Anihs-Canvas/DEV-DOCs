═══════════════════════════════════════════════════════════════════════
Before diving into the exam domains, this section builds your security
mental model. Essential for novices; useful refresher for everyone.

F.1 What Is Kubernetes Security & Why Does It Matter?
    • The Shared Responsibility Model — where Kubernetes ends and YOU begin
    • The "4 Cs of Cloud Native Security": Cloud → Cluster → Container → Code
    • The attack surface: API server, etcd, kubelet, container runtime, network
    • Real-world breaches: Tesla cryptojacking, Shopify rogue insider, Capital One SSRF
    • CKS exam philosophy: "Assume breach" thinking vs "trust but verify"
    • Why anihpj/jobpost is your target: Django + PostgreSQL + Redis — a real attack surface
    🟢 Novice

F.2 Security Terminology — The Lexicon You MUST Know
    • CIS Benchmarks, CVEs, CVSS scores, Zero-Day, Exploit vs Vulnerability
    • OPA (Open Policy Agent), Kyverno, Falco, Trivy, Grype, Cosign, Sigstore
    • mTLS (mutual TLS), TLS termination, Certificate Authorities (CA), PKI
    • Pod Security Standards (PSS): Privileged, Baseline, Restricted
    • Security Context, seccomp, AppArmor, SELinux, capabilities, syscalls
    • SBOM (Software Bill of Materials), SLSA framework, image immutability
    • Admission Controllers: Mutating vs Validating, webhooks, PSA (Pod Security Admission)
    • Audit Logs, Audit Policy, SIEM, threat detection, runtime security
    • eBPF (Extended Berkeley Packet Filter) — the kernel observability revolution
    🟢 Novice

F.3 The Kubernetes Attack Surface — Where Threats Live
    • External Attack Vectors: API server (6443), kubelet (10250), etcd (2379), exposed dashboards
    • Internal Attack Vectors: Compromised pod → lateral movement → ServiceAccount abuse
    • Supply Chain: Malicious images, poisoned dependencies, compromised registries
    • Network: East-West traffic (pod-to-pod), North-South (external-to-cluster)
    • Identity: ServiceAccount tokens, kubeconfig theft, RBAC misconfiguration
    • Data: Secrets in env vars, etcd unencrypted, logs leaking credentials
    • The "Crown Jewels" in anihpj/jobpost: PostgreSQL data (PII), Django SECRET_KEY, API tokens
    🟢 Novice | 🟡 Intermediate: Attack path diagrams, MITRE ATT&CK for Kubernetes matrix

F.4 anihpj/jobpost — The Application Under Attack
    • Full architecture diagram — where security controls apply at each layer
    • Django web tier: Static file serving, CSRF/XSS protections, session management
    • Django API tier: REST Framework auth, JWT tokens, rate limiting, CORS
    • PostgreSQL tier: Connection encryption, pg_hba.conf, audit logging
    • Redis: Password auth, protected mode, TLS (Redis 6+)
    • Dockerfile security: non-root user, distroless base, no secrets in layers
    • Complete file tree with Dockerfile, docker-compose, Kubernetes manifests

  Official CNCF sub-topics per domain (from linuxfoundation.org):
  
  Cluster Setup (15%):
    • Use Network security policies to restrict cluster level access
    • Use CIS benchmark to review the security configuration of Kubernetes
      components (etcd, kubelet, kubedns, kubeapi)
    • Properly set up Ingress with TLS
    • Protect node metadata and endpoints
    • Verify platform binaries before deploying

  Cluster Hardening (15%):
    • Use Role Based Access Controls to minimize exposure
    • Exercise caution in using service accounts e.g. disable defaults,
      minimize permissions on newly created ones
    • Restrict access to Kubernetes API
    • Upgrade Kubernetes to avoid vulnerabilities

  System Hardening (10%):
    • Minimize host OS footprint (reduce attack surface)
    • Using least-privilege identity and access management
    • Minimize external access to the network
    • Appropriately use kernel hardening tools such as AppArmor, seccomp

  Minimize Microservice Vulnerabilities (20%):
    • Use appropriate pod security standards
    • Manage Kubernetes secrets
    • Understand and implement isolation techniques (multi-tenancy,
      sandboxed containers, etc.)
    • Implement Pod-to-Pod encryption (Cilium, Istio)

  Supply Chain Security (20%):
    • Minimize base image footprint
    • Understand your supply chain (e.g. SBOM, CI/CD, artifact repositories)
    • Secure your supply chain (permitted registries, sign and validate
      artifacts, etc.)
    • Perform static analysis of user workloads and container images
      (e.g. Kubesec, KubeLinter)

  Monitoring, Logging and Runtime Security (20%):
    • Perform behavioral analytics to detect malicious activities
    • Detect threats within physical infrastructure, apps, networks, data,
      users and workloads
    • Investigate and identify phases of attack and bad actors within the
      environment
    • Ensure immutability of containers at runtime
    • Use Kubernetes audit logs to monitor access

    │ 🔬 UNDER THE HOOD 1.1: How NetworkPolicy Actually Works         │
    │ (Toggle section — shows iptables/eBPF rule translation)         │
    ├─────────────────────────────────────────────────────────────────┤
    │                                                                 │
    │  When you create a NetworkPolicy, your CNI plugin translates    │
    │  it into actual network rules. Here's what happens:              │
    │                                                                 │
    │  1. kubectl apply -f networkpolicy.yaml                         │
    │  2. API Server validates + stores in etcd                       │
    │  3. CNI controller (Calico/Cilium/Weave) WATCHES for changes    │
    │  4. CNI translates policy → iptables rules or eBPF programs     │
    │                                                                 │
    │  CALICO with iptables (legacy mode):                            │
    │  ┌─────────────────────────────────────────────────────────┐    │
    │  │ iptables -L cali-pi-allow-anihpj-api  (policy chain)   │    │
    │  │ Chain cali-pi-allow-anihpj-api                         │    │
    │  │ target  prot opt source      destination               │    │
    │  │ ACCEPT  tcp  --  anihpj-web  10.244.1.5   tcp dpt:8000│    │
    │  │ DROP    all  --  anywhere    anywhere                   │    │
    │  │ (Default deny at end of chain)                         │    │
    │  └─────────────────────────────────────────────────────────┘    │
    │                                                                 │
    │  CILIUM with eBPF (modern mode):                                 │
    │  ┌─────────────────────────────────────────────────────────┐    │
    │  │ eBPF program attached to pod's veth interface           │    │
    │  │ Policy loaded into BPF map:                             │    │
    │  │ {src_ip: 10.244.1.0/24, dst_port: 8000, action: ALLOW} │    │
    │  │ {src_ip: *,              dst_port: *,    action: DROP}  │    │
    │  │ (evaluated at line rate — no iptables traversal!)       │    │
    │  └─────────────────────────────────────────────────────────┘    │
    │                                                                 │
    │  KEY INSIGHT: NetworkPolicy is just metadata — the CNI does     │
    │  the actual enforcement. If your CNI doesn't support            │
    │  NetworkPolicy (e.g., Flannel without Calico), your policies    │
    │  are STORED in etcd but NEVER ENFORCED. Always verify:          │
    │  kubectl get networkpolicy → kubectl describe → TEST IT.        │
    │                                                                 │

DECISION TREES (15 Security Decision Trees: DT1-DT15)
═══════════════════════════════════════════════════════════════════════
Each decision tree is a flowchart: START at symptom → answer YES/NO →
follow branches → arrive at fix. Structured as Node-based paths.

  DT1: Pod Can't Access Another Pod — NetworkPolicy Debug
       NODE 1: Can pod A curl pod B by IP? → YES=NetworkPolicy not issue (check DNS/Service)
       → NO=NODE 2: kubectl get networkpolicy -n <ns> — any policies selecting pod A or B?
       → NO: CNI doesn't support NetworkPolicy (Flannel without Calico) → Install Calico/Cilium
       → YES=NODE 3: kubectl describe networkpolicy — is ingress allowed from pod A's labels?
       → YES=NODE 4: Is namespaceSelector matching? Are ipBlock CIDRs correct?
       → FIX: Correct selector/labels, add missing allow rule, or create new policy
       anihpj: anihpj-web can't reach anihpj-api:8000 despite NetworkPolicy allowing it

  DT2: TLS Certificate Error — Ingress/Cert-Manager Debug
       NODE 1: Browser shows what error? NET::ERR_CERT_AUTHORITY_INVALID vs ERR_CERT_DATE_INVALID
       → AUTHORITY_INVALID=NODE 2: Is it a self-signed cert? → Check if cert-manager issued it
       → DATE_INVALID=NODE 3: kubectl get certificate -o yaml | grep notAfter — expired?
       NODE 4: kubectl get certificaterequest,order,challenge — stuck at which stage?
       → Challenge pending=NODE 5: Can Let's Encrypt reach your cluster? (HTTP-01/DNS-01)
       → FIX: Fix DNS/Ingress, renew cert, or switch ClusterIssuer to production ACME URL

  DT3: "Forbidden" Error — RBAC Permission Debug
       NODE 1: Who is getting Forbidden? kubectl auth whoami (or check kubeconfig user)
       NODE 2: What action? kubectl auth can-i <verb> <resource> --as=<user> -n <ns>

       → DENIED? = NODE 3: kubectl get rolebinding,clusterrolebinding — any binding for user/SA?
       NODE 4: If binding exists, kubectl describe role <name> — do verbs/resources match?

       → HOST ACCESS=NODE 3: Does pod have privileged:true? hostPath? CAP_SYS_ADMIN?

       NODE 5: ISOLATE: Apply quarantine NetworkPolicy to pod (drop all ingress/egress)
       NODE 6: CAPTURE FORENSICS: kubectl get pod -o yaml > evidence.yaml + snapshot disk
       NODE 7: TERMINATE: kubectl delete pod <compromised> — force delete if stuck
       NODE 8: INVESTIGATE: Check audit logs, Falco alerts, container logs for IOCs
       anihpj: Falco detects xmrig in anihpj-api /tmp — cryptojacking incident response

  Appendix H:  Real-World Security Breaches — Lessons Learned for Kubernetes
       Every breach below maps directly to CKS domains and the security
       controls taught in this document.

       BREACH #1 — TESLA CRYPTOJACKING (2018)
       • What happened: Attackers exploited an unauthenticated Kubernetes
         dashboard exposed to the internet. Deployed crypto mining pods
         that consumed Tesla's AWS resources.
       • Root cause: Dashboard with no authentication, no NetworkPolicy,
         pod could access internet, no runtime detection.
       • CKS preventions:
         → NetworkPolicy: Block external egress from app pods (CS7, Q14)
         → RBAC: Dashboard requires authentication (CH1, Q31)
         → Falco: Detect unexpected process (crypto miner binary) (ML7, Q169)
         → PSA: Restricted profile prevents privileged pods (Q55-Q60)

       BREACH #2 — CAPITAL ONE S3 DATA BREACH (2019)
       • What happened: SSRF attack on a web application allowed attacker
         to access AWS EC2 metadata endpoint (169.254.169.254) and steal
         IAM temporary credentials for an S3 bucket with 100M+ records.
       • Root cause: No metadata endpoint protection, over-privileged IAM role.
       • CKS preventions:
         → NetworkPolicy: Block 169.254.169.254/32 from all pods (CS11, Q19)
         → IRSA: Use pod-level IAM (not node-level), least privilege (Q34, AWS.1)
         → Image scanning: Detect SSRF-vulnerable libraries (Q122, Q149)

       BREACH #3 — SHOPIFY ROGUE INSIDER (2020)
       • What happened: Rogue employee with overly broad cluster-admin
         access exfiltrated customer data from production databases.
       • Root cause: No least-privilege RBAC, no audit logging on Secret
         access, no just-in-time access.
       • CKS preventions:
         → RBAC: Namespace-scoped Roles, no cluster-admin for employees (CH3, Q29)
         → Audit log: Log all Secret access, RBAC changes (ML2, Q193)
         → Break-glass: Temporary, approved, audited access elevation

       BREACH #4 — SOLARWINDS SUPPLY CHAIN ATTACK (2020)
       • What happened: Attackers compromised SolarWinds build system,
         injected malicious code into Orion platform updates. 18,000+
         organizations affected including US government agencies.
       • Root cause: No build attestation, no signed artifacts, no SBOM.
       • CKS preventions:
         → Cosign/Sigstore: Sign all images, verify before deployment (Q140-Q143, SC4)
         → SLSA: Provenance attestation for every build (Q150-Q152, SC16)
         → SBOM: Know every dependency in your image (Q129-Q132, SC5)
         → CI/CD security: Secure build pipeline, no direct internet access (Q153-Q160)

       BREACH #5 — DOCKER HUB CREDENTIAL LEAK (2019)
       • What happened: Docker Hub database breach exposed 190,000 users'
         credentials and GitHub tokens. Autobuild images could be poisoned.
       • Root cause: Centralized registry with insufficient access controls.
       • CKS preventions:
         → Private registries: ECR, Harbor (with auth) instead of public (Q146, SC11)
         → ImagePullSecrets: Authenticate pulls (Q33, CH10)
         → Image digest pinning: Use sha256 not tags (Q126, SC2)

🗂️ HOW KUBERNETES SECURITY OBJECTS RELATE — The Relational Data Model
═══════════════════════════════════════════════════════════════════════
Understanding how security objects connect is critical for CKS. Below
is the relational model showing cardinality (1:1, 1:M, M:M) and how
objects chain together to enforce security.

┌──────────────────────────────────────────────────────────────────────┐
│ RBAC RELATIONSHIPS (Authorization Chain)                              │
│                                                                      │
│  ServiceAccount ──1:M──► RoleBinding ──M:1──► Role                  │
│       │                      │                    │                  │
│       │ (pod identity)       │ (maps SA to Role)  │ (permissions)    │
│       │                      │                    │                  │
│       │               ClusterRoleBinding ──M:1──► ClusterRole        │
│       │               (cluster-wide binding)      (cluster-wide)     │
│                                                                      │
│  EXAMPLE: anihpj-api-sa → RoleBinding:api-pod-reader → Role:pod-r    │
│           ^ServiceAccount     ^binds SA to Role       ^verbs:get,list│
│                                                                      │
│  KEY INSIGHT: 1 ServiceAccount can have MANY RoleBindings.          │
│  1 Role can be referenced by MANY RoleBindings.                      │
│  ClusterRoleBinding works the same but cluster-wide.                 │
│  RBAC is UNION of all bindings — most permissive wins.               │
└──────────────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────────────┐
│ NETWORK POLICY RELATIONSHIPS (Traffic Control Chain)                  │
│                                                                      │
│  Namespace ──1:M──► NetworkPolicy ──M:M──► Pod (via podSelector)    │
│     │                      │                     │                   │
│     │ (scope)              │ (rules)             │ (target)          │
│                                                                      │
│  NetworkPolicy                                                        │
│    └── ingress: [{from: [{podSelector: {app:web}},                   │
│                          namespaceSelector: {name: anihpj},          │
│                          ipBlock: {cidr: 10.0.0.0/8}]}]             │
│                                                                      │
│  KEY INSIGHT: NetworkPolicies are ADDITIVE — multiple policies       │
│  combine. A pod is ISOLATED when ANY policy selects it for that      │
│  direction (ingress/egress). Traffic is the UNION of all allows.     │
│  Selectors use AND within a from/to block, OR across blocks.         │
└──────────────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────────────┐
│ ADMISSION CONTROL CHAIN (Request Pipeline)                            │
│                                                                      │
│  kubectl apply ──► API Server                                        │
│       │              │                                               │
│       │              ├──① Authentication (Token/X509/OIDC)            │
│       │              │    └── Returns: UserInfo{username,groups}     │
│       │              │                                               │
│       │              ├──② Authorization (RBAC)                       │
│       │              │    └── All RoleBindings + ClusterRoleBindings │
│       │              │                                               │
│       │              ├──③ Mutating Admission (in order)              │
│       │              │    └── Kyverno/Gatekeeper → JSONPatch return  │
│       │              │                                               │
│       │              ├──④ Validating Admission (ALL must pass)       │
│       │              │    └── OPA/Gatekeeper → ALLOW/DENY            │
│       │              │    └── PSA → check namespace labels           │
│       │              │                                               │
│       │              └──⑤ Schema Validation → Store in etcd          │
│                                                                      │
│  KEY INSIGHT: Mutating runs BEFORE Validating. If a mutating         │
│  webhook adds securityContext, validating webhooks see the            │
│  MODIFIED object. Order matters.                                     │
└──────────────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────────────┐
│ DEFENSE-IN-DEPTH LAYERING — Where Each CKS Control Applies           │
│                                                                      │
│  LAYER 0: CODE — SAST (Bandit), dependency scan (pip-audit)          │
│     ↓                                                                │
│  LAYER 1: BUILD — Dockerfile hardening, multi-stage, no secrets      │
│     ↓         Trivy scan, SBOM (syft), Cosign sign, Kubesec/KubeLint │
│  LAYER 2: REGISTRY — ECR/Harbor, image scanning, immutability        │
│     ↓         ImagePolicyWebhook, permitted registries (OPA)         │
│  LAYER 3: ADMISSION — PSA, Kyverno mutate, OPA validate              │
│     ↓         ValidatingAdmissionWebhook, MutatingAdmissionWebhook   │
│  LAYER 4: RUNTIME — SecurityContext, seccomp, AppArmor, readOnlyRoot │
│     ↓         RuntimeClass (gVisor/Kata), NetworkPolicy default-deny │
│  LAYER 5: DETECTION — Falco (syscall), Audit logs (API), file int.   │
│     ↓         Tetragon (eBPF), network anomaly, threat intel         │
│  LAYER 6: RESPONSE — Falcosidekick → Slack/PagerDuty, auto-quarant.  │

│                                                                      │
│  ANIHPJ/JOBPOST EXAMPLE — Full defense chain:                        │

│                                                                      │
│  ATTACKER MUST BREAK ALL 7 LAYERS to exfiltrate data.                │

  Appendix L:  CKA ↔ CKS Crossover — What You Already Know (And What's New)
  Appendix M:  ⚡ CKS Exam Day — 20 Security Command Patterns (CRAM SHEET)
       Read this in the 30 minutes before your CKS exam.
       Each pattern includes: The One-Liner + What It Does + When To Use It.

       M.1:  Trivy Scan → Identify CVE → Fix Base Image → Re-scan
             trivy image --severity CRITICAL,HIGH anihpj-api:v2 | grep -E 'CRITICAL|HIGH'
             trivy image --ignore-unfixed anihpj-api:v2  # Only fixable CVEs
             # After fixing: trivy image anihpj-api:v2 --exit-code 1 --severity CRITICAL
             ⚡ SPEED TIP: Use trivy --skip-dirs /usr/local/lib/python3.12 if pip deps clean

       M.2:  Falco Install → Custom Rule → Verify Alert
             helm repo add falcosecurity https://falcosecurity.github.io/charts
             helm install falco falcosecurity/falco --set falco.jsonOutput=true
             # Test: kubectl exec deploy/anihpj-api -n anihpj -- whoami
             # Check: kubectl logs -l app=falco | grep "shell in container"
             ⚡ SPEED TIP: falco --list lists all loaded rules; falco --support shows driver info

       M.3:  etcd Encryption Enable + Verify
             # 1. Create /etc/kubernetes/encryption-config.yaml (aescbc + identity)
             # 2. Mount in kube-apiserver.yaml: --encryption-provider-config
             # 3. Verify: ETCDCTL_API=3 etcdctl get /registry/secrets/anihpj/ --prefix | xxd
             ⚡ SPEED TIP: Always encrypt BEFORE creating Secrets. Rewrite existing: kubectl get secrets --all-namespaces -o json | kubectl replace -f -

       M.4:  NetworkPolicy create + verify (allow + deny)
             kubectl create -f deny-all.yaml  # podSelector: {}
             kubectl run test --rm -it --image=busybox -- sh -c "wget -O- --timeout=2 anihpj-api:8000"
             # Should FAIL → NetworkPolicy working
             # Then add allow rule and test again
             ⚡ SPEED TIP: NetworkPolicy is ADDITIVE. Multiple policies COMBINE. Test BOTH ingress and egress.

       M.5:  RBAC: auth can-i, Role+RoleBinding creation
             kubectl auth can-i get pods --as=system:serviceaccount:anihpj:api-sa -n anihpj
             kubectl create role pod-reader --verb=get,list --resource=pods -n anihpj
             kubectl create rolebinding api-pod-reader --role=pod-reader --serviceaccount=anihpj:api-sa
             ⚡ SPEED TIP: Use kubectl auth can-i --list --as=<user> to audit all permissions

       M.6:  SecurityContext: Full Hardening Recipe
             securityContext:
               runAsNonRoot: true
               runAsUser: 1000
               runAsGroup: 3000
               fsGroup: 2000
               seccompProfile: {type: RuntimeDefault}
               capabilities: {drop: [ALL], add: [NET_BIND_SERVICE]}
               allowPrivilegeEscalation: false
               readOnlyRootFilesystem: true
             ⚡ SPEED TIP: Apply at PodSecurityContext level for all containers; override at container level if one needs different settings (e.g., init container runs as root briefly)

       M.7:  kube-bench run + fix specific CIS checks
             kubectl apply -f https://raw.githubusercontent.com/aquasecurity/kube-bench/main/job.yaml
             kubectl logs job/kube-bench | grep FAIL
             # Fix kubelet anonymous auth: edit /var/lib/kubelet/config.yaml → authentication:anonymous:enabled:false
             ⚡ SPEED TIP: Focus on FAIL items only — WARN and INFO are lower priority

       M.8:  Audit Policy create + verify logging
             # Create /etc/kubernetes/audit-policy.yaml with rules for Secrets, RBAC, exec
             # Mount in kube-apiserver.yaml: --audit-policy-file, --audit-log-path
             # Verify: cat /var/log/kubernetes/audit.log | jq '.user.username, .objectRef'
             ⚡ SPEED TIP: Use RequestResponse level for Secrets (captures the data), Metadata for everything else (smaller logs)

       M.9:  OPA/Gatekeeper ConstraintTemplate + Constraint
             # ConstraintTemplate (once): defines the Rego policy logic
             # Constraint (per-use): applies the template with parameters
             # Example: K8sRequiredLabels → constraint requires label "app" on all pods
             ⚡ SPEED TIP: Test locally first: opa test policy.rego; then kubectl apply --dry-run=server

       M.10: Kyverno validate + mutate pattern
             # Validate: kyverno apply policy.yaml --resource pod.yaml (local test)
             # Mutate: policy adds securityContext if missing
             # kubectl apply -f kyverno-policy.yaml → kubectl run test → verify mutation
             ⚡ SPEED TIP: Kyverno mutate rules show patches in resource annotation; check: kubectl get pod -o yaml | grep kyverno

       M.11: Cosign sign + verify (keyless)
             cosign sign anihpj/anihpj-api:v2.1.0  # Prompts OIDC login (GitHub/Google)
             cosign verify anihpj/anihpj-api:v2.1.0 --certificate-oidc-issuer https://accounts.google.com
             ⚡ SPEED TIP: cosign verify-attestation checks SBOM/provenance; cosign download sbom dumps the SBOM to stdout

       M.12: SBOM generate + CVE check
             syft anihpj/anihpj-api:v2.1.0 -o cyclonedx-json > sbom.json
             grype sbom:sbom.json  # OR: grype anihpj/anihpj-api:v2.1.0 (direct scan)
             ⚡ SPEED TIP: syft + grype = Trivy (Trivy does both in one tool)

       M.13: ImagePolicyWebhook configure + test
             # Create /etc/kubernetes/image-policy-webhook.yaml (kubeconfig to webhook)
             # Add to kube-apiserver: --admission-control-config-file + --enable-admission-plugins=ImagePolicyWebhook
             # Test: deploy pod with image from non-approved registry → should DENY
             ⚡ SPEED TIP: Set failurePolicy: Ignore during testing, Fail only when webhook is verified stable

       M.14: cert-manager + Let's Encrypt + TLS Ingress
             kubectl apply -f https://github.com/cert-manager/cert-manager/releases/latest/download/cert-manager.yaml
             # Create ClusterIssuer (Let's Encrypt prod) → Certificate → Ingress with TLS
             ⚡ SPEED TIP: Use staging issuer first (acme-staging-v02.api.letsencrypt.org) to avoid rate limits during testing

       M.15: Pod Security Admission (PSA) label + enforce
             kubectl label ns anihpj-prod pod-security.kubernetes.io/enforce=restricted
             kubectl label ns anihpj-prod pod-security.kubernetes.io/warn=restricted
             ⚡ SPEED TIP: Apply warn first, check logs, then enforce. Use audit for monitoring without breaking apps.

       M.16: AppArmor profile create + apply + debug
             # Profile in /etc/apparmor.d/container-django
             # pod annotation: container.apparmor.security.beta.kubernetes.io/anihpj-api: localhost/container-django
             # Debug: dmesg | grep -i apparmor OR aa-status | grep anihpj
             ⚡ SPEED TIP: Start in complain mode (aa-complain), check logs, then switch to enforce (aa-enforce)

       M.17: seccomp profile create + apply
             # Profile: {"defaultAction":"SCMP_ACT_ERRNO","architectures":["SCMP_ARCH_X86_64"],"syscalls":[...]}
             # Place in /var/lib/kubelet/seccomp/profiles/
             # Apply: seccompProfile: {type: Localhost, localhostProfile: "django.json"}
             ⚡ SPEED TIP: Use strace -c gunicorn to see which syscalls your app actually needs

       M.18: RuntimeClass gVisor/Kata create + apply
             # kubectl create -f runtimeclass.yaml (handler: runsc for gVisor)
             # Pod: runtimeClassName: gvisor
             # Verify: kubectl exec pod -- dmesg | grep -i gvisor
             ⚡ SPEED TIP: gVisor doesn't support all syscalls — if pod fails, check gVisor compatibility first

       M.19: Falco rule write + test + alert to Slack
             # Rule in /etc/falco/falco_rules.local.yaml
             # Test: falco --rulesfile /etc/falco/falco_rules.local.yaml (validates)
             # Trigger: kubectl exec pod -- /bin/sh -c "curl evil.com"
             ⚡ SPEED TIP: Use falco --list to see all loaded rules, --verbose for detailed event output

       M.20: Full CIS benchmark scan + remediation report
             kube-bench run --targets master,node,etcd,policies --outputfile report.txt
             grep FAIL report.txt | awk '{print NR": "$0}'  # Numbered failure list
             # Fix top 10, re-run, iterate
             ⚡ SPEED TIP: Master+Etcd checks run on control plane; Node checks run on workers; Policies checks cluster-wide

☁️ AWS-SPECIFIC SECURITY PATTERNS (Where Cloud Intersects CKS)
═══════════════════════════════════════════════════════════════════════
These patterns show how AWS services map to CKS security concepts.
Used for illustration where cloud-native patterns apply.

AWS.1 IRSA (IAM Roles for Service Accounts) — Pod-Level AWS Identity
      • Problem: Pods need AWS API access (S3, DynamoDB, Secrets Manager)
        but storing IAM access keys in Secrets is dangerous
      • Solution: IRSA maps a Kubernetes ServiceAccount to an IAM Role
        via OIDC federation. No static credentials.
      • How: SA annotation → OIDC provider → IAM Role trust policy → Pod gets
        temporary credentials via STS. Keys auto-rotate every hour.
      • Used in: CH9 (External Secrets), SC12 (ECR pull), SC19 (CI/CD auth)

AWS.2 ECR (Elastic Container Registry) Security
      • Image scanning on push (Inspector-based): automatic CVE detection
      • Immutable image tags: prevents tag overwrite attacks
      • Repository policy: restrict which IAM principals can push/pull
      • Lifecycle policies: auto-delete old/unused images (reduce attack surface)
      • Cross-account replication: DR + isolated environment testing
      • Used in: CH10 (ImagePullSecret), SC1-SC20 (supply chain), Appendix I

AWS.3 AWS Secrets Manager + External Secrets Operator
      • Secrets stored encrypted in AWS (never in etcd, even encrypted)
      • Automatic rotation via Lambda (e.g., RDS password every 30 days)
      • ExternalSecret CRD maps AWS Secret → Kubernetes Secret
      • IAM + IRSA ensures only authorized pods can read specific secrets
      • Used in: CH9, Q48 (external secrets), S19 (ExternalSecret sync)

AWS.4 AWS KMS for etcd Encryption
      • Instead of storing encryption keys on the control plane node,
        use AWS KMS plugin: all encrypt/decrypt operations go to KMS
      • KMS audit trail: CloudTrail logs every encrypt/decrypt
      • Key rotation: automatic annual rotation or manual on-demand
      • Used in: CH5, Q46 (EncryptionConfiguration)

AWS.5 AWS Signer + Container Image Signing
      • AWS Signer: managed signing service (alternative to self-hosted Cosign)
      • Signing profiles: define who can sign and what validation is applied
      • Integration with ECR: signed images marked as "verified"
      • Used in: SC4, SC16, SC18 (image signing and provenance)

AWS.6 GuardDuty + EKS Runtime Monitoring
      • GuardDuty now supports EKS: detects runtime threats in containers
      • Managed equivalent of Falco: no self-hosted infrastructure
      • Detects: crypto mining, privilege escalation, suspicious API calls
      • Integrates with AWS Security Hub for unified view
      • Used in: ML1-ML20 (runtime detection), Q169-Q178 (Falco)

AWS.7 Network Firewall + Security Groups (Defense in Depth)
      • AWS Network Firewall: L3/L4 filtering at VPC boundary
      • Security Groups: pod-level (via CNI), node-level (EC2)
      • Defense layers: SG (node) → NetworkPolicy (pod) → Network Firewall (VPC)
      • Used in: CS4 (NodePort exposure), CS7 (egress), SH13 (etcd access)

AWS.8 CloudTrail + Audit Logs (Compliance)
      • CloudTrail: all AWS API calls logged (complements K8s audit logs)
      • Combined: "who accessed the Secret?" → K8s audit log
                 "who assumed the IAM role?" → CloudTrail
      • CloudTrail Lake: SQL queries over audit history
      • Used in: ML2, ML9, ML14, Q161-Q168 (audit logging)
