Chapter 1: The 4Cs of Cloud Native Security

The 4Cs is the foundational framework for understanding cloud native security. Every security decision, every tool, every policy fits into one of these four concentric layers: Cloud, Cluster, Container, Code. Think of them as four defensive rings — if an attacker breaks through one, the next ring still protects your application.

🧠 Why Defense-in-Depth Matters — A Real Attack Scenario

Imagine an attacker finds a vulnerability in anihpj's Django code (Code layer). They get a reverse shell inside the container. But because you used readOnlyRootFilesystem and non-root user (Container layer), they can't install tools or escalate. They try to scan the network, but NetworkPolicies (Cluster layer) block all outbound traffic except to the API. They try to access cloud resources, but IRSA temporary credentials (Cloud layer) have expired. Four layers. Four failures for the attacker. One protected app. That's defense-in-depth.

🔑 IRSA — IAM Roles for Service Accounts

IRSA lets Kubernetes pods assume AWS IAM roles using OIDC federation — no static AWS credentials in your cluster. The anihpj-web pod gets temporary S3 credentials automatically. This is the right way to give pods cloud access.

❌ WITHOUT IRSA — Hardcoded Credentials

anihpj pod stores AWS_ACCESS_KEY_ID + AWS_SECRET_ACCESS_KEY as K8s Secrets or env vars. If pod is compromised → attacker gets permanent AWS keys. Key rotation requires pod restart.

✅ WITH IRSA — Temporary Credentials via OIDC

Pod has NO AWS credentials. K8s projects a JWT token → AWS STS validates via OIDC → returns temporary creds (15min-12hr). If pod is compromised → creds expire automatically.

🧠 Understanding the Attack Surface

The API Server (port 6443) is the most attacked component. It's the single entry point for all kubectl commands, CI/CD pipelines, operators. If compromised, the attacker owns the cluster. The defense is three-stage: AuthN verifies identity (certificates, tokens, OIDC), AuthZ checks permissions (RBAC with least privilege), Admission Control is the last line — it can reject a pod even if RBAC allowed it. For anihpj production: OIDC via Google Workspace, 3 RBAC roles (dev/ops/viewer), Kyverno blocking privileged pods and :latest tags.

💡 Multi-Stage Build for anihpj

Stage 1 (builder, ~500MB): Install Python deps + compile. Stage 2 (production, ~200MB): Copy ONLY compiled artifacts. Result: smaller image, fewer CVEs, faster pulls. Stage 1 is thrown away — attacker can't exploit build tools.

🧠 Why Containers Are The #1 Attack Vector

Studies show 80% of production images contain HIGH/CRITICAL vulnerabilities. Attackers scan registries for known CVEs. For anihpj: Trivy scans EVERY image — CVSS ≥ 7 = BLOCK. We use distroless Python (no shell, no package manager, no curl). Even if attacker gets code execution, they can't download tools. Minimal images aren't just smaller — they're fundamentally more secure. Also: never put secrets in Dockerfiles (layer history forever), use digests not tags, sign with Cosign so Kyverno verifies at admission.

1.5 Code Security (Layer 4) — Deep Dive

The innermost layer — your application code. This is where most breaches originate. SAST analyzes source code for security flaws. DAST tests the running application. SCA scans dependencies for known CVEs. Secrets detection finds accidentally committed credentials.

🧠 Code Security Is Not Optional — Here's Why

In 2024, supply chain attacks grew 200%. Attackers target open-source dependencies (remember log4shell?), inject malicious code into popular packages, and scan public repos for leaked credentials. For anihpj/jobpost Django: Bandit scans Python code for SQL injection, hardcoded passwords, unsafe deserialization. Snyk/Dependabot checks requirements.txt against CVE databases. truffleHog scans every git commit for accidentally committed secrets. pre-commit hooks block pushes that contain AWS keys or passwords. All of this runs BEFORE the Docker image is even built — catching issues at the cheapest possible stage.

⏱️ 10 Questions | Ch 1
Q1: Which of the 4Cs includes image scanning with Trivy?
  1. Cloud
  2. Cluster
  3. Container
  4. Code
✅ Answer

Answer: 3. Container (3rd C). Image scanning with Trivy/Grype analyzes container images for known CVEs — this is a Container-layer control. Don't confuse with Code layer (4th C) which covers SAST (static analysis of source code), dependency scanning, and secrets detection. The 4Cs go: Cloud→Cluster→Container→Code — image scanning sits firmly in the Container ring.

Q2: In the shared responsibility model, who secures the Kubernetes API Server?
  1. The cloud provider
  2. You (the customer)
  3. Both equally
  4. The CNCF
✅ Answer

Answer: 2. You (the customer). Even on managed K8s like EKS/AKS/GKE, the API Server security configuration is YOUR responsibility. The cloud provider: keeps the API server RUNNING (availability, patches, etcd replication). You must configure: authentication method (OIDC? certs?), RBAC policies, etcd encryption (EncryptionConfiguration), audit logging, public/private API endpoint. The provider manages the engine — you're the driver who decides where the car goes and who can ride.

Q3: IRSA (IAM Roles for Service Accounts) belongs to which layer?
  1. Cloud
  2. Cluster
  3. Container

2.2 Identity & Access Management (IAM)

4.1 Namespace Isolation

Namespaces are K8s' primary logical isolation mechanism. They don't provide true security isolation by themselves — a pod in namespace A can reach a pod in namespace B unless you add NetworkPolicies. Namespace + ResourceQuota + LimitRange + NetworkPolicy = real isolation.

🧠 Namespaces Are Soft Boundaries — Don't Be Fooled

A common beginner mistake: "I put the DB in the 'db' namespace, so the web app can't reach it." Wrong. By default, any pod can reach any other pod across namespaces. Namespaces only organize resources — they don't isolate network traffic. You need: (1) NetworkPolicy with podSelector/namespaceSelector to block cross-namespace traffic, (2) ResourceQuota to prevent one namespace from consuming all cluster resources, (3) LimitRange to enforce default CPU/memory limits per container, (4) RBAC to control who can deploy to each namespace. For anihpj: prod namespace has strict NetworkPolicy (web→api→db ONLY), staging is fully isolated from prod, and monitoring namespace can scrape metrics but can't modify anything.

4.2 Container Isolation

Linux provides 7 namespace types that isolate processes. seccomp filters system calls. AppArmor/SELinux provides mandatory access control. Together they prevent container escape.

⚠️ Never run privileged containers!

A privileged container bypasses ALL isolation, has access to ALL host devices, can load kernel modules. Use PSS Restricted + drop ALL capabilities + seccomp + AppArmor.

anihpj-web — Hardened Pod Security Context
apiVersion: v1
kind: Pod
metadata:
  name: anihpj-web
  namespace: anihpj-prod
spec:
  securityContext:          # Pod-level security
    runAsNonRoot: true      # ❌ Block root containers
    runAsUser: 1000         # Specific non-root UID
    runAsGroup: 3000
    fsGroup: 2000
    seccompProfile:         # System call filter
      type: RuntimeDefault  # Block dangerous syscalls
  containers:
  - name: web
    image: ghcr.io/anihpj/anihpj:v1.0@sha256:abc123
    securityContext:         # Container-level (overrides pod)
      allowPrivilegeEscalation: false  # ❌ No setuid binaries
      readOnlyRootFilesystem: true     # ❌ No writing to /
      capabilities:
        drop: ["ALL"]       # Drop ALL capabilities
        # add: ["NET_BIND_SERVICE"]  # Only if you need port < 1024
      # NEVER: privileged: true  ← this is an exam fail!

KCSA EXAM: Know the difference: pod-level securityContext applies to ALL containers. Container-level overrides pod-level. privileged: true bypasses EVERYTHING — never use it in production. allowPrivilegeEscalation: false blocks setuid binaries from gaining root. readOnlyRootFilesystem: true prevents attackers from installing tools.

4.3 Node Isolation

Use NodeSelectors, Node Affinity, and Taints/Tolerations to isolate sensitive workloads to dedicated nodes. For anihpj, database pods run on nodes with SSD storage and no other tenant workloads.

anihpj-db with node isolation
apiVersion: v1
kind: Pod
metadata:
  name: anihpj-db
  namespace: anihpj-prod
spec:
  # Only schedule on database-dedicated nodes
  nodeSelector:
    workload: database
    storage: ssd
  # Tolerate the database-only taint
  tolerations:
  - key: "dedicated"
    operator: "Equal"
    value: "database"
    effect: "NoSchedule"
  containers:
  - name: postgres
    image: postgres:15-alpine
    securityContext:
      runAsNonRoot: true
      runAsUser: 999
      readOnlyRootFilesystem: true
      capabilities:
        drop: ["ALL"]
      seccompProfile:
        type: RuntimeDefault
---
# Taint the database node (run once per node)
# kubectl taint nodes db-node-1 dedicated=database:NoSchedule
💡 Taints vs NodeSelectors — When to Use Each

NodeSelector: pod SAYS where it wants to run (simple, label-based). Node Affinity: pod says where it PREFERS to run (more flexible, supports In/NotIn/Exists operators). Taints + Tolerations: node REPELS pods unless they explicitly tolerate it (strongest isolation). For anihpj: database nodes are tainted with dedicated=database:NoSchedule — no other workload can land there even accidentally.

4.4 Multi-Tenancy Patterns

Soft multi-tenancy uses namespaces + RBAC + NetworkPolicies within a single cluster — suitable for trusted tenants (teams within the same company). Hard multi-tenancy uses separate clusters per tenant — required for untrusted tenants or strict compliance (PCI-DSS, HIPAA).

🧠 Choosing Your Tenancy Model

Soft = cheaper, easier, fewer clusters to manage. But one compromised namespace could affect others if NetworkPolicies are misconfigured. Hard = expensive, more operational overhead, but STRONG isolation — no shared control plane, no shared etcd. Tools like vcluster (virtual clusters within a namespace) and Capsule (namespace-as-a-service with tenant CRDs) bridge the gap — they give hard-tenancy-like isolation within a single physical cluster by creating virtual control planes per tenant. For anihpj SaaS: each paying customer gets a dedicated namespace with vcluster for API server isolation, but all share the same physical nodes for cost efficiency.

5.4 Admission Control — The Last Line of Defense

🔴 The etcd Threat: Why Encryption is Non-Negotiable

By default, Kubernetes Secrets are stored in etcd as base64-encoded plaintext. Base64 is NOT encryption — it's encoding. Anyone with access to the etcd data directory or a snapshot can read every secret. A single compromised backup file = every database password, API key, and token exposed forever. Always enable EncryptionConfiguration.

6.3 etcd Network Security

etcd should be isolated. Best practice: dedicated nodes or a separate network segment for etcd. Use mTLS for ALL communication — both peer-to-peer (between etcd members on port 2380) and client-to-server (API server to etcd on port 2379). The distinction between peer certificates (etcd-to-etcd) and client certificates (API-server-to-etcd) is important — they serve different purposes and should use different CAs. Firewall rules must allow ONLY the API server IP to reach etcd ports.

6.4 etcd Backup & Disaster Recovery

etcd snapshots are your insurance policy. Automate daily snapshots, encrypt them, and store them off-cluster. Test restoration quarterly — a backup you haven't tested is not a backup.

7.2 Kubelet Hardening

Beyond flags, three key mechanisms lock down the kubelet:

NodeRestriction Admission Controller: This built-in admission plugin ensures a kubelet can only modify its own Node object and the pods bound to it. Without it, a compromised kubelet on node-1 could modify node-2's labels or taints, or delete pods on other nodes — enabling lateral movement. NodeRestriction is enabled by default in kubeadm clusters but should be verified.

Node Authorizer: A special authorization mode that grants kubelets permission based on the pods scheduled to their node. A kubelet on node-1 can only read secrets/configmaps mounted by pods running on node-1 — not secrets from other namespaces or nodes. This is more restrictive than RBAC and specifically designed for kubelet workloads.

TLS Bootstrap: Instead of manually generating and distributing kubelet certificates, TLS bootstrapping lets kubelets automatically request certificates from the API server when they join the cluster. Certificates auto-rotate before expiry. This eliminates the operational nightmare of manually tracking node certificate expiration across hundreds of nodes. For anihpj: all worker nodes use TLS bootstrapping with automatic certificate rotation — zero manual intervention.

7.4 Pod Security Context

The 5 critical securityContext settings form your first defense against container escape. Each one is independent — you need ALL of them:

1. privileged: false — The most dangerous setting. A privileged container has access to ALL host devices (like plugging a USB directly into the server), can load kernel modules, and effectively has root on the host node. Never set this to true. Exam trap: privileged:true bypasses every other security control — even if you set runAsNonRoot, seccomp, and readOnlyRoot, privileged:true overrides them all.

2. allowPrivilegeEscalation: false — Prevents a process from gaining more privileges than its parent. Without this, a non-root process could potentially use a setuid binary to escalate to root. This flag specifically blocks the setuid/setgid mechanism.

3. readOnlyRootFilesystem: true — Makes the container's root filesystem immutable. Attackers cannot install rootkits, download tools, modify /etc/passwd, or plant backdoors. Only mounted volumes (PVCs, Secrets, ConfigMaps) remain writable. Real scenario: If an attacker gets a reverse shell in a read-only container, they can't even install netcat to connect out.

4. runAsNonRoot: true — Ensures the container process runs with a non-zero UID. Combined with a distroless base image (which has no root user), even if the container is compromised, the process has no root privileges on the host. The kubelet will refuse to start a container that tries to run as UID 0.

5. capabilities.drop: ["ALL"] — Linux capabilities grant specific kernel permissions (CAP_NET_RAW for ping, CAP_SYS_ADMIN for mounts, etc.). Dropping ALL removes every special permission. Add back only what's absolutely needed — for example, NET_BIND_SERVICE to bind to privileged ports (<1024) as non-root. The principle: start with nothing, add only what breaks.

KCSA EXAM: These 5 settings are the most-tested on the exam. Memorize them in order: privileged→allowPrivEsc→readOnlyRoot→runAsNonRoot→capabilities.drop. One privileged:true defeats them all.

8.2 Network Policies

NetworkPolicies are Kubernetes' built-in firewall. Without them, Kubernetes has a flat network — every pod can reach every other pod in the cluster, regardless of namespace. This is the #1 security misconception: "my pods are in different namespaces, so they're isolated." They are not. Only NetworkPolicies provide pod-to-pod traffic control.

How NetworkPolicies work: A NetworkPolicy selects pods using podSelector and defines what traffic is allowed IN (ingress) and OUT (egress). They are additive — multiple policies combine their allows. The key selectors are: podSelector (which pods in this namespace), namespaceSelector (pods from matching namespaces), and ipBlock (external CIDR ranges, e.g., 10.0.0.0/8).

The golden rule: Start with a default-deny-all policy, then add specific allow rules. If you only add allow rules without a default-deny, any pod not matched by an allow rule still has unrestricted access. Critical: ALWAYS allow DNS egress (port 53 UDP to kube-system) — if DNS is blocked, nothing works because services can't resolve.

anihpj NetworkPolicy — 3-Tier
# Default deny all ingress
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: {name: default-deny, namespace: anihpj-prod}
spec:
  podSelector: {}
  policyTypes: ["Ingress"]
---
# Allow web → api :8080
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: {name: allow-web-to-api, namespace: anihpj-prod}
spec:
  podSelector: {matchLabels: {tier: api}}
  policyTypes: ["Ingress"]
  ingress:
  - from: [{podSelector: {tier: web}}]
    ports: [{protocol: TCP, port: 8080}]
---

kube-proxy runs on every node managing iptables (default) or IPVS rules for service traffic. IPVS mode scales better for large clusters (uses hash tables vs linear iptables chains). Secure kube-proxy metrics (port 10249) behind localhost. If using eBPF-based CNI (Cilium), kube-proxy can be completely replaced — eliminating its attack surface entirely.

10.1 Authentication Deep Dive

OIDC (OpenID Connect) is the recommended authentication method for human users accessing Kubernetes. The flow: User logs into an Identity Provider (Google Workspace, Azure AD, Dex) → ID Provider issues a signed JWT (JSON Web Token) containing the user's identity and group memberships → kubectl presents this token to the API Server → API Server validates the token's signature against the ID Provider's public keys → extracts username and groups from the token claims → passes them to RBAC for authorization.

Why OIDC over static tokens: Static tokens live in a CSV file on the API server — they never expire, can't be rotated without restarting the API server, and anyone with file access can create admin tokens. OIDC tokens are short-lived (typically 1 hour), support MFA at the ID Provider level, and can be centrally revoked. For anihpj: developers authenticate via Google Workspace with MFA enforced, and their group membership (anihpj-developers, anihpj-ops) determines K8s RBAC role bindings.

ServiceAccount Tokens: Pods authenticate using ServiceAccount tokens — NOT OIDC. Modern K8s uses projected volume tokens (TokenRequest API) which are time-bound (default 1 hour), audience-scoped (only valid for specific API servers), and automatically rotated by the kubelet. Never use the legacy auto-mounted tokens from the default ServiceAccount — they have no expiry and persist forever. Set automountServiceAccountToken: false for pods that don't need API access.

10.2 RBAC Deep Dive

RBAC is built on 4 objects: Role (namespace-scoped permissions), ClusterRole (cluster-wide permissions), RoleBinding (grants a Role or ClusterRole to subjects within ONE namespace), ClusterRoleBinding (grants a ClusterRole across ALL namespaces). The critical distinction: a RoleBinding referencing a ClusterRole grants those cluster-wide permissions ONLY within the binding's namespace — a powerful pattern for giving namespace admins read-only access to cluster-scoped resources (nodes, PVs) without making them cluster-wide.

Aggregated ClusterRoles: You can compose ClusterRoles using label selectors. Create a ClusterRole with aggregationRule.clusterRoleSelectors — it automatically combines all ClusterRoles matching those labels. This is how the built-in admin/edit/view roles work: they aggregate sub-roles for different API groups. When you create a new CRD and ClusterRole for it, labeling it correctly automatically adds its permissions to admin/edit/view.

Chapter 12: Network Policies & Segmentation

NetworkPolicies are your cluster firewall. Without them, all pods can reach all other pods — zero isolation. This chapter covers K8s NetworkPolicies, CiliumNetworkPolicies, and micro-segmentation patterns.

12.1 Kubernetes Network Policies

NetworkPolicies use podSelector (which pods to apply to), namespaceSelector (which namespaces), ipBlock (CIDR ranges), and specify Ingress (inbound) and Egress (outbound) rules. They're namespace-scoped resources — each namespace needs its own policies.

12.2 Default Deny Policies

Start with default-deny-all ingress and default-deny-all egress. Then add specific allows. Critical: always allow DNS egress (port 53 UDP) — if DNS is blocked, nothing works. For anihpj: default-deny + DNS allow + web→api:8080 + api→db:5432 + web→internet:443.

12.3 Cilium Network Policies

CiliumNetworkPolicies (CNP) extend K8s NetworkPolicies with L7 rules (HTTP method, path, headers), FQDN-based egress (allow api.github.com), identity-based security (not just IP), and DNS-aware policies. For anihpj: CNP allows web→api only at GET /jobs/ — POST/PUT/DELETE blocked at L7.

12.4 Micro-Segmentation

Divide your cluster into security zones: DMZ (ingress), App (pods), Data (databases). Each zone gets its own NetworkPolicy. The principle: if one zone is compromised, the others remain protected. For anihpj: web zone can only reach api zone, api zone can only reach db zone, db zone has NO egress.

Chapter 15: Attack Vectors & Mitigations

This chapter covers the 6 most common Kubernetes attack vectors — from network attacks to privilege escalation to data exfiltration — with specific mitigations for each.

🔴 Advanced⏱️ ~2 hours

🎯 What You'll Learn

  • ✅ The 6 most common K8s attack vectors: network, container, privilege escalation, data, DoS, persistence
  • ✅ Privilege escalation chain: compromised container → privileged pod → host root → cluster
  • ✅ Defense at each step: PSS Restricted, seccomp, readOnlyRoot, NetworkPolicies, ResourceQuota
  • ✅ DoS protections: API Priority and Fairness (APF), rate limiting, resource quotas

15.1 Attacker on the Network

Threats: MITM attacks, network sniffing in flat networks, DDoS against API server. Mitigations: mTLS everywhere, NetworkPolicies, API server rate limiting. For anihpj: Cilium mTLS between services, private API endpoint, network segmentation.

15.2 Compromised Container / Malicious Code

Threats: Container escape (CVEs), reverse shells, cryptominers. Mitigations: seccomp, AppArmor, readOnlyRootFilesystem, non-root user, distroless base images. For anihpj: all containers run non-root, readOnlyRoot, drop ALL capabilities, RuntimeDefault seccomp.

15.3 Privilege Escalation

The most dangerous attack. A single privileged: true gives attacker root on the host. The chain: compromised container → privileged pod → host access → kubelet credential theft → cluster compromise. Stop this at every step: PSS Restricted (no privileged), seccomp (no dangerous syscalls), readOnlyRoot (no installing tools), NetworkPolicy (no lateral movement).

15.4 Access to Sensitive Data

Threats: Reading Secrets from API, accessing etcd directly, stealing SA tokens. Mitigations: etcd encryption, RBAC, short-lived tokens, projected volumes. For anihpj: EncryptionConfiguration with aescbc, SA tokens expire in 1 hour, Secrets mounted as tmpfs.

15.5 Denial of Service (DoS)

Threats: Resource exhaustion (CPU/memory/disk), API server overload, etcd overload. Mitigations: ResourceQuota, LimitRange, PriorityClass, API priority and fairness. For anihpj: each namespace has ResourceQuota, all pods have CPU/memory limits, critical pods get higher PriorityClass.

15.6 Persistence Mechanisms

Threats: Backdoor DaemonSets, malicious webhooks, hostPath mounts, static pods. Mitigations: Admission control (Kyverno/OPA), audit logging, image scanning. For anihpj: Kyverno policies audit all DaemonSet and webhook creations, Falco alerts on unexpected static pods.

18.1 SLSA Framework (Supply-chain Levels for Software Artifacts)

SLSA (pronounced "salsa") is a security framework that defines increasing levels of trust for software artifacts. It answers the question: "Can I trust this binary?" by requiring proof of provenance (where it came from and how it was built) and attestations (cryptographically signed statements about the artifact — who built it, from what source, using what commands).

18.2 Image Signing & Verification

Image signing proves WHO built the image and that it hasn't been tampered with. Cosign (part of Sigstore) enables keyless signing using OIDC — no long-lived keys to manage. The flow: developer pushes code → CI/CD builds image → Cosign signs with OIDC token → admission controller verifies signature before deployment.

🔐 Sign & Verify anihpj Image with CosignBash
# Keyless signing — Cosign uses OIDC (GitHub token) for identity
cosign sign ghcr.io/anihpj/anihpj:v1.0.0

# At deploy time — admission controller verifies
cosign verify \
  --certificate-identity anihpj/.github/workflows/build.yml@refs/heads/main \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  ghcr.io/anihpj/anihpj:v1.0.0

Sigstore (the ecosystem behind Cosign) provides: transparency log (Rekor), certificate authority (Fulcio), and OIDC identity. Together they make signing free, keyless, and auditable. For anihpj: every merged PR triggers a build → Cosign signs → Kyverno verifies before the pod starts.

Notary v2 / Notation is the OCI-native alternative — unlike Cosign (which stores signatures in a separate registry), Notation embeds signatures directly in the OCI image manifest. The KCSA may ask about both: Cosign = Sigstore ecosystem, Notation = OCI-native, integrated into Azure and AWS registries.

18.3 SBOM (Software Bill of Materials)

An SBOM is a machine-readable inventory of every component in your container image — like a nutrition label for software. It lists all packages, libraries, and dependencies. When a new CVE drops (like Log4Shell), you query your SBOM to find affected images instantly instead of scanning every image.

SBOM in CI/CD: Generate SBOM during every build, attach it to the image as an OCI artifact, and store it alongside the image in your registry. This creates a continuous, auditable record. Tools like Syft can run inside GitHub Actions, generating a fresh SBOM on every commit. For anihpj: the CI pipeline generates an SBOM → stores it as a build artifact → uploads it to Dependency-Track for continuous vulnerability monitoring.

📦 Generate SBOM for anihpj with SyftBash
# Generate SBOM in SPDX (ISO) format
syft ghcr.io/anihpj/anihpj:v1.0.0 -o spdx-json > anihpj-sbom.spdx.json

# Generate SBOM in CycloneDX (OWASP) format
syft ghcr.io/anihpj/anihpj:v1.0.0 -o cyclonedx-json > anihpj-sbom.cdx.json

# Scan the SBOM for vulnerabilities
grype sbom:anihpj-sbom.spdx.json

# Docker now has built-in SBOM (experimental)
docker sbom ghcr.io/anihpj/anihpj:v1.0.0

SPDX (ISO/IEC 5962:2021)

The international standard, created by the Linux Foundation. Uses package relationships: DEPENDS_ON, CONTAINS, GENERATED_FROM. Widely used in enterprise compliance.

CycloneDX (OWASP)

Designed for security/risk analysis. Native support for vulnerability disclosure (VEX). Lightweight JSON/XML. Preferred by security tools like Dependency-Track.

18.5 Secure Build Pipelines

A secure build pipeline ensures the artifact that reaches production is the same one that was built from source — with no tampering in between. Key principles: hermetic builds (no network during build), parameterized (no secrets hardcoded), reproducible (same input = same output), signed attestations (proves who built what).

name: Build & Sign anihpj
on: push
permissions:
  id-token: write   # Needed for OIDC
  contents: read
  packages: write
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Build Docker image
        run: docker build -t ghcr.io/${{ github.repository }}:${{ github.sha }} .
      - name: Generate SBOM with Syft
        uses: anchore/sbom-action@v0
        with: { image: ghcr.io/${{ github.repository }}:${{ github.sha }} }
      - name: Sign image with Cosign
        run: cosign sign --yes ghcr.io/${{ github.repository }}:${{ github.sha }}
      - name: Generate SLSA provenance
        uses: slsa-framework/slsa-github-generator/.github/actions/generate@v1
      - name: Push to registry
        run: docker push ghcr.io/${{ github.repository }}:${{ github.sha }}

19.2 Image Best Practices

Every line in your Dockerfile is a potential attack surface. Reduce it relentlessly: multi-stage builds (builder stage compiles, production stage only contains the binary), distroless base images (no shell, no package manager — nothing for an attacker to use), never :latest (use specific SHA256 digests), non-root users (USER 1000, not root).

Rootless containers take this further: the container runtime itself runs without root privileges. User namespaces map container root to an unprivileged host UID. Even if an attacker escapes the container, they land as an unprivileged user on the host — not root. For anihpj: all pods run with runAsNonRoot: true, drop ALL capabilities, and use readOnlyRootFilesystem.

20.2 Falco — Runtime Security Monitoring

Falco is the KCSA's favorite runtime security tool. It monitors Linux syscalls using either a kernel module (traditional, requires kernel headers) or an eBPF probe (modern, safer, no kernel module loading). On every syscall (execve, open, connect, etc.), Falco checks rules and triggers alerts.

Falco architecture: Falco engine (user-space) ← kernel module/eBPF (kernel-space). Rules define: condition (what to detect), output (alert message), priority (DEBUG to CRITICAL), tags (MITRE mapping). Alert outputs go to: stdout (default), file, syslog, webhook (HTTP POST), gRPC, or Falco Sidekick (forwards to Slack, PagerDuty, AWS SNS, etc.).

Built-in rules: Falco ships with 80+ default rules inspired by the CIS Benchmark — detecting things like "shell in a container", "unexpected privileged container", "write below /etc", "change thread namespace". You extend these with custom rules for your specific applications like anihpj.

- rule: Shell in anihpj Container
  desc: Detect bash/sh spawned in anihpj pods

    spawned_process
    and container.name startswith "anihpj"
    and proc.name in (bash, sh, zsh)

  priority: CRITICAL
  tags: [mitre_execution, anihpj]

# Rule: Unexpected outbound network connection
- rule: Unexpected Outbound from anihpj
  desc: Detect connections to unexpected IPs
  condition: >
    outbound
    and container.name startswith "anihpj"

  output: "UNEXPECTED outbound from %container.name to %fd.sip.name"
  priority: WARNING
  tags: [mitre_exfiltration, anihpj]

21.2 mTLS (Mutual TLS)

mTLS = both client AND server present certificates and verify each other. Regular TLS only verifies the server. In a service mesh, mTLS is transparent: the sidecar handles the TLS handshake automatically. Every pod gets an identity based on SPIFFE (spiffe://cluster.local/ns/anihpj/sa/web). This means you can write policies based on service identity, not IP addresses.

21.3 Authorization Policies (Istio)

Istio's AuthorizationPolicy allows fine-grained access control at the mesh level. You can allow/deny based on: service identity (SPIFFE), namespace, HTTP method/path, JWT claims, request headers.

JWT validation at the mesh: Instead of every service validating JWT tokens individually, Istio validates them at the ingress gateway or sidecar. The AuthorizationPolicy can check JWT issuer, audience, and custom claims — rejecting invalid tokens before they reach your application. For anihpj: the mesh validates that the JWT contains {"group": "anihpj-users"} before allowing access to the API.

Rotate mesh certificates regularly (default 24h in Istio — it's automatic). Monitor the mesh with Kiali (traffic visualization), Jaeger (distributed tracing), and Grafana (mesh metrics). For anihpj: strict mTLS + deny-all default + explicit allows for web→api, api→db.

22.2 cert-manager

cert-manager automates TLS certificate lifecycle in Kubernetes: request, renew, and revoke. It uses Issuer (namespace-scoped) and ClusterIssuer (cluster-scoped) CRDs. Certificates auto-renew before expiry — no more midnight "cert expired" pages.

22.3 Certificate Security Best Practices

Short-lived certificates (90 days or less) limit the damage window if a cert is compromised — cert-manager auto-renews them. Separate CAs for etcd, kubelet, and front-proxy — the cluster CA should NOT sign etcd certs. This way, compromise of one CA doesn't affect others. Private key protection: never store private keys in Git; use Kubernetes Secrets (encrypted at rest) or external KMS/Vault. Certificate revocation: cert-manager doesn't have built-in revocation (CRL/OCSP) — for production enterprise PKI, use HashiCorp Vault or Venafi which support full lifecycle including revocation.

⚠️ Certificate Expiry = Cluster Outage

If the API server certificate expires, kubectl stops working. If etcd peer certs expire, etcd loses quorum. Always monitor: kubeadm certs check-expiration and set Prometheus alerts at 30, 14, and 7 days before expiry. cert-manager auto-renews but you still need to MONITOR that renewal succeeded.

23.1 Overview of Compliance

Compliance = meeting regulatory, contractual, or industry requirements. Security = protecting confidentiality, integrity, and availability. You can be secure without being compliant (you encrypt data but can't prove it). You can be compliant without being secure (checkbox exercise without real protection). The goal: both.

Why compliance matters: Legal — GDPR fines up to 4% of global revenue. HIPAA violations = criminal charges. PCI-DSS non-compliance = losing the ability to process credit cards. Contractual — enterprise customers require SOC 2 reports before signing. Government contracts require FedRAMP. Trust — compliance certification is a market signal that you take security seriously.

The shared responsibility model applies to compliance too: the cloud provider certifies the infrastructure (AWS gets FedRAMP, not you). You certify what you deploy on it (your app, your configurations, your processes). In managed K8s: the provider handles control plane compliance; YOU handle pod security, RBAC, NetworkPolicies, encryption, and audit logging.

📎 Appendix D: Troubleshooting Security IssuesReference

Common security problems and their solutions — what to check when things break.

D.1 RBAC Issues

⚠️ "Error from server (Forbidden): pods is forbidden"

Problem: User/SA doesn't have permission for the requested action.

Diagnose:

kubectl auth can-i create pods --as=problem-user -n anihpj
kubectl auth can-i --list --as=problem-user -n anihpj
kubectl describe rolebinding -n anihpj | grep problem-user

Common causes: Typo in RBAC resource name, wrong namespace, SA not bound, ClusterRole used when Role needed (or vice versa). Fix: Verify RoleBinding subjects match the SA, verify verbs and resources are correct.

D.2 NetworkPolicy Issues

⚠️ "Connection refused" / "Connection timeout" between pods

Problem: NetworkPolicy blocking traffic, or no CNI supporting NetworkPolicy.

Diagnose:

kubectl get netpol -n anihpj                                          # List all policies
kubectl describe netpol allow-web-to-api -n anihpj                    # Check rule details
kubectl run test-pod --image=busybox --rm -it -- wget -O- http://anihpj-api:8080  # Test connectivity

Common causes: Default-deny blocks all traffic, missing DNS egress (port 53 UDP), wrong podSelector labels, no CNI that supports NetworkPolicy (Calico, Cilium, Weave). Fix: Always allow DNS egress, verify pod labels match selectors, confirm CNI supports NetworkPolicy.

D.3 Certificate Issues

⚠️ "x509: certificate has expired" / "Unable to connect to the server: x509"

Problem: Certificate expired or invalid. kubectl stops working if API server cert expires.

Diagnose:

kubeadm certs check-expiration                           # Check all cert expiry dates
openssl x509 -in /etc/kubernetes/pki/apiserver.crt -noout -dates  # Inspect specific cert
kubectl get certificates -A                              # cert-manager managed certs

Common causes: Cert expired (kubeadm certs last 1 year by default), wrong CA, time synchronization issues. Fix: Renew with kubeadm certs renew all, let cert-manager auto-renew, or manually generate new certs.

D.4 Audit Log Issues

⚠️ "No audit logs found" / "Audit logs flooding disk"

Problem: Audit logging not enabled, or logging too much causing disk pressure.

Diagnose: Check API server flags: --audit-policy-file and --audit-log-path must both be set. Check --audit-log-maxage, --audit-log-maxbackup, --audit-log-maxsize for rotation.

Common causes: Audit policy with RequestResponse level on all resources floods disk. Fix: Use Metadata level for most resources, RequestResponse only for Secrets access.

D.5 Admission Control Issues

⚠️ "Error: admission webhook denied the request" / Pod stuck "Pending"

Problem: Admission webhook (OPA/Kyverno/PSA) rejecting or blocking pod creation.

Diagnose:

kubectl describe pod failing-pod -n anihpj | grep -A10 Events
kubectl get validatingwebhookconfigurations,mutatingwebhookconfigurations
kubectl describe ClusterPolicy check-images                     # Kyverno
kubectl get constraint -A                                       # OPA/Gatekeeper

Common causes: Policy too strict, PSA enforce mode blocking pod, webhook service unreachable. Fix: Check webhook is running, review policy message in the error, temporarily use warn/audit mode instead of enforce.

D.6 Troubleshooting Decision Tree

1
Error message says "Forbidden" or "cannot"

→ RBAC issue (D.1). Check: kubectl auth can-i

2
Pods can't communicate / timeout

→ NetworkPolicy issue (D.2). Check: kubectl get netpol -A

3
kubectl won't connect / TLS error

→ Certificate issue (D.3). Check: kubeadm certs check-expiration

4
No audit trail / can't investigate

→ Audit log issue (D.4). Check: API server --audit-log-path flag

5
Pod stuck creating / webhook denied

→ Admission control issue (D.5). Check: describe pod → Events

This practice test covers every domain with representative questions. Time yourself: 40 minutes for 20 questions.

F.1 Overview of Cloud Native Security (14% — Questions 1-3)

Q1: Which of the 4Cs covers seccomp, AppArmor, and readOnlyRootFilesystem?
  1. Cloud
  2. Cluster
  3. Container
  4. Code
✅ Answer

3. Container. seccomp, AppArmor, and readOnlyRootFilesystem are container-level security controls (the 3rd C in defense-in-depth).

Q2: In managed K8s (EKS/AKS), who is responsible for encrypting Secrets in etcd?
  1. The cloud provider encrypts everything automatically
  2. You must configure EncryptionConfiguration
  3. Both share equally
  4. etcd doesn't need encryption on managed K8s
✅ Answer

2. You configure it. Managed K8s encrypts the etcd disk, but EncryptionConfiguration for Secrets is YOUR responsibility under shared responsibility.

Q3: Which tool uses eBPF to detect shell spawns in running containers?
  1. Trivy
  2. kube-bench
  3. Falco
  4. Cosign
✅ Answer

3. Falco. Falco uses eBPF/kernel module to monitor syscalls including execve (shell spawns). Trivy scans images, kube-bench checks CIS, Cosign signs images.

F.2 K8s Cluster Component Security (22% — Questions 4-7)

Q4: Which component stores ALL cluster state and must be encrypted at rest?
  1. kube-apiserver
  2. kube-scheduler
  3. etcd
  4. kube-controller-manager
✅ Answer

3. etcd. etcd is the distributed key-value store holding ALL cluster state — Secrets, pods, deployments, everything. Encrypt it.

Q5: The API server should use what TLS configuration?
  1. HTTP only (no TLS)
  2. Server-side TLS only
  3. mTLS — both client and server certificates
  4. No TLS needed — it's all internal
✅ Answer

3. mTLS. The API server requires mutual TLS — it presents a cert AND requires clients (kubectl, kubelet, controllers) to present valid certificates.

Q6: Which admission plugin restricts what objects a kubelet can modify?
  1. PodSecurity
  2. NodeRestriction
  3. AlwaysPullImages
  4. LimitRanger
✅ Answer

2. NodeRestriction. NodeRestriction limits kubelets to modifying only their own Node object and the pods bound to them — prevents a compromised kubelet from modifying other nodes.

F.3 K8s Security Fundamentals (22% — Questions 7-10)

Q7: By default, how are Secrets stored in etcd?
  1. AES-256 encrypted
  2. Base64-encoded plaintext
  3. bcrypt hashed
  4. Not stored in etcd at all
✅ Answer

2. Base64 plaintext. Default Secrets are base64-ENCODED (NOT encrypted). Base64 is encoding, not encryption. Always enable EncryptionConfiguration.

Q8: A RoleBinding in namespace 'anihpj' can reference which type(s) of role?
  1. Only a Role in the same namespace
  2. A Role in the same namespace OR a ClusterRole
  3. Only a ClusterRole
  4. RoleBindings reference users, not roles
✅ Answer

2. Role OR ClusterRole. A RoleBinding can bind either a namespaced Role OR a ClusterRole. If you bind a ClusterRole, the permissions only apply within that namespace.

Q9: Without NetworkPolicies, what traffic is allowed between pods?
  1. No traffic — pods are isolated by default
  2. All traffic — K8s has a flat network model
  3. Only same-namespace traffic
  4. Only HTTP traffic
✅ Answer

2. All traffic. K8s has a flat network model — every pod can reach every other pod by default. NetworkPolicies are the firewall that restricts this.

Q10: Which audit policy level captures both the request AND response body?
  1. None
  2. Metadata
  3. Request
  4. RequestResponse
✅ Answer

4. RequestResponse. RequestResponse captures both request and response bodies. Request captures only the request body. Metadata captures who/what/when only.

F.4 K8s Threat Model (16% — Questions 11-14)

Q11: The 'E' in STRIDE stands for what?
  1. Encryption
  2. Elevation of Privilege
  3. Exploitation
  4. Exfiltration
✅ Answer

2. Elevation of Privilege. STRIDE = Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, Elevation of Privilege.

Q12: What does a single privileged:true container allow an attacker to do?
  1. Nothing — it's just a label
  2. Gain root-level access to the host node
  3. Only access that pod's namespace
  4. Only access the container filesystem
✅ Answer

2. Root on the host. privileged:true bypasses ALL container isolation — access to all host devices, can load kernel modules, effectively host root. Always use PSS Restricted.

Q13: In an attack tree, the root node represents what?
  1. A specific exploit technique
  2. The attacker's ultimate goal
  3. A mitigation strategy
  4. A leaf vulnerability
✅ Answer

2. The attacker's goal. Root = ultimate goal (e.g., "Compromise anihpj DB"). Branches = intermediate steps. Leaves = specific attacks. Score each leaf with risk = likelihood × impact.

Q14: A threat with DREAD scores D:10 R:8 E:3 A:10 D:9. How should you prioritize?
  1. Ignore — below threshold
  2. Fix immediately — total score 40/50 is critical
  3. Add to next year's backlog
  4. Accept the risk
✅ Answer

2. Fix immediately. DREAD ≥ 30 = high priority. 40/50 is critical — all users affected, severe damage, easily reproducible, readily discoverable.
