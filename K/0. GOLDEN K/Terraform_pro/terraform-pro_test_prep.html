🚨 Critical Do's & Don'ts During The Exam
  • ✅ DO: Run terraform init as the FIRST command in every task directory. Without providers, nothing works.
  • ✅ DO: Use terraform plan -out=plan.tfplan before every apply. The plan output IS your safety net.
  • ✅ DO: Use terraform fmt -recursive to auto-format before submitting — clean code earns partial credit.
  • ✅ DO: Use terraform validate to catch syntax errors before plan (faster feedback loop).
  • ❌ DON'T: Run terraform destroy without reading the destroy plan first. You may destroy the wrong resources.
  • ❌ DON'T: Hardcode credentials in .tf files. Use env vars (AWS_ACCESS_KEY_ID) or shared credentials.
  • ❌ DON'T: Leave any task blank. Even partial work (correct provider block, valid HCL syntax) may earn partial credit.
  • ❌ DON'T: Forget to run terraform fmt before submitting — it's an automatic check in the exam environment.

Resource Lifecycle Q1 of 200
What does terraform init do when executed in a new Terraform configuration directory?
A) It creates all the infrastructure resources defined in the .tf files immediately
B) It initializes the working directory — downloads required providers, configures the backend, and sets up the .terraform/ directory
C) It validates the HCL syntax and outputs any errors without downloading anything
D) It only creates the terraform.tfstate file and nothing else
✅ Correct Answer: B

terraform init is the FIRST command you run in any Terraform configuration. It performs three critical tasks: (1) downloads provider plugins (e.g., hashicorp/aws) from the Terraform Registry into .terraform/providers/, (2) initializes the configured backend for state storage (S3, GCS, local, etc.), and (3) downloads referenced modules if any are declared.

📝 Detailed Explanation
What terraform init Actually Does — The 3 Core Tasks
  terraform init
  │
  ├─ 1️⃣ PROVIDER DOWNLOAD
  │   Reads required_providers {} block
  │   Downloads hashicorp/aws binary → .terraform/providers/
  │   Creates .terraform.lock.hcl (version pinning)
  │   Example: terraform init → downloads aws v5.0 provider
  │
  ├─ 2️⃣ BACKEND INITIALIZATION
  │   Reads terraform { backend "s3" {} } block
  │   Configures S3 bucket + DynamoDB lock table
  │   If migrating: prompts for state copy (local → S3)
  │   Example: terraform init -backend-config="bucket=anihpj-tfstate"
  │
  └─ 3️⃣ MODULE SETUP
      Reads module "vpc" { source = "./modules/vpc" } blocks
      Downloads external modules (registry, GitHub, S3)
      Caches modules in .terraform/modules/
      Example: terraform init → downloads terraform-aws-modules/vpc

For anihpj/jobpost on AWS, running terraform init in the anihpj-infra/ directory downloads the AWS provider (~80MB), configures the S3 backend for team state sharing, and downloads any referenced modules like terraform-aws-modules/vpc/aws and terraform-aws-modules/eks/aws. Without terraform init, no other terraform command works — plan, apply, and destroy all require initialized providers.

Resource Lifecycle Q2 of 200
What is the .terraform.lock.hcl file, and should you commit it to version control (Git)?
A) It is a temporary cache file that should be added to .gitignore — it regenerates on every terraform init
B) It is a dependency lock file that pins exact provider versions and hashes — you SHOULD commit it to Git for reproducible builds across your team and CI/CD
C) It stores sensitive credentials and must never be committed to any repository
D) It is only used by Terraform Cloud and has no purpose in local development workflows
✅ Correct Answer: B

The .terraform.lock.hcl file is Terraform's dependency lock file — similar to package-lock.json (npm) or Gemfile.lock (Bundler). It records the exact provider versions AND their content hashes so every team member and CI/CD pipeline downloads identical provider binaries. You MUST commit it to Git for reproducible infrastructure deployments.

📝 Detailed Explanation
.terraform.lock.hcl — What It Locks & Why It Matters
  .terraform.lock.hcl
  │
  ├─ 🔒 PROVIDER VERSION PINNING
  │   provider "registry.terraform.io/hashicorp/aws" {
  │     version     = "5.70.0"
  │     constraints = "~> 5.0"
  │     hashes = [
  │       "h1:abc123def456...",  ← SHA256 of the binary
  │       "zh:xyz789uvw012...",  ← zh = zip hash
  │     ]
  │   }
  │
  ├─ ✅ WHY COMMIT IT
  │   1. Reproducible builds — everyone gets the SAME provider version
  │   2. CI/CD consistency — no surprise upgrades breaking production
  │   3. Security — hashes prevent tampered/malicious provider binaries
  │   4. Cross-platform — locks hashes for linux_amd64, darwin_arm64, etc.
  │
  └─ ❌ WHAT GOES IN .gitignore (NOT the lock file)
      .terraform/          ← downloaded provider binaries (large, platform-specific)
      terraform.tfvars     ← may contain secrets (API keys, passwords)
      *.tfstate*           ← state files contain ALL resource data in plaintext
      crash.log            ← debug crash output

For anihpj/jobpost, the .terraform.lock.hcl ensures that when a teammate clones the repo and runs terraform init, they get exactly hashicorp/aws v5.70.0 — not v5.71.0 which might introduce a breaking change. Commit the lock file. Always.

Resource Lifecycle Q3 of 200
When and why should you run terraform init -upgrade instead of plain terraform init?
A) It should be run every time you execute terraform init — it is the standard initialization command
B) It only upgrades the Terraform CLI binary itself, not the providers
C) It upgrades provider and module versions to the latest allowed by your version constraints, updating the .terraform.lock.hcl file — use it when you want to adopt newer provider releases
D) It resets the entire .terraform/ directory and forces a clean download of all providers from scratch
✅ Correct Answer: C

terraform init -upgrade tells Terraform to ignore the existing .terraform.lock.hcl and re-evaluate provider/module version constraints against the registry. It downloads the latest versions that satisfy your constraints and updates the lock file. Plain terraform init respects existing lock file entries and will NOT upgrade unless the locked version is no longer available.

📝 Detailed Explanation
terraform init vs terraform init -upgrade — Side-by-Side
  PLAIN terraform init                    terraform init -upgrade
  ─────────────────────                   ────────────────────────
  │                                       │
  ├─ Reads .terraform.lock.hcl            ├─ IGNORES .terraform.lock.hcl
  │  "aws is locked at v5.70.0"           │  "Let me check the registry..."
  │                                       │
  ├─ Downloads aws v5.70.0 ✅              ├─ Registry says aws v5.72.0 is latest
  │  (respects existing lock)             │  "v5.72.0 satisfies ~> 5.0" ✅
  │                                       │
  └─ Lock file UNCHANGED                  ├─ Downloads aws v5.72.0
                                          │
                                          └─ UPDATES .terraform.lock.hcl
                                             "aws is now locked at v5.72.0"

  🔑 KEY RULE:
  • terraform init        = use what's locked (safe, reproducible)
  • terraform init -upgrade = check for newer allowed versions (upgrade path)

For anihpj/jobpost, if your required_providers block specifies aws = { source = "hashicorp/aws", version = "~> 5.0" }, running terraform init -upgrade would upgrade from aws v5.70.0 (locked) to v5.72.0 (latest in the ~>5.0 range). Run -upgrade intentionally, not by default — and always review what changed via git diff .terraform.lock.hcl.

Resource Lifecycle Q4 of 200
You need to configure a different S3 backend bucket for staging vs production without hardcoding values in backend.tf. How do you pass dynamic backend configuration?
A) Use terraform init -backend-config="key=value" or -backend-config=FILE to pass backend settings at initialization time — this is the standard CI/CD pattern
B) Use Terraform variables (terraform init -var 'bucket=staging') — backend config accepts variables like any other block
C) Edit the backend.tf file manually before each terraform init — there is no programmatic way to configure backends
D) Use environment variables like TF_BACKEND_BUCKET=staging — Terraform automatically reads them
✅ Correct Answer: A

Terraform's backend configuration cannot use variables or interpolation — it must be fully resolved before Terraform processes variables. The solution is partial backend configuration: omit the dynamic values from the backend block and pass them at init time via -backend-config flags or a separate config file.

📝 Detailed Explanation
Dynamic Backend Configuration — The CI/CD Pattern
  STEP 1: backend.tf (PARTIAL config — in Git)
  ─────────────────────────────────────────
  terraform {
    backend "s3" {
      encrypt = true        ← Static values go here
      region  = "us-east-1"
      # bucket, key, dynamodb_table are OMITTED
      # They will be provided at init time
    }
  }

  STEP 2: backend-staging.hcl (NOT in Git)
  ────────────────────────────────────────
  bucket         = "anihpj-tfstate-staging"
  key            = "infra/terraform.tfstate"
  dynamodb_table = "tf-locks-staging"

  STEP 3: Initialize with dynamic values
  ───────────────────────────────────────
  terraform init -backend-config=backend-staging.hcl

  ═══ OR pass inline ═══
  terraform init \
    -backend-config="bucket=anihpj-tfstate-staging" \
    -backend-config="key=infra/terraform.tfstate" \
    -backend-config="dynamodb_table=tf-locks-staging"

  🔑 CRITICAL: Backend blocks CANNOT use var.* or local.*
     They are evaluated BEFORE variables are processed

For anihpj/jobpost, the CI/CD pipeline uses this pattern to select the correct S3 backend per environment: GitHub Actions sets ENVIRONMENT=staging, and the pipeline runs terraform init -backend-config="backends/${ENVIRONMENT}.hcl". Never hardcode backend config — use -backend-config for multi-environment workflows.

Resource Lifecycle Q5 of 200
What does terraform plan actually do, and what do the symbols in its output mean?
A) It applies infrastructure changes immediately and shows the result — it is equivalent to terraform apply
B) It reads the current state, compares it against your .tf configuration files, and outputs a diff showing what will be created (+), destroyed (-), changed in-place (~), or replaced (-/+) — without making any changes
C) It only validates HCL syntax and does not compare against real infrastructure state
D) It downloads provider binaries and initializes the working directory before comparing state to config
✅ Correct Answer: B

terraform plan is Terraform's dry-run command — it reads the state file (what exists), reads your .tf files (what you want), calculates the difference, and outputs a human-readable plan. It makes ZERO changes to infrastructure. Understanding the 4 plan symbols is fundamental to safe Terraform operation.

📝 Detailed Explanation
terraform plan — The 4 Symbols & What They Mean
  terraform plan OUTPUT LEGEND
  ─────────────────────────────
  Symbol  Meaning              Example (anihpj)
  ──────  ───────────────────  ─────────────────────────────────
  +       CREATE — resource     + aws_s3_bucket.assets
          doesn't exist yet     → Terraform will create this bucket

  -       DESTROY — resource    - aws_security_group.old_sg
          will be removed       → Terraform will delete this SG

  ~       UPDATE IN-PLACE —     ~ aws_instance.web
          modify without recreate → Terraform will update tags only

  -/+     REPLACE — destroy     -/+ aws_launch_template.web
          then recreate         → AMI changed = must replace template

  PLAN FLOW:
  ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────────┐
  │ Read .tf │───▶│ Compare  │───▶│ Generate │───▶│ Output diff  │
  │ files    │    │ vs State │    │   Plan   │    │ (+ - ~ -/+)  │
  └──────────┘    └──────────┘    └──────────┘    └──────────────┘
       ↑               ↑              ↑                 ↑
  main.tf      terraform.tfstate   in-memory       NO changes made
  vars.tf                          calculation     to infrastructure

For anihpj/jobpost, before any production change you run terraform plan -out=plan.tfplan to save the plan. The team reviews it in a PR comment (GitHub Actions posts the plan output). Only after approval does terraform apply plan.tfplan execute exactly what was reviewed. Never apply without planning first — terraform plan is your safety net.

What is the purpose of terraform plan -out=FILE, and why is it critical for CI/CD pipelines?
A) It exports the plan as a human-readable JSON file for documentation purposes only

C) It saves a binary execution plan to a file — this plan can then be applied with terraform apply FILE, ensuring exactly what was reviewed is what gets deployed, with no drift between plan and apply

This ensures the infrastructure change reviewed in a PR is precisely what gets deployed.

Resource Lifecycle Q7 of 200
What does the -/+ symbol mean in terraform plan output, and how does it differ from ~ (update in-place)?
A) -/+ means the resource must be destroyed and recreated (forced replacement) — typically because an immutable attribute changed (AMI ID, availability zone); ~ means the resource is updated in-place without destruction
B) -/+ means the resource will be partially destroyed (only some attributes), while ~ means the entire resource will be recreated from scratch
C) -/+ and ~ are identical — both mean the resource will be updated without any destruction
D) -/+ means the plan failed validation and the resource needs manual intervention before applying
✅ Correct Answer: A

The -/+ (replace) symbol is the most disruptive plan action — it means Terraform will destroy the existing resource first, then create a new one. This happens when you change an attribute that cannot be modified in-place (like an EC2 instance's AMI, an RDS instance's availability zone, or a resource's force_new attribute). The ~ (update in-place) symbol means Terraform will modify the existing resource without destroying it.

📝 Detailed Explanation
-/+ (Replace) vs ~ (Update In-Place) — Critical Difference
  ~ UPDATE IN-PLACE (safe)              -/+ FORCE REPLACE (disruptive)
  ───────────────────────               ──────────────────────────────
  ~ aws_instance.web                    -/+ aws_instance.web
    tags.Name: "web-v1" → "web-v2"        ami: "ami-abc" → "ami-xyz"
                                            ↑ AMI change = force new resource
    🔄 Terraform UPDATES tags      
    ⏱️ ~2 seconds (no downtime)              💀 Terraform DESTROYS old instance
    🟢 Existing IPs preserved                🆕 Terraform CREATES new instance
    🟢 Existing EBS volumes stay             ⏱️ ~2 minutes (DOWNTIME!)
                                             🔴 NEW private IP assigned
                                             🔴 EBS root volume replaced
  ⚡ WHAT TRIGGERS -/+ (Force Replace):
  ┌──────────────────────────────────────────────────────────┐
  │  • Changing an EC2 AMI (ami-abc → ami-xyz)              │
  │  • Changing an RDS availability_zone                     │
  │  • Changing a resource's name/ID (immutable identifier)  │
  │  • Attributes marked force_new in the provider schema    │
  │  • Using terraform apply -replace=RESOURCE (explicit)    │
  └──────────────────────────────────────────────────────────┘

For anihpj/jobpost, if you change the AMI for the web server ASG launch template, Terraform will show -/+ — the old launch template is destroyed and a new one created. This means new EC2 instances get the new AMI, but running instances are NOT immediately replaced (the ASG handles rolling replacement). Always check for -/+ in production plans — it signals potential downtime.
