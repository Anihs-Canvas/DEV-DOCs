⚙️ Section 1: systemctl — Service Management

systemctl is the central management tool for controlling the systemd system and service manager. It manages the full K8s worker node stack — kubelet, containerd, kube-proxy, nginx, prometheus, sshd, and periodic timers — making it the most-used command in any Linux admin's daily workflow. Every service lifecycle operation flows through systemctl.

systemctl — The Systemd Control Interface

CORE systemctl Service Management Daily Operations

Control the systemd system and service manager — start, stop, monitor, and configure services

systemctl is the single most important command for managing Linux services. It controls the systemd init system (PID 1) that manages every process on a modern Linux server. Whether you're a DevOps engineer restarting a failed microservice, a platform engineer provisioning a new K8s node, or a DevSecOps specialist hardening service configurations — systemctl is the tool you reach for first.

For daily operations on the production node, systemctl handles:

  • Service Lifecycle: start, stop, restart, reload running services
  • Boot Configuration: enable/disable services to auto-start at boot
  • State Inspection: status, is-active, is-enabled, is-failed checks
  • Configuration Management: daemon-reload, show, cat, edit unit files
  • Process Control: kill, mask/unmask, set-property at runtime

Status Values You'll See Daily:

  • active (running) — Service is up and processing
  • active (exited) — One-shot service completed successfully
  • inactive (dead) — Service is stopped
  • failed — Service encountered an error and terminated
  • activating / deactivating — Transitional states

Syntax

systemctl [OPTIONS...] COMMAND [UNIT...]

# Available command groups:
systemctl start UNIT...        # Activate one or more units
systemctl stop UNIT...         # Deactivate one or more units
systemctl restart UNIT...      # Stop then start one or more units
systemctl reload UNIT...       # Reload configuration (if supported)
systemctl status UNIT...       # Show runtime status information
systemctl enable UNIT...       # Enable unit to start at boot
systemctl disable UNIT...      # Disable unit from starting at boot
systemctl list-units           # List loaded units
systemctl daemon-reload        # Reload systemd manager configuration
systemctl show UNIT            # Show all properties of a unit
systemctl cat UNIT             # Show unit file and drop-in contents
systemctl edit UNIT            # Create/edit a drop-in override
systemctl mask UNIT            # Mask a unit (prevent all starts)
systemctl unmask UNIT          # Unmask a unit
systemctl kill UNIT            # Send a signal to unit processes

# Common flags:
systemctl --no-pager           # Don't pipe output through a pager
systemctl --no-legend          # Hide column headers and footer
systemctl --all                # Show all units (including inactive)
Example: Quick Health Check

Scenario: Alex does a morning health sweep of all critical services.

Command:

systemctl is-active kubelet containerd nginx sshd && echo "---" && systemctl list-units --state=failed --no-legend

Output:

active active active active --- 0 loaded units listed.

📝 What happened: All four critical services are active. The --state=failed check returned zero failed units — the node is healthy. This one-liner is the core of every morning health check script. If any service showed inactive or appeared in the failed list, the script would trigger an alert.

Example 4: Find All Failed Units Across the System

Scenario: After a power outage, Alex checks if any units failed to start.

Command:

systemctl --state=failed --no-legend | wc -l && systemctl --state=failed

Output:

0 UNIT LOAD ACTIVE SUB DESCRIPTION 0 loaded units listed.

📝 What happened: Zero failed units — clean recovery. After any unexpected reboot, this is the first command to run. Non-zero output means something broke during boot. The --state=failed works on ALL unit types (services, mounts, devices, sockets), not just services.

Example 5: Check a Specific Property

Scenario: Jordan needs to know which user kubelet runs as.

Command:

systemctl show kubelet -p User -p Group -p ProtectSystem -p NoNewPrivileges --value

Output:

📝 What happened: show -p queries specific properties. kubelet runs as root (required for container orchestration) but has ProtectSystem=strict and NoNewPrivileges=yes for security hardening. The --value flag strips property names for clean scripting output.

The .service extension is optional — systemctl assumes it. Chain commands with && for health checks. Always run daemon-reload after editing unit files. Tab-completion works for unit names.

systemctl start

START systemctl Service Lifecycle SRE Essential

Start (activate) one or more systemd units — services, sockets, timers, or targets

systemctl start activates a systemd unit. If the unit is already active, this is a no-op — it won't restart or interrupt a running service. Units can be services (.service), sockets (.socket), timers (.timer), or targets (.target). The .service extension is assumed if omitted.

For the /sre-platform K8s worker node, systemctl start is used for:

  • Bringing up core K8s components after node reboot: kubelet, containerd, kube-proxy
  • Starting infrastructure services on demand: nginx, haproxy, sshd
  • Activating the full observability stack: prometheus, node_exporter, grafana
  • Launching timer-triggered backup services manually: k8s-snapshot.service
  • Firing up target groups to bring up entire service tiers: sre-production.target

Syntax

systemctl start UNIT...

# Common patterns:
systemctl start nginx                   # Start a single service (.service implied)
systemctl start kubelet.service         # Explicit .service extension
systemctl start kubelet containerd      # Start multiple units at once
systemctl start sre-production.target   # Start a target (triggers all Wants= units)

Parameters

ArgumentDescription
UNIT...One or more unit names to start. Space-separated. Extension defaults to .service.
--no-blockDo not wait for the operation to finish (async start).

Return Value

Exit CodeDescription
0Success — unit(s) started or already active
1Unit not found or failed to start
3Dependency failure — a Required= unit failed

journalctl — Centralized Log Query

Query the systemd journal — the centralized, structured logging system for all system messages

journalctl is the gateway to systemd-journald, the logging daemon that captures output from the kernel, system services, and applications. Unlike traditional syslog files scattered across /var/log/, journald stores everything in a single binary journal with rich metadata — timestamps, UID, PID, priority, and more. Every log entry is indexed and instantly searchable.

For daily operations on the production node, journalctl provides:

  • Service Logs: Filter by unit name to see exactly what a service logged
  • Time Windows: Zoom to specific time ranges — "last hour", "since yesterday", custom dates
  • Boot Sessions: View logs from current boot, previous boot, or any historical boot
  • Priority Filters: Show only errors, warnings, or debug-level messages
  • Kernel Messages: Equivalent to dmesg but with timestamps and filtering
  • Structured Output: Export as JSON for log aggregation tools

FUNDAMENTALS Unit Files Reference Daily Operations

Understand unit file locations, priority order, and the daemon-reload workflow

Systemd unit files are plain-text INI-style configuration files that define how services, sockets, timers, mounts, and other resources are managed. There are three standard locations with a strict priority order — higher-priority directories override lower ones. After creating or modifying ANY unit file, you must run systemctl daemon-reload to tell systemd to re-read its configuration.

Unit File Structure — [Unit] / [Service] / [Install]

STRUCTURE Unit Files Reference Daily Operations

Every unit file has three standard sections — [Unit] for metadata, [Service] for execution, [Install] for enable/disable

Systemd unit files use INI-style [Section] headers followed by Key=Value pairs. There are three universal sections, plus optional type-specific sections like [Socket] or [Timer]. Lines starting with # or ; are comments. Boolean values accept yes/no, true/false, or 1/0.

[Unit] — Metadata & Dependencies

Description=            # Human-readable description
Documentation=          # URLs to documentation
Requires=               # Hard dependency — unit FAILS if these fail
Wants=                  # Soft dependency — started alongside (failure tolerated)
After=                  # Ordering: start AFTER these units finish
Before=                 # Ordering: start BEFORE these units
BindsTo=                # Strong binding — stops if bound unit stops
PartOf=                 # Part of a larger unit (restart/stop propagates)
Conflicts=              # Mutually exclusive units
Condition*=             # Conditions that must be true for unit to start
Assert*=                # Assertions (fail unit if not true)

[Service] — Execution & Lifecycle

Type=                   # Startup type: simple, forking, oneshot, notify, dbus, idle
ExecStart=              # Command to start the service (REQUIRED)
ExecStartPre=           # Commands run BEFORE ExecStart
ExecStartPost=          # Commands run AFTER ExecStart
ExecReload=             # Command to reload configuration

Restart=                # Restart policy: no, on-success, on-failure, on-abnormal, always
RestartSec=             # Time to wait before restarting (e.g., 5s, 10s)
TimeoutStartSec=        # Timeout for startup (default 90s)
TimeoutStopSec=         # Timeout for graceful stop (default 90s)

Service Types — Type= Directive

TYPES Unit Files Reference Daily Operations

The Type= directive tells systemd how to know when the service is "ready" — choose the right type for your process

The Type= directive in the [Service] section defines the startup behavior. This is critical — choosing the wrong type causes systemd to misjudge the service state, leading to restart loops, dependency failures, or services that appear "active" but aren't actually ready.

Service Types

Type=simple     # (Default) Service is considered started immediately.
                # ExecStart is the main process. Do NOT fork.
                # Use for: foreground processes, most Go/Rust services.

Type=forking    # Service forks a child process. Parent exits after startup.
                # MUST specify PIDFile=. Used for traditional daemons.
                # Use for: legacy daemons that double-fork (nginx, sshd).

Type=oneshot    # Short-lived process. Systemd waits for it to exit.
                # Use RemainAfterExit=yes to consider the unit active after exit.
                # Use for: setup scripts, backup jobs, initialization tasks.

Type=notify     # Service sends a readiness signal via sd_notify().
                # Systemd waits for the notification before marking active.
                # Use for: modern services (kubelet, containerd, prometheus).

Type=dbus       # Service registers on D-Bus. Systemd waits for bus name.
                # Use for: D-Bus activated services (rare in container/K8s environments).

Type=idle       # Like simple, but delayed until all jobs are dispatched.
                # Use for: avoiding console output interleaving during boot.

Parameters

TypeReadiness SignalPIDFile Required?K8s Platform Usage
simpleImmediate (fork+exec done)Noprometheus, node_exporter, grafana
forkingParent exits (child running)Yesnginx (traditional daemon mode)
oneshotProcess exits (RemainAfterExit=yes)Nok8s-snapshot, init scripts
notifysd_notify("READY=1")Nokubelet, containerd
dbusD-Bus name acquiredNoRare in K8s env
idleLike simple (delayed)NoBoot-time services
💡 Pro Tips: Most modern services should use Type=notify — it gives systemd accurate readiness information. If your service doesn't support sd_notify, use Type=simple with ExecStartPost= for a readiness check script. Avoid Type=forking unless the service truly double-forks — PID file races are a common source of bugs. For oneshot backup jobs, always set RemainAfterExit=yes so systemctl is-active reflects the last run status.

Restart Policies — Restart= Directive

POLICY Unit Files Reliability Daily Operations

Control when systemd automatically restarts a failed service — essential for production reliability

The Restart= directive defines when systemd should automatically restart a service after it exits. Combined with RestartSec= (delay between restarts) and StartLimitBurst=/StartLimitIntervalSec= (rate limiting), this forms the foundation of production service reliability. For the K8s node, every critical service uses Restart=always or Restart=on-failure.

Restart Policies

Restart=no              # Never restart (default)
Restart=on-success      # Restart only on clean exit (exit code 0)
Restart=on-failure      # Restart on unclean exit, signal, or timeout
Restart=on-abnormal     # Restart on signal or timeout (not clean exit)
Restart=on-watchdog     # Restart on watchdog timeout
Restart=always          # Always restart — even on clean exit

Rate Limiting Directives

RestartSec=5s                   # Wait 5 seconds before restarting
StartLimitBurst=5               # Allow 5 restarts in...
StartLimitIntervalSec=30s       # ...30 seconds (then give up)
💡 Pro Tips: Use Restart=on-failure with RestartSec=5s for most production services. Restart=always is appropriate for K8s components (kubelet, containerd) that should never stay down. Set rate limits to prevent restart storms: StartLimitBurst=5 over StartLimitIntervalSec=30s. For oneshot services (backup jobs), leave Restart=no — restarting a completed backup would be wrong. Check restart behavior with systemctl show UNIT -p NRestarts.

Production-grade unit file for the Kubernetes kubelet — the node agent that registers the node and runs pods

Kubelet is the primary Kubernetes node agent. It registers the node with the API server, watches for pod assignments, and manages container lifecycles through the container runtime (containerd). This unit file includes security hardening, resource limits, and the correct dependency chain.

WantedBy=timers.target

# /etc/systemd/system/k8s-snapshot.service
[Unit]
Description=/sre-platform ETCD snapshot backup
After=network.target

[Service]
Type=oneshot
User=sre
WorkingDirectory=/sre-platform
ExecStart=/sre-platform/scripts/etcd-snapshot.sh
StandardOutput=journal
StandardError=journal
# Timer + oneshot service pattern for /sre-platform scheduled jobs:
#  OnCalendar=daily + OnCalendar=*-*-* 02:00:00: runs daily at 02:00
#  Persistent=true: if the node was down at 02:00, run immediately on next boot
#  RandomizedDelaySec=300: stagger by up to 5 minutes to avoid thundering herd
#  Type=oneshot: the service runs once and exits — no long-running process
#  User=sre: runs as the sre user, not root
💡 Pro Tips: Timers are superior to cron: they get all journald logging for free, support randomized delays (critical at scale), and can persist across missed runs. Use systemctl list-timers to see all timers with next run times. For manual triggering, start the .service directly — don't start the .timer. RandomizedDelaySec= is essential when many nodes run the same timer — without it, all nodes hit the backup server simultaneously.

Example 7: Drop-in Overrides — Modify Vendor Units Safely

OVERRIDE Unit Files Drop-in Daily Operations

Override specific directives in vendor-provided unit files without copying or modifying the original

Drop-in overrides are the SAFEST way to customize vendor-provided unit files. Instead of copying the entire unit file to /etc/systemd/system/ (which diverges from upstream on package updates), you create a .conf snippet in a UNIT.d/ directory. Systemd merges the drop-in with the base unit at runtime — your overrides take priority while the vendor file stays pristine.

📁 Context: /sre-platform — Drop-in Override Workflow

# Alex adds resource limits to kubelet via drop-in override:
alex@prod-node-01:~$ sudo mkdir -p /etc/systemd/system/kubelet.service.d

alex@prod-node-01:~$ cat > /tmp/10-resource-limits.conf << 'EOF'
[Service]
MemoryMax=2G
CPUQuota=200%
LimitNOFILE=65536
EOF
alex@prod-node-01:~$ sudo cp /tmp/10-resource-limits.conf /etc/systemd/system/kubelet.service.d/
alex@prod-node-01:~$ sudo systemctl daemon-reload

alex@prod-node-01:~$ systemctl show kubelet | grep -E "^(MemoryMax|CPUQuota|LimitNOFILE)="
MemoryMax=2147483648
CPUQuota=200%
LimitNOFILE=65536

alex@prod-node-01:~$ ls -la /etc/systemd/system/kubelet.service.d/
total 12
drwxr-xr-x 2 root root 4096 Jun 10 09:00 .
drwxr-xr-x 6 root root 4096 Jun 10 09:00 ..
-rw-r--r-- 1 root root   72 Jun 10 09:00 10-resource-limits.conf
# Drop-in override pattern for /sre-platform node customization:
#  /etc/systemd/system/kubelet.service.d/10-resource-limits.conf
#  Drop-in naming: NN-description.conf — numeric prefix controls merge order
#  Only override what you need — base unit stays untouched by package updates
#  daemon-reload REQUIRED after creating/modifying drop-ins

Example: Add Environment Variables via Drop-in

Scenario:

📄 Context — Environment Customization:

📁 Directory Snippet:

# Drop-in directory structure for adding env vars to prometheus:
/etc/systemd/system/
    └── 📁 prometheus.service.d/
        └── 📄 20-environment.conf    # Environment= overrides merged at runtime
# Jordan adds a custom environment variable to prometheus without touching its unit file
Jordan needs to set a custom HTTP proxy for Prometheus's external scrapes. A drop-in is the clean way.

Command:

sudo mkdir -p /etc/systemd/system/prometheus.service.d && echo -e '[Service]\nEnvironment=HTTP_PROXY=http://proxy.internal:3128\nEnvironment=HTTPS_PROXY=http://proxy.internal:3128\nEnvironment=NO_PROXY=localhost,127.0.0.1,.internal' | sudo tee /etc/systemd/system/prometheus.service.d/20-environment.conf && sudo systemctl daemon-reload && systemctl show prometheus -p Environment | tr ' ' '\n'

Output:

Environment=HTTP_PROXY=http://proxy.internal:3128 Environment=HTTPS_PROXY=http://proxy.internal:3128 Environment=NO_PROXY=localhost,127.0.0.1,.internal

📝 What happened: The drop-in snippet added three environment variables. When Prometheus starts, systemd merges these with the base unit file's settings. The vendor's prometheus.service in /usr/lib/systemd/system/ is completely untouched — future package updates won't overwrite Jordan's proxy settings. This is the recommended pattern for ALL unit file customizations.

💡 Pro Tips: Drop-in override priority: files in UNIT.d/ are merged in lexicographic order — use numeric prefixes (10-, 20-, 30-) to control merge order. To REMOVE a directive from the base unit, set it to empty: Environment=. Use systemctl cat UNIT to see the fully merged result. Drop-ins can also clear lists with ExecStart= (empty) before setting a new one. Never copy entire unit files for small changes — drop-ins are always the correct approach.

Unit File Checklist — Production Readiness

CHECKLIST Unit Files Production Best Practices

Before deploying a unit file to production, verify every item on this checklist

Use this checklist when writing or reviewing ANY unit file destined for the /sre-platform production node. Each item prevents a common failure mode. Alex and the team run through this list during code review for every new or modified unit file.

Production Readiness Checklist

✅ [Unit]
   ☐ Description= is meaningful and searchable in journalctl
   ☐ After=network.target (or network-online.target for network-dependent services)
   ☐ Requires=/Wants= declares all hard/soft dependencies
   ☐ PartOf=sre-production.target (if applicable)

✅ [Service]
   ☐ Type= matches the service's startup behavior
   ☐ Restart=on-failure (or always for critical infra) with RestartSec=5s+
   ☐ StartLimitBurst= and StartLimitIntervalSec= set to prevent restart storms
   ☐ ExecStart= uses absolute paths (never relative)
   ☐ User=/Group= set to non-root (unless root is required)
   ☐ ProtectSystem=strict or full (security hardening)
   ☐ NoNewPrivileges=yes (prevent privilege escalation)
   ☐ ReadWritePaths= declared when ProtectSystem=strict
   ☐ LimitNOFILE=65536 or higher for high-traffic services
   ☐ MemoryMax=/CPUQuota= set to prevent resource starvation
   ☐ TimeoutStopSec= set appropriately (not left at default 90s for slow-stopping services)

✅ [Install]
   ☐ WantedBy=multi-user.target (for auto-start at boot)
   ☐ Also= includes any companion socket/timer units

✅ Deployment
   ☐ Unit file is version-controlled in /sre-platform/systemd-units/
   ☐ Symlinked to /etc/systemd/system/ (not copied)
   ☐ sudo systemctl daemon-reload after every change
   ☐ systemctl enable UNIT (if auto-start desired)
   ☐ systemctl start UNIT && systemctl is-active UNIT verified
   ☐ journalctl -u UNIT -b --no-pager verified clean startup
   ☐ systemd-analyze verify /etc/systemd/system/UNIT passes validation
💡 Pro Tips: The most commonly missed items: forgetting daemon-reload after unit file changes (#1 cause of "it didn't work"), not setting StartLimitBurst= (leads to infinite restart loops), and using Type=forking without PIDFile= (causes systemd to kill the wrong process). Run systemd-analyze verify /path/to/unit as a pre-deployment check — it catches syntax errors and missing dependencies. This checklist should be part of EVERY unit file code review.
