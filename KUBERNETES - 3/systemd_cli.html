⚙️ Section 1: systemctl — Service Management

systemctl is the central management tool for controlling the systemd system and service manager. It manages the full K8s worker node stack — kubelet, containerd, kube-proxy, nginx, prometheus, sshd, and periodic timers — making it the most-used command in any Linux admin's daily workflow. Every service lifecycle operation flows through systemctl.

systemctl — The Systemd Control Interface

CORE systemctl Service Management Daily Operations

Control the systemd system and service manager — start, stop, monitor, and configure services

systemctl is the single most important command for managing Linux services. It controls the systemd init system (PID 1) that manages every process on a modern Linux server. Whether you're a DevOps engineer restarting a failed microservice, a platform engineer provisioning a new K8s node, or a DevSecOps specialist hardening service configurations — systemctl is the tool you reach for first.

For daily operations on the production node, systemctl handles:

  • Service Lifecycle: start, stop, restart, reload running services
  • Boot Configuration: enable/disable services to auto-start at boot
  • State Inspection: status, is-active, is-enabled, is-failed checks
  • Configuration Management: daemon-reload, show, cat, edit unit files
  • Process Control: kill, mask/unmask, set-property at runtime

Status Values You'll See Daily:

  • active (running) — Service is up and processing
  • active (exited) — One-shot service completed successfully
  • inactive (dead) — Service is stopped
  • failed — Service encountered an error and terminated
  • activating / deactivating — Transitional states

Syntax

systemctl [OPTIONS...] COMMAND [UNIT...]

# Available command groups:
systemctl start UNIT...        # Activate one or more units
systemctl stop UNIT...         # Deactivate one or more units
systemctl restart UNIT...      # Stop then start one or more units
systemctl reload UNIT...       # Reload configuration (if supported)
systemctl status UNIT...       # Show runtime status information
systemctl enable UNIT...       # Enable unit to start at boot
systemctl disable UNIT...      # Disable unit from starting at boot
systemctl list-units           # List loaded units
systemctl daemon-reload        # Reload systemd manager configuration
systemctl show UNIT            # Show all properties of a unit
systemctl cat UNIT             # Show unit file and drop-in contents
systemctl edit UNIT            # Create/edit a drop-in override
systemctl mask UNIT            # Mask a unit (prevent all starts)
systemctl unmask UNIT          # Unmask a unit
systemctl kill UNIT            # Send a signal to unit processes

# Common flags:
systemctl --no-pager           # Don't pipe output through a pager
systemctl --no-legend          # Hide column headers and footer
systemctl --all                # Show all units (including inactive)
Example: Quick Health Check

Scenario: Alex does a morning health sweep of all critical services.

Command:

systemctl is-active kubelet containerd nginx sshd && echo "---" && systemctl list-units --state=failed --no-legend

Output:

active active active active --- 0 loaded units listed.

📝 What happened: All four critical services are active. The --state=failed check returned zero failed units — the node is healthy. This one-liner is the core of every morning health check script. If any service showed inactive or appeared in the failed list, the script would trigger an alert.

Example 4: Find All Failed Units Across the System

Scenario: After a power outage, Alex checks if any units failed to start.

Command:

systemctl --state=failed --no-legend | wc -l && systemctl --state=failed

Output:

0 UNIT LOAD ACTIVE SUB DESCRIPTION 0 loaded units listed.

📝 What happened: Zero failed units — clean recovery. After any unexpected reboot, this is the first command to run. Non-zero output means something broke during boot. The --state=failed works on ALL unit types (services, mounts, devices, sockets), not just services.

Example 5: Check a Specific Property

Scenario: Jordan needs to know which user kubelet runs as.

Command:

systemctl show kubelet -p User -p Group -p ProtectSystem -p NoNewPrivileges --value

Output:

📝 What happened: show -p queries specific properties. kubelet runs as root (required for container orchestration) but has ProtectSystem=strict and NoNewPrivileges=yes for security hardening. The --value flag strips property names for clean scripting output.

The .service extension is optional — systemctl assumes it. Chain commands with && for health checks. Always run daemon-reload after editing unit files. Tab-completion works for unit names.

systemctl start

START systemctl Service Lifecycle SRE Essential

Start (activate) one or more systemd units — services, sockets, timers, or targets

systemctl start activates a systemd unit. If the unit is already active, this is a no-op — it won't restart or interrupt a running service. Units can be services (.service), sockets (.socket), timers (.timer), or targets (.target). The .service extension is assumed if omitted.

For the /sre-platform K8s worker node, systemctl start is used for:

  • Bringing up core K8s components after node reboot: kubelet, containerd, kube-proxy
  • Starting infrastructure services on demand: nginx, haproxy, sshd
  • Activating the full observability stack: prometheus, node_exporter, grafana
  • Launching timer-triggered backup services manually: k8s-snapshot.service
  • Firing up target groups to bring up entire service tiers: sre-production.target

Syntax

systemctl start UNIT...

# Common patterns:
systemctl start nginx                   # Start a single service (.service implied)
systemctl start kubelet.service         # Explicit .service extension
systemctl start kubelet containerd      # Start multiple units at once
systemctl start sre-production.target   # Start a target (triggers all Wants= units)

Parameters

ArgumentDescription
UNIT...One or more unit names to start. Space-separated. Extension defaults to .service.
--no-blockDo not wait for the operation to finish (async start).

Return Value

Exit CodeDescription
0Success — unit(s) started or already active
1Unit not found or failed to start
3Dependency failure — a Required= unit failed

Unit haproxy.service could not be found.

📝 What happened: The file exists on disk but systemd doesn't know about it yet. This is the #1 cause of "my new service doesn't work!" Always run systemctl daemon-reload after creating, editing, or deleting unit files. There's no automatic file watching — systemd only rescans when told.

💡 Pro Tips: Always run daemon-reload after any unit file change. Forgetting this is the #1 cause of "why isn't my new service working?" Use systemctl daemon-reload && systemctl restart UNIT to apply unit file changes. It's safe to run multiple times — idempotent. No services are restarted. If you see "Unit not found" for a file you just created, you forgot daemon-reload.

systemctl show / cat / edit

INSPECT & EDIT systemctl Configuration Daily Operations

Inspect unit properties, view unit file contents, and create drop-in overrides

Three essential commands for understanding and modifying how a service is configured. show dumps all runtime properties. cat displays the unit file and all active drop-ins. edit creates or opens a drop-in override file so you never modify the original unit.

Syntax

systemctl show UNIT                 # All properties (key=value)
systemctl show UNIT -p PROPERTY     # Single property
systemctl cat UNIT                  # Unit file + all drop-in overrides
systemctl edit UNIT                 # Create/edit drop-in in UNIT.d/override.conf
systemctl edit --full UNIT          # Edit the full unit file directly

systemctl mask / unmask

MASK systemctl Access Control Daily Operations

Completely prevent a unit from being started — stronger than disable

systemctl mask symlinks the unit file to /dev/null, making it impossible to start — even manually or as a dependency. Unlike disable (which only prevents auto-start at boot), mask blocks ALL activation attempts. Use this for services that must NEVER run on a specific node.

Syntax

systemctl mask UNIT        # Prevent ALL starts (symlink → /dev/null)
systemctl unmask UNIT      # Remove the mask
systemctl list-unit-files --state=masked  # List all masked units

📁 Context: /sre-platform — mask / unmask

# Morgan (Security Engineer) masks firewalld on nodes behind a hardware firewall:
morgan@prod-node-01:~$ sudo systemctl mask firewalld
Created symlink /etc/systemd/system/firewalld.service → /dev/null
morgan@prod-node-01:~$ sudo systemctl start firewalld
Failed to start firewalld.service: Unit firewalld.service is masked.
morgan@prod-node-01:~$ sudo systemctl unmask firewalld
Removed /etc/systemd/system/firewalld.service
# Key locations where mask/unmask operates:
#  /etc/systemd/system/                    # Mask creates symlink → /dev/null here
#  /lib/systemd/system/                    # Vendor units (mask overrides these)
#  Use list-unit-files --state=masked      # Audit all masked units

📄 Context — Absolute Prevention:

# Morgan uses mask for services that must NEVER run on specific nodes
# Mask > Disable: Disable prevents boot-start, Mask prevents ALL starts
# Use mask for conflicting services, security requirements, and maintenance locks
Example 1: Mask a Conflicting Service

Scenario: The node uses systemd-resolved, but NetworkManager tries to start its own dnsmasq.

Command:

sudo systemctl mask dnsmasq && systemctl status dnsmasq --no-pager 2>&1 | head -3

Output:

● dnsmasq.service Loaded: masked (Reason: Unit dnsmasq.service is masked.) Active: inactive (dead)

📝 What happened: dnsmasq is now masked. Even if NetworkManager tries to start it as a dependency, it will fail. The Loaded line shows masked. To undo: systemctl unmask dnsmasq.

Example 2: Mask to Prevent Accidental Start During Maintenance

Scenario: Alex masks kubelet during a storage migration to prevent anyone from accidentally starting it.

Command:

sudo systemctl mask kubelet && sudo systemctl start kubelet 2>&1; echo "Exit: $?"

Output:

Failed to start kubelet.service: Unit kubelet.service is masked. Exit: 1

📝 What happened: Even with sudo, kubelet CANNOT be started. The mask creates a symlink to /dev/null, making all start attempts fail. This is stronger than stop+disable — it prevents ANY activation. After the maintenance window, systemctl unmask kubelet restores normal operation.

Example 3: List All Masked Units

Scenario: Morgan (Security) audits which services are masked across the system.

Command:

systemctl list-unit-files --state=masked --no-legend

Output:

dnsmasq.service masked enabled firewalld.service masked enabled kubelet.service masked enabled

📝 What happened: Three services are masked — they CANNOT be started under any circumstances. This is a critical security audit command. Morgan runs it weekly to ensure no unauthorized masks (or unmasks) have occurred. The "enabled" in the vendor preset column means they WOULD be enabled if not masked.

Example 4: Unmask and Restore a Service

Scenario: The storage migration is complete — Alex unmasks kubelet and brings it back.

Command:

sudo systemctl unmask kubelet && sudo systemctl start kubelet && systemctl is-active kubelet && systemctl is-enabled kubelet

Output:

active enabled

📝 What happened: Unmasking restored kubelet's unit file symlink. The service started successfully and is back to enabled state. Unmasking doesn't automatically start the service — it just removes the block. The original enablement state is preserved.

Example 5: Mask vs Disable — The Practical Difference

Scenario: Morgan demonstrates why mask exists as a separate concept from disable.

Command:

echo "=== After disable ===" && sudo systemctl disable --now kubelet 2>/dev/null && sudo systemctl start kubelet 2>&1 | head -1; echo "=== After mask ===" && sudo systemctl mask kubelet && sudo systemctl start kubelet 2>&1 | head -1; sudo systemctl unmask kubelet && sudo systemctl enable kubelet

Output:

=== After disable === === After mask === Failed to start kubelet.service: Unit kubelet.service is masked.

📝 What happened: After disable, kubelet started successfully (no output = success). After mask, start FAILED. Disable prevents auto-start at boot but allows manual starts. Mask prevents ALL starts — manual, dependency-triggered, or boot-time. Use mask when you need absolute certainty a service won't run.

💡 Pro Tips: Mask is stronger than disable. Disable = don't start at boot. Mask = CANNOT be started at all. Use mask for conflicting services. unmask restores the unit. Check masked units with list-unit-files --state=masked. Never mask critical system services like systemd-journald.

systemctl kill

SIGNAL systemctl Process Control Daily Operations

Send a UNIX signal to one or more processes of a unit — fine-grained process control

systemctl kill sends a signal to the main process (and optionally all child processes) of a unit. Unlike stop (which sends SIGTERM and manages the lifecycle), kill gives you direct control over which signal to send. Common uses: SIGHUP for config reload, SIGTERM for graceful shutdown, SIGKILL as last resort, SIGUSR1 for application-specific triggers.

Syntax

systemctl kill UNIT...                   # Send SIGTERM (default)
systemctl kill -s SIGNAL UNIT...         # Send specific signal
systemctl kill -s HUP nginx              # SIGHUP — graceful reload
systemctl kill -s KILL kubelet           # SIGKILL — force kill
systemctl kill --kill-whom=all UNIT      # Kill all processes in cgroup

📁 Context: /sre-platform — systemctl kill

# Alex sends SIGHUP to nginx for a graceful reload without systemctl reload:
alex@prod-node-01:~$ sudo systemctl kill -s HUP nginx
alex@prod-node-01:~$ systemctl status nginx --no-pager | grep "Main PID"
   Main PID: 1201 (nginx)   # PID unchanged — reload, not restart!

# Emergency: force-kill a hung kubelet:
alex@prod-node-01:~$ sudo systemctl kill -s KILL kubelet
alex@prod-node-01:~$ systemctl is-active kubelet
inactive
# Key locations where systemctl kill operates:
#  Signal reference: man 7 signal            # Full signal list and meanings
#  /proc/PID/                                # Target process information
#  ExecReload= in unit files                 # Often maps to SIGHUP

📄 Context — Direct Signal Delivery:

# Alex uses systemctl kill for fine-grained process control
# Unlike stop (manages lifecycle), kill sends raw UNIX signals directly
# Common: HUP=reload, TERM=stop, KILL=force, USR1=app-specific
Example 1: Graceful Reload via SIGHUP

Scenario: Alex sends SIGHUP directly to nginx for config reload.

Command:

sudo systemctl kill -s HUP nginx && echo "PID unchanged: $(systemctl show -p MainPID --value nginx)"

Output:

PID unchanged: 1201

📝 What happened: SIGHUP told nginx to reload its config. Same effect as systemctl reload nginx. The PID stayed at 1201 — no restart, no downtime.

Example 2: Force Kill a Hung Process

Scenario: containerd is stuck and won't respond to SIGTERM.

Command:

sudo systemctl kill -s KILL containerd && sleep 2 && systemctl is-active containerd

Output:

inactive

📝 What happened: SIGKILL (signal 9) forcefully terminated containerd — no cleanup, no graceful shutdown. This is a last resort. systemd detected the process died and marked the unit as failed then auto-restarted it (Restart=always). Use SIGKILL only when SIGTERM doesn't work.

Example 3: Send SIGUSR1 for Application-Specific Action

Scenario: Taylor sends SIGUSR1 to a custom app to trigger log rotation without restarting.

Command:

sudo systemctl kill -s USR1 myapp && echo "Log rotation signal sent"

Output:

Log rotation signal sent

📝 What happened: SIGUSR1 (signal 10) is reserved for application-defined behavior. In this app, it triggers log file reopening — same effect as logrotate's postrotate script but without external tooling. SIGUSR1 and SIGUSR2 are commonly used for custom triggers in daemons.

Example 4: Kill All Processes in a Service's Cgroup

Scenario: nginx has orphaned worker processes after a crash. Alex kills all of them.

Command:

sudo systemctl kill -s KILL --kill-whom=all nginx && pgrep nginx | wc -l

Output:

0

📝 What happened: --kill-whom=all sent SIGKILL to every process in nginx's cgroup — not just the main PID. All orphaned workers were cleaned up. Without --kill-whom=all, only the main process would have been killed, leaving zombie workers behind. Zero remaining nginx processes confirmed.

Example 5: Signal Comparison — HUP vs TERM vs KILL

Scenario: Alex demonstrates the three most common signals and their effects.

Command:

echo "SIGHUP(1)=reload | SIGTERM(15)=graceful stop | SIGKILL(9)=force kill"; echo "---"; systemctl show nginx -p ExecReload --value; systemctl show nginx -p TimeoutStopSec --value

Output:

SIGHUP(1)=reload | SIGTERM(15)=graceful stop | SIGKILL(9)=force kill --- /bin/kill -s HUP $MAINPID 90s

📝 What happened: The nginx unit uses SIGHUP for reload (ExecReload) and allows 90 seconds for graceful SIGTERM stop. Key signal guide: HUP (1) = reload config, TERM (15) = please exit, KILL (9) = die now (can't be caught). Always try TERM before KILL. Never KILL a database — you'll corrupt data.

💡 Pro Tips: Default signal is SIGTERM (same as kill command). kill -s HUP = same as reload for services with ExecReload=SIGHUP. Use --kill-whom=all to signal all processes in the cgroup. SIGKILL (9) is last resort — no cleanup. SIGSTOP (19) pauses, SIGCONT (18) resumes. Check man 7 signal for the full signal list.
