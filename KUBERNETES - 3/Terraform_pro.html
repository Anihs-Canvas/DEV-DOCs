1.1 The Problem Terraform Solves

Imagine you've built anihpj — a Django app with a jobpost module listing jobs filtered by Skills, Location, and Author. It works perfectly on your laptop. But how do you run it in production so thousands of users can access it reliably?

📖 Key Term: Infrastructure as Code (IaC)

Infrastructure as Code is the practice of managing and provisioning infrastructure through machine-readable definition files rather than physical hardware configuration or interactive configuration tools. Terraform is the leading IaC tool — treating your cloud infrastructure the same way developers treat application code: versioned, tested, and automated.

The Pain of Manual Infrastructure

Before IaC, deploying infrastructure meant clicking through cloud consoles, running manual SSH commands, and hoping nothing went wrong. Each environment was a snowflake — unique, fragile, and impossible to reproduce.

😰 Deploying anihpj WITHOUT Terraform

  • 🔴 Onboarding a new developer: "Here's a 50-page wiki, good luck"

Why Manual Infrastructure Fails — The Snowflake Server Problem

Every manually-built server is a snowflake — unique, fragile, and impossible to perfectly reproduce. Here's why this matters:

🔄
Configuration Drift

You patch production server but forget staging. A month later, code that works in staging fails in production because the environments have diverged. Terraform eliminates drift by enforcing the SAME configuration everywhere.

📝
No Documentation

Infrastructure knowledge lives in someone's head. When they leave, nobody knows how to rebuild. With Terraform, the .tf files ARE the documentation — self-documenting infrastructure that anyone can read.

🔍
No Audit Trail

Who changed the security group last week? With manual changes, you'll never know. Terraform + Git gives you a complete version history of every infrastructure change — who, what, when, and why.

💸
Slow Recovery

AWS region goes down? With manual infrastructure, recovery means rebuilding from scratch. With Terraform, you run the same code in a different region — disaster recovery in minutes, not days.

1.2 Infrastructure as Code (IaC) Defined

📖 Official Definition

"Define your infrastructure in configuration files that you can version, reuse, and share — just like application code." In plain English: You write files describing what infrastructure you want (a VPC, an EKS cluster, a database), and Terraform makes it happen — correctly, consistently, every time.

Declarative vs Imperative — The Key Difference

This is THE most important concept in Terraform. With imperative tools (like Ansible or shell scripts), you say HOW to do something. With declarative tools (like Terraform), you say WHAT you want.

🔧 IMPERATIVE (Ansible, scripts)

You specify every step:

  • 1. Create VPC
  • 2. Create subnet
  • 3. Launch EC2
  • 4. Install Docker
  • 5. Configure K8s...

❌ "How to do it" — If step 3 fails, you're in an unknown state.

📋 DECLARATIVE (Terraform)

You state the desired end result:

resource "aws_vpc" "main" { cidr_block = "10.0.0.0/16" }
resource "aws_eks_cluster" "anihpj" { vpc_id = aws_vpc.main.id }

✅ "What I want" — Terraform figures out the correct order and handles failures.

Declarative Thinking is Tested Throughout the Exam

Every Terraform exam task follows this pattern: you're told WHAT infrastructure to create (not HOW). Your job is to write the correct .tf configuration. Terraform handles the ordering, parallelism, and error recovery. The exam tests whether you can express infrastructure requirements declaratively in HCL.

🏗️ The Construction Blueprint Analogy

Think of Terraform like an architectural blueprint for a building:

📐
Blueprint (.tf files)

You draw the blueprint specifying what the building should look like — number of floors, room sizes, materials. You don't specify HOW to pour concrete or WHERE to place scaffolding.

🏗️
Construction Crew (Terraform)

Terraform is the construction crew that reads your blueprint and figures out HOW to build it — in what order, with what tools, handling any problems along the way.

📋
Inspection Report (terraform plan)

Before building, you get an inspection report showing exactly what will be built, modified, or demolished. You approve it before any work begins.

📸
Progress Photo (State File)

The state file is like a progress photo — it shows what's already been built, so the crew knows what exists and what still needs to be done.

💡 Key Insight

If the blueprint says "3 floors" and a storm knocks down floor 2, the construction crew (Terraform) notices the difference between the blueprint (desired state) and reality (actual state), and rebuilds floor 2 automatically. This is self-healing infrastructure — the core promise of Terraform.

How Terraform Compares to Writing Scripts

Many beginners ask: "Why not just write a Python script that calls AWS APIs?" Here's why that doesn't work at scale:

🐍 Custom Script Approach
  • Write 500 lines of Python to create VPC, subnets, EC2
  • Handle errors manually (what if subnet creation fails midway?)
  • Track what was created — build your own "state" system
  • What if someone changed the security group manually? Script doesn't know
  • New team member: "Which script? What parameters?"

Result: You've accidentally built a bad version of Terraform

⚡ Terraform Approach
  • Write 50 lines of HCL describing desired state
  • Terraform handles errors, retries, and ordering automatically
  • State file tracks everything — Terraform knows if drift occurred
  • Manual changes detected on next terraform plan
  • New team member: git clone && terraform apply

Result: Battle-tested, community-supported, production-ready

⚠️ When NOT to Use Terraform

Terraform is powerful but not always the right tool. Consider alternatives when:

  • Simple, static infrastructure: A single EC2 instance that never changes — Terraform adds unnecessary complexity
  • Application configuration: Use Ansible, Chef, or Puppet for configuring software INSIDE servers (Terraform is for infrastructure, not app config)
  • Kubernetes-only workloads: If you ONLY use K8s, consider GitOps tools (ArgoCD, Flux) plus Crossplane for infrastructure
  • Multi-step workflows: Terraform is declarative, not procedural. Complex multi-step orchestration may need tools like Airflow or Temporal
Q1

What is the primary difference between declarative and imperative infrastructure management?

Show Answer & Explanation
✅ Answer

Declarative specifies WHAT you want (the desired end state), while imperative specifies HOW to achieve it (the exact steps).

📖 Explanation

Terraform is declarative: you write resource "aws_vpc" "main" { cidr_block = "10.0.0.0/16" } and Terraform figures out how to create it. Ansible is imperative: you write steps like "create VPC, then subnet, then EC2." Declarative is safer because you don't need to handle failures between steps — Terraform handles that automatically.

Q2

What file does Terraform use to track the mapping between your configuration and real-world resources?

Show Answer & Explanation
✅ Answer

The state file (terraform.tfstate).

📖 Explanation

The state file is a JSON document that maps resources in your .tf files to real cloud resources (e.g., aws_vpc.main → vpc-abc123). Without state, Terraform can't know what exists. State also tracks resource attributes, dependencies, and metadata. State should ALWAYS be stored remotely (S3, GCS, TFC) — never only on a local machine.

Q3

Which tool is best for multi-cloud infrastructure provisioning with state management?

Show Answer & Explanation
✅ Answer

Terraform — it's the only tool that combines multi-cloud support, rich state management, plan preview, and a dependency graph.

📖 Explanation

CloudFormation is AWS-only. Bicep is Azure-only. Ansible has no state management (it's configuration management, not provisioning). Pulumi is the closest competitor but has a smaller ecosystem. Terraform's unique combination of multi-cloud + state + plan + graph makes it the industry standard for IaC provisioning.

  🔑 terraform graph | dot -Tpng > graph.png (visualize as PNG!)

Why the Dependency Graph Matters

The dependency graph isn't just an optimization — it's what makes Terraform safe. Here's why:

🛡️
Safe Ordering

Terraform will NEVER try to create an EKS cluster before the VPC exists. The graph guarantees correct ordering — even if you list resources in the "wrong" order in your .tf files.

⚡
Maximum Parallelism

Resources that don't depend on each other are created simultaneously. With the default -parallelism=10, Terraform can create 10 independent resources at once — dramatically faster than sequential execution.

🔍
Failure Isolation

If one subnet creation fails, resources that DON'T depend on that subnet continue unaffected. Only dependent resources are blocked — partial success is better than total failure.

📊
Visualization

Run terraform graph | dot -Tpng > graph.png to generate a visual dependency graph. This is invaluable for understanding complex infrastructure and debugging ordering issues.

Show Answer & Explanation
✅ Answer

By building a Dependency Graph (DAG) from resource references in the configuration.

3.3 Your First Terraform Project — Hello anihpj!

Let's create your first Terraform resource: an S3 bucket for anihpj's static assets. In about 15 lines of code, you'll create real cloud infrastructure.

main.tf
terraform {
  required_version = ">= 1.5.0"
  required_providers {
    aws = { source = "hashicorp/aws"; version = "~> 5.0" }
  }
}
provider "aws" { region = "us-east-1" }

resource "aws_s3_bucket" "anihpj_assets" {
  bucket = "anihpj-static-assets-${random_id.bucket_suffix.hex}"
  tags = {
    Name = "anihpj-static-assets"; Environment = "dev"
    Project = "anihpj"; App = "jobpost"; ManagedBy = "terraform"
  }
}
resource "random_id" "bucket_suffix" { byte_length = 4 }

# WORKFLOW: init → fmt → validate → plan → apply → destroy
⚡ S3 Bucket Names Must Be Globally Unique

The random_id resource adds a random suffix to avoid name collisions. S3 bucket names are globally unique across ALL AWS accounts. Without the random suffix, your terraform apply would fail because someone else already used "anihpj-static-assets".

What Just Happened? — Understanding the Magic

Let's trace exactly what happened when you ran those commands:

terraform init

Read main.tf, discovered you need the aws and random providers, downloaded them from registry.terraform.io, and created .terraform.lock.hcl to pin their versions.

terraform plan

Compared your desired state (main.tf) with actual state (nothing exists yet — this is your first run). Determined: "I need to create 2 resources: aws_s3_bucket + random_id."

terraform apply

First created random_id.bucket_suffix (instant), then used its value to create aws_s3_bucket.anihpj_assets with a globally unique name. Wrote both resources to terraform.tfstate.

What if you run terraform apply again?

Terraform checks state, sees the bucket already exists, compares with .tf — no changes needed. Output: "No changes. Your infrastructure matches the configuration." This is idempotency — running the same command twice produces the same result.

Show Answer & Explanation

4.4 Locals — DRY Inside a Module

Locals define reusable expressions within a module. Unlike variables, locals can't be overridden from outside.

locals block
locals {
  common_tags = { Project = "anihpj"; ManagedBy = "terraform" }
  name_prefix = "${var.environment}-anihpj"
}
resource "aws_s3_bucket" "assets" { tags = merge(local.common_tags, { Name = local.name_prefix }) }
💡 Locals vs Variables — When to Use Which

Variables = inputs from the outside (can be overridden by callers). Locals = internal computations (can't be overridden). Use variables for things that CHANGE per environment (var.instance_size). Use locals for things you COMPUTE from other values (local.name_prefix = "${var.env}-${var.app}") or for constants shared across resources (local.common_tags). If you find yourself repeating the same expression, make it a local.

6.1 Resource Dependencies — Implicit vs Explicit

Implicit: Terraform figures it out from references. Explicit: You use depends_on. Prefer implicit — it's cleaner and safer.

✅ IMPLICIT (Preferred)
resource "aws_instance" "web" {
  subnet_id = aws_subnet.public.id  # ← Creates dependency
}

Terraform sees the reference and knows: subnet must be created FIRST. No extra code needed. 95% of dependencies should be implicit.

⚠️ EXPLICIT (Use Sparingly)
resource "null_resource" "cleanup" {
  depends_on = [aws_instance.web]  # ← Manual dependency
}

Use ONLY when Terraform can't infer the link (scripts after resource creation). Overusing depends_on creates unnecessary bottlenecks.

6.4 Dynamic Blocks — Generate Nested Blocks

Dynamic Block Example — Security Group

resource "aws_security_group" "web" {
  name = "anihpj-web-sg"
  
  dynamic "ingress" {
    for_each = var.ingress_ports
    content {
      from_port   = ingress.value
      to_port     = ingress.value
      protocol    = "tcp"
      cidr_blocks = ["0.0.0.0/0"]
    }
  }
}

6.5 The Splat Expression (*) and For Expressions

Answer: can(expr) returns true/false (boolean) — use in conditionals. try(expr, fallback) returns the expression value or fallback — use when you need the result.

Explanation: merge() combines maps left to right. Later maps override earlier ones for duplicate keys. So merge({a=1,b=2},{b=99}) gives {a=1,b=99} — the custom_tags override default_tags.

Answer: flatten()

8.2 Advanced For Expressions — Transforming Data

For expressions transform lists and maps into new collections. The syntax: [for item in collection : result] for lists, {for key, value in map : key => value} for maps. These are some of the most powerful — and most tested — HCL features.

8.2a List Transformation

Transform every element of a list into something new: [for item in list : expression]

List Transformation Examples
# Extract CIDR blocks from subnet objects
[for s in var.subnets : s.cidr_block]
# Input: [{name="pub", cidr="10.0.1.0/24"}, {name="priv", cidr="10.0.2.0/24"}]
# Output: ["10.0.1.0/24", "10.0.2.0/24"]

# Uppercase all environment names
[for env in var.environments : upper(env)]
# Input: ["dev", "staging", "prod"]
# Output: ["DEV", "STAGING", "PROD"]

# Generate AZ-qualified names
[for az in ["a","b","c"] : format("us-east-1%s", az)]
# Output: ["us-east-1a", "us-east-1b", "us-east-1c"]

8.2b List Filtering

Filter and transform simultaneously: [for item in list : result if condition]

List Filtering Examples
# Get only public subnet IDs
[for s in var.subnets : s.id if s.public == true]
# Filters out private subnets, returns only public subnet IDs

# Get only enabled instance names
[for i in var.instances : i.name if i.enabled]
# Skips disabled instances

# Get CIDR blocks larger than /24
[for s in var.subnets : s.cidr_block if tonumber(split("/", s.cidr_block)[1]) < 24]

8.4 Sensitive Data Handling 🎯

Terraform provides built-in mechanisms to protect sensitive data like passwords, API keys, and database credentials. The sensitive = true flag prevents values from appearing in plan/apply output and CLI displays.

🔒 Marking Variables Sensitive
variable "db_password" {
  type      = string
  sensitive = true  # Hidden from output
}

Prevents the value from appearing in: plan output, apply output, terraform console, and logs.

🔒 Marking Outputs Sensitive
output "rds_password" {
  value     = aws_db_instance.jobpost.password
  sensitive = true  # Hidden from CLI
}

Value is still in state file (encrypted in remote backends). Use terraform output -json to access programmatically.

NEVER hardcode secrets in .tf files. Q8.1 Write a conditional expression that sets instance_type to "t3.large" for prod and "t3.small" otherwise. ▼

Answer: instance_type = var.environment == "prod" ? "t3.large" : "t3.small"

Explanation: The ternary operator syntax is condition ? if_true : if_false. Always consider readability — for 3+ conditions, prefer lookup() with a map over nested ternaries.

Q8.2 What happens if you write var.flag ? var.optional.field : "default" and var.flag is false but var.optional is null? ▼

Answer: It FAILS. Both branches are evaluated regardless of the condition.

Fix: var.flag ? try(var.optional.field, "default") : "default"

Explanation: Terraform evaluates both branches at plan time. Even though var.flag is false, Terraform still tries to access var.optional.field and crashes. Wrap unsafe branches in try().

Q8.3 How do you extract only the public subnet IDs from a list of subnet objects? ▼

Answer: [for s in var.subnets : s.id if s.public == true]

Explanation: The if clause after the colon filters the list. Only elements where the condition is true are included. You can also combine with transformation: [for s in var.subnets : upper(s.name) if s.public].

Q8.4 Convert a list of subnet objects into a map of name → cidr_block. ▼

Answer: {for s in var.subnets : s.name => s.cidr_block}

Explanation: The curly brace form {for...in...: key => value} returns a map. The key expression (before =>) must be unique — duplicates will cause errors.

Q8.5 How do you test a CIDR block validation before putting it in a variable block? ▼

Answer: Use terraform console: > can(cidrnetmask("10.0.0.0/16")) → true

Explanation: The console lets you instantly test any function or expression. Test your validation logic there before adding it to variables.tf — this is the recommended exam workflow for debugging complex expressions.

Q8.6 How do you mark a variable as sensitive so its value never appears in plan output? ▼

Answer: Add sensitive = true to the variable declaration.

variable "db_password" {
  type      = string
  sensitive = true
}

Explanation: Sensitive variables are redacted in plan/apply output, console, and logs. The value still exists in state — ensure your remote state backend encrypts it. Use terraform output -json to access sensitive outputs programmatically.

Q8.7 You need to conditionally create a CloudWatch dashboard only in production. Write the resource block. ▼

Answer:

resource "aws_cloudwatch_dashboard" "main" {
  count          = var.environment == "prod" ? 1 : 0
  dashboard_name = "anihpj-${var.environment}"
  dashboard_body = jsonencode({...})
}

Explanation: count = condition ? 1 : 0 is the standard pattern for conditional resource creation. When count is 0, no resource is created. When 1, exactly one is created.

Q8.8 What does [for s in var.subnets : s.cidr_block] return? ▼

Answer: A list of strings containing only the cidr_block values from each subnet object.

Explanation: Square bracket [...] for-expressions always return lists. If the input is [{cidr="10.0.1.0/24"}, {cidr="10.0.2.0/24"}], the output is ["10.0.1.0/24", "10.0.2.0/24"].

Q8.9 How do you flatten a nested list-of-lists into a single flat list? ▼

Answer: flatten([[a,b],[c,d,e]]) returns [a,b,c,d,e]

Explanation: flatten() takes a list of lists and returns a single flat list. This is commonly used after nested for-expressions. Example: flatten([for env in var.envs : [for subnet in env.subnets : subnet.id]]).

Q8.10 You want to create a map where keys are environment names and values are their instance types. Write the for expression. ▼

Answer: {for config in var.env_configs : config.name => config.instance_type}

Explanation: This converts a list of objects into a lookup map. Result: {"dev" = "t3.small", "prod" = "t3.large"}. You can then use lookup(local.env_types, var.environment, "t3.medium") for safe access.

9.2 Custom Validation Rules 🎯

Validation blocks catch bad input early — at plan time — with clear, actionable error messages. Every variable with constraints should have validation rules.

5 Exam-Ready Validation Patterns for Anihpj
variable "environment" {
  type    = string
  default = "dev"

  # PATTERN 1: Allowed values check (most common)
  validation {
    condition     = contains(["dev", "staging", "prod"], var.environment)
    error_message = "Environment must be one of: dev, staging, prod. Got: ${var.environment}"
  }
}

variable "vpc_cidr" {
  type    = string

  # PATTERN 2: Format validation with regex/can()
  validation {
    condition     = can(cidrnetmask(var.vpc_cidr))
    error_message = "Invalid CIDR format: ${var.vpc_cidr}. Must be like 10.0.0.0/16."
  }
}

variable "instance_type" {
  type    = string

  # PATTERN 3: Regex pattern matching
  validation {
    condition     = can(regex("^t[23]\\.", var.instance_type))
    error_message = "Only t2/t3 instance families allowed. Got: ${var.instance_type}"
  }
}

variable "app_port" {
  type    = number

  # PATTERN 4: Numeric range check
  validation {
    condition     = var.app_port >= 1024 && var.app_port <= 65535
    error_message = "Port must be between 1024-65535. Got: ${var.app_port}"
  }
}

variable "cluster_name" {
  type    = string

  # PATTERN 5: String length check
  validation {
    condition     = length(var.cluster_name) >= 1 && length(var.cluster_name) <= 32
    error_message = "Cluster name must be 1-32 characters. Got: ${length(var.cluster_name)} chars."
  }
}

# PATTERN 6: Multiple validations on one variable
variable "db_engine" {
  type    = string
  default = "postgres"

  validation {
    condition     = contains(["postgres", "mysql", "mariadb"], var.db_engine)
    error_message = "Supported engines: postgres, mysql, mariadb."
  }
  validation {
    condition     = var.db_engine == "postgres" || var.db_engine == "mysql"
    error_message = "Anihpj only supports PostgreSQL and MySQL."
  }
}
💡 Validation Best Practices

1) Always include the actual value in error_message using ${var.name} — it saves hours of debugging. 2) Use can() to wrap functions that might error on bad input (like can(regex(...))). 3) One validation block per concern — combine related checks only if logically related. 4) Validation runs at plan time — before any resources are touched.

10.2 The State Lock — Preventing Race Conditions 🎯

When two people run terraform apply at the same time, they could both write to the state file simultaneously — corrupting it. State locking prevents this by ensuring only one process can modify state at a time.

State Locking — Alice vs Bob Timeline
TIME   ALICE (terraform apply)              BOB (terraform apply)
────────────────────────────────────────────────────────────────────
T+0s   Acquires state lock 🔒               Attempts acquire lock...
       │                                     WAITING ⏳
T+5s   Reads state from S3                  "Lock held by Alice"
       │                                     (terraform waits)
T+30s  Builds dependency graph              Still waiting...
       │
T+1m   Shows plan, Alice confirms           Waiting...
       "yes" (approves 15 changes)
T+3m   Applies changes to AWS               Waiting...
       Creates VPC, EKS, RDS
T+5m   Writes new state to S3              Waiting...
       Releases lock 🔓                     │
                                            "Lock acquired!" 🔒
T+6m   Done ✅                              Reads latest state from S3
                                            (includes Alice's new resources!)
                                            Builds graph, shows plan...

WITHOUT LOCKING: Both write simultaneously → state corruption → 💀
🔒 How Locking Works

Before any state-modifying operation (apply, destroy), Terraform acquires a lock. The backend stores this lock (DynamoDB for S3, object lock for GCS, lease blob for Azure).

⏱️ Lock Duration

The lock is held for the entire apply. If the process crashes, the lock stays — you need terraform force-unlock LOCK_ID to release it manually.

✅ Locking Backends

S3+DynamoDB, GCS, Azure, Terraform Cloud, Consul, pg all support locking. local and http backends do NOT — avoid them for team use.

⚠️ force-unlock — The Nuclear Option

terraform force-unlock LOCK_ID removes a lock. ONLY use this if you're 100% sure no one is running apply. If someone IS running terraform and you force-unlock, two applies will run simultaneously — corrupting the state. Always check with your team first!

Q2
What happens if two team members run terraform apply simultaneously without state locking?
Show Answer
Answer

State file corruption. Both processes write to the state file at the same time, creating an inconsistent state that doesn't match reality. One person's changes are lost, and the infrastructure drifts from what Terraform believes exists.

WITHOUT LOCKING:
Alice writes state ───┐
                      ├── STATE CORRUPTED 💀
Bob writes state ─────┘

WITH LOCKING:
Alice acquires lock → writes state → releases lock
Bob waits → acquires lock → reads updated state → writes state

Q7
What AWS services does the S3 backend use for state storage and locking, and why is the locking component necessary?
Show Answer
Answer

S3 stores the state file (with SSE encryption + versioning). DynamoDB provides distributed locking (table with LockID as primary key). S3 itself has no native locking mechanism — DynamoDB fills this gap.

Explanation

The DynamoDB table uses LockID as the hash key with PAY_PER_REQUEST billing. When Terraform starts an operation, it writes a lock entry; if another process holds the lock, it waits. The lock is released after state is written. Always enable S3 versioning on state buckets — it's your lifeline for recovery.

Q8

Explanation

Always verify with your team before force-unlocking. Check CI/CD pipelines — a stuck pipeline job may still hold the lock. If the original process is truly dead (killed mid-apply, network timeout), then force-unlock is safe. It's called the "nuclear option" for a reason.

Explanation

State files are JSON blobs that include every resource attribute — including password, access_key, secret_key fields. Even if you mark variables as sensitive = true, the values are still in the state file. Always use remote backends with encryption (S3+SSE, GCS+managed keys) and restrict access via IAM.

Q2

Show Answer
Answer

Explanation

⚠️ GOTCHA: import writes STATE, not .tf!

🆕 TF 1.5+: Declarative import Blocks

Terraform 1.5 introduced import blocks — you can now declare imports directly in .tf files instead of running CLI commands:

# File: imports.tf
import {
  to = aws_s3_bucket.anihpj_assets    # Resource address in state
  id = "anihpj-assets-prod"           # Real-world resource ID
}

resource "aws_s3_bucket" "anihpj_assets" {
  bucket = "anihpj-assets-prod"       # Must match what exists
  tags   = { Name = "anihpj-assets" }
}

# Now just run: terraform plan
# Terraform reads the import block, finds the bucket,
# checks if .tf matches, and imports automatically!

This is much cleaner than the CLI workflow — everything is declarative and version-controlled. The exam may test TF 1.5+ features.

Called by root or other modules via module "name" {}. Self-contained with variables, outputs, and resources.

🔗 Published Module

Shared via Registry, GitHub, or S3. Versioned with semver. Battle-tested by the community.

💡 The Module Mindset

Think: "What infrastructure pattern do I repeat?" That's a module waiting to be created. Anihpj examples: VPC (repeated per environment), EKS cluster (repeated for dev/staging/prod), RDS database (same config, different sizes). Modules eliminate copy-paste and make infrastructure consistent.

⚠️ Module Composition Pitfalls

(1) Circular dependencies: Module A depends on Module B which depends on Module A — Terraform will error. (2) Too many layers: 4-5 layers is the sweet spot; beyond that, plan times slow down. (3) Hardcoded references: Always use outputs — never hardcode IDs from one module into another.

🔀 Provider Passing — When Modules Need Different Providers

Child modules inherit providers from the root by default. But what if you need a module to use a different region or account?

Default: Inherited Provider
# Root: default provider = us-east-1
provider "aws" { region = "us-east-1" }

module "vpc" { source = "./modules/vpc" }
# VPC module automatically uses us-east-1
Override: Aliased Provider
# Root: two providers
provider "aws" { region = "us-east-1"; alias = "virginia" }
provider "aws" { region = "us-west-2"; alias = "oregon" }

module "dr_vpc" {
  source    = "./modules/vpc"
  providers = { aws = aws.oregon }  # Override!
}

🔑 This is exam Pattern 3: providers = { aws = aws.ALIAS } in the module block. Essential for multi-region and multi-account deployments.

Chapter 13 — Practice Questions

Q1
What is a Terraform module and how does it differ from a resource?
Show Answer
Answer

A module is a container for multiple resources that are used together. A resource manages a single cloud object (one EC2, one VPC). A module groups many resources (VPC + subnets + NAT + routes) into one reusable unit. Every Terraform directory is a root module.

Explanation

Modules enable reuse, organization, and encapsulation. Instead of copying 50 lines of VPC code into every environment, you call module "vpc" {} and pass parameters. The root module is the directory where terraform init runs; child modules are called via module blocks.

Q2
How do you access a module's output value from the root module?
Show Answer
Answer

module.NAME.OUTPUT_NAME. Example: module.vpc.vpc_id returns the VPC ID from the vpc module.

module "vpc" { source = "./modules/vpc" }
resource "aws_eks_cluster" "main" {
  vpc_id = module.vpc.vpc_id  # ← accessing module output
}
Explanation

The syntax is always module.LOCAL_NAME.OUTPUT_NAME. The local name is what you put after module in the block (e.g., module "vpc"). The output name must exist in the module's outputs.tf. This is one of the most tested patterns on the exam.

Q3
List at least 4 valid sources for Terraform modules.
Show Answer
Answer

1. Local path: "./modules/vpc"
2. Public Registry: "terraform-aws-modules/vpc/aws"
3. GitHub: "github.com/anihpj/terraform-aws-vpc"
4. S3: "s3::https://s3.amazonaws.com/bucket/vpc.zip"
Also: Private Registry, Bitbucket, GitLab, HTTP URLs, GCS buckets.

Explanation

The exam may ask "which of the following are valid module sources?" — all of the above are valid. Terraform supports local paths, registries (public and private), and any Git-based source. S3/GCS sources must point to zip/tar archives.

Q4
What is the root module and where does it get its name?
Show Answer
Answer

The root module is the working directory where you run terraform init. Every Terraform configuration has exactly one root module. It has no explicit name — it IS the root.

Explanation

This is a common exam trick question. The root module isn't declared with a module block — it's defined by the directory itself. All .tf files in the root directory belong to the root module. Child modules are called FROM the root module.

Q5
Your VPC module exposes vpc_id and public_subnet_ids as outputs. How do you use both in an EKS cluster resource?
Show Answer
Answer
module "vpc" { source = "./modules/vpc" }

resource "aws_eks_cluster" "main" {
  vpc_id     = module.vpc.vpc_id
  subnet_ids = module.vpc.public_subnet_ids
}
Explanation

Each output is accessed individually with module.NAME.OUTPUT. You can also reference the entire module output as an object: module.vpc is an object with .vpc_id and .public_subnet_ids attributes. You could pass it whole: vpc_config = module.vpc.

Q6
Where do child modules get their provider configurations from?
Show Answer
Answer

Child modules inherit providers from the root module unless explicitly overridden. If the root has provider "aws" { region = "us-east-1" }, all child modules use it.

Explanation

To override a provider in a child module, use the providers argument: module "replica" { providers = { aws = aws.us-west-2 } }. This is tested when you need different regions or aliased providers in different modules.

Q7
What is module composition and why is layer ordering important?
Show Answer
Answer

Module composition is building infrastructure in layers where each layer depends on the one below. Foundation → Network → Compute → Application. Ordering matters because upper layers need outputs from lower layers (e.g., EKS needs VPC ID).

Explanation

Proper layering creates clear dependency chains. If VPC changes, Terraform knows to re-evaluate EKS and Application layers. Without layering, you risk creating resources before their dependencies exist, causing apply failures.

Q8
How do you version-pin a module from the Terraform Registry?
Show Answer
Answer
module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "~> 5.0"  # Accept 5.x, NOT 6.x
}
Explanation

~> 5.0 means >= 5.0.0 and < 6.0.0 — you get bug fixes and new features but no breaking changes. >= 4.0, < 5.0 is an explicit range. 5.0.0 is exact pinning. Always pin registry modules to avoid surprise breaking changes.

Q9
What files should every well-structured module contain?
Show Answer
Answer

Minimum: main.tf (resources), variables.tf (inputs), outputs.tf (outputs)
Recommended: README.md (documentation), versions.tf (provider requirements), examples/ (usage examples)

Explanation

The standard module structure makes modules discoverable and consistent. The Registry requires main.tf, variables.tf, outputs.tf, and README.md. Examples help users understand how to call your module. Follow this convention for all modules.

Q10
What happens if you remove a module block from your root configuration?
Show Answer
Answer

All resources in that module will be DESTROYED. Terraform sees the module is no longer in the configuration and plans to delete everything it created.

Explanation

Removing a module call is equivalent to removing all its resources from .tf. Terraform's job is to make reality match config — if the module is gone from config, the resources must be gone from reality. Use terraform state rm first if you want to keep the resources but remove Terraform management.

14.3 Version Constraints — Pinning for Safety

Module versions follow semantic versioning (MAJOR.MINOR.PATCH). Pinning versions prevents surprise breaking changes.

ConstraintMeaningExampleAllows
version = "~> 1.2"Pessimistic: >= 1.2, < 2.0"~> 5.0"5.0.x, 5.1.x, ..., NOT 6.x
version = ">= 2.0, < 3.0"Explicit range">= 20.0, < 21.0"20.x.x only
version = "1.0.0"Exact pin"5.5.1"ONLY 5.5.1
⚠️ Version Bump = Breaking Changes

When a module goes from v1.x to v2.x, it's a MAJOR change — variables may be removed, outputs renamed, defaults changed. Always read the CHANGELOG before upgrading major versions. Use ~> to get safe minor/patch updates without breaking changes.

Q4
What does version = "~> 5.0" mean?
Show Answer
Answer

>= 5.0.0 and < 6.0.0. Accepts 5.0.x, 5.1.x, 5.99.x — any 5.x version. Rejects 6.0.0 and above (potential breaking changes).

Q5
Why should you avoid v0.x.x modules in production?
Show Answer
Answer

v0.x.x has no stability guarantees. The module author can make breaking changes in any minor/patch version. v1.0.0+ follows semantic versioning: breaking changes only in major versions. v0.5.1 → v0.6.0 could break your infrastructure without warning.

Show Answer
Answer

version = "~> 1.5" (pessimistic) OR version = ">= 1.5, < 2.0" (explicit). Both achieve the same result — ~> is more concise.

Q8

Show Answer
Answer

  vpc_id     = module.vpc.vpc_id
  subnet_ids = module.vpc.private_subnets

The VPC module's outputs (vpc_id, private_subnets) become the EKS module's inputs. This creates an implicit dependency — EKS won't be created until VPC is ready.

Q9
What does the single_nat_gateway = true argument do in the VPC module?
Show Answer
Answer

Creates only ONE NAT Gateway (shared across AZs) instead of one per AZ. This saves ~$32/month per additional NAT Gateway. Use in non-production environments. Prod should use one per AZ for high availability.

Q10
What happens if the registry module you're using gets a new major version (e.g., v5 → v6) with breaking changes?
Show Answer
Answer

If you pinned with version = "~> 5.0", nothing happens — Terraform will not upgrade to v6. Your infrastructure is safe. If you used no version constraint, Terraform would download the latest (v6) on next terraform init -upgrade, potentially breaking your configuration.

Chapter 16: Provisioners — Last Resort Configuration

Provisioners run scripts during resource creation or destruction. They're Terraform's escape hatch — a way to do things the provider doesn't support. But they come with serious limitations: no state tracking, no idempotency guarantees, and no drift detection. Think of them as the tool of last resort.

🔑 Key Exam Insight

The exam tests: (1) knowing when NOT to use provisioners, (2) local-exec vs remote-exec, (3) when = destroy for cleanup, and (4) on_failure = continue. The #1 exam trap: choosing a provisioner when user_data, Packer, or a provider resource would work better.

│  │   2. AWS API: Delete the resource                             │  │
│  │   3. Remove resource from state                                │  │
│  └───────────────────────────────────────────────────────────────┘  │
│                                                                      │
│  ⚠️  KEY INSIGHT: Provisioners run AFTER the resource is created    │
│     but BEFORE state is written. If provisioner fails:               │
│     → Resource is TAINTED (marked for recreation on next apply)     │
│     → State is NOT written (resource exists in AWS but not in state) │
└──────────────────────────────────────────────────────────────────────┘

Chapter 16 — Practice Questions

Q1
What is a provisioner and when should you use one?
Show Answer
Answer

A script runner during resource create/destroy. Use as last resort — only when the provider lacks support AND no better alternative exists (user_data, Packer, Ansible).

Explanation

Exam trap: "configure a web server" → answer is user_data/Packer, NEVER provisioner. Provisioners have no state, aren't idempotent, and slow down applies.

Q2
Where does local-exec run?
Show Answer
Answer

On the machine running Terraform (laptop, CI runner, TFC agent). Has access to your local tools and credentials.

Q3
What does the connection block configure?
Show Answer
Answer

SSH/WinRM connection for remote-exec: type, user, private_key/password, host (usually self.public_ip), port, timeout.

Q4
How to run a provisioner during terraform destroy?
Show Answer
Answer
provisioner "local-exec" { when = destroy; command = "cleanup.sh" }
Q5
What does on_failure = continue do?
Show Answer
Answer

Apply succeeds even if provisioner fails. Resource is NOT tainted. Use for optional tasks where failure shouldn't block deployment.

Q6
Why shouldn't you use provisioners to configure a web server?
Show Answer
Answer

No state tracking, not idempotent, slow. Use user_data (cloud-init), Packer (pre-baked AMI), or Ansible/Chef instead.

Q7
Write local-exec to update kubeconfig after EKS creation.
Show Answer
Answer
provisioner "local-exec" {
  command = "aws eks update-kubeconfig --name ${aws_eks_cluster.main.name} --region us-east-1"
}
Q8
What happens when a provisioner fails with default settings?
Show Answer
Answer

Resource is tainted — destroyed and recreated on next apply. The current apply fails.

Q9
Valid when argument values?
Show Answer
Answer

when = create (default) or when = destroy.

Q10
Most important limitation of provisioners?
Show Answer
Answer

No state tracking. Terraform doesn't record provisioner effects. Manual changes won't be detected or fixed, unlike provider resources which track state.

Chapter 17: Data Sources, External Providers & Null Resources

Beyond basic resources, Terraform provides advanced mechanisms for reading external data, calling external programs, and triggering actions without managing a real resource. These patterns are essential for real-world workflows.

🔑 Exam Focus

The exam tests: (1) data source chaining and lifecycle, (2) external data source limitations, (3) null_resource with triggers, and (4) terraform_data (TF 1.4+) as the modern replacement.

17.1 Advanced Data Source Patterns

Data sources read existing infrastructure at plan time. They cannot depend on resources being created in the same apply — unless you use depends_on.

Data Source Lifecycle — When They Execute
┌─────────────────────────────────────────────────────────────────┐
│                                                                  │
│  terraform plan:                                                 │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │ 1. Read ALL data sources (from existing infrastructure)   │   │
│  │ 2. Compute desired state from .tf files                   │   │
│  │ 3. Diff actual (from data sources) vs desired (.tf)       │   │
│  │ 4. Show plan                                              │   │
│  └──────────────────────────────────────────────────────────┘   │
│                                                                  │
│  terraform apply:                                                │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │ 1. Read data sources AGAIN (values may have changed!)     │   │
│  │ 2. Create/update resources                                │   │
│  │ 3. Write state                                            │   │
│  └──────────────────────────────────────────────────────────┘   │
│                                                                  │
│  ⚠️  Data sources execute BEFORE resource creation               │
│     → Can't read resources being created in the SAME apply       │
│     → Use depends_on to force ordering if needed                 │
└─────────────────────────────────────────────────────────────────┘
Data Source Chaining — Anihpj EKS Setup
# Chain: AMI → Subnets → Security Group → EC2
data "aws_ami" "ubuntu" {
  most_recent = true
  filter { name = "name"; values = ["ubuntu/images/hvm-ssd/ubuntu-jammy-22.04-*"] }
  owners = ["099720109477"]  # Canonical
}

data "aws_subnets" "private" {
  filter { name = "vpc-id"; values = [module.vpc.vpc_id] }
  filter { name = "tag:Tier"; values = ["private"] }
}

data "aws_security_group" "rds_sg" {
  filter { name = "group-name"; values = ["anihpj-rds-${var.environment}"] }
}

# Use chained data sources in a resource
resource "aws_instance" "bastion" {
  ami           = data.aws_ami.ubuntu.id
  instance_type = "t3.micro"
  subnet_id     = data.aws_subnets.private.ids[0]
  vpc_security_group_ids = [data.aws_security_group.rds_sg.id]
}
📖 Data Source (READ only)
data "aws_ami" "ubuntu" {
  most_recent = true
  owners = ["099720109477"]
}

Reads existing infrastructure. Runs at plan AND apply time. Cannot create or modify anything. Result is read-only reference stored in state.

🔧 Resource (CREATE/UPDATE/DELETE)
resource "aws_instance" "web" {
  ami           = data.aws_ami.ubuntu.id
  instance_type = "t3.medium"
}

Manages real cloud resources. Runs at apply time. Creates, updates, or destroys infrastructure. Fully tracked in state with drift detection.

17.2 The external Data Source — Call External Programs

The external data source runs an external program and reads JSON from its stdout. This lets you incorporate data from scripts, APIs, or tools that don't have Terraform providers.

external Data Source — Python Script + Terraform
# File: generate_id.py
#!/usr/bin/env python3
import json, sys, hashlib, datetime
input_data = json.load(sys.stdin)
unique_id = hashlib.md5(f"{input_data['env']}-{datetime.datetime.now()}".encode()).hexdigest()[:8]
print(json.dumps({"id": unique_id}))

# File: main.tf
data "external" "unique_id" {
  program = ["python3", "${path.module}/generate_id.py"]
  query   = { env = var.environment }
}

# Use the generated ID
resource "aws_s3_bucket" "unique" {
  bucket = "anihpj-${var.environment}-${data.external.unique_id.result.id}"
}

# ⚠️  LIMITATIONS:
# • Program must output valid JSON to stdout
# • Program is re-run on EVERY plan/apply (SLOW!)
# • No built-in caching or state tracking
⚠️ external Data Source Limitations

The external program runs on every plan and apply — there's no caching. If the program is slow, Terraform is slow. Also, the program must accept JSON on stdin and output JSON on stdout. Any stderr output is logged but ignored. Use sparingly — prefer native providers or http data source for API calls.

17.3 null_resource — Provisioner Without a Resource

null_resource behaves like a resource but manages nothing. Its purpose: to run provisioners that aren't tied to a real resource, especially with triggers that force re-execution when values change.

17.3a The triggers Pattern — Rerun When Values Change

null_resource triggers — K8s ConfigMap Watcher
# PROBLEM: When a ConfigMap changes, pods need to restart to pick up new config
# null_resource triggers can detect changes and trigger a rolling restart

resource "kubernetes_config_map" "app_config" {
  metadata { name = "jobpost-config" }
  data = { DATABASE_URL = "postgres://${aws_db_instance.jobpost.address}:5432/jobpost" }
}

resource "null_resource" "restart_pods" {
  triggers = {
    # Re-run when ConfigMap data changes
    config_hash = sha256(jsonencode(kubernetes_config_map.app_config.data))
  }

  provisioner "local-exec" {
    command = <<-EOT
      kubectl rollout restart deployment/jobpost -n ${var.environment}
      echo "Restarted jobpost pods due to config change"
    EOT
  }
}

17.3b local-exec with null_resource

null_resource + local-exec — Post-Apply Automation
resource "null_resource" "anihpj_health_check" {
  depends_on = [aws_eks_node_group.main]

  triggers = {
    # Re-run if cluster endpoint or node count changes
    endpoint = aws_eks_cluster.anihpj.endpoint
    nodes    = aws_eks_node_group.main.scaling_config[0].desired_size
  }

  provisioner "local-exec" {
    command = <<-EOT
      echo "Waiting for EKS nodes to be Ready..."
      kubectl wait --for=condition=Ready nodes --all --timeout=300s
      echo "All nodes Ready! Running smoke test..."
      curl -f https://${aws_eks_cluster.anihpj.endpoint}/healthz && echo "OK" || echo "FAIL"
    EOT
  }
}

17.4 terraform_data — The Modern Replacement (TF 1.4+)

terraform_data is the managed replacement for null_resource. It's a first-class managed resource that integrates better with the dependency graph.

🔴 null_resource (Legacy)
resource "null_resource" "example" {
  triggers = {
    hash = sha256(var.value)
  }
  provisioner "local-exec" {
    command = "echo trigger fired"
  }
}

❌ Still works but considered legacy
❌ Requires null provider

🟢 terraform_data (TF 1.4+)
resource "terraform_data" "example" {
  triggers_replace = {
    hash = sha256(var.value)
  }
  provisioner "local-exec" {
    command = "echo trigger fired"
  }
}

✅ Built-in — no extra provider
✅ triggers_replace is explicit about behavior

💡 When to Use terraform_data vs null_resource

Use terraform_data for new projects (TF 1.4+). The key difference: terraform_data.triggers_replace explicitly signals "changing this replaces the resource" — clearer intent than null_resource.triggers. Both support provisioners, but terraform_data is the future.

Chapter 17 — Practice Questions

Q1
When do data sources execute in the Terraform lifecycle?
Show Answer
Answer

At plan time (to build the plan) and again at apply time (to get current values). They cannot read resources being created in the same apply unless you use depends_on.

Q2
What does the external data source do?
Show Answer
Answer

Runs an external program, reads JSON from stdout, and exposes the result as a data source. Useful for scripts or tools without Terraform providers. Limitations: runs every plan/apply, no caching.

Q3
What is a null_resource and when would you use it?
Show Answer
Answer

A resource that manages nothing — used to run provisioners not tied to a real resource, especially with triggers to force re-execution when values change. Example: restart K8s pods when ConfigMap changes.

Q4
How do triggers work in null_resource?
Show Answer
Answer

When any trigger value changes, the null_resource is destroyed and recreated, re-running its provisioners. This is how you force a provisioner to re-execute when something changes.

Q5
Write a null_resource that restarts pods when ConfigMap data changes.
Show Answer
Answer
resource "null_resource" "restart" {
  triggers = { config_hash = sha256(jsonencode(kubernetes_config_map.app.data)) }
  provisioner "local-exec" { command = "kubectl rollout restart deploy/jobpost" }
}
Q6
What is terraform_data and when was it introduced?
Show Answer
Answer

TF 1.4+ managed replacement for null_resource. Uses triggers_replace instead of triggers — the name explicitly signals that changing the trigger replaces the resource. Built-in, no extra provider needed.

Q7
What format must external data source programs output?
Show Answer
Answer

Valid JSON on stdout. Input is read from stdin (also JSON). Stderr is logged but ignored. Any other output format causes an error.

Q8
Can a data source read a resource being created in the same apply?
Show Answer
Answer

Not by default — data sources execute before resource creation. To force ordering, use depends_on on the data source referencing the resource being created.

Q9
What's the difference between null_resource.triggers and terraform_data.triggers_replace?
Show Answer
Answer

Functionally identical, but triggers_replace is more explicit about behavior. Both replace the resource when trigger values change, re-running provisioners. terraform_data is the modern, built-in replacement for null_resource.

Q10
What is data source chaining and why is it useful?
Show Answer
Answer

Using one data source's output as another's input: data.aws_ami → data.aws_subnet → resource. This reads all necessary information from existing infrastructure before creating new resources, ensuring accuracy and avoiding hardcoded IDs.
