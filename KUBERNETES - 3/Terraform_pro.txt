Chapter 1: What is Terraform? (The Big Picture)
--------------------------------------------------------------------------------
    1.1  The Problem Terraform Solves
         - Before IaC: Manual click-ops, snowflake servers, "who changed what?"
         - Real-world scenario: Deploying anihpj infrastructure manually —
           SSH into EC2, install Docker, configure K8s, set up load balancer...
           Takes days, error-prone, impossible to reproduce exactly
         [PAIN POINT CARDS — "Manual Infrastructure Deployment" nightmare]
         ┌────────────────────────────────────────────────────┐
         │ 😰 Deploying anihpj WITHOUT Terraform              │
         │                                                    │
         │  • AWS Console: Click, click, click... 200+ steps │
         │  • Forget one security group rule = broken app     │
         │  • Staging ≠ Production = config drift             │
         │  • Onboarding a new dev: "Here's a 50-page wiki"  │
         │  • Disaster recovery: "Rebuild from memory"        │
         └────────────────────────────────────────────────────┘

    1.2  Infrastructure as Code (IaC) Defined
         - "Define your infrastructure in configuration files that you
           can version, reuse, and share — just like application code"
         - Declarative approach: You say WHAT you want, Terraform figures out HOW
         - Example: "I want an EKS cluster with 3 worker nodes, a PostgreSQL
           RDS instance, and a VPC with public/private subnets"
           → Terraform creates it ALL in the correct order
         [ANALOGY CARD: Terraform = Blueprint for your cloud infrastructure]

         [DECLARATIVE vs IMPERATIVE — Visual Comparison]

         [COMPARISON TABLE: Terraform vs CloudFormation vs Pulumi vs Ansible

           • Multi-cloud: One language for AWS, GCP, Azure, K8s, GitHub, etc.

Chapter 2: Terraform Architecture & How It Works
--------------------------------------------------------------------------------
    2.1  The Terraform Core Engine
         - What happens when you run `terraform apply`?
         - The reconciliation loop: Parse .tf → Load state → Build dependency graph →
           Compare desired vs actual → Generate execution plan → Apply changes →
           Update state file
         [ANIMATED FLOWCHART: terraform apply lifecycle step-by-step]

    2.2  Providers — The Bridge to Cloud APIs
         - What is a provider? (Plugin that translates HCL → API calls)
         - AWS Provider: Translates `resource "aws_instance"` → EC2 API calls
         - Provider configuration: region, credentials, version constraints
         - The Provider Registry: registry.terraform.io — 2,000+ providers

    2.3  The Dependency Graph
         - Terraform builds a Directed Acyclic Graph (DAG) from your config
         - It knows: "Create VPC FIRST, then subnets, then EKS, THEN deploy apps"
         - Parallel vs sequential execution — independent resources run concurrently
         [DIAGRAM: Dependency graph for anihpj infrastructure]
         VPC → Subnets → NAT Gateway → EKS Cluster → Node Groups → K8s Deployments

    🧪 TERRAFORM APPLY — COMPLETE LIFECYCLE ANATOMY
    ┌──────────────────────────────────────────────────────────────────┐
    │  STAGE         WHAT HAPPENS                   TIME               │
    │  ───────────────────────────────────────────────────────────────│
    │  1. PARSE      Reads all .tf files in        < 1 second          │
    │     .tf FILES  working directory. Validates                      │
    │                HCL syntax.                                       │
    │                                                                  │
    │  2. LOAD       Reads terraform.tfstate      < 2 seconds          │
    │     STATE      from local disk or remote                         │
    │                backend (S3/GCS/TFC).                             │
    │                                                                  │
    │  3. REFRESH    Queries cloud APIs for        5-60 seconds        │
    │     STATE      EVERY resource in state.      (depends on # of    │
    │                Detects drift (manual          resources)         │
    │                changes outside Terraform).                       │
    │                                                                  │
    │  4. BUILD      Creates dependency graph      < 1 second          │
    │     GRAPH      (DAG). Determines parallel                        │
    │                vs sequential execution order.                    │
    │                                                                  │
    │  5. PLAN       Compares desired (.tf) vs     1-30 seconds        │
    │                actual (state). Generates      (depends on        │
    │                diff: +create/-destroy/         complexity)       │
    │                ~update/-/+replace.                               │
    │                                                                  │
    │  6. SHOW       Displays plan to user.        Interactive          │
    │     PLAN       User reviews and types "yes"                      │
    │                or "no" to confirm.                               │
    │                                                                  │
    │  7. APPLY      Executes API calls to         30 sec - 20 min     │
    │                cloud providers in correct    (EKS cluster:       │
    │                order. Creates/updates          ~15 min)           │
    │                resources.                                        │
    │                                                                  │
    │  8. UPDATE     Writes new state file          < 1 second          │
    │     STATE      with resource IDs, attributes,                    │
    │                and metadata.                                     │
    │                                                                  │
    │  ⏱️  Total: 1-25 minutes (depends on resources)                  │
    │  🔑  Stage 3 (Refresh) is why terraform plan gets slower over time│
    └──────────────────────────────────────────────────────────────────┘

Chapter 3: Installing & Setting Up Terraform
--------------------------------------------------------------------------------
    3.1  Installation (macOS, Linux, Windows, Docker)
         - macOS: brew install terraform
         - Linux: Manual binary download or package manager
         - Windows: Chocolatey or manual .exe
         - Docker: hashicorp/terraform image
         - Verify: terraform version
         [STEP CARDS: 4 installation methods with terminal screenshots]

    3.2  The Terraform CLI — Commands You'll Use Daily
         - terraform init    — Initialize working directory (download providers)
         - terraform plan    — Preview changes (THE MOST IMPORTANT COMMAND)
         - terraform apply   — Create/update infrastructure
         - terraform destroy — Tear down everything
         - terraform fmt     — Format .tf files consistently
         - terraform validate — Check syntax
         [TERMINAL RECORDING CARD: Full workflow for anihpj infrastructure]

    3.3  Your First Terraform Project — Hello anihpj!
         - Create main.tf with an AWS S3 bucket for anihpj static files
         - Run terraform init → plan → apply
         - See the bucket appear in AWS Console (in ~10 seconds!)
         - Run terraform destroy to clean up

Chapter 5: Planning and Applying — The Heart of Terraform
--------------------------------------------------------------------------------
    5.1  terraform plan — Preview Before You Leap 🎯
         - What plan does: Reads .tf → Refreshes state → Compares → Shows diff
         - Plan output symbols: + create, - destroy, ~ update in-place, -/+ replace
         - terraform plan -out=plan.tfplan — Save plan for later apply
         - terraform plan -target=resource — Plan only specific resources
         [TERMINAL OUTPUT CARD: Annotated plan output with symbol legend]

    5.2  terraform apply — Make It Real 🎯
         - Apply workflow: Show plan → Ask confirmation → Execute → Update state
         - terraform apply plan.tfplan — Apply saved plan (no confirmation)
         - terraform apply -auto-approve — Skip confirmation (CI/CD pipelines)
         - Parallelism: -parallelism=N (default 10 concurrent operations)
         [FLOW DIAGRAM: apply step-by-step with timing annotations]

    5.3  terraform destroy — Clean Up Everything 🎯
         - Destroys ALL resources in the current state
         - terraform destroy -target=resource — Destroy specific resource
         - ⚠️ WARNING: terraform destroy is IRREVERSIBLE for most resources
         [DANGER CARD: Destroy precautions and best practices]

    5.4  Resource Lifecycle — Meta-Arguments 🎯
         - lifecycle { create_before_destroy, prevent_destroy, ignore_changes }
         - create_before_destroy: Create new resource before destroying old (zero-downtime)
         - prevent_destroy: Protect critical resources from accidental deletion
         - ignore_changes: Ignore specific attribute changes (e.g., tags added externally)
         [DECISION CARD: When to use each lifecycle rule for anihpj RDS, S3, EKS]

         - What state tracks: Resource IDs, attributes, dependencies, metadata
         - How state is used: Plan (compare), Apply (update), Destroy (remove)

    10.2 The State Lock — Preventing Conflicts 🎯
         - Why locking: Two people running `terraform apply` simultaneously = CORRUPTION
         - How locking works: Lock acquired before any state-modifying operation
         - Backend support: S3 + DynamoDB, Terraform Cloud, Consul, GCS
         - Force-unlock: terraform force-unlock LOCK_ID (DANGER: only if stuck!)
         [LOCKING VISUALIZATION: Two users trying to apply — one gets lock, one waits]

         [STATE LOCKING — RACE CONDITION PREVENTION]
         ┌──────────────────────────────────────────────────────────────────┐
         │  TIME  ALICE (terraform apply)      BOB (terraform apply)        │
         │  ───────────────────────────────────────────────────────────────│
         │  T+0s  Acquires state lock 🔒       Attempts acquire lock...     │
         │        │                            WAITING ⏳                    │
         │  T+5s  Reads state from S3          "Lock is held by Alice"      │
         │        │                            (terraform waits patiently)  │
         │  T+30s Builds dependency graph       Still waiting...            │
         │        │                                                     │
         │  T+1m  Shows plan, Alice confirms    Waiting...                  │
         │        "yes"                                                      │
         │  T+3m  Applies changes to AWS        Waiting...                  │
         │        Creates VPC, EKS, RDS                                     │
         │  T+5m  Writes new state to S3        Waiting...                  │
         │        Releases lock 🔓              │                            │
         │                                      "Lock acquired!" 🔒         │
         │  T+6m  Done ✅                       Reads latest state from S3  │
         │                                      Builds graph with Alice's    │
         │                                      new resources included!     │
         │                                                                  │
         │  WITHOUT LOCKING: Both write to state simultaneously             │
         │  → State file corruption → Infrastructure drift → 💀             │
         └──────────────────────────────────────────────────────────────────┘

Chapter 22: Security and Compliance
--------------------------------------------------------------------------------
    22.1 Secrets Management 🎯
         - NEVER hardcode secrets in .tf files!
         - AWS Secrets Manager / SSM Parameter Store: data source for secrets
         - HashiCorp Vault: vault_generic_secret data source
         - Environment variables: TF_VAR_db_password
         - tfvars files: MUST be .gitignore'd — NEVER committed to Git!
         [SECRETS FLOW DIAGRAM: Where secrets live and how Terraform accesses them]

    22.2 State File Security
         - State contains ALL resource attributes — including sensitive ones
         - S3: Enable encryption (SSE-S3 or KMS), block public access, enable versioning
         - Access control: Least privilege IAM for state bucket access
         - NEVER share state files — equivalent to sharing all your cloud credentials
         [SECURITY CHECKLIST CARD: 6 state file security must-haves]

    22.3 Policy as Code (Sentinel / OPA)
         - Pre-deployment enforcement: Block non-compliant resources before creation
         - Example Sentinel policies:
           • All S3 buckets must have server-side encryption
           • All EBS volumes must be encrypted with KMS
           • EKS clusters must be private endpoint only
           • RDS instances must have deletion protection
         [POLICY EXAMPLE: Complete Sentinel policy for S3 encryption enforcement]

    22.4 Audit Logging and Compliance
         - Terraform Cloud audit trails: Who ran what and when
         - AWS CloudTrail: Track API calls made by Terraform
         - Version control: Every infrastructure change is a git commit
         [AUDIT FLOW: Git commit → TFC run → CloudTrail API call → Audit log]
