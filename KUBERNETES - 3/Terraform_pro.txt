    1.2  Infrastructure as Code (IaC) Defined
         - "Define your infrastructure in configuration files that you
           can version, reuse, and share — just like application code"
         - Declarative approach: You say WHAT you want, Terraform figures out HOW
         - Example: "I want an EKS cluster with 3 worker nodes, a PostgreSQL
           RDS instance, and a VPC with public/private subnets"
           → Terraform creates it ALL in the correct order
         [ANALOGY CARD: Terraform = Blueprint for your cloud infrastructure]

         [DECLARATIVE vs IMPERATIVE — Visual Comparison]
         ┌────────────────────────────┐  ┌────────────────────────────┐
         │  🔧 IMPERATIVE (Ansible)   │  │  📋 DECLARATIVE (Terraform)│
         │                             │  │                             │
         │  1. Create VPC              │  │  resource "aws_vpc" "main" {│
         │  2. Create subnet           │  │    cidr_block = "10.0.0/16"│
         │  3. Create EC2              │  │  }                          │
         │  4. Install Docker          │  │                             │
         │  5. Configure K8s...        │  │  resource "aws_eks" "anihpj"│
         │                             │  │  { vpc = aws_vpc.main.id } │

    2.3  The Dependency Graph
         - Terraform builds a Directed Acyclic Graph (DAG) from your config
         - It knows: "Create VPC FIRST, then subnets, then EKS, THEN deploy apps"
         - Parallel vs sequential execution — independent resources run concurrently

    │                                                                  │
    │  LEVEL 1 (Foundation — runs FIRST):                              │

    🧪 TERRAFORM APPLY — COMPLETE LIFECYCLE ANATOMY
    ┌──────────────────────────────────────────────────────────────────┐
    │  STAGE         WHAT HAPPENS                   TIME               │
    │  ───────────────────────────────────────────────────────────────│
    │  1. PARSE      Reads all .tf files in        < 1 second          │
    │     .tf FILES  working directory. Validates                      │
    │                HCL syntax.                                       │
    │                                                                  │
    │  2. LOAD       Reads terraform.tfstate      < 2 seconds          │
    │     STATE      from local disk or remote                         │
    │                backend (S3/GCS/TFC).                             │
    │                                                                  │
    │  3. REFRESH    Queries cloud APIs for        5-60 seconds        │
    │     STATE      EVERY resource in state.      (depends on # of    │
    │                Detects drift (manual          resources)         │
    │                changes outside Terraform).                       │
    │                                                                  │
    │  4. BUILD      Creates dependency graph      < 1 second          │
    │     GRAPH      (DAG). Determines parallel                        │
    │                vs sequential execution order.                    │
    │                                                                  │
    │  5. PLAN       Compares desired (.tf) vs     1-30 seconds        │
    │                actual (state). Generates      (depends on        │
    │                diff: +create/-destroy/         complexity)       │
    │                ~update/-/+replace.                               │
    │                                                                  │
    │  6. SHOW       Displays plan to user.        Interactive          │
    │     PLAN       User reviews and types "yes"                      │
    │                or "no" to confirm.                               │
    │                                                                  │
    │  7. APPLY      Executes API calls to         30 sec - 20 min     │
    │                cloud providers in correct    (EKS cluster:       │
    │                order. Creates/updates          ~15 min)           │
    │                resources.                                        │
    │                                                                  │
    │  8. UPDATE     Writes new state file          < 1 second          │
    │     STATE      with resource IDs, attributes,                    │
    │                and metadata.                                     │
    │                                                                  │
    │  ⏱️  Total: 1-25 minutes (depends on resources)                  │
    │  🔑  Stage 3 (Refresh) is why terraform plan gets slower over time│
    └──────────────────────────────────────────────────────────────────┘

    2.4  Resource Addressing — How Terraform Names Things
         - Resource addressing syntax: <TYPE>.<NAME>
         - Example: aws_vpc.main.id, aws_eks_cluster.anihpj.endpoint
         - Implicit vs explicit dependencies (references vs depends_on)

    🧪 RESOURCE ADDRESSING — COMPLETE REFERENCE
    ┌──────────────────────────────────────────────────────────────────┐
    │  ADDRESSING PATTERN              EXAMPLE              RETURNS     │
    │  ───────────────────────────────────────────────────────────────│
    │  TYPE.NAME.ATTRIBUTE             aws_vpc.main.id      vpc-abc123 │
    │  TYPE.NAME.all.ATTRIBUTE         aws_instance.web[*]  ["i-1",    │
    │                                  .public_ip           "i-2"]     │
    │  module.NAME.OUTPUT              module.vpc.vpc_id    vpc-abc123 │
    │  data.TYPE.NAME.ATTRIBUTE        data.aws_ami.ubuntu  ami-xyz    │
    │                                  .id                              │
    │  TYPE.NAME[INDEX]                aws_instance.web[0]  First one  │
    │  TYPE.NAME["KEY"]                aws_instance.web    Instance    │
    │  (for_each, map key)             ["dev"]              for "dev"   │
    │  var.NAME                         var.environment     "prod"      │
    │  local.NAME                       local.common_tags  {Project=..}│
    │  path.module                      path.module         "./modules/ │
    │                                                       vpc"       │
    │  path.root                        path.root           "."        │
    │  path.cwd                         path.cwd            (working   │
    │                                                       directory) │
    │                                                                  │
    │  🔑 DEPENDENCY TYPES:                                            │
    │  IMPLICIT: Terraform figures it out (use resource references)    │
    │    resource "aws_instance" "web" {                               │
    │      subnet_id = aws_subnet.public.id  ← CREATES dependency     │
    │    }                                                             │
    │                                                                  │
    │  EXPLICIT: You tell Terraform (use depends_on)                   │
    │    resource "null_resource" "cleanup" {                          │
    │      depends_on = [aws_instance.web]  ← MUST wait for this     │
    │    }                                                             │
    │                                                                  │
    │  ⚠️  EXAM GOTCHA: Most dependencies should be IMPLICIT.          │
    │     Use depends_on ONLY when Terraform can't infer the link.     │
    └──────────────────────────────────────────────────────────────────┘

    5.1  terraform plan — Preview Before You Leap 🎯

    5.4  Resource Lifecycle — Meta-Arguments 🎯

    🧪 COUNT vs FOR_EACH — ANIHPJ REAL CODE EXAMPLE
    ┌──────────────────────────────────────────────────────────────────┐
    │  # SCENARIO: Create subnets for dev, staging, prod environments   │
    │                                                                  │
    │  # ❌ BAD: Using count (fragile — removes index 1 = re-create)   │
    │  resource "aws_subnet" "env" {                                   │
    │    count      = 3                                                │
    │    vpc_id     = aws_vpc.main.id                                  │
    │    cidr_block = "10.0.${count.index}.0/24"                       │
    │    tags       = { Name = "subnet-${count.index}" }               │
    │  }                                                               │
    │  # Result: aws_subnet.env[0]="dev", [1]="staging", [2]="prod"    │
    │  # Problem: Removing staging shifts all indexes → chaos          │
    │                                                                  │
    │  # ✅ GOOD: Using for_each (stable — key-based, never shifts)    │
    │  variable "environments" {                                       │
    │    type = map(object({                                            │
    │      cidr_block = string                                         │
    │      az         = string                                         │
    │    }))                                                           │
    │    default = {                                                   │
    │      dev     = { cidr_block = "10.0.1.0/24", az = "us-east-1a"}│
    │      staging = { cidr_block = "10.0.2.0/24", az = "us-east-1b"}│
    │      prod    = { cidr_block = "10.0.3.0/24", az = "us-east-1c"}│
    │    }                                                             │
    │  }                                                               │
    │                                                                  │
    │  resource "aws_subnet" "env" {                                   │
    │    for_each          = var.environments                          │
    │    vpc_id            = aws_vpc.main.id                           │
    │    cidr_block        = each.value.cidr_block                     │
    │    availability_zone = each.value.az                             │
    │    tags = {                                                      │
    │      Name = "anihpj-subnet-${each.key}"                         │
    │      Env  = each.key                                             │
    │    }                                                             │
    │  }                                                               │
    │  # Result: aws_subnet.env["dev"], ["staging"], ["prod"]          │
    │  # ✅ Removing "staging" = only staging subnet destroyed         │
    │  # ✅ Adding "uat" = only uat subnet created                     │
    │                                                                  │
    │  🔑 RULE: Use for_each when resources are named/different.       │
    │     Use count when resources are identical clones.               │

    │  Dynamic count           ✅ when count ✅ N/A          count     │

    🧪 FOR EXPRESSION PATTERNS — 6 ESSENTIAL USE CASES
    ┌──────────────────────────────────────────────────────────────────┐
    │  #1: LIST TRANSFORMATION (change each element)                    │
    │  [for s in var.subnets : s.cidr_block]                           │
    │  # ["10.0.1.0/24", "10.0.2.0/24", "10.0.3.0/24"]                │
    │                                                                  │
    │  #2: LIST FILTERING (keep only matching)                         │
    │  [for s in var.subnets : s.id if s.public == true]               │
    │  # Public subnet IDs only (filter out private)                   │
    │                                                                  │
    │  #3: MAP FROM LIST (key = element property)                      │
    │  { for s in var.subnets : s.name => s.cidr_block }               │
    │  # { "dev" = "10.0.1.0/24", "staging" = "10.0.2.0/24" }         │
    │                                                                  │
    │  #4: MAP FROM MAP (transform values)                             │
    │  { for k, v in var.instance_types : k => upper(v) }              │
    │  # { "dev" = "T3.SMALL", "prod" = "T3.LARGE" }                  │
    │                                                                  │
    │  #5: FLATTEN NESTED STRUCTURES                                   │
    │  flatten([for k, v in var.envs : [for s in v.subnets : {         │
    │    env = k; cidr = s.cidr; az = s.az                              │
    │  }]])                                                            │
    │                                                                  │
    │  #6: CONDITIONAL FILTER + TRANSFORM (combined)                   │
    │  [for i in var.instances : i.name if i.enabled]                  │
    │  # Only enabled instance names                                   │
    │                                                                  │
    │  🔑 EXAM: for expressions are tested in Domain 2 (Dynamic Config)│
    │     Know the difference: [for...] returns LIST,                   │
    │     {for...} returns MAP. Dot NOTATION works on maps!            │
    └──────────────────────────────────────────────────────────────────┘

    10.1 What is State? — The Brain of Terraform 🎯

    10.2 The State Lock — Preventing Conflicts 🎯
         - Why locking: Two people running `terraform apply` simultaneously = CORRUPTION
         - How locking works: Lock acquired before any state-modifying operation
         - Backend support: S3 + DynamoDB, Terraform Cloud, Consul, GCS
         - Force-unlock: terraform force-unlock LOCK_ID (DANGER: only if stuck!)
         [LOCKING VISUALIZATION: Two users trying to apply — one gets lock, one waits]

         [STATE LOCKING — RACE CONDITION PREVENTION]
         ┌──────────────────────────────────────────────────────────────────┐
         │  TIME  ALICE (terraform apply)      BOB (terraform apply)        │
         │  ───────────────────────────────────────────────────────────────│
         │  T+0s  Acquires state lock 🔒       Attempts acquire lock...     │
         │        │                            WAITING ⏳                    │
         │  T+5s  Reads state from S3          "Lock is held by Alice"      │
         │        │                            (terraform waits patiently)  │
         │  T+30s Builds dependency graph       Still waiting...            │
         │        │                                                     │
         │  T+1m  Shows plan, Alice confirms    Waiting...                  │
         │        "yes"                                                      │
         │  T+3m  Applies changes to AWS        Waiting...                  │
         │        Creates VPC, EKS, RDS                                     │
         │  T+5m  Writes new state to S3        Waiting...                  │
         │        Releases lock 🔓              │                            │
         │                                      "Lock acquired!" 🔒         │

Chapter 16: Provisioners — Last Resort Configuration
--------------------------------------------------------------------------------
    16.1 When to Use (and NOT Use) Provisioners
         - Provisioners run scripts on local/remote machines
         - Use Case: Bootstrap EKS node with custom agent, install monitoring
         - Anti-Pattern: "Use provisioner to configure the server" → Use user_data, 
           Ansible, Packer, or cloud-init instead!
         [DECISION FLOWCHART: Should I use a provisioner?]

    16.2 local-exec — Run on Your Machine
         - Runs command on the machine running Terraform
         - Example: local-exec to run kubectl apply after EKS creation
         - Example: local-exec to register new cluster with ArgoCD
         [CODE EXAMPLE: local-exec for kubectl deployment after EKS cluster ready]

    16.3 remote-exec — Run on Remote Machine
         - Runs scripts on a newly created instance via SSH/WinRM
         - Requires connection block (host, user, private_key)
         - Example: Install Docker on a fresh EC2 instance
         [CONNECTION REFERENCE: SSH connection block with all options]

    16.4 Provisioner Failures and Handling
         - on_failure = continue — Don't fail apply if provisioner fails
         - when = destroy — Run provisioner during destroy (cleanup scripts)
         - ⚠️ Provisioners are NOT tracked in state — Terraform can't detect drift
         [DANGER CARD: 5 reasons not to use provisioners in production]

Appendix C: Common Terraform Patterns
────────────────────────────────────────────────────────────────────────────────

    C.1  Environment Management Patterns
    ────────────────────────────────────
    ┌──────────────────────────────────────────────────────────────────────┐
    │  PATTERN                STRUCTURE                BEST FOR            │
    │  ─────────────────────────────────────────────────────────────────── │
    │  DIRECTORY PER ENV      envs/                      Large teams, full   │
    │                         ├── dev/                   isolation           │
    │                         │   ├── main.tf                                │
    │                         │   └── terraform.tfvars                       │
    │                         ├── staging/                                   │
    │                         └── prod/                                      │
    │                                                                      │
    │  WORKSPACE PER ENV      Single config +            Small/medium teams  │
    │                          terraform.workspace       (⚠️ weak isolation)  │
    │                          e.g., name = "app-${terraform.workspace}"     │
    │                                                                      │
    │  TERRAFORM CLOUD        HCP Terraform              Enterprise teams    │
    │  WORKSPACES             workspaces per env         (full governance)   │
    │                          with remote state                             │
    │                                                                      │
    │  VARIABLE PER ENV       Single config +            Medium teams        │
    │                          dev.tfvars                                     │
    │                          staging.tfvars                                │
    │                          prod.tfvars                                   │
    │                          terraform apply -var-file=prod.tfvars         │
    │                                                                      │
    │  MODULE PER ENV         env module called          Reusable patterns   │
    │                          with env-specific vars    across org          │
    │                          module "prod" { source = "./modules/env" }    │
    │                                                                      │
    │  ✅ BEST PRACTICE: Directory-per-environment with shared modules      │
    │  ✅ ALWAYS use separate state files per environment                   │
    │  ❌ NEVER share state between environments                            │
    └──────────────────────────────────────────────────────────────────────┘

    C.2  Module Composition Patterns
    ────────────────────────────────
    ┌──────────────────────────────────────────────────────────────────────┐
    │  PATTERN                DESCRIPTION              DIAGRAM             │
    │  ─────────────────────────────────────────────────────────────────── │
    │  FLAT MODULE            Single module            root/                │
    │                          with all resources      └── main.tf (all)    │
    │                          (for small projects)                         │
    │                                                                      │
    │  COMPOSITION            Root calls child         root/                │
    │  (recommended)          modules, passing          ├── main.tf          │
    │                          outputs between          └── modules/         │
    │                          them                     ├── network/        │
    │                                                   ├── compute/        │
    │                                                   └── database/       │
    │                                                                      │
    │  LAYERED                Split by layer           ├── 00-accounts/     │
    │                          (networking →            ├── 01-network/      │
    │                           compute → app)          ├── 02-compute/      │
    │                                                   └── 03-app/          │
    │                                                                      │
    │  MONOREPO               All infra in one         infra/               │
    │                          repo, organized by       ├── global/          │
    │                          environment/             ├── prod/            │
    │                          component                │   ├── vpc/          │
    │                                                   │   └── eks/          │
    │                                                   └── staging/         │
    │                                                                      │
    │  MICRO-MODULES          Tiny reusable            module "naming" {    │
    │                          modules (1-2              source = "./modules/naming" │
    │                          resources each)           prefix = "prod"    │
    │                                                   }                  │
    │                                                                      │
    │  ✅ Rule of thumb: If a pattern appears 3+ times, make it a module   │
    │  ✅ Modules should have: inputs.tf, outputs.tf, main.tf, variables.tf│
    │  ✅ Always version your modules (git tags or registry)               │
    └──────────────────────────────────────────────────────────────────────┘

    C.5  Error Handling Patterns
    ────────────────────────────
    ┌──────────────────────────────────────────────────────────────────────┐
    │  ERROR TYPE            PATTERN                EXAMPLE                │
    │  ─────────────────────────────────────────────────────────────────── │
    │  Variable Validation   variable "port" {       Catch bad input early   │
    │                          validation {                                  │
    │                            condition = var.port >= 1024 &&             │
    │                                       var.port <= 65535               │
    │                            error_message = "Port must be 1024-65535."  │
    │                          }                                            │
    │                        }                                              │
    │                                                                      │
    │  Pre-conditions        lifecycle {              Validate BEFORE apply   │
    │                          precondition {                                │
    │                            condition     = data.aws_region.current... │
    │                            error_message = "Region not supported."     │
    │                          }                                            │
    │                        }                                              │
    │                                                                      │
    │  Post-conditions       lifecycle {              Validate AFTER apply    │
    │                          postcondition {                               │
    │                            condition     = self.arn != ""              │
    │                            error_message = "ARN must not be empty."    │
    │                          }                                            │
    │                        }                                              │
    │                                                                      │
    │  Check blocks          check "ami_check" {      Assert infrastructure │
    │                          assert {                state (v1.5+)         │
    │                            condition = data.aws_ami.ubuntu...         │
    │                            error_message = "AMI not found."           │
    │                          }                                            │
    │                        }                                              │
    │                                                                      │
    │  try() fallback        ami = try(                Graceful fallback     │
    │                          data.aws_ami.new.id,                          │
    │                          data.aws_ami.fallback.id                      │
    │                        )                                               │
    │                                                                      │
    │  can() check           condition = can(          Test if expression    │
    │                          regex("^ami-", var.ami)   evaluates            │
    │                        )                                               │
    │                                                                      │
    │  ✅ Validate EARLY — at variable level when possible                 │
    │  ✅ Use pre/post-conditions for cross-resource validation            │
    │  ✅ Use try() for optional data sources                              │
    │  ✅ Use can() with variable validation for format checks             │

    E.8  GitHub Actions CI/CD Pipeline for Terraform
    ────────────────────────────────────────────────
    # .github/workflows/terraform.yml
    name: "Terraform CI/CD"

    on:
      push:
        branches: [main]
        paths: ["infra/**"]
      pull_request:
        branches: [main]
        paths: ["infra/**"]

    permissions:
      id-token: write
      contents: read

    jobs:
      terraform:
        name: "Terraform"
        runs-on: ubuntu-latest
        defaults:
          run:
            working-directory: infra/prod

        steps:
          - name: Checkout
            uses: actions/checkout@v4

          - name: Configure AWS Credentials (OIDC)
            uses: aws-actions/configure-aws-credentials@v4
            with:
              role-to-assume: arn:aws:iam::ACCOUNT:role/github-actions-tf
              aws-region: us-east-1

          - name: Setup Terraform
            uses: hashicorp/setup-terraform@v3
            with:
              terraform_version: "1.8"

          - name: Terraform Format Check
            run: terraform fmt -check -recursive

          - name: Terraform Init
            run: terraform init

          - name: Terraform Validate
            run: terraform validate

          - name: Terraform Plan
            id: plan
            run: terraform plan -no-color -out=plan.tfplan

          - name: Terraform Apply
            if: github.ref == 'refs/heads/main' && github.event_name == 'push'
            run: terraform apply -auto-approve plan.tfplan

Appendix F: Troubleshooting Guide
────────────────────────────────────────────────────────────────────────────────

    F.1  Common Error Messages and Solutions
    ────────────────────────────────────────
    ┌──────────────────────────────────────────────────────────────────────┐
    │  ERROR                                    CAUSE & FIX                │
    │  ─────────────────────────────────────────────────────────────────── │
    │  "Error: Failed to query available        Provider registry is        │
    │   provider packages"                       unreachable (network,      │
    │                                            firewall, proxy)            │
    │  FIX: Check internet connection. Use                                    │
    │  terraform init -plugin-dir=DIR for air-gapped.                        │
    │                                                                      │
    │  "Error: Inconsistent dependency           Provider constraint in      │
    │   lock file"                                required_providers doesn't │
    │                                            match lock file             │
    │  FIX: terraform init -upgrade to refresh.                              │
    │  Or: rm .terraform.lock.hcl && terraform init (careful!)             │
    │                                                                      │
    │  "Error: Provider configuration            Provider block missing      │
    │   not present"                              for a resource             │
    │  FIX: Ensure provider "name" { region = "..." } block exists.         │
    │  For aliased providers: provider = aws.replica in resource.           │
    │                                                                      │
    │  "Error: Unsupported argument"             Using argument not in       │
    │                                            resource schema             │
    │  FIX: Check terraform.io registry docs for correct argument name.     │
    │  Common: tags vs tag, ingress vs ingress_rules.                       │
    │                                                                      │
    │  "Error: Reference to undeclared           Variable not declared       │
    │   resource"                                  or wrong type/name         │
    │  FIX: Check variable name spelling. Remember TYPE.NAME format.        │
    │  aws_instance.web (not aws_instance["web"] in most cases).            │
    │                                                                      │
    │  "Error: Invalid count argument"           count value must be known   │
    │                                            at plan time                │
    │  FIX: count = var.enabled ? 1 : 0 (use conditional).                  │
    │  Don't use count = data.something (unknown until apply).              │
    │                                                                      │
    │  "Error: Invalid for_each argument"        for_each map must have      │
    │                                            known keys at plan time     │
    │  FIX: Use for_each = var.map (known) not for_each = data...           │
    │  For dynamic for_each: Use -target to create dependencies first.      │
    │                                                                      │
    │  "Error: Cycle: ..."                       Circular dependency found   │
    │  FIX: Check depends_on. Use data sources to break cycles.              │
    │  Can also restructure: output → data source in another config.        │
    └──────────────────────────────────────────────────────────────────────┘

    F.2  State Lock Issues
    ──────────────────────
    ┌──────────────────────────────────────────────────────────────────────┐
    │  ERROR                                    CAUSE & FIX                │
    │  ─────────────────────────────────────────────────────────────────── │
    │  "Error acquiring the state lock"          Another terraform is        │
    │                                            running OR crashed          │
    │  FIX (safe): Wait ~5 min. State locks auto-expire on some backends.   │
    │  FIX (verify first!):                                                     │
    │    1. Confirm NO other terraform is running (check CI/CD too!)        │
    │    2. terraform force-unlock LOCK_ID                                   │
    │    3. ⚠️  ONLY if you're 100% sure — can corrupt state!               │
    │                                                                      │
    │  "DynamoDB table not found"               State lock table missing    │
    │  FIX: Create the DynamoDB table with hash_key = "LockID".             │
    │  Or: Remove dynamodb_table from backend config (lose locking!).       │
    │                                                                      │
    │  "ConditionalCheckFailedException"        Lock already held or         │
    │                                            DynamoDB item exists        │
    │  FIX: Same as above — check for running terraform processes.          │
    │  Check DynamoDB console for stale lock entries.                        │
    │                                                                      │
    │  PREVENTION:                                                            │
    │  ✅ Always use DynamoDB with S3 backend for locking                   │
    │  ✅ Set CI/CD timeouts shorter than lock TTL                          │
    │  ✅ Monitor lock entries in CloudWatch/DynamboDB metrics              │
    │  ✅ Never kill terraform with SIGKILL (-9) — use SIGTERM              │
    └──────────────────────────────────────────────────────────────────────┘

    F.3  Provider Authentication Errors
    ────────────────────────────────────
    ┌──────────────────────────────────────────────────────────────────────┐
    │  ERROR                                    CAUSE & FIX                │
    │  ─────────────────────────────────────────────────────────────────── │
    │  AWS: "No valid credential sources       AWS credentials not found    │
    │   found"                                   in any source               │
    │  FIX (order of precedence):                                              │
    │    1. Check AWS_ACCESS_KEY_ID + AWS_SECRET_ACCESS_KEY env vars       │
    │    2. Check ~/.aws/credentials + ~/.aws/config                       │
    │    3. Check IAM instance profile (EC2) or IRSA (EKS pod)             │
    │    4. Check provider "aws" { profile = "..." }                        │
    │                                                                      │
    │  AWS: "AccessDenied" or "403"              IAM permissions missing    │
    │  FIX:                                                                   │
    │    1. Check IAM policy attached to role/user                          │
    │    2. Use AWS IAM Policy Simulator to test                            │
    │    3. Enable TF_LOG=TRACE to see exact API call                       │
    │    4. Check SCP (Service Control Policies) at org level               │
    │                                                                      │
    │  AWS: "The security token included        Temporary credentials       │
    │   in the request is expired"               expired                     │
    │  FIX: Refresh credentials. If using assume_role, check duration.      │
    │  For CI/CD: Use OIDC (preferred) or long-lived IAM user keys.        │
    │                                                                      │
    │  KUBERNETES: "Unauthorized"               Kubeconfig/ token invalid   │
    │  FIX:                                                                   │
    │    1. aws eks update-kubeconfig --region us-east-1 --name CLUSTER    │
    │    2. Check that data.aws_eks_cluster_auth is in providers.tf         │
    │    3. Verify IAM role has eks:DescribeCluster permission             │
    │                                                                      │
    │  DEBUGGING AUTH ISSUES:                                                │
    │  ✅ export TF_LOG=TRACE → search for "status code:" in output        │
    │  ✅ export AWS_DEBUG=true (for AWS SDK debugging)                     │
    │  ✅ terraform console → test data sources that need auth             │
    └──────────────────────────────────────────────────────────────────────┘

    F.4  Dependency and Graph Errors
    ────────────────────────────────
    ┌──────────────────────────────────────────────────────────────────────┐
    │  ERROR                                    CAUSE & FIX                │
    │  ─────────────────────────────────────────────────────────────────── │
    │  "Error: Cycle: resource_a →            Circular dependency detected  │
    │   resource_b → resource_a"                                           │
    │  FIX:                                                                   │
    │    1. terraform graph | grep "→" to visualize cycle                  │
    │    2. Break cycle with depends_on or restructure                      │
    │    3. Use data source for one side of the dependency                  │
    │                                                                      │
    │  "resource depends on resource           Non-existent dependency       │
    │   that doesn't exist"                                                │
    │  FIX: Check depends_on array for typos. Use TYPE.NAME format.        │
    │                                                                      │
    │  "Module x depends on module y"          Cross-module dependency      │
    │  FIX: Use module outputs as inputs:                                    │
    │  module "x" { vpc_id = module.y.vpc_id }                             │
    │  Or: depends_on = [module.y] in module "x"                            │
    │                                                                      │
    │  GRAPH DEBUGGING:                                                      │
    │  terraform graph | dot -Tpng > graph.png  # Full dependency graph    │
    │  terraform graph -type=plan | dot -Tpng > plan-graph.png  # Plan     │
    │                                                                      │
    │  Look for:                                                             │
    │  • Nodes with many incoming edges (potential bottlenecks)             │
    │  • Isolated subgraphs (missing dependencies)                          │
    │  • Circular arrows (cycles — MUST fix)                                │
    └──────────────────────────────────────────────────────────────────────┘

    F.5  Plan/Apply Failures
    ────────────────────────
    ┌──────────────────────────────────────────────────────────────────────┐
    │  ERROR                                    CAUSE & FIX                │
    │  ─────────────────────────────────────────────────────────────────── │
    │  "Error: error reading S3 bucket"         Resource was deleted         │
    │  "Error: Resource not found"               outside of Terraform        │
    │  FIX:                                                                   │
    │    1. terraform state rm TYPE.NAME (remove from state)                │
    │    2. terraform import TYPE.NAME ID (re-import if exists)             │
    │    3. Or: Re-create with terraform apply -replace=TYPE.NAME          │
    │                                                                      │
    │  "Error: Provider produced              Provider returned unexpected   │
    │   inconsistent result"                    result (API weirdness)       │
    │  FIX:                                                                   │
    │    1. Re-run. Many "inconsistent" errors are transient API issues.    │
    │    2. Check provider version (update if old).                          │
    │    3. terraform apply -refresh-only to sync state.                    │
    │                                                                      │
    │  "Error: error waiting for              Resource creation timeout     │
    │   EKS cluster to create"                                              │
    │  FIX:                                                                   │
    │    1. Check AWS console — resource might have created but TF timed out│
    │    2. terraform apply again (TF should detect existing resource)      │
    │    3. Extend timeout: timeouts { create = "60m" } in resource block   │
    │                                                                      │
    │  "Error: error deleting ... as          Resource has dependencies     │
    │   it has dependent objects"              preventing deletion           │
    │  FIX: Delete dependencies first, or use force_destroy (S3),           │
    │  or skip_final_snapshot (RDS). Check AWS console for dependents.      │
    │                                                                      │
    │  "Plan: X to add, Y to change,          Resources being replaced      │
    │   Z to destroy" for no reason             due to force-new changes     │
    │  FIX:                                                                   │
    │    1. Look for "(forces new resource)" in plan output                 │
    │    2. Common triggers: changing name, immutable attributes             │
    │    3. Use lifecycle { create_before_destroy = true } for zero-downtime│
    │    4. Use lifecycle { ignore_changes = [ami, ...] } if appropriate   │
    │                                                                      │
    │  GENERAL DEBUGGING WORKFLOW:                                           │
    │  ✅ Step 1: Read the FULL error message (not just the summary)        │
    │  ✅ Step 2: TF_LOG=TRACE terraform plan 2>&1 | grep -A5 "ERROR"     │
    │  ✅ Step 3: Check provider docs for correct argument names/types      │
    │  ✅ Step 4: terraform state show TYPE.NAME (check current state)      │
    │  ✅ Step 5: terraform console → test expressions interactively        │
    │  ✅ Step 6: Search terraform.io/docs for error message                 │
    └──────────────────────────────────────────────────────────────────────┘
