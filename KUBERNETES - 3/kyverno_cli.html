kyverno apply

APPLY Policy Validation CI/CD

Apply policies to resources and report validation results

The kyverno apply command tests Kyverno policies against Kubernetes resources locally — without installing Kyverno in the cluster. It's the primary way to validate policies in CI/CD pipelines, pre-commit hooks, and local development workflows.

For the anihpj Django project, this command is essential for:

  • Validating policies against jobpost deployment YAML before applying to production clusters
  • CI/CD pipeline gates that block non-compliant resources from being deployed
  • Dry-run policy testing with detailed pass/fail reports for each rule
  • Testing policies against multiple resource files simultaneously for cross-resource validation
  • Generating PolicyReport CRDs for integration with policy monitoring dashboards

Syntax

# Apply a policy to resource files
kyverno apply POLICY.yaml -r RESOURCE.yaml

# Apply with multiple resources
kyverno apply POLICY.yaml -r deployment.yaml -r service.yaml

# Apply to an entire directory of resources
kyverno apply POLICY.yaml -r ./k8s/anihpj/

# Generate PolicyReport output
kyverno apply POLICY.yaml -r RESOURCE.yaml --policy-report

# Apply with values file for policy variables
kyverno apply POLICY.yaml -r RESOURCE.yaml -f values.yaml

# Apply using cluster resources (requires kubeconfig)
kyverno apply POLICY.yaml -c

Parameters

ParameterTypeDescription
-r, --resourcestringPath to resource YAML file or directory (can be specified multiple times)
-c, --clusterboolUse cluster resources instead of local files (requires valid kubeconfig)
--policy-reportboolGenerate a PolicyReport custom resource as output
-f, --values-filestringPath to values file for policy variable substitution
--audit-warnboolTreat audit-level failures as warnings (non-zero exit code)
-o, --outputstringOutput format: text, json, yaml default: text
--namespace -nstringNamespace to apply policies against for cluster-scoped evaluation
--warn-exit-codeintExit code when only warnings are found default: 0

Return Value

Exit CodeDescription
0All resources passed all policy rules (pass)
1One or more policy violations found (fail)

kyverno test

TEST Policy CI/CD TDD

Execute Kyverno policy test suites from local files or remote git repositories

The kyverno test command provides a facility to test resources against policies by comparing expected results, declared in a test manifest file (kyverno-test.yaml), to actual results reported by Kyverno. It supports both local filesystems and remote git repositories.

For the anihpj Django project, this command is essential for:

  • Test-Driven Development (TDD) for Kyverno policies — write tests before policies
  • Regression testing when modifying existing policies to prevent unintended breakage
  • CI/CD integration with JUnit/Markdown output formats for automated policy validation gates
  • Selective test execution with --test-case-selector for rapid iteration during policy development
  • Git-based policy catalog testing directly from the Kyverno policies repository

Syntax

# Test from a local directory
kyverno test ./tests/anihpj/

# Test from a remote git repository
kyverno test https://github.com/kyverno/policies/pod-security --git-branch main

# Test with specific test case selector
kyverno test . --test-case-selector "policy=disallow-latest-tag, rule=require-image-tag, resource=test-require-image-tag-pass"

# Test with JUnit output for CI/CD
kyverno test ./tests/ -o junit

# Test with detailed results
kyverno test ./tests/ --detailed-results

# Fail if no tests are found (strict mode)
kyverno test ./tests/ --require-tests

Parameters

ParameterTypeDescription
pathstringPath to local folder or remote git repository containing test cases
-f, --file-namestringTest manifest filename default: kyverno-test.yaml
-b, --git-branchstringBranch of the remote git repository to test
-t, --test-case-selectorstringFilter test cases to run by policy, rule, and resource default: policy=*,rule=*,resource=*
-o, --output-formatstringOutput format: text, json, yaml, markdown, junit default: text
--detailed-resultsboolDisplay detailed pass/fail results for each test case
--fail-onlyboolDisplay only failing test cases in output
--require-testsboolReturn an error (exit code 1) if no test cases are found
--registryboolAccess image registries using local Docker credentials to populate external data
--remove-colorboolStrip ANSI color codes from output (useful for CI/CD logs)

Return Value

Exit CodeDescription
0All test cases passed — no policy violations detected
1One or more test cases failed — policy violations found

kyverno version

VERSION Utility Diagnostics

Display Kyverno CLI version, build date, Git commit, and Go runtime information

The kyverno version command prints detailed version information about the Kyverno CLI binary, including the semantic version, build timestamp, Git commit hash, and Go runtime version. This is critical for ensuring compatibility between the CLI and cluster-installed Kyverno.

For the anihpj Django project, this command is used for:

  • Verifying the installed CLI version matches the Kyverno version running in the production cluster
  • CI/CD pipeline version pinning — ensure consistent Kyverno CLI version across all pipeline runners
  • Troubleshooting policy behavior discrepancies between local kyverno apply and cluster enforcement
  • Pre-upgrade compatibility checks before rolling out new Kyverno versions

Syntax

# Display full version information
kyverno version

# Display version with help
kyverno version -h

Parameters

ParameterTypeDescription
-h, --helpboolDisplay help for the version command

Return Value

FieldDescription
VersionSemantic version of the Kyverno CLI (e.g., v1.12.0)
TimeBuild timestamp of the binary
Git CommitGit commit hash from which the binary was built
Go VersionGo runtime version used to compile the binary

📁 Context: anihpj Version Compatibility

Version Pinning: The anihpj project standardizes on Kyverno v1.12.x. All CI/CD runners and developer workstations must use the same CLI version to ensure consistent policy evaluation results between local testing and cluster enforcement.
# .github/workflows/kyverno-version-check.yaml
name: Kyverno Version Check
on:
  schedule:
    - cron: '0 6 * * 1'  # Every Monday at 06:00
jobs:
  verify-versions:
    runs-on: ubuntu-latest
    steps:
    - name: Check Kyverno CLI Version
      run: |
        EXPECTED_VERSION="v1.12.0"
        INSTALLED_VERSION=$(kyverno version | head -1 | awk '{print $3}')
        if [ "$INSTALLED_VERSION" != "$EXPECTED_VERSION" ]; then
          echo "::warning::Kyverno CLI version mismatch: expected $EXPECTED_VERSION, got $INSTALLED_VERSION"
        else
          echo "::notice::Kyverno CLI version $INSTALLED_VERSION matches expected"
        fi

---

CREATE Values Variables

Create a values file with global, namespace, rule, and resource scoped variables for policy parameterization

The kyverno create values command generates a Values resource that provides scoped variables for Kyverno policies. Variables can be defined at global, namespace-selector, rule, and resource levels — enabling environment-specific policy behavior without duplicating policy definitions.

For the anihpj Django project, this command is essential for:

  • Creating environment-specific values (production vs staging CPU/memory minimums)
  • Defining namespace-level variables for multi-tenant policy configurations
  • Setting rule-level overrides for specific policy rules without modifying the policy itself
  • Managing resource-specific variables (e.g., different limits for Deployments vs StatefulSets)

Syntax

# Create values with global and namespace scope
kyverno create values \
  -g request.mode=dev \
  -n prod,env=prod

# Create values with rule and resource scopes
kyverno create values \
  -g cluster=anihpj-prod \
  -n anihpj,env=production \
  --rule require-labels,check-team-label,required-label=team \
  --resource require-labels,Deployment,env=production

# Create and save to file
kyverno create values \
  -g cluster=anihpj-staging \
  -n anihpj,env=staging \
  --rule require-resource-limits,check-resource-limits,min-cpu=100m \
  -o values/staging.yaml

Scan JSON-compatible payloads against Kyverno-json policies and report violations

The kyverno json scan command evaluates JSON or YAML payloads against Kyverno-json validating policies. It supports label-based policy selection, JMESPath pre-processing of payloads, and text/JSON output formats. This is an experimental feature gated behind KYVERNO_EXPERIMENTAL=true.

For the anihpj Django project, this command is essential for:

  • Validating jobpost API request/response payloads against data quality standards
  • Pre-processing complex nested payloads with JMESPath before policy evaluation
  • Selectively applying policies based on labels (environment, severity, category)
  • Generating machine-readable JSON output for CI/CD pipeline integration

Syntax

# Basic scan of a payload against a policy
KYVERNO_EXPERIMENTAL=true kyverno json scan \
  --payload payload.json \
  --policy policy.yaml

# Scan with label selectors
KYVERNO_EXPERIMENTAL=true kyverno json scan \
  --payload payload.json \
  --policy policies/ \
  --labels "env=production,severity=high"

# Scan with JMESPath pre-processing
KYVERNO_EXPERIMENTAL=true kyverno json scan \
  --payload api-response.json \
  --pre-process "data.result" \
  --policy policies/

# JSON output format
KYVERNO_EXPERIMENTAL=true kyverno json scan \
  --payload payload.json \
  --policy policy.yaml \
  --output json

Parameters

ParameterTypeDescription
--payloadstringPath to JSON or YAML payload file to scan
--policystringArrayPath to Kyverno-json policy file(s) or directory (can be specified multiple times)
--labelsstringArrayLabel selectors to filter which policies are applied (e.g., env=production)
--pre-processstringArrayJMESPath expression(s) to pre-process the payload before scanning
--outputstringOutput format: text or json default: text
-h, --helpboolDisplay help for the scan command

Return Value

OutputDescription
Text summaryHuman-readable pass/fail report with rule-level details
JSON reportMachine-readable scan report with structured violation data
Exit 0All policy rules passed
Exit 1One or more policy violations found

kyverno completion

COMPLETION Shell Productivity

Generate shell autocompletion scripts for bash, zsh, fish, and PowerShell

The kyverno completion command generates shell-specific autocompletion scripts that enable Tab-based command, subcommand, flag, and argument completion for the Kyverno CLI. Supported shells: bash, zsh, fish, and PowerShell.

For the anihpj Django project, this command is essential for:

  • Accelerating Kyverno CLI workflows by reducing typing and preventing typos in command names
  • Onboarding new developers — autocompletion helps discover available commands and flags
  • CI/CD pipeline scripting — ensures consistent command syntax even in automated environments
  • Persistent shell setup by sourcing completion scripts in .bashrc, .zshrc, or $PROFILE

Syntax

# Bash
kyverno completion bash > /etc/bash_completion.d/kyverno
source <(kyverno completion bash)

# Zsh
kyverno completion zsh > "${fpath[1]}/_kyverno"
source <(kyverno completion zsh)

# Fish
kyverno completion fish > ~/.config/fish/completions/kyverno.fish

# PowerShell
kyverno completion powershell | Out-String | Invoke-Expression
kyverno completion powershell >> $PROFILE

Parameters

ParameterTypeDescription
[shell]stringTarget shell: bash, zsh, fish, or powershell (required positional)
-h, --helpboolDisplay help for the completion command

Return Value

OutputDescription
Shell script (stdout)Generated completion script for the specified shell — pipe to file or source directly

# failurePolicy: Ignore → If ConfigMap is missing, policy SKIPS evaluation
# Use Ignore for policies with external dependencies that may be temporarily unavailable
# Use Fail (default) for self-contained policies where errors indicate real problems

Command:

cat <<EOF | kubectl apply -f -
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: image-signature-check
spec:
  failurePolicy: Ignore            # Graceful if cosign not configured
  validationFailureAction: Enforce
  rules:
  - name: verify-image-signature
    match:
      any:
      - resources:
          kinds:
          - Pod
    context:
    - name: cosignConfig
      configMap:
        name: cosign-config
        namespace: kyverno
    verifyImages:
    - imageReferences:
      - "*"
      attestors:
      - count: 1
        entries:
        - keys:
            publicKeys: "{{ cosignConfig.data.publicKey }}"
EOF

Output:

clusterpolicy.kyverno.io/image-signature-check created # With failurePolicy: Fail (default): # If cosign-config ConfigMap is missing → ALL pod creations BLOCKED # Error: "failed to resolve cosignConfig: configmap not found" # This is a hard failure — cluster unusable until ConfigMap exists # With failurePolicy: Ignore: # If cosign-config ConfigMap is missing → policy EVALUATION SKIPPED # Pods are created without signature verification # Warning logged: "failed to resolve context, skipping rule" # Cluster remains operational while ConfigMap is being deployed # anihpj guideline: Use Ignore for policies with external dependencies # that are deployed separately (ConfigMaps, Secrets, external services)
Example 5: validationFailureActionOverrides — Namespace-Level Enforcement

Scenario: Use a single ClusterPolicy with Enforce in production namespaces but Audit in development namespaces — avoiding duplicated policies.

📄 Context — Per-Namespace Overrides:

# ClusterPolicy only — not available in namespaced Policy
# validationFailureAction: Enforce (default for all namespaces)
# Override: Audit in anihpj-dev, anihpj-staging
# Result: One policy, different behavior per namespace

Command:

cat <<EOF | kubectl apply -f -
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: require-labels
spec:
  validationFailureAction: Enforce        # Default: block in all namespaces
  validationFailureActionOverrides:       # ClusterPolicy only
  - action: Audit                         # Override: audit only in these namespaces
    namespaces:
    - anihpj-dev
    - anihpj-staging
  - action: Enforce                       # Explicit enforce in production
    namespaces:
    - anihpj
    - jobpost
  rules:
  - name: check-team-label
    match:
      any:
      - resources:
          kinds:
          - Deployment
    validate:
      message: "Deployment must have team label"
      pattern:
        metadata:
          labels:
            team: "?*"
EOF

Output:

clusterpolicy.kyverno.io/require-labels created # Enforcement behavior per namespace: # anihpj-dev: Audit (reports violation, allows deploy) # anihpj-staging: Audit (reports violation, allows deploy) # anihpj: Enforce (blocks non-compliant deployments) # jobpost: Enforce (blocks non-compliant deployments) # kube-system: Enforce (default — not in override list) # Verify overrides: # kubectl get clusterpolicy require-labels \ # -o jsonpath='{.spec.validationFailureActionOverrides}' # [{"action":"Audit","namespaces":["anihpj-dev","anihpj-staging"]}, # {"action":"Enforce","namespaces":["anihpj","jobpost"]}] # Advantage: One policy for all environments, no duplication
