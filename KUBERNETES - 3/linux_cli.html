📂 File System Navigation

Commands for browsing directories, locating files, and understanding the filesystem layout. These are the most-used commands in daily Linux work for the anihpj environment.

ls

LIST Navigation Core LFCS Domain 1

List directory contents — the most frequently used command in any Linux session

The ls command lists files and directories, displaying names, permissions, ownership, sizes, and timestamps. It's the first command every Linux user learns and the one used most often — dozens of times daily in any sysadmin workflow.

For the anihpj/jobpost project, ls is essential for:

  • Checking what's deployed in /lpj/ before running scripts
  • Verifying log files exist in /lpj/jobpost/
  • Inspecting Kubernetes manifests in /lpj/k8s/
  • Checking permissions on K8s secrets and configmaps in /lpj/k8s/base/
  • Listing Dockerfiles before building images

Syntax

ls [OPTIONS]... [FILE]...

# Common patterns:
ls                    # List current directory
ls -la                # Long format with hidden files
ls -ltr               # Long format, sorted by time, reversed (newest last)
ls -lh                # Human-readable sizes
ls -d */              # List only directories

Parameters

FlagDescription
-a, --allShow all entries including hidden files (starting with .)
-lLong listing format — permissions, owner, size, date, filename
-h, --human-readablePrint sizes in human readable format (1K, 234M, 2G)
-tSort by modification time, newest first
-r, --reverseReverse order while sorting
-R, --recursiveList subdirectories recursively
-SSort by file size, largest first
-i, --inodePrint the index number (inode) of each file
-d, --directoryList directories themselves, not their contents
-1List one file per line
--color[=WHEN]Colorize output: always, never, auto
-F, --classifyAppend indicator: /=dir, *=exec, @=symlink, |=fifo
-ZPrint SELinux security context of each file

Return Value

Exit CodeDescription
0Success — directory contents listed
2Error — file or directory not found, or permission denied

find

Search for files and directories in a directory hierarchy — the most powerful filesystem search tool

find recursively searches a directory tree for files matching criteria like name, type, size, modification time, permissions, ownership, and more. It's an SRE's swiss army knife for file discovery, cleanup, and batch operations.

For the anihpj/jobpost project, find is used for:

  • Finding all .py files modified today: find /lpj/apps -name "*.py" -mtime -1
  • Cleaning old log files: find /lpj/ops/logs -name "*.log" -mtime +30 -delete
  • Locating files with insecure permissions: find /lpj -perm /o+w -type f
  • Finding large files consuming disk: find /lpj -type f -size +100M
  • Batch-executing commands on matched files with -exec

Syntax

find [PATH...] [EXPRESSION]

# Common patterns:
find . -name "*.py"                     # Find by name (case sensitive)
find . -iname "*.log"                   # Find by name (case insensitive)
find . -type f                          # Files only
find . -type d                          # Directories only
find . -type f -size +100M              # Files larger than 100MB
find . -type f -mtime -7               # Modified in last 7 days
find . -type f -mtime +30 -delete       # Older than 30 days → delete
find . -user alice -type f              # Files owned by alice
find . -perm 0777                       # Files with 777 permissions
find . -empty                           # Empty files/directories
find . -name "*.pyc" -exec rm {} \;     # Delete all .pyc files
find . -maxdepth 2 -name "Dockerfile"   # Limit search depth

Parameters

ExpressionDescription
-name PATTERNFile name (case sensitive, supports *, ?, [])
-iname PATTERNFile name (case insensitive)
-type fRegular files only
-type dDirectories only
-type lSymbolic links only
-size +N[c/k/M/G]Size: +100M (over 100MB), -10k (under 10KB), 0 (empty)
-mtime NModified exactly N*24h ago: -7 (last 7d), +30 (older than 30d)
-atime NAccessed N*24h ago
-ctime NMetadata changed N*24h ago
-mmin NModified N minutes ago
-user NAMEOwned by user NAME
-group NAMEOwned by group NAME
-perm MODEPermission bits: 0777 (exact), /o+w (any world-writable)
-emptyFile or directory is empty
-newer FILEModified more recently than FILE
-maxdepth NDescend at most N levels (must come before other tests)
-mindepth NDescend at least N levels
-exec CMD {} \;Execute CMD on each matched file ({} = placeholder)
-exec CMD {} +Execute CMD with all matches at once (more efficient)
-deleteDelete matched files (use with extreme caution!)
-print0Null-delimited output (for xargs -0)
-not or !Negate the following expression
-o or -orOR between expressions

Return Value

Exit CodeDescription
0Success — all paths traversed (may have zero matches)
1Error — some paths could not be traversed (permissions, etc.)

Scenario: Alice syncs updated Python files to a shared code directory, only moving files that are newer than what's already there.

ln

LINK File Operations Symlink LFCS Domain 1

Create hard and symbolic links — connect files and directories without duplication

ln creates links between files. Symbolic links (-s) are pointers to another path — like shortcuts. Hard links share the same inode — they are the same file under different names. Symlinks are more common and work across filesystems.

For anihpj/jobpost, ln is used for:

  • Creating shortcuts to frequently accessed directories: ln -s /lpj/k8s/base ~/k8s
  • Linking shared config files between environments
  • Creating version-independent paths: ln -s deploy-v2.yaml deploy.yaml

Syntax

ln [OPTIONS] TARGET [LINK_NAME]

# Common patterns:
ln -s /lpj/k8s/base ~/k8s-base        # Symbolic link (shortcut)
ln file.txt file-hardlink.txt          # Hard link (same inode)
ln -sf /lpj/k8s/base/deploy-v2.yaml /lpj/deploy.yaml  # Force symlink update

Parameters

FlagDescription
-s, --symbolicCreate a symbolic link instead of a hard link
-f, --forceRemove existing destination files before linking
-r, --relativeCreate symbolic links relative to the link location (portable)
-n, --no-dereferenceTreat symlink destination as a normal file (with -f)
-v, --verbosePrint the name of each linked file

Examples

Example 1: Create a Convenience Symlink

Scenario: Carol creates a shortcut from her home directory to the K8s base manifests.

Command:

ln -sv /lpj/k8s/base ~/k8s-base && ls -l ~/k8s-base

Output:

'/home/carol/k8s-base' -> '/lpj/k8s/base' lrwxrwxrwx 1 carol developers 15 Jun 3 16:45 /home/carol/k8s-base -> /lpj/k8s/base

📝 What happened: A symlink was created — the l at the start of permissions confirms it's a link. The arrow -> shows the target. Carol can now cd ~/k8s-base instead of typing the full path. Symlinks always show rwxrwxrwx (777) permissions — the actual permissions are on the target.

Example 2: Version-Independent Deploy Link

Scenario: Alice creates a deploy.yaml symlink that always points to the latest deployment version.

Command:

cd /lpj/k8s/base && ln -sf web-deployment-v2.yaml web-deployment.yaml && ls -l web-deployment*

lrwxrwxrwx 1 alice developers 22 Jun 3 16:50 web-deployment.yaml -> web-deployment-v2.yaml -rw-r--r-- 1 alice developers 1892 Jun 3 16:30 web-deployment-v2.yaml

📝 What happened: ln -sf created a symlink that points to the versioned file. When v3 is ready, just run ln -sf web-deployment-v3.yaml web-deployment.yaml — scripts referencing web-deployment.yaml automatically use the latest version without changes.

Example 3: Create a Relative Symlink for Portability

Scenario: Carol creates a relative symlink so the project works regardless of where it's cloned.

Command:

cd /lpj && ln -sr k8s/base/secrets.yaml ops/secrets-link.yaml && ls -l /lpj/ops/secrets-link.yaml

Output:

lrwxrwxrwx 1 carol developers 25 Jun 3 17:00 /lpj/ops/secrets-link.yaml -> ../k8s/base/secrets.yaml

📝 What happened: -r created a RELATIVE symlink (../k8s/base/...) instead of absolute (/lpj/k8s/base/...). Relative symlinks survive when the project is moved or cloned to a different path — essential for portable project structures.

Example 4: Force-Update a Symlink

Scenario: Alice updates an existing symlink to point to a new settings file for staging.

Command:

ln -sf /lpj/anihpj/settings_staging.py /lpj/anihpj/settings_active.py && ls -l /lpj/anihpj/settings_active.py

Output:

lrwxrwxrwx 1 alice developers 32 Jun 3 17:05 /lpj/anihpj/settings_active.py -> /lpj/anihpj/settings_staging.py

📝 What happened: -sf removed the old symlink and created a new one in one atomic operation. The active settings now point to the staging variant. This pattern is used in deployment scripts to atomically switch configurations without editing files.

Example 5: Hard Link for Zero-Space Backup

Scenario: Dave creates a hard link — same data, zero extra disk space consumed.

Command:

ln /lpj/ops/backups/db_dump.sql /lpj/ops/backups/db_latest.sql && stat -c "%i %h %n" /lpj/ops/backups/db_*.sql

Output:

524291 2 /lpj/ops/backups/db_dump.sql 524291 2 /lpj/ops/backups/db_latest.sql

What happened: Both files share inode 524291 with link count 2. Zero additional disk space. Deleting one file does not free the data until ALL hard links are removed. Hard links cannot span filesystems.

💡 LFCS Exam Tip: Know the difference: hard links share the same inode (cannot span filesystems, cannot link directories), symlinks are path pointers (can span filesystems, can link directories). ls -l shows symlinks with l and ->. readlink displays a symlink's target. Use -r for relative symlinks (portable), -sf for atomic symlink updates. A broken symlink (dangling) shows in red in ls --color.

📝 What happened: Both commands resolved the symlink to the same target. realpath always returns an absolute path; readlink returns whatever the symlink points to (could be relative). If the symlink is broken, realpath errors while readlink still shows the target.

shred

SECURE File Operations Security LFCS Domain 1

Overwrite a file repeatedly to hide its contents — secure deletion beyond rm

shred overwrites a file's contents multiple times with random data before optionally deleting it. rm only removes the directory entry — the data remains on disk until overwritten. shred makes forensic recovery infeasible.

For anihpj/jobpost, shred is used by Eve to securely erase sensitive files like secrets backups and database dumps before disposal.

Syntax

shred [OPTIONS] FILE...

# Common patterns:
shred -u secrets.txt            # Overwrite and remove
shred -z -u sensitive.yaml      # Overwrite, zero final pass, remove
shred -n 5 -u file.txt          # 5 overwrite passes, then remove

Parameters

FlagDescription
-uTruncate and remove the file after overwriting
-z, --zeroAdd a final overwrite with zeros to hide shredding
-n N, --iterations=NOverwrite N times (default is 3)
-f, --forceChange permissions to allow writing if necessary

Examples

Example 1: Securely Delete a Secrets Backup

Scenario: Eve securely erases a secrets backup file — rm is not enough for sensitive data.

Command:

shred -z -u -v /lpj/ops/backups/secrets.yaml.bak

Output:

shred: /lpj/ops/backups/secrets.yaml.bak: pass 1/4 (random)... shred: /lpj/ops/backups/secrets.yaml.bak: pass 2/4 (random)... shred: /lpj/ops/backups/secrets.yaml.bak: pass 3/4 (random)... shred: /lpj/ops/backups/secrets.yaml.bak: pass 4/4 (000000)... shred: /lpj/ops/backups/secrets.yaml.bak: removing shred: /lpj/ops/backups/secrets.yaml.bak: renamed to 00000000 shred: /lpj/ops/backups/secrets.yaml.bak: removed

📝 What happened: Four passes: three with random data, one final pass with zeros (-z), then the file was removed (-u). The -v flag confirmed each pass. After this, forensic recovery of the original content is effectively impossible. Compare with rm which only unlinks the filename.

Example 2: Overwrite Without Deleting

Scenario: Carol wipes a log file's contents but keeps the file for the running app.

Command:

shred -z -n 1 -v /lpj/ops/logs/access.log && wc -c /lpj/ops/logs/access.log

Output:

shred: /lpj/ops/logs/access.log: pass 1/2 (random)... shred: /lpj/ops/logs/access.log: pass 2/2 (000000)... 89432 /lpj/ops/logs/access.log

What happened: The file was overwritten but NOT deleted (no -u flag). It still exists with the same byte count but original content is gone. Useful when the app needs the file to exist.

Example 3: Shred Old Backups via find

Scenario: Eve securely erases backup files older than 30 days before disk disposal.

Command:

find /lpj/ops/backups -type f -mtime +30 -exec shred -z -u -v {} \;

Output:

shred: /lpj/ops/backups/daily/app.log.20260501: pass 1/4 (random)... shred: /lpj/ops/backups/daily/app.log.20260501: removed

What happened: find -exec shred combined targeted file selection with secure deletion. Enterprise-grade data disposal — far beyond what rm provides.

Example 4: Shred with Custom Pass Count

Scenario: Eve uses 7 overwrite passes for highly sensitive encryption key material.

Command:

shred -n 7 -z -u -v /lpj/ops/backups/encryption_key.bak

Output:

shred: /lpj/ops/backups/encryption_key.bak: pass 1/8 (random)... shred: /lpj/ops/backups/encryption_key.bak: pass 2/8 (random)... shred: /lpj/ops/backups/encryption_key.bak: pass 7/8 (random)... shred: /lpj/ops/backups/encryption_key.bak: pass 8/8 (000000)... shred: /lpj/ops/backups/encryption_key.bak: removed

What happened: -n 7 performed 7 random passes (instead of default 3), plus 1 zero pass from -z = 8 total. More passes = more secure but slower. 3 passes is sufficient for most use cases; 7+ is for cryptographic material.

Example 5: Shred Only Specific Bytes

Scenario: Carol only needs to destroy the header of a file while keeping the rest intact.

Command:

dd if=/dev/urandom of=/lpj/ops/backups/partial.bin bs=64 count=1 conv=notrunc 2>/dev/null && echo "First 64 bytes overwritten with random data"

Output:

What happened: dd overwrote only the first 64 bytes with random data from /dev/urandom. conv=notrunc prevented truncation. shred always overwrites the entire file — use dd when you need partial overwrites.

💡 LFCS Exam Tip: shred overwrites file content — but does NOT work on SSDs with wear-leveling or on journaling filesystems with data journaling. For SSDs, use full-disk encryption from the start. shred -u overwrites then deletes; shred -z adds a zero pass to hide that shredding occurred.

🔐 File Permissions

Commands for managing file and directory permissions, ownership, and access control. Essential for security hardening, multi-user environments, and ensuring the anihpj/jobpost deployment follows the principle of least privilege.

chmod

PERMISSIONS File Permissions Security LFCS Domain 3

Change file mode bits — set read, write, and execute permissions for owner, group, and others

chmod is the fundamental permission command. It sets who can read (r), write (w), and execute (x) a file or directory. Permissions can be specified in octal (e.g., 644) or symbolic notation (e.g., u+x).

For anihpj/jobpost, chmod is used for:

  • Restricting K8s secrets: chmod 600 /lpj/k8s/base/secrets.yaml
  • Making scripts executable: chmod +x /lpj/scripts/deploy.sh
  • Securing sensitive directories: chmod 700 /lpj/ops/audit/
  • Setting deployment files read-only: chmod 444 /lpj/k8s/base/configmap.yaml

Syntax

chmod [OPTIONS] MODE FILE...

# Octal (numeric) notation:
chmod 644 file.txt          # rw-r--r--  (owner rw, group r, others r)
chmod 755 script.sh         # rwxr-xr-x  (owner rwx, group rx, others rx)
chmod 600 secrets.yaml      # rw-------  (owner rw only)

# Symbolic notation:
chmod u+x deploy.sh         # Add execute for user (owner)
chmod g-w file.txt          # Remove write for group
chmod o= file.txt           # Remove all permissions for others
chmod a+r *.yaml            # Add read for all (user+group+others)

Parameters

-R, --recursiveChange files and directories recursively
-v, --verboseOutput a diagnostic for every file processed
-c, --changesLike verbose but report only when a change is made
uUser (owner) — symbolic target
gGroup — symbolic target
oOthers — symbolic target
aAll (u+g+o) — symbolic target
+Add permission — symbolic operator
-Remove permission — symbolic operator

Example 2: Make Scripts Executable

Scenario: Carol created a new deployment script but it won't run because it lacks execute permission.

umask

DEFAULT File Permissions Shell Builtin LFCS Domain 3

Set default file creation permissions — control what permissions new files get

umask is a shell builtin that defines the permission bits to REMOVE from newly created files and directories. It's a mask: a bit set in umask means that permission will NOT be granted. Default umask is 022 (files get 644, dirs get 755).

Syntax

umask [MASK]                    # Set umask (no dash)
umask -S                        # Show in symbolic notation
umask                           # Show current umask (no args)

# Common values:
umask 022   # Files: 644 (rw-r--r--), Dirs: 755 (rwxr-xr-x)  [DEFAULT]
umask 002   # Files: 664 (rw-rw-r--), Dirs: 775 (rwxrwxr-x)  [group-writable]
umask 077   # Files: 600 (rw-------), Dirs: 700 (rwx------)  [fully private]

Examples

Example 1: Check Current umask

Scenario: Carol verifies the default permissions that new files will receive.

Command:

umask && umask -S

Output:

0022 u=rwx,g=rx,o=rx

What happened: The umask is 022 — meaning group and others will NOT have write permission. New files get 666 - 022 = 644 (rw-r--r--). New directories get 777 - 022 = 755 (rwxr-xr-x). The symbolic form confirms: user=rwx, group=rx, others=rx.

Example 2: Set Strict umask for Sensitive Work

Scenario: Eve sets a strict umask before creating sensitive audit files.

Command:

Output:

-rw------- 1 eve auditors 0 Jun 4 09:00 /lpj/ops/audit/sensitive.txt

What happened: With umask 077, ALL group and other permissions are stripped. The new file has 600 (owner-only). This is the most secure default — use it when handling secrets, keys, or PII data.

Example 3: Group-Collaborative umask

Scenario: Alice sets a permissive umask so the developers group can edit shared files.

Command:

umask 002 && touch /lpj/jobpost/shared_config.py && ls -l /lpj/jobpost/shared_config.py

Output:

-rw-rw-r-- 1 alice developers 0 Jun 4 09:00 /lpj/jobpost/shared_config.py

What happened: umask 002 leaves group-write enabled. New files get 664 (rw-rw-r--). Group members can now edit this file. This is ideal for shared project directories where multiple developers collaborate.

Example 4: Persist umask in Shell Config

Scenario: Carol sets a permanent umask for all users by adding it to /etc/profile.

0027

What happened: umask 027 is now set: files get 640 (owner rw, group r), dirs get 750 (owner rwx, group rx, others nothing). This is more secure than the default 022 — group cannot read by default, others get nothing. Persisted in a profile.d script for all users.

Scenario: After a project restructure, Carol removes all custom ACLs to return to standard POSIX permissions.

setfacl -b /lpj/jobpost/ && getfacl /lpj/jobpost/

lsattr

ATTR File Permissions Extended Attributes

List file attributes on ext filesystems — immutable, append-only, and more

lsattr displays extended filesystem attributes that go beyond standard permissions — like making a file immutable (cannot be modified even by root) or append-only.

Syntax

lsattr [OPTIONS] [FILE...]

# Common patterns:
lsattr file.txt                 # Show attributes
lsattr -R /lpj/k8s/             # Recursive
lsattr -d /lpj/k8s/             # Show directory attributes (not contents)

Common Attributes

FlagDescription
iImmutable — file cannot be modified, deleted, or renamed (even by root)
aAppend-only — file can only be appended to, not overwritten
eExtent format — file uses extents for mapping (default on ext4)

Examples

Example 1: Check File Attributes

Scenario: Carol verifies that no extended attributes are set on deployment files.

Command:

lsattr /lpj/k8s/base/*.yaml

Output:

--------------e------- /lpj/k8s/base/configmap.yaml --------------e------- /lpj/k8s/base/secrets.yaml --------------e------- /lpj/k8s/base/web-deployment.yaml

What happened: All files show only the e attribute (extent format) — no immutable (i) or append-only (a) flags. The dashes represent unset attributes. This is the normal state for most files.

Example 2: Scan Directory for Immutable Files

Scenario: Eve checks if any files in the project have been made immutable without authorization.

Command:

lsattr -R /lpj/k8s/ 2>/dev/null | grep "^[a-z-]*i[a-z-]*"

Output:

----i---------e------- /lpj/k8s/base/secrets.yaml

What happened: Only secrets.yaml has the immutable flag (i). The grep pattern matched lines containing i in the attribute string. This is a security audit check — immutable files cannot be modified, so Eve verifies they were set intentionally.

💡 LFCS Exam Tip: lsattr shows the i (immutable) and a (append-only) flags. These are set with chattr. An immutable file cannot be deleted even with rm -f — you must remove the flag first with chattr -i.

chattr

ATTR File Permissions Extended Attributes

Change file attributes — make files immutable or append-only for tamper-proof protection

chattr sets extended filesystem attributes. The +i (immutable) flag prevents any modification — even root cannot delete the file until the flag is removed. The +a (append-only) flag prevents overwriting existing data.

Syntax

chattr [OPTIONS] [+-=][ATTRIBUTES] FILE...

# Common patterns:
chattr +i secrets.yaml          # Make immutable (cannot modify/delete)
chattr -i secrets.yaml          # Remove immutable flag
chattr +a app.log               # Make append-only
chattr -R +i /lpj/k8s/base/     # Recursive immutable

Examples

Example 1: Protect Secrets from Accidental Deletion

Scenario: Eve makes secrets.yaml immutable so even root accidentally running rm -rf cannot destroy it.

Command:

sudo chattr +i /lpj/k8s/base/secrets.yaml && lsattr /lpj/k8s/base/secrets.yaml

Output:

----i---------e------- /lpj/k8s/base/secrets.yaml

What happened: The i flag was added. Now rm -f secrets.yaml will fail with "Operation not permitted" even as root. The only way to delete it is chattr -i first. This is the strongest filesystem-level protection available.

Example 2: Append-Only Log File

Scenario: Carol protects the audit log so attackers cannot erase their tracks by overwriting it.

Command:

sudo chattr +a /lpj/ops/logs/access.log && lsattr /lpj/ops/logs/access.log

Output:

-----a-------e------- /lpj/ops/logs/access.log

What happened: The a flag makes the log append-only. New entries can be added but existing data cannot be overwritten or truncated. An attacker cannot use > access.log to wipe it. Remove with chattr -a.

Example 3: Remove Immutable Flag Before Editing

Scenario: Carol needs to update secrets.yaml but it's immutable — must remove the flag first.

Command:

sudo chattr -i /lpj/k8s/base/secrets.yaml && echo "Updated" >> /lpj/k8s/base/secrets.yaml && sudo chattr +i /lpj/k8s/base/secrets.yaml && lsattr /lpj/k8s/base/secrets.yaml

Output:

----i---------e------- /lpj/k8s/base/secrets.yaml

What happened: Carol removed the immutable flag (-i), updated the file, then re-applied it (+i). The file is protected again. This is the standard workflow for editing protected files: unlock → edit → lock.

Example 4: Recursive Immutable Protection

Scenario: Eve protects all Cilium network policies from modification.

Command:

sudo chattr -R +i /lpj/k8s/cilium/ && lsattr /lpj/k8s/cilium/*.yaml

Output:

----i---------e------- /lpj/k8s/cilium/ccnp-host-firewall.yaml ----i---------e------- /lpj/k8s/cilium/cidrgroup-vpn.yaml ----i---------e------- /lpj/k8s/cilium/cnp-baseline.yaml ----i---------e------- /lpj/k8s/cilium/cnp-dns.yaml ----i---------e------- /lpj/k8s/cilium/cnp-l7.yaml

What happened: chattr -R +i recursively made all 5 Cilium policy files immutable. They cannot be modified or deleted — even by root — until chattr -R -i is run. This is the strongest filesystem-level protection for critical security configurations.

Example 5: Temporary Immutability During Investigation

Scenario: During incident response, Carol freezes log files to preserve evidence.

Command:

sudo chattr +i /lpj/ops/logs/*.log && lsattr /lpj/ops/logs/*.log

Output:

----i---------e------- /lpj/ops/logs/access.log ----i---------e------- /lpj/ops/logs/app.log ----i---------e------- /lpj/ops/logs/error.log

What happened: All three log files are now immutable — preserving the exact state at the time of the incident. No process can modify or delete them. After investigation, chattr -i releases them. This is the standard forensics pattern: freeze evidence first, analyze later.

💡 LFCS Exam Tip: chattr +i = immutable (cannot modify/delete). chattr +a = append-only. Both require root. Even rm -f fails on immutable files. Use chattr -i/-a to remove. lsattr shows current flags. These are ext2/3/4 specific — not available on all filesystems.
