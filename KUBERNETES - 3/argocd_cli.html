argocd login

LOGIN Authentication SSO Token

Log in to an ArgoCD server — authenticate the CLI for all subsequent GitOps operations

The argocd login command authenticates the ArgoCD CLI against an ArgoCD API server. It supports multiple authentication methods: SSO (OIDC/OAuth2), local username/password accounts, and bearer tokens. On successful authentication, a JWT token is stored locally for subsequent commands.

For the anihpj Django project, this command is essential for:

  • Authenticating developers against the anihpj ArgoCD instance before managing jobpost applications
  • CI/CD pipeline authentication using long-lived tokens generated with argocd account generate-token
  • Setting up named contexts for multi-cluster management (production vs staging ArgoCD instances)
  • SSO integration with the organization's identity provider (Okta, GitHub, Google Workspace)
  • Development environment setup with insecure mode for local testing

Syntax

# Login with SSO (recommended for production)
argocd login SERVER --sso

# Login with username and password
argocd login SERVER --username USER --password PASS

# Login with an auth token (CI/CD pipelines)
argocd login SERVER --auth-token TOKEN

# Login and skip TLS verification (development only)
argocd login SERVER --insecure

# Login with a named context for multiple servers
argocd login SERVER --name CONTEXT_NAME

# Login via port-forward (no ingress required)
argocd login SERVER --port-forward --port-forward-namespace argocd

Parameters

ParameterTypeDescription
SERVERstringArgoCD server address (e.g., argocd.anihpj.com or localhost:8080) (required positional)
--ssoboolAuthenticate via Single Sign-On (opens browser for OIDC/OAuth2 flow)
--usernamestringUsername for local account authentication
--passwordstringPassword for local account authentication
--auth-tokenstringBearer token for token-based authentication (or set ARGOCD_AUTH_TOKEN env var)
--namestringName for the connection context (default: server hostname)
--insecureboolSkip TLS certificate and domain verification
--port-forwardboolConnect via kubectl port-forward instead of direct network access
--port-forward-namespacestringNamespace for port-forward target default: argocd
--grpc-webboolUse gRPC-web protocol (for proxies that don't support HTTP/2)
--cert-filestringPath to TLS certificate file for server verification
--client-crtstringClient certificate for mutual TLS authentication
--client-crt-keystringClient certificate key for mutual TLS authentication
--skip-test-tlsboolSkip the TLS connectivity test during login

Return Value

Exit CodeDescription
0Login successful — JWT token stored in ~/.argocd/config for the context
1Login failed — invalid credentials, unreachable server, or TLS verification error

argocd logout

LOGOUT Authentication Security

Log out from the current ArgoCD server context and remove stored credentials

The argocd logout command removes the authentication token for the current or specified ArgoCD context. This is a security best practice on shared machines and when rotating credentials. After logout, subsequent commands will fail with an authentication error until a new login is performed.

For the anihpj Django project, this command is essential for:

  • Clearing credentials on shared CI/CD runner machines after pipeline completion
  • Rotating authentication contexts when switching between production and staging instances
  • Security compliance — logging out before leaving a shared workstation
  • Troubleshooting authentication issues by starting with a clean state

Syntax

# Logout from current context
argocd logout

# Logout from a specific context
argocd logout CONTEXT_NAME

Parameters

ParameterTypeDescription
[CONTEXT]stringName of the ArgoCD context to log out from (defaults to current context)
-h, --helpboolDisplay help for the logout command

Return Value

Exit CodeDescription
0Logout successful — token removed from context
1No active context or context not found

📁 Context: anihpj Security Best Practices

Shared Runner Hygiene: CI/CD runners always execute argocd logout as the last step in every pipeline job to prevent credential leakage between workflow runs.
# .github/workflows/deploy.yaml — Cleanup step
name: Deploy jobpost
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
    # ... build and deploy steps ...
    - name: Cleanup ArgoCD session
      if: always()
      run: |
        echo "Logging out of ArgoCD..."
        argocd logout 2>/dev/null || true
        echo "Cleared ArgoCD credentials from runner"

# Contexts stored in ~/.config/argocd/config
# After logout: auth-token field is removed from context entry
# Next pipeline run must login fresh with ARGOCD_AUTH_TOKEN env var

argocd context

CONTEXT Configuration Multi-Cluster

Manage ArgoCD connection contexts — list, switch, and delete server connections

The argocd context command manages named connection contexts to different ArgoCD servers. Each context stores the server URL, authentication token, and TLS settings. This enables seamless switching between multiple ArgoCD instances (e.g., production, staging, development) without re-authentication.

For the anihpj Django project, this command is essential for:

  • Switching between production and staging ArgoCD instances without re-login
  • Managing multiple cluster contexts for multi-region GitOps deployments
  • Cleaning up stale contexts from decommissioned ArgoCD instances
  • Scripting environment-aware deployments that target the correct cluster

Syntax

# List all configured contexts
argocd context

# Switch to a specific context
argocd context CONTEXT_NAME

# Delete a context
argocd context --delete CONTEXT_NAME

Parameters

ParameterTypeDescription
[CONTEXT]stringName of the context to switch to (lists all if omitted)
--deleteboolDelete the specified context instead of switching to it
-h, --helpboolDisplay help for the context command

Return Value

ActionOutput

SwitchConfirmation message: context switched
DeleteConfirmation message: context removed

#!/bin/bash
REQUIRED="v2.10"
CLI_VER=$(argocd version --client --short 2>/dev/null | grep -oP 'v\d+\.\d+')
SERVER_VER=$(argocd version --short 2>/dev/null | grep -oP 'v\d+\.\d+' | tail -1)

echo "CLI Version:    $CLI_VER"
echo "Server Version: $SERVER_VER"

if [[ "$CLI_VER" != "$REQUIRED"* ]]; then
  echo "❌ CLI version mismatch: expected $REQUIRED.x, got $CLI_VER"
  exit 1
fi
echo "✅ Version check passed — CLI $CLI_VER matches required $REQUIRED.x"

argocd relogin

RELOGIN Authentication Token Refresh

Refresh an expired authentication token without a full re-login flow

The argocd relogin command refreshes an expired or expiring authentication token. Unlike a full login, it preserves the existing context configuration (server URL, TLS settings) and only renews the token. This is the quickest way to re-authenticate when a session expires.

For the anihpj Django project, this command is essential for:

  • Quickly refreshing expired SSO tokens during long development sessions
  • Non-interactive token renewal in CI/CD pipelines (with token-based auth)
  • Restoring access after network interruptions without reconfiguring contexts

Syntax

# Refresh current context token
argocd relogin

# Refresh with password
argocd relogin --password NEWPASS

# Refresh with SSO
argocd relogin --sso

Parameters

ParameterTypeDescription
--ssoboolUse SSO to refresh the token
--passwordstringPassword for local account token refresh
-h, --helpboolDisplay help for the relogin command

Return Value

Exit CodeDescription
0Token refreshed — context re-authenticated

📁 Context

Token Lifecycle: ArgoCD tokens expire based on the OIDC provider settings (typically 8 hours for Okta). Use relogin to refresh without losing context configuration — much faster than a full login.

Create a new Application in ArgoCD — define the source repo, target cluster, and sync policy

The argocd app create command registers a new Application in ArgoCD. An Application binds a Git repository source to a target Kubernetes cluster, defining what to deploy, where to deploy, and how to keep it in sync. Supports Helm, Kustomize, Jsonnet, and plain YAML sources.

For the anihpj Django project:

  • Bootstrapping the jobpost-api application with automated sync from the GitHub repository
  • Creating environment-specific apps (production, staging) from the same repo with different paths
  • Defining Helm-based deployments with custom values files for each environment

Syntax

argocd app create APPNAME --repo REPO --path PATH --dest-server SERVER --dest-namespace NS
argocd app create APPNAME -f app-definition.yaml
