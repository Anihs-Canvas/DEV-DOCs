    1.2  The 8 Problems Microservices Create (That Istio Solves)
         - Problem 1: Reliability — what if user-service is slow or down?
           anihpj's jobpost-api keeps retrying, cascading failure!
         - Problem 2: Security — HTTP traffic between services is plain text
           Anyone on the network can read job listings, user data, tokens
         - Problem 3: Visibility — which service is slow? Which is failing?
           You see errors but don't know WHERE in the chain they start
         - Problem 4: Load balancing — you have 3 replicas of skills-service
           Which one handles the next request? Round-robin? Least connections?
         - Problem 5: Routing — how do you test a new version of jobpost-api
           without affecting real users? (canary deployments)
         - Problem 6: Retries & Timeouts — if skills-service times out,
           should jobpost-api retry? How many times? What timeout?
         - Problem 7: Circuit breaking — if auth-service is crashing,
           stop sending requests to it before the whole system falls over
         - Problem 8: Rate limiting — prevent one client from flooding
           your jobpost API with 10,000 requests per second

    1.3  The Naive Solution: Solving Problems in Application Code
         - Every team writes retry logic in Python/Django
         - Every team writes timeout code independently
         - Every team implements their own mTLS / token verification
         - The problems:
           • Code duplication across all services
           • Different teams implement it differently (bugs, inconsistency)
           • Hard to update — change retry logic = update 7 services
           • Language-locked — what if you add a Go service later?

    1.4  The Right Solution: Move Networking Logic Out of Your Code
         - What if EVERY service automatically got:
           ✅ Retries & timeouts — without writing a single line of code
           ✅ mTLS encryption — without changing your Django views.py
           ✅ Full distributed tracing — without adding any instrumentation
           ✅ Traffic routing (canary, blue/green) — via YAML not code
           ✅ Circuit breaking — automatic, policy-driven
           ✅ Rate limiting — enforced at the network layer
         - This is exactly what a SERVICE MESH provides
         - And Istio is the most popular service mesh for Kubernetes
         [SOLUTION REVEAL DIAGRAM: Code without networking vs with Istio]

         [THE SOLUTION: MOVE NETWORKING OUT OF APPLICATION CODE]

         │                                                        │

    1.5  Service Mesh Defined — The Core Concept
         - A service mesh is a dedicated infrastructure layer that handles
           service-to-service communication
         - It is "transparent" — your app code doesn't know it exists
         - It works by deploying a "proxy" alongside every service container
         - All traffic in and out of each service passes through this proxy
         - The proxies form the "data plane" — they DO the work
         - A central control component configures all the proxies — "control plane"

Chapter 2: Istio From First Principles
--------------------------------------------------------------------------------
    2.1  Istio Defined
         - Istio is an open-source service mesh for Kubernetes
         - Created by Google, IBM, and Lyft in 2017; CNCF graduated 2023
         - It adds a dedicated infrastructure layer on top of Kubernetes Services
         - Works by injecting an Envoy proxy sidecar into every Pod automatically
         - Your Django code at http://user-service/ — Istio intercepts it,
           encrypts it, retries it, traces it, routes it — all without code change
         [CARD: Istio quick facts — version, creator, license, CNCF status]

    2.2  What Exactly Does Istio Give You?
         - Automatic mTLS: every HTTP call between anihpj services becomes
           encrypted HTTPS — without adding SSL code in Django
         - Traffic routing: send 90% of traffic to jobpost-api:v1,
           10% to jobpost-api:v2 — gradual canary rollout via YAML
         - Retries: "retry this call to user-service 3 times if it fails"
         - Timeouts: "give up on auth-service after 5 seconds"
         - Circuit breaker: "if skills-service fails 5 times, stop calling it"
         - Fault injection: "artificially delay 10% of calls to test resilience"
         - Metrics: every request is measured — latency, error rate, throughput
         - Distributed tracing: follow a request from jobpost-api → user-service
           → auth-service → database, across ALL hops, with timing
         - Access control: "only jobpost-api is allowed to call user-service"

    2.4  Envoy — The Proxy That Makes It All Work
         - Istio's data plane uses Envoy Proxy (not Nginx, not HAProxy)
         - Envoy was created at Lyft to handle their microservices at scale
         - It is an L7 (application layer) proxy written in C++ — extremely fast
         - Envoy understands HTTP/1.1, HTTP/2, gRPC, TCP, WebSockets
         - Istio injects Envoy as a "sidecar" container in every Pod
         - Every request your Django service makes FIRST goes through Envoy
         - Envoy handles: routing, retry, timeout, mTLS, metrics, tracing

    2.6  Istio Key Terms and Vocabulary Glossary
         - Service Mesh: the network of proxies + control plane
         - Sidecar: the Envoy proxy container injected alongside your app
         - Data Plane: the collection of all Envoy sidecar proxies
         - Control Plane (istiod): the central component that configures proxies
         - VirtualService: Istio CRD for traffic routing rules
         - DestinationRule: Istio CRD for traffic policies (mTLS, load balancing)
         - Gateway: Istio CRD for ingress/egress to the mesh
         - ServiceEntry: Istio CRD to register external services in the mesh
         - PeerAuthentication: Istio CRD for mTLS mode per namespace/workload
         - AuthorizationPolicy: Istio CRD for access control (who can call what)
         - Workload: a Kubernetes deployment/pod managed by Istio
         - mTLS: Mutual TLS — both sides authenticate each other with certificates
         - xDS API: the protocol istiod uses to configure Envoy proxies

    3.2  istiod — The Control Plane (Deep Dive)
         - istiod is a single binary that replaced 3 separate components (v1.5+)
         - Old architecture: Pilot + Citadel + Galley (separate pods)
         - New architecture: all merged into one istiod pod
         - What istiod contains:
           a) Pilot: reads Istio CRDs (VirtualService, DestinationRule), converts
              them to Envoy xDS configuration, pushes to all sidecar proxies
           b) Citadel (now: Certificate Authority): issues and rotates mTLS
              certificates for every service in the mesh (SPIFFE/X.509 certs)
           c) Galley (now: Config Validation): validates Istio YAML before applying,
              watches Kubernetes API for changes
         - istiod runs in istio-system namespace
         [istiod INTERNALS DIAGRAM — what happens inside istiod]

         [istiod INTERNAL ARCHITECTURE — what lives inside the single binary]

         │                        istiod Pod                                 │
         │   ┌─────────────────────────────────────────────────────────┐    │
         │   │   PILOT sub-component (Traffic Config Manager)           │    │
         │   │   • Watches Kubernetes API for:                          │    │
         │   │     - VirtualService changes → convert to Envoy RDS      │    │
         │   │     - DestinationRule changes → convert to Envoy CDS     │    │
         │   │     - Gateway changes → convert to Envoy LDS             │    │
         │   │     - Service/Endpoint changes → convert to Envoy EDS    │    │
         │   │   • Pushes config to Envoy proxies via gRPC/xDS stream   │    │

    3.3  The Envoy Proxy — Deep Dive
         - Envoy is not just a proxy — it is a "programmable" proxy
         - istiod configures Envoy via the xDS API (Discovery Services):
           • LDS (Listener Discovery Service): which ports to listen on
           • RDS (Route Discovery Service): how to route requests
           • CDS (Cluster Discovery Service): which upstream services exist
           • EDS (Endpoint Discovery Service): which pod IPs are behind a service
         - Envoy's capabilities used by Istio:
           • HTTP request/response manipulation
           • Automatic metrics generation (RED metrics: Rate, Errors, Duration)
           • Distributed tracing header injection (x-b3-traceid, etc.)
           • mTLS termination and origination
           • Circuit breaking and outlier detection
           • Request retries with backoff
           • Fault injection (delays, aborts)
         [xDS PROTOCOL DIAGRAM: istiod → xDS → Envoy configuration flow]

         [HOW istiod CONFIGURES ENVOY — xDS flow]
         ┌────────────────────────────────────────────────────────┐
         │                                                        │
         │  You apply YAML:                                       │
         │  kubectl apply -f virtual-service.yaml                 │
         │         │                                             │
         │         ▼                                             │
         │  Kubernetes API Server stores it in etcd              │
         │         │                                             │
         │         ▼                                             │

    3.4  Automatic Sidecar Injection — How It Works
         - How Istio injects Envoy without changing your Deployment YAML
         - Kubernetes Mutating Admission Webhook: Istio registers a webhook
         - When a Pod is created, Kubernetes calls istiod's webhook FIRST
         - istiod modifies the Pod spec on the fly — adds the istio-proxy container
         - Also adds an init container (istio-init) that sets up iptables rules
         - iptables rules: redirect ALL inbound/outbound traffic through Envoy
         - Enable injection for a namespace: kubectl label namespace anihpj
           istio-injection=enabled
         - Or per-deployment: add annotation sidecar.istio.io/inject: "true"

    3.5  iptables — How Traffic Is Intercepted
         - iptables is a Linux firewall that redirects network packets
         - istio-init container runs as root to set iptables rules:
           • ALL outbound traffic → redirected to Envoy port 15001
           • ALL inbound traffic → redirected to Envoy port 15006
           • Envoy process itself is excluded (avoid infinite loop)
         - This is completely transparent to your Django app
         - Django thinks it's connecting directly to user-service:80
         - In reality: Django → iptables → Envoy → mTLS tunnel → remote Envoy → user-service
         [IPTABLES REDIRECT DIAGRAM showing the invisible interception]

         [IPTABLES PACKET JOURNEY — step by step through the network stack]
         ┌────────────────────────────────────────────────────────────────────┐
         │  OUTBOUND (jobpost-api calling user-service):                      │
         │                                                                    │
         │  ① Django code:  requests.get("http://user-service/api/users/")   │
         │  ② OS resolves:  user-service → ClusterIP 10.96.45.23:80          │
         │  ③ Packet enters: Linux network stack, destination 10.96.45.23:80 │
         │  ④ iptables rule: "OUTPUT chain → redirect to 127.0.0.1:15001"   │
         │  ⑤ Envoy receives packet on port 15001 (outbound listener)        │
         │  ⑥ Envoy looks up: "who is 10.96.45.23?" → it is user-service    │
         │  ⑦ Envoy applies:  routing rules, timeout, retry, circuit breaker │
         │  ⑧ Envoy initiates mTLS: presents jobpost-api certificate         │
         │  ⑨ Packet sent to: user-service Pod IP:15006 (not :80!)           │
         │                                                                    │
         │  INBOUND (user-service receiving):                                 │
         │                                                                    │
         │  ① Packet arrives at user-service Pod:15006                       │
         │  ② iptables rule: "PREROUTING → redirect to 127.0.0.1:15006"     │
         │  ③ Envoy receives on port 15006 (inbound listener)                │
         │  ④ Envoy verifies: mTLS certificate from jobpost-api Envoy       │
         │  ⑤ Envoy checks:   AuthorizationPolicy (is jobpost-api allowed?)  │
         │  ⑥ Envoy records:  request metric (latency timer starts)          │
         │  ⑦ Envoy forwards: to 127.0.0.1:8000 (Django on localhost)        │
         │  ⑧ Django sees:    normal HTTP request, no TLS needed!            │
         │                                                                    │
         │  KEY INSIGHT: Django never sees TLS. Envoy handles it all.        │
         │  Django talks plain HTTP on localhost. Envoy handles encryption    │
         │  between pods. Your code changes: ZERO. ✅                         │
         └────────────────────────────────────────────────────────────────────┘

         [IPTABLES RULES SET BY istio-init — the actual commands]
         ┌────────────────────────────────────────────────────────────────────┐
         │  # Rules added by istio-init container (simplified):               │

         │  # Redirect ALL outbound traffic to Envoy port 15001               │

Chapter 5: Gateway — The Front Door to Your Mesh
--------------------------------------------------------------------------------
    5.1  What is an Istio Gateway?
         - A Gateway is the entry point for traffic FROM OUTSIDE the mesh
         - It replaces (or works alongside) a Kubernetes Ingress
         - Deployed as its own Pod: istio-ingressgateway (Envoy-based)
         - More powerful than Ingress: supports header manipulation, mTLS,
           custom ports, weight-based routing, etc.
         - Two types:
           • IngressGateway: external traffic INTO the mesh
           • EgressGateway: controlled traffic OUT of the mesh (to external APIs)
         [GATEWAY POSITION DIAGRAM: internet → Gateway → VirtualService → Pods]

         [GATEWAY vs KUBERNETES INGRESS COMPARISON]
         ┌────────────────────────────────────────────────────────┐
         │  KUBERNETES INGRESS          ISTIO GATEWAY             │
         │  ──────────────────          ─────────────────         │
         │  ✅ Simple host/path routing  ✅ Same + more            │
         │  ❌ No header manipulation    ✅ Full header control     │
         │  ❌ No mTLS termination       ✅ mTLS at the edge        │
         │  ❌ No weighted routing       ✅ % traffic split        │
         │  ❌ Limited TLS options       ✅ Advanced TLS/SNI        │
         │  ❌ No egress control         ✅ Egress gateway          │
         └────────────────────────────────────────────────────────┘

    5.2  Gateway YAML — Accepting Traffic for anihpj
         - How to write a Gateway resource for anihpj.example.com
         - port 80 (HTTP) and port 443 (HTTPS with TLS certificate)
         - selector: istio: ingressgateway (which Envoy handles this)
         - hosts: ["anihpj.example.com"] (which hostnames to accept)
         [ANNOTATED Gateway YAML with every field explained]

         [COMPLETE ANNOTATED Gateway YAML for anihpj]

Chapter 6: VirtualService — Smart Traffic Routing
--------------------------------------------------------------------------------
    6.1  What is a VirtualService?
         - A VirtualService is Istio's routing rules for a service
         - It overrides Kubernetes' default routing (simple round-robin)
         - Defines: WHERE traffic goes, HOW MUCH traffic, WITH WHAT conditions
         - Works for traffic from:
           • External (via Gateway)
           • Internal service-to-service calls within the mesh
         - Attaches to a Kubernetes Service by name
         [VIRTUALSERVICE CONCEPT DIAGRAM: traffic fork based on rules]

    6.2  Basic Routing — Send All Traffic to One Version
         - jobpost-api has v1 and v2 deployments running simultaneously
         - By default, Kubernetes alternates between both
         - VirtualService: "Send 100% of traffic to subset: v1"
         - Subset is defined in DestinationRule (covered next)
         [YAML + TRAFFIC FLOW DIAGRAM: all traffic pinned to v1]

    6.3  Weight-Based Traffic Splitting (Canary Deployments)
         - Deploy jobpost-api:v2 (new version with better job search)
         - Start with 5% traffic to v2, 95% to v1
         - Gradually shift: 10%→25%→50%→100% as confidence grows
         - Roll back instantly by changing the weight — no downtime

    6.6  Retries — Automatic Failure Recovery
         - Without Istio: if user-service returns a 503, anihpj fails
         - With Istio VirtualService retries: automatically retry up to 3 times
         - Configure: attempts, perTryTimeout, retryOn (which error codes)
         - Important: retries only safe for idempotent requests (GET, not POST)
         - anihpj use case: retry GET /users/{id}/ if user-service is momentarily down
         [RETRY FLOW DIAGRAM: first call fails → Envoy retries → success]

         [RETRY TIMELINE — how Envoy handles a failing user-service call]
         ┌────────────────────────────────────────────────────────────────────┐
         │  Without retries (default Kubernetes):                             │
         │                                                                    │
         │  T=0ms:   jobpost-api → user-service → ❌ 503 Service Unavailable │
         │  T=1ms:   Envoy returns 503 to Django                             │
         │  T=2ms:   Django returns 500 to user browser                       │
         │  💥 User sees error even though user-service recovers in 200ms    │
         │                                                                    │
         │  With Istio retries (attempts: 3, perTryTimeout: 2s):             │

         │  T=0ms:   jobpost-api → user-service → ❌ 503 (attempt 1)         │
         │  T=100ms: Envoy retries: → user-service → ❌ 503 (attempt 2)      │
         │  T=200ms: Envoy retries: → user-service → ✅ 200 OK (attempt 3)  │
         │  T=201ms: Django receives response normally                        │
         │  ✅ User never sees an error — blip absorbed by retry              │
         │                                                                    │
         │  YAML config that makes this happen:                               │

         │    http:                                                           │

         │      - destination:                                                │
         │          host: user-service                                        │

    6.7  Timeouts — Don't Wait Forever
         - Without Istio: your Django code hangs waiting for slow services
         - With Istio: set a global timeout per service (e.g., 5s for skills-svc)
         - Request takes >5s → Envoy returns 408/504, doesn't hang Django
         - anihpj use case: skills-service timeout 3s — fast degradation

Chapter 7: DestinationRule — Traffic Policies and Load Balancing
--------------------------------------------------------------------------------
    7.1  What is a DestinationRule?
         - DestinationRule defines POLICIES for traffic going to a specific service
         - Works AFTER VirtualService routing decides WHERE to send traffic
         - VirtualService = the "GPS route" (which road to take)
         - DestinationRule = the "driving rules" (speed limit, lane choice)
         - Defines: load balancing algorithm, connection pool size, circuit breaker,
           TLS mode, and named subsets (for canary routing)
         [VS + DR RELATIONSHIP DIAGRAM]

         [VIRTUALSERVICE + DESTINATIONRULE — how they work together]
         ┌────────────────────────────────────────────────────────────────────┐
         │                                                                    │
         │  REQUEST: GET /jobs/                                               │
         │            │                                                       │
         │            ▼                                                       │
         │  ┌──────────────────────────────────────────────┐                 │
         │  │  VirtualService: "WHERE should this go?"     │                 │
         │  │  → match /jobs/* → destination: jobpost-api  │                 │
         │  │  → weight: 90% → subset: v1                  │                 │
         │  │  → weight: 10% → subset: v2                  │                 │
         │  └──────────────────────────┬───────────────────┘                 │
         │                             │  "I chose subset: v1"               │
         │                             ▼                                      │
         │  ┌──────────────────────────────────────────────┐                 │
         │  │  DestinationRule: "HOW should we send it?"   │                 │
         │  │  → subset v1 = pods with version: v1 label   │                 │
         │  │  → loadBalancer: LEAST_CONN                  │                 │
         │  │  → tls: mode: ISTIO_MUTUAL                   │                 │
         │  │  → circuitBreaker: consecutiveErrors: 5      │                 │

         │          [pod:v1-1]   [pod:v1-2]   [pod:v1-3]                     │
         │          (least conn picks the one with fewest active connections) │

    7.3  Load Balancing Algorithms
         - Default: ROUND_ROBIN (Kubernetes default, Envoy default)
         - LEAST_CONN: send to the pod with fewest active connections
         - RANDOM: random pod selection (surprisingly effective)
         - PASSTHROUGH: bypass Envoy load balancing
         - CONSISTENT_HASH: stick same user to same pod (session affinity)
           → anihpj use case: user-service sticky sessions by user ID header

    7.4  Circuit Breaking (Outlier Detection)
         - What is a circuit breaker? (borrowed from electrical engineering)
         - CLOSED: requests flow normally
         - OPEN: service is failing → Envoy STOPS sending requests to it
         - HALF-OPEN: after a pause, try again — if OK, close circuit
         - Configuration in DestinationRule: outlierDetection
           • consecutiveGatewayErrors: 5 → after 5 errors, eject host
           • interval: 30s → check every 30 seconds
           • baseEjectionTime: 30s → keep ejected for 30 seconds
           • maxEjectionPercent: 50 → never eject more than 50% of hosts
         - anihpj use case: if auth-service returns 5 consecutive 503s →
           stop sending requests, return error immediately, spare the service
         [CIRCUIT BREAKER STATE MACHINE DIAGRAM: Closed → Open → Half-Open]

         [CIRCUIT BREAKER STATE MACHINE]
         ┌────────────────────────────────────────────────────────┐
         │                                                        │
         │  ┌─────────────┐   5 errors    ┌─────────────────┐    │
         │  │   CLOSED    │ ─────────────▶│     OPEN        │    │
         │  │             │               │                 │    │
         │  │  Requests   │               │ Requests fail   │    │
         │  │  flow ✅    │               │ immediately ❌  │    │
         │  │  Success    │               │ (saves service) │    │

         │         ▲                               │              │

         │         │                     ┌─────────┴────────┐    │

Chapter 10: Distributed Tracing — Follow Any Request Across All Services
--------------------------------------------------------------------------------
    10.1 What is Distributed Tracing?
         - A single HTTP request to anihpj /jobs/ triggers 5+ service calls
         - Without tracing: you see an error but have no idea WHICH service caused it
         - With tracing: see the ENTIRE call chain — every hop, every duration
         - Key concepts:
           • Trace: the entire journey of one request (root span + child spans)
           • Span: one unit of work (one service call) with start time + duration
           • Trace ID: unique ID linking all spans of one request
           • Parent/Child: shows the hierarchy of calls
         [TRACE DIAGRAM: one request → many spans visualized as Gantt chart]

         [DISTRIBUTED TRACE — anihpj GET /jobs/ request]
         ┌──────────────────────────────────────────────────────────────┐
         │  Trace ID: 7f3e9a12b4c06d8e  Duration: 342ms                │
         │                                                              │
         │  ▶ jobpost-api (GET /jobs/)                    0ms → 342ms  │
         │    ▶ user-service (GET /users/42/)            12ms → 87ms   │
         │      ▶ auth-service (POST /validate-token/)  15ms → 45ms   │
         │    ▶ skills-service (GET /skills/?ids=1,2,3)  92ms → 287ms  │
         │      ← 195ms ← SLOW! This is the bottleneck                │
         │    ▶ location-service (GET /locations/7/)    295ms → 320ms  │
         │                                                              │
         │  🔍 skills-service call took 195ms — investigate!           │
         └──────────────────────────────────────────────────────────────┘

    10.2 How Istio Enables Tracing (Almost Automatically)
         - Istio's Envoy injects tracing headers automatically:
           x-request-id, x-b3-traceid, x-b3-spanid, x-b3-parentspanid
         - Your Django code MUST forward these headers between services!
         - Istio does the heavy lifting; you just propagate the headers
         [CODE EXAMPLE: Django middleware to forward Istio tracing headers]

         [REQUIRED: Header propagation in Django views.py]
         ┌────────────────────────────────────────────────────────┐
         │  # Add this to your Django views that call services:   │
         │                                                        │
         │  ISTIO_HEADERS = [                                     │
         │      'x-request-id',                                   │
         │      'x-b3-traceid',                                   │
         │      'x-b3-spanid',                                    │
         │      'x-b3-parentspanid',                              │
         │      'x-b3-sampled',                                   │
         │      'x-b3-flags',                                     │
         │  ]                                                     │
         │                                                        │
         │  def get_jobs(request):                                │
         │      # Forward headers to propagate trace context:     │
         │      headers = {h: request.META.get(                   │
         │          'HTTP_' + h.upper().replace('-', '_'))        │
         │          for h in ISTIO_HEADERS                        │
         │          if request.META.get(                          │
         │              'HTTP_' + h.upper().replace('-', '_'))    │
         │      }                                                 │
         │      users = requests.get('http://user-service/users/',│
         │                           headers=headers)             │
         └────────────────────────────────────────────────────────┘

Chapter 12: Mutual TLS (mTLS) — Encrypting Everything
--------------------------------------------------------------------------------
    12.1 The Security Problem Without mTLS
         - Inside a Kubernetes cluster: traffic is plain HTTP by default
         - Any compromised pod can sniff traffic from other services
         - Anyone with access to the network can read jobpost DB passwords,
           user tokens, session data passing between anihpj services
         - Traditional solution: implement TLS in every service → complex
         [THREAT DIAGRAM: rogue pod sniffing plain HTTP between services]

         [THREAT MODEL — what can go wrong WITHOUT Istio mTLS]
         ┌────────────────────────────────────────────────────────────────────┐
         │  ATTACK 1: Network Sniffing (Man-in-the-Middle)                    │
         │                                                                    │
         │  [jobpost-api] ──HTTP──▶ [user-service]                           │
         │                    │                                               │
         │              [😈 rogue-pod]                                        │
         │               (on same node)                                       │
         │               captures plain HTTP:                                 │
         │               "Authorization: Bearer eyJhbGci...  ← JWT STOLEN!   │
         │               "password=SuperSecret123"            ← DATA EXPOSED  │
         │                                                                    │
         │  ATTACK 2: Service Impersonation                                   │
         │                                                                    │
         │  [jobpost-api] ──HTTP──▶ [😈 fake-user-service]                   │
         │                          (attacker deployed a pod                  │
         │                           named "user-service" in a                │
         │                           different namespace)                     │
         │                          "I'm the real user-service — trust me!"  │
         │                          → Returns fake user data                  │
         │                                                                    │
         │  ATTACK 3: Lateral Movement                                        │
         │                                                                    │
         │  [😈 compromised skills-svc] ──HTTP──▶ [user-service]            │
         │  "Please give me all users' personal data..."                      │
         │  → No AuthorizationPolicy = request ALLOWED!                      │
         │  → All user data exfiltrated                                       │
         │                                                                    │
         │  WITH ISTIO mTLS + AuthorizationPolicy:                            │
         │  ✅ Attack 1 blocked: all traffic is encrypted                     │
         │  ✅ Attack 2 blocked: fake service has no valid SPIFFE cert        │
         │  ✅ Attack 3 blocked: AuthzPolicy denies skills-svc→user-svc call  │
         └────────────────────────────────────────────────────────────────────┘

    12.2 What is Mutual TLS (mTLS)?
         - Regular TLS: server proves identity to client (HTTPS website)
         - Mutual TLS: BOTH sides prove identity to each other
         - Istio issues X.509 SVID certificates (SPIFFE standard) to every workload
         - Certificate contains: spiffe://cluster.local/ns/anihpj/sa/jobpost-api
         - This certificate identifies the service, not just the node/IP
         - Rotation: certificates expire and rotate every 24 hours automatically
         [mTLS HANDSHAKE DIAGRAM: jobpost-api ↔ user-service certificate exchange]

         [mTLS EXPLAINED — what happens in each handshake]
         ┌────────────────────────────────────────────────────────┐
         │  WITHOUT mTLS (plain HTTP):                            │
         │  jobpost-api ──────────────────────────▶ user-service  │
         │               "GET /users/42 HTTP/1.1"                 │
         │               (anyone can read this!)                  │
         │                                                        │
         │  WITH mTLS (Istio automatic):                          │
         │                                                        │
         │  ① Envoy(jobpost) → "Hello, I am jobpost-api"         │
         │                    presents certificate (SVID)         │
         │  ② Envoy(user)   → "I am user-service"                │
         │                    presents certificate (SVID)         │
         │  ③ BOTH verify each other's certificates with istiod   │
         │  ④ Encrypted tunnel established                        │
         │  ⑤ "GET /users/42" sent through encrypted tunnel      │
         │                                                        │
         │  ✅ No code change in Django to get mTLS!              │
         │  ✅ Certificates auto-issued and rotated by istiod     │
         │  ✅ SPIFFE identity — tied to service, not IP          │
         └────────────────────────────────────────────────────────┘

    12.3 PeerAuthentication — Configuring mTLS Mode
         - PeerAuthentication is the Istio CRD that controls mTLS
         - Three modes:
           • PERMISSIVE: accept both plain HTTP and mTLS (migration mode)
           • STRICT: reject all plain HTTP — enforce mTLS everywhere
           • DISABLE: turn off mTLS (for debugging only)
         - Apply per namespace or per workload
         - anihpj: start with PERMISSIVE during migration, then STRICT
         [YAML: PeerAuthentication for anihpj namespace in STRICT mode]

         [PeerAuthentication YAML — enforce mTLS for anihpj]
         ┌────────────────────────────────────────────────────────┐
         │  apiVersion: security.istio.io/v1beta1                 │
         │  kind: PeerAuthentication                              │
         │  metadata:                                             │
         │    name: default                                       │
         │    namespace: anihpj                                   │
         │  spec:                                                 │
         │    mtls:                                               │
         │      mode: STRICT   # ALL traffic must use mTLS       │
         │                     # Plain HTTP will be rejected      │
         │                                                        │
         │  # Alternative: per-workload only                      │
         │  spec:                                                 │
         │    selector:                                           │
         │      matchLabels:                                      │
         │        app: user-service   # Only for user-service     │
         │    mtls:                                               │
         │      mode: STRICT                                      │
         └────────────────────────────────────────────────────────┘

    12.4 Certificate Lifecycle — How istiod Issues Certs
         - Every Pod gets an X.509 certificate at startup via istiod CA
         - Certificate Authority is built into istiod (no external CA needed)
         - SPIFFE Verifiable Identity Document (SVID) format
         - Rotation: 24-hour default, rotated 5 minutes before expiry
         - Plugging in external CAs (AWS ACM, Vault, Cert-Manager)
         [CERT ISSUANCE FLOW DIAGRAM: Pod starts → istiod issues cert → mTLS ready]

         [CERTIFICATE LIFECYCLE — full flow for anihpj]

Chapter 13: Authorization Policies — Who Can Call What
--------------------------------------------------------------------------------
    13.1 The Need for Service-Level Authorization
         - mTLS proves identity but doesn't restrict what is allowed
         - Without AuthorizationPolicy: any service can call any other service
         - anihpj threat: a compromised skills-service could call user-service
           and read all user data — even though it has no business doing so
         - Zero-trust principle: deny everything by default, allow explicitly
         [THREAT DIAGRAM: overly permissive mesh vs zero-trust mesh]

    13.2 AuthorizationPolicy — The Istio Firewall
         - AuthorizationPolicy is Istio's access control CRD
         - Works at L7 (HTTP): can allow/deny based on:
           • Source service identity (SPIFFE certificate)
           • HTTP method (GET, POST, DELETE)
           • HTTP path (/jobs/, /admin/)
           • HTTP headers (Authorization, x-user-id)
           • Source namespace
         - Default behavior: ALLOW ALL (if no policy exists)
         - With a DENY-ALL policy: must explicitly allow each path

         [AUTHORIZATIONPOLICY EVALUATION — how Istio decides ALLOW or DENY]
         ┌────────────────────────────────────────────────────────────────────┐
         │  Incoming request: skills-service → GET /users/42 → user-service  │
         │                                                                    │
         │  EVALUATION ORDER:                                                 │
         │                                                                    │
         │  1. Is there a CUSTOM policy (action: CUSTOM) for user-service?   │
         │     • YES → evaluate it first; if it rejects → DENY               │
         │     • NO  → continue                                               │
         │                                                                    │
         │  2. Is there a DENY policy matching this request?                  │
         │     • YES, DENY all traffic to user-service?                      │
         │       • Does it match source: skills-service? YES → DENY ❌        │
         │     • NO matching DENY → continue                                  │
         │                                                                    │
         │  3. Is there an ALLOW policy for user-service?                     │
         │     • YES, ALLOW from: jobpost-api only                           │
         │       • Does skills-service match? NO → implicit DENY ❌           │
         │                                                                    │
         │  4. No matching ALLOW found → DENY (when any policy exists)       │
         │                                                                    │
         │  RESULT: skills-service → user-service = ❌ DENIED (403)          │
         │                                                                    │
         │  KEY RULE: If ANY AuthorizationPolicy targets a workload,         │
         │  then all requests NOT explicitly ALLOWED are DENIED.             │
         └────────────────────────────────────────────────────────────────────┘

         [COMPLETE AUTHORIZATIONPOLICY YAML — deny-all then allow-list]
         ┌────────────────────────────────────────────────────────────────────┐
         │  # Step 1: Deny ALL traffic in anihpj namespace                   │
         │  apiVersion: security.istio.io/v1beta1                            │
         │  kind: AuthorizationPolicy                                        │
         │  metadata:                                                        │
         │    name: deny-all                                                 │
         │    namespace: anihpj                                              │
         │  spec: {}   ← empty spec = deny everything                       │
         │  ---                                                               │
         │  # Step 2: Allow ingress gateway → jobpost-api                    │
         │  kind: AuthorizationPolicy                                        │
         │  metadata:                                                        │
         │    name: allow-ingress-to-jobpost                                 │
         │    namespace: anihpj                                              │
         │  spec:                                                            │
         │    selector:                                                      │
         │      matchLabels: {app: jobpost-api}    ← applies to jobpost-api  │
         │    action: ALLOW                                                   │
         │    rules:                                                         │
         │    - from:                                                        │
         │      - source:                                                    │
         │          principals:                                              │
         │          - "cluster.local/ns/istio-system/sa/istio-ingressgateway"│
         │      to:                                                          │
         │      - operation:                                                 │
         │          methods: ["GET", "POST"]  ← only GET and POST           │
         │  ---                                                               │
         │  # Step 3: Allow jobpost-api → user-service (GET only)            │
         │  kind: AuthorizationPolicy                                        │
         │  metadata:                                                        │
         │    name: allow-jobpost-to-users                                   │
         │  spec:                                                            │
         │    selector:                                                      │
         │      matchLabels: {app: user-service}                             │
         │    action: ALLOW                                                   │
         │    rules:                                                         │
         │    - from:                                                        │
         │      - source:                                                    │
         │          principals:                                              │
         │          - "cluster.local/ns/anihpj/sa/jobpost-api"              │
         │      to:                                                          │
         │      - operation:                                                 │
         │          methods: ["GET"]                                         │
         │          paths: ["/api/users/*"]   ← restrict to specific paths  │
         └────────────────────────────────────────────────────────────────────┘

    13.3 Building a Zero-Trust Policy for anihpj
         [COMPLETE POLICY WALKTHROUGH]
         - Step 1: Deny everything in the anihpj namespace
         - Step 2: Allow external traffic in via ingressgateway only
         - Step 3: Allow jobpost-api to call user-service (GET only)
         - Step 4: Allow jobpost-api to call skills-service (GET only)
         - Step 5: Allow user-service to call auth-service (GET/POST)
         - Step 6: Allow NO cross-calls that aren't explicitly needed
         - Step 7: Allow metrics scraping (Prometheus to all services)
         [POLICY MATRIX DIAGRAM: who is allowed to call what]

         [ZERO-TRUST POLICY MATRIX for anihpj]

         │  SOURCE        │  TARGET          │  ALLOWED METHODS  │
         │  ──────────────│──────────────────│──────────────────  │
         │  ingressgw     │  jobpost-api     │  GET, POST        │

         │  jobpost-api   │  skills-service  │  GET only         │

Chapter 14: Canary Deployments — Safe Feature Releases

    16.3 Istio Ambient Mesh — Sidecar-Free Mode
         - New Istio architecture (v1.15+): no sidecar injection required!
         - Layer 4 (ztunnel): handles mTLS + basic routing without sidecar
         - Layer 7 (waypoint proxy): optional, per-namespace L7 features
         - Reduced overhead: no per-pod sidecar → less memory, faster startup
         - anihpj use case: ambient mode for lower-overhead deployments

Chapter 17: Running Istio in Production

    17.1 Upgrading Istio
         - Istio release cycle: minor release every ~3 months
         - Supported versions: latest + previous (N-1)
         - In-place upgrade: istioctl upgrade (risky — avoid in production)
         - Canary upgrade: run two istiod versions simultaneously
           • New istiod runs alongside old one
           • Migrate namespaces one by one to new version
           • Old istiod removed when all namespaces migrated
         [CANARY UPGRADE FLOW DIAGRAM: old + new istiod running in parallel]

    17.2 Performance Tuning and Resource Sizing
         - istiod CPU/memory: scale based on number of sidecars
         - Sidecar proxy overhead: ~100m CPU, 128Mi memory per pod
         - Reduce overhead: concurrency setting in sidecar, request compression
         - Protocol optimization: use HTTP/2 for gRPC services
         - Tracing sampling: reduce from 100% (dev) to 1% (production)
         [RESOURCE SIZING TABLE: 10 pods / 50 pods / 100 pods / 500 pods]

    17.4 Debugging and Troubleshooting Istio
         [COMMON PROBLEMS + SOLUTIONS TABLE]
         - Problem 1: Pod not in mesh (missing sidecar)
           → Check: kubectl get pod -o jsonpath='{.spec.containers[*].name}'
           → Fix: ensure namespace has istio-injection=enabled label
         - Problem 2: mTLS connection refused (503 errors)
           → Check: istioctl proxy-status (SYNCED?)
           → Check: PeerAuthentication mode (STRICT vs PERMISSIVE)
         - Problem 3: VirtualService not routing (traffic goes to wrong version)
           → Check: DestinationRule subsets match Pod labels exactly
           → Run: istioctl analyze -n anihpj (find config errors)
         - Problem 4: High latency after adding Istio
           → Check: sidecar concurrency setting
           → Check: tracing sampling rate (100% = expensive)
         - Problem 5: Circuit breaker tripping too often
           → Check: outlierDetection thresholds (may be too sensitive)

Appendix D: Common Istio Errors and Solutions
--------------------------------------------------------------------------------
    [TABLE: Error → Cause → Diagnostic Command → Fix]

    | Error / Symptom                   | Likely Cause                        | Fix                                     |
    | ──────────────────────────────────│─────────────────────────────────────│──────────────────────────────────────── │
    | Pod shows 1/1 not 2/2 containers  | Sidecar not injected                | Label namespace: istio-injection=enabled |
    | 503 RBAC: access denied           | AuthorizationPolicy blocking         | Add explicit ALLOW policy               |
    | 503 upstream connect error        | DestinationRule mTLS mode wrong     | Match PeerAuthentication mode            |
    | VirtualService not routing        | Subset not in DestinationRule       | Add matching subset to DR               |
    | Traffic still going to all pods   | Missing version: label on pods      | Add version label to Deployment         |
    | istioctl analyze: "host not found"| Service name mismatch in VS         | Match VS host to exact K8s svc name     |
    | High latency after Istio install  | Tracing 100% sampling overhead      | Set sampling to 1% in Telemetry         |
    | Circuit breaker tripping often    | outlierDetection too aggressive     | Increase consecutiveGatewayErrors       |
    | External API calls failing        | Mesh in REGISTRY_ONLY mode          | Add ServiceEntry for external host      |
    | PROXY_STATUS shows STALE          | Network issue to istiod             | Check istiod pod health                 |


Appendix E: Istio Terminology Glossary
--------------------------------------------------------------------------------
    [GLOSSARY TABLE: 40+ terms alphabetically sorted]

    | Term                   | Definition                                               |
    | ───────────────────────│────────────────────────────────────────────────────────  │
    | Ambient Mesh           | Sidecar-free Istio mode using ztunnel + waypoint proxies  |
    | AuthorizationPolicy    | Istio CRD for access control (who can call what)          |
    | Circuit Breaker        | Pattern: stop calls to a failing service automatically     │
    | CRD                    | Custom Resource Definition — extending Kubernetes API      │
    | Data Plane             | All Envoy sidecar proxies handling actual traffic          │
    | DestinationRule        | Policies for traffic going TO a service (LB, mTLS, CB)    │
    | Envoy                  | High-performance L7 proxy; Istio's sidecar proxy           │
    | Fault Injection        | Deliberately inject delays or errors to test resilience    │
    | Gateway (Istio)        | Entry/exit point to the mesh for external traffic          │
    | istiod                 | Istio control plane: Pilot + Citadel + Galley in one pod   │
    | istioctl               | Istio command-line tool (like kubectl for Istio)           │
    | Jaeger                 | Distributed tracing backend; visualizes trace spans        │
    | Kiali                  | Istio mesh visualization and management console            │
    | mTLS                   | Mutual TLS — both parties verify certificates              │
    | Outlier Detection      | DestinationRule setting that implements circuit breaking   │
    | PeerAuthentication     | Istio CRD configuring mTLS mode per namespace/workload     │
    | Pilot                  | istiod component: reads CRDs, configures Envoy via xDS     │
    | RED Metrics            | Rate, Errors, Duration — the three key service metrics     │
    | RequestAuthentication  | Istio CRD for JWT token validation at mesh level           │
    | Service Mesh           | Infrastructure layer for service-to-service communication  │
    | ServiceEntry           | Istio CRD to register external services in the mesh        │
    | Sidecar (container)    | Envoy proxy container injected alongside your app          │
    | Sidecar (resource)     | Istio CRD to configure sidecar proxy scope                 │
    | SPIFFE                 | Secure Production Identity Framework — cert standard used  │
    | SVID                   | SPIFFE Verifiable Identity Document — workload certificate  │
    | Telemetry              | Istio CRD for configuring metrics, tracing, logging        │
    | VirtualService         | Istio CRD defining routing rules for a service             │
    | Waypoint Proxy         | Ambient mesh L7 proxy per namespace (no sidecar needed)    │
    | xDS API                | Protocol used by istiod to configure Envoy proxies         │
    | ztunnel                | Ambient mesh L4 proxy; handles mTLS without sidecars       │
