Chapter 1: What is Backstage? (The Big Picture) 🎯 CBA 24% (Dev Workflow)
--------------------------------------------------------------------------------
    1.1  The Problem Backstage Solves
         - Developer experience before Backstage: chaos, scattered tools
         - The "cognitive load" problem — too many tools, too many places
         - Spotify's story: 100+ squads, 1000+ services, no central portal
         - How new developers spent 2 weeks just finding things
         - The "Where's Waldo?" problem in large engineering orgs
         [ILLUSTRATION: Fragmented tooling landscape before Backstage]

    1.2  Backstage Defined — The Simple Answer
         - Official definition: "An open platform for building developer portals"
         - What is a Developer Portal? Single pane of glass for your tech ecosystem
         - Backstage = Catalog + Templates + TechDocs + Plugins
         - Created by Spotify (internal name: "Backstage" = behind the scenes)
         - Donated to CNCF in 2020 (Sandbox → Incubating → Graduated 2024)
         - Built with TypeScript + React + Node.js
         [CARD: Quick facts — Creator, Year, CNCF status, Language, License]

         [THE BACKSTAGE ELEVATOR PITCH]

Chapter 3: Core Concepts & Terminology 🎯 CBA 24% (Dev Workflow)
--------------------------------------------------------------------------------
    3.1  Key Backstage Terminology
         - Entity: Any thing in your Catalog (service, API, user, team, etc.)
         - Kind: The type of entity (Component, API, User, Group, System, etc.)
         - Spec: The YAML definition of an entity (catalog-info.yaml)
         - Location: Where to find entity definitions (Git URL, file path)
         - Annotation: Metadata on entities (backstage.io/*)
         - Plugin: Extensible module adding features to Backstage
         - Template: Scaffolder blueprint for creating new projects
         [TERMINOLOGY GLOSSARY TABLE]

         - User: A person in the organization
         - Group: A team, squad, or organizational unit
         - Template: A scaffolder template definition

Appendix B: catalog-info.yaml Templates
----------------------------------------
    B.1  Component Template (all common fields)
         apiVersion: backstage.io/v1alpha1 | kind: Component
         spec: {type: service|website|library|CLI, lifecycle: production|experimental|deprecated, owner: group-name, system: system-name, providesApis: [api-name], dependsOn: [resource:db-name]}

    B.2  API Template (OpenAPI, AsyncAPI, GraphQL, gRPC)
         kind: API | spec.type: openapi|asyncapi|graphql|grpc
         spec.definition.$text: https://url-to-api-spec

    B.3  System Template
         kind: System | spec: {owner: group-name, domain: domain-name}

    B.4  Domain Template
         kind: Domain | spec: {owner: group-name}

    B.5  Resource Template (database, S3, pubsub, cache)
         kind: Resource | spec.type: database|s3-bucket|pubsub-topic|cache
         spec: {owner: group-name, system: system-name, dependencyOf: [component:svc-name]}

    B.6  User Template
         kind: User | spec.profile: {displayName, email, picture}
         spec.memberOf: [group-name]

    B.7  Group Template
         kind: Group | spec.type: team|squad|tribe
         spec: {profile: {displayName, email}, parent: parent-group, children: [child-groups], members: [user-names]}

    H.1  Key YAML Structures to Memorize
         ┌──────────────────────────────────────────────────────────────┐
         │  EVERY catalog-info.yaml MUST have:                          │
         │  • apiVersion: backstage.io/v1alpha1                         │
         │  • kind: (one of 9 kinds)                                    │
         │  • metadata: (at minimum: name)                              │
         │  • spec: (type-specific properties)                          │
         │                                                              │
         │  EVERY template.yaml MUST have:                              │
         │  • apiVersion: scaffolder.backstage.io/v1beta3               │
         │  • kind: Template                                            │
         │  • metadata: (name, title, description, tags)                │
         │  • spec: (owner, type, parameters, steps)                    │
         └──────────────────────────────────────────────────────────────┘

    H.2  Entity Kinds Quick Reference
         ┌──────────────────────────────────────────────────────────────┐
         │  KIND        USE FOR                 SPEC.TYPE EXAMPLES      │
         │  ─────────── ─────────────────────── ─────────────────────── │
         │  Component   Software YOU build      service, website, lib   │
         │  API         API definitions         openapi, asyncapi, etc  │
         │  System      Group of Component+Res  (product/application)   │
         │  Domain      Business area (Systems) (HR, Finance, etc.)     │
         │  Resource    Infrastructure you USE  database, s3, cache     │
         │  User        A person                (auto-discovered)       │
         │  Group       A team / squad          team, squad, tribe      │
         │  Template    Scaffolder blueprint    service, website        │
         │  Location    Where entities live     url, file               │
         └──────────────────────────────────────────────────────────────┘
