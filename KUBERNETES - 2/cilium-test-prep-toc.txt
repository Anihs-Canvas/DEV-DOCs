<div class="mcq-block" id="q1">
    <div class="mcq-number">
        <span class="domain-pill d1">Architecture</span>
        <span class="domain-pill">1.1 K8s Networking</span>
        Q1 of 200
    </div>
    <div class="mcq-question">
        What are the four fundamental Kubernetes networking rules?
    </div>
    <div class="mcq-options">
        <div class="mcq-option correct">A) Every Pod gets its own IP address. Pods on a node can communicate with all pods on all nodes without NAT. Agents on a node can communicate with all pods on that node. Pods can communicate with other pods without NAT.</div>
        <div class="mcq-option">B) All pods share the node IP. Pods communicate through NAT. Services use iptables only. DNS is optional.</div>
        <div class="mcq-option">C) Pods use host networking by default. CNI creates overlay networks. Containers share pod IP. Services are optional.</div>
        <div class="mcq-option">D) Each container gets a unique IP. Pods on different nodes need NAT. Services replace DNS. CNI is built into the kernel.</div>
    </div>
    <button class="mcq-toggle-btn" onclick="toggleAnswer('a1')">👁️ Show Answer & Explanation</button>
    <div class="mcq-answer" id="a1">
        <div class="answer-label">✅ Correct Answer: A</div>
        <p>The four fundamental rules are: (1) Every pod gets its own IP, (2) Pods can communicate across nodes without NAT, (3) Node agents can communicate with pods on that node, (4) Pods communicate without NAT. These rules drive the entire CNI model.</p>
        <div class="explanation-label">📝 Detailed Explanation</div>
        <p>Kubernetes networking is built on these four rules. Rule 1 means each pod has a unique, routable IP — unlike Docker where containers share the host IP. Rule 2 is why CNI plugins exist: they must set up routes so pod IPs are reachable across nodes. Rule 3 is why kubelet and health checks work. Rule 4 means no source NAT between pods — preserving the source IP for NetworkPolicies. Cilium implements these rules using eBPF instead of iptables/overlay networks.</p>
    </div>
</div>

  - .mcq-option.correct (green left border)
  - .mcq-answer (hidden by default, green left border when shown)

Each troubleshooting issue follows this structure:

<div class="ts-issue" id="ts-a1">
    <div class="ts-category">🟢 CATEGORY 1: ARCHITECTURE — Issue A1</div>
    <div class="ts-title">Pod Cannot Reach Another Pod on Different Node</div>
    <p><strong>Symptom:</strong> anihpj-web pod on node-1 (IP 10.0.1.5) cannot ping anihpj-api pod on node-2 (IP 10.0.2.9). Same-node pod communication works fine.</p>

    <h4>🔴 5 MOST Likely Causes (Check These First)</h4>
    <ol>
        <li><span class="cause-likely">VXLAN/Geneve tunnel not established:</span> Check <code>cilium status | grep "Encryption"</code> and tunnel interface. Run <code>ip link show cilium_vxlan</code>.</li>
        <li><span class="cause-likely">NetworkPolicy denying cross-node traffic:</span> Run <code>hubble observe --from-pod anihpj/anihpj-web-xxx --to-pod anihpj/anihpj-api-yyy</code>.</li>
        <li><span class="cause-likely">Routing misconfiguration:</span> Check if pod CIDR routes exist: <code>ip route | grep 10.0</code>. Ensure native routing mode has correct routes.</li>
        <li><span class="cause-likely">MTU mismatch:</span> Tunnel overhead reduces effective MTU. Check <code>cilium config | grep MTU</code>. Test with <code>ping -M do -s 1400 &lt;target&gt;</code>.</li>
        <li><span class="cause-likely">Firewall/security group blocking VXLAN port (8472/UDP):</span> Check cloud firewall rules, iptables, or security groups between nodes.</li>
    </ol>

    <h4>🟡 5 LESS Likely Causes (Rare But Possible)</h4>
    <ol>
        <li><span class="cause-less-likely">Cilium agent not running on destination node</span></li>
        <li><span class="cause-less-likely">BPF map corruption or exhaustion on either node</span></li>
        <li><span class="cause-less-likely">eBPF program detached from destination veth interface</span></li>
        <li><span class="cause-less-likely">Kernel bug in VXLAN/Geneve implementation (very rare)</span></li>
        <li><span class="cause-less-likely">Conntrack table overflow causing dropped connections</span></li>
    </ol>

    <h4>🟣 5 Most Likely Causes for a BRAND NEW Cluster</h4>
    <ol>
        <li><span class="cause-new-cluster">Cilium not fully deployed:</span> Check <code>cilium status --wait</code> — some nodes may still be initializing.</li>
        <li><span class="cause-new-cluster">Wrong tunnel protocol or routing mode:</span> Default is VXLAN; verify with <code>cilium config | grep tunnel</code>.</li>
        <li><span class="cause-new-cluster">Incorrect pod CIDR configuration:</span> Check <code>cilium config | grep cluster-pool-ipv4-cidr</code> matches your cluster network.</li>
        <li><span class="cause-new-cluster">Kube-proxy still running alongside Cilium KPR:</span> Check <code>kubectl get pods -n kube-system | grep kube-proxy</code>.</li>
        <li><span class="cause-new-cluster">CNI config not applied to new node:</span> Check <code>/etc/cni/net.d/05-cilium.conflist</code> exists on the worker node.</li>
    </ol>

    <div class="ts-solution">
        <strong>🔧 How to Solve:</strong>
        <p>1. Run <code>cilium connectivity test</code> to isolate the failure.<br>
        2. Check flows: <code>hubble observe --from-pod anihpj/anihpj-web-xxx --to-pod anihpj/anihpj-api-yyy</code><br>
        3. Check tunnel: <code>ip link show cilium_vxlan</code> — should be UP<br>
        4. If MTU: <code>cilium config set mtu 1400</code> (account for 50 bytes VXLAN overhead)<br>
        5. If routing: <code>ip route add 10.0.2.0/24 via &lt;node-2-ip&gt;</code></p>
    </div>

    <div class="ts-advice">
        <strong>💡 Personal Advice:</strong> Cross-node connectivity issues are almost always MTU or tunnel problems in production. Always run <code>cilium connectivity test</code> first — it checks all these automatically. For anihpj specifically, check that both the web and api pods have valid CiliumEndpoints with identities.
    </div>

<div class="decision-tree" id="dt1">
    <h4>🌳 DT-1: Pod Cannot Reach Another Pod</h4>
    <p><strong>Category:</strong> Architecture | <strong>Est. Time:</strong> 5-15 min</p>

    <pre>
    START: Pod A cannot reach Pod B
    │
    ├─ Q1: Can Pod A reach ANY pod (including itself)?
    │   ├─ YES → Issue is specific to Pod B or path between them
    │   │   ├─ Q2: Are Pod A and Pod B on the SAME node?
    │   │   │   ├─ YES → Check: cilium endpoint list (both present?)
    │   │   │   │   ├─ Both present → Check: hubble observe --from-pod A --to-pod B
    │   │   │   │   │   ├─ DROPPED → Network Policy blocking → Review CNPs
    │   │   │   │   │   └─ No flows → identity issue → Check CEP identity
    │   │   │   │   └─ B missing → kubectl describe cep -n NS B → Fix CEP
    │   │   │   └─ NO (different nodes) → Check: ip link show cilium_vxlan
    │   │   │       ├─ DOWN → Tunnel broken → Check node firewall, restart agent
    │   │   │       └─ UP → Check: ip route | grep &lt;pod-B-CIDR&gt;
    │   │   │           ├─ Route missing → Add route or check BGP config
    │   │   │           └─ Route exists → MTU issue → ping -M do -s 1400 B_IP
    │   │   └─ (DNS/Services handled in DT-2)
    │   └─ NO → Pod A has no network at all
    │       ├─ Check: kubectl describe pod A | grep -A5 Conditions
    │       │   ├─ CNI error → Check /etc/cni/net.d/ on node
    │       │   └─ PodRunning → Check: cilium endpoint list | grep A
    │       │       └─ Missing → agent issue → kubectl logs ds/cilium on node
    │       └─ FIX: Restart Cilium agent on pod's node if endpoint missing
    </pre>
</div>
