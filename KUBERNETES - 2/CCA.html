🐝 What is Cilium?

Cilium is an open-source CNI plugin powered by eBPF that provides networking, security, and observability for Kubernetes. Unlike traditional CNIs (Calico, Flannel) that use iptables, Cilium runs eBPF programs directly in the Linux kernel — making it 587x faster at scale. It replaces your CNI, kube-proxy, service mesh sidecar, and network policy engine — all with one eBPF-powered agent per node.

⚡

🛡️
Identity-Based Security

Policies based on pod labels, not fragile IP addresses. Survives pod restarts.

🔭
Hubble Observability

Built-in flow logs, service map, and latency metrics — no extra tools needed.

🌍
Multi-Cluster

Cluster Mesh connects pods across clusters — direct pod-to-pod, encrypted.

Understanding "Why" Matters on the CCA

The CCA exam tests your understanding of why Cilium uses eBPF instead of iptables. Key concepts to internalize from this chapter:

  • Kubernetes Network Model — The 4 rules that every CNI must implement. Cilium implements them via eBPF.
  • CNI Interface — How kubelet invokes CNI plugins. Cilium's CNI is a thin binary that delegates to the Cilium Agent.
  • iptables Limitations — Sequential O(n) rule matching vs eBPF O(1) hash lookups. This is the core argument for Cilium.
  • Stack Consolidation — Cilium replaces 4 separate tools (CNI, kube-proxy, service mesh, network policy engine) with ONE eBPF-powered agent.

1.1 The "Hello World" of K8s Networking

Imagine you've deployed anihpj (Django backend on port 8000) and PostgreSQL (database on port 5432) as two separate pods. They need to communicate. How does that actually work?

📖 The Kubernetes Network Model — 4 Fundamental Rules

Rule 1: Every Pod gets its OWN unique IP address — no NAT, no port mapping. Like every house has its own street address.

Rule 2: Pods on any node can communicate with ALL pods on ALL nodes WITHOUT NAT. Like being able to call any extension in any building.

Rule 3: Agents on a node (kubelet, daemons) can communicate with ALL pods on that node. Like the building manager can reach every desk.

Rule 4: Pods see their OWN IP as what other pods see — no "inside vs outside" confusion.

💡 These 4 rules define the "flat network" model. CNI plugins implement these rules differently. Cilium implements them with eBPF — the fastest way!

Pod-to-Pod on the SAME Node

Two pods on the same worker node communicate through a Linux bridge — just like two computers plugged into the same network switch. The Linux bridge (cbr0/cni0) acts as a virtual L2 switch connecting all pod veth interfaces.

1.2 The CNI (Container Network Interface) Explained

Think of CNI as the "network driver" for Kubernetes. Just like USB defines how devices connect, CNI defines how pods get network connectivity:

📖 CNI is a SPECIFICATION, not software

CNI defines 4 operations that a plugin must implement:

ADD: "Give this container a network!" → Allocates IP, creates veth pair, sets routes

DEL: "Remove this container's network!" → Releases IP, removes veth, cleans up

CHECK: "Is this container's network healthy?" → Verifies connectivity

VERSION: "What CNI spec version do you support?"

💡 CNI plugins are BINARIES on the node filesystem. kubelet executes them directly — no daemon needed!

CNI Flow — kubelet → CRI → CNI Plugin
  ① kubelet watches API Server → "New pod assigned: anihpj-abc123"
       │
       ▼
  ② kubelet calls CRI (Container Runtime) → "Start container: anihpj:v2"
       │
       ▼
  ③ containerd creates container (NO network yet! 😱)
       │
       ▼
  ④ kubelet calls CNI: /opt/cni/bin/cilium-cni ADD <config>

3.1 eBPF Explained Simply — "A Safe Sandbox Inside the Linux Kernel"

The best way to understand eBPF is through an analogy: eBPF is like JavaScript for the Linux kernel. Just as JavaScript runs safely inside your browser sandbox without crashing your operating system, eBPF programs run safely inside the Linux kernel with ZERO risk of crashing it.

The "e" in eBPF stands for "extended" — it evolved from classic BPF (Berkeley Packet Filter), which tcpdump has used since 1992 for packet filtering. The key insight: You can CHANGE how the kernel behaves — without changing kernel source code, loading kernel modules, or rebooting!

📖 Key Term: eBPF (extended Berkeley Packet Filter)

eBPF allows you to run SANDBOXED programs in the Linux kernel WITHOUT:

❌ Changing kernel source code

💡 Why the Verifier Matters (CCA Exam Key Point)

The eBPF verifier is what makes eBPF safe for production use. It mathematically proves that your program: (1) always terminates (no infinite loops), (2) never accesses memory out of bounds, (3) never dereferences NULL pointers, and (4) executes at most 1 million instructions. If ANY check fails, the program is REJECTED — the kernel refuses to load it. This is why eBPF can't crash your kernel, unlike traditional kernel modules.

🔄 eBPF Lifecycle — Layman's Terms (for anihpj)

① Write: You write a small C program that says "if port is 5432, drop the packet." ② Compile: clang turns it into eBPF bytecode. ③ Verify: The kernel's safety checker proves this program won't crash anything. ④ JIT: Bytecode is converted to native CPU instructions (x86/ARM). ⑤ Attach: You hook it to the TC (Traffic Control) layer. ⑥ Execute: Now EVERY packet passing through TC runs your program at native speed — for anihpj, every Django request and PostgreSQL query is checked in ~5 microseconds. ⑦ Communicate: Results (drop/allow, byte counts) are written to eBPF Maps — userspace (Cilium Agent, Hubble) reads them.

Q1
What is the eBPF verifier and what 5 things does it check?
Show Answer
Answer

The verifier checks: 1) No infinite loops (must terminate), 2) No out-of-bounds memory access, 3) Valid pointers (no NULL dereferences), 4) Maximum 1 million instructions, 5) All code paths reachable. The verifier mathematically proves these properties by simulating all possible execution paths.

Explanation

The verifier is what makes eBPF safe for production. Without it, eBPF programs could crash the kernel like traditional kernel modules. The CCA exam expects you to explain WHY eBPF is safer than kernel modules — the verifier is the answer.

Q2
Name 5 eBPF hook points from earliest to latest in the network stack. Which one does Cilium primarily use?
Show Answer
Answer

1) XDP (NIC driver — earliest, before SKB allocation), 2) TC Ingress (after XDP, before kernel stack), 3) TC Egress (outbound), 4) Socket hooks (per-socket), 5) kprobe/tracepoint (any kernel function). Cilium primarily uses TC hooks because they have full pod context (identity, labels, policy).

Explanation

Cilium specifically uses TC (Traffic Control) hooks, not XDP, because XDP is too early in the pipeline — it doesn't have access to pod identity information stored in eBPF maps. TC hooks have the right balance of speed and context.

Q3
How do eBPF programs communicate with userspace? Name 3 map types used by Cilium.
Show Answer
Answer

eBPF programs communicate with userspace exclusively through eBPF Maps — shared key-value data structures in kernel memory accessible via bpf() syscalls. Cilium uses: 1) BPF_MAP_TYPE_HASH (pod IP → identity), 2) BPF_MAP_TYPE_LRU_HASH (connection tracking), 3) BPF_MAP_TYPE_RINGBUF (Hubble flow events).

Q4
Why is an eBPF hash lookup O(1) while iptables is O(n)?
Show Answer
Answer

iptables stores rules as a linked list (chain) — each packet must walk through rules sequentially until a match is found. eBPF uses a hash table — the key (e.g., IP:port) is hashed to directly find the matching rule in constant time, regardless of how many rules exist.

Explanation

This is the core architectural difference. At 10,000 services, iptables does 10,000+ sequential checks per new connection. eBPF does ONE hash lookup. This is why Cilium exists — iptables literally cannot handle modern Kubernetes scale.

Q5
What does JIT compilation do for eBPF programs and why does it matter?
Show Answer
Answer

JIT (Just-In-Time) compilation converts eBPF bytecode into native x86/ARM machine instructions that run directly on the CPU. Without JIT, eBPF bytecode would be interpreted instruction-by-instruction (much slower). JIT compilation gives eBPF near-native performance.

Q6
Why can't you have an infinite loop in an eBPF program?
Show Answer
Answer

The eBPF verifier mathematically proves program termination by checking that all code paths are acyclic (no backward jumps that could create loops). It also enforces a maximum of 1 million instructions. Infinite loops in kernel space would hang the entire system — so the verifier prevents them entirely.

Q7
At which hook point does Cilium primarily attach its eBPF programs and why not XDP?
Show Answer
Answer

Cilium uses TC (Traffic Control) hooks. XDP is too early — it runs before the kernel allocates the SKB, so it has no access to pod identity, labels, or policy information stored in eBPF maps. TC hooks provide the right balance: very fast (near line rate) with full pod context.

Q8
What happens if the eBPF verifier rejects your program?
Show Answer
Answer

The kernel refuses to load the program. The bpf() syscall returns an error with a verifier log explaining what failed. The program is never executed — preventing any potential kernel crash. Developers must fix the issue and recompile. This is a safety feature, not a bug.

What's the difference between tunnel mode and direct routing in Cilium?
Show Answer
Answer

The Cilium Agent updates the IP→Identity eBPF map with the new IP. The policy rules (based on identities, not IPs) remain valid.

5.1 Prerequisites Check — Is Your Cluster Ready for Cilium?

Before installing Cilium, verify these requirements on EVERY node. Each requirement exists for a specific reason — skipping one leads to silent failures that are hard to debug later.

Why Kernel ≥ 5.10? Cilium relies on eBPF programs running inside the Linux kernel. Kernel 5.10 (released December 2020) was the first LTS kernel with mature eBPF support for networking. Kernels before 5.4 have limited eBPF capabilities and missing helper functions. The newer your kernel (5.15+, 6.1+), the more eBPF features Cilium can use — including faster maps, better verifier performance, and more program types. If you're on an older kernel, Cilium will fall back to a limited mode or refuse to start.

Why remove old CNI? You CANNOT run two CNI plugins simultaneously. Both will try to assign IP addresses to pods, manage network interfaces, and program routing tables. The result: IP conflicts, routing loops, and pods stuck in ContainerCreating. Always remove Calico, Flannel, Weave, or any other CNI before installing Cilium.

Why ≥ 4GB RAM? Cilium's eBPF maps live in kernel memory — each pod's identity, policy rules, and connection tracking state consume memory. With many pods, these maps can grow to hundreds of megabytes. The Cilium agent itself also needs memory for its control plane (gRPC, Hubble, policy computation). 4GB is the minimum; for production clusters with 100+ pods, plan for 8GB+ per node.

6.3 cilium monitor — Your Real-Time Packet Detective

cilium monitor is Cilium's built-in packet sniffer that shows you exactly what's happening to network traffic in real time — at the eBPF level. Unlike tcpdump which shows all packets, cilium monitor shows you Cilium's decisions about each packet: was it FORWARDED (allowed), DROPPED (denied by policy), or AUDIT (logged but not blocked)? Each entry includes the pod name, identity, port, and the specific policy rule that matched.

When to use it: Any time a pod can't connect to another pod or service. cilium monitor will tell you within seconds whether the packet was dropped by a policy, dropped by routing, or forwarded successfully. This eliminates hours of guesswork. The key filter is --type drop which shows only denied traffic — in a busy cluster, the unfiltered output is overwhelming.

7.1 Why Network Policies Matter — The "Zero Trust" Mentality

Default Kubernetes: ALL pods can talk to ALL pods — no isolation, no segmentation. A compromised pod can attack anything. Network Policies change this to a zero-trust model:

🚨 The Default K8s Networking Model is Dangerous

Kubernetes was designed with a "flat network" philosophy — every pod gets an IP, and every pod can reach every other pod across all namespaces. This was intentional for simplicity, but it means that if an attacker compromises any single pod in your cluster, they can reach every other pod — databases, internal APIs, monitoring systems, everything. This is the equivalent of having no locks on any door in an apartment building.

Zero Trust networking flips this model: "Never trust, always verify." Instead of assuming pods are safe because they're inside the cluster, you assume every connection could be malicious and explicitly define what's allowed. Everything else is denied. This is the fundamental shift that Network Policies enable.

🏢 The Apartment Building Analogy

Without policies (default K8s): An apartment building where every door is unlocked. Anyone can walk into anyone else's apartment — the mailman, a delivery person, a stranger off the street. If one apartment gets broken into, the thief has access to ALL apartments.

With Network Policies: Each apartment has a lock, and you give keys ONLY to people who need access. The mailman has a key to the lobby (ingress:80). The building manager has keys to the utility room (monitoring:9090). Your neighbor does NOT have a key to your apartment. And if someone breaks into one apartment, they can't reach any others because every door is locked by default.

For anihpj specifically: Your Django application has three tiers — a frontend nginx (public-facing), a backend Django (internal API + admin), and a PostgreSQL database (stores all data). Without policies, a compromised nginx pod could directly access the database. With policies, nginx can only reach Django on port 8000, and only Django can reach PostgreSQL on port 5432. This is called defense in depth — even if one layer is breached, the attacker is contained.

🔑 The Four Principles of Zero Trust Networking

1. Default Deny: Start by blocking everything. Then explicitly allow only what's needed.

2. Least Privilege: Give each pod ONLY the access it needs to do its job. No more.

3. Micro-Segmentation: Divide your cluster into small, isolated segments. Each segment has its own rules.

4. Assume Breach: Design policies assuming an attacker is already inside. Limit their lateral movement.

🔹 L3/L4 Rules — What K8s NetPol Covers

L3 = IP addresses and CIDR ranges (e.g., 10.0.0.0/8). L4 = TCP/UDP ports (e.g., :5432). K8s NetworkPolicy can say "allow traffic from namespace X on port 5432" — but it cannot inspect what's inside the packet. It doesn't know if it's HTTP, gRPC, DNS, or Kafka. This is the fundamental limitation that Cilium solves.

# K8s NetPol can only do THIS:
ingress:
  - from:
      - podSelector:
          matchLabels:
            app: anihpj
    ports:
      - port: 5432
        protocol: TCP
# ❌ Cannot say: "...but only GET /api/"
🔹 L7 Protocol-Aware Rules — Cilium's Superpower

Cilium's eBPF programs can parse application protocols at the kernel level — HTTP methods, paths, headers; gRPC methods; Kafka topics; DNS queries. This means you can write rules like "allow GET /api/v1 but block POST /admin" — something impossible with K8s NetPol.

# Cilium CNP can do THIS (impossible with K8s NetPol):
ingress:
  - toPorts:
      - ports:
          - port: "8000"
        rules:
          http:
            - method: "GET"         # ← L7! Kernel-level HTTP parsing
              path: "/api/v1/"      # ← URL path matching
            - method: "POST"
              path: "/admin/"
              headers:               # ← Header matching!
                - 'X-API-Key: secret'
🔹 Identity-Based Enforcement — The Core Design

K8s NetPol uses IP addresses for enforcement — pods get new IPs on restart, making rules fragile. Cilium assigns each pod a cryptographic identity based on its labels (e.g., app=anihpj, tier=backend). This identity survives pod restarts, IP changes, and node migrations. Cilium enforces policies based on who you ARE, not where you sit on the network.

7.3 Your First CiliumNetworkPolicy — Protect the Database

Scenario: In the anihpj application, only the Django backend pods should talk to PostgreSQL. The frontend nginx, monitoring tools, and any other pods have no business connecting directly to the database. If a pod gets compromised, the database should be the last thing an attacker can reach.

Why database protection is your #1 priority: The database contains ALL your application data — user accounts, job postings, payment information, everything. If an attacker reaches the database, they've won. That's why your first CNP should always protect the database. The rule is simple: only the pods that need the database can talk to it, and only on the database port.

Let's write this policy step by step. The policy says: "PostgreSQL pods (labeled app: postgres, component: database) should ONLY accept incoming TCP traffic on port 5432 from pods labeled app: anihpj, component: backend. Everything else is denied."

protect-postgres.yaml — CNP 
apiVersion: cilium.io/v2          # MUST be cilium.io/v2
kind: CiliumNetworkPolicy         # CNP (namespace-scoped)
metadata:
  name: protect-postgres
  namespace: anihpj               # Which namespace
spec:
  endpointSelector:               # WHICH PODS this applies to
    matchLabels:
      app: postgres               # → PostgreSQL pods (TARGET)
      component: database
  ingress:                        # INCOMING traffic rules
  - fromEndpoints:                # WHO can send traffic IN
    - matchLabels:
        app: anihpj               # → Only anihpj Django pods
        component: backend
    toPorts:                      # WHICH ports allowed
    - ports:
      - port: "5432"              # → Only PostgreSQL port
        protocol: TCP

💡 Everything NOT explicitly allowed → DENIED by default!
📖 The 4 Essential YAML Fields

endpointSelector: WHICH pods does this policy apply to? (the TARGET)

ingress: Rules for INCOMING traffic to the target pods.

egress: Rules for OUTGOING traffic from the target pods.

fromEndpoints/toEndpoints: WHO can send/receive traffic?

How Cilium Evaluates Network Policies — Rule Processing Order

Cilium checks policies in a specific priority order for EVERY packet. Understanding this is critical for the CCA exam:

  For EACH packet, Cilium checks in this order:

  ┌─────────────────────────────────────────────────────────────────┐
  │ 1. CNP (CiliumNetworkPolicy) — NAMESPACE-SCOPED               │
  │    ├── Checked FIRST (most specific wins)                       │
  │    ├── If CNP has a rule matching this traffic → USE IT         │
  │    │   (either ALLOW or DENY)                                   │
  │    └── If NO CNP rule matches → go to step 2                    │
  │                                                                  │
  │ 2. CCNP (CiliumClusterwideNetworkPolicy) — CLUSTER-WIDE       │
  │    ├── Checked SECOND (broader scope)                            │
  │    ├── If CCNP has a rule matching this traffic → USE IT         │
  │    └── If NO CCNP rule matches → go to step 3                    │
  │                                                                  │
  │ 3. Default DENY — CILIUM'S SECURE DEFAULT                       │
  │    ├── If NO policy matches → DENY the traffic                  │
  │    └── This is the "zero trust" default                          │
  └─────────────────────────────────────────────────────────────────┘

  KEY RULE: CNP OVERRIDES CCNP! Namespace policies take priority.
     More specific always wins over more general.

  EXAMPLE:
  Traffic: anihpj pod → postgres pod, port 5432
  1. Check CNP in namespace "anihpj":
     → "protect-postgres" CNP: ALLOWS anihpj→postgres:5432

  Traffic: external IP → postgres pod, port 5432
  1. Check CNP in namespace "anihpj":
     → "protect-postgres" CNP: only allows from anihpj label
     → NO MATCH (source doesn't have app=anihpj label)
  2. Check CCNP (cluster-wide): → NO CCNP matches
  3. Default DENY → DROP

7.4 Layer 7 Policies — HTTP-Aware Rules That Understand Your App

Cilium can inspect HTTP requests and enforce rules based on method, path, and headers — at the kernel level:

protect-django-admin.yaml — L7 CNP 
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: protect-django-admin
  namespace: anihpj
spec:
  endpointSelector:
    matchLabels:
      app: anihpj
  ingress:
  # RULE 1: Allow GET /jobs/ from ANY source
  - fromEndpoints:
    - {}                           # {} = ANY source
    toPorts:
    - ports:
      - port: "8000"
      rules:
        http:
        - method: "GET"            # ← L7! Cilium understands HTTP
          path: "/jobs/"           # ← Only this path!

  # RULE 2: Allow POST /admin/ ONLY from internal IPs
  - fromCIDR:
    - "10.0.0.0/8"                # Only internal network
    toPorts:
    - ports:
      - port: "8000"
      rules:
        http:
        - method: "POST"
          path: "/admin/"

💡 POST /admin/ from the internet → DROP at kernel level! 🔴

While Cilium's primary rate limiting is for API server protection, L7 HTTP header matching gives you fine-grained control over which requests reach your application — reducing load at the kernel level before the application even sees the traffic.

7.5 DNS-Based Policies — Allow Pods to Talk to Specific Domains

Cilium watches DNS requests and dynamically updates allowed IPs based on resolved FQDNs:

allow-egress-stripe.yaml — CNP with toFQDNs 
spec:
  endpointSelector:
    matchLabels:
      app: anihpj

7.6 Policy Audit Mode — Test Before You Enforce

NEVER enforce a policy immediately in production! Policy audit mode lets you observe what traffic would be blocked without actually blocking it. This is one of Cilium's most important safety features and a key CCA exam topic.

⚠️ The Golden Rule of Network Policies

ALWAYS audit before enforcing. A misconfigured policy can take down your entire application. Audit mode gives you a safety net — it logs violations but doesn't drop traffic. Run audit for at least 1-7 days before enforcing in production.

protect-postgres-audit.yaml — CNP with Audit 
apiVersion: cilium.io/v2

  name: protect-postgres

      app: postgres

    - matchLabels:
        app: anihpj
    toPorts:
    - ports:
      - port: "5432"

Chapter 8: CiliumClusterwideNetworkPolicy (CCNP) — Cluster-Level Rules

While CNPs are namespace-scoped, CCNPs apply across ALL namespaces. Think of CNPs as room-level locks — each namespace gets its own rules. CCNPs are building-level security — rules that apply to everyone, regardless of which room they're in. CCNPs are essential for cluster-wide concerns like blocking cloud metadata access, allowing monitoring across namespaces, and enforcing DNS security everywhere at once.

8.1 When You Need Cluster-Wide Policies

Use CCNP when you need rules that apply everywhere: block external access to kube-system, allow monitoring to scrape all namespaces, block metadata service access cluster-wide.

Why not just use CNPs everywhere? You could — but you'd need to create the same CNP in every single namespace, including future namespaces that don't exist yet. With a CCNP, you write the rule once and it automatically applies to all namespaces — present and future. This is especially important for security rules that should be universal, like blocking the cloud metadata endpoint (169.254.169.254) which is a common SSRF attack vector.

The priority rule is crucial: Cilium checks CNPs first, then CCNPs. This means a permissive CNP in one namespace can override a restrictive CCNP. For example, if a CCNP blocks all access to 169.254.169.254, but a CNP in the "untrusted" namespace explicitly allows it — the CNP wins. This is by design: more specific policies should have more control. But it also means you need to be careful — a single misconfigured CNP can punch a hole in your cluster-wide security.

💡 CNP vs CCNP Decision Rule

Use CNP when the rule is specific to one namespace (e.g., "protect the anihpj database"). Use CCNP when the rule applies cluster-wide (e.g., "block all pods from accessing 169.254.169.254 cloud metadata").

block-cloud-metadata.yaml — CCNP 
apiVersion: cilium.io/v2
kind: CiliumClusterwideNetworkPolicy  # ← CCNP (NOT CNP!)
metadata:
  name: block-cloud-metadata          # ← NO namespace field!
spec:                                 #    (applies cluster-wide)
  endpointSelector: {}                # ← {} = ALL pods in ALL namespaces
  egress:
  - toCIDR:
    - "169.254.169.254/32"           # Block cloud metadata IP
  # With NO allow rules, Cilium's default is DENY
  # → All egress to 169.254.169.254 is BLOCKED cluster-wide!

# Key differences from CNP:
#   1. kind: CiliumClusterwideNetworkPolicy (not CiliumNetworkPolicy)
#   2. NO namespace in metadata
#   3. Applies to ALL namespaces simultaneously
#   4. Checked AFTER CNP (CNP takes priority)

8.2 Real-World CCNP Scenarios for anihpj

Here are three CCNP scenarios you'll encounter in real production environments — each solves a problem that would be impractical with namespace-scoped CNPs alone.

🔴 CCNP 1: Block Cloud Metadata Access (SSRF Prevention)

Cloud providers expose a metadata service at 169.254.169.254 that returns sensitive credentials. A Server-Side Request Forgery (SSRF) attack tricks a pod into calling this endpoint, stealing IAM roles or API keys. Blocking this IP cluster-wide with a CCNP is a critical security control — one rule protects every pod in every namespace from this attack vector. The YAML for this is shown in section 8.1 above (block-cloud-metadata).

🟢 CCNP 2: Allow Monitoring Across All Namespaces

Prometheus needs to scrape /metrics endpoints on every pod. Without a CCNP, you'd have to create a CNP in every namespace allowing Prometheus access. Worse, when someone creates a new namespace, they'd forget to add the monitoring CNP — and their pods would be invisible to monitoring. A CCNP solves this elegantly: one rule, all namespaces, forever.

allow-monitoring.yaml — CCNP 
apiVersion: cilium.io/v2
kind: CiliumClusterwideNetworkPolicy
metadata:
  name: allow-monitoring
spec:
  endpointSelector: {}                # All pods in all namespaces
  ingress:
  - fromEndpoints:
    - matchLabels:
        app: prometheus               # Only Prometheus pods
        namespace: monitoring          # Only from monitoring namespace
    toPorts:
    - ports:
      - port: "9090"                  # Metrics port
        protocol: TCP

# This allows Prometheus (in monitoring namespace) to scrape
# /metrics on port 9090 from ALL pods in ALL namespaces.
# Without this CCNP, you'd need a CNP in EVERY namespace!
🟡 CCNP 3: DNS Allowlist — Prevent DNS Data Exfiltration

DNS tunneling is a technique where attackers encode stolen data into DNS queries to bypass egress controls. By restricting ALL pods to only use the cluster's internal CoreDNS (and blocking external DNS servers like 8.8.8.8), you prevent this attack vector. Combined with a CNP that uses toFQDNs to allow only specific approved external domains, you create a complete DNS security posture. Pods can resolve internal services and approved external APIs — but nothing else.

dns-allowlist.yaml — CCNP 
apiVersion: cilium.io/v2
kind: CiliumClusterwideNetworkPolicy
metadata:
  name: dns-allowlist
spec:
  endpointSelector: {}                # All pods
  egress:
  # Only allow DNS to trusted resolvers
  - toEndpoints:
    - matchLabels:
        "k8s:app": kube-dns          # Allow CoreDNS
    toPorts:
    - ports:
      - port: "53"
        protocol: UDP
  # Block DNS to ANY other destination
  - toFQDNs: []                        # Empty = block all external DNS

# This prevents DNS tunneling/data exfiltration — pods can only
# use the cluster's internal CoreDNS, not external DNS servers.
# Combined with a CNP that allows specific toFQDNs for approved
# external domains, this creates a complete DNS security posture.

10.3 Enabling Mutual TLS (mTLS) for anihpj

Mutual TLS (mTLS) means BOTH sides of a connection prove their identity with certificates — the client verifies the server AND the server verifies the client. Cilium automates certificate issuance and rotation using cert-manager or its built-in SPIFFE-based certificate authority:

cilium-config — Enable mTLS 
# Enable mTLS cluster-wide with one flag:
cilium install --set encryption.enabled=true \
               --set encryption.type=wireguard \
               --set authentication.mutual.spire.enabled=true

# Or patch an existing installation:
cilium config set authentication-mutual-spire-enabled true

# Verify mTLS is working:
cilium status | grep Authentication
# → Authentication: OK (SPIFFE)
🔐 How Cilium mTLS Works — 4 Steps

1. Identity Provisioning: SPIFFE assigns each pod a cryptographic identity based on its labels (e.g., spiffe://cluster.local/ns/anihpj/sa/default).

2. Certificate Issuance: Cilium's SPIRE agent automatically issues short-lived X.509 certificates to each pod.

3. Automatic Rotation: Certificates are rotated before expiry — no pod restarts, no application changes.

4. eBPF Enforcement: The eBPF socket program performs the TLS handshake at the kernel level. Application code doesn't change — it still calls connect("postgres", 5432).

11.1 How kube-proxy Works (and Why It's Slow)

kube-proxy watches the Kubernetes API for Services and Endpoints, then programs iptables rules on every node to implement load balancing. The problem: iptables rules are evaluated sequentially — every packet must walk through every rule until it finds a match:

📖 A simple analogy: Imagine a security guard checking IDs at a building with 5000 employees. With iptables (O(n)), the guard checks each person against a list of 5000 names — one by one — until finding a match. With eBPF (O(1)), the guard has a lookup table — "Bob → desk 42" — and finds the answer instantly, regardless of how many employees there are. Now imagine doing this for every single packet — millions per second. That's why iptables doesn't scale and eBPF does.

kube-proxy iptables — O(n) Rule Walking

       ▼
  ┌─────────────────────────────────────────────┐
  │  iptables nat PREROUTING chain               │
  │  ┌─────────────────────────────────────────┐ │
  │  │ RULE 1:   dst 10.96.0.10:53 → DNS ❌    │ │
  │  │ RULE 2:   dst 10.96.0.1:443 → API ❌    │ │
  │  │ RULE 3:   dst 10.96.42.100:8000 → ✅    │ │
  │  │ ...                                       │ │
  │  │ RULE 5000: dst 10.96.99.50:9090 → ❌     │ │
  │  └─────────────────────────────────────────┘ │
  │                                               │
  │  😱 5000 rules × every packet = SLOW          │

11.2 Cilium's eBPF Load Balancer — How It Replaces kube-proxy

Cilium's eBPF load balancer operates at the socket level, before packets even enter the TCP/IP stack. Services are stored in eBPF hash maps — lookup is O(1) regardless of how many services you have. Maglev consistent hashing ensures even backend distribution and connection affinity:

🔑 Maglev Hashing — Why It Matters

Maglev is a consistent hashing algorithm developed by Google. It ensures: (1) Backend changes only affect ~1/N of connections (not all), (2) Connections to the same 5-tuple always go to the same backend (affinity), (3) Load is evenly distributed across backends. When a backend pod dies, only its connections are rehashed — all other connections remain undisturbed.

📡 How Cilium Handles Each Service Type

ClusterIP: eBPF socket-level NAT — connect() syscall is intercepted and destination IP:port is rewritten before the packet enters the TCP stack. No iptables, no netfilter.

NodePort: eBPF programs attached to the host network namespace intercept packets arriving at the NodePort. The packet is DNAT'd to the backend pod — all in kernel eBPF.

ExternalIPs: eBPF programs answer ARP requests for the external IP and route incoming traffic to backend pods. Combined with BGP, this provides full external load balancing.

12.1 What is BGP? (Border Gateway Protocol — The Internet's Routing Protocol)

BGP (Border Gateway Protocol) is how the internet routes traffic between networks. Think of it as GPS for network packets — routers use BGP to tell each other "I know how to reach IP range X." Cilium uses BGP to tell your physical network "Service IP 192.168.1.100 can be reached through this Kubernetes node."

12.2 Cilium BGP Configuration

Cilium uses the CiliumBGPPeeringPolicy CRD to configure BGP peers. This tells Cilium which routers to peer with and which Service IPs to announce:

bgp-peering-policy.yaml 
apiVersion: cilium.io/v2alpha1
kind: CiliumBGPPeeringPolicy
metadata:
  name: upstream-routers
spec:
  nodeSelector:
    matchLabels:
      kubernetes.io/os: linux
  virtualRouters:
  - localASN: 65001              # Your AS number
    exportPodCIDR: true           # Announce pod IPs too
    serviceSelector:
      matchExpressions:
      - key: somekey
        operator: NotIn
        values: ["never-match"]
    neighbors:
    - peerAddress: "10.0.0.1/32" # Upstream router IP
      peerASN: 65000              # Router's AS number

# What Cilium can advertise via BGP:
#   ✅ LoadBalancer IPs (external access)
#   ✅ ClusterIP ranges (internal service reachability)
#   ✅ Pod CIDRs (direct pod access from outside)
#   ❌ Not for: cloud envs (EKS/GKE/AKS handle this natively)
🌐 BGP Configuration Essentials

localASN: Your private AS number (64512-65534 for private use).

peerAddress: Upstream router IP that Cilium peers with.

peerASN: The router's AS number.

exportPodCIDR: Set to true if you want external access directly to pod IPs (advanced).

serviceSelector: Controls which Service IPs are advertised. Use label selectors to be selective.

16.1 Why Encrypt Pod Traffic?

In a default Kubernetes cluster, pod-to-pod traffic travels in plain text over the network. Anyone with access to the physical network (a compromised switch, a rogue network admin, a misconfigured VLAN) can sniff database passwords, API keys, and user data.

📬 Think of encryption like sending a sealed envelope vs a postcard: Without WireGuard, your pod traffic is like a postcard — anyone handling it along the way can read the contents (passwords, API keys, user data). With WireGuard, every packet is sealed in an unbreakable envelope — only the intended recipient can open it. And the best part? Your application doesn't even know the envelope exists — it just sends the postcard as usual, and Cilium seals it at the kernel level.

Encryption provides three critical benefits:

Without vs With WireGuard Encryption
  WITHOUT ENCRYPTION                  WITH WIREGUARD
  anihpj ── plain text ──▶ postgres  anihpj ──🔒 encrypted──▶ postgres
  😱 Anyone can sniff                ✅ Data is unreadable
     "SELECT * FROM users"              on the wire
     passwords visible!                 Even if network is compromised!

  🔧 APPLICATION CODE: UNCHANGED!
  Django still: connect("postgres", 5432)
  Cilium handles encryption transparently at the kernel level
📋 Why Encryption Matters — 3 Reasons

1. Defense in Depth: Network policies protect at L3/L4/L7. Encryption protects the data itself. If policies fail, data is still safe.

2. Compliance: HIPAA, PCI-DSS, and GDPR require data encryption in transit. WireGuard encryption satisfies these requirements.

3. Zero-Trust Networking: Assume the network is hostile. Encrypt everything. Trust nothing. Verify always.

16.2 WireGuard vs IPSec — Which Should You Choose?

💡 Recommendation: Use WireGuard unless you have specific hardware offload requirements. It's faster, simpler, and Cilium handles all key management automatically.

16.4 Node-to-Node Encryption — How Cross-Node Encryption Works

When pods are on different nodes, Cilium establishes a WireGuard tunnel between the nodes. Each node has a WireGuard key pair, and Cilium automatically distributes public keys to all other nodes:

  ┌─────────────────────────┐             ┌─────────────────────────┐

  │     │                    │             │     ▲                    │
  │     │ plaintext inside   │             │     │ plaintext inside   │
  │     │ the node           │             │     │ the node           │
  │     ▼                    │             │     │                    │
  │ Cilium eBPF intercepts   │             │ Cilium eBPF decrypts    │
  │     │                    │             │     │                    │

18.1 The Egress Problem — What IP Does Your Pod Use Externally?

🏢 Think of it like a large office building: Every desk (pod) has an internal extension number (10.0.1.5). When someone calls an external number (api.stripe.com), the office phone system replaces the internal extension with the building's main number (the node's IP). The external party sees the building's number — not the individual desk. Now imagine you need Stripe to whitelist your calls. Which number do you give them? The building number changes if you move desks (pod restarts on a different node). Egress Gateway solves this by routing all external calls through a dedicated reception desk with a fixed, permanent phone number.

By default, when a pod calls an external API, Kubernetes performs SNAT (Source NAT) — the pod's internal IP is replaced with the node's IP. This creates two problems:

Default Egress vs Egress Gateway
  DEFAULT (SNAT to Node IP):
  anihpj pod → Node IP (10.0.0.1) → api.stripe.com
  ❌ Node IP changes if pod moves to different node
  ❌ Different pods on different nodes → different IPs
  ❌ Can't whitelist at the API side

  WITH EGRESS GATEWAY:
  anihpj pod → Gateway Node (192.168.1.100) → api.stripe.com
  ✅ Fixed, predictable IP regardless of pod location
  ✅ All anihpj pods egress through the same gateway
  ✅ Whitelist 192.168.1.100 at stripe.com once!

18.2 Cilium Egress Gateway — Fixed IP for Outbound Traffic

egress-gateway-policy.yaml 
apiVersion: cilium.io/v2
kind: CiliumEgressGatewayPolicy
metadata:
  name: anihpj-stripe-egress
spec:
  selectors:
  - podSelector:
      matchLabels:
        app: anihpj              # Apply to anihpj pods
  destinationCIDRs:
  - "54.187.0.0/16"             # Stripe's IP range
  egressGateway:
    nodeSelector:
      matchLabels:
        egress: gateway           # Gateway node label
    egressIP: "192.168.1.100"    # Fixed egress IP

# Now all anihpj → Stripe traffic exits through
# 192.168.1.100 — a fixed, whitelistable IP!

20.1 Domain 1: Architecture & Concepts (30%) — 20 Questions

Architecture Practice Questions

Q1
What makes eBPF safe for production kernel use?
Show Answer
Answer

The eBPF verifier — it mathematically proves programs always terminate, never access memory out of bounds, and execute at most 1M instructions. Unsafe programs are rejected before loading.

Q2
Which Cilium component runs as a DaemonSet?
Show Answer
Answer

The Cilium Agent — one per node. The Operator runs as a Deployment (cluster-wide tasks like IPAM).

Q3
How does Cilium assign identities to pods?
Show Answer
Answer

Based on pod labels. All pods with the same set of labels get the same numeric identity. The CiliumIdentity CRD stores this mapping.

Q4
What is the difference between CNP and CCNP?
Show Answer
Answer

CNP (CiliumNetworkPolicy) is namespace-scoped. CCNP (CiliumClusterwideNetworkPolicy) applies cluster-wide across all namespaces. CNP takes priority over CCNP.

Q5
What CRDs does Cilium create on installation?
Show Answer
Answer

9 CRDs including CiliumNetworkPolicy, CiliumClusterwideNetworkPolicy, CiliumEndpoint, CiliumIdentity, CiliumNode, CiliumBGPPeeringPolicy, and others.

Q6
What is the eBPF datapath? Why is it faster than iptables?
Show Answer
Answer

The eBPF datapath processes packets directly in the kernel at the lowest hook points (XDP, TC). Unlike iptables which processes rules sequentially (O(n)), eBPF uses hash maps for O(1) lookups — making it up to 587x faster with 10,000 rules.

Q7
What is a CiliumEndpoint? How is it different from a Kubernetes Endpoint?
Show Answer
Answer

A CiliumEndpoint (CEP) is a CRD representing each pod's networking state — its identity, IP, policy enforcement status, and eBPF map references. Kubernetes Endpoints just list pod IP:port pairs for Services. CEP is much richer, tracking per-pod security state.

Q8
What happens when a pod with identity 12345 restarts and gets a new IP?
Show Answer
Answer

The pod keeps identity 12345 (based on labels). All existing policies referencing identity 12345 continue working — no policy updates needed. The new IP is mapped to the same identity. This is why identity-based policies are so powerful.

Q9
What kernel hooks does Cilium use for networking?
Show Answer
Answer

XDP (earliest hook, before SKB allocation), TC ingress/egress (traffic control), socket layer (connect/accept), and cgroup hooks (socket-level enforcement). XDP is the fastest since it processes packets before the kernel allocates memory.

Q10
What is the Cilium Operator and why is it a Deployment, not a DaemonSet?
Show Answer
Answer

The Operator handles cluster-wide tasks: IPAM (allocating pod CIDRs), garbage collecting old CiliumIdentities, synchronizing with KVStore, and managing node heartbeats. It runs as a Deployment (usually 1-2 replicas) because it doesn't need to be on every node — it works at the cluster level.

20.2 Domain 2: Network Policy (20%) — 15 Questions

Network Policy Practice Questions

Q1
What does {} mean in fromEndpoints?
Show Answer
Answer

ALLOW FROM ANY SOURCE — all pods, all namespaces, all CIDRs. Use for public endpoints like frontend. Never use for databases.

Q2
How does toFQDNs work in a CiliumNetworkPolicy?
Show Answer
Answer

Cilium watches DNS responses, caches resolved IPs for the FQDN, and dynamically adds them to the allowed egress eBPF map. When DNS TTL expires, IPs are removed.

Q3
What is policy audit mode?
Show Answer
Answer

Audit mode (enableAudit: true) LOGS policy violations but does NOT block traffic. Use it to observe what WOULD be blocked before enforcing.

Q4
Which takes priority: CNP or CCNP?
Show Answer
Answer

CNP (namespace-scoped) takes priority over CCNP (cluster-wide). More specific wins over more general.

Q5
Why must you always allow DNS (UDP 53) in egress policies?
Show Answer
Answer

Pods need DNS to resolve service names and external domains. Without it, pods can't discover services. Always add egress UDP 53 to CoreDNS.

Q6
What is the difference between toPorts and toServices in CNP?
Show Answer
Answer

toPorts filters by port number and protocol (L3/L4). toServices maps to Kubernetes Services by name, allowing Cilium to enforce policy at the service level rather than individual pods. toServices survives pod IP changes automatically.

Q7
What is a CiliumClusterwideNetworkPolicy? When would you use it?
Show Answer
Answer

CCNP applies across ALL namespaces in the cluster. Use it for: (1) Monitoring/security tools that need cluster-wide access, (2) Default-deny-all baseline policies, (3) DNS policies that apply everywhere. CNP takes priority over CCNP.

Q8
How do you write a policy that allows HTTP GET to /api/v1 but blocks POST/PUT/DELETE?
Show Answer
Answer

Use L7 rules with toPorts.rules.http: - method: GET; path: /api/v1/.*. Only GET is allowed to that path. POST/PUT/DELETE are implicitly denied (default deny behavior). The policy must also include the standard toPorts for the TCP port.

Q9
What happens when two CNPs select the same pod with conflicting rules?
Show Answer
Answer

Rules are UNIONED — the pod gets the MOST permissive combination. If Policy-A allows port 80 and Policy-B allows port 443, the pod gets both. This is different from firewalls where last rule wins.

Q10
How does Cilium handle DNS-based egress policies differently from IP-based?
Show Answer
Answer

With toFQDNs, Cilium watches DNS responses and dynamically populates the egress eBPF map with resolved IPs. When DNS TTL expires, old IPs are removed and new ones added on the next DNS query. This means policies automatically track changing IPs without manual updates — unlike IP-based rules that break when IPs change.

20.3 Domain 3: Service Mesh & LB (20%) — 15 Questions

Service Mesh Practice Questions

Q1
How much RAM does Cilium's sidecar-less mesh add per pod?
Show Answer
Answer

Zero (0 MB). eBPF programs run in the kernel — no sidecar container, no proxy process, no extra memory.

Q2
What flag enables kube-proxy replacement?
Show Answer
Answer

--set kubeProxyReplacement=true during cilium install.

Q3
What is Maglev hashing used for?
Show Answer
Answer

Consistent hashing for service load balancing. Ensures even backend distribution, connection affinity, and minimal disruption when backends change.

Q4
How does Cilium handle canary deployments?
Show Answer
Answer

Identity-based traffic splitting. Pods with different labels get different identities. eBPF load balancers split traffic by identity — no sidecar needed.

Q5
What CRD configures BGP peering?
Show Answer
Answer

CiliumBGPPeeringPolicy (apiVersion: cilium.io/v2alpha1).

Q6
What is the difference between Cilium's mTLS and Istio's mTLS?
Show Answer
Answer

Cilium's mTLS uses the kernel's eBPF + WireGuard/IPSec — no sidecar, no Envoy proxy. Istio uses sidecar Envoy proxies for mTLS. Cilium's approach is lower latency (no userspace proxy hop), lower resource usage, and transparent to applications.

Q7
What is an Ingress resource vs CiliumIngressClass? How do they relate?
Show Answer
Answer

Ingress is the standard K8s resource for HTTP routing. CiliumIngressClass is a custom IngressClass that tells the cluster to use Cilium's built-in Envoy-based ingress controller instead of nginx/traefik. No separate ingress controller deployment needed.

Q8
How does Cilium implement L7 load balancing (HTTP/gRPC)?
Show Answer
Answer

Cilium embeds a minimal Envoy proxy (per-node, not per-pod) for L7 processing. eBPF redirects traffic to the local Envoy on the same node, which handles HTTP/gRPC routing, retries, timeouts, and rate limiting. The application pod never sees Envoy — it's transparent.

Q9
What is the difference between DSR and SNAT for Service load balancing?
Show Answer
Answer

DSR (Direct Server Return): Backend pod responds directly to the client, bypassing the load balancer on the return path. Faster, but requires special network setup. SNAT: Load balancer rewrites source IP to its own, so return traffic comes back through it. Simpler but adds a bottleneck. Cilium supports both modes.

Q10
What replaces kube-proxy when kubeProxyReplacement is enabled?
Show Answer
Answer

eBPF programs attached to each node's network devices handle Service ClusterIP translation, NodePort, ExternalIPs, and LoadBalancer services. Maglev consistent hashing distributes traffic. The eBPF socket-level load balancer handles connect() syscall redirection, eliminating the iptables DNAT hop entirely.

Observability Practice Questions

Q1

hubble observe --verdict DROPPED

Q2
What is Hubble Relay?
Show Answer
Answer

A cluster-wide deployment that aggregates flow data from all Cilium agents. CLI and UI connect to Relay for a unified view.

Q3
What Hubble metrics are available?
Show Answer
Answer

Flow (TCP), HTTP (L7), DNS, TCP flags, ICMP, and Drop (policy denies). Enable with hubble.metrics.enabled.

How do you access Hubble UI?

Q5
What does Hubble show that tcpdump doesn't?
Show Answer
Answer

Pod names, namespaces, Kubernetes identities, policy verdicts, HTTP methods/paths, DNS queries, and the specific policy rule that matched.

Q6
How do you filter Hubble flows to show only HTTP traffic from a specific pod?
Show Answer
Answer

hubble observe --from-pod namespace/podname --protocol http or use --from-label app=frontend --http-method GET. Combine with --verdict FORWARDED or --verdict DROPPED for policy troubleshooting.

Q7
What is the Hubble Service Map and how is it generated?
Show Answer
Answer

The Service Map is a real-time dependency graph in Hubble UI showing which services talk to which. It's built from Hubble flow data — each flow between identities becomes an edge in the graph. Green edges = allowed, red edges = dropped, thickness = traffic volume.

Q8
How do you integrate Hubble metrics with Prometheus?
Show Answer
Answer

Enable with hubble.metrics.enabled and configure which metrics to expose. Cilium agents expose a /metrics endpoint. Use a Prometheus ServiceMonitor or PodMonitor to scrape. Common metrics: hubble_flows_processed_total, hubble_tcp_flags_total, hubble_http_requests_total.

Q9
What's the difference between cilium monitor and hubble observe?
Show Answer
Answer

cilium monitor shows raw eBPF events from a SINGLE node — packet-level debugging. hubble observe shows cluster-wide flow data aggregated through Hubble Relay — higher-level, policy-aware, with pod names and verdicts. Use monitor for low-level debugging, hubble for operational visibility.

Q10
How can you troubleshoot why a pod can't reach an external API?
Show Answer
Answer

Step 1: hubble observe --from-pod ns/pod --verdict DROPPED to see if a policy is blocking it. Step 2: Check cilium policy get for the pod's namespace. Step 3: Verify DNS resolution: hubble observe --from-pod ns/pod --to-port 53. Step 4: Check egress gateway and toFQDNs policies if configured.

Appendix B: Cilium YAML Templates

Ready-to-use YAML templates for common Cilium configurations. CCA Exam Tip: You won't be asked to write YAML from scratch, but you WILL be asked "what does this policy do?" — understand each field's purpose!

B.1 Basic Allow — Ingress from Same Namespace

Allows pods with app: frontend to reach app: backend on port 8000. All other traffic is denied.

YAML
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: allow-same-ns
  namespace: anihpj
spec:
  endpointSelector:
    matchLabels:
      app: backend
  ingress:
  - fromEndpoints:
    - matchLabels:
        app: frontend
    toPorts:
    - ports:
      - port: "8000"
        protocol: TCP
🧩 What Each Field Does (Novice Friendly!)

endpointSelector — "WHO does this policy protect?" Here it protects pods labeled app: backend. Think of it as the "target" of the policy.

ingress — "WHO can talk TO the protected pods?" Inbound traffic rules. (Egress would be "where can protected pods send traffic OUT to?")

fromEndpoints — "Which OTHER pods are allowed in?" Here only pods with app: frontend. Empty {} means "anyone."

toPorts — "On which ports can they connect?" Here only TCP port 8000 is open. Without this, even allowed pods can't actually reach the app!

B.2 L7 HTTP Rules — Allow Only GET to /api/v1

L7 filtering: only HTTP GET requests to /api/v1/* paths are allowed. POST/PUT/DELETE blocked. Regex path matching.

YAML
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: l7-api-get-only
  namespace: anihpj
spec:
  endpointSelector:
    matchLabels:
      app: backend
  ingress:
  - fromEndpoints:
    - matchLabels:
        app: frontend
    toPorts:
    - ports:
      - port: "8000"
        protocol: TCP
      rules:
        http:
        - method: GET
          path: "/api/v1/.*"
💡 L7 vs L3/L4 — The Novice Distinction

L3/L4 (B.1): Only cares about IP addresses and port numbers — "You can knock on port 8000." Simple, fast, but dumb.

L7 (B.2): Reads the actual HTTP request — "You can knock on port 8000, but ONLY with a GET to /api/v1/*." Smarter, but needs Envoy proxy. The rules.http section is nested UNDER toPorts — you must still specify the TCP port FIRST, then add HTTP rules on top.

CCA Exam Pattern: If a question mentions "HTTP method," "path," "headers," or "gRPC" → it's an L7 question. Look for rules: in the YAML.

B.3 DNS-Based Egress — Allow Only api.github.com

Egress policy: first rule allows DNS (UDP 53 to CoreDNS), second rule uses toFQDNs to only allow HTTPS to api.github.com. DNS is a prerequisite!

YAML
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata:
  name: allow-github-api
  namespace: anihpj
spec:
  endpointSelector:
    matchLabels:
      app: backend
  egress:
  - toEndpoints:
    - matchLabels:
        io.kubernetes.pod.namespace: kube-system
        k8s-app: coredns
    toPorts:
    - ports:
      - port: "53"
        protocol: UDP
  - toFQDNs:
    - matchName: api.github.com
    toPorts:
    - ports:
      - port: "443"
        protocol: TCP
⚠️ The #1 CCA Mistake: Forgetting DNS!

If you restrict egress but DON'T allow DNS (UDP 53), NOTHING WORKS. Why? Because pods need to resolve domain names before they can connect. Even toFQDNs: api.github.com needs DNS to find the IP addresses.

Rule of thumb: Every egress policy MUST start with a DNS rule allowing UDP 53 to CoreDNS (kube-system). Without it, toFQDNs rules will silently fail because the pod can't look up the domain.

CCA Exam Pattern: If you see a policy with toFQDNs but NO DNS rule → it's broken. The exam WILL test this!

B.4 Default Deny All — Cluster-Wide Baseline

CCNP with empty endpointSelector: {} matches ALL pods. Empty ingress: [] and egress: [] means deny everything. The strongest baseline.

YAML
apiVersion: cilium.io/v2
kind: CiliumClusterwideNetworkPolicy
metadata:
  name: default-deny-all
spec:
  endpointSelector: {}
  ingress: []
  egress: []
🔒 Zero-Trust Foundation — Apply This FIRST!

This is the most important policy you'll write. Think of it as locking ALL doors in a building before deciding which ones to unlock. Without it, any pod can talk to any other pod — that's the K8s default.

endpointSelector: {} — empty curly braces = "select EVERY pod in the entire cluster." No exceptions.

ingress: [] — empty list = "nobody can talk TO any pod." All incoming traffic rejected.

egress: [] — empty list = "no pod can talk OUT to anywhere." All outgoing traffic rejected.

After applying this: Every pod is completely isolated. You then apply B.1-B.3 type policies to selectively ALLOW needed traffic. This is called "default-deny, explicit-allow" — the gold standard of zero-trust security.

B.5 CCNP — Monitoring Access (Cluster-Wide Allow)

Cluster-wide policy allowing Prometheus/Grafana monitoring pods to scrape metrics from all pods on port 9090. Uses fromEndpoints with namespace + label selectors.

YAML
apiVersion: cilium.io/v2
kind: CiliumClusterwideNetworkPolicy
metadata:
  name: allow-monitoring
spec:
  endpointSelector: {}
  ingress:
  - fromEndpoints:
    - matchLabels:
        app: prometheus
        io.kubernetes.pod.namespace: monitoring
    toPorts:
    - ports:
      - port: "9090"
        protocol: TCP
  - fromEndpoints:
    - matchLabels:
        app: grafana
        io.kubernetes.pod.namespace: monitoring
    toPorts:
    - ports:
      - port: "3000"
        protocol: TCP
🔭 Why CCNP? The "Cross-Namespace Exception" Pattern

After applying B.4 (default-deny-all), monitoring in the monitoring namespace is blocked from scraping metrics from pods in anihpj namespace. You need a CCNP to punch a cluster-wide hole.

Key difference from CNP: CCNP uses namespace + label together: io.kubernetes.pod.namespace: monitoring AND app: prometheus. This means "Prometheus pods from the monitoring namespace ONLY" — not just any pod named Prometheus.

Why two ingress rules? Prometheus scrapes on port 9090, Grafana needs port 3000. Each fromEndpoints block is independent — they're OR'd together (union semantics).

B.6 CiliumBGPPeeringPolicy

Configures BGP peering with an external router (ASN 65000). Cilium nodes with bgp: enabled label advertise Service LoadBalancer IPs via BGP.

YAML
apiVersion: cilium.io/v2alpha1
kind: CiliumBGPPeeringPolicy
metadata:
  name: bgp-peer-router
spec:
  nodeSelector:
    matchLabels:
      bgp: enabled
  virtualRouters:
  - localASN: 65001
    neighbors:
    - peerAddress: 10.0.0.1/32
      peerASN: 65000
🌐 BGP in Plain English — The "Phone Book" Analogy

What BGP does: BGP is like a phone book for networks. Your Cilium nodes tell the router: "Hey, Service IP 192.168.1.100 lives on MY node. Send traffic for that IP to me." The router updates its routing table and forwards accordingly.

localASN: 65001 — "My network's ID number is 65001." Private ASNs are 64512-65534 (for internal use).

peerASN: 65000 — "My neighbor router's network ID is 65000."

peerAddress: 10.0.0.1/32 — "The router lives at IP 10.0.0.1."

CCA Exam Tip: BGP is in the Service Mesh domain (20%). Know that BGP is what makes LoadBalancer Services work without a cloud provider!

B.7 CiliumEgressGatewayPolicy

Routes all egress traffic from app: backend pods through a specific gateway node with static IP 203.0.113.10. Useful for IP whitelisting with external services.

YAML
apiVersion: cilium.io/v2
kind: CiliumEgressGatewayPolicy
metadata:
  name: egress-static-ip
spec:
  selectors:
  - podSelector:
      matchLabels:
        app: backend
  destinationCIDRs:
  - 0.0.0.0/0
  egressGateway:
    nodeSelector:
      matchLabels:
        egress-gw: true
    egressIP: 203.0.113.10
🏢 The "Office Building" Analogy for Egress Gateway

The problem: Your anihpj backend pods run on 10 different nodes, each with a different public IP. An external payment API (Stripe, PayPal) requires you to whitelist IPs. You can't whitelist 10 IPs that change every time pods restart.

The solution: Egress Gateway forces ALL outbound traffic from selected pods through ONE designated node with ONE static IP. The external service sees only 203.0.113.10 — regardless of which pod or node initiated the request.

destinationCIDRs: 0.0.0.0/0 — "route ALL destinations through the gateway." You can narrow this to only specific external services.

CCA Exam Scenario: "A company needs to connect to an external API that requires IP whitelisting. Which Cilium feature?" → Egress Gateway!

B.8 CiliumLocalRedirectPolicy — Local DNS Cache

Redirects DNS queries (UDP 53) to a local DNS cache pod on the same node instead of going through CoreDNS Service. Reduces DNS latency by keeping traffic local.

YAML
apiVersion: cilium.io/v2
kind: CiliumLocalRedirectPolicy
metadata:
  name: local-dns
spec:
  redirectFrontend:
    toPorts:
    - port: "53"
      protocol: UDP
  redirectBackend:
    localEndpointSelector:
      matchLabels:
        app: local-dns-cache
    toPorts:
    - port: "53"
      protocol: UDP
🏠 The "Corner Store vs Supermarket" Analogy

Without Local Redirect: Every DNS query from a pod travels across the network to CoreDNS (the "supermarket" — central but far away). Network hop + queue + processing = latency.

With Local Redirect: Cilium intercepts DNS packets BEFORE they leave the node and redirects them to a local cache pod (the "corner store" — right next door). Same node = near-zero latency.

redirectFrontend — "Which traffic do we intercept?" Here: anything going to UDP port 53 (DNS).

redirectBackend — "Where do we send it instead?" To the local DNS cache pod on the same node.

⚖️ Policy Precedence Rules — Which Policy Wins?
1 CNP overrides CCNP — Namespace-specific policy ALWAYS wins over cluster-wide. Think of CNP as the "boss" and CCNP as the "company policy" — boss overrides.
2 More specific > Less specific — A policy with app: backend,env: prod (2 labels) beats one with just app: backend (1 label). More labels = more specific.
3 Multiple policies = UNION — If Policy-A allows port 80 and Policy-B allows port 443, the pod gets BOTH. Policies ADD, they don't replace each other.
4 L4 + L7 on same rule = AND — The L4 port must match AND the L7 rule must match. Both conditions must be true for traffic to pass.

📝 Appendix B — CCA Practice Questions (8 Questions)

Q1
What's the difference between CNP and CCNP?
Show Answer
Answer

CNP (CiliumNetworkPolicy) is namespace-scoped — rules apply only within one namespace. CCNP (CiliumClusterwideNetworkPolicy) applies across ALL namespaces. CNP has higher priority and can override CCNP rules.

Q2
What does endpointSelector: {} mean?
Show Answer
Answer

Empty curly braces select ALL pods in the scope (all pods in the namespace for CNP, all pods cluster-wide for CCNP). Used in default-deny-all and monitoring access policies.

Q3
Why must every egress policy include a DNS rule (UDP 53 to CoreDNS)?
Show Answer
Answer

Pods need DNS to resolve domain names before connecting to external services. Without it, even toFQDNs rules fail because the pod cannot look up the domain's IP address. The DNS rule must come FIRST in the egress list.

Q4
What is the difference between ingress and egress in a CiliumNetworkPolicy?
Show Answer
Answer

Ingress controls who can send traffic TO the selected pods (inbound). Egress controls where the selected pods can send traffic TO (outbound). Think: "In-gress = IN-coming" and "E-gress = EX-it."

Q5
What's the difference between L4 and L7 policy rules?
Show Answer
Answer

L4 (Layer 4): Filters by port number and protocol (TCP/UDP) — "Allow port 8000." Fast, enforced in eBPF. L7 (Layer 7): Reads the application protocol — "Allow HTTP GET to /api/v1." Requires Envoy proxy, smarter but slightly more overhead. L7 rules nest UNDER L4 rules (rules.http under toPorts).

Q6
A company needs to ensure all outbound traffic from backend pods goes through a single static IP for whitelisting. Which Cilium policy should they use?
Show Answer
Answer

CiliumEgressGatewayPolicy (B.7). It routes selected pods' egress traffic through a designated gateway node with a fixed IP. External services see only that single IP regardless of how many backend pods exist.

Q7
If two CiliumNetworkPolicies select the same pod, how are their rules combined?
Show Answer
Answer

Rules are UNIONED (added together). The pod gets the most permissive combination of all policies. If Policy-A allows port 80 and Policy-B allows port 443, the pod can receive traffic on both ports. Policies never cancel each other out.

Q8
What is the recommended order to apply policies for zero-trust security?
Show Answer
Answer

1. Default-deny-all CCNP (B.4) — lock everything. 2. DNS egress rule — allow pods to resolve names. 3. App-specific CNPs (B.1/B.2) — open specific needed ports. 4. L7 rules (B.2) — add HTTP-level restrictions. 5. Egress controls (B.3/B.7) — restrict external access. This is the "default-deny, explicit-allow" zero-trust pattern.

Q1
What is eBPF and why is it important for Cilium?
Show Answer
Answer

eBPF (Extended Berkeley Packet Filter) runs sandboxed programs in the Linux kernel without changing kernel source code. It's Cilium's core engine — replacing iptables, kube-proxy, and sidecar proxies with fast, safe kernel-level programs (up to 587x faster than iptables).

Q2
What is the difference between CNP and CCNP?
Show Answer
Answer

CNP (CiliumNetworkPolicy) is namespace-scoped. CCNP (CiliumClusterwideNetworkPolicy) applies cluster-wide across ALL namespaces. CNP has higher priority and can override CCNP rules.

Q3
What is Cilium Identity and how does it differ from IP-based security?
Show Answer
Answer

Identity is a numeric label assigned to all pods sharing the same label set. Unlike IP-based security, identity-based policies survive pod restarts and IP changes — the identity stays the same while the IP changes.

Q4
What is KPR (Kube-Proxy Replacement)?
Show Answer
Answer

KPR replaces kube-proxy's iptables-based Service load balancing with eBPF programs. Benefits: O(1) hash table lookups instead of O(n) iptables chains, Maglev consistent hashing, socket-level redirection (no DNAT hop).

Q5
What is the eBPF verifier and why does it matter?
Show Answer
Answer

The verifier is the kernel's safety gate for eBPF. It mathematically proves every program: (1) always terminates, (2) never accesses out-of-bounds memory, (3) executes at most 1M instructions. Unsafe programs are rejected — this is why eBPF is safe for production.

Q6
What is Maglev hashing used for in Cilium?
Show Answer
Answer

Maglev is a consistent hashing algorithm for Service load balancing. It ensures even backend distribution with minimal disruption when backends change. Provides connection affinity (same client → same backend).

Q7
What does "sidecar-less service mesh" mean in Cilium?
Show Answer
Answer

Traditional service meshes (Istio) inject a sidecar proxy container into every pod — consuming memory and adding latency. Cilium's mesh uses eBPF in the kernel + per-node Envoy — zero sidecar containers, zero per-pod memory overhead, lower latency.

This is the actual CiliumNetworkPolicy you would apply to secure the anihpj backend. It combines ingress rules (allow frontend) and egress rules (DNS + database).

metadata:
  name: secure-backend
  namespace: anihpj
spec:
  endpointSelector:
    matchLabels:
      app: backend        # Protects ALL backend pods
  ingress:                # WHO can reach the backend?
  - fromEndpoints:
    - matchLabels:
        app: frontend     # Only frontend pods
    toPorts:
    - ports:

  egress:                 # Where can the backend reach OUT?
  - toEndpoints:           # RULE 1: DNS (ALWAYS first!)

        io.kubernetes.pod.namespace: kube-system

        protocol: UDP
  - toEndpoints:           # RULE 2: Database access

        app: postgres
    toPorts:
    - ports:

What is the correct order for applying NetworkPolicies in a zero-trust setup?
Show Answer
Answer

1. Default-deny-all CCNP (lock everything), 2. DNS egress rule (allow name resolution), 3. App-specific CNPs (frontend→backend→database), 4. L7 rules (optional), 5. Egress controls (optional).

How do you verify WireGuard encryption is active?
Show Answer
Answer

cilium encrypt status — all nodes should show "OK" with the encryption type (WireGuard/IPSec). If not active, check kernel module: modprobe wireguard.

Q4
What ServiceMonitor configuration scrapes Hubble metrics from Cilium agents?
Show Answer
Answer

Use a Prometheus ServiceMonitor with selector: matchLabels: app: cilium, endpoint port hubble-metrics, and namespaceSelector: matchNames: [kube-system].

Q5
How does Cilium enable canary deployments without sidecars?
Show Answer
Answer

Cilium uses identity-based traffic splitting. The canary pods get a different label (e.g., version: canary) which maps to a different Cilium identity. eBPF load balancers split traffic by identity — no sidecar proxy needed.

Q6
What command validates the entire Cilium deployment end-to-end?
Show Answer
Answer

cilium connectivity test — runs 21+ tests covering pod-to-pod, Services, DNS, NetworkPolicy, Encryption, Hubble, and Performance.

Q7
Why does the anihpj Dockerfile use gunicorn instead of the Django dev server?
Show Answer
Answer

The Django dev server (manage.py runserver) is single-threaded and not designed for production. Gunicorn is a production-grade WSGI server with multiple workers, proper logging, and can handle concurrent requests. The CMD uses 3 workers bound to 0.0.0.0:8000.

Q8
What Grafana panels would you create to monitor anihpj with Hubble metrics?
Show Answer
Answer

1. HTTP Request Rate monitoring hubble_http_requests_total, 2. Policy Drops tracking hubble_drop_total, 3. DNS Query Rate via hubble_dns_responses_total, 4. TCP Flow Rate by Verdict using hubble_tcp_flags_total.
