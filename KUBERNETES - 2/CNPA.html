1.1 The Evolution of Software Delivery

Software delivery has evolved through five major eras. Each solved problems of the previous one — but introduced new challenges. Understanding this journey is essential for every Platform Engineer.

Think of it as "building the paved road" so developers don't have to navigate the muddy path of infrastructure themselves.

1.2 Cloud Native Defined — The CNCF Definition

The Cloud Native Computing Foundation (CNCF) defines cloud native technologies as those that "empower organizations to build and run scalable applications in modern, dynamic environments such as public, private, and hybrid clouds."

📖 The CNCF (Cloud Native Computing Foundation)

The CNCF is a Linux Foundation project founded in 2015 that hosts critical cloud native components like Kubernetes, Prometheus, Envoy, and 200+ other projects. The CNPA certification is also administered by the Linux Foundation.

📦
Containers

Standardized packaging of applications with all dependencies. Docker, containerd, and CRI-O are the most common runtimes. Containers are the "building blocks" of cloud native.

🕸️
Service Mesh

Infrastructure layer for service-to-service communication. Handles mTLS, traffic splitting, retries, and observability. Istio, Linkerd, and Cilium are popular choices.

📦
Microservices

Architectural pattern where applications are built as small, independent, loosely-coupled services. Each service owns its data and can be deployed independently.

🗿
Immutable Infrastructure

Servers/containers are never modified after deployment — they are replaced. "Cattle, not pets." If an anihpj container has an issue, we replace it, not fix it in place.

📜
Declarative APIs

You declare WHAT you want, the system figures out HOW to achieve it. Kubernetes YAML says "I want 3 replicas" — K8s makes it happen without you specifying steps.

2.1 Why Containers? The "Works on My Machine" Problem

Every developer has experienced this: anihpj runs perfectly on your laptop (Python 3.11, Django 5.2), but crashes in production (Python 3.8, missing dependencies). Containers solve this by packaging the application with ALL its dependencies into a single, portable unit.

3.2 Control Plane Components — The Platform Engineer's Perspective

a) kube-apiserver — "The Front Door"

Every kubectl command, every CI/CD deploy, every platform API call goes through the API Server. It handles authentication (who are you?), authorization (what can you do?), and admission control (should we allow this?). This is where your IDP's API integration happens!

b) etcd — "The Brain's Memory"

etcd is a distributed key-value store that holds ALL cluster state: every Pod, Service, ConfigMap, and Secret. It uses the Raft consensus algorithm and needs an odd number of nodes (3, 5, or 7). If you lose etcd, you lose everything — BACK IT UP!

c) kube-scheduler — "The Tetris Master"

Watches for new pods with no assigned node and decides where to place them. Uses a 2-step process: Filtering (which nodes can run this pod?) and Scoring (which is the best fit?). Considers resource requests, affinity rules, and taints/tolerations.

d) kube-controller-manager — "The Reconciliation Loop"

3.3 Worker Node Components — Where the Work Happens

a) kubelet — "The Node Manager"

Runs on every worker node as a systemd service. Takes PodSpecs from the API server and ensures containers are running and healthy. Reports node/pod health back to the control plane.

b) kube-proxy — "The Traffic Cop"

Network proxy on every node that maintains network rules (iptables/IPVS). Implements the Kubernetes Service abstraction — routes traffic to the correct backend pod.

c) Container Runtime — "The Engine"

Actually runs containers. containerd is the default since K8s 1.24 (Docker deprecated). Kubernetes is runtime-agnostic via the CRI (Container Runtime Interface).

6.2 Services Deep Dive — The 4 Types

a) ClusterIP (Default)

Exposes the service on a cluster-internal IP. Only reachable from within the cluster. This is the default type and is used for pod-to-pod communication. The anihpj Django service uses ClusterIP internally.

b) NodePort

Exposes the service on each Node's IP at a static port (range: 30000-32767). You can access the service from outside the cluster using <NodeIP>:<NodePort>. Good for development and debugging.

c) LoadBalancer

Exposes the service externally using a cloud provider's load balancer. AWS creates an NLB/ALB, GCP creates a Cloud Load Balancer. This is the standard way to expose services in production on managed K8s.

d) ExternalName

Maps the service to a DNS name (CNAME). No proxying — just a DNS alias. Useful for accessing external services (like an RDS database) through a consistent internal name.

6.4 DNS in Kubernetes — Service Discovery

Kubernetes runs CoreDNS as the cluster DNS server. Every Service gets a DNS record: <service>.<namespace>.svc.cluster.local. Pods can discover services by name without hardcoding IPs.

📖 DNS Pattern

anihpj pods can reach the database service at postgres-service.anihpj-prod.svc.cluster.local. This is how the Django settings.py configures DATABASE_HOST — by service name, not IP!

8.5 CI Best Practices for Platform Engineers

As a platform engineer, you're not just writing CI pipelines — you're designing the CI experience for all your development teams. These best practices ensure your CI platform is fast, reliable, and developer-friendly.

✅ CI Best Practices Checklist
  1. Fast feedback — Keep CI under 10 minutes. Developers lose focus after 10 min. Use parallel jobs and smart test selection.
  2. Deterministic builds — Same input → same output, always. Pin all dependency versions. Use lockfiles (poetry.lock, Pipfile.lock).
  3. Caching — Cache pip dependencies, Docker layers, and build artifacts. Don't download the internet on every run.
  4. Parallelization — Run lint, test, and security scans simultaneously. Use matrix builds for multi-version testing.
  5. Flaky test management — Quarantine flaky tests; don't ignore them. They erode trust in CI. Track flakiness metrics.
  6. Branch protection — Require CI to pass before merge. Block direct pushes to main. Enforce via GitHub/GitLab settings.
  7. Test isolation — Each test should be independent. No shared state. Use service containers for databases.
  8. Security scanning — SAST (Bandit), dependency scanning, container scanning (Trivy) on every PR.
  9. Artifact management — Store test reports, coverage data, and build logs. Don't lose evidence.
  10. Pipeline as code — CI config lives in the repo. Version controlled. Reviewable. Auditable.

9.1 What is Continuous Delivery vs Continuous Deployment?

These terms are often confused, but they have distinct meanings. Understanding the difference is critical for the CNPA exam and for designing your platform's delivery strategy.

📦
Continuous Delivery

Every change is deployable — but deployment is manual (approval gate). The anihpj team reviews and approves each production deployment. "We COULD deploy anytime; we CHOOSE when."

🚀
Continuous Deployment

Every change that passes CI is automatically deployed to production. No human approval — the pipeline decides. "If CI passes, it ships." Requires extremely strong test coverage and monitoring.

9.2 Deployment Strategies — The Complete Guide

Choosing the right deployment strategy is one of the most impactful decisions a platform engineer makes. Each strategy balances risk, speed, complexity, and cost differently.

a) Rolling Update (Kubernetes Default)

Gradually replaces old pods with new ones — zero downtime, but no environment isolation during deployment. Controlled by maxSurge (how many extra pods to create) and maxUnavailable (how many pods can be down).

Rolling Update Visualization
  Before:   [P1-v1] [P2-v1] [P3-v1]  ← All running v1
  Step 1:   [P1-v1] [P2-v1] [P3-v1] [P4-v2]  ← maxSurge=1, new v2 pod created
  Step 2:   [P1-v1] [P2-v1]         [P4-v2] [P5-v2]  ← One v1 removed, one v2 added
  Step 3:   [P1-v1]                 [P4-v2] [P5-v2] [P6-v2]  ← Continue...
  Final:                        [P4-v2] [P5-v2] [P6-v2]  ← All v2, zero downtime!

b) Blue-Green Deployment

Two identical environments: Blue (current/production) and Green (new version). Switch traffic all at once via Service selector. Instant rollback — just switch the Service back to Blue.

Route a small percentage of traffic to the new version, monitor metrics, and gradually increase the percentage. Example: 5% → 25% → 50% → 100%. Requires traffic splitting via Ingress controller or Service Mesh (Istio/Linkerd).

9.3 ArgoCD — GitOps Continuous Delivery

9.4 Progressive Delivery with Argo Rollouts

Argo Rollouts is a Kubernetes controller and CRD that replaces the standard Deployment resource. It gives you Blue-Green and Canary deployment strategies natively in Kubernetes, plus automatic analysis and rollback.

📝 Argo Rollout for anihpj — Canary Deployment

anihpj-rollout.yaml
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: anihpj
spec:
  replicas: 5
  selector:
    matchLabels:
      app: anihpj
  strategy:
    canary:
      steps:
        - setWeight: 5      # 5% traffic to new version
        - pause: {duration: 5m}  # Wait 5 minutes, monitor
        - setWeight: 25     # 25% traffic
        - pause: {duration: 10m}
        - setWeight: 50     # 50% traffic
        - pause: {duration: 10m}
        - setWeight: 100    # 100% — fully promoted!
      analysis:
        templates:
          - templateName: error-rate-check
          - templateName: latency-check
        startingStep: 1     # Start analysis after step 1
  template:
    spec:
      containers:
        - name: anihpj
          image: ghcr.io/anihpj/anihpj:v2
          ports:
            - containerPort: 8000

10.2 Docker Build Optimization for Platform Engineers

The default Docker build works — but as a platform engineer, you can dramatically improve build speed, image size, and security. Here are the techniques that matter:

📦 Multi-Stage Builds — Separate Build from Runtime

Dockerfile (Optimized Multi-Stage)
# ──── STAGE 1: BUILD ────
FROM python:3.11-slim AS builder
WORKDIR /app
RUN apt-get update && apt-get install -y --no-install-recommends \
    gcc libpq-dev && rm -rf /var/lib/apt/lists/*
COPY requirements.txt .
RUN pip install --user --no-cache-dir -r requirements.txt

# ──── STAGE 2: RUNTIME (Distroless-like) ────
FROM python:3.11-slim
WORKDIR /app
# Copy ONLY the installed packages from builder (not gcc, not dev libs)
COPY --from=builder /root/.local /root/.local
# Copy application code LAST (changes most frequently)
COPY . .
ENV PATH=/root/.local/bin:$PATH
USER 1000:1000
EXPOSE 8000
CMD ["gunicorn", "anihpj.wsgi:application", "--bind", "0.0.0.0:8000"]

🪜 Layer Caching — Order Matters!

Docker Layer Caching Strategy
  ❌ BAD (Cache busted every code change):
  COPY . .                    ← Changes every commit → cache MISS
  RUN pip install -r req.txt  ← Runs EVERY time → SLOW

  ✅ GOOD (Dependencies cached):
  COPY requirements.txt .     ← Only changes when deps change
  RUN pip install -r req.txt  ← Cached 95% of the time → FAST!
  COPY . .                    ← Only this layer is rebuilt

  ⚡ BUILD TIME: Bad ~5 min → Good ~30 sec (10x faster!)

💡 BuildKit & Multi-Arch

Use docker buildx build --platform linux/amd64,linux/arm64 for multi-architecture images. Run anihpj on cheaper ARM (Graviton) instances — saving 20-40% on compute costs. BuildKit also enables --mount=type=cache for pip cache and --mount=type=secret for passing credentials without baking them into the image.

📝 CI Integration — Trivy in GitHub Actions

CI Trivy Scanning Step
# Scan filesystem for vulnerabilities BEFORE building the image
- name: Trivy FS Scan
  uses: aquasecurity/trivy-action@master
  with:
    scan-type: 'fs'
    scan-ref: '.'
    severity: 'CRITICAL,HIGH'
    exit-code: 1          # FAIL the build on findings
    format: 'sarif'
    output: 'trivy-results.sarif'

# Scan the BUILT image
- name: Trivy Image Scan
  uses: aquasecurity/trivy-action@master
  with:
    image-ref: 'ghcr.io/anihpj/anihpj:${{ github.sha }}'
    severity: 'CRITICAL,HIGH'
    exit-code: 1
⚠️ Critical Policy

Block deployments on CRITICAL and HIGH vulnerabilities. Your CI pipeline should FAIL if Trivy finds any critical or high CVEs. This is non-negotiable for production images. Configure exit-code: 1 and severity: 'CRITICAL,HIGH'.

10.4 Image Signing and Supply Chain Security

How do you know the image running in production is the exact same image that passed your CI pipeline — and not one swapped by an attacker? Image signing answers this question cryptographically.

🔐 Cosign — Sign and Verify Container Images

Cosign (part of the Sigstore project) signs container images and stores the signature in the same registry. It supports keyless signing using OIDC (OpenID Connect) — your CI provider's identity (e.g., GitHub Actions) becomes the signer. No keys to manage, rotate, or lose!

Cosign in CI Pipeline
# Step 1: Install Cosign
- uses: sigstore/cosign-installer@v3

# Step 2: Sign the image (keyless, via OIDC)
- name: Sign Image
  run: |
    cosign sign \
      --yes \
      ghcr.io/anihpj/anihpj@${{ steps.build.outputs.digest }}
  env:
    COSIGN_EXPERIMENTAL: "true"  # Enable keyless signing

# Step 3: Verify BEFORE deployment (in CD pipeline)
- name: Verify Signature
  run: |
    cosign verify \
      --certificate-identity https://github.com/anihpj/anihpj/.github/workflows/ci.yml@refs/heads/main \
      --certificate-oidc-issuer https://token.actions.githubusercontent.com \
      ghcr.io/anihpj/anihpj:${{ github.sha }}

🏭 SLSA Framework — Supply-chain Levels for Software Artifacts

SLSA (pronounced "salsa") is a security framework from Google/OpenSSF that defines increasing levels of supply chain integrity:

LevelNameRequirements
🔴 L0NoneNo guarantees
🟠 L1ProvenanceBuild is scripted; provenance shows how artifact was built
🟡 L2Hosted BuildBuild runs on hosted platform (GitHub Actions); signed provenance
🟢 L3Hardened BuildIsolated, ephemeral, hermetic builds; non-falsifiable provenance

📋 SBOM — Software Bill of Materials

An SBOM is a machine-readable inventory of every component inside your image — like a nutrition label for software. Generated with Syft or Trivy. Critical for vulnerability management: when Log4Shell hits, you can instantly query SBOMs to find affected images.

10.5 Container Registry Best Practices

Your container registry is the distribution hub for your platform. Treat it as critical infrastructure — because if your registry is down, your platform can't deploy anything.

🏷️ Tagging Strategy — Never Use :latest in Production!

📝 CI Job — Generate Smart Tags

CI Tag Generation
- name: Generate Image Tags
  id: tags
  run: |
    echo "sha_tag=ghcr.io/anihpj/anihpj:${{ github.sha }}" >> $GITHUB_OUTPUT
    echo "version_tag=ghcr.io/anihpj/anihpj:v$(cat VERSION)-${{ github.sha }}" >> $GITHUB_OUTPUT
    echo "env_tag=ghcr.io/anihpj/anihpj:${{ github.ref_name }}" >> $GITHUB_OUTPUT

✅ Registry Best Practices Checklist

✅ Registry Best Practices
  1. Immutable tags — Never overwrite; use unique version tags. Once pushed, a tag should be permanent.
  2. Hybrid tag strategy — anihpj:v1.2.3-prod-abc1234 (semver + env + git SHA)
  3. Retention policies — Auto-delete images older than 90 days or keep only last N versions
  4. Vulnerability scanning — Scan at registry level continuously, not just during CI
  5. NEVER use :latest in production manifests! It's mutable, unpredictable, and dangerous.
  6. Proxy cache — Cache Docker Hub images locally to reduce external pulls and avoid rate limits
  7. Access control — Use least privilege: devs can push, CD system can pull, nobody else
  8. Geo-replication — Replicate registries across regions for disaster recovery and faster pulls
🟡 Platform Engineering Context

As a platform engineer, you'll configure the registry as part of your IDP's infrastructure. Key decisions: public vs private registry, retention policies, geo-replication, and integration with your CI/CD and security scanning pipelines. The registry is the bridge between CI (build) and CD (deploy).
