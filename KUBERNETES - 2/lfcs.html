🎯 LFCS Exam Strategy

Exam Environment Setup

The LFCS is a 2-hour live terminal exam via PSI Bridge. You get 1-5 Linux VMs. tmux is available — start a named session immediately. Read all questions first.

The 3-Pass Strategy

Pass 1: Answer everything you know in <60 seconds each. Pass 2: Attempt harder tasks using man pages. Pass 3: Revisit skipped tasks with remaining time.

Making Changes Persistent

Always verify changes survive a reboot — systemctl enable, /etc/fstab entries, crontab -e. The exam checks persistence. Don't just apply changes — make them permanent.

Domain Time Allocation

Allocate time proportional to domain weight. Essential Commands (25%) = ~30 min. Service Config (20%) = ~24 min. Process Mgmt (20%) = ~24 min. Storage (13%) = ~16 min. Networking (12%) = ~14 min. Users (10%) = ~12 min.

Common Exam Mistakes to Avoid

  • Not running systemctl enable — change not persistent
  • Forgetting sudo or not checking if you're root
  • Wrong file path (relative vs absolute)
  • Not verifying the change worked (systemctl status)
  • Spending too long on one task — move on and return

Pre-Exam Checklist

  • ✅ Practice every domain in a live VM — not just reading
  • ✅ Know: man pages, systemctl, chmod/chown, fdisk/mkfs/mount, iptables/ufw
  • ✅ tmux: create session immediately on exam start
  • ✅ Start with high-confidence tasks; skip unknowns
  • ✅ Verify every change with status commands

⚠️ Case Sensitivity — Linux's #1 Gotcha

On Linux: manage.py, Manage.py, and MANAGE.PY are three completely different files. This bites developers coming from Windows constantly. Always type filenames exactly as they appear.

Everything is a File

📄
Regular Files

Text files, Python scripts, images, binaries — all accessed the same way with open()

🔌
Devices

/dev/sda (hard disk), /dev/null (black hole), /dev/random — all files

⚙️
Processes & Kernel

/proc/cpuinfo, /proc/meminfo — kernel state exposed as readable text files

🔗
Network Sockets

Unix sockets like /run/gunicorn.sock — Nginx talks to Gunicorn through a file

📁
Directories

A directory is just a special file that lists other files — same read/write/execute model

🔧
Config Files

All system config is plain text in /etc/ — edit with any text editor, no GUI needed

3.3 Absolute vs Relative Paths

Every file path is either absolute (starts with /) or relative (starts from where you are now). This distinction is critical for scripts, cron jobs, and systemd service files.

4.1 The Permission Model — Three Levels

Every file and directory has exactly one owner, belongs to exactly one group, and has permission settings for three distinct audience levels.

Decoding the Permission String — Every Character Explained
  -  r w x   r - x   r - -
  │  └─┴─┘   └─┴─┘   └─┴─┘
  │   OWNER   GROUP   OTHER
  │
  └── File type: - = file, d = directory, l = symlink, s = socket

  r = Read    (4) → view contents  / list directory
  w = Write   (2) → modify file    / create files in directory
  x = Execute (1) → run as program / enter directory (cd)
  - = No permission (0)

  EXAMPLE: -rwxr-xr--
    Owner (rwx) = 4+2+1 = 7  → read, write, execute
    Group (r-x) = 4+0+1 = 5  → read and execute
    Other (r--) = 4+0+0 = 4  → read only
    Octal notation: 754

4.2 chmod — Changing Permissions

chmod sets permissions. Two modes exist — know both, as the LFCS uses both.

✏️ Symbolic Mode (u/g/o/a + r/w/x)
# WHO: u=owner, g=group, o=other, a=all
# WHAT: r=read, w=write, x=execute

chmod u+x script.sh      # add execute for owner
chmod g-w config.cfg     # remove write from group
chmod o=r readme.txt     # set other to read-only
chmod a+r /var/www/html  # readable by everyone
chmod ug+rw shared.txt   # r+w for owner and group
🔢 Octal Mode (most common on LFCS)
# NNN = owner, group, other (r=4 w=2 x=1)

chmod 755 script.sh      # rwxr-xr-x
chmod 644 config.cfg     # rw-r--r--
chmod 600 .env           # rw-------
chmod 700 ~/.ssh         # rwx------
# Recursive (entire tree):
chmod -R 755 /var/www/anihpj/

4.4 Special Permission Bits — SUID, SGID, Sticky Bit

Beyond rwx, Linux has three special bits that modify how permissions work. These appear on the LFCS exam and in real security audits.

s
SUID — Set User ID (4xxx)

Run the file as its owner, regardless of who calls it.

⚡ ls shows s in owner execute

# passwd writes to /etc/shadow
# SUID lets it run as root!

s
SGID — Set Group ID (2xxx)

On directories: new files inherit the directory's group automatically.

⚡ ls shows s in group execute

# Files created inside get
# group=devteam automatically!

t
Sticky Bit (1xxx)

Only the file's owner can delete it — even if others have write access.

⚡ ls shows t in other execute
$ ls -la /

# Everyone writes to /tmp
# But only YOU delete YOUR files

4.5 umask — Default Permission Mask

umask controls what permissions are automatically subtracted when you create a new file or directory. Think of it as a protective filter applied to every new file — the bits set in umask are blocked from the default maximum.

How umask Calculation Works — Three Common Values
  FILE max = 666 (files can never be executable by default)
  DIR  max = 777

  umask 022 (system default):          umask 027 (secure):
    File: 666 - 022 = 644  rw-r--r--    File: 666 - 027 = 640  rw-r-----
    Dir:  777 - 022 = 755  rwxr-xr-x    Dir:  777 - 027 = 750  rwxr-x---

  umask 077 (most restrictive):
    File: 666 - 077 = 600  rw-------    ← owner ONLY
    Dir:  777 - 077 = 700  rwx------    ← owner ONLY

  NOTE: Files can NEVER be executable by default.
  You must explicitly chmod +x to make a file executable.

5.6 I/O Redirection and Pipes

Redirection and pipes are the Unix philosophy in action: small tools that do one thing well, connected to form powerful workflows. Every LFCS task involves at least one pipe or redirect.

I/O Redirection — All Operators Explained
  STANDARD STREAMS:
    stdin  (0) ← keyboard input (or a file via <)
    stdout (1) → terminal output (or a file via > or >>)
    stderr (2) → error messages (or a file via 2>)

  REDIRECTION OPERATORS:
    cmd > file          overwrite file with stdout (creates or truncates)

    cmd > file 2>&1    redirect both stdout AND stderr to file

    cmd1 | cmd2         stdout of cmd1 → stdin of cmd2

  SPECIAL TARGETS:
    /dev/null           black hole — discard unwanted output silently
    /dev/stdin          standard input as a file path
    /dev/tee            split output to both screen and file

✅ Complete Automated Backup Script for anihpj
#!/bin/bash
# /usr/local/bin/anihpj-backup.sh
# Automated backup: code + database + offsite sync

set -euo pipefail   # exit on error, undefined vars, pipe failures

DATE=$(date +%Y-%m-%d)
BACKUP_DIR=/backups/anihpj/$DATE
REMOTE="backup@192.168.1.10:/backups/anihpj/"

# Create today's backup directory
mkdir -p "$BACKUP_DIR"

# 1. Code backup with xz compression
echo "[$(date)] Backing up application code..."
tar -cJf "$BACKUP_DIR/code.tar.xz" /var/www/anihpj/

# 2. Database backup
echo "[$(date)] Backing up PostgreSQL database..."
pg_dump -U postgres anihpj_db > "$BACKUP_DIR/db_$DATE.sql"
gzip "$BACKUP_DIR/db_$DATE.sql"

# 3. Config backup
echo "[$(date)] Backing up configs..."
tar -cJf "$BACKUP_DIR/configs.tar.xz" /etc/nginx/ /etc/systemd/system/anihpj.service

# 4. Sync offsite
echo "[$(date)] Syncing to remote backup server..."

# 5. Remove backups older than 30 days
find /backups/anihpj/ -maxdepth 1 -type d -mtime +30 -exec rm -rf {} +

9.1 Combining Tools — The Unix Philosophy

The Unix philosophy is: write programs that do one thing and do it well, and that work together through text streams. Pipes are the glue. Understanding this mental model makes you a dramatically better command-line user.

The Unix Pipeline — Data Flows Left to Right Through Specialized Tools
  INPUT                TOOLS                              OUTPUT
  ──────        ─────────────────────────────────        ──────────────
  nginx         grep " 500 "     → filter lines          "192.168.1.5"
  access.log ──▶ awk '{print $1}'→ extract IP column ──▶ "10.0.0.22"

                 uniq -c         → count each unique     (count+IP per line)

  Each tool:  reads stdin → transforms → writes stdout
  No tool knows what comes before or after it.
  This is composability — mix any tools in any order.
xargs — Bridging Pipes to Arguments
  PROBLEM: some commands don't read from stdin — they need ARGUMENTS
  SOLUTION: xargs converts stdin lines into command arguments

  find /tmp -name "*.pyc" | rm              ← WRONG, rm ignores stdin

  find /tmp -name "*.pyc" | xargs rm        ← each line becomes an arg

  ───────────────────────────────────────────────────────────────────

  grep -rl "localhost" /etc/nginx/ | xargs grep -n "listen"

  # Process files with spaces in names (use -0 + find -print0):
  find /var/log -name "*.log" -print0 | xargs -0 wc -l

  -I {} — use placeholder for each item:
  find . -name "*.py" | xargs -I {} cp {} /tmp/backup/
|
Pipe — Stream to Stream

Connects stdout of one command to stdin of the next. Both run simultaneously. No disk I/O between steps.

xargs

Takes lines from stdin and passes them as arguments. Use when the next command needs arguments, not stdin.

9.4 awk Advanced — Arrays, printf, Multi-File Processing

awk's real power comes from its associative arrays — a built-in key→value store that lets you group, count, and correlate data across multiple records. Combined with printf, you can generate clean tabular reports from raw logs.

    /var/log/nginx/access.log | sort -rn | head -10

  awk '{codes[$9]++} END {for (c in codes) print codes[c], c}' \
    /var/log/nginx/access.log | sort -rn

  # Sum bytes transferred per URL:
  awk '{bytes[$7] += $10} END {for (url in bytes) print bytes[url], url}' \
    /var/log/nginx/access.log | sort -rn | head -10

  awk printf — FORMATTED TABLE OUTPUT:
  ─────────────────────────────────────────────────────────────────────

10.5 Loops — for, while, until

Loops let you repeat operations across files, lines, or numeric ranges. The most common patterns: iterate over files, read a file line by line, and poll until a condition is met.

  ─────────────────────────────────────────────────────────────────────

10.7 Error Handling and Logging

Production scripts must fail loudly and cleanly. The set options and trap make your scripts safe by default — stopping immediately on errors and always cleaning up temporary files.

set Options — Make Scripts Fail Safely
  Add this at the top of EVERY production script:
  ─────────────────────────────────────────────────────────────────────
  set -euo pipefail
       │││
       ││└── pipefail: pipeline fails if ANY command in it fails
       ││             (without this: "false | true" exits 0 — WRONG)
       │└─── u: treat unset variables as errors (prevents typos like $USRE)
       └──── e: exit immediately on any command that returns non-zero

  set -x    → debug mode: print each command before running it
  set +x    → turn off debug mode (useful to toggle in sections)

  EXAMPLES OF WHAT THESE PREVENT:
  ─────────────────────────────────────────────────────────────────────
  Without set -e:
    rm -rf "$TMPDIR/"            ← if $TMPDIR is empty, this becomes rm -rf /!
  With set -u:
    rm -rf "${TMPDIR:?tmpdir not set}/"  ← safer with :? expansion

  TRAP — run cleanup on exit, error, or interrupt:
  ─────────────────────────────────────────────────────────────────────
  TMPFILE=$(mktemp)              ← create unique temp file

  cleanup() {
      rm -f "$TMPFILE"           ← delete temp file on any exit
      echo "Cleanup done"
  }
  trap cleanup EXIT              ← runs cleanup() on EXIT (normal or error)
  trap cleanup INT TERM          ← also on Ctrl+C or kill signal

  SIGNALS (for trap):
    EXIT  → any exit (normal or error)
    INT   → Ctrl+C
    TERM  → kill / systemctl stop
    ERR   → any command fails (like set -e but more flexible)

#!/bin/bash
# =============================================================
# health-check.sh — Full anihpj stack health check
# Returns: 0 = healthy, 1 = something wrong
# Schedule: */5 * * * * /usr/local/bin/health-check.sh
# =============================================================

PASS=0; FAIL=0
REPORT=()
DISK_WARN=80      # alert if disk > 80% used
MEM_WARN=10       # alert if memory < 10% free
CERT_WARN_DAYS=14 # alert if cert expires in < 14 days

ok()   { REPORT+=("  [OK]   $1"); (( PASS++ )); }
fail() { REPORT+=("  [FAIL] $1"); (( FAIL++ )); }
warn() { REPORT+=("  [WARN] $1"); }

# ── Service checks ──────────────────────────────────────────
systemctl is-active --quiet nginx      && ok "nginx is running"      || fail "nginx is DOWN"
systemctl is-active --quiet anihpj     && ok "gunicorn is running"   || fail "gunicorn is DOWN"
systemctl is-active --quiet postgresql && ok "postgresql is running" || fail "postgresql is DOWN"

# ── HTTP checks ─────────────────────────────────────────────
HTTP80=$(curl -s -o /dev/null -w "%{http_code}" http://localhost/ 2>/dev/null || echo "000")
[[ "$HTTP80" == "200" || "$HTTP80" == "301" || "$HTTP80" == "302" ]] \
    && ok "HTTP port 80 → $HTTP80" || fail "HTTP port 80 returned $HTTP80"

HTTP8K=$(curl -s -o /dev/null -w "%{http_code}" http://localhost:8000/health/ 2>/dev/null || echo "000")
[[ "$HTTP8K" == "200" ]] && ok "Gunicorn port 8000 → 200" || fail "Gunicorn port 8000 → $HTTP8K"

# ── Database check ──────────────────────────────────────────
pg_isready -U postgres -d anihpj_db -q 2>/dev/null \
    && ok "PostgreSQL accepting connections" || fail "PostgreSQL not ready"

# ── Disk space check ────────────────────────────────────────
DISK_PCT=$(df / | awk 'NR==2 {gsub(/%/,"",$5); print $5}')
(( DISK_PCT < DISK_WARN )) \
    && ok "Disk usage ${DISK_PCT}% (threshold: ${DISK_WARN}%)" \
    || fail "Disk ${DISK_PCT}% used — above ${DISK_WARN}% threshold!"

# ── Memory check ────────────────────────────────────────────
MEM_FREE_PCT=$(free | awk '/^Mem/ {printf "%.0f", $7/$2*100}')
(( MEM_FREE_PCT > MEM_WARN )) \
    && ok "Memory available: ${MEM_FREE_PCT}% (threshold: >${MEM_WARN}%)" \
    || fail "Low memory: only ${MEM_FREE_PCT}% available!"

# ── SSL certificate check ───────────────────────────────────
CERT="/etc/letsencrypt/live/anihpj.com/cert.pem"
if [[ -f "$CERT" ]]; then
    DAYS_LEFT=$(( ($(date -d "$(openssl x509 -enddate -noout -in "$CERT" | cut -d= -f2)" +%s) - $(date +%s)) / 86400 ))
    (( DAYS_LEFT > CERT_WARN_DAYS )) \
        && ok "SSL cert valid for ${DAYS_LEFT} more days" \
        || fail "SSL cert expires in ${DAYS_LEFT} days!"
else
    warn "SSL cert not found at $CERT"
fi

# ── Report ──────────────────────────────────────────────────
echo "===== anihpj Health Report — $(date '+%Y-%m-%d %H:%M') ====="
printf '%s\n' "${REPORT[@]}"
echo "======================================================"
echo "Passed: $PASS | Failed: $FAIL"

[[ $FAIL -eq 0 ]] && exit 0 || exit 1

11.4 Log Rotation Script — Automated Log Management

Log files grow indefinitely without management. This script compresses old logs, deletes stale archives, and sends an email summary. The cron schedule runs it nightly so it never needs manual attention.

Log Lifecycle — From Active to Archive to Deletion
  ACTIVE LOG              AGE: 0-6 days
  app.log                 → being written to now by gunicorn/nginx

      │ at 7 days old
      ▼
  COMPRESSED              AGE: 7-29 days
  app.log.gz              → gzip compressed, stored in same directory

      │ at 30 days old
      ▼
  DELETED                 AGE: 30+ days
  (removed)               → too old to be useful, disk freed

  IMPLEMENTATION:
  find /var/log/anihpj -name "*.log" -mtime +6 → compress to .gz
  find /var/log/anihpj -name "*.gz"  -mtime +29 → delete
Complete Log Rotation Script + Cron Schedule
#!/bin/bash
# =============================================================
# rotate-logs.sh — Compress old logs, delete stale archives
# Schedule: 0 3 * * * /usr/local/bin/rotate-logs.sh
# =============================================================
set -euo pipefail

LOG_DIR="/var/log/anihpj"
COMPRESS_AFTER=7    # days: compress logs older than this
DELETE_AFTER=30     # days: delete compressed logs older than this
REPORT_LOG="$LOG_DIR/rotation.log"
ADMIN_EMAIL="admin@anihpj.com"

log() { echo "[$(date '+%H:%M:%S')] $*" | tee -a "$REPORT_LOG"; }

COMPRESSED=0
DELETED=0
FREED=0

log "===== Log rotation started $(date '+%Y-%m-%d') ====="

# ── Compress logs older than COMPRESS_AFTER days ────────────
while IFS= read -r -d '' LOGFILE; do
    SIZE=$(stat -c %s "$LOGFILE" 2>/dev/null || echo 0)
    gzip -f "$LOGFILE"
    log "Compressed: $(basename "$LOGFILE") (${SIZE} bytes)"
    (( COMPRESSED++ ))
    (( FREED += SIZE ))
done < <(find "$LOG_DIR" -maxdepth 2 -name "*.log" -not -name "rotation.log" \
              -mtime "+$COMPRESS_AFTER" -print0)

# ── Delete compressed logs older than DELETE_AFTER days ─────
while IFS= read -r -d '' GZFILE; do
    SIZE=$(stat -c %s "$GZFILE" 2>/dev/null || echo 0)
    rm -f "$GZFILE"
    log "Deleted: $(basename "$GZFILE") (${SIZE} bytes)"
    (( DELETED++ ))
    (( FREED += SIZE ))
done < <(find "$LOG_DIR" -maxdepth 2 -name "*.gz" \
              -mtime "+$DELETE_AFTER" -print0)

# ── Signal nginx and gunicorn to reopen log files ───────────
systemctl kill -s HUP nginx    2>/dev/null || true
systemctl kill -s USR1 anihpj  2>/dev/null || true

# ── Summary ─────────────────────────────────────────────────
FREED_MB=$(( FREED / 1048576 ))
SUMMARY="Log rotation done: compressed=$COMPRESSED deleted=$DELETED freed=${FREED_MB}MB"
log "===== $SUMMARY ====="

# Email summary (requires mailutils/sendmail):
echo "$SUMMARY" | mail -s "anihpj Log Rotation — $(date +%F)" "$ADMIN_EMAIL" 2>/dev/null || true

# ── CRON SETUP (run: crontab -e) ────────────────────────────
# 0 3 * * * /usr/local/bin/rotate-logs.sh
# This runs every night at 3 AM — zero maintenance needed

12.2 useradd, usermod, userdel

useradd creates users; usermod modifies existing accounts; userdel removes them. Master these three commands — they appear in nearly every LFCS exam scenario.

⚙️ useradd — Key Flags
  useradd [OPTIONS] username

  Flag        Meaning                          Example
  ──────────────────────────────────────────────────────────────────────────
  -m          Create home directory            useradd -m alice
  -d PATH     Set custom home dir              useradd -m -d /data/alice alice
  -s SHELL    Set login shell                  useradd -m -s /bin/bash alice
  -u UID      Assign specific UID              useradd -u 1500 alice
  -g GROUP    Set primary group                useradd -g developers alice
  -G g1,g2    Set supplementary groups         useradd -G sudo,docker alice
  -r          Create system account (UID<1000) useradd -r -s /usr/sbin/nologin anihpj

🔧 usermod — Modifying Existing Accounts
  usermod [OPTIONS] username

  Action                              Command
  ──────────────────────────────────────────────────────────────────────────
  Add to supplementary group          usermod -aG docker alice      ← -a is CRITICAL
  Replace ALL supplementary groups    usermod -G docker alice       ← DANGER: removes others
  Change login shell                  usermod -s /bin/bash alice
  Lock account (prefix ! in shadow)   usermod -L alice
  Unlock account                      usermod -U alice
  Rename username                     usermod -l newname oldname
  Move home directory                 usermod -m -d /newhome alice
  Disable interactive login           usermod -s /usr/sbin/nologin alice
  Set account expiry                  usermod -e 2026-12-31 alice

  ⚠️  WARNING: Always use -aG (append), never just -G alone
      usermod -G docker alice  →  alice LOSES all other groups except docker!
🗑️ userdel — Removing User Accounts
  userdel [OPTIONS] username

  Option    Effect
  ─────────────────────────────────────────────────────────────────────────
  (none)    Delete user from /etc/passwd, /etc/shadow, /etc/group

  -f        Force deletion even if user is logged in (dangerous!)

  1. Lock account first:         usermod -L alice
  2. Verify no running processes: ps aux | grep alice
  3. Backup home if needed:      tar czf alice_home.tar.gz /home/alice
  4. Delete:                     userdel -r alice

  $ find / -nouser -o -nogroup 2>/dev/null

12.4 Switching Users — su and sudo

su switches the current identity completely; sudo grants temporary elevated privilege for a specific command. sudo is the modern best practice for servers.

🔁 su vs sudo — When to Use Which
  su (Switch User)                         sudo (Superuser Do)
  ─────────────────────────────────────── ─────────────────────────────────────────
  su -                  → root shell       sudo command         → run ONE command as root
  su - alice            → alice's shell    sudo -u alice cmd    → run as alice
  su -c "cmd" alice     → one command      sudo -i              → interactive root shell
  (requires alice's password)              (requires YOUR password + sudoers entry)

  Key differences:
  ┌──────────────────┬──────────────────────────┬──────────────────────────┐
  │ Aspect           │ su                        │ sudo                     │
  ├──────────────────┼──────────────────────────┼──────────────────────────┤
  │ Password needed  │ Target user's password    │ Your own password        │
  │ Audit trail      │ Poor (who ran su?)        │ Full (logged to syslog)  │
  │ Granularity      │ All-or-nothing            │ Per-command control      │

🎯 LFCS Exam Tip — sudoers Drop-in Files

The exam often asks you to configure sudo for a specific user. Use the drop-in pattern:

  1. Run sudo visudo -f /etc/sudoers.d/username
  2. Add the rule: username ALL=(ALL) NOPASSWD: /path/to/command
  3. Set permissions: sudo chmod 0440 /etc/sudoers.d/username
  4. Verify: sudo -l -U username

13.1 Understanding Groups

13.3 Managing Group Membership

There are two ways to manage group membership: usermod -aG (modifies /etc/passwd and /etc/group) and gpasswd (group administrator tool). Both work — know both for the exam.

👥 Group Membership Operations
  METHOD 1: usermod (most common)
  ─────────────────────────────────────────────────────────────────────────
  usermod -aG groupname username    # ADD to supplementary group ✓
  usermod -G groupname username     # REPLACE all supplementary groups ✗ DANGER

  The -a flag (append) is MANDATORY. Without it:
  Before: alice: alice,sudo,docker,developers
  usermod -G developers alice
  After:  alice: alice,developers   ← sudo and docker REMOVED!

  METHOD 2: gpasswd (group password tool — also manages membership)
  ─────────────────────────────────────────────────────────────────────────
  gpasswd -a alice developers       # add alice to developers ✓
  gpasswd -d alice developers       # remove alice from developers ✓
  gpasswd -M alice,bob developers   # SET members (replaces all — use carefully)
  gpasswd -A alice developers       # make alice a group administrator

  METHOD 3: newgrp (session-only switch)
  ─────────────────────────────────────────────────────────────────────────
  newgrp developers                 # switch active group for current shell
  touch newfile                     # newfile owned by group developers
  exit                              # return to normal group
  (Does NOT add to /etc/group — only affects current session)

13.4 Shared Directories with Group Permissions

The SGID (Set Group ID) bit on a directory ensures that files created inside inherit the directory's group — the cornerstone of shared project directories on Linux servers.

📁 SGID Shared Directory — How anihpj Uses It
  Goal: nginx (www-data), gunicorn (anihpj), and deploy all share /var/www/anihpj

  SETUP:
  sudo groupadd -g 1500 webteam
  sudo usermod -aG webteam www-data
  sudo usermod -aG webteam anihpj
  sudo usermod -aG webteam deploy

  sudo chown -R root:webteam /var/www/anihpj
  sudo chmod 2775 /var/www/anihpj      ← 2 = SGID bit

  Permission breakdown of 2775:
  ┌──────────────────────────────────────────────────────────────────────┐
  │  2    7    7    5                                                    │
  │  │    │    │    └── Others: r-x (read + execute)                    │
  │  │    │    └─────── Group:  rwx (read + write + execute)            │
  │  │    └──────────── Owner:  rwx (read + write + execute)            │
  │  └───────────────── SGID bit: new files inherit group "webteam"     │
  └──────────────────────────────────────────────────────────────────────┘

  Result:
  deploy creates: /var/www/anihpj/app.py → owner=deploy, group=webteam  ✓
  nginx reads:    /var/www/anihpj/app.py → group=webteam → r-x access   ✓
  anihpj writes:  /var/www/anihpj/logs/  → group=webteam → rwx access   ✓

  Verify SGID is set (s in group execute position):
  ls -ld /var/www/anihpj
  drwxrwsr-x 3 root webteam 4096 May 24 22:00 /var/www/anihpj
              ↑ s = SGID set
🔒
Special Permission Bits
BitOn FileOn Directory
SUID (4)Runs as file owner (e.g. passwd)No effect
SGID (2)Runs as file's groupNew files inherit directory's group ✓
Sticky (1)No effectOnly owner can delete their files (e.g. /tmp)
⚙️
Set / Remove Special Bits
# Set SGID on directory
chmod g+s /var/www/anihpj
chmod 2775 /var/www/anihpj

# Set sticky bit (shared /tmp-like dir)
chmod +t /shared/uploads
chmod 1777 /shared/uploads

# Remove SGID
chmod g-s /var/www/anihpj

# Verify (look for s/S/t/T in ls -l)
ls -ld /var/www/anihpj
# drwxrwsr-x → SGID set, execute allowed
# drwxrwSr-x → SGID set, NO execute (S=uppercase)

14.1 Password Aging with chage

chage (change age) controls the lifecycle of a user's password — how long it is valid, when to warn the user, and what happens when it expires.

14.2 PAM — Pluggable Authentication Modules

PAM is a middleware layer between applications (login, ssh, su, sudo) and the actual authentication mechanism (password, LDAP, Kerberos). Every service that authenticates users has a PAM configuration file.

🔌 PAM Architecture — How Authentication Flows
  Application Layer         PAM Layer                    Backend
  ─────────────────        ─────────────────────         ─────────────────
  ┌──────────────┐         ┌─────────────────────┐       ┌──────────────┐
  │ sshd         │──────►  │ /etc/pam.d/sshd     │──────►│ pam_unix.so  │ (/etc/shadow)
  └──────────────┘         │  auth required ...  │       └──────────────┘
  ┌──────────────┐         └─────────────────────┘       ┌──────────────┐
  │ sudo         │──────►  ┌─────────────────────┐──────►│ pam_ldap.so  │ (LDAP/AD)
  └──────────────┘         │ /etc/pam.d/sudo      │       └──────────────┘
  ┌──────────────┐         └─────────────────────┘       ┌──────────────┐
  │ login        │──────►  ┌─────────────────────┐──────►│ pam_pwquality│ (complexity)
  └──────────────┘         │ /etc/pam.d/login     │       └──────────────┘
                           └─────────────────────┘       ┌──────────────┐
                                                          │ pam_faillock │ (lockout)
  /etc/pam.d/ key files:                                  └──────────────┘
  ├── common-auth        ← included by most services
  ├── common-account
  ├── common-password    ← password quality rules
  ├── common-session
  └── sshd, sudo, login, su   ← service-specific overrides
📄 PAM Configuration Line Syntax
  type    control   module-path         arguments
  ────────────────────────────────────────────────────────────────────────
  auth    required  pam_unix.so         nullok try_first_pass
  auth    requisite pam_pwquality.so    retry=3
  account required  pam_faillock.so     authsucc audit
  session optional  pam_systemd.so

  TYPE — what phase:
  ├── auth        Verify identity (password check)
  ├── account     Account validity (expired? locked?)
  ├── password    Password update rules
  └── session     Setup/teardown (mount homedirs, env vars)

  CONTROL — what to do with result:
  ├── required    Must succeed — but continue checking all modules
  ├── requisite   Must succeed — stop immediately on failure
  ├── sufficient  If success, skip remaining same-type modules
  └── optional    Failure is OK (informational only)

  Common modules:
  pam_unix.so        Standard password/shadow authentication
  pam_pwquality.so   Password complexity enforcement
  pam_faillock.so    Account lockout after N failed attempts
  pam_limits.so      Apply /etc/security/limits.conf
  pam_env.so         Set environment variables
🔒 pam_pwquality — Enforcing Password Complexity

Configure in /etc/security/pwquality.conf (or as module args):

# /etc/security/pwquality.conf
minlen = 12          # minimum length
dcredit = -1         # require at least 1 digit
ucredit = -1         # require at least 1 uppercase
lcredit = -1         # require at least 1 lowercase
ocredit = -1         # require at least 1 special char
difok = 5            # must differ by 5 chars from old password
retry = 3            # allow 3 attempts before failing

14.3 /etc/security/limits.conf — Resource Limits

Resource limits prevent individual users or services from consuming all system resources. They are enforced by the pam_limits.so PAM module at login time.

📊 limits.conf Format and Common Types
  domain     type    item      value
  ──────────────────────────────────────────────────────────────────────────
  alice      soft    nproc     100       # alice: max 100 processes (soft)
  alice      hard    nproc     200       # alice: absolute max 200 processes
  @developers soft   nofile    4096      # developers group: max 4096 open files
  *          hard    nofile    65536     # all users: hard limit 65536 files
  anihpj     soft    nproc     50        # anihpj service: max 50 processes
  anihpj     hard    memlock   unlimited # anihpj: unlimited memory locking

  DOMAIN options:
  ├── username     → specific user
  ├── @groupname   → all members of group
  └── *            → all users (except root)

  TYPE options:
  ├── soft   → advisory limit (user can increase up to hard limit)
  └── hard   → absolute ceiling (only root can exceed)

  ITEM (common):
  ┌──────────────┬──────────────────────────────────────────────────────┐
  │ nofile       │ Max open file descriptors (default: 1024, often low) │
  │ nproc        │ Max number of processes                               │
  │ memlock      │ Max locked memory (KB)                                │
  │ stack        │ Max stack size (KB)                                   │
  │ cpu          │ Max CPU time (minutes)                                │
  │ maxlogins    │ Max simultaneous logins                               │
  │ fsize        │ Max file size (KB)                                    │
  └──────────────┴──────────────────────────────────────────────────────┘

14.4 Account Security Best Practices

A well-hardened Linux server minimises attack surface by removing unnecessary accounts, locking down privilege escalation, and auditing who has access.

🔐 Security Audit Commands — Know Your System
  AUDIT CATEGORIES AND COMMANDS:
  ─────────────────────────────────────────────────────────────────────────
  1. Find privileged accounts:
     awk -F: '$3 == 0' /etc/passwd          # UID=0 accounts (only root is expected)
     grep -E '^sudo|^wheel' /etc/group       # members with sudo/wheel access
     grep -rh 'ALL=' /etc/sudoers /etc/sudoers.d/  # sudo rules

  2. Find weak/dangerous accounts:
     awk -F: '$2 == ""' /etc/shadow          # accounts with NO password
     awk -F: '$2 !~ /^[!*$]/' /etc/shadow    # accounts with active passwords
     awk -F: '$7 !~ /nologin|false/' /etc/passwd | awk -F: '$3 >= 1000'  # shell users

  3. Find inactive accounts:
     lastlog | grep 'Never logged in'        # accounts that never logged in
     lastlog -b 90                           # inactive for 90+ days

  4. Find orphaned files (user deleted but files remain):
     find / -nouser -o -nogroup 2>/dev/null

  5. Check locked/unlocked accounts:
     passwd -S -a 2>/dev/null | grep ' LK '  # locked accounts
     passwd -S -a 2>/dev/null | grep ' PS '  # active accounts
