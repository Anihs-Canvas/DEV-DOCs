1.1 The Problem That Created Linux

To understand Linux, you need to understand why it was created. The story begins in 1991 at the University of Helsinki, where a 21-year-old Finnish student named Linus Torvalds faced a problem: he wanted to learn about operating systems, but UNIX — the dominant OS of the time — was expensive and proprietary. Students simply couldn't afford it.

📖 Key Term: Kernel

The kernel is the core program of an operating system. It talks directly to hardware (CPU, RAM, disk, network) and manages resources. Linux is technically "just" a kernel — the GNU Project provided all the tools (shell, compiler, text editors) that made it a complete OS. This is why some people insist on calling it GNU/Linux.

At the same time, Richard Stallman had been working on the GNU Project since 1984 — creating free, open-source replacements for UNIX tools (compilers, editors, shell utilities). By 1991, GNU had everything... except a working kernel. Linus's kernel filled that exact gap. The combination — Linux kernel + GNU tools = a complete, free, open-source operating system — changed computing forever.

The "Everything is a File" Philosophy

This is the single most important concept in Linux. Everything — hardware devices, running processes, network connections, kernel settings — is represented as a file. This means you can use the same tools (cat, grep, echo) to interact with ANYTHING.

Everything is a File — Real Examples
  /dev/sda          → your hard drive (block device file)
  /dev/null         → a black hole (discard output forever)
  /dev/random       → random number generator device
  /proc/cpuinfo     → your CPU info (virtual kernel file)
  /proc/1234/       → all info about process with PID 1234
  /proc/net/tcp     → active TCP connections (virtual file)
  /sys/class/net/   → your network interfaces as files

  This unification means: cat, grep, echo, awk work on ALL of
  these. Same tool, hardware OR process OR network OR config.

1.3 Linux Distributions — Choosing the Right One

A Linux distribution (or "distro") is a complete operating system built from: the Linux kernel + GNU tools + a package manager + default software. Think of the kernel as the engine and the distribution as the entire car — different cars (distros) can use the same engine (kernel) but offer completely different experiences.

📖 Key Term: Distribution (Distro)

A distribution = Linux kernel + software selection + package manager + configuration defaults. Ubuntu, Rocky Linux, Debian, and Arch are all distributions. They all use the Linux kernel but differ in package managers, default software, release cycles, and target audiences.

1.4 The Linux Kernel — The Heart of the OS 🎯

The kernel is the core program that talks directly to hardware. It manages CPU time scheduling (which process runs when), RAM allocation (who gets memory), I/O (disk reads/writes), filesystem access, and networking. Without the kernel, nothing works — it's the bridge between your programs and the physical machine.

Kernel Layers — User Space vs Kernel Space

4.1 The Permission Model — Three Levels

Every file and directory in Linux has permissions for three levels: Owner (the user who owns it), Group (members of the file's group), and Other (everyone else). Three permission bits apply to each level: Read (r), Write (w), and Execute (x).

Permission String Decoded — Every Bit Explained
   - r w x   r - x   r - -
   │ │ │ │   │ │ │   │ │ │
   │ └─┴─┘   └─┴─┘   └─┴─┘
   │  OWNER   GROUP   OTHER
   │
   └─ File type: - = regular, d = dir, l = link

  r = Read    (4) → view file contents / list directory
  w = Write   (2) → modify file / create files in directory
  x = Execute (1) → run as program / enter directory
  - = No permission (0)

  EXAMPLE: -rwxr-xr--
    Owner  (rwx) = 7  → can read, write, execute
    Group  (r-x) = 5  → can read and execute
    Other  (r--) = 4  → can only read
    Written as octal: 754
👤
Owner (u)

The user who owns the file. Typically the creator. Only root can change ownership.

👥
Group (g)

Members of the file's group. Used for team access to shared directories.

🌍
Other (o)

Everyone else on the system. Usually the most restricted level.

🔢
Octal

r=4, w=2, x=1. Add them: rwx=7, r-x=5, r--=4. chmod 754 = rwxr-xr--.

4.2 chmod — Changing Permissions 🎯

PermissionOctalUse Case
-rw-------600Private SSH key (~/.ssh/id_rsa), .env secrets
-rw-r--r--644Config files, static HTML, source code
-rwxr-xr-x755Scripts, directories, executables
drwx------700Private directory (home dir)
drwxr-xr-x755Public-read directory (/var/www)
-rwxrwxrwx777⚠️ DANGEROUS — never use in production!
chmod for anihpj — Correct Permissions
  chmod 644 /var/www/anihpj/*.py      # source files (owner rw, others r)
  chmod 755 /var/www/anihpj/           # project directory (must be executable to cd into)
  chmod 600 /var/www/anihpj/.env       # secrets! owner-only read/write
  chmod 700 /home/anihpj/.ssh/         # SSH directory — private
  chmod 600 /home/anihpj/.ssh/id_rsa   # private key — EXTREMELY restrictive
⚠️ 777 = "Everyone Can Do Everything" — NEVER in Production

chmod 777 gives read, write, and execute to every user on the system. It's the most common security mistake beginners make. If you're tempted to use 777 to "fix" a permission problem, you're masking the real issue. Find the correct owner/group and use the minimum permissions needed.

4.3 chown & chgrp — Changing Ownership 🎯

Setting Up anihpj Ownership Correctly
  # Static files: anihpj user owns, www-data group can read
  chown -R anihpj:www-data /var/www/anihpj/
  chmod -R 750 /var/www/anihpj/

  # .env: ONLY anihpj user can read (not even www-data!)
  chown anihpj:anihpj /var/www/anihpj/.env
  chmod 600 /var/www/anihpj/.env

  # Verify:
  ls -la /var/www/anihpj/.env
  # → -rw------- 1 anihpj anihpj 512 May 24 /var/www/anihpj/.env

  # Add yourself to www-data group for read access:
  usermod -aG www-data owner
📖 Only Root Can Change Owner

Regular users can change the group of files they own (to a group they belong to), but only root can change the owner. If you get "Operation not permitted" from chown, you need sudo.

4.4 SUID, SGID, Sticky Bit 🎯

The Three Special Permission Bits
  SUID (Set User ID) — chmod 4xxx or chmod u+s
    File runs as its OWNER, not the caller.
    $ ls -la /usr/bin/passwd
    -rwsr-xr-x 1 root root 68208 /usr/bin/passwd
         ^── 's' = SUID: runs as root even when called by normal users

  SGID (Set Group ID) — chmod 2xxx or chmod g+s
    New files inherit the DIRECTORY'S group (not the creator's).
    Perfect for shared team directories.
    $ ls -la /projects/
    drwxr-sr-x 2 root developers 4096 /projects/anihpj/
           ^── 's' = SGID: new files auto-get 'developers' group

  Sticky Bit — chmod 1xxx or chmod +t
    Only the FILE OWNER can delete their files from the directory.
    $ ls -la /tmp
    drwxrwxrwt 12 root root 4096 /tmp
              ^── 't' = Sticky: you can't delete other people's files
💡 Find SUID Files (Security Audit)

find / -perm -4000 -type f 2>/dev/null — lists all SUID binaries. SUID files are potential security risks because they run with elevated privileges. Regularly audit this list on production servers.

4.5 umask — Default Permission Mask 🎯

How umask Works — Subtraction from Maximum
  New file max = 666 (files are NEVER executable by default)
  New dir  max = 777

  umask = 022 (Ubuntu default):
    File: 666 - 022 = 644  (-rw-r--r--)
    Dir:  777 - 022 = 755  (drwxr-xr-x)

  umask = 027 (more restrictive):
    File: 666 - 027 = 640  (-rw-r-----)  ← group read, other nothing
    Dir:  777 - 027 = 750  (drwxr-x---)

  umask = 077 (most restrictive):
    File: 666 - 077 = 600  (-rw-------)  ← owner only
    Dir:  777 - 077 = 700  (drwx------)

  For anihpj service user: set umask 027 in ~/.bashrc
