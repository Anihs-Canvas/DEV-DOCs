1.1 The Problem That Created Linux

To understand Linux, you need to understand why it was created. The story begins in 1991 at the University of Helsinki, where a 21-year-old Finnish student named Linus Torvalds faced a problem: he wanted to learn about operating systems, but UNIX — the dominant OS of the time — was expensive and proprietary. Students simply couldn't afford it.

📖 Key Term: Kernel

The kernel is the core program of an operating system. It talks directly to hardware (CPU, RAM, disk, network) and manages resources. Linux is technically "just" a kernel — the GNU Project provided all the tools (shell, compiler, text editors) that made it a complete OS. This is why some people insist on calling it GNU/Linux.

At the same time, Richard Stallman had been working on the GNU Project since 1984 — creating free, open-source replacements for UNIX tools (compilers, editors, shell utilities). By 1991, GNU had everything... except a working kernel. Linus's kernel filled that exact gap. The combination — Linux kernel + GNU tools = a complete, free, open-source operating system — changed computing forever.

🌍 The Open Source Philosophy — Why It Matters for Your Career

Linux isn't just an operating system — it's the most successful example of the open source development model. Understanding this philosophy is essential for any IT professional because it shapes how modern infrastructure is built, maintained, and secured.

👁️
Transparency = Security

With proprietary software, you trust the vendor. With open source, millions of eyes review the code. Security vulnerabilities are found and fixed faster. For anihpj in production, this means the entire stack — from the kernel to Nginx to PostgreSQL — has been audited by thousands of experts worldwide.

🔧
You Can Fix It Yourself

When something breaks in proprietary software, you wait for the vendor. In Linux, you can read the source code, understand the bug, apply a patch, and recompile — all without waiting. This is why companies like Google, Facebook, and Amazon run Linux: they need that level of control at scale.

💰
No License Costs, No Vendor Lock-In

Deploying anihpj on Linux means zero per-server licensing. Need to scale from 1 to 100 servers? Just spin them up — no CALs, no per-core fees, no license audits. This is why startups and enterprises alike build on Linux.

🌐
The Standard Platform

Linux is the lingua franca of cloud computing. Docker containers run Linux. Kubernetes orchestrates Linux. AWS, GCP, and Azure all run Linux. Master Linux and you've mastered the platform that powers the entire internet.

📖 How the Linux Ecosystem is Organized

The Linux Foundation (founded 2000) employs Linus Torvalds and other key developers. It oversees Linux kernel development, provides the LFCS/CKA/CKAD certifications, and hosts hundreds of open source projects including Kubernetes, Node.js, and Hyperledger. The kernel.org website is where the official Linux kernel source code lives. Thousands of contributors from competing companies (Intel, Red Hat, Google, Samsung, Oracle) collaborate openly — this is what makes Linux unstoppable.

📜 The GPL License — Why Linux is Forever Free

Linux is released under the GNU General Public License v2 (GPLv2). This license guarantees four essential freedoms: (1) run the program for any purpose, (2) study and modify the source code, (3) redistribute copies, (4) distribute modified versions. The key provision — copyleft — means anyone who distributes modified Linux must also release their modifications under GPL. This prevents companies from taking Linux, improving it, and keeping those improvements proprietary. It's the legal mechanism that has kept Linux free and open for 30+ years.

The "Everything is a File" Philosophy

This is the single most important concept in Linux. Everything — hardware devices, running processes, network connections, kernel settings — is represented as a file. This means you can use the same tools (cat, grep, echo) to interact with ANYTHING.

Everything is a File — Real Examples
  /dev/sda          → your hard drive (block device file)
  /dev/null         → a black hole (discard output forever)
  /dev/random       → random number generator device
  /proc/cpuinfo     → your CPU info (virtual kernel file)
  /proc/1234/       → all info about process with PID 1234
  /proc/net/tcp     → active TCP connections (virtual file)
  /sys/class/net/   → your network interfaces as files

  This unification means: cat, grep, echo, awk work on ALL of
  these. Same tool, hardware OR process OR network OR config.

1.3 Linux Distributions — Choosing the Right One

A Linux distribution (or "distro") is a complete operating system built from: the Linux kernel + GNU tools + a package manager + default software. Think of the kernel as the engine and the distribution as the entire car — different cars (distros) can use the same engine (kernel) but offer completely different experiences.

I/O Redirection & Pipes — The Power of Connecting Commands 🎯

One of Linux's superpowers is the ability to chain commands together using pipes and redirect their input/output. This is tested heavily on the LFCS exam and is essential for real-world troubleshooting.

I/O Redirection — Complete Reference
  >  file     → Redirect stdout to file (OVERWRITES)
  >> file     → Redirect stdout to file (APPENDS)
  2> file     → Redirect stderr (errors) to file
  2>&1        → Merge stderr into stdout (send errors to same place)
  &> file     → Redirect BOTH stdout and stderr to file (Bash shorthand)
  < file      → Use file as stdin (input) for a command
  |           → PIPE: send stdout of left command to stdin of right
  |&          → Pipe BOTH stdout and stderr to next command

  ANIHPJ PRODUCTION EXAMPLES:
    # Save deployment output AND errors to a log:
    python manage.py migrate >> /var/log/anihpj/deploy.log 2>&1

    # Count running gunicorn workers:
    ps aux | grep gunicorn | grep -v grep | wc -l

    # Find which port nginx is listening on:
    ss -tulnp | grep nginx

    # Discard all error messages (send to /dev/null):
    find / -name "*.pyc" 2>/dev/null

    # Top 10 IPs hitting anihpj (from nginx access log):
    awk '{print $1}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head -10
⚠️ > vs >> — The #1 Redirection Mistake

> file OVERWRITES the file completely — all previous content is lost. >> file APPENDS to the end. Beginners often use > when they mean >> and accidentally destroy log files or configuration data. Always double-check!

4.1 The Permission Model — Three Levels

Every file and directory in Linux has permissions for three levels: Owner (the user who owns it), Group (members of the file's group), and Other (everyone else). Three permission bits apply to each level: Read (r), Write (w), and Execute (x).

Permission String Decoded — Every Bit Explained
   - r w x   r - x   r - -
   │ │ │ │   │ │ │   │ │ │
   │ └─┴─┘   └─┴─┘   └─┴─┘
   │  OWNER   GROUP   OTHER
   │
   └─ File type: - = regular, d = dir, l = link

  r = Read    (4) → view file contents / list directory
  w = Write   (2) → modify file / create files in directory
  x = Execute (1) → run as program / enter directory
  - = No permission (0)

  EXAMPLE: -rwxr-xr--
    Owner  (rwx) = 7  → can read, write, execute
    Group  (r-x) = 5  → can read and execute
    Other  (r--) = 4  → can only read
    Written as octal: 754

The user who owns the file. Typically the creator. Only root can change ownership.

👥

🌍

Everyone else on the system. Usually the most restricted level.

🔢

r=4, w=2, x=1. Add them: rwx=7, r-x=5, r--=4. chmod 754 = rwxr-xr--.

4.2 chmod — Changing Permissions 🎯

There are two ways to use chmod: symbolic mode (letters) and octal mode (numbers). Both are tested on the LFCS exam.

chmod — Symbolic Mode vs Octal Mode
  SYMBOLIC MODE (letters — intuitive, good for single changes):
    chmod u+x script.sh       # Add execute for user (owner)
    chmod g-w file.txt        # Remove write from group
    chmod o=rx dir/           # Set other to exactly r-x
    chmod a+r *.py            # Add read for ALL (user+group+other)
    chmod ug=rwx,o=rx script  # User+group=rwx, other=rx

  OCTAL MODE (numbers — precise, set ALL bits at once):
    chmod 755 script.sh       # rwxr-xr-x (common for executables)
    chmod 644 file.txt        # rw-r--r-- (common for config files)
    chmod 600 secret.key      # rw------- (private keys/secrets)
    chmod 750 dir/            # rwxr-x--- (group access, no other)

  RECURSIVE (apply to all files/dirs under a path):
    chmod -R 755 /var/www/anihpj/   # ⚠️ makes ALL files executable!
    find /var/www -type f -exec chmod 644 {} \;  # files only
    find /var/www -type d -exec chmod 755 {} \;  # dirs only

4.3 chown & chgrp — Changing Ownership 🎯

📖 Only Root Can Change Owner

Regular users can change the group of files they own (to a group they belong to), but only root can change the owner. If you get "Operation not permitted" from chown, you need sudo.

4.4 SUID, SGID, Sticky Bit 🎯

The Three Special Permission Bits
  SUID (Set User ID) — chmod 4xxx or chmod u+s
    File runs as its OWNER, not the caller.
    $ ls -la /usr/bin/passwd
    -rwsr-xr-x 1 root root 68208 /usr/bin/passwd
         ^── 's' = SUID: runs as root even when called by normal users

  SGID (Set Group ID) — chmod 2xxx or chmod g+s
    New files inherit the DIRECTORY'S group (not the creator's).
    Perfect for shared team directories.
    $ ls -la /projects/
    drwxr-sr-x 2 root developers 4096 /projects/anihpj/
           ^── 's' = SGID: new files auto-get 'developers' group

  Sticky Bit — chmod 1xxx or chmod +t
    Only the FILE OWNER can delete their files from the directory.
    $ ls -la /tmp
    drwxrwxrwt 12 root root 4096 /tmp
              ^── 't' = Sticky: you can't delete other people's files
💡 Find SUID Files (Security Audit)

find / -perm -4000 -type f 2>/dev/null — lists all SUID binaries. SUID files are potential security risks because they run with elevated privileges. Regularly audit this list on production servers.

🔬 Beyond Basics: File Attributes — Making Files Immutable

Beyond standard permissions, Linux supports extended file attributes that add another layer of protection. The most powerful is the immutable attribute — even root cannot modify or delete an immutable file without first removing the attribute.

File Attributes — chattr & lsattr
  lsattr file              → List extended attributes on a file
  chattr +i file           → Make file IMMUTABLE (cannot modify, delete, rename, or link)
  chattr -i file           → Remove immutable attribute
  chattr +a file           → Append-only (can only add data, cannot modify existing)
  chattr +i /etc/ssh/sshd_config   → Lock SSH config from tampering
  lsattr /etc/ssh/sshd_config      → ----i---------e-- /etc/ssh/sshd_config
  # The 'i' flag means: even root cannot delete this file without chattr -i first!

  PRODUCTION SECURITY:
    chattr +i /etc/resolv.conf     → Prevent DNS hijacking by malware
    chattr +i /etc/shadow          → Prevent unauthorized password changes
    chattr +a /var/log/anihpj/app.log  → Log file: append-only (can't erase evidence!)

  ⚠️ WARNING: chattr +i makes a file truly immutable. You must chattr -i first
     before any update, including system package upgrades. Use sparingly.

🔬 Beyond Basics: Access Control Lists (ACLs) — Preview

Standard Linux permissions (owner-group-other) only allow three levels of access. What if you need to give Alice read access, Bob write access, and no one else anything? Standard permissions can't do this — but ACLs can. This is covered in detail in Chapter 45, but here's a preview so you understand what's possible beyond basic permissions:

ACLs vs Standard Permissions — The Difference
  STANDARD PERMISSIONS (only 3 levels):
    -rw-r----- 1 root developers /projects/anihpj/config.ini
    Owner(root)=rw, Group(developers)=r, Other=nothing
    ❌ Can't give Alice (in developers) write but Bob (also in developers) read-only

  WITH ACLs (per-user, per-group control):
    $ getfacl /projects/anihpj/config.ini
    user::rw-           # Owner permissions
    user:alice:rw-      # Alice gets read+write
    user:bob:r--        # Bob gets read only
    group::r--          # Group default
    mask::rw-           # Maximum for named users/groups
    other::---          # Everyone else gets nothing

    setfacl -m u:alice:rw /projects/anihpj/config.ini   # Give Alice rw
    setfacl -m u:bob:r /projects/anihpj/config.ini      # Give Bob read
    getfacl /projects/anihpj/config.ini                  # Verify ACLs

4.5 umask — Default Permission Mask 🎯

How umask Works — Subtraction from Maximum
  New file max = 666 (files are NEVER executable by default)
  New dir  max = 777

  umask = 022 (Ubuntu default):
    File: 666 - 022 = 644  (-rw-r--r--)
    Dir:  777 - 022 = 755  (drwxr-xr-x)

  umask = 027 (more restrictive):
    File: 666 - 027 = 640  (-rw-r-----)  ← group read, other nothing
    Dir:  777 - 027 = 750  (drwxr-x---)

  umask = 077 (most restrictive):
    File: 666 - 077 = 600  (-rw-------)  ← owner only
    Dir:  777 - 077 = 700  (drwx------)

  For anihpj service user: set umask 027 in ~/.bashrc

  for i in {1..10}; do
      echo "Iteration $i"
  done

  # WHILE: continue while condition is true
  while systemctl is-active --quiet anihpj; do
      echo "Waiting for anihpj to stop..."
      sleep 2
  done

  # WHILE READ: process file line by line
  while IFS= read -r line; do
      echo "Line: $line"
  done < /etc/passwd

  # UNTIL: continue until condition becomes true
  until curl -s http://localhost:8000/health; do
      echo "Waiting for health check..."
      sleep 3
  done

  set -euo pipefail
  LOGFILE="/var/log/anihpj/deploy_$(date +%Y%m%d_%H%M%S).log"

      die "Migrations failed, rolled back to $OLD_COMMIT"

  log "📂 Collecting static files..."
  python manage.py collectstatic --noinput || log "⚠️ collectstatic warning"

  log "🔄 Restarting services..."

  sudo systemctl reload nginx || log "⚠️ nginx reload warning"

  log "✅ Deployment complete!"
  # Send notification
  echo "anihpj $BRANCH deployed at $(date)" | mail -s "Deploy OK" admin@anihpj.com

11.2 Backup Script

Complete Database + Source Code Backup with Rotation
  #!/bin/bash
  set -euo pipefail

  BACKUP_ROOT="/backups/anihpj"
  DATE=$(date +%Y%m%d_%H%M%S)
  BACKUP_DIR="$BACKUP_ROOT/$DATE"
  RETENTION_DAYS=7

  mkdir -p "$BACKUP_DIR"

  echo "💾 Starting backup to $BACKUP_DIR"

  # 1. PostgreSQL dump
  echo "🗄️ Dumping PostgreSQL..."
  sudo -u postgres pg_dump anihpj > "$BACKUP_DIR/database.sql"
  gzip "$BACKUP_DIR/database.sql"
  echo "   → database.sql.gz ($(du -h "$BACKUP_DIR/database.sql.gz" | cut -f1))"

  # 2. Source code archive
  echo "📦 Archiving source code..."
  tar -czf "$BACKUP_DIR/source.tar.gz" \
      --exclude='venv' --exclude='__pycache__' --exclude='*.pyc' \
      /var/www/anihpj/
  echo "   → source.tar.gz ($(du -h "$BACKUP_DIR/source.tar.gz" | cut -f1))"

  # 3. Environment file
  echo "🔐 Backing up .env..."
  cp /var/www/anihpj/.env "$BACKUP_DIR/env.backup"
  chmod 600 "$BACKUP_DIR/env.backup"

  # 4. Sync to remote
  echo "☁️ Syncing to remote..."
  rsync -avz --delete "$BACKUP_ROOT/" backup@remote:/backups/anihpj/ \
      || echo "⚠️ Remote sync failed (non-fatal)"

  # 5. Rotate old backups
  echo "🧹 Rotating backups older than $RETENTION_DAYS days..."
  find "$BACKUP_ROOT" -maxdepth 1 -type d -mtime +$RETENTION_DAYS -exec rm -rf {} \;

  echo "✅ Backup complete: $BACKUP_DIR"

11.3 Health Check Script

Complete Health Check — Usable with Nagios/Icinga/Zabbix
  #!/bin/bash
  # Exit 0 = healthy, Exit 1 = warning, Exit 2 = critical
  ISSUES=0
  WARNINGS=0

  check() {
      local desc="$1"
      local cmd="$2"
      local level="${3:-CRIT}"
      if eval "$cmd"; then
          echo "✅ $desc"
      else
          if [ "$level" = "WARN" ]; then
              echo "⚠️ $desc"
              ((WARNINGS++))
          else
              echo "❌ $desc"
              ((ISSUES++))
          fi
      fi
  }

  echo "=== anihpj Health Check: $(date) ==="

  # Nginx
  check "Nginx running" \
      "systemctl is-active --quiet nginx"

  # Gunicorn
  check "Gunicorn running" \
      "systemctl is-active --quiet anihpj"

  # HTTP response
  check "HTTP 200 on port 80" \
      "curl -sf -o /dev/null http://localhost:80/"

  # PostgreSQL
  check "PostgreSQL accepting connections" \
      "sudo -u postgres pg_isready -q"

  # Disk usage
  check "Disk usage < 80%" \
      '[ $(df / | awk "NR==2{print \$5}" | tr -d "%") -lt 80 ]' \
      "WARN"

  # Memory
  check "Memory free > 10%" \
      '[ $(free | awk "/^Mem:/{printf \"%.0f\", \$4/\$2*100}") -gt 10 ]' \
      "WARN"

  echo "=== Result: ${ISSUES} critical, ${WARNINGS} warnings ==="

  if [ $ISSUES -gt 0 ]; then
      exit 2   # Critical
  elif [ $WARNINGS -gt 0 ]; then
      exit 1   # Warning
  else
      exit 0   # All healthy
  fi

  #!/bin/bash
  # rotate_logs.sh — compress old logs, delete ancient ones

  LOG_DIR="/var/log/anihpj"
  COMPRESS_DAYS=7
  DELETE_DAYS=30

  echo "🔄 Rotating logs in $LOG_DIR"

Q5
In the backup script, why do we use rsync -avz --delete instead of just scp?
Click to reveal answer
✅ Answer

rsync only transfers changed files (delta transfer), -a preserves permissions/ownership/timestamps, -z compresses during transfer, --delete removes remote files that no longer exist locally. scp always transfers everything and doesn't handle deletion or file attributes as well.
