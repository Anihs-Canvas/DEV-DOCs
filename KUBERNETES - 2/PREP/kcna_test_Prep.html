🚨 Critical Do's & Don'ts During The Exam
  • ✅ DO: Use kubectl create ... --dry-run=client -o yaml to generate YAML in seconds — never type manifests from scratch.
  • ✅ DO: Run kubectl config use-context <given-context> as the FIRST command for every task. Wrong context = 0 points.
  • ✅ DO: Use kubectl explain <resource> --recursive when you forget a field name. It's faster than searching docs.
  • ✅ DO: Create a debug pod: kubectl run test --rm -it --image=busybox -- sh to test DNS, connectivity, and curl from inside the cluster.
  • ❌ DON'T: Spend more than 7 minutes on any single task. Flag it, move on, return with fresh eyes.
  • ❌ DON'T: Forget to set the namespace. Many tasks require -n flag. Use kubectl config set-context --current --namespace=<ns> to save typing.
  • ❌ DON'T: Leave any task blank. Even partial work (creating the namespace, writing partial YAML) may earn partial credit.
  • ❌ DON'T: Use kubectl delete pod on a static pod — you must delete the manifest file from /etc/kubernetes/manifests/.

K8s Fundamentals Q1 of 200
What is a container? Choose the most accurate description of how containers work in Linux.
A) A lightweight virtual machine that runs its own guest operating system kernel
B) A process isolated using Linux namespaces and constrained by cgroups — it shares the host kernel, NOT a mini VM
C) A compressed archive of application files that runs in a sandboxed interpreter
D) A hardware-level virtualization technology that partitions CPU and memory for each application
✅ Correct Answer: B

A container is a process — not a VM. It uses Linux namespaces to isolate what the process can see (PID, network, mount, UTS, IPC, user, cgroup namespaces) and cgroups (control groups) to limit what resources it can use (CPU, memory, disk I/O, PIDs).

K8s Fundamentals Q2 of 200
What is the OCI (Open Container Initiative) and what does it standardize?
A) A Linux kernel module that enables container isolation through namespaces and cgroups
B) A Kubernetes API group that defines how pods communicate with container runtimes
C) An open governance structure that maintains three specifications: image-spec (how images are built), runtime-spec (how containers run), and distribution-spec (how images are shared via registries)
D) A Docker-specific file format (.oci) used to define multi-container applications for deployment
✅ Correct Answer: C

The Open Container Initiative (OCI) is a Linux Foundation project that creates open industry standards for containers. It defines three specifications: image-spec (how container images are packaged — layers, manifests, configs), runtime-spec (how containers are executed — the lifecycle from creation to deletion, implemented by runc), and distribution-spec (how container images are pushed/pulled between registries — the HTTP API that Docker Hub, ECR, GCR, and Harbor all implement).

K8s Fundamentals Q3 of 200
How do Dockerfile layers work, and why does the order of instructions matter?
A) Each instruction (FROM, RUN, COPY, etc.) creates a new read-only layer stacked on top of the previous one. Layers are cached — if a layer hasn't changed, Docker reuses it. This is why COPY requirements.txt before COPY . speeds up builds: dependency installation is cached when only source code changes
B) All Dockerfile instructions are merged into a single compressed layer at build time; the order of instructions has no effect on caching or image size
C) Each instruction creates a separate writable layer that persists after the container stops, allowing changes to be saved back to the image automatically
D) Layers are created only by RUN instructions; COPY and ADD instructions modify the existing layer in-place without creating new layers
✅ Correct Answer: A

Every instruction in a Dockerfile produces a new read-only layer. These layers are stacked using a Union Filesystem (OverlayFS). Docker caches each layer — if a layer and all layers above it haven't changed, Docker reuses them from cache, dramatically speeding up rebuilds.

📝 Detailed Explanation
Dockerfile Layer Caching — Why Order Matters
  ❌ BAD ORDER (slow rebuilds — cache invalidated early):
  FROM python:3.12-slim          ← Layer 1 (rarely changes)
  COPY . /app                    ← Layer 2 ❌ changes every code edit!
  RUN pip install -r requirements.txt  ← Layer 3 MUST rebuild
  CMD ["gunicorn", "..."]        ← Layer 4
  → Every code change invalidates Layer 2, so Layer 3 ALWAYS reruns

  ✅ GOOD ORDER (fast rebuilds — cache preserved):
  FROM python:3.12-slim          ← Layer 1 (cached)
  COPY requirements.txt /app/    ← Layer 2 ✅ only changes when deps change
  RUN pip install -r /app/requirements.txt  ← Layer 3 ✅ cached!
  COPY . /app                    ← Layer 4 ← only THIS changes on code edits
  CMD ["gunicorn", "..."]        ← Layer 5 (cached)
  → Code edits only invalidate Layer 4. Layers 1-3 come from cache!

  LAYER CACHING RULES:
  ┌────────────────────────────────────────────────────────────┐
  │ 1. If a layer changes → ALL subsequent layers must rebuild │
  │ 2. Put SLOW-CHANGING instructions FIRST (OS, deps)         │
  │ 3. Put FAST-CHANGING instructions LAST (source code)       │
  │ 4. This is why COPY requirements.txt BEFORE COPY .         │
  └────────────────────────────────────────────────────────────┘

For anihpj/jobpost, the optimized Dockerfile puts COPY requirements.txt and RUN pip install before COPY . /app. When a developer changes the Django views but not the dependencies, only the final COPY layer rebuilds — saving 2-3 minutes per build. This is also why images share layers: if 10 microservices all use FROM python:3.12-slim, that base layer is stored ONCE on disk.

K8s Fundamentals Q4 of 200
What is a multi-stage Docker build and why is it used?
A) A technique where multiple Dockerfiles are combined at runtime to create a single running container
B) A Dockerfile with multiple FROM statements — each starts a new stage. The first stage(s) build/compile the application, and the final stage copies ONLY the needed artifacts, producing a minimal runtime image without build tools, compilers, or source code
C) A Docker Compose feature that orchestrates multiple containers (web, database, cache) in a single build pipeline
D) A CI/CD pattern where the same image is deployed to dev, staging, and production stages with different environment variables
✅ Correct Answer: B

A multi-stage build uses multiple FROM statements in a single Dockerfile. Each FROM begins a new stage with a fresh base image. The build stage(s) contain compilers, SDKs, and all dependencies needed to compile the app. The final runtime stage uses COPY --from=builder to grab only the compiled artifacts — resulting in a much smaller, more secure image.

🟢 Storage Issues — PVC, PV, StorageClass, and Mount Failures

Storage is often the FIRST thing to break because it involves multiple components: PVC → StorageClass → Provisioner → PV → Mount. When any link in this chain fails, your pod can't start or your data is at risk.

📌 ST1–ST3: PVC Binding Failures

ST1
💾 CATEGORY 1: STORAGE — Issue ST1
PVC Stuck in Pending State — No PV Bound

🔍 Symptom: kubectl get pvc shows STATUS: Pending indefinitely. kubectl describe pvc shows "no persistent volumes available for this claim." The anihpj-db PostgreSQL pod can't start because its PVC won't bind.

  kubectl get pvc
  NAME         STATUS    VOLUME   CAPACITY   STORAGECLASS   AGE
  anihpj-pvc   Pending                      fast-ssd       5m

  kubectl describe pvc anihpj-pvc
  Events:
    Warning  VolumeBinding  no persistent volumes available for this claim
    Warning  VolumeBinding  storageclass.storage.k8s.io "fast-ssd" not found
🔴5 Most Likely Causes
  1. StorageClass does not exist: The PVC references a StorageClass that hasn't been created. kubectl get sc — if "fast-ssd" is missing, create it or fix the PVC's storageClassName.
  2. No matching PV available: In static provisioning, no PV matches the PVC's storage size, access mode, or selector. kubectl get pv — check capacity and accessModes.
  3. StorageClass provisioner not installed: The CSI driver (e.g., ebs.csi.aws.com) is not deployed. kubectl get pods -n kube-system | grep csi — provisioner pods must be Running.
  4. Access mode mismatch: PVC requests ReadWriteMany but only ReadWriteOnce PVs exist. Check kubectl get pv -o yaml | grep -A2 accessModes.
  5. StorageClass has volumeBindingMode: WaitForFirstConsumer and no pod uses the PVC yet. The PV is only created when a pod actually references the PVC.
🟡5 Less Likely Causes
  1. CSI driver pod CrashLoopBackOff — provisioner can't create volumes
  2. Cloud provider API rate limiting — too many PVCs created simultaneously
  3. PVC selector labels don't match any PV labels
  4. Node where CSI driver runs has taint without toleration
  5. storageClassName: "" (empty string, not null!) — requests a PV with NO StorageClass, but all PVs have one
🟣5 New Cluster Causes
  1. No default StorageClass set: kubectl get sc — look for "(default)". Without it, PVCs without storageClassName won't bind. Set: kubectl patch sc <name> -p '{"metadata":{"annotations":{"storageclass.kubernetes.io/is-default-class":"true"}}}'
  2. CSI driver not yet installed — common in fresh kubeadm clusters
  3. Cloud credentials not configured for CSI driver to provision volumes
  4. RBAC for CSI driver service account missing
  5. kubelet missing --cloud-provider flag for legacy in-tree provisioners
🔍 What to Look At:
kubectl get sc,pv,pvc --all-namespaces The full storage stack in one view — see StorageClass, PV, and PVC together.
kubectl describe pvc <name> The Events section tells you exactly why binding failed — always read the events first.
🎯 #1 Root Cause: StorageClass does not exist or is misnamed. The PVC references a StorageClass that hasn't been created — the most common CKA exam pitfall.
🔧 How to Solve:
1. Verify StorageClass exists kubectl get sc If the StorageClass referenced by the PVC is missing, create it or fix the PVC's storageClassName.
2. Check provisioner and parameters kubectl describe sc <name> Verify the provisioner is correct and the CSI driver is installed and running.
3. Static provisioning kubectl get pv Create a PV matching the PVC's requested size, accessMode, and selector labels.
4. Dynamic provisioning Install the CSI driver: kubectl apply -f <csi-driver-url>. Verify CSI pods are Running in kube-system.
5. Set default StorageClass kubectl patch sc <name> -p '{"metadata":{"annotations":{"storageclass.kubernetes.io/is-default-class":"true"}}}' PVCs without an explicit storageClassName will use the default.
💡 Personal Advice:
Always verify StorageClass FIRST. The #1 PVC issue on the CKA exam is a missing or misnamed StorageClass. Run kubectl get sc before writing any PVC YAML.
Empty string is NOT null. storageClassName: "" Requests a PV with NO StorageClass — different from omitting the field entirely. Know this distinction.
CSI driver must be Running. Even with correct StorageClass, if the CSI provisioner pod is CrashLoopBackOff, no volumes will be created.
WaitForFirstConsumer delays binding. If volumeBindingMode is WaitForFirstConsumer, the PV is only created when a pod actually uses the PVC. Don't mistake this for a failure.

M.1 — etcd Backup & Restore (Full TLS Flags)
1

Backup:

ETCDCTL_API=3 etcdctl --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  snapshot save /opt/etcd-backup.db

Restore:

ETCDCTL_API=3 etcdctl --data-dir=/var/lib/etcd-restore \
  snapshot restore /opt/etcd-backup.db

⚠️ After restore: Update etcd static pod manifest (/etc/kubernetes/manifests/etcd.yaml) to point --data-dir to the new path, then restart kubelet. Also update the --initial-cluster-token to a new value.
