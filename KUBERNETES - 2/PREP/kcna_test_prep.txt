    🐳 DOCKERFILE PREVIEW (Multi-stage, Distroless):
    # Stage 1: Builder
    FROM python:3.12-slim@sha256:abc... AS builder
    WORKDIR /app
    COPY requirements.txt .
    RUN pip install --no-cache-dir -r requirements.txt
    COPY . .

    # Stage 2: Runtime (distroless — no shell, no package manager, minimal CVEs)
    FROM gcr.io/distroless/python3-debian12:nonroot
    COPY --from=builder /usr/local/lib/python3.12/site-packages /usr/local/lib/python3.12/site-packages
    COPY --from=builder /app /app
    WORKDIR /app
    USER 1000:1000
    CMD ["gunicorn", "anihpj.wsgi:application", "--bind", "0.0.0.0:8000"]

    🔬 UNDER THE HOOD 1.1: What Actually IS a Container?
    ┌─────────────────────────────────────────────────────────────────┐
    │                                                                 │
    │  A container is NOT a lightweight VM. It's a PROCESS with       │
    │  isolation. Here's what happens when you run a container:        │
    │                                                                 │
    │  LINUX NAMESPACES (7 types — each isolates something):          │
    │  ┌────────────────────────────────────────────────────────┐    │
    │  │ PID namespace  → Container sees only its own processes │    │
    │  │ NET namespace  → Container has its own IP, ports       │    │
    │  │ MNT namespace  → Container has its own filesystem      │    │
    │  │ UTS namespace  → Container has its own hostname        │    │
    │  │ IPC namespace  → Isolated inter-process communication  │    │
    │  │ USER namespace → Container's root ≠ host's root        │    │
    │  │ CGROUP namespace → Container sees its own cgroup limits│    │
    │  └────────────────────────────────────────────────────────┘    │
    │                                                                 │
    │  CGROUPS (Control Groups — limit what containers can use):     │
    │  ┌────────────────────────────────────────────────────────┐    │
    │  │ cpu.max        → "use at most 2 CPU cores"             │    │
    │  │ memory.max     → "use at most 512MB RAM"               │    │
    │  │ blkio.max      → "use at most 100 IOPS"                │    │
    │  │ pids.max       → "at most 100 processes"               │    │
    │  └────────────────────────────────────────────────────────┘    │
    │                                                                 │
    │  CONTAINER = namespaces (what you can see) + cgroups            │
    │             (what you can use) + rootfs (your files)            │
    │                                                                 │
    │  This is why containers start in milliseconds (no OS boot!)     │
    │  and why they are lightweight (share host kernel).              │
    └─────────────────────────────────────────────────────────────────┘

    🔄 Deployment Rolling Update Step-by-Step:
    ┌─────────────────────────────────────────────────────────────────┐
    │  OLD ReplicaSet (v1): 3 pods                     kubectl apply  │
    │  ┌───┐ ┌───┐ ┌───┐                                              │
    │  │v1 │ │v1 │ │v1 │    maxSurge=1, maxUnavailable=1              │
    │  └───┘ └───┘ └───┘                                              │
    │                                                                 │
    │  Step 1: Create 1 new v2 pod (surge beyond desired count)       │
    │  ┌───┐ ┌───┐ ┌───┐ ┌───┐                                        │
    │  │v1 │ │v1 │ │v1 │ │v2 │  ← NEW pod created                     │
    │  └───┘ └───┘ └───┘ └───┘                                        │
    │                                                                 │
    │  Step 2: Terminate 1 old v1 pod (stay within unavailable limit) │
    │  ┌───┐ ┌───┐        ┌───┐                                       │
    │  │v1 │ │v1 │        │v2 │  ← OLD pod removed                    │
    │  └───┘ └───┘        └───┘                                       │
    │                                                                 │
    │  Step 3-6: Repeat until all pods are v2                         │
    │  ┌───┐ ┌───┐ ┌───┐                                              │
    │  │v2 │ │v2 │ │v2 │  ← ALL new, zero downtime!                   │
    │  └───┘ └───┘ └───┘                                              │
    └─────────────────────────────────────────────────────────────────┘

1.5 Scheduling: Labels, Selectors, Affinity & Taints (8 Qs) — Q35-Q42
    Q35: Labels — key-value pairs for organizing resources (app: anihpj-api, tier: backend)
    Q36: Selectors — equality-based (app=nginx) vs set-based (env in (prod,staging))
    Q37: nodeSelector — simplest scheduling constraint ("put me on a GPU node")

    🎯 Labels & Selectors — The Matchmaker Analogy:
    ┌─────────────────────────────────────────────────────────────────┐
    │                                                                 │
    │  LABELS = Sticky notes you put ON resources                     │

    │                                                                 │
    │  SELECTORS = The "looking for..." criteria                      │
    │  Service: "Send traffic to pods where app=anihpj-api"           │
    │  Deployment: "Manage pods where app=anihpj-api, version=v2"     │
    │                                                                 │
    │  THE MATCH:                                                      │
    │  ┌──────────────────┐         ┌──────────────────┐              │

    │  │ selector:        │ MATCH!  │ labels:          │              │
    │  │   app:anihpj-api │         │   app:anihpj-api │              │
    │  └──────────────────┘         └──────────────────┘              │
    │                                                                 │
    │  WRONG SELECTOR = Service has NO endpoints = 503 errors!        │
    │  This is the #1 cause of "my Service doesn't work."             │

2.1 Kubernetes Networking (12 Qs) — Q89-Q100
    Q89:  Service types — ClusterIP, NodePort, LoadBalancer, ExternalName
    Q90:  ClusterIP — internal-only virtual IP (kube-proxy load balances to pods)
    Q91:  NodePort — opens a port (30000-32767) on EVERY node
    Q92:  LoadBalancer — cloud LB (AWS NLB, GCP TCP LB) → NodePort → pods
    Q93:  Service selectors — how Service finds pods (must match pod labels!)
    Q94:  Endpoints — the actual pod IPs a Service routes to (kubectl get endpoints)
    Q95:  Ingress — L7 HTTP/HTTPS routing (host + path → backend Service)
    Q96:  Ingress TLS termination — TLS Secret + hosts in Ingress spec
    Q97:  NetworkPolicy — firewall rules for pod-to-pod traffic (CNI must support it)
    Q98:  CNI (Container Network Interface) — plugin system for pod networking
    Q99:  CoreDNS — the cluster DNS server (ConfigMap: Corefile, plugins)
    Q100: kube-proxy modes — iptables (sequential) vs IPVS (hash table, faster)

2.2 Kubernetes Security Fundamentals (10 Qs) — Q101-Q110
    Q101: Authentication vs Authorization vs Admission Control (the 3 A's of security)
    Q102: RBAC — Role (namespace-scoped) vs ClusterRole (cluster-scoped)
    Q103: RoleBinding vs ClusterRoleBinding — binding subjects to roles
    Q104: ServiceAccounts — identity for pods (each namespace has a "default" SA)
    Q105: automountServiceAccountToken — when you DON'T want a token in your pod
    Q106: Pod Security Standards (PSS) — Privileged, Baseline, Restricted
    Q107: Pod Security Admission (PSA) — enforce/audit/warn modes at namespace level
    Q108: TLS in Kubernetes — API server, kubelet, etcd, Ingress certificates
    Q109: Secret encryption at rest — EncryptionConfiguration for etcd
    Q110: ImagePullSecrets — authenticating to private container registries

2.3 Troubleshooting & Debugging (12 Qs) — Q111-Q122
    Q111: Node conditions — Ready, MemoryPressure, DiskPressure, PIDPressure, NetworkUnavailable
    Q112: kubectl describe node — reading node conditions and events
    Q113: Pod lifecycle debugging — Pending, CrashLoopBackOff, ImagePullBackOff, OOMKilled
    Q114: kubectl describe pod — reading Events section for clues
    Q115: Liveness probe — "is my app alive?" (restart if failing)
    Q116: Readiness probe — "is my app ready to serve?" (remove from Service if failing)
    Q117: Startup probe — "is my app done booting?" (gives slow apps extra time)
    Q118: kubectl logs — --previous (crashed container), --tail, --since, --timestamps
    Q119: kubectl exec — debugging inside a running container
    Q120: kubectl port-forward — accessing pod ports locally for debugging
    Q121: kubectl top pod/node — how metrics-server collects data (kubelet Summary API)
    Q122: kubectl events — cluster-level event log (--sort-by='.lastTimestamp')

2.4 Storage in Kubernetes (10 Qs) — Q123-Q132
    Q123: Volumes vs VolumeMounts — the "plug and socket" analogy
    Q124: emptyDir — tied to pod lifecycle, data deleted on pod restart
    Q125: hostPath — mounts node filesystem into pod (security risk! use sparingly)
    Q126: PersistentVolume (PV) — cluster-wide storage resource (like a parking spot)
    Q127: PersistentVolumeClaim (PVC) — request for storage (like a parking reservation)
    Q128: StorageClass — the "menu" of storage types (fast-ssd, slow-hdd, aws-ebs)
    Q129: accessModes — RWO (ReadWriteOnce), ROX (ReadOnlyMany), RWX (ReadWriteMany)
    Q130: CSI (Container Storage Interface) — pluggable storage drivers (AWS EBS, NFS, Ceph)
    Q131: Dynamic provisioning — StorageClass → CSI driver → cloud volume → PV → PVC
    Q132: Why anihpj-db uses StatefulSet + PVC — stable identity + persistent storage

2.5 Advanced Orchestration Concepts (12 Qs) — Q133-Q144
    Q133: Service Mesh — Istio, Linkerd, Envoy sidecar proxy pattern

    Q135: Traffic splitting — canary deployments: 90% v1, 10% v2 via service mesh
    Q136: RuntimeClass — selecting runtime per pod (runc vs gVisor vs Kata)

    Q139: PodDisruptionBudget (PDB) — minimum pods that must stay running during eviction
    Q140: PriorityClass — which pods get evicted first under resource pressure
    Q141: Overprovisioning & FinOps — resource optimization, cost allocation, right-sizing
