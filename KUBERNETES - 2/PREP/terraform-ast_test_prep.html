IaC Concepts Q1 of 200
What is Infrastructure as Code (IaC)?
A) Writing scripts that sequentially execute CLI commands to provision servers one at a time
B) Managing and provisioning infrastructure through machine-readable definition files rather than manual processes or interactive configuration tools
C) Using a graphical user interface to drag-and-drop cloud resources into a canvas
D) Storing server IP addresses and passwords in a version-controlled text file
✅ Correct Answer: B

Infrastructure as Code (IaC) is the practice of managing and provisioning infrastructure through machine-readable definition files rather than manual processes. Instead of clicking through the AWS Console to create an EC2 instance, you write a .tf file describing what you want, and Terraform makes it happen.

📝 Detailed Explanation
IaC vs Manual Provisioning — The Fundamental Difference
  MANUAL (ClickOps — What IaC REPLACES):
  ┌─────────────────────────────────────────────────────────┐
  │ Developer: "I need an EC2 instance for the anihpj API"  │
  │                                                         │
  │ 1. Log into AWS Console                                 │
  │ 2. Navigate: EC2 → Launch Instance                      │
  │ 3. Choose AMI: Ubuntu 22.04 (which one? There are 100s) │
  │ 4. Choose instance type (t3.micro? t3.medium?)          │
  │ 5. Configure VPC, subnet, security group (click click)  │
  │ 6. Add storage (gp3, 20GB)                              │
  │ 7. Add tags (Name: anihpj-api, Env: prod)               │
  │ 8. Review and launch                                    │
  │ 9. Repeat for dev, staging, prod (3× the clicking!)     │
  │                                                         │
  │ ❌ Problems: Error-prone, not repeatable, no version    │
  │    history, "Bob knew how to set this up but Bob left"  │
  └─────────────────────────────────────────────────────────┘

  IaC (Terraform — The Modern Way):
  ┌─────────────────────────────────────────────────────────┐
  │ # anihpj-api.tf — ONE file defines the infrastructure   │
  │ resource "aws_instance" "anihpj_api" {                  │
  │   ami           = "ami-0c55b159cbfafe1f0"               │
  │   instance_type = "t3.medium"                           │
  │   subnet_id     = aws_subnet.private.id                 │
  │   vpc_security_group_ids = [aws_security_group.api.id]  │
  │   tags = { Name = "anihpj-api", Env = "prod" }         │
  │ }                                                       │
  │                                                         │
  │ $ terraform apply  ← Done. 3 environments = 3 tfvars   │
  │                                                         │
  │ ✅ Benefits: Version-controlled (git), repeatable,      │
  │    auditable, self-documenting, team-collaborative      │
  └─────────────────────────────────────────────────────────┘

Why A is wrong: IaC is DECLARATIVE (you describe the desired end state), not imperative (step-by-step scripts). Why C is wrong: That's a UI-based approach — the opposite of IaC. Why D is wrong: Storing passwords in text files is NOT IaC — it's a security anti-pattern.

IaC Concepts Q2 of 200
What is the "Snowflake Server" problem that IaC solves?
A) Servers that run too cold and need additional cooling in the data center
B) Servers that are too unique to be cloned or replicated efficiently
C) Servers that become unique and irreplaceable over time due to manual, undocumented changes — making them impossible to reproduce
D) Servers running Snowflake OS, a specialized Linux distribution
✅ Correct Answer: C

A "Snowflake Server" is a server that has been manually configured over time with undocumented changes — a package installed here, a config tweaked there — until it becomes unique and irreplaceable. Like a snowflake, no two are alike. If it fails, you can't rebuild it because nobody knows exactly what's on it.

📝 Detailed Explanation

IaC eliminates snowflake servers by defining infrastructure as version-controlled code. With Terraform, you destroy the old server and terraform apply creates an identical replacement. For anihpj/jobpost, this means the production Django server can be recreated in minutes — not days — because every package, config, and firewall rule is in code.

IaC Concepts Q4 of 200
What is "Configuration Drift" in the context of Infrastructure as Code?
A) When the real-world state of infrastructure diverges from what is defined in code, usually due to manual changes made outside of Terraform
B) When Terraform code slowly becomes outdated as new provider versions are released
C) When two team members edit the same .tf file simultaneously and create a merge conflict
D) When the terraform.tfstate file becomes corrupted due to network issues during apply
✅ Correct Answer: A

Configuration drift happens when someone makes a change directly in the AWS Console (or via CLI) that Terraform doesn't know about. Now the real infrastructure differs from what's in your .tf files and terraform.tfstate.

📝 Detailed Explanation
$ terraform plan ← Detects drift by comparing state vs real world # aws_security_group.anihpj_api has changed ~ resource "aws_security_group" "anihpj_api" { id = "sg-0a1b2c3d4e5f67890" name = "anihpj-api-sg" ~ ingress { ~ from_port = 80 → 8080 ← Someone changed this manually! ~ to_port = 80 → 8080 protocol = "tcp" cidr_blocks = ["0.0.0.0/0"] } tags = { Name = "anihpj-api-sg" } } Plan: 0 to add, 1 to change, 0 to destroy. ← Terraform will FIX the drift on next apply

Terraform detects drift during terraform plan — it compares the state file with the real world and shows the differences. If you then run terraform apply, Terraform corrects the drift by bringing infrastructure back to the desired state defined in code. For anihpj/jobpost, if someone manually changes the RDS instance type from db.t3.medium to db.t3.large in the AWS Console, the next terraform plan will show that change and offer to revert it.

IaC Concepts Q5 of 200
Which statement BEST describes the relationship between IaC and version control (Git)?
A) IaC files should NOT be stored in Git because they contain sensitive infrastructure information
B) IaC files SHOULD be stored in Git — enabling code review, change tracking, rollbacks, and team collaboration on infrastructure changes
C) IaC and Git are completely independent — Terraform has its own built-in version control system
D) Only the terraform.tfstate file should be stored in Git; .tf files should be local-only
✅ Correct Answer: B

IaC and version control are fundamentally complementary. Your .tf files should be stored in Git, enabling: code review (PR review infrastructure changes like code changes), change tracking (git blame shows who changed what), rollbacks (git revert to undo bad infrastructure changes), and collaboration (multiple team members working on infrastructure safely).

📝 Detailed Explanation

  │  ✅ COMMIT TO GIT                    ❌ NEVER COMMIT TO GIT      │

  │                (main, vars, output)                 cache dir   │
  │                                                       │
  │  *.tfvars      Variable values       terraform.tfstate  STATE!  │
  │                (non-sensitive)       terraform.tfstate.backup    │
  │                                                       │
  │  .terraform.lock.hcl  Lock file      *.plan          Plan files │
  │                (provider checksums)                  (binary)    │

Which of the following BEST describes a DECLARATIVE approach to infrastructure?

In a declarative approach, you describe the DESIRED END STATE ("I want 3 EC2 instances"), and the tool (Terraform) figures out the sequence of API calls needed to make it happen. You don't specify HOW — just WHAT.

📝 Detailed Explanation
Declarative (Terraform) vs Imperative (Scripts)
  DECLARATIVE (Terraform HCL):

    instance_type = "t3.medium"

  }
  # "I want 3 instances." Terraform handles creation order.

  IMPERATIVE (AWS CLI / Python boto3):
  for i in range(3):
      aws ec2 run-instances --image-id ami-xxx --count 1 ...
      wait_until_running()
      print(f"Instance {i+1} created")
  # "DO step 1, then step 2, then step 3." You control the order.

  KEY DIFFERENCE:
  • Declarative: define target state → tool computes diff → applies
  • Imperative: define exact sequence → execute step-by-step
  • Terraform is DECLARATIVE. Ansible playbooks and shell scripts
    are IMPERATIVE.

Option A is imperative (step-by-step instructions). Option C is imperative with a conditional. Option D is imperative (Python script). Only B describes the WHAT without the HOW — the essence of declarative IaC.

🟢 Storage Issues — PVC, PV, StorageClass, and Mount Failures

Storage is often the FIRST thing to break because it involves multiple components: PVC → StorageClass → Provisioner → PV → Mount. When any link in this chain fails, your pod can't start or your data is at risk.

📌 ST1–ST3: PVC Binding Failures

ST1
💾 CATEGORY 1: STORAGE — Issue ST1
PVC Stuck in Pending State — No PV Bound

🔍 Symptom: kubectl get pvc shows STATUS: Pending indefinitely. kubectl describe pvc shows "no persistent volumes available for this claim." The anihpj-db PostgreSQL pod can't start because its PVC won't bind.

  kubectl get pvc
  NAME         STATUS    VOLUME   CAPACITY   STORAGECLASS   AGE
  anihpj-pvc   Pending                      fast-ssd       5m

  kubectl describe pvc anihpj-pvc
  Events:
    Warning  VolumeBinding  no persistent volumes available for this claim
    Warning  VolumeBinding  storageclass.storage.k8s.io "fast-ssd" not found
🔴5 Most Likely Causes
  1. StorageClass does not exist: The PVC references a StorageClass that hasn't been created. kubectl get sc — if "fast-ssd" is missing, create it or fix the PVC's storageClassName.
  2. No matching PV available: In static provisioning, no PV matches the PVC's storage size, access mode, or selector. kubectl get pv — check capacity and accessModes.
  3. StorageClass provisioner not installed: The CSI driver (e.g., ebs.csi.aws.com) is not deployed. kubectl get pods -n kube-system | grep csi — provisioner pods must be Running.
  4. Access mode mismatch: PVC requests ReadWriteMany but only ReadWriteOnce PVs exist. Check kubectl get pv -o yaml | grep -A2 accessModes.
  5. StorageClass has volumeBindingMode: WaitForFirstConsumer and no pod uses the PVC yet. The PV is only created when a pod actually references the PVC.
🟡5 Less Likely Causes
  1. CSI driver pod CrashLoopBackOff — provisioner can't create volumes
  2. Cloud provider API rate limiting — too many PVCs created simultaneously
  3. PVC selector labels don't match any PV labels
  4. Node where CSI driver runs has taint without toleration
  5. storageClassName: "" (empty string, not null!) — requests a PV with NO StorageClass, but all PVs have one
🟣5 New Cluster Causes
  1. No default StorageClass set: kubectl get sc — look for "(default)". Without it, PVCs without storageClassName won't bind. Set: kubectl patch sc <name> -p '{"metadata":{"annotations":{"storageclass.kubernetes.io/is-default-class":"true"}}}'
  2. CSI driver not yet installed — common in fresh kubeadm clusters
  3. Cloud credentials not configured for CSI driver to provision volumes
  4. RBAC for CSI driver service account missing
  5. kubelet missing --cloud-provider flag for legacy in-tree provisioners
🔍 What to Look At:
kubectl get sc,pv,pvc --all-namespaces The full storage stack in one view — see StorageClass, PV, and PVC together.
kubectl describe pvc <name> The Events section tells you exactly why binding failed — always read the events first.
🎯 #1 Root Cause: StorageClass does not exist or is misnamed. The PVC references a StorageClass that hasn't been created — the most common CKA exam pitfall.
🔧 How to Solve:
1. Verify StorageClass exists kubectl get sc If the StorageClass referenced by the PVC is missing, create it or fix the PVC's storageClassName.
2. Check provisioner and parameters kubectl describe sc <name> Verify the provisioner is correct and the CSI driver is installed and running.
3. Static provisioning kubectl get pv Create a PV matching the PVC's requested size, accessMode, and selector labels.
4. Dynamic provisioning Install the CSI driver: kubectl apply -f <csi-driver-url>. Verify CSI pods are Running in kube-system.
5. Set default StorageClass kubectl patch sc <name> -p '{"metadata":{"annotations":{"storageclass.kubernetes.io/is-default-class":"true"}}}' PVCs without an explicit storageClassName will use the default.
💡 Personal Advice:
Always verify StorageClass FIRST. The #1 PVC issue on the CKA exam is a missing or misnamed StorageClass. Run kubectl get sc before writing any PVC YAML.
Empty string is NOT null. storageClassName: "" Requests a PV with NO StorageClass — different from omitting the field entirely. Know this distinction.
CSI driver must be Running. Even with correct StorageClass, if the CSI provisioner pod is CrashLoopBackOff, no volumes will be created.
WaitForFirstConsumer delays binding. If volumeBindingMode is WaitForFirstConsumer, the PV is only created when a pod actually uses the PVC. Don't mistake this for a failure.

M.1 — etcd Backup & Restore (Full TLS Flags)
1

Backup:

ETCDCTL_API=3 etcdctl --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  snapshot save /opt/etcd-backup.db

Restore:

ETCDCTL_API=3 etcdctl --data-dir=/var/lib/etcd-restore \
  snapshot restore /opt/etcd-backup.db

⚠️ After restore: Update etcd static pod manifest (/etc/kubernetes/manifests/etcd.yaml) to point --data-dir to the new path, then restart kubelet. Also update the --initial-cluster-token to a new value.
