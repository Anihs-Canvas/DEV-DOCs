🏗️ The anihpj/jobpost Project — Your Running Example

anihpj is a Django-based job posting platform. jobpost is the application: employers post jobs, applicants apply. The stack: Django (web+api) + PostgreSQL (database) + Redis (cache/queue).

On AWS via Terraform: EC2 (Django), RDS (PostgreSQL), ElastiCache (Redis), S3 (static files + state), ALB (load balancer), Route53 (DNS), IAM (permissions), VPC (networking).

Every MCQ ties back to this real app. You'll terraform plan/apply real infrastructure as you learn.

🚨 Critical Do's & Don'ts During The Exam
  • ✅ DO: Read every question TWICE. HashiCorp exams are known for tricky wording — one word changes the answer.
  • ✅ DO: Use process of elimination. Even if you're unsure, ruling out 2 wrong options gives you a 50/50 chance.

  • ❌ DON'T: Confuse mutable vs immutable infrastructure. Terraform typically DESTROYS and RECREATES, not updates in-place.

  • ❌ DON'T: Leave any question blank. There's no penalty for wrong answers — always guess if unsure.

📁 Complete Terraform Project Structure — Every File Explained

This is the exact file tree you'd use to deploy anihpj/jobpost. Each file has a single responsibility — separation of concerns is key to maintainable Terraform.

📂 terraform-anihpj/ 
├── 📄 main.tf              ← Root: providers + module calls
├── 📄 variables.tf         ← All input variables + validation
├── 📄 outputs.tf           ← ALB DNS, DB endpoint, S3 URLs
├── 📄 terraform.tfvars     ← Environment-specific values
├── 📄 versions.tf          ← Provider + Terraform version pins
├── 📄 backend.tf           ← S3 + DynamoDB remote state
├── 📄 locals.tf            ← Common tags, naming prefixes
├── 📄 data.tf              ← Data sources (AMI, AZs, account)
│
├── 📂 modules/
│   ├── 📂 networking/      ← VPC, subnets, NAT GW, IGW, routes
│   ├── 📂 compute/         ← EC2, ASG, launch templates, ALB
│   ├── 📂 database/        ← RDS PostgreSQL, ElastiCache Redis
│   ├── 📂 storage/         ← S3 buckets, IAM policies
│   ├── 📂 dns/             ← Route53 zones, records, ACM certs
│   └── 📂 security/        ← Security groups, KMS keys, IAM roles
│
└── 📂 environments/
    ├── 📂 dev/              ← dev.tfvars → t3.micro, 1 instance
    ├── 📂 staging/          ← staging.tfvars → t3.small, 2 instances
    └── 📂 prod/             ← prod.tfvars → t3.medium, 3+ instances
🔑 Key Design Decisions
  • Modules = reusable, testable, versioned
  • locals.tf = DRY principle (tags computed once)
  • backend.tf = remote state with S3 + DynamoDB lock
  • versions.tf = pin provider versions (no surprises)
  • environments/ = separate tfvars per env
  • data.tf = dynamic lookups (AMI, AZs, account ID)
  • outputs.tf = expose what downstream needs
  • variables.tf = validation blocks for safety

🔒 Security Best Practices — Protect Your Infrastructure

Security in Terraform is about keeping secrets OUT of your code and state, enforcing least privilege, and never hardcoding credentials. These are the non-negotiable rules.

  • ✅ Use env vars: AWS_ACCESS_KEY_ID
  • ✅ Use sensitive = true on outputs

  • ✅ .gitignore tfvars with secrets
  • ✅ Ephemeral resources (Terraform 1.10+)

  • ❌ NEVER: commit .tfstate to git
  • ✅ S3 with encrypt = true

  • ✅ Restrict S3 bucket with IAM policy

⚠️ Common Terraform Anti-Patterns — What NOT To Do

These mistakes appear on the exam AND in real-world interviews. Know them cold.

❌ Hardcoding Values 
# WRONG:
resource "aws_instance" "api" {
  ami           = "ami-0c55b159cbfafe1f0"  ← Hardcoded AMI
  instance_type = "t3.medium"             ← Hardcoded type
}

# RIGHT:
resource "aws_instance" "api" {
  ami           = data.aws_ami.ubuntu.id  ← Dynamic lookup
  instance_type = var.instance_type       ← Parameterized
}
❌ Monolithic main.tf 
# WRONG: 500+ lines in one file
# main.tf has VPC + EC2 + RDS + S3
# + ALB + Route53 + IAM + KMS...
# Impossible to navigate or reuse

# RIGHT: Split into modules
# networking/ compute/ database/
# storage/ dns/ security/
# Each module = one concern
❌ Local State in Teams 
# WRONG: Each dev has own local state
# Dev A: terraform.tfstate (has EC2)
# Dev B: terraform.tfstate (has RDS)
# → Out of sync, conflicts, drift!

# RIGHT: Remote state with locking
backend "s3" {
  bucket         = "anihpj-tfstate"
  dynamodb_table = "tfstate-lock"
}
❌ Overusing provisioners 
# WRONG: Provisioner for everything
provisioner "remote-exec" {
  inline = [
    "apt-get update",
    "apt-get install nginx",
    "pip install django",
    "systemctl start gunicorn"
  ]
}  ← Breaks idempotency + slow

# RIGHT: Packer-built AMI or user-data
user_data = templatefile("bootstrap.sh", {...})

What is Infrastructure as Code (IaC)?
A) Writing scripts that sequentially execute CLI commands to provision servers one at a time
B) Managing and provisioning infrastructure through machine-readable definition files rather than manual processes or interactive configuration tools
C) Using a graphical user interface to drag-and-drop cloud resources into a canvas

✅ Correct Answer: B

Infrastructure as Code (IaC) is the practice of managing and provisioning infrastructure through machine-readable definition files rather than manual processes. Instead of clicking through the AWS Console to create an EC2 instance, you write a .tf file describing what you want, and Terraform makes it happen.

📝 Detailed Explanation
IaC vs Manual Provisioning — The Fundamental Difference
  MANUAL (ClickOps — What IaC REPLACES):
  ┌─────────────────────────────────────────────────────────┐
  │ Developer: "I need an EC2 instance for the anihpj API"  │
  │                                                         │
  │ 1. Log into AWS Console                                 │
  │ 2. Navigate: EC2 → Launch Instance                      │
  │ 3. Choose AMI: Ubuntu 22.04 (which one? There are 100s) │
  │ 4. Choose instance type (t3.micro? t3.medium?)          │
  │ 5. Configure VPC, subnet, security group (click click)  │
  │ 6. Add storage (gp3, 20GB)                              │
  │ 7. Add tags (Name: anihpj-api, Env: prod)               │
  │ 8. Review and launch                                    │
  │ 9. Repeat for dev, staging, prod (3× the clicking!)     │
  │                                                         │
  │ ❌ Problems: Error-prone, not repeatable, no version    │
  │    history, "Bob knew how to set this up but Bob left"  │
  └─────────────────────────────────────────────────────────┘

  IaC (Terraform — The Modern Way):
  ┌─────────────────────────────────────────────────────────┐
  │ # anihpj-api.tf — ONE file defines the infrastructure   │
  │ resource "aws_instance" "anihpj_api" {                  │
  │   ami           = "ami-0c55b159cbfafe1f0"               │
  │   instance_type = "t3.medium"                           │
  │   subnet_id     = aws_subnet.private.id                 │

IaC Concepts Q6 of 200
Which of the following BEST describes a DECLARATIVE approach to infrastructure?
A) "Step 1: Create VPC. Step 2: Create subnet. Step 3: Launch EC2. Step 4: Attach EBS."
B) "I want 3 EC2 instances of type t3.medium in subnet-abc with security group sg-xyz" — Terraform figures out HOW to make it happen
C) "if instance_count < 3: aws ec2 run-instances --count 1 --type t3.medium"
D) Writing a Python script that uses boto3 to sequentially create AWS resources
✅ Correct Answer: B

In a declarative approach, you describe the DESIRED END STATE ("I want 3 EC2 instances"), and the tool (Terraform) figures out the sequence of API calls needed to make it happen. You don't specify HOW — just WHAT.

📝 Detailed Explanation
Declarative (Terraform) vs Imperative (Scripts)
  DECLARATIVE (Terraform HCL):
  resource "aws_instance" "anihpj_api" {
    count         = 3
    ami           = "ami-0c55b159cbfafe1f0"
    instance_type = "t3.medium"
    subnet_id     = "subnet-abc"
  }
  # "I want 3 instances." Terraform handles creation order.

  IMPERATIVE (AWS CLI / Python boto3):
  for i in range(3):
      aws ec2 run-instances --image-id ami-xxx --count 1 ...
      wait_until_running()
      print(f"Instance {i+1} created")
  # "DO step 1, then step 2, then step 3." You control the order.

  KEY DIFFERENCE:
  • Declarative: define target state → tool computes diff → applies
  • Imperative: define exact sequence → execute step-by-step
  • Terraform is DECLARATIVE. Ansible playbooks and shell scripts
    are IMPERATIVE.

Option A is imperative (step-by-step instructions). Option C is imperative with a conditional. Option D is imperative (Python script). Only B describes the WHAT without the HOW — the essence of declarative IaC.
