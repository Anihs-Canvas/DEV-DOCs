1.1 Kubernetes Networking Fundamentals (Q1-Q10)

Architecture Q1 of 200
What are the four fundamental Kubernetes networking rules that every CNI plugin must satisfy?
A) Each Pod gets its own IP. Pods can communicate across nodes without NAT. Node agents can communicate with all pods on that node. Pods communicate without NAT between each other.
B) All pods share the node IP. Pods communicate through NAT. Services use iptables. DNS is optional.
C) Pods use host networking by default. CNI creates overlay networks only. Containers share pod IP.
D) Each container gets a unique IP. Pods on different nodes always need NAT. Services replace DNS.
✅ Correct Answer: A

The four fundamental rules: (1) Every pod gets its own unique IP address, (2) Pods on a node can communicate with all pods on all nodes without NAT, (3) Agents on a node (like kubelet) can communicate with all pods on that node, (4) Pods can communicate with each other without Network Address Translation.

📝 Detailed Explanation
The 4 Fundamental K8s Networking Rules
  RULE 1                    RULE 2                    RULE 3                    RULE 4
  ┌─────────────────┐      ┌─────────────────┐      ┌─────────────────┐      ┌─────────────────┐
  │ Each Pod gets   │      │ Pods can talk   │      │ Node agents     │      │ No NAT between  │
  │ its OWN IP      │      │ across nodes    │      │ can reach all   │      │ pods            │
  │                 │      │ WITHOUT NAT     │      │ pods on node    │      │                 │
  │ Pod A: 10.0.1.5│      │ 10.0.1.5 ───►  │      │ kubelet ───►   │      │ 10.0.1.5 ───►  │
  │ Pod B: 10.0.1.6│      │   10.0.2.9     │      │   10.0.1.5     │      │   10.0.2.9     │
  │ Pod C: 10.0.2.9│      │ (same IP seen) │      │ (direct access)│      │ (source IP     │
  └─────────────────┘      └─────────────────┘      └─────────────────┘      │  preserved)    │
                                                                             └─────────────────┘
  ✅ Cilium: eBPF O(1) hash maps    ❌ Legacy: iptables O(n) rule walking

These rules are the foundation of Kubernetes networking. Rule 1 means each pod has a routable IP — unlike Docker where containers share the host IP. Rule 2 is WHY CNI plugins exist: they must set up routes so pod IPs are reachable cross-node. Rule 3 enables health checks and readiness probes. Rule 4 preserves source IPs for NetworkPolicy enforcement. Cilium implements all four using eBPF instead of iptables/overlays, providing O(1) performance at scale.

Architecture Q2 of 200
What is the primary role of a CNI (Container Network Interface) plugin in Kubernetes?
A) Managing container storage volumes and persistent volume claims
B) Allocating IP addresses to pods and setting up network routes so pods can communicate across nodes
C) Providing DNS resolution for Kubernetes services and external domains
D) Managing authentication and RBAC for pod-to-pod communication
✅ Correct Answer: B

The CNI plugin's core job is IPAM (IP Address Management) — assigning each pod a unique IP — and establishing network routes so those IPs are reachable from any node in the cluster.

📝 Detailed Explanation

CNI is called by the kubelet at pod creation time (CMD_ADD) and deletion time (CMD_DEL). The CNI spec defines a simple JSON config file in /etc/cni/net.d/. When a pod is created, kubelet calls the CNI binary which: (1) allocates an IP from the pod CIDR range, (2) creates a veth pair connecting the pod namespace to the host, (3) configures routes so the pod IP is reachable. Cilium's CNI does this via eBPF — allocating IPs through its IPAM and creating eBPF-based routes instead of iptables rules.

Architecture Q3 of 200
How does a Kubernetes Service provide stable networking for pods that are constantly being created and destroyed?
A) Services create static IP addresses for each pod that never change
B) Services use DNS round-robin that updates instantly when pods change
C) Services provide a stable virtual IP (ClusterIP) and use label selectors to automatically discover matching pods, with kube-proxy or Cilium handling the traffic routing
D) Services create a dedicated proxy container for each application to handle routing

Architecture Q4 of 200
What is the difference between overlay networking and native routing in Kubernetes?
A) Overlay is for cloud only; native routing is for bare metal only
B) Overlay encapsulates pod traffic inside another protocol (VXLAN/Geneve) so the physical network doesn't need pod routes; native routing adds pod CIDR routes directly to the network
C) Overlay is faster than native routing; native routing is more secure than overlay
D) Overlay uses eBPF; native routing uses iptables. They cannot be used together.
✅ Correct Answer: B

Overlay encapsulates pod traffic inside VXLAN or Geneve tunnels, hiding pod IPs from the physical network. Native routing adds actual pod CIDR routes to the network's routing table so routers can forward pod traffic directly.

📝 Detailed Explanation

Overlay (VXLAN/Geneve): Pod packet is wrapped in another IP+UDP header. The outer header uses node IPs that the physical network understands. Advantage: works on any network without reconfiguration. Disadvantage: ~50 bytes overhead per packet, slight CPU cost for encap/decap. Native routing: Pod CIDR routes are added to the network (via BGP or static routes). Physical routers forward pod traffic directly. Advantage: no encapsulation overhead, better performance. Disadvantage: requires the network to know about pod IPs — usually needs BGP. Cilium supports both modes: tunnel mode (VXLAN/Geneve) and native routing mode (with or without BGP).

Architecture Q5 of 200
In a Kubernetes cluster with Cilium, how does a pod on node-1 (IP 10.0.1.5) send a packet to a pod on node-2 (IP 10.0.2.9) using VXLAN tunnel mode?
A) Pod-1 sends to node-2 IP directly. Node-2 NATs to pod-2 IP.
B) Pod-1 sends to 10.0.2.9. Cilium eBPF on node-1 encapsulates the packet in VXLAN with outer dst=node-2 IP. Node-2 Cilium decapsulates and delivers to pod-2.
C) Pod-1 sends to kube-proxy which creates an iptables DNAT rule to pod-2 IP.
D) Pod-1 sends to the service ClusterIP which then routes to pod-2 through the API server.
✅ Correct Answer: B

In VXLAN tunnel mode, Cilium's eBPF programs on the source node encapsulate the original packet inside a VXLAN header with the destination node's IP. The destination node decapsulates and delivers to the target pod.

📝 Detailed Explanation
VXLAN Tunnel — Step-by-Step Packet Walk
  STEP 1: Pod-1 sends packet           STEP 2: Cilium eBPF on node-1
  ┌────────────────────────┐           ┌──────────────────────────────┐
  │ anihpj-web pod         │           │ TC ingress on veth (host)    │
  │ eth0: 10.0.1.5         │           │ • Lookup dst 10.0.2.9        │
  │                        │           │ • Found: pod-2 on node-2     │
  │ Src: 10.0.1.5          │           │ • Node-2 IP: 192.168.1.2     │
  │ Dst: 10.0.2.9 ─────────┼──►        │ • Encapsulate in VXLAN!      │
  └────────────────────────┘           └──────────────┬───────────────┘
                                                      │
  STEP 3: Physical network routes     STEP 4: Cilium eBPF on node-2   STEP 5: Deliver
  ┌──────────────────────────────┐    ┌──────────────────────────────┐ ┌──────────────┐
  │ VXLAN packet:                │    │ VXLAN interface (cilium_vxlan)│ │ anihpj-api   │

The packet flow: (1) Pod-1 sends packet with src=10.0.1.5, dst=10.0.2.9 via its veth. (2) Cilium's eBPF TC program on the veth sees the packet and looks up the destination. (3) It finds pod-2 is on node-2 and encapsulates in VXLAN. (4) The physical network routes this to node-2. (5) Node-2 decapsulates and delivers to pod-2.

Architecture Q7 of 200
How does CoreDNS provide service discovery in Kubernetes?
A) CoreDNS watches pod IPs and creates /etc/hosts entries in every pod
B) CoreDNS watches the Kubernetes API for Services and Pods, and responds to DNS queries with ClusterIPs for services and pod IPs for headless services
C) CoreDNS is an external DNS service that requires manual configuration for each service
D) CoreDNS replaces kube-proxy and handles all service traffic routing
✅ Correct Answer: B

CoreDNS watches the Kubernetes API server for Services and Pods, automatically creating DNS records. A service `anihpj-api` in namespace `anihpj` gets the FQDN `anihpj-api.anihpj.svc.cluster.local` resolving to its ClusterIP.

📝 Detailed Explanation

CoreDNS runs as a Deployment in kube-system and uses the `kubernetes` plugin to watch the API server. For every Service, it creates: (1) An A/AAAA record for the service name → ClusterIP, (2) SRV records for named ports. For headless services (clusterIP: None), it returns pod IPs directly. DNS is critical — if CoreDNS is blocked by a NetworkPolicy, pods cannot resolve service names. Cilium can enforce DNS-based policies (toFQDNs) that integrate with CoreDNS responses for identity-aware filtering of external domains.

Architecture Q9 of 200
Why is iptables-based kube-proxy considered problematic at scale (5000+ services)?
A) iptables cannot handle UDP traffic, only TCP
B) iptables rules are evaluated sequentially (O(n) complexity) — with 5000 services, every packet may traverse 5000+ rules. Rule updates take 30+ seconds and connection tracking tables overflow
C) iptables requires a kernel module that is deprecated since Linux 5.0
D) iptables can only handle 100 services maximum before crashing the kube-proxy process
✅ Correct Answer: B

iptables walks rules sequentially — every packet must traverse all matching rules. With thousands of services, this becomes extremely slow (O(n) vs Cilium's O(1)). Rule updates are also expensive and cause connection tracking table pressure.

📝 Detailed Explanation
Aspectiptables kube-proxyCilium eBPF KPR
LookupO(n) — walks ALL rules sequentiallyO(1) — single hash map lookup
10k ServicesEvery packet traverses 10,000+ rulesSame single lookup regardless of count

Cilium's KPR solves all three problems: (1) eBPF hash maps provide O(1) backend lookup regardless of service count, (2) eBPF programs at the socket layer intercept connect() before the TCP stack — no iptables traversal, (3) Maglev consistent hashing ensures even backend distribution.

Architecture Q10 of 200
What is a veth (virtual ethernet) pair and how is it used in Kubernetes pod networking?
A) A veth pair is a virtual switch that connects multiple pods on the same node
B) A veth pair is a pair of connected virtual network interfaces — one end goes into the pod's network namespace (as eth0), the other stays in the host namespace. It acts like a virtual cable connecting the pod to the host
C) A veth pair is a virtual ethernet bridge used exclusively by the Docker runtime
D) A veth pair is a Kubernetes resource that defines virtual host-to-pod routing rules

What happens when a Cilium agent restarts? Do existing connections survive?

Architecture Q27 of 200
How does Cilium ensure that a pod cannot spoof another pod's identity?
A) Cilium uses TLS certificates to authenticate pod identities
B) Cilium's eBPF programs on the host veth track which identity is assigned to each veth interface. When a packet arrives from a pod, the eBPF program looks up the source veth and assigns the identity — the pod cannot control this
C) Cilium uses port-based authentication — each identity uses a unique port range
D) Cilium relies on Kubernetes RBAC to prevent identity spoofing
✅ Correct Answer: B

Identity is enforced at the kernel level by eBPF. When a packet arrives from a pod's veth interface, the eBPF program knows exactly which endpoint (and thus which identity) that interface belongs to. The pod cannot fake its source identity — it's assigned by the kernel based on the veth.

📝 Detailed Explanation

This is one of Cilium's strongest security properties. The eBPF program attached to the host end of each pod's veth maintains a mapping: veth interface → endpoint ID → security identity. When a packet enters the host namespace from that veth, the eBPF TC ingress program stamps it with the pod's identity. The pod cannot modify this — it doesn't have access to the host veth or the eBPF programs. Even if a compromised pod crafts packets with fake source IPs, the identity is always correct because it comes from the veth-to-identity mapping, not from the packet headers. Only a root-equivalent host attacker can bypass this.
