🗺️ GitOps: The Complete Picture — Summary & How to Implement

Before diving into the chapters, here's a bird's-eye view of everything you'll learn — what GitOps is, how it works, how it transforms the anihpj/jobpost project, and the exact steps to implement it in production.

⚙️ What is GitOps? — The Elevator Pitch

❌ BEFORE GITOPS — Manual Chaos
  • SSH into servers at 2 AM
  • kubectl apply -f from laptops
  • "Who changed replicas from 3 to 1?"
  • Git says v2, cluster runs v1 — drift!
  • CI/CD pipeline holds cluster admin creds
  • Rollback = searching through backups
  • "Works on my machine!" syndrome
✅ WITH GITOPS — Automated Harmony
  • Sleep through incidents — agent auto-heals
  • Only change is git push
  • Full audit trail: every change = Git commit
  • Git = cluster. Always in sync. Zero drift.
  • No cluster creds outside the cluster
  • Rollback = git revert (30 seconds)
  • "Works on Git!" = works everywhere
💡 The Thermostat Analogy

You set your thermostat to 72°F (declare desired state in Git). The thermostat constantly reads the room temperature and turns heat/AC on/off to match 72°F (GitOps agent reconciles). You never touch the heater directly — you only change the thermostat setting. That's GitOps.

🏛️ The 4 Pillars of GitOps

📝
1. DeclarativeDescribe WHAT you want in YAML — not HOW to do it. "I want 3 replicas of anihpj on port 8000."
🔒
2. Versioned & ImmutableEvery change is a Git commit. Full history. Rollback = git revert. No "mystery changes."
🔄
3. Pulled AutomaticallyAgent INSIDE the cluster pulls from Git. No external push. Cluster is self-healing.
🔍
4. Continuously ReconciledAgent watches 24/7. Drift detected → auto-corrected. Manual changes auto-reverted.

🔗 The CI/CD → GitOps Handoff — Where CI Ends & GitOps Begins

🟦 CI (Continuous Integration)
1. Developer pushes code
2. Run tests & lint
3. Build Docker image
4. Push to registry
5. ✋ CI STOPS HERE
⟶
🟩 GitOps (Continuous Deployment)
1. 🤚 GITOPS STARTS
2. CI commits new image tag to config repo
3. GitOps agent detects Git change
4. Agent syncs cluster to match Git
5. Rolling update completes ✅
🔑 The Golden Rule

CI builds and tests. GitOps deploys. CI never touches the cluster directly. The handoff is a Git commit updating the image tag in the config repo. The GitOps agent takes it from there.

"Manifest says Ship v2 at Berth 3. Make it so."

Constantly checks the manifest against reality. If a ship is at the wrong berth, it redirects it.

"Manifest says 3 cranes. I only see 2. Adding one now."
🚢Container Ships

Ships arrive with containers (Docker images). The harbor master assigns them to the correct berth.

"anihpj:v2 arriving. Berth 3 ready. Unloading now."

🛟Tugboats

"anihpj.example.com/jobs → Berth 3, Port 8000."
🔐Customs Office

1.2 GitOps Defined — The Simple Explanation

📖 Official Definition

"GitOps is a set of practices for managing infrastructure and application configurations using Git as the single source of truth, with automated reconciliation to ensure the actual state matches the desired state."

In plain English: Instead of telling Kubernetes what to do with kubectl commands, you write what you want in Git. A robot (ArgoCD/FluxCD) inside your cluster reads Git and makes it happen — continuously.

1.5 The Pull-Based Model — Why It's Revolutionary

The pull-based model is GitOps' secret weapon. Instead of your CI/CD pipeline pushing changes into the cluster (which requires giving the pipeline cluster credentials), the GitOps agent pulls from Git from inside the cluster.

💡 Think of It This Way

In traditional CI/CD, your pipeline is like a delivery driver with a key to your house. In GitOps, the delivery driver leaves the package (config) at a pickup point (Git), and your house (cluster) has its own person (agent) who goes out to get it. The delivery driver never gets a key!

4.3 Principle 3: Pulled Automatically

The GitOps agent runs INSIDE the cluster and pulls configuration from Git. This is the security game-changer. Your CI pipeline never needs cluster credentials — it only needs to push YAML to a Git repo. The agent inside the cluster handles everything else.

4.4 Principle 4: Continuously Reconciled

The agent constantly checks: "Does the cluster match Git?" If not, it fixes it. This is the self-healing magic of GitOps. The reconciliation loop runs every 3 minutes (by default) and ensures actual state = desired state.

  ⏰ T=3min: Git=3, Cluster=3 → SYNCED ✅ (auto-healed!)

6.2 Branching Strategies for GitOps

GitOps works best with Trunk-Based Development — short-lived feature branches merged frequently to main. Avoid GitFlow's long-lived branches which cause merge conflicts and deployment drift.

⚠️ Avoid Environment Branches

Some teams use branches like dev, staging, production to represent environments. This is an anti-pattern in GitOps! It causes drift between branches and makes it unclear which branch represents the "real" state. Instead, use directory-based environments with Kustomize overlays — all in the main branch.

7.2 How ArgoCD Works — The Reconciliation Engine

5-Step Reconciliation Loop (every 3 minutes)
  STEP 1: FETCH — Repo Server: git pull origin main. Changed? → continue.
  STEP 2: RENDER — Read deployment.yaml, run Kustomize/Helm → final manifests.
  STEP 3: COMPARE — Git says replicas=3, Cluster has replicas=2 → OUT OF SYNC!
  STEP 4: SYNC — kubectl apply the rendered manifests → Cluster now has 3.
  STEP 5: HEALTH — Are pods running? Healthy? → 3/3 → HEALTHY ✅
  
  Result: App shows "Synced" + "Healthy" 🟢

  name: anihpj-prod
  namespace: argocd

Chapter 13: Secrets Management in GitOps

Git stores everything in plaintext — but your deployment needs passwords, API keys, and certificates. This chapter covers the 4 major approaches to managing secrets in GitOps without exposing sensitive data.

🟡 Intermediate⏱️ ~2 hours🔐 Critical

13.1 The GitOps Secret Problem

🔴 NEVER Do This!

apiVersion: v1\nkind: Secret\nmetadata:\n name: db-credentials\ndata:\n password: c3VwZXJzZWNyZXQ= ← Base64 is NOT encryption! Anyone with repo access can decode this. And it stays in Git history FOREVER — even after you delete the file.

13.2 Sealed Secrets — Encrypt at Commit Time

Sealed Secrets uses asymmetric encryption. Your laptop has the cluster's PUBLIC key (safe to share). Only the cluster has the PRIVATE key (never leaves). You encrypt with the public key → commit the encrypted blob → the cluster decrypts with the private key.

Terminal
# Install kubeseal CLI
# Create a regular Secret (NEVER commit this!)
kubectl create secret generic db-credentials \
  --from-literal=password=supersecret \
  --dry-run=client -o yaml > secret.yaml

# Encrypt it with the cluster's public key
kubeseal --scope cluster-wide -f secret.yaml -o yaml > sealed-secret.yaml

# sealed-secret.yaml is SAFE to commit to Git!
# It contains encrypted data that only YOUR cluster can decrypt
git add sealed-secret.yaml && git commit -m "Add encrypted DB credentials"

# ArgoCD syncs the SealedSecret → controller decrypts → creates K8s Secret
Sealed Secrets Workflow
  DEV LAPTOP                        GIT REPO                    K8s CLUSTER
  ┌──────────────┐                 ┌──────────┐               ┌──────────────┐
  │ kubeseal     │──encrypts with──▶│ Sealed   │──ArgoCD syncs─▶│ Sealed Secret│
  │ (public key) │   cluster's      │ Secret   │               │ Controller   │
  │              │   PUBLIC key     │ (SAFE!)  │               │ decrypts with│
  │ password:    │                 └──────────┘               │ PRIVATE key  │
  │ supersecret  │                                            │ → K8s Secret │
  └──────────────┘                                            └──────────────┘
  ✅ Encrypted blob safe in Git   ✅ Only cluster can decrypt   ✅ Pods use it

13.3 External Secrets Operator (ESO) — Pull Secrets at Runtime

ESO pulls secrets from cloud providers (AWS Secrets Manager, GCP Secret Manager, Azure Key Vault, HashiCorp Vault) at runtime. Secrets NEVER touch Git — not even encrypted. The cluster authenticates via IAM roles and fetches secrets on a schedule.

ESO Architecture — Pulling Secrets from Cloud
  ☁️ AWS SECRETS MANAGER (or GCP/Azure/Vault)
  ┌─────────────────────────────────────────────────────────────────┐
  │  secret: prod/anihpj/db-password = "supersecret"               │
  └──────────────────────┬──────────────────────────────────────────┘
                         │ IAM Role / Service Account
                         ▼
  KUBERNETES CLUSTER
  ┌─────────────────────────────────────────────────────────────────┐
  │  External Secrets Operator (ESO):                               │
  │  1. Reads ExternalSecret CRD                                    │
  │  2. Authenticates to AWS/GCP/Azure (IAM federation)             │
  │  3. Pulls secret value from cloud provider                      │
  │  4. Creates K8s Secret in the target namespace                  │
  │  5. Refreshes on interval (e.g., every 1 hour)                  │
  │                                                                  │
  │  💡 ADVANTAGE: Secrets NEVER in Git — not even encrypted!       │
  │  💡 Centralized management meets enterprise compliance          │
  └─────────────────────────────────────────────────────────────────┘
external-secret.yaml — ESO for anihpj
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: anihpj-db-credentials
  namespace: anihpj
spec:
  refreshInterval: 1h           # Re-sync every hour
  secretStoreRef:
    name: aws-secrets-manager   # References SecretStore
    kind: SecretStore            # or ClusterSecretStore for cluster-wide
  target:
    name: db-credentials        # Target K8s Secret name
    creationPolicy: Owner       # ESO manages lifecycle
  data:
    - secretKey: password       # Key in the target K8s Secret
      remoteRef:
        key: prod/anihpj/db-password  # Path in AWS Secrets Manager
        property: password             # Property in the secret
# Result: K8s Secret "db-credentials" with key "password"
# Value pulled from AWS at sync time — never in Git!

13.4 SOPS — Encrypt with GPG or Cloud KMS

SOPS (Secrets OPerationS) encrypts specific values in YAML/JSON files using GPG, Age (X25519), or cloud KMS (AWS KMS, GCP KMS, Azure Key Vault). The key insight: only the VALUES are encrypted, the structure remains readable. FluxCD has native SOPS support — it decrypts during reconciliation. ArgoCD requires the ArgoCD Vault Plugin or a custom plugin.

Terminal — SOPS with Age
# Create an Age key (X25519 — modern, simpler than GPG)
age-keygen -o age-key.txt
# Public key: age1ql3z7hjy54pw3hyww5...

# Create a .sops.yaml config file
cat <<EOF > .sops.yaml
creation_rules:
  - path_regex: .*.yaml
    age: >-
      age1ql3z7hjy54pw3hyww5lay...
EOF

# Encrypt a secret file (only values are encrypted!)
sops --encrypt secret.yaml > secret.enc.yaml

# secret.enc.yaml — SAFE FOR GIT!
# apiVersion: v1
# kind: Secret
# metadata:
#   name: db-credentials
# data:
#   password: ENC[AES256_GCM,data:...<encrypted>...,iv:...,type:str]
# sops:
#   age: <public key info>
#   lastmodified: 2026-06-03T12:00:00Z

# ArgoCD: use argocd-vault-plugin with SOPS support

Chapter 16: FluxCD Fundamentals

FluxCD was the original GitOps operator — it predates ArgoCD and was the first to graduate CNCF. 🟡 Intermediate⏱️ ~1.5 hours🏗️ Architecture

16.1 What is FluxCD?

FluxCD was created at Weaveworks (2016) and became a CNCF Graduated project in 2023. Its core philosophy: everything is a controller. Rather than one big reconciler, Flux splits responsibilities across independent controllers that communicate through Kubernetes custom resources (CRDs).

🧠 Kitchen Brigade Analogy — Understanding Micro-Controllers

ArgoCD is like one head chef doing everything — cooking, plating, cleaning. If the chef is overwhelmed, everything slows down. FluxCD is like a professional kitchen brigade: the sauce chef (Source Controller) fetches ingredients from Git, the grill chef (Kustomize Controller) applies them to the cluster, the pastry chef (Helm Controller) handles Helm charts, and the expediter (Notification Controller) calls out when dishes are ready. Key insight: If the pastry chef has a problem, the grill keeps running. This is FluxCD's fault isolation — each controller fails independently.

16.5 Flux Kustomization — The Reconciliation Engine

The Kustomization CRD is Flux's workhorse. It takes artifact from a source → runs kustomize build (or plain YAML) → applies to the cluster → continuously watches for drift. It supports dependency ordering via dependsOn, health checks, and pruning.

kustomization.yaml — anihpj App
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: anihpj
  namespace: flux-system
spec:
  interval: 5m                    # Reconcile every 5 minutes
  sourceRef:
    kind: GitRepository
    name: anihpj-config
  path: ./apps/anihpj             # Path within the repo
  prune: true                     # Delete removed resources
  wait: true                      # Wait for all resources to be ready
  timeout: 3m                     # Max reconciliation time
  healthChecks:                   # Custom health checks
    - apiVersion: apps/v1
      kind: Deployment
      name: anihpj-web
      namespace: anihpj
  dependsOn:                      # Ordering: DB before app
    - name: postgres
  # Drift detection (default: enabled)
  # If someone manually changes the cluster, Flux reverts it!
  force: false                    # Don't force-recreate immutable fields

Chapter 17: FluxCD Helm Integration

FluxCD has first-class Helm support through the Helm Controller. Instead of running helm install manually, you define a HelmRelease CRD — and Flux manages the full lifecycle: install, upgrade, rollback, test, and uninstall. This is how Flux becomes a complete GitOps platform for Helm-based applications.

17.1 HelmRelease CRD — Declarative Helm Releases

The HelmRelease CRD replaces helm install and helm upgrade. You declare the chart, values, and upgrade strategy — Flux does the rest. Supports valuesFrom to pull values from ConfigMaps and Secrets.

helmrelease.yaml — PostgreSQL for anihpj
apiVersion: helm.toolkit.fluxcd.io/v2
kind: HelmRelease
metadata:
  name: anihpj-postgres
  namespace: anihpj
spec:
  interval: 10m                   # Reconcile every 10 minutes
  chart:
    spec:
      chart: postgresql
      version: "15.x"             # Major version 15, any patch
      sourceRef:
        kind: HelmRepository
        name: bitnami
        namespace: flux-system
  values:
    auth:
      database: jobpost
      username: anihpj
      # Password from Secret — NEVER in plaintext!
  valuesFrom:
    - kind: Secret
      name: postgres-credentials  # Pull password from K8s Secret
      valuesKey: password
      targetPath: auth.password   # Map to values.auth.password
  upgrade:
    remediation:
      retries: 3                  # Retry 3 times on failure
      remediateLastFailure: true # Rollback on failure
  test:
    enable: true                  # Run helm test after upgrade
  rollback:
    timeout: 5m
    cleanupOnFail: true

18.2 ImageRepository & ImagePolicy CRDs

ImageRepository scans a container registry and records all available tags. ImagePolicy selects which version to use — by semver, alphabetical, numerical, or regex. Together they determine the "latest good version" for your app.

image-automation.yaml — anihpj
# ─── IMAGE REPOSITORY: Scan registry ───
apiVersion: image.toolkit.fluxcd.io/v1beta2
kind: ImageRepository
metadata:
  name: anihpj
  namespace: flux-system
spec:
  image: ghcr.io/anihpj/anihpj
  interval: 5m                    # Scan every 5 minutes
  secretRef:
    name: ghcr-auth               # For private registries
---
# ─── IMAGE POLICY: Select version ───
apiVersion: image.toolkit.fluxcd.io/v1beta2
kind: ImagePolicy
metadata:
  name: anihpj
  namespace: flux-system
spec:
  imageRepositoryRef:
    name: anihpj
  policy:
    semver:
      range: ">=1.0.0 <3.0.0"    # Accept 1.x and 2.x, reject 3.x
  # Alternative policies:
  # alphabetical: { order: asc }  -- "latest", "stable"
  # numerical: { order: asc }     -- "1", "2", "10"
  # regex: { pattern: '^v\d+\.\d+\.\d+$' }

18.3 Image Update Automation — Git-Based Updates

The ImageUpdateAutomation CRD ties everything together. It watches ImagePolicy resources, and when a new version is selected, it commits the updated image tag back to your Git config repo. The Flux Kustomize/Helm controllers then pick up the change and deploy.

image-update-automation.yaml
apiVersion: image.toolkit.fluxcd.io/v1beta2
kind: ImageUpdateAutomation
metadata:
  name: anihpj-automation
  namespace: flux-system
spec:
  interval: 10m
  sourceRef:
    kind: GitRepository
    name: anihpj-config       # Which repo to commit to
  git:
    checkout:
      ref:
        branch: main
    commit:
      author:
        email: flux@anihpj.dev
        name: flux-bot
      messageTemplate: |
        🔄 [auto] Update {{ .AutomationObject }} image
        from {{ .From }} to {{ .To }}
        {{ range .Updated.ImagePolicy -}}
        - {{ .Name }}: {{ .From }} → {{ .To }}
        {{ end }}
    push:
      branch: main            # Push directly to main (or use PRs)
  update:
    path: ./apps/anihpj       # Where to update image references
    strategy: Setters          # Find and replace image tags

19.3 Webhook Receivers — Instant Reconciliation

By default, Flux polls Git at intervals. Webhook receivers eliminate the polling delay — GitHub/GitLab pushes trigger instant reconciliation. This is especially important for CI/CD pipelines where you want near-instant deployment after a push.

webhook-receiver.yaml — Instant Sync
# ─── RECEIVER: Listen for GitHub webhooks ───
apiVersion: notification.toolkit.fluxcd.io/v1beta2
kind: Receiver
metadata:
  name: github-receiver
  namespace: flux-system
spec:
  type: github
  events:
    - push                        # Trigger on git push
  secretRef:
    name: webhook-token           # HMAC secret from GitHub settings
  resources:
    - kind: GitRepository
      name: anihpj-config         # Which source to reconcile
# Once configured, add the webhook URL in GitHub:
# https://flux-webhook.anihpj.dev/hook/<hash>
# Now: git push → GitHub webhook → Flux reconciles in seconds!

21.2 Argo Rollouts — Progressive Delivery for ArgoCD

Argo Rollouts is a Kubernetes controller and CRD that replaces the standard Deployment resource. It gives you canary and blue-green strategies with metric-based promotion. ArgoCD natively understands Rollouts — you can see the progressive delivery status in the ArgoCD UI.

rollout.yaml — Canary Deployment for anihpj
apiVersion: argoproj.io/v1alpha1
kind: Rollout                    # ← Replaces "Deployment"
metadata:
  name: anihpj-web
  namespace: anihpj
spec:
  replicas: 5
  selector:
    matchLabels:
      app: anihpj
  template:                     # Same pod template as Deployment
    metadata:
      labels:
        app: anihpj
    spec:
      containers:
      - name: web
        image: ghcr.io/anihpj/anihpj:v2.1.0
        ports:
        - containerPort: 8000
  strategy:
    canary:                     # ← Progressive delivery strategy
      steps:
      - setWeight: 10           # Step 1: 10% traffic to v2
      - pause: {duration: 2m}   # Wait 2 minutes
      - setWeight: 25           # Step 2: 25% traffic
      - pause: {duration: 5m}   # Wait 5 minutes
      - setWeight: 50           # Step 3: 50% traffic
      - pause: {duration: 5m}
      - setWeight: 100          # Step 4: 100% — fully promoted!
      # Auto-rollback if metrics fail (e.g., error rate > 1%)
      analysis:
        templates:
        - templateName: anihpj-error-rate
# Once promoted, Rollout acts like a normal Deployment

21.3 Canary Deployments — Gradual Traffic Shifting

Canary deployments gradually shift a percentage of live traffic to the new version while monitoring error rates, latency, and saturation. If metrics degrade, the rollout auto-aborts and reverts to the stable version — without human intervention.

1
Deploy Canary

2
Shift 10%

3
Monitor

Prometheus checks error rate, latency, saturation for 2 min

4
Promote or Rollback

Metrics OK → increase to 25%. Metrics BAD → instant rollback to v1.

5

25% → 50% → 100%. Each step gated by metric analysis.

21.4 Blue-Green Deployments — Instant Cutover

Blue-green runs two complete environments: Blue (current/active) and Green (new version). Once Green is verified healthy, traffic instantly switches via a Service selector change. Rollback is equally instant — just point back to Blue.

rollout-bluegreen.yaml — Blue-Green for anihpj
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: anihpj-web
spec:
  replicas: 3
  strategy:
    blueGreen:
      activeService: anihpj-web-active     # Points to Blue
      previewService: anihpj-web-preview   # Points to Green
      autoPromotionEnabled: false           # Manual promotion
      # After manual verify: "argocd app promote anihpj-web"
      # Traffic instantly switches Blue ↔ Green
      # Rollback: "argocd app rollback anihpj-web" — instant!
  # 💡 Best for: Stateful apps, breaking schema changes
  # 💡 Trade-off: Needs 2x resources during cutover

21.5 Flagger — Progressive Delivery for FluxCD

Flagger is FluxCD's progressive delivery operator. It uses a Canary CRD and integrates with service meshes (Istio, Linkerd) and ingress controllers (NGINX, Contour) to perform traffic shifting with automated metric analysis.

22.1 Service Mesh and GitOps — Natural Partners

A service mesh manages service-to-service communication: mTLS (automatic encryption), traffic splitting (for canary deployments), retries, timeouts, and circuit breaking. These configurations are perfect for GitOps — they're YAML-defined, environment-specific, and critical enough to require audit trails.

🚦 Traffic Police Analogy — What a Service Mesh Does

Imagine a city with no traffic lights. Cars (requests) go directly between buildings (services). No one knows about accidents (failures) until it's too late. A service mesh is like installing smart traffic lights (Envoy/Linkerd proxies) at every intersection: they encrypt conversations (mTLS), direct some traffic to new routes (canary), retry if a car stalls (retries), and close roads that are overwhelmed (circuit breaking). The traffic rules (VirtualService, ServiceProfile) are stored in Git — change them with a PR, and the mesh enforces them automatically.

22.2 Istio + GitOps — Traffic Management as Code

Istio's VirtualService (traffic routing rules) and DestinationRule (subset definitions, load balancing, TLS) work together. The VirtualService says "send 10% to v2," and the DestinationRule defines what "v2" means. Both are YAML resources stored in Git.

destination-rule.yaml — Defining v1 and v2 Subsets
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: anihpj-web
  namespace: anihpj
spec:
  host: anihpj-web
  subsets:
  - name: v1                    # Stable version
    labels:
      version: "1.9"
  - name: v2                    # Canary version
    labels:
      version: "2.1"
  trafficPolicy:
    loadBalancer:
      simple: LEAST_REQUEST     # Distribute load efficiently
    connectionPool:
      tcp:
        maxConnections: 100     # Circuit breaker: max 100 connections
    tls:
      mode: ISTIO_MUTUAL        # Enforce mTLS for this service
# 💡 VirtualService uses these subsets in its route destinations
# 💡 Change subsets in Git → ArgoCD syncs → new versions appear/disappear
virtual-service.yaml — Canary Traffic Split for anihpj
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: anihpj-web
  namespace: anihpj
spec:
  hosts:
  - anihpj-web
  http:
  - match:
    - headers:
        canary:
          exact: "true"           # Internal test traffic → always v2
    route:
    - destination:
        host: anihpj-web
        subset: v2
      weight: 100
  - route:                        # Regular traffic → gradual split
    - destination:
        host: anihpj-web
        subset: v1                # Stable version
      weight: 90                  # 90% to v1
    - destination:
        host: anihpj-web
        subset: v2                # Canary version
      weight: 10                  # 10% to v2
# Change weights in Git → ArgoCD syncs → Istio shifts traffic!
# This is GitOps-driven canary deployment at the mesh level.

25.2 GitHub Actions + GitOps — CI for anihpj

GitHub Actions builds the Docker image, runs tests, and updates the config repo with the new tag. This is the most common CI setup for GitOps.

.github/workflows/ci.yml — Complete CI for anihpj
name: CI — Build, Test & Update Config
on:
  push:
    branches: [main]
    tags: ['v*']                  # Trigger on version tags
jobs:
  build-and-update:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      # ─── LINT ───
      - run: pip install flake8 && flake8 jobpost/
      # ─── TEST ───
      - run: pip install -r requirements.txt && python manage.py test jobpost
      # ─── BUILD & PUSH ───
      - uses: docker/build-push-action@v5
        with:
          push: true
          tags: ghcr.io/anihpj/anihpj:${{ github.ref_name }}
      # ─── UPDATE CONFIG REPO (HANDOFF TO GITOPS) ───
      - uses: actions/checkout@v4
        with:
          repository: anihpj/anihpj-config
          token: ${{ secrets.CONFIG_REPO_TOKEN }}
      - run: |
          cd apps/anihpj
          kustomize edit set image ghcr.io/anihpj/anihpj:${{ github.ref_name }}
          git config user.name "CI Bot"
          git commit -am "🔄 CI: Update anihpj to ${{ github.ref_name }}"
          git push
# 💡 ArgoCD/Flux detects the commit → auto-deploys!

25.3 GitLab CI + GitOps

GitLab CI follows the same pattern: build → test → push image → update config repo. GitLab's built-in Container Registry and Kubernetes integration make it particularly smooth. Note: GitLab Auto DevOps deploys directly to the cluster — bypassing Git. For GitOps, use a custom pipeline that commits to the config repo instead, giving you the audit trail Auto DevOps lacks.

.gitlab-ci.yml — GitLab Pipeline for anihpj
stages: [test, build, update-config]
variables:
  IMAGE: registry.gitlab.com/anihpj/anihpj

test:
  stage: test
  script:
    - pip install flake8 && flake8 jobpost/
    - python manage.py test jobpost

build:
  stage: build
  script:
    - docker build -t $IMAGE:$CI_COMMIT_TAG .
    - docker push $IMAGE:$CI_COMMIT_TAG
  only: [tags]                    # Only build on version tags

update-config:
  stage: update-config
  script:
    - git clone https://gitlab-ci-token:${CI_JOB_TOKEN}@gitlab.com/anihpj/anihpj-config.git
    - cd anihpj-config/apps/anihpj
    - kustomize edit set image $IMAGE:$CI_COMMIT_TAG
    - git commit -am "CI: Update to $CI_COMMIT_TAG" && git push
  only: [tags]
# 💡 ArgoCD watches anihpj-config → auto-deploys on commit

27.2 Managing 100+ Applications at Scale

At scale, you can't manually create each Application. Use ApplicationSets with generators (list, cluster, SCM, matrix) to auto-create Applications. Standardize deployment patterns with a company-wide "golden Application template."

ApplicationSet — Auto-Onboarding New Teams
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: team-apps
spec:
  generators:
    - git:
        repoURL: https://github.com/anihpj/anihpj-config
        revision: main
        directories:
        - path: teams/*              # One app per team directory
  template:
    metadata:
      name: '{{path.basename}}'
      labels:
        team: '{{path.basename}}'
        managed-by: appset
    spec:
      project: '{{path.basename}}'
      source:
        repoURL: https://github.com/anihpj/anihpj-config
        path: '{{path}}'
      destination:
        server: https://kubernetes.default.svc

          prune: true

27.3 GitOps Governance — Policy as Code

Use OPA/Gatekeeper to enforce policies before and after deployment. Require labels, resource limits, security contexts, and approved registries. Policies stored in Git = auditable governance.

  name: requireresourcelimits

    spec:
      names:
        kind: RequireResourceLimits

🧠 8 Key Concepts You MUST Memorize for the CGOA Exam
1. Pull vs Push

GitOps agent PULLS from Git. CI/CD PUSHES to cluster. This is THE most tested concept.

2. ArgoCD = UI + SSO + RBAC

Monolithic, Projects, ApplicationSets. Image Updater is separate, updates cluster directly.

3. FluxCD = Micro-Controllers

Native SOPS, Git-based image automation. CLI-focused. No built-in SSO or rich UI.

4. Drift = Cluster ≠ Git

selfHeal=true auto-corrects. Without it, manual sync needed. Always testable.

5. 4 Secret Solutions

Sealed Secrets (simplest) → ESO (cloud) → SOPS (Flux native) → Vault (enterprise).

6. CI/CD Handoff = Git Commit

CI builds → commits tag to config repo. CD (GitOps) detects commit → deploys.

7. Canary vs Blue-Green

Canary: gradual % + metrics. Blue-green: 2 full envs, instant switch, 2x resources.

8. Never :latest in Production

Tags must be immutable: semver (v1.2.3), Git SHA, or hybrid (v1.2.3-abc1234).

B.1 Dockerfile — anihpj Django App (Multi-Stage Build)

Dockerfile — Multi-Stage (Smaller & More Secure)
# Stage 1: Build dependencies (BIG image ~500MB, THROWN AWAY)
FROM python:3.12-slim AS builder
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir --user -r requirements.txt
# Stage 2: Production image (SLIM, only ~200MB!)
FROM python:3.12-slim
WORKDIR /app
# Copy ONLY the installed packages from builder — NOT the full SDK
COPY --from=builder /root/.local /root/.local
COPY . .
ENV PATH=/root/.local/bin:$PATH
ENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1
RUN python manage.py collectstatic --noinput
EXPOSE 8000
CMD ["gunicorn", "anihpj.wsgi:application", "--bind", "0.0.0.0:8000", "--workers", "4"]
# 💡 Stage 1 = ~500MB (thrown away). Stage 2 = ~200MB (deployed).
# 💡 Multi-stage = faster pulls, smaller attack surface, no build tools in prod!
💡 Why Multi-Stage Build?

Single-stage images include compilers, git, and build tools (~500MB) — all of which are security risks in production. Multi-stage builds copy ONLY the compiled artifacts to a fresh slim image (~200MB). Result: smaller images, faster CI, fewer vulnerabilities.

Answer: 2. In push-based CI/CD, pipeline must hold cluster credentials. If compromised, attacker gets cluster access. GitOps agent runs inside cluster.

🏆 CGOA Exam Quick Reference — 95%+ Readiness

📖 Must-Know Definitions (Guaranteed to Appear)
GitOps

Git as single source of truth + declarative config + automated reconciliation. Agent PULLS, never pushes.

Pull vs Push

GitOps = PULL (agent fetches from Git). CI/CD = PUSH (pipeline sends to cluster). Most tested concept.

Reconciliation

Observe → Diff → Act loop. Compares Git (desired) vs Cluster (actual). Corrects drift.

Drift

Cluster state ≠ Git state. selfHeal=true auto-corrects. Without: OutOfSync until manual sync.

Declarative Config

YAML/JSON describes desired state. No imperative scripts. "What you want" not "how to do it."

Immutable Tags

semver (v1.2.3), Git SHA, hybrid (v1.2.3-abc1234). NEVER :latest or :main in production.

🔷 ArgoCD Quick Facts (30% of Exam)
Components

API Server + Repo Server + App Controller + Redis + Notifications Controller. Monolithic architecture.

Application CRD

source (repo+path) + destination (cluster+namespace) + syncPolicy (automated/manual).

Sync Policies

automated.prune=true (delete removed). automated.selfHeal=true (auto-correct drift).

ApplicationSet

Generators: List, Cluster, Git, SCM, Matrix, Merge. Auto-creates Applications from templates.

App of Apps

Root app → child apps via Git directory. One kubectl apply bootstraps entire cluster.

Key Commands

argocd app create/sync/diff/rollback. argocd cluster add. argocd admin export (backup).

🟢 FluxCD Quick Facts (20% of Exam)
Architecture

Micro-controllers: Source, Kustomize, Helm, Notification, Image Automation. Each independent.

Key CRDs

GitRepository (source) + Kustomization (reconcile) + HelmRelease (Helm) + ImagePolicy.

Bootstrap

flux bootstrap github → installs controllers, connects to Git, pushes config. Self-managing.

Image Automation

Flux commits to Git (pure GitOps). ArgoCD Image Updater patches cluster directly. KEY distinction.

SOPS

Native SOPS support. Decrypts at reconciliation. ArgoCD needs plugin (argocd-vault-plugin).

HelmRelease

Declarative Helm. values + valuesFrom + upgrade.remediation + rollback. Replaces helm CLI.

🔐 Secrets Management — Decision Cheat Sheet
Sealed Secrets

No external deps. Asymmetric encryption. Best for: simple setups, small teams.

ESO

Cloud-native. Secrets never in Git. Best for: AWS/GCP/Azure shops.

SOPS

Encrypt values, keep structure. Flux native. Best for: FluxCD users, GPG/Age.

Vault

Enterprise KMS. Dynamic creds. Full audit. Best for: compliance (SOC2/HIPAA).
