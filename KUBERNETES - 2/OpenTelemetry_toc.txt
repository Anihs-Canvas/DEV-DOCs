    Chapter 1: What is Observability? — The Big Picture
    ────────────────────────────────────────────────────
      1.1  The Evolution: Monitoring → Observability
           - Traditional Monitoring: CPU > 90%? Alert! RAM > 80%? Alert!
           - You knew WHAT was wrong (resource saturated) but rarely WHY
           - Pre-computed dashboards: you can only answer questions you predicted
           - Observability: Ask NEW questions about your system WITHOUT new code
           - The shift: "Is my server up?" → "Why is checkout latency p95 at 4.2s?"
           - Observability = Metrics + Traces + Logs + Context
           [TIMELINE: 2000s Nagios → 2010s Graphite/Grafana → 2020s OTel + Jaeger]

           [EVOLUTION STRIP]
           ┌──────────────┐  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐
           │  📟 2000s    │  │  📊 2010s     │  │  🔍 2018+     │  │  🧠 2022+     │
           │  Monitoring  │  │  Metrics+Vis  │  │  Distributed  │  │  Observability│

      1.2  The Three Pillars: Logs, Metrics, and Traces
           a) Logs — "What happened?"
              - Timestamped, immutable records of discrete events
              - Structured logging (JSON) vs Unstructured (plain text)
              - Examples: "User 42 created JobPost #7", "DB connection timeout"
              - Key attributes: timestamp, severity, message, trace_id, span_id
              [LOG LINE ANATOMY — annotated JSON log with trace correlation]
              ┌─────────────────────────────────────────────────────────────┐
              │ {"timestamp":"2026-06-06T14:30:00Z","severity":"ERROR",     │
              │  "message":"Failed to save JobPost","trace_id":"a1b2c3...",│
              │  "span_id":"d4e5f6...","service":"jobpost","user_id":42}   │
              └─────────────────────────────────────────────────────────────┘

           b) Metrics — "How much?"
              - Numeric measurements aggregated over time intervals
              - Counter: Only increases (request_count, error_count, jobs_created)
              - Gauge: Goes up and down (active_connections, queue_depth, cpu_temp)
              - Histogram: Distribution (request_duration_seconds, payload_size_bytes)
              - Example: anihpj POST /jobs/ latency p99 = 1.2s (Histogram)
              [METRIC TYPES VISUAL — 4 instrument illustrations]
              ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐
              │📈 Counter│  │📊 Gauge   │  │📉 Histo  │  │🧭 Summary│
              │ Only ↑   │  │ Up & Down │  │ Buckets   │  │Quantiles │
              │requests  │  │connections│  │durations  │  │p50,p95,p99│

              └──────────┘  └──────────┘  └──────────┘  └──────────┘

           c) Traces — "Where in the journey?"
              - A trace = a tree of spans showing the path of a request
              - Each span = a single unit of work (DB query, HTTP call, cache lookup)
              - Shows: parent-child relationships, timing, errors at each step
              - Example: User POST /jobs/ → Django view → validate → save DB → cache

              │ ├── Span: jobs.views.create_job (230ms)                 │
              │ │   ├── Span: auth.validate_token (8ms)                 │

              │ │   └── Span: redis.SET cache (12ms)                    │
              │ └── Span: django.response (5ms)                         │
              └─────────────────────────────────────────────────────────┘

      1.3  Why Traditional Monitoring Falls Short in Microservices
           - Monolith: 1 process, 1 log file, easy to debug
           - Microservices: 50+ services, requests bounce across network
           - "Where did this request fail?" — impossible with metrics alone
           - "Which service caused the latency spike?" — guesswork without traces
           - The cardinality explosion: 100 services × 50 endpoints × 10 status codes
           - Traditional monitoring dashboards break down at scale
           [BEFORE/AFTER: Monolith debugging vs Microservices debugging]

      1.4  Observability vs Monitoring — Key Differences
           [COMPARISON TABLE]

           |-----------------|-------------------------|---------------------------|

    Chapter 2: Introduction to OpenTelemetry
    ────────────────────────────────────────
      2.1  What is OpenTelemetry (OTel)?
           - CNCF incubating project (formed from OpenTracing + OpenCensus merger, 2019)
           - A collection of APIs, SDKs, and tools to generate, collect, and export
             telemetry data (traces, metrics, and logs)
           - NOT a backend — it does NOT store or visualize data
           - The "universal language" for observability data (like TCP/IP for networking)
           - Three key properties:
             • Vendor-neutral: Switch backends without changing instrumentation
             • Cross-language: Python, Java, Go, JS, .NET, Rust, C++ (same concepts)
             • Community-owned: 1,600+ contributors, 50+ vendors support OTLP
           [CARD: OTel at a Glance — founded, merged, CNCF status, contributors]

      2.2  The Problem OTel Solves — Vendor-Neutral Observability
           - Before OTel: Vendor-specific SDKs lock you in
             • New Relic agent, Datadog dd-trace, Dynatrace OneAgent — all proprietary
             • Switching vendors = re-instrument ENTIRE codebase
             • Multi-cloud teams use 3+ different observability tools
           - With OTel: Instrument ONCE, export ANYWHERE
             • Same spans go to Jaeger (dev), Grafana Tempo (staging), Datadog (prod)
             • No code changes — just change the OTel Collector exporter config
           [BEFORE/AFTER: Vendor lock-in vs OTel freedom]
           ┌────────────────────────────┐   ┌──────────────────────────────┐
           │ BEFORE OTel (Lock-in)      │   │ WITH OTel (Freedom)          │
           │                            │   │                              │
           │ App → dd-trace → Datadog   │   │ App → OTel SDK → OTel Col → │
           │ App → newrelic → New Relic │   │   ├── Jaeger (traces)       │
           │ App → dynatrace → Dynatrace│   │   ├── Prometheus (metrics)  │
           │                            │   │   ├── Loki (logs)           │
           │ ❌ 3 SDKs, 3 integrations  │   │   └── Datadog (all 3)       │
           │ ❌ Switching = rewrite     │   │   ✅ 1 SDK, many exporters  │
           └────────────────────────────┘   └──────────────────────────────┘

      2.3  OTel's Place in the CNCF Ecosystem
           - CNCF Observability landscape:
             • Metrics: Prometheus (graduated), Cortex, Thanos, Mimir
             • Traces: Jaeger (graduated), Zipkin, Grafana Tempo
             • Logs: Fluentd (graduated), Fluent Bit, Grafana Loki
             • Profiles: Pyroscope, Parca
           - OTel is the GATHERER for all of the above
           - OTel does NOT replace Prometheus — it COMPLEMENTS it
           - Prometheus scrapes metrics; OTel pushes OR scrapes

      2.4  The OpenTelemetry Project Structure (Signals, API, SDK, Collector)
           - Signals: The types of data OTel handles
             • Traces — distributed request paths
             • Metrics — numeric measurements
             • Logs — timestamped events (stable in 2024+)
             • Baggage — contextual key-value data propagated alongside traces
           - API: Language-specific interfaces (opentelemetry-api package)
             • Defines WHAT you can do (interfaces, abstract classes)
             • No implementation — just contracts
           - SDK: Language-specific implementations (opentelemetry-sdk package)
             • The actual code that does the work (sampling, batching, exporting)
           - Collector: Standalone binary (otelcol)
             • Receives telemetry from many sources
             • Processes, filters, enriches, batches
             • Exports to one or many backends
           [LAYER DIAGRAM: API → SDK → Collector → Backend]

      2.5  OTel vs Prometheus vs Jaeger vs Fluentd — What Goes Where?
           [COMPARISON TABLE — who does what]
           | Tool          | Signal   | Role in the Stack                     |
           |---------------|----------|---------------------------------------|
           | OpenTelemetry | All 3    | Generate + collect + export telemetry |
           | Prometheus    | Metrics  | Scrape + store + alert on metrics     |
           | Jaeger        | Traces   | Store + visualize distributed traces  |
           | Fluentd/Bit   | Logs     | Collect + aggregate + forward logs    |
           | Grafana       | All 3    | Visualize (dashboards, explore, alert)|
           | Loki          | Logs     | Store + query logs (like Prometheus   |
           |               |          |   but for logs)                       |
           | Tempo         | Traces   | Store + query traces (like Prometheus |
           |               |          |   but for traces)                     |
           - Key insight: OTel is the PRODUCER; Prometheus/Jaeger are CONSUMERS
           - OTel + Prometheus: OTel generates metrics, Prometheus scrapes them
           - OTel + Jaeger: OTel generates spans, Jaeger stores and displays them

      2.6  Key Terminology: Signals, Providers, Exporters, Processors, Receivers
           - Signal: A type of telemetry (Traces, Metrics, Logs)
           - TracerProvider: Creates Tracers (the entry point for trace creation)
           - MeterProvider: Creates Meters (the entry point for metric creation)
           - LoggerProvider: Creates Loggers (the entry point for log emission)
           - Span: A single operation within a trace (named, timed, attributed)
           - Span Context: The IDs (trace_id, span_id) that propagate across services
           - Exporter: Sends telemetry to a backend (OTLP, Jaeger, Prometheus, Console)
           - Processor: Middleware in the pipeline (Batch, Filter, Attribute, Transform)
           - Receiver: Entry point in the Collector (OTLP, Jaeger, Prometheus, Kafka)
           - Resource: Metadata about the entity producing telemetry (service.name,
             service.version, host.name, container.id)
           - Semantic Conventions: Standardized attribute names across all languages
             (e.g., http.method, http.status_code, db.system, db.operation)
           [TERMINOLOGY MAP — visual relationship diagram]
           TracerProvider ──▶ Tracer ──▶ Span ──▶ SpanProcessor ──▶ Exporter
           MeterProvider  ──▶ Meter  ──▶ Instrument ──▶ MetricReader ──▶ Exporter
           LoggerProvider ──▶ Logger ──▶ LogRecord ──▶ LogRecordProcessor ──▶ Exp.

      2.7  Hands-On: Install OTel in a Python Project
           Step 1: pip install opentelemetry-api opentelemetry-sdk
           Step 2: pip install opentelemetry-exporter-otlp-proto-grpc
           Step 3: Create a minimal trace script:
               from opentelemetry import trace
               from opentelemetry.sdk.trace import TracerProvider
               from opentelemetry.sdk.trace.export import ConsoleSpanExporter, BatchSpanProcessor
               provider = TracerProvider()
               processor = BatchSpanProcessor(ConsoleSpanExporter())
               provider.add_span_processor(processor)
               trace.set_tracer_provider(provider)
               tracer = trace.get_tracer(__name__)
               with tracer.start_as_current_span("hello-otel") as span:
                   span.set_attribute("user.id", 42)
                   print("Span created!")

           Step 4: Run it — see JSON output on console (trace_id, span_id, name, attributes)
           Step 5: Same pattern works across ALL languages
           Step 6: This is MANUAL instrumentation — we'll automate in Chapter 6

    Chapter 3: OpenTelemetry Architecture Deep Dive
    ───────────────────────────────────────────────
      3.1  The OTel Architecture at a Glance
           - Three layers: API (interfaces) → SDK (implementation) → Collector (pipeline)
           - Two deployment models:
             a) Direct export: App SDK → Backend (simple, used in development)
             b) Collector-based: App SDK → Collector → Backend(s) (production)
           - The Collector is OPTIONAL but RECOMMENDED for production
           - Why the Collector matters:
             • Centralized configuration (don't configure exporters in every app)
             • Batching and retry (reduce network overhead to backends)
             • Enrichment (add cluster/region attributes without touching app code)
             • Routing (send traces to Jaeger, metrics to Prometheus, logs to Loki)
             • Filtering (drop health-check spans to reduce cost)
           [ARCHITECTURE: Side-by-side — Direct vs Collector deployment models]
           ┌─────────────────────────────┐  ┌───────────────────────────────┐
           │ DIRECT (Development)        │  │ COLLECTOR (Production)         │
           │                             │  │                               │
           │ anihpj → OTel SDK → Jaeger  │  │ anihpj → OTel SDK → OTel Col→│
           │ anihpj → OTel SDK → Prometh │  │    ├── Jaeger (traces)       │
           │                             │  │    ├── Prometheus (metrics)  │
           │ ❌ Config per app           │  │    └── Loki (logs)           │
           │ ❌ No batching/filtering    │  │    ✅ Central config         │
           │ ❌ Tight coupling to backend│  │    ✅ Batch, filter, enrich  │
           └─────────────────────────────┘  └───────────────────────────────┘

      3.2  The OpenTelemetry API — Interfaces for Telemetry
           - API = contracts, no implementation
           - Tracer API: get_tracer(), start_span(), span context management
           - Meter API: get_meter(), create_counter(), create_histogram()
           - Context API: attach/detach context, propagation across threads/coroutines
           - Baggage API: store/retrieve key-value pairs in context
           - Why separate API from SDK?
             • Library authors depend ONLY on API (no SDK opinion)
             • Application owners choose which SDK implementation
             • API stays stable; SDK can evolve
             • Multiple SDKs can coexist (mocking in tests)
           [CODE: Library author vs App owner dependency diagram]
           ┌─────────────────────┐      ┌─────────────────────┐
           │ Library Author      │      │ Application Owner   │
           │ (e.g., Django OTel  │      │ (e.g., anihpj team) │

           │                     │      │                     │

      3.3  The OpenTelemetry SDK — Implementation and Configuration
           - SDK = the real implementation (sampling, batching, resource detection)
           - TracerProvider: Creates tracers, holds sampling policy, span processors
           - SpanProcessor: Hook into span lifecycle (on_start, on_end)
             • BatchSpanProcessor — production (batches spans, async export)
             • SimpleSpanProcessor — development (exports immediately, synchronous)
             • Custom processors for your own logic
           - Sampler: Decides which spans to keep
             • AlwaysOn, AlwaysOff, TraceIdRatioBased, ParentBased
           - MeterProvider: Creates meters, holds metric readers and exporters
           - MetricReader: Pulls metrics from instruments
             • PeriodicExportingMetricReader — exports on interval (60s default)
           - LoggerProvider: Creates loggers, holds log processors and exporters
           - Configuration via environment variables:
             • OTEL_SERVICE_NAME=anihpj
             • OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317
             • OTEL_TRACES_SAMPLER=traceidratio
             • OTEL_TRACES_SAMPLER_ARG=0.1 (keep 10%)
           [DIAGRAM: SDK internals — Provider → Processor → Exporter pipeline]

      3.4  The OpenTelemetry Collector — Receivers, Processors, Exporters
           - The Collector is a standalone Go binary (otelcol or otelcol-contrib)
           - Three pipeline stages (in order):
             a) Receivers: Accept telemetry data (OTLP gRPC/HTTP, Jaeger, Prometheus)
             b) Processors: Transform/filter/batch (Batch, MemoryLimiter, Filter)
             c) Exporters: Send to backends (OTLP, Jaeger, Prometheus, Logging)
           - Connectors: Bridge between pipelines (SpanMetrics, ServiceGraph)
           - Extensions: Non-pipeline features (health_check, pprof, zpages, oauth2client)
           - Deployment as Agent (sidecar): 1 per node, lightweight, local batching
           - Deployment as Gateway (centralized): 1 per cluster, heavy processing

      3.5  The OTLP Protocol — How Telemetry Data Travels
           - OTLP = OpenTelemetry Protocol (the standard wire format)
           - Encodes traces, metrics, and logs as Protocol Buffers (protobuf)
           - Transports:
             • gRPC (port 4317): Binary protobuf, streaming, high performance
             • HTTP/1.1 (port 4318): JSON or binary protobuf, firewall-friendly
           - Why OTLP matters:
             • One protocol for ALL three signals (no Jaeger protocol for traces +
               Prometheus exposition format for metrics + Fluentd for logs)
             • Standardized by IETF
             • All major backends now accept OTLP natively
           [PROTOCOL COMPARISON TABLE]
           | Transport | Port  | Format         | Use Case                    |
           |-----------|-------|----------------|-----------------------------|
           | gRPC      | 4317  | Binary protobuf| Service-to-collector (fast)|
           | HTTP/1.1  | 4318  | JSON or binary | Browser, firewall-friendly |
           | HTTP/2    | 4317  | Binary protobuf| Streaming telemetry        |

      3.6  The OpenTelemetry Protocol (OTLP) over gRPC and HTTP
           - gRPC: High-performance, bidirectional streaming, requires HTTP/2
           - HTTP: Works anywhere HTTP works (browsers, lambdas, restrictive networks)
           - Content-Type headers:
             • application/x-protobuf (binary)
             • application/json (debugging, web-friendly)
           - Default endpoints:
             • Traces: http://collector:4318/v1/traces
             • Metrics: http://collector:4318/v1/metrics
             • Logs: http://collector:4318/v1/logs
           - Compression: gzip supported to reduce bandwidth

      3.7  Resource Detection and Semantic Conventions
           - Resource: Describes the entity producing telemetry
           - Every span, metric, and log carries resource attributes
           - Key resource attributes:
             • service.name: "anihpj" (REQUIRED — the most important attribute)
             • service.version: "2.4.1"
             • service.namespace: "production"
             • host.name, container.id, k8s.pod.name, k8s.namespace.name
           - Auto-detection via resource detectors:
             • OTEL_RESOURCE_ATTRIBUTES env var
             • otel.resource.detectors (Docker, Kubernetes, AWS, GCP, Azure)
           - Semantic Conventions: Standard names for common attributes
             • http.method (not "method" or "http_method" — standardized!)
             • http.status_code, http.url, http.route
             • db.system, db.operation, db.name
             • This is HOW OTel achieves vendor neutrality — everyone speaks same names

    Chapter 4: Context Propagation and Sampling
    ───────────────────────────────────────────
      4.1  What is Context Propagation?
           - Context: Metadata that travels WITH a request across service boundaries
           - In a monolith: no need — everything runs in one process
           - In microservices: essential — how do you correlate spans across services?
           - Example: anihpj frontend → auth service → jobpost API → PostgreSQL
             • Without propagation: 4 disconnected traces, no correlation
             • With propagation: 1 trace with 4 nested spans, full visibility
           - Context carries:
             • trace_id (which trace does this span belong to?)
             • span_id (which span is the parent of the next span?)
             • trace_flags (is this trace sampled?)
             • baggage (custom key-value pairs — user_id, tenant_id, cart_id)
           [DIAGRAM: Context flow across services]
           ┌──────────┐    traceparent    ┌──────────┐    traceparent    ┌──────────┐
           │ Service A│ ───header────▶ │ Service B│ ───header────▶ │ Service C│
           │ Span A   │                  │ Span B   │                  │ Span C   │
           │trace_id=X│                  │trace_id=X│                  │trace_id=X│
           │span_id=A │                  │parent_id=│                  │parent_id=│
           │          │                  │    A     │                  │    B     │
           └──────────┘                  └──────────┘                  └──────────┘
           All three spans share trace_id=X → one unified trace in Jaeger!

      4.2  Trace Context (W3C Trace-Context Standard)
           - W3C Trace-Context: The standard for context propagation (NOT OTel-specific)
           - Two HTTP headers:
             a) traceparent: 00-{trace_id}-{span_id}-{trace_flags}
                • Version: 00 (current)
                • trace_id: 32 hex chars (16 bytes)
                • span_id: 16 hex chars (8 bytes) — the parent span
                • trace_flags: 01 = sampled, 00 = not sampled
                Example: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
           - tracestate: Vendor-specific key-value pairs (optional)
                Example: vendor1=opaqueValue1,vendor2=opaqueValue2
           - How propagation works:
             1. Service A starts a span, sets traceparent header on outgoing HTTP request
             2. Service B receives request, extracts traceparent, creates child span
             3. Service B's span has same trace_id, parent_span_id = Service A's span_id
           [ANATOMY: traceparent header breakdown — annotated]
           ┌─────────────────────────────────────────────────────────────────┐
           │ traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01 │
           │               │  │                              │                │ │
           │               │  └── trace_id (32 hex)──────────┘                │ │
           │               │         span_id (16 hex) ────────────────────────┘ │
           │               └── version                                          │
           │                      trace_flags (01 = sampled) ───────────────────┘
           └─────────────────────────────────────────────────────────────────┘

      4.3  Baggage — Passing Custom Data Across Services
           - Baggage: Key-value pairs that travel WITH the trace context
           - Header: baggage: key1=value1,key2=value2 (comma-separated)
           - Use cases:
             • user_id=42 → all downstream services see which user made the request
             • tenant_id=acme-corp → multi-tenant observability
             • environment=staging → filter traces by environment
             • cart_id=abc123 → trace an e-commerce cart through checkout
           - CRITICAL: Baggage values are propagated to ALL downstream services
             • NEVER put secrets in baggage (it's visible in headers!)
             • Keep baggage small (headers have size limits)
           - Baggage vs Span Attributes:
             • Baggage: travels across services automatically
             • Span Attributes: stay on one span, must be manually forwarded
           [CODE: Setting baggage in Python]
           from opentelemetry import baggage
           ctx = baggage.set_baggage("user.id", "42")

      4.4  How Context Flows: HTTP Headers (traceparent, tracestate)
           - Typical HTTP request with context:
             GET /api/jobs/ HTTP/1.1
             Host: anihpj.example.com
             traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             tracestate: dd=s:1;t.dm:-4
             baggage: user_id=42,tenant=acme
           - Extraction (incoming request):
             1. Extract traceparent from headers
             2. Build a SpanContext from it
             3. Create a new span with parent = extracted span_id
           - Injection (outgoing request):
             1. Get current span's context
             2. Serialize as traceparent header
             3. Add to outgoing HTTP request headers
           - Automatic propagation: Most HTTP libraries auto-inject/extract via instrumentation
           - Manual propagation: When using raw sockets or custom protocols
           [FLOWCHART: Extract → Process → Inject cycle]

      4.5  Sampling Fundamentals — Head Sampling vs Tail Sampling
           - Why sample? 100% of traces at scale = too much data, too expensive
           - Head Sampling: Decision made at span START (before seeing the full trace)
             • Pros: Simple, low overhead, doesn't store unsampled spans
             • Cons: Can't know if a trace contains an error before sampling
             • Example: "Keep 10% of traces" — you might drop the 0.1% that have errors
           - Tail Sampling: Decision made at trace END (after seeing the full trace)
             • Pros: Can keep ALL error traces, all slow traces (latency > 2s)
             • Cons: Must store spans temporarily, higher overhead, Collector-only
             • Example: "Keep all traces with status=ERROR OR duration > 5s"
           [COMPARISON: Head vs Tail Sampling decision tree]
           ┌──────────────────────────┐  ┌──────────────────────────────┐
           │ HEAD SAMPLING            │  │ TAIL SAMPLING                │
           │ (SDK, span start)        │  │ (Collector, after trace done)│
           │                          │  │                              │
           │ 🔹 Probabilistic: 10%    │  │ 🔹 Error-based: keep all     │
           │ 🔹 Rate-limiting: 100/s  │  │    traces with ERROR status  │
           │ 🔹 AlwaysOn/AlwaysOff    │  │ 🔹 Latency-based: keep all   │
           │                          │  │    traces > 2s               │
           │ ❌ Can't see errors      │  │ 🔹 Composite: any of above   │
           │ ❌ Can't see slow traces │  │ ✅ Keeps interesting traces  │
           │ ✅ No storage overhead   │  │ ❌ Must buffer all spans     │
           └──────────────────────────┘  └──────────────────────────────┘

      4.6  Sampling Strategies: AlwaysOn, AlwaysOff, Probabilistic, Rate-Limiting
           a) AlwaysOn (ALWAYS_ON): Record every span — dev/staging only
           b) AlwaysOff (ALWAYS_OFF): Record nothing — effectively disables tracing
           c) TraceIdRatioBased (probabilistic):
              • Hash trace_id → compare against ratio
              • ratio=1.0 = 100%, ratio=0.1 = 10%, ratio=0.01 = 1%
              • Deterministic: same trace_id always gets same decision
              • This is what you use in production
           d) ParentBased: Child spans follow parent's sampling decision
              • If parent was sampled → child IS sampled (maintains trace integrity)
              • If parent was NOT sampled → child NOT sampled
              • If no parent (root span) → use delegate sampler (e.g., TraceIdRatioBased)
           e) RateLimiting: Max N spans per second (not recommended — breaks traces)
           - Configuring sampling in code:
             sampler = ParentBased(root_sampler=TraceIdRatioBased(ratio=0.1))

      5.1  What is Manual Instrumentation?
           - You write code to create spans, metrics, and logs explicitly
           - Full control over: span names, attributes, events, status codes
           - When to use manual instrumentation:
             • Custom business logic (not covered by auto-instrumentation)
             • Adding domain-specific attributes (user_id, order_total, plan_type)
             • Fine-grained spans within a function (validation, calculation, save)
           - Trade-off: More control BUT more code to write and maintain
           - Best practice: Start with auto-instrumentation, add manual for gaps

      5.2  The OTel Python SDK — Setup and Configuration
           - Core packages:

      5.3  Creating Spans Manually (Tracer Provider, Spans, Span Events)
           a) Starting and ending spans
              - Context manager (recommended): with tracer.start_as_current_span("name"):
              - Manual: span = tracer.start_span("name"); ...; span.end()
              - ALWAYS end spans — leaked spans waste memory
           b) Adding attributes, events, and status to spans
              - Attributes: span.set_attribute("key", "value") — max 128 per span
              - Events: span.add_event("cache.miss", attributes={"key": "user:42"})
                • Events have a timestamp (time when the event occurred)
                • Use for notable moments within a span's lifetime
              - Status: span.set_status(StatusCode.OK) or StatusCode.ERROR
                • If unset, status defaults to UNSET
                • Set ERROR + record exception for failed spans
              - Recording exceptions:
                try:
                    ...
                except Exception as ex:
                    span.record_exception(ex)
                    span.set_status(StatusCode.ERROR, str(ex))
           c) Span kind (SERVER, CLIENT, INTERNAL, PRODUCER, CONSUMER)
              - SERVER: Incoming request (HTTP server handling a request)
              - CLIENT: Outgoing request (HTTP client calling another service)
              - INTERNAL: Internal operation (function, computation, no RPC)
              - PRODUCER: Sending a message (Kafka producer, SQS send)
              - CONSUMER: Receiving a message (Kafka consumer, SQS receive)
              - Why kind matters: Jaeger/Grafana show different icons per kind

           a) Counters, UpDownCounters, Histograms, ObservableGauges
              - Counter: counter.add(1) — request count, error count, job count
                • Value must be >= 0, only increases (monotonic)

                • Good buckets give you useful p50/p95/p99
              - ObservableGauge: Point-in-time value — CPU temp, memory usage
                • Callback-based: OTel calls your function to get the current value
              - ObservableUpDownCounter: Async up-down counter

      6.1  What is Auto-Instrumentation?
           - Automatically generates telemetry WITHOUT modifying your code
           - Uses monkey-patching to hook into frameworks and libraries
           - Covers: HTTP frameworks (Django, Flask, FastAPI), databases (psycopg2,
             redis, pymongo), HTTP clients (requests, urllib, aiohttp), gRPC, Celery
           - The magic: pip install + environment variables → instant observability
           - What you get for Django out of the box:
             • Every HTTP request → automatically a trace with nested spans
             • Django middleware span, URL routing span, view execution span
             • DB queries auto-instrumented (SQL, duration, rows affected)
             • Cache operations auto-instrumented (key, hit/miss, duration)
             • Request/response headers, status codes automatically captured
           [BEFORE/AFTER: Django app with no changes → full telemetry in Grafana]

      6.2  How Auto-Instrumentation Works (Monkey-Patching, Bytecode)
           - Instrumentors are small libraries that modify existing code at import time
           - Example: opentelemetry-instrumentation-django wraps Django's WSGI handler
           - The wrapper: start_span → call original handler → end_span
           - How it hooks into Django:
             1. At import time, monkey-patches django.core.handlers.wsgi.WSGIHandler
             2. Original __call__ method is wrapped in a span
             3. Request attributes (method, path, status) extracted as span attributes
           - Same pattern for ALL instrumentations:
             • psycopg2: Wraps cursor.execute() → captures SQL + duration
             • redis: Wraps execute_command() → captures command + key + duration
             • requests: Wraps Session.send() → captures method + URL + status

      6.4  Auto-Instrumenting Databases (PostgreSQL, Redis)

             • Span name: "SELECT anihpj_jobpost" or "INSERT"
             • Attributes: db.name, db.user, net.peer.name, net.peer.port
             • Duration: How long the query took (for latency analysis)

             • Don't log full Redis values (may contain PII/sensitive data)

      7.6  Best Practices for Production Instrumentation
           • ALWAYS set OTEL_SERVICE_NAME (otherwise spans are "unknown_service")
           • Use BatchSpanProcessor (not SimpleSpanProcessor) in production
           • Set OTEL_TRACES_SAMPLER=traceidratio + OTEL_TRACES_SAMPLER_ARG=0.1 (start with 10%)
           • Don't instrument health-check endpoints (waste of data):
             • In Collector: filter out GET /health, GET /ready spans
           • Keep span attribute cardinality LOW (no user emails, no unbounded IDs)
             • ❌ span.set_attribute("user.email", email) — high cardinality, PII
             • ✅ span.set_attribute("user.plan", plan_type) — low cardinality (~3 values)
           • Set span status explicitly: Don't leave spans as UNSET
           • Always record exceptions: span.record_exception(ex) in except blocks
           • Monitor the monitoring: Track OTel SDK memory usage, span export failures

    Chapter 8: Understanding Distributed Traces
    ───────────────────────────────────────────
      8.1  What is a Distributed Trace?
           - A trace = the complete journey of a request through a distributed system
           - Analogy: A parcel tracking number that shows every stop in the delivery chain
           - Key insight: ONE trace contains multiple spans from different services
           - Example: User clicks "Post Job" in anihpj
             • Span 1 (nginx): Receive HTTP request (10ms)
             • Span 2 (anihpj-api): Authenticate token (25ms)
             • Span 3 (anihpj-api): Validate job data (8ms)
             • Span 4 (postgresql): INSERT INTO jobpost (180ms) ← slow!
             • Span 5 (redis): SET cache:job:42 (5ms)
             • Span 6 (anihpj-api): Return response (3ms)
             → Total trace: 231ms, bottleneck is the DB insert
           - In Jaeger: All the above spans are visualized as a waterfall

      8.2  The Anatomy of a Trace: Trace ID, Span ID, Parent Span ID
           - Trace ID (32 hex chars / 16 bytes): Identifies the entire request journey
             • All spans in the same trace share the same trace ID
             • Example: 4bf92f3577b34da6a3ce929d0e0e4736
           - Span ID (16 hex chars / 8 bytes): Identifies a single operation
             • Unique within the trace
             • Example: 00f067aa0ba902b7
           - Parent Span ID: The span that called this span
             • Root span has NO parent (it's the entry point)
             • Creates the tree structure (every span knows who called it)
           - Trace Flags (8 bits): Sampling decision, debug flag

      8.3  Span Lifecycle: Start → Set Attributes → Add Events → Set Status → End
           - Every span goes through these phases:
             1. Start: tracer.start_span("name") or context manager entry
                • Clock starts ticking immediately
                • Span context created (trace_id, span_id, parent_span_id)
             2. Set Attributes: span.set_attribute("key", value)
                • Metadata about the operation (http.method, db.system, user.id)
                • Attributes are immutable after span ends
                • Max 128 attributes per span (configurable)
             3. Add Events: span.add_event("name", attributes={...}, timestamp=...)
                • Timestamped annotations (like log lines inside a span)
                • Use for notable moments: "cache.miss", "retry.attempt", "timeout"
                • Events have their own timestamps independent of span start/end
             4. Set Status: span.set_status(StatusCode.OK) or StatusCode.ERROR
                • OK: Operation succeeded
                • ERROR: Operation failed (record the exception too!)
                • UNSET: Default — span created but status not explicitly set
             5. End: span.end() or context manager exit
                • Clock stops, duration is calculated
                • Span is passed to SpanProcessor → exporter → backend
           [LIFECYCLE VISUAL: Annotated timeline — start → attrs → events → status → end]

      8.4  Span Kinds: SERVER, CLIENT, INTERNAL, PRODUCER, CONSUMER
           - SERVER: "I received a request" (Django view, HTTP server, gRPC server)
           - CLIENT: "I made a request" (HTTP client, gRPC client, DB client)
           - INTERNAL: "I did some work internally" (computation, validation, serialization)
           - PRODUCER: "I sent a message" (Kafka producer, SQS send, RabbitMQ publish)
           - CONSUMER: "I received a message" (Kafka consumer, SQS receive, RabbitMQ)
           - Why span kind matters:
             • Jaeger/Tempo use different icons/colors for each kind
             • Service maps auto-generate from SERVER↔CLIENT relationships
             • Error budgets: You care about SERVER errors, not CLIENT errors
           [TABLE: Span kind → typical name → example from anihpj]

      8.5  Span Events — Timestamped Annotations Within a Span
           - Events are like "mini-logs" inside a span
           - Each event has: name, timestamp, optional attributes
           - Use cases:
             • "retry.attempted": {"attempt": 3, "max_retries": 5}
             • "cache.miss": {"key": "user:42", "ttl": 300}
             • "circuit_breaker.opened": {"threshold": 5, "reset_timeout": 30}
             • "rate_limit.applied": {"tokens_remaining": 0}
           - Events vs Attributes:
             • Attributes: describe the WHOLE span (http.method, db.system)
             • Events: mark SPECIFIC moments within a span (retry, cache miss)
           [CODE: Adding events throughout a span's lifetime — annotated example]

      8.6  Span Links — Connecting Related Traces
           - Links connect spans from DIFFERENT traces
           - Use cases:
             • "This batch job trace is linked to 50 individual record traces"
             • "This compensation transaction is linked to the original failed transaction"
             • "This async callback is linked to the request that triggered it"
           - Each link contains: trace_id, span_id, optional attributes
           - Links ≠ parent/child: Links are a flat relationship, not hierarchical
           [DIAGRAM: Span links connecting two separate traces]

      8.7  The Trace Lifecycle: In-Process → On-Wire → Collector → Backend
           - Phase 1 — In-Process (SDK):
             • Span is created, populated, ended
             • SpanProcessor receives the ended span
             • BatchSpanProcessor queues it, waits for batch or timeout
           - Phase 2 — On-Wire (OTLP):
             • Batch sent via gRPC or HTTP to Collector (port 4317/4318)
             • Protobuf-encoded for efficiency
           - Phase 3 — Collector:
             • Receivers accept the OTLP data
             • Processors: batch, filter, enrich, transform
             • Exporters: send to one or more backends
           - Phase 4 — Backend (Jaeger/Tempo/Datadog):
             • Store spans in database (Elasticsearch, Cassandra, S3)
             • Index by: trace_id, service name, operation name, tags, duration
             • Make available for query/visualization

      9.1  Tracing HTTP Requests (Incoming and Outgoing)
           - Incoming (SERVER spans):
             • Created by Django auto-instrumentation at the WSGI layer
             • Attributes: http.method, http.url, http.scheme, http.status_code,
               http.user_agent, net.host.name, net.host.port
             • Span name: "GET /api/jobs/" or "POST /api/jobs/"
           - Outgoing (CLIENT spans):
             • Created when anihpj calls external services (auth, notification, payment)
             • Auto-injected traceparent header → context propagates
             • Attributes: http.method, http.url, http.status_code, net.peer.name
             • If the downstream service is also instrumented → spans link up automatically
           [CODE: Incoming and outgoing spans in anihpj views]

      9.2  Tracing Database Queries (PostgreSQL via Django ORM)
           - Every ORM call creates a CLIENT span with db.system=postgresql
           - Span name: The SQL operation type ("SELECT", "INSERT", "UPDATE", "DELETE")
           - Span duration: Exactly the database query time (critical for performance)
           - Attributes captured:
             • db.system: "postgresql"
             • db.name: "anihpj"
             • db.statement: "SELECT * FROM anihpj_jobpost WHERE id = $1"
             • db.operation: "SELECT"
             • net.peer.name: "postgresql.anihpj.svc"
           - N+1 query detection: Multiple DB spans with same operation = N+1 problem!
             • Traces make N+1 painfully visible — each query is a span in the waterfall
           [JAEGER SCREENSHOT: Trace with N+1 query pattern — 50+ identical DB spans]

      9.3  Tracing Cache Operations (Redis GET/SET)
           - Redis operations create CLIENT spans with db.system=redis
           - Span name: "GET", "SET", "HGET", "DEL" (the Redis command)
           - Attributes: db.statement (key pattern), db.redis.database_index
           - Cache hit vs miss: Not auto-captured as span attribute — add manually:
             • For GET: if result is None → span.set_attribute("cache.hit", False)

    Chapter 10: Trace Analysis and Debugging
    ────────────────────────────────────────
      10.1  Reading a Trace — Understanding the Waterfall View
           - Waterfall = horizontal bars showing span duration, offset, and nesting
           - Left-to-right: Time axis (root span starts at 0ms)
           - Top-to-bottom: Call hierarchy (root → children → grandchildren)
           - Color coding: Grey=OK, Red=ERROR, Yellow=slow (configurable threshold)
           - Key information in the waterfall:
             • Span depth: How many layers of nesting? (deep = many service calls)
             • Span width: How long? (wide = slow operation)
             • Gaps between spans: Waiting time between calls
             • Parallel spans: Spans at same indentation that overlap = concurrent calls
           [ANNOTATED WATERFALL: Labels pointing to depth, width, gaps, parallel spans]

      10.2  Identifying Bottlenecks from Trace Data (Slow DB Queries, N+1)
           - Pattern 1 — One very wide span: An operation is just slow
             • Example: DB INSERT spanning 180ms while others are 5-15ms
             • Action: Investigate that specific query (missing index? table lock?)
           - Pattern 2 — Many identical nested spans: N+1 query problem
             • Example: 50 "SELECT" spans inside a loop, each 15ms = 750ms total
             • Action: Use select_related() or prefetch_related() to batch queries
           - Pattern 3 — Deep nesting: Too many service hops
             • Example: Span depth of 12 means 12 service-to-service calls
             • Action: Merge services, use caching, or batch API calls
           - Pattern 4 — Gaps between spans: Waiting time (not compute)
             • Example: 200ms gap between "send_email" start and "SMTP" span
             • Action: Check external service latency, connection pool exhaustion
           [VISUAL: 4 bottleneck patterns with annotated waterfall screenshots]

      10.3  Error Root Cause Analysis with Traces
           - When a user reports "Job creation failed":
             1. Search traces by: service=anihpj-api, operation=POST /api/jobs/, status=ERROR
             2. Open the trace → error span is highlighted RED
             3. Expand the error span → see exception.type, exception.message
             4. Read the stacktrace: Which line of code threw?
             5. Look at parent spans: What led to this operation?
             6. Look at sibling spans: Did a dependent call fail first?
           - Example: Trace shows "INSERT INTO jobpost" span has ERROR status
             • Exception: "IntegrityError: duplicate key value violates unique constraint"
             • Parent span: "validate_job_data" — did it check for duplicates?
             • Root cause: Race condition — two requests with same title

      11.1  What is Jaeger? (Uber → CNCF Graduated)
           - Created by Uber Technologies in 2015 to trace 1,000+ microservices
           - Donated to CNCF in 2017, graduated (top maturity level) in 2019
           - Purpose: Distributed tracing — store, search, and visualize traces
           - Jaeger DOES NOT do metrics or logs — traces only
           - Jaeger is a BACKEND (consumer), OTel is the PRODUCER
           - Key features:
             • Trace search and visualization (waterfall view)
             • Service dependency graphs (auto-generated from traces)
             • Performance monitoring (latency percentiles per service/operation)
             • Adaptive sampling (remote sampling configuration)
           [CARD: Jaeger quick facts — creator, year, CNCF status, language (Go)]

      11.2  Jaeger Architecture: Agent → Collector → Query → Storage
           - Jaeger Agent: Listens for spans on UDP (compact thrift protocol)
             • Deployed as a DaemonSet (one per node)
             • Buffers spans, forwards to Collector
             • With OTel: Agent is often REPLACED by OTel Collector
           - Jaeger Collector: Receives spans, validates, indexes, stores
             • Can receive directly from apps (bypassing Agent)
           - Jaeger Query: API + UI for searching and viewing traces
           - Storage backends:
             • Elasticsearch (production, 7.x/8.x)
             • Cassandra (production, high write throughput)
             • Badger (embedded, for all-in-one/testing)
             • Memory (testing only)
             • Kafka (as buffer between Collector and storage)

    Chapter 12: Understanding OpenTelemetry Metrics
    ───────────────────────────────────────────────
      12.1  What are OTel Metrics?
           - Metrics = numeric measurements collected over time intervals
           - Different from traces: metrics are aggregated, traces are individual requests
           - OTel metrics are Prometheus-compatible by design
           - The Metrics Data Model (simplified):
             • Instrument: The metric definition (counter, histogram, etc.)
             • Measurement: A single data point (counter value = 42)
             • Metric Stream: Aggregated measurements (sum, count, buckets)
             • Metric Point: One timestamped value in a stream
           - Key difference from traces: Metrics are aggregated at collection time
           - Example: "How many POST /api/jobs/ requests in the last 5 minutes?"
           [DIAGRAM: From instrument to backend — the metric pipeline]

      12.2  The Metrics Data Model: Instruments → Meter → MetricReader → Exporter
           - MeterProvider: Creates Meters (like TracerProvider creates Tracers)
           - Meter: Creates Instruments (counters, histograms, etc.)
           - Instrument: Captures measurements (counter.add(1), histogram.record(0.15))
           - MetricReader: Collects measurements from instruments
             • PeriodicExportingMetricReader: Collects on a timer (default: 60s)
             • PullMetricReader: Waits for Prometheus to scrape
           - MetricExporter: Sends collected metrics to a backend
             • OTLP Metric Exporter (push)
             • Prometheus Exporter (pull — exposes /metrics endpoint)
           - Aggregation: How measurements are combined
             • Counter → Sum (total)
             • Histogram → Explicit Buckets (count per bucket + sum + count)
             • LastValue → Gauge (most recent value)
           [PIPELINE: Instrument → Meter → MetricReader → Aggregation → Exporter]

      12.3  Metric Instruments Deep Dive
            a) Counter — Only goes up
               • Monotonic (value never decreases)
               • Use: request_count, error_count, jobs_created_total
               • API: counter.add(1) or counter.add(amount, attributes={...})
               • Prometheus: counter → _total suffix convention
               • Example: Counter for anihpj jobs created:
                 job_counter = meter.create_counter("jobs.created.total", "Total jobs created")
                 job_counter.add(1, {"status": "published", "plan": "premium"})

            b) UpDownCounter — Goes up AND down
               • Non-monotonic (can increase or decrease)
               • Use: active_connections, queue_depth, in_flight_requests
               • API: updown.add(1) or updown.add(-1)
               • Prometheus: gauge
               • Example: Active WebSocket connections:
                 ws_counter = meter.create_up_down_counter("ws.connections.active")
                 ws_counter.add(1)  # connection opened
                 ws_counter.add(-1)  # connection closed

            c) Histogram — Distribution of values
               • Records individual values, groups them into buckets
               • Use: request_duration_seconds, payload_size_bytes, query_rows_returned
               • API: histogram.record(value, attributes={...})
               • Buckets are EXPLICIT (you define the boundaries):
                 [0, 0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5, 10]
               • Prometheus: histogram (with _bucket, _sum, _count)
               • From buckets you can calculate: p50, p95, p99 (approximate)
               • Example: anihpj request latency:
                 latency = meter.create_histogram("http.request.duration",
                     unit="s", description="Request duration in seconds")
                 latency.record(0.235, {"method": "POST", "route": "/api/jobs/"})

            d) ObservableGauge — Point-in-time value (callback-based)
               • OTel calls YOUR function to get the current value
               • Use: CPU temperature, memory usage, thread pool size, cache size
               • API: meter.create_observable_gauge("name", callback)
               • The callback runs on MetricReader's collection interval
               • Example: Current cache size:
                 def get_cache_size(options):
                     yield Observation(len(cache._cache), {})

            e) ObservableUpDownCounter — Async UpDownCounter
               • Like UpDownCounter but callback-based
               • Use: Queue depth where you can't increment/decrement individually
           [TABLE: Instrument → Synchronous/Async → Monotonic → Prometheus type → Use case]

      12.4  Synchronous vs Asynchronous Instruments
           - Synchronous (you call it):
             • Counter, UpDownCounter, Histogram
             • You invoke .add() or .record() in your code
             • Measurement happens at the moment of the call
             • Good for: Events triggered by your code (request received, job created)
           - Asynchronous (OTel calls you):
             • ObservableGauge, ObservableUpDownCounter, ObservableCounter
             • OTel calls your callback function on a timer
             • Measurement happens at collection time
             • Good for: Values that exist independently (CPU %, memory used, queue size)

           - Example without attributes: jobs_created_total = 1000
           - Example with attributes:
             • jobs_created_total{status="published"} = 800
             • jobs_created_total{status="draft"} = 150

      13.1  RED Metrics: Rate, Errors, Duration (The Golden Signals)
           - RED method: The minimum viable metrics for ANY service
           - Rate: Requests per second (counter: http_requests_total)
             • "How much traffic is this service handling?"
             • Split by: method (GET/POST), route (/api/jobs/), status (2xx/4xx/5xx)
           - Errors: Failed requests per second (counter: http_errors_total)
             • "How many requests are failing?"
             • What counts as error: 5xx responses, timeouts, exceptions
           - Duration: Request latency distribution (histogram: http_request_duration_seconds)
             • "How fast/slow are requests?"
             • Key percentiles: p50 (typical), p95 (worst normal), p99 (near worst)
           - PromQL examples:
             • Rate: rate(http_requests_total[5m])
             • Error ratio: rate(http_errors_total[5m]) / rate(http_requests_total[5m])
             • p95 latency: histogram_quantile(0.95, rate(http_request_duration_seconds_bucket[5m]))
           [TABLE: RED → Instrument → Attributes → PromQL → Dashboard widget]

      13.2  USE Metrics: Utilization, Saturation, Errors (Resource View)
           - USE method: For infrastructure/resources (not services)
           - Utilization: % of resource used
             • CPU utilization %, memory usage %, disk space %, network bandwidth %
             • ObservableGauge: node_cpu_utilization, node_memory_utilization
           - Saturation: Amount of work queued/waiting
             • CPU run queue length, memory swap usage, disk I/O queue depth
             • ObservableUpDownCounter: node_cpu_run_queue, postgresql_connections_waiting
           - Errors: Resource-level errors
             • Disk read errors, network packet drops, OOM kills
             • Counter: node_network_drops_total
           - RED for services, USE for infrastructure — complementary methods

      13.3  Business Metrics: Job Posts Created, Applications Submitted
           - Technical metrics (RED/USE) tell you IF the system works
           - Business metrics tell you WHAT users are doing
           - Essential business metrics for anihpj/jobpost:
             • jobs.created.total: Counter, split by plan (free/premium/enterprise)
             • jobs.viewed.total: Counter, split by job category, source
             • applications.submitted.total: Counter, split by job_id, applicant_plan
             • users.registered.total: Counter, split by signup source
             • revenue.estimated: ObservableGauge (premium jobs × price)
           - These metrics go to business dashboards (Grafana) AND OTel backends
           - Connects engineering work to business outcomes:

      13.5  Histogram Bucket Configuration — Getting Your Distribution Right
           - Bad buckets = misleading percentiles
           - Example: HTTP latency with buckets [0.1, 0.5, 1, 5]
             • If your real latency is 100ms-300ms, all values fall in first bucket
             • You can only say "p99 is between 0 and 100ms" — useless!
           - Good bucket strategy:
             1. Know your SLO: "p99 must be < 500ms"
             2. Put buckets around the SLO: [0.01, 0.05, 0.1, 0.25, 0.5, 0.75, 1, 2.5, 5]
             3. Your SLO (500ms) has buckets on both sides → precise p99 calculation
             4. Include buckets for the "long tail" (1s, 2.5s, 5s, 10s) to catch outliers
           - Rule of thumb: 10-15 buckets, exponentially spaced
           - Configuring in OTel Python:
             from opentelemetry.sdk.metrics.view import ExplicitBucketHistogramAggregation
             # Apply to a specific instrument via View (see 13.6)
           [VISUAL: Histogram with poor buckets vs good buckets — annotated]

      13.6  Cardinality Management — Avoiding High-Cardinality Labels
           - Cardinality = number of unique label value combinations
           - Prometheus recommendation: < 10 unique values per label, < 100 combinations
           - High cardinality kills:
             • Memory: Each unique time series consumes ~1-3 KB in Prometheus
             • 1,000,000 time series × 2KB = 2GB just for that metric
             • Query speed: Scanning millions of series for a single query
           - What NOT to use as labels:
             ❌ user_id, email, session_id, request_id, ip_address, trace_id
             ✅ http_method (GET/POST/PUT/DELETE = 4 values)
             ✅ http_status_code (2xx/3xx/4xx/5xx = ~4 values)
             ✅ user_plan (free/premium/enterprise = 3 values)
             ✅ endpoint (/jobs/, /users/, /auth/ = bounded)
           - OTel SDK has View-based filtering to drop high-cardinality attributes

      14.1  Prometheus as a Metrics Backend (Pull Model)
           - Prometheus uses a PULL model: It scrapes targets, they don't push
           - OTel default is PUSH: SDK pushes to Collector, Collector pushes to backend
           - Bridge the gap: OTel Collector exposes a /metrics endpoint for Prometheus
           - Or: OTel SDK can expose /metrics directly (Prometheus exporter)
           - Prometheus data model:
             • Metric name: http_requests_total
             • Labels: {method="POST", route="/api/jobs/", status="201"}
             • Timestamp + value: @1717718400 42
           - Prometheus TSDB (Time Series Database): Optimized for metric storage
             • 2-hour blocks, compressed, append-only
           [DIAGRAM: Pull (Prometheus scrapes) vs Push (OTel pushes)]

      14.2  Configuring OTel Collector to Export to Prometheus
           - Option A: Prometheus scrapes the OTel Collector:

                 protocols:

                     endpoint: 0.0.0.0:4317
             exporters:

      14.3  The Prometheus Exporter vs OTLP Metric Export
           - Prometheus Exporter (Pull):
             • Pros: No configuration on Prometheus side for OTLP
             • Pros: Works with existing Prometheus setups
             • Cons: Pull model friction (firewalls, ephemeral instances)
             • Cons: Two protocols in your pipeline (OTLP → Prometheus exposition format)
           - OTLP Metric Export (Push):
             • Pros: Consistent protocol (OTLP everywhere)
             • Pros: Push works better for serverless/ephemeral workloads
             • Cons: Requires Prometheus to support OTLP ingestion (newer feature)
           - Recommendation: Use OTLP for internal telemetry pipeline, Prometheus
             exporter only at the final hop if Prometheus doesn't support OTLP natively

      15.1  What are OTel Logs?
           - Logs: Immutable, timestamped records of discrete events
           - OTel Logs signal: The newest signal (stable in 2024)
           - NOT a replacement for Python logging / log4j / zap
           - Purpose: Connect existing logging to OTel's context propagation
           - Benefits of OTel logs:
             • Automatic trace_id + span_id injection into log records
             • Send logs through the same OTLP pipeline as traces and metrics
             • One protocol (OTLP) for all three signals
             • Correlated telemetry: Click a log line → see the trace → see the metrics
           [CORRELATION DIAGRAM: Trace in Jaeger ↔ Log in Loki ↔ Metric in Grafana]

      15.2  The Logs Bridge API — Bridging Existing Logging to OTel
           - Key principle: DO NOT replace your logger. BRIDGE it.
           - Python: Connect `logging` module to OTel via LoggingHandler
             import logging
             from opentelemetry._logs import set_logger_provider
             from opentelemetry.sdk._logs import LoggerProvider
             from opentelemetry.sdk._logs.export import BatchLogRecordProcessor
             from opentelemetry.exporter.otlp.proto.grpc._log_exporter import OTLPLogExporter

             logger_provider = LoggerProvider(resource=resource)
             set_logger_provider(logger_provider)
             exporter = OTLPLogExporter(endpoint="http://collector:4317", insecure=True)
             logger_provider.add_log_record_processor(BatchLogRecordProcessor(exporter))

             # Bridge Python logging to OTel
             from opentelemetry.instrumentation.logging import LoggingInstrumentor
             LoggingInstrumentor().instrument(set_logging_format=True)

             # Now any logging.getLogger() call is bridged to OTel
             logger = logging.getLogger(__name__)
             logger.info("User created job", extra={"user_id": 42, "job_id": 99})
             # Automatically gets trace_id + span_id injected!
           - Java: log4j/logback bridge
           - JavaScript: winston/pino bridge
           [CODE: Complete logging bridge setup for Python, Java, JS — single snippet each]

      15.3  Log Data Model: Timestamp, Severity, Body, Attributes, Trace Context
           - LogRecord fields:
             • Timestamp: When the event occurred (nanosecond precision)
             • ObservedTimestamp: When the log was collected (may differ from timestamp)
             • SeverityNumber: Numeric severity (1=TRACE → 24=FATAL)
             • SeverityText: Human-readable severity ("INFO", "ERROR", "WARN")
             • Body: The log message (string or structured AnyValue)
             • Attributes: Key-value metadata (same as span attributes)
             • TraceId + SpanId: The trace context (auto-injected!)
             • Resource: The entity producing the log (service.name, etc.)
           - OTel severity mapping:
             | OTel          | Python logging | Meaning                        |
             |---------------|-----------------|--------------------------------|
             | TRACE (1)     | DEBUG           | Very detailed, diagnostic only |
             | DEBUG (5)     | DEBUG           | Debugging information          |
             | INFO (9)      | INFO            | General operational messages   |
             | WARN (13)     | WARNING         | Warning, not an error          |
             | ERROR (17)    | ERROR           | A failure occurred             |
             | FATAL (21)    | CRITICAL        | Application cannot continue    |
           [LOG RECORD ANATOMY: Annotated JSON showing all fields]

      15.4  Structured Logging vs Unstructured Logging
           - Unstructured (bad): "User 42 created job 99 titled Software Engineer"
             • Parsing required: regex, unreliable, breaks when message format changes
             • Cannot query: "Show me all logs where user_id=42"
           - Structured (good):
             {"timestamp":"...","severity":"INFO","body":"Job created",
              "attributes":{"user_id":42,"job_id":99,"job_title":"Software Engineer",
              "plan":"premium"}}
             • Machine-parseable: JSON
             • Queryable: In Loki/Elasticsearch → {user_id=42}
             • Aggregatable: Count logs by plan type
           - Anihpj rule: ALL logs MUST be structured JSON in production
           [BEFORE/AFTER: Unstructured log line → JSON equivalent]

      15.5  Log Correlation — Connecting Logs to Traces (Trace ID Injection)
           - The killer feature: Every log gets trace_id + span_id automatically
           - Before OTel: grep for "User 42" in 10 log files → hope to find the error
           - After OTel:
             1. See error span in Jaeger → note trace_id: 4bf92f35...
             2. Query Loki: {trace_id="4bf92f35..."} → see ALL logs for that request
             3. Click log line → "db connection timeout at PostgreSQL"
             4. Switch to Grafana → see metrics for the same time period
             5. Root cause found in 30 seconds instead of 30 minutes
           - How trace_id injection works:
             • At log emission time, OTel checks the current span context
             • If a span is active, its trace_id + span_id are added to the LogRecord
             • This happens automatically via LoggingInstrumentor
           [CORRELATION WORKFLOW: Trace (Jaeger) → trace_id copy → Logs (Loki) → find]

    Chapter 16: The OpenTelemetry Collector
    ───────────────────────────────────────
      16.1  What is the OTel Collector? (Vendor-Agnostic Telemetry Pipeline)
           - Standalone Go binary (no dependencies, ~30MB)
           - Sits between your applications and observability backends
           - Three core functions:
             • RECEIVE: Accept telemetry from many sources (OTLP, Jaeger, Prometheus)
             • PROCESS: Transform, filter, batch, enrich the telemetry
             • EXPORT: Send to one or more backends (Jaeger, Prometheus, Datadog, etc.)
           - Why use the Collector:
             • Centralized configuration — don't configure exporters in every app
             • Batching and retry — reduce network overhead
             • Enrichment — add cluster/region/tenant attributes without touching app code
             • Routing — traces → Jaeger, metrics → Prometheus, logs → Loki
             • Filtering — drop health-check spans to reduce cost
             • Protocol conversion — receive OTLP, export to Jaeger native format
           - otelcol vs otelcol-contrib:
             • otelcol: Core receivers, processors, exporters
             • otelcol-contrib: Community-contributed components (more options)
           [ARCHITECTURE: Collector as the central routing layer between apps and backends]

      16.2  Collector Deployment Modes: Agent (Sidecar) vs Gateway (Centralized)
           - Agent (Sidecar/Node Agent):
             • Deployed per-node (DaemonSet in K8s)
             • Each app sends to local Agent, Agent forwards to Gateway/Backend
             • Pros: Local batching, reduced network, no SPOF
             • Cons: More collector instances to manage
           - Gateway (Centralized):
             • One (or few) collector(s) per cluster
             • All apps send directly to Gateway
             • Pros: Centralized config, fewer instances
             • Cons: Network dependency, potential SPOF (mitigate with multiple replicas)
           - Recommended architecture: Agent (sidecar) → Gateway → Backend
             • Agent: Lightweight batching and attribute enrichment
             • Gateway: Advanced processing, multi-backend routing
           [DEPLOYMENT DIAGRAM: Agent → Gateway → Backends — K8s cluster layout]

      16.3  Receivers: OTLP, Jaeger, Prometheus, Zipkin, Kafka, Filelog
           - OTLP Receiver: The primary receiver (gRPC port 4317, HTTP port 4318)
           - Jaeger Receiver: Accepts Jaeger thrift protocol (legacy)
           - Prometheus Receiver: Scrapes Prometheus targets (Collector as scraper)
           - Zipkin Receiver: Accepts Zipkin spans (legacy)
           - Kafka Receiver: Consumes telemetry from Kafka topics
           - Filelog Receiver: Tails log files (container logs, app logs)
           - Host Metrics Receiver: Collects CPU, memory, disk from the host OS
           - Kubeletstats Receiver: Collects pod/container metrics from Kubelet
           [TABLE: Each receiver → protocol → default port → use case]

      16.4  Processors: Batch, Memory Limiter, Attribute, Filter, Transform
           a) Batch Processor: Groups spans/metrics/logs into batches for efficient export
              • Config: timeout (max wait), send_batch_size (max batch), send_batch_max_size
              • Default: 200ms timeout, 8192 batch size
              • CRITICAL: Always use this processor in production
           b) Memory Limiter: Prevents OOM by limiting memory usage
              • check_interval, limit_mib, spike_limit_mib
              • Soft limit: Start rejecting data → Hard limit: Force GC
           c) Attributes Processor: Add/update/delete attributes on telemetry
              • Add cluster/region attributes: {k8s.cluster.name: "prod-us-east"}
              • Hash sensitive data: SHA256(email) instead of raw email
              • Delete high-cardinality attributes: drop user.id
           d) Filter Processor: Drop telemetry based on conditions
              • Drop health-check spans: GET /health, GET /ready
              • Drop specific noisy endpoints: GET /metrics
           e) Transform Processor: OTTL (OpenTelemetry Transformation Language)
              • Advanced data manipulation with a query language
              • Example: Set span name from http.route if available
           [CODE: Each processor configuration in YAML — production examples]

      16.5  Exporters: OTLP, Jaeger, Prometheus, Logging, Kafka, File
           - OTLP Exporter: Send to another Collector or OTLP-native backend (gRPC/HTTP)
           - Jaeger Exporter: Send spans in Jaeger thrift format (gRPC port 14250)
           - Prometheus Exporter: Expose /metrics endpoint for Prometheus to scrape
           - Prometheus Remote Write: Push metrics directly to Prometheus-compatible backend
           - Logging Exporter: Print to stdout (debugging/development)
           - Kafka Exporter: Publish telemetry to Kafka topics
           - File Exporter: Write telemetry to files (JSON or protobuf)
           - Load Balancing Exporter: Route to multiple backends with consistent hashing
           [TABLE: Exporter → signal support → protocol → use case]

      16.6  Connectors: Span Metrics, Service Graph
           - Connectors bridge between pipeline types (e.g., traces → metrics)
           - Span Metrics Connector: Derives RED metrics from trace spans
             • Counts requests, errors, duration from spans → creates metrics
             • No need to instrument metrics separately for basic RED signals
             • Metric names: calls_total, latency_bucket, errors_total per service
           - Service Graph Connector: Builds a service dependency map from spans
             • Emits metrics: client → server call counts per time window
             • Grafana Node Graph visualizes this

    Chapter 17: OpenTelemetry Exporters
    ───────────────────────────────────
      17.1  What are Exporters? — The Telemetry Exit Point
           - Exporters send telemetry OUT of the OTel pipeline to backends
           - Can exist in TWO places:
             a) SDK Exporter: Directly in your app (SimpleSpanProcessor → OTLPSpanExporter)
             b) Collector Exporter: In the Collector pipeline (production)
           - SDK exporters are simple: one signal, one destination
           - Collector exporters are powerful: routing, load-balancing, multi-destination
           - All exporters support: TLS/mTLS, authentication headers, retry, timeout
           [DIAGRAM: SDK exporters vs Collector exporters]

      17.2  OTLP Exporter (gRPC and HTTP/Protobuf)
           - The STANDARD exporter — use this whenever possible
           - gRPC (port 4317):
             • Binary protobuf, streaming, high performance
             • Default for service-to-service communication
           - HTTP/Protobuf (port 4318):
             • Binary protobuf over HTTP, no streaming required
             • Browser-friendly, works with restrictive firewalls
           - Configuration (SDK):
             from opentelemetry.exporter.otlp.proto.grpc.trace_exporter import OTLPSpanExporter
             exporter = OTLPSpanExporter(
                 endpoint="http://collector:4317",
                 insecure=True,
                 headers={"api-key": "xxx"},  # optional auth
                 timeout=10  # seconds
             )
           - Configuration (Collector):
             exporters:
               otlp:
                 endpoint: backend:4317
                 tls:
                   cert_file: /certs/client.crt
                   key_file: /certs/client.key
           [CODE: Both SDK and Collector OTLP configuration]

      17.3  Console/Logging Exporter (For Debugging)
           - Prints telemetry to stdout in human-readable or JSON format
           - Development only — NOT for production (noise + performance)
           - Two variants:
             • ConsoleSpanExporter: Prints spans to stdout (OTel SDK)
             • logging exporter: Prints telemetry to Collector's stdout
           - Useful for: "Am I generating spans at all?", "What attributes are on this span?"
           [TERMINAL: Console exporter output for a single span — annotated]

      17.4  Jaeger Exporter (Traces)
           - Two options:
             a) OTLP to Jaeger (recommended): Jaeger accepts OTLP natively on port 4317
                • Just use the OTLP exporter, point to Jaeger's OTLP endpoint
             b) Native Jaeger exporter: Uses Jaeger's thrift protocol
                • Legacy approach; OTLP is preferred
           - Collector config for OTLP → Jaeger:
             exporters:
               otlp/jaeger:
                 endpoint: jaeger-collector:4317
                 tls:
                   insecure: true
           [CONFIG: Both OTLP and native Jaeger approaches]

      17.5  Prometheus Exporter (Metrics — Pull)
           - Exposes an HTTP /metrics endpoint (Prometheus exposition format)

             scrape_configs:

           - Push metrics via OTLP over HTTP (alternative to Prometheus pull)
           - Use when:
             • Your backend supports OTLP native ingestion (Grafana Cloud, Datadog)
             • You have ephemeral workloads that can't be scraped (serverless, batch)
             • You want consistent protocol across all signals

      17.7  Zipkin Exporter, Kafka Exporter, File Exporter
           - Zipkin Exporter: For legacy Zipkin installations
           - Kafka Exporter: Publish telemetry to Kafka (decoupled, replayable)

      18.1  Open Source Backends: Jaeger, Grafana (Tempo, Loki, Mimir, Pyroscope)
           - The LGTM Stack (Grafana ecosystem) — fully open source, fully OTLP-native:
             • Loki: Log aggregation. Like "Prometheus, but for logs."
               - Label-based indexing (not full-text like Elasticsearch)
               - LogQL query language: {service="anihpj"} |= "ERROR"
               - S3/GCS object storage = cheap, virtually infinite retention
               - OTLP ingestion: Send logs via OTLP → Loki stores them
             • Grafana: Unified visualization. The "glass pane" for all your data.
               - Single UI for: traces (Tempo), metrics (Mimir/Prometheus), logs (Loki)
               - Correlate: Click a log line → "View trace" → opens Tempo
               - Alerting: Unified rules across all data sources
               - Dashboard as Code: JSON exports, GitOps-friendly
             • Tempo: Distributed tracing backend. "Prometheus, but for traces."
               - Object storage (S3/GCS/Azure Blob) — CHEAP, scales infinitely
               - TraceQL: Trace query language (like PromQL for traces)
               - No indexing of span attributes (unlike Jaeger) — cost-effective at scale
               - OTLP-native: Accepts OTLP directly, no protocol translation
             • Mimir: Long-term metrics storage. Horizontally scalable Prometheus.
               - 1 billion+ active series, multi-tenant
               - S3-backed storage, 100% Prometheus compatible
               - Query across clusters (global view)
           - Plus Pyroscope: Continuous profiling (the emerging 4th signal)
             • Shows CPU/memory flame graphs per service
             • Integrates with Grafana: Click span → "View profile" → flame graph
           - The LGTM stack advantage: Every component speaks OTLP natively
             • One protocol, one Collector, one visualization layer
           - Deployment options:
             a) Grafana Cloud (managed): Free tier (10K metrics, 50GB traces, 50GB logs)
             b) Self-hosted with Helm charts (grafana/helm-charts)
             c) Docker Compose for local development

      18.2  Commercial Platforms: Datadog, Honeycomb, New Relic, Dynatrace, Splunk
           - Datadog:
             • All-in-one platform: infrastructure, APM, logs, RUM, profiling, security
             • OTel integration: Datadog Exporter OR OTLP native ingestion (newer)
             • Auto-correlation: Traces automatically linked to logs and host metrics
             • Pricing: Per-host ($15-40/host/month) or per-GB ingested
             • Best for: Teams wanting "one platform for everything" (not just observability)
             • OTel Collector → Datadog:
               exporters:
                 datadog:
                   api:
                     key: ${DD_API_KEY}
                     site: datadoghq.com
             • Key feature: Watchdog AI — automated anomaly detection
             • Drawback: Expensive at scale; per-host pricing penalizes microservices
           - Honeycomb:
             • Observability-first (NOT APM). Founded by Charity Majors (ex-Facebook).
             • Core differentiator: High-cardinality analytics
               - While Prometheus limits label cardinality to ~10 values...
               - Honeycomb lets you query by user_id, trace_id, session_id — ANY field
             • BubbleUp: Statistical analysis that compares slow traces vs fast traces
               and identifies "what's different?" — without you writing any query
             • SLO-based: Define SLOs, Honeycomb shows you error budget in real-time
             • Pricing: Per-event ingested ($0.10/1M events for free tier)
             • OTLP-native: Honeycomb was one of the EARLIEST OTel adopters (2019)
             • Best for: Teams that want "unknown unknowns" discovery (not pre-built dashboards)
             • Honeycomb query example:
               "Show me P95 latency for POST /api/jobs/ grouped by user.plan"
               → Reveals: Premium users = 235ms, Free users = 89ms (cache difference?)
           - New Relic:
             • Traditional APM (Application Performance Management) — one of the originals
             • Recently added OTLP native ingestion (catching up to OTel standard)
             • Strengths: Service maps, deployment markers, JVM/.NET deep instrumentation
             • Pricing: Per-GB ingested (free tier: 100GB/month)
             • Best for: Java/.NET shops with existing New Relic investment
           - Dynatrace:
             • Enterprise APM with AI-driven root cause (Davis® AI engine)
             • OneAgent: Single agent for auto-instrumentation (no code changes)
               - Covers: Java, .NET, Node.js, Python, Go, PHP, databases, infrastructure
             • OTel integration: OneAgent + OTel Collector for custom instrumentation
             • Strengths: Automatic service discovery, topology mapping, real-user monitoring
             • Pricing: Per-host (full-stack) or per-GB (infrastructure only)
             • Best for: Large enterprises needing "push-button" APM with AI root cause
           - Splunk Observability Cloud:
             • Built on SignalFx (metrics) + Omnition (traces) acquisitions
             • NoSample™: Full-fidelity tracing — stores EVERY span (not sampled)
               - But: Expensive at scale (you pay for every stored span)
               - Compromise: Ingest all, but set shorter retention for full-fidelity
             • Splunk Enterprise integration: Logs in Splunk, traces/metrics in Observability
             • Strengths: Real-time streaming analytics, AI-driven alerting
             • Pricing: Per-host or per-GB (complex — talk to sales)
             • Best for: Splunk-heavy organizations extending to traces and metrics

      18.3  How OTel Enables Backend Switching (No Code Changes!)
           - The OTel promise: Instrument once, export anywhere — FOREVER
           - REAL example: anihpj switching from Jaeger to Grafana Tempo
             • Step 1: Current Collector config → Jaeger
               exporters:
                 otlp:
                   endpoint: jaeger:4317
             • Step 2: Change ONE line
               exporters:
                 otlp:
                   endpoint: tempo:4317  # ← ONLY THIS CHANGES
             • Step 3: Restart Collector (docker restart otel-collector)
             • Result: All traces now in Tempo. Zero code changes in anihpj.
             • anihpj doesn't even know — it just keeps sending OTLP to Collector
           - REAL example: Switching from self-hosted to Grafana Cloud
             • Before: endpoint: local-collector:4317
             • After: endpoint: grafana-cloud.example.com:4317

             exporters:
               otlp/jaeger:
                 endpoint: jaeger:4317     # Keep existing

                 endpoint: tempo:4317      # Evaluate new
             • Both backends receive the SAME data simultaneously

      18.5  Choosing the Right Backend for Your Platform
           - Decision Framework — answer these 6 questions in order:
             1. SCALE: How many spans/metrics/logs per second?
                • < 1K spans/s: Any backend (even SQLite-backed Jaeger)
                • 1K-10K spans/s: Jaeger with Elasticsearch, Tempo with S3
                • 10K-100K spans/s: Tempo/Mimir with S3, or commercial (Datadog, Honeycomb)
                • > 100K spans/s: Tempo/Mimir scaled out, or Honeycomb/Datadog Enterprise
             2. RETENTION: How long must you keep data?
                • < 7 days: Any backend
                • 30-90 days: Object storage backends (Tempo, Loki, Mimir)
                • > 1 year: Commercial with cold storage tiers, or self-hosted S3
             3. TEAM SIZE: Who will operate the observability platform?
                • 1-3 engineers: Use MANAGED (Grafana Cloud free tier, Honeycomb, Datadog)
                • 4-10 engineers: Self-hosted viable with LGTM stack
                • 10+ engineers: Self-host OR managed (cost decision)
             4. BUDGET: Monthly observability spend?
                • < $100: Self-hosted LGTM (just infra costs) OR Grafana Cloud free tier
                • $100-500: Grafana Cloud Pro OR Honeycomb free tier
                • $500-2000: Datadog, Honeycomb Pro, or self-hosted at scale
                • > $2000: Dynatrace, Splunk, or Datadog Enterprise
             5. EXISTING TOOLS: What do you already use?
                • Already use Grafana? → Add Tempo + Loki + Mimir (LGTM)
                • Already use Datadog? → Use Datadog's OTLP ingestion
                • Already use Splunk? → Splunk Observability Cloud
                • Greenfield? → LGTM (free, open source, OTLP-native)
             6. HIGH CARDINALITY NEEDS: Do you need to query by user_id, trace_id?
                • Yes → Honeycomb (built for it) or Tempo (TraceQL)
                • No → Any backend

      18.6  Cost Considerations — Telemetry Data Volume
           - Understanding your telemetry DATA VOLUME (not just spans/second):
             • 1 span ≈ 1-5 KB (depending on attributes)
             • 1 metric series ≈ 10-50 bytes per scrape
             • 1 log line ≈ 200-800 bytes (structured JSON)
           - Estimating anihpj monthly volume:
             • Scenario A — Development (10 req/s, 8 hours/day):
               - Traces (100%): ~2.8M spans/month → ~14 GB stored
               - Metrics: ~200 series → negligible
               - Logs: ~5M lines/month → ~4 GB
             • Scenario B — Production (100 req/s, 24/7):
               - Traces (10% sampling): ~2.6M spans/month → ~10 GB stored
               - Metrics: ~500 series → 15 MB
               - Logs: ~15M lines/month → ~12 GB
             • Scenario C — High Scale (1000 req/s, 24/7):
               - Traces (1% sampling): ~2.6M spans/month → ~10 GB stored
               - BUT: If 100% sampling → 260M spans/month → ~1 TB stored!
               - THIS is why sampling matters at scale
           - Cost reduction strategies (ranked by impact):
             1. 🔴 SAMPLING: 100% → 10% = 90% cost reduction (traces only)
                • Set OTEL_TRACES_SAMPLER=traceidratio + OTEL_TRACES_SAMPLER_ARG=0.1
             2. 🟡 FILTER HEALTH CHECKS: Drop /health, /ready, /metrics spans
                • These can be 15-30% of all traffic!
                • Collector filter processor: drop span.name in ["GET /health", "GET /ready"]
             3. 🟡 SHORTEN RETENTION: 30 days → 7 days (if you don't need history)
                • 4x cost reduction on storage
             4. 🟢 REDUCE ATTRIBUTES: Each span attribute = storage cost
                • Remove: user.email, request.body, full SQL queries (keep parameterized)
                • Keep: user.id (low cardinality), http.method, http.status_code
             5. 🟢 LOG LEVEL FILTERING: Don't send DEBUG logs to production
                • Python: logging.getLogger().setLevel(logging.INFO)
                • Collector: Filter logs where severity < INFO

      19.3  Key Concepts to Memorize
            a) OTel Architecture (API, SDK, Collector, OTLP)
               • API = interfaces (no implementation)
               • SDK = implementation (sampling, batching, exporting)
               • Collector = standalone pipeline (receive, process, export)
               • OTLP = wire protocol (gRPC:4317, HTTP:4318)
               • TracerProvider → Tracer → Span
               • MeterProvider → Meter → Instrument
               • LoggerProvider → Logger → LogRecord
            b) Signal Types (Traces, Metrics, Logs)
               • Traces: Spans with trace_id + span_id + parent_span_id
               • Metrics: Counters, Histograms, Gauges
               • Logs: Timestamped events with severity
            c) Instrumentation Types (Manual vs Auto)
               • Manual: tracer.start_as_current_span("name") — full control
               • Auto: opentelemetry-instrument — zero code, less control
               • Libraries: opentelemetry-instrumentation-django/redis/requests
            d) Context Propagation (W3C Trace-Context)
               • traceparent header: 00-{trace_id}-{span_id}-{flags}
               • Propagation: Extract → Process → Inject
               • Baggage: Key-value context across services
            e) Sampling Strategies
               • Head: Decision at span start (SDK)
               • Tail: Decision after span ends (Collector)
               • Config: OTEL_TRACES_SAMPLER + OTEL_TRACES_SAMPLER_ARG

      19.4  Common Exam Traps and How to Avoid Them
           • Trap 1: "OTel is a backend" → WRONG. OTel is instrumentation + collection.
             Answer: "OTel generates and collects telemetry; Jaeger/Prometheus store it."
           • Trap 2: "OTel replaces Prometheus" → WRONG. OTel COMPLEMENTS Prometheus.
             Answer: "OTel generates metrics; Prometheus scrapes and stores them."
           • Trap 3: "Auto-instrumentation covers everything" → WRONG.
             Answer: "Auto covers frameworks; custom business logic needs manual instrumentation."
           • Trap 4: "OTLP is only gRPC" → WRONG. OTLP supports gRPC (4317) AND HTTP (4318).
           • Trap 5: "Context propagation is automatic" → PARTIALLY TRUE.
             Answer: "It's automatic IF you use auto-instrumentation with HTTP/gRPC. Manual protocols need manual context propagation."
           • Trap 6: Confusing counter vs histogram.
             Answer: Counter for COUNT (requests), Histogram for DISTRIBUTION (latency).
           • Trap 7: "Sampling applies to all signals" → WRONG.
             Answer: Sampling is primarily for TRACES. Metrics are aggregated (not sampled).
           • Trap 8: "Collector is required" → WRONG. Collector is OPTIONAL but RECOMMENDED.

      21.2  Uber's Journey from Jaeger to OpenTelemetry

           - Key Insight: "Even Jaeger's creator is adopting OTel — it IS the standard"
           - Results:
             • Unified traces + metrics + logs under one protocol (OTLP)
             • 30% reduction in instrumentation code (OTel is simpler than Jaeger native)
             • Multi-backend: Traces to Jaeger, metrics to M3, logs to internal platform

           - Current: Stable Traces + Metrics, Stable Logs (2024)

             • Server-side auto-instrumentation improvements (eBPF-based)

             • AI/ML observability: LLM tracing, embedding metrics

             • Automated instrumentation: Zero-config observability
           - Vision: OTel becomes the TCP/IP of observability — every application,
             framework, and cloud service emits OTLP natively
           [TIMELINE: OTel evolution from 2019 (merger) through 2030 (ubiquitous)]

      22.2  Profiling Signal — The 4th Pillar
           - Currently: Traces + Metrics + Logs = 3 pillars
           - Coming: Profiling = the 4th signal (continuous profiling)
           - What is profiling? "Where is my CPU time spent?"
             • Shows: Function call frequency, CPU usage per function, memory allocation
             • Complements traces: Trace shows WHERE time is spent, profile shows WHY
           - OTel Profiling SIG: Standardizing profiling data model
           - Integration: Pyroscope (Grafana) supports OTel profiling
           - Use case: Trace shows "GET /jobs/ is slow" → Profile shows "sort() function
             takes 80% of CPU" → Fix the sort algorithm
           [DIAGRAM: 4 pillars — Traces, Metrics, Logs, Profiles with interconnections]

      22.3  Continuous Profiling Integration (Pyroscope, Parca)
           - Pyroscope: Grafana's continuous profiling platform (open source)
           - Parca: Alternative open-source continuous profiling (Polar Signals)
           - OTel + Pyroscope:
             • OTel SDK collects profile data
             • OTLP (with profiling extension) sends to Collector
             • Collector exports to Pyroscope
             • Grafana visualizes traces AND profiles side by side
           [CODE: OTel profiling instrumentation (experimental API)]

      22.4  Client-Side/RUM (Real User Monitoring) with OTel
           - Currently: OTel is primarily server-side
           - Coming: Browser RUM (Real User Monitoring) with OTel JS SDK
           - What RUM captures:
             • Page load time, Time to Interactive, First Contentful Paint
             • JavaScript errors, AJAX request timing
             • User interactions (clicks, navigations)
           - End-to-end trace: Browser span → Nginx span → Django span → DB span
             • traceparent injected into browser AJAX requests
             • Full visibility from user click to database query
           [DIAGRAM: End-to-end trace — Browser → CDN → API → DB]

      22.5  eBPF-Based Auto-Instrumentation
           - eBPF: Linux kernel technology for safe, efficient observability
           - OTel + eBPF: Auto-instrumentation without code changes OR library injection
           - How it works:
             • eBPF programs attach to kernel functions (syscalls, network stack)
             • Automatically capture HTTP requests, DB queries, gRPC calls
             • NO application code changes, NO language-specific configuration
           - Current state: Experimental (Go auto-instrumentation uses eBPF)
           - Future: Universal auto-instrumentation across ALL languages via eBPF
           [DIAGRAM: eBPF instrumentation — kernel-level observation without code changes]

      22.6  OTel and AI: Automated Anomaly Detection
           - OTel generates massive amounts of telemetry data

             • Anomaly detection: "This latency pattern is unusual"
             • Root cause suggestion: "The DB span is 10x slower than normal"
             • Predictive alerting: "Error rate will breach SLO in 30 minutes"
             • Capacity forecasting: "You'll need 50% more pods by next month"
           - How OTel enables AI:
             • Standardized data format (OTLP) → easy to feed into ML models

      E.1  Sampling Configuration Reference

             • Example: Keep 100% errors + all traces > 5s + 10% of remaining
           [CODE: Both head and tail sampling configurations]

      E.2  Head-Based vs Tail-Based Sampling Decision Tree
           - Use HEAD sampling when:
             • You want to reduce SDK overhead
             • You don't need to guarantee error traces are kept
             • Volume is predictable
           - Use TAIL sampling when:
             • You MUST keep all error traces
             • You need to sample based on trace duration
             • You can tolerate the Collector buffering overhead
           - Use BOTH when:
             • Head sampling reduces volume at source (e.g., 50%)
             • Tail sampling selects interesting traces from the 50%
           [FLOWCHART: "Which sampling strategy?" — decision tree]

      E.3  Performance Benchmarks (OTel SDK Overhead)
           - Typical OTel SDK overhead (Python):
             • No instrumentation: 100% throughput (baseline)
             • Auto-instrumentation only: ~98% throughput (2% overhead)
             • Manual instrumentation (10 spans/req): ~95% throughput (5% overhead)
             • With metrics (5 instruments): ~93% throughput (7% overhead)
             • With logs bridge: ~90% throughput (10% overhead)
           - Batching reduces overhead: BatchSpanProcessor vs SimpleSpanProcessor
             • SimpleSpanProcessor (sync): ~20% overhead at high load
             • BatchSpanProcessor (async): ~2-5% overhead at high load
           - Memory: ~5-20MB for SDK + auto-instrumentation
           [TABLE: Overhead by feature — throughput %, memory MB, CPU %]

      E.4  Resource Limits and Collector Sizing
           - Collector sizing guidelines:
             • Small (< 1K spans/s): 256Mi memory, 0.5 CPU
             • Medium (1K-10K spans/s): 512Mi memory, 1 CPU
             • Large (10K-100K spans/s): 2Gi memory, 2-4 CPU
             • X-Large (> 100K spans/s): 4Gi+ memory, 4-8 CPU
           - Batch processor tuning:
             • Smaller timeout = lower latency, more network calls
             • Larger timeout = higher latency, fewer network calls
             • Recommended: 5-10s timeout, 512-8192 batch size
           - Memory limiter: Set to 80% of container limit
           [TABLE: Sizing by throughput — memory, CPU, replicas, batch config]
