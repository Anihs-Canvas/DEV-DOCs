🎯 EX267 Exam Strategy

Master the 2-Hour Performance-Based Exam

Hands-on CLI + OpenShift Console tasks. Pass: 68% (210/300). Here's your battle-tested strategy.

First 5 Minutes — Setup Ritual

  • ✅ Set up aliases: alias ogp='oc get pods', alias oaf='oc apply -f', export do="--dry-run=client -o yaml"
  • ✅ Verify context: oc whoami, oc project
  • ✅ Check cluster health: oc get nodes, oc get clusteroperators
  • ✅ Set mental checkpoints: 30min → 60min → 90min → 110min → 120min
  • ✅ Write down key numbers: GPU types (A100=80GB, H100=80GB), MIG max=7, NVLink=900GB/s

3-Pass Time Management

1
Pass 1 (0-30 min)

Easy tasks first (project creation, data connections). Flag harder ones.

2
Pass 2 (30-100 min)

Medium tasks (notebooks, pipelines, model serving). Process flagged items.

3
Pass 3 (100-120 min)

Hard tasks (GPU, troubleshooting). Review, verify, never leave blank.

Top 10 Mistakes That Cost Points

  • 1. Not switching project context: Always run oc project <name> first
  • 2. Forgetting to create PVC for notebooks: Data science needs persistent storage — check PVC status
  • 3. Not labeling GPU nodes: oc label node <name> nvidia.com/gpu.present=true
  • 4. Using kubectl when oc is needed: Routes, BuildConfigs, DeploymentConfigs need oc
  • 5. Ignoring SCC for AI workloads: GPU pods need privileged or custom SCC
  • 6. Not verifying model endpoints: Always curl the inference endpoint after deploy
  • 7. Forgetting data connection YAML syntax: Triple-check S3 credentials in secrets
  • 8. Pipeline step timeout too short: AI training can take minutes — set appropriate timeouts
  • 9. Not using oc explain for CRDs: OpenShift AI uses many custom resources
  • 10. Skipping verification: Always run oc get or oc describe after every change

Exam Day Checklist

  • ✅ Quiet room, stable internet, system test completed 24h before
  • ✅ Government-issued ID ready, webcam and microphone working
  • ✅ Bookmarked docs.openshift.com reference pages (pre-loaded in exam browser)
  • ✅ Scratch paper for key numbers and YAML skeletons
  • ✅ Water nearby, no electronics on desk except exam computer
  • ✅ 39 chapters studied + 12 labs completed + 90+ practice questions done!

  apiVersion: serving.kserve.io/v1beta1
  kind: InferenceService
  metadata: { name: ${MODEL_NAME} }
  spec:
    predictor:
      model:
        modelFormat: { name: ${FORMAT} }  # pytorch, tensorflow, onnx, sklearn
        storageUri: ${S3_URI}             # s3://bucket/model-path

🧑‍🏫 Novice's Corner — How OpenShift Components Work Together (Step by Step)

Scenario: You deploy anihpj. Here's exactly what happens behind the scenes:

1. You run oc new-app anihpj:latest → CLI sends request to API Server (the front door — ALL requests go through it).

2. API Server authenticates you (OAuth: "Who are you?") and authorizes (RBAC: "Are you allowed?"). If approved, it writes the desired state to etcd (the cluster's database).

3. The Scheduler watches for unassigned Pods. It scores every worker node: "Which has enough CPU/RAM? Which is least loaded?" It picks the best node and updates etcd.

4. The Kubelet on the chosen node sees the assignment. It tells CRI-O: "Pull image anihpj:latest and run it." CRI-O pulls the image, creates the container with a random UID (security!), and starts gunicorn.

5. The Controller Manager constantly reconciles: "Are 3 replicas running? Is one unhealthy? Create a replacement!" This reconciliation loop is Kubernetes' most powerful concept.

6. Kube-Proxy writes iptables rules so traffic to the Service IP gets load-balanced across all healthy Pods. The Route (HAProxy) handles external TLS termination.

🎯 Key Insight: You never told OpenShift "run this on node 5, open port 8080, set up iptables rule X." You declared "I want 3 copies of anihpj, always healthy." The platform figured out the rest. This is declarative infrastructure — the paradigm shift that makes OpenShift so powerful.

2.1 What is a Container? (The Shipping Analogy)

The best way to understand containers is through the shipping industry analogy:

Physical Shipping Containers → Software Containers
  🌍 PHYSICAL WORLD                              💻 SOFTWARE WORLD
  ─────────────────────────────────              ──────────────────────────────
  📦 Shipping Container                          📦 Software Container
     • Standard size (20ft/40ft)                    • Standard format (OCI image)
     • Fits on any ship, truck, train               • Runs on any container runtime
     • Contents isolated from other containers      • Process isolated from other containers
     • Stackable, portable, predictable             • Stackable, portable, predictable

  🚢 Container Ship                              ☸️ OpenShift Cluster
     • Carries thousands of containers              • Runs thousands of pods
     • Automated loading/unloading (cranes)         • Automated scheduling (kubelet)
     • Port authority manages everything            • Control plane manages everything

Container Image = The blueprint (like a shipping container specification). Container = The running instance (like an actual loaded container on a ship).

🧑‍🏫 Novice's Corner — Containers vs Virtual Machines

This is the most important distinction for newcomers:

Virtual Machine: Each VM has its own full operating system (kernel + user space). A server running 10 VMs runs 10 copies of Linux. Heavy, slow to start (minutes), gigabytes of RAM overhead.

Container: All containers on a host share the SAME Linux kernel. Each container only has the application and its dependencies. A server running 100 containers runs ONE kernel. Light, starts in milliseconds, megabytes of overhead.

This is why OpenShift can run hundreds of pods on a single node — they're containers, not VMs. The isolation comes from Linux kernel features (namespaces and cgroups), not from running separate operating systems.

2.3 Building Containers for OpenShift — The anihpj Dockerfile

Here's a production-ready multi-stage Dockerfile for deploying anihpj on OpenShift:

Dockerfile — anihpj/jobpost Production Build 
# ===== STAGE 1: BUILD =====
FROM registry.access.redhat.com/ubi9/python-311 AS builder
USER 0
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
RUN python manage.py collectstatic --noinput

# ===== STAGE 2: RUNTIME =====
FROM registry.access.redhat.com/ubi9/python-311
USER 1001  # OpenShift runs as random UID — match with numeric user
WORKDIR /app
COPY --from=builder /app /app
COPY --from=builder /usr/local/lib/python3.11/site-packages /usr/local/lib/python3.11/site-packages
EXPOSE 8080
CMD ["gunicorn", "anihpj.wsgi:application", "--bind", "0.0.0.0:8080", "--workers", "4"]
💡 OpenShift Dockerfile Best Practices
  • Use UBI (Universal Base Image) — Red Hat's official images are optimized for OpenShift
  • Don't use root — OpenShift runs containers as random UIDs. Your app must work without root
  • Use numeric USER — USER 1001 works better than USER appuser on OpenShift
  • Multi-stage builds — Keep runtime images small by separating build from runtime
  • EXPOSE the right port — OpenShift Services forward to the port you EXPOSE (typically 8080)

🧑‍🏫 Novice's Corner — Dockerfile Line-by-Line

FROM registry.access.redhat.com/ubi9/python-311 AS builder — Start from Red Hat's official Python image. "AS builder" names this stage so we can copy from it later.

USER 0 — Temporarily switch to root (UID 0) for the build stage. We need root to install packages. This is OK because it's ONLY the build stage — the runtime stage drops root.

COPY requirements.txt . — Copy ONLY the requirements file first. Why? Docker caches layers. If requirements.txt hasn't changed, the pip install layer is cached — builds are 10x faster.

FROM registry.access.redhat.com/ubi9/python-311 — Second FROM starts a NEW, clean stage. The build tools (gcc, headers) from stage 1 are gone — keeping the final image small and secure.

USER 1001 — Switch to a non-root user. OpenShift will override this with a random UID, but setting a non-zero value is good practice and signals intent.

COPY --from=builder — Copy ONLY the needed artifacts from the build stage. The final image doesn't contain compilers, dev headers, or source code — just the running app.

2.7 Container Security Basics — Running as Non-Root

⚠️ Why Root Containers Are Dangerous

A container running as root can: escape the container in certain scenarios, access host filesystems, modify kernel parameters, and install malicious software. OpenShift prevents this by default — every container runs as a random UID from a high range (typically 1000650000+).

💡 Making Your Image OpenShift-Compatible
  • Don't use USER root — use USER 1001 or any non-zero UID
  • Make sure files are world-readable (OpenShift's random UID needs access)
  • Don't write to root-owned directories (use /tmp or a mounted volume)
  • Test with: oc run test --image=your-image --command -- id

3.7b Systematic Debugging Checklist for EX267

When something breaks during the exam, follow this checklist IN ORDER:

🔍 The 5-Minute Debug Protocol
  1. Check context: oc whoami, oc project — are you in the right project?
  2. Check pod status: oc get pods -o wide — Running? Pending? CrashLoopBackOff?
  3. Check events: oc get events --sort-by='.lastTimestamp' | tail -20 — cluster diary
  4. Check logs: oc logs <pod> --tail=50 (add --previous if it crashed)
  5. Describe the pod: oc describe pod <pod> — OOM kills, image errors, SCC denials
  6. Check resources: oc adm top pods, oc describe quota — hitting limits?
  7. Debug interactively: oc debug pod/<pod> — creates a debug copy you can explore

5.2 OpenShift Local (CRC) — Your Practice Environment

5.3 The openshift-install Binary & Bootstrap Process

Production OpenShift clusters are created using the openshift-install binary. The key configuration file is install-config.yaml which defines networking, platform, and cluster details. This single YAML file is everything the installer needs.

install-config.yaml — The Single Configuration File
apiVersion: v1
baseDomain: example.com              # Your DNS domain
metadata:
  name: anihpj-cluster               # Cluster name
platform:
  aws:                               # Cloud provider (aws/azure/gcp/vsphere/none)
    region: us-east-1
pullSecret: '{"auths":{...}}'        # From cloud.redhat.com
sshKey: 'ssh-rsa AAAAB3Nza...'      # SSH key for node access

networking:
  clusterNetwork:
  - cidr: 10.128.0.0/14             # Pod network (CANNOT change later!)
    hostPrefix: 23                   # /23 = 512 pods per node
  serviceNetwork:
  - 172.30.0.0/16                    # Service IP range (CANNOT change!)
  networkType: OVNKubernetes         # Default CNI

compute:
- name: worker
  replicas: 3                        # 3 worker nodes
  platform:
    aws:
      type: m5.xlarge               # 4 vCPU, 16 GB

controlPlane:
  name: master
  replicas: 3                        # 3 control plane nodes
  platform:
    aws:
      type: m5.2xlarge              # 8 vCPU, 32 GB

6.2 Configuring HTPasswd Identity Provider

HTPasswd is the simplest IdP — users and (hashed) passwords stored in a file. Perfect for EX267 practice and small teams. Here's the complete walkthrough for our anihpj data science team:

Adding anihpj Team Users via HTPasswd (Step-by-Step)
# Step 1: Install htpasswd utility (if not present)
yum install -y httpd-tools          # RHEL/Fedora
apt-get install -y apache2-utils    # Ubuntu

# Step 2: Create htpasswd file with 3 anihpj team users
htpasswd -c -B htpasswd anihpj-admin      # -c = create, -B = bcrypt
htpasswd -B htpasswd anihpj-ds            # Data scientist — notebooks & pipelines
htpasswd -B htpasswd anihpj-viewer       # Read-only — view dashboards

# Step 3: Store as a Secret in openshift-config namespace
oc create secret generic htpass-secret \
  --from-file=htpasswd=htpasswd \
  -n openshift-config

# Step 4: Update the OAuth CR to use HTPasswd
oc patch oauth cluster --type=merge -p '
spec:
  identityProviders:
  - name: htpasswd_provider
    mappingMethod: claim
    type: HTPasswd
    htpasswd:
      fileData:
        name: htpass-secret'

# Step 5: Wait for OAuth pods to restart
oc get pods -n openshift-authentication -w

# Step 6: Test login as each user
oc login -u anihpj-admin https://api.crc.testing:6443
oc whoami    # Should show: anihpj-admin

# Step 7: Grant cluster-admin to anihpj-admin
oc adm policy add-cluster-role-to-user cluster-admin anihpj-admin
🔑 Mapping Method Options

mappingMethod: claim — every unique identity gets a unique user (use this). mappingMethod: lookup — maps to existing identities only. mappingMethod: generate — generates a username from the identity (default). For EX267, know that claim is the preferred method.

🧑‍🏫 Novice's Corner — SCC: "Why Does My Pod Keep Failing?"

The #1 reason pods fail on OpenShift when they work fine on vanilla Kubernetes is SCC violations. Here's why:

Vanilla K8s: Pods can run as root by default. Your Dockerfile says USER root — it works.

OpenShift: The restricted SCC is applied to ALL pods by default. It says: "You CANNOT run as root. You CANNOT use host networking. You CANNOT access host filesystem." If your container tries any of these — it's denied at admission time before the pod even starts.

Fix: Either build your image to work as non-root (preferred) OR assign a more permissive SCC like anyuid or privileged to the service account: oc adm policy add-scc-to-user anyuid -z default -n my-project

Edge — you want HTTPS but your app doesn't handle TLS (this is 80% of cases). Passthrough — your app handles its own TLS and you need end-to-end encryption (model serving endpoints). Re-encrypt — you want different certificates for external vs internal traffic (enterprise security policies).

🧠 How to Choose: The AI Storage Decision Framework

"Does it need a POSIX filesystem?" (files, directories, permissions like a normal disk)

  • YES, single user → Block (RWO) — notebook workspace, database
  • YES, multiple users → File (RWX) — shared datasets, distributed training
  • NO, accessed via API → Object (S3) — pipeline artifacts, model files

"Is it the final model artifact?" → Object (S3) — version it like code, serve it via S3 endpoint or OCI container registry.

"Does it need to survive pod restarts?" → Any PVC or S3 — NOT emptyDir (ephemeral), NOT container filesystem (lost on restart).

🗂️ When to Use NooBaa vs PVC

Use NooBaa (S3): Pipeline artifacts, model files, training datasets shared across teams, anything that needs S3 API compatibility. Use PVC: Notebook workspaces (personal), databases, anything that needs a filesystem. NooBaa = object storage (PUT/GET objects), PVC = block/filesystem storage (mount as directory).

8.5 Storage Best Practices for Production AI

✅ 10 Storage Rules for AI Workloads

  1. Data locality: Keep data near compute (same availability zone). Cross-AZ data transfer = latency + $$$
  2. storage = dataset × 3: Plan capacity for raw data + processed data + trained models. A 50Gi dataset needs ~150Gi.
  3. Notebook workspace = PVC (RWO): Each notebook gets its own workspace PVC. Don't share notebook workspaces.
  4. Shared datasets = PVC (RWX) or S3: Use ReadWriteMany (NFS/EFS) or S3 for data accessed by multiple pods.
  5. Pipeline artifacts = S3 (NooBaa): Pipelines pass data between steps via S3. Never use local pod storage.
  6. Model storage = S3 or OCI registry: Trained models are artifacts — version them like code. Store in S3 buckets or OCI container registry.
  7. Cache frequently accessed datasets: Use local SSD storage for hot data. Offload cold data to S3.
  8. Backup PVCs regularly: Use CSI snapshots or Velero for backup. PVCs are NOT backed up by default.
  9. Set Reclaim Policy: Retain: Change from default Delete to Retain for production PVCs — prevents accidental data loss.
  10. Monitor storage usage: Use oc describe pvc and Prometheus alerts. Running out of storage = pod eviction.

9.3 Source-to-Image (S2I) — Build Without a Dockerfile

🧑‍🏫 Novice's Corner — "Why S2I Instead of a Dockerfile?"

You already have a Dockerfile for anihpj — why use S2I? S2I builder images are maintained by Red Hat — they include security patches, best-practice configurations, and are optimized for OpenShift. When a critical Python vulnerability is patched, Red Hat updates the builder image, and you just rebuild — no Dockerfile changes needed.

When to use Dockerfile instead: You have custom system dependencies (like CUDA for GPU, or complex C libraries), or you need very specific build logic that S2I can't express. For most Python/Django apps, S2I is faster and safer.

Customizing S2I: You can add .s2i/bin/assemble (custom build script) and .s2i/bin/run (custom startup script) in your repo. S2I runs these instead of the default — giving you full control while keeping the builder image maintained by Red Hat.

9.6 Health Checks — Liveness, Readiness, and Startup Probes

Kubernetes doesn't know if your app is actually working — it only knows if the process is running. Probes tell Kubernetes when to restart, when to send traffic, and when to wait for initialization.

│                    🏥 KUBERNETES HEALTH PROBES                      │

│                                                                     │

DeploymentConfig rollback: oc rollback dc/anihpj reverts to the last successful deployment. OpenShift keeps a full deployment history — use oc rollout history dc/anihpj to see all versions. Route-level rollback: If doing canary with route weights, just set v2 weight to 0: oc set route-backend anihpj-canary anihpj-v2 --weight=0. ImageStream rollback: Re-tag the old image: oc tag anihpj:old-version anihpj:latest — ImageChange trigger auto-redeploys the old version.

Scheduling Examples for anihpj
# 1. NODE SELECTOR — Simple: Django on SSD nodes
oc patch deploy/anihpj -p '{"spec":{"template":{"spec":{"nodeSelector":{"disktype":"ssd"}}}}}'

# 2. NODE AFFINITY — Django MUST be on SSD, PREFER zone-a
oc patch deploy/anihpj -p '{"spec":{"template":{"spec":{"affinity":{"nodeAffinity":{"requiredDuringSchedulingIgnoredDuringExecution":{"nodeSelectorTerms":[{"matchExpressions":[{"key":"disktype","operator":"In","values":["ssd"]}]}]},"preferredDuringSchedulingIgnoredDuringExecution":[{"weight":1,"preference":{"matchExpressions":[{"key":"topology.kubernetes.io/zone","operator":"In","values":["us-east-1a"]}]}}]}}}}}}'

# 3. TAINT + TOLERATION — GPU training on dedicated GPU nodes
# Admin taints the GPU node:
oc adm taint nodes gpu-node-1 nvidia.com/gpu=true:NoSchedule
# Pod needs toleration to run there:
oc patch deploy/gpu-training -p '{"spec":{"template":{"spec":{"tolerations":[{"key":"nvidia.com/gpu","operator":"Equal","value":"true","effect":"NoSchedule"}]}}}}'
📍 Quick Scheduling Reference

nodeSelector: Simplest — just key=value. Affinity: Complex rules — required vs preferred, In/NotIn/Exists operators. Taints/Tolerations: Node says "stay away unless you have this toleration" — great for dedicated GPU or high-memory nodes. Topology Spread: Balance pods across zones/hosts — critical for HA deployments.

11.1 What is an Operator? (The Simple Explanation)

- name: APP_NAME
  value: anihpj
- name: DB_USER
  value: anihpj
  required: true
- name: DB_PASSWORD
  generate: expression
  from: "[a-zA-Z0-9]{16}"    # Auto-generated random password
- name: DB_NAME
  value: anihpj
- name: REPLICAS
  value: "3"
objects:
# --- PostgreSQL ---
- apiVersion: apps/v1
  kind: Deployment
  metadata:
    name: ${APP_NAME}-db

🧠 When to Use Which?

Templates: OpenShift-native, appears in Console +Add page, parameter-based. Best for: teams fully on OpenShift. Helm: Universal K8s packaging, rich ecosystem, built-in release management. Best for: multi-platform, complex apps. Kustomize: Built into oc/kubectl, overlay-based, no templates. Best for: GitOps workflows (ArgoCD, Flux).

Almost, but with AI superpowers. Yes, a Data Science Project creates a standard OpenShift namespace. 13.2 Project Configuration — Users, Resources, and Limits

Once your project exists, you need to add team members and set resource boundaries. This prevents a single notebook from consuming all available GPU capacity.

8 Project Settings for AI Workloads
# 1. Add data scientists to the project
oc adm policy add-role-to-user edit alice -n anihpj-ml
oc adm policy add-role-to-user edit bob -n anihpj-ml
oc adm policy add-role-to-user view carol -n anihpj-ml

# 2. Create SA for pipelines
oc create sa pipeline-runner -n anihpj-ml
oc adm policy add-role-to-user edit -z pipeline-runner -n anihpj-ml

# 3. Set resource quota (prevents runaway GPU usage!)
oc create quota anihpj-ml-quota -n anihpj-ml \
  --hard=cpu=16,memory=64Gi,requests.nvidia.com/gpu=2,persistentvolumeclaims=10

# 4. Set LimitRange (defaults for pods without explicit resources)
cat <<EOF | oc apply -f -
apiVersion: v1
kind: LimitRange
metadata:
  name: notebook-defaults
  namespace: anihpj-ml
spec:
  limits:
  - default: { cpu: "2", memory: "4Gi" }
    defaultRequest: { cpu: "1", memory: "2Gi" }
    type: Container
EOF

# 5. Allow GPU node access (taint toleration)
oc patch namespace anihpj-ml -p '{"metadata":{"annotations":{"scheduler.alpha.kubernetes.io/defaultTolerations":"[{\"key\":\"nvidia.com/gpu\",\"operator\":\"Exists\",\"effect\":\"NoSchedule\"}]"}}}'

# 6. Grant SCC for GPU workloads
oc adm policy add-scc-to-user privileged -z default -n anihpj-ml

# 7. Set network policy (isolate from other teams)
oc create -f - <<EOF
kind: NetworkPolicy
apiVersion: networking.k8s.io/v1
metadata: { name: deny-from-other-namespaces, namespace: anihpj-ml }
spec:
  podSelector: {}
  ingress:
  - from:
    - podSelector: {}
EOF

# 8. Verify all settings
oc describe quota anihpj-ml-quota -n anihpj-ml
oc get limitrange -n anihpj-ml
oc get networkpolicy -n anihpj-ml

def train_model(data_path: str) -> str:

16.4 Feature Engineering Best Practices for Production AI

✅ Feature Engineering Best Practices

  1. Version your features: Use DVC or Feature Store (Feast) — never lose track of how features were created
  2. Feature pipeline = code: Feature engineering code lives in Git. No manual Excel transformations.
  3. Train/serve consistency: The EXACT same preprocessing code must run in training AND inference. Use scikit-learn Pipelines to encapsulate.
  4. Scale gracefully: Start with pandas, graduate to Dask when data exceeds RAM, Spark when it exceeds node capacity
  5. Monitor feature drift: Features in production WILL drift from training data. Use TrustyAI or custom monitoring to detect.
  6. Use Data Connections, not hardcoded paths: S3 paths and DB credentials come from Data Connections — portable across environments

18.1 What is Model Registry?

The Model Registry stores trained models as versioned OCI (Open Container Initiative) artifacts — the same format as container images. This means your models live in the same registry as your application images, with the same security, RBAC, and replication. Each model version has: a unique version number, stage tags (dev/staging/prod/archived), metadata (framework, metrics, training data hash), and deployment history.

🧑‍🏫 Novice's Corner — "Why Can't I Just Save the Model to S3?"

Without it, you're managing model files manually, which is error-prone and doesn't scale beyond 2-3 models.

Key insight for EX267: The exam expects you to know that models are stored as OCI artifacts in the same OpenShift internal registry that stores container images. A model is just another artifact — versioned, tagged, and deployable.

19.1 End-to-End Pipeline Design

A production training pipeline connects: Data Validation → Feature Engineering → Model Training → Evaluation → Model Registration. Each stage has pass/fail gates — if data validation fails, the pipeline stops; if model accuracy drops below threshold, the model is NOT registered. 19.2 Incremental Training & Updates

Instead of retraining from scratch every time, incremental training: loads the previous model checkpoint, trains only on NEW data (last 24 hours), and updates model weights. This reduces training time from hours to minutes and GPU costs by 80%+. Use with scikit-learn warm_start=True or PyTorch checkpoint loading.

19.3 Multi-Model Training

anihpj needs multiple models: job classifier (categorize jobs), skill extractor (NER to extract skills from text), salary predictor (regression), and recommendation ranker (learning-to-rank). Run these as parallel pipeline branches — all fed from the same data ingestion but trained independently. Use DAG (Directed Acyclic Graph) pipelines in kfp to express parallelism.

19.4 Pipeline Optimization

Cache intermediate results (don't re-compute features if data hasn't changed). Use spot/preemptible instances for training (with checkpointing). Parallelize independent steps. Compress artifacts for faster S3 transfers. Profile each step to find bottlenecks.

21.1 What is Model Serving?

Model serving is the process of making your trained ML model available as an API endpoint for real-time predictions. Instead of running inference manually in a notebook, you deploy the model to a server that handles requests 24/7 — scaling up for traffic spikes and down to zero when idle.

🧑‍🏫 Novice's Corner — "I trained a model. Now what?"

Training a model in a notebook is like baking one cake in your kitchen. Model serving is like opening a bakery — you need to handle multiple customers simultaneously, keep the cakes fresh, and never run out. KServe is your bakery manager: it takes your cake recipe (model), sets up the display case (API endpoint), hires staff as needed (autoscaling), and closes when there are no customers (scale to zero).

Batch vs Real-time: Batch inference = process 10,000 job postings overnight (cheap, slow). Real-time inference = user clicks "Find Jobs" → model responds in <100ms (expensive, fast). OpenShift AI supports both — batch via pipelines, real-time via KServe.

21.3 Inference Endpoint Lifecycle

An inference endpoint goes through: Create (deploy InferenceService CR) → Ready (pod running, health check passing) → Serving (accepting requests via Route) → Scaling (KPA/HPA adjusts replicas based on load) → Idle (scale to zero if no requests for N minutes) → Delete (remove CR, pods terminated). With KServe + Knative, cold starts from zero take ~200-500ms.

21.4 Serving Architecture Map

Single-Model (KServe)

One InferenceService = one model endpoint. Best isolation, dedicated resources. Predictable latency. Recommended for anihpj production models.

Multi-Model (ModelMesh)

Many models share a pool of serving pods. Cost-efficient for models with low/irregular traffic. Models loaded/unloaded on demand.

Model Storage Options

Models can come from: S3 bucket (via NooBaa/MinIO), OCI container registry, PVC, or HuggingFace Hub. KServe auto-downloads from the specified URI.

Chapter 22: Production Model Serving with KServe

KServe is the standard for serving individual models on OpenShift AI. It provides GPU acceleration, autoscaling (scale-to-zero), canary deployments, and explainability — all configured through a single InferenceService YAML. This is the EX267 core serving chapter.

🔴 Advanced⏱️ ~2.5 hours🚀 KServe🎯 EX267 25%

22.1 KServe Fundamentals

KServe (formerly KFServing) is a Kubernetes CRD-based model serving framework. You define an InferenceService YAML specifying the model location, framework, and resources — KServe handles everything else: downloading the model, starting the server, exposing the endpoint, and autoscaling.

22.2 Deploying an Inference Service

Deploy anihpj Job Classifier with KServe
apiVersion: serving.kserve.io/v1beta1
kind: InferenceService
metadata:
  name: anihpj-job-classifier
  namespace: anihpj-ml
  annotations:
    serving.kserve.io/enable-prometheus-scraping: "true"
spec:
  predictor:
    minReplicas: 1
    maxReplicas: 5
    scaleTarget: 10          # Scale based on concurrent requests
    scaleMetric: concurrency
    model:
      modelFormat:
        name: sklearn         # sklearn, pytorch, tensorflow, xgboost...
      storageUri: s3://anihpj-models/job-classifier/v1
      resources:
        requests: { cpu: "1", memory: "2Gi" }
        limits: { cpu: "2", memory: "4Gi", "nvidia.com/gpu": 1 }
    # S3 credentials auto-injected from Data Connection!

# Deploy and check:
oc apply -f inference-service.yaml
oc get inferenceservice -n anihpj-ml
# NAME                    URL                                              READY
# anihpj-job-classifier  https://anihpj-job-classifier-anihpj-ml.apps...  True

# Test the endpoint:
curl -k https://anihpj-job-classifier-anihpj-ml.apps.cluster.example.com/v1/models/anihpj-job-classifier:predict \
  -H "Content-Type: application/json" \
  -d '{"instances": [{"description": "Python developer AWS...", "skills": "python,aws"}]}'

22.3 InferenceService Configuration

Key config: storageUri (s3://, oci://, pvc://, hf://), modelFormat (auto-detects server), minReplicas (0 for scale-to-zero, 1+ for warm), canaryTrafficPercent (for canary deployments).

22.4 Transformer & Explainer

Transformer: Pre/post-processing container that runs alongside the predictor. Example: convert JSON input to model-specific format, or filter PII from requests. Explainer: Optional container providing model explanations (SHAP, LIME) — accessible via a separate endpoint for debugging and compliance.

22.5 GPU-Accelerated Inference

For GPU inference, add nvidia.com/gpu: 1 to resource limits. KServe automatically schedules the pod on GPU nodes. For LLM serving, vLLM and TGI runtimes are GPU-optimized — they use PagedAttention for 20x faster token generation compared to vanilla HuggingFace.

22.6 Monitoring & Debugging

KServe exposes Prometheus metrics: request count, latency percentiles, error rates. Access via: oc get inferenceservice anihpj-job-classifier -o yaml to see status conditions. Check predictor pod logs: oc logs deploy/anihpj-job-classifier-predictor.

Chapter 23: Multi-Model Serving — ModelMesh 🎯🔴 Advanced · 🎯 EX267

Chapter 23: Serving Many Models Efficiently

ModelMesh is designed for organizations running dozens or hundreds of models. Instead of one pod per model, multiple models share a pool of serving pods — dramatically reducing resource costs for models with low or sporadic traffic.

🔴 Advanced⏱️ ~1 hour🕸️ ModelMesh

23.1 What is ModelMesh?

ModelMesh loads multiple models into shared serving pods. Models are paged in/out of memory on demand — inactive models consume zero memory. This allows running 100+ models on the same infrastructure that would only support 5-10 with KServe single-model serving.

23.2 Deploying to ModelMesh

Models are registered via a ServingRuntime CR (defines the server type — Triton, MLServer, OVMS) and a InferenceService CR pointing to the runtime. ModelMesh handles the routing: incoming requests are directed to the appropriate pod that has the requested model loaded.

23.3 Scaling & Performance

ModelMesh scales at the pod level (HPA) — adding more serving pods as total load increases. Individual models can be pinned to specific pods for guaranteed capacity. Cache eviction policies control which models stay in memory under pressure.

Click

Chapter 24: Beyond Basic Serving

For specialized use cases — maximum throughput, custom preprocessing, streaming inference, and edge deployment — OpenShift supports advanced serving patterns beyond KServe and ModelMesh.

🔴 Advanced⏱️ ~1 hour🔬 Advanced

24.1 Triton Inference Server

NVIDIA Triton is the highest-performance inference server — supports multiple frameworks (PyTorch, TF, ONNX, TensorRT), dynamic batching, concurrent model execution, and GPU optimization. Deploy as a ServingRuntime on OpenShift. Best for: maximum throughput, multi-framework shops, GPU-accelerated inference.

24.2 Custom Servers (FastAPI)

When you need custom preprocessing or business logic beyond what KServe provides, deploy a FastAPI/Flask app as a standard OpenShift Deployment. Add a Route, configure HPA, and you have a custom inference server. Trade-off: you manage everything (scaling, monitoring, model loading) yourself.

24.3 Streaming Inference (Kafka)

For real-time streaming predictions (e.g., classify every new job posting instantly), use Kafka + KServe: job postings published to Kafka topic → KServe inference pod consumes stream → predictions written to output topic. Use Strimzi (Kafka Operator) on OpenShift for managed Kafka.

24.4 Edge Inference Patterns

For low-latency inference at the edge: deploy lightweight models (ONNX, TensorRT) using OpenShift at the edge (Single Node OpenShift). Models are pushed from the central registry to edge clusters. Useful for: real-time skill matching on job portals, instant salary predictions.
