🏆 Top 5 KCA Exam Tips
  1. Know the 4 policy types cold — Validate, Mutate, Generate, VerifyImages are the backbone of the exam

Understanding "Why" Matters on the KCA

The KCA tests your understanding of why Kyverno exists, not just how to write policies. Key concepts to internalize:

  • Pull vs Push Model — Kyverno is a Kubernetes-native admission controller. It intercepts requests at the API server level before resources are persisted to etcd.
  • Declarative vs Imperative — Kyverno policies are declarative: you declare WHAT you want enforced, not HOW to enforce it.
  • YAML-Native — This is Kyverno's biggest differentiator. No new language (like Rego for OPA). If you know Kubernetes YAML, you know Kyverno.

1.1 The Problem Kubernetes Policies Solve

Kubernetes is incredibly powerful — but power without guardrails is dangerous. Out of the box, anyone with kubectl access can deploy anything to any namespace. There's no built-in way to say "all containers must have resource limits" or "only images from our private registry are allowed."

Imagine you've built anihpj — a Django app with a jobpost module. Without policies:

😰 Managing anihpj WITHOUT Policies
  • 🔴 Developer deploys anihpj with :latest tag — no way to know what version is running
  • 🔴 Pod scheduled without CPU/memory limits — can consume all node resources
  • 🔴 Database password stored in plaintext ConfigMap — visible to anyone with cluster access
  • 🔴 No way to enforce that every Deployment has a team label for cost tracking
  • 🔴 Compliance audit = manual spreadsheet of "did you set resource limits?"
🎉 Managing anihpj WITH Kyverno Policies
  • ✅ Validate policy blocks :latest tags — only explicit versions allowed
  • ✅ Mutate policy auto-adds default CPU/memory limits if not specified
  • ✅ Validate policy prevents plaintext secrets — forces use of Sealed Secrets/ESO
  • ✅ Validate policy requires team label on every resource
  • ✅ PolicyReports auto-generate compliance evidence for auditors

1.2 Policy-as-Code Defined

📖 What is Policy-as-Code?

Policy-as-Code is the practice of defining rules and governance in machine-readable configuration files (YAML/JSON), version-controlled alongside application code. Instead of manual enforcement ("please set resource limits"), policies are automatically validated at deployment time.

Chapter 1 — Practice Questions

Q1
Which of the following BEST describes why Kubernetes needs a policy engine like Kyverno?
Show Answer
Answer

Kubernetes has no built-in governance beyond basic RBAC. Anyone with kubectl access can deploy any resource without restrictions on image tags, resource limits, or security contexts. A policy engine adds automated guardrails at the admission control level.

Explanation

RBAC controls WHO can do WHAT. Kyverno controls WHAT they can do. RBAC says "Alice can create Deployments." Kyverno says "Deployments must have resource limits and cannot use :latest tags." These are complementary — you need both.

Q2
Kyverno registers as which type(s) of admission webhooks in Kubernetes?
Show Answer
Answer

Both MutatingAdmissionWebhook and ValidatingAdmissionWebhook. Kyverno handles both mutation (modifying resources in-flight) and validation (passing or blocking resources).

Explanation

This is a key KCA exam point. Kyverno is one of the few policy engines that handles BOTH mutation and validation. OPA/Gatekeeper can do both but requires separate configurations. PSA (built-in) is validation-only.

Q3
What is the primary advantage of Kyverno being "YAML-native" compared to OPA/Gatekeeper's Rego language?
Show Answer
Answer

No new language to learn. Kyverno policies are written in the same YAML format as Kubernetes resources. Teams already familiar with K8s can write policies immediately without learning Rego, reducing the learning curve from weeks to minutes.

Explanation

For KCA, remember: Kyverno = YAML, OPA = Rego. This is Kyverno's biggest differentiator and a commonly tested concept. The YAML-native approach means policies are CRDs that can be deployed with kubectl apply, stored in Git, and managed with GitOps tools.

Q4
What was the Kubernetes-native policy mechanism that existed before Kyverno and OPA, and what happened to it?
Show Answer
Answer

PodSecurityPolicy (PSP). PSPs were deprecated in Kubernetes 1.21 and removed in Kubernetes 1.25. They only covered Pod-level security and lacked the flexibility of modern policy engines.

Explanation

The KCA may test your knowledge of PSP's deprecation as context for why Kyverno exists. PSP was limited to Pod security and used a different model (no admission webhooks). Kyverno and OPA replaced PSPs in the ecosystem.

Q5
In the admission control flow, in what order do MutatingAdmissionWebhooks and ValidatingAdmissionWebhooks execute?
Show Answer
Answer

Mutating webhooks run FIRST, then Validating webhooks run SECOND. This ensures that any modifications (added labels, default values) are in place before validation checks occur.

Explanation

This ordering is critical: if a Kyverno mutate policy adds a label team: anihpj, a later validate policy can check that this label exists. If validate ran first, it would fail because the label hasn't been added yet. Processing order: Mutate → Generate → VerifyImages → Validate.

Q6
A developer deploys an anihpj pod with image: anihpj:latest and no resource limits. Which Kyverno policy types could address these issues?
Show Answer
Answer

Validate policy to BLOCK :latest tags. Mutate policy to auto-add default resource limits if not specified.

Explanation

Validate = "Thou shalt not use :latest." Mutate = "If no limits are set, I'll add defaults." Both work together — Mutate adds defaults, Validate blocks what can't be fixed automatically.

Q7
What happens to existing resources in the cluster when a new Kyverno validate policy is created with background: true?
Show Answer
Answer

All existing resources matching the policy are scanned and results are recorded in PolicyReports. If validationFailureAction: Enforce, existing non-compliant resources are NOT deleted — they generate a fail report. Only NEW resources are blocked.

Explanation

This is a common KCA trap. background: true means "scan existing resources and report violations" — it does NOT mean "delete existing non-compliant resources." Kyverno never deletes existing resources without a Cleanup Policy.

Q8
Which Kubernetes API resources does Kyverno register to receive admission review requests?
Show Answer
Answer

ValidatingWebhookConfiguration and MutatingWebhookConfiguration. These tell the API server to send admission review requests to Kyverno's webhook endpoint.

Explanation

Kyverno creates two webhook configurations at install time. You can verify them: kubectl get validatingwebhookconfigurations and kubectl get mutatingwebhookconfigurations. Look for resources with "kyverno" in the name.

Q9
What is the key advantage of storing Kyverno policies as Kubernetes CRDs in Git?
Show Answer
Answer

GitOps for governance. Policies are version-controlled, peer-reviewed via PR, deployed through CI/CD pipelines, and auditable through Git history. Changes to policies follow the same workflow as application changes.

Explanation

Policy-as-Code means policy changes are code changes. You can see WHO changed WHAT policy WHEN. Roll back a bad policy with git revert. This is impossible with manual policy enforcement.

Q10
A team wants to enforce that all anihpj deployments have a required team label BEFORE the resource is created. Which Kyverno policy type and action should they use?
Show Answer
Answer

Validate policy with validationFailureAction: Enforce. The validate rule checks for the presence of the team label in the resource's metadata. If missing, the resource is blocked at admission time.

Explanation

Validate + Enforce = immediate blocking. An alternative is Validate + Audit (warn but allow), useful during policy rollout. A Mutate policy could auto-add the label, but that defeats the purpose of requiring developers to set it themselves.

Q1
Which Kyverno controller is responsible for scanning EXISTING resources in the cluster?
Show Answer
Answer

The Background Controller. It periodically scans existing resources and generates PolicyReports for any violations found.

Explanation

The Background Controller is the "security camera" — it watches everything already in the building, not just new arrivals. The Admission Controller only handles NEW resources.

Q2
If a developer runs kubectl apply -f anihpj-deploy.yaml, in what order do Kyverno's policy types process the request?
Show Answer
Answer

Mutate → Generate → VerifyImages → Validate. This is the mandatory processing order and a frequently tested KCA concept.

Explanation

Mutate runs first so defaults are in place. Generate creates additional resources if needed. VerifyImages checks signatures. Validate runs last — it sees the final state of the resource after all mutations.

Q3
Which Kyverno controller generates PolicyReport and ClusterPolicyReport CRDs?
Show Answer
Answer

The Reports Controller. It aggregates results from both the Admission Controller (real-time) and Background Controller (periodic scans) into PolicyReport CRDs.

Explanation

The Reports Controller does not evaluate policies itself — it collects results from the other controllers and formats them into PolicyReport resources. Think of it as the "secretary" that writes the report after the "inspectors" (Admission + Background) do their checks.

Q4
What happens if the Kyverno Admission Controller pod crashes while failurePolicy: Fail is set on the webhook?
Show Answer
Answer

ALL new resource requests are BLOCKED. The API server cannot reach Kyverno, and failurePolicy: Fail tells it to reject requests when the webhook is unavailable.

Explanation

This is the "security vs availability" tradeoff. failurePolicy: Fail = cluster is safe but frozen (no new resources). failurePolicy: Ignore = cluster is operational but unprotected (resources bypass policy checks). Production typically uses Fail.

Q5
How do you verify that Kyverno's webhook configurations are properly registered after installation?
Show Answer
Answer

Run kubectl get validatingwebhookconfigurations and kubectl get mutatingwebhookconfigurations. Look for resources with "kyverno" in the name. Each should show the Kyverno service as the webhook endpoint.

Explanation

Kyverno creates at least two webhook configs at install time. If they're missing, the API server won't send admission requests to Kyverno, and policies won't be enforced — even if Kyverno pods are running!

Q6
What is the scope difference between a ClusterPolicy and a namespaced Policy?
Show Answer
Answer

ClusterPolicy applies to ALL namespaces in the cluster. Policy applies only to the namespace where it is created. ClusterPolicy cannot be restricted to specific namespaces without using match/exclude blocks.

Explanation

Use ClusterPolicy for org-wide rules ("every Deployment must have labels"). Use namespaced Policy for team-specific rules ("anihpj-dev can use NodePort services"). A ClusterPolicy without proper exclude blocks will apply to kube-system and kyverno namespaces!

Q7
Which two webhook configurations does Kyverno create, and which policy types does each handle?
Show Answer
Answer

ValidatingWebhookConfiguration handles Validate and VerifyImages policies. MutatingWebhookConfiguration handles Mutate and Generate policies.

Explanation

Mutate and Generate modify resources → they go through the MutatingWebhook. Validate and VerifyImages only check → they go through the ValidatingWebhook. Both webhooks are served by the same Kyverno service on different paths.

Q8
What CRD does Kyverno use to trigger background re-evaluation of existing resources when a policy changes?
Show Answer
Answer

UpdateRequest. When a policy is modified, Kyverno creates UpdateRequest CRDs for all matching resources, triggering the Background Controller to re-evaluate them against the updated policy.

Explanation

Without UpdateRequests, changing a policy would only affect NEW resources. UpdateRequests ensure existing resources are also re-checked. You can see them: kubectl get updaterequests -A.

Q9
What is the purpose of the Cleanup Controller, and what CRD does it use?
Show Answer
Answer

The Cleanup Controller deletes resources matching CleanupPolicy or ClusterCleanupPolicy CRDs. It runs on a cron schedule and removes resources based on TTL or conditions (e.g., "delete Pods older than 24 hours").

Explanation

Cleanup is Kyverno's garbage collection feature. Unlike Validate/Mutate which run at admission time, Cleanup runs periodically (cron-based). Common use: delete ephemeral test resources in dev namespaces after 24h.

Q10
A team deploys Kyverno and creates a ClusterPolicy with background: false. What effect does this have?
Show Answer
Answer

The policy only applies to NEW resources created after the policy exists. Existing resources are NOT scanned, and no PolicyReports are generated for them. The policy still applies at admission time for new resources.

Explanation

background: false = skip existing resources. This is useful when you know existing resources are compliant and want to reduce load. background: true (default) scans everything and generates reports. Use false for performance-sensitive clusters with many existing resources.

Chapter 3 — Practice Questions

Q1
What is the difference between match.any and match.all in a Kyverno policy?
Show Answer
Answer

match.any uses OR logic — the policy matches if ANY condition is true. match.all uses AND logic — ALL conditions must be true for the policy to match.

Explanation

This is tested on the KCA. Example: match.any with kinds=[Deployment, Pod] means "match Deployments OR Pods." match.all with kinds=[Deployment] and namespaces=[anihpj-prod] means "match Deployments AND they must be in anihpj-prod."

Q2
If a resource matches BOTH the match block and the exclude block of a policy, what happens?
Show Answer
Answer

The resource is EXCLUDED. The exclude block takes precedence over the match block. Kyverno checks exclude FIRST.

Explanation

This is a classic KCA trap. The evaluation order is: 1) Check exclude → if match, skip. 2) Check match → if match, apply. 3) Check preconditions → if fail, skip. Exclude always wins.

Q3
What does validationFailureAction: Audit mean, and how does it differ from Enforce?
Show Answer
Answer

Audit = the resource is allowed through but a violation is logged in the PolicyReport. Enforce = the resource is BLOCKED and an error is returned to the user. Audit is safe for testing new policies; Enforce is for production enforcement.

Explanation

Always start with Audit when deploying a new policy. This lets you see what would be blocked without actually blocking anything. Once you're confident there are no false positives, switch to Enforce. The KCA asks about this distinction frequently.

Q4
In a Kyverno policy pattern, what does the wildcard "?*" mean?
Show Answer
Answer

"?*" means the field must exist and must be non-empty. It matches any string value that has at least one character, but does not match null, missing, or empty values.

Explanation

Wildcards are KCA-tested: "*" = any value including empty/null. "?*" = any non-empty value (field must be present AND have content). Use "?*" when you require a field like team: "?*" to ensure developers actually set the label.

Q5
What is the difference between (anchored), -(non-anchored), and +(conditional) anchors in Kyverno patterns?
Show Answer
Answer

(anchored) — field MUST match. -(non-anchored) — if field exists, it SHOULD match, but its absence is OK. +(conditional) — if the resource has labels at all, THEN this field MUST match.

Explanation

Example: (app): "anihpj" = app MUST be anihpj. -(team): "?*" = if team exists, it must be non-empty, but resources without team label pass. +(cost-center): "?*" = if the resource has ANY labels, cost-center must exist.

Q6
Which context source would you use to look up allowed container registries from a ConfigMap?
Show Answer
Answer

ConfigMap context. You reference a ConfigMap in the policy's context block, and Kyverno reads its data at policy evaluation time. Example: look up allowed-registries from a ConfigMap named registry-policy.

Explanation

ConfigMap context is the most common dynamic data source. It lets you change policy behavior (e.g., allowed registries) by updating a ConfigMap instead of modifying the policy YAML. The policy references the ConfigMap data via variables.

Q7
When would you use preconditions instead of match or exclude?
Show Answer
Answer

Use preconditions when you need to skip a rule based on the VALUE of a resource field (dynamic condition), not just the resource type/namespace (static matching). Preconditions use JMESPath expressions.

Explanation

match/exclude = "is this a Deployment in anihpj-prod?" (static). Preconditions = "does this resource have env=prod AND replicas > 1?" (dynamic). Use preconditions for value-based conditional execution within a rule.

Q8
What standard Kyverno policy annotations should you include for documentation and discoverability?
Show Answer
Answer

policies.kyverno.io/title, policies.kyverno.io/category, policies.kyverno.io/severity, policies.kyverno.io/subject, and policies.kyverno.io/description. These are standard metadata annotations for policy documentation.

Explanation

These annotations don't affect policy behavior but are critical for policy management at scale. They enable filtering (kubectl get clusterpolicy -l policies.kyverno.io/category=Best Practices) and auto-documentation with kyverno docs.

Q9
Can a single Kyverno ClusterPolicy contain multiple rules? If so, how are they evaluated?
Show Answer
Answer

Yes. A ClusterPolicy can contain multiple rules in spec.rules[]. Each rule is evaluated independently — one rule can pass while another fails. If ANY rule in Enforce mode fails, the resource is blocked.

Explanation

This is efficient — one ClusterPolicy can enforce multiple related checks (e.g., require labels AND require resource limits AND require non-root). You don't need separate policies for each check. Rules are evaluated independently in parallel.

Q10
How would you write a Kyverno policy pattern to require that an anihpj Deployment's container image comes from ghcr.io/anihs-canvas/?
Show Answer
Answer

Use a validate pattern with: spec.template.spec.containers[].image: "ghcr.io/anihs-canvas/*". The "*" wildcard matches any image name within the ghcr.io/anihs-canvas registry path.

Explanation

For more complex registry validation, use a deny rule with JMESPath conditions: check if the image does NOT start with the allowed registry. Example: deny.conditions.all[0].key: "{{ images.containers.*.registry || '' }}" operator: NotEquals value: "ghcr.io".

4.1 What are Validate Policies?

A validate policy is a pass/fail check. The resource either meets the requirements (✅ allowed) or doesn't (❌ blocked). Validate policies never modify the resource — they only inspect.

4.3 Deny Rules — Conditional Blocking

When pattern matching isn't flexible enough, use deny rules with JMESPath conditions. Deny rules are perfect for "block if X but not Y" logic.

# BLOCK anihpj deployments using :latest image tag
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: block-latest-tag
spec:
  validationFailureAction: Enforce
  rules:
  - name: deny-latest-image-tag
    match:
      any:
      - resources:
          kinds: [Pod]
          namespaces: ["anihpj-*"]
    validate:
      message: "Using :latest tag is prohibited for anihpj images"
      deny:
        conditions:
          any:
          - key: "{{ images.containers.*.tag || '' }}"
            operator: Equals
            value: "latest"
          # Also block images with NO tag (implicit :latest)
          - key: "{{ images.containers.*.tag }}"
            operator: Equals
            value: ""

The KCA exam WILL test anchors. Here's the definitive reference: (name) = field MUST exist (required anchor) — if missing, the pattern doesn't match, and if using deny rules, the resource is blocked. -(name) = wildcard deny anchor — prevents extra fields beyond what's specified. +(name) = conditional anchor (mutate only) — adds the field ONLY if it doesn't already exist. Remember: ()="must have", -()="nothing else", +()="add if missing".

8.1 JMESPath in Kyverno — Query Language for Policies

📖 What is JMESPath?

JMESPath is a JSON query language. In Kyverno, it's used to extract and evaluate data from resources at policy evaluation time. Think of it as "jq for Kyverno policies."

# JMESPath EXPRESSIONS CHEAT SHEET
# Access the resource being evaluated:
{{ request.object.metadata.name }}               # Resource name
{{ request.object.metadata.labels.app }}          # Label value
{{ request.object.spec.replicas }}                # Deployment replicas

# Array operations:
{{ images.containers[0].name }}                   # First container name
{{ images.containers[*].image }}                  # All container images
length({{ images.containers }})                   # Number of containers

# String operations:
contains('{{ request.object.metadata.name }}', 'anihpj')  # Check if name contains
{{ request.object.metadata.labels.env || 'dev' }}          # Default value if null

# Math / comparison:
{{ request.object.spec.replicas > '1' }}          # Boolean comparison
{{ multiply('100', '2') }}                        # Math operations
Always wrap JMESPath expressions in {{ }}. Use || for default values: {{ variable || 'default' }}. The [*] wildcard iterates over all array elements.

📖 Mutate vs Generate — Key Distinction

apiVersion: kyverno.io/v1
kind: CleanupPolicy
metadata:
  name: cleanup-anihpj-test-pods
  namespace: anihpj-dev
spec:

  match:

    - resources:
        kinds: [Pod]
        namespaces: ["anihpj-dev"]

⚠️ KCA GOTCHA: Cleanup is NOT Real-Time

Unlike Mutate/Validate which run at admission time, Cleanup is scheduled. A resource that violates the cleanup conditions will continue to exist until the next cron trigger. Cleanup also does NOT block resource creation — it only deletes existing resources on schedule.

🎓 KCA Exam Tip: mutateDigest

When mutateDigest: true, Kyverno MUTATES the image reference from a tag (like :v1) to a digest (@sha256:abc123...). This prevents TOCTOU (time-of-check-time-of-use) attacks — the image can't change between verification and runtime. The KCA loves to ask about this.

# VERIFYIMAGES POLICY: Require signed anihpj images
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: verify-anihpj-images
spec:
  validationFailureAction: Enforce
  background: true
  rules:
  - name: check-anihpj-image-signature
    match:
      any:
      - resources:
          kinds: [Pod]
          namespaces: ["anihpj-*"]
    verifyImages:
    - imageReferences:
      - "ghcr.io/anihpj/*"
      - "docker.io/anihpj/*"
      attestors:
      - count: 1
        entries:
        - keys:
            publicKeys: |-
              -----BEGIN PUBLIC KEY-----
              MFkwEwYHKoZIzj0CAQYIKoZIzj0DAQcDQgAE...
              -----END PUBLIC KEY-----
      mutateDigest: true

🔴 Why Image Verification Matters — A Supply Chain Attack Scenario

Imagine this real-world attack chain that VerifyImages prevents:

  1. Step 1: Attacker compromises your CI/CD pipeline or gains push access to your registry
  2. Step 2: Attacker pushes a backdoored anihpj:v1.0 image — same tag, different code
  3. Step 3: Kubernetes scheduler picks the new image for the next rolling update
  4. Step 4: 💥 Attacker now has code running inside your production cluster

WITH Kyverno VerifyImages + Cosign: Step 2 fails — the attacker can't sign with your key. Step 3 never happens because Kyverno blocks the unsigned/tampered image. mutateDigest: true ensures Step 3 is impossible even if the tag is overwritten — because the digest is immutable.

apiVersion: kyverno.io/v2

Namespace-scoped. A PolicyException only applies within its namespace. To exempt across namespaces, create a PolicyException in each namespace.

Q3
Can a single PolicyException exempt multiple policies?
Show Answer
Answer

Yes. The spec.exceptions array can list multiple policyName entries. One exception can exempt a resource from several policies at once.

Q4
What happens if you omit ruleNames in the exceptions block?
Show Answer
Answer

The exception applies to ALL rules in the specified policy. If you specify ruleNames, only those specific rules are exempted — other rules in the same policy still apply.

Q5
Why are exceptions preferred over modifying the policy for one-off bypasses?
Show Answer
Answer

Exceptions create an audit trail — you can see WHO was exempted, WHEN, and WHY. Modifying the policy hides the exception from auditors and weakens security for everyone.

Q6
Can PolicyExceptions use conditions (e.g., only exempt if a label is set)?
Show Answer
Answer

Yes. Use spec.conditions to add conditional logic. Example: only exempt if label emergency: "true" is set. Resource without the label still gets blocked.

Q7
An anihpj admin pod needs to bypass the "must have limits" policy. What do you create?
Show Answer
Answer

A PolicyException in the anihpj namespace, matching the admin pod by name, referencing require-resource-limits as the policyName. This exempts only that specific pod.

Q8
Do PolicyExceptions work with ClusterPolicies and namespaced Policies?
Show Answer
Answer

Yes. PolicyExceptions work with both ClusterPolicies and namespaced Policies. The exception just needs to be in the same namespace as the resource being exempted.

Q9
Can a PolicyException exempt resources from background scans?
Show Answer
Answer

Yes. Exceptions apply to both admission and background scans. If a resource is exempted, it won't show violations in PolicyReports either.

Q10
What's the difference between a PolicyException and a policy's exclude block?
Show Answer
Answer

PolicyException is a separate CRD (auditable, temporary, specific). exclude block is built into the policy (permanent, applies to all matching resources). Exceptions = surgical bypass. Exclude = permanent carve-out.

By default, the policy evaluation fails and may block the resource (depending on failurePolicy). Configure failurePolicy: Ignore if you want the policy to pass when the API is unavailable.

💡 Context Anti-Patterns to Avoid

❌ Hardcoding values in every policy instead of using ConfigMap context → When the value changes, you update 50 policies instead of 1 ConfigMap.
❌ Making API calls without caching awareness → API call responses are cached for ~10 minutes. If your external API updates every minute, Kyverno may use stale data.
❌ Using imageRegistry context for every Pod → Registry calls add latency. Only use imageRegistry context when you actually need image metadata.
❌ Not setting failurePolicy for API calls → If your external API is down, do you want policies to fail (block resources) or pass (allow unchecked)? Choose explicitly.

kind: ClusterPolicy
metadata:
  name: require-anihpj-team-label
  annotations:
    policies.kyverno.io/title: "Require team label on all anihpj resources"
    policies.kyverno.io/description: "All Deployments, Pods, and Services in anihpj-* namespaces must have a 'team' label for cost tracking and ownership."
    policies.kyverno.io/category: "Compliance"
    policies.kyverno.io/severity: "high"
    policies.kyverno.io/subject: "Deployment, Pod, Service"
    policies.kyverno.io/owner: "platform-team@anihpj.com"
    policies.kyverno.io/version: "1.0.0"
    policies.kyverno.io/minversion: "1.11.0"
spec:
  validationFailureAction: Enforce

  rules:
  - name: check-team-label
    match:
      any:
      - resources:
          kinds: [Deployment, Pod, Service]
          namespaces: ["anihpj-*"]

      message: "Resource {{ request.object.metadata.name }} must have label 'team' for cost tracking. Contact platform-team@anihpj.com for help."

        metadata:

            team: "?*"    # Must exist and be non-empty

📖 Clear Error Messages Matter

The message field in your validate rules is what developers see when their deployment is blocked. A good message tells them: (1) WHAT went wrong, (2) WHY this rule exists, and (3) HOW to fix it. Bad example: "validation failed". Good example: "Resource anihpj-deploy must have label 'team' for cost tracking. Add 'team: anihpj' to metadata.labels. Contact platform-team@anihpj.com for exceptions."

📦 Policy Versioning Strategy

Policies are code — they need versioning. Use policies.kyverno.io/version annotation with semantic versioning (MAJOR.MINOR.PATCH):

🔴 MAJOR bump

Breaking change — policy now blocks previously-allowed resources. Requires team communication and migration plan.

🟡 MINOR bump

New rule added, new resource kind matched, new condition. Backward-compatible but more restrictive.

🟢 PATCH bump

Message text update, annotation change, bug fix in match pattern. No change to enforcement behavior.

⚠️ Policy Rollback Best Practices

If a policy causes issues: (1) Don't delete it — use kubectl edit clusterpolicy <name> to change validationFailureAction to Audit first. This stops blocking but keeps reporting. (2) Only delete after you've fixed the root cause. (3) If using GitOps/ArgoCD, git revert the policy change — ArgoCD syncs back the working version. (4) Always have a rollback runbook documented.

20.3a Policy Not Matching

Check match and exclude blocks. Verify kinds (case-sensitive!), namespaces, and selector labels match the resource. Use kyverno apply policy.yaml --resource resource.yaml to test locally. Remember: match.any = OR logic, match.all = AND logic.

20.3b Webhook Not Called

Verify: kubectl get validatingwebhookconfigurations and kubectl get mutatingwebhookconfigurations. Look for kyverno entries. Check kubectl get pods -n kyverno — all pods should be Running. Check webhook namespaceSelector — if set, Kyverno only watches namespaces matching those labels.

20.3c Debugging with Logs

kubectl logs -n kyverno deployment/kyverno-admission-controller -f — streams admission logs. Look for "admission review" entries. kubectl logs -n kyverno deployment/kyverno-background-controller — shows background scan activity. Use --tail=100 for recent logs and --since=5m for time-filtered logs.

20.3d failurePolicy: Fail vs Ignore

The most critical production setting. When Kyverno's webhook is unreachable: Fail = BLOCK all requests (cluster is safe but frozen). Ignore = ALLOW all requests (cluster stays operational but unprotected). Use Fail in production, Ignore in development.

20.4 Backup & Disaster Recovery

Kyverno policies are just CRDs stored in etcd. If Kyverno goes down:

  • failurePolicy: Fail → All new resources are BLOCKED. Existing resources continue running. The cluster is SAFE but FROZEN.
  • failurePolicy: Ignore → All new resources are ALLOWED without policy checks. The cluster works but is UNPROTECTED.

⚠️ Backup Strategy

Policies are CRDs — back them up like any Kubernetes resource: kubectl get clusterpolicies -o yaml > backup-policies.yaml. Even better — they should be in Git (GitOps). If you lose all policies, restore from Git with ArgoCD or kubectl apply -f backup-policies.yaml. No special backup tool needed.

🔴 Production Incident Scenario: Kyverno Blocks Everything

Situation: 9 AM Monday. A platform engineer updates a policy to add a new required label. The policy's match block accidentally uses kinds: ["*"] instead of kinds: [Deployment]. Suddenly, ALL new resources across ALL types are blocked. Developers can't deploy anything.

Response (learn this order!):

  1. Immediate: kubectl edit clusterpolicy <name> → change validationFailureAction to Audit (stops blocking, keeps reporting)
  2. Fix: Correct the match block (kinds: ["*"] → kinds: [Deployment])
  3. Verify: kyverno apply policy.yaml --resource test-deploy.yaml — confirm it only matches Deployments
  4. Restore: Change back to Enforce and apply
  5. Prevent: Add preconditions or more specific match blocks. Always Audit-before-Enforce for new policies.

⚡ How Many Policies is Too Many?

A general guideline: under 100 ClusterPolicies with under 500 total rules across all policies. Beyond that, evaluate if you can consolidate. Each rule adds ~1-2ms to admission latency. Always monitor kyverno_admission_review_latency as you add policies.

📊 Policy Drift Detection

Policy drift happens when resources that were compliant at creation time become non-compliant later (e.g., someone edits a ConfigMap that a generate policy created). Kyverno detects drift through: (1) Background scans — periodic re-evaluation of existing resources, (2) generate.synchronize: true — Kyverno reverts unauthorized changes to generated resources, (3) PolicyReports — show which currently-running resources violate policies. Monitor kyverno_policy_results_total{result="fail"} for unexpected spikes — that's drift happening.

apiVersion: kyverno.io/v1

metadata:
  name: require-labels           # ← Unique name
  annotations:                   # ← Documentation
    policies.kyverno.io/title: "Require team label"

  validationFailureAction: Enforce  # ← Audit | Enforce
  background: true                  # ← Scan existing resources?
  rules:
  - name: check-team-label       # ← Rule name
    match:                       # ← What to evaluate
      any:                       # ← any=OR, all=AND
      - resources:
          kinds: [Deployment]    # ← K8s resource kinds
    exclude:                     # ← What to skip (optional)
      any:
      - resources:
          namespaces: [kube-system]
    validate:                    # ← Validate | Mutate | Generate | VerifyImages
      message: "..."             # ← User-facing error message
      pattern:                   # ← Expected resource structure
        metadata:
          labels:
            team: "?*"
F.6 AdmissionReport

Namespaced. Detailed per-resource admission review results. Shows which rule matched and the result (pass/fail) for each resource evaluated at admission time. More granular than PolicyReport.

F.6 BackgroundScanReport

Namespaced. Results from background scans of existing resources. Separate from AdmissionReport to distinguish "failed at admission" from "existing resource non-compliant."

🎓 KCA Exam: CRD Scope Matters

The KCA frequently asks: "Which CRD is cluster-scoped vs namespace-scoped?" Cluster-scoped: ClusterPolicy, ClusterPolicyReport, ClusterCleanupPolicy. Namespace-scoped: Policy, PolicyReport, CleanupPolicy, PolicyException, UpdateRequest, AdmissionReport, BackgroundScanReport. Exception: there is no "ClusterPolicyException" — PolicyException is ALWAYS namespaced.

⚡ KCA: This comparison is frequently tested

The KCA expects you to know: (1) Kyverno = YAML, OPA = Rego. (2) Kyverno has Generate and Cleanup; OPA doesn't. (3) Both have Validate and Mutate capabilities. (4) Kyverno is CNCF Incubating; OPA is CNCF Graduated. When the exam asks "why Kyverno?", the answer is almost always about YAML-native simplicity AND the unique Generate/VerifyImages/Cleanup features.

🆕 CEL vs JMESPath — Modern Kyverno Policy Expressions

Kyverno now supports Common Expressions Language (CEL) as an alternative to JMESPath for writing policy conditions. CEL is a Google-developed expression language used in Kubernetes ValidatingAdmissionPolicies. Key differences: JMESPath is great for JSON traversal and filtering (mature, widely documented). CEL is more expressive for complex logic (macros, type safety, compilation). For the KCA exam, focus on JMESPath — it's the primary expression language tested. CEL support is newer and less likely to appear on the current exam version. Know that both exist and that Kyverno is moving toward CEL support.
