🚨 Critical Do's & Don'ts During The Exam
  • ✅ DO: Use kubectl create ... --dry-run=client -o yaml to generate YAML in seconds — never type security manifests from scratch.
  • ✅ DO: Run kubectl config use-context <given-context> as the FIRST command for every task. Wrong context = 0 points.
  • ✅ DO: Verify RBAC with kubectl auth can-i --list --as=<user> before and after changes. Know the verbs: get, list, watch, create, update, patch, delete.
  • ✅ DO: Use kubeadm certs check-expiration and openssl x509 -noout -dates to inspect certificate validity.
  • ❌ DON'T: Spend more than 7 minutes on any single task. Flag it, move on, return with fresh eyes.
  • ❌ DON'T: Forget security context fields: runAsNonRoot: true, readOnlyRootFilesystem: true, capabilities.drop: [ALL], allowPrivilegeEscalation: false.
  • ❌ DON'T: Leave any task blank. Even partial work (creating the NetworkPolicy YAML, writing partial RBAC rules) may earn partial credit.
  • ❌ DON'T: Forget --certificate-authority, --client-certificate, and --client-key flags when running etcdctl — etcd always requires TLS in CKS exam clusters.

1.1 Network Security & NetworkPolicy FundamentalsQ1-Q12

Cluster Setup Q1 of 200
What is a Kubernetes NetworkPolicy and what problem does it solve?
A) A NetworkPolicy is a firewall rule that blocks all external traffic to the cluster from the internet
B) A NetworkPolicy is a Kubernetes resource that acts as a "pod-level firewall" — it controls which pods can communicate with each other (ingress/egress) using selectors, effectively implementing micro-segmentation
C) A NetworkPolicy is a DNS policy that controls how pod hostnames resolve within the cluster
D) A NetworkPolicy is a load-balancing rule that distributes traffic across pod replicas
✅ Correct Answer: B

A NetworkPolicy is Kubernetes' built-in micro-segmentation firewall. It controls traffic flow at Layer 3/4 (IP address + port) between pods using label selectors, namespace selectors, and IP blocks — no VLANs or physical firewalls needed.

📝 Detailed Explanation
NetworkPolicy — The Pod-Level Firewall
  WITHOUT NetworkPolicy (default: ALL traffic allowed)
  ┌──────────────────────────────────────────────────────────────┐
  │  anihpj-web ──► anihpj-api ──► anihpj-db ──► anihpj-redis   │
  │  All pods can talk to ALL other pods — flat network           │
  │  ⚠️ Compromised web pod can directly access the database!     │
  └──────────────────────────────────────────────────────────────┘

  WITH NetworkPolicy (default-deny + explicit allows)
  ┌──────────────────────────────────────────────────────────────┐
  │  anihpj-web ──► anihpj-api:8000  ✅  (explicitly allowed)    │
  │  anihpj-web ──► anihpj-db:5432   ❌  (BLOCKED by policy!)    │
  │  anihpj-api  ──► anihpj-db:5432  ✅  (explicitly allowed)    │
  │  anihpj-api  ──► anihpj-redis:6379 ✅                        │
  │                                                               │
  │  Key insight: Web tier CANNOT talk directly to DB.           │
  │  It MUST go through the API. This limits blast radius.       │
  └──────────────────────────────────────────────────────────────┘

For anihpj/jobpost, this is critical: if the Django web frontend is compromised, the attacker cannot directly access PostgreSQL because NetworkPolicy only allows api → db:5432, not web → db:5432. This is the principle of least privilege applied to network traffic.

CKS Exam Note: NetworkPolicies are a CORE CKS topic. You MUST know: (1) They are ADDITIVE — multiple policies combine. (2) A pod is ISOLATED when ANY policy selects it for that direction. (3) They require a CNI that supports them — Calico, Cilium, and Weave Net work; Flannel alone does NOT.

💾 Category 1: Storage Troubleshooting (10 Issues)ST1-ST10

🟢 Storage Issues — PVC, PV, StorageClass, and Mount Failures

Storage is often the FIRST thing to break because it involves multiple components: PVC → StorageClass → Provisioner → PV → Mount. When any link in this chain fails, your pod can't start or your data is at risk.

📌 ST1–ST3: PVC Binding Failures

ST1
💾 CATEGORY 1: STORAGE — Issue ST1
PVC Stuck in Pending State — No PV Bound

🔍 Symptom: kubectl get pvc shows STATUS: Pending indefinitely. kubectl describe pvc shows "no persistent volumes available for this claim." The anihpj-db PostgreSQL pod can't start because its PVC won't bind.

  kubectl get pvc
  NAME         STATUS    VOLUME   CAPACITY   STORAGECLASS   AGE
  anihpj-pvc   Pending                      fast-ssd       5m

  kubectl describe pvc anihpj-pvc
  Events:
    Warning  VolumeBinding  no persistent volumes available for this claim
    Warning  VolumeBinding  storageclass.storage.k8s.io "fast-ssd" not found
🔴5 Most Likely Causes
  1. StorageClass does not exist: The PVC references a StorageClass that hasn't been created. kubectl get sc — if "fast-ssd" is missing, create it or fix the PVC's storageClassName.
  2. No matching PV available: In static provisioning, no PV matches the PVC's storage size, access mode, or selector. kubectl get pv — check capacity and accessModes.
  3. StorageClass provisioner not installed: The CSI driver (e.g., ebs.csi.aws.com) is not deployed. kubectl get pods -n kube-system | grep csi — provisioner pods must be Running.
  4. Access mode mismatch: PVC requests ReadWriteMany but only ReadWriteOnce PVs exist. Check kubectl get pv -o yaml | grep -A2 accessModes.
  5. StorageClass has volumeBindingMode: WaitForFirstConsumer and no pod uses the PVC yet. The PV is only created when a pod actually references the PVC.
🟡5 Less Likely Causes
  1. CSI driver pod CrashLoopBackOff — provisioner can't create volumes
  2. Cloud provider API rate limiting — too many PVCs created simultaneously
  3. PVC selector labels don't match any PV labels
  4. Node where CSI driver runs has taint without toleration
  5. storageClassName: "" (empty string, not null!) — requests a PV with NO StorageClass, but all PVs have one
🟣5 New Cluster Causes
  1. No default StorageClass set: kubectl get sc — look for "(default)". Without it, PVCs without storageClassName won't bind. Set: kubectl patch sc <name> -p '{"metadata":{"annotations":{"storageclass.kubernetes.io/is-default-class":"true"}}}'
  2. CSI driver not yet installed — common in fresh kubeadm clusters
  3. Cloud credentials not configured for CSI driver to provision volumes
  4. RBAC for CSI driver service account missing
  5. kubelet missing --cloud-provider flag for legacy in-tree provisioners
🔍 What to Look At: kubectl get sc,pv,pvc --all-namespaces — the full storage stack in one view. kubectl describe pvc <name> — the Events section tells you exactly why binding failed.
🔧 How to Solve:

1. kubectl get sc — verify the StorageClass exists
2. kubectl describe sc <name> — check provisioner and parameters
3. For static: kubectl get pv — create a PV matching the PVC's size/accessMode
4. For dynamic: install CSI driver: kubectl apply -f <csi-driver-url>
5. Set default SC: kubectl patch sc <name> -p '{"metadata":{"annotations":{"storageclass...is-default-class":"true"}}}'

💡 Personal Advice: The #1 PVC issue on the CKA exam is a missing or misnamed StorageClass. The exam environment may have a StorageClass named "standard" but your PVC says "fast-ssd". Always run kubectl get sc FIRST before writing any PVC YAML. Also: storageClassName: "" (empty string) is NOT the same as omitting storageClassName — empty string requests a PV with NO StorageClass.

Tenet: When a PVC stays Pending, the #1 cause is a StorageClass name mismatch. The StorageClass must exist with the EXACT name specified. On a StatefulSet, volumeClaimTemplates are IMMUTABLE — you must DELETE the StatefulSet and recreate it with the corrected StorageClass. Never try to patch or edit a running StatefulSet's PVC template. On the CKA exam, "PVC stuck Pending due to StorageClass typo" is one of the most common tasks.

M.1 — etcd Backup & Restore (Full TLS Flags)
1

Backup:

ETCDCTL_API=3 etcdctl --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  snapshot save /opt/etcd-backup.db

Restore:

ETCDCTL_API=3 etcdctl --data-dir=/var/lib/etcd-restore \
  snapshot restore /opt/etcd-backup.db

⚠️ After restore: Update etcd static pod manifest (/etc/kubernetes/manifests/etcd.yaml) to point --data-dir to the new path, then restart kubelet. Also update the --initial-cluster-token to a new value.
