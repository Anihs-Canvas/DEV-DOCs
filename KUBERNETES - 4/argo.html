📜 The Evolution to GitOps

Understanding the journey from manual deployments to automated GitOps

🖥️
Pre-2010
Manual SSH Deploy

SCP files, restart services by hand. "It worked on my machine!" No audit trail, no rollback.

❌ Unreliable
⚙️
2010-2015
CI/CD Scripts

Jenkins, bash scripts, Capistrano. Automated but imperative. Configuration drift rampant.

⚠️ Drift-prone
📦
2015-2018
Containers + CI Push

Docker + CI pushes to K8s. Better packaging. But CI needs cluster credentials — security risk.

🟡 Almost there
⚓
2018-Present
GitOps (ArgoCD)

Git is the single source of truth. ArgoCD pulls from Git. No external cluster credentials.

✅ Production Ready
🚀
2023+
Progressive Delivery

Argo Rollouts + Analysis. Canary, Blue-Green. Metrics-driven automated promotion.

🏭
Factory = CI Pipeline

GitHub Actions / Jenkins builds the container image (builds the "shipping container")

📦
Warehouse = Registry

Docker Hub / GHCR stores built images ready for deployment

📋
Manifest = Git YAML

Kubernetes YAML files in Git declare what, how many, and where

⚓
Captain = ArgoCD

Reads the manifest, ensures the dock matches exactly

🏗️
Dock = K8s Cluster

Where containers are unloaded, run, and managed

🔄
Tugboat = Sync

Brings new containers from warehouse to dock

💡 THE KEY INSIGHT: GitOps = The Captain Doesn't Push

Traditional CI/CD (Push): The factory ships directly to the dock → Factory needs dock keys 🔑 (SECURITY RISK!)

GitOps (Pull): The factory updates the manifest (Git). The captain (ArgoCD) continuously checks the manifest vs dock → Captain is INSIDE the dock (no external credentials exposed!)

🎯 CAPA Exam Strategy EXAM PREP

CAPA Exam Strategy — Your Blueprint for Success

The Certified Argo Project Associate (CAPA) exam is a 90-minute, multiple-choice exam with approximately 60 questions. You need 75% to pass. This section gives you every strategy, tip, and checklist you need to walk in confident and walk out certified.

🎯 Exam Prep ⏱️ 90 min exam 📝 ~60 questions 📊 75% to pass

First 5 Minutes — Your Setup Ritual

When your exam terminal opens, do these things BEFORE touching any questions. This ritual saves 15-20 minutes across the exam.

# 1. VERIFY YOUR ENVIRONMENT
kubectl version --short
argocd version --short

# 2. CHECK CURRENT CONTEXT
kubectl config current-context

# 3. LIST ALL AVAILABLE CLUSTERS (for context switching questions)
kubectl config get-contexts

# 4. VERIFY ARGOCD IS ACCESSIBLE
argocd login --grpc-web <ARGO_SERVER> --insecure
argocd app list

# 5. SET BOOKMARKS
# Open: kubernetes.io/docs, argocd.io/docs, falco.org/docs
💡 PRO TIP: Read ALL questions first

Skim every question before answering any. Mark the easy ones. You'll find that later questions sometimes give you hints for earlier ones.

1.2 GitOps Defined — The 4 Principles

📖 Official Definition

GitOps is a set of practices that use Git pull requests to manage infrastructure and application configurations. Git is the single source of truth, and automated processes ensure the actual state matches the desired state.

📋
1. Declarative Configuration

Everything is expressed as YAML/JSON in Git. The entire system is described, not scripted. You declare WHAT you want (3 replicas, image v1.2, port 8080), not HOW to get there.

📦
2. Versioned & Immutable

Git stores the full history of every change. Who changed what, when, and why. Every commit is a potential rollback point. The desired state is immutable — changes create new commits, never mutate existing ones.

🔄
3. Pulled Automatically

An agent (ArgoCD) runs INSIDE the cluster and continuously pulls the desired state from Git. No external system needs cluster credentials. The pull model is inherently more secure.

🛡️
4. Continuously Reconciled

The agent continuously monitors both Git and the cluster. Any difference (drift) is detected and can be auto-corrected. This is self-healing at the deployment level — if someone manually deletes a pod, ArgoCD recreates it.

Show Answer

Explanation

3.5 Immutable Infrastructure Meets GitOps

Immutable infrastructure means you never modify running resources — you replace them with new ones. GitOps naturally supports this:

📦
Immutable Images

Docker images are built once, tagged, and never changed. anihpj:v1.2 always means the exact same code. If you need to change something, you build v1.3.

🔄
Replace, Don't Modify

When you update from v1.2 to v1.3, ArgoCD doesn't modify running pods. It creates new pods with v1.3, waits for them to be Ready, then terminates v1.2 pods. Rolling update = safe replacement.

📋
Git = The Recipe

Just like a recipe doesn't change after cooking, your Git config is immutable. Changes create new commits — you never edit existing commits. ArgoCD always deploys from the current HEAD of the branch.

🎯
Reproducible Deployments

Given the same Git commit, ArgoCD will always produce the same Kubernetes state. This makes debugging, auditing, and compliance far easier than traditional deployment methods.

⚠️ CAPA Gotcha: Architecture Traps

  • Application Controller uses leader election — Only ONE instance is active. The API Server and Repo Server are stateless and can scale. Don't confuse which components can scale horizontally.
  • ArgoCD is NOT a CI tool — It doesn't build images or run tests. It deploys existing images based on Git config. CI builds; CD (ArgoCD) deploys.
  • The Repo Server doesn't store credentials — Credentials are stored as Kubernetes Secrets. The Repo Server reads them when cloning.
  • CRDs are in argoproj.io/v1alpha1 — Not argocd.io. This is a common CAPA trick answer. The API group is argoproj.io.

Chapter 4 CAPA Quick Wins: Memorize: API Server = gateway (REST+gRPC), Repo Server = Git clone + manifest render, App Controller = reconciliation brain (leader election), Redis = cache. The CRDs are Application, ApplicationSet, and AppProject — all in argoproj.io/v1alpha1.

Polling (default 3 min): Simple, no extra config, works everywhere. Webhook: Instant detection, requires ArgoCD to be reachable from the internet (or Git provider). Use webhooks for production; polling is fine for learning and small deployments.

8.2 Creating the ArgoCD Application (CLI Method)

# Create the anihpj Application with auto-sync
argocd app create anihpj-jobs \
  --repo https://github.com/Anihs-Canvas/anihpj-gitops.git \
  --path apps/anihpj/overlays/dev \
  --dest-server https://kubernetes.default.svc \
  --dest-namespace anihpj-dev \
  --sync-policy automated \
  --auto-prune \
  --self-heal \
  --sync-option CreateNamespace=true

# FLAG EXPLANATIONS:
# --repo:           Git repository containing K8s manifests
# --path:           Directory within the repo (Kustomize overlay)
# --dest-server:    Target K8s cluster (in-cluster)
# --dest-namespace: Namespace to deploy into
# --sync-policy:    automated = auto-sync on changes
# --auto-prune:     Delete resources removed from Git
# --self-heal:      Auto-correct manual drift
# --sync-option:    CreateNamespace=true = auto-create ns

# VERIFY
argocd app get anihpj-jobs

8.3 Creating the ArgoCD Application (Declarative YAML)

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: anihpj-jobs
  namespace: argocd
  finalizers:
    - resources-finalizer.argocd.argoproj.io  # Clean up on delete
spec:
  project: default
  source:
    repoURL: https://github.com/Anihs-Canvas/anihpj-gitops.git
    targetRevision: main
    path: apps/anihpj/overlays/dev
  destination:
    server: https://kubernetes.default.svc
    namespace: anihpj-dev
  syncPolicy:
    automated:
      prune: true      # Delete removed resources
      selfHeal: true   # Auto-correct drift
    syncOptions:
      - CreateNamespace=true

CAPA questions frequently test the difference between prune (delete resources not in Git) and self-heal (auto-correct drift). Remember: prune = garbage collection of removed resources. self-heal = auto-correction of modified resources. They solve different problems!

9.1 Understanding Sync — The Heart of ArgoCD

What "Sync" actually means: making Kubernetes match Git. ArgoCD uses a 3-way diff comparing Desired (Git), Live (K8s), and Last Applied (cached) states. Under the hood, ArgoCD computes a hash of the rendered manifests and compares it to the last synced hash — if they differ, the app is OutOfSync.

ARGOCD SYNC — FULL SEQUENCE (T=0 to T=4)
⏱️ T=0: ArgoCD polls Git (every 3 min or webhook trigger)
  GIT REPO ──Desired State──▶ REPO SERVER (renders YAML)

⏱️ T=1: 3-Way Diff Computed
  ┌──────────────┐  ┌──────────────┐  ┌──────────┐
  │ DESIRED (Git)│  │ LIVE (K8s)   │  │ LAST     │
  │ replicas: 3  │  │ replicas: 2  │  │ APPLIED  │
  │ image: v1.2  │  │ image: v1.1  │  │replicas:2│
  └──────────────┘  └──────────────┘  └──────────┘
  CHANGES: replicas 2→3, image v1.1→v1.2

⏱️ T=2: STATUS: 🔴 OutOfSync → Manual sync or Auto-sync triggered

⏱️ T=3: Sync Execution
  PreSync Hook → SYNC (Apply changes) → PostSync Hook
  If FAIL → SyncFail Hook

⏱️ T=4: STATUS: 🟢 Synced + 🟢 Healthy
🟢 Synced

K8s matches Git exactly. No drift detected.

🔴 OutOfSync

K8s differs from Git. Sync needed.

🔵 Unknown

Can't determine state (repo unreachable?).

🟢 Healthy

All resources running correctly.

🟡 Progressing

Resources being created/updated.

🔴 Degraded

Something wrong (pods crashing).

📊 Sync Status Quick Reference

🟢 Synced: K8s = Git. No drift. 🔴 OutOfSync: K8s ≠ Git. Needs sync. 🔵 Unknown: Can't determine — repo unreachable or app newly created. Sync status and health status are independent!

🔬 How ArgoCD Detects Drift

ArgoCD doesn't compare YAML line-by-line. It renders the manifests from Git, computes a SHA256 hash, and compares it to the hash from the last successful sync. If the hashes differ → OutOfSync. This is why even a tiny change (e.g., 1 CPU millicore) triggers sync detection — the hash changes.

9.3 Automated Sync — ArgoCD Syncs for You

syncPolicy:
  automated:
    prune: true      # Delete resources removed from Git
    selfHeal: true   # Auto-correct manual changes (drift)
  syncOptions:
    - CreateNamespace=true
    - PruneLast=true
⚠️ Prune Danger

Auto-prune WILL delete StatefulSet PVCs if removed from Git. Use PrunePropagationPolicy or exclude PVCs from pruning.

✅ Self-Heal Safety

Self-heal only corrects drift on existing resources. It doesn't delete anything — it only reverts changes. Safe to enable in production.

⚠️ CAPA Gotcha: Sync Traps

  • Prune ≠ Self-Heal — Prune DELETES resources not in Git. Self-Heal CORRECTS modified resources. They are completely different operations.

📝 Chapter 9 — CAPA Practice Questions

Q1
What is the difference between Prune and Self-Heal in ArgoCD sync?
Show Answer
Answer

Prune DELETES resources that exist in K8s but are no longer in Git. Self-Heal CORRECTS modified resources back to their Git-defined state. They are independent and solve different problems.

Explanation
Prune = garbage collection. Self-heal = drift correction. You can have prune without self-heal (delete removed resources but don't auto-correct drift), or self-heal without prune (auto-correct but keep orphaned resources).
Q2
What does the --prune flag do in argocd app sync?
Show Answer
Answer

It deletes Kubernetes resources that are present in the cluster but no longer defined in the Git repository. Without it, removed resources remain in K8s.

Explanation
Pruning is disabled by default for safety. If you remove a Deployment from Git and sync without prune, it stays running. Prune makes Git truly the single source of truth by removing anything not declared there.
Q3
What is a sync wave and how do you set it?
Show Answer
Answer

A sync wave controls the order in which resources are created during a sync. Set via the annotation argocd.argoproj.io/sync-wave: "N" where lower numbers are created first.

Explanation
Waves are essential when resources have dependencies. For example, a ConfigMap (wave 1) should exist before the Deployment that uses it (wave 2), and a DB migration Job (wave 1) should complete before the app starts (wave 3).
Q4
What are the four types of sync hooks?
Show Answer
Answer

PreSync (before sync), Sync (replace normal sync), PostSync (after successful sync), and SyncFail (after failed sync).

Explanation
Hooks are Jobs or Pods annotated with argocd.argoproj.io/hook: PreSync|Sync|PostSync|SyncFail. They run as part of the sync process and can block sync progression until they complete successfully.
Q5
What is a 3-way diff in ArgoCD?
Show Answer
Answer

ArgoCD compares Desired state (Git) vs Live state (K8s) vs Last Applied state (cached). This allows it to detect both what needs to change and what was manually modified.

Explanation
A simple 2-way diff (Git vs Live) can't distinguish between "I changed this in Git" and "someone manually changed this in K8s." The 3-way diff uses the Last Applied state as a reference point to identify the source of changes.
Q6
Why should you be careful with auto-prune on StatefulSets?
Show Answer
Answer

Deleting a StatefulSet does NOT delete its PVCs by default. But if pruning is configured to cascade, auto-prune could delete PVCs — resulting in permanent data loss.

Explanation
StatefulSet PVCs are intentionally preserved when the StatefulSet is deleted (they outlive the pods). Pruning with cascading delete can destroy your database. Always exclude database PVCs from pruning.
Q7
What happens if a PreSync hook fails?
Show Answer
Answer

The sync is aborted. The Sync and PostSync hooks are NOT executed. If a SyncFail hook is configured, it runs instead. The application remains in its current state.

Explanation
This is a safety mechanism. If a database backup (PreSync) fails, you don't want the deployment to proceed. Hooks are sequential and blocking by default.
Q8
Can you have auto-sync enabled but keep prune disabled?
Show Answer
Answer

Yes. automated: {} enables auto-sync. Adding prune: true is a separate decision. You can auto-sync without pruning — changes in Git are applied, but removed resources stay in K8s.

Explanation
This is a common configuration for production: auto-sync ensures new changes are deployed automatically, but prune remains off so that removed resources aren't accidentally deleted.
Q9
What annotation sets a sync wave on a resource?
Show Answer
Answer

argocd.argoproj.io/sync-wave: "N" where N is an integer. Resources with lower numbers are synced first. Resources without this annotation default to wave 0.

Explanation
All resources without an explicit wave annotation are wave 0. Negative waves (e.g., "-1") are synced before wave 0. Waves don't work across Applications — only within a single Application.
Q10
What is the difference between argocd app sync --force and a normal sync?
Show Answer
Answer

Normal sync applies changes incrementally. --force deletes and recreates resources if there's a conflict (e.g., an immutable field was changed). It's a more aggressive reconciliation.

Explanation
Use --force when normal sync fails due to field immutability (like changing a Deployment's selector). It will delete the old resource and create a new one, causing a brief downtime.

# argocd-cm ConfigMap — custom health check for Django
data:
  resource.customizations: |
    apps/Deployment:
      health.lua: |
        hs = {}
        hs.status = "Progressing"
        hs.message = ""
        if obj.status ~= nil then

            end
          end
        end

10.4 Application Health vs Resource Health

An ArgoCD Application is only as healthy as its least healthy resource. If you have 10 resources and 1 is Degraded, the entire Application shows Degraded. This propagates upward through the resource tree — check individual resources to find the root cause.

💡 Key Insight

Synced ≠ Healthy. An app can be perfectly Synced (K8s matches Git) but Degraded (pods are crash-looping because of a code bug). Always check both statuses independently.

⚠️ CAPA Gotcha: Health Traps

  • Health and Sync are INDEPENDENT — Don't confuse them. An app can be Synced but Degraded, or Healthy but OutOfSync.
  • One degraded resource degrades the entire app — Check the resource tree to find which specific resource is causing the issue.

List Generator

Cluster Generator

Discovers clusters from ArgoCD's registered cluster list. Use cluster labels to select specific clusters.

generators:
- clusters:
    selector:
      matchLabels:

Git Directory Generator

Scans directories in a Git repository — each directory becomes an Application.

generators:
- git:
    repoURL: https://github.com/org/gitops.git
    directories:
    - path: apps/*

Git File Generator

Reads a JSON/YAML file from Git as the parameter source. Perfect for centralizing app definitions in a single config file — update the JSON, and all Applications update.

generators:
- git:
    repoURL: https://github.com/Anihs-Canvas/anihpj-gitops.git
    revision: main
    files:
    - path: apps/config.json
  # config.json contains:
  # [
  #   {"app": "anihpj", "ns": "anihpj-dev", "env": "dev"},
  #   {"app": "anihpj", "ns": "anihpj-staging", "env": "staging"},
  #   {"app": "redis", "ns": "redis-prod", "env": "prod"}
  # ]

Matrix Generator

Cartesian product of two generators. All apps × all environments = N×M applications. Use when you need every combination of two dimensions.

generators:
- matrix:
    generators:
    - list:                        # Generator A: apps
        elements:
        - app: anihpj
        - app: redis
        - app: postgres
    - list:                        # Generator B: environments
        elements:
        - env: dev
        - env: staging
        - env: prod
# Result: 3 apps × 3 envs = 9 Applications
MATRIX VISUAL: apps × envs = 9 applications

Merge Generator

Combines parameters from multiple generators without multiplying. Unlike Matrix (Cartesian product), Merge produces a union of items, merging overlapping fields.

generators:
- merge:
    generators:
    - clusters: {}           # Generator 1: all clusters
    - list:                  # Generator 2: common config
        elements:
        - team: platform
          costCenter: "12345"
    mergeKeys:
    - name  # Merge by cluster name

Auto-discovers repositories in a GitHub, GitLab, or Bitbucket organization. Every new repo is automatically detected and becomes an Application.

generators:
- scmProvider:

13.5 Kustomize Components and Patches

🔧 Strategic Merge Patch

Default patch type. Merge YAML fields. Delete a field by setting it to null. Most intuitive approach.

🎯 JSON 6902 Patch

RFC 6902 standard. Use add, remove, replace operations with JSON paths. More precise for array operations.

🧩 Components

Reusable patch groups. Apply the same monitoring sidecar, network policy, or security context across ALL apps.

kind: Deployment

      path: /spec/template/spec/containers/-

14.1 Sync Windows — Controlling WHEN Syncing Happens

Sync windows restrict when ArgoCD is allowed to auto-sync. They're defined at the AppProject level (not per-Application) and use CRON expressions for scheduling.

SYNC WINDOWS — ALLOW vs DENY
       MIDNIGHT                 NOON              MIDNIGHT
          │                       │                   │
  ┌───────┼───────────────────────┼───────────────────┼───────┐
  │ DENY  │     ALLOW WINDOW      │    DENY WINDOW    │ DENY  │
  │  🚫   │  ┌─────────────────┐  │  ┌─────────────┐  │  🚫   │
  │       │  │ Auto-sync OK    │  │  │ NO auto-sync│  │       │
  │       │  │ 2AM - 6AM UTC   │  │  │ 8AM - 5PM   │  │       │
  │       │  └─────────────────┘  │  │ (Biz Hours) │  │       │
  │       │                       │  └─────────────┘  │       │
  └───────┴───────────────────────┴───────────────────┴───────┘
          00   02       06   08           17   20     24

  ALLOW window: Sync ONLY during this time (all other times = blocked)
  DENY window:  NEVER sync during this time (all other times = allowed)
  Manual sync:  Can override DENY windows if manualSync: true

# AppProject with sync windows
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: anihpj-prod
spec:
  syncWindows:
  - kind: deny                     # Block sync during business hours
    schedule: "0 8 * * 1-5"        # Mon-Fri, 8 AM UTC
    duration: 9h                   # Lasts 9 hours (until 5 PM)
    applications:                  # Apply to specific apps only
    - anihpj-prod
    manualSync: true               # Allow manual sync during deny window

  - kind: allow                    # Only sync during maintenance window
    schedule: "0 2 * * 0"          # Sunday, 2 AM UTC
    duration: 4h                   # Lasts 4 hours (until 6 AM)
    namespaces:
    - anihpj-prod                   # Apply to all apps in this namespace
⚠️ CRON Times are UTC!

All sync window CRON expressions use UTC time, not your local timezone. A deny window 0 8 * * 1-5 runs Mon-Fri 8 AM UTC — which may be 3 AM EST or 5 PM JST. Always convert!

14.3 Diff Customization — Ignoring Unwanted Differences

Sometimes K8s modifies resources automatically (e.g., HPA sets replicas, mutating webhooks inject sidecars). These changes cause false OutOfSync states. Diff customization tells ArgoCD to ignore specific fields.

# In Application spec — ignore specific fields
spec:
  ignoreDifferences:
  - group: apps
    kind: Deployment
    jsonPointers:                    # Ignore these JSON paths
    - /spec/replicas                 # HPA manages replicas
    - /spec/template/metadata/annotations/kubectl.kubernetes.io~1restartedAt

# In argocd-cm ConfigMap — system-wide customizations
data:
  resource.customizations: |
    apps/Deployment:
      ignoreDifferences: |
        jsonPointers:
        - /spec/replicas

# Ignore entire resource types (system-level in argocd-cm)
  resource.compareoptions: |
    ignoreResourceStatusField: all   # Ignore ALL status fields
💡 Common Uses for Diff Customization

HPA: Ignore /spec/replicas — HPA scales independently. Sidecar injection: Ignore injected container fields. Managed fields: Ignore metadata.managedFields. Status: Ignore status sub-resources entirely.

🏢 Real-World: Why Diff Customization Matters

"anihpj runs an HPA that auto-scales from 3 to 10 pods during peak hours. Without ignoreDifferences on /spec/replicas, ArgoCD sees 10 pods in K8s vs 3 in Git → constantly OutOfSync! Adding the ignore rule lets the HPA scale freely while ArgoCD still catches real config drift (wrong image, missing env vars)."

14.4 Progressive Syncs with ApplicationSet

When deploying across multiple clusters or environments, you want to roll out changes gradually — not all at once. Progressive syncs let you sync one Application at a time, waiting for each to be healthy before proceeding.

# ApplicationSet with progressive syncs (RollingSync)
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: anihpj-progressive
spec:
  strategy:
    type: RollingSync                # Progressive rollout
    rollingSync:
      steps:
      - matchExpressions:           # Step 1: Dev first
        - key: env
          operator: In
          values:
          - dev
        maxUpdate: 1                 # 1 app at a time
      - matchExpressions:           # Step 2: Then staging
        - key: env
          operator: In
          values:
          - staging
        maxUpdate: 1
      - matchExpressions:           # Step 3: Finally prod
        - key: env
          operator: In
          values:
          - prod
        maxUpdate: 1
  generators:
  - list:
      elements:
      - env: dev
      - env: staging
      - env: prod
PROGRESSIVE SYNC ROLLOUT
  Step 1: ┌──────┐  Sync dev → Wait healthy → ✅
          │ DEV  │
          └──────┘
                    ↓
  Step 2:          ┌──────────┐  Sync staging → Wait healthy → ✅
                    │ STAGING  │
                    └──────────┘
                                  ↓
  Step 3:                        ┌──────┐  Sync prod → Wait healthy → ✅
                                  │ PROD │
                                  └──────┘
  If any step fails → rollout STOPS. Subsequent envs stay unchanged.

⚠️ CAPA Gotcha: Sync Windows & Diff Traps

  • Sync windows use UTC only — A window at "0 8 * * *" runs at 8 AM UTC, not your local 8 AM. This causes unexpected "why isn't my sync running?" moments.
  • Deny windows are NOT default-deny — If you don't configure any sync windows, all times are allowed. Adding a deny window blocks ONLY that window.
  • ignoreDifferences uses JSON pointers — Not YAML paths! ~1 replaces / in the path (e.g., ~1restartedAt = /restartedAt).

✅ Built-in: role:admin

Read-only access to everything. Can view apps, repos, clusters. Cannot sync, delete, or modify. Hardcoded — no policy needed.

🔗 The g-Policy (Group Mapping)

The g, <group-claim>, <role> policy maps OIDC groups to ArgoCD roles. This is separate from p policies (which define what roles can do). Think: g = "who are you?", p = "what can you do?"

17.2 Sealed Secrets (Bitnami)

Sealed Secrets uses asymmetric encryption: you encrypt with a public key (via kubeseal), commit the encrypted blob to Git, and the in-cluster controller decrypts it with the private key.

# 1. Install the Sealed Secrets controller
kubectl apply -f https://github.com/bitnami-labs/sealed-secrets/releases/latest/download/controller.yaml

# 2. Create a regular Kubernetes Secret (NEVER commit this)
kubectl create secret generic db-credentials \
  --from-literal=username=anihpj_user \
  --from-literal=password=s3cr3t_p@ss \
  --dry-run=client -o yaml > secret.yaml

# 3. Seal it (encrypt with cluster's public key)
kubeseal --format yaml < secret.yaml > sealed-secret.yaml

# Tip: Fetch the controller's certificate for offline sealing
kubeseal --fetch-cert --controller-name=sealed-secrets > pubkey.pem
# Then seal without cluster access: kubeseal --cert pubkey.pem ...

# 4. Delete the plaintext secret.yaml, commit sealed-secret.yaml to Git
rm secret.yaml
git add sealed-secret.yaml && git commit -m "Add sealed DB credentials"

# 5. ArgoCD deploys SealedSecret CRD → Controller decrypts → K8s Secret created
# sealed-secret.yaml (SAFE to commit to Git)
apiVersion: bitnami.com/v1alpha1
kind: SealedSecret
metadata:
  name: db-credentials
  namespace: anihpj-prod
spec:
  encryptedData:
    username: AgBy8kF3t9X...encrypted_base64...
    password: AgCk7mN2pQ4...encrypted_base64...

17.3 External Secrets Operator (ESO)

ESO doesn't store secrets in Git at all. Instead, you commit an ExternalSecret CRD that references where to find the secret — and ESO fetches it at runtime.

# Step 1: SecretStore — tells ESO WHERE to fetch secrets from
apiVersion: external-secrets.io/v1beta1
kind: SecretStore
metadata:
  name: aws-secrets-manager
spec:
  provider:
    aws:
      service: SecretsManager
      region: us-east-1
      auth:
        secretRef:
          accessKeyIDSecretRef:
            name: aws-credentials
            key: access-key
          secretAccessKeySecretRef:
            name: aws-credentials
            key: secret-access-key

--- # Step 2: ExternalSecret — WHAT to fetch
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: anihpj-db-credentials
spec:
  refreshInterval: 1h                    # Auto-rotate hourly
  secretStoreRef:
    name: aws-secrets-manager
    kind: SecretStore
  target:
    name: db-credentials                 # K8s Secret name to create
  data:
  - secretKey: username
    remoteRef:
      key: prod/anihpj/db                # AWS Secrets Manager path
      property: username
  - secretKey: password
    remoteRef:
      key: prod/anihpj/db
      property: password

17.4 SOPS + Age/Cloud KMS

SOPS (Secrets OPerationS) encrypts only the values in YAML/JSON files — keys remain readable. This makes Git diffs still meaningful while keeping secrets safe.

# Before SOPS encryption (NEVER commit):
db_username: anihpj_user
db_password: s3cr3t_p@ss

# After SOPS encryption (SAFE to commit):
db_username: ENC[AES256_GCM,data:abc123...,iv:def456...,tag:ghi789...,type:str]
db_password: ENC[AES256_GCM,data:xyz789...,iv:uvw012...,tag:rst345...,type:str]
sops:
  age:
  - recipient: age1abc...               # Age public key
  kms:
  - arn: arn:aws:kms:us-east-1:123...   # AWS KMS key ARN
# Encrypt with Age key
sops --encrypt --age age1abc... secrets.yaml > secrets.enc.yaml

# Decrypt for viewing
sops --decrypt secrets.enc.yaml

# ArgoCD integration: Use a CMP (Config Management Plugin)
# to sops-decrypt before kustomize build / helm template
💡 SOPS vs Sealed Secrets: When to Use Which

SOPS = better for multi-cluster (same encrypted file can be decrypted by different keys). Sealed Secrets = simpler setup, cluster-specific encryption. ESO = enterprise with existing secrets infrastructure (Vault, AWS Secrets Manager).

⚠️ CAPA Gotcha: Secrets Traps

  • SealedSecret is cluster-specific — The encryption is tied to the controller's private key. A SealedSecret from cluster A can't be decrypted on cluster B unless you share the private key.
  • ESO creates K8s Secrets, not ArgoCD secrets — The resulting K8s Secret is NOT managed by ArgoCD at all. You won't see it in the ArgoCD UI.
  • SOPS needs a CMP plugin for ArgoCD — Unlike Sealed Secrets and ESO, SOPS doesn't have a native controller. You need to configure a Config Management Plugin to decrypt before apply.

20.4b Parameters

# Input parameters — passed at workflow submission
spec:
  arguments:
    parameters:
    - name: image-tag
      value: "v1.2.3"

# Output parameters — produced by a step
- name: build-image
  container:
    image: docker
  outputs:
    parameters:
    - name: image-digest
      valueFrom:
        path: /tmp/digest.txt

# Passing between steps
- name: deploy
  arguments:
    parameters:
    - name: digest
      value: "{{steps.build-image.outputs.parameters.image-digest}}"

20.4c Artifacts

# Output artifact — file produced by a step
- name: generate-report
  container:
    image: python
  outputs:
    artifacts:
    - name: test-report
      path: /tmp/report.html
      s3:
        key: reports/{{workflow.name}}/report.html

# Input artifact — file consumed by a step
- name: analyze
  inputs:
    artifacts:
    - name: test-report
      path: /tmp/report.html
      s3:
        key: reports/{{workflow.name}}/report.html

20.4d Exit Handlers

# Exit handler — runs regardless of success or failure
spec:
  templates:
  - name: cleanup      # Always runs at workflow end

      image: alpine
      command: [sh, -c]
      args: ["echo 'Cleaning up regardless of result'"]

20.4e Loops and Conditionals

# withItems — repeat step for each item
- name: run-tests

  - - name: test
      template: unit-test
      withItems:
      - python
      - javascript
      - go

- name: deploy-prod
  when: "{{workflow.status}} == Succeeded"

- name: deploy-envs

  • Blue-Green needs two Services — activeService and previewService. The Rollouts controller switches the selector, not you.
  • Canary traffic splitting requires a Service Mesh or Ingress — The Rollout itself doesn't do traffic splitting. It relies on the service mesh (Istio, Linkerd) or ingress controller.

Chapter 21 CAPA Quick Wins: Rollout CRD replaces Deployment for advanced strategies. Blue-Green = active/preview + promote(). Canary = setWeight steps + analysis. AnalysisTemplate = metric-driven auto-rollback. Rollouts + ArgoCD = GitOps progressive delivery.

23.3 Scaling ArgoCD for Enterprise

📈 API Server

Horizontally scalable. Run multiple replicas behind a load balancer. Stateless — no leader election needed.

📦 Repo Server

Horizontally scalable. Each replica handles repo cloning independently. Consider sharding by repo type (git, helm, OCI).

🔄 App Controller

Single active (leader election). Only one controller reconciles apps at a time. Others are hot standby. Shard by cluster for scale.

🗄️ Redis

Single instance or HA with Sentinel. Stores app cache and sync state. If Redis goes down, ArgoCD continues but performance degrades.

25.2 Multi-Tenancy Patterns

🏠 Namespace per Team

Each team gets their own namespace. Simple RBAC via K8s. ArgoCD deploys to respective namespaces. Best for: Small orgs, clear team boundaries.

📁 AppProject per Team

Each team has an AppProject with RBAC, resource allow-lists, and sync windows. Teams can only see and manage their own apps. Best for: Enterprise multi-tenancy.

☸️ Shared ArgoCD

One ArgoCD instance serves all teams. Cost-effective. RBAC + AppProjects enforce isolation. Risk: Noisy neighbor, single point of failure.

🔀 Dedicated ArgoCD

Each team/tenant gets their own ArgoCD instance. Maximum isolation. Risk: Higher operational overhead, harder to maintain consistency across instances.

Q1
What are the three layers of the App of Apps pattern?
Show Answer
Answer

Root (meta-app) → Infrastructure (platform services) → Applications (team workloads). Each layer deploys the next.

Q2
What's the recommended GitOps repo directory structure?
Show Answer
Answer

apps/<app>/overlays/<env>/ — standard Kustomize layout. Separate config repo from source code repo. One branch (main) with directories for environments.

Q3
How do you rollback a bad deployment in ArgoCD?
Show Answer
Answer

argocd app rollback <app> <history-id> then argocd app sync <app> --force. This reverts to a previous known-good state.

Q4
What should you do if ArgoCD itself is down and you need to deploy urgently?
Show Answer
Answer

Manually kubectl apply the manifests, document the change in Git, and when ArgoCD recovers, ensure Git matches cluster state so it doesn't revert your emergency fix.
