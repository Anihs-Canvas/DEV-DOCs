F.5 The Sidecar Pattern vs Ambient Mesh — Understanding Both Approaches
    • Sidecar: one Envoy per pod (istio-proxy container) — mature, battle-tested
    • Ambient Mesh: no sidecar! — ztunnel (L4) + waypoint proxy (L7) per node
    • Trade-offs: sidecar (resource overhead, pod coupling) vs ambient (newer, fewer features)
    • When to use which: production today = sidecar; future = ambient for new deployments
    • How anihpj/jobpost runs with sidecar vs ambient — resource comparison
    • ztunnel: Rust-based, lightweight, handles mTLS + L4 authZ (no L7)
    • waypoint: per-namespace/per-SA L7 policy enforcement (replaces sidecar for L7)
    🟢 Novice | 🟡 Intermediate

CATEGORY 2: TRAFFIC MANAGEMENT (25% = 50 Questions) — Q31-Q80
───────────────────────────────────────────────────────────────────────
"This is the heart of Istio — controlling HOW traffic flows through your
mesh. It's like being a city traffic engineer: you set speed limits
(timeouts), redirect traffic (routes), close broken roads (circuit
breaking), and test new roads with a few cars (canary deployments)."

Key Concepts:
  • VirtualService: match by URI, headers, method, query params; route to destinations
  • DestinationRule: subsets (v1, v2), load balancing (ROUND_ROBIN, LEAST_REQUEST, RANDOM)
  • Gateway: ingress (external→mesh) and egress (mesh→external)
  • ServiceEntry: register external services (AWS RDS, Stripe API, S3)
  • Traffic splitting: canary (90% v1 / 10% v2), A/B testing (header-based), blue/green
  • Fault injection: delays and aborts for resilience testing (chaos engineering)
  • Circuit breaking: outlier detection, connection pool limits, max retries
  • Timeouts, retries, and retry budgets

Official Istio sub-topics:
  • Configure request routing with VirtualService (path, header, weight-based)
  • Configure destination rules with subsets (v1, v2, v3) and load balancing policies
  • Set up ingress and egress gateways for controlled mesh entry/exit
  • Perform traffic splitting — canary deployments, A/B testing, blue/green
  • Implement fault injection — delays and HTTP aborts for testing
  • Configure circuit breakers — outlier detection, connection pool management
  • Set up timeouts, retries with retry budgets, and connection timeouts
  • Use ServiceEntry to register external services inside the mesh

         Symptom: istio-init container crashes repeatedly
         Root Cause: iptables rules conflict with existing network configuration
    MA3: Injection Webhook Not Called — Pod Created Without Modification
         Symptom: kubectl label ns istio-injection=enabled but new pods have no sidecar
         Root Cause: istio-sidecar-injector MutatingWebhook misconfigured or istiod not running

MA4-MA6: Control Plane Issues
    MA4: istiod CrashLoopBackOff — Control Plane Down
         Symptom: All mesh features stop working, istiod pod keeps restarting
         Root Cause: istiod cannot reach API server, misconfigured certificate, or resource starvation
    MA5: Envoy Sync Stale — Proxy Not Receiving Updates
         Symptom: istioctl proxy-status shows STALE for all proxies
         Root Cause: Network partition between istiod and Envoy sidecars
    MA6: Envoy Hot Restart Failure — Config Not Reloading
         Symptom: Changes to VirtualService not reflected in traffic behavior
         Root Cause: Envoy stuck with old config, drain not completing

MA7-MA9: Envoy Proxy Issues
    MA7: Envoy Memory Leak — Sidecar Consuming Excessive RAM
         Symptom: istio-proxy container memory grows unbounded, pod eventually OOMKilled
         Root Cause: Too many clusters/routes (scope with Sidecar resource), or WASM plugin leak
    MA8: Envoy High CPU — Proxy Consuming All CPU
         Symptom: istio-proxy using 100% of allocated CPU
         Root Cause: High traffic volume, complex regex matching, or WASM filter overhead

DECISION TREES (15) — Systematic Istio Troubleshooting
═══════════════════════════════════════════════════════════════════════

DT1:  Pod Not Injected — No istio-proxy Sidecar
      Start: kubectl get pods → only 1/1 containers (should be 2/2)
      → Check namespace label (istio-injection=enabled)?
      → Check injection webhook running?
      → Check pod annotation (sidecar.istio.io/inject: "true")?
      → Check istiod health?

DT2:  VirtualService Not Routing — 503 "No Healthy Upstream"
      Start: curl returns 503 → Check VirtualService host matches Service name?
      → Check DestinationRule subsets match pod labels?
      → Check port number in VirtualService matches Service port?
      → Check Envoy config_dump for route configuration?

DT3:  mTLS Handshake Failure — Connection Refused
      Start: Traffic blocked with TLS error → Check PeerAuthentication mode?
      → Check both sides have istio-proxy injected?
      → Check certificates (istioctl proxy-config secret)?
      → Check CA cert not expired?

DT4:  Sidecar Config Stale — Sync Not Updating
      Start: istioctl proxy-status shows STALE → Check istiod running?
      → Check network between istiod and Envoy (port 15012)?
      → Check istiod logs for xDS push errors?
      → Restart istiod?

DT5:  Kiali Shows "Unknown" Services
      Start: Services in Kiali graph are gray → Check Prometheus scraping?
      → Check Service exists in Kubernetes?
      → Check namespace selected in Kiali?
      → Check Kiali connected to correct Prometheus?

DT6:  JWT Authentication Failing — All Requests 401
      Start: JWT token rejected → Check iss claim matches RequestAuthentication?
      → Check JWKS URI reachable from istiod?
      → Check token not expired?
      → Check audience matches?

DT7:  Egress Traffic Blocked — Cannot Reach External Services
      Start: curl to external URL fails → Check ServiceEntry exists?
      → Check Egress Gateway configured correctly?
      → Check AuthorizationPolicy allows egress?
      → Check DNS resolution (ServiceEntry DNS type)?

DT8:  AuthorizationPolicy Not Enforcing — Traffic Not Blocked
      Start: ALLOW policy created but unauthorized traffic passes → Check policy scope (namespace/workload)?
      → Check principal SPIFFE ID format correct?
      → Check no overlapping DENY policy?
      → Check policy created in correct namespace?

DT9:  Canary Traffic Split Not Working
      Start: Weight-based split but traffic not distributed → Check DestinationRule subsets?
      → Check VirtualService weight totals 100?
      → Check subset labels match pods?
      → Check no other VirtualService for same host?

DT10: Gateway Not Receiving External Traffic
      Start: curl to external IP fails → Check Gateway selector matches ingressgateway pod?
      → Check Gateway server port matches Service targetPort?
      → Check istio-ingressgateway Service type (LoadBalancer vs ClusterIP)?
      → Check firewall rules allowing port?

DT11: Envoy Memory/CPU Pressure — Sidecar Resource Exhaustion
      Start: istio-proxy OOMKilled or CPU throttled → Check Sidecar resource for scoping?
      → Check many VirtualServices/DestinationRules?
      → Check WASM plugins enabled?
      → Tune ProxyConfig for resource limits?

DT12: Istio Upgrade Failed — Mesh in Broken State
      Start: After upgrade, mesh features broken → Check CRDs match control plane version?
      → Check all istiod pods Running new version?
      → Check Envoy proxies restarted with new version?
      → Rollback to previous revision?

DT13: Circuit Breaker Ejected All Endpoints — Complete Outage
      Start: All pods ejected, service down → Check outlier detection thresholds?
      → Check maxEjectionPercent (default 10%, is it set to 100%?)?
      → Check all pods really unhealthy or false positives?
      → Increase baseEjectionTime, lower consecutive errors threshold?

DT14: DNS Resolution Failure for ServiceEntry
      Start: External service unreachable → Check ServiceEntry resolution type (DNS vs STATIC)?
      → Check hosts field correct (FQDN)?
      → Check DNS in mesh (CoreDNS for cluster, ServiceEntry for external)?
      → Check egress ALLOW AuthorizationPolicy?

DT15: Complete Mesh Degradation — Multiple Symptoms
      Start: Multiple issues simultaneously → Check istiod health first!
      → Check cert expiry (istioctl proxy-config secret)?
      → Check resource pressure (nodes, pods)?
      → Check recent config changes (git log / kubectl events)?
      → istioctl bug-report → collect all diagnostics

═══════════════════════════════════════════════════════════════════════

┌──────────────────────────────────────────────────────────────────────┐
│ TRAFFIC ROUTING CHAIN (How Resources Connect)                        │
│                                                                      │
│  Gateway ──► VirtualService ──► DestinationRule ──► Service ──► Pod │
│     │              │                   │              │         │   │
│     │ (L4-L6)      │ (L7 routing)      │ (subsets, LB) │         │   │
│     │              │                   │              │         │   │
│  Example:          │                   │              │         │   │
│  Gateway:443       │                   │              │         │   │
│    └─ TLS: job.com │                   │              │         │   │
│                     └─ Match: /api/* → │              │         │   │
│                                        └─ Subset: v1 ─┤         │   │
│                                          LB: ROUND_ROBIN          │   │
│                                                        │         │   │
│                                                    anihpj-api    │   │
│                                                    ClusterIP     │   │
│                                                                  │   │
│                                                          ┌───────┘   │
│                                                          │           │
│                                                       Pods:        │
│                                                       v1 (app=v1)  │
│                                                       v2 (app=v2)  │
│  KEY INSIGHT: Gateway handles L4-L6 (TLS, port, SNI).             │
│  VirtualService handles L7 routing (path, header, weight).        │
│  DestinationRule handles destination behavior (LB, circuit breaker)│
│  Service is the Kubernetes abstraction for pod discovery.         │
│  Pods are the actual endpoints (IP addresses).                    │
└──────────────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────────────┐
│ SECURITY CHAIN (Identity → AuthN → AuthZ)                            │
│                                                                      │
│  SPIFFE ──► PeerAuthentication ──► RequestAuthentication ──► AuthZ  │
│    │               │                        │                   │   │
│    │ (identity)    │ (transport auth: mTLS) │ (request auth: JWT)│   │
│    │               │                        │                   │   │
│  Istio CA         PERMISSIVE/STRICT        JWT validation        │   │
│  (istiod)         │                        │                   │   │
│    │               │                        │                   │   │
│    ▼               ▼                        ▼                   ▼   │
│  spiffe://cluster.local/ns/anihpj/sa/anihpj-api                   │   │
│                                                                     │   │
│  AuthorizationPolicy:                                               │   │
│  - ALLOW {principals: ["cluster.local/ns/anihpj/sa/anihpj-api"]}  │   │
│          {to: [{operation: {ports: ["5432"]}}]}                    │   │
│                                                                     │   │
│  KEY INSIGHT: SPIFFE is the foundation. mTLS verifies identity.    │
│  RequestAuthentication validates end-user credentials (JWT).       │
│  AuthorizationPolicy uses ALL of these to make allow/deny decisions.│
└──────────────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────────────┐
│ OBSERVABILITY CHAIN (Request → Data → Insight)                       │
│                                                                      │
│  Request ──► Envoy Sidecar                                          │
│                │                                                     │
│                ├──► Metrics (istio_requests_total) → Prometheus     │
│                │       └──► Grafana Dashboard                        │
│                │       └──► Kiali Service Graph                      │
│                │       └──► AlertManager (alerts)                   │
│                │                                                     │
│                ├──► Traces (b3/w3c headers) → Jaeger/Zipkin         │
│                │       └──► Distributed Trace View                  │
│                │       └──► Span details (timing per service)       │
│                │                                                     │
│                └──► Access Logs → stdout                             │
│                        └──► Fluentd/Fluent Bit                      │
│                            └──► Elasticsearch / Loki / Splunk       │
│                                └──► Kibana / Grafana (log queries)  │
│                                                                      │
│  KEY INSIGHT: All three pillars originate from Envoy.               │
│  Zero application code needed. Istio provides complete observability│
│  out of the box for every service in the mesh.                      │
└──────────────────────────────────────────────────────────────────────┘
