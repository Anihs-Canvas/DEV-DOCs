🚨 Critical Do's & Don'ts During The Exam
  • ✅ DO: Use kubectl create ... --dry-run=client -o yaml to generate YAML in seconds — never type manifests from scratch.
  • ✅ DO: Run kubectl config use-context <given-context> as the FIRST command for every task. Wrong context = 0 points.
  • ✅ DO: Use kubectl explain <resource> --recursive when you forget a field name. It's faster than searching docs.
  • ✅ DO: Create a debug pod: kubectl run test --rm -it --image=busybox -- sh to test DNS, connectivity, and curl from inside the cluster.
  • ❌ DON'T: Spend more than 7 minutes on any single task. Flag it, move on, return with fresh eyes.
  • ❌ DON'T: Forget to set the namespace. Many tasks require -n flag. Use kubectl config set-context --current --namespace=<ns> to save typing.
  • ❌ DON'T: Leave any task blank. Even partial work (creating the namespace, writing partial YAML) may earn partial credit.
  • ❌ DON'T: Use kubectl delete pod on a static pod — you must delete the manifest file from /etc/kubernetes/manifests/.

Platform Arch Q1 of 200
What is the PRIMARY purpose of an Internal Developer Platform (IDP) in a cloud native organization?
A) To replace Kubernetes entirely with a simpler abstraction layer for developers
B) To provide a centralized ticketing system where developers request infrastructure from Ops teams
C) To reduce developers' cognitive load by providing self-service APIs, golden path templates, and automated infrastructure — treating the platform as a product
D) To monitor all developer activity and enforce strict compliance rules across the organization
✅ Correct Answer: C

An Internal Developer Platform (IDP) is a product, not a project. Its goal is to reduce the cognitive load on developers by providing self-service capabilities — they can provision databases, namespaces, TLS certificates, and deploy applications without filing tickets or waiting for Ops. The platform abstracts away infrastructure complexity while still giving developers the autonomy they need.

Platform Arch Q2 of 200
Which of the following is NOT a core cloud native design principle?
A) Declarative configuration — define the desired state of your infrastructure and applications, not step-by-step procedures to achieve it
B) Immutable infrastructure — replace servers and containers instead of patching or modifying them in place after deployment
C) Manual approval gates at every deployment stage to ensure maximum quality and prevent any errors from reaching production
D) The 12-Factor App methodology — building applications that are portable, stateless, and designed for cloud-native environments from the start
✅ Correct Answer: C

Manual approval gates are the antithesis of cloud native. Cloud native design principles emphasize automation, speed, and developer autonomy. Manual approvals create bottlenecks — they slow down delivery, increase lead time, and contradict the DevOps principle of "you build it, you run it." Instead, cloud native platforms rely on automated testing, canary deployments, policy-as-code, and progressive delivery to ensure quality WITHOUT manual intervention.

Platform Arch Q3 of 200
In a Docker multi-stage build, what is the PRIMARY benefit of using a separate "builder" stage before the final runtime stage?
A) It allows running multiple containers simultaneously from a single Dockerfile during development
B) It separates build-time dependencies (compilers, dev headers) from the final runtime image — dramatically reducing image size and attack surface
C) It automatically parallelizes the image build process across all available CPU cores for faster builds
D) It enables hot-reloading of application code without rebuilding the container image during local development
✅ Correct Answer: B

Multi-stage builds solve a fundamental container problem: build tools pollute the runtime. Without multi-stage, you'd either ship compilers and dev headers in production (bloated, insecure) or use complex scripts outside Docker. Multi-stage lets you compile/build in one stage, then copy ONLY the final binary/artifact into a clean, minimal runtime image.

📝 Detailed Explanation
Multi-Stage Docker Build — Builder vs Runtime
  ┌─────────────────────────────────────────────────────────────────────┐
  │              MULTI-STAGE DOCKER BUILD FOR anihpj/jobpost             │
  │                                                                     │
  │  STAGE 1: BUILDER (600 MB+)              STAGE 2: RUNTIME (~150 MB) │
  │  ┌──────────────────────────┐           ┌──────────────────────────┐│
  │  │ FROM python:3.12         │           │ FROM python:3.12-slim    ││
  │  │ (includes gcc, headers,  │           │ (minimal, no compilers)  ││
  │  │  pip, dev libs...)       │           │                          ││
  │  │                          │           │ COPY --from=builder      ││
  │  │ COPY requirements.txt .  │           │   /root/.local → /app    ││
  │  │ RUN pip install --user   │ ──COPY──▶ │   (only .whl + bins)    ││
  │  │   -r requirements.txt    │           │                          ││
  │  │                          │           │ COPY . .                 ││
  │  │ ❌ DISCARDED after build │           │ USER anihpj (non-root)   ││
  │  └──────────────────────────┘           │ CMD ["gunicorn", "..."] ││
  │                                         └──────────────────────────┘│
  │                                                                     │
  │  WHAT'S NOT IN RUNTIME:              WHAT IS IN RUNTIME:            │
  │  ❌ gcc, g++, make                   ✅ Python runtime (slim)       │
  │  ❌ -dev headers (libpq-dev, etc.)   ✅ pip packages (compiled)     │
  │  ❌ pip cache, build artifacts       ✅ Application code            │
  │  ❌ git, curl, build tools           ✅ Non-root user (anihpj)      │
  │                                                                     │
  │  RESULT: 4x smaller image, 80% fewer CVEs, faster pull/deploy      │
  └─────────────────────────────────────────────────────────────────────┘

  🐳 ACTUAL DOCKERFILE (anihpj/jobpost):
  ─────────────────────────────────
  FROM python:3.12-slim AS builder
  WORKDIR /app
  COPY requirements.txt .
  RUN pip install --no-cache-dir --user -r requirements.txt

  FROM python:3.12-slim
  RUN useradd --create-home anihpj
  WORKDIR /app
  COPY --from=builder /root/.local /home/anihpj/.local
  COPY . .
  RUN chown -R anihpj:anihpj /app
  USER anihpj
  ENV PATH=/home/anihpj/.local/bin:$PATH
  CMD ["gunicorn", "anihpj.wsgi:application", "--bind", "0.0.0.0:8000", "--workers", "4"]

The anihpj/jobpost Dockerfile uses exactly this pattern: the builder stage compiles Python dependencies (which need gcc, libpq-dev for psycopg2), then the runtime stage copies only the compiled wheels into a slim image running as a non-root user. Result: 150 MB vs 600+ MB, and the attack surface is dramatically smaller.

Why not A? Multi-stage builds produce ONE final image — not multiple containers. Why not C? Docker builds are sequential by default; multi-stage doesn't parallelize automatically. Why not D? Hot-reloading is a Docker Compose volume-mount feature, unrelated to multi-stage builds.

Platform Arch Q4 of 200
In Kubernetes, which control plane component is responsible for continuously watching the cluster state and running loops to move the actual state toward the desired state?
A) kubelet — the node agent that manages container lifecycles and reports node/pod status back to the API server
B) kube-scheduler — the component that watches for unscheduled pods and assigns them to the best-fit worker node
C) kube-controller-manager — it runs multiple controller loops (node, replication, endpoint, serviceaccount) that reconcile actual state with desired state
D) kube-apiserver — the front-end that validates REST requests and persists all cluster state into the etcd key-value store
✅ Correct Answer: C

The kube-controller-manager is the brain of Kubernetes. It runs multiple independent controller loops — each one watches for drift between the desired state (what you declared in YAML) and the actual state (what's running). When a pod dies, the replication controller creates a new one. When a node goes down, the node controller marks it NotReady. This reconciliation loop is the core design pattern of Kubernetes.

🔴5 Most Likely Causes
  1. StorageClass does not exist: The PVC references a StorageClass that hasn't been created. kubectl get sc — if "fast-ssd" is missing, create it or fix the PVC's storageClassName.
  2. No matching PV available: In static provisioning, no PV matches the PVC's storage size, access mode, or selector. kubectl get pv — check capacity and accessModes.

  4. Access mode mismatch: PVC requests ReadWriteMany but only ReadWriteOnce PVs exist. Check kubectl get pv -o yaml | grep -A2 accessModes.
  5. StorageClass has volumeBindingMode: WaitForFirstConsumer and no pod uses the PVC yet. The PV is only created when a pod actually references the PVC.
🟡5 Less Likely Causes
  1. CSI driver pod CrashLoopBackOff — provisioner can't create volumes
  2. Cloud provider API rate limiting — too many PVCs created simultaneously
  3. PVC selector labels don't match any PV labels
  4. Node where CSI driver runs has taint without toleration
  5. storageClassName: "" (empty string, not null!) — requests a PV with NO StorageClass, but all PVs have one
🟣5 New Cluster Causes
  1. No default StorageClass set: kubectl get sc — look for "(default)". Without it, PVCs without storageClassName won't bind. Set: kubectl patch sc <name> -p '{"metadata":{"annotations":{"storageclass.kubernetes.io/is-default-class":"true"}}}'
  2. CSI driver not yet installed — common in fresh kubeadm clusters
  3. Cloud credentials not configured for CSI driver to provision volumes
  4. RBAC for CSI driver service account missing
  5. kubelet missing --cloud-provider flag for legacy in-tree provisioners
🔍 What to Look At:
kubectl get sc,pv,pvc --all-namespaces The full storage stack in one view — see StorageClass, PV, and PVC together.
kubectl describe pvc <name> The Events section tells you exactly why binding failed — always read the events first.
🎯 #1 Root Cause: StorageClass does not exist or is misnamed. The PVC references a StorageClass that hasn't been created — the most common platform infrastructure pitfall.
🔧 How to Solve:
1. Verify StorageClass exists kubectl get sc If the StorageClass referenced by the PVC is missing, create it or fix the PVC's storageClassName.
2. Check provisioner and parameters kubectl describe sc <name> Verify the provisioner is correct and the CSI driver is installed and running.
3. Static provisioning kubectl get pv Create a PV matching the PVC's requested size, accessMode, and selector labels.
4. Dynamic provisioning Install the CSI driver: kubectl apply -f <csi-driver-url>. Verify CSI pods are Running in kube-system.
5. Set default StorageClass kubectl patch sc <name> -p '{"metadata":{"annotations":{"storageclass.kubernetes.io/is-default-class":"true"}}}' PVCs without an explicit storageClassName will use the default.
💡 Personal Advice:
Always verify StorageClass FIRST. The #1 PVC issue in platform engineering is a missing or misnamed StorageClass. Run kubectl get sc before writing any PVC YAML.
Empty string is NOT null. storageClassName: "" Requests a PV with NO StorageClass — different from omitting the field entirely. Know this distinction.
