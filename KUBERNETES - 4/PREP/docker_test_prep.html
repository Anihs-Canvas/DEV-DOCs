Orchestration Q1 of 200
What command initializes a Docker Swarm cluster on the current node, making it the first manager?
A) docker swarm create --manager
B) docker cluster init --role manager
C) docker swarm init
D) docker swarm start --advertise-addr eth0
✅ Correct Answer: C

docker swarm init initializes a new Swarm cluster. The node where you run this command becomes the first manager node in the swarm. This is the foundational command — without it, there are no services, no overlay networks, and no orchestration.

📝 Detailed Explanation
Docker Swarm Architecture — Manager & Worker Nodes
  ┌─────────────────────────────────────────────────────────────────┐
  │                     DOCKER SWARM CLUSTER                         │
  │                                                                 │
  │  ┌─────────────────────────┐    ┌─────────────────────────┐    │
  │  │  MANAGER NODE (anih)    │    │  WORKER NODE            │    │
  │  │  ┌───────────────────┐  │    │  ┌───────────────────┐  │    │
  │  │  │ docker swarm init │  │    │  │ docker swarm join │  │    │
  │  │  │ → Raft consensus  │  │    │  │ → Runs tasks only │  │    │
  │  │  │ → Orchestration   │  │    │  │ → No management   │  │    │
  │  │  │ → Service API     │  │    │  └───────────────────┘  │    │
  │  │  └───────────────────┘  │                               │    │
  │  │  Generates join tokens: │    ┌─────────────────────────┐    │
  │  │  $ docker swarm         │    │  WORKER NODE            │    │
  │  │    join-token manager   │    │  (same join mechanism)  │    │
  │  │    join-token worker    │    └─────────────────────────┘    │
  │  └─────────────────────────┘                                   │

After docker swarm init, Docker prints the join command that worker nodes use: docker swarm join --token SWMTKN-1-xxx 192.168.1.10:2377. For the anihpj/jobpost stack, you'd deploy the web, API, database, and Redis as Swarm services across your worker nodes for high availability.

💡 DCA Exam Tip: The DCA exam tests your knowledge of docker swarm init, docker swarm join, docker swarm join-token (rotate), and docker swarm leave. Remember: swarm init creates the cluster; swarm join adds nodes.

Orchestration Q2 of 200
After running docker swarm init on the manager, the output shows a command to add workers. What command does a worker node run to join the swarm?
A) docker swarm join --token SWMTKN-1-xxx <manager-ip>:2377
B) docker node connect --swarm <manager-ip>
C) docker swarm add-worker --manager <manager-ip>:2377
D) docker swarm attach --token SWMTKN-1-xxx
✅ Correct Answer: A

docker swarm join --token <token> <manager-ip>:2377 is the exact command printed by docker swarm init. The token is a SWMTKN (Swarm Token) that authenticates the joining node to the cluster. Port 2377 is the Swarm control plane port.

📝 Detailed Explanation

  │ Swarm initialized...    │              │                         │

  │ docker swarm join \     │──────────────▶│   --token SWMTKN-1-... │
  │   --token SWMTKN-1-...  │   copy+paste  │   192.168.1.10:2377    │
  │   192.168.1.10:2377     │              │                         │

     $ docker swarm join-token worker   → shows worker token

After joining, the worker node appears in docker node ls on the manager. For the anihpj/jobpost stack, you'd add at least 2-3 worker nodes so your web, API, and database services can be distributed across the swarm for high availability and load balancing.

💡 DCA Exam Tip: Remember that docker swarm join requires BOTH the token AND the manager IP:port. The token proves you're authorized; the IP:port tells the node where to find the manager. If port 2377 is blocked by a firewall, the join will fail with "connection refused".

Orchestration Q3 of 200
What is the fundamental difference between a Docker Swarm manager node and a worker node?
A) Managers run containers; workers only store logs and metrics
B) Managers handle cluster orchestration (scheduling, desired state, API); workers only execute tasks (run containers)
C) Workers manage the swarm; managers run user applications
D) There is no difference — all nodes in a swarm are equal
✅ Correct Answer: B

Managers run the control plane: they maintain the desired state, schedule services onto nodes, serve the Swarm API, and use Raft consensus to agree on cluster state. Workers are "dumb executors" — they receive tasks from managers and run containers. Workers do NOT participate in orchestration decisions.

📝 Detailed Explanation
Manager vs Worker — Responsibilities Split
  ┌─────────────────────────────────────────────────────────────────┐
  │                     MANAGER NODE                                 │
  │  ┌───────────────────────────────────────────────────────────┐  │
  │  │  ✅ Cluster orchestration           ✅ Scheduling          │  │
  │  │  ✅ Maintain desired state          ✅ Serve Swarm API     │  │
  │  │  ✅ Raft consensus (leader/follower)✅ docker node ls/promote │
  │  │  ✅ Store cluster config in Raft log                       │  │
  │  │  ❌ Can also RUN containers (by default)                   │  │
  │  │     → docker node update --availability drain <manager>    │  │
  │  │       to prevent managers from running workloads           │  │
  │  └───────────────────────────────────────────────────────────┘  │
  └─────────────────────────────────────────────────────────────────┘

  ┌─────────────────────────────────────────────────────────────────┐
  │                     WORKER NODE                                  │
  │  ┌───────────────────────────────────────────────────────────┐  │
  │  │  ✅ Execute tasks (run containers)                         │  │
  │  │  ✅ Report status back to managers                        │  │
  │  │  ✅ Pull images, start/stop containers                    │  │
  │  │  ❌ CANNOT manage the swarm                               │  │
  │  │  ❌ CANNOT schedule services                              │  │
  │  │  ❌ CANNOT run docker node ls, docker service create       │  │
  │  └───────────────────────────────────────────────────────────┘  │
  └─────────────────────────────────────────────────────────────────┘

  Promote a worker to manager:  docker node promote <worker>
  Demote a manager to worker:   docker node demote <manager>

For the anihpj/jobpost production deployment, you'd typically run 3 managers (for Raft quorum) and 2-5 workers (for workload capacity). Managers can also run containers by default, but in production you should drain managers so they focus only on orchestration.

💡 DCA Exam Tip: The DCA exam will ask you to docker node promote and docker node demote. Remember: worker → manager = promote; manager → worker = demote. Also know that docker node update --availability drain prevents a node from receiving new tasks.

Orchestration Q4 of 200
A production Docker Swarm should have an odd number of manager nodes. What is the maximum number of manager failures a 5-manager swarm can tolerate and still function?
A) 1 manager failure — the remaining 4 vote and the majority wins
B) 5 manager failures — Swarm uses a round-robin failover, not quorum
C) 3 manager failures — any number less than 5 keeps the swarm alive
D) 2 manager failures — Raft requires (N/2)+1 managers for quorum, so 3 out of 5 must be healthy
✅ Correct Answer: D

Docker Swarm uses the Raft consensus algorithm, which requires a majority (quorum) of managers to be healthy: ⌊N/2⌋ + 1. With 5 managers, quorum is 3 — so you can lose 2 managers and the swarm still functions. If you lose a 3rd, the swarm becomes unavailable (no new services, no scheduling).

📝 Detailed Explanation
Raft Quorum — Why Odd Numbers Matter

PVC Stuck in Pending State — No PV Bound

🔍 Symptom: kubectl get pvc shows STATUS: Pending indefinitely. kubectl describe pvc shows "no persistent volumes available for this claim." The anihpj-db PostgreSQL pod can't start because its PVC won't bind.

  kubectl get pvc
  NAME         STATUS    VOLUME   CAPACITY   STORAGECLASS   AGE
  anihpj-pvc   Pending                      fast-ssd       5m

  kubectl describe pvc anihpj-pvc
  Events:
    Warning  VolumeBinding  no persistent volumes available for this claim
    Warning  VolumeBinding  storageclass.storage.k8s.io "fast-ssd" not found
🔴5 Most Likely Causes
  1. StorageClass does not exist: The PVC references a StorageClass that hasn't been created. kubectl get sc — if "fast-ssd" is missing, create it or fix the PVC's storageClassName.
  2. No matching PV available: In static provisioning, no PV matches the PVC's storage size, access mode, or selector. kubectl get pv — check capacity and accessModes.
  3. StorageClass provisioner not installed: The CSI driver (e.g., ebs.csi.aws.com) is not deployed. kubectl get pods -n kube-system | grep csi — provisioner pods must be Running.
  4. Access mode mismatch: PVC requests ReadWriteMany but only ReadWriteOnce PVs exist. Check kubectl get pv -o yaml | grep -A2 accessModes.
  5. StorageClass has volumeBindingMode: WaitForFirstConsumer and no pod uses the PVC yet. The PV is only created when a pod actually references the PVC.
🟡5 Less Likely Causes
  1. CSI driver pod CrashLoopBackOff — provisioner can't create volumes
  2. Cloud provider API rate limiting — too many PVCs created simultaneously
  3. PVC selector labels don't match any PV labels
  4. Node where CSI driver runs has taint without toleration
  5. storageClassName: "" (empty string, not null!) — requests a PV with NO StorageClass, but all PVs have one
🟣5 New Cluster Causes
  1. No default StorageClass set: kubectl get sc — look for "(default)". Without it, PVCs without storageClassName won't bind. Set: kubectl patch sc <name> -p '{"metadata":{"annotations":{"storageclass.kubernetes.io/is-default-class":"true"}}}'
  2. CSI driver not yet installed — common in fresh kubeadm clusters
  3. Cloud credentials not configured for CSI driver to provision volumes
  4. RBAC for CSI driver service account missing
  5. kubelet missing --cloud-provider flag for legacy in-tree provisioners
🔍 What to Look At:
kubectl get sc,pv,pvc --all-namespaces The full storage stack in one view — see StorageClass, PV, and PVC together.
kubectl describe pvc <name> The Events section tells you exactly why binding failed — always read the events first.
🎯 #1 Root Cause: StorageClass does not exist or is misnamed. The PVC references a StorageClass that hasn't been created — the most common CKA exam pitfall.
🔧 How to Solve:
1. Verify StorageClass exists kubectl get sc If the StorageClass referenced by the PVC is missing, create it or fix the PVC's storageClassName.
2. Check provisioner and parameters kubectl describe sc <name> Verify the provisioner is correct and the CSI driver is installed and running.
3. Static provisioning kubectl get pv Create a PV matching the PVC's requested size, accessMode, and selector labels.
4. Dynamic provisioning Install the CSI driver: kubectl apply -f <csi-driver-url>. Verify CSI pods are Running in kube-system.
5. Set default StorageClass kubectl patch sc <name> -p '{"metadata":{"annotations":{"storageclass.kubernetes.io/is-default-class":"true"}}}' PVCs without an explicit storageClassName will use the default.
💡 Personal Advice:
Always verify StorageClass FIRST. The #1 PVC issue on the CKA exam is a missing or misnamed StorageClass. Run kubectl get sc before writing any PVC YAML.
Empty string is NOT null. storageClassName: "" Requests a PV with NO StorageClass — different from omitting the field entirely. Know this distinction.
CSI driver must be Running. Even with correct StorageClass, if the CSI provisioner pod is CrashLoopBackOff, no volumes will be created.
WaitForFirstConsumer delays binding. If volumeBindingMode is WaitForFirstConsumer, the PV is only created when a pod actually uses the PVC. Don't mistake this for a failure.
